1 · 业务背景

把安全治理接回原部署入口，保留运维已经熟悉的操作方式。

毕昇以私有化方式交付企业客户。不同公司的中间件密码与解密密钥应彼此独立，交付源码不能携带通用解密密钥或可直接使用的默认中间件密码。

本次覆盖 MySQL、Redis、MinIO、Elasticsearch、Milvus，复用现有 Fernet 加密、配置模型与部署脚本。用户已明确：安全治理不得增加正常部署命令；必要信息在原安装过程中引导填写。

交付要求当前方案
部署入口不变bash docker/install.sh 或 bash scripts/deploy.sh install；运维继续使用原入口。
密码由客户提供首次隐藏输入并确认本公司的密码；部署密钥自动生成，组件密码不自动随机替代。
后续操作简单再次部署复用现用身份与配置；失败处理后重新执行原命令，无需人工拼接配置包、密钥路径和版本号。
存量数据安全识别已有数据和原容器，维护确认后迁移密文；中间件实际密码与认证状态保持不变。
交付结果可核实标准单机已完成真实组件、新装、改密、回退与原命令续跑；DM 和未配置的完整业务链路仍待验证。
本文 v2.0 已全面替换旧部署主线。下面明确区分“原命令部署”“旧版密文迁移”和“实际账号改密维护”。原来的多命令准备流程不再是正常安装前置条件。操作见 HTML 运维手册 · 正式设计与实现 · 任务进度 · 验证记录。

“改造前”沿用 2026-11-11 的静态核查记录；“本地实现”依据当前工作区源码及2026-11-13隔离环境真实验收。未对客户实际服务器执行部署或改密。

3 · 技术解决方案总览

正常部署只暴露原命令和必要引导，底层安全工具在安装器内部执行。

已对齐结论

议题已确认处理方式
正常入口bash docker/install.sh / bash scripts/deploy.sh install；不新增必做命令。
输入与密钥密码由客户提供；首次隐藏输入并二次确认。密钥由安装器为该部署创建，既有密钥不得被新密钥替换。
参数与生效配置包、密钥路径、文件组权限和 revision（非秘密版本号）自动管理；路径/key/revision 成组写入 .env。

维护边界旧版密钥迁移须确认维护及其他节点停写；真实账号改密、密钥轮换仍是独立维护变更。

3.1 安装器负责什么

阶段内部动作运维需要做什么
准备首次复制 .env，识别历史数据/容器，锁定同一部署目录；拉取并检查工具镜像入口。执行原命令；镜像不兼容时按提示选择配套镜像。
密码输入检测五个基础组件及已配置统计 ES；隐藏输入、二次确认、复用密码校验。首次输入本公司密码；输入错误仅重问当前组件。
文件准备内部 keygen/prepare/check；生成新版本目录，设置权限并保存 prepared 指针。无需手动创建密钥、配置包或版本。
启动标准新装/普通部署：原生组件启动与新连接检查通过后才继续启动应用；旧版 adopt：走受控 DB 迁移分支。按提示等待；最后验证启用的业务。
重复 / 失败复用现用配置和身份，保留断点计划；缺文件时引导匹配备份。修复失败原因，再执行原命令。

3.2 自动化与 prepare-only

无人值守的新装可通过 BISHENG_CREDENTIAL_INPUTS_FILE 指向受限密码文件清单，仍执行原命令；已有配置不会因清单内容变化而静默改密。标准交互部署不需要该文件。

--prepare-only 在首次无配置包时只复制参数并用进程内占位路径校验 Compose 结构，不要求密码、工具镜像或联网，不把占位路径写入 .env；已有完整配置时执行本地离线检查，仍不拉取或启动服务。它不代表真实认证与业务已验证。

3.3 加密格式与覆盖契约（安装器内部管理）

继续使用 Fernet，不改变业务数据库表结构；配置解析后客户端只接收已解密值。各进程启动读取密钥环快照，变更后必须重建或重启全部消费者，不承诺热更新。

输入 / 字段当前处理契约
BS_SECRET_KEYS_FILE进程可见的绝对文件路径；Compose 标准路径为 /run/secrets/bisheng-fernet-keys.json，只读挂载；普通 .env 仅保存宿主机路径引用。
外置密钥环JSON version=1、有序 keys 数组；首项用于加密，全环用于兼容解密。主密钥独立复检不能被旧密钥解密成功替代。
database_urlURL 密码段沿用 Fernet 密文，不额外包 encrypt(...)；通过现有 SQLAlchemy URL 处理，避免特殊字符重复编码。
redis_url / celery_redis_url覆盖 URL、字典中的 URL、password 与 sentinel_password，按各消费者接口解析；外部 Sentinel 支持范围单独验收。
MinIO / ES / Milvus独立密码字段使用 encrypt(...) 标记；覆盖 MinIO secret_key、知识/统计 ES basic_auth 密码、Milvus password/token，冲突身份来源明确失败。
!env 与旧来源共享安全读取并拒绝多源冲突，不 source/eval 客户文件。旧版导入物化实际容器来源，后续不依赖已替换容器中的旧密码环境；不改了 YAML 却继续被旧明文覆盖。
# 格式说明；由工具生成，不需要运维填写这些占位值
BS_SECRET_KEYS_FILE=/run/secrets/bisheng-fernet-keys.json

# MySQL 的 URL 密码段沿用原格式

# 其他独立密码字段的标记形式（示意）
secret_key: "encrypt(<Fernet密文>)"
内部模式作用边界
fresh完整客户密码输入生成全新配置。仅真正新装；原安装器自动调用。
adopt-key导入既有身份，仅迁移密钥/密文。保持真实密码和认证状态，记录 pending；不可接收新密码清单。
password-change从现用配置包生成指定组件的新配置，联动已知消费者。专项维护；不自动修改服务器账号，不改其他组件权限和密码。
key-rotation保留实际密码，仅按新密钥重加密配置。专项维护；数据库存量密文和全部进程仍需配套迁移与验证。
底层工具的定位：docker/credentials.sh 和重加密脚本是安装器内部能力及专项维护入口。其显式路径参数保留兼容，但不再列为正常部署必做操作。

4 · 外置密钥生命周期与旧版迁移

密钥用于加解密密码；更换密钥只改变密文，不能代替修改真实中间件密码。

4.1 新装与重复部署

  1. 原命令识别为全新部署后，引导客户填写并确认密码。
  2. 内部创建独立外置密钥及加密配置；密钥不写源码、普通 .env 或后端镜像。
  3. 只读挂载同一密钥与配置给 API、Worker；标准 Worker 容器内的 Beat/Linsight 一起重建。
  4. 启动前检查密钥和密文；后续部署复用现用文件，不重新生成或覆盖。

4.2 旧版密钥外置：由原入口引导执行

  1. 识别既有数据/原容器；提示维护负责人确认维护窗口、其他节点停写，并明确允许暂停本机标准应用容器。
  2. 读取原后端容器的 config.yaml、环境快照与旧密钥到受限文件；无法自动读取时，引导提供对应备份路径。新发布源码不内置旧密钥，也不从 Git 自动查找旧密钥。
  3. 建立“新主密钥 + 旧解密密钥”的过渡环；以 adopt-key 模式重加密配置，保留真实账号密码、认证状态和待治理清单。
  4. 文件检查及镜像准备通过后，暂停本机标准 frontend、gateway、backend-worker、backend；执行数据库预检、受控密文备份、分批重加密和缓存处理。
  5. 已有计划时通过 resume 续跑，再执行新主密钥独立复检；失败保持应用停止并保留计划。
  6. 复检成功后只重建应用，原生中间件及其原挂载不重建；原 Gateway 容器保留原挂载恢复。随后验证组织同步、沙箱及其他业务。
迁移对象处理边界
静态数据库、Redis、MinIO、ES、Milvus 凭据保持实际密码不变，只更新业务密文及部署读取方式。
org_sync_config.auth_config重加密整段组织同步 JSON 密文，保留租户、时间和业务含义。
config 的 sandbox_endpoint.token_enc只改准确的密文字段，保留 endpoint 和未知 JSON 字段。
config:sandbox_endpoint处理实际 Redis 实例/DB 的指定缓存；不能靠等待 TTL 代替迁移完成检查。
独立加密体系不迁移 app-runtime payload 或 app-publish 的独立密钥数据，不把维护逻辑塞入 Alembic revision。
旧版迁移不等于密码治理完成。旧弱密码或无认证状态会记录为 pending（待治理项），不能标为已修复。当前安装器不会自动删除过渡环中的旧密钥；退役须在全节点、全密文和真实业务验收后另做。多节点停写须由维护负责人执行，脚本只能暂停本机约定名称的容器。

4.3 后续轮换及失败恢复

情形处理
独立密钥轮换专项维护中先确保全部进程具备新密钥解密能力，再切换首密钥、重加密存量值、处理缓存并复检；不同时改真实组件密码。
密钥 / 配置丢失在原入口提供同一部署的匹配备份并通过检查；非交互环境明确停止，不生成替代密钥。
部分迁移失败保留新旧过渡环、备份和计划；保持维护停写，修复后原命令续跑。
回退旧镜像旧镜像不能读取新密钥密文；维护负责人必须核对匹配的配置、密钥与数据库恢复点，不能只换镜像或盲目全库回退。
全部有效密钥与备份丢失现有密文无法用新密钥解开；需要人工重置可重置的账号并重新录入凭据，不能承诺恢复所有历史加密数据。

5 · MySQL：自动新装与真实改密维护

同一批客户输入覆盖 MySQL、毕昇、OpenFGA 及启用的 Gateway 初始化任务。

5.1 新装：原安装器自动完成

  1. 在原安装命令中接收并确认公司 MySQL 密码，复用已有弱值和格式校验。
  2. 生成 mysql.password、mysql-client.cnf 和 openfga.yaml；原生 MySQL 读取 MYSQL_ROOT_PASSWORD_FILE。
  3. 加密同一个密码并写入生成配置的 database_url，保留 host、port、库名及参数；URL 密码段沿用 Fernet 密文格式。
  4. 同步 OpenFGA/openfga-migrate 和启用 Gateway 时的 root 初始化凭据；Gateway 自有业务账号密码保持独立。
  5. 启动数据库及必要初始化任务，用应用网络中的新连接检查凭据后继续启动后端。
真实验收补充：CR MySQL8.0.43的原bootstrap脚本不能安全处理含单引号的密码；本项目以专用wrapper安全序列化SQL/CNF，保留vendor生命周期和mysql用户降权。初始化失败后存在部分数据时会安全停止，不自动清空目录或重置root；需按确认的恢复点处理。相同含单引号密码新装及后续改密、回退均已复检。

5.2 已初始化账号改密：独立维护

  1. 确认维护窗口、有效管理身份和恢复材料；准备新密码及配套配置，暂不启用。
  2. 暂停受影响业务和消费者，通过 MySQL 管理接口修改实际账号密码；只修改初始化文件不会修改已有账号。
  3. 用新建连接确认服务端真实状态，再切换客户端配置及所有消费者。
  4. 重建受影响进程，验证数据库迁移、API/Worker 读写、OpenFGA 权限及 Gateway，之后恢复流量。
影响 / 故障处理与恢复
遗漏消费者可能造成 API、Worker、授权或初始化任务失联；必须覆盖全部实际使用该账号的连接。
OpenFGA 的凭据格式使用受控原生 Go DSN 配置；不能把毕昇密文交给它，也不假设镜像存在 Shell。
服务端改密前失败保持原账号和配置；修复准备阶段问题，不启动真实改密。
服务端已改、客户端失败修复配置/挂载/URL 编码；需回退时通过有效管理身份恢复服务端密码并同步消费者，不能只还原文件。
成功标准新连接与业务均通过并保留数据；本地已通过锁定镜像的数据库读写及OpenFGA启动，完整权限业务仍需专项验收。

6 · Redis：缓存、队列与 Gateway 联动

Redis 密码需要覆盖全部消费者，连接健康不能以 NOAUTH 当作成功。

6.1 新装：原安装器自动完成

  1. 在原命令内接收并确认 Redis 密码。
  2. 生成受限 Redis 密码文件与 ACL 哈希配置，保留标准部署既有权限语义。
  3. 同步 redis_url、celery_redis_url、Linsight/Beat 使用的配置以及启用的 Gateway Redis 配置。
  4. 启动 Redis 并完成新连接认证检查，通过后继续启动应用。

6.2 已有密码轮换：独立维护

  1. 保留有效管理通道，准备新密码和客户端配置；按原生 ACL 机制设置新旧密码过渡。
  2. 把过渡 ACL 同步到持久化配置；源文件只读挂载时更新源，不假设 ACL SAVE 能写入。
  3. 切换全部消费者并用新连接验证；核对任务投递、消费和实际执行结果。
  4. 确认全部消费者切换后撤销旧密码，再次同步持久化配置。
影响 / 场景处理与恢复
缓存 / 队列 / 网关遗漏分别验证请求缓存、Celery、Linsight、Beat 与 Gateway；漏配可能只损坏部分功能。
保留自定义权限增量工具仅替换目标凭据，保留可解析旧 ACL 权限和其他用户；复杂引号/转义 ACL 拒绝自动转换，不扩大权限。
旧密码仍可用恢复旧客户端配置并检查新值、ACL 和 URI 编码；确认前不撤销旧密码。
旧密码已撤销用有效管理身份恢复必要过渡凭据并持久化，再恢复客户端。
Sentinel / Cluster / TLS数据节点、Sentinel、复制和监控认证需专项适配；当前缓存与 Celery 结构支持有差异，不承诺新增 Cluster broker 支持。
任务结果不确定先核对真实执行结果再决定重试；不清队列、不清空 Redis、不关闭认证。

7 · MinIO：毕昇与 Milvus 对象存储凭据同步

MinIO 的对象存储身份与 Milvus 登录身份分开；更换对象存储密码必须联动 Milvus。

7.1 新装：原安装器自动完成

  1. 在原命令中接收并确认 MinIO 密码；标准交互新装保留已有 MINIO_ROOT_USER 标识，未提供时使用 minioadmin 用户名，密码仍由客户输入。
  2. 生成 minio.user / minio.password，MinIO 通过原生文件变量读取账号和密码。
  3. 业务配置中 object_storage.minio.secret_key 保存标记密文；Milvus 的对象存储原生配置使用同一实际凭据。
  4. 启动对象存储及关联中间件，完成新连接检查，再启动毕昇。

7.2 现用 root 凭据变更：独立维护

  1. 准备新 MinIO 原生凭据、毕昇密文及 Milvus 对象存储配置，保留匹配的旧版本。
  2. 暂停上传、解析及关联任务，等待在途操作结束并停止受影响消费者。
  3. 切换原生凭据并重建 MinIO，使启动进程读取新值；保留全部数据目录。
  4. 用新凭据验证已有对象读取和新上传下载，再启动带新对象凭据的 Milvus 并验证查询/写入。
  5. 重建毕昇进程，验证上传、下载、预签名链接和入库，然后恢复任务。
影响 / 故障处理与恢复
毕昇初始化权限对象存储初始化会访问 bucket/policy，本次不顺带改成更低权限账号；需实测真实初始化与业务。
Milvus 未同步向量关联对象可能无法访问；需恢复同一组 MinIO、Milvus 对象配置和毕昇凭据。
旧预签名 URL / 临时令牌原方案已识别可能受 root 凭据变更影响，需用配套版本复现并重签；对象数据不会因改凭据而自动删除。
切换失败成组恢复旧 MinIO 文件、Milvus 对象配置和毕昇密文，按依赖恢复；不删除 bucket 或对象。

8 · Elasticsearch：新装认证与存量改密

知识 Elasticsearch 和独立统计 Elasticsearch 都通过既有 basic_auth 字段统一解密。

8.1 新装：原安装器自动完成

  1. 在原命令内接收并确认 ES 密码；基础配置启用独立统计 ES 时，单独询问它的密码，不默认复用另一集群。
  2. 生成原生密码文件与服务端认证配置；配套标准单机模板使用 Bitnami 的 ELASTICSEARCH_PASSWORD_FILE。
  3. 将 vector_stores.elasticsearch.ssl_verify.basic_auth 的密码保存为标记密文；统计 ES 复用相同配置模型。
  4. 启动并等待中间件存活，执行只读认证新连接检查，再启动后端。
标准单机策略：当前默认采用 HTTP；集群/TLS 部署必须提供匹配证书、原生参数与信任链并专项验证。安装器不会因认证或 TLS 失败而临时关闭安全能力。独立统计集群的服务端由其管理流程负责，填写客户端密码不等于自动修改外部集群。

8.2 存量无认证启用 / 已有认证改密：独立维护

  1. 确认服务端实际状态、管理身份、维护窗口与恢复入口；准备配套新凭据。
  2. 无认证环境按锁定镜像设置服务端安全配置并重启；已有认证环境通过用户改密接口修改真实密码，不以初始化变量代替。
  3. 用新连接验证真实认证状态，按部署要求验证 TLS/CA；只改密码通常不需要重启服务端，启用安全配置则需要。
  4. 切换应用和统计 ES 配置，重建全部相关客户端进程，验证既有索引查询、新文档写入及统计链路后恢复任务。
影响 / 故障处理与恢复
仅页面能打开不能证明检索、入库和统计成功；只读认证 check 也不代替这些业务验证。
服务端成功、客户端失败修复密文、挂载和解析；需回退时用有效管理凭据恢复真实密码并同步客户端。
管理身份失效按配套镜像验证过的 reset-password 恢复流程处理；工具路径和前置条件仍需真实镜像验收。
恢复底线不删除 .security 或业务索引，不关闭认证、TLS 或证书校验。

9 · Milvus：登录认证与对象凭据分离

Milvus 登录密码与其访问 MinIO 的密码是两组独立凭据，不能用同一修改动作混在一起。

9.1 真正新装：原安装器自动完成

  1. 在原命令中接收并确认 Milvus 登录密码；按组件限制检查输入。
  2. 生成 common.security.authorizationEnabled 与 defaultRootPassword 配置，在第一次初始化之前挂载 user.yaml。
  3. 毕昇 connection_args 保存加密 password；配置解析也覆盖 token，拒绝冲突身份来源。
  4. 启动 Milvus，用新建客户端验证认证；应用启动后还须验证 collection 及知识库实际读写。

9.2 存量开认证或改密：独立维护

  1. 暂停相关业务，确认已有 root 或有效管理身份；准备恢复材料。
  2. 通过配套用户管理接口修改实际账号密码，不能认为修改 defaultRootPassword 会覆盖既有 root。
  3. 存量无认证启用认证时按原生流程重启；用全新连接确认新密码及无凭据拒绝行为。
  4. 切换毕昇密文并重建同步、异步和 ORM 相关进程，避免连接 alias 沿用旧状态。
  5. 验证已有 collection 查询、新写入及知识库业务，确认后恢复任务。
影响 / 故障处理与恢复
只改 defaultRootPassword它是初始化输入，不代替既有 root 的真实改密。
改密响应失败 / 超时原方案已核查 2.5.10 存在写密码后更新认证缓存的时序；失败响应不能直接当作未改密，分别用新建连接确认新旧值。
客户端失败使用有效管理身份恢复必要凭据，配套恢复配置并重建连接；认证缓存异常按锁定版本流程处理。
全部管理身份失效停止自动切换，人工恢复；不清空 etcd，不重建 collection，不降级无认证。
版本组合项目 Milvus 2.5.10 与后端配套 SDK 需要真实组合验收，/healthz 不代替登录及业务权限验证。

10 · 统一影响范围与失败恢复规则

优先按失败场景恢复，保持现用身份和数据；正常失败重试仍使用原命令。

失败 / 场景安装器行为运维动作与完成标志
密码输入不一致 / 弱值仅重问当前组件；关闭回显后显示提示，避免快速粘贴泄漏。在当前提示重新输入并确认；通过后出现下一组件。
镜像不可用 / 不兼容不继续启动服务；交互模式可引导选择配套工具镜像。修复网络、权限或按提示提供镜像，原命令继续。
非交互且缺密码输入明确停止，不使用默认密码。改用交互终端；自动化使用受限输入清单，原命令不变。

并发安装 / 上次退出存活 PID 的锁拒绝并发；明确已退出 PID 可由原命令回收。等待当前安装结束；不手动删除仍有效的锁。
实际账号改密失败 / 超时此为独立维护状态，不由正常 install 自动回滚账号。用新连接确认服务端状态，再决定继续或用有效管理身份成组恢复；不能只恢复客户端文件。

10.1 状态、权限和备份

  1. 凭据状态目录默认在 docker/.generated/credential-security，目录 0700；输入/密钥默认 0600；仅显式挂载的配置包文件按部署组设置 0640，密钥不随之放宽。
  2. 每次准备写全新版本目录；prepared.env 原子保存路径，现用 .env 的配置包/key/revision 在私有临时副本中准备后整体替换，避免半写入。
  3. 挂载或环境变化后重建受影响容器；单纯 restart 不保证新 env 或挂载来源生效。
  4. 把 .env、受限凭据目录、外部指定文件及数据库恢复点纳入公司现有备份制度；密钥不能依赖需要它解锁的数据库/对象服务提供。
数据底线：不清空 Redis/队列，不删除 MySQL 数据、ES 索引、MinIO 对象或 Milvus 元数据来修复认证。日志与故障材料不得打印完整连接串、密码、密钥或完整敏感配置。回退时核对新业务数据及在途任务，不盲目全库恢复。
