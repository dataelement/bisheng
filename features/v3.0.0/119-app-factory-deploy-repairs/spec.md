# Feature: 应用工场交付契约与诊断修复

**关联 PRD**：[PRD-1 §3.1 DEV-03/DEV-04、§3.2 应用运行时](<../../../docs/PRD/3.0-release/3.0 应用工场 PRD-1 专业开发者通道与应用运行时.md>)；[F086](../086-vibe-runtime-delivery/spec.md)；[F114](../114-vibe-permission-actions/spec.md)。本轮用户确认方案及来源问题见 [discovery.md](./discovery.md)。

**优先级**：P1；**所属版本**：v3.0.0；**依赖**：F053/F054/F055/F086/F059/F114，权限与身份沿用 F048/F113。

**状态**：需求发现及本文 42 条正式规格已于 2026-11-03 由用户分别确认；进入设计，尚未业务编码。

本次纳入：新清单默认口径与官方示例、运行变量、默认入口、静态产物、发布诊断、镜像可用性和离线材料指引；116 特有镜像补齐单独记录。原领域对象 Owner 不变，本 Feature 仅协调既有能力修复。

明确排除：旧运行控制接口恢复；新编排后端；应用移交/数据迁移；历史诊断回填；批量重建现存应用；自动放宽网络、依赖版本或权限；补充报告仅列标题的恢复/16251/16283/Authorization 问题；全量测试。上述场景不因本次修复取得额外授权。

## 1. 用户故事

作为应用开发者，我希望按平台分发的示例就能发布，并使用约定的入口、数据库与静态资源目录，以便不必先了解平台内部执行路径。

作为有权排障的开发者，我希望知道发布失败在哪一阶段、具体缺少什么和可读的应用输出，以便修复后再提交。

作为运行环境维护者，我希望在发布前发现缺失的运行材料，并可独立补齐指定节点，以便不影响其它运行环境和已有应用。

## 2. 验收标准

### 2.1 新清单与历史兼容

- **AC-01** — WHEN 开发者从平台获取 CLI 脚手架、部署纳管或平台能力接线示例，THE SYSTEM SHALL 提供清单版本 2、默认应用包交付的有效示例，且配套说明一致。
- **AC-02** — WHEN 新提交未显式指定清单版本，THE SYSTEM SHALL 将其按清单版本 2 处理；未指定交付方式时采用 bundle。
- **AC-03** — WHEN 新提交显式使用清单版本 1，THE SYSTEM SHALL 保留现有 source-image 兼容语义；不得由此调用已退役的运行控制接口。
- **AC-04** — WHEN 读取或继续处理历史已冻结版本，THE SYSTEM SHALL 保持原清单与交付语义；历史缺版本不能因新默认值被重新解释为版本 2。
- **AC-05** — WHEN 开发者显式选择版本 2 的 bundle、image 或 source-image，THE SYSTEM SHALL 继续按既有能力和资格受理；未知版本或不合法组合应明确拒绝。

### 2.2 运行环境契约

- **AC-06** — WHEN 启动遵循托管契约的应用，THE SYSTEM SHALL 提供约定的数据库连接地址及文件路径，二者指向同一应用数据库；官方写库示例不得回退到只读源码目录。
- **AC-07** — WHEN 启动应用版本，THE SYSTEM SHALL 提供实际应用标识、slug、版本及健康路径；这些值不得因 Docker bundle、兼容源码镜像或 K8s 路径而缺失或指向另一应用。
- **AC-08** — WHEN Python 应用使用约定的框架根路径环境变量启动，THE SYSTEM SHALL 使其与该次应用访问前缀一致；Node 的约定根路径别名亦应一致。
- **AC-09** — WHEN 启动审批或管理预览，THE SYSTEM SHALL 使用该预览的版本、访问前缀和独立数据上下文，保持 F114 的身份和密钥边界。
- **AC-10** — WHEN 同一应用正常停止后再次启动，THE SYSTEM SHALL 保留其已提交的数据；运行契约修复不得创建第二个意外的数据库文件。
- **AC-11** — WHEN 更新平台运行组件，THE SYSTEM SHALL 不主动重建现存正式应用或改写其数据；新增变量在新发布或正常获授权重建时生效。

### 2.3 启动入口

- **AC-12** — WHEN 存在有效的显式启动配置，THE SYSTEM SHALL 优先使用该配置；其次采用有效 Procfile 的 web 命令，不得被语言默认入口覆盖。
- **AC-13** — WHEN Python 应用没有显式启动命令或 Procfile，THE SYSTEM SHALL 依次采用存在的 main.py、app.py 脚本入口。
- **AC-14** — WHEN Node 应用没有显式启动命令或 Procfile，THE SYSTEM SHALL 依次采用 scripts.start、有效的 main、server.js、index.js、app.js、main.js。
- **AC-15** — WHEN 采用 Node 的 start 脚本，THE SYSTEM SHALL 支持脚本中的本地可执行文件及既有命令语义；不得额外执行 npm start 的隐式前后置生命周期。
- **AC-16** — IF 声明的入口非法、越出应用边界或没有任何可用入口，THEN THE SYSTEM SHALL 拒绝并明确指出入口问题及补救方法，不将其描述为单纯缺依赖。

### 2.4 静态产物

- **AC-17** — WHEN 发布已经准备好的纯静态文件，THE SYSTEM SHALL 支持包根、dist、build、public 四个入口位置；多个位置同时存在时按根、dist、build、public 的既有文档顺序选择。
- **AC-18** — WHEN 发布请求实际执行了静态构建，THE SYSTEM SHALL 在构建完成后选择 dist、build、public、根中的有效产物，避免源码根入口遮盖已生成的构建结果。
- **AC-19** — IF 静态构建未完成前没有入口文件，THEN THE SYSTEM SHALL 不仅因该文件尚未生成就拒绝具有有效构建步骤的请求；没有构建步骤的上传包应在准备阶段检查入口。
- **AC-20** — IF 构建或准备结束后仍无可用静态入口，THEN THE SYSTEM SHALL 明确拒绝，不出现“上线成功但站点根目录不可访问”；有效站点应正确提供入口及静态资源。

### 2.5 失败原因与输出

- **AC-21** — WHEN 依赖安装或交付准备失败，THE SYSTEM SHALL 返回可观测错误 16227，并保留能区分依赖、入口、材料和镜像问题的具体原因及处置提示。
- **AC-22** — WHEN 启动退出或启动探活失败，THE SYSTEM SHALL 返回可观测错误 16228；其它迁移、恢复、取消等失败不得被统一改成启动失败。
- **AC-23** — WHEN 启动失败且执行体输出仍可获得，THE SYSTEM SHALL 在清理前保留最后至多 40 行、总量至多 16 KiB 的脱敏输出；无法读取输出时保留主要失败原因并明确日志不可用。
- **AC-24** — WHEN 现有公开诊断入口返回失败，THE SYSTEM SHALL 向有权调用者同时提供一致的阶段、具体原因、操作追踪标识及可用日志，不能只提示“见下方日志”却不给输出。
- **AC-25** — WHILE 返回诊断信息，THE SYSTEM SHALL 不泄露实际密钥、控制凭据或其它租户内容；详细诊断与日志仅向现有具备该应用 edit 资格的合法调用者提供。
- **AC-26** — WHEN CLI 输出人类可读或机器可读的失败，THE SYSTEM SHALL 保留相同的真实错误与补救信息；兼容收到旧 16124 时给出启动排障文案，而非“未登记错误码”。
- **AC-27** — WHEN 平台分发本次 CLI 修复，THE SYSTEM SHALL 交付实际包含该修复的可安装版本；新下载安装后行为应与源码一致。

### 2.6 镜像完整性

- **AC-28** — WHEN 某交付请求进入依赖准备或启动前置检查，THE SYSTEM SHALL 确认该次所需的准备、运行及适用基础镜像在目标节点可用；缺失时在无谓的依赖构建和审批前尽早拒绝并指出缺失材料。
- **AC-29** — WHEN 检查镜像可用性，THE SYSTEM SHALL 基于该次实际固定的镜像身份与目标架构，不以同名标签或只有 preparer 就认定 runtime 存在。
- **AC-30** — IF 前置检查后镜像被移除、变更或节点信息失效，THEN THE SYSTEM SHALL 在产生效果前再次核验并拒绝不一致的交付，不能沿用过期的成功判断。
- **AC-31** — WHEN 某节点仅缺少特定语言或交付方式的镜像，THE SYSTEM SHALL 限定对应请求的失败范围，不因此中断其它可用应用或关闭全平台业务入口。
- **AC-32** — WHEN 当前镜像策略禁止自动拉取，THE SYSTEM SHALL 保持该策略并提示维护者补齐指定镜像；不得因本次修复暗中启用拉取或以构建镜像替代运行镜像。

### 2.7 离线材料与环境指引

- **AC-33** — WHILE bundle 准备处于离线模式，THE SYSTEM SHALL 使用内置、已导入或可复用的有效材料，不尝试联网补齐；缺失依赖或不满足精确版本时明确失败。
- **AC-34** — WHERE bundle 的受控联网下载已由环境配置允许，THE SYSTEM SHALL 仅在需要准备材料时按既有受控来源下载；后续安装/编译继续保持既有隔离，应用运行期出网规则独立生效。
- **AC-35** — WHEN 开发者使用离线环境，THE SYSTEM SHALL 说明材料可按目标应用、平台和精确依赖准备及导入，不能把当前内置包数量宣称为产品永久上限。
- **AC-36** — IF 缺包、版本冲突、锁定文件或离线材料不完整导致失败，THEN THE SYSTEM SHALL 给出可核实的原因及材料准备指引，不静默修改依赖版本，也不在预检宣称所有依赖已可安装。
- **AC-37** — WHEN 导入或使用额外材料，THE SYSTEM SHALL 维持既有材料归属、应用、租户、架构和真实主体资格，不能因排障扩大权限或跨应用复用私有材料。

### 2.8 环境处置与不变量

- **AC-38** — WHEN 按授权修复 116 的镜像缺失，THE SYSTEM SHALL 只补齐该节点已启用交付所需的固定镜像，并独立记录核验结果；不能在通用发布行为中包含 116 专属地址或放行规则。
- **AC-39** — WHEN 执行本次环境修复，THE SYSTEM SHALL 保持其它环境、平台服务与存量正式应用的运行状态及现有网络/拉取策略；如需处理额外存量实例，应单独列明并在实际授权下执行。
- **AC-40** — WHEN 应用正常返回 HTTP 500、502 或 503，THE SYSTEM SHALL 保留其响应状态；连接中断等传输失败继续按既有过渡行为处理，不混为同一种故障。
- **AC-41** — IF 发布因容量不足被拒绝，THEN THE SYSTEM SHALL 说明资源不足和可用处置方式，不能把某次资源快照描述为全环境固定的单并发限制；不得自动提高预算。
- **AC-42** — WHEN 开发者使用本次分发的官方 Python 示例和有效材料，THE SYSTEM SHALL 支持其经过正常预检、审批、上线及访问流程，写入并读取本应用数据库；同一应用正常停止再上线后仍可读取该记录。

## 3. 边界情况

- 新提交缺版本与历史冻结版本缺版本的解释必须区分；未知版本明确失败，不能静默走另一种交付。
- 显式完整镜像入口继续由镜像或合法配置决定，不对任意完整镜像强加源码文件回落。
- 有静态构建步骤但产物尚未生成，与上传包遗漏构建产物是两种情况；文档和错误不能混淆。
- 失败输出可能不存在或包含敏感值；不能因抓取日志失败覆盖主要故障，不能扩大诊断读取资格。
- 预检只描述已验证的镜像/材料状态；在途变更仍须执行前拒绝。source-image 的既有构建隔离策略本轮不重写。
- 对历史失败不回填错误码或伪造日志，对现存应用不自动触发重建。镜像导入不代表本 Feature 代码已部署。
