## 0. 最终业务口径

本功能只为阿里百炼明确的临时限流增加一层**限流识别和繁忙展示能力**，不得接管或改写现有模型调用与业务执行逻辑。

下列概念彼此独立，文档、代码和测试不得再混称为“恢复”或“重试”：

| 术语 | 含义 | 本期原则 |
|---|---|---|
| 模型健康状态 | 既有 `llm_model.status` 所表达的最近一次模型调用成功或失败 | 完全沿用旧逻辑；429 仍是失败，成功仍恢复正常 |
| 限流展示状态 | 当前租户下某个实际模型配置是否处于 `recovering/busy` | Redis 临时投影；只服务页面展示与换模候选过滤 |
| 后台模型探测 | 不携带用户上下文的最小模型调用，用于判断限流是否解除 | 只更新模型健康状态和限流展示状态，不处理用户请求 |
| 任务内部自动重试 | 任务模式中间件对可重试异常执行的既有退避重试 | 429 与其他同类可重试异常一致，F051 不得绕过或改变 |
| 任务失败处理 | 自动重试用尽后的既有失败落档、事件发送和任务收敛 | 429 与其他执行错误一致，只允许附加限流展示字段 |
| 用户主动重试 | 用户在失败提示上点击 Retry 后重新执行原请求 | 各入口沿用自己的既有恢复语义；后台探测绝不触发 |

### 范围边界

**本次纳入：**

- 识别阿里百炼明确的临时限流，并向四个入口提供统一、脱敏的繁忙状态。
- 维护按叶子租户和实际模型配置隔离、带 TTL 的临时限流展示状态。
- 使用有限后台探测及时更新模型状态，但不保存、枚举或重放用户会话。
- 工作台日常模式、知识空间 AI 会话、订阅频道 AI 会话在当前页面支持重试原请求和主动换模。
- 工作台任务模式只增加限流识别和中性繁忙展示，内部自动重试、失败处理和用户 Retry 均沿用原逻辑。
- 限流提示常驻提供换模入口；页面和后端均不维护手动重试次数。

**本次明确排除：**

- 不保存“等待模型恢复后自动执行”的会话集合，不扫描会话，不由 probe 调度业务执行。
- 不新增 `model_call_execution` 或其他执行控制表，不复制会话信息，不增加会话删除联动。
- 不为任务模式新增 recovery API、任务队列协议、专用 checkpoint 分支或页面重试计数。
- 不改变任一入口原有的模型可见性、在线状态、权限、能力校验和模型集合规则。
- 不把 Redis 限流状态写回 `llm_model.status`，也不从健康状态推导限流状态。
- 不处理阿里百炼以外供应商的新增限流体验；它们继续走现有错误处理。
- 不自动换模，不修改默认模型，不承诺跨刷新、跨标签页或跨设备的严格重试次数和 exactly-once。

## 1. 用户故事

### 1.1 普通会话用户

作为使用工作台日常模式、知识空间或订阅频道 AI 会话的用户，  
我希望模型临时限流时看到可理解的繁忙提示，并能在原位置重试或选择其他模型，  
以便无需重复输入，也不会在历史中产生失败回答或重复用户消息。

### 1.2 任务模式用户

作为执行长任务的用户，  
我希望 429 像其他可重试的任务执行错误一样经过既有自动重试、失败处理和 Retry 链路，  
以便限流展示能力不会改变任务原有的进度、错误和副作用语义。

### 1.3 运维人员

作为有权排查模型调用问题的运维人员，  
我希望能够定位具体租户、模型、入口及探测结果，  
以便分析限流而不向终端用户暴露供应商原始信息或用户上下文。

## 2. 验收标准

### 2.1 限流识别与原业务链路

- **AC-01** — WHEN 阿里百炼对当前模型调用明确返回临时限流，THE SYSTEM SHALL 将本次调用识别为模型服务繁忙，并产生本期定义的限流展示状态。
- **AC-02** — IF 阿里百炼返回欠费、未购买、鉴权失败、内容安全拦截或其他永久错误，THEN THE SYSTEM SHALL 沿用该错误原有处理语义，且不得创建限流展示状态。
- **AC-03** — WHERE 模型供应商不是阿里百炼，THE SYSTEM SHALL 不启用本期新增的繁忙标记、后台探测、页面计数或换模提示。
- **AC-04** — WHEN 某个实际模型配置触发临时限流，THE SYSTEM SHALL 只影响当前租户下该模型配置，不得按展示名称影响其他模型。
- **AC-05** — WHERE 系统启用多租户，THE SYSTEM SHALL 隔离不同叶子租户的限流展示状态和探测过程。
- **AC-06** — WHEN 终端用户查看限流结果，THE SYSTEM SHALL 只展示标准繁忙状态、提示和操作，不得展示供应商原始错误码、请求 ID 或原始详情。
- **AC-07** — WHEN 临时限流被识别，THE SYSTEM SHALL 为授权运维保留可关联到租户、模型、入口、时间和探测结果的脱敏诊断信息。
- **AC-08** — IF 本期新增的分类、Redis、Celery、日志或状态投影逻辑失败，THEN THE SYSTEM SHALL 保持原模型异常的传播、重试、失败处理和响应语义，不得吞掉、替换或阻断原业务链路。

### 2.2 模型健康状态与限流展示状态

- **AC-09** — WHEN 任一真实模型调用返回 429，THE SYSTEM SHALL 继续沿用既有健康状态逻辑将该调用记为失败；WHEN 模型调用成功，THE SYSTEM SHALL 继续沿用既有逻辑恢复健康状态。
- **AC-10** — WHEN 后台探测调用成功或失败，THE SYSTEM SHALL 像其他模型调用一样更新既有模型健康状态。
- **AC-11** — THE SYSTEM SHALL 将模型健康状态与 Redis 限流展示状态作为两个独立状态源；任一状态不得覆盖、推导或代替另一状态。
- **AC-12** — WHEN 某模型首次命中临时限流，THE SYSTEM SHALL 将当前租户下该模型的限流展示状态设为 `recovering` 并设置有限有效期。
- **AC-13** — WHEN 同一模型在限流展示状态存在期间再次命中临时限流，THE SYSTEM SHALL 刷新其有效期并保护新状态不被旧调用结果覆盖。
- **AC-14** — WHILE 模型处于 `recovering/busy`，THE SYSTEM SHALL 在模型选择器中以灰色状态和“· 服务繁忙”后缀展示，但不得强制替换用户当前选择。
- **AC-15** — WHILE 模型处于 `recovering/busy`，THE SYSTEM SHALL 允许用户在普通模型选择器中继续主动选择该模型。
- **AC-16** — WHEN 限流展示状态变化，THE SYSTEM SHALL 自动更新当前页面，无需用户手动刷新。
- **AC-17** — WHEN 后台探测或真实用户调用确认模型成功且未出现更新的限流事实，THE SYSTEM SHALL 及时清除该模型的限流展示状态。
- **AC-18** — WHEN 限流展示状态有效期到期且期间没有新的临时限流，THE SYSTEM SHALL 将页面投影恢复为正常。
- **AC-19** — IF 模型被停用、删除、收回权限或因既有规则不可用，THEN THE SYSTEM SHALL 继续沿用原模型不可用逻辑；限流状态消失不得恢复其可选性。

### 2.3 工作台任务模式保持原样

- **AC-20** — WHEN 任务模式中的模型调用触发临时 429，THE SYSTEM SHALL 让该异常进入与其他同类可重试异常完全相同的既有中间件分类和退避重试流程。
- **AC-21** — THE SYSTEM SHALL 不因识别出阿里临时限流而提前抛出、跳过、减少、增加或改变任务模式既有自动重试和降级行为。
- **AC-22** — IF 任务模式自动重试最终仍失败，THEN THE SYSTEM SHALL 沿用既有失败处理写入状态、`output_result`、失败轮次和错误事件，并按原规则收敛未完成任务；本期只能附加标准限流展示字段。
- **AC-23** — WHEN 任务模式用户点击 Retry，THE SYSTEM SHALL 继续以原 `sessionVersionId` 和原问题调用既有 `continueConversation` 链路。
- **AC-24** — THE SYSTEM SHALL 不为任务模式新增 recovery endpoint、recovery command、attempt 状态、专用 checkpoint 续跑或新的队列字段。
- **AC-25** — THE SYSTEM SHALL 不在任务模式维护本期手动重试计数，也不新增本期换模入口。
- **AC-26** — WHEN 任务模式发生非阿里 429、超时、连接错误、5xx 或其他既有错误，THE SYSTEM SHALL 保持其原有分类、自动重试、降级和失败行为。
- **AC-27** — IF 限流观察或限流状态写入失败，THEN THE SYSTEM SHALL 仍执行与未接入 F051 时相同的任务自动重试和最终失败处理。

### 2.4 后台模型探测

- **AC-28** — WHEN 某模型首次进入临时限流，THE SYSTEM SHALL 启动最多三次、间隔为 15/30/60 秒的有限后台探测。
- **AC-29** — WHILE 后台探测运行，THE SYSTEM SHALL 不携带用户问题、历史、附件、工具、execution、session 或 chat 标识。
- **AC-30** — THE SYSTEM SHALL 不保存、排队、查询或枚举触发限流的用户会话，也不得由探测结果自动重发、续跑或生成任何用户请求结果。
- **AC-31** — WHEN 探测成功，THE SYSTEM SHALL 只更新模型健康状态与对应租户模型的限流展示状态。
- **AC-32** — WHEN 探测仍返回同类临时限流且次数未用尽，THE SYSTEM SHALL 只安排下一次模型探测；WHEN 次数用尽，THE SYSTEM SHALL 停止本轮探测并保持 `busy` 直到真实成功或 TTL 到期。
- **AC-33** — IF 探测返回非限流错误、模型已删除、停用或不可见，THEN THE SYSTEM SHALL 停止本轮探测，不得宣称模型已恢复，也不得改变用户会话。
- **AC-34** — WHEN 限流 key 被删除或过期后重新创建，THE SYSTEM SHALL 拒绝旧轮次的排队探测和迟到结果，旧任务不得接管、清除或耗尽新轮次状态。
- **AC-35** — WHEN 同一限流轮次在探测排队期间收到新的 429，THE SYSTEM SHALL 允许已排队探测接管该轮次最新版本，同时不得重复投递同一探测槽位。
- **AC-36** — IF Redis 或 Celery 不可用，THEN THE SYSTEM SHALL 记录降级信息并保留当前调用原有错误响应；限流展示可缺失或等待 TTL，但不得触发任何用户业务执行。

### 2.5 非任务入口的当前页面恢复

- **AC-37** — WHEN 日常、知识或频道入口收到临时限流，THE SYSTEM SHALL 先保留原用户消息，并且不得生成失败机器人回答记录或把限流控制状态写入会话历史。
- **AC-38** — WHILE 当前页面仍展示该受限请求且用户尚未发送新消息，THE SYSTEM SHALL 在原位置提供重试和更换模型操作。
- **AC-39** — WHEN 用户点击重试，THE SYSTEM SHALL 从既有原用户消息读取请求内容，在原位置执行一次新的模型调用，不得创建第二条用户消息；日常模式 SHALL 启动一轮新的日常调用，不依赖或续跑任务 checkpoint。
- **AC-40** — WHEN 用户选择更换模型，THE SYSTEM SHALL 使用当前入口既有候选集合和能力规则，排除当前模型及处于 `recovering/busy` 的候选，并使用用户选择的模型继续原请求。
- **AC-41** — IF 用户确认时目标模型已进入 `recovering/busy`，THEN THE SYSTEM SHALL 使用统一 SSE 终态错误拒绝本次操作并保留原请求；其他模型错误沿用入口旧逻辑。
- **AC-42** — IF 原消息、资源权限、安全进度或必要恢复信息已不可用，THEN THE SYSTEM SHALL 使用统一 SSE 终态错误明确告知当前请求无法重试，不得伪装成新的 429，也不得静默从头执行。
- **AC-43** — WHILE 一次手动恢复正在执行，THE SYSTEM SHALL 禁止当前页面再次并行触发相同操作；后端只允许使用短时防重复保护，不建立持久执行状态机。
- **AC-44** — WHILE 当前页面仍允许恢复原请求，THE SYSTEM SHALL 常驻提供更换模型入口，不得以手动重试次数作为显示条件，也不得在任意次数后自动弹出换模弹窗。
- **AC-45** — THE SYSTEM SHALL 不维护、不展示手动重试次数或剩余次数；页面刷新后允许限流操作入口消失。
- **AC-46** — WHEN 用户选择模型继续原请求，THE SYSTEM SHALL 同步将当前入口输入框的模型选择更新为该模型，并将其视为用户手动选择；不得修改管理员默认模型。
- **AC-47** — IF 换模恢复已进入原模型调用链但返回鉴权、欠费、内容过滤或其他模型错误，THEN THE SYSTEM SHALL 只按入口原有错误展示处理，不得额外提示“换模被拒绝”；只有 `12048/recovery_rejected` 表示恢复操作本身被拒绝。
- **AC-48** — WHEN 用户发送一条新消息，THE SYSTEM SHALL 保留旧限流提示但立即关闭旧请求的重试和换模入口；新消息独立执行。
- **AC-49** — WHEN 当前页面收到多个尝试的迟到结果，THE SYSTEM SHALL 只将当前仍在等待的尝试更新到原请求位置。
- **AC-50** — WHEN 恢复成功，THE SYSTEM SHALL 按当前入口既有格式只写一条正常回答；知识、频道和日常模式均不得重复用户消息，日常模式中由用户主动重试发起的新调用沿用普通日常调用的工具执行语义。
- **AC-51** — WHERE 页面刷新、切换会话或重新进入入口，THE SYSTEM MAY 不恢复限流卡、失败片段和操作入口，但 SHALL 继续从既有业务记录展示原用户消息和正常结果。

### 2.6 四入口一致性与降级边界

- **AC-52** — THE SYSTEM SHALL 在工作台日常模式、任务模式、知识空间 AI 会话和订阅频道 AI 会话中使用同一阿里临时限流分类和同一模型级展示状态。
- **AC-53** — WHEN 同一租户的多个页面查看同一实际模型配置，THE SYSTEM SHALL 最终展示一致的 `recovering/busy/normal` 状态。
- **AC-54** — WHERE 不同入口已有不同模型权限、在线状态和能力规则，THE SYSTEM SHALL 继续使用原入口规则，不得因本功能扩大或收窄模型集合。
- **AC-55** — WHEN 任一入口返回真实限流、恢复拒绝或其他错误，THE SYSTEM SHALL 使用统一 SSE/WS 错误结构；页面 SHALL 将标准错误映射为对应语言的主要提示。
- **AC-56** — THE SYSTEM SHALL 保证 F051 的分类、状态、探测、日志和页面增强均为原业务链路的附加能力；移除或故障降级 F051 后，除缺少繁忙展示与主动恢复增强外，原模型调用和错误处理 SHALL 保持可用。

## 3. 边界情况

- 同一租户、同一模型短时间并发收到多个 429：只允许有限探测，不允许形成与请求数相同的探测风暴。
- 旧探测任务在 key 删除后迟到，新 key 已由新 429 创建：旧任务必须空操作。
- 真实用户成功与另一调用的新 429 并发：成功只能清除自己观察到的旧版本，不能清除更新的限流事实。
- 后台 probe 成功但原页面仍显示旧请求：只更新模型状态，不自动恢复该请求；用户仍决定是否重试。
- 模型恢复后又立即限流：以最新真实调用事实为准，页面重新进入 `recovering/busy`。
- 用户在两个标签页同时点击：产品只要求页面内 pending 和短时防重，不承诺跨页面 exactly-once；迟到结果不得覆盖当前页面的新尝试。
- 非任务入口的恢复信息过期或业务记录已删除：返回明确的恢复拒绝，不重建用户请求。
