# 昆联多租户接入与 Workflow 资产调用改造规划

更新日期：2026-11-11

状态：首批规格、修订设计与任务规划已确认；基础声明和 Workflow 专属创建已本地实施及验证（12 / 42 项任务）。自动开通与多租户登录全链路尚待实施，未部署。本文不代表服务器已支持下列新增能力。

## 目标与已确认决策

先让昆联可信目录中的有效租户和用户能够使用毕昇工作流，再补齐将已发布 Workflow 作为平台资产供其他租户 Agent 调用的闭环。

用户已确认：

- 为可信目录中的有效租户自动创建独立毕昇租户。
- 为已开通租户的有效用户自动配置“工作流管理入口＋新建工作流”的最小基础角色。不包含管理员身份，不自动取得其他人 Workflow 的权限。
- 自动创建能力只覆盖 Workflow，不自动授予通用 `create_app`；已有独立人工通用权限保留。设计采用现有角色体系中的 `create_workflow` 子能力。

第二项调整此前 F118 的“基础菜单由管理员提前配置”决定。首批已按确认规划进入本地实施，现有服务器规则尚未改变。

## 已核对的现状

| 环节 | 当前能力与缺口 | 处理原则 |
| --- | --- | --- |
| 登录 | 网关和后端都按单个允许租户和 Workspace 清单校验。昆联 20261111 配置也明确客户端只开放 Workflow 试点租户。 | 双端协同支持新的租户准入；真实开放以昆联客户端实际授权范围为准，不能只删除校验。 |
| 目录与用户 | 全租户目录已落地；只有显式建立本地映射的成员才投影成本地用户。当前定时全量同步为 300 秒。 | 增加自动开通与后续用户投影，保留完整批次、补同步、失败重试和旧批次保护。不能将现有轮询称为实时推送。 |
| 基础入口 | 用户无角色或可用菜单时，后端拒绝登录。已有试点账号通过人工配置入口。 | 增加最小基础角色的自动配置；具体 Workflow 的查看、编辑、发布、运行仍独立鉴权。 |
| 反向运行 | 已有固定版本、持久运行、幂等、交互、取消与查询的 Mock 实现；正式身份与服务装配仍留 TODO。 | 优先接通同租户正式适配，再扩展资产消费；不能把 Mock 通过算成正式接口交付。 |
| 跨租户资产 | 当前运行入口先拒绝租户不匹配的 Workflow；原共享服务并非任意租户之间的 Workflow 资产分发。 | 独立定义发布者、消费租户、实际用户、固定版本和撤销规则；继续经过统一权限入口。 |

现状依据：`sso_sync` 登录与目录编排、`tenant`／`user`／`role` 原领域服务、反向运行应用及登记仓储、原租户共享服务，以及昆联已交付联调配置。此前服务器试点的真实验证见 [联调部署与验证记录](../../../features/v3.0.0/118-kunlian-sso-user-sync/联调部署与验证记录-20261111.md)。

## 分批实施

| 顺序 | 开发内容 | 复用能力 | 验收出口 | 外部依赖 |
| --- | --- | --- | --- | --- |
| **第一批：多租户与新用户开通** | 自动开通有效租户、稳定映射、用户投影、最小基础角色；网关与后端协同校验租户及 Workspace；明确待同步与失败状态。 | 既有租户创建与成员服务、用户投影栅栏、角色／菜单服务、同步任务、SSO 和管理页。 | A、B 两个有效租户分别登录和创建自己的 Workflow；新成员同步后可进入；跨租户访问、管理员权限和他人资源权限均不随基础角色放开；失败重试不重复创建。 | 本地可先 Mock；真实多租户登录需要昆联扩展现有客户端范围及提供对应测试身份。首批 [规格](../../../features/v3.0.0/130-kunlian-tenant-onboarding/spec.md)。 |
| **第二批：同租户正式反向调用** | 将已有反向运行接上真实接入方与实际用户身份、发布版本登记及运行适配。先运行独立 Workflow。 | 已有创建／发布登记、固定版本执行、幂等、状态／结果、人工输入与取消。 | 昆联 Agent 使用已登记固定版本运行同租户 Workflow；重复请求返回同次运行；可查状态和结果；撤权后新访问拒绝。 | 确认 Access Token 能否复用、接收方与委托范围、版本绑定及正式请求样例。不默认要求昆联新增鉴权接口。 |
| **第三批：跨租户 Workflow 资产消费** | 发布者允许指定消费范围；消费租户实际用户调用已登记固定版本；取消资产分发或下线后阻断新运行。 | 前两批身份与运行闭环、统一权限入口、持久运行及发布登记。共享服务只作为机制参考，不直接套用任意跨租户。 | A 发布，获准 B／C 可调用，D 不可调用；B 不能编辑 A 的 Workflow；B／C 输入与结果隔离；升级不改变在途版本；撤销后新请求拒绝。 | 确认昆联现有平台资产标识、分发授权的权威来源与撤销方式、实际调用者身份。跨租户底层模型／知识／工具权限须另行明确，首轮使用不依赖这些资源的测试流程。 |
| **第四批：增量时效与运维补齐** | 根据实际新用户生效时效补事件触发或增量，完善同步与开通诊断、真实故障恢复和容量验证。 | 全量对账、受控补同步、已有诊断与补偿。 | 双方约定的新用户生效时效可测；通知丢失后可由对账恢复；不重复创建、不误删、不恢复被管理员撤销的资格。 | 优先确认已有事件／增量能力。没有时继续全量对账与补同步，不虚构事件接口。 |

依赖顺序为“第一批 → 第二批 → 第三批”。第四批的诊断随第一批建设，增量接入和时效验收由上游能力决定。每批分别编写并确认规格、设计、任务后实施，避免将多种授权变化一次性放开。

## 首批验证安排

1. 定向验证两个租户的开通、重名、重复同步、停用与恢复，以及基础角色范围。
2. 集成验证并发开通、部分失败重试、跨 Worker 接续、目录完整发布和权限投影未完成时拒绝准入。
3. 隔离 Mock 浏览器验证 A／B 分别登录、管理页、新建与编辑自己的 Workflow、SSO 回跳和越权拒绝。
4. 网关与后端共同验证租户／Workspace 组合，防止两个合法租户的参数混用；复验原单租户配置与其他登录方式。
5. 真实昆联多租户、真实数据库／OpenFGA、DM8 和服务器启用验证均单独记录；未执行时标记 `NOT_RUN`。

## 昆联目前需要提供或确认

| 事项 | 需要的结果 |
| --- | --- |
| 多租户客户端范围 | 将已交付客户端扩展到目标租户，或说明现有多租户客户端接入方式；提供各租户与 Workspace 的可信对应规则。已交付单租户凭据与回调不重复索取。 |
| 测试身份 | 至少两个有效租户的可登录用户，以及可新增、停用／恢复的测试成员。 |
| 实际用户调用身份 | 确认现有 Access Token 是否允许用于 Agent 调用 Workflow，并说明接收方、用户、租户及授权范围的校验规则。 |
| 资产分发依据 | 现有 Workflow 资产、固定版本、消费租户授权及撤销如何查询或传递；优先复用既有能力。 |
| 同步时效 | 希望新用户多久可用，已有通知／增量是否可复用；空租户若不在用户目录中返回，如何被发现。 |

前两项决定第一批能否真实验收；第三、四项分别决定后续反向调用和跨租户资产接入。未收到材料前可先做隔离 Mock。

## 风险与实施边界

- 自动开通会新增本地租户、用户及基础角色关系；不会迁移既有账号和业务资产，不按名称合并租户，不授予租户管理员或全局管理员。
- 自动规则只管理其来源记录；管理员明确阻断的资格不能因下次同步被自动补回。停用保留人工授权与资产，访问继续按当前资格判断。
- 开通失败不得将用户落到默认租户，也不得将未完成权限投影视为就绪。上游返回的未知状态不能解释为有效。
- 首批代码保持旧配置可用；新规则单独启用并纳入策略修订。启用失败时停止新增开通并阻断未就绪准入，保留已生成对象及补偿记录，不通过删除租户或回灌整库回退。
- 跨租户调用不得通过关闭租户过滤、伪装成创建者或跳过统一权限判断实现。模型平台的跨租户改造不属于本仓库实施范围。
- 本轮不部署、不更改服务器策略、不提交推送；现有未提交的联调修复保持原样。
