### should-fix

**S1：工具、工作流两张创建操作表应先接受一次删减论证。**

锚点：`design.md:213–220,265–271`；工具当前的直接缺陷在 `src/backend/bisheng/tool/domain/services/tool.py:263–274` 与 `tool/domain/models/gpts_tools.py:473–486`：显式写登录租户，父子分两次提交。工作流在 `api/v1/workflow.py:443` 同样显式写登录租户。

直接修复是冻结合法T、父子或flow/v0显式同T、一个SQL事务。权限投影跨事务的不确定性确实需要业务pending，尤其超级管理员可能绕过权限判断；但这不直接推出**另一张完整操作表**。设计已经要求父资源增加状态和操作引用，操作表又保存该资源已有的T、actor、target ID。

方向：优先评估删除 `tool_creation_operation` 与 `workflow_creation_operation`，由各自父资源行保存固定创建所需的状态、稳定权限key/原始意图及必要错误；权限恢复通过窄门面查找、恢复原冻结投影。若需要重试时间、审计进度，仍应逐字段证明是否必须独立成表。不能仅删表后恢复为“hook异常便删除资源”。

安全底线：

- 同SQL事务完成父子/版本；业务pending早于外部投影，READY晚于投影确认。
- 保存或可无歧义计算稳定权限key；结果未知不重新构造权限计划。
- 正常使用及super均检查pending。
- 只有需要自动恢复的固定阶段才加调度；AC-28–30并未直接要求工具和工作流各自有一套新的HTTP操作中心及60秒扫描服务。

这是可保持AC-28–30的具体缩减机会，但需要设计补齐字段与恢复证明，不能直接断言已安全。

**S2：把“角色/部门/用户三层持久编排”作为已批准广义政策工作的成本，而非六项租户修复的必然成本。**

锚点：`design.md:143–190,262–264`。已有 `user_role.py:70–88` 是简单绑定增删；共享ORM `database/models/user_role.py:12–28` 没有来源或终止历史。因此“失效绑定不复活”确实要删除/终止并留下审计，但不必然要求每个定义变更先全员预留、封闭、批量发布三个层次的操作。

方向：在设计中分开：

1. 修角色定义/菜单在定义O中读写、用户绑定显式写H、部门B与人员H最终校验。
2. 同步完成可共同提交的绑定终止和审计。
3. 需要跨批次、跨DSH传播、进程退出后继续的操作，才进入持久编排。

如果实际绑定集合必须支持无上限批量变更，或者明确保持当前AC-13/17的跨系统收敛保障，持久记录有合理依据；没有规模证据时不应把最复杂方案当唯一可行方案。**也不能承诺删掉三表后仅靠实时过滤满足AC-09/10/12**：过滤旧行会在作用域扩大或回迁后复活。

**S3：DSH全模型封闭是实质性系统改造，必须独立标注取舍，不能包装成缓存刷新。**

锚点：`design.md:166–179` 修改按人账本、direct并发准入、Lua admit、Redis重建、ModelVisibility/CreditRule写入者；这已远超六项HTTP租户错位。

它并非完全无需求依据：`spec.md:72–73` 的AC-17/18要求DSH后续决策一致、故障不得降为不限。源码也支持现有桥接不足：`permission/domain/services/legacy_rbac_sync_service.py:92–113` 的多个旧回调已退休；`dsh/domain/repositories/unified_policy.py:47–64` 的可见性、额度各自有版本，不能用一次旧回调证明人员角色变更已传播。

方向：明确两种交付选择。保留完整AC-17/18，就保留可证明的版本化发布/恢复能力，但另做小范围设计；若本批只修六个管理缺陷，就明确延期**AC-17的DSH传播部分、AC-18的DSH失败闭锁部分，以及AC-13涉及跨系统主属收敛的部分**。不得删掉桥接后继续宣称40条全部满足，也不得把既有DSH操作表当任意业务operation容器。

**S4：知识复制的持久操作和逐项映射有充分依据，不宜为减少表数一起删除。**

锚点：`design.md:234–256,267–268`；现有 `knowledge_service.py:2563–2605,2616–2655` 先改变源，再建目标、投影、审计、投递；`create_knowledge_base:894–905` 覆写租户并提前初始化外部索引。QA worker在 `worker/knowledge/qa.py:83–110` 为每批生成新SQL行与新向量插入，重复执行不能天然保证同目标数据。

方向：六项缺陷阶段先拆掉覆写H的创建helper、先验证范围、源目标SQL原子预留；完整恢复阶段保留业务持久意图、稳定目标与逐项映射。`knowledge_copy_operation` 与 `knowledge_copy_item` 是七表中依据最强的两张。能否把item放入有界manifest是物理存储选择；现有分页批量复制说明不能默认清单小到适合一个无限JSON字段。

外部attempt隔离是对auto-id、不确定插入的一种合理保守解；如要删除，应先证明具体存储支持稳定ID和可重放写入。Celery task_id、源COPYING状态、权限投影账本都不能替代它。

### 最小修复应如何划界

建议先交付一批**无新业务操作表的租户正确性修复**，保留必要资源pending字段及安全拒绝：

- 角色及菜单以已授权定义O读取、查重和单事务更新；不扩大所有DAO的过滤豁免。现有错误点见 `role_service.py:409–458`。
- 普通角色绑定按人员H；候选与最终写都校验部门B、成员资格和管理权；跨租户兼属修改在任何其他字段提交前拒绝。
- 工具父子和workflow/v0显式同T、单事务；资源自身保存必要pending状态，失败不得作为可用资源消费。
- 知识复制按源T验证和预留；不调用覆写H、提前初始化外部系统的创建helper。
- quota分别解决合法全局定义读取、个人与T计量、独立余额比较、失败非零。当前真实问题见 `quota_service.py:152–164,325–355,616–626`，这些无需新额度账本。

**这不是完整40条AC的替代实现。** 如果本批停止于上述边界，需用户明确确认以下延期或收窄：

| AC | 需要明确延期的结果 |
|---|---|
| AC-08、AC-14 | SSO/默认授予/所有旧生产者统一且重放不重发。 |
| AC-09、AC-10、AC-12 | 所有组织/作用域/迁移入口的绑定终止、不复活及回迁语义。 |
| AC-13 | 主属和跨系统政策未收敛时的持久诊断、恢复与敏感写闭锁。 |
| AC-17 | 本批未接入消费者的政策传播，尤其DSH；不能只写“菜单和quota已修”。 |
| AC-18 | 未覆盖消费者的失败闭锁，尤其审批、DSH。 |
| AC-21、AC-24、AC-25 | 若只修角色配额读取，则旧频道预算责任、迁出止增与交接仍未完成。 |
| AC-32–35 | 复制全过程可恢复、重启/重复投递幂等、未知外部效果安全恢复及逐项结果验证。 |
| AC-36 | 对未改造的后台恢复路径，不能宣称已冻结T并重验当前资格。 |
| AC-40 | 普通审计可保留；完整绑定终止及失败恢复结果追踪只对本批真正覆盖路径成立。 |

AC-30不建议简单延期：只要仍有SQL成功、外部权限失败窗口，就应保留业务pending及正常消费拒绝。AC-31的范围验证应立即做。AC-39只读盘点也不依赖七张新表，可以保留。
