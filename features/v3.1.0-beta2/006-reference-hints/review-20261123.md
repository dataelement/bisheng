## 问题与代码证据

### D1：托管应用的名称到原目标 ID 映射没有设计兼容路径（high）

设计位置：`design.md §4.3`（第 83 行）及 §4.1/§4.5。对应 AC-07、AC-13。

- `src/backend/bisheng/app_publish/application/reference_source_owner.py::_frozen`（428–448 行）：从旧引用明细建立 slot→TargetKey 映射，随后要求 source set ready、摘要一致；该逻辑发生在公共 source_read._index 之前。
- `src/backend/bisheng/app_publish/domain/services/reference_extractor.py::extract_app_references`：必须传入完整的 resolved_targets，名称声明不能直接得到原目标 ID。
- `src/backend/bisheng/app_publish/domain/services/version_service.py`：创建版本时保留原 capabilities，injections 初始为空，已解析映射进入引用写入。
- `src/backend/test/knowledge_unification/test_app_saved_capabilities.py::test_saved_inspect_reports_frozen_identity_not_renamed_or_reused_name`：原模型 11 改名、模型 13 接管 alpha 名称后，历史应用仍指向 11，并标记 binding_identity_changed。

因此，保留现状会使索引缺失继续阻断应用；直接按当前名称重建又可能改掉旧版本绑定。设计尚未区分这项现存业务绑定语义与可滞后的反向提示索引。

### D2：跨空间移动仍将引用维护放在主事务内（high）

设计位置：`design.md §4.5`（第 114 行起）。对应 AC-07、AC-08 及主流程不依赖引用的范围。

- `src/backend/bisheng/knowledge/application/move_processing_owner.py::aensure_logical`：在逻辑切换的 SAVEPOINT 内同步调用 `amove_file_ownership`（约 331–350 行）。
- `src/backend/bisheng/knowledge/application/reference_target_owner.py::amove_file_ownership`：执行引用 runtime 类型、目标 receipt、逻辑上下文校验并同步更新引用归属。
- `src/backend/bisheng/resource_reference/application/write_runtime.py::arefresh_file_target_ownership`：继续依赖严格 owner scope 和引用仓储更新。

该路径既没有列入主流程拆分表，也没有对应异步目标归属处理。引用更新失败仍可阻断移动，内容关联的 target_space_id 更新也不属于现有“仅来源根发生保存”的触发条件。

### D3：旧名称助手在来源加载层仍依赖索引（medium）

设计位置：`design.md §4.1`（第 64 行）及 §4.5。对应 AC-07、AC-13。

- `src/backend/bisheng/assistant/application/reference_source_owner.py::_load`（200–218 行）：调用 ahas_legacy_name_retention 后选择历史或普通提取器。
- `src/backend/bisheng/assistant/domain/repositories/reference_source_repository.py::ahas_legacy_name_retention`（37–65 行）：读取 BusinessReferenceSet 的提取器标记、ready、effective 和 revision。

因此，仅取消公共 _index、target repository 及 Run 校验不等于解除全部索引准入。旧模型名称没有可用索引标记时，来源加载就会先报配置解析错误，查看和修复可能无法进入。

### D4：知识删除接口缺少独立引用失败状态的落点（medium）

设计位置：`design.md §6.1`（152–155 行）。对应 AC-04。

- `src/frontend/platform/src/controllers/API/knowledgeDeletion.ts::DeleteImpact/DeletePrecheck`：预检携带顶层业务 check_complete 及 impact，没有嵌套 inspection；impact 也没有引用查询成功标记。
- `src/frontend/platform/src/pages/KnowledgePage/components/KnowledgeDeletionDialog.tsx`：complete 来自 view.result.check_complete，引用展示来自 view.result.impact；complete 同时参与按钮可执行判断及不可用提示。
- `src/backend/bisheng/knowledge/application/knowledge_delete_precheck.py`：现有响应的 impact 包含引用计数、source_page、file_count，顶层写入 check_complete/can_execute。

文档对模型式 inspection.check_complete 的说明，尚不能对应到知识删除预检的现有响应。两种完成状态需要明确的数据落点，才能避免继续禁用删除或把引用失败显示成空结果；这不要求新增完整性三态或治理协议。
