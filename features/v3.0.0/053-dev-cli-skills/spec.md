>
> - **本次纳入**：
>   - **CLI 包工程与安装件平台分发**：可安装的 `bisheng` CLI 发布件；平台自身提供下载端点与版本信息（纯内网零公网依赖、下载不要求密钥或登录态）；CLI 与平台版本对齐、不兼容时明确提示；五个子命令与 `--help`；非交互（agent）可用、机器可读输出、输出永不回显密钥明文
>   - **`login`**：以服务账号密钥登录目标平台，仅验密钥有效不验权限位；凭据落本地用户目录、属主可读、不落工程目录；输出服务账号与其资源归属人；成功后自动执行一次 `skills sync`；**持 `delegate` 位的密钥在 `login` 即拒**并提示「委托专用、本地开发另发一把」（INV-31）；同机多平台凭据隔离；平台侧 login 校验入口（含 `delegate` 拒绝）由本 Feature 拥有
>   - **`skills sync` 与 DEV-03 两包技能包**：从已登录平台拉两包到本地用户目录、幂等覆盖更新、与平台版本对齐；两包内容——「部署纳管」（`bisheng-app.yaml` 写法 / 能力声明 / 安全红线 / 托管运行契约 / deploy 工作流与预检排障指引）与「平台能力接线」（模型与应用数据库两条标准库接法由本 Feature 交付；SDK 三件套用法章节含 auth 静默失败点显著标注随 F057 交付后补齐、其验收随 F057）；每包 SKILL.md + 可运行样例 + 连通自检脚本（接线包自检脚本随 F057 补齐）；触发描述不绑产品名；内外同源单一来源；非 Claude Code 引擎经 AGENTS.md 引用；平台侧技能包分发端点由本 Feature 拥有
>   - **`dev`**：本地运行应用 + 内置迷你代理注入与线上同构的身份头（= 当前密钥对应的服务账号）+ 剥离伪造头 + 起本地 SQLite 并注入与线上同名的连接环境变量 + 注入与线上同名的平台接线环境变量 + 输出明示注入身份来源；**无 `--as`**；不代理平台能力调用
>   - **`deploy`（命令侧）**：以 `bisheng-app.yaml` 为发布输入并做本地必填校验；按忽略规则打包当前项目为版本快照 → 上传 → 触发 F055 发布管线 → 分阶段输出托管预检 / 安全扫描 / 审批单状态（默认到审批单生成即返回，`--wait` 至审批终态与上线结果）；准入闸 = 密钥的 `app:manage` 位（GOV-07 ②）；在途审批单拒绝并提示；改 / 删列须 `--confirm-schema-change` 或交互确认；归属人不同的密钥 deploy 既有应用被拒并提示归属；首发输出应用标识、后续以之关联同一应用；上传体量上限与忽略规则
>   - **`logs`**：查看自己应用（= 密钥资源归属人 owner 的应用）的运行日志，需 `app:manage`、owner-only；内容范围与权限口径与 MCP 应用日志工具（F052）、应用详情页运行日志（F054 WB-13）三入口一致
>   - **DEV-01 ⑤ 接入信息区**（platform 服务账号详情页「API 密钥」tab 顶部）：MCP 地址 / OpenAI 兼容 base URL / CLI 下载链接 / `bisheng login` 指引 + 「一键复制接入信息」；不含 key 值或任何可换取 key 值的凭据；未部署开放能力层不出现
>   - **`bisheng-app.yaml` 的消费**：它是 `deploy` 的发布输入与 `dev` 的启动依据；其对外形态（名称 / 描述 / 图标 / `runtime` / 端口 / 档位 / 能力声明 / 应用数据表结构 / 出站域名白名单）**由 F055 拥有**（release-contract 表 1 候选 AppManifest：发布输入的权威 = 管线校验方），本 Feature 的 CLI 按该形态打包、本地校验必填项、`dev` 据此启动，**不自定义任何字段**；「部署纳管」包只教写法、引用 F055 的定义
> - **本次明确排除**：
>   - **发布管线服务端**（托管预检 / 安全扫描规则集 / 审批单生成与预置审批流 / 上线终检 / 版本记录与快照写入 / 结构演进的服务端判定与迁移前快照 / 元信息与档位随 deploy 更新的落库 / `deploy` · `logs` 的服务端权限判定含拒 `delegate`）与 **`bisheng-app.yaml` 对外形态的定义**（AppManifest）——**F055**；本 Feature 的 `deploy` 只验收命令行为，管线阶段用「经 F055」措辞
>   - **实例运行日志的读取接口与 WB-13 详情页运行日志 tab**——**F054**（`logs` 只消费）；**MCP 六类工具（含应用状态 / 日志工具）与统一检索门面**——**F052**；**模型协议面**——**F051**；**服务账号、密钥签发与三扩展位的表单层**——**F049**；**应用运行时、app-proxy 与线上身份注入**——**F054**
>   - **SDK 三件套（auth / retrieve / storage）与开发者指南**——**F057**；「平台能力接线」包中的 **SDK 用法章节与其自检脚本随 F057 交付后补齐、验收随 F057**（本 Feature 不单独承诺接线包内容可通过），`dev` 注入的环境变量名与 F057 / F054 对齐但不拥有 SDK 本身
>   - **`init` / 工程骨架生成**（PRD-1 DEV-04 一句话「命令数刻意收在最少」）；**五命令之外的任何子命令**（如 `logout` / `whoami`——登出 = 删除本地凭据文件或对同一平台重新 `login` 覆盖）
>   - **`--as` 身份模拟及任何指定其他用户身份的入口**（PRD-1 §5.1 / DEV-05 ①）——本地验 per-user 差异的路径 = 发布后用真实账号访问
>   - **CLI 调用限流、token 用量上限**（PRD-1 §5.2 顺延）；**第三方 MCP 网关、本地端专有插件**（§5.1）；**平台侧接入信息的分享链接 / 二维码 / 站内信推送**（DEV-01 ⑤ 本版不做——走企业既有渠道）
>   - **CLI 侧复制一份密钥扫描规则集做本地预扫**——扫描只在 F055 服务端做一次（同一规则集、不分叉），CLI 只结构性排除自身产物（§4 决议-2）
>   - **单文件二进制安装件**（§4 决议-1 备选，v3.1 视客户反馈）；**平台侧回滚**（RT-05 顺延——CLI 路径等价手段是本地 checkout 旧版本重新 `deploy`）

## 1. 用户故事

作为 **开发者（owner）**，
我希望 **拿到管理员转来的一段接入信息与一把 key 后，一条 `login` 就接好平台、本地 `dev` 跑起来时应用拿到的身份结构与线上一模一样、`deploy` 一条命令走完预检 → 扫描 → 审批、`logs` 能看到自己应用的日志**，
以便 **把本地开发的存量应用交给平台托管、发给同事用，全程不离开终端，也不用为「本地」和「线上」写两套身份与数据库代码**。

作为 **开发者的本地 coding agent**，
我希望 **`login` 后技能包已经在本地、每个命令都能在无 TTY 下跑通且输出可解析、预检与扫描失败时能拿到「缺什么、怎么改」而不是堆栈**，
以便 **凭技能包 + CLI + MCP 自主完成声明补全 → deploy → 预检修复 → 审批状态跟踪的闭环，不需要开发者中途接管**。

作为 **租户管理员**，
我希望 **在服务账号详情页一键复制出不含 key 值的接入信息发给开发者，而 CLI 通道只认 key 上的 `app:manage` 位、不碰角色配置**，
以便 **放开一个人的 CLI 部署能力只需签一把 key，回收只需吊销那把 key，不引入新的角色权限点，也不用担心接入信息本身泄漏**。

作为 **平台管理员 / IT（信创与纯内网环境）**，
我希望 **CLI 安装件与技能包都由平台自己分发、随平台版本一起升级、不访问任何公网地址**，
以便 **离线环境也能完整走通开发者通道，且升级平台后开发者只需从平台重新下载或重跑一次 `skills sync`**。

## 2. 验收标准

> AC 编号在本特性内唯一。括号内标注对应 PRD-1 条目与验收序号（如 `↔DEV-04 验收 5`）、伴生 PRD 附录 B.2 及跨 Feature 不变量。属于服务端管线 / 运行时的行为用「经 F055」「经 F054」措辞——本 Feature 只验收 CLI 侧的命令行为与呈现。错误码仅作可观测行为引用，定义在 design.md。2026-08-17 审查修订后编号保持稳定：拆分用 `AC-31a/b/c`、删除留墓碑（AC-39）、新增末尾追加（§2.9），见文末附表。

### 2.1 安装件与分发、CLI 通用行为

- **AC-01** — THE SYSTEM SHALL 提供 `bisheng` CLI 安装件并由平台自身分发（下载端点 + 当前版本信息）；同一分发端点亦承载 bisheng-sdk 发布件及平台声明的 SDK 最低兼容版本（F057 AC-01 / AC-03 消费）；纯内网环境零公网依赖即可下载与安装；下载链接即接入信息区展示的链接（AC-44），下载不要求持有密钥或平台登录态。（↔DEV-04 需求描述 / DEV-01 ⑤；§4 决议-1 / 决议-11）
- **AC-02** — THE SYSTEM SHALL 使 CLI 安装件随平台版本发布、版本号与平台版本对齐，`bisheng --version` 可显示；WHEN 命令与平台交互, THE SYSTEM SHALL 校验 CLI 与目标平台的兼容性——IF 不兼容, THEN 拒绝执行并提示从该平台重新下载（给出下载链接）；兼容但落后时仅提示不阻断。（↔DEV-03 规则「版本对齐」；§4 决议-7）
- **AC-03** — THE SYSTEM SHALL 提供且仅提供五个子命令 `login` / `skills sync` / `dev` / `deploy` / `logs`（各带 `--help`）；THE SYSTEM SHALL NOT 提供 `init` / 工程骨架生成、`--as` 或任何指定其他用户身份的参数。（↔DEV-04 界面表 / DEV-05 ① / §5.1）
- **AC-04** — THE SYSTEM SHALL 使每个命令在非交互环境（无 TTY，如被本地 coding agent 调用）可完整执行：每处交互确认均有等价命令行参数、结果以确定的退出码与可读文本给出、并提供机器可读的输出模式；THE SYSTEM SHALL 在任何输出、本地日志与错误信息中不回显密钥明文（至多掩码）。（↔§3.1「本域的操作者是 agent」/ NFR-2）
- **AC-05** — WHERE 开放能力层未部署, THE SYSTEM SHALL 使安装件下载端点、技能包分发端点与 login 校验入口均不可达（呈不存在），平台其余功能零变化；CLI 对此给出可读原因（AC-10）。（↔GOV-10 规则 / DEV-01 ⑥；F049 AC-49）

### 2.2 `login` 与凭据

- **AC-06** — WHEN 开发者以目标平台地址与服务账号密钥执行 `bisheng login`, THE SYSTEM SHALL 向该平台校验密钥有效（未撤销且未过期，模式 S），**不校验任何权限位**；通过后把凭据写入本地用户目录，并输出登录成功、目标平台地址、服务账号名称及其**资源归属人**（后者即此后 `deploy` 出的应用 owner）。（↔DEV-04 界面表 login / DEV-01 ①「login 与 skills sync 仅验 key 有效」/ 伴生 B.2 CLI 行）
- **AC-07** — THE SYSTEM SHALL 把 CLI 凭据存放在本地用户目录、以属主可读写的文件权限保存，不落当前工程目录，且不进入 `deploy` 上传包（AC-32）；密钥可经交互式隐藏输入或环境变量传入，不强制以命令行参数明文传递。（↔DEV-01 ④ / 验收 4）
- **AC-08** — WHEN `login` 成功, THE SYSTEM SHALL 自动执行一次 `skills sync`（AC-14），开发者无需再手动敲；IF 该次自动 sync 失败, THEN THE SYSTEM SHALL 保持登录成功、输出失败原因并提示可手动重跑 `skills sync`。（↔DEV-04 界面表 login / 验收 11；DEV-03 规则）
- **AC-09** — IF 密钥持有 `delegate` 位, THEN THE SYSTEM SHALL 在 `login` 即拒绝：不写入凭据、错误明确指向「这把 key 配置为委托专用，本地开发请另发一把」；THE SYSTEM SHALL NOT 静默按服务账号身份继续（不得表现为登录成功），也不得只返回一个参数类错误码。（↔DEV-02 ④ / 验收 10；DEV-01 ① / 验收 10；INV-31）
- **AC-10** — IF `login` 使用的密钥无效 / 已撤销 / 已过期、目标平台不可达、或目标平台未部署开放能力层, THEN THE SYSTEM SHALL 拒绝登录并输出原因；**可区分的粒度是这三组**（密钥类失效 / 平台不可达 / 未部署开放能力层），组内不细分——F049 已落码把「不存在、已撤销、已过期」收进同一个 `26002`（一码一文案，服务端不给区分信号），CLI 不得臆造区分；未勾选任何权限位的有效密钥 SHALL 可正常 `login` 与 `skills sync`。（↔DEV-01 验收 5）
- **AC-11** — WHEN 已登录后密钥被撤销、到期、或所属服务账号被停用 / 删除, THE SYSTEM SHALL 使此后任一需要平台交互的命令报鉴权失败并提示重新 `login`（生效上界同凭据底座 5 秒）。（↔DEV-04 验收 1 / DEV-01 验收 2、7）
- **AC-12** — THE SYSTEM SHALL 支持同一台机器对多个平台地址分别 `login`：凭据按平台地址隔离保存、互不覆盖；命令默认作用于最近一次 `login` 的平台，并可显式指定目标平台；对同一平台重复 `login` 覆盖旧凭据。（§3 边界）
- **AC-13** — THE SYSTEM SHALL 使持 `delegate` 位的密钥在 CLI 侧的 `login` 即拒（AC-09）；「登录后才被编辑加上 `delegate`」的历史 key 在 `deploy` / `logs` 的服务端入口按权限位被拒由 **F055 AC-04** 承接（INV-31 落点），CLI 把该拒绝原样呈现、拒绝形状同 AC-09、不得静默落回模式 S。（↔INV-31「三面在通道入口按权限位直接拒绝」）

### 2.3 `skills sync` 与 DEV-03 两包技能包

- **AC-14** — WHEN 执行 `bisheng skills sync`, THE SYSTEM SHALL 从已登录平台拉取平台**当前版本**的两包技能包到本地用户目录、幂等可重复；重复执行以平台当前版本覆盖更新本地内容（平台升级后重跑即更新到新版本），并输出每包的名称、版本与更新结果。（↔DEV-03 规则「版本对齐」/ 验收 1、4；DEV-04 验收 11）
- **AC-15** — THE SYSTEM SHALL 使技能包内容随平台版本一同发布、由平台端点分发（无公网依赖），且平台内任何消费者（含后续造应用引擎）与 CLI 拉取的是同一份内容，不维护第二份。（↔DEV-03 规则「内外同源」/ 验收 2；§4 决议-4）
- **AC-16** — THE SYSTEM SHALL 使「部署纳管」包包含：`bisheng-app.yaml` 的写法（形态由 F055 定义，AC-30；含名称 / 描述 / 图标 / `runtime` / 端口 / 档位、**应用数据表结构声明**与**出站域名白名单**两项的写法，引用 F055）、能力声明写法、安全红线（禁写鉴权 / 连接串 / 密钥；密钥用环境变量引用而非硬编码）、托管运行契约（平台托管提供什么 / 应用不得自带或依赖什么，DEV-04 契约表）、`deploy` 工作流与预检排障指引（声明补全 → deploy → 预检修复 → 审批状态跟踪）。（↔DEV-03 表「部署纳管」/ DEV-04 托管运行契约）
- **AC-17** — THE SYSTEM SHALL 使「平台能力接线」包由本 Feature 交付其**包结构与两条不走 SDK 的标准库接法**——模型（官方 OpenAI 兼容客户端 + 平台注入的 base URL 与凭据、模型名即模型管理原名、无逻辑档位转换）、应用数据库（标准库连平台注入的连接环境变量、加列自动 / 改删列须确认的结构演进策略）；**SDK 三件套用法章节**——auth（读平台注入身份即得用户、**禁止自建登录页**）、retrieve（检索用法与 per-user 过滤语义）、storage（附件存取）——在 F057 交付后补齐、其验收随 F057。其中 auth 一节的「显著标注」按可判定形式落地：**独立成章、章首置顶警示块（点明唯一「写错了应用照样跑起来、只是身份是错的」静默失败点）、且列在包首页目录第一条**。（↔DEV-03 表「平台能力接线」/ DEV-07 / RT-05）
- **AC-18** — THE SYSTEM SHALL 使每包由 SKILL.md、可运行样例与连通自检脚本组成（「部署纳管」包三件由本 Feature 交付；「平台能力接线」包的样例与自检脚本中涉及 SDK 的部分随 F057 补齐、验收随 F057）；WHEN 自检脚本在已配好的环境执行, THE SYSTEM SHALL 通过；WHEN 缺少配置（未 `login` / 未 sync / 缺权限位 / 平台不可达）, THE SYSTEM SHALL 输出可读的失败原因而非堆栈；样例与脚本中不出现任何真实密钥（占位符或环境变量引用）。（↔DEV-03 验收 1；NFR-2）
- **AC-19** — THE SYSTEM SHALL 使两包的触发描述以通用意图表述（如「将本地项目部署 / 发布到企业的应用平台」）、不绑定产品名；目标平台实例由 `login` 凭据与 sync 来源决定、与名称无关。（↔DEV-03 规则「触发描述不绑产品名」/ 验收 5）
- **AC-20** — THE SYSTEM SHALL 使本地技能目录的布局可被非 Claude Code 引擎经 AGENTS.md 引用同一目录（sync 完成后输出引用方式指引）。（↔DEV-03 验收 3）
- **AC-21** — WHEN 本地技能包文件已被开发者修改, THE SYSTEM SHALL 在 sync 时仍以平台版本覆盖，并在输出中列出被覆盖的文件（技能包是平台发布物，不做本地合并、不保留本地改动）。（§4 决议-8）
- **AC-22** — THE SYSTEM SHALL 使技能包在评测样本上达到：① 触发——**≥ 10 条**不含产品名的中性部署表述（如「把这个应用部署到公司的应用平台」）作为样本，「部署纳管」包触发率 **100%**（本 Feature 验收）；② auth 静默失败点——**≥ 5 个**「未读包 vs 读包」对照样本，读过「平台能力接线」包后 agent 生成的应用不自建登录页与鉴权逻辑、改读平台注入身份的比例 **100%**（该章随 F057 补齐，此项验收随 F057）。（↔DEV-03 验收 5、6 / DEV-05 验收 4；NFR-1.3）

### 2.4 `dev` 本地运行与身份注入

- **AC-23** — WHEN 执行 `bisheng dev`, THE SYSTEM SHALL 按 `bisheng-app.yaml` 声明的启动信息与端口拉起应用进程，并在其前置一个内置迷你代理作为唯一本地访问入口；代理向应用注入与托管运行期（F054 app-proxy）**结构一致**的身份头（含主体类型 = 服务账号）与**每请求的短时访问凭据句柄**（结构同 F054 AC-34，由迷你代理以当前 `login` 密钥换取或本地签发，login 密钥本身不进入应用进程），身份 = 当前 `login` 密钥所对应的服务账号；应用读注入头 / SDK auth / SDK retrieve 的代码与线上零差异。（↔DEV-05 需求表 / 验收 1；INV-32 候选）
- **AC-24** — THE SYSTEM SHALL 在 `dev` 输出中明示当前注入身份的来源与账号（服务账号名、目标平台地址）以及本地访问地址，避免开发者误以为在以他人身份运行。（↔DEV-05 界面与交互）
- **AC-25** — THE SYSTEM SHALL 使 `dev` 不提供 `--as` 或任何指定其他用户身份的入口；迷你代理在转发前剥离客户端携带的任何平台身份注入头（剥离规则与 F054 一致：按下划线 / 连字符 / 大小写归一化等价类匹配），伪造头对应用无效。（↔DEV-05 ① / 验收 2；§5.1；INV-32 候选）
- **AC-26** — WHEN `dev` 启动, THE SYSTEM SHALL 提供一个本地 SQLite 应用数据库并以与托管运行期**同名**的连接环境变量注入应用进程；数据在 `dev` 重启间保留、位于项目本地且不进入 `deploy` 上传包（AC-32）。（↔DEV-05 ③ / DEV-07 appdb；F054 AC-44）
- **AC-27** — THE SYSTEM SHALL 向应用进程注入与托管运行期同名的一组平台接线环境变量（模型协议面 base URL 与凭据、平台地址、应用标识、附件存储句柄〔本地期指向项目本地附件目录，SDK storage 同一 API〕等，清单与 F054 / F057 对齐），使技能包与 SDK 教的写法本地线上零差异；SDK auth / retrieve / storage 所需的访问者凭据只经每请求注入（AC-23），不以进程级环境变量提供。（↔DEV-07「刻意不进 SDK 的两样」/ DEV-05 一句话）
- **AC-28** — WHILE `dev` 运行, WHEN 应用经 SDK / MCP / 模型协议面调用平台能力, THE SYSTEM SHALL 使其按该服务账号**被显式授予**的范围放行（经 F052 / F051 面执行，过滤强度与 fail-closed 行为与线上一致）；权限引擎不可用时得到明确错误而非未过滤或部分过滤的结果；`dev` 迷你代理只注入身份与环境、不代理这些调用。（↔DEV-05 ③ / 验收 3；NFR-1.4；§4 决议-3）
- **AC-29** — IF 未 `login`、凭据无效或目标平台不可达, THEN THE SYSTEM SHALL 拒绝启动 `dev` 并提示先 `login`；`dev` 本身不校验权限位（同 `login`）；WHEN 运行中密钥被撤销, THE SYSTEM SHALL 使后续平台能力调用被拒（AC-11），本地注入身份不因此变化，重启 `dev` 时被拒。（§4 决议-9）

### 2.5 `deploy`（命令侧）

- **AC-30** — THE SYSTEM SHALL 以项目根的 `bisheng-app.yaml` 为发布输入，并**按 F055 定义的对外形态**（名称 / 描述 / 图标 / `runtime` / 端口 / 档位 / 能力声明 / 应用数据表结构 / 出站域名白名单；必填 / 可选与缺省值均以 F055 为准，允许「只导入不集成」的最小声明）打包与本地校验必填项，**不自定义任何字段**；权威校验在 F055 托管预检。IF 文件缺失或必填项缺失 / 不合法, THEN THE SYSTEM SHALL 在本地拒绝、指出缺失项、不上传。（↔DEV-04 规则「发布输入以 bisheng-app.yaml 为准」；release-contract 表 1 AppManifest；§4 决议-5）
- **AC-31** — WHEN 执行 `bisheng deploy`, THE SYSTEM SHALL 把当前项目按忽略规则（AC-32）打包为一份版本快照、上传平台并触发发布管线（经 F055）；上传前先完成 AC-30 的本地校验与 AC-33 的目标应用确认输出。（↔DEV-04 流程 / 界面表 deploy；§4 决议-2）
- **AC-31a** — WHILE `deploy` 进行中, THE SYSTEM SHALL 逐阶段输出结果：发布前安全扫描 → 托管预检 → 审批单生成（**扫描先于预检**，见文末决议；CLI 只按服务端实际推进的阶段顺序呈现，不得把顺序硬编码成断言）；IF 任一阶段失败, THEN THE SYSTEM SHALL 终止、输出该阶段的可读原因（AC-35 / AC-36）并以非零退出码结束。（↔DEV-04 流程 ①–③）
- **AC-31b** — THE SYSTEM SHALL 使 `deploy` 默认在审批单生成（待审）后返回，输出审批单标识与状态跟踪方式（应用详情页 · 发布 / MCP 应用状态工具 / `deploy --wait`）。（↔DEV-04 流程 ③ / DEV-02 ③；§4 决议-10）
- **AC-31c** — WHERE 带 `--wait`, THE SYSTEM SHALL 持续输出直至审批终态与上线结果之一出现并据此结束：通过并上线（输出入口地址）/ 待上线（资源不足，提示 owner 手动上线路径）/ 驳回（输出理由全文）/ 撤回；四种终态各有可区分的退出码。（↔DEV-04 流程 ③④ / RT-03 ⑤⑥；§4 决议-10）
- **AC-32** — THE SYSTEM SHALL 在打包时遵守忽略规则：默认排除版本控制元数据、依赖安装目录、本地 SQLite 数据文件、本地附件目录与 CLI 凭据，并遵守项目的 `.gitignore` 类忽略文件；IF 上传体量超过部署配置的上限, THEN THE SYSTEM SHALL 拒绝并提示当前体量与忽略建议，不上传。（§3 边界；§4 决议-2）
- **AC-33** — WHEN 首发 `deploy` 成功进入管线, THE SYSTEM SHALL 输出平台分配的应用标识与入口地址（只读信息；二维码不在 CLI 提供、去应用详情页取，§4 决议-12）；此后 `deploy` / `logs` 以该应用标识关联同一应用（标识由 CLI 随项目保存、可显式指定，不要求开发者手写），迭代 `deploy` 上传前输出目标应用的名称与标识；同租户内应用同名不构成冲突。（↔F054 AC-01 / AC-08；§4 决议-6）
- **AC-34** — IF 密钥未持 `app:manage` 位, THEN THE SYSTEM SHALL 拒绝 `deploy`（首发与迭代同此；服务端按位拒绝、经 F049 鉴权依赖，服务端判定见 F055 AC-04），CLI 输出明确指出缺该位、请租户管理员编辑密钥；该判定与资源归属人有无「创建应用」角色权限、其角色是否被调整、其账号是否被停用**无关**。（↔GOV-07 ② / 验收 2、3；DEV-04 规则「准入闸」；伴生 B.2）
- **AC-35** — IF 托管预检失败（依赖平台不提供的中间件、应用包声明不合法、启动探活失败）, THEN THE SYSTEM SHALL 输出缺失项与改造指引（经 F055 返回），且不生成审批单；IF 发布前安全扫描命中, THEN THE SYSTEM SHALL 输出命中规则与文件位置、**不含密钥值本身**，本地修复后可重新 `deploy`。（↔DEV-04 流程 ①② / 验收 2、4；DEV-01 验收 8；NFR-2）
- **AC-36** — WHEN 管线报告本次迭代包含改 / 删列的结构变更, THE SYSTEM SHALL 在未获显式确认时终止、不生成审批单；确认方式为交互式确认或 `--confirm-schema-change`（非交互环境未带该参数视为未确认）；获确认后继续进入管线，迁移前自动留生产数据快照由 F055 承诺。（↔DEV-04 流程 ① / 验收 10；RT-05）
- **AC-37** — IF 同一应用存在在途审批单, THEN THE SYSTEM SHALL 拒绝再次 `deploy` 并提示在途单与撤回路径（应用详情页 · 发布）。（↔DEV-04 流程 ③ / 验收 5）
- **AC-38** — IF 用资源归属人不同的密钥 `deploy` 既有应用, THEN THE SYSTEM SHALL 拒绝并在提示中说明该应用归属谁（经 F054 AC-07）；首发 `deploy` 的应用 owner = 该密钥所属服务账号的资源归属人，不因任何请求头改变。（↔DEV-04 规则「谁 deploy 上去的就归谁」/ 验收 9；F049 定义 6）
- **AC-39** — *（已删除，2026-08-17 审查裁定 2：原文全为 F055 服务端行为的复述——每次发布必审、扫描同规则集、元信息与档位随 deploy 更新——旅程一致性以一句「经 F055 验证」并入 AC-50；编号保留不复用）*
- **AC-40** — WHERE 工场运行时层未部署, THE SYSTEM SHALL 使 `deploy` 与 `logs` 被拒并提示「本环境未启用应用工场」，不返回未定义错误；`login` / `skills sync` / `dev` 只依赖开放能力层、不受工场运行时层开关影响。（↔GOV-10 三层部署形态）

### 2.6 `logs`

- **AC-41** — WHEN 执行 `bisheng logs`, THE SYSTEM SHALL 输出目标应用的运行日志（可查看最近一段、可按时间范围、可持续跟随新日志）；仅对当前密钥资源归属人 owner 的应用放行、需 `app:manage` 位；内容范围与权限口径与应用详情页运行日志（F054 WB-13）、MCP 应用状态 / 日志工具（F052）**完全一致**（内容范围一致，同 F054 AC-23）。（↔DEV-04 界面表 logs / 日志三入口表 / 验收 12；伴生 B.2）

### 2.7 接入信息区（DEV-01 ⑤）

- **AC-44** — WHERE 开放能力层已部署, THE SYSTEM SHALL 在服务账号详情页「API 密钥」tab 顶部展示接入信息区：MCP Server 地址（F052）、OpenAI 兼容 base URL（F051）、CLI 安装包下载链接（AC-01；是链接不是文件——管理员转发链接、开发者自行下载）、`bisheng login` 指引（含平台地址与命令示例、密钥以占位符表示）；WHERE 未部署, 该区不出现，服务账号模块其余部分不受影响。（↔DEV-01 界面表「接入信息区」/ ⑥；GOV-10 验收 4；F049 AC-49）

- **AC-46** — WHEN 开发者拿到一键复制的接入信息文本与单独转交的 key 值, THE SYSTEM SHALL 使其据此完成 `bisheng login` 并调通一次 MCP 工具（经 F052）。（↔DEV-01 验收 9）

- **AC-53** — IF `bisheng-app.yaml` 缺失或必填项缺失 / 不合法, THEN THE SYSTEM SHALL 拒绝启动 `dev` 并列出缺失项（校验口径同 AC-30、形态以 F055 为准）。（↔DEV-05 需求描述；补 §2.4 缺口）

## 3. 边界情况

> 只写期望的对外行为；实现层的落点、缓存与文件布局细节见 design.md §5。

- **凭据文件是「属主可读」的本地资产，不是工程资产**：只在本地用户目录、以属主可读写权限保存（Windows 上以等价的用户级访问控制实现）；任何命令不把它写进工程目录，`deploy` 打包结构性排除它（AC-07 / AC-32）。同一机器多个平台的凭据按平台地址隔离，命令默认最近一次 `login` 的平台、可显式指定（AC-12）——凭据不「合并」、不「切换全局状态」。
- **主要操作者是 agent、不是人**：每个命令都必须在无 TTY 下可用（AC-04）；凡有交互确认的地方（`--confirm-schema-change`、覆盖确认等）都有参数等价物；错误信息给「缺什么 / 怎么改」而非堆栈——这是 DEV-04 验收 7「全程不离开本地对话」成立的前提。未 `login` 直接跑命令同样要给出「先 login」的确定提示与非零退出码（AC-51），而不是网络错误。
- **离线 / 纯内网零公网依赖**：安装件、技能包、版本信息全部由平台自身分发（AC-01 / AC-15）；CLI 自身不访问任何公网地址；应用依赖包在构建期经平台内网镜像安装是 F054 / F055 的契约，CLI 只在预检失败时把原因原样呈现。**版本对齐靠「从自家平台拉」天然成立**，不靠公网 registry。
- **`deploy` 上传体量与忽略规则**：默认排除版本控制元数据、依赖安装目录（依赖由平台构建期安装）、本地 SQLite 数据文件、CLI 凭据，并遵守项目 `.gitignore` 类文件；超上限拒绝并提示（AC-32）。上限是部署配置项（默认值见 design）。密钥扫描**不在 CLI 侧复制一份**——服务端一次、同一规则集，避免两套规则漂移；CLI 只保证自己的产物不进包。
- **密钥被吊销 / 过期 / 服务账号停用后的命令行为**：任一需平台交互的命令报鉴权失败并提示重新 `login`（AC-11）；运行中的 `dev` 不会崩——本地注入身份不变，但后续平台能力调用被拒，重启 `dev` 时被拒（AC-29）；本地凭据文件不自动删除（重新 `login` 覆盖即可）。
- **`skills sync` 覆盖本地改动**：技能包是平台发布物，sync 是平台 → 本地的单向覆盖，本地改动会被覆盖并在输出中列出（AC-21）；开发者的自定义应放在技能目录之外（如自己的 AGENTS.md 引用），不改平台包。
- **平台升级后 CLI 版本不匹配**：命令执行前比对；不兼容即拒绝并给出从当前平台重新下载的链接，兼容但落后仅提示（AC-02）；`skills sync` 与安装件的版本都以「登录的那个平台」为准，同机多平台各自对齐。
- **`dev` 注入的是服务账号，本地看不到 per-user 差异（DEV-05 ②）**：本地不存在「真实访问者」，张三 vs 李四的差异本地无从复现，与提不提供模拟开关无关；验证路径 = 发布后用真实账号访问（AC-49）。由此本地能检索到的知识库 ⊆ 该服务账号被授予范围，可能**窄于**线上真实用户——开发期只会「本地看得少」，不会「本地能跑、线上越权」（AC-28）。
- **`delegate` 的三处拒绝形状一致**：CLI `login`（本 Feature，AC-09）、`deploy` / `logs` 的服务端入口（F055 AC-04，CLI 原样呈现，AC-13）、以及 F051 / F052 两面——一律「按权限位在入口直接拒绝、错误指向委托专用」；**不得**表现为按服务账号身份正常执行（静默落回模式 S），也不得只回参数错误码（INV-31）。签发侧的互斥硬阻断随 F050，运行期拒绝是对历史 key 的兜底。
- **两个部署开关的组合矩阵**：`login` / `skills sync` / `dev` 只依赖开放能力层；`deploy` / `logs` 同时依赖工场运行时层（AC-05 / AC-10 / AC-40）。未部署开放能力层 → 三个分发 / 校验入口不存在、接入信息区不出现、CLI 给可读原因；仅部署开放能力层 → 前三个命令可用、后两个提示「本环境未启用应用工场」。CLI 不得对「端点不存在」返回未定义错误。
- **`deploy` 与本地改码解耦**：提交后本地继续改码不影响已提交的版本快照（下次 `deploy` 才生成新版本，RT-03）；在途审批单存在时再次 `deploy` 被拒，撤回只能在应用详情页 · 发布做（AC-37）——CLI 不提供撤回命令。
- **应用标识的解析与误投风险**：标识由 CLI 随项目保存、可显式指定（AC-33）；项目被复制到另一目录或标识丢失时须显式指定；指定了归属人不同的应用会被归属校验拒绝（AC-38），但指定了**同一归属人的另一个应用**会真的更新那个应用——因此迭代 `deploy` 上传前必须输出目标应用名称与标识（AC-33），非交互模式下这是唯一的护栏。
- **CLI 与平台的全部交互都在凭据校验之后**：本 Feature 新增的平台侧端点（技能包分发、login 校验、`deploy` / `logs` 消费的 F055 / F054 端点）与既有开放 API 走 F049 同一条凭据校验路径（INV-27）；唯一匿名可达的是安装件下载与版本信息（AC-01），它不含任何业务数据或平台内部信息（落点见 §4 决议-11）。商业版前置网关的部署形态下上述交互同样须可达（design 落点）。
- **接入信息不机密、key 机密**：一键复制文本可随时重发、不限次数、不含 key 或可换取 key 的凭据（AC-45）；key 只有签发时一次、由管理员单独转交（F049 AC-02 / AC-45）。技能包样例与 `dev` 输出同样不出现真实密钥（AC-04 / AC-18）。
- **`bisheng-app.yaml` 只有一个定义方（F055）、三个消费方（F053 CLI / F054 运行时 / 「部署纳管」包）**：CLI 本地只做「存在 + 必填 + 可解析」级校验（AC-30 / AC-53），权威校验在 F055 托管预检；CLI 与技能包都不得自定义字段或缺省值，否则开发者会遇到「本地过、上传被拒」或「技能包教的写法预检不认」——三处同源是 spec 级要求而非实现巧合（release-contract 表 1 AppManifest）。

## 4. 待澄清决议

> 2026-08-17 用户授权全自动模式：以下各项按建议直接定案，记录理由与备选供追溯；spec 评审（`/sdd-review`）后如有 high 级发现再增补。Discovery §4.2 次级决策清单中「CLI 安装包形态（wheel + 内网镜像 vs 单文件二进制，F053）」在此定案。

- **[决议-1] CLI 安装件形态 = Python wheel + 平台自身分发端点；单文件二进制作为 v3.1 备选。** 理由：全仓无任何可发布包工程（Discovery §2.9），wheel 是最低成本、跨平台、可同时放进平台内网 pip 镜像与直接下载的形态；目标用户是会用 coding agent 的业务技术员，Python 环境常备；MVP-114 纵切明确「wheel + 下载端点」。代价：开发者机器需 Python 运行时。**何时重新考虑**：客户反馈安装门槛（无 Python 的 Windows 终端）成为主要阻碍时，补单文件二进制、下载端点按平台 / 架构分发。
- **[决议-2] `deploy` 走 HTTP 上传版本快照（打包上传），不走 git push；忽略规则 = `.gitignore` 类文件 + 内置排除；密钥扫描只在服务端做一次。** 理由：平台无 git 服务端、CLI 应用不要求是 git 仓库（存量项目直接导入，§1.3 前提 1）；快照语义与 RT-05「只增不改的版本记录」一致；git push 需自建 git 服务与鉴权改造、体量与收益不匹配。CLI 侧不复制扫描规则集——同一规则集分两处必漂移，且发布前扫描是 F055 与平台内发布同门的承诺；CLI 只结构性排除自己的产物（凭据 / 本地 sqlite）。**何时重新考虑**：PRD-2 引入平台内代码托管后可加 git 通道，但 `deploy` 语义不变。
- **[决议-3] `dev` 迷你代理只注入身份头与同名环境变量，不代理平台能力调用。** 理由：与线上同构——托管运行期 app-proxy 也只注入身份与访问凭据句柄，应用经 SDK / 标准库直连平台能力面（F051 / F052），不经代理转发出站；若 CLI 代理能力调用，等于在本地复制一层能力路由与过滤逻辑，与 INV-36「检索门面单一路径」相悖。代价：`dev` 需注入使 SDK 与标准库接法可用的凭据与地址（同名环境变量，AC-27），凭据即当前 login 的密钥、权限 = 该服务账号被授予范围。
- **[决议-4] 两包技能包随平台版本打包在后端发布件内、由后端端点分发，`skills sync` 从该端点拉取。** 理由：版本对齐天然成立（拉哪个平台就是哪个版本）、零公网依赖（信创 / 内网硬要求）、内外同源只有一份（未来造应用引擎读同一份，DEV-03 验收 2）。备选 = 独立仓库或公网 registry：内网不可达、版本必漂移，否决。**何时重新考虑**：技能包更新节奏显著快于平台版本时，可加「平台侧热更新技能包」但分发端点与同源原则不变。
- **[决议-5] `bisheng-app.yaml` 的对外形态由 F055 拥有（release-contract 表 1 候选 AppManifest），本 Feature 只消费：CLI 按 F055 定义的形态打包与校验必填项、`dev` 据此启动、「部署纳管」包只教写法并引用 F055 的定义，三处均不自定义字段与缺省值。** 理由（2026-08-17 审查裁定 1，替代初稿「对外形态归本 Feature」）：发布输入的权威 = 管线校验方——预检拒不拒是 F055 说了算，写法若由 F053 定义就会出现「技能包教的写法预检不认」；F055 spec 范围边界 RT-04 段已把名称 / 描述 / 图标 / `runtime` / 端口 / 档位 / 能力声明 / 应用数据表结构 / 出站域名白名单九项收进其对外形态。本 Feature 保留的诉求只有一条：最小声明必须允许「只导入不集成」的存量应用零集成导入（§1.3 前提 1），由 F055 的必填集承接。**何时重新考虑**：无——owner 归属已由 release-contract 表 1 登记，变更须先改表 1。
- **[决议-6] 应用标识由 CLI 在首发后随项目保存、后续 `deploy` / `logs` 据此关联；可显式指定覆盖；不要求开发者手写进 manifest。** 理由：F054 定应用标识首发确定、不可改、名称可重（AC-01 / AC-08），靠名称关联不可行；让开发者手写标识易错且首发前不存在。迭代 `deploy` 上传前输出目标应用名称与标识作为误投护栏（AC-33 / §3）。保存位置与文件形态属 design。
- **[决议-7] CLI 版本策略：与平台版本同号发布，命令执行前比对；不兼容即阻断并提示从当前平台重新下载，兼容但落后仅提示。** 理由：`/api/v1/env` 的版本字段不可靠（CLAUDE.md §7 已知陷阱）、CLI 须有自己的兼容判定；阻断优于「看起来能跑、行为悄悄不对」。兼容判据（主 / 次 / 补丁）与探测方式属 design。
- **[决议-8] `skills sync` 对本地改动单向覆盖并列出被覆盖文件，不做三方合并、不做覆盖前确认。** 理由：技能包是平台发布物而非用户资产；合并会让本地包偏离平台版本、验收 2「内外同源」失效；覆盖前确认对 agent 调用不友好（`login` 自动触发的 sync 尤其如此）。开发者的自定义放技能目录之外。
- **[决议-9] `dev` 命令本身不校验权限位（同 `login` / `skills sync`），只验密钥有效；应用在 `dev` 期查组织身份仍按 `identity:read` 判（F052）。** 冲突来源：PRD-1 DEV-01 ① 映射表 CLI 列在 `identity:read` 行写「dev 身份注入」，而伴生 PRD 附录 B.2（权限位清单的权威出处）CLI 行只列 `login` / `skills sync`（不验位）、`deploy` / `logs`（`app:manage`），未列 `dev`。裁决：`dev` 注入的是服务账号**自身**身份、属「读自己」，不消费高危的全租户组织架构可读位；若 `dev` 准入要求 `identity:read`，则每把开发者 key 都被迫携带高危位，与 DEV-02 ②「边界由给不给位承担」背道而驰。PRD-1 该表述理解为「dev 期应用若查组织身份须持该位」。**已回修（2026-08-17）**：PRD-1 DEV-01 ① 表 CLI 列 `identity:read` 行已改为「—（dev 注入的是服务账号自身身份、不验位）」，两册与本 spec 一致。
- **[决议-10] `deploy` 默认跟踪到「审批单已生成（待审）」即返回；`--wait` 持续跟踪至审批终态与上线结果（AC-31b / AC-31c）。** 理由：审批是人工动作、可能跨天，默认阻塞对 agent 与终端都不友好；PRD 把审批状态跟踪的主路径定为 MCP 应用状态工具（DEV-02 ③ / DEV-04 验收 7）；MVP-114 纵切上 F052 不在首波，`--wait` 承接演示剧本中「审批通过 → 上线」的等待与结果输出（mvp-114-path §2「轮询状态并输出预检 / 扫描 / 审批结果」）。
- **[决议-11] 安装件下载端点匿名可达（不要求密钥或登录态），随开放能力层开关存在，不进 `/api/v2` 命名空间。** 理由：安装件与版本信息不机密（DEV-01 ⑤「接入信息不机密、可随时重发」）；管理员转发链接、开发者在拿到 key 前就可安装是 PRD 明写的场景（「是链接不是文件」）；INV-27 约束的是 `/api/v2/**` 业务端点，静态发布件不在其列——但为不制造「`/api/v2` 下有匿名端点」的例外，端点放在该命名空间之外（落点属 design）。
- **[决议-12] CLI 首发成功后打印入口地址（只读 URL），不提供二维码；二维码仍去应用详情页 · 发布取。** 理由：PRD-1 §2.2「哪些操作必须去界面上做」表把「取入口链接与二维码」列为无命令行等价物的操作，但入口地址是 F054 AC-25 定义的、版本无关的只读信息，`deploy` 结果里打印它对开发者与 agent 都是零成本的无害扩展（不新增命令、不改任何状态、不承载分发面）；二维码属界面产物，CLI 不生成也不下载。**何时重新考虑**：产品明确要求 CLI 完全不呈现入口地址时删掉该输出即可，不影响其它 AC。
- **[决议-13] `deploy` 的两道门顺序定为「发布前安全扫描 → 托管预检」，与 PRD-1 DEV-04 字面列举的顺序相反（AC-31a）。** 理由：①扫描的输入是**源码包**，不依赖构建产物，而预检要真起一次构建与探活（分钟级）——含裸密钥的包不该先烧这份算力；②失败更快 = 开发者一次 `deploy` 的反馈时延更短，而扫描命中是新手最高频的失败；③DEV-04 的四步是**逻辑分组**（说清"要过哪几道门"），AC 层只约束「两道门都过、任一失败都不进审批」，未把顺序写成契约。**这是对 PRD 字面顺序的一处自觉偏离，已按 SDD-Guide 偏离再确认规则登记。** 影响面：F055 design D5 同批订正、F055 `STAGE_LABELS` 与 README 阶段文案随之调整；CLI 侧**不得把阶段顺序硬编码成断言**，只按服务端推进的阶段依次呈现（这样将来再调顺序 CLI 零改动）。**何时重新考虑**：若预检里出现"必须先构建才能取到的扫描对象"（如扫描镜像层而非源码），顺序须换回来。
