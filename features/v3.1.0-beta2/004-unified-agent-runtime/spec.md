# Feature: 日常对话与深度研究统一（F004-unified-agent-runtime）

> **本文档定位 — 纯 What。** 只写做什么、验收标准、不做什么。所有 How 写在 [design.md](./design.md)。

**关联 PRD**: 无独立 PRD。需求来自 2026-11-17 的需求讨论，用户已确认需求发现结论（见本目录 [prototype/index.html](./prototype/index.html) 与 `src/backend/scripts/spike_unified_runtime/README.md`）。
**优先级**: P0
**所属版本**: v3.1.0-beta2
**依赖**: F016-daily-chat-generated-files（v3.1.0-beta1，日常对话生成文件的展示）、F073（开放 API 的深度研究接口）、F132（长期记忆）

> **术语（全文只用这些词）**
> - **会话**：工作台里的一条对话，包含多轮消息。
> - **直接回答**：用户未打开「深度研究」开关时的回答方式。agent 不先列计划。
> - **深度研究**：用户打开「深度研究」开关后的回答方式。agent 先列计划，再按计划执行。
> - **运行**：agent 为回应一条用户消息所做的一次连续工作，从开始到结束、停止或等待用户回答为止。
> - **计划**：深度研究的一次运行里，agent 列出的有序条目清单。
> - **计划条目**：计划里的一行，状态为未开始、进行中、已完成、已取消之一。
> - **插话**：用户在一次运行尚未结束时发出的消息。
> - **工作区**：一个会话里用户上传的文件和 agent 生成的文件的集合。

> **范围边界**
> - **本次纳入**：
>   - 直接回答与深度研究在同一个会话里使用，行为只在“是否先列计划”上不同。
>   - 深度研究的计划可见、可被用户修改；运行期间用户可以插话。
>   - 直接回答获得深度研究已有的能力：agent 向用户提问、使用技能、文件进入工作区。
>   - 文件在生成时即可查看和下载。
>   - 直接回答的响应速度不低于现状。
> - **本次明确排除**：
>   - agent 自行判断是否进入深度研究。原因：用户已决定只由开关控制。
>   - 计划写出后等待用户确认再执行。原因：用户已决定立即执行。
>   - 多个后台任务并行、由主 agent 管理（async subagents）。原因：实测必须部署额外服务，延后评估。
>   - 桌面端 DeepSeek Harness 的任何改动。原因：它的 agent 在客户端运行，不在本特性范围。
>   - 用户在界面上直接拖动、编辑计划条目。原因：本期只通过发消息修改计划。
>   - 定时或外部事件唤醒 agent。原因：超出本期范围。

## 1. 用户故事

**A. 做长任务的业务用户**
作为 **用深度研究做报告、分析、文档的用户**，
我希望 **在 agent 工作时能看到它的计划，并且随时用一句话修改计划或补充要求**，
以便 **不用等几十分钟后才发现方向不对，再从头重做**。

**B. 日常提问的用户**
作为 **在工作台日常提问的用户**，
我希望 **不打开深度研究也能让 agent 生成文件、在信息不足时向我提问、使用技能**，
以便 **简单的事不必切换到一个更慢的模式**。

**C. 通过开放 API 调用深度研究的集成方**
作为 **已经接入开放 API 的系统**，
我希望 **现有的请求和响应保持不变**，
以便 **平台升级后我的集成不需要修改**。

**D. 平台管理员**
作为 **管理员**，
我希望 **额度、并发、内容安全、审计下载这些管控在统一后继续生效**，
以便 **统一不带来管控缺口**。

## 2. 验收标准

### 2.1 同一个会话，两种回答方式

- **AC-01** — THE SYSTEM SHALL 在同一个会话里同时支持直接回答和深度研究，用户每发一条消息都可以切换「深度研究」开关。
- **AC-02** — WHEN 用户在关闭「深度研究」开关的状态下发送消息, THE SYSTEM SHALL 直接开始回答，不显示计划。
- **AC-03** — WHEN 用户在打开「深度研究」开关的状态下发送消息, THE SYSTEM SHALL 先显示计划，再开始执行。
- **AC-04** — WHEN 用户在同一个会话里先用直接回答、后用深度研究（或顺序相反）, THE SYSTEM SHALL 让后一次运行能读到前一次运行的对话内容和工作区文件。
- **AC-05** — WHEN 用户勾选了工具后发送消息, THE SYSTEM SHALL 让 agent 在直接回答和深度研究两种方式下都能调用这些工具。
- **AC-43** — WHEN 用户选择了知识库后发送消息, THE SYSTEM SHALL 让 agent 在两种方式下都能检索这些知识库，检索范围限于该用户有权限的内容。
- **AC-44** — WHEN 用户打开了联网搜索后发送消息, THE SYSTEM SHALL 让 agent 在两种方式下都能联网搜索。
- **AC-45** — WHEN 用户勾选了技能后发送消息, THE SYSTEM SHALL 让 agent 在两种方式下都能使用这些技能。
- **AC-46** — WHEN 用户勾选了代码执行工具后发送消息, THE SYSTEM SHALL 让 agent 在两种方式下都能执行代码并读写工作区文件。
- **AC-47** — WHEN agent 在直接回答的运行里需要用户提供信息, THE SYSTEM SHALL 按 AC-20、AC-21 的方式提问和继续，与深度研究相同。
- **AC-48** — WHERE 长期记忆已开启, THE SYSTEM SHALL 让 agent 在两种方式下都能读取和写入该用户的长期记忆。
- **AC-06** — IF 当前用户没有深度研究的使用权限, THEN THE SYSTEM SHALL 不显示「深度研究」开关，直接回答不受影响。

### 2.2 计划

- **AC-07** — WHEN 深度研究的一次运行开始, THE SYSTEM SHALL 在 agent 写出计划后立即显示全部计划条目，并且不等待用户确认就开始执行第一条。
- **AC-08** — WHILE 深度研究的一次运行在进行, THE SYSTEM SHALL 显示每个计划条目的当前状态，以及“已完成条数 / 总条数”。
- **AC-09** — WHEN agent 改写、增加或取消了计划条目, THE SYSTEM SHALL 在 2 秒内把变化显示出来，未被改动的计划条目保持原有的状态和位置。
- **AC-10** — WHEN 一个计划条目被改写, THE SYSTEM SHALL 在该计划条目上显示改写后的文字，并保留改写前的文字供对照。计划条目上不标注修改来源，用户的插话消息本身就是记录。
- **AC-11** — WHEN 用户刷新页面或重新打开会话, THE SYSTEM SHALL 显示与刷新前一致的计划，包括被改写和被取消的计划条目。

### 2.3 插话

- **AC-12** — WHILE 一次运行在进行, THE SYSTEM SHALL 保持输入框可输入、发送按钮可用。
- **AC-13** — WHEN 用户插话, THE SYSTEM SHALL 立即在会话里显示这条消息，并在消息下方显示“已发送，排队处理中”。
- **AC-14** — WHEN agent 读取了一条插话, THE SYSTEM SHALL 让该消息下方的“已发送，排队处理中”消失，不再显示其他状态文字。
- **AC-15** — WHEN 用户插话, THE SYSTEM SHALL 让 agent 在完成当前正在执行的一步操作后、开始下一步之前读到这条消息，不中断当前这一步。
- **AC-16** — WHEN 用户在一次运行里连续发出多条插话, THE SYSTEM SHALL 按发送顺序把它们全部交给 agent，不丢失、不重复。
- **AC-17** — IF 一条插话到达时该次运行已经结束, THEN THE SYSTEM SHALL 把这条消息当作一条新的用户消息，开始一次新的运行。
- **AC-18** — WHEN 插话的内容是修改计划（例如“第 3 步改成做 PPT”）, THE SYSTEM SHALL 让 agent 据此修改计划，已完成的计划条目和已生成的文件保留。
- **AC-19** — WHILE 直接回答的一次运行在进行, THE SYSTEM SHALL 同样接受插话，行为与 AC-13、AC-14、AC-15、AC-16 相同。

### 2.4 agent 向用户提问

- **AC-20** — WHEN agent 需要用户提供信息才能继续, THE SYSTEM SHALL 在会话里显示问题和可选项，并把该次运行标为“等待用户回答”。
- **AC-21** — WHEN 用户回答了问题（点击选项或输入文字）, THE SYSTEM SHALL 从提问处继续该次运行，已完成的计划条目和已生成的文件保留。
- **AC-22** — WHILE 一次运行在等待用户回答, THE SYSTEM SHALL 不占用该用户或其部门的并发名额。
- **AC-23** — WHERE 请求来自开放 API 的无人值守调用, THE SYSTEM SHALL 不向用户提问，由 agent 自行按最合理的假设继续。

### 2.5 文件与工作区

- **AC-24** — WHEN agent 在一次运行里生成了一个交付文件, THE SYSTEM SHALL 在该文件写完后 5 秒内让用户可以在工作区里预览和下载它，不等待该次运行结束。
- **AC-25** — WHEN 直接回答的一次运行通过代码执行生成了交付文件, THE SYSTEM SHALL 在回答下方和工作区里都显示该文件，并且可以预览和下载。
- **AC-26** — THE SYSTEM SHALL 让一个会话里的每次运行都能读取该会话工作区里已有的文件，包括用户上传的和此前运行生成的。
- **AC-27** — WHEN 用户在文件生成 7 天之后打开会话, THE SYSTEM SHALL 仍然可以预览和下载该文件。
- **AC-28** — IF 一个文件的访问者不是会话本人、也不具备审计权限, THEN THE SYSTEM SHALL 拒绝预览和下载。

### 2.6 停止、失败与恢复

- **AC-29** — WHEN 用户点击停止, THE SYSTEM SHALL 在 5 秒内结束该次运行，保留已完成的计划条目、已生成的文件和已输出的文字。
- **AC-30** — WHEN 用户在一次运行被停止或失败之后发送新消息, THE SYSTEM SHALL 在同一个会话里继续，agent 能读到此前的对话内容、计划和工作区文件。
- **AC-31** — WHEN 用户在一次运行进行中关闭页面或断网，之后重新打开会话, THE SYSTEM SHALL 显示该次运行在此期间产生的全部内容，并继续显示后续进展。
- **AC-32** — IF 一次运行因为模型或工具错误而失败, THEN THE SYSTEM SHALL 在会话里显示失败原因和可用于排查的编号，并保留失败前的全部内容。
- **AC-33** — WHEN 部署由多个服务节点组成, THE SYSTEM SHALL 让 AC-12 至 AC-32 的行为不依赖于用户的请求落在哪个节点。

### 2.7 响应速度

- **AC-34** — WHEN 用户在直接回答方式下发送一条不带附件的消息, THE SYSTEM SHALL 让“收到请求到向模型发出请求”的时间中位数不超过 0.3 秒、90 分位不超过 1.5 秒。统一前在 114 上的测量值是中位数 0.16 秒、90 分位 1.34 秒（11 个请求）。模型自身的首 token 时间不计入本条。
- **AC-35** — WHEN 用户在深度研究方式下发送消息且有空闲的执行名额, THE SYSTEM SHALL 在 3 秒内显示“已开始”的可见反馈（思考内容或第一步操作）。统一前 114 上模型首 token 的 90 分位是 2.15 秒。
- **AC-51** — WHEN 用户发送一条带附件的消息, THE SYSTEM SHALL 在 2 秒内显示“正在读取附件”的可见反馈，并在读取完成后继续回答。
- **AC-36** — IF 深度研究没有空闲的执行名额, THEN THE SYSTEM SHALL 显示排队位置，轮到时自动开始。

### 2.8 管控与兼容

- **AC-37** — THE SYSTEM SHALL 对直接回答和深度研究使用同一套额度规则：额度不足时在运行开始前拒绝，并显示额度不足的提示。
- **AC-38** — THE SYSTEM SHALL 对用户输入和 agent 输出继续执行内容安全检测，插话的内容同样受检测。
- **AC-39** — THE SYSTEM SHALL 保持开放 API 现有日常对话接口和深度研究接口的请求格式、响应格式和状态含义不变。（2026-11-20 扩到日常对话：开放 API 日常对话也迁到统一运行时，见 design 决策 14）
- **AC-40** — WHEN 用户打开统一之前创建的会话（包括旧的日常对话和旧的深度研究任务）, THE SYSTEM SHALL 正常显示其消息、计划、结果和文件，并允许在该会话里继续发送消息。
- **AC-41** — WHEN agent 的回答引用了知识库或联网搜索的内容, THE SYSTEM SHALL 在回答里显示引用角标，点击角标可以看到对应来源；同一会话里直接回答和深度研究的角标编号不重复。
- **AC-49** — WHEN 知识库检索结果里包含图片且模型支持读图, THE SYSTEM SHALL 让 agent 在两种方式下都能读取这些图片的内容。
- **AC-50** — WHEN 用户在统一之前已经有长期记忆, THE SYSTEM SHALL 在统一之后继续使用这些记忆，不需要用户重新建立。
- **AC-42** — THE SYSTEM SHALL 在 MySQL 和 DM8 两种数据库上都满足以上验收标准。

## 3. 边界情况

- 当用户插话的同时 agent 恰好完成最后一步时，系统应保证这条消息要么被本次运行读取，要么触发一次新的运行（AC-17），不允许消息既不被读取也不触发运行。
- 当用户插话要求修改一个已完成的计划条目时，系统应由 agent 决定是重做还是说明无法修改，已生成的文件不自动删除。
- 当用户插话的内容与计划无关（例如问一个新问题）时，系统应由 agent 在当前运行里回答或记下，不因此丢弃计划。
- 当用户在等待回答（AC-20）期间不回答而是发送了其他内容时，系统应把这条内容当作对问题的回答交给 agent。
- 当用户在运行中停止后立刻再次发送消息时，系统应保证不会同时存在同一个会话的两次运行。
- 当两个浏览器标签页打开同一个会话时，两处都应显示相同的计划和消息，任一处的插话在另一处可见。
- 当 agent 在计划中间插入一个新条目时，其后未改动的计划条目应保持各自原有的状态（AC-09）。具体对齐方法见 design.md §5。
- 当直接回答的运行没有产生任何文件时，系统不应为该会话显示空的工作区入口提示。
- 当一次运行等待用户回答超过 7 天时，系统不再保留提问处的进度；用户此后在该会话里发送消息，系统开始一次新的运行，agent 仍能读到此前的对话内容和工作区文件。
