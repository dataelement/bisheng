## 1 结论

869条记录中，正常290、异常579。异常主要是审计正文采集不完整，不是579次模型调用失败。异常记录中557条的模型、接口响应、用量均成功，只有正文采集失败；不应把这些记录改成正常掩盖缺失。

## 3 机制与复现

- ModelAuditRuntime：每API进程独立有界内存队列；跨API/模型请求共享该进程队列，不共享消费能力。
- AuditCapture.output：每个统一接口流式增量独立编码投递，16KiB是单次编码的最大块，而非跨delta累积阈值。几十字节的delta也能成为一个事件。
- BoundedAuditQueue：每个事件至少额外计4096字节成本，事件数和字节预算任一达界即拒绝；单个消费者顺序await consumer(event)。
- Writer/Storage：逐块加密、MinIO写入并回读校验，再SQL持久化；请求正文完整性需要在相应时机核验。大量小事件会放大对象存储和事务次数。
- Capture一旦关键投递失败即停采该请求后续正文，但不影响模型调用和用量；这解释了“模型成功但审计原文不完整”。

本机仅合成数据，真实BoundedAuditQueue/AuditCapture，不连接109/模型/存储：在消费者未获调度的突发输入中，4096事件时拒绝1次，队列成本17137651字节（尚未到64MiB），请求正文102412字节（尚未到16MiB），期望输出4095块、收到4094块，capture_failed=true。该实验验证机制与数据形态，不是线上吞吐测试，也不能据此把所有历史失败都归同一原因。

## 4 调查阶段建议

本节记录调查阶段的备选建议，不代表后续全部实施。用户随后确认正文只在调用结束后交后台持久化；当前实现以 [design.md](./design.md) 0.12 与 [validation-results.md](./validation-results.md) 的“正文延后持久化”章节为准，不采用下文的短时间窗刷出方案，也未新增持久化失败原因枚举。

1. 优先把流式增量按请求有界批量封装，保留原增量边界/顺序；按字节与短时间窗刷出，减少事件、MinIO对象和SQL事务数。不能简单拼成不可还原的大字符串。
2. 后台批量SQL、有限并发写入，同一请求/通道保持顺序；终止事件须等此前已接收批次收敛，防止乱序造成假缺口。保留模型链路非阻断和有限内存原则。
3. 分开预留终止/响应/结算控制事件容量，避免正文队列挤满后连失败事实都丢失。
4. 持久化安全的固定失败原因：队列事件数/字节超限、单请求预算、编码、密钥、存储重试耗尽、退出未刷完；不存正文、密钥或任意异常字符串。关联计量应能区分这些原因。
5. 用主/子Agent并发、长上下文和慢MinIO做隔离压测，分别测事件产生/消费速率、队列峰值与拒绝数、存储延迟、主链路时延；不以调大队列作为最终修复。

缺失的历史原文不能由回填恢复；不能重新调用模型“补原文”，也不把PARTIAL改成COMPLETE。新代码上线后可改善新请求，旧异常应如实保留。
