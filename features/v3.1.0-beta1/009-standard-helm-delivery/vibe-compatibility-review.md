不能将“新 spec 未重抄所有旧 AC”直接判作冲突。这里列出的是被本次参数化、默认开关、种子初始化或诊断解耦直接触及、需要明确承接的边界。

## 4. 未发现被新需求取消的核心流程

- 发布仍必审，沿用 INV-34、F055 AC-01/07/10/23、F086 AC-33。实际管线继续扫描/声明校验/适用构建/探活后才记录正式版本与请求审批；没有新增完整镜像免审入口。
- 审批前构建/探活失败与审批后容量不足仍分阶段处理；后者保留待上线版本及已通过审批，不把环境配置有效当作应用已上线。
- 入口授权、租户范围、审批预览身份与秘密边界不变。Manager、Helper、业务容器不因此获得平台 MySQL/MinIO 主凭据或集群管理身份。
- Gateway 可选与当前 3.1 原生 DSH 独立没有冲突；关闭 Gateway 不改变 Backend 的应用审批和 F048 授权。
- 代码沙箱与 Vibe RuntimeClass 是不同功能；前者默认启用不构成更改后者三档隔离/回退合同的授权。

## 5. 后续设计和验证必须覆盖

1. Backend/Manager 的配置来源与保护历史协同；无报告及报告变化不影响业务，实际错误不得被覆盖。
2. 发布必审、审批前失败不建单、审批后资源不足保留原单、候选真实就绪后切流。
3. 新装默认开启与升级 false/端点/凭据/会话保持；关闭 Vibe 的引导与隐藏；开放能力层独立。
4. 新/旧清单、完整 image、离线/在线阶段、默认环境变化对历史冻结版本的配对回归。
5. 档位初始值与已编辑值、运行实例冻结、预约/配额、默认恢复预算、Manager 短暂不可用及 RuntimeClass 回退。
6. UID 停止证明、旧 false 历史、未知写入者、快照确认和保留卷的失败路径。
7. 发行镜像与架构/catalog 证据单独验收；本轮不以静态模板或模拟测试宣称真实新集群部署成功。
