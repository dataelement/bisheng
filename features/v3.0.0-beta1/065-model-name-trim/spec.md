# Feature: 模型名称首尾空格兼容（F065）

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
>
> spec 只回答 **做什么 / 验收标准 / 不做什么**。
> **所有 How 一律不写在这里。** How 的唯一真相在 [design.md](./design.md)。

**关联 PRD**: 《3.0 beta2》§5.7 模型名称前后空格报错问题
**优先级**: P1
**所属版本**: v3.0.0-beta1
**依赖**: 既有模型管理页 `ModelConfig`、`POST/PUT /api/v1/llm`。无前置未交付 Feature。

> **范围边界**
> - **本次纳入**：
>   - 添加或更新服务商下的模型时，对「模型名称」做首尾空格兼容，保存成功后库里的名称不含首尾空白。
>   - 去掉空格后名称为空、或与同一服务商下其它模型重名，仍按现有校验拦截，不得写入。
> - **本次明确排除**：
>   - 不改服务商名称、模型展示名（`name`，如 `model 1`）、密钥 / endpoint 以外的配置字段。密钥与 endpoint 已有 `strip_config_whitespace`，不在本 Feature 重做。
>   - 不做存量行回填脚本或 Alembic 数据迁移；已入库的脏名称靠用户再次保存清洗。
>   - 不新增错误码、不改 19802 文案、不改租户可见性判定。
>   - 不改微调任务名、工作台默认模型选择器、开放 API 按名称点模型等其它入口的输入框（写入仍走同一后端契约）。
>   - 不处理名称中间的空格（厂商合法名里可能有空格，只去首尾）。

---

## 1. 用户故事

作为 **模型管理员**，
我希望 **在「模型名称」里误带首尾空格时仍能保存成功**，
以便 **不必反复对照厂商文档排查「模型不存在 / 不可见」这类误导报错**。

---

## 2. 验收标准

> AC-ID 在本特性内唯一。Small feature，采用 EARS 句型。

- **AC-01** — WHEN 管理员在添加或更新服务商时，任一模型条目的「模型名称」带有首尾空格（含半角空格、制表符、换行）, THE SYSTEM SHALL 在写入前去掉这些首尾空白，并按去掉后的名称落库。
- **AC-02** — WHEN 去掉首尾空白后名称非空且不超过 100 字符、且同一服务商下不与其它模型重名, THE SYSTEM SHALL 允许保存；不得仅因原始输入带首尾空白而失败。
- **AC-03** — WHEN 去掉首尾空白后名称为空, THE SYSTEM SHALL 拒绝保存，并沿用现有「模型名称不可为空」提示，不得写入空白名称。
- **AC-04** — WHEN 去掉首尾空白后，同一服务商下出现两条相同名称, THE SYSTEM SHALL 拒绝保存，并沿用现有重名提示。
- **AC-05** — THE SYSTEM SHALL 把写入后的名称原样用作厂商请求的 `model` 参数；首尾空白不得进入该参数。
- **AC-06** — THE SYSTEM SHALL 不回填历史已入库、名称仍带首尾空白的行；WHEN 管理员再次保存该服务商, THE SYSTEM SHALL 按 AC-01 清洗本次提交的名称。

---

## 3. 边界情况

- 只输入空格：视为空名称，走 AC-03。
- `gpt-4` 与 ` gpt-4 ` 在同一服务商下同时提交：清洗后重名，走 AC-04。
- 名称中间的空格（如 `gpt 4`）保留，不折叠、不替换。
- 全角空格、不间断空格：与 Python / JS `strip()` / `trim()` 行为一致即可，不另定义空白字符表。
- 直调 `POST/PUT /api/v1/llm`（不经管理后台页）也必须满足 AC-01～AC-05。
