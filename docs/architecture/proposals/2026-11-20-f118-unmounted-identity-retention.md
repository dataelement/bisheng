# F118：取消租户身份后的历史数据保留兼容

状态：用户已确认“按保留兼容方案修复并继续升级”；实现/验证进行中。实施依据同步到 F118 AC-135～137、D13，现场业务/权限记录保留，最终执行结果以阶段日志为准。

## 问题与用户决定

升级停在正式全量预检，错误为 `f118_snapshot_global_original_orphan`。用户要求“数据不动，可能是取消了租户身份”，并确认没有其他人同时操作升级。

原历史计划的既定清理、三个经用户确认的目录继承修复均已完成；新的历史准备计划 `blocked=[] / preparation_complete=true`。正式迁移 Run 尚未创建，业务服务保持停止。

2026-11-20 在现场使用同一服务配置、显式拥有并关闭的数据库上下文，只读核对得到：

- 实际 tenant 行有 2 个；权限记录涉及另外 206 个缺失租户。
- 206 个缺失租户逐一对应 `tenant.unmount` 审计，`tenant_id`、`target_type=tenant`、`target_id` 精确一致，不只是审计总数相等。
- 这些缺失租户没有 user_tenant 绑定，也没有当前部门挂载。当前唯一子租户挂载指向实际存在的租户。
- 缺失租户名下 3,708 个工具类别全部为 `is_preset=1` 的预置副本；知识库、文件、工作流、助手、频道、看板、应用未发现缺租户业务行。
- 四张原始权限表各有 3,709 条缺租户关联。assignee 的 Grant 父记录存在且租户一致。
- 多出来的 1 组权限属于已迁回有效租户的助手；原租户的取消审计记录了 `migrated_counts.assistant=1`。该助手目前只有旧租户权限 mode，没有有效租户的新 mode。

以上支持“取消租户身份后的保留记录”这一分类。当前及 v3.0.2 的 `unmount_child` 会将子租户归档并保留 tenant 行，因此审计不能单独证明这些 tenant 行后来由哪个操作删除；不据此重建租户、推断授权或修改数据归属。

## 当前代码边界

- `tenant_mount_service.py` 明确保留预置工具副本，不将其重复迁回 Root；普通业务资源在取消身份时迁回 Root。
- `PermissionMigrationSnapshotRepository.avalidate_global_integrity` 对四张权限原始表做实际 Tenant 父存在性校验，当前一律拒绝缺租户原始行。
- 该校验既用于 M2 初查，也用于权限转换的中间状态和最终 CURRENT 切换。只删掉初查中的一次校验不能完成迁移。
- 正式迁移按实际 Tenant 清单冻结和签发 Coverage，不能把缺失 ID 自动补成新租户。
- 原 Run 使用封闭、带哈希的 baseline/plan 和 checkpoint。新增保留分类必须进入原冻结合同；不能靠临时跳过开关或复跑时重新解释旧 Run。

## 拟议行为与验收条件

1. **业务、权限原始行和归属保持。** 不删除工具副本、助手、mode、Grant、assignee、visible-source；不补 tenant 行、不改 tenant_id、不将旧权限收编到 Root，不创建新的人员或角色授权。
2. **只接纳可证明的取消身份残留。** ID 必须为合法正数且实际 Tenant 不存在；具备精确取消租户审计，当前无用户绑定及部门挂载。工具必须是原租户的预置副本；其他资源类型继续拒绝，助手仅允许有明确迁出审计、实际资源仍存在于有效租户、无同对象有效租户 mode 冲突的原关联。
3. **保留对象不能侵入实际转换范围。** 明确核对原 FGA 对象及 Grant 键与有效资源 mode、命名空间目标不冲突。普通缺租户行、孤立或跨租户 assignee、非 CURRENT 投影、不明下游、新增或不匹配的审计继续阻塞。不能把助手旧权限转换为新的 Root 授权；其既有无有效租户 mode 的失效状态也不在本方案自动修复。
4. **实际租户正常迁移。** Tenant/Coverage 清单仍只含实际存在的租户，正常业务、权限目录、知识命名空间、引用转换及最终就绪校验保持原合同。历史残留不获得 Coverage，也不获得运行时访问资格。
5. **保留事实可验证且可续跑。** 新 Run 的冻结元数据加入显式保留策略版本、数量及原事实摘要；baseline 和 plan 必须一致。摘要覆盖精确取消审计、原权限行、预置工具原行、缺失身份和迁出目标的结构事实。有效租户助手正常业务载荷由既有来源快照验证，不把正常引用转换误判为保留数据漂移。
6. **全过程重验。** 首次业务写入前、权限转换恢复/中间检查和最终切换事务中，重读原事实并比较冻结摘要。租户恢复、重新挂载、出现用户绑定、增加或修改保留行、审计变化均拒绝；保留原 Run/checkpoint，不重建 baseline 消除差异。
7. **原 Run 不改合同。** 未携带该策略的既有冻结 Run 继续原严格校验；不自动升级、删字段或替换材料。原 `f118-history.json` 及已完成事件保持原样。
8. **原 FGA 关系保持。** 整个原 Store 已由正式快照冻结；针对保留对象明确验证计划不产生新的授权或删除原关系。切换前后普通用户对有效资源的权限不扩大、不因该分类丢失；失效原关联不借迁移恢复为新授权。

## 实现范围

- 在应用编排侧组合租户、部门、审计、工具/助手与权限只读事实。跨业务 Owner 的判定不下沉到 permission repository，不修改在线租户生命周期或业务权限入口。
- 权限仓库保留原默认严格行为；只有本次冻结且通过当前原生事实复验的集合可以作为已分类保留对象，其余全局完整性检查继续执行。
- 更新新 Run 元数据的封闭编码、baseline/plan 一致性校验和恢复读取。正式转换在首次写入和最终发布前使用原摘要，不能只在 CLI 首次运行时检查。
- 通过主键/tenant-leading 索引进行最多 200 行的分页读取，流式计算摘要；Owner 存在性按有限 ID 批次查询，不为每条残留重复扫描全表或重读大载荷，不引入部署租户总数上限。
- 不新增数据库表、手工 SQL 修复命令、DBA 证明参数或忽略完整性的命令行开关。

## 必须补充的验证

原生 SQL + 严格 FGA 传输测试，不能只 mock 校验结果：

- 有精确取消审计的预置副本和已迁出助手可保留，原业务行/权限行/归属及相关 FGA 键保持。
- 缺审计、错误目标、仍有挂载/用户绑定、非预置工具、资源不存在、有效 mode 冲突、失效投影及跨租户 Grant 父关系均拒绝。
- 冻结前预览、首次 apply、M3/权限写入中断、最终切换中断后沿原 Run 恢复，不重复写入或扩张选中范围。
- 冻结后 SQL、审计、身份、挂载及 FGA 漂移被发现；原材料不被覆盖，旧 Run 没有新策略时保持原行为。
- 实际 Tenant 清单及 Coverage 不包含历史缺失 ID；有效租户非管理员列表/详情权限保持；原已失效助手不被自动重新授权。
- 多于 200 个取消身份与大量预置副本的分页、有限内存、查询数量验证。无 N+1、笛卡尔积或重复全表校验。
- 运行既有历史准备、namespace、冻结/恢复、来源转换、原生投影与最终 Coverage 回归；真实 MySQL 现场先重新 dry-run，通过后才首次冻结新 Run。DM8 使用相同 ORM/类型，真实双库验收单独标记，不以 SQLite 替代。
