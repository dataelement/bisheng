## 8. 用户纠正：部署入口与操作体验优先（2026-11-12）

用户明确否定新增大量人工准备步骤的部署体验，要求运维继续执行原有命令；需要的信息可以在同一次部署过程中引导补齐。本条覆盖此前将独立keygen/prepare/check作为正常部署前置步骤的安排。

- 保留 `bash docker/install.sh` 与 `bash scripts/deploy.sh install`，后者继续转发前者。
- 标准新装由安装脚本完成镜像准备、缺失信息引导、首次外置key创建、配置加密、原生消费者同步、权限/挂载、检查及启动。
- 缺少客户密码时在当前部署会话隐藏输入并确认；密码仍由客户提供，不自动生成中间件密码，不使用统一弱密码。
- 正常重复部署复用已保存的密码、key及配置，不重复询问、不重新生成、不自动改账号密码。
- 正常部署不要求用户理解keyring、bundle、revision，也不要求执行辅助工具或填写其路径参数。
- 存量部署或失败重试先识别已有状态；必要的旧配置/key/管理信息通过同一入口引导恢复，不能按新装覆盖原有身份和数据。
- 只有显式要求的真实改密或密钥轮换才进入对应维护流程，不能在普通启动时默认执行。

当前install.sh仍强制要求预先生成配置包，因此不满足本次修正。已有200项聚焦回归证明基础安全能力，不证明“一条命令部署”已经实现。下一轮围绕原安装入口补充交互、复用和失败重试验收，原长SOP不作为正常部署的合格交付。

## 9. 2026-11-14 增量发现：普通账号与全量落盘加密

本节并入原 `discovery-encrypted-files.md`。用户当时确认：持久磁盘只保存加密密码，运行时允许在进程或受控内存文件系统里使用明文，密钥继续独立受限保存。

2026-11-15 选项 C 改变了这个边界：应用配置字段仍加密，原生中间件文件改为受限明文挂载，Go 垫片和 tmpfs 交付门禁拆除。下面的「建议行为」和 tmpfs 约束是当天的发现，不是现行设计。现行条文在 spec 的选项 C 与 design §4.14。166 的只读环境事实仍然有效。

### 已核实的问题

1. `credential_bundle.py::_native` 把 MySQL、Redis、MinIO、ES 及 Milvus 初始化密码或依赖密码写入原生文件。当时只有后端 `config.yaml` 的受管密码字段加密，Redis ACL 为哈希。
2. `credential_inputs.py` 与 `credential-install.sh` 接受或生成明文输入；`credential_rotation.py::prepare_rotation` 保存 inputs、source、captured-base 和完整 stages，包含明文恢复副本。
3. `credentials.sh` 已按宿主调用者 UID/GID 运行工具，`secret_crypto.py` 已允许 0640 密钥，但 install.sh 仍让密钥保持原权限。非 root 后端/Worker 读取和原生镜像降权当时没有完整证据。
4. 166 验收目录和密钥属于 root，位于 `/root`。不能拿这个目录证明普通账号可部署。
5. 2026-11-14 只读检查 166：没有 UID 1000～65533 的可登录普通账号；未启用 swap；内核 3.10.0-1160.119.1.el7.x86_64；Docker 不是 rootless。这只能说明普通客户端账号可以访问已授权的 Docker，不能证明 rootless daemon 可用。
6. 当时的 spec 明确排除「强制所有部署 Secret 文件加密」。这次发现改变了该边界。旧验收记录不能挪作新能力的通过证据。

### 当时建议、后来被选项 C 取代的行为

| 对象 | 2026-11-14 的建议 |
| --- | --- |
| 操作入口 | 保留 `bash docker/install.sh` 和原包装命令；不增加运维必执行的解密、权限或清理脚本 |
| 部署账号 | 能访问部署目录且已获 Docker/Compose 授权；不要求 root 登录，不自动授予 sudo，不在部署时创建系统用户或系统组 |
| 文件归属 | 由部署账号创建并拥有文件；0600/0640 按读取主体使用，不放宽为 0666/0777 |
| 持久配置 | 原生文件、输入副本、阶段配置、旧版备份和恢复材料都用认证加密保存；Base64、改后缀或只靠权限不算加密 |
| 运行时 | 解密只发生在进程内存或经核实的容器 tmpfs；禁止先解密到宿主普通目录、容器可写层或持久数据卷 |
| 中间件兼容 | 原生程序继续读自己的文件格式；适配器把加密产物恢复到内存，复用 vendor 生命周期和非 root 降权 |
| 输入 | 隐藏输入后直接加密保存；取消和失败不得留下明文临时文件 |
| 恢复 | 敏感检查点加密；断电、重启、同一命令续跑和配对回退从密文恢复 |
| 外置密钥 | 独立于源码和密文保存；密钥文件不用同目录另一把写死密钥再加密 |

「密码」包括 MySQL、Redis、MinIO、ES、Milvus 以及 OpenFGA、Gateway 等消费者使用的同源凭据。不扩张成系统文件、客户业务数据或第三方密码库的透明磁盘加密。镜像仓库登录凭据不是这五类中间件密码。

选项 C 保留了入口、部署账号、文件归属、外置密钥和应用字段加密。原生文件、tmpfs 启动和「持久磁盘不得有任何明文密码文件」不再成立。

### 当时的技术约束

- Docker Compose 的 file secret 只是文件挂载，不会把宿主原文件自动加密。
- tmpfs 不能跨容器共享，也可能进入 swap。无 swap 的预检是当时密封方案的前提，不是选项 C 的交付条件。166 当时无 swap，不能代表所有客户机器。
- MySQL 初始化 SQL、Bitnami ES 生成配置、Milvus user.yaml、OpenFGA 无 shell 镜像、Redis 降权和 MinIO 健康检查都要按真实镜像核实。
- 旧文件要先读入并核对，再切换挂载；失败时保留可恢复状态。不擅自删除客户原始输入或外部备份。普通 unlink 不能证明 SSD、快照和旧备份上的字节不可恢复。
- 宿主普通账号能操作 Docker，不等于容器内进程使用同一 UID，也不等于 Docker rootless。

依据：[Docker tmpfs](https://docs.docker.com/engine/storage/tmpfs/)、[Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)，2026-11-14 核查。这两份资料只说明机制，不证明私有镜像适配成功。

本轮发现只做了代码盘点和 166 只读检查，没有创建用户、改密码、启动容器或删除文件。

### 当时的验收矩阵草案

选项 C 之后，「持久目录不得出现明文密码」不再是通过条件。下表只保留当天识别的风险。

| 范围 | 主要风险 | 必须观察的结果 |
| --- | --- | --- |
| 输入、密钥、配置包 | key 不匹配、密文被篡改、输入取消泄露 | 应用字段加密；坏密文在使用前拒绝 |
| 原生启动 | vendor 把明文写回数据卷，降权后读不到文件 | 实际进程能认证；选项 C 下改为检查受限明文挂载，而不是 tmpfs |
| 健康检查 | 密码进入 argv、环境变量或日志 | Docker inspect、进程参数、日志和配置渲染不含已知密码 |
| 改密计划与恢复 | 恢复材料丢失、重复写账号 | 原生写入之后、配置激活之前中断，仍能用原命令续跑或受控回退 |
| 旧版迁移 | 中断丢配置、误删用户文件 | 切换前旧服务可恢复；切换后不依赖旧明文挂载才能启动 |
| 普通账号权限 | 隐式 sudo、root 持有文件、其他人能读密钥 | 隔离普通账号无 sudo 完成部署；未授权账号不能读密钥 |
| 原入口与业务 | 自动化输入抢占交互 | 原命令可保留、单选和全选；登录、知识检索、权限和 Worker 通过 |
| 磁盘扫描 | 只扫当前文件，漏掉历史或转义副本 | 扫描范围可复现；Milvus 内部 Base64 按用户确认除外 |
