# 毕昇云端工作台协议（Agent 执行）

云端工作台就是企业托管应用；本规范由当前企业服务器提供，和应用托管共用发布、审批、权限与数据协议。Agent 应访问本网址阅读，不要求用户提供本地 Markdown 附件。

适用于毕昇客户端 bisheng-work，云端为企业自己的毕昇服务。不修改公开 DSH，也不要求用户提供发布 Key。

## 先判断部署方式

在写包或业务代码前，从已确认上下文判断：谁使用、最小业务流程、关闭客户端后是否要继续运行、是否多人共享业务数据、是否依赖本机文件。仅个人且无持续运行需求优先本地；定时采集、Webhook、持续任务或多人协作优先云端；有本机依赖时采用组合方案。信息不足时逐次问一个必要问题，不重复问已知信息。将理由、个人/共享状态和并发冲突规则写入项目需求记录；上传不等同于已经完成长期运行验收。

## 使用与开发

账号、租户和部署地址复用客户端当前配置；云端页不提供另一套连接或 Key 设置。客户端已登录就直接加载，切换账号或企业后重新发现应用并清除旧的发布选择；未登录只进入客户端统一登录。

普通使用：从「云端工作台」中选择工作台，加载正式网址，应用入口使用当前毕昇用户身份校验 use 权限。没有源码工程和本地业务进程。

业务查询、填写记录、改变已有配置优先调用业务 API。只有用户明确请求修改样式、布局或应用功能时才获取源码；不能因为用户打开应用而自动下载工程。源代码包含业务逻辑，按企业授权范围使用；不要请求/保存主 Token、服务账号 Key、网页登录 Cookie 或业务数据库。

先调用 `cloud_workbench` 的 `guide` 操作获取当前企业服务器的 guideUrl，访问这个网址阅读协议，无需获取本机登录 Token；后续操作也通过该工具执行。底层已认证的本机 Harness 通道为 `POST /api/desktop-workbenches/cloud`，请求体为 JSON：

- `{"operation":"list"}`：本人能使用的上线应用，按 next_cursor 分页。
- `{"operation":"list","managed":true}`：本人可编辑的应用。
- `{"operation":"create"}`：分配全新的独立开发目录，返回 projectId 与 path。先明确业务需求，再在该目录写源码和 bisheng-app.yaml；不要执行下载来源不明的安装脚本。
- `{"operation":"checkout","appId":"实际应用ID","versionId":"指定正式版本ID"}`：服务端验证源码编辑权限，校验归档身份与 SHA-256 后安全解包，返回 projectId/path/baseVersionId。仅在返回的目录开发，不覆盖用户已有目录。
- `{"operation":"publish","projectId":"上述真实ID","releaseNotes":"更新说明"}`：打包受管目录并以本人身份提交原发布流水线。首次发布不要求外部仓库；不打包数据、密钥、node_modules、符号链接。更新使用 checkout 的基线；冲突时先比较/合并，不能绕过基线覆盖。不要自动确认破坏性数据库变更。
- `{"operation":"progress","appId":"实际ID","deploymentId":"回执真实ID"}`：查询扫描、预检、审批和上线。上传成功仅表示收到提交，不能报告上线完成。

这些是已登录本机接口，不是应用内接口；远程业务页面不能访问此通道。退出、切换企业或登录过期后重新连接；不要跨企业复用开发项目进行发布。失败须保留源码和真实回执。

发布进入 failed 后停止轮询，向用户报告阶段、错误码、平台提示和管理入口。只有平台诊断明确指向应用源码时，才在当前工程内修复、自测并重新请求发布确认；平台、节点或传输问题交由管理员处理。不要为排查发布失败而扫描本机、读取平台源码、宿主进程环境、Docker 或服务配置与凭据。

## 企业 SDK 与运行合同

create/checkout 返回当前企业的 toolkit 地址，保留反向代理子路径。先读取 versionsUrl 与 sdkGuideUrl，platformWiringUrl 返回 tar.gz 技能包，下载到临时目录并解包，先读 SKILL.md，再读其中的实时协作样例；不要把归档当纯文本反复请求。本地测试也从 sdkIndexUrl 获取该服务器发布的 bisheng-sdk 版本，不扫描本机或到公开 PyPI 搜索企业 SDK。上传包只声明依赖，不夹带 SDK wheel 或已安装依赖；托管构建器负责安装。服务器缺少或不兼容的工具包属于部署前置条件，不能自行编造鉴权与持久化协议。

## 共享业务协议

云端源码是不可变版本；数据通过云端业务 API 写入持久存储，不使用浏览器 localStorage 保存唯一共享真相。使用 SDK 0.1.2 的 `bisheng_sdk.realtime.RealtimeStore` 时，SQLite 业务记录、revision、请求幂等结果和事件日志在一个事务中提交。只适用于现有单写入应用运行合同，不启用多个实例同时写同一 SQLite 文件。

业务 HTTP 接口读取平台代理确认的访问者身份，按应用自身规则检查数据读写权限；不要信任前端传入的 userId/tenantId。SSE 只发布已授权的失效通知，客户端重新读取有权查看的数据；按 cursor 补偿，过期重新获取带水位的快照。同一记录的旧 revision 返回冲突，幂等键按访问者隔离。SDK 会校验同一操作的完整值，重试时必须提交相同的业务输入；不能把每次变化的时间戳或随机值混入幂等请求，否则合法重试会变为操作冲突。应测试跨秒和响应丢失后的重试。未提交草稿的基线 revision 与最新服务端快照分开保存；SSE、后台读取和断线重连不能自动推进草稿基线，只能由用户显式确认重基。延迟返回的旧快照不能回退已观察版本；恢复权限后，显式重载还需恢复订阅。个人筛选、滚动和未提交输入默认不同步。个人草稿、缓存及其基线必须在取得可信身份后，按租户、应用和用户隔离；同一浏览器切换账号不能恢复上一位用户的草稿或“我的已保存”状态。授权失败时停止订阅，保留当前用户草稿供恢复，不能继续展示其他身份的缓存。逐字共同编辑/画布 CRDT 需要另行明确需求。

后台任务、定时调度、Webhook 由云端运行，不能使用页面定时器承担 24 小时任务。上线后引导设置团队可见范围，未授权同事不能访问；不要擅自扩大范围。

只有经过校验的成功写入回执才能清除待重试操作和未提交草稿。HTTP 409 后拉取的快照仍是读取结果，不能沿用保存成功分支：必须保留草稿及其基线，直到用户明确重基并成功写入。测试应驱动真实异步界面处理器覆盖这条路径。断线恢复应通过有上限的退避连续尝试；一次快照恢复请求失败不能终止后续重连。保留游标及草稿，鉴权或授权失败时停止，并在恢复权限后的显式重载中恢复订阅。

## 必须验收

至少验证普通用户允许/拒绝、两个不同账号读写同步、并发冲突、重试幂等、断线补偿、权限撤销、版本更新和应用进程重建后数据回读。关闭客户端后验证所需后台任务仍运行。没有实测的项目明确列为待验收。仅源码构建成功不等于企业服务器已部署或客户端已安装。

## 由 Agent 完成发布交互

「云端工作台」独立展示企业托管的工作台；客户端「应用」和管理端「构建 → 应用」也提供同一目录入口；该页只负责发现和使用工作台，不提供手动发布表单。用户从「制作我的工作台」或已有工作台的开发对话提出需求；Agent 在对话里完成以下流程，不要求用户再去点发布按钮：

1. 复用上下文完成部署需求分析，用业务语言说明本地、云端或混合方案的理由，确认最小范围。
2. 开发并验证后，向用户展示本次变更、拟发布目标、数据结构影响和建议的团队可见范围。已有明确发布授权时继续执行；没有授权时在对话里确认，不能把同意开发当成同意上线或扩大权限。
3. 使用 `cloud_workbench` 工具的 create/checkout、publish、progress 操作和真实 projectId、版本基线、发布回执。create/checkout 后检查返回的 developmentWorkspace 状态。ready 为 false 时停止写入，请用户把返回的准确目录作为开发会话工作区打开，携带已确认需求和 projectId 继续。仅改变 working_directory 不会改变可写工作区；不能为此查阅 Desktop 内部实现或扩大 sandbox 权限。
4. Agent 提交现有扫描、预检和审批流程并查询进度；区分“已提交”“等待审批”“已上线”，不替用户或管理员自动审批。失败保留源码、回执和修复说明；版本冲突先比较合并。
5. 确认正式入口可访问后告诉用户如何在工作台列表打开，并继续引导 owner 设置团队可见范围；未获授权不改变成员权限。

发布是对话里的开发流程；日常打开、查询、修改业务记录都不会触发源码下载或代码发布。
