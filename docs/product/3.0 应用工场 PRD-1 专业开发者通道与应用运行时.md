## 1. 综述

**一句话定位：让专业开发者把本地开发的存量应用按需集成企业的知识/模型/身份能力、导入平台纳管发布——本地 coding agent 一句话完成部署；应用跑在平台托管的运行环境里，发布进应用广场、同事即点即用，审批/权限/配额/审计全程自动生效。本册同时交付两条造应用旅程共享的地基：应用运行时、发布审批管线与治理面——《PRD-2 造应用工作台》的对话式造应用站在同一地基上。**

三大能力（对应功能需求三个域的归属）：

| 能力 | 一句话 | 承载域 |
|------|--------|--------|
| 导 | 本地项目按需集成平台能力、经 CLI 导入纳管：MCP（调用）/ 技能包（知识）/ SDK（代码）/ CLI（工作流）四面供给，本地 coding agent 对话式完成部署与排障 | §3.1 开发者通道（DEV） |
| 接与跑 | 应用托管在平台运行环境，经能力总线接入知识库/模型/身份，天生认识组织架构与权限；统一入口与应用广场承载使用 | §3.2 运行时与发布（RT） |
| 管 | 发布审批/权限/资源档位与配额/审计全程自动生效，本地造的和平台造的应用治理面前无差别 | §3.3 治理（GOV） |

本册交付边界一览：

| 维度 | 本版做 | 本版明确不做（详见 §5） |
|------|--------|------------------------|
| 开发者 | MCP / 技能包（四个开发技能包）/ SDK / CLI 四面按需集成；存量本地项目导入纳管；本地对话式部署 | 本地端专有插件；第三方 MCP 网关 |
| 发布 | 首发与迭代每次发布均需审批；发布前密钥扫描门；资源档位选择（平台预置模板）；版本前向回滚；入口链接 + 二维码 | 公网域名/公开可见性/SEO/水印 |
| 部署 | 三层部署形态（工场运行时层可整层不装），工场为可选组件 | K8s 多机；自定义运行环境构建 |

## 2. 用户与旅程

### 2.1 用户

| 用户 | 要什么 | 主要触达面 |
|------|--------|-----------|
| 业务技术员（主用户，会用 coding agent 的人） | 本地开发的应用部署到平台给大家用 | 专业开发者通道（§3.1） |
| 平台管理员 / IT | 自建应用看得见、管得住、出事能兜底 | 治理与管理面（§3.3） |
| 普通业务用户 | 在应用广场找到并直接使用同事造的工具 | 统一入口与应用广场（§3.2） |

角色定义（全文角色词汇的单一出处）：

| 角色 | 定义 | 典型动作（详见 §3.3 角色×动作矩阵） |
|------|------|------|
| 平台超管 | 平台级运维管理员 | 维护资源档位规格、按租户设定实例配额、跨租户审计 |
| 租户管理员 | 租户内治理角色 | 签发/吊销个人 key、标签设置、停运/重新启用、配置审批人、查本租户审计、配置能力总线、配置角色的应用工场菜单与新建权限 |
| 审批人 | GOV-02 配置的发布审批处理人 | 处理审批单、审读视图与预览试用 |
| 开发者（owner） | 导入/创建应用的所有者 | 集成与导入、发布/撤回/回滚、可见范围设置、改码权交接、删除 |
| 普通业务用户 | 广场使用者 | 发现并使用可见范围内应用 |

注：单租户部署下平台超管与租户管理员可为同一人；本册后文提及角色时一律使用上表中的具体角色名，不泛称「管理员」。

### 2.2 主旅程：专业开发者 本地开发 → 集成平台能力 → 导入纳管

1. 开发者已在本地（vscode / cursor / coding agent）把应用开发得七七八八——这一段平台不参与。
2. 需要平台能力时按需集成：租户管理员签发个人 API key（DEV-01）；经 MCP 使用检索/身份/应用数据等工具、经双协议直连平台托管模型（DEV-02）；按需引入 SDK（DEV-07）；`bisheng skills sync` 拉取毕昇开发技能包获取接入知识（DEV-03）。集成是可选项：不用任何平台能力的存量应用也可直接导入。
3. 本地联调：`bisheng dev` 运行应用并注入与线上同构的平台身份，应用不写登录页（DEV-05）。
4. `bisheng deploy` 导入纳管，经统一发布管线（预检 → 扫描 → 审批 → 托管上线，DEV-04）；`bisheng logs` 排障。
5. 导入后默认仍本地改码、deploy 更新；可交接给平台管家（改码权归属与交接规则见 DEV-06）。

### 2.3 使用旅程：普通业务用户

已发布应用的使用与来源无关：普通业务用户经应用广场 / 入口链接 / 扫二维码免二次登录使用，各自只看到权限内数据（RT-01 / RT-02）。

## 3. 功能需求

### 3.1 专业开发者通道（DEV）

**本域交付：已有本地项目的开发者（vscode / cursor / coding agent 开发的存量应用，0.9 → 1）按需集成平台能力、导入平台纳管发布。**

- **四面供给定位**：MCP（调用）/ 技能包（知识）/ SDK（代码）/ CLI（工作流），定位为按需集成而非从零起步工具链，全部走标准协议、无本地专有插件；集成是可选项，不用任何平台能力的存量应用也可直接导入。
- **操作者模型**：四面供给的直接操作者是开发者的本地 coding agent——开发者在本地对话里提出部署诉求，agent 凭技能包 + CLI + MCP 完成部署与排障全流程、不离开本地对话（端到端验收见 DEV-04）。
- **同治理承诺**：导入后与平台内造的应用同治理——同一条发布管线、同审批、同权限、同审计（DEV-04）。

**DEV-01 个人 API key**
- 需求描述：租户管理员为开发者签发个人 API key，开发者凭它接入 MCP 工具面、模型双协议面与 CLI（DEV-02 / DEV-04）。key 值仅在签发时一次性展示，此后管理面与开发者侧任何界面只见掩码（与密钥零暴露同口径，NFR-2）。
- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 个人 key 管理（tab） | 管理后台-API key 管理页（三类 key 同页，GOV-08；本条目管个人 key tab） | 个人 key 列表 + 「签发」按钮 + 行上调整 scope / 吊销 / 用量入口 + 审计入口（GOV-04） |
| 签发弹窗 | 个人 key tab「签发」按钮 | 字段见下 |
| 一次性展示弹窗 | 签发提交成功后弹出 | 完整 key 值 + 复制按钮 + 红字警示「关闭后不可再查看，遗失只能吊销后重新签发」 |
| 我的 API key | 工作台账户菜单（头像下拉）新增入口，弹窗承载（与账户菜单既有设置项同形态） | 本人 key 掩码列表 + 自助吊销 + 接入信息区 |

  - 个人 key 列表字段：key 掩码（掩码口径全平台统一 = 前缀 + 末四位，GOV-08 凭据底座）、持有人、scope、状态（启用/已吊销）、创建时间、过期时间（未设置显示「长期有效」）、最近调用时间、用量入口（按 key 账单，GOV-04）；支持按持有人搜索/筛选；空态文案「尚未签发任何个人 key」。
  - 签发弹窗字段：持有人（用户选择器，单选）、scope（复选，五项全集见规则与边界，各项附白话用途说明——部署应用需勾选「应用发布与运维」；默认勾选检索/模型/身份查询）、过期时间（可选，默认长期有效）、备注（可选）。
  - 吊销：行上按钮 + 二次确认弹窗，明示「吊销后该 key 自下一次调用起在 MCP / 模型协议 / CLI 三面均被拒绝」；租户管理员与持有人本人均可发起。
  - 我的 API key：本人 key 掩码列表（scope / 状态 / 最近使用 / 用量）+ 自助吊销；接入信息区集中展示 MCP Server 地址、OpenAI/Anthropic 兼容 base URL、CLI 安装包下载（平台自身分发，无公网依赖）与 `bisheng login` 指引，开发者接入所需的地址与安装件在此一站可查；空态文案「暂无个人 key，请联系租户管理员签发」。
- 规则与边界：
  - scope 枚举五项，签发默认勾选前三项（最小集）；scope 与三面能力的映射如下（`login` 与 `skills sync` 仅验 key 有效，不验 scope）：

| scope | MCP 工具 | 模型协议面 | CLI |
|-------|---------|-----------|-----|
| 检索 | 知识库检索、知识库清单查询 | — | — |
| 模型 | 模型清单查询 | OpenAI/Anthropic 双协议直连 | — |
| 身份查询 | 用户身份/组织查询 | — | dev 身份注入 |
| 应用数据 | 应用数据表结构与数据查询 | — | — |
| 应用发布与运维 | 应用状态/日志自查 | — | deploy / logs |

  - key 值仅签发时一次性展示，此后一切界面只见掩码。
  - scope 签发后可由租户管理员行上调整，即时生效、无需重签，变更计审计（GOV-04）。
  - key 可吊销；调用频率限流本版不做（顺延 §5.2）。
  - token 用量只计量不设上限，账单按 key 归属（GOV-04）；每次调用审计到人。
  - 凭据形态与底座：个人 key 属个人主体轨凭据（前缀 `bs-pat-`），生成/哈希存储/校验/展示/撤销全部遵循 GOV-08 统一凭据底座（与《3.0 开放 API 鉴权与身份传递 PRD》R1 同源）。
  - 过期时间可选，默认长期有效（签发人 = 租户管理员、账号禁用自动失效已兜底）；设置过期的 key 到期自动失效、事件计审计（GOV-04）。
  - key 不落工程仓库：CLI 凭据存本地用户目录（属主可读权限），技能包红线引导用环境变量引用而非硬编码；平台自签发 key 前缀模式内置于发布前密钥扫描规则集（RT-03 / DEV-04）——开发者把自己的 key 硬编码进应用产物，deploy 时即被阻断。
  - 泄漏应急：支持按持有人一键吊销名下全部个人 key（GOV-08 批量撤销）；吊销生效上界 5 秒（底座撤销主动清缓存，通常即时）。
  - 账号被禁用/删除时，名下个人 key 全部自动失效（MCP / 模型协议 / CLI 三面即刻拒绝），事件计审计。
  - 未部署开放能力层时，本条两个入口（管理后台 API key 管理页、工作台账户菜单「我的 API key」）均不展示（GOV-07）。
- 验收要点：
  1. key 的每次调用可在审计中归属到持有人，用量计入该 key 的用量账单（GOV-04）。
  2. 吊销后的 key 自下一次调用起在 MCP / 模型协议 / CLI 三面均被拒绝。
  3. key 值签发展示一次后不可再查看，任何界面仅见掩码。
  4. CLI 凭据存本地用户目录（属主可读），不落工程仓库。
  5. 签发时指定的 scope 生效；未指定时为默认最小三项；租户管理员行上调整 scope 即时生效、无需重签；超出 scope 的调用在 MCP / 模型协议 / CLI 三面均被拒绝（按 scope 映射表逐项验证）。
  6. 持有人在工作台账户菜单「我的 API key」中可见本人 key 掩码/scope/状态/用量，可自助吊销。
  7. 账号被禁用后其名下 key 自下一次调用起三面均被拒绝，事件计审计。
  8. 将本人个人 key 明文写入应用产物并 deploy，被发布前密钥扫描阻断（平台 key 前缀模式在规则集内，DEV-04 / RT-03）。

**DEV-02 MCP 工具面**
- 需求描述：平台以 MCP Server（个人 API key 鉴权、scope 过滤）对外提供以下工具，与平台内管家同一工具面、内外同源；权限边界与平台 UI 同源。模型调用不走 MCP，走模型双协议直连面。

| 工具 | 用途 |
|------|------|
| 知识库检索 | 检索结果可见范围 ⊆ 该开发者平台 UI 权限，不新增数据面 |
| 知识库清单查询 | 列出该开发者权限内可声明接入的知识库及其标识，供能力声明填写（RT-04 / GOV-05） |
| 模型清单查询 | 查询可用模型；模型调用本身不走 MCP |
| 用户身份/组织查询 | 应用开发中查身份与组织架构 |
| 应用数据表结构与数据查询 | 开发与排障时操作应用自有数据 |
| 应用状态/日志自查 | deploy 后本地 agent 可自行「读日志 → 修 → 再发」闭环，含审批状态查询 |

- 模型双协议直连面：

| 要素 | 约定 |
|------|------|
| 协议 | OpenAI 兼容 / Anthropic 兼容原生协议，支持流式 |
| 鉴权 | 个人 API key（DEV-01） |
| 可用模型范围 | 租户管理员经能力总线配置的可用模型（GOV-05） |
| 计量 | 用量计入按 key 账单（GOV-04） |
| 适用对象 | 本地引擎，以及客户自装的 Claude Code 等工具，同样经此接入 |

- 规则与边界：
  - 知识库检索与清单查询结果 ⊆ 该开发者自身知识库权限（NFR-1），与平台 UI 可见范围同源。
  - 检索过滤强度口径：与平台工作台检索走同一条双层过滤路径（索引层预过滤 + 结果层批量校验兜底，含文件级权限）；不得复用既有开放 API 中仅做知识库级一次校验、无文件级过滤的旧检索路径（两条路径的强度差异已在《3.0 开放 API 鉴权与身份传递 PRD》附录 B 核实）。
  - fail-closed（NFR-1.4）：权限评估失败 → 返回错误，绝不返回未过滤或部分过滤的结果集；无法确立调用者身份 → 拒绝，不降级。
  - 用户身份/组织查询结果 ⊆ 该开发者平台 UI 组织可见范围。
  - 应用数据与应用状态/日志工具仅对该开发者为 owner 的应用可用（CLI `logs` 同口径，DEV-04），日志内容范围与工作台运行日志同规则（WB-13）；租户管理员查他人应用日志走工作台/管理面，不走个人 key 通道。
  - 应用状态工具返回审批终态与驳回理由全文（本地排障闭环依赖，DEV-04）。
  - 模型调用不走 MCP。
- 验收要点：
  1. 上表六类工具经 MCP 全部可调用；超出 key scope 的工具调用被拒绝（按 DEV-01 scope 映射表逐 scope 验证拒绝行为）。
  2. 经 MCP 检索到的知识库内容不超出该开发者在平台 UI 中的可见范围。
  3. 对非本人 owner 应用的数据/状态/日志工具调用被拒绝。
  4. 讲 OpenAI 或 Anthropic 协议之一的本地工具可直连平台托管模型并流式返回，用量计入该 key 的用量账单。
  5. 身份/组织查询不返回该开发者组织可见范围外的部门与用户。
  6. 租户管理员的个人 key 经 MCP 查询非本人 owner 应用的日志被拒绝。
  7. 应用状态工具可查到审批驳回终态及驳回理由全文。
  8. 集合相等：经 MCP 检索的结果与该开发者本人在平台工作台内对同一知识库检索的结果集合相等——不多给也不少给，验证样本须含文件级权限差异（同库内部分文件无权）场景。
  9. 人为使权限引擎不可用，MCP 检索返回明确错误，而非未过滤或部分过滤的结果（NFR-1.4）。

**DEV-03 毕昇开发技能包（首发四包）**
- 需求描述：平台能力的使用知识以开放技能格式（SKILL.md + 可运行样例 + 连通自检脚本）发布，`bisheng skills sync` 从自家平台拉取。首发四包：

| 技能包 | 内容 |
|--------|------|
| 应用包规范 | bisheng-app.yaml / 能力声明 / 安全红线（禁写鉴权·连接串·密钥）/ 托管运行契约（平台托管提供与不提供什么，DEV-04）/ deploy 工作流与预检排障指引（声明补全 → deploy → 预检修复 → 审批状态跟踪） |
| 登录权限接入 | 读平台注入身份即得用户 / 代理用户身份调用 |
| 数据 | 应用数据 SDK 范式 / 迁移策略 / 知识库检索用法 |
| 模型接线 | 双协议接入方式 / 模型名即平台模型管理原名（无逻辑档位转换）/ token 计量 |

- 规则与边界：
  - 从自家平台拉取，与平台版本天然对齐，无公网依赖。
  - 重复 sync 以平台当前版本覆盖更新本地技能包。
  - 与平台内造应用引擎读同一份内容，不维护两套文档。
  - 技能包的触发描述以通用意图表述（如「将本地项目部署 / 发布到企业的应用平台」），不依赖特定产品名——BiSheng 是 ToB 开源平台，企业部署常用自有品牌名。
  - 目标平台实例由 login 凭据与 skills sync 的来源平台确定，与名称无关。
- 验收要点：
  1. `bisheng skills sync` 后本地存在四包，每包含可运行样例与自检脚本；自检脚本对已配好的环境执行通过，对缺失配置给出可读的失败原因。
  2. 四包内容与平台内引擎所用平台能力指令同源一份（抽查关键规则一致）。
  3. 非 Claude Code 引擎可经 AGENTS.md 引用同一技能目录使用。
  4. 平台升级后再次 sync，本地技能包更新到平台当前版本内容。
  5. 以不含产品名的自然语言（如「把这个应用部署到公司的应用平台」）向本地 agent 提出部署诉求，能正确触发技能包进入部署流程。

**DEV-04 CLI 命令集**
- 需求描述：`bisheng` CLI 是本地开发者与平台交互的工作流入口，五个命令覆盖「接入 → 本地联调 → 发布 → 排障」四个环节。deploy 的发布管线与平台内应用同一条——本地造的和平台造的应用，治理面前无差别（同审批、同权限、同审计）。CLI 安装包由平台自身分发（下载指引见 DEV-01 接入信息区），纯内网环境零公网依赖。

| 环节 | 命令 | 行为 |
|------|------|------|
| 接入 | login | 以个人 API key 登录目标平台（DEV-01），凭据落本地用户目录 |
| 接入 | skills sync | 从已登录平台拉取毕昇开发技能包（DEV-03） |
| 本地联调 | dev | 在本地运行应用并注入与线上同构的平台身份（DEV-05） |
| 发布 | deploy | 把当前项目作为版本快照提交发布，唯一发布通道；管线见下 |
| 排障 | logs | 查看本人 owner 应用的运行日志（owner-only，与 MCP 日志面同口径，DEV-02；日志内容范围与工作台运行日志同规则，WB-13） |

- 流程（deploy 发布管线四步）：
  1. **托管预检**：依赖构建 / 应用包声明校验 / 启动探活，判定标准 = 托管运行契约（见下）；首发 deploy 同时校验租户实例配额，超限原地拒绝（GOV-03）。失败 → 原地拒绝，说明缺失项与改造指引，不进入审批。预检检出破坏性结构变更（改/删列）→ 要求显式确认（交互确认或 `--confirm-schema-change`），未确认则拒绝；迁移前自动快照的承诺不变（RT-05）。
  2. **发布前安全扫描**：与平台内发布同一规则集，产物含裸密钥/连接串即阻断（RT-03）。扫描命中 → deploy 原地失败，输出命中规则与文件位置（不含密钥值本身，NFR-2），本地修复后重新 deploy（平台内应用的对应分支为回流管家改写，RT-03，两路径分述）。
  3. **审批**：首发与迭代每次 deploy 均生成审批单，迭代审批单含四类变更摘要（RT-03/04）；同一应用同时至多一个在途审批单，在途期间再次 deploy 被拒绝并提示；审批人对导入应用的预览试用以待上线版本快照起审批期临时实例（RT-03）。驳回 → owner 经发布面（WB-14）或 MCP 应用状态工具（DEV-02）查看驳回理由，修改后重新 deploy 生成新审批单。
  4. **上线托管**：审批通过后应用在平台托管环境运行、进入广场（RT-01 / RT-02）。
- 托管运行契约（预检第 1 步的判定标准，随「应用包规范」技能包对外，本地开发期即可对照，DEV-03）：

| 平台托管提供 | 应用不得自带或依赖 |
|-------------|-------------------|
| 语言运行时 | 数据库 / 消息队列 / 缓存等中间件 |
| 应用数据库 | 白名单外的外网地址 |
| 附件/文件存储 | — |
| 能力总线各项能力与密钥注入 | — |
| 依赖包经平台内网镜像安装 | — |

  契约内的应用保证可托管；契约外的依赖在预检被拒绝并给出改造指引（数据改接平台应用数据库的范式见 DEV-03 数据技能包与 DEV-07 SDK），不承诺自动改造。
- 规则与边界：
  - 首次 deploy 的 key 持有人 = 该应用唯一 owner；后续 deploy 仅 owner 本人的 key 可执行，非 owner 的 key 被拒绝并提示应用归属；归属转移见 §5.2。
  - 发布输入以 bisheng-app.yaml 为准：能力声明与资源档位在应用包中声明（档位未声明时为默认推荐档，GOV-03）；应用元信息（名称/描述/图标）亦取自应用包、随 deploy 更新（RT-02）。
  - 可见范围不在应用包内——首发默认仅 owner，审批通过后由 owner 在发布面设置（GOV-01）。
  - 审批状态跟踪两渠道：工作台发布面（WB-14），或经 MCP 应用状态工具查询（DEV-02）。
  - 撤回在工作台发布面完成，是端到端流程中唯一需离开本地对话的操作。
  - 无「新建应用」权限的用户 CLI 首发 deploy 被拒绝（GOV-07）；其已导入应用的迭代 deploy 不受影响。
- 验收要点：
  1. 五个命令按上表行为可用；key 被吊销后 CLI 命令报鉴权失败并提示重新 login。
  2. `bisheng deploy` 的每次发布（首发与迭代）均进入审批流（RT-03/04），迭代审批单含变更摘要；发布前扫描与平台内发布同一规则集（常见凭据模式正则清单 + 数据库连接串模式 + 平台自签发 key 前缀模式，GOV-08），规则集内样本 100% 被阻断。
  3. 经 CLI 导入发布的应用在广场、权限、审计中的表现与平台内造的应用一致；bisheng-app.yaml 声明的资源档位生效，未声明时为默认推荐档。
  4. 依赖平台不提供的中间件（如自带数据库）的项目 deploy 被预检拒绝，报错说明缺失项与改造指引；预检失败不产生审批单。
  5. 同一应用存在在途审批单时再次 deploy 被拒绝并有明确提示。
  6. 预检通过并经审批的应用在平台托管环境正常启动运行。
  7. 端到端：在本地 coding agent 对话中以自然语言提出部署诉求（表述不含特定产品名，DEV-03），agent 凭技能包 + CLI + MCP 完成应用包声明补全 → deploy → 预检失败修复 → 审批状态跟踪，全程开发者不离开本地对话。
  8. 非 owner 的个人 key 对既有应用 deploy 被拒绝并提示归属。
  9. 含改/删列的迭代 deploy 未经显式确认被预检拒绝；确认后进入管线，且迁移前自动留快照。

**DEV-05 bisheng dev 本地运行与平台身份注入**
- 需求描述：应用永远只读平台注入的身份信息、不对外提供登录页。`bisheng dev` 在本地运行应用并注入与线上同构的平台身份：注入身份 = 开发者本人（经个人 key 换取），本地与线上应用代码零差异。不提供模拟其他用户身份（与 §5.1 模拟视角同口径）。本地运行期应用经 SDK / MCP 调用的平台能力按开发者本人权限放行，权限边界与线上一致（NFR-1）。
- 验收要点：
  1. `bisheng dev` 下应用取到的身份为开发者本人，注入结构与线上一致、应用代码零差异；不存在指定其他用户身份的入口。
  2. 本地运行中应用调用知识库检索等平台能力，结果按开发者本人权限过滤。
  3. 应用代码中不存在登录页与自建鉴权逻辑，身份唯一来源为平台注入（NFR-1.3）。

**DEV-06 导入应用的改码权归属与交接**
- 需求描述：本地开发的应用导入纳管后，「谁改代码」默认不变——仍是开发者在本地改，改完 `bisheng deploy` 重新发布，改到满意再 deploy 即可，与「本地写代码 → push 发布」的日常开发方式一致。平台只保存每次 deploy 推上来的版本快照：应用运行、代码玻璃盒展示的都是最新已发布版本，本地的中间改动对平台不可见、也无需感知。
- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 改码权归属区 | 工作台该应用发布面（WB-14） | 当前归属状态标识（本地开发者 / 平台管家）+ 「交接给管家」或「收回到本地」按钮（按当前状态二选一展示） |
| 交接确认弹窗 | 「交接给管家」按钮 | 明示「交接后本地 `bisheng deploy` 将失效，此后在工作台对话里提需求由管家改码」 |
| 收回确认弹窗 | 「收回到本地」按钮 | 明示「收回后管家退回只读，本地 `bisheng deploy` 恢复可用」 |
| CLI 侧拒绝提示 | 改码权在管家时执行 `bisheng deploy` | 提示「改码权已交接平台，需先在发布面收回」（本条） |

- 状态：

| 改码权归属 | 进入条件 | 该状态下可做什么（谁） | 去向 |
|-----------|---------|----------------------|------|
| 在本地（默认） | 导入即默认；owner 收回后 | 本地 deploy 可用（owner）；平台侧管家对该应用只读、不改码；资源/数据面、运行日志、发布面的版本 / 审批状态 / 可见范围 / 停运等运营动作照常可用（与平台内应用一致） | 交接 → 在管家 |
| 在管家 | owner 交接后 | 与平台内造的应用一样，在工作台对话里提需求由管家改码（owner）；本地 deploy 被拒绝并提示 | 收回 → 在本地 |

- 流程：
  - 交接：① owner 在发布面点「交接给管家」→ ② 确认弹窗确认 → ③ 即时生效并计审计，本地 deploy 自此失效。
  - 收回：① owner 在发布面点「收回到本地」→ ② 确认弹窗确认 → ③ 即时生效并计审计，管家退回只读、本地 deploy 恢复。
- 规则与边界：
  - 同一时刻只能有一头能改码（本地 deploy 与平台管家互斥），防止本地与平台同时改、互相覆盖。
  - 交付时序：本册先行交付、PRD-2 造应用工作台（管家）未上线期间，改码权恒为「在本地」——发布面不出现改码权归属区与交接入口，GOV-09 列表的改码权归属列恒为「本地」；交接/收回机制随 PRD-2 管家上线启用。
  - 交接与收回均仅由 owner 发起，均计审计。
  - 交接与收回本身不改代码与能力声明、不产生发布，也就不产生审批单。
  - 存在在途审批单时，交接与收回被拒绝，提示先撤回或待审批出终态（RT-03）。
  - 交接后该应用具备工作台草稿沙箱，审批人预览试用的承载随之切换为草稿沙箱（RT-03）。
- 验收要点：
  1. 未交接时，平台工作台对该应用无改码入口，管家不产生任何代码改动；数据面、运行日志与发布面运营动作照常可用。
  2. owner 交接后，可在工作台对话迭代该应用；此时本地 deploy 被拒绝并提示「需先收回改码权」；收回后本地 deploy 恢复可用。
  3. 应用当前改码权归属及每次交接/收回在审计中可查。
  4. 存在在途审批单时发起交接/收回被拒绝并有明确提示。

  ※ 交付时序：本册单独交付期间验「改码权恒为在本地、发布面无交接入口」即达标；验收 2、4 及验收 3 的交接/收回部分随 PRD-2 管家上线验收。

**DEV-07 bisheng-sdk（代码面）**
- 需求描述：Python 首发的 bisheng-sdk 提供五件套薄封装，是平台能力的代码面供给：

| 模块 | 用途 | 权限/边界要点 |
|------|------|--------------|
| auth | 读平台注入身份 | 身份唯一可信来源是平台注入（NFR-1.3） |
| retrieve | 知识库检索 | 托管运行期：结果 = 能力声明知识库 ∩ 当前访问用户可见范围（文件级、fail-closed，详 GOV-05）；本地 dev 期按开发者本人权限（DEV-05） |
| chat | 模型调用 | 可用模型范围 = 能力总线配置（GOV-05） |
| storage | 附件文件存取 | 平台托管存储 |
| appdb | 应用数据库读写 | 应用自有数据库 |

  存量本地项目按需引入 SDK；平台内模板生成的应用预接线同一 SDK——本地手写的与平台内生成的应用是同一套调用范式。

  随 SDK 发布开发者指南（安装、五件套用法、与技能包/CLI 的配合）。
- 验收要点：
  1. 五件套 API 可用：auth 取到平台注入身份、retrieve 结果受调用者权限过滤、chat 可调平台托管模型、storage 可存取附件、appdb 可读写应用数据库。
  2. 平台内模板生成的应用与按需引入 SDK 的本地应用使用同一调用范式（抽查关键调用一致；依赖 PRD-2 WB-01 模板交付，前置依赖声明见 §1）。
  3. 开发者指南随版本发布，按指南可走通 login → dev → deploy 完整流程。

### 3.2 应用运行时与发布（RT）

**本域交付：应用发布后「跑起来、被找到、被用起来」的全部行为——统一入口、应用广场、版本与回滚、发布审批流、资产持久与稳定性承诺。**

#### 应用状态机（域级约定）

应用生命周期由两条正交状态线描述：**应用态**（应用当前对外可用性）与**审批单态**（单次发布请求的处理进度）；版本记录的终态标注见 RT-05。本小节为域级约定，供 RT / GOV 各条目统一引用，不新增条目编号；GOV-09 应用管理列表的「发布状态」字段引用本枚举。

应用态：

| 状态 | 进入条件 | 该状态下可做什么（谁） | 去向 |
|------|---------|----------------------|------|
| 草稿 | 创建/导入后未曾上线；首发被驳回或撤回后 | 提交发布、`bisheng deploy`、修改草稿（owner） | 首发审批通过且上线成功 → 已上线；显式删除 → 已删除 |
| 已上线 | 首发/迭代/回滚审批通过且上线成功 | 使用（可见范围内用户）；提交迭代/回滚、调整可见范围（owner）；停运（owner / 租户管理员）；标签设置（租户管理员） | 停运 → 已停运；删除 → 已删除 |
| 待上线（配额不足） | 审批通过但上线终检发现实例配额不足（GOV-03） | 配额释放后手动上线（owner，无需重新审批） | 上线成功 → 已上线 |
| 已停运 | owner 或租户管理员停运 | 重新启用（owner / 租户管理员，叠加 GOV-03 配额校验）；提交发布（审批通过仅落为待运行版本，不自动重新启用）；删除（owner） | 重新启用 → 已上线；删除 → 已删除 |
| 已删除 | owner 走显式删除流程（RT-07） | —（仅审计可查） | 终态 |

审批单态：待审 / 通过 / 驳回 / 已撤回 / 已取消（应用删除时在途审批单自动取消，RT-07）。迭代审批被驳回不改变应用「已上线」态——当前版本继续运行，仅待上线版本标记被驳回（RT-03）。

#### 事件触达（域级约定）

跨角色事件「一方动作、另一方需要知道」的触达渠道全文统一为两种，本小节为域级约定、供全册各域条目统一引用——各条目的「通知/提示」措辞均指向此处，不逐条重复：

- **站内消息**：复用平台既有消息通知能力，接收方在工作台「消息提醒」入口（铃铛图标，含未读角标）查看；审批类事件同时进入审批中心待办（GOV-02）。管理后台不设消息面——租户管理员与审批人的消息一律在工作台侧接收。
- **界面自查**：状态与结果在固定界面常驻可查（发布面、应用管理列表、「我的 API key」等），随时可达、不依赖消息。

| 事件 | 接收方 | 站内消息 | 自查落点 |
|------|--------|---------|---------|
| 审批单生成（首发/迭代/回滚，含未配置审批人的兜底单） | 审批人（或兜底租户管理员） | ✓（复用审批中心既有触达） | 审批中心待办（RT-03 / GOV-02） |
| 审批通过/驳回 | owner | ✓ | 发布面审批状态区（WB-14）；MCP 应用状态工具（DEV-02） |
| owner 撤回在途审批单 | 已收到待办的审批人 | ✓（复用审批中心既有触达） | 审批中心（RT-03） |
| 应用删除致在途审批单取消 | 审批人 | ✓ | 审批中心（RT-07） |
| 上线终检配额不足、应用入待上线态 | owner、租户管理员 | ✓ | 发布面（owner）；应用管理列表状态筛选（租户管理员，GOV-03 / GOV-09） |
| 配额释放后可手动上线 | owner | —（无主动提示） | 发布面待上线态「手动上线」（GOV-03） |
| 租户管理员停运/重新启用/代调可见范围 | owner | ✓ | 发布面状态与审计记录（RT-07 / GOV-01） |
| 应用 token 强制吊销 | owner | ✓ | 发布面失效提示（GOV-08） |
| 声明能力被收回（模型下线/知识库收回） | owner | — | 发布面/资源面失效提示（GOV-05） |
| 个人 key 签发完成 | 持有人 | —（无主动通知；key 值经签发时一次性展示、由租户管理员转交） | 「我的 API key」列表（DEV-01） |
| 个人 key 被吊销/账号禁用自动失效 | 持有人 | — | 下一次调用被拒（CLI 提示重新 login，DEV-04）；「我的 API key」状态 |
| 应用上架/新获可见权限 | 可见范围内用户 | —（本版不做上新推送） | 应用广场（RT-02）；owner 自行转发入口链接 |

- 本约定只覆盖事件发生时的一次性触达；催办、超时提醒与升级机制本版不做（§5.2）。
- 站内消息为通知性质、不承载操作，处理动作一律回各自界面完成。

**RT-01 统一入口与平台登录复用**
- 需求描述：每个已发布应用拥有内网统一入口 `/apps/{应用标识}`；应用不自建登录，复用 BiSheng 平台既有登录方式（账号密码、SSO 扫码等，与平台登录配置一致），应用自动获得当前访问者的身份与组织信息——应用侧零登录代码。
- 界面与交互（访问分支）：

| 访问者状态 | 系统行为 |
|-----------|---------|
| 已登录平台 + 在可见范围内 | 点开即用、免二次登录，进入应用并注入访问者身份与组织信息 |
| 无登录态（含手机扫码访问） | 重定向到平台登录页（含平台已配置的 SSO 方式），登录成功后回跳原应用地址 |
| 已登录平台 + 无可见范围权限 | 进入统一「无权限」页 |

- 界面与交互（四类兜底页）：

| 兜底页 | 触发场景 | 页面要素 |
|--------|---------|---------|
| 无权限页 | 已登录但不在应用可见范围内 | 应用名与 owner + 无访问权限文案 + 引导联系应用 owner 或租户管理员开通权限（与已停用页指引口径一致） + 「返回广场」按钮；本版不含在线申请入口 |
| 未部署工场引导页 | 本环境未启用应用工场运行时层（GOV-07） | 「本环境未启用应用工场」文案 + 引导联系平台超管开启 |
| 已停用页 | 应用处于已停运态（RT-07） | 应用名 + 已停用提示 + 引导联系应用 owner 或租户管理员 + 「返回广场」按钮 |
| 应用不存在页 | 访问已删除应用的存量链接/二维码，或从未上线（草稿/待上线态）应用的入口地址 | 「应用不存在或未上线」文案 + 「返回广场」按钮 |

- 验收要点：
  1. 已登录平台的用户点开应用链接直接进入，无二次登录。
  2. 应用内能正确取得当前访问者身份与组织信息（如应用内显示当前访问者姓名/部门）。
  3. 无登录态的浏览器扫码访问，重定向到平台登录页（含平台已配置的 SSO 登录方式），登录成功后直达原应用。
  4. 无可见范围权限的用户访问入口得到统一「无权限」页，页面含 owner 与开通指引。
  5. 已删除应用的存量入口链接/二维码访问得到「应用不存在或未上线」页，不落报错页。

**RT-02 应用广场**
- 需求描述：已发布应用进入应用广场，与工作流/助手并列呈现，接入广场既有的标签分类体系；用户只看到自己可见范围内的应用，从广场直接进入使用。
- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 广场应用卡片 | 应用广场（与工作流/助手卡片同构） | 图标、应用名、一句话描述、标签、owner；点击卡片进入使用 |
| 标签筛选 | 应用广场既有筛选区 | 筛选行为与既有广场一致；未设标签的应用在默认分类中正常可见 |

- 规则与边界：
  - 应用与工作流/助手共用同一套标签体系，复用现有标签机制与打标交互，不新建标签体系。
  - 标签设置入口唯一：应用管理列表（GOV-09），由租户管理员为应用关联/变更标签；owner 侧不提供自助打标。
  - 未设标签不影响应用进入广场与默认分类可见。
  - 应用元信息（名称/描述/图标）来源：CLI 导入应用取自 bisheng-app.yaml、随 deploy 更新（deploy 本身走审批，DEV-04）；平台内造应用在对话/发布面生成，owner 可在发布面修改。
  - 元信息不属能力声明：修改不构成发布、不触发审批，修改计审计（GOV-04）。
  - 广场按可见范围过滤，无权限用户的广场中不出现该应用。
- 验收要点：
  1. 应用发布且审批通过后出现在有权限用户的应用广场中。
  2. 租户管理员可在应用管理列表中为已发布应用设置/变更标签（GOV-09）；设置后广场按该标签筛选可见此应用，未设标签的应用在广场默认分类中正常可见。
  3. 无权限用户的广场中不出现该应用。
  4. 从广场可直接打开应用使用。
  5. 广场卡片展示图标/应用名/描述/标签/owner；owner 修改元信息后广场随之更新且不产生审批单，修改计审计。

**RT-03 发布审批流（首发与迭代均需审批）**
- 需求描述：任何发布（首发与迭代）都必须走审批，不存在免审路径（回滚同样以发布审批形式进入同一流程，RT-05）；审批接入平台审批中心，审批人在审批中心处理应用发布审批单（场景接入与审批人配置见 GOV-02）。
- 流程：
  1. owner 提交发布（工作台发布面或 `bisheng deploy`）；首发提交时校验租户实例配额，超限即拒（GOV-03，迭代发布替换已运行实例、不受此限）。
  2. 冻结生成待上线版本快照（审读的权威对象）。
  3. 发布前安全扫描——与 CLI deploy 同一管线同一门，规则集见 DEV-04。产物含裸密钥/连接串即阻断发布：平台内应用 → 回流管家改写；CLI 应用 → deploy 原地失败并输出命中规则与文件位置（不含密钥值本身，NFR-2），本地修复后重新 deploy。
  4. 生成审批单，进入平台审批中心；审批人收到站内消息与待办（§3.2 事件触达）。
  5. 通过 → 上线终检（实例配额，GOV-03）：终检通过 → 上线、进入广场；终检配额不足 → 应用入「待上线（配额不足）」态（见域级应用状态机），配额释放后 owner 手动上线、无需重新审批。
  6. 驳回 → 首发：应用回草稿态；迭代：应用保持已上线、当前版本继续运行，仅待上线版本标记被驳回。owner 在发布面可见驳回状态与理由，修改后重新提交生成新审批单。
- 界面与交互（审批单详情页，位置：平台审批中心-应用发布场景-审批单详情）：

| 区块 | 内容 |
|------|------|
| 头部基本信息 | 应用名、owner、来源（平台内造 / CLI 导入）、类型标识（首发 / 迭代 / 回滚 → 目标版本）、提交时间 |
| 能力声明白话摘要区 | 待上线版本的能力声明白话摘要（定义见 RT-04） |
| 可见范围区 | 提交时快照，标注「仅供参考，可见范围变更即时生效、不经审批」（GOV-01） |
| 资源档位区 | 所选资源档位（GOV-03） |
| 迭代变更摘要区 | 迭代/回滚时呈现相对上一已发布版本的四类变更、分行展示（RT-04）；无变更时显式展示「无变更」 |
| 操作区 | 通过、驳回（驳回理由必填）、「查看待上线版本」审读视图入口 |

- 界面与交互（审读视图）：左侧文件树 + 右侧只读代码内容；tab 承载能力声明完整清单 / 版本历史 / 文件差异（迭代时，呈现方式同 WB-15 差异查看）；「预览试用」按钮置顶。
- 预览试用：审批人入口一致，按该应用当前有无草稿沙箱（即改码权是否在平台管家，DEV-06）分两种承载：

| 承载判定 | 承载方式 | 生命周期 | 配额计入 |
|---------|---------|---------|---------|
| 有草稿沙箱（平台内造，或 CLI 导入且已交接管家） | 复用 owner 的草稿沙箱直接打开预览，不为审批单独起实例；审批期间草稿已有新改动、与待上线版本不一致时，预览处明确提示 | 随草稿沙箱 | 不涉及 |
| 无草稿沙箱（CLI 导入且改码权在本地） | 以待上线版本快照拉起审批期临时预览实例（复用 deploy 预检启动探活的同一能力），连应用草稿库 | 审批人按需拉起；审批出终态（通过/驳回/撤回/取消）即回收；长期未处理超时回收（默认 7 天，部署配置项）；回收后可再次拉起 | 不计入租户应用实例数配额（GOV-03） |

- 临时预览实例界面状态：

| 状态 | 界面表现 | 去向 |
|------|---------|------|
| 未拉起 | 「拉起预览」按钮 | 拉起 → 拉起中 |
| 拉起中 | 进度展示；失败时展示失败原因 | 成功 → 运行中；失败 → 未拉起（可重新拉起） |
| 运行中 | 「打开预览」+「手动回收」操作 | 审批终态 / 超时 / 手动回收 → 已回收 |
| 已回收（含超时回收） | 「重新拉起」按钮 | 拉起 → 拉起中 |

- 规则与边界：
  - 审读的权威对象 = 提交发布时冻结的待上线版本快照。
  - owner 的草稿对话不对审批人开放（WB-16）；审批人不获得工作台草稿入口。
  - 审批期间 owner 可继续对话改草稿，改动不影响已提交的待上线版本。
  - 同一应用同时至多一个在途审批单；再次提交须先撤回在途审批单。
  - 审批人预览身份与数据边界：注入身份 = 审批人本人；平台能力按 owner 权限放行（审批例外条款、计审计，NFR-1.2）；草稿库对审批人可写入试用数据。
  - 审批期试用数据归宿：平台内应用发布时「保留」的范围冻结为提交发布时刻的草稿库快照，审批期新增试用数据一律不带入生产（RT-06）；CLI 导入应用首发生产库默认空库初始化。
  - 审批单催办/超时提醒本版不做（§5.2）；紧急场景的应急路径 = 停运即时止血（RT-07，无需审批）+ 回滚走正常审批恢复（RT-05）。
- 验收要点：
  1. 除审批人经审读视图与预览试用外，首次发布的应用在审批通过前不可被任何其他用户访问。
  2. 审批人可在审批单中看到能力声明摘要、可见范围与资源档位，并可打开待上线版本的只读审读视图（代码、能力声明完整清单、版本历史；迭代时含相对上一已发布版本的文件差异）。
  3. 平台内应用：审批人可从审读视图打开草稿沙箱预览试用；草稿与待上线版本不一致时预览处有明确提示。审批人不可见草稿对话，也不获得工作台草稿入口。
  4. 驳回后 owner 在发布面可见驳回状态与理由，可修改后再次提交。
  5. 提交的产物含明文密钥/连接串时发布被阻断，且分路径处置到位：平台内应用 → 阻断并回流管家改写；CLI 导入应用 → deploy 失败并返回命中项与整改指引（与 DEV-04 验收口径对齐）。
  6. 审批中 owner 可撤回审批单；撤回后修改再提交生成新审批单。
  7. CLI 导入应用：审批人可从审读视图以待上线版本快照拉起临时预览实例试用；审批出终态后实例被回收；该实例不占用租户应用实例数配额。
  8. 审批人预览期间应用以审批人身份注入、平台能力按 owner 权限放行，预览行为计审计。
  9. 临时预览实例超时回收后可再次拉起（超时时限取部署配置）。
  10. 迭代审批被驳回时应用保持已上线、当前版本继续服务，仅待上线版本被弃。

**RT-04 迭代发布审批与能力声明定义**
- 需求描述：本条给出能力声明的权威定义（全文唯一出处），并约定迭代发布的审批要求与迭代审批单的变更摘要呈现。

> **能力声明** = 应用声明接入的平台能力显式清单：知识库、模型、密钥引用等总线能力。WB-14 发布面与 RT-03 审批单两处展示同源于此。

- 术语统一：发布面展示 = 能力声明完整白话清单（WB-14）；审批单展示 = 能力声明白话摘要；审读视图展示 = 能力声明完整清单。全文按此措辞。
- 迭代审批单变更摘要（在首发审批单内容——能力声明摘要 + 可见范围 + 资源档位——之上，额外呈现相对上一已发布版本的变更摘要，供审批人快速判断）：

| 变更类别 | 说明/回链 |
|---------|----------|
| 能力声明变更 | 含新增密钥引用 |
| 可见范围变更 | 相对上一次审批单快照，仅供审批人参考——可见范围变更即时生效、不经审批、仅计审计（GOV-01） |
| 表结构变更 | WB-09 / RT-05 |
| 资源档位变更 | GOV-03 |

  四类均无变更时，摘要区明确展示「无变更」。

- 规则与边界：
  - 从企业安全出发，每次迭代发布均需审批，不存在免审路径。
  - 「发布后迭代 = 继续对话」仅指改动过程无需打开工程；上线生效仍以审批通过为准。
  - 可见范围变更不经审批、即时生效、计审计（GOV-01 / GOV-04）。
- 验收要点：
  1. 未改能力声明与可见范围的迭代发布同样生成审批单，审批通过前新版本不上线。
  2. 迭代审批单中可见相对上一版本的四类变更摘要；无变更时显示「无变更」。
  3. 新接入知识库、新增密钥引用、可见范围变更均在审批单变更摘要中明确呈现；审批单中呈现的可见范围变更摘要以提交时快照为基线。

**RT-05 版本与回滚语义**
- 需求描述：版本记录于提交发布时生成，并标注终态（已上线 / 被驳回 / 已撤回）；回滚 = 基于历史版本前向新建一条版本记录（非原地覆盖），部署历史线性、全程可审计。
- 回滚处置（各资产对象是否随回滚回退）：

| 资产对象 | 是否随回滚回退 | 说明 |
|---------|--------------|------|
| 代码 | 回退 | 与能力声明、平台注入配置作为同一个版本快照统一回退，杜绝「回退代码却留下新配置」；代码/配置回滚无损 |
| 能力声明 | 回退 | 同一快照统一回退 |
| 平台注入配置 | 回退 | 同一快照统一回退 |
| 资源档位 | 回退 | 档位入版本快照、随回滚回退（CLI 路径档位本就声明在应用包内，DEV-04）；回滚审批单中呈现档位变更 |
| 生产数据 | 不回退 | 默认不回滚 |
| 可见范围 | 不回退 | 不属版本快照，回滚后保持当前设置 |

- 结构演进（结构变更随迭代发布生效的确定规则）：

| 变更类型 | 确认时机 | 发布时行为 |
|---------|---------|-----------|
| 加列 | 无需确认 | 自动迁移 |
| 改/删列 | 工作台路径：草稿期 WB-09 闸口确认；CLI 路径：deploy 时显式确认（DEV-04） | 发布时不再二次确认；在发布摘要中展示；迁移前自动留生产数据快照 |

- 界面与交互（回滚发起）：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 版本列表 | 工作台发布面（WB-14 / WB-15） | 全量展示全部版本记录：版本号、类型（首发 / 迭代 / 回滚 → vN）、提交时间、终态标注（已上线 / 被驳回 / 已撤回）；曾上线版本行上提供「回滚到此版本」按钮 |
| 回滚确认弹窗 | 版本列表「回滚到此版本」按钮 | 目标版本号 / 时间 / 该版本能力声明摘要 + 明示「将生成回滚审批单、审批通过后生效」「生产数据不回滚」 |
| 在途回滚单展示 | 发布面审批状态区 | 提交后显示在途回滚审批单；审批单头部类型标识「回滚 → vN」（RT-03） |

- 规则与边界：
  - 回滚同样提交发布审批，审批单标注回滚及目标历史版本；回滚审批单进入 GOV-02 配置的同一审批链。
  - 回滚仅 owner 在发布面发起；租户管理员的应急处置手段 = 停运（RT-07）。
  - 回滚目标仅限曾上线版本；被驳回/已撤回版本留在版本列表供追溯，不可选作回滚目标。
  - 提交回滚前须先撤回在途审批单（单一在途，RT-03）。
- 验收要点：
  1. 回滚操作后版本列表新增一条记录（指向历史版本内容），历史记录不被覆盖或删除。
  2. 回滚后应用的代码与能力声明均恢复到目标版本，注入配置不残留新版本内容。
  3. 回滚不改变生产库中的业务数据。
  4. 含改/删列的结构变更在迭代发布时自动留有迁移前快照并在发布摘要中展示（确认已在草稿期 WB-09 闸口或 CLI deploy 显式确认环节完成，发布时不二次确认）。
  5. 回滚产生标注为回滚的审批单，审批通过后生效；回滚后可见范围保持回滚前设置。
  6. 被驳回/已撤回的版本留在版本列表并标注终态，不可被选作回滚目标。
  7. 非 owner 用户无回滚发起入口。

*（RT-06 预览自测数据发布去留：工作台预览流程专属条目，见 PRD-2 §3.3。）*

**RT-07 代码资产持久与显式删除**
- 需求描述：应用的运行实例只是可随时回收的执行体、自身不保存任何唯一数据——代码、对话、应用数据的真身恒在平台存储（每轮代码版本 WB-15 + 发布版本快照 RT-05 双保险）；删除唯经「显式删除应用」流程，除此不存在任何资产删除路径。
- 操作表：

| 动作 | 发起人 | 入口 | 确认 | 审计 | 生效表现 |
|------|--------|------|------|------|---------|
| 停运 | owner / 租户管理员 | owner：发布面运营动作区（WB-14）；租户管理员：应用管理列表（GOV-09） | 二次确认（明示入口与广场将呈已停用） | 计审计 | 入口与广场呈「已停用」页（RT-01）；资产不受影响 |
| 重新启用 | owner / 租户管理员 | 同停运 | — | 计审计 | 恢复访问；叠加 GOV-03 实例配额校验 |
| 显式删除 | 仅 owner（租户管理员不可删除，处置手段 = 停运；owner 离职场景回链 §5.2 归属转移） | 发布面底部危险操作区（WB-14） | 二次确认弹窗：输入应用名确认 + 明示删除范围（代码/对话/应用数据全部删除、不可恢复）+ 删除动作计审计提示 | 计审计 | 资产删除，应用入「已删除」终态；存量入口链接/二维码访问呈「应用不存在或未上线」页（RT-01） |

- 规则与边界：
  - 只回收执行体、不触碰存档与版本记录的场景：应用停运、闲置回收、实例崩溃、工场运行时层整体不部署（GOV-07）。
  - 存档随平台数据一同备份。
  - 删除时在途审批单自动取消（入「已取消」态，§3.2 审批单态）并站内消息通知审批人（§3.2 事件触达）。
  - 停运态允许提交发布；审批通过仅落为待运行版本、不自动重新启用；重新启用时叠加 GOV-03 配额校验（见域级应用状态机）。
- 验收要点：
  1. 应用停运/实例回收后重新启用，代码、对话历史、生产数据完整无损。
  2. 除显式删除流程外，不存在任何导致应用资产被删的操作路径。
  3. 显式删除需二次确认，删除动作在审计记录中可查。
  4. 停运期间访问入口与广场呈已停用提示，重新启用后恢复。
  5. 租户管理员发起删除被拒（其处置手段仅停运可用）；owner 删除后在途审批单自动取消且审批人收到站内消息通知。
  6. 停运态提交发布，审批通过后应用不自动启用，重新启用后新版本生效。

**RT-08 稳定性承诺（产品级）**
- 需求描述：应用与平台、应用与应用之间运行隔离：单个应用崩溃只影响该应用自身并自动恢复，平台其余功能与其他应用不受影响——「应用可以不稳定，平台必须正常」。新版本上线/回滚生效的切换期间，应用入口呈短暂「发布中」提示、不落报错页，切换完成自动恢复；应用崩溃后的自动恢复窗口内，入口同构呈「应用恢复中」提示、不落报错页。
- 验收要点：
  1. 人为使某应用崩溃，平台主功能与其他应用访问正常。
  2. 崩溃应用在无人工干预下 5 分钟内自动恢复可用（本承诺同时列为 NFR-6）。
  3. 版本切换窗口内访问应用不出现报错页，切换完成后自动恢复正常访问。
  4. 崩溃-恢复窗口内访问应用入口得到「应用恢复中」提示而非报错页。

*（RT-09 iframe 嵌入升级（postMessage 协议 + 域名白名单）：平台既有嵌入能力的独立安全修复（修社区 #1705），与应用工场无功能依赖，不随本册交付，顺延登记于 §5.2。）*

### 3.3 治理与管理面（GOV）

**GOV-01 权限资源类型与授权交互**
- 需求描述：应用可见范围授权复用平台现有通用授权交互（按用户/部门/用户组授予），由 owner 从发布面弹窗发起（WB-14）。工作台会话与管家同为平台权限体系的资源类型，其授权语义见 PRD-2 对应条目与上游《产品方案》，本条不展开。
- 规则与边界：
  - 常规授权路径唯一入口 = owner 在发布面打开通用授权弹窗（WB-14）。
  - 可见范围变更即时生效（自被授权用户的下一次请求起，作用于入口访问与广场可见性，RT-01/RT-02）、不经审批、计审计（GOV-04）。
  - 在途审批单中的可见范围呈现为提交发布时的快照、标注仅供参考（RT-03）。
  - 可见范围不属版本快照、不随回滚回退（RT-05）；首发默认仅 owner，审批通过后由 owner 在发布面设置（RT-03）。
  - 租户管理员可在应用管理列表行上打开同款授权弹窗，查看并代 owner 调整可见范围（GOV-09），代调整计审计（GOV-04），覆盖误授权紧急收权与 owner 离职等兜底场景。
- 验收要点：
  1. 应用可像其他平台资源一样在通用授权弹窗中按用户/部门/用户组授权。
  2. 授权变更自被授权用户的下一次请求起生效于入口访问与广场可见性（RT-01/RT-02）。
  3. 租户管理员可在应用管理列表打开任一应用的授权关系查看并调整，调整计审计。
  4. owner 变更可见范围不产生审批单，变更事件在审计中可查。

**GOV-02 发布审批场景配置**
- 需求描述：应用发布作为审批中心的新场景接入，租户管理员可配置审批人/审批链（复用审批中心既有配置能力）。首发与迭代每次发布均走审批（RT-03/04），不提供免审配置项。
- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 「应用发布」场景配置 | 管理后台-审批中心-场景配置（新增场景行/卡片） | 审批人/审批链选择（复用审批中心既有配置交互）；未配置时场景行显式提示「未配置审批人，审批单将落到租户管理员」 |

- 规则与边界：
  - 每次发布（首发与迭代）必审，无免审路径与配置项（RT-03/RT-04）；回滚审批单进入同一审批链（RT-05）。
  - 租户未配置审批人时，兜底审批人 = 租户管理员，发布不因未配置而卡死；多名租户管理员时兜底单对全体可见、按或签处理——任一人处理即出终态（复用审批中心既有多候选或签口径）。
  - 审批人候选 = 租户内任意用户（复用审批中心既有口径）。
  - 提交人位于审批链中时自动跳过该审批人、落到其他管理员；全租户仅一名管理员时允许自审，强制计审计标注。
- 验收要点：
  1. 租户管理员可为发布场景配置审批人。
  2. 未配置审批人的租户提交发布（首发或迭代），审批单落到租户管理员。
  3. 提交人在审批链中时该节点被自动跳过；仅一名管理员的租户自审单在审计中带自审标注。

**GOV-03 资源档位与配额**
- 需求描述：平台预置服务器资源档位模板，应用发布时只能从中选档，不提供自定义资源规格；租户级配额仅「应用运行实例数」一项，token 用量不设限制（§5.2）。
- 档位（本版三档；规格为初始默认值，部署配置项提供、平台超管可调整；档位数与命名为开放项，见 §6）：

| 档位 | 规格（部署配置项提供初始默认值） | 白话适用说明 |
|------|---------------------------------|-------------|
| 轻量 | 1 核 CPU / 2 GB 内存 | 适合表单、台账类轻量应用 |
| 标准 | 2 核 CPU / 4 GB 内存 | 适合多数日常业务应用 |
| 性能 | 4 核 CPU / 8 GB 内存 | 适合数据处理量大、访问人数较多的应用 |

- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 资源档位管理 | 管理后台-系统管理页新增「资源档位」tab（平台超管；未部署工场运行时层时不出现，GOV-07） | 档位列表：名称、CPU/内存、适用说明、启用状态、使用中应用数；行内编辑规格与说明；停用档位时提示影响（存量应用不动、发布面不再可选） |
| 租户实例数配额设定 | 多租户部署：管理后台-租户管理页配额弹窗（平台超管，与既有存储配额同弹窗并列）；单租户部署（无租户管理页）：系统管理页「资源档位」tab 内实例配额区 | 各租户实例数上限设定，未设定默认不限（显示「未设置（不限）」）；下调至低于存量时提示「存量不受影响、仅拦新发布与重新启用」 |
| 本租户配额视图 | 「应用工场」入口页「应用管理」tab 顶部用量条（租户管理员，只读，GOV-09） | 本租户实例数已用/上限只读展示，未设上限显示「不限」 |
| 发布时档位选择 | 工作台发布面（WB-14）；CLI 路径在应用包中声明（DEV-04） | 从启用中的预置档位选择，每档展示规格与适用说明 |

- 规则与边界：
  - 只能从预置档位模板中选择，不提供自定义资源规格；单应用单实例，不提供实例数/并发调节（§5.1）。
  - 默认推荐档 = 轻量档：工作台发布面默认选中（WB-14），CLI 路径应用包未声明档位时取此档（DEV-04）。
  - 工场新增配额仅「应用运行实例数」一项；平台既有存储配额照常适用：应用代码存档计入、附件不计入。
  - 配额校验时点：提交发布时预检 + 上线时终检；终检失败 → 审批单保持通过、应用进入「待上线（配额不足）」态（§3.2 应用状态机）并提示 owner 与租户管理员（站内消息 + 界面自查，§3.2 事件触达）；配额释放后 owner 手动上线（无主动提示，经发布面自查）、无需重新审批。
  - 未设定实例配额的租户默认不限，预检与终检放行。
  - 超限拦截范围 = 新发布与重新启用；已运行应用不受影响；配额下调至低于存量时，存量不受影响、仅拦新增动作。
  - 档位停用只拦新选择，存量应用沿用原档位继续运行与迭代；规格调整自应用下一次发布/重新启用生效。
  - 审批期临时预览实例不计入租户实例数配额（RT-03）。
  - token 用量只计量不设上限（按 key 账单，GOV-04），精细成本控制本版不做（§5.2）。
- 验收要点：
  1. 资源档位模板由平台预置、平台超管可调整规格与启用状态；发布时业务人员只能从预置模板中选择，不存在自定义资源规格与实例数/并发调节入口。
  2. 租户实例数配额超限后，新发布与重新启用被拦截并有明确提示；已运行应用不受影响。
  3. 配额下调至低于存量后，已运行应用不受影响，新发布与重新启用被拦截。
  4. 审批通过但配额不足的应用进入待上线态并提示；配额释放后 owner 手动上线成功、无需重新审批。
  5. 档位停用后存量应用照常运行与迭代发布，新发布不可再选该档位。
  6. 未设定实例配额的租户发布不被配额拦截，配额设定处显示「未设置（不限）」。

**GOV-04 全链路审计**
- 需求描述：应用工场全生命周期动作与用量全链路留痕：从造应用、接能力、发布运维到密钥与 key 事件，审计记录可在管理面查询，用量账单按 key 归属。
- 审计事件清单（每类记录至少含操作人/时间/对象/动作/结果；「关键记录内容」列仅列该类特有要素）：

| 事件类别 | 来源条目 | 关键记录内容 |
|---------|---------|-------------|
| 造应用（谁造了什么应用） | WB（平台内造）/ DEV-04（CLI 导入） | 创建/导入动作、应用名 |
| 接入知识库/模型等能力 | GOV-05 | 应用、能力声明变更内容 |
| 应用运行期能力调用（检索/模型） | GOV-05 / GOV-08 | 双归属：actor = 应用（应用 token），subject = 当前访问用户——同时回答「哪个应用调的」与「以谁的名义调的」 |
| 访问记录（谁在用） | RT-01 | 访问用户、应用、访问时间 |
| 生产数据行编辑 | WB-06 | 应用、数据对象、编辑动作 |
| 发布/回滚/删除动作 | RT-03/05/07 | 应用、版本、动作结果（含停运/重新启用） |
| 密钥录入与吊销事件（不含值） | WB-05 | 密钥引用名、动作；不记录密钥值 |
| 改码权交接与收回 | DEV-06 | 交接双方、应用 |
| 按 key 的用量账单 | DEV-01 / GOV-08 | key 归属（个人 key 归持有人、应用 token 归应用）、时间段、token 用量、调用次数 |
| key 签发/scope 调整/吊销/自动失效 | DEV-01 / GOV-08 | key 类型与掩码、动作、失效原因 |
| 可见范围变更 | GOV-01 | 变更人（owner 或代调整的租户管理员）、应用、变更内容 |
| 元信息修改、标签设置 | RT-02 | 对象、变更前后内容（应用工场权限点变更走既有角色审计，GOV-07） |

- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 审计查询面 | 管理后台-审计页（扩展既有审计页，新增上表事件类型枚举） | 筛选器：时间范围、操作人、事件类型、对象应用，平台超管视角另有租户筛选；列表列：时间/操作人/对象/动作/结果（超管视角含租户列）；支持导出 |
| 按 key 用量账单 | 管理后台-API key 管理页行内「用量」入口（GOV-08 / DEV-01） | key 掩码、持有人、时间段筛选、token 用量、调用次数；支持按模型拆分（模型名即平台原名） |

- 规则与边界：
  - 审计记录不出现密钥明文等敏感值（NFR-2）。
  - 查询权限：租户管理员可查本租户全部事件；跨租户查询仅平台超管——经审计页租户筛选，或经租户管理视图切至目标租户查看（含该租户 API key 管理页的按 key 账单，矩阵注）。
  - key 持有人经工作台账户菜单「我的 API key」查本人 key 用量（DEV-01）。
  - owner 应用侧审计/访问记录自查本版不提供（§5.2）。
- 验收要点：
  1. 上述每类事件发生后在审计面可查到记录（操作人/时间/对象/动作）。
  2. 审计记录中不出现密钥明文等敏感值。
  3. 用量账单可按 key 归属查询。
  4. 租户管理员查询不到其他租户的审计事件；平台超管可跨租户查询。
  5. key 持有人可查本人 key 用量账单，不可查他人。

**GOV-05 能力总线配置（管理员）**
- 需求描述：能力总线 = 应用消费平台能力的统一通道，核心承诺「配置一次、声明使用、零新建配置面」：底层账号与端点只在管理面配置一次，应用经能力声明获得使用权（发布审批即授权，RT-03/04），业务人员与 AI 均不接触底层账号与端点。本版总线范围 = 模型、知识库、密钥引用三项，配置动作全部复用既有界面、不新建配置页：
- 界面与交互：

| 能力项 | 谁在哪配置 | 应用如何获得使用权 |
|--------|-----------|-------------------|
| 模型 | 租户管理员在既有模型管理页配置服务商凭据并启用模型——按租户配置一次，租户内助手/工作流与工场应用共享同一份，无需为工场重复配置 | 应用在能力声明中写模型名（即模型管理页原名，无逻辑档位转换，DEV-03），审批通过后由平台在运行时注入调用通道 |
| 知识库 | 无新增配置动作：建库与授权走既有知识库管理与权限体系 | 应用在能力声明中声明接入的知识库，审批通过 = 应用侧授权；运行时应用内检索可及范围 = 能力声明知识库（显式白名单收窄）∩ 当前访问用户可见范围（逐资源鉴权、含文件级权限，NFR-1）——两层缺一不可，检索范围规则详见「规则与边界」 |
| 密钥引用 | owner 在工作台密钥子页录入应用自有第三方凭证（PRD-2 WB-05） | 引用名进入能力声明（RT-04），运行时按引用注入值，密钥值零暴露（NFR-2）。造应用引擎自身的模型凭据另见凭据档案（PRD-2 GOV-06），与应用能力声明无关 |

- 规则与边界：
  - 「集成管理」只在管理面，不进工作台；工作台（造应用侧）无任何底层账号/端点配置入口。
  - 知识库检索范围规则（与《3.0 开放 API 鉴权与身份传递 PRD》同一口径）：
    - 两层过滤 = 声明层 + 用户层：声明层是显式白名单收窄——未声明的知识库对应用整体不可及，即使当前访问用户本人有权限；用户层是按当前访问用户身份的逐资源鉴权（纯替换语义——声明范围内，结果与该用户在平台内自行检索完全一致，不多给也不少给）。
    - 口径澄清：声明层是对显式白名单的收窄，不涉及对两个主体可见集求交，与《开放 API 鉴权与身份传递 PRD》§4.4.4 否决的「权限取交集」不是一回事——该 PRD 的同构机制即「资源白名单 + 纯替换」，两文档口径一致。
    - 过滤强度：文件级，与平台工作台检索同一条双层过滤路径（索引层预过滤 + 结果层批量校验兜底，同 DEV-02 口径）。
    - fail-closed（NFR-1.4）：无法取得当前访问用户身份 → 检索拒绝，绝不回退为按应用声明全量放行；权限评估失败 → 明确错误态，绝不返回未过滤或部分过滤的结果集。
  - 能力收回后行为：已上线应用声明使用的能力被收回（模型下线、知识库删除或权限收回）时，应用对该能力的调用得到明确错误态、不回退旧值、应用整体保持可用；owner 在发布面/资源面可见失效提示（与 WB-05 密钥吊销同语义）。
- 验收要点：
  1. 租户管理员在管理面完成一次能力配置后，域内应用无需再配即可声明使用。
  2. 工作台（造应用侧）不存在任何底层账号/端点配置入口。
  3. 生产实例实际可用能力 = 其声明且经审批的能力集合，未声明能力不可调用；草稿/预览期按「已声明 + owner 本人权限」放行（未发布可完整试用，WB-04）。
  4. 收回某已上线应用声明的能力后，该能力调用返回明确错误态、应用其余功能可用，owner 可见失效提示。
  5. 用户本人有权限、但应用能力声明未包含的知识库，经该应用不可检索（声明层白名单生效）。
  6. 应用已声明、但当前访问用户无权限的知识库内容（含库内无权文件）不出现在该用户的检索结果中；声明范围内的检索结果与该用户在平台内自行检索的结果集合相等。
  7. 人为使权限引擎不可用，应用内检索得到明确错误态，而非未过滤或部分过滤的结果（NFR-1.4）。

*（GOV-06 引擎与凭据档案配置：造应用引擎专属条目，见 PRD-2 §3.3。）*

**GOV-07 应用工场权限控制与可选部署**
- 需求描述：应用工场的启用范围由两层控制：租户内走平台既有角色权限体系（「应用工场」菜单可见性 + 「新建应用」权限点，零新增开关页与新概念）；部署级可选让不需要工场的客户不装工场运行时层，平台其余功能行为零变化、无新增常驻负担。
- 两层控制：

| 层 | 控什么 | 配置位置 | 关闭/不装后的行为 |
|----|--------|---------|------------------|
| 角色权限（租户内） | 「应用工场」菜单可见性与「新建应用」权限点，两个独立配置项 | 管理后台-系统管理-角色权限（既有角色配置面新增，变更走既有角色审计） | 无「新建应用」权限：不见新建入口、CLI 首发 deploy 被拒，既有应用的运行、访问、迭代与管理入口不受影响；菜单被隐藏：进不了应用工场页，既有应用照常运行、同事访问与广场使用不受影响（使用面权限走应用可见范围，RT-01/RT-02），恢复管理入口需管理员调整其角色菜单权限 |
| 部署开关 | 工场运行时层 | 部署配置 | 工作台与应用广场入口不出现；应用链接呈统一引导页；平台其余功能行为零变化；无新增常驻负担 |

- 三层部署形态（层内技术构成见上游《产品方案》§4，本表只写行为差异）：

| 层 | 用户可感知能力 | 可否独立部署 |
|----|---------------|-------------|
| 平台核心 | 平台既有全部功能 | 基座，必装 |
| 开放能力层 | 个人 API key、模型双协议接入、MCP 工具面 | 可独立于工场运行时层部署（不装工场也可用） |
| 工场运行时层 | 应用托管运行、应用广场、发布管线 | 可整层不装 |

- 规则与边界：
  - 「新建应用」权限只控新建入口（工作台新建按钮与 CLI 首发 deploy 同口径），不影响既有应用的运行、访问、迭代发布与 owner 管理入口。
  - 灰度放量 = 运营上按角色开权限：上线初期只给试点角色勾「新建应用」，放量即扩到更多角色，不另设独立开关。
  - 菜单与新建权限可独立组合：只给菜单不给新建 = 该角色可管理存量应用、不可新建。
  - 部署/升级后的默认值：「应用工场」菜单默认仅租户管理员角色开启（保证治理面可达），「新建应用」权限全角色默认关闭；开通 = 租户管理员为目标角色勾选（即灰度放量动作）；存量环境升级同此默认。
  - 未部署工场运行时层时，访问应用路径呈统一引导页（RT-01），不报错。
  - 开放能力层可独立部署：不装工场也可用个人 API key / 模型双协议接入 / MCP（DEV-01/DEV-02）。
  - 未部署开放能力层时，个人 API key 相关入口整体不出现：管理后台「API key 管理页」与工作台账户菜单「我的 API key」均不展示（DEV-01 / GOV-08）。
- 验收要点：
  1. 无「新建应用」权限的用户看不到新建入口；其既有应用的运行、访问、迭代发布与工作台管理入口不受影响。
  2. 未部署工场运行时层的环境中，平台既有功能回归测试全部通过、行为无变化。
  3. 未部署工场时访问应用路径得到统一引导页而非报错。
  4. 仅部署开放能力层时，个人 API key、模型协议接入、MCP 工具面可正常使用。
  5. 无「新建应用」权限用户的 CLI 首发 deploy 被拒并有明确提示；其已导入应用的迭代 deploy 正常。
  6. 未部署开放能力层的环境中，管理后台 API key 管理页与工作台账户菜单「我的 API key」入口均不出现。
  7. 角色菜单权限未含「应用工场」菜单的用户看不到该菜单；其既有应用的运行与他人访问不受影响。

**GOV-08 API key 三类体系与开放 API 鉴权改造**
- 需求描述：平台 API key 分个人 key、应用 token、会话 key 三类，签发/分配/吊销归管理面；既有 v2 开放 API 从「内网可信」模型改为 key 鉴权。本条为总纲：v2 开放 API 鉴权改造的细化需求与验收以同目录《3.0 开放 API 鉴权与身份传递 PRD》为准，两处互链。
- 统一凭据底座（三类 key 与开放 API 密钥同一底座，细化以该 PRD R1 为准）：密码学合格随机源生成；服务端仅存单向哈希（SHA-256）、不用可逆加密、明文不可还原；校验恒时比较 + fail-closed；明文仅签发时一次性展示，此后一切界面只见掩码（掩码口径 = 前缀 + 末四位）；吊销为软撤销、记录保留供审计追溯，撤销主动清缓存、生效上界 5 秒；key 前缀即主体类型（个人主体轨 `bs-pat-`、服务账号轨 `bs-sak-`），前缀模式内置于发布前密钥扫描规则集（RT-03 / DEV-04），并可注册到代码托管平台的密钥扫描规则。
- key 类型（凭据形态映射到该 PRD 的「双轨主体」模型：个人主体轨 / 服务账号轨）：

| 类型 | 凭据形态 | 持有者/主体 | 权限来源 | 签发时机/方式 | 吊销 | 用户感知 |
|------|---------|------------|---------|--------------|------|---------|
| 个人 key | 个人主体轨（`bs-pat-`） | 开发者（自然人） | 动态继承持有人当前权限 ∩ key scope（DEV-01） | 租户管理员在管理面签发（DEV-01） | 管理面/持有人本人吊销；账号禁用自动失效 | 开发者可见掩码 |
| 应用 token | **服务账号密钥（`bs-sak-`）**——应用即一个不可登录的服务账号主体 | 应用（非自然人的一等主体） | 能力声明（发布审批通过即授权，GOV-05），不继承任何自然人权限 | 发布时按能力声明自动签发 | 系统自动管理；管理面可强制吊销 | 对 owner 与使用者零感知；管理面 tab 可查、可强制吊销 |
| 会话 key | 短时效派生凭据 | 工作台会话 | 会话发起人权限 | 随会话自动签发 | 随会话结束自动吊销 | 全程零感知，不设管理界面；事件仅审计可查 |

  应用 token 采用服务账号密钥形态的产品意义：应用的权限锚定在「服务账号 + 能力声明」上、独立于任何自然人——owner 账号被禁用/删除时，其名下个人 key 全部失效（DEV-01），但应用 token 与应用运行不受影响，同事使用不中断（owner 离职的归属接管见 §5.2 归属转移；管理侧兜底手段 = 停运，RT-07）。

- 流程（v2 开放 API 鉴权改造）：
  1. 兼容窗口开启，窗口时长为部署配置项。
  2. 窗口内旧调用方式可用，并记迁移告警；存量调用方须在窗口期内完成迁移——迁移用**服务账号密钥**：为每个存量调用方创建服务账号（不可登录的一等主体）、按最小权限授权后签发密钥，不用任何自然人的个人 key（生产集成不应因某员工离职而中断；个人访问令牌属该 PRD 的 P1 范围，且不面向系统对系统集成）。签发者 = 租户管理员，迁移责任人 = 各调用方 owner；细化见《3.0 开放 API 鉴权与身份传递 PRD》R4 / R8。
  3. 窗口结束后，未带 key 的调用被拒绝。
- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| API key 管理页 | 管理后台-API key 管理（未部署开放能力层时整页入口不出现，GOV-07） | 个人 key tab（界面构成见 DEV-01）；应用 token tab（未部署工场运行时层时本 tab 不出现）：所属应用、scope（= 能力声明）、签发时间、状态、用量入口（按应用归属，GOV-04）、强制吊销与重新签发操作及后果提示，tab 内注明「应用 token 为系统自动管理的服务账号密钥」；服务账号 tab：开放 API 集成调用方的服务账号与其密钥管理，构成与验收以《3.0 开放 API 鉴权与身份传递 PRD》R5 为准，本册不展开；会话 key 不设管理 tab，页内说明其自动生命周期 |
| 迁移告警查看 | 管理后台-审计页专项筛选（GOV-04） | 调用方来源/路径/次数/最近调用时间 |
| 兼容窗口状态 | API key 管理页顶部 | 兼容窗口剩余时间 + 窗口结束后行为说明 |

- 规则与边界：
  - 应用 token 生命周期：每次发布按新能力声明重签、旧 token 即刻失效；停运冻结、删除吊销、回滚随目标版本能力声明重签（RT-05/RT-07）。
  - 应用 token 强制吊销后：应用保持已上线态、入口可正常访问，平台能力调用即刻失败（错误态语义同 GOV-05 能力收回）；owner 收到站内消息并在发布面可见失效提示（§3.2 事件触达）；恢复 = 应用 token tab「重新签发」（按当前已上线版本能力声明重签）或随下一次发布自动重签。适用分工：疑似 token 泄漏 / 应用滥用平台能力 → 强制吊销（保留应用对外可访问）；应用整体需要下线 → 停运（RT-07）。
  - 批量撤销（泄漏应急）：支持按主体一键吊销名下全部 key——个人 key 按持有人、服务账号密钥按服务账号；吊销生效上界 5 秒（底座撤销主动清缓存）。
  - 个人 key 与《3.0 开放 API 鉴权与身份传递 PRD》的个人访问令牌（该 PRD P1）同轨同底座；是否合并为同一凭据实例（一把 key 同时通行 MCP/模型/CLI 与开放 API）随该 PRD P1 落地定夺（§6 开放问题）。
  - 三类 key 的签发/吊销/自动失效事件均计审计（GOV-04）。
  - key 值零暴露口径同 NFR-2：仅签发时一次性展示，此后一切界面只见掩码（DEV-01）。
- 验收要点：
  1. 个人 key 可在管理面签发与吊销。
  2. 应用 token 与会话 key 由系统自动签发/回收；应用 token 管理面可查询、可强制吊销，会话 key 不设管理界面、其事件经审计可查。
  3. 三类 key 事件（签发/吊销/自动失效）均计审计。
  4. 兼容窗口内旧 v2 调用可用且产生迁移告警；窗口结束后未带 key 的调用被拒绝。
  5. 迭代发布后旧应用 token 失效、新 token 按新能力声明生效；应用删除后其 token 全部失效。
  6. 强制吊销后应用入口可访问、平台能力调用返回明确错误态；重新签发后恢复。
  7. owner 账号被禁用后，其名下个人 key 三面失效（DEV-01），但其应用的 token 与应用运行不受影响，可见范围内用户正常使用。
  8. 存量 v2 调用方迁移时签发的是服务账号密钥（绑定不可登录的服务账号），而非任何自然人的个人 key。

- 需求描述：管理后台提供应用管理列表，收口租户管理员对应用的治理动作，列出租户内全部已发布应用（含停运态）。
- 界面与交互（位置：「应用工场」主导航入口页内的「应用管理」tab，与 owner 视角的「我的应用列表」并列（PRD-2 §3.1），仅租户管理员角色可见。不新增一级菜单、不并入「构建」页——构建页是创建编辑面的卡片流，本列表是治理面的表格；菜单可见性与部署开关沿用「应用工场」菜单一份控制，GOV-07）：

| 界面要素 | 构成 |

| 顶部用量条 | 本租户应用实例数已用/上限（未设上限显示「不限」，GOV-03） |
| 列表列 | 应用名、owner、发布状态（引用 §3.2 应用状态机枚举）、资源档位、标签、来源（平台内造/CLI 导入）、改码权归属（DEV-06，便于定位问题应用找谁改码） |

- 规则与边界：
  - 从未发布的纯草稿应用不出现在列表（草稿 owner-only，WB-16）；其存在性经审计「谁造了什么应用」可查（GOV-04）。
  - 标签设置收口于本列表，owner 侧不提供自助打标（RT-02）。
- 验收要点：
  1. 租户管理员可在列表中看到租户内全部已发布应用（含停运态）及其 owner、发布状态、资源档位、标签、来源、改码权归属。
  2. 列表行上可完成标签设置、授权关系查看与调整（GOV-01）、停运/重新启用。
  3. 从未发布的草稿应用不出现在列表中。
  4. 可按发布状态/标签/来源筛选、按应用名/owner 搜索。

## 4. 非功能需求

仅列产品可感知项，均为跨域不变量，具体行为落在所回链条目中：

- **NFR-1 权限与数据边界不变量**
  1. 应用（及其内 AI）可访问的知识库范围 ⊆ 当前用户自身权限（含文件级权限，RT-01 / DEV-02 / DEV-05；审批人预览例外见 NFR-1.2）；托管运行期进一步收窄为 = 能力声明知识库 ∩ 当前访问用户可见范围（GOV-05）。
  2. 草稿全程 owner-only；唯一例外是审批期间审批人经审读视图与预览试用（含按 owner 权限放行的平台能力调用，属审批例外、计审计，RT-03；工作台侧回链 WB-16），此外无任何旁路。
  3. 应用获得的身份信息唯一可信来源是平台注入，客户端伪造的身份信息一律无效（RT-01 / DEV-05）。
  4. 权限评估 fail-closed：无法确立调用者/访问用户身份即拒绝，绝不回退为放行；权限评估失败即报错，绝不返回未过滤或部分过滤的结果集（GOV-05 / DEV-02）。
- **NFR-2 密钥零暴露**：密钥值不经对话、不写日志、不回显、不进代码；一切界面只见引用名与掩码；平台自签发 key 服务端仅存单向哈希、明文不可还原、仅签发时展示一次（GOV-08 凭据底座）；发布产物不得含裸密钥/连接串——发布前扫描门，规则集内置平台自签发 key 前缀模式（RT-03 / DEV-04 / WB-05 / GOV-04）。
- **NFR-3 资产持久承诺**：运行实例可任意回收；代码/对话/应用数据真身恒在平台存储，删除唯经显式删除流程（RT-07 / GJ-01）。
- **NFR-4 可选部署承诺**：不部署工场运行时层的环境，平台既有功能零新增常驻负担、行为零变化（GOV-07）。
- **NFR-5 审计可追溯**：造/接/发布/回滚/删除/生产数据编辑/密钥事件/改码权交接全链路留痕（GOV-04）。
- **NFR-6 稳定性承诺**：应用与平台、应用与应用运行隔离，单应用崩溃只影响自身并在时限内自动恢复（RT-08）。

## 5. 范围外与顺延

### 5.1 本版明确不做

| 项 | 说明 |
|----|------|
| 模拟其他用户身份（bisheng dev） | 不做（DEV-05）；工作台预览的模拟视角见 PRD-2 §5.1 |
| 公网域名 / 公开可见性 / SEO / 水印 | 内网入口 + 权限体系，无「公开」开关 |
| 自定义资源规格 / 实例数与并发调节 / 自动扩缩容 | 发布时从平台预置资源模板选档（GOV-03 / WB-14）；单应用单实例 |
| token 用量限制 | 不做（私有化环境自有模型与算力；精细成本控制顺延见 §5.2） |
| K8s 多机 / 自动扩缩容 / GPU / 应用间编排 / 自定义运行环境构建 | 单机形态承载本版容量 |
| 本地端专有插件 | 不做；四面供给全走标准协议，任何本地引擎零改造接入（§3.1） |
| 已定顺延 v3.1 的项 | 只在 §5.2 维护（精细成本控制、调用既有工作流/助手、第三方 MCP 网关等），本表不重复 |

### 5.2 v3.1 顺延清单

- 精细成本控制：token 按人记账与成本可视、会话级单轮/单会话预算、预算触顶「走完当前回合再拦截 → 转管理员」处置流程（本版仅保留应用实例数配额，GOV-03）。
- 存量代码执行点（workflow CodeNode / gpts local executor）迁入沙箱设施。
- 应用退役与归属转移（owner 离职接管、长期无人维护自动归档下线）。
- 敏感字段分类分级与受控导出/脱敏（等保 2.0 / 数据安全法）。
- 能力总线暴露「调用既有工作流/助手」作为应用能力。
- 第三方 MCP server 接入网关化；多机调度。
- 审批单超时提醒、催办与升级机制（本版应急路径 = 停运即时止血 + 回滚走正常审批，RT-05 / RT-07）。
- owner 应用侧审计与访问记录自查视图（本版审计查询仅管理面，GOV-04）。
- 个人 API key 调用频率限流（防滥用；本版 key 用量只计量、不设上限，DEV-01）。
- 既有 iframe 嵌入安全升级（原 RT-09）：postMessage 通信协议规范化 + 嵌入域名白名单（白名单外拒绝嵌入通信，修社区 #1705）。平台既有能力的独立安全修复、与工场无功能依赖，可随任意平台版本交付。
