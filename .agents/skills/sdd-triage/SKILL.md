# Sdd Triage

先读 [阶段交接规则](../sdd-workflow/references/stage-contract.md)。

## 方法

从原始描述开始，区分目标行为与实际行为。优先查相关规则、入口、使用方和可用复现或日志证据。
源码说明当前实现，不等同于已验证的生产行为。新项目以目标和已有约束为依据。
沿必要调用关系判断共享机制、对外契约、状态与副作用，避免无关全仓扫描。命名歧义仅在影响根因、范围或风险时澄清，已有定义直接复用。

新增模块或功能扩展走完整 SDD。对 Bug，用下表判断直接修复资格。

## 简单 Bug 准入：五项全部满足

| 条件 | 依据 |
|---|---|
| 预期明确 | 正确行为有可靠依据，无须新增产品决定 |
| 根因明确 | 有复现、日志或代码因果证据，能解释修复为什么有效 |
| 影响有界 | 检查必要使用方，能说明受影响行为和边界 |
| 风险较低 | 保持既有契约、数据含义和核心业务规则，修改容易撤回 |
| 可以验证 | 能以合理成本验证原问题和最可能受影响的相邻行为 |

文件数、行数、前后端划分只是辅助信息。一行访问控制变更可能高风险；前后端各修一个局部映射也可能简单。
根因尚未查清时继续有界排查。验证条件不足时可做已授权的可逆修复准备，但不承诺简单路径已经完成。
诊断与开发侧使用源码、日志及适当的 mock／隔离单元、接口和功能测试，不仅限于轻量静态检查。真实部署 E2E 后置验收，不为决定路径先在本机复刻整套环境。UI 执行遵守单独约定；需要后置证据的简单修复明确保留待验收状态。

普通定位不足以解释的 Bug，按需使用[原症状反馈方法](../sdd-implement/references/bug-feedback.md)，在获准的隔离层验证假设；不把无复现、缺资料直接等同于必须走全流程。

## 需要共同决定的情况

已经发现跨模块连锁影响、重要数据或权限风险、既有契约变化、重大方案取舍，或需要推翻已确认内容时：
给出已知原因和证据、影响、未知项、选项及推荐，与用户决定切入点。
复杂 Bug 不自动变成完整 SDD；按既有需求和设计是否仍有效选择必要阶段。

## 完成与交接

沿用[产物存放与维护约定](../sdd-workflow/references/artifact-storage.md) 中的已有任务标识和登记。新完整任务确定项目／模块／版本及位置，简单 Bug 可复用 issue 或短记录，保持与风险相称的产物数量。
输出任务类型、研发切入路径、五项判断的简短依据、必要开发验证方式、测试岗位待验收项和未决事项。研发的目标是完成验证并交接，不自动把简单 Bug 切入 sdd-acceptance。
简单问题用几句话交接给 sdd-implement 即可；复杂问题的技术诊断完成不代表人工决策已经完成。
修复中出现新证据或影响扩散时再次分流。
