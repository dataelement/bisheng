# Sdd Plan

先读 [阶段交接规则](../sdd-workflow/references/stage-contract.md)。

## 输入与方法

核对有效的需求和设计确认、用例及项目执行条件。必要条件缺失时先补齐，不自行代签确认。
沿用[产物存放与维护约定](../sdd-workflow/references/artifact-storage.md) 中的特性标识、登记和有效文件位置。计划列出受影响产物、必要知识更新与交接，位置／版本变化时同步关联；简单修复可在现有短记录承载。
按可验证的行为切分任务，说明每项做什么、需求来源、前置依赖、修改边界和验证结果应是什么。
研发任务只安排应用修改及各对应项目/test/ 的开发测试，UI／真实集成／E2E 的验收工程工作单列为测试岗位交接项，不混入研发必须完成或等待的任务集合。
文件列表可以辅助定位，但任务应能交付可判断的行为。优先纵向切片：例如先交付一个包含权限、接口与状态变化的可验证导出行为，再补重试；不机械拆为先建完所有表再写完所有接口。广泛迁移可按风险先扩展、再迁移、最后移除，不能为纵切破坏兼容。
任务沿用已确认概念及技术映射，既有登记保留必要术语引用。多任务确有阻塞时用明确依赖检查循环；简单任务不为图或编号另造流程。
把 mock／fake／隔离 fixture 准备、已有测试复用、执行命令及清理成本纳入安排。命令从项目配置查证，区分可隔离的单元／接口／功能测试与真实部署 E2E；未知时先探索，不编造可执行命令。
开发任务安排所需单元、接口、功能和契约验证，不能只列静态检查。真实部署 E2E 及昂贵真实依赖验证放到开发完成后的 CI／共享验收环境，不要求本机部署全栈；UI 执行遵守单独约定。方法见[测试环境与证据策略](../sdd-test-cases/references/test-strategy.md)。
按修改影响选择本轮用例，合适节点汇总必要回归；结合实际耗时拆分高成本套件，不为运行快删除关键断言或任意减少必须覆盖的场景。

普通工作默认顺序推进。具备协作能力且获得相应授权时，可把独立任务并行安排；共享文件、合并与验证依赖需明确。
根据风险安排局部验证和最终验收，避免每个切片都重复全量扫描或无理由安装整个环境。
重要设计或需求变化交回相应阶段确认；计划内的普通实施细节自主处理。

## 产物与完成标准

完整任务可用已有项目格式或简短计划，包含：
- 稳定任务标识、行为目标和需求／设计依据。
- 依赖、必要前置条件及修改边界。
- 验证场景、方法、执行阶段、真实／替身边界或实际查证的命令。
- 完成证据及当前状态。

研发任务合起来覆盖研发交付范围，每项能执行、能验证，阻塞依赖有明确处理办法，才算计划就绪。计划终点包含代码审核和提测材料；不安排研发自动调用独立验收或触发并等待验收 CI。
计划完成不代表实现完成。勾选实施任务以前，需要当前代码所需单元／接口／功能测试、适用静态检查及审核依据；无法由隔离测试证明的真实依赖结论保持待验收，不能据此勾选整体验收完成。
简单 Bug 直接修复时，本能力的有效内容可以压缩成几句话，不另建庞大任务文档。
