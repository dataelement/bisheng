# 测试用例推导方法

## 来源与预期

先从已确认需求和业务规则得到可观察预期，再使用明确技术契约细化执行方式。
代码、日志和实际行为用于定位和执行，不单独定义正确结果。
为每条验收条件关联至少一种可信验证方式；覆盖未明确时如实标记缺口。

## 按风险选择方法

| 风险／规则 | 可用推导方法 |
|---|---|
| 长度、大小、范围、数量 | 等价类及边界值；数值来自规则或契约 |
| 多个条件共同决定结果 | 决策表、相关条件组合；避免无意义全排列 |
| 业务状态变化 | 状态转换、禁止转换、部分完成与恢复 |
| 权限与数据归属 | 普通允许／拒绝配对，相关角色与跨边界访问 |
| 依赖失败或耗时 | 超时、取消、部分成功、恢复；验证无错误遗留状态 |
| 共享状态并行修改 | 有控制的竞争与顺序验证，必要时使用真实存储或消息机制 |
| 重复请求／投递／重试 | 检查幂等或业务定义的重复结果、副作用次数 |
| 偶发时序问题 | 受控调度或合理重复运行，区分不稳定性与业务幂等 |

具体字段、单一意图、独立前提、数据、预期与四部分输出遵守 [测试用例写作与完成标准](case-writing-standard.md)，同时保留岗位、工程、阶段和真实／替身证据边界。
数据隔离及清理限定到用例自己创建的对象，避免影响他人资源。

开发期使用 mock／隔离环境执行所需单元、接口和功能场景；真实部署 E2E 和昂贵的真实依赖验证集中到开发完成后的验收。UI、浏览器、截图执行遵守单独约定。用例定义、脚本准备、待验收和真实运行结果分别记录。

## 质量复核

- 验收条件是否都被映射，已识别的重要风险是否有反例或失败场景。
- 预期是否明确，能否区分正确与错误，而非仅检查执行结束或 HTTP 成功。
- 拒绝操作是否检查必要的无副作用行为。
- mock 是否保留了被验证的真实逻辑；需要真实依赖的结论是否被模拟测试冒充。
- 并发用例是否存在真实竞争条件，而非只是依次调用两次。
- 重复运行同一测试用于检查不稳定性，不能替代重复提交业务用例。
- 已有用例是否可以复用，重复用例和维护成本是否合理。

对重要逻辑可按成本使用属性测试或变异检查辅助检查断言；这些不是每个任务的固定门槛。
用例设计完成与执行通过分别记录，不能从用例文档直接生成通过报告。
