### R1：补齐策略变更审计（high）

**依据**：[Spec AC-29](./spec.md) 的实际条目见 `spec.md:112`，要求审计席位、模型范围和月上限的管理员变更。`dsh_user_policy` 只有当前模型列表、当前限额、version 和 updated_by；`dsh_admin_operation` 仅定义 REVOKE / REASSIGN / SYNC_PROFILE，Gateway operation 也只有席位操作。

**触发与影响**：管理员先将额度从 1000 调至 100，再由另一管理员调至 500。按现有数据结构只能看到最后一次状态，无法还原两次变更的操作者与前后值；模型白名单同样如此。请求明细保存 policy_version，不能代替完整配置历史。

**建议**：明确沿用哪个既有审计业务入口，或扩展本功能操作记录；固定 actor、目标租户/用户、操作 ID、前后模型集合/限额、旧新 version、时间及结果。在 SQL 策略提交时同事务记录已提交变更，Redis 同步结果另行更新，区分“策略已提交但仍冻结”和“已经生效”。不要求为审计另建重复策略真相。

**复核用例**：连续两次修改可逐条追溯；并发 expected_version 冲突不伪造成功记录；SQL 提交后 Redis 安装失败仍能查明已提交版本及生效状态。对应 AC-29。

### R2：统一 Root 共享模型验收（high）

**依据**：`spec.md:98` 的 AC-18 限定“当前租户中已配置”，`spec.md:101` 的 AC-21 要求拒绝“不属于当前租户”的模型；Design §4.4 和 Release B2-INV-3 则允许既有业务认可的 Root 共享。OQ-02 仍写“待同步确认 Spec 用语”。当前 `LLMService.get_model_for_call` 已有 Root 共享处理，这是实际功能边界，不能由 DSH 直接比较物理 tenant_id 替代。

**触发与影响**：Root 的模型合法共享给子租户，管理员把它加入该用户 DSH 清单。遵循 Design 的开发会允许调用，按 Spec 字面编写的验收会判定越权。此前报告标为 medium，本轮按 checklist“与 spec 矛盾为 high”提升级别；不表示重新否定既有共享机制。

**建议**：按当前设计方向将 Spec 改为“既有模型业务确认该租户合法可访问，且管理员开放给 DSH 的模型”，并明确合法共享与未经授权跨租户读取的区别。须经需求确认后同步 Spec、Design OQ-02 和相关验收说明；不需要新增客户端字段。

**复核用例**：当前租户自有且获授权模型成功；合法 Root 共享且获授权模型成功；其他租户非共享模型拒绝；取消共享或 DSH 授权后新调用拒绝。

### R3：消除 License 过期语义歧义（medium）

**依据**：`spec.md:131` 笼统规定“License 过期、失效”时禁止发席、发证和新调用。Design §4.5.4 则将旧商业 License 和 DSH entitlement 独立判定；兼容矩阵 `design.md:405` 写“原过期/损坏 License → 不放行”，而 `:408` 对“旧 trial 已过期、DSH 扩展仍有效”允许独立校验。

**触发与影响**：客户旧 trial 到期但 DSH entitlement 尚在有效期内，开发与测试可能分别选择拒绝所有 DSH 或继续允许。兼容旧商业行为本身没有问题；缺的是明确“过期”指哪一层，不能靠实现人员猜测。

**建议**：保留已设计的两类授权独立计算方向，补充术语及判定表，明确外层不可解码、旧商业期满、DSH 扩展缺失/失效这三种情况；收窄矩阵笼统“原过期”行的适用条件，并同步 Spec §3。这里是定义歧义，因此列 medium，不推断用户已要求旧 trial 到期必须关闭 DSH。

**复核用例**：两类授权有效/过期的四种组合，加外层损坏、无扩展和篡改扩展；新 Gateway 不改变旧接口的授权判定与响应。旧版本二进制能否读取新增扩展仍须用真实 License 样本单独验证。

### R4：补齐 Token 身份显示的数据依赖（medium）

**依据**：`client-api.md:230–235` 规定 user.username、user.display_name、tenant.name 均必返，`:249` 规定刷新返回相同字段。内部 `identity/redeem` 只列实例/租户/用户 ID 及状态，`identity/check` 只列可登录状态。席位资料投影有用户名称，却没有租户名称；`profiles/upsert` 的定义也未解决该字段与刷新时新鲜度。

**触发与影响**：两个仓库分别按所列接口实现后，Gateway 不能仅靠这些响应生成完整冻结 Token 成功体；让客户端额外读普通用户 API 会违反已冻结用法。

**建议**：明确可信身份 DTO 与来源。可在 redeem/check 返回规范化 user、tenant 显示对象及必要资料版本，或明确一条已有受信业务查询路径；规定名称缺失时的确定性回退值，以及刷新使用当前资料还是登录快照。内部接口表、资料投影与 Token 组装规则须一致，客户端保持现有响应字段。

**复核用例**：首次换证与刷新都具备完整字段；用户/租户改名的行为符合约定；不接受客户端自报显示信息作为可信身份；身份服务失败不伪造完整登录成功体。

### R5：把 UNKNOWN 补记与解冻落成可执行流程（medium）

**依据**：Design 明确未知 usage=NULL、暂停受影响用户、取得可靠用量后恢复；模型明细允许 RECONCILED，但 §6 没有定义对应操作入口或内部任务契约，OQ-04 仍将最终人工处置留待确认。

**触发与影响**：一次上游断流或进程退出后即可能进入 UNKNOWN。即使运维后来取得可靠用量，也不知道应调用哪个服务、以什么授权与 request_id/version 提交、如何避免重复补记，以及何时可以解除冻结；一直无法取得用量时的产品状态同样未定。故障关闭是正确保护，但还不是完整恢复方案。

**建议**：定义一期可执行的后台任务或受控运维命令，不要求增加客户端 API；写明责任模块、证据来源、幂等补记、审计及解冻条件。多个 UNKNOWN 并存时不能因其中一个补记就放行；配额存储故障或策略同步冻结也不能被该操作误解冻。明确永久无法核实的处置边界，或把持续冻结及运营处理方式作为一期显式限制确认。

**复核用例**：重复补记只增加一次实际用量；两个 UNKNOWN 只解决一个时仍拒绝新准入；最后一个解决且其他门禁健康后恢复；跨月按原月份补记，不重发模型。
