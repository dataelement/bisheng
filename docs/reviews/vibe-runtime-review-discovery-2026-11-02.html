1. 已核实的问题

项目 当前事实与原因 建议范围
1. 健康、重启、启动时间 页面已有三个字段。116 的实例 API 返回 health=null、restart_count=0，缺少 started_at。同一容器实际 StartedAt=2026-10-30T10:33:15.363879485Z、重启 0 次，未配置 Docker HEALTHCHECK。v2 状态投影遗漏启动时间，并只读取 Docker Health，未用平台已有 HTTP 探活结果；K8s 投影也遗漏启动时间。 补齐 Docker/K8s 当前应用执行体的启动时间；健康沿已有实际探活/Ready 事实呈现，不能把 Running 或缺失数据冒充健康。真实 0 次保留为 0，未知不可显示成 0。
2. 模型调用访问用户为空 当前 116 Root、近 7 天查询返回 34 条记录，访问用户候选已有用户 ID 3。截图中的“应用自身”记录未保存自然人访问身份，现有候选只枚举日志中真实存在的 user/natural_person。未复现当前候选整体为空。 保留真实身份过滤；存在用户记录时应能选、能筛选。只有应用自身调用时明确说明无访问用户记录；查询失败、搜索无匹配与无用户记录不能混为一谈。不从应用负责人、登录人或访问时间推测历史访问者，不回填旧日志。
3. 审批可见范围为空 发布场景 Handler 只复制 payload.visibility_snapshot，发布管线未填充此字段；客户端始终读取历史 detail_snapshot，该字段为空就展示空文案。 打开审批详情时读取应用当前有效的人员、部门和用户组授权摘要；只读展示，修改授权仍走既有权限流程并立即生效。保留原审批快照，不重写历史记录。
4. 首次提交空文案 客户端把空数组统一翻译为“暂无可见范围信息”，没有区分“确认只有负责人”与“未知/查询失败”。 仅当当前权限查询成功、确认没有负责人以外的有效普通访问授权时，显示“仅负责人可见”。首发后若已新增授权，仍展示最新对象。缺失数据、失败、应用已删除不能伪装为负责人可见。
5. 租管没有新建知识库按钮 116 正式 GET /tenants/60/admins 确认 gzx01（849）为租户 60 管理员。角色菜单查询没有 create_knowledge。前端路由为租管补了 knowledge，但页面新建按钮仍只认 admin/create_knowledge；后端 create 也只认 create_knowledge 菜单，单改按钮会继续被拒绝。 统一前后端的本租户知识库新建资格：当前租户管理员可新建文档/QA 知识库；普通用户继续走原创建菜单。租管不能借此选择其它租户。保留模型可用性、容量等既有检查。

已通过截图使用的 120:3002 入口再次对照：近 7 天、不限制应用时访问用户候选为 1；限定截图中的应用自身调用示例 c117490880544bf9b695019394488478 时候选为 0，两次均为业务码 200。先核对 120/116 鉴权公钥一致，再使用内存会话查询；未更新任一环境服务。

2. 已确认的业务边界

用户于 2026-11-02 明确回复“确认边界，进入正式规格”，确认以下 D1–D4；这不代替后续 spec、design 的单独确认。

D1. 运行信息表示真实当前执行体

  • Docker 使用精确绑定的当前容器；K8s 使用精确绑定的当前 Pod/应用容器，不混入初始化/维护容器。
  • 健康优先反映已有平台探活/Ready 结果，明确区分正常、异常、启动中、未知；本次不新增独立监控系统或定时探活体系。
  • 重启次数表示当前应用执行体的实际重启计数，不把版本升级、替换实例和应用历史发布次数累加为重启次数。
  • 不重建现有应用来补显示信息；时间按现有统一时间展示工具转换。

D2. 模型调用保留真实身份

  • 候选来自当前授权租户/应用/时间范围内的真实用户调用记录；过滤使用相同范围。
  • 应用以自身身份调用模型时，记录不代表某个自然人。需要按人查询的新调用，应由应用按现有 SDK/OBO 契约转发访问者身份，本次不替已有应用改码。
  • 不新增虚构人员候选，不把“用户不存在于这些记录”解释为全租户人员都可筛选；无记录提示三语交付。

D3. 审批只读展示当前授权

  • 这是对 F055 AC-24“提交时可见范围快照”的明确修订：代码、声明、版本、审批决策仍冻结；仅可见范围区改为查询时的最新授权，并标注“当前可见范围，授权变更即时生效，不影响审批”。
  • 按现有 F048 use 生效动作识别访问授权，涵盖直接及现有继承语义；不能按模型名字认定权限。
  • 展示人员、部门、用户组名称与类型；部门/组不展开成全部成员。服务账号不是普通浏览者，不作为人员行列出。
  • 不枚举所有因管理员身份而隐式可见的账号；这些身份继续按既有平台规则生效。
  • 当前审批阅读资格仍须校验。跨租户、失去资格、权限依赖不可用时不得泄露当前授权目录；不能借当前摘要获得应用 edit/manage_permission 或源码访问权。
  • 进行中和已进入终态的、仍有合法阅读资格的审批详情，均显示当前授权；历史快照不改写。已删除应用与不可确认权限分别提示原因。
  • 人员迁租户、停用、授权撤销与模型动作变化不能被误写成“仍可访问”；不迁移应用或授权，不修补存量历史数据。

D4. 知识库创建资格

  • 当前有效的租户管理员默认可在自己所属租户新建文档/QA 知识库，前端入口和后端资格一致；不信任前端传来的管理员标记。
  • 新资源仍归当前创建人及其所属租户，不用页面管理视角改变归属。超管与普通用户沿现有创建规则。
  • 不扩大一般部门管理员的权限，不新增角色或批量补写用户授权。
  • 本次只修新建，复制仍保留原创建菜单和源资源读取资格；页面共享条件需拆清，不能顺带放开复制。

4. 定向验证计划

  1. 状态投影：Docker 有/无原生健康检查、探活成功/失败/未知、重启为 0/正数/缺失；启动时间、执行体身份匹配；K8s 应用容器与初始化容器分离。
  2. 模型记录：自然人/OBO 与应用自身配对；候选和列表过滤一致；租户、应用、时间与无候选/搜索空/加载失败边界；不篡改历史记录。
  3. 审批范围：负责人可见、多类授权、授权变更后刷新、进行中/终态、use 与其它动作区分、继承、人员失效、跨租户与无权拒绝；当前摘要失败不影响不可变审批数据。
  4. 新建知识库：无 create_knowledge 菜单的本租管允许；无菜单普通用户拒绝、有菜单普通用户允许；跨租户拒绝、文档与 QA 一致、复制资格不扩展。
  5. 仅运行上述相关测试、变更文件静态检查与必要页面验证；真实部署/写入验收另行明确，不自动更新 116 或 120 服务。
