# F068 代码执行沙箱测试报告

- **测试依据**：《F068 代码执行沙箱测试用例》（同目录）
- **测试时间**：2026-10-29 至 10-30（台北时间）
- **测试环境**：116 上的 `bisheng-test-*` 容器组（Docker Compose）
- **镜像**：
  - runner：`bisheng-sandbox:release`，2026-10-28 14:32 构建，测试期间没有变化；
  - backend：`bisheng-backend:release`。测试期间 CI 自动重新部署了 3 次，最后一次是 10-29 22:28 构建。
- **执行方式**：除特别说明外都是「沙箱运行」。任务模式用的模型是 908（minimax2.5）。

---

## 1. 结论

**F068 现在不能按「沙箱运行」默认开启上线。** 正常的单任务链路基本都通过了。但并发、超时、长任务、大工作区这几种情况会让 runner 丢会话或卡死，部分情况下 runner 主进程会被杀掉，用户看到的是看不懂的 28001 或 28006，任务里的代码调用全部失败。

问题集中在 runner 和执行器的会话管理这一层：

- **D1** runner 同一时间只执行一段代码；
- **D2** 超时后杀不掉用户进程；
- **D3** 工作区太大时 runner 主进程被内存超限杀掉；
- **D4** 会话一旦丢失，执行器不会重新申请；
- **D5** 僵尸进程不回收；
- **D6** 进程被杀后，返回结果看不出原因。

这 6 个缺陷的根因都已经定位到代码行，建议作为一组一起修，修完后重跑第 5 节（R1–R5）的用例。

**修复情况（2026-10-30 补记）**：D1–D7、D9、D10、D11–D14、D16 已在 feat/3.0.0 修复，修复内容和验收结果见第 7 节。D8 和 D15 不在这次修复范围内。

正常链路这边，任务模式的核心链路（TC-10 到 TC-22）、技能包、子代理并行、日常会话、代码节点、本地隔离、runner 不可达时的报错都通过了。

### D1 runner 同一时间只执行一段代码（P0）

- **现象**：同一个 runner 上的两个会话同时执行 `sleep 10`，总耗时 20.1 秒：第二个会话等第一个结束后才开始。在这期间发出的 `/health` 请求也等了 18.1 秒才返回。这个结果来自最小复现脚本，配置是默认的 `max_sessions=50`。
- **根因**：两个原因叠加：
  - `exec_code` 是 `async def`，却直接调用同步的 `handle_exec`，后者会阻塞在 `subprocess.communicate` 上（`src/sandbox-runner/app.py:163`）。`put_files` 也同样同步调用了 `handle_put_files`（`app.py:121`）。
  - uvicorn 只开了 1 个 worker（`serve.py:46`）。

  所以只要有一段代码在执行，这个 runner 的事件循环就被占住，任何请求都处理不了。
- **影响**：`SANDBOX_MAX_SESSIONS=50` 实际上只能做到「同一时间 1 个执行」。并发时，其他请求等满 30 秒超时后，执行器报 28001「执行环境不可达」，但 runner 其实是正常的。TC-31 中，runner-2 有空闲槽位，却因为正在执行代码而接不了新会话。TC-54 的并发转换失败，以及 TC-36 拷贝 1.5GB 很慢，可能也和这个有关。
- **建议**：把 `handle_exec` 和 `handle_put_files` 放到线程池里执行（`run_in_threadpool`），或者改成异步子进程。修完后用最小复现脚本复测，两个会话的总耗时应接近 10 秒。

### D2 超时后杀不掉用户进程（P0，R1 成立）

- **现象**：日常会话里执行 `sleep(100000)`，超时设为 60 秒。到 60 秒时，模型收到的是 `SandboxProtocolError`（28006，「执行环境返回无效」），而不是「执行超时」。超时 412 秒之后，runner-2 里这个进程（uid 10000）还在运行，而它所在的会话目录已经被删掉了。
- **根因**：超时后，runner 调用 `os.killpg(..., SIGKILL)` 去杀用户进程组，这一步报 `PermissionError: Operation not permitted`（`src/sandbox-runner/execute.py:82`）。runner 容器只有 `SETUID SETGID CHOWN DAC_OVERRIDE` 这几项能力，没有 `CAP_KILL`，所以杀不掉其他 uid 的进程。这个异常让 exec 接口返回 HTTP 500，执行器就把它报成了 28006。
- **影响**：
  - 每次超时都会留下一个进程，占着内存和进程数配额；
  - 模型看不出这次失败是超时；
  - 留下的进程，它的 uid 会被后来的会话复用（D9）；
  - 任务模式的超时写死为 3600 秒，走的是同一段 runner 代码。我没有实测这 1 小时，但可以确定结果一样。
- **建议**：
  - 给 runner 加上 `CAP_KILL`，或者以会话 uid 的身份发送信号；
  - `_kill_group` 失败时不能抛异常，应该退而尝试 `proc.kill()`，并返回 exitcode 124；
  - 执行器收到 124 时，要给出「执行超时」的提示。

### D3 大工作区让 runner 主进程被内存超限杀掉（P0，R4 成立）

- **现象**：任务里上传 32 个 48MB 的文件，共 1.5GB。copy-in 期间，runner-1 的内存涨到 1.27GiB 以上，最后 runner 主进程（UID 0，RSS 2GB）被 OOM killer 杀掉，容器在 22:51:44 重启。这个任务收到 `Isolation environment unreachable`，同一 runner 上的其他会话也全部丢失。
- **根因**：
  - copy-in 只有单文件上限（50MB），没有总量上限，所以 48MB 的文件全部会被拷进去；
  - 两端都把整个请求体读进内存：执行器把所有文件读成 dict 再打成完整的 tar.gz（`container_executor.py:168-189`），runner 用 `await request.body()` 一次性读完后再解包（`app.py:115`）；
  - runner 容器的内存上限是 2GB。
- **建议**：
  - 增加 copy-in 总量上限，超过时跳过并提示，和单文件超限的处理方式一样；
  - 两端都改成流式传输和解包；
  - 让 runner 主进程比用户进程更晚被内存超限选中（`oom_score_adj`）。

### D4 会话丢失后不会恢复（P0，R3、R4 成立）

- **现象**：
  - **TC-34**：执行中重启 runner。之后执行器拿着旧的 session_id 去 copy-in，连续 3 次收到 `session missing`，每次调用都报 28006，直到任务结束。
  - **TC-32**：租约 TTL 设为 60 秒。两次代码调用之间要做联网检索，这期间租约过期。之后每次代码调用都报 28006，模型大约每 3 秒重试一次，一共失败 57 次，最后是我手动中止的。
  - **TC-33**：会话 A 的 `sleep(120)` 正常结束，`exitcode=0`。27 毫秒后，runner 以 `reason=idle` 回收了这个会话。接下来的 copy-out 找不到会话，`before.txt` 和 `after.txt` 都丢了，模型收到 28006。
  - **TC-31**：一个已经建好的会话排在前一段代码后面等了 2 分钟（D1），还没开始执行就被当成空闲回收了。
- **根因**：
  - 执行器在会话丢失时直接报 28006，不会重新申请租约；
  - runner 只在每个请求开始时刷新 `last_active`（`src/sandbox-runner/leases.py:113`），`reap_expired` 也不看会话是否正在执行（`leases.py:61`）。
- **影响**：默认 TTL 是 900 秒。生产环境中，单次执行超过 15 分钟，或两次代码调用间隔超过 15 分钟，都会遇到这个问题；任何一次 runner 重启（包括 D3）都会让正在跑的任务失去执行能力。
- **建议**：
  - 执行器收到 404 时清掉旧租约，重新申请，并把工作区重新拷进去；
  - runner 在 exec 结束时也刷新 `last_active`；
  - 回收时跳过持有执行锁的会话。

### D5 僵尸进程不回收（P0）

- **现象**：
  - runner-2 上做一次普通的 soffice 文档转 PDF，结束后留下 5 个僵尸进程（gpgconf、gpg、gpgsm）；
  - fork 测试（TC-98）在 runner-1 上留下 244 个僵尸 python 进程，只能重启容器恢复。

  每个 runner 的进程数上限是 256，大约做 50 次转换后，这个 runner 就再也创建不了进程，但 `/health` 仍然返回 ok。
- **根因**：runner 的 PID 1 是 `python serve.py`，它不回收孤儿进程。
- **建议**：在 compose 里给 runner 加 `init: true`，helm 也做对应修改；或者在镜像里用 tini 作为 PID 1。

### D6 进程被杀后看不出原因（P1）

- **现象**：
  - **TC-35**：内存耗尽的循环被 cgroup OOM 杀掉；
  - **TC-37**：死循环在 601.2 秒被 CPU 时间上限杀掉。

  两次模型收到的都是 `exitcode=-9`，stdout 和 stderr 为空。runner 日志里也只有 `exitcode=-9`，没有 `exec oom`。
- **根因**：runner 直接把 `proc.returncode` 当作 exitcode（`src/sandbox-runner/execute.py:149`）。Python 里被信号杀掉的进程，返回码是负的信号值 `-9`，不是 shell 风格的 `137`。所以 runner 的 `if exitcode == 137` 分支（`execute.py:154`）和执行器里对 137 的判断，一次都执行不到。
- **好的一面**：内存超限只杀掉了那一个用户进程，runner 没有重启，同一 runner 上的其他会话和下一次调用都正常。
- **建议**：
  - 把负的返回码换算成 `128 + 信号值`；
  - 在执行器里为 137（被杀）和 CPU 超限各补一句给模型看的说明。

### D7 停止任务后代码继续运行（P1）

- **现象**：21:52:11 点击停止，worker 在 21:52:42 把任务标为 terminated。但沙箱里的 `sleep 300` 一直跑到 21:57:01 才结束，会话直到这时才释放。用例要求 30 秒内释放。
- **根因**：`ContainerExecutor.execute_code` 用同步 HTTP 请求等待 exec 返回。取消任务中断不了这个请求，执行器也没有向 runner 发送终止。
- **建议**：任务取消时，由执行器调用 runner 的删除会话接口，强制结束会话并杀掉进程。这一步依赖 D2 的修复。

### D8 网络隔离不完整（P1）

- **现象**：沙箱里连 MySQL、Redis、MinIO、ES、OpenFGA、Milvus 都失败，但 `backend:7860` 和 `code-runner-2:8080` 能连通，显示 OPEN。
- **影响**：用户代码可以直接调用后端 API，也可以访问其他 runner 的接口。其他 runner 的接口需要 token 才能用。
- **建议**：把 runner 放进独立网络，只允许 backend 和 worker 单向访问 runner。

### D9 uid 撞号（P1，R6 成立）

- **现象**：会话 B 还在运行时，新建的会话 C 也分到了 uid 10001。C 用明确路径读 B 的目录被拒绝，返回 PermissionError，因为执行前目录属主是 root、权限 0700；在 `/proc` 里也看不到 B 的进程。所以这次没有复现跨会话读取。
- **根因**：`uid = 10000 + (len(self._leases) % 1000)`（`src/sandbox-runner/leases.py:81`），会话释放后再新建，就会和还活着的会话撞号。
- **风险**：如果 D2 留下的进程和新会话 uid 相同，它就能读写新会话已经属于这个 uid 的工作目录。
- **建议**：维护一个正在使用的 uid 集合，分配时跳过集合里的 uid。

### D10 runner 运行身份和资源上限（P1，R7 成立）

- runner 主进程以 uid 0 运行，容器 `NanoCpus=0`、`CpuQuota=0`，没有 CPU 上限。这和 AC-14，以及对外说的「非 root」不一致。
- 用户进程的 `os.getgroups()` 返回 `[0]`，也就是保留了附加组 root。

### D11 到 D16（P2）

- **D11 中文字体**：镜像里装了文泉驿（`wqy-zenhei`），但 matplotlib 默认的 `font.sans-serif` 是 DejaVu Sans，标题中的中文触发 `Glyph … missing` 告警，显示成方框。建议在镜像里放一份 matplotlibrc，把文泉驿加进默认字体。
- **D12 本地方式不建目录**：沙箱方式的 runner 在每次执行前创建 `output/` 和 `scratch/`（`execute.py:115`），本地方式不建。TC-11、TC-13、TC-19、TC-40 在本地方式下，第一次写交付物都报「目录不存在」，模型要多调用一次才能成功。工具说明里虽然写了要先 `os.makedirs`，但两种方式的表现应该一致。
- **D13 缓存进产物清单**：runner 把 HOME 和 XDG 目录都设为工作目录，soffice、fontconfig、dconf 的缓存（`fontconfig/*.cache-9`、`dconf/user` 等）出现在工具结果的文件清单里，也进了 `all_from_session_files`：一次任务有 38 个 LibreOffice 文件、9 个 fontconfig 文件、1 个 dconf 文件。结果区的交付物不受影响，前端也不读这个字段。问题是模型会看到无关文件，而且这些文件每次调用都要来回拷贝。建议把 HOME 指向 `scratch/` 或会话外的临时目录。
- **D14 getpass**：沙箱的 `/etc/passwd` 里没有 uid 10000 及以上的条目，`getpass.getuser()` 和 `pwd.getpwuid()` 都会报 KeyError。本地隔离方式有 `sandbox` 用户，没有这个问题。
- **D15 流式超时不一致**：test 环境 nginx 对日常会话接口设的是 `proxy_read_timeout 300s`，而代码执行的超时是 600 秒：本地方式写死在 `local_executor.py:34`，沙箱方式的默认值也是 600。执行超过 300 秒时，日常会话的流先被切断，用户只看到连接中断。
- **D16 代码节点没有 return**：报的是普通 500「main function output must be dict」，信息能看懂，但不是用例写的 28008。缺少 `main` 的情况在运行时报错；保存草稿是否报错，这次没测。

验收和修复之后仍有以下几点需要知道：

1. TC-35 的原始代码先撞上进程的 2GB `RLIMIT_AS`，结果是 `MemoryError`（exitcode 1），不会走到 137。要验证 137/memory，需要另一个会话先占住内存，再让本会话逐页写入大块内存。
2. 用户进程被 OOM 杀掉后，`docker inspect` 会把 runner 容器标为 `OOMKilled=true`，但 runner 本身没有重启。监控不能把这个标志当作 runner 崩溃。
3. 请求体不带 Content-Length 且超过上限时，客户端看到的是连接重置，而不是 413。执行器会先按总量上限截断，不会发出这样的请求。
4. `TMPDIR` 仍在工作目录里，用户代码留下的临时文件可能进入产物；拷出和 stdout 仍然整块放在内存里。
5. 验收镜像里的 tini 是从宿主机的 docker-init 拷入的，因为 116 没有外网。Dockerfile 里的 `apt install tini` 要以第一次 CI 构建为准。
6. Compose 新增 CPU 上限，默认值 2。宿主机少于 2 核时必须把 `SANDBOX_CPUS` 设成 1，否则 Docker 拒绝启动 runner。
