# 后台组合编辑的事务边界调整（已确认）

## 发现

`DepartmentService._apply_local_primary_department_change` 不仅更新成员关系，还在提交后处理部门授权、知识空间派生权限和租户切换。`UserGroupService.areplace_user_memberships` 也逐组调用各自所属的写入服务。将这些流程全部放进新事务，需要改造现有权限投影、调岗和恢复机制，超出账号与昵称字段改造。

原 design §4.4 将整张人员表单承诺为单一事务，范围偏大。此项调整只针对该技术承诺；账号大小写、昵称规则、历史数据、原权限边界和页面范围均不变。

## 建议方案

后台仍保留当前的一个保存按钮。

1. 完成原人员管理权限及来源检查，读取原昵称；实际改名先按新规则校验，原值不变不校验。
2. 按既有所属服务处理部门、用户组和角色；这些操作失败时，不提交本次昵称。
3. 其他操作成功后，最后在一个事务中写入昵称、主动保护标记、DSH 资料版本和改名审计。此事务失败，昵称及上述附属状态全部回滚。
4. 取消和失败保留前端草稿；改名不改变账号、身份、密码或原有会话。

本人昵称接口始终只有上述昵称事务，不涉及其他人员字段。

这保证本次昵称不出现“后续人员操作失败，但昵称已提前修改”。既有部门、组、角色操作仍按原事务和恢复机制执行，不新增对这些操作的全局回滚承诺。

## 另一方案

保留原设计的整表单同事务：将调岗、组成员、权限投影、租户迁移及恢复一起纳入本次改造，并补充相应的事务和故障恢复设计、实现及回归。
