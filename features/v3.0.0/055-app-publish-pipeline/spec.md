> **范围边界**
>
> 本 Feature 是「怎么上线」这一段的全部服务端与发布面：从提交发布到上线终检的管线、平台预置的审批流、只增不改的版本记录、资源档位实体、以及应用经能力声明获得平台能力的总线。它站在 F054 的领域模型与运行时之上，把「一次 deploy」变成「一个已上线、可被找到、可被治理的应用」。**本册托管应用的唯一创建与提交路径是 CLI `deploy`**（平台内造应用随 PRD-2），发布面「提交发布」在本册对 CLI 应用不可用。

>   - **PRD-2 最小面**：**WB-14 发布面**（提交发布 + 档位选择〔本册对 CLI 应用不可用〕· 审批状态区含驳回理由全文、结构变更提示与撤回 · 能力声明完整清单〔含失效标记〕· 版本列表 · 可见范围区**槽位**〔内容与行为归 F056〕· 运营动作区〔停运 / 重新启用调 F054；待上线态出现「手动上线」〕· 入口链接与二维码〔F054 壳呈现〕· 危险操作区〔显式删除调 F054〕）；**WB-15 版本 tab**（全部版本记录：版本号 / 类型 / 提交时间 / 终态 / 能力声明摘要；只读；差异查看：迭代版本相对上一已发布版本的文件变更清单与内容差异）；审批状态只读接口（供发布面与 F052 MCP 应用状态工具消费）
>   - **审批类事件触达**（§3.0.3）：审批单生成 → 审批人；通过 / 驳回 → owner；owner 撤回 → 已收到待办的审批人；删除致取消 → 审批人；待上线态 → owner 与租户管理员（单租户回退平台超管）；资源释放后可手动上线与声明能力被收回 → 无主动提示（发布面自查）——复用审批中心与站内消息既有触达
> - **本次明确排除**：
>   - **App / AppVersion / AppInstance 领域对象、五个应用态动作、编排器与 app-proxy（含预览入口路由）、构建页与详情页壳、`app` 资源类型注册**——F054（本 Feature 调用其对象与动作、填充其详情页的发布 / 版本 tab）
>   - **应用广场、授权交互（含发布面可见范围区的内容与行为）、审计查询面、GOV-07 界面通道、非审批类事件触达**——F056
>   - **CLI 命令本身**（打包 / 上传 / 轮询 / 交互确认 / `logs` 输出）——F053；本 Feature 只做服务端接收、状态接口与权限判定
>   - **模型协议面**（F051）、**统一检索门面与知识库清单查询、MCP 应用状态工具**（F052）——本 Feature 只定义能力总线如何注入 / 收回，以及提供状态只读接口
>   - **密钥引用**（GOV-05 第三项）——本册不做（Discovery N4 已定）；能力声明中出现密钥引用时预检提示本版不支持
>   - **平台侧回滚、迭代审批单变更摘要、应用标签设置、租户级实例数配额、审批单催办 / 超时提醒 / 升级机制、免审配置项**（PRD-1 §5.2 / 不存在）
>   - **平台内造应用的发布面提交、密钥扫描回流管家、owner 草稿沙箱预览、审批期试用数据「保留」选项、工作台路径的改删列草稿期闸口（WB-09）**——PRD-2
>   - **k8s 形态下的构建 / 上线 / 终检差异**——F059（本 Feature 的管线对形态无感）
>   - **应用运行期凭据的产品化**（管理入口、强制吊销 tab、会话 key）——已取消（PRD-1 §5.2）；**发布期依赖 CVE 扫描 / SBOM**（v3.1）

## 1. 用户故事

作为 **开发者（owner）**，
我希望 **`bisheng deploy` 之后不用离开本地就能知道预检哪里没过、扫描命中了什么、审批到哪一步、被驳回的理由是什么；通过后应用自动上线，容量不够时我能在资源释放后自己点一下上线、不用重新走审批**，
以便 **发布是一条可预期、可自查的流水线，而不是黑盒**。

作为 **审批人（部门管理员 / 租户管理员）**，
我希望 **在审批中心看到这次发布接了哪些平台能力、给谁看、用多大资源，能打开待上线版本的代码只读审读，必要时拉一个临时实例试用一下再决定**，
以便 **审的是冻结的那份快照而不是元信息两行字，非技术审批人也能负责任地批**。

作为 **租户管理员**，
我希望 **平台一部署好就有一套可用的发布审批流程（我部门的部门管理员或我来批），我不用先去配置；需要收紧时再改审批人；应用要用哪个模型、哪些知识库，在我原来配模型和知识库的地方配一次就够**，
以便 **治理默认在场，而不是先做一堆配置才能跑通第一次发布**。

作为 **平台超管**，
我希望 **资源档位是三档预置、可调规格可停用，应用只能从中选，选了什么容器就限多少**，
以便 **单机上的应用密度可控、不会有人给自己开一个吃光机器的规格**。

作为 **普通业务用户**，
我希望 **应用里检索到的知识库内容不超过我自己在平台里能看到的范围，也不超过应用声明接入的范围**，
以便 **用同事造的应用不会让我看到不该看的东西，也不会因为应用作者权限大而放大给我**。

## 2. 验收标准

> AC 编号在本特性内唯一。括号内标注对应 PRD-1 条目与验收序号（如 `↔RT-03 验收 3`）；与 F054 存在调用关系的条目注明「调用 F054 AC-xx」。错误码仅作可观测行为引用，定义在 design.md。

### 2.1 提交发布与冻结快照

- **AC-01** — WHEN 服务端接收到 CLI `bisheng deploy` 提交的应用包, THE SYSTEM SHALL 走**同一条**管线：冻结待上线版本快照 → 托管预检 → 密钥扫描 → 落正式版本记录 + 生成审批单 → 审批 → 上线终检；发布面提交入口（平台内造应用）随 PRD-2 启用后走同一管线，本册只验收 CLI 入口。管线的每个节点结果（提交 / 首发导入 / 预检失败 / 扫描阻断 / 审批单生成与四个终态 / 待上线成因 / 手动上线）**均计审计且携带应用标识与版本号**——本 Feature 是这些事件的写入方，审批单终态复用审批中心既有事件并须能按对象应用筛选，F056 负责其在审计面可查。（↔RT-03 流程① / DEV-04 验收 2 / GOV-04 事件清单「造应用」「发布 / 删除动作」）
- **AC-02** — WHEN 提交发布, THE SYSTEM SHALL 立即冻结快照（代码、能力声明、注入配置、档位标识同属一个快照），审读与上线的权威对象即该快照，提交后 owner 的任何改动不影响它；WHEN 预检与扫描通过, THE SYSTEM SHALL 落正式版本记录（版本号、首发 / 迭代、提交时间、终态待标注）；预检或扫描失败的提交**不进入版本列表**（快照临时保留供排障、可读原因经 AC-11 返回）。（↔RT-03 规则 / RT-05 需求描述 / DEV-04 验收 4）
- **AC-03** — IF 同一应用已存在在途审批单, 或应用处于待上线态, THEN THE SYSTEM SHALL 拒绝新的提交并提示（前者：须先撤回；后者：须先手动上线或删除）。（↔RT-03 规则 / DEV-04 验收 5 / §3.0.2 待上线态可做动作）
- **AC-04** — WHEN 服务端处理 `deploy`（首发与迭代）或 `logs`, THE SYSTEM SHALL 要求该密钥持 `app:manage` 位（缺位 → 拒绝并明确提示）；首发以该密钥所属服务账号的资源归属人为应用 owner（写入 F054 AC-07 的 owner 字段）；迭代 `deploy` 与 `logs` 只对该归属人 owner 的应用放行，其他应用一律拒绝并提示归属（含租户管理员名下服务账号的密钥）；持 `delegate` 位的密钥在这两个服务端入口一律被拒、错误指向「委托专用、本地开发另发一把」（INV-31）。（↔GOV-07 验收 2 / DEV-04 验收 9 / 12；DEV-02 ③ ④ / 验收 6 / 10）
- **AC-05** — WHEN 提交通过预检与扫描, THE SYSTEM SHALL 从 `bisheng-app.yaml` 取应用元信息（名称 / 描述 / 图标）并**立即**更新应用（不等审批；元信息不属发布、不经审批、计审计），取能力声明与档位入快照（未声明档位取轻量）；预检或扫描失败不更新元信息。（↔DEV-04 规则 / RT-02 规则 / GOV-03 验收 2）
- **AC-06** — WHERE 应用为 CLI 导入且平台侧无草稿工作区, THE SYSTEM SHALL 使发布面「提交发布」不可用并提示以 `bisheng deploy` 提交。（§4 决议-2）

### 2.2 托管预检与密钥扫描

- **AC-07** — WHEN 进入托管预检, THE SYSTEM SHALL 依次校验 `bisheng-app.yaml` 声明（必填项、`runtime` 取值、端口、档位存在且启用、能力声明格式、**所引模型在本租户已启用且按 F051 名称解析规则可唯一解析〔裸名歧义 → 拒绝并提示限定名〕、所引知识库存在且为 F052 统一检索门面支持的类型**）、执行依赖构建、执行启动探活（调用 F054 AC-15 / AC-18）；任一失败 → 原地拒绝、说明缺失项与改造指引、**不进入审批、不产生审批单、不进版本列表**。（↔DEV-04 流程① / 验收 4；GOV-05）
- **AC-08** — IF 应用包依赖托管契约外的中间件（自带数据库 / 消息队列 / 缓存）或白名单外外网地址, THEN THE SYSTEM SHALL 在预检拒绝并给出改造指引（数据改接平台应用数据库的范式）。（↔DEV-04 托管运行契约 / 验收 4）
- **AC-09** — WHEN 预检检出应用数据表的破坏性结构变更（改 / 删列；表由 `bisheng-app.yaml` 声明、平台建表，DEV-07 ②）, THE SYSTEM SHALL 要求显式确认（CLI 交互确认或 `--confirm-schema-change`）；未确认 → 拒绝；已确认 → 进入管线，发布时不再二次确认，审批单与发布面审批状态区展示该结构变更。（↔DEV-04 验收 10 / RT-05 结构演进表 / DEV-07 ②）
- **AC-10** — WHEN 进入发布前密钥扫描, THE SYSTEM SHALL 用与平台内发布**同一规则集**（常见凭据模式正则清单 + 数据库连接串模式 + `bs-sak-` 前缀模式）扫描产物；命中 → 阻断发布，输出命中规则与文件位置、**不含密钥值本身**；规则集内样本 100% 被阻断。（↔RT-03 流程③ / 验收 5；DEV-04 验收 2 / 8）
- **AC-11** — WHEN 预检或扫描失败, THE SYSTEM SHALL 把失败阶段与原因以可机读 + 可读两种形态返回给 CLI（供 F053 输出与本地 agent 排障）并在发布面审批状态区可见。（↔DEV-04 验收 7）

### 2.3 平台预置审批流（GOV-02）

- **AC-12** — WHEN 全新部署后未做任何审批配置直接发布, THE SYSTEM SHALL 正常生成审批单，审批人 = 应用 owner 主部门的部门管理员 ∪ 租户管理员（同一节点或签）；界面不出现「未配置审批人」提示。（↔GOV-02 验收 1）
- **AC-13** — WHEN 部门管理员或租户管理员任一人处理, THE SYSTEM SHALL 立即出终态并同步关闭另一方的待办。（↔GOV-02 验收 2）
- **AC-14** — IF owner 无主部门、或其主部门未设部门管理员, THEN THE SYSTEM SHALL 仍把审批单落到租户管理员，发布不卡死；部门只取 owner **主部门**且不向上级部门回溯。（↔GOV-02 验收 3 / 规则）
- **AC-15** — WHEN 来源 ②（租户管理员）解析为空, THE SYSTEM SHALL 按当前租户区分：**Root 租户（单租户部署形态）→ 回退为平台超管**，未做任何配置即可发布；非 Root 租户无租户管理员且来源 ① 亦空 → 走 AC-18 异常态。（↔GOV-02 验收 6 / 规则）
- **AC-16** — WHEN 提交发布, THE SYSTEM SHALL 以应用 owner（资源归属人自然人，**不是服务账号**）为审批单申请人，并带上其主部门标识供审批人解析；owner 无主部门时该来源按空处理（AC-14）并在审批单头部标注「无部门管理员来源」。（↔RT-03 流程④；INV-29）
- **AC-17** — IF 申请人本人位于审批人候选中, THEN THE SYSTEM SHALL 自动跳过其本人落到其余候选；WHERE 全租户仅一名管理员且无其他候选, THE SYSTEM SHALL 允许自审并强制在审计中标注自审。（↔GOV-02 验收 7）
- **AC-18** — IF 两个审批人来源均解析为空, THEN THE SYSTEM SHALL 使实例进入审批中心异常态并通知管理员（本租户租户管理员；Root 租户为平台超管）处理，**发布不被放行、也不静默卡死**。（↔GOV-02 验收 8）
- **AC-19** — THE SYSTEM SHALL 在管理后台审批中心场景配置中展示「应用发布」场景及其预置流程当前配置；WHEN 租户管理员改配审批人 / 审批链, THE SYSTEM SHALL 使新配置生效于此后的审批单，且平台升级不重置其配置（按租户 + 场景判存在即跳过预置）。（↔GOV-02 界面表 / 验收 4）
- **AC-20** — WHEN 新建租户, THE SYSTEM SHALL 同步为该租户落库「应用发布」预置流程，使其首次发布即可正常生成审批单。（↔GOV-02 验收 5）
- **AC-21** — THE SYSTEM SHALL 使审批中心「租户管理员」审批人来源解析为**当前租户的真实租户管理员**（而非系统超级管理员近似）；该修正对**一切**使用该来源的既有场景与人工配置的流程同样生效，release note 声明为行为变更。（↔§3.3 锚点表 GOV-02 行 1）
- **AC-22** — IF 审批实例不处于待审状态（已执行 / 执行失败 / 异常 / 已撤回 / 已取消）, THEN THE SYSTEM SHALL 拒绝撤回操作。（↔Discovery §2.4 `withdraw` 终态守卫）
- **AC-23** — THE SYSTEM SHALL 使首发与迭代每次发布均生成审批单，不存在任何免审配置项；能力声明与可见范围未变的迭代同样必审。（↔RT-03 / RT-04 验收 1 / GOV-02 规则）

### 2.4 审批人侧：审批单、审读视图、临时预览实例

- **AC-24** — WHEN 审批人打开应用发布审批单, THE SYSTEM SHALL 展示头部基本信息（应用名 / owner / 来源：平台内造或 CLI 导入 / 首发或迭代 / 提交时间）、能力声明白话摘要、可见范围快照（标注「仅供参考，可见范围变更即时生效、不经审批」）、所选资源档位、含结构变更时的「结构变更」行，以及操作区（通过 / 驳回〔理由必填〕/ 「查看待上线版本」）。（↔RT-03 审批人侧表 / 验收 2）
- **AC-25** — WHEN 审批人打开审读视图, THE SYSTEM SHALL 展示待上线版本的只读文件树与代码内容，tab 含能力声明完整清单 / 版本历史 / 文件差异（迭代时相对上一已发布版本），「预览试用」按钮置顶；owner 的草稿对话（若有）不开放。（↔RT-03 审读视图 / 验收 2）
- **AC-26** — WHEN 审批人点击「拉起预览」, THE SYSTEM SHALL 以待上线版本快照拉起审批期临时预览实例（调用 F054 探活能力与预览入口 AC-37；不占应用运行实例名额；连一个临时空库）；拉起失败展示原因并允许重新拉起；运行中提供「打开预览」与「手动回收」。（↔RT-03 预览试用表 / 验收 7）
- **AC-27** — WHILE 审批人在临时预览实例中试用, THE SYSTEM SHALL 注入审批人本人身份，平台能力按 **owner** 权限放行（NFR-1.2 审批例外条款，INV-36 已登记该例外）并计审计；临时库对审批人可写入试用数据。（↔RT-03 规则 / 验收 8 / NFR-1.2）
- **AC-28** — WHEN 审批出终态（通过 / 驳回 / 撤回 / 取消）或超过部署配置的超时（默认 7 天）, THE SYSTEM SHALL 回收临时预览实例；回收后可再次拉起。（↔RT-03 预览试用表 / 验收 7 / 9）
- **AC-29** — THE SYSTEM SHALL 使审批期试用数据不带入生产：CLI 导入应用首发生产库默认空库初始化。（↔RT-03 规则）
- **AC-30** — THE SYSTEM SHALL 使首次发布的应用在审批通过前不可被除审批人（经审读视图与预览试用）外的任何其他用户访问。（↔RT-03 验收 1）

### 2.5 审批结果与上线终检

- **AC-31** — WHEN 审批通过, THE SYSTEM SHALL 调用 F054 上线动作（AC-65）：容量通过 → 已上线、进入广场可见范围；容量不足 → 审批单保持通过、应用态待上线（资源不足）、不对外服务、通知 owner 与租户管理员并提示成因；拉起或探活因非容量原因失败 → 应用态待上线（成因：上线失败）、通知 owner 可修复后重试手动上线或重新提交（§4 决议-8）。（↔RT-03 流程⑤ / 验收 3；GOV-03 验收 5）
- **AC-32** — WHILE 应用处于待上线态, THE SYSTEM SHALL 在发布面运营动作区提供「手动上线」；WHEN owner 点击, THE SYSTEM SHALL 调用 F054 手动上线动作，**无需重新审批**；仍失败则保持待上线并提示成因。（↔GOV-03 验收 5 / §3.0.2）
- **AC-33** — WHEN 首发被驳回, THE SYSTEM SHALL 使应用保持草稿态；WHEN 迭代被驳回, THE SYSTEM SHALL 保持应用已上线、当前版本继续运行，仅待上线版本标记为被驳回（F054 AC-05）；两者 owner 均可在发布面审批状态区看到驳回状态与**理由全文**，修改后重新提交生成新审批单。（↔RT-03 流程⑥ / 验收 4 / 10）
- **AC-34** — WHEN owner（申请人）撤回在途审批单, THE SYSTEM SHALL 使审批单置已撤回、待上线版本标记已撤回、通知已收到待办的审批人；owner 修改后再提交生成新审批单。（↔RT-03 验收 6）
- **AC-35** — WHEN 应用被删除（F054 动作通知）, THE SYSTEM SHALL 自动取消其在途审批单（置已取消）、通知审批人并计审计（含应用标识与版本号）。（↔RT-07 验收 5 / §3.0.2 / GOV-04）
- **AC-36** — WHILE 应用处于已停运态, THE SYSTEM SHALL 允许提交发布；审批通过仅落为待运行版本、不自动重新启用（F054 AC-04）；重新启用后新版本生效。（↔RT-07 验收 6）
- **AC-37** — WHEN 迭代发布上线, THE SYSTEM SHALL 使应用运行期获得的能力即为新能力声明所列，旧声明中已移除的能力在 5 秒内不可用（INV-28 撤销上界）。（↔GOV-08 验收 6）
- **AC-38** — THE SYSTEM SHALL 提供审批状态只读接口（当前审批单状态、驳回理由全文、待上线成因），供发布面与 F052 MCP 应用状态工具消费，两处返回一致。（↔RT-03 流程⑥ / DEV-02 验收 7）

### 2.6 版本记录与结构演进（RT-05 / WB-15）

- **AC-39** — THE SYSTEM SHALL 在应用详情页「版本」tab 只读展示全部正式版本记录：版本号 / 类型 / 提交时间 / 终态标注（已上线 / 被驳回 / 已撤回；待上线版本显示「待上线」）/ 能力声明摘要；不提供回滚入口。（↔RT-05 验收 1 / 4）
- **AC-40** — THE SYSTEM SHALL 使正式版本记录不被覆盖或删除，同一应用历史版本完整可追溯（F054 AC-02 只增不改）。（↔RT-05 验收 2）
- **AC-41** — WHEN 查看迭代版本, THE SYSTEM SHALL 提供相对上一已发布版本的文件变更清单与内容差异（版本 tab 与审读视图同一呈现）。（↔WB-15 / RT-03 验收 2）
- **AC-42** — WHEN 迭代发布含加列的结构变更, THE SYSTEM SHALL 在上线时自动迁移、无需确认；WHEN 含已确认的改 / 删列变更, THE SYSTEM SHALL 在迁移前**自动留生产数据快照**并在审批单与发布面展示结构变更。（↔RT-05 结构演进表 / 验收 3）
- **AC-43** — THE SYSTEM SHALL 使任一正式版本的快照可被完整取回（供审读视图、审批期预览拉起与将来回滚），且快照内容不可被修改。（↔RT-05 / RT-07 需求描述）

### 2.7 资源档位（GOV-03）

- **AC-44** — THE SYSTEM SHALL 预置三档**平台级**（跨租户共享）资源档位（轻量 1C/2G · 标准 2C/4G · 性能 4C/8G，各附白话适用说明），规格初始默认值取自部署配置项；不提供自定义规格。（↔GOV-03 档位表 / 验收 1）
- **AC-45** — WHERE 工场运行时层已部署, THE SYSTEM SHALL 在系统管理页提供「资源档位」tab（仅平台超管）：列表（名称 / CPU 内存 / 适用说明 / 启用状态 / 使用中应用数）、行内编辑规格与说明、停用（提示存量应用不动、发布面不再可选）；未部署不出现。（↔GOV-03 界面表 / 验收 1）
- **AC-46** — WHEN CLI 提交, THE SYSTEM SHALL 取 `bisheng-app.yaml` 声明的档位、未声明取轻量、声明了已停用或不存在的档位则预检拒绝；发布面选档（默认轻量）随平台内造应用的提交入口一并启用（PRD-2）。（↔GOV-03 验收 2 / 3）
- **AC-47** — WHEN 档位被停用, THE SYSTEM SHALL 使存量应用照常运行与迭代发布（沿用原档位），新发布不可再选该档位。（↔GOV-03 验收 3）
- **AC-48** — THE SYSTEM SHALL 把所选**档位标识**写入版本快照；F054 按该档位的当前规格设置实例限额，规格调整自应用下一次发布 / 重新启用生效（F054 AC-63 / 64）。（↔GOV-03 验收 4 / 规则）

### 2.8 能力总线（GOV-05：模型 + 知识库）

- **AC-49** — WHEN 租户管理员在既有模型管理页配置服务商凭据并启用模型, THE SYSTEM SHALL 使域内应用无需再配即可在能力声明中写该模型名（模型管理页原名）；审批通过后由平台在运行时注入调用通道（经 F051 平台 OpenAI 兼容面 + 应用运行期凭据）。（↔GOV-05 界面表 · 模型 / 验收 1）
- **AC-50** — WHEN 应用在能力声明中声明接入知识库, THE SYSTEM SHALL 在审批通过时视为应用侧授权；运行时应用内检索可及范围 = 能力声明知识库 ∩ 当前访问用户可见范围（文件级、经 F052 统一检索门面）——访问用户由 F054 AC-34 注入的短时访问凭据确立、白名单由平台侧按该应用**当前生效能力声明**确定（应用不可自报白名单）；托管期检索入口（SDK retrieve / 能力总线）以此两者为入参，且**声明范围内的检索结果与该用户在平台内自行检索的结果集合相等**（不多给不少给）。（↔GOV-05 界面表 · 知识库 / 验收 5 / 6）
- **AC-51** — THE SYSTEM SHALL 使生产实例实际可用能力 = 其声明且经审批的能力集合；未声明的能力不可调用（用户本人有权限但应用未声明的知识库经该应用不可检索）。（↔GOV-05 验收 3 / 5）
- **AC-52** — IF 无法取得当前访问用户身份, THEN THE SYSTEM SHALL 拒绝应用内检索、绝不回退为按声明全量放行；IF 权限评估失败, THEN THE SYSTEM SHALL 返回带错误码的失败响应（非空结果、非部分结果）。（↔GOV-05 fail-closed / 验收 7 / NFR-1.4）
- **AC-53** — WHEN 已上线应用声明的能力被收回（模型下线、知识库删除或权限收回）, THE SYSTEM SHALL 使应用对该能力的调用得到**带能力名与「已收回」原因的错误响应**（可与普通失败区分）、不回退旧值、应用整体保持可用；owner 在发布面能力声明清单对应项见「已失效 + 原因」标记。（↔GOV-05 规则 / 验收 4）
- **AC-54** — THE SYSTEM SHALL 使工作台 / 构建区不存在任何底层账号 / 端点配置入口，能力配置只在管理面。（↔GOV-05 验收 2）
- **AC-55** — WHEN 应用运行期经能力总线调用模型或检索, THE SYSTEM SHALL 记录审计双归属：actor = 应用、subject = 当前访问用户（由 F054 AC-34 注入的短时访问凭据确立；**仅模型调用**允许在应用后台任务等无访问用户上下文时以应用自身发起、subject 记为「应用自身」并显式标注——检索无访问用户一律拒绝，AC-52；**不得**记为任意用户），含模型名与 token 数（模型）或检索目标（知识库）；WHEN 每次发布, THE SYSTEM SHALL 记录能力声明变更审计（应用、变更内容）。（↔GOV-04 事件清单「应用运行期能力调用」「接入知识库 / 模型等能力」/ 验收 3；subject 列随 F050）
- **AC-56** — IF 能力声明中出现密钥引用, THEN THE SYSTEM SHALL 在预检提示本版不支持并拒绝。（Discovery N4）

### 2.9 应用运行期凭据（不作产品概念）

- **AC-57** — WHEN 发布审批通过, THE SYSTEM SHALL 按新能力声明为该应用签发 / 重签运行期凭据（F049 底座、主体类型 = 托管应用）并注入实例；旧声明对应的凭据在 5 秒内失效。（↔GOV-08 规则 / 验收 6；INV-28）
- **AC-58** — WHEN 应用停运, THE SYSTEM SHALL 使其运行期凭据拒绝调用（主体停用语义，非新增状态枚举），重新启用后恢复；WHEN 应用删除, THE SYSTEM SHALL 撤销之；两者事件计审计。（↔GOV-08 规则 / GOV-04 事件清单；INV-28）
- **AC-59** — THE SYSTEM SHALL NOT 提供任何应用运行期凭据的查看、吊销或管理入口，且该主体不出现在服务账号管理列表；应急处置只有停运一条路。（↔GOV-08 验收 7）
- **AC-60** — WHEN owner 自然人账号被禁用, THE SYSTEM SHALL 使其应用照常运行、可见范围内用户正常使用。（↔GOV-08 验收 5）

### 2.10 发布面（WB-14 最小形态）

- **AC-61** — THE SYSTEM SHALL 在应用详情页「发布」tab 提供：提交发布 + 档位选择（本册对 CLI 应用不可用，AC-06）、审批状态区（待审 / 通过 / 驳回 / 已撤回 / 待上线成因 + 驳回理由全文 + 结构变更提示 + 在途时「撤回」按钮）、能力声明完整白话清单（含失效标记）、版本列表（只读，同版本 tab）、可见范围区槽位（内容与行为归 F056）、运营动作区（停运 / 重新启用调 F054；待上线态出现「手动上线」）、入口链接与二维码（F054 壳呈现）、底部危险操作区（显式删除调 F054，仅 owner；已上线态置灰须先停运）。（↔RT-03 owner 侧表 / §1 WB-14 最小形态）
- **AC-62** — THE SYSTEM SHALL 使发布面对 owner 可见可操作；租户管理员可查看并执行停运 / 重新启用（既有权限模型），但不可撤回审批单、不可删除、不可手动上线（仅 owner）。（↔§3.3 角色矩阵）
- **AC-63** — WHEN 声明能力被收回, THE SYSTEM SHALL 在发布面能力声明清单对应项显示「已失效 + 原因」标记（AC-53）。（↔GOV-05 验收 4）

### 2.11 审批类事件触达（§3.0.3）

- **AC-64** — WHEN 审批单生成 / 通过 / 驳回 / 被撤回 / 因删除被取消, THE SYSTEM SHALL 经平台既有站内消息与审批中心待办触达对应接收方（审批人 / owner / 已收到待办的审批人）；WHEN 上线终检遇容量不足或上线失败, THE SYSTEM SHALL 触达 owner 与租户管理员（Root 租户为平台超管）；资源释放后可手动上线与能力被收回两类**不主动提示**，仅发布面自查。（↔§3.0.3 事件表）
- **AC-65** — THE SYSTEM SHALL 使站内消息为通知性质、不承载操作；处理动作一律回发布面或审批中心完成。（↔§3.0.3）

## 3. 边界情况

- **本册只有 CLI 一条提交路径**：发布面「提交发布」对 CLI 应用不可用（§4 决议-2），驳回后修改只能在本地重新 `deploy`；平台内造应用的发布面提交随 PRD-2 走同一管线。
- **在途 / 待上线两态都不接受新提交**：在途须先撤回；待上线须先手动上线或删除。撤回是 owner 独有动作，管理员不可代行；非待审状态不可撤回。
- **审的是快照不是工作区**：审批期 owner 本地继续改码或再次 `deploy` 不影响已提交版本（再次 deploy 会因在途审批单被拒）。
- **申请人是自然人**：审批单申请人 = 应用 owner（资源归属人），不是发起 deploy 的服务账号——服务账号不出现在任何面向人的场景（INV-29）；提交人跳过、撤回主体、通知接收方都以 owner 计。
- **审批人来源解析的空值场景**：owner 无主部门 / 主部门无部门管理员 → 落租户管理员；租户管理员为空且为 Root 租户 → 平台超管；非 Root 租户两者皆空 → 异常态通知管理员、不放行不卡死。**不再叠加任何额外兜底规则**。
- **提交人跳过与自审**：提交人是候选之一时跳过本人；仅一名管理员且无其他候选时允许自审，审计必须标注——这是唯一允许「自己批自己」的情形。
- **上线终检失败不是审批失败**：审批单保持通过；应用态待上线（成因：资源不足 / 上线失败）；手动上线不重审；手动上线仍失败则原地提示，不改变审批结论。
- **待上线态可直接删除**（无运行实例）；已停运态提交发布通过后不自动启用。
- **能力声明与可见范围分离**：可见范围不属版本快照、不经审批、即时生效；审批单里的可见范围只是提交时刻的快照，标注仅供参考。
- **能力总线的两层过滤 ≠ 权限取交集**：声明层是显式白名单收窄，用户层是按当前访问用户的逐资源鉴权（纯替换）；结果不多给不少给。**审批期预览是唯一例外**：注入审批人身份、平台能力按 owner 权限放行、计审计（NFR-1.2；INV-36 登记）。
- **模式 D 委托头绝不用于应用内身份传递**：托管运行期以平台登录态为信任根（app-proxy 注入），复用委托管道会把管理员挡在所有应用之外（伴生 PRD 检查 3）。
- **能力收回是可区分的错误不是回退**：调用得到带能力名与「已收回」原因的错误、应用其余功能可用；owner 看提示去改声明再发布；不存在「静默回退到旧值」。
- **应用运行期凭据零感知**：主体类型是「托管应用」而非服务账号（不进服务账号列表、无资源归属人要求）；签发 / 重签 / 停用 / 撤销全部随应用态与发布自动发生，无界面；疑似泄漏或滥用一律停运。
- **临时预览实例的资源**：不占应用运行实例名额，但受编排器整体容量约束；审批出终态或超时即回收，回收后可再拉起；连临时空库。
- **档位是平台级实体**：跨租户共享、平台超管维护；停用只拦新选择；快照记档位标识、规格取当前值。
- **密钥扫描是 presence check**：只查有无裸密钥 / 连接串，不判鉴权对错；运行时隔离仍是主保障。
- **结构演进快照**：改 / 删列迁移前自动留生产数据快照是硬承诺；应用数据表由应用包声明、平台建表（DEV-07 ②）。
- **`tenant_admin` 来源修正的行为变更**：一切使用该来源的场景与人工流程的实际审批人会从「系统超管」变为「真租户管理员」，release note 显著说明。

## 4. 待澄清决议

> 2026-08-17 用户授权全自动模式：以下各项按建议直接定案，记录理由供追溯；同日 `/sdd-review` 独立审查后增补决议-8 / -9 并修订决议-4 / -5。

- **[决议-1] 能力总线本版只做模型 + 知识库两项，密钥引用随 PRD-2。**（Discovery N4 已定，release-contract 未映射项同步收口）声明中出现密钥引用时预检拒绝并提示（AC-56）。
- **[决议-2] CLI 导入应用的发布面「提交发布」不可用、提示走 `bisheng deploy`；本册管线只验收 CLI 入口。** 理由：CLI 应用在平台侧无草稿工作区，发布面提交无可冻结的新快照；若允许「重提上一份包」会制造两个语义不同的提交动作。**何时重新考虑**：DEV-06 改码权交接随 PRD-2 落地后，发布面提交对已交接应用开放。
- **[决议-3] 审批人侧全部界面落在 client 审批中心弹窗（既有处理面），场景配置落 platform 审批中心场景配置。** 理由：PRD-1 §3.0.3 与 Discovery D5 已定处理面在 client；审读视图的文件树 + 只读代码是弹窗内的新增内容区。
- **[决议-4] 应用运行期凭据 = F049 底座签发、主体类型为「托管应用」（不是服务账号）。**（审查修订：原「每应用一个隐藏服务账号」与 F049 服务账号列表全量可见 / 资源归属人必填相冲突）理由：GOV-08 明令不作产品概念、无管理入口；作为独立主体类型既不污染服务账号列表、也不需要归属人（应用 owner 即归属）；F049 底座只需支持第二类主体绑定（F049 spec 范围边界已注明）。**何时重新考虑**：若将来要在管理面查看应用凭据（PRD-1 §5.2 已取消），再评估是否升格为可见主体。
- **[决议-5] 临时预览实例超时默认 7 天，部署配置项；拉起复用 F054 探活能力与预览入口路由，连一个临时空库。**（审查修订：统一为空临时库，去掉「草稿库」歧义）
- **[决议-6] 上线终检失败时版本记录终态标注为「待上线」（非 RT-05 三终态之一，作为过程态显示），应用态为待上线；手动上线成功后终态改为「已上线」、不产生新版本记录。** 理由：终态标注反映该版本的最终去向，过程态可显示但不算终态；应用态反映当前可用性；两条正交状态线是 §3.0.2 的既定模型。
- **[决议-7] MVP-114 首波边界**：管线端点（接收 / 快照 / 预检 / 扫描 / 版本记录 / 审批单 / 终检 / 上线）+ `deploy` / `logs` 服务端权限判定 + GOV-02 预置流程与三前置 + GOV-03 三档 seed 与选档 + WB-14 最小发布面（状态区 / 运营动作 / 入口链接槽位）+ 元信息随提交更新；纵切外：审读视图与临时预览实例、能力总线注入与收回、应用运行期凭据、结构演进快照、WB-15 差异、档位管理 tab、`withdraw` 守卫、事件触达全表——见 [../mvp-114-path.md](../mvp-114-path.md) §2。
- **[决议-8] 上线拉起 / 探活因非容量原因失败 → 应用态待上线（成因：上线失败），可重试手动上线或重新提交。**（审查新增）理由：PRD 只定义容量成因；把「上线失败」作为待上线态的第二种成因（界面显示具体成因）比引入新应用态更贴合 §3.0.2 两条正交状态线，且复用手动上线路径。
- **[决议-9] 预检 / 扫描失败的提交不进版本列表；正式版本记录在通过预检与扫描时落。**（审查新增）理由：RT-05 三种终态覆盖不了「预检失败」，DEV-04 验收 4 又要求预检失败不产生审批单；把失败提交挡在版本列表之外，版本列表只含进过审批流的版本，读者不必区分「失败版本」。
