# 代码节点执行约定加固

状态：已实现（`code_parse.py`、`errcode/sandbox.py`、`api_errors` 28007/28008、`test/sandbox/test_sandbox_code_parser.py`）；真实 E2B 与容器环境的验证尚未执行。

参照 2.x 代码节点漏洞补丁（`docs/workflow/代码节点漏洞补丁说明.md`、`docs/workflow/code_parse.py`），挑出对 3.0 仍然成立的检查。3.0 的代码节点已经不在后端进程里执行用户代码，执行走代码执行器的 `execute_code`（见 [代码节点与代码执行器共用执行后端](./代码节点与代码执行器共用执行后端.md)）；隔离边界是容器 runner、E2B，或本机模式的 uid 隔离（见 [第一步](./LocalExecutor安全优化方案-第一步-uid隔离.md)）。本文只补"执行约定"上的缺口，不改隔离方式。

## 目标

- 缺 `main` 在上线、调试或运行构建节点时报错，不等到进沙箱。保存草稿不检查。
- 节点的返回值和用户的 `print` 走两条通道，上游数据里的任何字符串都不能让结果被误判。
- 结果有大小上限，超限给出明确错误，不出现"截断后 JSON 解析失败"这种看不出原因的报错。
- 失败信息只带末尾一段，不把整份 stderr 写进运行日志和页面。

超时不单设。代码节点继续用各执行器现有的超时：本机、容器默认 600 秒，E2B 用 SDK 默认值。`_invoke_execute` 不传 `timeout`。

**不解决**：用户代码能做什么（能导入哪些库、能不能联网、能不能读写文件）。这由执行器所在的隔离环境决定，本文不加静态白名单，理由见"不做"。

## 现状（已对照代码核实）

| 位置 | 现状 |
|---|---|
| `SandboxCodeParser.parse_code`（`workflow/nodes/code/code_parse.py`） | 只做 `ast.parse`。没有 `main` 时，要到沙箱里执行包装脚本才报 `NameError` |
| `build_code_node_wrapper` | 用户源码原样拼在前面，后面追加 `_bisheng_*` 变量调用 `main`，结果以 `__BISHENG_CODE_NODE_RESULT__` 加 JSON 打到 stdout；序列化失败打 `__BISHENG_CODE_NODE_UNSERIALIZABLE__` |
| `_parse_sentinel` | stdout 里**任意位置**出现 `UNSERIALIZABLE` 就报 28005；结果取最后一个 `RESULT` 之后的那一行。用户 `print` 和结果混在同一个流里 |
| `SandboxCodeParser.exec_method` | 非零退出时 `RuntimeError(logs)`，`logs` 是执行器返回的整份 stderr |
| `LocalExecutor._execute_code` | 非零退出返回整份 stderr，不截断（只有超时分支用 `_tail` 截到 8000 字符）；成功返回 stdout |
| `ContainerExecutor._logs_from` | 成功返回 stdout，失败返回 stderr（为空时退回 stdout）；runner 端不截断 |
| `E2bCodeExecutor.execute_code` | 成功返回 stdout，失败返回 stderr 加错误文本 |
| `_invoke_execute` | 调 `execute_code` 不传 `timeout`。本机、容器默认 600 秒，E2B 不传就用 SDK 默认值 |

两个具体问题：

- **上游数据可以触发误判。** 例如 `main` 里 `print(上游节点输出)`，而上游内容恰好含 `__BISHENG_CODE_NODE_UNSERIALIZABLE__`，节点会报"输出不可序列化"。哨兵是固定字符串，写在源码里，谁都能拼出来。
- **结果行必须落在第一步的输出窗口里。** 本机模式每个流保留开头 4 MiB、结尾 512 KiB，两者之和以内的内容会原样拼回。结果上限 4 MiB 再加 nonce 前缀，小于这个窗口，整行不会被截断。窗口装不下时中间被丢掉，`json.loads` 失败，报出来的会是 28005，与真实原因无关。

## 设计

### 1. 构建节点时检查 `main`

`SandboxCodeParser.parse_code` 在 `ast.parse` 之后，检查模块顶层是否有 `def main`：

- 有 `FunctionDef`，名字是 `main`：通过。
- 只有 `async def main`：拒绝，提示 `main` 不能是 `async`。包装脚本同步调用它，得到的是协程对象，序列化必然失败。
- 都没有：拒绝，提示需要一个顶层 `main` 函数。

检查写在 `CodeNode.__init__` 调用的 `parse_code` 里，不在保存草稿的接口上。真正构建节点的地方有三处：上线时 `update_flow_status` 会构建一次 `Workflow`；单节点调试 `run_once` 会构建这个节点；每次工作流运行都会构建图。保存草稿不经过这里。报错沿用现有方式：`CodeNode._parse_code` 把异常包成 `CodeNode {name} exec code error: …`，和语法错误一样在构建节点时失败，不会进沙箱。

只认模块顶层的 `def main`，这一点已确认，不再等现场数据扫描。`main = …`、`from x import main`、写在 `if` / `try` 里或类方法上的 `def main`，构建节点时都拒绝，提示需要一个顶层 `main` 函数。运行时本来就是执行完整个模块再按全局名字调用，这些写法今天能跑。

**已上线的工作流。** 编辑器里已经是这种写法的节点，升级后下一次运行就会在构建图时失败，不是等用户再次保存才被拒。上线、单节点调试同样会失败。发布说明里要写明：先把这些节点改成模块顶层的 `def main`，再升级。按默认模板写的 `def main(...)` 不受影响。

**不检查** `main` 的参数是否与节点输入对应：运行时 `main(**params)` 不匹配会得到明确的 `TypeError`，提前检查要处理默认值和 `**kwargs`，收益小。

### 2. 结果通道与日志分开

包装脚本改成下面的结构（示意）：

```python
import json as _j, linecache as _lc, os as _o, sys as _s, traceback as _tb, types as _t

if "ipykernel" in _s.modules:
    # E2B run_code: logs.stdout is this Python stream, not fd 1.
    _out = _s.stdout
    _s.stdout = _s.stderr
else:
    # Script (local / container): the parent reads fd 1 through a pipe.
    # dup is non-inheritable; utf-8 so the locale cannot break non-ASCII JSON
    _out = _o.fdopen(_o.dup(1), "w", encoding="utf-8")
    _o.dup2(2, 1)                     # print and child processes follow fd 1
    _s.stdout = _s.stderr
    # The built-in hook reads source from disk, not linecache; skip this
    # script's own frame when the error comes from user code.
    _s.excepthook = lambda t, v, tb: _tb.print_exception(t, v, tb.tb_next or tb)

_src = USER_SOURCE        # same string constant passed to compile
_lines = _src.splitlines(True)
if _lines and not _lines[-1].endswith("\n"):
    _lines[-1] += "\n"
# mtime is None: traceback calls checkcache first, and a real mtime would
# stat "<code-node>", fail, and drop this entry before the line is read.
_lc.cache["<code-node>"] = (len(_src), None, _lines, "<code-node>")

# A plain dict would set __module__ to "__main__" without putting the class
# on sys.modules["__main__"], and pickle would fail to find it.
_user = _t.ModuleType("__main__")
_s.modules["__main__"] = _user
exec(compile(_src, "<code-node>", "exec"), _user.__dict__)
_ret = _user.__dict__["main"](**_j.loads(PARAMS_JSON))
try:
    _data = _j.dumps(_ret, ensure_ascii=False).encode("utf-8")
except (TypeError, ValueError):
    _line = NONCE + ":unserializable\n"
else:
    if len(_data) > LIMIT:
        _line = NONCE + ":too_large:" + str(len(_data)) + "\n"
    else:
        _line = NONCE + ":ok:" + _data.decode("utf-8") + "\n"
_out.write(_line)
_out.flush()
```

要点：

- **先改道，再执行用户代码。** 用 `"ipykernel" in sys.modules` 区分，结果都写回改道前留下的那个流对象。没有 ipykernel 时是本机和容器：它们用 `python 脚本` 起进程，父进程用管道接 1 号文件描述符。`os.fdopen(os.dup(1), "w", encoding="utf-8")` 留下这根管道，再 `dup2(2, 1)` 并把 `sys.stdout` 指到 stderr，用户的 `print` 和子进程的输出都进 stderr。有 ipykernel 时是 E2B：`sandbox.run_code` 在 Jupyter 内核里执行，`execution.logs.stdout` 收的是内核换成的 `sys.stdout`，不是 1 号文件描述符。先留下这个对象，再把 `sys.stdout` 指到 `sys.stderr`。`os.write(1, …)` 进的是内核进程自己的日志，`logs.stdout` 里没有结果行，节点会因没有合法结果行失败。内核里子进程继承的是真实文件描述符，输出本来就不会进 `logs.stdout`，所以这条路径不改 1 号描述符。两种路径都对留下的流对象 `write` 结果行并 `flush`。stdout 上只有这一行。脚本方式的结果流必须写明 `encoding="utf-8"`：结果是 `ensure_ascii=False` 的 JSON，常含中文；`local_isolation=off` 时子进程直接继承后端进程的环境变量，区域设置不是 UTF-8 时，不写明编码会在 `main` 跑完之后、写结果那一步抛 `UnicodeEncodeError`，报错看起来像用户代码出错。后端按 UTF-8 解码这根管道，两端一致。
- **用户代码用 `compile(…, "<code-node>", …)` 单独编译**，以字符串常量（`repr`）嵌进包装脚本，再 `exec` 进一个新建的模块。好处是 traceback 的行号就是用户编辑器里的行号，文件名是 `<code-node>`，不暴露 R 或临时目录路径。包装脚本自己的名字留在原来的全局变量里，用户的顶层名字（包括 `_bisheng_*`）落在这个新模块上，两边不撞。`compile` 只把文件名和行号写进 code object，源码文本不保留。traceback 再靠 `linecache.getline` 取那一行，而 `"<code-node>"` 这种尖括号名字在 `linecache.updatecache` 里直接返回空列表，所以帧下面不会出现源码。登记必须写在包装脚本里、`exec` 之前（traceback 在子进程里格式化，登记在后端进程没有用）：`linecache.cache["<code-node>"] = (len(source), None, lines, "<code-node>")`。`mtime` 用 `None`，否则打印前的 `checkcache` 会对这个名字做 `os.stat`，失败后把登记删掉，源码行仍然出不来。脚本方式下还要换掉 `sys.excepthook`：解释器自带的钩子是 C 实现，按文件名直接读磁盘、不查 `linecache`，未捕获异常照样不带源码行。换成 `traceback.print_exception` 之后登记才起作用；顺带跳过包装脚本自己那一帧，临时文件路径不会出现。用户代码之外的错误（例如参数名不匹配，报在包装脚本的调用行上）只有这一帧，原样打印。E2B 内核用 IPython 自己的格式化，本来就查 `linecache`，不换钩子。
- **这个模块要放进 `sys.modules["__main__"]`。** `ModuleType("__main__")` 的 `__dict__` 自带 `__name__ == "__main__"`，用户定义的类和函数的 `__module__` 因此是 `"__main__"`。pickle（以及 `multiprocessing`、`joblib`、`pandas.to_pickle`）按 `sys.modules[类.__module__]` 找这个类，找不到就抛 `PicklingError`。只传 `{"__name__": "__main__"}` 这种普通字典时，`__module__` 写对了，类却不在 `sys.modules["__main__"]` 上，今天能 `pickle.dumps` 的自定义对象会失败。换成模块对象之后，`sys.modules["__main__"].类 is 类`，同一次执行里的 `dumps` / `loads` 与现在一致。
- **`NONCE` 每次调用由后端用 `secrets.token_hex(16)` 生成。** 后端只接受这样的 stdout：去掉末尾换行后恰好一行，并以 `NONCE + ":"` 开头。上游数据里出现什么字符串都不会被当成结果。用户代码自己往保存下来的结果流写东西不在防范范围内，那是作者自己的代码。
- **结果上限 `LIMIT = 4 * 1024 * 1024`（4 MiB）**，与 2.x 补丁的 `STDOUT_LIMIT` 相同。比的是 JSON 的 UTF-8 字节数，不含 nonce 前缀。包装脚本里先判断，后端解析时再判断一次。三种后端用同一个值。
- **不另给代码节点放宽 stdout。** 本机模式开头 4 MiB、结尾 512 KiB，已经装得下一条「4 MiB JSON + nonce 前缀」。容器 runner 从管道读完整 stdout。E2B 成功时返回的是 `logs.stdout` 里收齐的文本，也不按 512 KiB 截断；这份文本来自改道前的 `sys.stdout`，不是 1 号文件描述符。三种后端的结果上限相同，写结果的那一端不相同。stdout 实际写出的字节多于保留下来的（被截断）时，不拿残行去 `json.loads`，按没有合法结果行处理（28008）。超限时包装脚本写的是很短的 `too_large` 行，会被完整读到，后端报 28007。
- 解析结果：

  | stdout | 处理 |
  |---|---|
  | `NONCE:ok:<json>` | `json.loads` 后交给 `_parse_code_output`，后者照旧检查是 `dict`、包含每个输出字段 |
  | `NONCE:unserializable` | 28005 `SandboxCodeNodeOutputError`，不变 |
  | `NONCE:too_large:<n>` | 新错误码 28007 `SandboxCodeNodeOutputTooLargeError`，文案写明上限和实际大小 |
  | 退出码非零 | 见第 3 条 |
  | 退出码为零但没有合法的结果行（例如 `main` 里或顶层调用 `sys.exit(0)` / `os._exit(0)`，或用户往留下的结果流里写了别的内容） | 新错误码 28008 `SandboxCodeNodeNoResultError`，文案写明代码运行结束但没有返回结果。现在这种情况报 28005「不可序列化」，用户会去查返回值，而真正的原因是根本没有返回 |

- 成功时用户的 `print` 进 stderr，三种执行器成功时都只返回 stdout，所以不会出现在节点结果和运行日志里。这与 2.x 补丁一致；失败时 `print` 会出现在第 3 条的末尾片段里，用来排错。

### 3. 失败信息截尾

`exec_method` 在退出码非零时截断 `logs` 再抛出。截断写在 `code_parse.py` 里，三种后端共用，不调用 `LocalExecutor._tail`。`_tail` 是本机执行器的私有方法，只服务于解释器交给模型的失败日志：默认 8000 个字符，超出时加的是英文 `"[... earlier output truncated ...]\n"`。代码节点在容器和 E2B 上也会走到这里，工作流层不应依赖它。

上限是 **4096 个字符**（Python `str` 的 `len`，一个汉字算 1）。`logs` 已经是字符串，按字节切会切在 UTF-8 序列中间。不超过 4096 原样抛出；超出时保留末尾 4096 个字符，前面加一行 `"[... earlier output omitted ...]\n"`（与其他后端错误信息一样用英文，后端不做多语言）。这一行不算进 4096，避免把 traceback 末尾的原因挤掉。

改成 `<code-node>` 编译后，用户代码那几帧本来就不含路径，包装脚本自己那一帧由上面换掉的 `excepthook` 跳过。出错那一行源码靠上面的 `linecache` 登记出现在 `File "<code-node>", line N` 的下一行。

## 不做

| 2.x 补丁里的检查 | 不做的原因 |
|---|---|
| 导入白名单（16 个标准库模块加 `pymysql`） | 补丁自己说明它"不是安全边界"。3.0 的执行环境是带 pandas、requests 的完整 Python，白名单会挡掉大量正常写法。拦截清单里 2.x 的 48 个节点在白名单下就有 15 个被拦（`codecs`、`eval`、`type(obj).__name__`、`requests`） |
| 禁用 `eval`、`exec`、`open`、`getattr` 等名字，禁止下划线开头的属性，禁 `class`、装饰器、非常量默认值，顶层只能是字面量赋值 | 同上。这些规则配合补丁的进程内 runner 才有意义；3.0 把代码当脚本整体执行，`import os` 本来就允许，单独禁 `open` 没有意义 |
| 受限 builtins、只读模块代理 | 只适用于"在受控的 `exec` 环境里跑"。3.0 没有这层可挂 |
| `chroot /opt/code-root` | 要改镜像。本机的 chroot 方案暂时不做；代码节点需要这层隔离时走容器模式 |
| 环境变量白名单、只保留管道 fd、独立 uid 池、按 uid 清场、失败不退回进程内执行 | 本机模式由第一步覆盖（代码节点走临时模式）；容器模式由 runner 负责；E2B 在远端 |
| `RLIMIT_CPU` 25 秒、`AS` 1 GiB、`FSIZE` 0、`NPROC` 1 | 第一步已有上限（`AS` 2 GiB、`nproc` 256）。照搬 `NPROC=1` 会让 numpy 的 BLAS 线程起不来，因为 3.0 允许这些库。若要给代码节点单独一档更紧的上限，另行评估 |
| 代码节点单独的超时（2.x 补丁为 30 秒） | 不增加。沿用执行器现有超时：本机、容器 600 秒，E2B 用 SDK 默认值 |
| `patch-mcp-stdio.py` | 与代码节点无关 |

`local_isolation=off` 或第一步尚未上线时，本机模式的代码节点以 root 跑、继承全部环境变量。这时静态检查也挡不住，靠的是 `workflow.code_node_enabled` 默认关闭。

## 测试

不需要 root：

- 没有 `main`、只有 `async def main`、`main = …`、`from x import main`、或 `def main` 写在 `if` / `try` / 类里面时，`parse_code` 失败，错误信息说明原因；模块顶层有 `def main` 时通过。
- `main` 里 `print("__BISHENG_CODE_NODE_UNSERIALIZABLE__")`、`print` 一个伪造的 `xxx:ok:{}` 行，结果仍是 `main` 的真实返回值。
- 脚本方式下，顶层 `print` 和 `subprocess.run(["echo", "x"])` 的输出不出现在 stdout。
- 返回 `set()` 等不可序列化对象得到 28005；返回超过 4 MiB 的字典得到 28007，信息里有实际大小。
- `main` 里 `sys.exit(0)`、顶层 `os._exit(0)`、往留下的结果流里写一行非 nonce 开头的内容，都得到 28008，不是 28005。
- 脚本方式下，用户代码第 3 行抛异常，失败信息里是 `File "<code-node>", line 3`，紧接着的下一行是这一行源码，且不含临时目录路径。
- 脚本方式下，子进程环境的区域设置不是 UTF-8（例如 `LANG=C`、不设 `PYTHONUTF8`）时，返回含中文的 dict 仍能完整解析。
- stderr 超过 4096 个字符时只保留末尾 4096 个字符，前面有省略提示行，且末尾含异常类型和消息。不超过 4096 个字符时原文抛出，不加这行提示。
- 用户代码定义名为 `_bisheng_params` 等的顶层变量，不影响调用。
- 用户代码里的类实例可以 `pickle.dumps` 再 `pickle.loads`，类能按 `__main__` 找到。

需要 root（`local_isolation=uid`）：

- 返回约 3 MiB 的结果，经本机输出窗口（开头 4 MiB、结尾 512 KiB）后完整解析。

容器模式：

- 同一组用例对 `type=container` 跑一遍，结果一致。

E2B：

- mock `sandbox.run_code`：只有写进改道前 `sys.stdout` 的结果行算 stdout，`os.write(1, …)` 不算；`print` 不出现在这份 stdout 里。
- 在真实 E2B 上跑以下几项。mock 盖不住内核是否把这个流对象收进 `logs.stdout`，也盖不住 IPython 的 traceback 格式：
  - 顶层 `def main` 返回一个小 dict，结果行能被解析。
  - 用户代码第 3 行抛异常，失败信息里能看到 `<code-node>` 和行号 3，以及这一行源码。IPython 的格式和脚本方式不同（形如 `File <code-node>:3`），断言不能照搬脚本方式那一条。错误文本来自 `execution.error.traceback`，常带 ANSI 颜色控制字符，会占 4096 个字符的截尾预算，这是现状，不在本文处理。
  - 用户代码里的类实例可以 `pickle.dumps` 再 `pickle.loads`。在内核里替换 `sys.modules["__main__"]` 会换掉 IPython 自己的用户命名空间模块，需要实测确认不影响这次执行。
