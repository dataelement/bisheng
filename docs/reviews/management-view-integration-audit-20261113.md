## 2. 访客链接配置 404 的原因

1. `src/backend/bisheng/common/middleware/admin_scope.py` 登记了 `/api/v1/flows` 和工作流创建/编辑，却未登记 `/api/v1/guest-link`。
2. 后者是已登录用户管理应用访客链接开关的配置接口，不是匿名访客执行接口。路由源码明确标注 `Management API`，并使用登录依赖。
3. `src/backend/bisheng/public_endpoints/domain/services/guest_link.py:125` 在权限判断前调用 `FlowDao.aget_flow_by_id`。请求未进入管理上下文，仍按账号 Root 租户过滤，租户 60 的工作流因而被查成不存在，返回业务码 404。
4. `src/frontend/platform/src/components/bs-comp/apiComponent/ChatLink.tsx` 加载链接设置时发出该 GET；`src/frontend/platform/src/controllers/request.ts:216` 对 GET 的业务码 403/404 做整页跳转。因此附属配置错误把已能打开的主资源编辑页送到 `/404`。

同一加载函数也处理助手；访客链接 PATCH 同样未接入统一管理范围及预期租户校验。助手与 PATCH 是源码确认的同路径影响，本轮未通过写数据实测。

修复应仅覆盖已认证的访客链接管理配置，保留 `visible`/`share` 动作和候选执行人资格校验；不能把匿名执行入口一并纳入管理选择。PATCH 应校验预期管理租户；前端附属配置加载失败应局部展示错误和重试，主资源确实不存在时才跳整页 404。

## 5. 避免持续漏接的统一方案（建议，未实施）

用户关心的是超管切换后整个管理端的行为一致性。当前实现不能证明已经没有遗漏：管理范围依赖 `MANAGEMENT_API_PREFIXES`，预期租户写校验依赖另一份规则，前端又维护独立 URL 正则。未登记的路由仍可运行，并悄悄使用账号主属租户。修复单个 URL 不能消除这个结构性问题。

### 5.1 每个实际路由有范围声明，未声明不能通过检查

使用路由元数据或统一路由构造入口声明请求范围，而非再建一份独立 URL 清单：

| 范围 | 数据范围与授权来源 |
| --- | --- |
| 租户管理 | 经过服务端核验的管理目标；非超管只能使用其合法自身管理范围；保留具体资源动作权限 |
| 个人身份 | 当前用户主属租户和个人权限；不读取超管管理选择 |
| 平台全局 | 仅属于平台级的数据和设置；仍检查相应管理资格，不等于绕过全部业务隔离 |
| 凭据或能力限定 | 已验证机器凭据、分享链接、回调或工作负载的范围；各入口保持独立认证，不继承浏览器管理选择 |

同范围模块在路由组声明，子接口自动继承；一个模块中混用管理、个人、匿名用途时，拆分路由组或显式声明具体端点，禁止通过模块名称猜测。不同 HTTP 方法可以有不同声明，写入标识按实际副作用声明，不假设所有 GET 都无副作用。

启动及持续集成枚举实际注册的路由，要求范围声明完整且无冲突；遗漏即失败，不默认归为个人接口。构建检查须覆盖启用/关闭特性后的不同路由组合；WebSocket、挂载子应用和非 Python 服务单列入口契约，不能只统计 FastAPI 的 HTTP 路由就宣称覆盖全部管理端请求。

该校验只能防止“未声明”，不能自动证明“声明正确”。需要同时核对业务规则和实际对象归属。

### 5.2 一个统一入口核验并固定请求范围

复用当前身份校验、`TenantScopeService`、`management_tenant_scope` 和数据库租户过滤。逻辑顺序是验证真实身份、确定路由用途、核验管理选择及目标状态、比较预期租户、为业务处理绑定固定范围，结束后恢复上下文。选择只确定操作对象，不增加资源动作权限，也不改 JWT、账号主属或普通角色绑定。

技术入口必须处于路由匹配之后，例如统一路由包装或依赖；不能假设当前前置 `BaseHTTPMiddleware` 已经能读到最终路由元数据。实施时还要验证认证依赖、范围绑定、资源权限依赖的执行顺序，避免业务查询先于范围生效。

不提供一个含糊的“租户 ID”供所有用途复用。当前身份和本次管理目标分别可取得；领域接口按用途消费明确的范围。迁移时逐项修正把 `login_user.tenant_id` 用于目标资源创建的代码，不能仅换路由声明就认为看板、角色等已正确写入。

### 5.3 前端统一携带快照，后端负责裁决

平台浏览器的公共请求层统一携带服务器确认过的当前管理目标快照；无需再按每条业务 URL 决定是否附带。服务器根据路由声明决定是否消费它；个人、平台、凭据入口不得因收到此头而改作用域。范围读取/切换入口需要明确的自举规则，避免首次加载还没有快照便无法获取快照。

所有管理写操作统一要求预期目标；缺失、不符或无法核实则拒绝。管理读取也校验已有快照，返回实际范围并拒绝混入旧响应。请求一经准入便使用冻结的目标，不能在保存中途重新读取 Redis 而改投其他租户。只校验租户标识可以防止跨租户错投，不代表能识别 A→B→A 的所有旧表单版本；资源版本冲突仍由现有业务版本规则处理。

异步任务在提交时保存并携带已核验的目标，使用现有任务/资源字段恢复执行范围，不在执行时读取用户后来选中的租户。浏览器缓存、表单和旧请求须按管理目标隔离并在切换后失效。

前端存在 `/api/sensitive/...` 等非 `/api/v1` 请求，不能只检查 Python 路由。实际部署经过 Java 网关或其他后端的管理请求，也必须在对应服务执行同样的范围契约；代理转发请求头本身不是授权证明。

### 5.4 用两层自动验证防漏和防错

第一层是路由完整性检查：发现未声明、声明冲突、管理写入未走统一准入、不同部署组合遗漏入口时失败。范围清单从真实路由生成，不再维护第二份手工列表作为真相。

第二层是跨租户业务链测试：用主属 Root、管理子租户的超管，以及普通用户/子租户管理员，验证列表、详情、创建、初始版本、访客链接、候选人、保存、复制、删除、导出、异步任务。断言响应和实际持久化对象的租户、关联对象归属、权限均正确，不能只断言没有 404 或 HTTP 200。必需反例包括伪造目标、旧表单、两个标签页、旧请求晚返回、管理选择过期，以及角色/引用校验异常仍被拒绝。

对截图中的审计页面，应分别覆盖各标签、筛选候选项、查询、分页及导出。顶部显示所选租户不能证明所有下游接口都使用该范围；空列表也不能单凭截图判为范围错误。

### 5.5 控制实施范围

不新增业务表，不改变账号归属，不批量迁移数据，沿用现有租户过滤和资源授权。分阶段先清点并声明全部入口，再按模块迁移并完成对应业务链验证；旧、新路径不能同时叠加设置上下文，最终退出手工路径清单。全路由强校验在声明补齐且真实覆盖验证通过后启用，避免先在运行环境启用而阻断所有存量接口。

该方案涉及公共路由、公共请求层及实际错误用租户的消费点，范围大于单个白名单补丁；它仍不要求重写所有领域服务或新增通用操作中心。实施前需要按项目规范确认范围及技术设计，本轮仅记录建议。

## 6. 资源租户与创建人主属租户不一致的关联读取

超管主属 Root、在租户 A 创建资源是合法场景。资源、初始版本、权限模式、授权及授权来源记录应归资源租户 A；创建人仍记录真实账号 ID，账号不因此成为 A 的成员，也不复制账号或改写主属。

当前源码核对：

- `User` 是平台身份记录，本表及其基类没有 `tenant_id`；主属通过 `UserTenant` 等事实表达。工作流列表在 `src/backend/bisheng/api/services/workflow.py:201` 按资源记录引用的用户 ID 查询名称。因此这一条名称读取链路不会仅因创建人主属 Root 就被 A 的租户过滤掉。
- 标准授权列表通过 `TenantPermissionSubjectDirectory.display_names` 按现有授权记录的用户 ID 装饰名称，不要求该用户出现在当前租户的新增授权候选列表中。
- 创建者授权在 `src/backend/bisheng/permission/application/control_state.py:902` 使用 `target.tenant_id` 构造授权身份；持久化 `PermissionGrant` 使用 `grant.tenant_id`，`PermissionGrantAssignee` 使用对应授权行的租户。它们不应按创建人的 Home 保存到 Root。
- 授权列表入口要求 `manage_permission`。有资源查看权不代表能查看完整授权清单；二者必须区分，不将权限拒绝误判为创建人跨租户导致授权丢失。
- 另有用于应用发布“当前可见人员”摘要的 `describe_active_sources`，会过滤主属不匹配的用户；调用处对 owner 当前资格也做主属匹配。该摘要表达当前有效使用者，与历史创建人、原始授权清单语义不同，不能直接复用来展示后两者。超管跨租户创建时该摘要应如何呈现，仍需结合真实账号和权限规则回归，不能据此直接放开普通外租户用户授权。

统一原则：先验证查看者可访问该资源，再按资源及其授权引用的明确人员 ID 返回最小展示信息；不开放跨租户人员目录。新增授权候选、现有授权记录展示、当前使用资格分别校验。人员停用、迁出或删除时保留创建和授权来源事实，实际访问按当前有效规则决定；名称不可解析时明确显示已删除或不可用，不能因此隐藏资源或整条授权。

验收应增加：Root 超管在 A 创建后，A 的普通获权用户可看到创建人最小信息；A 的有权权限管理员可见现有创建者授权和本租户授权；新增人员候选仍受 A 的规则限制；本人名称展示不泄露账号密码、联系方式等无关身份信息；迁出/停用后历史展示与当前访问资格分别正确。本轮为源码核对，尚未用子租户普通账号完成这些现场验收。
