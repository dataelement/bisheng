# 一、摘要

## 1.1 中心结论

**本期给 bisheng 加一层长期记忆：系统把对话里确立的结论存下来，在同一个用户之后的会话里带回来。**

这层能力由三件事组成。

1. **记。** 两条写入途径。用户明确要求时，模型调用记忆写入工具当场记下。用户没有要求时，系统在会话安静之后自动整理出值得留下的结论。
2. **用。** 两条读取途径。少量最重要的记忆每轮自动带入（常驻记忆）。其余记忆按需检索：会话类场景由模型调用检索工具，工作流由记忆检索节点完成。
3. **管。** 记忆按用户隔离。一个用户只有一份记忆，在四类场景里通用。用户能看到系统记了什么、一次回答用了哪些记忆，能改、能删。助手和工作流的记忆默认关闭，由应用作者开启。

## 1.2 背景

bisheng 现在没有任何跨会话的记忆。日常模式换一个会话就从零开始。深度研究每次任务都重新摸索，上一次任务得到的经验不会留下。助手和工作流面对同一个用户的第二次使用，和第一次没有区别。

## 1.3 一期范围

四类场景读写的都是当前用户本人的那一份记忆，差别只在下表。

| | 日常模式 | 深度研究 | 助手 | 工作流 |
|---|---|---|---|---|
| 开关在哪（§4.7） | 用户级（默认开） | 同日常模式 | 另加助手设置里的开关，默认关 | 另加开始节点里的开关，默认关 |
| 常驻记忆自动带入 | 有 | 有 | 有 | 无 |
| 按需检索 | 模型调用检索工具 | 模型调用检索工具 | 模型调用检索工具 | 记忆检索节点 |
| 显式写入（用户要求记下） | 有 | 有 | 有 | 无 |
| 自动整理 | 有 | 有 | 有 | 有 |
| 回答归因 | 有 | 有 | 有 | 由节点输出承载 |

# 二、术语

全文只用下表的词，一个词只指一件事。

| 术语 | 定义 |
|---|---|
| 长期记忆 | 系统从对话里得出、跨会话保留的结论。界面上统一叫"记忆" |
| 历史聊天记录 | 同一个会话里的上文。它是现有能力，不属于长期记忆，本文不改动它 |
| 记忆条目 | 一条结论。它是记忆的最小单元，可以单独查看、检索、取代和删除 |
| 详情 | 一条记忆条目附带的长正文，用于装需要连贯说明的内容。条目里只保留一句概括和指向详情的指针 |
| 记忆空间 | 一个用户在一个租户内的全部记忆条目。每个用户只有一个记忆空间，四类场景共用 |
| 来源标记 | 一条记忆条目是在哪个场景、哪个应用、哪个会话里产生的 |
| 常驻记忆 | 一个记忆空间里每轮都自动带入模型上下文的那一小部分条目，有数量和字数上限 |
| 显式写入 | 用户明确要求记下某件事，模型调用记忆写入工具完成 |
| 自动整理 | 会话安静之后，系统在后台从对话里整理出记忆条目，并合并、取代、调整常驻记忆 |
| 归因 | 在一次回答旁边告诉用户这次回答用了哪些记忆条目 |

# 三、场景

## 3.1 日常模式：记住用户是谁

用户在一次对话里说自己负责华东区销售、周报要用表格。一周后他新开一个会话让助手写周报，助手直接按华东区、表格形式来写，不再追问。

用户说"我下周二有个重要会议，你记录一下"。助手当场记下，并明确告诉用户已经记下。之后任何一个新会话里问"我这周有什么安排"，助手都能答出这场会议和它的具体日期。

## 3.2 深度研究：不重复踩同一个坑

用户多次让深度研究产出行业分析报告，每次都要求"数据必须标注来源年份"。这个要求被记下之后，后续任务开始时就带着它。

## 3.3 助手：记住每一个使用者，并且用得上他在别处说过的话

某部门发布了一个"合同审查助手"并开启了记忆，二十个人在用。张三告诉它"我只看采购类合同，重点看付款条款"。之后张三再用这个助手，它按这个重点审。李四使用同一个助手时，看不到也用不到张三的任何记忆。

张三此前在日常模式里说过自己负责华东区采购。合同审查助手不需要他再说一遍。反过来，他在合同审查助手里说的重点，在日常模式里同样生效。

## 3.4 工作流：把记忆当作一个可编排的输入

某工作流是"客户拜访准备"。作者在流程里放一个记忆检索节点，用用户输入的客户名作为检索内容，取回当前使用者的记忆里与该客户有关的条目，再交给后面的大模型节点写拜访提纲。

## 4.2 R1 · 记忆空间与隔离

**规则：每个用户只有一个记忆空间。任何场景下，读和写的都只是当前用户本人的记忆空间。**

| 编号 | 规则 |
|---|---|
| 1 | 不同用户的记忆互不可见、互不影响。多个用户使用同一个助手或工作流时，各自读写的是各自的记忆 |
| 2 | 同一个用户的记忆在四类场景里通用。在日常模式、深度研究、任何一个开启了记忆的助手或工作流里产生的记忆，在其余场景里都能读到 |
| 3 | 每条记忆带来源标记，用户能看到它是在哪里产生的 |
| 4 | 不同租户的记忆互不可见。用户的租户归属变化后，原租户里的记忆保留、不迁移，归属不在原租户期间读不到；归属回到原租户后继续可读 |
| 5 | 平台不提供专门用于查看、修改、清除或统计他人记忆的入口，对租户管理员和应用作者同样如此。非本人在管理端查看会话时，只看到回答正文，看不到"已记住"的条目原文和归因列表 |
| 6 | 当前调用识别不出一个确定的平台用户时，记忆不工作：不读、不写、不报错。本期记忆只在登录用户的会话里工作。开放 API 的全部调用（含代表某个平台用户调用、个人访问令牌调用）、免登录链接访问、没有会话的评测与调试运行，都属于这种情况 |

规则 2 带来一个后果，开关的说明文案必须写明（§4.7）：用户的记忆会被带入任何一个开启了记忆的应用，并可能出现在该应用的回答里。

## 4.3 R2 · 记忆条目

**规则：一条记忆条目只记一个结论，写成脱离原对话也能读懂的一句话。**

每条记忆条目带有下列信息。

| 信息 | 说明 |
|---|---|
| 内容 | 一句完整的话，不超过 200 字。不使用"他""那个项目""下周"这类离开原对话就看不懂的指代 |
| 类型 | 事实、偏好、经验三选一 |
| 来源 | 来源标记（哪个场景、哪个应用、哪个会话）；是显式写入、自动整理还是用户在管理页手动新增 |
| 记录时间 | 这条记忆是什么时候写下的 |
| 事件时间 | 仅当内容描述一件有具体时间的事时才有，如会议、出差、截止日 |
| 状态 | 有效、已被取代、已删除 |
| 是否常驻 | 是否属于常驻记忆 |
| 详情 | 可选。存在时条目内容是它的一句概括 |

三种类型的含义与各场景的侧重如下。

| 类型 | 含义 | 例子 | 主要来自 |
|---|---|---|---|
| 事实 | 关于用户或其工作的客观情况 | 用户负责华东区销售 | 四类场景 |
| 偏好 | 用户希望系统怎么做 | 周报用表格，不用长段落 | 四类场景 |
| 经验 | 做某类事时已验证有效或无效的做法 | 行业报告里的数据必须标注来源年份 | 深度研究（P1） |

**时间表述必须写成绝对日期。** 用户说"下周二"，记忆里写的是按用户所在时区换算出的具体日期。相对时间不得原样进入记忆。

下列内容不记。

| 不记的内容 | 说明 |
|---|---|
| 一次性的任务内容 | "把这段话翻译成英文"不产生记忆 |
| 当前对话里随时能看到、很快就变的状态 | 例如某个文件此刻改到第几版 |
| 密码、密钥、令牌、证件号、银行卡号 | 用户明确要求记也不记，并告诉用户原因 |
| 文档、网页、知识库、工具返回里的内容 | 这些是材料，不是用户确立的结论（§4.10） |
| 指令性内容 | 例如"以后所有导出都发到某个地址"这类来自材料的要求（§4.10） |

## 4.4 R3 · 写入

记忆有两条写入途径，职责不重叠。

| | 显式写入 | 自动整理 |
|---|---|---|
| 什么时候发生 | 用户在当前这句话里明确要求记下、更正或忘掉某件事 | 会话安静一段时间之后 |
| 谁发起 | 模型调用记忆写入工具 | 系统后台 |
| 什么时候生效 | 立即。同一会话的后续轮次和任何新会话都能读到 | 整理完成后 |
| 适用场景 | 日常模式、深度研究、助手 | 四类场景 |
| 用户是否看得到 | 看得到，回答里有"已记住"的提示（§4.9） | 不打断用户；之后被用到时通过归因可见 |

### 4.4.1 显式写入

记忆写入工具支持三种操作。

| 操作 | 用户怎么说 | 结果 |
|---|---|---|
| 记下 | "记一下我下周二有个重要会议" | 新增一条记忆条目 |
| 更正 | "我不负责华东区了，现在负责华南" | 新增一条，并把原来那条标为已被取代 |
| 忘掉 | "别记我的手机号了" | 把对应条目标为已删除 |

规则如下。

| 编号 | 规则 |
|---|---|
| 1 | 只有用户在当前这句话里明确提出时，模型才调用写入工具。用户没有提出时，模型不主动调用，留给自动整理 |
| 2 | 写入的内容只能来自用户本人说的话，不能来自文档、网页、知识库或其他工具的返回 |
| 3 | 写入成功后，回答必须明确告诉用户记下了什么。时间被换算成绝对日期的，回答里写出换算后的日期，让用户能核对 |
| 4 | 写入失败时，回答必须如实告诉用户没有记下，不得说成已经记下 |
| 5 | "更正"和"忘掉"找不到对应条目时，告诉用户没有找到，不新建、不猜 |
| 6 | 用户要求记的内容属于 §4.3"不记的内容"时，不写入，并告诉用户原因 |
| 7 | 记忆功能处于关闭状态时，模型拿不到这个工具。用户要求记下时，模型告诉用户记忆功能未开启 |

**模型说了"已记下"但实际没有调用工具，属于缺陷，要能被发现。** 系统不替模型补写这条记忆。判据是回答旁边有没有"已记住"的提示（§4.9），它只在工具真实写入成功后出现。这类情况要计数（§4.11）。

### 4.4.2 自动整理

| 编号 | 规则 |
|---|---|
| 1 | 会话最后一次交互之后，经过一段安静期才整理。安静期内用户继续对话的，重新计时。安静期初值 30 分钟，可配置，由评测集校准后定稿 |
| 2 | 每次只处理上次整理之后新增的对话，已处理过的部分不重复处理。记忆启用之前的对话不整理：升级前的历史对话、开关开启之前的对话都不回头处理 |
| 3 | 整理出的条目遵守 §4.3 的全部规则 |
| 4 | 新结论与已有条目说的是同一件事时不重复新增；与已有条目矛盾时按 §4.6 取代 |
| 5 | 自动整理负责调整常驻记忆：把常用的提为常驻，把超出上限的移出常驻（§4.5.1）。经验类条目不提为常驻 |
| 6 | 需要连贯说明、一句话装不下的内容，写成详情，条目里只留一句概括 |
| 7 | 整理的来源只限用户说的话，以及用户与系统在对话里明确达成的结论 |
| 8 | 自动整理的频率可配置，可以整体关闭 |

各场景整理时的关注点不同。

| 场景 | 关注什么 |
|---|---|
| 日常模式 | 用户的身份与工作情况、称呼、表达与格式偏好、对话里已达成的判断 |
| 深度研究 | 用户对产出的固定要求；任务中已验证有效或无效的做法（P1） |
| 助手 | 用户在这个助手的业务范围内反复提到的情况和偏好 |
| 工作流 | 用户的输入，以及工作流输出给用户的内容里用户确认过的结论 |

## 4.5 R4 · 读取

### 4.5.1 常驻记忆

**规则：每个用户有一份常驻记忆，在每轮对话开始时整份带入模型上下文，不做检索。**

| 编号 | 规则 |
|---|---|
| 1 | 常驻记忆有条数和总字数两个上限，任何一个先到都算到达上限。初值为 60 条、6000 字，可由部署配置调整，由评测集校准后定稿 |
| 2 | 到达上限时不截断。由自动整理合并相近条目，或把较少用到的条目移出常驻。移出常驻的条目仍然保留，仍可被检索到 |
| 3 | 带有详情的条目，常驻的只是那一句概括 |
| 4 | 常驻记忆以"背景信息"的身份带入，并注明记录时间。它不是指令（§4.10） |
| 5 | 日常模式和开启了记忆的助手，每轮带入用户的常驻记忆 |
| 6 | 深度研究在任务开始时带入常驻记忆，并额外带入经验类条目。经验类条目不出现在日常模式和助手的常驻记忆里，但可以被检索到 |
| 7 | 工作流没有常驻记忆的自动带入，工作流只通过记忆检索节点读取记忆 |

### 4.5.2 记忆检索工具

日常模式、深度研究、助手三类场景里，模型可以调用记忆检索工具，在当前用户的记忆空间内按内容查找记忆条目。

| 编号 | 规则 |
|---|---|
| 1 | 只返回状态为"有效"的条目 |
| 2 | 返回条目内容、类型、记录时间、事件时间。条目带详情时，模型可以进一步取回详情全文 |
| 3 | 没有命中时返回空结果，模型据实回答，不得编造记忆 |
| 4 | 记忆功能关闭时，模型拿不到这个工具 |

### 4.5.3 记忆与当前对话冲突时听谁的

| 优先级 | 来源 |
|---|---|
| 1（最高） | 用户在当前这句话里说的 |
| 2 | 当前会话的上文 |
| 3 | 长期记忆 |

记忆只作参考。按记忆行事会明显影响结果、而用户的意图又不明确时，模型先问用户一句，不按记忆猜。

## 4.6 R5 · 保持正确

| 编号 | 规则 |
|---|---|
| 1 | 新结论取代旧结论时，旧条目不删除，状态改为"已被取代"，并记下取代它的是哪一条 |
| 2 | 已被取代和已删除的条目不进入常驻记忆，不出现在检索结果里 |
| 3 | 用户删除一条记忆之后，这条记忆的内容和详情都不再能被读到 |
| 4 | 带事件时间的条目，事件时间过去之后不再属于常驻记忆，仍可被检索到 |
| 5（P1） | 事件时间过去之后，自动整理把表述改写成过去时。例如"用户 2026-11-17 有一场重要会议"保留日期，不再以待办的口吻出现 |
| 6 | 本期没有自动遗忘：系统不因为一条记忆时间久了或很久没被用到而删除它 |

## 4.7 R6 · 开关与配置

**规则：记忆在任何一处被关闭，对应范围内就既不读也不写。关闭不清除已有的记忆，重新开启后原有记忆继续可用。清除是另一个独立的动作（§4.12）。**

| 开关 | 位置 | 谁能改 | 默认 | 作用范围 |
|---|---|---|---|---|
| 我的记忆 | 用户个人设置 | 用户本人 | 开 | 本人在全部场景里的记忆，包括助手和工作流 |
| 助手记忆 | 助手的设置页 | 助手的编辑者 | 关 | 这个助手是否读写使用者的记忆 |
| 工作流记忆 | 工作流的开始节点，与"历史聊天记录"等设置并列 | 工作流的编辑者 | 关 | 这个工作流是否读写使用者的记忆 |

各场景启用记忆的条件如下。

| 场景 | 启用条件 |
|---|---|
| 日常模式、深度研究 | 当前用户的"我的记忆"开 |
| 助手 | 上一行的条件，并且该助手的助手记忆开 |
| 工作流 | 第一行的条件，并且该工作流的工作流记忆开 |

补充规则如下。

| 编号 | 规则 |
|---|---|
| 1 | 没有租户级的记忆开关。管理端的工作台配置里只有一项与记忆有关：后台整理记忆时使用的模型，未选择时用工作台模型列表的第一个 |
| 2 | 用户关闭"我的记忆"后，任何应用都读不到也写不进他的记忆，其他使用者不受影响 |
| 3 | 助手记忆、工作流记忆的开关跟随应用版本保存和发布，与应用的其他设置一致 |
| 4 | 助手记忆开启后，这个助手获得常驻记忆带入、检索工具、写入工具和自动整理，作者不需要再单独配置工具 |
| 5 | 工作流记忆开启后，这个工作流的对话进入自动整理，记忆检索节点可以使用 |
| 6 | 工作流里放了记忆检索节点、但工作流记忆是关闭的，上线时校验不通过，提示作者先开启工作流记忆 |
| 7 | 助手记忆、工作流记忆的开关旁边用一句话说明开启的含义：本应用会读取并写入每个使用者自己的记忆；使用者的记忆可能出现在本应用的回答里；不同使用者之间互不可见 |
| 8 | 升级到带有本功能的版本之后，每个用户的"我的记忆"为开，所有已有的助手和工作流的记忆开关都是关 |

## 4.8 R7 · 工作流记忆检索节点

工作流新增一种节点，名称为"记忆检索"。它在当前使用者本人的记忆空间里检索记忆条目，不限于在本工作流里产生的记忆。

输入参数如下。

| 参数 | 说明 | 默认 | 约束 |
|---|---|---|---|
| 检索内容（query） | 用什么去查。可以直接输入文字，可以引用其他节点的变量，也可以两者混写 | 无 | 必填。运行时取值为空的，返回空结果 |
| 最大检索数量（limit） | 最多返回多少条 | 20 | 整数，1 到 100 |

输出如下。

| 输出 | 说明 |
|---|---|
| 检索结果 | 一个列表，按与检索内容的相关程度从高到低排列，最多 limit 条。可以被后续节点作为变量引用 |
| 列表里的每一项 | 记忆内容、类型、记录时间、事件时间（有则带）、来源标记。条目带详情时，内容为详情全文 |

规则如下。

| 编号 | 规则 |
|---|---|
| 1 | 只在当前使用者本人的记忆空间内检索，只返回状态为"有效"的条目 |
| 2 | 没有命中时输出空列表，节点正常结束，不中断流程 |
| 3 | 当前调用识别不出确定的平台用户（§4.2 规则 6），或当前使用者关闭了"我的记忆"时，输出空列表，节点正常结束 |
| 4 | 检索结果被后续大模型节点引用时，以"背景信息"的身份提供（§4.10） |
| 5 | 一个工作流里可以放多个记忆检索节点 |
| 6 | 节点的运行日志里能看到本次检索内容和返回条数 |

## 4.9 R8 · 用户可见与可控

| 能力 | 规则 |
|---|---|
| "已记住"提示 | 显式写入成功后，这次回答旁边出现提示，点开能看到本次操作涉及的条目原文。记下、更正、忘掉三种操作都有提示，提示上可以直接撤销：撤销"更正"后原条目恢复有效，撤销"忘掉"后该条目恢复有效 |
| 回答归因 | 一次回答用到了记忆时，回答旁边能看到两部分：本轮检索取回的条目逐条列出；本轮带入的常驻记忆通过一个入口整份查看，不区分其中哪条被用到 |
| 就地删除 | 在归因里可以直接删除某一条记忆 |
| 记忆管理页 | 用户个人设置里新增"记忆"一项，见下表 |

"已记住"提示、归因、就地删除适用于日常模式、深度研究和助手。工作流的输出由作者编排，本期不对工作流的最终输出做自动归因。

记忆管理页的能力如下。

| 能力 | 规则 |
|---|---|
| 查看 | 列出本人全部有效条目，每条显示内容、类型、记录时间、事件时间、来源标记、是否常驻 |
| 编辑 | 修改一条记忆的内容。按"更正"处理：原条目变为已被取代，新内容成为有效条目 |
| 新增 | 用户手动写一条记忆。内容同样遵守 §4.3 的规则 |
| 删除 | 删除单条 |
| 清空 | 清空本人全部记忆，需要二次确认 |

本期不做搜索和筛选。

## 4.10 R9 · 安全与可信

记忆是系统自己从内容里整理出来的，而被处理的内容不一定可信。一段藏在文档或网页里的话如果被写进记忆，会在之后每一个会话里被当成可信信息。下面三条用来切断这条路径。

| 编号 | 规则 |
|---|---|
| 1 | 只记结论，不记指令。写入和自动整理的来源都只限用户本人说的话，以及用户与系统明确达成的结论。文档、网页、知识库、工具返回里的内容不能成为记忆 |
| 2 | 记忆被带入模型上下文时，一律标注为背景信息并注明记录时间。模型不得把记忆当作必须执行的指令 |
| 3 | 每条记忆保留来源会话。发现某个会话的内容有问题时，能够找出并撤回由它产生的全部记忆 |

## 4.11 R10 · 效果度量

**规则：功能上线时必须同时具备下列指标，否则无法判断记忆有没有起作用。**

| 指标 | 说明 |
|---|---|
| 写入量 | 显式写入、自动整理各新增多少条；多少条被取代、被删除 |
| 读取情况 | 多少条记忆被带入过、被检索命中过；多少条从写下到现在一次都没被读到 |
| 详情打开率 | 带详情的条目里，详情被取回的比例 |
| 用户纠正 | 用户通过归因或管理页删除的条数；用户撤销显式写入的次数 |
| 声称未写入 | 回答里说了已记下、但没有成功写入的次数（§4.4.1） |

指标按租户、场景、应用可拆分，只统计数量，不包含记忆内容。指标是供研发与产品判断效果的数据，本期不做管理端的统计页面。

**开工前要先有评测集。** 用 bisheng 的真实对话建几十道题，每道题在"带记忆"和"不带记忆"两种条件下各跑一遍，比较得分差。评测集是本期的交付物之一。

## 4.12 R11 · 数据生命周期

| 事件 | 记忆怎么处理 |
|---|---|
| 关闭任何一处记忆开关 | 保留已有记忆，停止读写 |
| 用户删除单条记忆 | 该条及其详情不可再读 |
| 用户清空记忆 | 本人全部条目及详情不可再读 |
| 用户删除某个会话 | 由该会话产生的记忆保留。删除会话的交互不改 |
| 应用被删除 | 用户在该应用里产生的记忆保留，来源标记仍显示原应用的名称 |
| 用户被停用 | 记忆保留，停用期间不读不写；重新启用后继续可用 |
| 用户账号被删除 | 本期不做。平台目前没有删除账号的功能 |
| 用户的租户归属变化 | 原租户内的记忆保留、不迁移；归属回到原租户后继续可读 |

删除和清空都留审计记录。审计记录写明谁、何时、做了什么，不包含记忆内容。

| D1 | 记忆以条目为单元；需要连贯说明的长正文放详情，条目里存指针 | 按条查询、按条授权、审计是硬需求；叙事性内容一句话装不下 | 逐项讨论确认 |
| D2 | 采纳《memory 方案调研（结构版）》§7.2 决策表的全部建议，包括实体关系表本期只建不写 | 用户确认 | 2026-11-13 |
| D3 | 写入由"只做后台写入"改为两条途径：显式写入工具加自动整理 | 用户明确要求记下时应当场记下并当场反馈；自动整理承担用户没有提出时的沉淀。调研结论"只靠主模型在会话内写不够"仍然成立，所以模型只在用户明确提出时写 | 2026-11-13 |
| D4 | 一期范围由"仅日常模式"扩大为日常模式、深度研究、助手、工作流四类场景 | 用户确认 | 2026-11-13 |
| D5 | 助手与工作流的记忆开关默认关闭；多个用户使用同一个应用时记忆按用户隔离 | 用户确认 | 2026-11-13 |
| D6 | 工作流新增记忆检索节点，参数为检索内容和最大检索数量（默认 20） | 用户确认 | 2026-11-13 |
| D7 | 工作流不自动带入常驻记忆，只通过记忆检索节点读取 | 工作流是作者显式编排的，自动往每个大模型节点里加内容会改变作者的设计 | 2026-11-13 |
| D8 | 模型声称已记下而未写入时，系统不补写，只暴露和计数 | 补写会掩盖模型缺陷，使它无法被度量 | 2026-11-13 |

## 7.2 逐项确认的结果（2026-11-13）

| 编号 | 决策 | 依据或被否决的方案 |
|---|---|---|
| D9 | 一个用户只有一份记忆，四类场景都能读能写，每条记忆带来源标记。不存在按应用隔离的记忆 | v0.1 把"多个用户使用同一个应用时记忆隔离"写成了"按应用再按用户隔离"，属于误读，已更正。已知后果：用户的记忆会进入任何开启了记忆的应用的回答，应用作者可以通过提示词取到；由应用开关默认关和开关说明文案承担告知 |
| D10 | 日常模式与深度研究共用同一份记忆；经验类条目不进日常模式和助手的常驻记忆 | 两者是同一个用户在工作台里的两种用法 |
| D11 | "我的记忆"默认开（原含"租户记忆开关默认开"，已被 D33 取代） | 被否决：默认关（升级后功能无人可见） |
| D12 | 免登录链接、开放 API 只带外部用户标识的调用，本期不支持记忆 | 运行时读不到外部用户标识；外部用户不是平台用户 |
| D13 | 租户管理员和应用作者对用户的记忆没有任何操作，包括查看、清除、统计页面 | 被否决：管理员可按用户清除并查看统计 |
| D14 | 记忆管理页进 P0，支持查看、编辑、手动新增、删除、清空 | 显式写入和跨场景通用之后，用户需要一个能看到全貌并改正的地方 |
| D15 | 工作流记忆的开关放在开始节点 | 工作流没有独立的设置入口。被否决：新做工作流设置入口；不设开关 |
| D16 | 用户删除会话时记忆保留，删除会话的交互不改 | 记忆是已确立的结论，不是对话的副本 |
| D17 | 四类场景同一个版本交付 | 用户确认 |
| D18 | 常驻记忆上限初值 60 条、6000 字，安静期初值 30 分钟，均可配置 | 初值没有硬依据，取的是偏保守的一档，由评测集校准后定稿 |

|---|---|---|
| D19 | 用户被停用时记忆保留、停止读写，重新启用后继续可用（账号删除时的处理见 D30） | 平台的停用可逆，且组织同步和 SSO 会强制触发。被否决：停用即删 |

## 7.4 设计阶段的裁定（2026-11-13）

| 编号 | 决策 | 依据或被否决的方案 |
|---|---|---|
| D27 | 详情是写一次不改的对象，直接存对象存储；不复用深度研究的工作区后端 | 编辑即取代，一条详情创建后不再修改，原方案要防的并发覆盖不存在。附录 A.3 中"写入收敛到单写者""grep 不当主召回""后端抽到公共层"三条不再适用 |
| D28 | 归因分两部分：检索取回的条目逐条列出；常驻记忆整份可查看，不标哪条被用到 | 被否决：让模型标注用到的常驻条目（三套引用机制要各做一遍，且标注是否准确无法保证） |
| D29 | 实体关系表本期不建，改判 D2 | 空表要在两套数据库方言上维护，却没有读者和写者；避免回填靠的是条目表字段写全 |
| D30 | 账号被删除时清除记忆，本期不做 | 平台没有删除账号的功能。被否决：先做一个没有调用方的清除能力 |

| D31 | 开放 API 的全部调用本期不支持记忆，包括代表平台用户调用和个人访问令牌调用 | 登录用户与开放 API 的调用共用同一批服务函数，下游分不出主体类型；开放 API 的助手入口没有会话也不存消息。被否决：只支持有会话的开放调用；全部支持 |
| D32 | 助手的工具回调落库、连接内切换会话、深度研究分享链接等不确定点，编码最前面用小实验验证后再定 | 两轮纸面审查都在同一类位置发现问题 |

| D33 | 去掉租户级的记忆开关，只保留"我的记忆"、助手记忆、工作流记忆三处；工作台配置里保留"记忆整理使用的模型" | 用户于 2026-11-13 裁定。后果：租户管理员不能在租户范围内关闭记忆；整体停用后台整理只能靠部署配置 |

## A.2 命名约束

代码里已有多处叫 memory 的东西，都指会话内的历史消息或检查点，与长期记忆无关：工作流的 `GraphState.history_memory`（`backend/bisheng/workflow/graph/graph_state.py:3,12,17`）、`bisheng_langchain/memory/`、LangGraph 的 `MemorySaver`。新模块、新表、新接口的命名要避开这些名字。用户可见文案里目前没有"记忆"一词，现有相关文案叫"历史聊天记录"，两者在界面上不得混用。

## A.3 来自调研的实现约束

| 约束 | 说明 |
|---|---|
| 详情层的写入收敛到单写者 | 详情放在对象存储上，现有工作区后端的写是无条件覆盖。详情的写入和合并只由自动整理做，按记忆空间加锁。一个用户的记忆现在会被多个场景和应用同时写，这条约束比单场景时更要紧。AC-M36 验的是这一条 |
| 显式写入不破坏单写者 | 写入工具只新增条目行和改条目状态，不写详情文件。条目行的新增不是"读整份再写回"，不存在整份覆盖的问题 |
| 一条记忆跨两个存储 | 条目在关系库，详情在对象存储，没有事务。删除先删对象再删行；读取时对象缺失要退回条目自身的内容，不能报错 |
| 检索复用现有检索栈 | 向量库与搜索引擎已在部署中，不为记忆新建检索组件；不依赖达梦的原生向量能力 |
| 工作区后端要抽到公共层 | 日常模式不使用 deepagents，详情层要用的那套后端目前只在深度研究里 |
| 不新增 config.yaml 顶层键 | 新顶层键会让旧镜像拒绝启动。部署级参数默认注释掉，或放进已有的配置位置 |
| 常驻记忆不整行重写大 JSON | 达梦上热路径整行重写大 JSON 会耗尽 undo |
| 批量更新和删除要手写租户条件 | 租户自动过滤只拦截查询 |
| 字段一次写全 | 作用域、成立时间段与记录时间两组时间字段、来源会话、取代关系，本期都落库，避免以后回填 |
