## 0. 摘要

**BiSheng 3.0 让不会编程的业务人员在平台里对话式造应用，并让每一个应用天生长在企业治理之内。** 三句话说完：

1. **造**：浏览器内「对话 + 实时预览 + 一键发布」的造应用工作台；引擎复用开源 coding agent（可替换适配层，不自研不绑定）。
2. **接与跑**：应用跑在平台沙箱运行时；经统一的企业能力总线接入企业的知识库、模型与身份（能力总线的技术构成见 §3.4）——生成的应用天生认识组织架构和权限。
3. **活与管**：每个应用绑定一个常驻**应用管家**——造它、改它（发布后迭代 = 继续对话）；发布审批、权限、配额、审计全程自动生效。（定时解读数据、主动预警一类的持续看护能力本版不做、v3.1 重新立项，见 §3.2/§5.4）

## 1. 背景与痛点

### 1.1 背景：应用生产方式正在换代

- **对话取代画布**：字节把扣子的拖拽画布整体撤下，换成对话式生成（扣子编程）；百度秒哒 8 个月生成 50 万应用、81% 用户非程序员；美团 NoCode 非技术岗使用者是技术岗的 3 倍——「说需求出应用」已被市场验证，且主力用户是业务人员而非开发者。
- **企业侧同样成立**：招商银行低代码体系年新增应用 2831 个、59.4% 出自业务人员——但银行对 AI 编程明确「审慎」（技术债与治理顾虑）。
- **引擎已是公共品**：Qwen Code / Codex CLI（Apache-2.0）、Kimi Code CLI（MIT）等开源 coding agent 成熟且可自由内嵌，平台不必自研引擎。

**结论：应用的稀缺环节不再是「会不会造」，而是「有没有一个带企业上下文、有治理的地方去造和跑」。**

### 1.2 痛点：业务人员的三个诉求 + IT 的一个焦虑

来自内部用户/客户的真实原声：

1. **「我能不能直接在 bisheng 上 vibe coding，把企业的用户体系、知识库、数据都接进应用里？」**——想造，但缺一个带企业上下文的地方（主诉求）。
2. **「我用 Claude Code 在本地开发了应用，希望部署到 bisheng 让大家访问；应用不稳定，但平台要正常。」**——造完了，没地方跑、没人能访问。
3. **「应用搭好了，需要一个 agent 持续为我解读、分析、预警。」**——跑起来了，还想让它自己会看数据。

IT 侧的焦虑是 shadow AI：员工绕开 IT 用公共 AI 工具造应用 → 数据外泄、无人运维、审计缺失。IBM《Cost of a Data Breach 2025》：20% 数据泄露事件涉及 shadow AI（均损 $4.63M）；Lovable 生成的 170+ 应用数据库对匿名请求裸奔（CVE-2025-48757）。**「与其堵，不如给一条有治理的路」——这是 IT 部门愿意引入本能力的根本理由。**

### 1.3 市场空档

| 玩家 | 现状 | 空档 |
|------|------|------|
| 扣子编程（字节） | 对话式造应用 + 托管 PG/对象存储/能力集成注册表/时间点恢复/一键部署，数据面最完整 | **只在云端 SaaS**、公开部署、按积分计费，私有化无供给 |
| Coze Studio 开源版 | 无 vibe coding / 托管能力，2026.02 更新放缓 | 开源侧留白 |
| Dify | 纯配置式工作流范式（DSL） | 无代码应用生成/托管信号 |
| Lovable / bolt / v0 / Replit | UX 机制成熟（本文大量借鉴） | 公有云 SaaS + 安全事故频发 |
| Manus | 全栈脚手架 + 全托管 DB/存储/定时/发布、无锁定可导出源码 | 公有云（Cloud Run）+ 积分制、外部 SaaS 集成、双向同步公有 GitHub，内网合规不适用 |
| Databricks Apps | 验证「平台托管内部应用」的真实需求（正式发布前半年即 2500+ 组织 / 2 万应用） | 绑定自家数据栈，不做国内私有化 |

**「私有化环境下的对话式造应用 + 托管 + 治理」目前无人占位；扣子在教育市场，窗口在收窄。**

## 2. 产品定位与设计理念

### 2.1 定位

```
BiSheng ≤2.6：平台即 IDE —— 应用用画布在平台内搭，表达力受画布上限约束
BiSheng 3.0 ：平台即应用工场 + 运行时 —— 业务人员对话式造应用，
              应用跑在平台沙箱里、接着企业的知识/模型/身份、由常驻管家负责造与改，
              治理自动生效
```

差异化判断：**引擎是公共品，竞争在「壳」**。对话生成应用的能力，各家很快都会有；但应用要真正在企业里活下来，需要的是身份与权限、知识库与数据、审批与审计——这些恰好是 BiSheng 已经建成的部分，而 Lovable/扣子们要么没有、要么短期给不出私有化供给。生成的应用在 BiSheng **天生认识企业组织架构、天生长在治理之内**，这是本方案真正的护城河。

### 2.2 设计理念（三条）

**① Vibe with the agent, not the code —— 应用管家。** 业务人员相处的对象不是代码，而是一个长期存在的 agent；代码只是它的产物。每个应用绑定一个管家，贯穿两种状态：

- **造**：从一句话需求开始，澄清、生成、预览、发布；
- **改**：发布后迭代 = 继续对话（「把导出加个 Excel 格式」），管家在草稿沙箱改好、预览确认、点更新上线——业务人员永远不需要「打开工程」。

（管家按时间/事件唤醒、解读数据增量并主动推简报一类的持续看护能力，本版不做、v3.1 重新立项，见 §3.2/§5.4。）

造它的、改它的是同一个 agent，**会话随应用终身存续**、上下文零移交——这是对「session 用完即弃」类产品的结构性差异。

**② 引擎复用，不自研、不绑定。** coding agent 是快速演进的公共品，自研必然落后；绑定单一引擎则被别人的断代绑架。平台通过可替换的引擎适配层（§4.2）驱动开源 coding agent，默认引擎可按租户配置、可随生态演进更换。

**③ 平台管安全，AI 只管功能。** 「让 LLM 生成正确的鉴权代码」被证明不可靠（Lovable 170+ 应用数据库裸奔），扫描器也只能查有无、查不出对错。BiSheng 不把安全押在「AI 写对代码」上，而是由平台运行环境强制保障：生成应用默认仅企业内可见、所有流量过平台身份网关、数据访问走平台注入的租户隔离连接、沙箱出站白名单、发布走审批。AI 生成的代码只负责业务功能——写得再差，也越不过平台划定的安全边界：代码里没有裸连接串，也没有自己发明的登录。（发布前对产物做「查有无」的裸密钥/连接串扫描是低成本兜底，落在扫描器擅长的那一层；但主保障始终是运行环境，不是扫描。）

### 2.3 目标用户与核心旅程

| 用户 | 要什么 |
|------|--------|
| **业务人员**（主用户，非程序员） | 把脑子里的表单/看板/小工具变成同事能用的应用，不学编程、不等排期 |
| 平台管理员 / IT | 业务自建应用看得见、管得住、出事能兜底 |
| 业务技术员（会用 Claude Code 的少数派） | 本地开发的应用部署到平台给大家用 |
| 普通业务用户 | 在应用广场找到并直接使用同事造的工具 |

一段旅程：销售运营专员说「做一个销售周报看板，数据用上周台账」。管家澄清两个问题后开始工作，她看着右侧预览成形，中途说「大客户单独列一栏」——管家查了知识库里的口径改好了。点发布、主管审批，同事用企业账号直接打开，各自只看到自己权限内的数据。（她后来还想要「每周一早上把异常客户推到企微群」——这类持续看护能力本期不做、v3.1 再议。）**她全程没看过一行代码，但代码一直都在那里，IT 全程可见可审。**

## 3. 产品功能结构

```
应用工场
├─ 造应用工作台     左：对话 + AI 任务清单；右：多功能面板（业务人员主界面）
│                   右侧四核心 tab：预览 · 资源（数据默认子页+知识库/模型）· 代码（只读玻璃盒·高级）· 发布（含版本回滚/审批/可见范围）
├─ 应用管家         造 / 改 一体的常驻 agent（持续看护本期不做，v3.1 再议）
├─ 应用运行时       沙箱托管、统一入口、版本回滚（草稿与生产同一套设施）
├─ 企业能力总线     API key · 双协议模型代理 · MCP Server · SDK
├─ 治理面           发布审批 · 权限 · 配额 · 审计 · 日志
└─ 专业开发者通道   本地开发旁路：MCP（调用）+ 技能包（知识）+ SDK（代码）+ CLI（工作流）四面供给（§3.6）
```

### 3.1 造应用工作台

核心机制（取六家对标产品的收敛范式，结合 BiSheng 独有优势）：

| 机制 | 规格 |
|------|------|
| 一句话起步 + 澄清前置 | 写码前先「梳理需求 → 确认要点 → 匹配平台资源（知识库）」，避免零碎指令越改越乱；澄清交互**以选项式为主**——管家把问题连同候选答案一起给出，业务人员点选即可，尽量不要求打字描述技术细节，且一轮问完、数量有界（复用灵思任务模式澄清环与选项式提问的成熟经验） |
| 左对话 + 右多功能面板 | 左栏 = 与管家的持久对话 + AI 任务清单（可勾选待办）；右栏 = 多 tab 功能面板（预览/数据/代码/发布），默认停在预览。代码是右栏里一个高级只读玻璃盒——可见、但不必看（纯黑盒出问题没有逃生通道）。面集详见 §3.1.1 |
| 计划清单（复用引擎原生行为） | 「想/做分离」不作为独立机制强调、**不设用户开关**——复用 coding agent 原生的计划/待办行为：讨论/疑问类输入只回答不改码；大改先列可勾选计划清单（即左栏 AI 任务清单）确认后动手，小改直接做并在清单上打勾 |
| 代码版本管理 | 每轮改动自动生成代码版本，可回滚、可查看版本差异（文件变更清单 + 行级 diff）；**生产数据默认不回滚**、schema 演进需迁移策略（回滚语义见 §3.3） |
| 报错一键回流 + 修错改到好为止 | 运行报错/截图、以及**构建与依赖安装失败**（自托管镜像下 pip/npm 解析失败是高频失败模式）都一键回流，管家以业务人员能懂的话解释并自动修、改到好为止（SaaS 的「花钱买 bug、再花钱修 bug」bug-loop 是全行业最大口碑杀手，私有化部署天然没有这层焦虑）；按人记账/会话预算/触顶处置等精细成本控制本版不做、v3.1 再议（租户级配额兜底，防「帮我修」成为资源旁路，§4.7） |
| 基础组件平台自带 | 数据库/对象存储/登录/权限这些基础组件由平台提供、开箱即用，**不让 AI 从头写**：应用数据库 = **平台托管、按 app 独立**（小档 SQLite-per-app / 中档 Postgres schema，与平台 MySQL·DM8 解耦——生成代码不认 DM8 方言，故不复用平台库；单文件 SQLite 顺带简化每轮存档，租户隔离连接注入）；登录与权限 = 平台身份桥接，生成应用天生认识组织架构（如何递到管家手里见 §4.4） |
| 自动数据后台 | 业务应用大多是「表单 + 列表 + 看板」——生成应用自动附带数据管理页（查/改/导出/回溯）；**表结构演进由平台内建、不让 AI 手写**：改表结构时管家以「加列安全、改删列需确认 + 迁移前快照」的业务语言引导、AI 不手写 DDL。行级归属 / owner 字段 / 「仅本人/全部」按表模式本期不做、v3.1 再议 |
| 存量数据导入 | 台账/信息收集类应用的第一步几乎都是「把现有 Excel 搬进来」（§2.3 旅程「数据用上周台账」即此场景）——双路径：对话里传 Excel/CSV → 管家建表灌数；数据面亦有显式「导入 Excel/CSV」入口 |
| 附件字段开箱即用 | 上报/整改类首发模板的核心交互是拍照/传附件：附件字段上传 + 数据面行内预览/下载为**本版基线**（SDK storage 承载、落平台对象存储、不计入租户存储配额）；推迟到 v3.1 的只是独立的对象存储管理面（§3.1.1） |
| 草稿 / 生产分离 | 管家只碰草稿沙箱；「发布」才产出独立生产实例；线上回滚与草稿存档是两套、都要有；**草稿全程 owner-only**——对话、预览、数据均仅 owner 可见可试，想给同事用就发布（授权试用/共建本版不做） |
| 预置模板起步 + 组织模板库 | 模板可选、非必选，允许从空白生成（应用双来源 = 平台内 0→1 对话式造 + 本地项目导入纳管，见 §3.6）：**首发 6 类模板**——信息收集上报 / 业务台账 / 检查整改闭环 / 数据看板+AI 解读 / 知识问答页 / 轻审批·督办跟踪（经通用模板市场实证 + 央国企场景两路调研定夺，详见附录《预置模板首发清单调研》）；每个模板 = 「一张表+一条流+一个看板」的微应用，不做行业大套件 |
| 逃生梯度 | 报错回流 → 代码玻璃盒 → 导出工程；后续版本加点选局改（Design Mode 式） |

#### 3.1.1 右侧多功能面工作台（四核心 tab + 弹窗）

对标产品（扣子编程 / Manus）的共性是「左侧持久对话 + 右侧多 tab 功能面板」。BiSheng 沿用这套信息架构，但按**业务人员主用户**收敛面集、按**不做 SaaS + 治理自动生效**替换 SaaS 面：右侧只暴露**四个核心 tab**，其余走弹窗或顺延。

| tab | 业务人员一句话价值 | 优先级 | 承载 |
|-----|------------------|--------|------|
| **预览** | 看应用长啥样、点点试用，没发布也能用 | 默认展示 | iframe 托管；桌面/移动两态切换；出错时内联「报错/构建失败 → 帮我修」回流条（不做独立终端）；不做「模拟用户」视角切换与样本数据播种——想看其他用户视角，用真实账号访问已发布应用 |
| **资源** | 应用的数据和可用的平台资源都在这：数据能查改导入导出回溯，知识库/模型能逛能接 | 默认展示 | 四个子页、默认停在「数据」（数据是资源的一部分，采纳扣子集成面的分组结构）。**数据子页**：数据管理页 + 导入（Excel/CSV）+ 附件列行内预览/下载（见 §3.1 自动数据后台）；**无草稿/生产切换器、随应用状态自动跟随**——未发布=草稿库（承接导入），发布后=生产库：业务人员看数据就是看真数据；预览试用产生的草稿数据在预览里的应用自带数据页自见，草稿库是管家迭代的工作区内部事务（切换器是开发者构件，与删终端同一取舍）；编辑生产行需二次确认并计审计；绑应用自有库，与产物文件预览是两个数据面。**知识库子页**：owner 可见的库可浏览、可「接入本应用」；**模型子页**：管理员配置的可用模型只读展示，应用用平台默认配置（更换交互 v3.1 再议）。**密钥子页**：本应用第三方凭证 masked 录入/吊销，只见引用名与掩码（见 §3.3） |
| **代码（玻璃盒）** | 想看应用咋搭的、或让技术同事帮调，可打开 | 高级折叠·**只读** | 文件树 + 只读渲染 + 导出工程；内含只读「运行日志」子页（草稿 dev server + 生产容器日志，按权限可见）——技术同事帮调的排障面、SaaS 终端/控制台的私有化替代；不做交互式终端与 SQL 查询（数据出口走导出）；改码走对话、不在此编辑 |
| **发布** | 发给同事用，谁能看走权限、上线要主管审批 | 次级 | manifest/capabilities 白话摘要 + 审批状态（审批中心 F025；首发与迭代每次发布均走审批，见 §3.5）+ **版本回滚**（前向新建、代码/配置无损、生产数据默认不回滚）+ 入口链接与二维码（上报/检查类应用移动端扫码打开，央国企「贴码上报」经典用法）；「可见范围」（权限弹窗）走弹窗、不占 tab |

**业务人员视角的取舍**（区别于扣子编程的开发者中心 IDE）：**数据是一等内容、归于「资源」tab**——业务微应用里数据就是产品本身，资源 tab 默认停在数据子页；数据是资源的一部分，与知识库/模型同处一 tab；**代码降为高级只读玻璃盒、删掉终端/控制台**——交互式终端是纯开发者构件，业务人员的等价物是「出错→让管家修」一个按钮，技术同事帮调的等价物是玻璃盒内的只读运行日志；**「集成管理」移出工作台、归管理面**——模型/知识库/搜索等能力由管理员经能力总线（§3.4）按租户配置一次、域内共享，业务人员与 AI 都不碰底层账号端点；资源可发现性双轨——「资源」tab 知识库/模型子页（取可发现性不取配置面：只放可挑选的实例；应用模型用平台默认配置、子页只读展示（更换交互 v3.1 再议）——与造应用引擎的模型零感知是两回事；无环境变量/配置项）+ 管家对话内带候选上门（复用选项式提问：库名 + 一句话描述，点选即接入；试检索命中预览为 v3.1 增强）；应用接了哪些知识库/模型在资源 tab 各子页即可看到（capabilities chips 常驻展示层不做），发布面呈完整白话清单。排序按业务人员使用频次（预览/数据每次都看 > 版本/发布改完才碰 > 代码/设置偶尔），而非扣子的开发生命周期（代码为中心）。

**私有化替换对照**（对标 SaaS 面 → BiSheng）：

| 对标 SaaS 面 | BiSheng 私有化替代 |
|-------------|-------------------|
| 公网自定义域名 / 公开可见性 | 内网 slug `/apps/{slug}` + OpenFGA 权限（无「公开」开关） |
| 自定义资源规格 / 实例数与并发调节 | 平台预置资源模板（轻量/标准/性能类，管理员可调）发布时选档；单应用单实例；token 用量不设限制 |
| GitHub 公有双向同步 | 导出工程到内网（逃生梯度末端） |
| 环境变量 dev/prod 面 | 资源 tab 密钥子页 masked 录入 + `BISHENG_*` 平台注入变量只读 |
| 数据库时间点恢复（PITR） | 生产数据默认不回滚；数据备份自助恢复顺延 v3.1 |
| 交互式终端 / SEO / 隐藏水印 | 删除（报错回流替代终端；内网应用无 SEO/水印概念） |

v3.1 顺延：独立「设置」面、管家持续看护（定时任务 cron 与通知偏好、看护总览）、代码可编辑、数据自助恢复、对象存储独立面、schema 变更管理面（见 §5.2）。

### 3.2 应用管家

- **造 / 改**：见 §3.1；**管家的会话随应用终身存续**——工作区快照 + 对话历史与应用绑定存储，不随发布、容器回收或时间流逝而丢失；应用创建三个月后回来提一句需求，管家仍带着全部上下文接得住。
- **持续看护上线应用（定时解读数据、主动预警）及其依赖的平台触发/调度子系统——本版不做，v3.1 重新立项**（设计要点已归档至 §5.2，见 §5.4）。

### 3.3 应用运行时与发布

- **应用包规范 `bisheng-app.yaml`**（发布时由管家自动生成）：

```yaml
name: sales-weekly           # 入口路径 /apps/sales-weekly
runtime: python3.11          # python3.11 | node20 | static
entry: streamlit run app.py --server.port $PORT
capabilities:                # 声明式能力申请，审批即授权
  knowledge: [kb_123]
  models: [qwen3-max]
  secrets: [webhook_token]   # 应用级密钥引用；值存平台 secret store（Fernet），注入同 capabilities
appdb: sqlite                # sqlite（小档，单文件）| postgres（中档，独立 schema）
resources: light             # 平台预置资源模板档位（轻量/标准/性能类），发布时选择，杜绝自定义规格博弈
```

- **统一入口**：`/apps/{slug}`，访问复用平台既有登录（账号密码 / SSO 扫码），已登录免二次登录；应用广场与工作流/助手并列呈现。
- **稳定性承诺**：应用容器与平台进程零共享，单应用崩溃只自愈该容器，平台与其他应用不受影响。
- **代码资产持久（应用下线/资源释放不丢码）**：容器只是无状态执行体——代码、对话、应用数据的真身恒在平台存储：每轮改动自动生成代码版本（§4.1）+ 每次发布的版本快照（代码 + capabilities + 注入变量，见下条）。应用下线、idle 回收、容器崩溃乃至运行时组件整体卸载（compose profile 缺席），都只回收执行体、不触碰存档与版本记录；存档随平台数据一同备份，删除唯经「显式删除应用」流程（确认 + 审计；退役/归档见 §5.2）。每轮存档按策略裁旧（近 N 轮 + 里程碑轮），发布版本永久保留，占用计租户存储配额。
- **版本与回滚**：每次发布生成版本记录；回滚 = 基于历史版本**前向新建一条版本记录**（非原地覆盖），部署历史线性、全程可审计；代码 + capabilities + 平台注入变量作为**同一个版本快照**统一回退，杜绝「回退代码却留下新配置」的漂移。**代码/配置回滚无损；生产数据默认不回滚**（有状态生产应用回滚会丢回滚点后的数据），republish 涉 schema 演进需策略（仅增列 / 迁移前快照 / 人工确认）。
- **应用密钥录入**：业务人员给应用赋值 secret 走工作台资源 tab 密钥子页 / 管理面的 masked 录入控件，值直写平台 secret store（Fernet），**不经对话、不写日志、不回显**，代码里只出现引用名；不提供「在对话里粘贴密钥」的路径（避免明文落进会话历史与审计日志）。
- 本版不做：k8s 多机、公网域名、应用间编排、GPU、自动扩缩容、Dockerfile 自定义构建。其中 k8s 多机不做的理由：客户部署基线是 compose 单机、信创环境普遍无 k8s（要求 k8s = 抬高全平台准入门槛）；v3.0 微应用容量单机 + 准入/idle 回收/cgroup 可承载；且非死路——intent-reconcile 模型即 k8s 心智，v3.1 多机只换 runtime-manager 执行后端（docker API → k8s API），backend 与 app-proxy 契约不动（§5.2）。

### 3.4 企业能力总线

能力总线 = 平台内置能力（模型 / 知识库 / 身份组织 / 对象存储…）与外部集成的**统一注册表**：由管理员按租户/部门**配置一次、域内所有应用共享**，应用经声明式 capabilities 申请、平台在容器启动时注入——业务人员与 AI 都不碰底层账号与端点。构成如下：

- **API key 体系**：个人 key（本地开发者）/ 应用 token（发布时按 capabilities 签发）/ 会话 key（工作台沙箱随会话吊销）；scope + 配额 + 可吊销；替换现有 v2 开放 API 的「内网可信」模型。
- **双协议模型代理**：对外暴露 OpenAI 兼容 + Anthropic 兼容两个协议面，任何讲两种协议之一的引擎（含客户自装的 Claude Code）都能直连平台托管模型。做 Anthropic 面的依据：DeepSeek/智谱/Kimi/Qwen/MiniMax 五家均官方提供 Anthropic 兼容端点，该协议已成国产模型事实第二标准。**实现上采用现成开源代理（LiteLLM / one-api 类）承载协议面，不自研 Anthropic `/v1/messages` 长尾**（content blocks / tool_use / SSE / thinking / prompt caching 语义）；**BishengLLM 退居 provider 路由的唯一真相**（现成代理经其**自定义 provider/回调扩展点**调用 BishengLLM 解析租户模型配置与端点——BishengLLM 只提供解析、不自建 HTTP 面；LiteLLM 可作库内嵌 backend、one-api 类可独立进程，二者皆经此扩展点回连，不重实现、防两层漂移）。三个必钉约束：① license 核查（LiteLLM 企业功能单独授权、商业私有化须确认；one-api/new-api 为 MIT）；② 记账回流一处（外部代理 per-key 用量喂回 `llm_token_log`/配额——现记账是 `on_llm_end` 按叶子租户、须补 per-key 归属，避免两套账单）；③ 与 §4.3 auth_profile 三路径协同。平台今日无此模型网关代理（现有 `/api/v2/assistant/chat/completions` 是按 UUID 分发到 Assistant、非裸模型透传）。
- **BiSheng MCP Server**（streamable HTTP，key 鉴权，scope 过滤）：知识库检索、模型清单、用户身份/组织查询、应用数据库 schema/查询（管家迭代应用时用）、应用状态/日志自查（本地开发者 deploy 后 agent 可自排障闭环）；**调用企业既有工作流/助手作为应用能力**（如表单提交即触发一条审批/自动化，放大既有资产复用、不让 AI 裸调）列为 v3.1 扩展；数据语义层（本体）查询作为后续扩展方向。平台自己的灵思/助手/工作流同样可消费——内外同源。
- **bisheng-sdk**（Python 首发）：auth / retrieve / chat / storage / appdb 五件套薄封装，模板预接线（行级归属 / owner 字段本期不做，v3.1 再议）。
- **毕昇开发技能包**（Agent Skills 开放格式：SKILL.md + 样例 + 自检脚本）：平台能力的**使用知识**——MCP 管「调用」、技能包管「会用」；随平台版本发布、`bisheng skills sync` 从自家平台拉取（天然版本对齐，无公网 registry 依赖）；与工作台沙箱内引擎的平台能力指令**内外同源一份内容**（§3.6、§4.2），不维护两套文档。

### 3.5 治理面

- 应用/工作台会话/管家均为权限体系（OpenFGA）资源类型，授权复用现有通用授权交互；
- 发布走审批中心（F025 新场景）：首发与迭代每次发布均走审批，不设免审路径（企业安全要求）；迭代审批单额外呈现相对上一版本的 capabilities / 可见范围 / 表结构 / 资源档位四类变更摘要，供审批人快速判断；「发布后迭代 = 继续对话」指改动过程无需打开工程，上线生效以审批通过为准；审批单提供待上线版本的只读审读视图（代码 / capabilities 完整清单 / 版本历史与 diff）+ 预览试用（平台内应用复用 owner 草稿沙箱、不为审批单独起实例，草稿有新改动时提示与快照不一致；CLI 导入应用以待上线版本快照起审批期临时实例，终态即回收、不计实例配额）；草稿对话仍仅 owner 可见；
- 全链路审计（谁造了什么、接了哪些知识库、谁在用）、按 key 的用量账单、租户级容器与 token 配额；
- **引擎与模型接入统一由管理员配置**：用哪个引擎、走平台模型代理还是客户订阅、凭据档案的创建与分配，全部是管理面决策（§4.3），业务人员零感知；
- 灰度手段：应用工场按租户/用户组开关。

### 3.6 专业开发者通道（本地开发旁路）

会用 coding agent 的开发者在本地把应用开发到七七八八，按需集成平台能力（个人 key / MCP / 技能包 / SDK 均按需取用），再经 `bisheng deploy` 导入发布纳管——与平台内 0→1 对话式造应用构成应用双来源（本地导入 = 0.9→1 纳管），应用仍长在企业能力与治理之内。设计原则与「引擎复用」同源：**全部走标准协议（MCP / Agent Skills / OpenAI·Anthropic 协议），不做任何本地端专有插件**——Claude Code / Codex / Qwen Code 等任何本地引擎零改造接入。平台能力按四个面对外供给：

| 供给面 | 承载 | 要点 |
|--------|------|------|
| 调用面 | BiSheng MCP Server（§3.4；streamable HTTP + 个人 API key，scope 过滤） | 检索/身份组织/appdb/应用状态·日志——本地 agent 可以自己「deploy → 读日志 → 修」闭环；与平台内管家同一工具面、内外同源。**模型不走 MCP**：本地引擎经双协议代理直连（原生协议、支持流式），MCP 只管模型清单查询 |
| 知识面 | 毕昇开发技能包（§3.4；Agent Skills 开放格式，Claude Code 原生识别、其它引擎经 AGENTS.md 引用同一目录——技能本质是 markdown，引擎无关） | 首发四包：**应用包规范**（bisheng-app.yaml/capabilities/安全红线：禁写鉴权·连接串·密钥）· **登录权限接入**（读头即身份/OBO）· **数据**（appdb SDK 范式/迁移策略/知识库检索用法）· **模型接线**（双协议代理接入/模型名即平台模型管理里的原名，无逻辑档位转换/token 计量）；每包带可运行样例 + 连通自检脚本 |
| 代码面 | bisheng-sdk（§3.4 五件套） | 模板预接线；本地写的与平台内生成的应用是同一套调用范式 |
| 工作流面 | `bisheng` CLI：login / dev / deploy / logs / skills sync 五命令 | 不设 init / 工程骨架——开发者从本地已有项目出发，按需集成平台能力；skills sync 从自家平台拉技能包；deploy 导入发布、进同一发布管线（构建 → 发布前扫描 → 审批 → 沙箱托管）——本地造的和平台造的，治理面前无差别 |

- **登录不对外提供「登录页」**：应用永远只读头取身份（SDK 一行）。本地开发期由 `bisheng dev` 起迷你 app-proxy，向本地应用注入与线上同构的 `X-BiSheng-User-*` 头（= 开发者本人，经个人 key 换 OBO），本地/线上代码零差异；不提供 `--as` 虚拟用户模拟——平台能力调用（检索/模型）恒以 key 属主真实身份计权限、配额与审计。
- **数据出到本地的治理三条线**：① 个人 key scope 默认最小（检索/模型/身份查询），可吊销、配额限流、调用审计到人；② 经 MCP 检索可见的知识库数据 ⊆ 该开发者平台 UI 权限（INV-7 外推，不新增数据面）；③ key 不落 repo：CLI 凭据存本地用户目录（0600 权限），技能包红线教 agent 用环境变量引用而非硬编码。
- 客户自装 Claude Code（专有 license，不入平台镜像）同样经此四面接入：双协议代理连平台托管模型、MCP 接企业上下文（§4.3 路径 B 治理不变）。

**与 k8s/通用运维平台的区别（纳管的额外价值）**：k8s 解决「进程怎么跑」，BiSheng 纳管解决「应用怎么在企业里被使用和被管住」——不同层、不互替（底座 v3.1 可跑上 k8s）。内部应用直接上 k8s，SSO 对接、权限模型、模型 key 申请与记账、上线审批、被同事找到全部要自建——这层「每个应用重复造一遍」的成本恰是企业内小应用死掉的原因；在 BiSheng 声明 capabilities 即注入：

| k8s/运维平台给的 | BiSheng 纳管在其上叠加的 |
|---|---|
| 调度 / 伸缩 / 自愈（进程级） | 统一入口 `/apps` 复用平台登录（已登录免二次登录）+ 应用广场可发现——发布对象是业务用户，不是运维 |
| Service/Ingress（网络可达） | 身份注入（读头即得组织身份）+ OpenFGA 可见范围 |
| ConfigMap/Secret（值的存放） | 企业能力按 capabilities 声明注入：知识库检索（权限随人）、模型代理（token 计量）、secret store |
| 无 | 发布审批 · 配额 · 全链路审计——shadow AI 的答案不是「有地方跑」，是「跑在治理里」 |
| 无 | 应用管家：报错回流排障（定时解读/预警 v3.1 再议） |

manifest 也不同量级：`bisheng-app.yaml` 面向应用（几行声明），不是面向基础设施的 helm/yaml。**导入应用谁改代码**：默认仍是开发者在本地改、改完 `bisheng deploy` 重新发布——平台只保存每次 deploy 的版本快照（运行与玻璃盒展示均以此为准），本地中间改动平台不感知、也无需感知；平台侧管家对其只读、不改码；owner 可把应用交给平台管家接管，之后像平台内造的应用一样在工作台对话里迭代——同一时刻只能有一头能改码，防止本地与平台双头改码、互相覆盖。**导入能否托管靠契约 + 预检保证**：平台托管提供什么（运行时 / 应用数据库 / 文件存储 / 能力总线 / 密钥注入）随「应用包规范」技能包对外、本地开发期即可对照；deploy 先过托管预检（依赖构建 / 声明校验 / 启动探活），契约外依赖（自带数据库、消息队列等中间件）原地拒绝并给出改造指引，不进入审批。

## 4. 技术架构方案

### 4.1 总体架构

```
业务人员浏览器（对话 + 预览 + 玻璃盒）
   │ WS/SSE（归一化事件流）
BiSheng backend（编译期/运行期零 docker 依赖，arch-guard 加 import 禁令强制）
   ├─ vibe_builder 模块：会话编排 / 引擎适配层 / 快照恢复 / 发布编排
   ├─ open_platform 模块：API key（三类）/ OBO token / 配额
   ├─ 模型代理（现成代理 LiteLLM/one-api 承载协议面 + BishengLLM provider 路由）
   ├─ mcp_server 模块：平台能力 MCP 化
   └─ app_runtime 模块：manifest 生成 / 向 runtime-manager 下发期望态 intent（声明期望、不直连 docker）
runtime-manager（独立最小权限编排器，唯一持 docker 访问）
   ├─ intent 驱动 reconcile：构建 / 容器生命周期 / 日志探活 / 崩溃自愈
   ├─ 准入控制 · idle 回收 · 并发上限 · cgroup 硬隔离（容量/密度治理）
   └─ 沙箱容器（草稿态与生产态同一套设施）
        ├─ 草稿：引擎 CLI + 工作区 + dev server（预览经 /apps/preview/{session}/）
        └─ 生产：应用容器（/apps/{slug}/）
app-proxy（版本无关鉴权代理，唯一暴露 /apps）：验会话 + 签 OBO + 注入头 + 反代容器，支持 WebSocket
   └─ nginx（开源）与 Java 网关（商业）都只把 /apps 转发到它——安全逻辑一处实现、不随部署形态分叉
```

工作区与会话持久化：**每轮修改自动生成代码版本；对话上下文独立持久化**，均落平台存储并与应用绑定——这既是工作台「回滚」的承载，也是「管家会话随应用终身存续」的承载：容器随时可回收，回来即恢复。**承载方式据实**：灵思 workspace 是 per-file write-through 对象缓存（非时间点快照），无法直吃 builder 工作区的 git + node_modules（万级小文件、git 语义），故须**新增 tar/bulk-snapshot 层**（应用库选单文件 SQLite 后，数据部分的存档简化为「tar 一个文件」）；「无损」限定草稿/代码，生产数据回滚语义见 §3.3。前端归属：工作台放 client（业务人员所在 SPA，初版交互稿：https://claude.ai/design/p/8e7bca96-b23b-4901-9468-80ad5bbad5e9?file=%E5%BA%94%E7%94%A8%E5%B7%A5%E5%9C%BA+Demo.dc.html&via=share ），管理面放 platform。

工作台前端复用（已探查证实，client SPA）：「左对话 + 右多 tab」的外壳 BiSheng 已有——`ChatView` 即「左持久对话 + 右 docked 面板 + 响应式/全屏」，**唯一净新建的外壳是右侧多 tab 层**（`useWorkspacePanel` 加 `activeTab`、`WorkspacePanel` 顶部加 tab strip，绑定对象从灵思会话换成 builder 草稿会话；tab strip 须同时进 docked 与全屏两份实例、保持轻）。逐 tab 复用：左栏对话+任务清单 = `TaskTurnPanel` / `PinnedTaskPanel` / `TaskModeInput`；预览 = `WebView`（iframe srcDoc）+ `PreviewBody` + `FilePreview`(compactMode)；数据（读）= `DataTable`（可编辑网格为净新建、写走 appdb/MCP）；发布 = `ApprovalCenterDialog`(F025，面内按钮拉起、不塞进窄面板)；可见范围 = `PermissionDialog`（ReBAC，加 App 资源类型）；client 版本回滚组件为净新建（platform `useVersion`/`DiffFlowPage` 语义是工作流节点图 diff，只借概念不搬代码）。**集成管理/能力总线配置归 platform 管理面、不进 client 工作台**（见 §3.1.1 取舍）。

### 4.2 引擎适配层与选型

**RuntimeAdapter 抽象**（Python），按「CLI 进程 + JSONL/JSON-RPC 事件流」建模：

- 统一 `run(RunConfig) → {sessionId, text, structured, usage}` 契约；公共必备只有 run()，undo/compact/steer 按引擎能力可选——差异不抹平、在上层显式分叉；
- 流式事件归一化为五类（text_delta / thought / tool_use / tool_input_delta / tool_result）上抛，前端渲染与引擎解耦，换引擎不动 UI；
- 引擎可用性探测 + 依赖注入；引擎选择同样是管理员配置的结果（用户组覆盖 > 租户默认 > 平台默认），业务人员不感知引擎；
- 模型与凭据：适配层不关心引擎用什么模型、以谁的身份跑——统一由「凭据档案」承载（见 §4.3）；
- 指令单一来源：CLAUDE.md/AGENTS.md 软链或编译，避免多引擎指令漂移；该文件同时**兼作应用的机器可读设计意图沉淀**（数据模型 / 视图 / 流程 / 口径），管家跨轮乃至数月后迭代时先读、稳住多轮一致性——沿用此单一来源、不另起平行文档；平台能力的使用规范抽出为毕昇开发技能包承载（§3.6），沙箱内引擎与本地开发者读同一份。

### 4.3 引擎凭据与模型接入（coding agent 用什么模型、以谁的身份跑）

引擎跑起来需要两样东西：**模型访问**（调哪个大模型）和**身份凭据**（以谁的名义调）。平台把两者统一抽象为**凭据档案**——引擎适配层 RunConfig 上的一个 `auth_profile` 字段，与引擎种类正交，换路径不换适配层。

**立场先说清：走哪条路径、用哪份凭据，是管理员的部署配置决策，不是业务人员的选择。** 下述 A/B/C 三条路径全部在管理面配置生效，业务人员在工作台里永远只是「开始造应用」，对引擎、模型、凭据零感知。

```
凭据档案 = { 类型:     平台模型代理 | 订阅登录态（Claude Code / Codex / Kimi）| 厂商 API key,
            内容:     加密存储（复用平台 Fernet 加密），如 ~/.claude 目录、auth.json、key,
            分配:     由管理员创建并分配（全租户 / 用户组 / 指定用户）,
            并发上限: 同一档案同时最多 N 个会话 }
```

**路径 A：平台模型代理（默认，规模化主路径）。** 引擎经能力总线的双协议模型代理（§3.4）使用平台托管的国产模型，接线方式按引擎所讲协议分两种：

- Anthropic 协议引擎：会话容器内设 `ANTHROPIC_BASE_URL/AUTH_TOKEN` 指向平台代理（token = 会话 key），并把 opus/sonnet/haiku 三档默认模型映射到租户配置的强/中/快三档国产模型（duoduo `compatible_endpoint` 的成品做法）；
- OpenAI 协议引擎：同理设 base_url + 会话 key；对 Kimi Code 这类不读 shell 环境变量凭据的引擎，改为 per-session 生成其 config.toml 注入容器。

治理全在平台手里：会话 key 随会话签发/吊销、scope 最小化、配额限流、token 用量计量。这是唯一不依赖任何外部账号可得性的路径，适用于所有客户。

**路径 B：客户订阅（BYO 凭据：Claude Code / Codex / Kimi 席位）。** 订阅的登录态本质是一份磁盘凭据（`~/.claude` 目录 / `$CODEX_HOME/auth.json`）；duoduo 已验证「凭据完全委托给 CLI 自己的登录态」的机制可行——其 `claude_code_local` 短路模式：**不注入任何 `ANTHROPIC_*` 环境变量，且启动时反向清除环境里残留的 API key 防止劫持订阅路径**（此细节照抄）。平台化为三个环节：

1. **绑定（一次性，管理面操作）**：管理员在后台发起——服务账号型订阅由管理员直接完成官方登录流（订阅无头场景有 setup-token 长期令牌方式；Codex 走设备码登录）；个人席位型由管理员向席位持有人发送授权邀请，对方完成一次授权即收档。登录态落盘 → 加密入档，管理面可随时吊销；
2. **注入（每次会话）**：沙箱容器启动时把档案挂载为容器内 `$HOME/.claude`（或设 CLAUDE_CONFIG_DIR）/ `$CODEX_HOME`，走短路模式；
3. **治理（平台必须补的三件）**：**并发闸**——订阅限额按账号计（滚动窗口 + 周上限），档案级并发上限（建议 1-2），限额报错友好化（「订阅额度用尽，xx 点重置」）；**归属**——计费虽在订阅侧，平台仍从引擎 usage 事件流记每人每会话的 token 台账；**隔离**——档案只注入其分配范围内用户的会话容器，分配与使用全程审计。

两点注意：①**全员共用一个订阅账号不可作为产品承诺**——违反消费者条款（账号共享）、限额不够分（两三个并发会话即顶满）、用量无法归属到人；只可小规模试点，合规路径是每人/每组一个席位；②**Claude Code 二进制不得打进平台镜像**（无分发授权）——客户自装到宿主机或自备镜像层，平台以挂载方式调用；Codex CLI（Apache-2.0）可直接内置沙箱镜像。

定位：BYO 增值路径——已有订阅的客户白赚顶级引擎质量；规模化主路径仍是路径 A。

**路径 C：客户自有厂商 API key。** 企业已采购的模型 API（DeepSeek/GLM 等）建议配置为平台代理的上游、仍经代理转发——保留记账/限流/审计；直连厂商 endpoint 作为例外场景（档案类型 = API key，注入方式同路径 A）。

**路径解析与降级（均为管理员配置的结果）**：解析链 = 用户组级配置 > 租户级默认 > 系统默认（平台代理），全部在管理面设定，业务人员无从选择也无需选择；「订阅额度用尽自动降级切平台代理」同样是管理员预配的策略开关——对业务人员只表现为「一直可用」，最多收到一条降级提示。同一套适配层，只换 `auth_profile` 的取值。

**引擎 × 路径兼容矩阵**：

| 引擎 | 平台模型代理 | 客户订阅 |
|------|-------------|---------|
| Qwen Code | ✓（双协议均可） | —（无订阅形态） |
| Codex CLI | ✓（OpenAI 面） | ✓（ChatGPT 席位） |
| Kimi Code CLI | ✓（双协议，生成 config.toml） | ✓（Kimi For Coding） |
| Claude Code（客户自装） | ✓（Anthropic 面） | ✓（Claude 席位） |

**统一治理底线**（无论哪条路径）：凭据只进属主会话容器、沙箱出站白名单只放行对应 endpoint、用量台账到人、全程审计。

### 4.4 基础组件注入机制（不让 AI 写的部分，怎么递到管家手里）

数据库/登录/权限/存储这些基础组件「平台自带、AI 不写」，靠四条通道让管家**知道有、直接用、不越界**：

1. **模板预接线**：预置模板里 SDK 已引入，读当前用户、查数据表、检索知识库的样例调用就在代码里——管家照现成范式扩展，而不是自由发挥；
2. **声明式资源清单**：应用要用什么平台能力（知识库/模型等）写进 manifest 的 capabilities，应用自有数据表结构亦随 manifest 声明（由平台建库建表，非「接入」既有能力），平台在容器启动时注入凭据与连接——代码里永远不出现连接串和密钥；平台注入的系统变量统一带 `BISHENG_` 保留前缀（用户/AI 自定义键禁用该前缀，防覆盖），草稿沙箱与生产实例的注入变量物理隔离、生产变量发布时才落；
3. **MCP 工具面**：建表/改表结构/读写数据/查身份/检索知识库都是平台 MCP 工具，管家调用工具完成，而非生成底层实现代码；
4. **引擎指令约束 + 纠偏 + 发布前扫描**：引擎系统指令明确禁写鉴权/数据库连接/加密逻辑，管家若违规生成则视为错误、引导改写为平台组件调用；「引导」之外再加一道**发布前「查有无」扫描**——对生成产物正则/AST 扫裸连接串与明文密钥，命中即阻断发布、回流管家改写（只做 presence check，不判鉴权对错——那类「对错」扫描器查不出，仍交运行环境兜底）；两层都失效时，还有 §4.5 的运行环境兜底（代码里没有凭据可泄、网络上没有旁门可走）。

### 4.5 沙箱与安全模型

| 隔离档位 | 实现 | 适用 |
|----------|------|------|
| 基础档（默认） | Docker 加固：read-only rootfs、no-new-privileges、独立网络、资源限额、崩溃自愈 | 所有环境 |
| 推荐档 | + gVisor（runsc 换入 Docker runtime，**无需 KVM/k8s**） | x86_64/ARM64，标准信创虚机可用 |
| 加固档 | Kata/Firecracker microVM | 客户有裸金属/KVM 时可选 |

选型依据：Firecracker/Kata 依赖 KVM，客户虚机普遍无嵌套虚拟化（信创云尤甚），不能作默认；内部应用的现实威胁是**数据外渗与越权**而非内核逃逸——**默认出站白名单**（仅放行平台 API 与显式声明域名）比换 runtime 更重要；LoongArch 等 gVisor 不支持的架构回退基础档。

**编排特权（全案最重安全约束）**：容器由独立最小权限编排器 **runtime-manager** 生管——它是唯一持 docker 访问的组件，backend 编译期/运行期零 docker 依赖（arch-guard import 禁令强制；取证：现网 backend 无 docker 依赖，`docker.sock` 仅出现在 CI）；backend 只向它下发**期望态 intent**（声明式，manager 自 reconcile），绝不把 `/var/run/docker.sock` 挂进 backend 或起 DinD——否则控制面即握 root-on-host、与「安全来自笼子」（§2.2③）自相矛盾，私有化银行/信创客户安全团队必一票否决。runtime-manager 独立受限 service account、凭据与 backend 隔离；容量/密度治理（准入控制、idle 回收、并发上限、cgroup 硬隔离）挂在它上面，兜住「平台正常即使某应用崩」。

**出站白名单 × 依赖安装（构建/运行两段分离）**：生成应用要 pip/npm install（社区 #1568），运行期 egress 锁死后包怎么装？**构建期与运行期 egress 分离**——构建期只放行**平台自托管的 PyPI/npm 镜像**（白名单里的受控条目、非洞：版本可 pin、可缓存、信创可离线预灌），运行期不放行任何包源。发布期除 §4.4④「查有无」裸密钥扫描外，可扩展为一道完整**发布期安全门**：对应用拉入的依赖做 CVE 扫描 + SBOM 留痕（信创软件供应链安全刚需）——裸密钥 presence 检测为本版基线，依赖 CVE/SBOM 视人力可 v3.1 补齐。

**鉴权注入（app-proxy 层，版本无关）**：`auth_request` 现网零使用、纯新建，且 Java 网关只认 `/api/**`、有自己的 Sa-Token/SSO + 自定义 WS filter、完全不认 `/apps`（据 `docs/architecture/11-gateway.md`）——故验会话 + 签 OBO + 注入头 + 反代容器统一收在 **app-proxy** 一个组件里，nginx（开源）与 Java 网关（商业）都只把 /apps 转发到它，安全逻辑一处实现、不随版本分叉：

```
浏览器 → nginx / Java 网关 → app-proxy /apps/{slug}/*（或 /apps/preview/{session}/*）
  ├─ 验平台会话 + OpenFGA viewer 检查（/apps/preview/* 仅 owner——草稿 owner-only，§3.1）
  ├─ 签发短时 OBO token（scope = 应用 capabilities ∩ 用户自身权限）
  ├─ 注入头：X-BiSheng-User-* / X-BiSheng-Access-Token
  └─ 反代容器（支持 WebSocket）
```

两个躲不掉的不变量：① **header 防伪**——app-proxy 剥离客户端伪造的 `X-BiSheng-*` 头，容器仅经 app-proxy 可达（不暴露直连端口）；② **WS 长连接的 OBO 过期/吊销策略**——握手时鉴权一次不够，长连接期间 OBO 过期或权限被撤须有中断策略。app-proxy 与 runtime-manager 是邻居，可同组件可拆。

- 应用启动注入应用 token（M2M，后台逻辑用）；请求级注入 OBO 用户 token（以当前用户权限调知识库——知识库权限对应用内每个用户自然生效，「AI 可见性 ⊆ 用户 UI 可见性」不变量外推到应用场景）。
- 应用侧零登录代码：读头即得身份，SDK 一行拿到。

### 4.6 平台既有资产复用

### 4.7 合规与风险

合规预判：新模块 DDD 分层（C1）；新表 MySQL/DM8 双方言（C2，**但生成应用自己的库不受 C2 约束、走 SQLite/Postgres**）；全部带 tenant_id、容器/镜像/存储前缀租户隔离（C3）；应用/会话/管家均为 OpenFGA 资源类型、预览与生产统一过 **app-proxy** 无旁门（C4）；错误码遵 **C5**（非 C6；C6 是禁硬编码密钥）——段位须避开已占用段（130=chat、160=dataset），建议 161 起 4 段、最终以 release-contract 定；应用级 secret store 复用 **C6** Fernet；双前端纪律不变（C7）。

**数据分类分级（v3.1 治理预留）**：报销/上报类应用天然采集 PII 与敏感字段，等保 2.0 + 数据安全法要求分类分级、脱敏导出、访问留痕——本版审计已留痕，**平台侧敏感字段打标 + 受控导出/字段脱敏**（仍属「平台管、AI 不写」）作 v3.1 治理面预留；这是竞品普遍不做、对央国企的硬合规差异化。

| 风险 | 对策 |
|------|------|
| **引擎在国产模型上的实效未知（最大技术风险）** | Wave-0 PoC 先行；适配层保证引擎可换；模板 + 澄清前置降低对模型上限的依赖 |
| 引擎 API 漂移/断代 | 引擎依赖收口在 RuntimeAdapter 单模块；pin 版本 |
| 造应用会话 token 成本 | 本版不设 token 限制（私有化自有模型与算力）；模板起步减少从零生成消耗；精细成本控制 v3.1 再议 |
| 跑任意代码的安全暴露 | 沙箱分档 + 出站白名单 + capabilities 最小授权 + 发布审批 + 审计 |
| 生成应用质量差/改不动 | 版本回滚（代码无损）+ 修错回流（改到好为止、token 照常计量）+ 玻璃盒逃生 + 模板起步（可选，降低从零生成难度） |
| 客户环境差异 | 工场/沙箱为可选组件（三层部署形态见 §4.8），缺席时平台其余功能完整；gVisor 不可用自动回退 |
| 订阅路径依赖外部账号可得性与限额 | 档案级并发闸 + 限额友好提示 + 一键降级切平台代理续跑（§4.3） |
| **控制面特权（编排 root-on-host）** | 独立最小权限 runtime-manager 唯一持 docker，backend 零 docker 依赖（arch-guard 强制）、intent-based RPC、凭据隔离（§4.5） |
| **容量/密度（单机 N 用户各开沙箱 + 生产容器）** | 准入控制 + idle 回收 + 并发上限 + cgroup 硬隔离，挂 runtime-manager；档位=平台预置资源模板（发布时选择） |
| **应用级 secret 无落点** | 新建应用 secret store（Fernet），声明式注入（同 capabilities + 发布审批） |
| **Anthropic 兼容面耦合引擎实效风险** | 翻译层劣化 tool-calling 会加重模型实效风险；采现成代理省自研长尾、协议面稳定性外包成熟实现（§3.4） |

### 4.8 体量与部署形态（不需要的客户可以不装）

**体量判断据实说：应用工场是 v3.0 的主体工程**——净新建六块核心基建（§4.6）、F100-F112 十二个 feature、五个波次，并引入 docker 编排特权与容器密度这类全案最重的安全/运维负担。但重量分布不均，按「重的可选、轻的共用」切三层部署形态：

| 层 | 组件 | 重量 | 部署形态 |
|---|------|------|---------|
| 平台核心 | 现有 BiSheng 全部功能 | — | 不变；不装工场时**零新常驻进程、行为零变化** |
| 开放能力层 | open_platform（API key 三类）· 模型代理（现成代理 + BishengLLM 路由）· mcp_server | 轻：backend 模块 + 可选代理进程，零 docker 依赖 | 独立开关。**不要工场也独立有价值**：API key 替换 v2「内网可信」模型、双协议代理让客户自装 Claude Code 等工具直连平台托管模型、MCP 对外开放企业能力——§3.6 本地开发者只依赖此层 |
| 工场运行时层 | runtime-manager · app-proxy · 沙箱容器群 · vibe_builder/app_runtime 模块 · client 工作台入口（触发/调度子系统本版不做、v3.1 随看护立项，成型后归平台层，工作流定时/知识库同步共用，见 §5.2） | 重：全案最重最险都在此层（编排特权、容量密度、gVisor） | compose profile 可选，缺席降级语义见下 |

**缺席降级语义**（不装工场运行时层）：工作台/应用广场入口不出现（部署级开关，与 §3.5 租户灰度开关是两层）；nginx/Java 网关无 /apps 转发目标，统一引导页；新表随 alembic 建、空置无害（C2 双方言不受影响）；开放能力层若已装则照常工作。

**边界纪律（防「可选」名存实亡）**：backend 核心路径禁 import 工场模块（arch-guard 新增禁令，与「backend 零 docker 依赖」同一机制强制）；依赖单向——工场调核心 API，核心不感知工场；与核心共享的只有权限（OpenFGA 资源类型）与审批（F025 场景）这类**注册式扩展点**——注册才生效、不注册零成本。

### 5.2 下一版（v3.1）

**应用管家持续看护立项并正式可用**（本版不做、v3.1 重新立项）——让管家持续看护上线应用：看护总览（一屏看住所有看护任务的状态灯 / 上次运行 / 累计花费 / 历史简报）、花费先估后用（开启前出示预估、可走审批、超预算自动停）、巡检频率自动调节（有情况勤看、平稳时少跑）；点选局改（对着预览点选即改）；模板库深化；第三方 MCP server 接入网关化；存量代码执行点（workflow CodeNode / gpts local executor）迁入沙箱设施；k8s 多机调度。

看护立项时须一并新建**平台触发/调度子系统**（cron/webhook 触发器、常驻生命周期、预算闸、机队观测、at-least-once 交付幂等去重）——灵思 worker 是一次性会话模型、丢弃终态队列项、无 cron/webhook、默认 compose 都不起，非直接复用（见 §4.6）；管家看护是该子系统首个消费者，工作流定时/知识库定时同步与「应用级触发器执行动作（汇总/物化看板快照）」同样可复用。设计要点（自原 §3.2 规格归档，供 v3.1 立项）：
  - 触发：定时（cron）+ 事件（webhook），由该子系统提供；
  - 省钱：数据探测零 LLM（与上次游标比对，无增量不唤醒模型）；使命进 system prompt，每次唤醒只注入增量元数据（token 成本不随运行次数膨胀）；
  - 降噪：两级过滤（有没有新 → 值不值得打扰）；每次唤醒只发一份合并简报（一句话结论 + 分条信号 + 建议动作）；无信号绝不发「本轮无事」；宁少报不多报；
  - 推送：经新建的通知服务发出——站内信（现有）+ 企微/钉钉/飞书群机器人 + 通用 webhook（借 workflow 群机器人 webhook 逻辑；org_sync 仅入站目录同步、无外发能力，平台今日无通用外发通知服务）；收件人创建时锁定，agent 不得动态选择；调度为 at-least-once，推送须按幂等键去重（同一增量在去重窗口内只推一次）；
  - 成本：创建时出示花费预估（巡检频率 × 模型）确认后生效；预算上限超限自动暂停；
  - 观测：看护总览面板；简报卡片可嵌入（iframe）到第三方系统页面（复用 F109 白名单机制）。

其余 v3.1 增量：**应用数据备份与自助恢复**（独立于版本回滚的误操作兜底、用户显式发起可审计，不动摇「生产数据默认不回滚」不变量）；**应用退役与归属转移**（owner 离职/转岗接管、长期无人维护应用自动归档下线，补 OpenFGA owner 转移流，防孤儿/僵尸应用）；**敏感字段分类分级与受控导出/脱敏**（等保 2.0 / 数据安全法，平台侧打标，见 §4.7）；**能力总线暴露「调用既有工作流/助手」作为应用能力**；**应用所有者使用情况视图**（复用审计事件流、零新增埋点，只给 owner 看调用量/活跃用户/趋势，非产品成功指标看板）。

5. `/apps`（含 preview + WebSocket）路由与鉴权在 **app-proxy 层统一**（nginx 与 Java 网关都只转发到 app-proxy，安全逻辑不分叉）——据 `docs/architecture/11-gateway.md`，Java 网关只认 `/api/**`、有自己的 Sa-Token/SSO + 自定义 WS filter、不认 `/apps`，故这是**设计任务**而非「待对齐」；待细化 header 防伪与 WS 长连 OBO 过期/吊销两个不变量的落地。
