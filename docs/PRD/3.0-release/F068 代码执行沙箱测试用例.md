# F068 代码执行沙箱测试用例

- **对应功能**：F068 代码执行沙箱统一底座。设计文档在 `features/v3.0.0-beta1/068-code-execution-sandbox/`
- **代码基线**：`origin/feat/3.0.0`（2026-10-17）。这个功能已经合进 `release`
- **测试环境**：test 环境（116 上的 `bisheng-test-*` 容器组，Docker Compose）。Helm 部署时，把 `docker exec` 换成 `kubectl exec`，容器名按实际改
- **用例来源**：按代码编写。第 1 节「高风险点」是读代码得出的判断，标「推断」的条目可信度更低
- **执行记录**：2026-10-29 至 10-30 在 test 环境执行过一轮，结果和缺陷见同目录的《F068 代码执行沙箱测试报告》。2026-10-30 按实测改正了几处过时的前提：runner 会话上限（第 1 节 R2、R4，TC-31）、本地隔离默认开启（TC-03、第 8 节）、权限收紧的时机（第 8 节）

## 1. 高风险点

下表是读代码发现的风险。用例里的 R1–R8 指这张表。第 5 节的用例专门验证 R1–R5，建议冒烟通过后先跑。

| 编号 | 风险 | 依据 | 实测成立时的影响 |
|---|---|---|---|
| R1 | 沙箱错误可能直接中断任务模式（推断） | 28001/28002/28003/28006 是抛出的异常。LangGraph `ToolNode` 默认只吞参数校验错误，任务模式没有配置 `handle_tool_errors`。日常会话有 `_handle_agent_tool_error` 兜底 | 本地模式超时时，模型拿到超时说明后任务继续；沙箱运行超时则整个任务失败 |
| R2 | 并发容量少于任务模式并发数 | runner 默认 `SANDBOX_MAX_SESSIONS=50`（代码默认值，仓库 compose 和 helm values 也是 50），test 环境 2 个 runner 共 100 个槽位。任务模式整轮占用一个会话，包括模型思考时间。领不到槽位时不排队，直接报 28002 | 默认配置下槽位很难占满，要复现得临时调小上限（见 TC-31）。实测发现真正的瓶颈是 runner 同一时间只执行一段代码，见测试报告 |
| R3 | 空闲 15 分钟回收打断长任务 | `SANDBOX_LEASE_TTL_S=900`，活跃时间只在执行开始时刷新。执行器拿到 404 后不会重新领租约。任务模式单次超时设为 3600 秒 | 两次代码调用相隔超过 15 分钟时报 28006；单次执行超过 15 分钟时，工作目录可能在执行中被删 |
| R4 | 资源限制叠加导致误判 | `mem_limit: 2g` 由同一 runner 上的全部会话（最多 50 个）和 runner 主进程共享；`/tmp` tmpfs 不限大小，占用同一份内存；子进程 `RLIMIT_AS=2GB`、`RLIMIT_CPU=600s` | 工作区大时 OOM；runner 被杀后所有会话丢失；原生报错不指向资源限制，容易被误判为功能缺陷 |
| R5 | 子代理并行共用同一个执行器（推断） | 子代理的工具和主代理是同一批实例。copy-out 只按最近一次 exec 前的快照做差 | 并行时产物被算到别的子代理结果里，或丢失 |
| R6 | 同一 runner 上两个会话可能拿到相同 uid | `uid = 10000 + 当前会话数`，会话释放后再新建会撞号 | 同一容器内两个会话互相可读，违反跨会话隔离 |
| R7 | 与安全评审口径不一致 | runner 容器没有 CPU 上限；runner 主进程以 root 运行，带 `SETUID`/`DAC_OVERRIDE` 能力。2026-10-17 在 test 环境核实：`NanoCpus=0`、`User=0` | AC-14 的 CPU 上限没有落地；对外说「非 root」需要先对齐口径 |
| R8 | 时区可能不对（推断） | 沙箱 Dockerfile 里没有看到安装 `tzdata` | `datetime.now()` 是 UTC，报告日期和时间慢 8 小时 |

## 2. 通用准备

### 2.1 环境与执行方式

1. 登录 116，设置容器名变量。下文所有 `docker` 命令都在 116 上执行：

   ```bash
   ssh root@192.168.106.116
   BACKEND=bisheng-test-backend
   WORKER=bisheng-test-backend-worker        # 任务模式 worker 也在这个容器里
   RUNNER1=bisheng-test-code-runner-1
   RUNNER2=bisheng-test-code-runner-2
   ```
2. 确认 runner 镜像和后端镜像是要测的版本：

   ```bash
   docker inspect -f '{{.Config.Image}} {{.Created}}' $RUNNER1 $WORKER
   ```

   test 环境用 `release` 标签的镜像。先确认镜像在 F068 最新提交之后构建过。
3. 进入平台管理端，打开「工具 → 内置工具 → 代码执行器」。「代码执行方式」有三个选项：
   - **本地隔离运行**（`type=local`）
   - **沙箱运行**（`type=container`）
   - **E2B沙箱运行**（`type=e2b`）

   用例里写「沙箱运行」，就先选这一项并保存。
4. 检查 runner 连通性。两条命令都应返回 `{"status":"ok"}` 或类似的健康响应：

   ```bash
   for c in $BACKEND $WORKER; do
     docker exec $c curl -sS -m 5 http://code-runner-1:8080/health; echo
   done
   ```
5. 测试期间开两个终端跟日志：

   ```bash
   # 终端 1：两个 runner
   docker logs -f --since 1m $RUNNER1 2>&1 | grep -E "session|exec|oom|capacity" &
   docker logs -f --since 1m $RUNNER2 2>&1 | grep -E "session|exec|oom|capacity"
   # 终端 2：worker（任务模式、工作流）
   docker logs -f --since 1m $WORKER 2>&1 | grep -iE "sandbox|code interpreter|2800[0-9]"
   ```

### 2.2 让模型原样执行代码

很多用例要求模型执行一段指定的代码。在对话框里先写下面这段固定前缀，再接代码块。下文用 **【原样执行】** 指代这段前缀：

> 请调用代码执行器，原样运行下面的 Python 代码，不要改写、不要拆分，也不要先做别的事；运行后把完整输出原样贴给我。

模型有时仍会改写代码。每条用例执行后，展开工具调用详情，确认实际执行的就是给定代码。如果被改写，就重新发一次。

### 2.3 结果记录

每条用例记录以下内容：用例编号、执行方式、通过或失败、会话链接、工具调用详情截图，以及 runner 日志里相关的 `session_id`。

## 3. 冒烟（每次部署后先跑）

### TC-01 沙箱运行基本可用

- **前置**：执行方式为「沙箱运行」。
- **步骤**：
  1. 在任务模式中发送【原样执行】加下面的代码：

     ```python
     import os, sys, getpass
     print("cwd:", os.getcwd())
     print("uid:", os.getuid(), "user:", getpass.getuser())
     print("python:", sys.executable)
     print("ls:", sorted(os.listdir(".")))
     ```
- **预期**：
  - `cwd` 以 `/tmp/sessions/` 开头。
  - `uid` 不是 0。
  - `python` 是 `/app/.venv/bin/python` 一类的路径。
  - `ls` 里有 `output`、`scratch`。
  - runner 日志依次出现 `session created`、`exec start`、`exec done exitcode=0`。

### TC-02 任务结束释放会话

- **步骤**：
  1. 等 TC-01 的任务结束。
  2. 查看 runner 日志。
- **预期**：出现 `session deleted ... reason=client`，`slots` 回到 `0/2`。

### TC-03 执行方式切换不需要重启

- **步骤**：
  1. 把执行方式改成「本地隔离运行」，保存。不要重启任何服务。
  2. 新开一个任务，再跑 TC-01 的代码。
  3. 改回「沙箱运行」，新开一个任务，再跑一次。
- **预期**：
  - 第 2 步 runner 日志没有新会话。`cwd` 显示为任务工作区 `/root/.cache/bisheng/linsight/...`。本地隔离默认开启，test 环境也是开启的：uid 在 30000–39999 之间，代码实际在 `/tmp/bisheng-local-run/run-*` 里运行，输出里的路径会被改写回工作区路径，见第 8 节。如果 uid 是 0，说明本地隔离被关掉了。
  - 第 3 步的 `cwd` 回到 `/tmp/sessions/`。
- **关联**：AC-22。

## 4. 任务模式核心链路

### TC-10 读取用户上传的原件

- **前置**：准备 `sales.xlsx`，包含两列「地区」「金额」，10 行数据。
- **步骤**：
  1. 在任务模式里上传 `sales.xlsx`。
  2. 发送：「用代码读取我上传的 Excel，按地区汇总金额，把结果打印出来。」
- **预期**：
  - 模型在代码里用 `uploads/sales.xlsx` 读文件，不报 `FileNotFoundError`。
  - 汇总数值和手工计算一致。

### TC-11 产物出现在结果区

- **步骤**：发送【原样执行】加下面的代码：

  ```python
  import pandas as pd
  pd.DataFrame({"a": [1, 2], "b": [3, 4]}).to_excel("output/report.xlsx", index=False)
  print("done")
  ```
- **预期**：
  - 结果区出现 `report.xlsx`，可以下载，打开后内容正确。
  - 在同一轮里接着说「用 read_file 读一下 /output/report.xlsx 的信息」，模型能读到。

### TC-12 根目录文件被移到 `output/`

- **步骤**：发送【原样执行】加下面的代码：

  ```python
  open("root_file.txt", "w").write("hello")
  print("written")
  ```
- **预期**：
  - 工具结果里提示文件已移到 `output/root_file.txt`。
  - 结果区出现 `root_file.txt`。

### TC-13 输入文件不进入产物清单

- **前置**：沿用 TC-10 的会话，`uploads/sales.xlsx` 已存在。
- **步骤**：发送【原样执行】加下面的代码：

  ```python
  import pandas as pd
  df = pd.read_excel("uploads/sales.xlsx")
  df.to_csv("output/sales.csv", index=False)
  print(len(df))
  ```
- **预期**：产物清单里只有 `sales.csv`，没有 `sales.xlsx`。

### TC-14 跨轮继承上一轮的产物

- **步骤**：
  1. 在 TC-11 的任务完成后，在同一会话里继续追问：「在刚才的 report.xlsx 里加一列 c = a + b，另存为 report2.xlsx。」
- **预期**：
  - 模型能读到 `output/report.xlsx`。
  - 新产物 `report2.xlsx` 里的 c 列是 4、6。
  - runner 日志里，这一轮是一个新的 `session created`。

### TC-15 技能包可执行

- **前置**：在任务模式里勾选 bisheng-docx、bisheng-pptx、bisheng-xlsx 技能。
- **步骤**：分三次新任务发送：

  - 版式符合技能定义：docx 是公文版式，xlsx 里的公式能算出值。

### TC-16 `ask_user` 等待后恢复

  2. 澄清提问出现后，等 2 分钟再回答。
  3. 回答后继续执行，过程中要用到代码。
- **预期**：
  - 第 1 步结束时，runner 日志有 `session deleted`。
  - 恢复后出现新的 `session created`，代码能读到之前上传的文件。

### TC-17 读取 `large_tool_results`

### TC-18 单个文件超过 50MB 被跳过

  1. 上传 `big.csv`，同时上传一个小文件 `small.txt`。
  2. 发送【原样执行】加下面的代码：

     ```python
     import os
     ```

  - 输出里有 `small.txt`，没有 `big.csv`。
  - 工具结果里出现 `[SYSTEM NOTICE] Copy-in skipped an oversized file: uploads/big.csv`。
  - 如果上传接口本身就拒收 60MB 文件，记录上传上限，然后把这条用例改成「上限附近的文件」。

## 5. 失败与边界（R1–R5，优先测）

### TC-30 执行超时（R1）

- **前置**：执行方式为「沙箱运行」。任务模式的超时在代码里写死为 3600 秒，不能通过配置缩短，所以这条用例要等 1 小时。可以先在日常会话里做对照：日常会话用 `sandbox_conf.default_timeout_s`（默认 600 秒）。在 backend 上临时设置 `BS_SANDBOX_CONF__DEFAULT_TIMEOUT_S=60` 并重建，可以把日常会话的超时缩到 60 秒。
- **步骤**：发送【原样执行】加下面的代码：

  ```python
  import time
  time.sleep(100000)
  ```
- **预期**：模型收到「执行超时、产物不存在」的结果后继续工作，任务不失败。
- **判定**：如果整个任务直接进入失败状态，或页面报错、停止，说明 R1 成立，记缺陷。
- **对照**：切到「本地隔离运行」重做一次，对比两种方式的表现。

### TC-31 容量满（R2）

- **前置**：runner 默认每个 50 个会话，下面 5 个并发填不满。先临时把 runner 的 `SANDBOX_MAX_SESSIONS` 改成 `2` 并重建两个 runner，得到 2 × 2 = 4 个槽位：

  ```bash
  cd /opt/server/bisheng-test && cp -p docker-compose.yml docker-compose.yml.bak-tc31-$(date +%Y%m%d-%H%M%S)
  # 把 runner 的 SANDBOX_MAX_SESSIONS: '50' 改成 '2'（两个 runner 共用同一个 environment 锚点）
  docker compose up -d --no-deps code-runner-1 code-runner-2
  docker logs --since 1m $RUNNER1 2>&1 | grep ready   # 应显示 max_sessions=2
  ```

  测完用备份恢复 compose 并再次重建 runner。CI 每次自动部署都按这份 compose 重建容器，所以不要把改动留在环境里。
- **步骤**：
  1. 用 5 个浏览器窗口（可以是同一账号）各开一个任务模式会话。
  2. 每个会话都发送【原样执行】加下面的代码，尽量在 10 秒内全部发出：

     ```python
     import time
     time.sleep(120)
     print("done")
     ```
  3. 第 5 个任务发出后，再到工作台日常会话里发送【原样执行】加 `print(1)`。
- **预期**：前 4 个任务正常执行。第 5 个任务和日常会话要么排队等待，要么给出看得懂的「执行资源已满」提示。
- **判定**：
  - 第 5 个任务整体失败，说明 R1 和 R2 同时成立。
  - 日常会话显示「工具执行失败: …28002…」：记录原文，评估提示能否看懂。
  - 在 worker 日志里搜 `28002` 或 `at capacity` 作为佐证。

### TC-32 两次代码调用相隔超过 15 分钟（R3）

- **步骤**：
  1. 在任务模式发送：「先用代码打印 1；然后等我。」
  2. 在同一轮里制造超过 15 分钟的间隔。最可控的方式是临时把 runner 的 `SANDBOX_LEASE_TTL_S` 改成 `60`，重建 runner。然后发一个先执行代码、再做 2 分钟以上联网检索、最后再执行代码的需求，例如：「先用代码打印当前时间；再联网搜 10 篇关于大模型 Agent 的文章并逐篇总结；最后用代码把总结字数统计出来。」
- **预期**：最后一次代码调用成功。如果租约已过期，执行器应自动重新领租约。
- **判定**：最后一次调用报 28006（`Isolation environment response is invalid`）或任务失败，说明 R3 成立。

### TC-33 单次执行超过空闲回收时间（R3）

- **前置**：沿用 `SANDBOX_LEASE_TTL_S=60`。
- **步骤**：
  1. 会话 A 发送【原样执行】加下面的代码：

     ```python
     import time
     open("output/before.txt", "w").write("1")
     time.sleep(120)
     open("output/after.txt", "w").write("2")
     print("finished")
     ```
  2. A 执行 70 秒后，在会话 B 发送【原样执行】加 `print(1)`。B 会触发 runner 的回收检查。
- **预期**：A 正常完成，产物里有 `before.txt` 和 `after.txt`。
- **判定**：如果 runner 日志在 A 结束前出现 A 的 `session deleted reason=idle`，或 A 报 28006，说明 R3 成立。

### TC-34 执行中 runner 重启（R4）

- **步骤**：
  1. 任务模式发送【原样执行】加 `import time; time.sleep(60)`。
  2. 执行 10 秒后运行 `docker restart $RUNNER1`；如果会话落在 runner-2，就重启 runner-2，看日志确认。
  3. 等这次调用返回后，在同一轮里再让模型执行 `print(1)`。
- **预期**：第一次调用返回可归因的错误。第二次调用能重新领到租约并成功。
- **判定**：第二次及以后的调用都报 28006，或任务失败。

### TC-35 OOM（R4）

- **步骤**：发送【原样执行】加下面的代码：

  ```python
  data = []
  while True:
      data.append(bytearray(100 * 1024 * 1024))
  ```
- **预期**：返回内容能看出是内存不足，例如 `MemoryError` 或 exitcode 137 时说明是内存超限。下一次调用能正常执行。

## 8. 本地隔离运行（10-14 新增）

10-14 起，「本地隔离运行」让代码以临时普通 uid（30000–39999）在私有目录 `/tmp/bisheng-local-run/run-*` 里执行。

**开关**：配置项是 `sandbox_conf.local_isolation`，可以用环境变量 `BS_SANDBOX_CONF__LOCAL_ISOLATION` 覆盖。代码默认值是 `uid`，也就是默认开启；只有显式写 `off` 或空字符串才关闭，写错的值一律按开启处理。仓库里的 compose 也通过 `.env` 的 `LOCAL_ISOLATION` 默认传 `uid`。2026-10-30 核实：test 环境的 `config.yaml` 写的是 `local_isolation: uid`，compose 没有设置这个变量，所以本地隔离是开启的，跑本节用例前不需要改配置。用下面的命令确认：

```bash
docker exec $WORKER grep -A6 '^sandbox_conf:' /app/bisheng/config.yaml | grep local_isolation
docker exec $WORKER env | grep LOCAL_ISOLATION   # 没有输出表示没有用环境变量覆盖
```

**权限收紧的时机**：收紧不在 worker 启动时做，而是每个进程第一次执行本地代码时，在预检里把 `/app/bisheng`、`/app/data` 改为 0700，再用探针确认临时 uid 读不到它们。因此：

- 新启动的容器里，`/app/bisheng` 是 755，要等这个容器第一次本地执行后才变成 0700。backend 和 worker 两个容器各自独立收紧。2026-10-30 实测：worker 首次本地执行前 `/app/bisheng` 是 755，执行后是 700。
- `/app/data` 是挂载卷，权限改在宿主机的目录上，容器重建后仍然是 0700。
- `config.yaml` 本身应为 `600 root`。如果宿主机上的文件对组或其他用户可读，worker 日志会出现 `is group/other readable` 告警。

所以检查权限时，要先在同一个容器里执行一次本地代码，再看 `stat -c %a /app/bisheng`。

  ```bash
    curl -s -o /dev/null -w "no-token:%{http_code}\n" -X POST http://code-runner-1:8080/v1/sessions
  '
  ```
- **预期**：`wrong-lease:403`，`no-token:401` 或 403。测试创建的会话会在空闲超时后被回收，也可以手动 DELETE。

### TC-98 资源上限

- **步骤**：在沙箱运行下分别执行：
  1. fork 炸弹：`import os` 后执行 `while True: os.fork()`。
  2. 跑满 CPU：`while True: pass`，执行期间在宿主机用 `docker stats $RUNNER1` 观察 CPU 占用。
- **预期**：
  - fork 被 `pids_limit` 或 `RLIMIT_NPROC` 拦住，宿主机不受影响。
  - CPU 占用能看出有上限。
- **判定**：如果 CPU 能吃满宿主机所有核，说明 R7（AC-14 未落地）成立。

### TC-99 runner 自身的运行身份（R7）

- **步骤**：运行 `docker exec $RUNNER1 ps -eo uid,user,cmd`。
- **记录**：runner 主进程的 uid（预计是 0），交给安全评审对齐「非 root」的口径。
