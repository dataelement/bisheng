# 安全响应流程

对外承诺见根目录 [`SECURITY.md`](../SECURITY.md)。本文是内部怎么兑现它。

---

## 为什么需要这份文档

2026 年 4 月到 9 月，至少 7 份漏洞报告在 GitHub 上公开，其中多份的正文里写着同一句话：**"先走私密通道报过，没有收到任何回应。"**

- `#2189` / `#2190`：分别通过 GHSA 私密公告提交，正文注明"reported on 1 June 2026, no response"
- `#2415`：正文写"private security-advisory drafts on this repository have historically received no response"
- `#1959`：正文建议我们开启私密上报（其实**已经开着**，只是没人看）

后果不是漏洞本身，而是：带完整 PoC 的攻击步骤在补丁发布前就全网公开，而且每份报告都附带一句"我先私下说过了"。**私密通道开着却没人值守，比不开更糟** —— 研究者白等一轮，然后带着火气公开。

当前事实（2026-09 核查）：

| 项 | 状态 |
|---|---|
| GitHub 私密漏洞上报 | **已开启**（`private-vulnerability-reporting` → `enabled: true`） |
| 已发布的安全公告 | **0 份** |
| 公开未关闭的安全类 issue | 6 份以上 |

---

## 值守

**每周至少查看一次**，查看人固定到具体的人，不是"团队"。

要查的三个地方：

1. `https://github.com/dataelement/bisheng/security/advisories` —— 草稿公告**不会**给 issue 订阅者发通知，只有仓库管理员能看到，最容易漏的就是这里
2. 仓库 issue 列表里带安全字样的新条目
3. Dependabot 告警（当前 264 条，另行排期，不走本流程）

## 分级与时限

时限从**收到**算起，不是从开始处理算起。

| 级别 | 判据 | 首次回应 | 给出结论 | 修复发布 |
|---|---|---|---|---|
| 紧急 | 未认证即可远程执行代码、越权读取他人数据 | 1 个工作日 | 3 个工作日 | 尽快，可走热修版本 |
| 高 | 已认证用户可提权、越权、任意文件读写 | 3 个工作日 | 10 个工作日 | 下一个发布版本 |
| 中 / 低 | 需要特定配置或本地权限才能利用 | 3 个工作日 | 10 个工作日 | 正常排期 |
| 不成立 | 路径已不存在、不可利用、或属于部署配置 | 3 个工作日 | 10 个工作日 | 说明原因并关闭 |

**"首次回应"不需要结论，一句"收到，正在核实"即可。** 这一句就能避免绝大多数"等不到就公开"。

## 处理流程

### 1. 确认能不能复现

不要凭报告正文下判断，**对着当前代码核实**，结论只有三种：

- **成立** → 按下面走
- **路径已不存在** → 查清是哪个提交、哪个版本移除的，回复里写明版本号（例：#2162、#2067、#1995 都是 v2.4.0 已移除）
- **报告正确但不可利用** → 说清挡住它的是什么。如果挡住它的是一个**巧合**而不是一道检查，仍然要加固（例：#1994 的 `save_download_file` 靠哈希前缀意外挡住）

### 2. 定级、开分支

安全修复走轻量流程，不要求完整 SDD，但**必须有测试**，且测试要覆盖报告里给出的每一个 PoC 载荷。

分支落在**当前发布线**上（参见根 `AGENTS.md` 的分支规则）。跨版本线只能 cherry-pick。

### 3. 修复的两条原则

- **在根上修，不要在入口上堵。** 删掉一个接口不等于删掉它背后的能力：#1995 里接口在 v2.4.0 就删了，但那份含 8 处 `exec()` 的文件在仓库里又躺了半年。
- **不要用黑名单做沙箱。** 限制 builtins、禁用模块、AST 校验这类方案在 Python 里挡不住绕过，别把它当成修复。

### 4. 发布与公告

修复发布后：

1. 把对应的草稿公告补全并**发布**，申请 CVE 编号
2. 回复公开 issue，写明修复在哪个版本
3. 需要客户动手的（改配置、改密钥、跑迁移脚本），写进部署文档并单独通知

**发布公告不是可选项。** 客户做合规审计时要的是公告记录，不是散落在 issue 里的讨论。

## 回复的写法

这批报告的作者水平很高，PoC 都能复现。回复要满足三点：

1. **承认属实的部分**，不要含糊其辞
2. **没修的就说没修**，写清楚现状和计划，不要用"已优化"之类的措辞掩盖
3. **前期失联是我们的问题**，直接认，不要解释

关于修复范围也要诚实：部分修复要说明剩下什么。例如 #2190 的模板归属，存量模板在被迁移前仍可被读取 —— 这一条主动说明，比等对方按 PoC 验出来再问要好。

## 已知教训

- **验收时记下的"Follow-up"没有归口就等于没记。** F014 验收文档里早就写明"环境变量覆盖不生效"，一年后被外部研究者当成漏洞报回来（#2415）。
- **删接口时要连带清理它背后的实现。**
- **默认配置就是绝大多数客户实际在跑的配置。** 自带的 compose 里写死的密钥、映射出去的管理端口，都要按"一定会被原样使用"来对待。
