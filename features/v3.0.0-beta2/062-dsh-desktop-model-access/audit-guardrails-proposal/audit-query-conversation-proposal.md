# 审计筛选简化与会话分组技术方案

日期：2026-10-16；2026-10-19 用户确认并开始实施。状态：已确认。代码基线：6f0e93a05e。

本次统一模型名称查询和请求状态，默认按会话组织审计记录，未关联请求单独展示。模型请求及其输入输出仍是审计事实，不把多次模型请求重建成未经核实的客户端聊天记录。

本文件为已确认增量方案；同步修改 spec.md、design.md、tasks.md 并开发服务端及管理页，不修改客户端协议或线上数据。

## 1 方案结论

| 事项 | 建议方案 |
|---|---|
| 常用筛选 | 仅用户、时间范围、查询、重置和高级筛选入口 |
| 模型筛选 | 移至高级筛选；一个可输入的候选框，统一按完整名称 `提供方 / 模型名` 精确查询，不再由页面提交模型 ID |
| 模型候选 | 聚焦自动展开并加载当前租户开放模型；输入只搜索候选目录，点击查询才查审计；允许手填已删除模型的完整历史名称 |
| 请求状态 | 列表只显示正常或异常，高级筛选只保留一个状态条件；底层四个事实轴保留，异常原因可展开 |
| 会话展示 | 默认会话列表，展开会话后分页加载请求；未关联会话的请求放在独立视图 |
| 大表查询 | 复用完整模型名称摘要索引；新增可索引的请求状态和轻量会话索引，不在审计明细上做全量分组、模糊查询或前端分页后分组 |
| 客户端改动 | 本轮不需要。复用已上报的会话、请求用途、子 Agent 和父会话字段；缺失字段继续明确展示未知 |

已确认的产品取舍有两个：正常表示“当前未发现异常”，进行中仍归正常并明确提示；会话列表第一版按“首次收录时间”倒序，以免正在活跃的会话反复移动而破坏翻页。具体规则见第 4 节和第 5 节。

## 3 模型筛选与候选交互

### 3.1 统一按完整展示名精确匹配

界面字段名为“模型”，值形如 `volces / deepseek-v4-1-flash-260910`。无论来自候选还是手填，最终只提交同一个 `model_name` 参数。

这里的“提供方和模型名精确匹配”具体采用现有完整展示名的原值相等语义，不增加独立的提供方筛选框，也不把完整展示名按 `/` 拆成两个字段。提供方或模型名称自身可能含 `/`；本轮无需恢复两个原始字段。若以后要分别检索两者，需要另外定义结构化快照，不能从历史展示名猜测拆分。

例如选择同名模型配置 7 或 19，最终都传 `model_name=volces / deepseek-v4-1-flash-260910`，查询同一完整名称下的全部历史请求，不再限制某个配置 ID。提供方、模型改名后，新旧名称分别查询；配置删除不影响旧名称查询。这个行为与原先“按 ID 跨改名查历史”不同，是本轮统一口径的明确变化。

匹配规则：

- 对审计表使用完整原值和现有 `model_name_digest`；不做大小写折叠、模糊匹配或自动补全查询值。摘要索引负责定位，返回前继续核对原始字符串。
- 选中候选直接复制候选的完整名称。手填内容除空字符串代表不筛选外，按原值查询；不静默 trim 或按分隔符重写。
- 只输入 `deepseek` 可以过滤候选，但不意味着查所有名称含 deepseek 的审计。未选择时点击查询，按输入原值精确查询；无命中就正常返回空结果，提示应使用完整名称。
- 保留审计事实中的 `model_id`，仅用于内部追踪；本轮不删除旧字段、旧索引或历史数据。新界面和新增会话 API 不使用 ID 筛选。
- 历史名称摘要尚为 NULL 的记录必须先按现有回填流程补齐；禁止为兼容旧数据增加全表名称扫描兜底。

### 3.2 聚焦即展开的输入候选框

移除独立“选择模型”按钮及面板里的第二个搜索框。输入框既是最终值，也是候选搜索入口。

| 操作 | 行为 |
|---|---|
| 点击或键盘聚焦 | 展开候选；空值加载当前租户首批开放模型，有输入则按该输入搜索 |
| 输入 | 250 ms 防抖调用候选目录 API，重置候选分页；不请求审计日志 |
| 选择候选 | 填入完整名称，关闭候选，保留焦点；只修改筛选草稿 |
| 回车 | 有显式高亮候选时选择该候选；没有时提交精确查询；输入法组合期间不处理回车 |
| 清空 | 清除模型条件并重新加载候选首批；不自动应用整组筛选 |
| Esc 或点击外部 | 关闭候选，不清空已输入内容，不自动选中第一项 |
| 加载失败或无候选 | 展示重试或空状态；继续允许手填历史完整名称 |
| 切租户或输入变化 | 取消旧请求并用请求序号拒绝过期响应；清理旧租户候选和选择 |

候选只搜索授权租户开放模型目录，可在目录数据上做包含匹配；它与审计日志精确查询是两条不同的数据路径。每页 20 个候选，不一次性向浏览器发送全部目录。服务端以完整名称去重后再分页，避免多个配置 ID 产生重复候选或错误的 total。

复用现有 Input、Popover、Command 交互基础，不新造基础组件。使用 combobox/listbox 语义、上下方向键、活动选项和加载提示；Popover 不抢走输入焦点。已落地的 Input、Tag 规范优先，其他能力沿用现有 Platform 及 Client 可搜索选择实现，实施前核对 `@bisheng/ui` 落地状态与 Platform 兼容性，不在本轮迁移整套组件。

## 4 正常与异常的判定

### 4.1 状态含义和映射

统一请求状态为 `NORMAL` 和 `ABNORMAL`。**正常表示当前已保存的事实中没有发现异常，不承诺请求已结束、客户端已收到响应或正文已全部落库。** 仍进行中或等待异步确认的请求，旁边显示“进行中”或“等待记录补齐”的说明，不新增第三个状态筛选项。

以下任一异常条件成立，请求整体即为异常；其他合法组合为正常。多个异常原因同时保留，不互相覆盖。

| 事实维度 | 正常条件 | 异常条件和展示原因 |
|---|---|---|
| 模型结果 | `RUNNING`、`SUCCEEDED` | `FAILED` 模型调用失败；`CANCELLED` 调用已取消；`UNKNOWN` 模型结果未确认 |
| 接口响应 | `RUNNING`、`COMPLETED` | `ERROR` 响应发生错误；`INTERRUPTED` 响应发送中断；`UNKNOWN` 响应结果未确认 |
| 用量结算 | `PENDING`、`SETTLED` | `USAGE_UNKNOWN` 用量未取得；`UNCERTAIN` 结算结果未确认 |
| 正文留存，生效模式为 `METADATA` | `NOT_CAPTURED`，符合仅保存元数据策略 | 其他值为记录状态不一致，不据此宣称模型调用失败 |
| 正文留存，生效模式为 `CONTENT` | `PENDING`、`COMPLETE`，且没有已知采集失败 | `PARTIAL` 正文未完整；`NOT_CAPTURED` 正文未留存；`capture_failed=true` 正文采集发生异常 |
| 未识别的模式或事实枚举 | 无 | 记录状态无法识别，保守归异常并保留原值供排障 |

补充边界：

- 用户主动取消也归异常，含义是未正常完成，不把它写成供应商故障。
- 仅元数据模式没有正文是正常；关闭模式不会产生本功能的新请求行，不构造“关闭请求”参与统计。
- 旧客户端缺会话 ID、来源种类缺失、标题生成、压缩请求和子 Agent 都不因其类型被判异常。来源声明问题单独提示，不混入这四个事实维度。
- 已有后台观察窗口及活动确认逻辑负责将失活的 RUNNING/PENDING 转为 UNKNOWN、UNCERTAIN、PARTIAL 或 NOT_CAPTURED；不是超过固定模型总耗时就判失败。巡检延迟期间仍可能显示正常并提示未确认，必须监测巡检积压。
- `PARTIAL` 可能只是当前异步事实尚未补齐，后续完整性核验通过可以恢复正常。文案为“正文未完整”，不写“正文永久丢失”。
- 正文读取失败、无权读取、浏览器取消展开，是此次读取结果，不反向改写已保存的请求状态。MinIO 后来不可用也不能仅凭已有 COMPLETE 声称此刻一定可读取。
- 整条审计完全失写仍可能没有可筛选的请求行，不能因为异常筛选为空就宣称没有审计缺口。

### 4.2 存储与查询

新增 `audit_status` 持久化字段和 `(tenant_id,audit_status,started_at,request_id)` 联合索引；请求接口、会话明细及卡片共用服务端状态，不在前端另算一套。

纯函数 `derive_audit_status` 根据本条请求已保存的事实生成状态和固定原因代码。原因可在返回元数据时从四轴推导，不额外保存可漂移的文案。审计异步写入器和失活巡检在修改事实的同一事务内更新 `audit_status`，并遵守现有请求行锁及状态版本。重试和迟到事实不会让旧投影覆盖新状态。

查询只增加 `audit_status=NORMAL|ABNORMAL` 等值条件，不在线拼四轴的 OR 表达式，不从取回的一页中过滤。模型和状态同时查询时，以名称索引或状态索引定位，另一条件作为剩余过滤；**精确匹配不等于任何条件组合都自动高效**，是否补充名称与状态联合索引以双库执行计划和压力数据为准。

迁移先增加可空状态列，不把历史未知行默认写成正常。按请求主键分批、行锁或版本保护回填，以同一个函数计算；新写入直接计算。完成目标租户状态回填并核验前，不开放其二态筛选；仍可通过原请求明细能力查看历史，不能悄悄漏掉 NULL 行。

### 4.3 页面呈现

卡片原四项状态替换为一个状态标签及简短原因，例如“异常 · 用量未取得”；多原因时显示首个固定优先级原因及“另 2 项”，点击状态说明查看全部原因和底层事实。优先级为模型、响应、用量、正文，只用于展示，不影响判定。

已结束且无异常用正常成功色；正常但未完成的辅助说明用中性文字，不用失败红。异常中的明确失败使用危险语义，未知或待补齐原因使用警告语义；文字始终保留“正常/异常”，不只靠颜色。请求详情仍能看见四轴事实及时间，默认列表不再重复四组技术标签。

高级筛选“状态”只有全部、正常、异常；“全部”是无条件，不是第三种持久化状态。正文大小和 Token 用量可保留，缺少用量仍显示未知，不填零。

## 5 按会话组织记录

### 5.1 分组规则和浏览层级

分组使用已有 `conversation_key=SHA256(JSON([tenant_id,user_id,conversation_id]))`。其中 tenant/user 来自模型调用时的认证身份，conversation_id 是经过基本校验的客户端声明。不同用户、不同租户的同名 ID 必须是不同组；客户端同一用户误复用 ID 仍可能误合并，服务端不能通过内容验真。

建议首页采用两个并列视图“会话日志”和“未关联请求”，默认会话日志。切换只查询选中视图，不为了显示全量数量扫描另一视图；不显示未经计算的数量徽标。

```text
审计日志    用户 [全部用户]    时间 [全部时间]    [查询] [重置] [高级筛选]

[会话日志]  [未关联请求]

▸ 用户 dshadmin · 会话 session-a · 最近请求 14:07 · 已存 12 个请求 · 异常 1
▾ 用户 dshadmin · 会话 session-b · 最近请求 14:01 · 已存 3 个请求 · 正常
    14:00 普通会话 · 提供方 / 模型名 · 正常          [请求详情] [查看原文]
    14:01 压缩请求 · 提供方 / 模型名 · 正常          [请求详情] [查看原文]
    [加载更多请求]

未关联请求视图
    14:03 标题生成 · 提供方 / 模型名 · 正常 · 未关联会话   [查看原文]
```

上图是信息结构说明，不是新的视觉规范。用户名以授权目录可取到的信息显示；账号已删除或目录无该人时显示历史用户编号，不丢弃审计记录。

- 会话默认折叠，展开先取该会话的请求元数据，分页每页 20 条；点击某条“查看原文”才触发其正文读取及访问留痕。会话展开本身不取正文。
- 同一会话内按 `(started_at,request_id)` 升序展示；压缩、标题生成保留各自请求位置，不另建会话或假装成用户聊天气泡。相同开始时间用 request_id 稳定排列，并行不代表真实因果顺序。
- 子 Agent 保留自己的会话组，不与父会话合并。展开后按请求显示子 Agent 来源及直接父会话入口，仍按同租户、同历史用户授权定位。不同请求的父关系可能冲突，不能将第一条的父声明冻结为权威会话关系，不递归加载任务树。
- 无有效会话 ID 的请求逐条展示，不按登录 session_id、时间接近、正文相似度或父编号猜分组，也不把所有 NULL 会话归成一大组。
- 不读取正文推导会话标题，不另调模型生成摘要。第一版使用已有会话编号及用户、时间区分；无标题是预期行为。
- 不做跨请求输入历史去重或新增消息猜测。每个请求的输入输出是原件；会话只改善浏览组织，不承诺等同于客户端完整聊天记录。

### 5.2 筛选作用范围

用户、时间、模型、状态和请求/会话编号均作用于**请求事实**。会话进入结果的条件是“至少一条请求同时满足全部条件”，不能用一条请求匹配模型、另一条匹配异常而误命中。

例如按模型 A + 异常筛选：会话中只有模型 A 的正常请求和模型 B 的异常请求，则该会话不命中。

展开默认只展示符合当前条件的请求，并明确写“当前仅显示筛选命中的请求”。会话头部的已存请求数和异常数是**全会话已索引记录的汇总**，不得标成筛选命中数。提供“查看全部已存请求”操作，显式进入固定租户、固定历史用户和会话的明细，清除其他过滤并提示范围变化；返回恢复原筛选、页游标与滚动位置。

请求详情和原文权限不因会话存在而扩大。客户端父编号和请求参数均不能改变授权租户。

### 5.3 轻量会话索引

新增 `dsh_model_audit_conversation`，只存归组和计数，不存请求正文、消息来源数组或模型目录历史。

| 字段 | 用途 |
|---|---|
| `conversation_key` | 既有三元组派生键，作为稳定组标识；读取必须校验当前授权范围 |
| `tenant_id`、`user_id`、`conversation_id` | 历史归属及客户端声明原值；摘要命中后核验原值，不将摘要当授权 |
| `listed_at` | 首次创建该索引行时固定的服务端 UTC 时间，只用于目录稳定排序，后续永不改 |
| `first_request_at`、`last_request_at` | 已索引请求开始时间的最小值和最大值；迟到写入可更新，不参与目录排序 |
| `request_count`、`abnormal_count` | 已索引的全会话请求数和异常数；不包含完全失写的请求 |
| `updated_at` | 索引变更时间，展示索引延迟及排障，不是总体审计覆盖率 |

目录初版按 `(listed_at,conversation_key)` 倒序，用固定键翻页；页面明确标注“按会话首次收录时间排序”，不能声称按最近活跃排序。会话头同时展示最近请求时间，老会话出现新请求不移动目录位置。历史回填的 listed_at 是回填收录时间，不是客户端创建时间，同批历史会话的排序不表达其原始创建顺序。若后续确认必须最近活跃排序，需另设计共享快照或接受活跃会话移动造成的弱一致翻页，不能把简单 MAX 排序说成稳定快照。

建议索引：`(tenant_id,listed_at,conversation_key)`、`(tenant_id,user_id,listed_at,conversation_key)`，以及归组键的唯一约束。索引模型纳入租户自动注入注册，按双库字段及迁移约定实施。

### 5.4 投影更新不阻塞模型调用或审计原件落库

会话索引是可重建投影，不能让其写失败导致已经可保存的审计原件也回滚。

在请求表增加 `group_index_pending` 和 `group_indexed_status`：后者为空表示尚未计入会话汇总。新关联请求首次落库、或请求二态状态变化时，在原审计事务中仅标记待投影；不直接更新会话汇总。增加 `(tenant_id,group_index_pending,request_id)` 索引，通过现有后台调度执行独立的有界投影任务。

投影任务每批最多 100 条，先锁请求行再锁其唯一会话行：尚未计入时 request_count 加一；已计入时按旧、新二态状态调整 abnormal_count；以 started_at 更新最早和最近请求时间。最后同时保存 group_indexed_status 和清除 pending 标记，整段在**独立投影事务**内提交。摘要对应的 tenant/user/conversation 原值不一致必须拒绝归并并报警。

状态变化与投影通过同一请求行锁串行；重复执行不重复计数，迟到旧事件不覆盖新状态。会话首次并发创建的唯一键冲突只重试本次投影事务。正文分片增加但状态未变化，不反复锁会话计数行，避免高并发会话形成热点。

投影失败只保留待处理标记并重试，不阻塞模型、不回滚已提交的请求审计。会话目录与汇总允许短暂延迟；页面显示会话索引更新时间和延迟说明，提供“请求明细”降级入口。已关联但暂未投影的记录不能被伪装成未关联请求。

### 5.5 查询与性能边界

会话目录以授权租户内的会话索引表为外层，再用按会话键定位的请求 EXISTS 判断是否存在匹配请求。EXISTS 内的所有条件绑定同一条请求，并复用会话联合索引、时间范围及可选名称/状态索引。不对审计表在线 GROUP BY、DISTINCT、COUNT 全量会话，也不先取一页请求再由浏览器分组。

SQL 所需租户约束由既有 profile_scope 和自动注入产生；服务层不手写绕过租户过滤的查询。ORM 查询位于 Repository，授权和筛选语义位于 Service。

目录初版采用有界扫描预算：每轮先从会话索引按游标取至多 100 个候选，再用一次批量、限定这些 key 的 EXISTS 查询返回命中标记，不逐会话发 N+1 查询，也不能直接把 EXISTS 放在无界目录查询后面再 LIMIT 20。未用完的已扫描候选不能直接跨过：若本批命中超出剩余页容量，游标只前进到本页最后消费的候选，余下候选下次继续检查。单次请求最多检查 1,000 个候选且受查询超时约束。过滤条件稀疏时允许不足 20 条甚至空页，但只要还有候选，就返回最后消费位置的游标及 `scan_limited=true`，页面显示“本批未找到更多匹配，继续查找”，不能将其显示为“没有结果”。扫描预算用完不后台无限重试。

候选预算限制的是目录数量，不保证单个 EXISTS 的读取成本。实现阶段分别评估超长会话及稀疏模型/状态筛选；必要时为会话内模型、状态查询增加 `(tenant_id,user_id,conversation_key,model_name_digest,started_at,request_id)` 或状态对应索引，不能未测就声称任何组合都常数耗时。若真实数据仍不满足交互时延，需要更细粒度的查询投影或更窄时间范围；不退回无界大表聚合。

未关联视图继续按请求游标分页，使用 `association_status=UNASSOCIATED` 精确条件，建议增加 `(tenant_id,association_status,started_at,request_id)`。无模型或状态条件时走关联/时间索引，有条件时以执行计划选适当索引，不声称一个索引覆盖所有组合。

目录游标绑定授权租户、用户、全部已应用过滤、排序和初次查询上界；更换筛选重开游标。详情有独立游标。排序键不变可以避免活跃更新移动会话，但新提交、迟到数据和状态改变仍是实时数据，不承诺跨页数据库快照；刷新重新开始，前端按稳定键去重。不得把游标上界或本页水位宣传成完整覆盖率。

## 6 管理 API 增量

路径均位于 `/api/v1/dsh/admin/model-audit`，示例为解包后的业务数据，继续使用现有响应包装与管理员授权。

| 接口 | 增量契约 |
|---|---|
| `GET /models` | 保留按需目录搜索，新增完整名称去重；候选含 `name`，页面不再依赖 `id`。搜索长度上限与完整名称 2048 字符对齐，避免选中完整长名称后无法重新打开候选；输入和候选请求各自有长度校验 |
| `GET /requests` | 新页面只传完整 `model_name` 和可选 `audit_status`，支持未关联精确条件；返回二态状态及固定原因码；原四轴只在详情或诊断数据保留 |
| `GET /conversation-groups` | 新接口，接收已应用的用户、时间、模型、状态及定位条件，返回会话目录、next_cursor、scan_limited 和索引进度，不返回正文 |
| `GET /conversation-groups/{key}/requests` | 先验证组所属历史租户和用户，按当前已应用条件分页返回同组请求；参数不能覆盖组归属；响应含明确筛选范围 |
| `GET /conversations` | 保留现有指定用户和会话的请求分页语义，供“查看全部已存请求”与旧页面兼容，不改成目录列表 |
| 请求详情、父会话定位、`POST /requests/{id}/body-access` | 保持现有逐次授权、原文加密回读和先留访问日志语义 |

新会话接口通过严格查询 DTO 拒绝 model_id、四轴筛选和其他未知参数，避免框架默认忽略未声明参数。旧 `/requests` 的历史 ID/四轴参数仅在滚动发布兼容期保留，新页面不再发送；兼容期后清理前先核对所有调用方，不能用“页面不用”直接证明接口没有其他消费者。

请求例子：

```http
GET /api/v1/dsh/admin/model-audit/conversation-groups?tenant_id=1&user_id=1&model_name=volces%20%2F%20deepseek-v4-1-flash-260910&audit_status=ABNORMAL&start_at=2026-10-15T00%3A00%3A00Z&end_at=2026-10-16T00%3A00%3A00Z&limit=20
```

服务端先授权 tenant 1，将 model_name 原值计算为摘要，以同一请求同时满足用户、完整名称、异常和半开时间范围为命中条件，然后返回命中会话。时间始终筛选请求 started_at，不筛选会话 listed_at。

```json
{
  "items": [{
    "conversation_key": "<64位派生键>",
    "user_id": 1,
    "conversation_id": "session-a",
    "listed_at": "2026-10-15T12:00:01Z",
    "last_request_at": "2026-10-15T12:08:00Z",
    "request_count": 12,
    "abnormal_count": 1,
    "summary_scope": "ALL_INDEXED_REQUESTS",
    "request_filter_scope": "MATCHING_REQUESTS"
  }],
  "next_cursor": "<opaque-cursor>",
  "scan_limited": false,
  "progress": {"indexing_pending": true, "coverage": "OBSERVABLE_ESTIMATE"}
}
```

`indexing_pending` 应从已授权租户的待投影索引有界探测取得；无法探测时返回未知而非 false。不返回未经核验的全局待处理总数。会话状态若展示，按 abnormal_count 大于零判异常，范围明确为全部已索引请求，不是本次筛选；若对应请求已更新但投影滞后，详情状态暂时领先汇总是允许且应提示的。

## 7 发布与历史数据处理

1. 增加状态列、投影字段、会话表及索引，基于实施时唯一 Alembic head 编写双库迁移；DDL 不扫描回填，不删除旧索引或原件。
2. 新写入与巡检先部署统一状态计算及待投影标记，独立任务开始维护新会话索引；所有进程保持兼容旧 API。
3. 使用可断点、可预览、按租户分批的后台脚本补齐旧名称摘要、状态和待投影标记，再通过同一幂等投影路径收录历史会话。不得另写一条与实时路径不同的汇总逻辑。
4. 大历史租户不能以整租户长事务执行 COUNT/GROUP BY；通过分批已核验行数、已索引计数以及抽样归组核对建立回填结果。回填期间页面保留请求明细入口并显示索引建设中，不能称为全部会话。
5. 回填结束后至少完成一次从头补漏扫描，处理期间的新写入和旧行状态变化；再按租户开放会话视图与二态筛选。持续投影积压不要求等于零，但须显示可观测延迟并具备告警。
6. 前端切换新契约。回退时只退界面和消费者行为，保留审计事实、原件、密钥和可重建索引；不调整租户采集模式或请求主流程。

## 8 实施拆分与验收

| 阶段 | 改动范围 | 验收重点 |
|---|---|---|
| 第一阶段 | 模型移入高级筛选、可输入候选框、唯一完整名称查询路径、三语文案 | 不新增审计模糊查询；手填/选择行为一致；候选故障不影响手填 |
