## 1. 目标与用户故事

文档知识库并入知识空间。前台与后台操作同一资源、目录、版本和授权；后台补齐普通文件管理并承载高级处理能力，前台保留简化使用方式。存量资源可迁移，旧应用和调用方继续工作。

- 作为知识使用者，我希望从工作台访问同一份知识内容，后台更新后可以看到最新结果，已有文档引用继续有效。
- 作为内容维护者，我希望在后台管理多层目录、文件和版本，在移动、删除及批量操作前看清影响并取得逐项结果。
- 作为空间维护者，我希望集中配置模型和各文件类型的默认处理规则，查看处理任务并恢复失败项。
- 作为租户管理员，我希望从独立管理页签盘点本租户空间，同时保持普通授权列表的资源边界。
- 作为运维与集成维护者，我希望在一次维护窗口完成可核对、可恢复的迁移，并让既有应用及 3.x 调用无须重新绑定。
- 作为模型管理员，我希望删除前识别有效业务引用，避免删除仍被业务配置使用的模型。

**纳入**：PRD §1.1–§1.8，包括模型删除的业务引用保护；以及用户于 2026-11-03 追加确认的**全平台所有权限模型移除独立“使用（use）”动作，由可见性承担原使用准入**。QA 数据与产品入口保持独立，但其权限模型同样参加本次全局动作收敛。\
**排除**：QA 知识库合并、已退役个人文档库恢复、新切分算法、跨租户移动、前台高级配置入口、前台空间复制新入口、全平台审计改版、模型选择列表及高级参数改版、分享链接签发授权加固（2026-11-06 用户移出，另记独立待办）、新旧资源双写、文件 edit 动作适用范围扩展，以及 Worker 在途异步写入与用户后续修改之间的竞态一致性治理。正常重建冲突限制、任务幂等及配置/索引过期检查仍保留。标签、版本、相似文档按现有功能开关开放。

## 2. 需求口径与来源优先级

### 2.1 已确认的 D-01 / Q-01：全平台移除独立使用动作

用户于 2026-11-03 选择 Q-01 的 A，并进一步明确：“**所有的权限模型里都去掉了使用这个权限动作。不仅仅是知识空间**”。本次确认替代此前仅描述知识空间的范围：

- 全平台标准、自定义、预设及系统权限模型均不再提供独立“使用（use）”动作；原使用准入由资源可见性承担。已可见的主体可使用其可见资源，不再单独授予或检查使用权限。
- 覆盖知识库（包括 QA）、知识空间、工作流、助手、工具、托管应用、灵思 Skill 及其他资源模型；原本没有 use 的模型无需新增任何替代动作。
- 文件级可见性、主版本、处理状态、租户、凭证范围、有效身份及业务执行条件仍须满足；重命名、编辑、下载、删除、发布等其他动作不因使用动作移除而被授予，重命名继续校验独立的 rename 动作。
- 保留现有主体与可见范围。“原已可见但无 use”在转换后获得对应使用资格，属于本次明确确认的预期变化，记录对账即可，不再作为待业务裁定的迁移阻断。没有可见性的主体不能因为去掉 use 获得访问。
- 原来仅选 use 的权限模型及其有效授权，转换后仍须保持原可见性和可撤销性，不得因剩余具体动作为空而丢失授权，也不得为了保留授权而额外授予下载或编辑等动作。
- 图23及 §1.7 中“只有可见性不能用于应用检索”的旧说法被本确认取代。历史发布/审计快照可保留原文；当前生效模型及运行授权不保留可独立生效的 use。

### 2.2 已确认的 Q-04-2：模型引用仅按业务配置检查

用户明确选择：模型删除只根据业务绑定配置及仍生效的默认配置判断，不单独考虑任务和模型的绑定关系。任务通过所属业务资源/有效业务版本读取模型配置，配置已解除后，任务本身不再形成独立删除阻断。

本次确认替代 PRD §1.8 和前版草案中“运行中/可重试任务单独计为模型引用”的要求。任务处理记录与历史模型标识可保留作审计，但不作为模型绑定来源；文件解析/切分配置快照仍按原规则保留，两者不混同。

### 2.3 验收约定

Q-05 后续修订已确认：空间和模型配置有引用也支持显式强制删除；强删后保留原业务 ID/绑定为失效关系，手动修复，不自动改写业务配置。该结论替代前稿一律禁止强删的条款，清空规则保持。

下文采用 EARS 条件句。`系统应`对应 SHALL。完整 spec 已于 2026-11-05 获用户确认，作为本轮技术设计评审的需求基线；实现后仍须验证才能声称验收通过。D-01 / Q-01 的全平台范围、存量转换规则，以及 Q-02-1 的角色集合、Q-02-2 的租户范围及 Q-02-3 的完整管理操作及 Q-03 的清空保护规则、Q-04-1 的维护任务处置/脚本边界及 Q-04-2 的仅按业务配置检查模型引用已确认；其余验收要求亦已纳入本次完整 spec 确认；技术设计与实施验收分别处理。

## 3. 验收标准

### 3.1 入口、列表与前后台范围（PRD §1.2、§1.3.1）

- **AC-01** — 当用户进入知识管理入口时，系统应在前后台统一使用“知识空间”名称，并保留 QA 知识库独立入口。
- **AC-02** — 当用户从前后台访问同一空间时，系统应展示相同资源标识及同一份内容、目录、版本、成员和授权状态；另一端刷新或重新进入后应读取最新数据。
- **AC-03** — 当用户仅具后台菜单权限时，普通“知识空间”页签应仅列出其有权访问的资源；直接访问无权对象也不能取得名称及内容。
- **AC-04** — 当具备合法后台入口资格的平台超管或相应租户管理员进入后台时，系统应提供与“知识空间”“QA 知识库”并列的独立“知识空间管理”页签，展示当前租户全部知识空间。只有这两类管理员可进入；部门管理员、资源所有者、资源管理者及其他用户不得仅凭这些身份显示/进入该页签，也不得直接调用其管理清单取得全量数据，其普通资源访问仍按原授权执行。具体租户范围遵守 AC-05；管理操作遵守 AC-84。
- **AC-05** — 当用户在普通页签与管理页签之间切换时，系统应分别执行对应数据范围检查，不得通过普通列表请求获得管理范围；置顶不应成为后台可见条件。当进入“知识空间管理”时，超管应默认查看所属租户，并可切换到其他具体租户；租户管理员仅能管理所属租户。系统每次仅展示当前选定的一个具体租户，不提供跨租户汇总或空租户代表全平台的清单，直接接口请求也应遵守同一范围。
- **AC-06** — 当用户从前台创建空间时，系统应只提供名称、说明、共享、加入审批及广场发布等可操作项，并采用工作台现行默认模型和默认处理规则。Embedding 只在创建时复制为该空间自身的模型配置与引用；之后更换或清空工作台默认 Embedding 不修改已有空间，不触发已有空间重建。
- **AC-07** — 当用户从后台创建空间时，系统应预选与前台相同的默认模型，允许选择可用模型及按文件类型设置空间默认切分策略。
- **AC-08** — 当仅获某文件夹或文件授权的用户访问空间时，系统应只开放该授权范围，不因此开放整个空间或其他子项。

### 3.2 普通文件管理与批量操作（PRD §1.2.2、§1.3.2）

- **AC-09** — 当用户在任一端执行普通文件管理时，系统应支持多层目录、文件夹上传、文件上传、网页导入、预览、下载及重命名，并沿用知识空间已有目录深度、同层文件夹重名、文件格式和大小规则。
- **AC-10** — 当后台上传文件或新版本时，系统应形成与前台一致的版本关系和目录路径，保留历史版本；只有处理成功的主版本参与检索。
- **AC-11** — 当标签、版本及相似文档能力被现有开关启用时，两端应按同一开关及规则提供能力；相似文档可按现有规则预览、保留两份或作为新版本。
- **AC-12** — 当用户执行批量删除、下载、标签或重试时，系统应逐项校验权限及状态，列明无权、处理中和不支持的不可执行项。
- **AC-13** — 当批量请求存在不可执行项时，系统应先请求用户确认跳过；仅在确认后执行有效项并展示逐项结果，取消后所有对象保持原状。
- **AC-14** — 当后台用户执行上传等普通管理操作时，系统应与前台执行同一部门空间审批、内容安全、格式和配额规则。
- **AC-15** — 当用户从后台设置成员、权限模式、私有共享、加入审批或广场发布时，系统应操作同一空间并产生与前台相同的授权及业务结果。
- **AC-16** — 当用户从后台使用广场发现、加入、订阅、置顶或文件/文件夹问答时，系统应允许跳转对应前台页面；后台无需复制这些完整交互。

### 3.3 移动（PRD §1.3.3）

- **AC-17** — 当用户移动文件或文件夹时，系统应同时校验源对象移动权限及目标容器上传权限；跨租户、移入自身或子目录、超过现有深度和同名规则的移动应被拒绝。
- **AC-18** — 当用户提交跨空间移动前，系统应要求确认目标、版本、元数据和权限影响；取消确认不改变资源。
- **AC-19** — 当跨空间移动生效时，系统应一起迁移当前及全部历史版本，文件夹包含子项，并保留文件标识、版本关系及仍可用的引用。
- **AC-20** — 当文件移到目标空间后，图片、附件和原始文件应继续可访问；随后删除源空间不得损坏已移动内容。
- **AC-21** — 当源与目标具有同名同类型元数据字段时，系统应保留对应值；其余值仅在确认后清除，前台提示丢失风险、后台提供字段明细；源空间标签不带入目标空间，后续使用目标标签体系。
- **AC-22** — 当移动对象采用继承权限时，系统应使其跟随新父级；自定义权限应保留，子项分别保持自身模式；确认时说明继承范围改变及自定义授权保留。
- **AC-23** — 当跨空间检索迁移未完成时，系统应展示进度，并排除旧空间残留检索结果；完成后按目标模型提供检索。
- **AC-24** — 如果跨空间移动处理失败，系统应保留文件、版本和已确认的归属结果，允许重试同一次任务，不重复移动或创建版本。

### 3.4 复制与删除（PRD §1.3.4）

- **AC-25** — 当源空间创建者从后台复制空间时，系统应复制目录、文件、全部版本、标签、元数据及解析配置，生成独立资源、独立索引和独立任务状态；其他用户不能复制空间。
- **AC-26** — 当复制完成时，系统应使副本创建者成为所有者，按现行复制规范处理权限模式与普通授权，不照搬原创建者的受保护身份；复制前应说明授权复制范围。
- **AC-27** — 当复制空间时，系统应使副本默认不发布到广场，不复制订阅、置顶及聊天记录。
- **AC-28** — 如果空间或其中内容仍有有效业务引用，系统应默认阻止普通删除，展示类型、数量和有权查看的对象/入口；具有原操作权限者可按 AC-90 明确确认后强制删除空间。空间级绑定和直接文件引用均纳入影响检查，无权来源不得泄露名称或内容。清空仍须先解除有效引用；单独删除文件或文件夹遵守 AC-94，仅检查其实际删除范围的直接引用，不把空间整体绑定作为拦截条件。管理员及新旧入口遵守相同模式和权限。
- **AC-29** — 当仅存在历史对话引用或审计记录时，系统不应以此阻止删除或清空；确认须说明对应历史内容引用将不可访问，取消不改变内容。清空删除全部内容并保留空间本身；普通删除、强制删除、清空分别遵守 AC-28、AC-90–AC-92 和相应操作权限。

### 3.5 权限与应用检索（PRD §1.4、§1.7；D-01）

- **AC-30** — 当用户查看目录或预览时，系统应按目标对象的有效可见性授权；继承模式使用继承而来的权限，自定义模式使用本级自定义权限，不由业务入口另设模式分支。查看不得自动获得下载、编辑、移动、删除或授权管理能力。
- **AC-31** — 当用户创建文件夹、上传、重命名、移动、下载或删除时，系统应沿用现有各业务用例的授权目标和相应动作，不扩展文件 edit 的适用范围；文件及文件夹重命名继续校验目标 rename，不以 edit 替代或隐含授予 rename。继承/自定义由同一权限规则解析，不因本轮统一额外叠加空间编辑、单独文件可见性或其他动作。移动分别检查源与目标动作；资源存在、归属、版本、处理状态及 AC-94 的直接引用保护仍须满足。引用保护是业务条件，不是额外授权动作。
- **AC-32** — 当用户修改成员授权或权限模式时，系统应校验目标对象的权限管理能力；修改名称、说明和高级配置应校验空间编辑能力；私有共享、广场变更若涉及授权，还应校验权限管理能力。
- **AC-33** — 当用户通过网页调用高级功能时，系统应保持原后台入口资格及现有用例的授权映射；空间默认、模型修改/重建、元数据结构，以及原本按容器 edit 鉴权的高级重新处理/切分、Chunk 编辑/删除和文件元数据值修改，继续校验所属知识库/空间的 edit。已有文件重试、重命名等操作继续使用其原目标和动作，不统一改成文件 edit，也不新增文件 edit 适用范围。继承/自定义由同一权限协议处理，文件归属、版本和处理冲突仍须校验。
- **AC-34** — 当执行空间级模型或元数据结构任务时，系统应以空间编辑权限确定处理范围；详情只显示操作者有权查看的文件内容，其余只提供数量与状态。
- **AC-35** — 当开放 API、SDK 或 MCP 调用相关能力时，系统应校验现有凭证范围、有效操作者及资源权限，不要求服务账号拥有网页菜单，也不允许以此绕过资源鉴权。
- **AC-36** — 当有效身份可见空间时，系统应允许其选择该空间作为知识来源并使用该空间；具体检索仍只返回该身份可见、处理成功的主版本内容。
- **AC-37** — 当应用使用历史知识绑定时，系统应继续解释原绑定，无需重新绑定或重新发布；QA 仍单独选择。迁移前后应按相同身份、应用配置及问题核对可见文件范围与检索来源；已可见但原无 use 所产生的使用资格变化按 Q-01 记录为预期变化，其他非预期范围差异阻断切换。

### 3.6 默认策略及高级处理（PRD §1.5.1–§1.5.2）

- **AC-38** — 当后台创建、编辑或打开解析与切分设置时，系统应读取和更新同一份空间默认配置，并分别保存普通文档和表格规则。
- **AC-39** — 当配置普通文档时，系统应复用现有自动、自定义、层级切分能力及对应参数；图片、OCR、公式识别、页眉页脚过滤等选项只对既有支持类型提供。
- **AC-40** — 当配置表格时，系统应支持现有每段最多行数、追加表头及表头起止行规则，不套用普通文档规则，也不将某个上传文件的临时配置保存为空间默认值。
- **AC-41** — 当用户切换文件类型时，系统应保留各类型未保存输入；只有创建或保存成功后配置才生效，取消、校验失败和保存失败均不得修改已保存配置。
- **AC-42** — 如果配置不满足既有参数范围与格式，包括重叠长度大于分段长度、表头开始行晚于结束行，系统应拒绝保存并展示对应错误。
- **AC-43** — 当上传适用文件时，系统应优先采用显式批次或文件配置，否则继承对应类型的空间默认值，再使用现行系统默认值；专用网页及音视频规则保持优先，不展示或保存不支持参数。
- **AC-44** — 当修改空间默认配置或历史空间缺少配置时，系统不应自动重处理历史文件；既有文件应保留其实际使用的处理配置。
- **AC-45** — 当用户确认重新处理或重新切分时，系统应只处理指定文件；重新切分前应提示会覆盖该版本分段与人工调整。
- **AC-46** — 当用户编辑或删除 Chunk 时，系统应只更新指定版本检索内容，不修改原始文件。
- **AC-47** — 当新增元数据字段时，系统应使历史文件对应值为空；重命名或删除字段须二次确认并同步处理文件及索引；修改文件元数据值须展示对应检索更新的成功或失败结果。
- **AC-48** — 当显式修改某个知识空间自身的 Embedding 模型时，系统应先校验目标可用，二次确认后重建历史检索数据；模型重建及手动全量重建应复用现有分段和元数据并保留人工 Chunk 修改，重新解析或切分须独立发起。

### 3.7 异步任务及恢复（PRD §1.5.3）

- **AC-49** — 当提交模型重建、批量重新处理、元数据结构变更或跨空间检索迁移时，系统应提供可查询的任务记录；提交成功只表示已接收，实际索引处理完成后才显示完成。
- **AC-50** — 当任务执行时，前台应显示处理中、完成或失败等简化状态；后台应展示范围、实际进度、失败项及重试入口，并遵守 AC-34 的详情可见性。
- **AC-51** — 当模型重建进行中时，系统应保留目录、原文件预览和下载，暂停该空间检索并说明原因，同时暂停同空间上传、新版本、Chunk/元数据修改及移入移出等冲突操作。
- **AC-52** — 当某空间执行重建时，系统不应阻塞无关空间的正常操作。
- **AC-53** — 当任务部分失败时，系统应恢复成功文件检索、明确排除失败文件、展示部分失败及重试入口，保留原始文件、版本和权限，不使整个空间长期不可访问。
- **AC-54** — 当用户重试失败任务时，系统应在相关模型业务配置及索引处理范围未发生变化的前提下，沿用原任务恢复失败项，不重复生成文件、版本或授权；若模型配置或目标索引已被后续操作替换，应将旧任务标记为已过期，拒绝新启动处理步骤及提交陈旧任务结果，保留结果及失败项供查看，由用户通过新的重建流程处理。空间名称、说明等无关修改不使任务过期；恢复原模型仍须重新重建。该要求保留任务级过期检查，不涵盖已在途异步请求迟到与用户后续修改的竞态一致性治理。

### 3.8 存量迁移与配额（PRD §1.6.1–§1.6.3）

- **AC-55** — 当升级执行迁移时，系统应迁移存量文档知识库，继续保留已有知识空间；QA 不纳入文档空间迁移。
- **AC-56** — 当运维完成任务收尾并停止旧服务后，系统应在停服期间开展正式盘点与迁移预检，按租户核对资源、创建者、文件、版本、标签、元数据、模型/索引、授权、业务引用及运行任务记录，并在任何转换写入前冻结正式基线与转换计划。停服前的维护准备或工期估算不作为正式盘点结果或冻结基线。转换前已存在、原目标 ID 明确的失效引用应按 AC-93 保留并标记，不单独阻断升级；其他创建者缺失、配置解析歧义、非法跨租户关系、数据或模型/索引异常仍须处理。Q-01 的 use 预期变化单列；不得把迁移失败伪装为存量失效，也不得猜测主体或目标范围。
- **AC-57** — 当资源转换时，系统应保留资源及文件标识、原始文件、索引位置、模型、元数据及业务引用，不因类型转换重新切分或默认重建全部向量。
- **AC-58** — 当迁移文件缺少版本记录时，系统应补建首个主版本，已有版本不得重复创建；标签关联应同步转换且不重复。
- **AC-59** — 当迁移授权时，系统应保留原明确主体、可见范围及 use 之外的动作效果；原使用准入按 D-01 / Q-01 转为可见性，不新增全员可见范围；不得通过会清理授权的普通私有化操作完成迁移；迁移后默认不发布到广场。
- **AC-60** — 当资源尚未发布到广场时，系统不应因此禁止其合法访问或处理；广场发布、处理状态与授权应分别生效。
- **AC-61** — 当迁移空间计入配额时，系统应持续豁免其个人可新建空间数量，创建校验和配额显示采用同一口径，并保留按租户可核对的迁移来源；资源转换不增加文件存储用量。
- **AC-62** — 如果迁移使租户空间总数超过上限，系统应保留存量空间并限制继续新增；迁移后新增空间和文件仍须遵循现行个人、租户及部门配额规则。
- **AC-63** — 当执行正式迁移时，升级文档应明确要求依次完成任务收尾、停服及一致备份，再在停服期间正式盘点、预检、冻结基线与转换计划，之后执行转换及全租户验证，由运维统一恢复业务，不双写。运维负责停服、任务收尾、备份与恢复；迁移脚本只处理正式盘点、数据预检、基线/计划、转换、校验及检查点恢复，不检测是否已停服，也不启动、停止或等待服务。预检或冻结未完成不得进入转换；失败则继续维护，转换中断后沿原冻结基线和计划的检查点修复重跑，必要时完整恢复备份后再决定开放。
- **AC-64** — 当准备结束维护时，应以停服后、转换写入前冻结的正式基线核对资源/文件数量、版本、标签元数据、有效授权、配额、应用依赖、预览下载和抽样检索。各租户已核对的存量失效引用应与该基线一致，保留配置、标记、清单及受影响操作的明确失败，不要求这些既存失效配置在升级后自动恢复可执行。全部覆盖及迁移一致性检查通过才恢复业务，正常业务不因已登记的存量失效引用被整体阻断。

### 3.9 调用兼容（PRD §1.6.4）

- **AC-65** — 自 3.1.0-beta1 起，当调用方请求创建旧文档类型 `type=0` 时，系统应实际创建统一空间；QA `type=1` 保持原行为，新调用采用空间 `type=3`。
- **AC-66** — 在 3.x 内，当调用方使用旧文档列表、详情、创建、上传、复制、删除和检索等已支持能力时，系统应保留原请求方式、返回结构及旧类型表示，内部执行同一资源与规则；不得绕过删除保护、权限和处理状态。
- **AC-67** — 当使用旧资源标识查询或修改授权时，系统应解析到统一空间的同一份授权，不允许存在两套可独立修改的权限数据。
- **AC-68** — 当既有前后台、助手、工作流、工作台、托管应用、开放 API、SDK 和 MCP 解释旧类型标识时，系统应保持调用有效，并保留历史发布记录原内容；无需为兼容重写历史发布内容或要求重发。
- **AC-69** — 当规划退出旧调用兼容时，最早应安排在 4.0，实际停用仍须另行公告，不得在 3.x 提前停用。

### 3.10 模型删除的引用保护（PRD §1.8）

- **AC-70** — 当删除单个大语言、向量、重排、语音识别或语音合成模型、编辑服务移除模型、或删除整个模型服务时，系统应执行同一引用保护；服务删除须检查全部模型，并保持现有管理员准入、租户归属及共享服务只读规则。
- **AC-71** — 当检查模型引用时，系统应覆盖本规格 §3.15.1 列明的已保存业务配置、版本及默认槽位；即使草稿暂不能运行、助手或工作流下线、应用停止、频道同步暂停，只要配置仍保存引用便保留关系。工作流非当前版本及仍有管理预览入口的托管应用历史版本也计入；纯对话、审计和评测结果不构成模型绑定。运行、失败、排队或可重试任务不单独建立模型绑定或删除阻断。
- **AC-72** — 当删除共享模型时，系统应覆盖实际引用它的其他租户；无权展示的依赖在普通模式下仍阻止删除，强制模式下也必须计入影响确认，只返回依赖类型、数量及受限摘要，不因强制模式开放其他租户的删除权限或共享服务写权限。
- **AC-73** — 如果存在有效模型引用，系统应默认阻止普通删除，展示有权对象的名称、版本与入口，并指导先在业务中更换模型、调整默认或解除绑定；也应提供按 AC-90 确认后的强制删除。强制删除保留原业务配置及失效绑定，不自动清空配置、不静默切换其他模型。
- **AC-74** — 当知识空间更换向量模型后，普通删除应在必要重建和业务切换完成、原模型不再被有效配置引用后允许；用户也可按 AC-90 强制删除原模型，并承担相关空间/默认/版本配置失效的已确认影响，原任务冲突及状态规则仍生效。不因历史或可重试任务记录保留模型 ID 而阻止删除。
- **AC-75** — 当只存在历史对话、审计或仅展示的历史快照时，系统不应仅因这些记录阻止删除，并应保留已有名称及标识快照。
- **AC-76** — 当执行最终保存或删除时，系统应重新检查最新引用；普通模式下有引用则整次拒绝，强制模式下须核对已确认的目标及影响范围，发生变化须重新确认。任一模式遇检查失败、覆盖未就绪或服务异常，整次模型/服务修改均不执行，不得部分保存清单或配置。
- **AC-77** — 当通过任一前端、批量入口或旧接口执行模型删除时，系统应遵守同一规则；重复请求不得重复删除或误报成功。

### 3.11 全平台权限动作收敛（用户追加确认；D-01 / Q-01）

- **AC-78** — 当用户查看、配置或授予当前生效的任一标准、自定义、预设或系统权限模型时，系统应不再提供、保存或返回可独立生效的“使用（use）”动作。
- **AC-79** — 当有效主体使用知识库（含 QA）、知识空间、工作流、助手、工具、托管应用、灵思 Skill 或其他资源时，系统应按对应资源可见性确定原使用准入，不再要求独立使用授权；该主体仍须满足原有租户、身份、凭证范围、子项可见性、资源状态和业务执行条件。
- **AC-80** — 当迁移全平台权限模型和授权时，系统应按 AC-56、AC-63、AC-85 在运维停服及一致备份后正式盘点，冻结原主体、可见集合及非 use 动作效果，并纳入同一正式基线和转换计划；不使用维护前授权快照作为正式基线。迁移应保留原主体、可见范围、原 model_key、管理等级及 use 之外的动作选择，包含文件/文件夹的独立 rename 授权，不将其合并为 edit。旧文档库统一为知识空间时，同一模型按既有 SPACE 动作适用范围执行；默认 editor 的 create_folder/upload_file、manager/owner 的 share 等由资源类型切换产生的适用变化，以及原主体已可见但缺少 use 所新增的使用资格，应逐模型纳入正式计划与对账报告的已确认预期变化，不因此阻断切换。不得据此向自定义模型补入未选择的动作，纯 use 模型仍按 AC-81 仅保原可见与撤销；其他非预期差异阻断切换。
- **AC-81** — 如果权限模型原本仅含 use，系统应在移除该动作后仍保留其有效主体的原可见性、原授权来源和撤销能力；有权限管理能力的操作者应能通过原入口移除该主体的对应授权，不因剩余具体动作为空就将其判为不可管理。撤销一个来源只移除该来源的贡献，其他合法来源继续生效；不得删除有效授权、扩大主体范围或额外授予下载、编辑、删除等其他动作。
- **AC-82** — 当受支持的旧调用、历史配置或固定协议字段仍表达旧使用资格时，系统应按可见性解释兼容含义，不形成独立 use 权限来源；历史发布及审计快照保留原内容，当前运行规则按新语义执行。
- **AC-83** — 当上线全平台使用动作收敛时，系统应一致更新模型配置、授权展示、资源选择、调用入口及异步执行准入；任一旧入口不得继续独立检查 use 或通过遗留规则绕过可见性及其他限制。

### 3.12 管理页签完整管理（Q-02-1–Q-02-3 已确认）

- **AC-84** — 当平台超管或相应租户管理员通过管理页签操作当前选定的具体租户内资源时，系统应允许查看空间详情与文件内容、管理授权和配置、上传、移动、下载及删除；仍须执行配额、内容安全、部门审批、引用保护与任务冲突检查，不因管理员身份跳过这些业务条件。空间复制仍仅允许源空间创建者，不因管理员身份豁免；所有操作仍遵守 AC-04、AC-05 的角色及具体租户边界，清空的引用保护遵守已确认 Q-03 及 AC-28、AC-29。

### 3.13 升级期间任务处置（Q-04-1 已确认）

- **AC-85** — 当运维准备执行迁移时，升级流程应暂停受影响任务的新派发与启动，等待运行中任务自然完成，确认旧 Worker 无活跃写入后停止旧服务并完成一致备份，再在停服期间运行迁移脚本，先正式盘点、预检并冻结基线与计划，之后才执行转换；如果超过维护窗口预算仍未完成，应保持维护并交人工处置，不自动强杀或继续转换。排队任务应保留，在升级后校验通过再恢复；停服、任务收尾、备份和恢复由升级运维流程执行，不作为迁移脚本的停服检测或控制职责。

### 3.14 任务读取业务模型配置（Q-04-2 已确认）

- **AC-86** — 当任务执行或重试需要模型时，系统应从所属业务配置读取模型，并在任务领取、重试及可控处理步骤核对相关业务配置与目标索引是否仍适用；配置/索引已被后续操作替换则按 AC-54 拒绝陈旧步骤，不将新模型用于旧任务剩余项混合处理。无合法配置或目标已被删除时明确失败，不从任务参数/历史恢复绑定。该过期检查不建立任务模型引用、不阻止模型删除；文件解析/切分快照、进度和幂等恢复仍保留。Worker 在途异步写入与用户后续修改之间的竞态按 §1 的本轮范围排除。

### 3.15 业务绑定同步维护（验收要求已确认，实现方案待技术设计评审）

- **AC-87** — 当业务新增、修改/解除配置、删除、复制或导入涉及空间、直接文件或模型引用时，系统应由业务侧从最终有效配置提取完整引用集合，在保存业务配置的同一事务内同步新增、移除或更新绑定；任一失败整体回滚，重复保存不生成重复绑定，不允许仅删除绑定记录绕过仍存在的业务配置。
- **AC-88** — 当 §3.15.1 中实际业务配置及版本发生变化时，系统应独立维护对应来源版本的绑定；非当前、下线、停止或同步暂停本身不解除关系，暂不能运行的已保存草稿也保留。只有原配置槽位解除/改绑或来源通过既有业务操作被删除/失效时移除相应关系；工作流删除版本、助手删除/移除知识来源、频道解散/移除同步目标、空间或 QA 删除、默认模型槽位替换等按表执行，不新增通用版本退役功能。文件移动同步归属；清空保留空间模型绑定；任务不作为来源。
- **AC-89** — 当升级启用绑定查询保护时，系统应按 §3.15.1 同一业务口径回填全部已保存来源及版本，包含零引用来源和 AC-93 的已登记存量失效关系；已完整核对并标记的存量失效不是覆盖缺口。覆盖未就绪、检查异常或未解释的不一致不得认定无引用。并发保存与删除不得产生未登记引用或非预期失效，配置与绑定一起成功或失败；强删及存量已登记失效均保留供修复。

| 工作流及技能的已保存配置与版本 | 当前配置及全部未删除的已保存版本，含暂不能运行的草稿、非当前版本 | 删除整个工作流；成功删除非当前工作流版本；在某版本移除知识来源/相关节点、将模型 M1 改为 M2 并保存 | 下线、取消当前版本、缺其他运行参数；不把非当前版本称为仅展示历史 |
| 助手 | 当前模型及已选知识来源；当前没有独立助手历史版本退役能力 | 删除助手；在知识来源列表移除某空间并保存；替换助手模型 | 助手下线；不为助手虚构发布版本退役操作 |
| 托管应用 | 已提交冻结版本中的声明/注入引用，含当前、待上线、发布流程中的版本，以及仍有管理预览入口的历史版本；应用停止也保留 | 删除整个托管应用后解除其来源关系；新版本修改声明/注入只生成新版本关系，不清旧版本 | 被新版本替代、撤回/拒绝、仅在只读列表展示；历史版本仍可能管理预览，现有版本列表无退役/删除/回滚写入口 |
| 频道到知识空间同步 | 主频道/子频道保存的目标空间及文件夹配置，含同步开关关闭时保留的选项 | 解散频道；在同步设置中移除/清空目标空间或文件夹并保存 | 关闭同步开关、取消个人订阅；选定目标仍保存就保留关系 |
| 知识空间/QA 的模型配置 | 自身当前及仍生效的阶段切换模型槽位 | 删除空间/QA 使自身配置失效；更换模型且旧业务槽位真正解除 | 清空内容、停止任务、任务完成；模型重建切换前仍生效的原槽位继续保留 |
| 系统/租户默认模型配置 | 工作台/灵思、知识、助手、工作流和评测的已保存生效原始模型槽位，含 Root 继承来源 | 相应设置页更换模型；业务支持恢复继承时移除本租户覆盖，不移除 Root 原槽位 | 没有任务运行、消费者暂未使用；清除必填模型不作为新增功能 |
| 评测任务/报告、历史对话、审计 | 不作为独立空间/模型配置来源；评测模型由评测默认配置及被测业务配置承担引用 | 删除评测记录、对话或审计不释放其他业务/默认配置关系 | 不能因保留任务/结果记录就绑定模型，也不能把工作流/托管应用的可用版本等同于这些记录 |

本轮未确认存在可统一套用的“业务版本退役后仅供查看”状态，因此不按该泛称批量解除绑定。将来某业务提供明确的不可执行历史状态时，须另行规定其进入/恢复行为。日常维护、迁移回填和删除检查共用本表口径；本轮不扩展业务的删除、下线或版本管理功能。

### 3.16 强制删除与失效引用（Q-05 已确认）

- **AC-90** — 当知识空间删除或单模型删除、编辑服务移除模型、整模型服务删除存在业务引用时，系统应提供显式强制删除模式；默认仍为普通删除。强制模式须完成当前目标及引用影响的二次确认，沿用既有删除/编辑准入、租户及共享只读规则，不扩大权限；仅允许越过已知引用阻断，不绕过检查失败、覆盖未就绪、业务状态或任务冲突。清空不包含在本轮强制范围。
- **AC-91** — 当强制删除生效时，系统应保留引用方原 ID、版本和绑定，识别并展示“引用已失效”，空间直接文件关系也随空间删除失效。执行/发布或重新启用受影响配置时明确失败，不自动移除、忽略失效资源或回退其他模型；原可编辑来源/版本可保留未改动的失效槽位并逐项保存修复，剩余失效项继续提示且禁止执行/发布。不可变托管应用历史版本保持原内容，不为修复新增历史版本编辑或退役功能；任务不建立模型绑定。
- **AC-92** — 当用户修复失效配置时，系统应通过原业务槽位解除或改绑，按 AC-87 同事务更新对应来源/版本；强删失效和 AC-93 的存量失效都允许逐项保存修复，其他未变失效项继续保留，运行/发布仍失败。不同工作流版本独立修复或按既有删除版本操作移除；助手修改当前配置；托管应用新版本只修复新配置，旧历史关系保留直至来源按其生命周期失效。新建/复制/导入不得新增已删目标关系；原标记与来源对账保留，不自动清除或复活目标。

### 3.17 存量失效引用与文件删除保护（2026-11-04 已确认）

- **AC-93** — 当停服后的正式盘点与预检确认原目标 ID 明确、目标已不存在，并在转换写入前将其纳入冻结正式基线时，系统应保留原配置、版本和引用关系，标记“存量失效引用”，列入可定位来源的人工修复清单，完整回填和对账后允许升级；不要求新系统强删记录、不伪造强删历史、不自动解绑定或回退模型，详情保留并提示失效，执行受影响配置时明确失败，正常业务继续工作。仅因旧类型查询或转换错误造成的目标未找到不属于存量失效；配置解析歧义、非法跨租户关系和迁移自身不一致仍按既有失败规则处理。重跑沿用该停服后冻结的原正式基线与计划，不将本次脚本造成的不一致重新归为存量失效。
- **AC-94** — 当通过已有入口删除文件或文件夹及其实际涵盖的版本时，系统应检查本次实际删除对象及其内容/版本的直接业务引用；有直接引用则拦截该删除项并展示可见的依赖及解除入口，不能自动删除来源配置。仅绑定整个空间的业务不阻止日常删除其中普通文件；文件夹内任一待删对象有直接引用则整项文件夹删除不执行。混合批量请求按 AC-12、AC-13 确认跳过被拦截项，取消零修改，最终执行前复查新增引用。文件/文件夹不提供强制删除，不能通过强制参数绕过；仅检查目标对应删除动作并执行上述业务保护，无权详情继续裁剪。历史对话/审计不作为直接有效业务绑定。删除应复用知识空间现有的权限投影顺序，权限投影未成功不得先完成业务删除；成功后再提交业务删除并继续对象、索引清理，清理失败按原计划恢复。
