## 评估结论与证据范围

兼容旧Gateway的直接代码改动集中在两个聊天回写入口、会话归属恢复、会话建立顺序和共享前端请求范围资料。未修改Java、数据库结构或历史记录。该增量的代码范围较小；包含此前租户统一改造的整个版本仍需按业务链回归，不能只测这两个接口。

**当前不能认定整条聊天链路已完成兼容：首次拦截记录按主属创建后，如果同一会话继续在管理目标租户正常执行，存在会话重复创建及消息、会话归属不一致的风险。源码和隔离SQL已确认冲突机制，真实旧Gateway/browser触发时序尚未验证。应先闭环该问题，再把完整聊天兼容判为通过。**

源码范围：codex/3.1.0-beta1/optional-gateway-compat工作区（含未提交新文件），基线089e152db046237e30a2115fe2e5600a2d16188d。Gateway调用协议核对基线62399806，非现场镜像证明。此评估只新增文档与验证记录，没有修改业务代码、部署或写入业务环境。远端连接刷新未成功；合入前仍需核对最新发布线。

QA指测试验收。文内优先级：发布前必须通过、重点回归、补充验证；主QA表保留项目模板的P0（发布前必须通过）和P1（重点回归）。本轮验收标准为AC-60、AC-61、AC-62、AC-63、AC-64、AC-65；此前统一租户范围见AC-41至AC-59。

## 历史数据和可见性

- 零新增表、列、迁移，不搬迁历史资源、消息、账号、角色或授权；不把创建人的主属反推成资源租户。
- 无会话的首次拦截按真实主属。Root超管管理甲租户时产生的首次拦截记录在Root，而非甲；不能将甲视图看不到该记录直接报为丢失。已有甲会话的第一次拦截仍属于甲。
- 他人/已删除会话、独立API会话、孤儿消息、未知归属、消息与会话租户或应用不一致、已停用租户会被拒绝。历史行保留，但原来可以错误写入的路径可能不再可写。历史用户主属已变化的普通用户，不能继续按旧租户回写。
- 已有消息的回写是对原记录的修正，不等于重新执行应用。当前实现对已有会话不重新要求应用可执行；首次无会话则需要应用存在、未删除且有使用权限。
- 旧Gateway敏感词配置和部门限流存储、缓存、计数均未改。页面范围不等于后端授权；旧直连接口既有授权缺口仍未解决，不能作为已通过项目。

## 当前发现的首要风险

### 首次拦截后继续同一会话

条件：真实主属Root的超管管理甲租户；拦截发生时不存在持久会话，因此本轮POST建立Root会话；后续正常工作流沿已验证的甲租户执行，且继续使用原chat_id。

[工作流正常消息保存](../../src/backend/bisheng/worker/workflow/redis_callback.py)的RedisCallback.save_chat_message先写消息，再按当前范围查会话；查不到时创建会话。Root会话对甲租户的自动过滤查询不可见，复用同一全局唯一chat_id可能触发重复主键；先前的甲租户消息可能已经提交。[助手正常保存](../../src/backend/bisheng/common/chat/client.py)的ChatClient.add_message也需覆盖首次拦截后的同连接和重连行为，不能只验证回写接口。

本轮在一次性SQLite中复现了上述存储机制：首次Root会话成功；在甲租户查询该会话返回空；甲租户消息可先提交；再创建同chat_id的甲会话出现唯一键冲突；最终出现Root会话关联两种租户消息。这是隔离机制证明，不是已经跑通真实WebSocket时序的端到端复现。验证脚本在/private/tmp/test_optional_gateway_continuation_probe.py，输出在/private/tmp/optional-gateway-continuation-probe.log，未触及现场数据。

建议：在毕昇侧把正常聊天写入与拦截回写的会话衔接闭环，不能静默改首次主属或搬迁已有会话；在闭环前不宣称完整兼容。具体采用继续原会话还是显式交接新会话，须由修复设计明确，不能由QA自行假定。

### 其他重点

- **页面提示不代表落库成功。**旧Gateway敏感词回调可能只记录后端响应，仍向页面发送拦截内容；必须刷新重读并核对消息/会话，不能只看页面或HTTP 200。
- **分步提交与重试。**新建会话、审计/遥测、消息对、违规状态不是同一数据库事务；超时或后续失败可能留下空会话、重复消息或状态不一致。代码没有新增幂等保证，不能按“重试必然只写一次”验收。
- **首次校验增加依赖。**新增会话首次回写还会执行原使用权限判断，需验证权限服务不可用、应用半成品、失权等情况不会变成错误放行。
- **时延。**修改回写前增加消息、会话、租户状态三次窄定位；首次新增还有孤儿检查、应用定位和权限调用。查询使用既有主键或会话编号索引，但现场仍需测数据库往返、长连接响应时延和失败恢复，不能仅以SQL条数推断性能达标。
- **限流提示的原协议。**核对的旧Java限流超额分支直接返回提示并关闭连接，不走该敏感词POST保存路径。不要把原本没有落库的限流提示判成本轮新增回写回归；真实版本若行为不同，按实际调用链补测。

## 测试环境与执行顺序

至少两种拓扑：不部署Gateway，以及保持实际旧Gateway镜像和原配置。记录准确镜像/提交，不能只写“旧版”。使用同版本Platform、Client、Python、Worker及隔离的MySQL/DM8测试环境；新Java独立分支不是前提，若单独启用则增加组合回归。

准备：主属Root且可管理甲/乙租户的超管；甲、乙普通用户和租户管理员；甲主属兼属乙部门人员；Root共享助手；甲/乙工作流；已有甲会话；专用已删/孤儿/冲突样本。账号和数据使用e2e-f009-标记，损坏记录只在可控非业务测试库构造；测试前后保留按编号的归属、数量、内容和状态快照，清理仅本批数据。

1. 先测两种拓扑的登录、自举、普通用户及超管子租户核心资源创建；同时测试流式与长连接路径。
2. 优先闭环“首次拦截→修改输入→正常继续→刷新历史→重连”，分别覆盖工作流和助手、同租户及主属不同于管理目标的超管。
3. 再测已有会话拦截、输出拦截的流式/非流式PUT、切换后延迟回写及普通用户Root共享资源。
4. 测匿名、过期、撤权、伪造编号、他人/已删/API会话、错误租户、孤儿及停用状态；每个允许路径配对一个拒绝路径。
5. 测故障注入、超时重试、旧配置页面切换与直接接口既有边界；最后完成此前统一租户改造的业务链回归。

成功必须同时满足：页面反馈正确、重新查询仍正确、消息和会话归属一致、无跨租户副作用。拒绝必须同时满足：错误可定位、数据数量/内容/归属不变、后续合法请求不受残留上下文影响。
