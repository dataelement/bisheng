# BiSheng 3.0 产品方案：应用工场

> 版本：v3.0（2026-07-24）　状态：待评审；已纳入资深架构师技术架构 review（见同目录 review 文档）；评审通过后进入 release-contract + SDD 拆解

## 0. 摘要

**BiSheng 3.0 让不会编程的业务人员在平台里对话式造应用，并让每一个应用天生长在企业治理之内。** 三句话说完：

1. **造**：浏览器内「对话 + 实时预览 + 一键发布」的造应用工作台；引擎复用开源 coding agent（可替换适配层，不自研不绑定）。
2. **接与跑**：应用跑在平台沙箱运行时；经统一的企业能力总线接入企业的知识库、模型与身份（能力总线的技术构成见 §3.4）——生成的应用天生认识组织架构和权限。
3. **活与管**：每个应用绑定一个常驻**应用管家**——造它、改它（发布后迭代 = 继续对话）、守它（定时解读数据、主动预警）；发布审批、权限、配额、审计默认在场。（「守」态本版先定稿规格 + 预留数据表，运行时是否本版落地待定夺，见 §3.2/§5.4）

## 1. 背景与痛点

### 1.1 背景：应用生产方式正在换代

- **对话取代画布**：字节把扣子的拖拽画布整体撤下，换成对话式生成（扣子编程）；百度秒哒 8 个月生成 50 万应用、81% 用户非程序员；美团 NoCode 非技术岗使用者是技术岗的 3 倍——「说需求出应用」已被市场验证，且主力用户是业务人员而非开发者。
- **企业侧同样成立**：招商银行低代码体系年新增应用 2831 个、59.4% 出自业务人员——但银行对 AI 编程明确「审慎」（技术债与治理顾虑）。
- **引擎已是公共品**：Qwen Code / Codex CLI（Apache-2.0）、Kimi Code CLI（MIT）等开源 coding agent 成熟且可自由内嵌，平台不必自研引擎。

**结论：应用的稀缺环节不再是「会不会造」，而是「有没有一个带企业上下文、有治理的地方去造和跑」。**

### 1.2 痛点：业务人员的三个诉求 + IT 的一个焦虑

来自内部用户/客户的真实原声：

1. **「我能不能直接在 bisheng 上 vibe coding，把企业的用户体系、知识库、数据都接进应用里？」**——想造，但缺一个带企业上下文的地方（主诉求）。
2. **「我用 Claude Code 在本地开发了应用，希望部署到 bisheng 让大家访问；应用不稳定，但平台要正常。」**——造完了，没地方跑、没人能访问。
3. **「应用搭好了，需要一个 agent 持续为我解读、分析、预警。」**——跑起来了，还想让它自己会看数据。

IT 侧的焦虑是 shadow AI：员工绕开 IT 用公共 AI 工具造应用 → 数据外泄、无人运维、审计缺失。IBM《Cost of a Data Breach 2025》：20% 数据泄露事件涉及 shadow AI（均损 $4.63M）；Lovable 生成的 170+ 应用数据库对匿名请求裸奔（CVE-2025-48757）。**「与其堵，不如给一条有治理的路」——这是 IT 部门愿意引入本能力的根本理由。**

### 1.3 市场空档

| 玩家 | 现状 | 空档 |
|------|------|------|
| 扣子编程 | 对话式造应用 + 一键托管，形态最完整 | **只在云端 SaaS**，私有化无供给 |
| Coze Studio 开源版 | 无 vibe coding / 托管能力，2026.02 更新放缓 | 开源侧留白 |
| Dify | 纯配置式工作流范式（DSL） | 无代码应用生成/托管信号 |
| Lovable / bolt / v0 / Replit | UX 机制成熟（本文大量借鉴） | 公有云 SaaS + 安全事故频发 |
| Databricks Apps | 验证「平台托管内部应用」的真实需求（正式发布前半年即 2500+ 组织 / 2 万应用） | 绑定自家数据栈，不做国内私有化 |

**「私有化环境下的对话式造应用 + 托管 + 治理」目前无人占位；扣子在教育市场，窗口在收窄。**

## 2. 产品定位与设计理念

### 2.1 定位

```
BiSheng ≤2.6：平台即 IDE —— 应用用画布在平台内搭，表达力受画布上限约束
BiSheng 3.0 ：平台即应用工场 + 运行时 —— 业务人员对话式造应用，
              应用跑在平台沙箱里、接着企业的知识/模型/身份、由常驻管家照看，
              治理默认在场
```

差异化判断：**引擎是公共品，竞争在「壳」**。对话生成应用的能力，各家很快都会有；但应用要真正在企业里活下来，需要的是身份与权限、知识库与数据、审批与审计——这些恰好是 BiSheng 已经建成的部分，而 Lovable/扣子们要么没有、要么短期给不出私有化供给。生成的应用在 BiSheng **天生认识企业组织架构、天生长在治理之内**，这是本方案真正的护城河。

### 2.2 设计理念（三条）

**① Vibe with the agent, not the code —— 应用管家。** 业务人员相处的对象不是代码，而是一个长期存在的 agent；代码只是它的产物。每个应用绑定一个管家，贯穿三种状态：

- **造**：从一句话需求开始，澄清、生成、预览、发布；
- **改**：发布后迭代 = 继续对话（「把导出加个 Excel 格式」），管家在草稿沙箱改好、预览确认、点更新上线——业务人员永远不需要「打开工程」；
- **守**：设定巡检节奏后，管家按时间或事件唤醒，解读应用数据的增量，值得说才说，把 30 秒能读完的简报推到企微/飞书/站内信。

造它的、改它的、守它的是同一个 agent，**会话随应用终身存续**、上下文零移交——这是对「session 用完即弃」类产品的结构性差异。

**② 引擎复用，不自研、不绑定。** coding agent 是快速演进的公共品，自研必然落后；绑定单一引擎则被别人的断代绑架。平台通过可替换的引擎适配层（§4.2）驱动开源 coding agent，默认引擎可按租户配置、可随生态演进更换。

**③ 平台管安全，AI 只管功能。** 「让 LLM 生成正确的鉴权代码」被证明不可靠（Lovable 170+ 应用数据库裸奔），扫描器也只能查有无、查不出对错。BiSheng 不把安全押在「AI 写对代码」上，而是由平台运行环境强制保障：生成应用默认仅企业内可见、所有流量过平台身份网关、数据访问走平台注入的租户隔离连接、沙箱出站白名单、发布走审批。AI 生成的代码只负责业务功能——写得再差，也越不过平台划定的安全边界：代码里没有裸连接串，也没有自己发明的登录。

### 2.3 目标用户与核心旅程

| 用户 | 要什么 |
|------|--------|
| **业务人员**（主用户，非程序员） | 把脑子里的表单/看板/小工具变成同事能用的应用，不学编程、不等排期 |
| 平台管理员 / IT | 业务自建应用看得见、管得住、出事能兜底 |
| 业务技术员（会用 Claude Code 的少数派） | 本地开发的应用部署到平台给大家用 |
| 普通业务用户 | 在应用广场找到并直接使用同事造的工具 |

一段旅程：销售运营专员说「做一个销售周报看板，数据用上周台账」。管家澄清两个问题后开始工作，她看着右侧预览成形，中途说「大客户单独列一栏」——管家查了知识库里的口径改好了。点发布、主管审批，同事用企业账号直接打开，各自只看到自己权限内的数据。一个月后她说「每周一早上把异常客户推到企微群」——同一个管家接下了这活。**她全程没看过一行代码，但代码一直都在那里，IT 全程可见可审。**

## 3. 产品功能结构

```
应用工场
├─ 造应用工作台     对话 + 实时预览 + 发布（业务人员主界面）
├─ 应用管家         造 / 改 / 守 三态一体的常驻 agent
├─ 应用运行时       沙箱托管、统一入口、版本回滚（草稿与生产同一套设施）
├─ 企业能力总线     API key · 双协议模型代理 · MCP Server · SDK
├─ 治理面           发布审批 · 权限 · 配额 · 审计 · 日志
└─ 专业开发者通道   CLI 部署旁路（本地开发的应用走同一管线）
```

### 3.1 造应用工作台

核心机制（取六家对标产品的收敛范式，结合 BiSheng 独有优势）：

| 机制 | 规格 |
|------|------|
| 一句话起步 + 澄清前置 | 写码前先「梳理需求 → 确认要点 → 匹配平台资源（知识库/数据表）」，避免零碎指令越改越乱；澄清交互**以选项式为主**——管家把问题连同候选答案一起给出，业务人员点选即可，尽量不要求打字描述技术细节，且一轮问完、数量有界（复用灵思任务模式澄清环与选项式提问的成熟经验） |
| 三分区工作台 | 对话 + 实时预览为主界面；代码是可选玻璃盒——可见、可改、但不必看（纯黑盒出问题没有逃生通道） |
| 想 / 做分离 | 规划态（只讨论不改码）与执行态显式区分 |
| 每轮自动存档（含数据） | 每次改动自动快照 = 代码 + 对话上下文 + 应用数据库；**草稿/代码回滚无损**（生成新版本卡、历史可重放），**生产数据默认不回滚**、schema 演进需迁移策略（回滚语义见 §3.3） |
| 修错免费 + 报错一键回流 | 「帮我修」不额外计量；报错/截图一键贴回对话（SaaS 按 token 计费的 bug-loop 是全行业最大口碑杀手，私有化部署天然免疫） |
| 基础组件平台自带 | 数据库/对象存储/登录/权限这些基础组件由平台提供、开箱即用，**不让 AI 从头写**：应用数据库 = **平台托管、按 app 独立**（小档 SQLite-per-app / 中档 Postgres schema，与平台 MySQL·DM8 解耦——生成代码不认 DM8 方言，故不复用平台库；单文件 SQLite 顺带简化每轮存档，租户隔离连接注入）；登录与权限 = 平台身份桥接，生成应用天生认识组织架构（如何递到管家手里见 §4.4） |
| 自动数据后台 | 业务应用大多是「表单 + 列表 + 看板」——生成应用自动附带数据管理页（查/改/导出/回溯） |
| 草稿 / 生产分离 | 管家只碰草稿沙箱；「发布」才产出独立生产实例；线上回滚与草稿存档是两套、都要有 |
| 预置模板起步 + 组织模板库 | 不从空白生成：**首发 6 类模板**——信息收集上报 / 业务台账 / 检查整改闭环 / 数据看板+AI 解读 / 知识问答页 / 轻审批·督办跟踪（经通用模板市场实证 + 央国企场景两路调研定夺，详见附录《预置模板首发清单调研》）；每个模板 = 「一张表+一条流+一个看板」的微应用，不做行业大套件；同事造好的应用可一键复刻到自己空间再改，可见范围走权限体系——好应用在企业内自发扩散 |
| 逃生梯度 | 报错回流 → 代码玻璃盒 → 导出工程；后续版本加点选局改（Design Mode 式） |

### 3.2 应用管家

- **造 / 改**：见 §3.1；**管家的会话随应用终身存续**——工作区快照 + 对话历史与应用绑定存储，不随发布、容器回收或时间流逝而丢失；应用创建三个月后回来提一句需求，管家仍带着全部上下文接得住。
- **守**（持续看护上线应用）——本版先把「守」态的规格定稿并预留数据表；**是否在本版就实现，待定夺**：建议等开发进入后半段、按剩余人力决定，不足则顺延 v3.1（见 §5.4）。**底层依赖一个新建的平台触发/调度子系统**（cron/webhook 触发器、常驻生命周期、预算闸、机队观测）——灵思 worker 是一次性会话模型、丢弃终态队列项、无 cron/webhook、默认 compose 都不起，非直接复用；管家是该子系统首个消费者，工作流定时/知识库定时同步同样可复用（见 §4.6）。规格如下：
  - 触发：定时（cron）+ 事件（webhook）——由平台触发/调度子系统提供（新建）；
  - 省钱：数据探测零 LLM（与上次游标比对，无增量不唤醒模型）；使命进 system prompt，每次唤醒只注入增量元数据（token 成本不随运行次数膨胀）；
  - 降噪：两级过滤（有没有新 → 值不值得打扰）；每次唤醒只发一份合并简报（一句话结论 + 分条信号 + 建议动作）；无信号绝不发「本轮无事」；宁少报不多报；
  - 推送：经**新建的通知服务**发出——站内信（现有）+ 企微/钉钉/飞书群机器人 + 通用 webhook（借 workflow 群机器人 webhook 逻辑；org_sync 仅入站目录同步、无外发能力，平台今日无通用外发通知服务）；**收件人创建时锁定，agent 不得动态选择**；
  - 成本：创建时出示花费预估（巡检频率 × 模型）确认后生效；预算上限超限自动暂停；
  - 观测：看护总览面板（状态灯 / 上次运行 / 累计花费 / 简报历史）；简报卡片可嵌入（iframe）到第三方系统页面。

### 3.3 应用运行时与发布

- **应用包规范 `bisheng-app.yaml`**（发布时由管家自动生成）：

```yaml
name: sales-weekly           # 入口路径 /apps/sales-weekly
runtime: python3.11          # python3.11 | node20 | static
entry: streamlit run app.py --server.port $PORT
capabilities:                # 声明式能力申请，审批即授权
  knowledge: [kb_123]
  models: [qwen3-max]
  secrets: [webhook_token]   # 应用级密钥引用；值存平台 secret store（Fernet），注入同 capabilities
appdb: sqlite                # sqlite（小档，单文件）| postgres（中档，独立 schema）
resources: small             # small | medium 固定档位，杜绝配额博弈
```

- **统一入口**：`/apps/{slug}`，同事免二次登录直接访问；应用广场与工作流/助手并列呈现。
- **稳定性承诺**：应用容器与平台进程零共享，单应用崩溃只自愈该容器，平台与其他应用不受影响。
- **版本与回滚**：每次发布生成版本记录，一键回滚——**代码/配置回滚无损；生产数据默认不回滚**（有状态生产应用回滚会丢回滚点后的数据），republish 涉 schema 演进需策略（仅增列 / 迁移前快照 / 人工确认）。
- 本版不做：k8s 多机、公网域名、应用间编排、GPU、自动扩缩容、Dockerfile 自定义构建。

### 3.4 企业能力总线

- **API key 体系**：个人 key（本地开发者）/ 应用 token（发布时按 capabilities 签发）/ 会话 key（工作台沙箱随会话吊销）；scope + 配额 + 可吊销；替换现有 v2 开放 API 的「内网可信」模型。
- **双协议模型代理**：对外暴露 OpenAI 兼容 + Anthropic 兼容两个协议面，任何讲两种协议之一的引擎（含客户自装的 Claude Code）都能直连平台托管模型。做 Anthropic 面的依据：DeepSeek/智谱/Kimi/Qwen/MiniMax 五家均官方提供 Anthropic 兼容端点，该协议已成国产模型事实第二标准。**实现上采用现成开源代理（LiteLLM / one-api 类）承载协议面，不自研 Anthropic `/v1/messages` 长尾**（content blocks / tool_use / SSE / thinking / prompt caching 语义）；**BishengLLM 退居 provider 路由的唯一真相**（现成代理经其**自定义 provider/回调扩展点**调用 BishengLLM 解析租户模型配置与端点——BishengLLM 只提供解析、不自建 HTTP 面；LiteLLM 可作库内嵌 backend、one-api 类可独立进程，二者皆经此扩展点回连，不重实现、防两层漂移）。三个必钉约束：① license 核查（LiteLLM 企业功能单独授权、商业私有化须确认；one-api/new-api 为 MIT）；② 记账回流一处（外部代理 per-key 用量喂回 `llm_token_log`/配额——现记账是 `on_llm_end` 按叶子租户、须补 per-key 归属，避免两套账单）；③ 与 §4.3 auth_profile 三路径协同。平台今日无此模型网关代理（现有 `/api/v2/assistant/chat/completions` 是按 UUID 分发到 Assistant、非裸模型透传）。
- **BiSheng MCP Server**（streamable HTTP，key 鉴权，scope 过滤）：知识库检索、模型清单、用户身份/组织查询、应用数据库 schema/查询（管家迭代应用时用）、应用状态自查；数据语义层（本体）查询作为后续扩展方向。平台自己的灵思/助手/工作流同样可消费——内外同源。
- **bisheng-sdk**（Python 首发）：auth / retrieve / chat / storage / appdb 五件套薄封装，模板预接线。

### 3.5 治理面

- 应用/工作台会话/管家均为权限体系（OpenFGA）资源类型，授权复用现有通用授权交互；
- 发布走审批中心（F025 新场景）：capabilities 变更、可见范围扩大触发重审；
- 全链路审计（谁造了什么、接了哪些知识库、谁在用）、按 key 的用量账单、租户级容器与 token 配额；
- **引擎与模型接入统一由管理员配置**：用哪个引擎、走平台模型代理还是客户订阅、凭据档案的创建与分配，全部是管理面决策（§4.3），业务人员零感知；
- 灰度手段：应用工场按租户/用户组开关。

### 3.6 专业开发者通道（旁路）

`bisheng` CLI（init / deploy / logs）+ 应用模板 + `.mcp.json` 预配置：本地用 Claude Code/codex 开发的应用，经同一发布管线、同一审批与治理上平台——本地造的和平台造的，在治理面前无差别。客户自装 Claude Code 时经双协议代理连平台托管模型、经 MCP 接企业上下文。

## 4. 技术架构方案

### 4.1 总体架构

```
业务人员浏览器（对话 + 预览 + 玻璃盒）
   │ WS/SSE（归一化事件流）
BiSheng backend（编译期/运行期零 docker 依赖，arch-guard 加 import 禁令强制）
   ├─ vibe_builder 模块：会话编排 / 引擎适配层 / 快照恢复 / 发布编排
   ├─ open_platform 模块：API key（三类）/ OBO token / 配额
   ├─ 模型代理（现成代理 LiteLLM/one-api 承载协议面 + BishengLLM provider 路由）
   ├─ mcp_server 模块：平台能力 MCP 化
   └─ app_runtime 模块：manifest 生成 / 向 runtime-manager 下发期望态 intent（声明期望、不直连 docker）
runtime-manager（独立最小权限编排器，唯一持 docker 访问）
   ├─ intent 驱动 reconcile：构建 / 容器生命周期 / 日志探活 / 崩溃自愈
   ├─ 准入控制 · idle 回收 · 并发上限 · cgroup 硬隔离（容量/密度治理）
   └─ 沙箱容器（草稿态与生产态同一套设施）
        ├─ 草稿：引擎 CLI + 工作区 + dev server（预览经 /apps/preview/{session}/）
        └─ 生产：应用容器（/apps/{slug}/）
app-proxy（版本无关鉴权代理，唯一暴露 /apps）：验会话 + 签 OBO + 注入头 + 反代容器，支持 WebSocket
   └─ nginx（开源）与 Java 网关（商业）都只把 /apps 转发到它——安全逻辑一处实现、不随部署形态分叉
```

工作区与会话持久化：**每轮修改自动存档 = 工作区文件 + 对话上下文 + 应用数据库**，统一落 MinIO 并与应用绑定——这既是工作台「回滚」的承载，也是「管家会话随应用终身存续」的承载：容器随时可回收，回来即恢复。**承载方式据实**：灵思 workspace 是 per-file write-through 对象缓存（非时间点快照），无法直吃 builder 工作区的 git + node_modules（万级小文件、git 语义），故须**新增 tar/bulk-snapshot 层**（应用库选单文件 SQLite 后，数据部分的存档简化为「tar 一个文件」）；「无损」限定草稿/代码，生产数据回滚语义见 §3.3。前端归属：工作台放 client（业务人员所在 SPA，初版交互稿：https://claude.ai/design/p/8e7bca96-b23b-4901-9468-80ad5bbad5e9?file=%E5%BA%94%E7%94%A8%E5%B7%A5%E5%9C%BA+Demo.dc.html&via=share ），管理面放 platform。

### 4.2 引擎适配层与选型

**RuntimeAdapter 抽象**（Python），按「CLI 进程 + JSONL/JSON-RPC 事件流」建模：

- 统一 `run(RunConfig) → {sessionId, text, structured, usage}` 契约；公共必备只有 run()，undo/compact/steer 按引擎能力可选——差异不抹平、在上层显式分叉；
- 流式事件归一化为五类（text_delta / thought / tool_use / tool_input_delta / tool_result）上抛，前端渲染与引擎解耦，换引擎不动 UI；
- 引擎可用性探测 + 依赖注入；引擎选择同样是管理员配置的结果（用户组覆盖 > 租户默认 > 平台默认），业务人员不感知引擎；
- 模型与凭据：适配层不关心引擎用什么模型、以谁的身份跑——统一由「凭据档案」承载（见 §4.3）；
- 指令单一来源：CLAUDE.md/AGENTS.md 软链或编译，避免多引擎指令漂移。

**引擎矩阵（2026-07 调研 + 对抗验证，一手来源核实）**：

**Wave-0 PoC（先测后定）**：薄版 adapter × {Qwen Code, Codex CLI}（Kimi Code 可选 spike）× {GLM-5.2, DeepSeek-V4, Qwen3.7-Max}（经平台代理）× 3 个代表性造应用任务（取自首发模板：信息收集上报 / 数据看板+AI 解读 / 知识问答页）。评测口径不止「单发成功率」——**真正的失败模式是「demo 能跑、多轮飘」（tool-calling 可靠性经翻译层退化，灵思已踩过），单发任务测不出，故须含多轮鲁棒性口径**（连续修改/纠错下的稳定性）；按成功率/多轮鲁棒性/轮次/token 成本设**量化 go/no-go gate** 定默认引擎。**同时把「模板生成器」纳入 PoC 作对照基线**——「业务应用大多表单+列表+看板」意味着模板/DSL 可能不止是 fallback、甚至该是主干、coding agent 作逃生梯度；引擎 vs 模板的主次由 PoC 数据决定、不预设。**引擎在国产模型上的实效是全案最大技术未知数；若结论是「无任何开源 coding agent 能在国产模型上稳定多轮驱动造应用」，模板生成器即成主干退路——「不自研引擎」原则本身没有退路（Claude Code 永不内嵌）。**

### 4.3 引擎凭据与模型接入（coding agent 用什么模型、以谁的身份跑）

引擎跑起来需要两样东西：**模型访问**（调哪个大模型）和**身份凭据**（以谁的名义调）。平台把两者统一抽象为**凭据档案**——引擎适配层 RunConfig 上的一个 `auth_profile` 字段，与引擎种类正交，换路径不换适配层。

**立场先说清：走哪条路径、用哪份凭据，是管理员的部署配置决策，不是业务人员的选择。** 下述 A/B/C 三条路径全部在管理面配置生效，业务人员在工作台里永远只是「开始造应用」，对引擎、模型、凭据零感知。

```
凭据档案 = { 类型:     平台模型代理 | 订阅登录态（Claude Code / Codex / Kimi）| 厂商 API key,
            内容:     加密存储（复用平台 Fernet 加密），如 ~/.claude 目录、auth.json、key,
            分配:     由管理员创建并分配（全租户 / 用户组 / 指定用户）,
            并发上限: 同一档案同时最多 N 个会话 }
```

**路径 A：平台模型代理（默认，规模化主路径）。** 引擎经能力总线的双协议模型代理（§3.4）使用平台托管的国产模型，接线方式按引擎所讲协议分两种：

- Anthropic 协议引擎：会话容器内设 `ANTHROPIC_BASE_URL/AUTH_TOKEN` 指向平台代理（token = 会话 key），并把 opus/sonnet/haiku 三档默认模型映射到租户配置的强/中/快三档国产模型（duoduo `compatible_endpoint` 的成品做法）；
- OpenAI 协议引擎：同理设 base_url + 会话 key；对 Kimi Code 这类不读 shell 环境变量凭据的引擎，改为 per-session 生成其 config.toml 注入容器。

治理全在平台手里：会话 key 随会话签发/吊销、scope 最小化、配额限流、token 记账到人。这是唯一不依赖任何外部账号可得性的路径，适用于所有客户。

**路径 B：客户订阅（BYO 凭据：Claude Code / Codex / Kimi 席位）。** 订阅的登录态本质是一份磁盘凭据（`~/.claude` 目录 / `$CODEX_HOME/auth.json`）；duoduo 已验证「凭据完全委托给 CLI 自己的登录态」的机制可行——其 `claude_code_local` 短路模式：**不注入任何 `ANTHROPIC_*` 环境变量，且启动时反向清除环境里残留的 API key 防止劫持订阅路径**（此细节照抄）。平台化为三个环节：

1. **绑定（一次性，管理面操作）**：管理员在后台发起——服务账号型订阅由管理员直接完成官方登录流（订阅无头场景有 setup-token 长期令牌方式；Codex 走设备码登录）；个人席位型由管理员向席位持有人发送授权邀请，对方完成一次授权即收档。登录态落盘 → 加密入档，管理面可随时吊销；
2. **注入（每次会话）**：沙箱容器启动时把档案挂载为容器内 `$HOME/.claude`（或设 CLAUDE_CONFIG_DIR）/ `$CODEX_HOME`，走短路模式；
3. **治理（平台必须补的三件）**：**并发闸**——订阅限额按账号计（滚动窗口 + 周上限），档案级并发上限（建议 1-2），限额报错友好化（「订阅额度用尽，xx 点重置」）；**归属**——计费虽在订阅侧，平台仍从引擎 usage 事件流记每人每会话的 token 台账；**隔离**——档案只注入其分配范围内用户的会话容器，分配与使用全程审计。

两点注意：①**全员共用一个订阅账号不可作为产品承诺**——违反消费者条款（账号共享）、限额不够分（两三个并发会话即顶满）、用量无法归属到人；只可小规模试点，合规路径是每人/每组一个席位；②**Claude Code 二进制不得打进平台镜像**（无分发授权）——客户自装到宿主机或自备镜像层，平台以挂载方式调用；Codex CLI（Apache-2.0）可直接内置沙箱镜像。

定位：BYO 增值路径——已有订阅的客户白赚顶级引擎质量；规模化主路径仍是路径 A。

**路径 C：客户自有厂商 API key。** 企业已采购的模型 API（DeepSeek/GLM 等）建议配置为平台代理的上游、仍经代理转发——保留记账/限流/审计；直连厂商 endpoint 作为例外场景（档案类型 = API key，注入方式同路径 A）。

**路径解析与降级（均为管理员配置的结果）**：解析链 = 用户组级配置 > 租户级默认 > 系统默认（平台代理），全部在管理面设定，业务人员无从选择也无需选择；「订阅额度用尽自动降级切平台代理」同样是管理员预配的策略开关——对业务人员只表现为「一直可用」，最多收到一条降级提示。同一套适配层，只换 `auth_profile` 的取值。

**引擎 × 路径兼容矩阵**：

| 引擎 | 平台模型代理 | 客户订阅 |
|------|-------------|---------|
| Qwen Code | ✓（双协议均可） | —（无订阅形态） |
| Codex CLI | ✓（OpenAI 面） | ✓（ChatGPT 席位） |
| Kimi Code CLI | ✓（双协议，生成 config.toml） | ✓（Kimi For Coding） |
| Claude Code（客户自装） | ✓（Anthropic 面） | ✓（Claude 席位） |

**统一治理底线**（无论哪条路径）：凭据只进属主会话容器、沙箱出站白名单只放行对应 endpoint、用量台账到人、全程审计。

### 4.4 基础组件注入机制（不让 AI 写的部分，怎么递到管家手里）

数据库/登录/权限/存储这些基础组件「平台自带、AI 不写」，靠四条通道让管家**知道有、直接用、不越界**：

1. **模板预接线**：预置模板里 SDK 已引入，读当前用户、查数据表、检索知识库的样例调用就在代码里——管家照现成范式扩展，而不是自由发挥；
2. **声明式资源清单**：应用要用什么（数据表/知识库/模型）写进 manifest 的 capabilities，平台在容器启动时注入凭据与连接——代码里永远不出现连接串和密钥；
3. **MCP 工具面**：建表/改表结构/读写数据/查身份/检索知识库都是平台 MCP 工具，管家调用工具完成，而非生成底层实现代码；
4. **引擎指令约束 + 纠偏**：引擎系统指令明确禁写鉴权/数据库连接/加密逻辑，管家若违规生成则视为错误、引导改写为平台组件调用——「引导」这一层若失效，还有 §4.5 的运行环境兜底（代码里没有凭据可泄、网络上没有旁门可走）。

### 4.5 沙箱与安全模型

| 隔离档位 | 实现 | 适用 |
|----------|------|------|
| 基础档（默认） | Docker 加固：read-only rootfs、no-new-privileges、独立网络、资源限额、崩溃自愈 | 所有环境 |
| 推荐档 | + gVisor（runsc 换入 Docker runtime，**无需 KVM/k8s**） | x86_64/ARM64，标准信创虚机可用 |
| 加固档 | Kata/Firecracker microVM | 客户有裸金属/KVM 时可选 |

选型依据：Firecracker/Kata 依赖 KVM，客户虚机普遍无嵌套虚拟化（信创云尤甚），不能作默认；内部应用的现实威胁是**数据外渗与越权**而非内核逃逸——**默认出站白名单**（仅放行平台 API 与显式声明域名）比换 runtime 更重要；LoongArch 等 gVisor 不支持的架构回退基础档。

**编排特权（全案最重安全约束）**：容器由独立最小权限编排器 **runtime-manager** 生管——它是唯一持 docker 访问的组件，backend 编译期/运行期零 docker 依赖（arch-guard import 禁令强制；取证：现网 backend 无 docker 依赖，`docker.sock` 仅出现在 CI）；backend 只向它下发**期望态 intent**（声明式，manager 自 reconcile），绝不把 `/var/run/docker.sock` 挂进 backend 或起 DinD——否则控制面即握 root-on-host、与「安全来自笼子」（§2.2③）自相矛盾，私有化银行/信创客户安全团队必一票否决。runtime-manager 独立受限 service account、凭据与 backend 隔离；容量/密度治理（准入控制、idle 回收、并发上限、cgroup 硬隔离）挂在它上面，兜住「平台正常即使某应用崩」。

**出站白名单 × 依赖安装（构建/运行两段分离）**：生成应用要 pip/npm install（社区 #1568），运行期 egress 锁死后包怎么装？**构建期与运行期 egress 分离**——构建期只放行**平台自托管的 PyPI/npm 镜像**（白名单里的受控条目、非洞：版本可 pin、可缓存、信创可离线预灌），运行期不放行任何包源。

**鉴权注入（app-proxy 层，版本无关）**：`auth_request` 现网零使用、纯新建，且 Java 网关只认 `/api/**`、有自己的 Sa-Token/SSO + 自定义 WS filter、完全不认 `/apps`（据 `docs/architecture/11-gateway.md`）——故验会话 + 签 OBO + 注入头 + 反代容器统一收在 **app-proxy** 一个组件里，nginx（开源）与 Java 网关（商业）都只把 /apps 转发到它，安全逻辑一处实现、不随版本分叉：

```
浏览器 → nginx / Java 网关 → app-proxy /apps/{slug}/*（或 /apps/preview/{session}/*）
  ├─ 验平台会话 + OpenFGA viewer 检查
  ├─ 签发短时 OBO token（scope = 应用 capabilities ∩ 用户自身权限）
  ├─ 注入头：X-BiSheng-User-* / X-BiSheng-Access-Token
  └─ 反代容器（支持 WebSocket）
```

两个躲不掉的不变量：① **header 防伪**——app-proxy 剥离客户端伪造的 `X-BiSheng-*` 头，容器仅经 app-proxy 可达（不暴露直连端口）；② **WS 长连接的 OBO 过期/吊销策略**——握手时鉴权一次不够，长连接期间 OBO 过期或权限被撤须有中断策略。app-proxy 与 runtime-manager 是邻居，可同组件可拆。

- 应用启动注入应用 token（M2M，后台逻辑用）；请求级注入 OBO 用户 token（以当前用户权限调知识库——知识库权限对应用内每个用户自然生效，「AI 可见性 ⊆ 用户 UI 可见性」不变量外推到应用场景）。
- 应用侧零登录代码：读头即得身份，SDK 一行拿到。

| BishengLLM 统一封装 + token 记账 | 模型代理 provider 路由、会话/管家账单 | ⚠️ **库可复用、HTTP 协议面净新建**：BishengLLM 是进程内库类、无 `/v1/messages`；记账 `on_llm_end` 按叶子租户、须改按 key 归属（协议面决定采用现成代理，见 §3.4） |
| 灵思澄清环 / 任务模式经验 | 造应用的需求澄清前置、想做分离 | ✅ prompt/UX 经验直接复用 |
| MinIO + 灵思 workspace | 工作区持久化与恢复 | ⚠️ **借 MinIO、非快照**：workspace_backend 是 per-file write-through 对象缓存、不吃 git+node_modules；须新增 tar/bulk-snapshot 层（见 §4.1） |
| 灵思 deep-agent + 中间件 + 模型容错 | 管家「守」态的**单次执行** | ✅ 单次执行可复用 |
| 灵思 worker / 队列 / 状态机 | 管家「守」态的**调度与生命周期** | ❌ **一次性会话模型**：worker 丢弃终态队列项、无 cron/webhook、默认 compose 都不起——常驻实体的触发/调度/生命周期是净新建平台能力（见 §4.1、§5 F108） |
| org_sync 企微/钉钉/飞书 | 管家推送 | ❌ **零外发**：org_sync 纯入站目录同步；平台今日无通用外发通知（仅站内信 + 一个客户专属转发器）；须新建通知服务、借 workflow 群机器人 webhook 逻辑 |
| share_link + iframe.js | 简报卡片与应用嵌入 | ⚠️ **postMessage + 域名白名单净新建**：现 iframe 嵌 chatbot 非简报卡；订阅/文章简报 iframe 虽有 postMessage 但 `targetOrigin '*'` 无 origin 校验，可借鉴但须补白名单 |
| E2B executor copy-in/out 先例 | 沙箱文件交换 | ⚠️ 现 code interpreter **默认走 LocalExecutor（worker 原生子进程、无沙箱）**、E2B 远程执行器非默认；本地 docker 沙箱对两者都是净新建 |

**净新建核心基建（不在复用表内、却决定成败，须显式排期与安全评审）**：① **runtime-manager**（独立最小权限编排器，唯一持 docker，全案最重最险，安全评审前置）；② **app-proxy**（版本无关鉴权代理，取代 auth_request、消解网关冲突）；③ **模型代理协议面**（Anthropic/OpenAI 兼容，采现成代理承载）；④ **workspace tar/snapshot 层**；⑤ **平台触发/调度子系统**（管家守态、工作流定时、知识库定时同步共用）；⑥ **应用级 secret store**（Fernet，见 §4.7）。

### 4.7 合规与风险

合规预判：新模块 DDD 分层（C1）；新表 MySQL/DM8 双方言（C2，**但生成应用自己的库不受 C2 约束、走 SQLite/Postgres**）；全部带 tenant_id、容器/镜像/存储前缀租户隔离（C3）；应用/会话/管家均为 OpenFGA 资源类型、预览与生产统一过 **app-proxy** 无旁门（C4）；错误码遵 **C5**（非 C6；C6 是禁硬编码密钥）——段位须避开已占用段（130=chat、160=dataset），建议 161 起 4 段、最终以 release-contract 定；应用级 secret store 复用 **C6** Fernet；双前端纪律不变（C7）。

| 风险 | 对策 |
|------|------|
| **引擎在国产模型上的实效未知（最大技术风险）** | Wave-0 PoC 先行；适配层保证引擎可换；模板 + 澄清前置降低对模型上限的依赖 |
| 引擎 API 漂移/断代 | 引擎依赖收口在 RuntimeAdapter 单模块；pin 版本 |
| 造应用会话 token 成本 | 会话 key 配额 + 单轮/单会话预算上限 + 模板起步减少从零生成；成本对用户可见 |
| 跑任意代码的安全暴露 | 沙箱分档 + 出站白名单 + capabilities 最小授权 + 发布审批 + 审计 |
| 生成应用质量差/改不动 | 存档回滚（草稿/代码无损）+ 修错免费 + 玻璃盒逃生 + 模板起步（不从空白开始） |
| 客户环境差异 | 工场/沙箱为可选组件（compose profile），缺席时平台其余功能完整；gVisor 不可用自动回退 |
| 订阅路径依赖外部账号可得性与限额 | 档案级并发闸 + 限额友好提示 + 一键降级切平台代理续跑（§4.3） |
| **控制面特权（编排 root-on-host）** | 独立最小权限 runtime-manager 唯一持 docker，backend 零 docker 依赖（arch-guard 强制）、intent-based RPC、凭据隔离（§4.5） |
| **容量/密度（单机 N 用户各开沙箱 + 生产容器）** | 准入控制 + idle 回收 + 并发上限 + cgroup 硬隔离，挂 runtime-manager；档位固定 small/medium |
| **应用级 secret 无落点** | 新建应用 secret store（Fernet），声明式注入（同 capabilities + 发布审批） |
| **Anthropic 兼容面耦合引擎实效风险** | 翻译层劣化 tool-calling 会加重模型实效风险；采现成代理省自研长尾、协议面稳定性外包成熟实现（§3.4） |

### 5.4 开放问题

1. **命名**：能力域名暂定「应用工场」、入口动词暂用「造应用」，均非最终命名；最终命名待评审（要求：业务人员一听即懂、易记）。
2. Wave-0 PoC 立项（最紧急）：任务集设计、评测口径、三模型接入。
3. release-contract（v3.0.0）初始化：领域对象归属（App/AppVersion/ApiKey/BuilderSession/Guardian…）、错误码段位（引 C5，避开 130=chat/160=dataset，建议 161 起）、不变量草案（「预览与生产必须过 app-proxy」「OBO scope ⊆ 用户实际权限」「引擎依赖收口 RuntimeAdapter」「凭据档案只注入其分配范围内的会话」「backend 零 docker 依赖，容器编排唯经 runtime-manager」「app-proxy 剥离客户端伪造 X-BiSheng-* 头」）。
4. 造应用工作台交互稿评审：细化三分区布局、选项式澄清、玻璃盒展开方式（初版交互稿见 §4.1）。
5. `/apps`（含 preview + WebSocket）路由与鉴权在 **app-proxy 层统一**（nginx 与 Java 网关都只转发到 app-proxy，安全逻辑不分叉）——据 `docs/architecture/11-gateway.md`，Java 网关只认 `/api/**`、有自己的 Sa-Token/SSO + 自定义 WS filter、不认 `/apps`，故这是**设计任务**而非「待对齐」；待细化 header 防伪与 WS 长连 OBO 过期/吊销两个不变量的落地。
6. 内部 dogfood：首批用工场造 5-10 个内部工具（优先从首发 6 类模板场景选题，兼作 PoC 素材）。
7. 管家「守」态是否纳入本版实现：本版基线 = 只定稿规格 + 预留数据表（F108）；建议开发进入后半段时按剩余人力决定是否实现，不足则顺延 v3.1——**待定夺**。
