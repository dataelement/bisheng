# 工作流逻辑删除技术方案

日期：2026-11-03。状态：按用户确认的低复杂度方向修订，尚未实施；目标版本与特性编号待排期。

**主表只增加一个 `is_delete` 标记。删除时改标记，正常查询和新操作排除已删除记录；正在执行的工作流沿用现有行为，不额外协调。**

## 1 范围

- 保留工作流主记录、定义、版本、会话和附件；已删除工作流不再出现在普通列表、搜索及推荐中，不接受新的编辑、发布、调试或调用。
- 历史会话、文件和审计按各自既有权限读取，不因普通资源查询过滤而消失。
- 已保存模板和已复制的工作流保留；不能再以已删除工作流为来源新建。
- 建议已删除记录不占用业务配额和新建重名检查，重新创建时生成新 ID。
- 在途请求、已入队任务和等待输入的实例不做额外协调；可能继续，也可能因现有检查而失败，不承诺强制停止、持续运行或最终完成。
- 本期不增加删除中状态、删除进度表、删除专用重试任务、执行实例索引、定时实例清理、业务版本号、回收站或恢复能力。

## 2 数据改动

`flow` 表新增 `is_delete`：非空整数，默认 0；0 表示正常，1 表示已删除。沿用现有 `FlowVersion.is_delete` 的命名和取值习惯，不改变 `status` 的上下线含义。

存量记录默认 0。只为工作流启用新的删除行为；共享表中其他类型保持原有语义。删除标记仅由后端控制，不允许普通编辑请求提交或覆盖。

不新增删除时间和操作人字段，本次沿用现有审计记录。主记录标记与关联版本标记在同一数据库事务提交，定义内容不清空。

## 3 删除流程

保留现有删除接口及处理顺序，仅把物理删除改为标记更新：

1. 读取正常工作流，按现有统一权限入口校验删除权限。
2. 沿用现有 F048 权限删除投影；其成功后才提交业务删除标记，遵循架构约束。
3. 在同一事务内将主记录 `is_delete` 改为 1，将关联版本 `is_delete` 改为 1。
4. 沿用现有审计、用户组资源清理、会话信息保存、访客链接清理及遥测流程。
5. 保持现有成功响应和异常处理方式，不增加删除进度查询接口。重复删除沿用普通资源不存在的响应，不为此增加恢复流程。

**取舍：**权限服务与业务数据库之间仍不是一个事务。权限撤销成功后若标记提交失败，可能出现“记录还在、权限已撤销”；后置清理失败也可能需要排查日志。沿用现有权限账本与运维修复机制，本期不新建自动补偿系统，也不承诺所有中断都能通过再次点击删除恢复。

## 4 必须一起修改的入口

### 正常读取和新操作

- `FlowDao` 中正常的单条、批量、名称、列表和计数查询统一增加 `is_delete=0`。
- 统一应用列表在工作流 UNION 子查询内部过滤，列表与计数保持一致，不能分页后再剔除。
- 补齐绕过 DAO 的直接读取：创建重名检查、模板来源、推荐校验、权限迁移来源等。原始 SQL 和别名查询也要核查。
- 网页、构建预览、API v2/v3、匿名分享在发起新操作时检查父工作流未删除。权限适配器不再为已删除记录提供正常业务目标，管理员同样遵守资源存在性。
- 不改 Worker 的执行调度、运行状态机和等待输入机制，不增加删除与任务启动之间的全局同步保证。

### 写入和历史

- 普通修改使用带 `is_delete=0` 条件的字段更新；更新不到记录时拒绝保存，不能重新插入旧对象，也不能把标记恢复为 0。
- 修改版本时，在同一事务中检查并锁定父记录，再更新版本；删除事务使用同一父记录锁，避免删除后又写入可用版本。不增加通用版本号体系。
- 历史查看优先使用已有会话及审计展示信息；确需读取已删除主记录时，增加工作流域内部的专用 Repository 读取，先校验历史权限，不向普通 API 开放绕过过滤参数。
- 运行中的回调若受普通查询过滤影响，按现有失败路径处理；本期不为在途完成增加运行快照等新机制。

## 5 影响范围

| 范围 | 主要改动 |
|---|---|
| 数据模型和迁移 | `database/models/flow.py` 增加标记；Alembic 增量迁移 |
| 删除接口和服务 | `api/v1/flows.py`、`api/services/flow.py`，保留原调用链及清理行为 |
| 普通查询和版本写入 | `FlowDao`、`api/v1/workflow.py`、`api/services/workflow.py`、`database/models/flow_version.py` |
| 权限及资源引用 | `api/services/f048_application_permission.py`、权限迁移来源、模板来源、推荐和分享相关查询 |
| 新调用入口 | 网页、构建预览、`workflow/domain/services/published_workflow_service.py` 及公开调用入口 |
| 历史和前端 | 校验历史、审计、文件读取及旧页面不可用提示，维持现有删除交互 |

遵循 `docs/constitution.md` 的分层、双库、多租户和权限约束。复用现有 DAO 时修改既有查询；新增专用读取走工作流域 Repository。权限模块不反向读取工作流模型，不直接操作 OpenFGA。

## 6 发布和验收

1. 使用双库通用字段与默认值完成迁移，验证 MySQL、DM8 存量记录均为未删除。
2. 更新全部相关 API 和后台进程，确认旧版本退出后开放删除；旧代码仍可能物理删除或忽略标记。
3. 验收主记录和版本仍在库中、标记正确，列表与数量一致，旧详情/分享入口及新的调用不可使用，历史仍按原权限可读。
4. 验收非管理员、管理员、不同租户，以及删除与旧页面保存并发时不会恢复标记或插回记录。
5. 回滚必须保留删除过滤和禁止物理删除的兼容处理，或暂停相关入口；不能直接退回忽略标记的旧代码。

不把在途实例立即停止或全部成功完成列为验收条件。此前已物理删除的主记录不能自动恢复；保留数据持续占用存储，清理期限另议。
