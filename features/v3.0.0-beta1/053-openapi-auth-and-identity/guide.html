开放 API 鉴权导读

给平台的对外接口装上锁、发钥匙、并且说清楚"每次调用是以谁的名义"。这页用大白话讲清需求和技术实现，适合刚接手的同学 10 分钟读完。

需求来源：PRD v2.4（2026-08-28） 设计定稿：2026-08-31

1 · 为什么要做

BiSheng 除了自己的网页界面，还给客户的系统留了一组接口，叫 开放 API。客户的 OA、CRM 这些系统通过它来触发工作流、检索知识库、跟助手对话。

现在的问题：这扇门没锁。任何能连到服务器的人都能直接调，不需要任何凭证。更糟的是，请求里可以写一个 user_id 说"我是张三"，系统就真的按张三的权限给数据。等于"匿名"和"冒充"两个洞叠在一起。

而且现有的接口文档还建议客户把那个兜底账号配成超级管理员。最坏的情况是：任何人都能用超管权限、指定任意员工的身份、读走平台上全部知识库，还能调用没上线的草稿工作流。这在等保测评里是明确的失分项，"部署在内网"不算缓解。

2 · 要做成什么样：三层机制

一

调用必须带钥匙

每次调开放 API 都要带一把平台签发的 密钥，没带就返回 401。老的"兜底用户"配置删掉，没有任何回落路径，也不设兼容开关。

二

钥匙必须有主人

主人两种。服务账号：给公司的系统用，管理员建、管理员授权，建的时候要指定一个 资源归属人。个人访问令牌：员工自己领，权限就是他自己的，场景是把 Claude Code、openclaw 这类个人 AI 助手接进来查公司知识库。

三

说清以谁的名义

默认以钥匙主人自己的身份跑，叫 自身身份。如果管理员给这把钥匙开了 委托 能力，每次调用就必须声明代表哪个员工，过五道检查后整个换成那个员工的身份执行，叫 代表他人。

一个容易混的点："自身身份"的主人既可以是服务账号，也可以是员工本人（个人令牌）。判断是哪种模式，看的是权限基准是谁，不是钥匙主人是谁。

3 · 四种客户场景

分类依据是客户接入时真的要做的判断：这把钥匙谁配的？背后有没有最终用户？这些用户在平台上有账号吗？

场景例子用什么钥匙以谁身份
系统集成ERP 每天凌晨把新合同同步进知识库服务账号自身身份
平台同批用户中粮：员工在集团 OA 里提问，必须看到他在毕昇里能看的那些库，不多不少服务账号 + 委托代表他人（代表张三）
外部用户对外客服机器人，访客不是平台用户服务账号自身身份，可带 访客标识 只用于分会话
员工自助接入员工把 Claude Code / openclaw 接进来查知识库个人令牌自身身份（员工本人）

外部用户场景的关键澄清：客户常说"不要做权限过滤"。直接照做会变成无边界的数据出口。正确做法是过滤照做，基准换成服务账号：管理员给这个服务账号授权"对外可以开放的那几个库"，那就是这个机器人的边界。

4 · 一次调用怎么走

所有 /api/v2 请求走同一条检查管线，顺序固定。设计里叫"槽位"，后面加新检查只能插进既定位置，不能另起一条路。

①

拿钥匙

从请求头取 Authorization: Bearer …。两个 WebSocket 接口另外接受分享页的票据。

没带 / 格式错 → 401
②

验钥匙

算 哈希去数据库找，恒时比较，看有没有被 撤销、有没有过期，再按主人类型解析主人是否有效。结果在 Redis 缓存 3 秒。

无效 / 撤销 / 过期 → 401主人被停用 → 401
③

定租户 + 限流

把请求锁定在钥匙所属的 租户里；同时按这把钥匙做 限流。

超限 → 429
④

查权限位

每个接口都标了需要哪个 权限位。钥匙没勾对应的位就拒绝，而且错误信息会说缺哪一位。

缺位 → 403
⑤

定身份模式

看请求头有没有 代表谁。

没带 → 自身身份执行身份 = 钥匙主人。开了委托的钥匙漏带 → 400 报错，不降级。
带了 → 代表他人过五道关：①钥匙有委托能力 ②目标是真人、存在、没禁用、同租户 ③目标不是管理员 ④目标在允许范围内 ⑤这个接口支持委托。全过才把身份换成目标。
任一关不过 → 403两个身份头一起传 → 400
⑥

执行业务 + 记账

按执行身份的资源权限过滤（走平台既有的 权限引擎）。响应完成后写一条 调用审计。

200权限引擎不可用 → 503

三条铁律贯穿全程：没凭据就拒绝；缺身份就报错、不降级；权限判定失败就报错、绝不返回没过滤干净的数据。设计里反复否决的都是"返回 200 加一个悄悄缩水或悄悄放大的结果集"这种形状。

5 · 界面上会多什么

管理后台（platform）

系统管理里新增一个菜单「服务账号」：建账号（填名称、描述、资源归属人）→ 发钥匙（勾权限位、可选开委托并圈范围、可选 IP 白名单和限流）→ 给它授权哪些知识库。明文只显示一次，必须勾"我已保存"才能关窗。旁边一个同级 tab「个人访问令牌」是管理员的台账：能看本租户谁领了令牌、最后什么时候用、能强制吊销；还有一个租户级开关和默认有效期（默认一年）。

员工个人中心（client）

头像菜单里多一项「API 令牌」：一键领、一人一把、不填任何参数。页面上还有一段可复制的安装提示词，贴给 AI 助手它就会自己去下载 技能包装好。

升级影响

这是破坏性变更、不设兼容开关。客户升级后，所有老的开放 API 调用会立刻 401，必须先建服务账号、发钥匙、在调用代码里加请求头。请求参数里的裸 user_id 也一并移除。这要靠发布说明提前沟通，由客户安排窗口期。

6 · 设计要点

下面是设计文档里最值得先知道的几条决定，每条都带"为什么"。

底座怎么来
从 vibe 分支直接 cherry-pick 5 个提交，不重写。省 5～7 人天，还保住了测试。vibe 那边文档里"个人令牌整条否决"的结论已经被 PRD 推翻，接手的人别被误导。
为什么一条管线
多人并行开发，只有把检查顺序钉死，大家才不会各自在接口里补判断。任何新检查只能插进既定槽位。
"代表他人"为什么是纯替换
曾考虑"取被代表人和服务账号权限的交集"，否决：权限引擎不支持列举两个人的可见集求交，成本也翻倍。现在是整个换成目标员工的身份，服务账号自己的授权不参与。这意味着"代表他人"是提权有上界（最多拿到一个真实员工的真实权限），不是"恒为降权"。
个人令牌为什么不做快照
每次调用按持有人当时的权限算。做快照反而要多写代码，还会在授权撤销后继续放行。管理员的令牌照常享受管理员短路，但不跨租户——一把常驻在外部 AI 助手里的密钥不该横跨全平台。
检索为什么要补文件级过滤
现在开放 API 的检索只按"整个知识库能不能看"过滤，网页界面是按"单个文件能不能看"过滤的。不补的话，"代表张三"返回的结果会比张三自己在网页里搜到的多，连文件名带正文一起泄露。
审计为什么单独建表
逐次调用是高频访问日志，混进操作审计表会把审计页拖垮。用进程内队列每秒批量落库，代价是进程崩溃最多丢 1 秒记录，可接受。
对外对话接口用什么格式
用平台自己的业务语义（问什么、在哪个会话、挂哪些知识库、开哪些工具），不模仿 OpenAI。原因：OpenAI 那套是"模型侧"契约，要调用方自己拼消息历史和系统提示词，跟我们要开放的"应用侧"能力对不上。
P2 运营能力
限流（令牌桶）、日配额、IP 白名单、幂等键，全部基于 Redis，且 Redis 挂了一律拒绝。平台现有那条并发槽位原语是 Redis 挂了就放行的，不能照抄。

7 · 名词表

正文里悬停过的词，这里集中列一遍，方便查。

开放 API
/api/v2 开头的接口，给客户系统调；网页用的是 /api/v1。
密钥 / API Key
bs-sak-…（服务账号）或 bs-pat-…（个人令牌），放在 Authorization: Bearer 请求头。服务器只存哈希。
服务账号
不能登录的机器账号，管理员建、管理员授权，不占席位，不出现在任何选人框里。
资源归属人
服务账号必填的一个真人，它经 API 创建的资源都算这个人的。
个人访问令牌（PAT）
员工自助领的密钥，权限动态继承本人，离职即失效，本期只能读知识库。
权限位（scope）
钥匙上勾的"能做哪类事"，模块 + 动作级，默认全不勾。
委托（delegate）
一个单独的权限位。开了就必须每次声明代表谁，并配一张"允许代表谁"的白名单（按人或按部门）。
自身身份 / 代表他人
两种身份模式，判据是权限基准是谁。内部简写 S / D，对外文档只用中文名。
X-Bisheng-On-Behalf-Of
请求头，值是用户 ID，表示"代表这个人"。
X-Bisheng-End-User
请求头，随便填的访客标识，只分会话、不影响权限。
租户
多租户下的一个公司 / 子公司。钥匙不跨租户。
撤销
让钥匙作废，软删除、留审计、5 秒内全节点生效。
fail-closed
拿不准就拒绝。Redis 挂、权限引擎挂、信息不足，一律报错，绝不放行。
审计双归属
每次调用同时记"哪把钥匙调的"和"以谁的名义调的"。
share-token
免登录分享链接自带的票据，只在两个 WebSocket 和分享专用接口上认。
限流 / 日配额 / 幂等键
按钥匙计的每分钟上限、每日上限、防重复执行的请求头。
技能包 / 安装提示词
给 AI 助手的 zip 包和一段安装指令，员工复制粘贴就能接入。
401 / 403 / 429 / 503
没验证通过 / 没权限 / 太频繁 / 后端依赖不可用（拒绝而非放行）。
错误码 260xx
本模块的业务错误码段，比如 26003 缺权限位、26016 开了委托却没说代表谁、26040 个人令牌功能没开。
vibe 分支 / cherry-pick
