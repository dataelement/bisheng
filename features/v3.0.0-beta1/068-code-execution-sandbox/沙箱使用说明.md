# 沙箱使用说明

本文写**页面上怎么选执行方式、任务里文件该写到哪、提示词怎么约束**。Runner、token、服务地址、环境变量见 [沙箱部署说明.md](./沙箱部署说明.md)。

选「沙箱运行」之前，部署侧要先把 `code-runner` 和 token 配好。存量升级不会自动改成沙箱。地址和令牌也可以在这个弹窗里改，见下一节。页面改不了网络可达性：backend、worker、灵思仍然要能访问你填的地址。

---

## 1. 选择执行方式

只有全局超级管理员能改。打开管理端的**构建 → 工具**，左侧停在**内置工具**，找到**代码执行器**，点这一行右侧的设置图标。弹出的对话框标题是「编辑内置工具」。

对话框里「代码执行方式」有三个单选：

| 选项 | 选它的时候 |
|------|------------|
| 本地隔离运行 | 代码在 backend / worker 本机执行。`sandbox_conf.local_isolation`（或 `BS_SANDBOX_CONF__LOCAL_ISOLATION`）为 `uid` 时，子进程使用临时 uid；为 `off` 时仍以服务进程自己的用户跑。弹窗里不填地址。开启条件和目录权限见部署说明「本机执行的 uid 隔离」 |
| 沙箱运行 | 代码进入自建 `code-runner`。选中后填写每台副本的地址和访问令牌。留空的那一项回退到部署配置；清空已保存的页面值即恢复为部署配置。页面上的值优先于环境变量和 `config.yaml` |
| E2B沙箱运行 | 走云端 E2B。选中后才出现服务提供方、Domain、API Key，与自建副本池无关 |

点**保存**。执行方式写入 `t_gpts_tools_type.extra` 的 `type`（`local` / `container` / `e2b`）。若这次改了沙箱地址或令牌，会先单独保存那两项，成功后再保存执行方式。任务模式、日常会话、助手、工作流里的代码执行器，以及代码节点，都按这一份来。

保存后的地址和令牌在 60 秒内对下一次执行生效：日常会话的下一条消息、已经打开的助手的下一轮对话（不用断开重连）、工作流的下一次运行。写缓存失败时，旧值仍靠缓存自己的 60 秒 TTL 到期后让出。正在跑的任务本轮仍用旧副本。测试连接只代表处理这次请求的 backend，不代表 worker 或灵思。缓存 key `config:sandbox_endpoint` 所在的 Redis db 跟 `redis_url` 走，发行配置是 `/1`。

## 2. 任务模式（灵思）

1. 打开工作台客户端，路径 `/workspace`。Helm 部署下客户端在前端 Service 的 `4001` 端口，默认只在集群内可达，Ingress 也只转发 `3001`。要从浏览器打开，需在部署时配 `frontend.service.clientNodePort`（Service 类型为 NodePort）或 `clientHostPort`。
2. 切到**任务模式**，工具里勾选**代码执行器**；要用知识库就一并勾选。
3. 执行方式选的是「沙箱运行」时，token 和服务地址还要能打到 runner。Compose 里灵思在 worker 容器内，已能访问。Helm 的灵思是单独 Deployment，沙箱 chart 的网络策略默认已放行。老环境升级时若沿用了旧的放行列表，任务模式会连不上 runner，见部署说明「Linsight 进程」。

任务工作区（MinIO `workspace/{session_version_id}/`）会在 exec 前 copy-in：

| 路径 | 用途 |
|------|------|
| `output/` | **交付区**。只有这里会被收获给用户下载 |
| `scratch/` | 中间稿，跨轮不播种 |
| `uploads/` | 用户上传原件与解析出的 `.md` |
| `skills/` | 本轮技能包，只读 |
| `large_tool_results/` | 工具结果太大时的落盘，给模型稍后读取，**不是交付物** |

文件工具带前导斜杠（`/output/x`），沙箱 cwd 是工作区根，代码里必须写成相对路径 `output/x`。

## 3. 工作流代码节点

代码节点有两个互不相干的设置，不要合成一个开关：

| 要回答的问题 | 在哪里设置 | 说明 |
|------|------|------|
| 能不能跑 | 系统配置 `workflow.code_node_enabled`，必须是字面量 `true`（配置键是 `workflow`，种子在 `initdb_config.yaml`） | 默认关闭。不是 `true` 时节点直接拒绝执行，与执行方式无关 |
| 在哪里跑 | 管理端「代码执行方式」，见第 1 节 | 页面写入 `extra.type`。「沙箱运行」进入 `code-runner`，「本地隔离运行」在本机执行 |

其他说明：

- 编辑器「运行一次」在 backend 进程里执行，异步运行在 Celery worker。仓库默认的 Compose / Helm 已让这两个进程访问 runner。
- 节点里写的是模块顶层的 `def main`。语法检查仍在本地 `ast.parse`，只有真正执行才进入所选的执行方式。

---

## 4. 日常会话 / 助手

同样勾选代码执行器。用户自己上传的附件只抽文本进 prompt，原件不送进沙箱。日常会话里，知识库检索引用到的图片会写到工作区的 `uploads/kb/`，代码里用这个相对路径读；执行方式为 `e2b` 时不写。助手没有这一步。一次 `run` 结束即 `DELETE` 租约。
