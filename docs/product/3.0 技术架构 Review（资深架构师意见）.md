## 1. 总体判断

方案**方向可行、战略框定正确**（引擎是公共品、竞争在「壳」与治理底座；设计理念三条——应用管家 / 引擎复用 / 安全来自笼子——也立得住）。

技术架构的核心病灶只有一个：**§4.4「既有资产复用」表约一半失真——最重、最险的几块基建被当成「复用」轻描淡写，导致关键路径比波次图显示的更长、更险。** 本 review 的价值在于把「以为能复用、实为新建」的隐性工作量显式化，避免立项后在地基上返工。

## 3. 发现（按严重度分档）

### Tier 1 — 会动摇根基，须在立项前拍板

**T1-1 容器编排的「特权悖论」（全案最重、与安全叙事自相矛盾）**
- app_runtime 让 backend 用 docker SDK 生管每 app/session 的兄弟容器 → 需把 `/var/run/docker.sock` 挂进 backend 或 DinD = **root-on-host**。控制面因此握有系统里最大的特权，直接违背 §2.2③「安全来自笼子」。
- 它在方案里被当成「构建（docker SDK）/ 生命周期 reconcile」一笔带过，实为**最重、最新、最险**的一块，不在复用表内却决定成败。
- 私有化 toB 客户安全团队一定会审这条；「平台 backend 对宿主机有 root」对银行/信创客户基本是一票否决。
- **→ 建议方向（已对齐）：独立最小权限编排器 `runtime-manager`**。硬约束：① runtime-manager 是唯一持有 docker 访问的组件，backend 编译期/运行期零 docker 依赖（arch-guard 加 import 禁令）；② RPC 契约 intent-based（声明期望态、manager 自 reconcile），非远程调 docker 命令；③ manager 独立受限 service account，凭据与 backend 隔离。

**T1-2 引擎在国产模型上的实效 = 存在性风险，但无 Plan B**
- 方案自己点名这是「全案最大技术未知数」，Wave-0 PoC 前置正确。
- 但若 PoC 结论是「没有任何开源 coding agent 能在国产模型上稳定驱动多轮造应用」，「不自研引擎」原则**没有退路**（Claude Code 又永不内嵌）——整个产品命题落空。
- 真正的失败模式不是「崩」而是「demo 能跑、多轮飘」（tool-calling 可靠性经翻译层退化，灵思已踩过）；3 个单发任务测不出。
- 「业务应用大多表单+列表+看板」（§3.1）意味着模板/DSL 可能不止是 fallback、甚至该是主干、coding agent 作逃生梯度。
- **→ 建议方向（已对齐）：F100 加量化 go/no-go gate + 多轮鲁棒性口径 + 模板生成器入 PoC 作对照基线**；引擎 vs 模板的主次关系由 PoC 数据决定，不预设。

**T1-3 管家值守态是全新常驻 agent 原语，不是灵思 worker 的复用**
- 灵思是一次性/终态会话模型（worker 丢弃终态队列项、单 thread=session），**无 cron/webhook 触发、无常驻生命周期**，默认 compose 都不起该 worker。
- 拆两个轴：**单次执行**（✅ 可复用灵思 deep-agent + 中间件栈 + workspace + 模型容错）vs **常驻实体的调度与生命周期**（❌ 全新：cron/webhook producer、armed/paused/预算超限 生命周期、零-LLM 游标水位、机队观测）。后者本质是**平台级触发/调度子系统**（v2.6 完全没有；频道信息源不更新事故的根因就是缺 Beat+default worker），管家只是首个消费者，且该原语可被工作流定时/知识库定时同步复用。
- **→ 建议方向（已对齐）：F108 从「管家值守态」重标为「平台触发/调度子系统 + 管家作首个消费者」**，实现仍 defer——defer 掉的是可复用平台能力，而非「以为能复用实为新建」的隐性债。

### Tier 2 — 实质设计缺口，须在 design 阶段解决

**T2-1 auth_request/OBO 100% 新建 + 与商业版 Java 网关真冲突（开放问题 #5 是冲突不是待对齐）**
- 网关只路由 `/api/**`、有自己的 Sa-Token/SSO 鉴权 + 自定义 WS filter（`SelfWebsocketRoutingFilter`），**完全不认 `/apps`**。/apps（含 preview + WebSocket）走网关还是绕过、双重鉴权如何协调、WS 如何过——全未解。
- 商业版会话是网关的 Sa-Token cookie 而非 backend JWT——「auth_request→backend 验会话」在商业版悬空。
- **→ 建议方向（已对齐）：独立 app-proxy 层（版本无关）**——验会话+签 OBO+注入头+反代容器收在一个组件，nginx（开源）与 Java 网关（商业）都只把 /apps 转发到它，安全逻辑一处实现不分叉、网关冲突消解。两个不变量（不论选型都躲不掉）：① header 防伪（剥离客户端伪造 `X-BiSheng-*` + 容器仅经 proxy 可达）；② WS 长连接的 OBO 过期/吊销策略（握手一次不够）。app-proxy 与 runtime-manager 是邻居，可同组件可拆。

**T2-2「应用数据库」引擎未定 + 与 C2 双方言 / 回滚语义冲突**
- §3.1「应用数据库 = 平台托管」指生成应用**自己的库**，方案没交代由什么引擎承载。纯 DM8 信创环境下，生成的应用代码不认 DM8 方言（C2 是平台表的法，管不到生成代码）→ 要么被迫再引入 SQLite/MySQL（削弱信创单库叙事），要么应用跑不起来。
- 「每轮存档含应用数据库」+「生产回滚」对**有状态生产应用**意味着：回滚会丢回滚点后的生产数据、schema 演进无迁移脚本。「恢复无损」对生产态是 overclaim。
- **→ 建议方向（已对齐）：应用库 = SQLite-per-app（小档）+ Postgres schema（中档），与平台 MySQL/DM8 解耦**。一箭三雕：绕开生成代码不认 DM8 方言、单文件 SQLite 顺带解 workspace 快照难题（tar 一个文件=一次存档）、天然按 app 隔离、映射 small|medium 两档。回滚语义收窄：**代码/配置回滚=无损；生产数据默认不回滚；republish schema 演进需策略（仅增列/迁移前快照/人工确认）**——「恢复无损」限定草稿+代码。

**T2-3 双协议模型代理不是「暴露 BishengLLM」**
- Anthropic `/v1/messages` 兼容面是有长尾的兼容工程（content blocks / tool_use / streaming SSE / thinking / prompt caching 语义），要让 Claude Code/Codex/Qwen Code 都真跑通并非补个端点。且记账要从 callback-per-tenant 改成 per-key 归属 + 限流。它在**关键路径**上（F102 卡 F103/F110），且**耦合 T1-2**——翻译层劣化 tool-calling 会加重模型实效风险。
- **→ 建议方向（已对齐）：采用现成代理（LiteLLM/one-api）做协议面**，BishengLLM 退居 provider 路由；省 Anthropic 长尾自研。三个必钉约束：① license 核查（LiteLLM 企业功能单独授权，商业私有化要确认；one-api/new-api MIT）；② BishengLLM 仍是 provider 路由唯一真相（现成代理调 BishengLLM 解析端点，不重实现租户模型配置，防漂移）；③ 记账回流一处（外部代理 per-key 用量喂回 `llm_token_log`/`QuotaService`，避免两套账单）。与方案 §4.3 已定的 auth_profile 三路径协同。

**T2-4 出站白名单 vs 依赖安装的矛盾**
- egress 白名单是对的威胁模型，但生成应用要 pip/npm install（社区 #1568）。白名单锁死后依赖怎么装？方案引了 #1568 但没设计这条。
- **→ 建议方向（已对齐）：构建期/运行期 egress 分离 + 平台自托管 PyPI/npm 镜像进构建白名单**。镜像是白名单里的受控条目而非洞；附带版本可 pin/可缓存/信创可离线预灌。运行期不放行任何包源。

**T2-5 workspace 快照层缺失**（承 §2 复用表）——git + node_modules 规模需要新的 tar/bulk-snapshot 层，直接决定「每轮自动存档 / 恢复无损 / 容器可回收回来能续」这几条机制能否成立。（T2-2 选 SQLite-per-app 后，应用数据部分的快照自动简化为「tar 一个文件」。）

### Tier 3 — 澄清/补齐，不阻塞（处置已定）

- **T3-1 错误码段位撞车**：§4.5「错误码建议 130-133 段（C6）」——① 错误码是 **C5** 不是 C6；② **130 段已被 `chat` 占用**（C5 明列）。→ **引用改 C5，段位挪到 160-163（160+ 未占）**。
- **T3-2 org_sync 推送 = 假**：org_sync 零外发（纯入站目录同步），群机器人只存在于 workflow 工具（`t_gpts_tools.json` 钉钉/企微 webhook）。→ **管家推送改「新建通知服务，借 workflow 群机器人 webhook 发送逻辑」，并入 T1-3 触发/调度子系统的推送出口，一起 defer**。
- **T3-3 postMessage + 域名白名单是新建**，iframe 现嵌 chatbot 非简报卡。→ **§4.4 改「新建 postMessage + 域名白名单；简报卡是新用途」，F109 定性改「重构」**。
- **T3-4 容量/密度模型缺失**：单机 docker 下 N 用户各开 builder 沙箱 + 生产容器，资源竞争 / 冷启动 / idle 回收无模型。→ **补风险表 + 把准入控制/idle 回收/并发上限挂到 runtime-manager；「平台正常即使应用崩」补 cgroup 硬隔离兜底**。
- **T3-5 应用 secrets 管理缺失**：capabilities 只声明 knowledge/models，外部集成 secret 无落点。→ **补应用级 secret store（复用 C6 Fernet），注入同 capabilities（声明式 + 发布审批）**。

## 4. 值得肯定（避免只挑刺）

引擎=公共品/护城河=治理 的战略框定；「安全来自笼子」不信任生成代码的降维；OBO 双轨（借 Databricks Apps）；egress 白名单 > 换 runtime 的威胁模型排序；gVisor 免 KVM 应对信创无嵌套虚拟化；Wave-0 把最大未知前置；值守态 zero-LLM 游标 diff 降本；把值守态降级为「spec 冻结」的容量务实。

## 附录 A：若采纳，对产品方案的回写映射（§级）

> 供决定回写方案时参考；本 review 未直接改动方案文档。

- **§4.1 总体架构** — 新增 `runtime-manager`（独立最小权限编排器，唯一持 docker 访问）；`app_runtime` 改为「向 runtime-manager 下发 intent」不直连 docker。新增 `app-proxy`（版本无关鉴权代理）层，取代 nginx auth_request 叙事。模型代理改为「采用现成代理（LiteLLM/one-api）+ BishengLLM provider 路由」。
- **§4.2 引擎（F100）** — 加量化 go/no-go gate + 多轮鲁棒性口径 + 模板生成器对照基线；补 fallback（模板/DSL，主次由 PoC 定）。
- **§4.3 沙箱与安全** — 编排改 runtime-manager（不挂 docker.sock 进 backend）；app-proxy 鉴权取代 auth_request，补 header 防伪 + WS 生命周期两个不变量；egress 分构建/运行两段 + 自托管镜像；补容量/准入/idle 回收（挂 runtime-manager）+ cgroup 硬隔离兜底。
- **§3.1 / §3.3 应用库与回滚** — 应用库明确 SQLite（小）+ Postgres（中），与平台 MySQL/DM8 解耦；「恢复无损」收窄到草稿/代码，补生产数据/schema 演进语义；补应用级 secret store。
- **§4.4 复用表据实重标** — workspace 快照 / 灵思 worker 值守 / org_sync 推送 / iframe 从「复用」改为「借经验 / 部分 / 新建」；`runtime-manager`、`app-proxy`、模型代理协议面 显式列为**新建核心基建**。
- **§4.5 合规与风险** — 错误码 `130-133（C6）`→ 改引 **C5** + 段位挪 **160-163**；风险表补：容量/密度、应用 secrets、Anthropic 兼容面耦合 T1-2、编排特权（已解为 runtime-manager）。
- **§3.2 守态 + F108** — 重标为「平台触发/调度子系统 + 管家作首个消费者」；org_sync 推送改「新建通知服务」。
- **§5 波次重排** — runtime-manager 安全评审前置 Wave-1；F100 加 gate；被低估的净新建（app-proxy、模型代理面、workspace 快照层、触发子系统）并回关键路径与工作量估计。
- **§5.4 开放问题 #5** — 从「待对齐」升级为「/apps 路由与鉴权在 app-proxy 层统一（网关只转发）」设计任务。
