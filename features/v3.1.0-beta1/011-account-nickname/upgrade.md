# F011 账号与昵称升级运行说明

## 当前交付边界

本地两个前端继续通过开发代理连接 `http://192.168.106.116:3001`。本地后端代码、迁移和测试不等于公司测试环境已经发布。

后台组合编辑已按用户确认的 [事务范围](./design-adjustment.md) 完成接入。本地实现与验证已完成；正式发布前仍需完成真实双库及目标服务验收。

## 数据与版本

| 对象 | 变更 |
| --- | --- |
| user.user_name / external_id | 保留原长度 128 / 255 及原值。新建和实际改名在写入时校验。 |
| account_rule_version | 新列，默认 0；新本地账号由服务设为 1。 |
| account_match_key | 新列，默认 legacy；v1 写入原账号的 SHA-256。 |
| nickname_customized | 新列，默认 false；实际人工改名后置为 true。 |
| legacy_sso_name | 新列，默认 NULL；v0 首次人工改名时保存旧 SSO 识别名称。 |
| 来源唯一约束 | 二列 source / external_id 改为三列 source / external_id / account_match_key。 |
| user_account_reservation | 新表，记录 v1 精确占用；停用或删除人员不释放。 |
| user_identity_write_guard | 新表，低频身份创建共用一行锁。首次使用由 repository 在独立事务初始化。 |

迁移：`v310b1_f011_account_identity`，父版本：`v310b1_f009_system_profiles`。新表沿用项目模型发现与启动建表机制；迁移处理已有表增列及索引。

## 发布前只读核对

研发在目标库分别执行 MySQL / DM8 核对并保存结果：

1. 确认当前 Alembic head、user 表字段、原唯一索引名称和实际字符比较配置。
2. 统计历史空账号、超过新上限的账号和昵称；只记录统计与行 ID，不改写原值。
3. 使用目标库原比较规则检查跨 source 的同账号候选，覆盖启用、禁用及已删除状态。存在歧义时记录原 user_id；不自动合并或清洗。
4. 确认旧 `/user/sso` 调用方是否发送 external_id。旧名称匹配需保留原 user_name 的比较语义。
5. 盘点后台、注册、SSO、组织同步、导入、脚本和直接 SQL 写入器。恢复写入前，各身份创建入口必须统一进入新占用事务。
6. 备份数据库及对应后端、前端构建版本。保存预检统计，作为升级后原值核对依据。

不在迁移中执行 UPDATE、改大小写、trim、截断、账号去重或昵称清洗。

## 发布顺序

1. 完成目标环境代码复审、双库升级及并发验证。
2. 暂停注册、本地创建和外部身份写入，排空旧版本请求；停止旧同步任务。禁止新旧身份写入程序混跑。
3. 在目标构建执行 `uv run alembic heads`，确认单头后执行 `uv run alembic upgrade head`。升级任务使用项目统一在线环境和模型发现入口。
4. 检查新增列默认值、三列唯一约束、legacy_sso_name 索引及两个新表；再次比对原账号、昵称和 user_id。
5. 启动完整新后端及同步任务，在专用测试租户验证后恢复身份写入。
6. 发布两个前端。检查注册、登录、后台创建/编辑、成员搜索/复制、个人改名及其他端的资料刷新。

## 必须在目标环境完成的验证

| 验证 | 结果要求 |
| --- | --- |
| 两个仅大小写不同的新账号 | 能独立创建、登录；各自密码和 user_id 不混用。 |
| 新账号命中历史兼容范围 | 明确冲突，旧数据和占用保持原样。 |
| 同账号并发创建 | 仅一个身份与登记成功；失败不留下角色、组或登记残片。 |
| 不同大小写账号并发 | 无历史冲突时均成功。 |
| 历史长账号、原大小写、前导零 | 仍按原规则登录、展示和完整复制。 |
| 昵称 32 / 33 个字符 | 新建和实际改名分别允许 / 拒绝，补充汉字和补充平面字符。 |
| 人工改名与同步竞争 | 最终保留主动昵称，其他权威字段继续同步；账号及会话保持不变。 |
| 审计或资料版本写入失败 | 昵称、保护标记及资料版本一起回滚。 |
| 非管理员改自己 / 指定他人 | 本人成功；额外目标字段或越权目标拒绝。 |
| 旧 SSO 改名后再次登录 | 原绑定仍指向同一 user_id，新昵称不变成登录账号。 |

## 自动化入口

- 本地隔离检查：`test/user/test_identity_rules.py`、`test_account_identity_repository.py`、`test_account_login_rules.py`、`test_nickname_*.py` 等，详见 [verification.md](./verification.md)。
- 真实双库并发：`test/user/test_account_identity_dual_db.py`。仅接受空的专用测试数据库。设置 `F011_MYSQL_TEST_URL` / `F011_DM8_TEST_URL`，并明确设置 `F011_OWN_EMPTY_TEST_DATABASE=yes`。测试拒绝已有表的库，只清理本套创建的表。
- 真实 HTTP：`test/e2e/test_e2e_account_nickname.py`，复用项目 E2E helpers。需已部署 F011 后端、专用租户及普通用户，设置 `E2E_API_BASE`、`E2E_F011_FIXTURE` 和短期 `E2E_F011_USER_TOKEN`。fixture 包含 user_id、account、nickname、tenant_id、tenant_name，账号/昵称/租户名使用 e2e-f011- 前缀；测试恢复该用户的原有效昵称。
- 未配置上述环境的测试会明确跳过，不能计为目标环境通过。

## 故障处理

先暂停新建和身份同步写入，保留数据及当前构建证据。已有 v1 账号、主动昵称或旧 SSO 识别快照时，迁移会拒绝直接降级。

不得直接恢复旧二列唯一约束、切回模糊登录、删除新账号或清空登记。优先前向修复；确需回退，由研发依据备份和新身份清单制定独立方案。

只读预检、迁移、双库运行及公司环境发布均由研发在目标环境执行。本次未对公司测试库执行上述写入。
