## 1. 综述

### 1.1 一句话定位

本册让专业开发者把本地开发好的应用部署到 BiSheng 平台上运行，并开放给企业内的同事使用。开发者在本地用自己的 IDE 或 coding agent 写代码，需要时通过 MCP、OpenAI 兼容模型接口、SDK 接入平台的知识库、模型和用户身份。开发完成后，开发者执行 `bisheng deploy` 把应用提交到平台。平台对每次提交做预检和密钥扫描，再经审批后托管运行。应用上线后，owner 在平台上设置可见范围，范围内的同事就能从应用广场打开使用。审批、权限和审计由平台统一执行，应用代码不需要处理这些事情。

### 1.2 为什么做

企业里有越来越多的员工会用 coding agent 开发小应用，例如表单、台账、看板和内部工具。这些应用开发完之后通常没有地方运行。开发者要么自己找服务器部署，要么放弃。自己部署的应用要单独处理登录、权限、数据库和模型密钥，IT 部门看不到它们，也管不住它们。这类绕开 IT 的自建应用（shadow AI）会带来数据外泄和审计缺失的风险。

BiSheng 已经具备企业身份、组织架构、权限体系、知识库、模型管理、审批和审计能力。本册把这些能力开放给本地开发的应用使用，并提供一个托管运行环境。这样，开发者省去了重复建设登录和权限的工作，IT 部门也得到了一条有治理的上线通道。

本册和通用容器平台（例如 k8s）解决的问题不同。容器平台负责让进程运行起来。本册在运行之上增加了五件事：应用复用平台登录、应用自动获得访问者身份、应用按声明接入知识库和模型、每次上线经过审批、应用在广场中可被同事找到。

### 1.3 五条设计前提

下面五条前提贯穿全册。读正文前先掌握它们，正文中的大部分规则都可以从这五条推出。

| # | 前提 | 含义 |
|---|---|---|
| 1 | 平台能力按需集成 | MCP 工具、技能包、SDK 和 CLI 四种接入方式都是可选的。不使用任何平台能力的存量应用也可以直接部署。四种方式全部使用标准协议，任何本地 coding agent 不需要改造即可接入 |
| 2 | 同一条发布管线 | CLI 部署的应用和将来在平台内造的应用走同一条发布管线，审批、权限和审计规则相同 |
| 3 | 凭据以鉴权 PRD 为准 | 服务账号、密钥底座和权限位清单定义在鉴权 PRD。本册只增加三项：权限位清单中的「本地开发工具包」三个权限位、服务账号详情页的接入信息区、若干落地口径 |

## 2. 用户与旅程

### 2.1 用户与角色

| 用户 | 需求 | 主要使用面 |
|---|---|---|
| 业务技术员（主用户，会用 coding agent） | 把本地开发的应用部署到平台给同事用 | 专业开发者通道（§3.1） |
| IT 与平台管理员 | 看得到、管得住员工自建的应用，出问题时能处置 | 治理与管理面（§3.3） |
| 普通业务用户 | 在应用广场找到并使用同事开发的应用 | 统一入口与应用广场（§3.2） |

下表是全文角色名称的唯一出处。正文提到角色时一律使用表中名称，不泛称「管理员」。

| 角色 | 定义 | 典型动作 |
|---|---|---|
| 平台超管 | 平台级运维管理员 | 维护资源档位、跨租户查询审计 |
| 租户管理员 | 租户内的治理角色 | 签发和吊销服务账号密钥、下线和重新上线应用、配置审批人、查询本租户审计 |
| 审批人 | 处理发布审批单的人，来源由 GOV-02 预置流程决定 | 审读代码、预览试用、通过或驳回 |
| owner | 应用的所有者。CLI 首次部署的应用，owner 是所用密钥对应服务账号的资源归属人 | 部署、审批期预览待上线版本、撤回审批、设置可见范围、下线、删除 |
| 普通业务用户 | 应用的使用者 | 在可见范围内发现并使用应用 |

单租户部署下，平台超管和租户管理员可以是同一个人。

面向终端用户的兜底页文案是唯一例外，这些页面使用中性称呼「平台管理员」。原因是兜底页由应用入口组件 app-proxy 渲染。app-proxy 是独立进程，读不到平台的多租户开关，无法按部署形态选择「租户管理员」或「平台超管」。标准安装默认单租户，而单租户下不存在租户管理员，页面上写「请联系租户管理员」会指向一个不存在的人。

### 2.2 主旅程：本地开发、集成平台能力、部署上线

1. 开发者在本地用 IDE 或 coding agent 开发应用。平台不参与这一步。
2. 开发者需要平台能力时，请租户管理员建服务账号并签发密钥（DEV-01）。开发者的 coding agent 通过 MCP 调用检索、身份和应用数据工具，通过 OpenAI 兼容协议调用平台模型（DEV-02），按需引入 SDK（DEV-07）。技能包在 `bisheng login` 时已经自动拉取（DEV-03）。如果应用不需要平台能力，开发者跳过这一步。
3. 开发者执行 `bisheng dev`，在本地运行应用。CLI 注入与线上结构相同的身份，应用不需要登录页（DEV-05）。
4. 开发者执行 `bisheng deploy`，应用进入发布管线：预检、密钥扫描、审批、上线（DEV-04、RT-03）。开发者用 `bisheng logs` 查看日志排障。
5. 应用首次上线后，owner 在平台上打开应用详情页，在「发布」tab 设置可见范围（GOV-01）。如果 owner 不设置，应用虽然已上线，但只有 owner 自己能看到。这是首次上线后必须做的一步，也是整个旅程中第一次离开命令行。
6. 之后的迭代仍然是本地改代码、再次 `deploy`。代码修改只能在本地进行，平台对 CLI 部署的应用代码只读。

下表列出没有命令行对应操作、必须在平台界面上完成的操作。入口都在 platform 端「构建 → 应用」中该应用的详情页（导航见 §3.0.1）。

| 操作 | 何时需要 | 出处 |
|---|---|---|
| 设置可见范围 | 首次上线后必须做 | GOV-01 |
| 待上线状态下手动上线 | 审批通过但运行环境容量不足时 | GOV-03 |
| 撤回在途审批单 | 提交后想撤回时 | RT-03 |
| 下线、重新上线 | 需要临时停止服务时 | RT-07 |
| 显式删除 | 应用退役时（须先下线） | RT-07 |
| 获取入口链接和二维码 | 分发给同事时 | RT-01 |

除设置可见范围外，其余操作都是按需触发。审批状态有两个查询途径：应用详情页和 MCP 应用状态工具（DEV-02），因此 coding agent 在本地就能跟踪审批进度。

### 2.3 使用旅程：普通业务用户

普通业务用户通过应用广场、入口链接或二维码打开应用。已登录平台的用户不需要再次登录。每个用户在应用里只看到自己有权限的数据（RT-01、RT-02）。

#### 3.0.1 承载面与导航

托管应用与工作流、助手共用 platform 端「构建」区的同一个应用列表，不另设入口。完整导航路径如下，全文提到「应用详情页 · X」时都指这条路径的终点：

```
platform 端
  └─ 左侧主菜单「构建」
       └─ 应用列表（既有卡片流页）
            · 顶部：搜索 + 应用类型筛选 + 状态筛选 + 标签筛选
            · 应用类型筛选新增第三项「托管应用」，与「工作流」「助手」并列
            · 卡片：图标、名称、描述、创建人、类型角标、版本下拉、上下线开关
            └─ 点击托管应用卡片
                 └─ 应用详情页：发布 · 数据 · 运行日志 · 版本（四个 tab）
```

应用列表复用构建页的既有能力：搜索、筛选、标签、上下线开关和版本下拉。owner 看到的是自己的应用。租户管理员通过平台既有的权限模型，天然能看到本租户的全部应用，因此本册不另建治理列表。

应用详情页有四个 tab，内容如下。PRD-2 曾计划在这个页面左侧加入对话区，这部分已随 PRD-2 搁置，本册的详情页没有对话区。

| tab | 内容 | 编号 |
|---|---|---|
| 发布 | 提交发布与档位选择、审批状态与驳回理由、撤回、能力声明清单、应用密钥、可见范围、下线与重新上线、待上线时的手动上线、入口链接与二维码、底部危险操作区（删除）。各区块的定义见 RT-03 | WB-14 |
| 数据 | 查看、编辑和导出应用自有数据库中的数据；编辑生产数据前须二次确认，编辑动作计审计 | WB-06 |
| 运行日志 | 只读的应用运行日志，权限与内容范围和 CLI `logs` 一致（DEV-04） | WB-13 |
| 版本 | 版本列表、终态标注、相邻版本的文件差异（RT-05） | WB-15 |

四个 tab 的编号沿用 PRD-2 的 WB 前缀，因为它们在 PRD-2 中定义过完整形态。本册交付的形态以上表为准。

卡片上只保留列表级的轻操作，即上下线开关和版本下拉。提交发布、设置可见范围和删除这类需要上下文的操作都在详情页完成。

托管应用放在构建区而不是 client 端，原因有三点。第一，工作流、助手和托管应用都是用户造出来的东西，放在一处便于查找。第二，构建页的列表、筛选、上下线和权限能力可以直接复用，owner 和租户管理员看的是同一个页面。第三，平台分工因此更清楚：造和管在 platform 端，用在 client 端（应用广场和 `/apps/{slug}` 在 client 端）。

#### 3.0.2 应用状态机

应用的生命周期用两条互相独立的状态线描述。应用状态表示应用当前能否对外提供服务，审批单状态表示一次发布请求的处理进度。版本记录的终态见 RT-05。构建页卡片和筛选器上的「发布状态」使用同一组状态值。

应用状态：

| 状态 | 进入条件 | 可做的操作 | 去向 |
|---|---|---|---|
| 草稿 | 首次部署后尚未上线；首次发布被驳回或撤回 | owner 提交发布、再次部署 | 首次审批通过并上线成功 → 已上线；删除 → 已删除 |
| 已上线 | 审批通过且上线成功 | 可见范围内用户使用；owner 提交迭代、调整可见范围；owner 或租户管理员下线。本状态不能直接删除，须先下线（RT-07） | 下线 → 已下线 |
| 待上线（资源不足） | 审批通过，但上线终检发现运行环境容量不足（GOV-03） | owner 在资源释放后手动上线，不需要重新审批；owner 删除 | 上线成功 → 已上线；删除 → 已删除 |
| 已下线 | owner 或租户管理员下线 | owner 或租户管理员重新上线（同样检查运行环境容量）；owner 提交发布（审批通过后只记为待运行版本，不自动上线）；owner 删除 | 重新上线 → 已上线；删除 → 已删除 |
| 已删除 | owner 执行显式删除（RT-07） | 无，只能在审计中查到 | 终态 |

审批单状态有五个：待审、通过、驳回、已撤回、已取消。应用被删除时，在途审批单自动变为已取消（RT-07）。迭代审批被驳回时，应用保持已上线状态，当前版本继续运行，只有待上线版本被标记为驳回（RT-03）。

#### 3.0.3 事件触达

一方操作后需要另一方知道的事件，全文统一使用两种触达渠道。

第一种是站内消息。它复用平台既有的消息通知能力，接收方在工作台的「消息提醒」入口（铃铛图标）查看。审批类事件同时进入审批中心的待办。管理后台没有消息面，租户管理员和审批人的消息都在工作台接收。站内消息只做通知，不承载操作，处理动作回到各自的界面完成。

第二种是界面自查。状态和结果常驻在固定界面上，例如应用详情页的发布 tab、构建页的应用列表和管理后台的密钥管理页，用户随时可以查看。

| 事件 | 接收方 | 站内消息 | 自查位置 |
|---|---|---|---|
| 审批单生成（首发或迭代） | 审批人 | 有（审批中心既有触达） | 审批中心待办 |
| 审批通过或驳回 | owner | 有 | 发布 tab 的审批状态区；MCP 应用状态工具 |
| owner 撤回在途审批单 | 已收到待办的审批人 | 有 | 审批中心 |
| 应用删除导致在途审批单取消 | 审批人 | 有 | 审批中心 |
| 上线终检容量不足，应用进入待上线 | owner、租户管理员 | 有 | 发布 tab（owner）；构建页状态筛选（租户管理员） |
| 资源释放后可以手动上线 | owner | 无 | 发布 tab 的「手动上线」按钮 |
| 租户管理员下线或重新上线应用 | owner | 有 | 发布 tab 的状态；审计记录 |
| 声明的能力被收回（模型下线、知识库收回） | owner | 无 | 发布 tab 的失效提示 |
| 服务账号密钥签发完成 | 资源归属人 | 无 | 开发者侧没有自查位置。租户管理员通过企业既有渠道转交密钥和接入信息（DEV-01） |
| 密钥被吊销或服务账号被禁用 | 资源归属人 | 无 | 下一次调用被拒绝，CLI 提示重新 login（DEV-04） |
| 应用上架或用户新获可见权限 | 可见范围内的用户 | 无（本版不做上新推送） | 应用广场；owner 自行转发入口链接 |

本约定只覆盖事件发生时的一次性触达。催办、超时提醒和升级机制本版不做（§5.2）。

### 3.1 专业开发者通道（DEV）

本域让已有本地项目的开发者按需集成平台能力，并把项目部署到平台。六个条目按开发者的使用顺序排列：

| 条目 | 解决的问题 |
|---|---|
| DEV-01 | 开发者如何拿到凭据，凭据能做什么 |
| DEV-02 | coding agent 如何调用平台能力 |
| DEV-03 | coding agent 如何学会使用平台能力 |
| DEV-04 | 开发者如何完成部署和排障 |
| DEV-05 | 应用如何在本地运行并获得身份 |
| DEV-07 | 应用代码如何调用平台能力 |

本域的直接操作者通常是开发者的 coding agent，而不是开发者本人。开发者在本地对话中提出部署要求，coding agent 读取技能包，调用 CLI 和 MCP，完成部署和排障。DEV-04 验收 7 检查的就是这一点。

本域用「本地开发三面」统称 MCP 工具面、模型协议面和 CLI 三个对外接口。三面使用同一把服务账号密钥鉴权。

---

**DEV-01 服务账号密钥（本地开发用途）**

> 开发者使用的密钥就是鉴权 PRD 中的服务账号密钥，不是一种新的密钥类型。签发表单、密钥底座和权限位清单都沿用鉴权 PRD，应用工场只在权限位清单中增加了三个权限位。

**需求描述。** 租户管理员为开发者建立服务账号，并把该开发者指定为服务账号的资源归属人，然后签发密钥。服务账号是不能登录的平台主体。开发者用这把密钥接入本地开发三面。

密钥的能力由两层条件共同决定：密钥上勾选的权限位，以及租户管理员显式授予该服务账号的资源。密钥不继承任何自然人的权限。

本地开发只接受服务账号密钥。鉴权 PRD 场景四另有个人访问令牌，它固定只持有 `knowledge:read` 一个权限位，不能用于部署、模型调用和身份查询。

密钥明文只在签发时展示一次，由租户管理员转交开发者，此后任何界面只显示掩码（NFR-2）。

**界面与交互。** 本条没有独立界面。签发、列表和吊销都使用鉴权 PRD 中服务账号模块的界面，下表只写应用工场的增量。

| 界面 | 应用工场增量 |
|---|---|
| 服务账号新建表单 | 在资源归属人选择处增加风险提示：该账号首次部署的应用以此人为 owner；删除应用和撤回审批单只有 owner 能做，平台超管和租户管理员都不能代做；归属人在创建时固定，以后修改不影响已有应用。因此归属人选错后，本版只能由管理侧下线应用 |
| 密钥签发表单 | 权限位清单新增「本地开发工具包」一组三个权限位，每个附用途说明，并提示「部署应用需要勾选 `app:manage`」，默认全不勾。`identity:read` 显示醒目的风险标注：勾选后本租户组织架构全部可读，不能限制到部分部门。`delegate` 与这三个权限位互斥，同时勾选时无法保存，提示「配了委托的密钥不能用于本地开发，请另发一把」 |
| 密钥列表、明文展示弹窗、吊销 | 沿用鉴权 PRD。列表的权限位列包含新增三位；吊销确认文案增加一句「MCP、模型协议和 CLI 将同时拒绝这把密钥」；开发者没有自助吊销入口 |
| 接入信息区 | 位于服务账号详情页「API 密钥」标签页顶部。展示 MCP Server 地址、OpenAI 兼容 base URL、CLI 安装包下载链接和 `bisheng login` 指引，并提供「一键复制接入信息」按钮。未部署开放能力层时不显示 |

**规则与边界。**

① 权限位与本地开发三面的对应关系见下表。`login` 和 `skills sync` 只校验密钥有效，不校验权限位。唯一的例外是 `delegate`：持有它的密钥在 `login` 时就被拒绝，理由见 DEV-02 规则 ④。

| 权限位 | 来源 | MCP 工具 | 模型协议面 | CLI |
|---|---|---|---|---|
| `knowledge:read` | 鉴权 PRD 既有，复用 | 知识库检索、知识库清单 | — | — |
| `model:invoke` | 应用工场新增 | 模型清单 | OpenAI 兼容调用 | — |
| `identity:read` | 应用工场新增 | 用户身份与组织查询 | — | — |
| `app:manage` | 应用工场新增 | 应用数据查询、应用状态与日志 | — | `deploy`、`logs` |
| `delegate` | 鉴权 PRD 既有 | 全部拒绝 | 全部拒绝 | `login` 即拒绝 |

新增的三个权限位与鉴权 PRD 既有的权限位在同一张清单、同一个签发表单里，默认全不勾。它们不构成第二个权限维度。同一把勾了 `knowledge:read` 的密钥，通过开放 API 检索和通过 MCP 检索，得到的可见集合相同。`model:invoke` 与鉴权 PRD 的 `chat:invoke` 互不包含：前者是直接调用模型，后者是调用平台的会话能力。

② 凭据规则。密钥的生成、哈希存储、校验、展示和吊销都遵循 GOV-08 的统一密钥底座，密钥前缀是 `bs-sak-`。租户管理员可以在签发后修改权限位，修改立即生效，不需要重新签发，修改动作计审计。密钥可以设置过期时间，默认长期有效，到期自动失效并计审计。本版不做调用频率限流（§5.2）。模型 token 用量只计量、不设上限，每次调用按密钥记录。

③ 权限模型。服务账号的资源授权只有一个入口：租户管理员在服务账号详情页的「资源授权」标签页中授予。服务账号不出现在各资源的授权选人框中，这样普通资源所有者不能单方面扩大一把密钥的数据范围。

`identity:read` 是高风险权限位。勾选后，密钥能读取本租户的全部组织架构，包括姓名、部门和层级。平台没有把部分部门授予服务账号的机制，所以这个范围不能收窄。风险控制只能靠「给不给这个权限位」。租户隔离仍然有效，跨租户的数据读不到。

资源归属人只决定归属，不出借权限。在应用工场里它有两个作用。第一，CLI 首次部署的应用，owner 就是密钥对应服务账号的资源归属人。第二，应用数据、状态和日志工具以及 CLI `logs` 只对该归属人作为 owner 的应用生效。租户管理员修改资源归属人后，修改只影响以后创建的应用，已部署应用的 owner 不变。

④ 安全约束。CLI 把凭据保存在本地用户目录，文件只有属主可读，不写入工程仓库。技能包要求 coding agent 通过环境变量引用密钥，不在代码里硬编码。发布前的密钥扫描规则包含 `bs-sak-` 前缀，硬编码进应用代码的密钥在部署时被拦截（RT-03）。发现密钥泄漏时，资源归属人联系租户管理员吊销；租户管理员可以一键吊销某个服务账号名下的全部密钥，吊销在 5 秒内生效。服务账号被禁用或删除时，名下全部密钥自动失效。资源归属人离职时，平台不自动处理，须由租户管理员回收其服务账号（自动回收见 §5.2）。

⑤ 接入信息的传递。「一键复制」生成一段格式化文本，包含 MCP Server 地址、OpenAI 兼容 base URL、CLI 下载链接和 `bisheng login` 指引。租户管理员把这段文本通过企业微信、邮件等既有渠道发给开发者。文本可以随时复制，内容实时生成。这段文本不包含密钥明文，也不包含任何能换取密钥明文的凭据。接入信息不保密，可以随时重发；密钥明文保密，只展示一次，由租户管理员单独转交。本版不做分享链接、二维码或站内信推送接入信息。

⑥ 可选部署。未部署开放能力层时，新增的三个权限位和接入信息区都不显示。服务账号模块本身随鉴权 PRD 交付，始终存在（GOV-10）。

**验收要点。**

1. 每次调用都能在审计中追溯到密钥及其服务账号和资源归属人，模型调用包含模型名和 token 数（GOV-04）。
2. 密钥吊销后，下一次调用在 MCP、模型协议面和 CLI 上都被拒绝。
3. 密钥明文签发时展示一次，之后任何界面只显示掩码。
4. CLI 凭据保存在本地用户目录，只有属主可读，不写入工程仓库。
5. 签发表单默认不勾任何权限位。不带权限位的密钥只能执行 `login` 和 `skills sync`，其余三面能力和开放 API 都被拒绝。租户管理员修改权限位后立即生效，不需要重新签发。超出权限位的调用在三面都被拒绝（按规则 ① 的表逐个权限位验证）。
6. 密钥能访问的数据 = 权限位允许的范围 ∩ 服务账号被授予的资源。未授予的资源不可访问，检索和清单查询都不返回。同一把持有 `knowledge:read` 的密钥，经开放 API 检索和经 MCP 检索得到相同的可见集合。
7. 服务账号被禁用后，名下密钥从下一次调用起在三面都被拒绝，禁用事件计审计。
8. 把密钥明文写入应用代码后执行部署，发布前密钥扫描拦截部署（DEV-04、RT-03）。
9. 「一键复制」的文本包含 MCP 地址、模型 base URL、CLI 下载链接和 login 指引，不包含密钥明文或可换取明文的凭据。开发者凭这段文本加上单独转交的密钥，能完成 `bisheng login` 并成功调用一次 MCP 工具。
10. `delegate` 与「本地开发工具包」三个权限位不能同时勾选，签发和编辑表单都拒绝保存并提示。已存在的此类历史密钥在三面调用时被明确拒绝（DEV-02 规则 ④）。

---

**DEV-02 MCP 工具面与模型协议面**

> 平台能力通过两个接口对外：工具走 MCP，模型走 OpenAI 兼容协议。两者都用服务账号密钥鉴权，都以服务账号自身的身份执行，都按权限位过滤。

**需求描述。** 平台运行一个 MCP Server，用服务账号密钥鉴权，按权限位过滤，对外提供下表六类工具。工具的权限边界与平台界面上的权限体系一致。模型调用不走 MCP，因为模型调用需要原生协议和流式输出，所以平台另外提供一个 OpenAI 兼容的模型接口。

| 工具 | 用途 |
|---|---|
| 知识库检索 | 在服务账号被授予的知识库中检索 |
| 知识库清单 | 列出服务账号被授予的知识库及其标识，供填写能力声明（RT-04） |
| 模型清单 | 查询可用模型；模型调用本身不走 MCP |
| 用户身份与组织查询 | 开发期查询用户身份和组织架构 |
| 应用数据查询 | 开发和排障时读写应用自有数据库 |
| 应用状态与日志 | 部署后查询审批状态和运行日志，使 coding agent 能完成「读日志、修改、再部署」的循环 |

**界面与交互。** 本条没有平台界面。开发者需要的地址和接入指引集中在 DEV-01 的接入信息区。

模型协议面的约定如下：

| 要素 | 约定 |
|---|---|
| 协议 | OpenAI 兼容协议，支持流式输出。本版不提供 Anthropic 兼容协议 |
| 鉴权 | 服务账号密钥（DEV-01） |
| 可用模型 | 租户管理员在模型管理页启用的模型（GOV-05） |
| 计量 | 每次调用按密钥记录 token 数（GOV-04） |
| 适用对象 | 支持 OpenAI 协议的 coding agent，例如 Qwen Code、Codex CLI、Kimi Code。只支持 Anthropic 协议的工具（例如 Claude Code）不能调用平台模型，但仍可以通过 MCP、技能包、SDK 和 CLI 接入平台的其他能力 |

**规则与边界。**

① 知识库检索的范围和过滤强度。检索和清单查询的结果不超出服务账号被显式授予的知识库（NFR-1）。过滤必须做到文件级：MCP 检索与平台工作台检索使用同一条过滤路径，即索引层预过滤加结果层批量校验。旧的开放 API 检索路径只在知识库级校验一次，不做文件级过滤，MCP 检索不得复用它。权限评估失败时，MCP 返回错误，不返回未过滤或部分过滤的结果。无法确认调用者身份时，MCP 拒绝调用。

② 身份与组织查询的边界。持有 `identity:read` 的密钥可以读取本租户的全部组织架构。平台不支持把部分部门授予服务账号，服务账号本身也不属于任何部门，所以这个范围无法收窄。风险控制靠「给不给这个权限位」，签发表单必须醒目提示（DEV-01）。跨租户的部门和用户一律读不到。如果以后要收窄，只能从工具能力上限制，例如只允许按 user_id 单个查询、不提供组织树列举，这属于独立议题。

③ 应用类工具只能操作自己的应用。应用数据、应用状态与日志两类工具，以及 CLI `logs`，只对密钥资源归属人作为 owner 的应用生效，查询他人的应用一律被拒绝。开发者日常不会碰到这个限制，因为首次部署的应用 owner 就是资源归属人。这条规则限制的是密钥泄漏后的影响范围：密钥是保存在开发者电脑上的文件，如果没有这条限制，任何一把密钥泄漏都会让全租户应用的数据和日志被读走。租户管理员要查他人应用的日志，走应用详情页，不走密钥通道。应用状态工具返回审批终态和驳回理由全文。

④ 本地开发三面只以服务账号自身身份执行，持 `delegate` 的密钥被拒绝。鉴权 PRD 定义了两种身份模式：自身身份（模式 S）和代表他人（模式 D，需要 `delegate` 权限位）。本地开发三面只支持模式 S。持有 `delegate` 的密钥在通道入口被拒绝，CLI 在 `login` 时就拒绝，提示「这把密钥配置为委托专用，本地开发请另发一把」。

做出这个决定的依据是：代表他人执行只在有第三方自然人在场时才有意义，而本地开发的两端是开发者本人和他的 coding agent，没有被代表的人。逐个工具看，模式 D 在这里没有用处，还会造成两类损害。模型清单和组织查询的范围本来就是租户级配置，换成被代表用户后结果不变。知识库清单的用途是填写应用级的能力声明，如果按被代表用户返回，开发者会把某一个人的可见范围写进声明，运行期再按访问用户过滤一次，结果是两次收窄，而且不报错。应用数据、状态和日志工具在模式 D 下会把规则 ③ 的「只能操作一个人的应用」扩大成「委托范围内所有人的应用」。

拒绝必须在入口按权限位直接执行，不得实现成「没带委托头就按模式 S 执行」。鉴权 PRD 规定持 `delegate` 的密钥漏传身份头时返回错误、不降级，静默按模式 S 执行正是该文否决的失败方式；而返回一个参数错误码，coding agent 又无法理解原因。

托管应用运行期同样不使用模式 D：访问用户的身份由 app-proxy 根据平台登录态注入（RT-01）。因此应用工场全册没有模式 D 场景。

**验收要点。**

1. 六类工具都能经 MCP 调用。密钥不持有对应权限位时调用被拒绝（按 DEV-01 规则 ① 的表逐个权限位验证）。
2. 经 MCP 检索到的内容不超出服务账号被显式授予的知识库。
3. 用 A 的密钥查询 B 的应用（数据、状态、日志）被拒绝；查询 A 自己部署的应用正常。
4. 支持 OpenAI 协议的工具能调用平台模型并获得流式返回，调用按密钥记录。只支持 Anthropic 协议的工具连接被拒绝，并得到明确提示。
5. 不持 `identity:read` 的密钥调用身份与组织查询被拒绝。持有时能读取本租户组织架构，读不到其他租户的部门和用户。
6. 经 MCP 查询他人应用的日志一律被拒绝，即使密钥属于租户管理员名下的服务账号。
7. 应用状态工具能查到审批驳回状态和驳回理由全文。
8. 经 MCP 检索的结果与服务账号被授予范围的预期集合相等，不多也不少。测试样本须包含未授予的知识库，以及同一知识库内部分文件无权限的情况。
9. 使权限引擎不可用后，MCP 检索返回明确错误，不返回未过滤或部分过滤的结果（NFR-1）。
10. 持 `delegate` 的密钥在 MCP、模型协议面和 CLI `login` 三处都被拒绝，提示指向「委托专用，本地开发另发一把」。验证时须确认它没有按服务账号身份正常执行，也没有只返回一个参数错误码。

**DEV-03 开发技能包（两包）**

> MCP 负责调用，技能包负责告诉 coding agent 怎么用。平台能力的使用说明以开放技能格式随平台版本发布，coding agent 读取后才知道如何写应用包声明、如何调用 SDK。

**需求描述。** 技能包采用开放技能格式，每个包包含 SKILL.md、可运行样例和连通自检脚本，开发者用 `bisheng skills sync` 从自己的平台拉取。首发两个包：

| 技能包 | 使用时机 | 内容 |
|---|---|---|
| 部署纳管 | 准备把应用部署到平台时 | `bisheng-app.yaml` 写法；能力声明（包括密钥引用）；安全红线（不写鉴权、不写连接串、不写密钥）；托管运行契约（DEV-04）；部署流程与预检排障 |
| 平台能力接线 | 写代码调用平台能力时 | SDK 三个模块（DEV-07）：auth、retrieve、storage。另外两种不经 SDK 的接法：模型用官方 OpenAI 客户端加平台注入的 base_url 和密钥；应用数据库用标准库连接平台注入的连接参数，并遵守结构演进规则（RT-05） |

「平台能力接线」包中的 auth 一节必须醒目标注。原因是读取身份是唯一一种写错后应用照常运行、但身份是错的场景，平台不会报任何错误。

技能包分为两个，判断依据是「coding agent 不预先知道会不会失败，以及能否从平台报错中自己学会」。部署纳管的知识必须预先知道，因为预检只报告缺什么，不教怎么写。SDK 和两种标准库接法是同一件事，所以合为一包。两个包对应两种互相独立的使用方式：只部署不集成，以及只集成暂不部署。合成一个包会让每种使用方式都读到无关内容。技能包和平台内引擎读同一份内容，包越少，需要保持一致的内容越少。

**界面与交互。** 本条没有平台界面。技能包被拉到本地用户目录，由 coding agent 直接读取。

**规则与边界。** 技能包从开发者自己的平台拉取，版本与平台一致，不依赖公网。重复执行 `skills sync` 时，平台当前版本覆盖本地内容。`bisheng login` 成功后自动执行一次 sync，开发者不需要单独执行。技能包的触发描述不包含产品名，使用「把本地项目部署到企业的应用平台」这样的通用表述，因为企业部署 BiSheng 时常用自有品牌名。目标平台由 login 凭据决定，与名称无关。

**验收要点。**

1. 执行 `bisheng skills sync` 后，本地有两个包，每个包含可运行样例和自检脚本。自检脚本在配置正确的环境下通过，在缺少配置时给出可读的失败原因。
2. 两个包的内容与平台内引擎使用的平台能力说明是同一份（抽查关键规则一致）。
3. 非 Claude Code 的 coding agent 可以通过 AGENTS.md 引用同一个技能目录。
4. 平台升级后再次 sync，本地技能包更新为平台当前版本的内容。
5. 用不含产品名的自然语言（例如「把这个应用部署到公司的应用平台」）向 coding agent 提出部署要求，能触发「部署纳管」包。
6. 未读技能包时，coding agent 倾向于自建登录页；读过「平台能力接线」包后，coding agent 改为读取平台注入的身份，不写登录页（NFR-1）。

**DEV-04 CLI 命令集**

> 五个命令覆盖接入、本地运行、发布和排障。`deploy` 是 CLI 唯一的发布入口，它与平台内发布走同一条管线。

**需求描述。** `bisheng` CLI 是开发者与平台交互的命令行工具。CLI 安装包由平台自己分发，下载链接在 DEV-01 的接入信息区，纯内网环境也能安装。

**界面与交互。** 命令行就是本条的交互面。

| 环节 | 命令 | 行为 |
|---|---|---|
| 接入 | `login` | 用服务账号密钥登录平台，凭据保存在本地用户目录；登录成功后自动执行一次 `skills sync` |
| 接入 | `skills sync` | 从已登录的平台拉取技能包（DEV-03），用于平台升级后的更新 |
| 本地运行 | `dev` | 在本地运行应用，注入身份并提供本地应用数据库（DEV-05） |
| 发布 | `deploy` | 把当前项目作为一个版本提交发布，管线见下文 |
| 排障 | `logs` | 查看自己应用的运行日志；查询他人应用被拒绝 |

运行日志有三个入口，权限规则和内容范围完全相同，区别只在操作者：

| 入口 | 适用场景 |
|---|---|
| MCP「应用状态与日志」工具（DEV-02） | coding agent 使用，是「部署、读日志、修改、再部署」循环的默认路径 |
| CLI `bisheng logs` | 开发者本人在终端使用，或者未配置 MCP 时使用 |
| 应用详情页 · 运行日志 | 需要图形界面时使用；租户管理员查看他人应用只能走这个入口 |

**发布管线。** `deploy` 依次执行四步：

① 托管预检。平台构建依赖、校验应用包声明并启动探活，判断标准是下文的托管运行契约。预检失败时，`deploy` 直接失败并说明缺失项和改造方法，不生成审批单。如果预检发现改列或删列，开发者必须显式确认（交互确认，或加 `--confirm-schema-change` 参数），否则 `deploy` 被拒绝。迁移前自动留快照（RT-05）。

② 发布前密钥扫描。规则集与平台内发布相同，产物中有明文密钥或连接串时部署被拦截。CLI 输出命中的规则和文件位置，但不输出密钥值本身（NFR-2）。开发者在本地修复后重新部署。

③ 审批。首发和迭代的每次部署都生成审批单，审批人由 GOV-02 的预置流程确定。同一应用同时最多有一张在途审批单，在途期间再次部署被拒绝并提示。审批人和 owner 都可以用待上线版本快照拉起临时预览实例（RT-03）。审批被驳回后，owner 在发布 tab 或通过 MCP 应用状态工具查看驳回理由，修改后重新部署，生成新的审批单。

④ 上线托管。审批通过后，应用在平台托管环境中运行并进入广场（RT-01、RT-02）。

**托管运行契约。** 预检按下表判断应用能否托管。这张表也随「部署纳管」技能包发布，开发者在本地开发时就能对照。

| 平台提供 | 应用不得自带或依赖 |
|---|---|
| 语言运行时 | 数据库、消息队列、缓存等中间件 |
| 应用数据库 | 白名单以外的外网地址 |
| 附件与文件存储 | — |
| 能力总线的各项能力，包括应用密钥的注入 | — |
| 依赖包经平台内网镜像安装 | — |

符合契约的应用保证可以托管。不符合契约的依赖在预检时被拒绝，并给出改造方法，例如把自带数据库改为使用平台应用数据库（做法见「平台能力接线」技能包）。平台不承诺自动改造。

**规则与边界。** 首次部署时，密钥对应服务账号的资源归属人成为应用的唯一 owner。资源归属人是服务账号的必填字段，所以不存在无 owner 的部署。之后只有资源归属人相同的密钥才能再次部署这个应用，换一把归属人不同的密钥部署会被拒绝，提示中说明应用的归属。owner 转移见 §5.2。

发布的输入以 `bisheng-app.yaml` 为准。能力声明和资源档位都写在这个文件里，未声明档位时取默认档（GOV-03）。应用名称、描述和图标也取自这个文件，随部署更新（RT-02）。

可见范围不在应用包里，`deploy` 不处理它。首次上线后，owner 必须到应用详情页设置可见范围，否则只有 owner 能看到应用（GOV-01）。撤回、下线和删除等其他界面操作按需进行（§2.2）。

首次部署的准入条件是密钥上的 `app:manage` 权限位。CLI 不检查资源归属人有没有「创建应用」权限，因为那个权限点只控制界面上的新建入口，两个入口各自独立（GOV-07）。CLI 只以服务账号自身身份执行，持 `delegate` 的密钥在 `login` 时就被拒绝，所以部署的 owner 始终等于资源归属人，不会因任何请求头而改变。

**验收要点。**

1. 五个命令按上表行为可用。密钥被吊销后，CLI 命令报鉴权失败并提示重新 login。
2. 每次 `bisheng deploy`（首发和迭代）都进入审批流（RT-03、RT-04）。发布前扫描与平台内发布使用同一规则集，包括常见凭据正则、数据库连接串和平台密钥前缀（GOV-08），规则集内的样本 100% 被拦截。
3. CLI 部署的应用在广场、权限和审计中的表现与平台内应用一致。`bisheng-app.yaml` 声明的资源档位生效，未声明时为默认档。
4. 依赖平台不提供的中间件（例如自带数据库）的项目在预检时被拒绝，报错说明缺失项和改造方法，且不生成审批单。
5. 同一应用有在途审批单时，再次部署被拒绝并有明确提示。
6. 通过预检和审批的应用在托管环境中正常启动运行。
7. 端到端：开发者在 coding agent 对话中用自然语言（不含产品名）提出部署要求，coding agent 凭技能包、CLI 和 MCP 完成声明补全、部署、预检失败修复和审批状态跟踪。这一段全程不离开本地对话。
8. 承接上条：首次上线后，owner 在应用详情页设置可见范围，被授权的同事能从应用广场打开应用。验证「上线」和「可用」是两个步骤，缺少第二步时同事看不到应用。
9. 用 A 的密钥部署 B 的已有应用被拒绝，提示说明应用的归属。
10. 包含改列或删列的迭代部署，未经显式确认时被预检拒绝；确认后进入管线，并在迁移前自动留快照。
11. `bisheng login` 成功后，本地已有技能包，不需要手动执行 `skills sync`。平台升级后重新执行 `skills sync` 能更新到当前版本。
12. 同一应用的运行日志，经 MCP 工具、CLI `logs` 和应用详情页三个入口获取，内容范围和权限判定一致。

**DEV-05 本地运行与平台身份注入**

> 应用只读取平台注入的身份，不写登录页。`bisheng dev` 在本地注入与线上结构相同的身份，所以同一份代码在本地和线上都能运行。

**需求描述。** `bisheng dev` 在本地运行应用，并以与线上相同的方式注入身份，应用不需要为本地和线上写两套代码。

| 项 | 线上托管运行 | 本地 `bisheng dev` |
|---|---|---|
| 身份来源 | app-proxy 验证平台会话后注入当前访问用户 | CLI 内置的本地代理注入密钥对应的服务账号 |
| 应用读取方式 | 读注入的身份头，或调用 `SDK.auth` | 完全相同 |
| 平台能力按谁的权限放行 | 当前访问用户 | 服务账号被显式授予的范围（NFR-1） |

身份的唯一可信来源是平台注入，应用不得自建登录页或鉴权逻辑（NFR-1）。

**界面与交互。** 本条没有平台界面。`bisheng dev` 的终端输出必须写明当前注入的身份来源和账号，避免开发者误以为自己在以其他人的身份运行。

**规则与边界。**

① 不提供本地身份模拟参数。CLI 不提供 `--as <user>` 一类的参数。这类参数让开发者随意填一个 user_id 就能让 `SDK.auth` 返回那个人，等于一个绕过平台准入的后门。鉴权 PRD 中「裸 user_id 参数」的安全缺口正是这类问题。平台支持代表他人执行，但那条路是开放 API 的模式 D，它需要 `delegate` 权限位和委托范围，经过五道准入检查并留下双归属审计，而且不作用于本地开发三面（DEV-02 规则 ④）。`--as` 和模式 D 的区别在于这次操作是否经过平台授权。

② 本地无法验证不同用户的行为差异。本地注入的是服务账号，不是自然人，本地也没有真实的访问者，所以「张三看到什么、李四看到什么」这类差异在本地无法复现。验证方法是发布后用真实账号访问应用。

③ 权限边界与线上规则一致。本地运行时，应用经 SDK 或 MCP 调用平台能力，按服务账号被显式授予的权限放行，过滤强度和 fail-closed 行为与线上相同。`bisheng dev` 在本地启动一个 sqlite 数据库，并注入与线上同名的连接环境变量，使应用用标准库写的数据访问代码在本地和线上一致（DEV-07）。本地能检索到的知识库不超出服务账号被授予的范围，可能比线上真实用户看到的少。这个差异只会导致「本地看到的少」，不会导致「本地能运行、线上越权」。

**验收要点。**

1. `bisheng dev` 运行时，应用读到的身份是密钥对应的服务账号，注入结构与线上一致，应用代码不需要修改。
2. CLI 没有任何指定其他用户身份的参数。伪造注入头对应用无效，身份的唯一来源是平台注入（NFR-1）。
3. 本地运行时，应用调用知识库检索等平台能力，结果按服务账号被授予的权限过滤。权限引擎不可用时返回明确错误，不返回未过滤的结果（NFR-1）。
4. 应用代码中没有登录页和自建鉴权逻辑。
5. 同一份代码不加修改执行 `bisheng deploy` 上线后，应用在托管环境读到的是当前访问用户的身份（RT-01）。

**DEV-07 bisheng-sdk**

> SDK 只封装平台特有、且写错会造成安全问题的三件事：auth、retrieve、storage。模型调用和应用数据库不进 SDK，因为它们已有行业标准库。

**需求描述。** SDK 首发 Python 版本，提供三个模块。每个模块都要回答「为什么需要 SDK，而不是直接调用」。

| 模块 | 用途 | 为什么需要 SDK | 权限要点 |
|---|---|---|---|
| auth | 读取平台注入的身份 | 读身份是唯一一个写错后应用照常运行、但身份是错的场景，平台不会报错。SDK 用一行调用把正确做法变成默认做法 | 身份唯一来源是平台注入（NFR-1） |
| retrieve | 知识库检索 | 检索必须以当前访问用户的身份进行，而不是以应用自身的身份进行，选错即越权。SDK 把这个选择固定下来 | 托管运行时：结果 = 能力声明中的知识库 ∩ 当前访问用户的可见范围，文件级过滤（GOV-05）；本地运行时按服务账号被授予的权限（DEV-05） |
| storage | 附件文件存取 | 平台必须居中：按应用隔离存取范围，不计入租户存储配额，不向应用暴露底层对象存储 | 托管契约禁止应用自带文件存储（DEV-04） |

下表记录不进 SDK 的两项及其理由，防止实施时按习惯加回来。

| 项 | 不进 SDK 的理由 | 应用怎么用 |
|---|---|---|
| 模型调用 | 模型接口只提供 OpenAI 兼容协议，这本身就是行业标准，官方 `openai` 库可以直接使用。自研封装只省去 base_url 和密钥两行赋值，却让开发者学一套非标准 API，失去官方库的流式、重试和类型支持，并让平台承担这些功能的维护 | 用官方 OpenAI 客户端，base_url 和密钥取平台注入的环境变量 |
| 应用数据库 | 支持封装的理由都能被「注入连接 + 标准库」替代：环境变量引用不是字面量，不会触发密钥扫描；建表和改表由平台根据应用包声明执行，应用只读写已有的表；SQLAlchemy 本身就屏蔽了 sqlite 和 postgres 的差异；租户隔离由注入的连接承担；结构演进预检在平台侧执行 | 用 SQLAlchemy 等标准库连接平台注入的连接环境变量；本地由 `bisheng dev` 提供同名变量（DEV-05） |

**界面与交互。** 本条没有平台界面。开发者接触的是 SDK 包和随包发布的开发者指南。

**规则与边界。** 平台内模板生成的应用（PRD-2）和本地应用使用同一套 SDK 调用方式。SDK 随版本发布开发者指南，内容包括安装、三个模块的用法、模型和数据库的标准库接法，以及与技能包和 CLI 的配合。以后要新增 SDK 模块，必须先证明它同时满足「平台特有」和「写错会造成安全问题」两个条件。

**验收要点。**

1. 三个模块可用：auth 读到平台注入的身份，retrieve 的结果按调用者权限过滤，storage 能存取附件。
2. 不经 SDK 的两条路径可用：用官方 OpenAI 客户端加平台注入的 base_url 和密钥能调用平台模型；用标准数据库库加平台注入的连接环境变量能读写应用数据库。
3. 平台内模板生成的应用与本地引入 SDK 的应用使用同一调用方式。本项依赖 PRD-2 的模板，随 PRD-2 搁置，本版不验收。
4. 开发者指南随版本发布，按指南能走通 login、dev、deploy 的完整流程。

### 3.2 应用运行时与发布（RT）

本域覆盖应用部署之后的全部行为：如何被访问、如何被找到、如何上线、如何留痕、如何退役、出问题时怎么办。CLI 部署的应用和将来在平台内造的应用，从提交发布开始走同一套流程，本域的条目对两者一样适用。

| 问题 | 条目 | 本域的答案 |
|---|---|---|
| 如何被访问 | RT-01 | 复用平台登录，应用不写登录代码 |
| 如何被找到 | RT-02 | 与工作流、助手进入同一个广场 |
| 如何上线 | RT-03、RT-04 | 每次发布都审批，审批对象是能力声明和冻结的快照 |
| 如何留痕与演进 | RT-05 | 版本记录只增不改，表结构变更随发布生效 |
| 如何退役 | RT-07 | 资产保存在平台，只有 owner 能显式删除 |
| 出问题时怎么办 | RT-08 | 应用崩溃只影响自身，自动恢复 |

---

**RT-01 统一入口与平台登录复用**

> 应用不自建登录。用户用平台已有的登录方式登录，已登录用户点开即用，应用不需要写登录代码。

**需求描述。** 每个已发布的应用有一个内网入口 `/apps/{应用标识}`。应用复用平台的登录方式，包括账号密码和 SSO 扫码，与平台登录配置一致。应用自动获得当前访问者的身份和组织信息。

**界面与交互。** 访问时按访问者状态分支处理：

| 访问者状态 | 系统行为 |
|---|---|
| 已登录平台，且在可见范围内 | 直接进入应用，注入访问者的身份和组织信息 |
| 未登录（包括手机扫码） | 跳转到平台登录页（包括已配置的 SSO 方式），登录后回到原应用地址 |
| 已登录平台，但不在可见范围内 | 显示「无权限」页 |

四类兜底页：

| 兜底页 | 触发场景 | 页面内容 |
|---|---|---|
| 无权限页 | 已登录但不在可见范围内 | 应用名、owner、无权限说明、引导联系 owner 或平台管理员开通、「返回广场」按钮。本版没有在线申请入口 |
| 未部署引导页 | 本环境未部署工场运行时层（GOV-10） | 「本环境未启用应用工场」说明、引导联系平台管理员 |
| 已下线页 | 应用处于已下线状态（RT-07） | 应用名、已下线提示、引导联系 owner 或平台管理员、「返回广场」按钮 |
| 应用不存在页 | 访问已删除应用的旧链接或二维码，或访问从未上线（草稿、待上线）的应用 | 「应用不存在或未上线」说明、「返回广场」按钮 |

**规则与边界。** 访问者的身份和组织信息由平台在入口注入，客户端传入或伪造的身份一律无效（NFR-1）。应用不自建登录，也不自己解析凭据。能否进入应用由可见范围决定，入口访问和广场展示使用同一份可见范围（GOV-01），变更从用户的下一次请求起生效。应用标识在首次发布时确定，迭代发布、下线和重新上线都不改变入口地址和二维码，已经分发出去的链接长期有效。

**验收要点。**

1. 已登录平台的用户点开应用链接直接进入，不需要再次登录。
2. 应用能读到当前访问者的身份和组织信息，例如在应用中显示访问者姓名和部门。
3. 未登录的浏览器扫码访问时，跳转到平台登录页（包括已配置的 SSO 方式），登录后直接进入原应用。
4. 不在可见范围内的用户访问时看到「无权限」页，页面包含 owner 和开通指引。
5. 访问已删除应用的旧链接或二维码时看到「应用不存在或未上线」页，不出现报错页。

---

**RT-02 应用广场**

> 已发布的托管应用与工作流、助手并列出现在同一个广场，使用同一套标签体系。用户只看到自己可见范围内的应用。

**需求描述。** 已发布的应用进入应用广场，与工作流、助手并列展示，接入广场已有的标签分类。用户只看到自己可见范围内的应用，可以从广场直接打开使用。

**界面与交互。** 广场卡片与工作流、助手的卡片结构相同，展示图标、应用名、一句话描述和 owner，点击卡片打开应用。

**规则与边界。** 托管应用使用广场已有的标签体系，不新建标签体系。本版不提供给托管应用打标签的入口（§5.2），未打标签的应用在广场默认分类中正常显示。应用的名称、描述和图标取自 `bisheng-app.yaml`，随部署更新，而部署本身经过审批（DEV-04）。名称、描述和图标不属于能力声明，修改它们不触发审批，但计审计（GOV-04）。广场按可见范围过滤，无权限用户的广场中不出现该应用。

**验收要点。**

1. 应用发布并审批通过后，出现在有权限用户的应用广场中。
2. 未打标签的应用在广场默认分类中正常显示，可以被搜索和浏览到。
3. 无权限用户的广场中不出现该应用。
4. 用户能从广场直接打开应用。
5. 广场卡片展示图标、应用名、描述和 owner。owner 修改这些信息后广场随之更新，不生成审批单，修改计审计。

---

**RT-03 发布审批流**

> 任何发布都必须审批，平台不提供免审路径。审批人审的是提交时冻结的待上线版本快照，可以只读审读代码，也可以拉起临时实例预览试用。owner 在审批期间也可以拉起临时实例，查看自己提交的版本在平台上的实际效果。

**需求描述。** 应用发布接入平台审批中心，审批人在审批中心处理发布审批单（审批场景与审批人见 GOV-02）。首次发布和迭代发布都必须审批，平台不提供任何免审配置。

**流程。**

① owner 提交发布。CLI 路径由 `bisheng deploy` 提交（DEV-04）。

② 平台冻结生成待上线版本快照。快照是审批人审读的对象。

③ 平台执行发布前密钥扫描，规则集见 DEV-04。产物中有明文密钥或连接串时，发布被拦截，CLI 输出命中规则和文件位置，不输出密钥值本身（NFR-2）。

④ 平台生成审批单，进入审批中心。审批人由 GOV-02 预置流程确定，收到站内消息和待办（§3.0.3）。提交时必须携带 owner 的主部门，因为部门管理员这一审批人来源依赖它，缺失时审批单会全部落到租户管理员。

⑤ 审批通过后，平台做上线终检，检查运行环境容量（GOV-03）。终检通过时，应用上线并进入广场。终检未通过时，应用进入「待上线（资源不足）」状态（§3.0.2），资源释放后由 owner 手动上线，不需要重新审批。

⑥ 审批驳回时，首次发布的应用回到草稿状态；迭代发布的应用保持已上线，当前版本继续运行，只有待上线版本被标记为驳回。owner 在发布 tab 的审批状态区看到驳回状态和理由全文，也可以通过 MCP 应用状态工具查询（DEV-02）。owner 修改后重新提交，生成新的审批单。

**界面与交互：owner 侧。** 位置是应用详情页的「发布」tab（导航见 §3.0.1）。CLI 部署的应用与其他应用使用同一页面。

| 区块 | 内容 |
|---|---|
| 提交发布 | 「提交发布」按钮和资源档位选择（GOV-03）。CLI 路径由 `bisheng deploy` 提交，不必来此页 |
| 审批状态区 | 当前审批单状态（待审、通过、驳回、已撤回）、驳回理由全文、「撤回」按钮（待审时可用）、待上线版本的预览（待审时可用，状态与操作同下文「预览试用」） |
| 能力声明清单 | 应用声明使用的全部平台能力（定义见 RT-04） |
| 应用密钥 | 本应用使用的第三方密钥：引用名、掩码、状态（已录入或缺少值）、最近修改时间；owner 可以录入、修改和删除（GOV-05） |
| 版本列表 | 全部版本记录和终态，只读（RT-05） |
| 可见范围 | 当前可见范围状态和「设置可见范围」按钮，按钮打开平台通用授权弹窗（GOV-01）。首次上线后必须设置 |
| 运营操作区 | 下线、重新上线（RT-07）；待上线状态时显示「手动上线」（GOV-03） |
| 入口链接与二维码 | 用于分发给同事（RT-01） |
| 危险操作区（底部） | 显式删除，仅 owner 可见（RT-07） |

**界面与交互：审批人侧。** 位置是平台审批中心 → 应用发布场景 → 审批单详情。

| 区块 | 内容 |
|---|---|
| 基本信息 | 应用名、owner、来源（CLI 部署或平台内造）、类型（首发或迭代）、提交时间 |
| 能力声明摘要 | 待上线版本的能力声明摘要（RT-04） |
| 可见范围 | 提交时的快照，标注「仅供参考，可见范围变更立即生效，不经审批」（GOV-01） |
| 资源档位 | 所选档位（GOV-03） |
| 操作区 | 通过、驳回（必须填写理由）、「查看待上线版本」入口 |

审读视图左侧是文件树，右侧是只读代码。审读视图的 tab 包括能力声明完整清单、版本历史，以及迭代时相对上一版本的文件差异。「预览试用」按钮位于顶部。

**预览试用。** CLI 部署的应用没有草稿沙箱，所以审批人和 owner 用待上线版本快照拉起审批期临时预览实例。这个实例复用部署预检的启动探活能力，连接应用的草稿数据库。owner 需要预览，是因为本地运行（DEV-05）覆盖不到托管环境的全部差异，例如构建产物、只读文件系统和出站白名单。

| 项 | 约定 |
|---|---|
| 拉起 | 审批人在审读视图、owner 在发布 tab 的审批状态区按需拉起，平台不预先启动。只有审批单处于待审时可以拉起 |
| 进入 | 每个实例只有拉起它的人能进入。owner 进不了审批人拉起的实例，审批人也进不了 owner 拉起的实例 |
| 回收 | 审批单进入终态（通过、驳回、撤回、取消）时回收；长期未处理时超时回收，默认 7 天，可在部署配置中修改；回收后可以再次拉起 |
| 资源 | 不占用应用运行实例的名额 |

临时预览实例有四个界面状态：

| 状态 | 界面 | 去向 |
|---|---|---|
| 未拉起 | 「拉起预览」按钮 | 拉起 → 拉起中 |
| 拉起中 | 进度；失败时显示原因 | 成功 → 运行中；失败 → 未拉起，可重试 |
| 运行中 | 「打开预览」和「手动回收」 | 审批终态、超时或手动回收 → 已回收 |
| 已回收 | 「重新拉起」按钮 | 拉起 → 拉起中 |

**规则与边界。** 审批人审读的对象是提交时冻结的待上线版本快照。审批期间 owner 可以继续在本地改代码，改动不影响已提交的快照，下一次 `deploy` 才生成新版本。同一应用同时最多一张在途审批单，再次提交前须先撤回。

审批人预览时，应用注入的身份是审批人本人，平台能力按 owner 的权限放行，这是一个审批例外，计审计（NFR-1）。owner 预览时，应用注入的身份是 owner 本人，平台能力按 owner 本人的权限放行，不属于审批例外，拉起和回收同样计审计。owner 只能预览已提交审批的版本；提交之前要验证效果，用本地运行（DEV-05）。审批人和 owner 都可以在草稿数据库中写入试用数据。CLI 部署的应用首次上线时，生产数据库从空库初始化，审批期的试用数据不带入生产。

本版不做审批单的催办和超时提醒（§5.2）。紧急情况下的处理方式是：下线立即止血（RT-07，不需要审批），再部署旧版本走正常审批恢复（RT-05）。

**验收要点。**

1. 首次发布的应用在审批通过前，除 owner 和审批人经审读视图和预览试用外，任何其他用户都不能访问。
2. 审批人在审批单中能看到能力声明摘要、可见范围和资源档位，并能打开待上线版本的只读审读视图（代码、能力声明完整清单、版本历史；迭代时包括相对上一版本的文件差异）。
3. 审批通过后进入上线终检。容量充足时，应用上线并出现在可见范围内用户的广场中（RT-02）。容量不足时，应用进入「待上线（资源不足）」状态，不对外服务，owner 和租户管理员收到通知（§3.0.3）；资源释放后 owner 手动上线成功，不需要重新审批（GOV-03）。
4. 驳回后，owner 在发布 tab 看到驳回状态和理由，修改后能再次提交。
5. 提交的产物包含明文密钥或连接串时，`deploy` 失败并返回命中项和修改指引（与 DEV-04 验收 2 一致）。
6. 审批期间 owner 能撤回审批单，撤回后修改再提交，生成新的审批单。
7. 审批人能在审读视图中用待上线版本快照拉起临时预览实例；审批单进入终态后实例被回收。
8. 审批人预览时，应用注入的身份是审批人本人，平台能力按 owner 权限放行，预览行为计审计。
9. 临时预览实例超时回收后能再次拉起，超时时长取部署配置。
10. 迭代审批被驳回时，应用保持已上线，当前版本继续服务，只有待上线版本被丢弃。
11. 审批单待审期间，owner 能在发布 tab 拉起待上线版本的临时预览实例。应用注入的身份是 owner 本人，平台能力按 owner 本人的权限放行；拉起和回收计审计。owner 不能进入审批人拉起的实例，审批人也不能进入 owner 拉起的实例。

**RT-04 能力声明定义**

> 本条是「能力声明」的唯一定义，并规定迭代发布同样必须审批。

**需求描述。** 能力声明是应用声明使用的平台能力清单。本版包括三项：知识库、模型和密钥引用。密钥引用是应用使用的第三方密钥的名字，密钥值由 owner 在平台上录入（GOV-05）。能力声明写在 `bisheng-app.yaml` 中，发布 tab 和审批单展示的内容都来自它。

**界面与交互。** 本条没有独立界面。能力声明在三处展示，用词统一如下：发布 tab 展示「能力声明清单」，审批单展示「能力声明摘要」，审读视图展示「能力声明完整清单」。

**规则与边界。** 迭代发布与首次发布同样必须审批，即使能力声明没有变化（RT-03）。可见范围的变更不经审批，立即生效，计审计（GOV-01、GOV-04）。

新增或删除密钥引用属于能力声明变更，须经审批。修改已录入密钥的值不属于能力声明变更，不经审批（GOV-05）。

本版不做迭代审批单的变更摘要（§5.2），审批人通过审读视图的文件差异比对。将来补做时，摘要应覆盖能力声明、可见范围、表结构和资源档位四类变更。

**验收要点。**

1. 能力声明和可见范围都没有改变的迭代发布同样生成审批单，审批通过前新版本不上线。
2. 新接入的知识库或模型、新增的密钥引用，都出现在审批单的能力声明摘要中。

---

**RT-05 版本记录与结构演进**

> 每次提交发布生成一条版本记录并标注终态，部署历史是线性的、可审计的。本版不做平台侧回滚，CLI 用户的回退方法是在本地检出旧版本后重新部署。

**需求描述。** 平台在每次提交发布时生成一条版本记录，并在审批结束后标注终态（已上线、被驳回、已撤回）。版本记录同时用于审计追溯、审批快照和资产持久（RT-07），所以即使不做回滚也必须保留。

每条版本记录包含版本号、类型（首发或迭代）、提交时间、终态、代码快照、能力声明、平台注入配置和资源档位。后四项属于同一个快照，将来做回滚时一起回退，避免出现「代码回退了、配置还是新的」。

**表结构演进规则：**

| 变更类型 | 何时确认 | 发布时的行为 |
|---|---|---|
| 加列 | 不需要确认 | 自动迁移 |
| 改列、删列 | `deploy` 时显式确认（DEV-04） | 发布时不再确认；在发布摘要中展示；迁移前自动保存生产数据快照 |

**界面与交互。** 版本列表位于应用详情页 · 版本，展示全部版本记录的版本号、类型、提交时间、终态和能力声明摘要，并提供相邻版本的文件差异。列表只读，不提供回滚入口。

**规则与边界。** 版本记录只增不改，被驳回和已撤回的版本同样留在列表中。本版不做平台侧回滚（§5.2），原因是本册的用户在本地有完整的 git 历史，检出旧版本后重新 `deploy` 就是等价的回退方法，而且同样经过审批。新版本出问题时，第一手段是下线（RT-07），下线立即生效，不需要审批。

**验收要点。**

1. 每次提交发布都生成一条版本记录，包含版本号、类型、提交时间和终态。被驳回和已撤回的版本同样显示在列表中并标注终态。
2. 版本记录不会被覆盖或删除，同一应用的历史版本可以完整追溯。
3. 包含改列或删列的迭代部署，在发布摘要中展示结构变更，并在迁移前自动保存生产数据快照。
4. 版本列表只读，没有回滚入口。

**RT-07 资产持久与显式删除**

> 应用的运行实例可以随时回收，代码和应用数据始终保存在平台存储中。删除只能由 owner 通过显式删除流程完成，除此之外没有任何删除资产的途径。

**需求描述。** 应用的运行实例不保存唯一数据。代码和应用数据保存在平台存储中，每次发布的版本快照（RT-05）提供代码备份。资产只能通过「显式删除应用」流程删除。

**界面与交互。**

| 操作 | 发起人 | 入口 | 确认方式 | 生效表现 |
|---|---|---|---|---|
| 下线 | owner、租户管理员 | owner 在发布 tab 的运营操作区；租户管理员在构建页的卡片上 | 二次确认，说明入口和广场将显示已下线 | 入口和广场显示已下线页（RT-01），资产不受影响 |
| 重新上线 | owner、租户管理员 | 同下线 | 无 | 恢复访问；同样检查运行环境容量（GOV-03） |
| 显式删除 | 仅 owner | 卡片 ⚙️ 菜单的「删除」（与工作流、助手一致），或发布 tab 底部的危险操作区 | 二次确认弹窗，不要求输入应用名，弹窗中说明删除范围；已上线状态下入口置灰，须先下线 | 资产删除，应用进入已删除状态；旧链接和二维码显示「应用不存在或未上线」页 |

三个操作都计审计。

**规则与边界。** 删除的确认强度与工作流相同：保留二次确认，但不要求输入应用名。要求输入应用名的强确认成本高，用户也会用复制粘贴应付，防护效果不随之提高。本册改用前置状态来加强保护：已上线状态下删除入口置灰，提示「请先下线」，owner 必须先下线再删除。草稿、待上线（资源不足）和已下线三种状态可以直接删除，它们的共同点是没有对外服务的运行实例。下线本身有可察觉的后果，同事访问会立刻看到已下线页，所以误操作会被及时发现，并且留有恢复的机会。

确认弹窗必须说明删除范围。托管应用的删除会一并删除代码和应用生产数据（例如用户填报的业务记录），影响比删除一条工作流大，文案不能只写「确定删除吗」。

租户管理员不能删除应用，管理侧的处置手段是下线。owner 离职后的应用归属见 §5.2。

应用下线、空闲回收、实例崩溃和工场运行时层整体不部署时，平台只回收运行实例，不触碰代码存档和版本记录。存档随平台数据一同备份。删除应用时，在途审批单自动取消（§3.0.2），审批人收到站内消息（§3.0.3）。已下线状态下可以提交发布，审批通过后只记为待运行版本，不自动上线；重新上线时同样检查运行环境容量。

**验收要点。**

1. 应用下线或实例回收后重新上线，代码和生产数据完整。
2. 除显式删除流程外，没有任何操作会删除应用资产。
3. 已上线状态下删除入口置灰并提示「请先下线」。下线后可以删除，弹出二次确认（不要求输入应用名），文案说明删除范围包括代码和生产数据。草稿和待上线状态可以直接删除。删除动作可在审计中查到。
4. 下线期间访问入口和广场显示已下线提示，重新上线后恢复。
5. 租户管理员发起删除被拒绝。owner 删除后，在途审批单自动取消，审批人收到站内消息。
6. 已下线状态下提交发布，审批通过后应用不自动上线；重新上线后新版本生效。

**RT-08 稳定性承诺**

> 单个应用崩溃只影响它自己，并自动恢复。版本切换和恢复期间，访问者看到过渡提示，不看到报错页。

**需求描述。** 应用与平台之间、应用与应用之间运行隔离。单个应用崩溃不影响平台其他功能和其他应用，并在 5 分钟内自动恢复。

**界面与交互。** 两个过渡状态都不显示报错页：

| 过渡状态 | 触发场景 | 入口表现 | 结束 |
|---|---|---|---|
| 发布中 | 新版本上线的切换期间 | 显示「发布中」提示 | 切换完成后恢复正常访问 |
| 应用恢复中 | 应用崩溃后的自动恢复期间 | 显示「应用恢复中」提示 | 恢复后恢复正常访问 |

**规则与边界。** 本承诺与运行时形态无关（§1.3 前提 4），所有形态的验收标准和时限相同。5 分钟的恢复时限同时登记为 NFR-6。

**验收要点。**

1. 人为使某个应用崩溃后，平台主要功能和其他应用的访问正常。
2. 崩溃的应用在无人工干预的情况下 5 分钟内恢复可用（NFR-6）。
3. 版本切换期间访问应用不出现报错页，切换完成后恢复正常访问。
4. 崩溃恢复期间访问应用入口看到「应用恢复中」提示，不看到报错页。

### 3.3 治理与管理面（GOV）

本域回答管理员的两个问题：员工自建的应用能不能看到，能不能管住。八个条目按管理对象分为五组：

| 管理对象 | 条目 | 本域的答案 |
|---|---|---|
| 谁能造、谁能用 | GOV-07（能造）、GOV-01（能用） | 都沿用平台已有的权限能力，本册不新建 |
| 每次上线怎么审 | GOV-02 | 平台预置审批流程，部署即生效 |
| 给多少资源、能用哪些能力 | GOV-03、GOV-05 | 档位三选一；能力配置一次，应用声明使用 |
| 留什么痕、密钥怎么管 | GOV-04、GOV-08 | 全链路留痕；密钥四条产品承诺 |
| 装不装 | GOV-10 | 工场运行时层可以整层不装 |

本域的设计取向是默认可用、按需收紧（§1.3 前提 5）。租户管理员不做任何配置，第一次发布也能走通；需要收紧时再逐项配置。本域不建独立的管理后台应用列表，因为租户管理员在构建页天然能看到本租户全部应用，授权、下线和审计分别由 GOV-01、RT-07 和 GOV-04 承担。

**角色与操作权限矩阵。** 下表是全文角色权限的唯一出处，细则以「出处」列的条目为准。✓ 表示有权执行，— 表示无权。

| 操作 | 平台超管 | 租户管理员 | 审批人 | owner | 出处 |
|---|---|---|---|---|---|
| 签发、吊销服务账号密钥（勾 `app:manage` 即放行 CLI 部署） | — | ✓ | — | — | DEV-01、GOV-07 |
| 下线、重新上线应用 | — | ✓ | — | ✓ | RT-07 |
| 删除应用 | — | — | — | ✓ | RT-07 |
| 撤回在途审批单 | — | — | — | ✓ | RT-03 |
| 处理审批单（审读、通过、驳回） | — | ✓（预置流程中的审批人来源之一） | ✓ | — | RT-03、GOV-02 |
| 审批期预览待上线版本 | — | ✓（仅作为审批人时） | ✓ | ✓ | RT-03 |
| 配置发布审批人 | — | ✓ | — | — | GOV-02 |
| 维护资源档位 | ✓ | — | — | — | GOV-03 |
| 查询审计记录 | ✓（跨租户） | ✓（本租户） | — | — | GOV-04 |
| 配置能力总线（模型、知识库） | — | ✓ | — | — | GOV-05 |
| 配置「创建应用」权限（只控制界面入口） | — | ✓ | — | — | GOV-07 |
| 调整应用可见范围 | — | ✓（本租户任一应用，平台既有行为） | — | ✓ | GOV-01 |

平台超管可以通过平台已有的租户切换能力代行租户管理员的全部操作，审计中记录的操作人是平台超管本人。切换后，管理后台、构建页和审计查询都以目标租户为上下文。

删除应用和撤回审批单两个操作只有 owner 能做，平台超管和租户管理员都不能代做。管理侧的处置手段是下线（RT-07）。owner 离职等归属问题见 §5.2。

**GOV-01 权限资源类型与授权**

> 应用的可见范围完全复用构建页卡片 ⚙️ 菜单中的「管理权限」弹窗，与工作流、助手使用同一个入口、同一个弹窗、同一套语义，本册不新建授权界面。可见范围变更立即生效，不经审批，计审计。

**需求描述。** 托管应用注册为平台权限体系的一种资源类型，可见范围可以按用户、部门和用户组授予。

**界面与交互。** 有两个入口，打开的是同一个弹窗：

| 入口 | 位置 | 使用者 | 作用 |
|---|---|---|---|
| 卡片 ⚙️ →「管理权限」（主入口） | 构建页应用列表，与工作流、助手一致 | owner；租户管理员（本租户任一应用） | 日常调整 |
| 发布 tab 的可见范围区 | 应用详情页 · 发布 | owner | 流程引导：展示当前可见范围；首次上线后仍为「仅 owner 可见」时醒目提示，并提供设置按钮 |

发布 tab 也放一个入口，是因为首次上线后设置可见范围是必须的一步。如果只有卡片入口，owner 发布完要返回列表找到卡片再点齿轮，操作流程会中断。发布 tab 的入口只是同一个弹窗的第二个触发点，加上一处状态展示，不是第二套授权界面。

卡片 ⚙️ 菜单现有「管理权限、创建模板、复制、删除」四项。对托管应用，「管理权限」和「删除」直接复用，「创建模板」和「复制」不显示，因为它们涉及代码和应用数据的复制，语义尚未定义。删除项受 RT-07 的前置状态约束，并且只对 owner 显示。

**规则与边界。** 可见范围变更从被授权用户的下一次请求起生效，作用于入口访问和广场展示（RT-01、RT-02），不经审批，计审计（GOV-04）。审批单中展示的可见范围是提交时的快照，标注「仅供参考」，因为它在审批期间可能被修改。可见范围不属于版本快照（RT-05）。应用首次上线时默认只有 owner 可见。

租户管理员可以直接查看和调整本租户任一应用的可见范围。这是平台既有权限模型的结果，工作流和助手也是如此，本册保持一致，变更计审计并记录变更人。

**验收要点。**

1. 两个入口（卡片 ⚙️ →「管理权限」和发布 tab 的可见范围区）打开的是同一个弹窗，可以按用户、部门和用户组授予。
2. 授权后，被授权用户的下一次请求就能在广场中看到并打开应用；撤销授权同样立即生效（RT-01、RT-02）。
3. 首次上线后未设置可见范围时，发布 tab 醒目提示「仅 owner 可见」并提供设置入口。
4. 租户管理员能查看和调整本租户任一应用的可见范围，变更计审计并记录变更人（GOV-04）。
5. 可见范围变更不触发审批，也不进入版本快照（RT-03、RT-05）。
6. 托管应用卡片的 ⚙️ 菜单只显示「管理权限」和「删除」两项，不显示「创建模板」和「复制」；已上线状态下删除项不可用并提示须先下线（RT-07）。

**GOV-02 发布审批场景（平台预置流程）**

> 审批开箱即用，不需要先配置。平台预置一套流程，审批人是 owner 所属部门的部门管理员和租户管理员，或签，任何一人处理即出结果。

**需求描述。** 应用发布作为审批中心的一个新场景接入。平台预置一套默认审批流程，部署后立即生效，租户管理员不需要先配置。租户管理员可以在此基础上修改审批人和审批链。

**预置流程规格：**

| 项 | 取值 | 说明 |
|---|---|---|
| 场景 | 「应用发布」 | 随部署启用 |
| 分支 | 一条无条件分支 | 所有发布都审批，没有直通分支 |
| 节点 | 一个节点，或签 | 任何一个审批人处理即出结果 |
| 审批人来源 | ① owner 主部门的部门管理员 ② 租户管理员，两者并列；单租户部署下 ② 改为平台超管 | 复用审批中心已有的两种审批人来源 |

**界面与交互。** 管理后台 → 审批中心 → 场景配置中新增「应用发布」场景，展示预置流程的当前配置，可以修改审批人和审批链（复用审批中心已有的配置交互）。界面不出现「未配置审批人」的提示，因为预置流程保证始终有审批人来源。

**规则与边界。** 每次发布（首发和迭代）都必须审批，没有免审路径，也没有免审配置项。

审批人是部门管理员和租户管理员的并集，或签，谁先处理谁决定结果。部门管理员负责本部门人员的日常治理，租户管理员是更高一级的权限，也在部门管理员缺位时承接审批，所以不需要额外的兜底规则。部门取 owner 的主部门，不向上级部门查找。owner 没有部门，或主部门没有部门管理员时，这一来源为空，审批由租户管理员承接。两个来源同时为空时，审批单进入审批中心的异常状态，并通知管理员处理，发布不被放行，也不会无提示地卡住。

提交人本人在审批人候选中时（例如 owner 自己就是部门管理员），系统跳过提交人，由其他候选人审批。如果全租户只有一名管理员且没有其他候选人，允许自审，审计中加自审标注。

单租户部署下，租户管理员来源改为平台超管。单租户下平台超管实际承担租户管理员的职责，这样「部署即生效」在单租户形态下同样成立。如果不改，这一来源始终为空，owner 又没有部门管理员时，第一次发布就会卡住。

预置流程覆盖每个租户，包括新建的租户：租户创建时同步写入预置流程。预置按「租户 + 场景」判断是否已存在，已存在时跳过，所以租户管理员改过的配置在平台升级后不会被重置。

**验收要点。**

1. 全新部署后不做任何审批配置，直接发布应用就能生成审批单，审批单落到 owner 主部门的部门管理员和租户管理员。
2. 部门管理员或租户管理员任一人处理后即出结果，另一方的待办同步关闭。
3. owner 没有部门或部门没有部门管理员时，审批单落到租户管理员，发布不卡住。
4. 租户管理员能修改审批人和审批链，修改后平台升级不会重置。
5. 新创建的租户中首次发布应用，能正常生成审批单。
6. 单租户部署下不做任何审批配置即可发布，审批单落到平台超管。
7. 提交人在审批人候选中时，节点跳过提交人本人；只有一名管理员的租户中的自审单在审计中带自审标注。
8. 两个审批人来源都为空时，审批单进入异常状态并通知管理员，发布不被放行。

**GOV-03 资源档位**

> 应用的资源规格只能从平台预置的档位中选择，不提供自定义。档位是运行环境给容器设定资源上限的唯一依据。

**需求描述。** 平台预置资源档位，应用发布时从中选择，不提供自定义资源规格。

本版有三个档位。下表是初始默认值，由部署配置提供，平台超管可以修改。

| 档位 | 默认规格 | 适用说明 |
|---|---|---|
| 轻量 | 0.5 核 CPU / 1 GB 内存 | 表单、台账类轻量应用 |
| 标准 | 2 核 CPU / 4 GB 内存 | 多数日常业务应用 |
| 性能 | 4 核 CPU / 8 GB 内存 | 数据处理量大、访问人数多的应用 |

轻量档原定 1 核 / 2 GB，实现时下调为 0.5 核 / 1 GB。原因是 1 核让 CPU 配额先于机器本身成为上线瓶颈：8 核机器按 0.8 的超售系数只能同时运行 6 个轻量应用，而实测五个在线应用合计只用了 0.05% CPU。0.5 核下带重依赖的应用冷启动约 2.4 秒，健康检查窗口仍有 4 倍余量（F055 spec 决议-10）。

**界面与交互。**

| 界面 | 位置 | 内容 |
|---|---|---|
| 资源档位管理 | 管理后台 → 系统管理 → 「资源档位」tab，仅平台超管可见；未部署工场运行时层时不显示 | 档位列表：名称、CPU、内存、适用说明、启用状态、使用中的应用数。可以在行内编辑规格和说明。停用档位时提示影响：存量应用不受影响，发布时不再可选 |
| 发布时选择档位 | 发布 tab；CLI 路径在 `bisheng-app.yaml` 中声明 | 从启用中的档位选择，每档展示规格和适用说明 |

**规则与边界。** 只能从预置档位中选择，不提供自定义规格。每个应用只有一个实例，不提供实例数和并发调节（§5.1）。默认档是轻量档：发布 tab 默认选中它，CLI 未声明档位时也取它。停用档位只阻止新的选择，存量应用继续按原档位运行和迭代。档位规格的修改从应用下一次发布或重新上线起生效。

档位与运行时形态无关：单机形态由运行时组件设容器资源上限，k8s 形态映射为 Pod 的 requests 和 limits。

上线可能因运行环境容量不足而失败（单机形态是机器资源耗尽，k8s 形态是集群无可调度资源）。上线终检发现容量不足时，审批单保持通过，应用进入「待上线（资源不足）」状态（§3.0.2），并通知 owner 和租户管理员（§3.0.3）。资源释放后，owner 在发布 tab 手动上线，不需要重新审批。

应用代码存档和附件本版都不计入平台存储配额（§5.2）。模型 token 用量只计量、不设上限。本版不做租户级实例数配额（§5.2）。

**验收要点。**

1. 资源档位由平台预置，平台超管可以修改规格和启用状态。发布时只能从预置档位中选择，没有自定义规格、实例数或并发调节的入口。
2. 未声明档位的 CLI 应用使用轻量档；发布 tab 默认选中轻量档。
3. 档位停用后，存量应用照常运行和迭代发布，新发布不能再选该档位。
4. 所选档位在运行环境中实际生效，容器或 Pod 的资源上限与档位规格一致。
5. 上线终检容量不足时，应用进入待上线状态并提示原因；资源释放后 owner 手动上线成功，不需要重新审批。

**GOV-04 全链路审计**

> 应用的创建、能力接入、运行期调用、发布运维和密钥事件全部留痕，管理面可以查询和导出。租户管理员查本租户，平台超管可以跨租户查。

**需求描述。** 应用工场的全部关键事件都记录审计，审计记录可以在管理面查询。

审计事件清单如下。每类记录至少包含操作人、时间、对象、动作和结果，「特有内容」列只列该类事件额外记录的内容。

| 事件类别 | 来源条目 | 特有内容 |
|---|---|---|
| 应用创建（CLI 首次部署） | DEV-04 | 应用名 |
| 能力声明变更 | GOV-05 | 应用、能力声明变更内容 |
| 应用运行期的能力调用（检索、模型） | GOV-05、GOV-08 | 双归属：调用方是哪个应用，以哪个访问用户的名义调用 |
| 应用访问 | RT-01 | 访问用户、应用、访问时间 |
| 生产数据编辑 | 应用详情页 · 数据 | 应用、数据对象、编辑动作 |
| 发布、下线、重新上线、删除 | RT-03、RT-07 | 应用、版本、结果 |
| 模型调用 | DEV-01、GOV-08 | 归属（服务账号密钥调用归服务账号，应用运行期调用归应用）、模型、时间、token 数。逐条记录，本版不做聚合账单（§5.2） |
| 应用密钥的录入、修改、删除 | GOV-05 | 应用、引用名、动作；不记录密钥值 |
| 密钥签发、权限位修改、吊销、自动失效 | DEV-01、GOV-08 | 密钥掩码、动作、失效原因；应用运行期凭据的自动签发和回收同样记录 |

**界面与交互。** 审计查询在管理后台的审计页进行，分两部分。

| 位置 | 承载的事件 | 构成 |
|---|---|---|
| 已有审计 tab（扩展事件类型） | 操作类事件：应用创建、能力声明变更、生产数据编辑、发布运维、密钥事件、可见范围变更、名称描述图标修改 | 筛选：时间范围、操作人、事件类型、对象应用；平台超管另有租户筛选。列表列：时间、操作人、对象、动作、结果，平台超管视角另有租户列。支持导出 |
| 新增「应用运行记录」tab | 运行期高频记录：模型调用、应用运行期的能力调用、应用访问 | 三类记录各自一个子视图。筛选：时间范围、应用、服务账号密钥（模型调用）、访问用户；平台超管另有租户筛选。列表列按类别不同：模型调用列出归属、模型、token 数；能力调用列出应用、能力、以谁的名义调用、结果；访问记录列出访问用户、应用、时间。支持导出。未部署工场运行时层时不显示 |

**规则与边界。** 审计记录中不出现密钥明文等敏感值（NFR-2）。租户管理员可以查询本租户的全部事件，跨租户查询仅限平台超管。开发者没有自助查询入口，需要时由租户管理员导出后转交。owner 在应用侧自查审计和访问记录本版不提供（§5.2）。

**验收要点。**

1. 上表每类事件发生后，在审计页能查到记录（操作人、时间、对象、动作）。
2. 审计记录中不出现密钥明文等敏感值。
3. 模型调用可以按密钥或按应用追溯到具体调用记录，包括模型和 token 数。
4. 租户管理员查不到其他租户的审计事件；平台超管可以跨租户查询。

> 当前实现状态：三类运行期记录已经写入，「应用运行记录」tab 尚未实现，验收 1 和验收 3 在它实现前无法通过。

**GOV-05 能力总线**

> 模型和知识库在管理面配置一次，租户内的应用通过能力声明使用。应用调用第三方系统用的密钥由 owner 录入，平台在运行时注入。业务人员和 AI 都不接触底层的账号和端点，应用代码里也不出现密钥值。

**需求描述。** 能力总线是应用使用平台能力的统一通道。底层账号和端点只在管理面配置一次，应用通过能力声明获得使用权，发布审批通过即授权（RT-03、RT-04）。本版能力总线包括模型、知识库和应用密钥三项。模型和知识库的配置全部复用已有界面，不新建配置页；应用密钥由 owner 在应用详情页录入。

**界面与交互。**

| 能力 | 谁在哪里配置 | 应用如何获得使用权 |
|---|---|---|
| 模型 | 租户管理员在已有的模型管理页配置服务商凭据并启用模型。租户内的助手、工作流和托管应用共享这份配置 | 应用在能力声明中写模型名（与模型管理页的名称相同），审批通过后，平台在运行时注入调用通道 |
| 知识库 | 没有新增配置。建库和授权走已有的知识库管理和权限体系 | 应用在能力声明中写要使用的知识库，审批通过即授权。运行时检索范围见下文 |
| 应用密钥 | owner 在应用详情页 · 发布的「应用密钥」区录入，只用于本应用 | 应用在能力声明中写引用名，审批通过后，平台在应用启动时把值注入为环境变量 |

**规则与边界。** 能力配置只在管理面进行，应用侧没有任何底层账号或端点的配置入口。

已上线应用声明的能力被收回时（模型下线、知识库删除或权限收回），应用调用该能力得到明确错误，不回退到旧值，应用的其余功能保持可用。owner 在发布 tab 看到失效提示。

**应用密钥。** 应用调用平台以外的系统（例如企业微信 webhook、内部 ERP 接口）时需要密钥，这类密钥由 owner 在发布 tab 的「应用密钥」区录入。应用在 `bisheng-app.yaml` 的能力声明中只写引用名，平台在应用启动时把值注入为同名环境变量。密钥值加密存储，录入后任何界面只显示引用名和掩码，平台不回显明文，也不把它写入日志（NFR-2）。只有 owner 能录入、修改和删除密钥；租户管理员能看到引用名和状态，看不到值。

新增或删除引用名属于能力声明变更，随发布审批生效（RT-04）。修改已录入的值不经审批：owner 保存后，平台重启应用实例使新值生效，修改动作计审计（GOV-04）。

能力声明引用了一个还没有录入值的密钥时，`deploy` 输出警告，发布 tab 和审批单都标注「缺少值」，但发布不被阻断。这样设计是因为应用首次部署后才在平台上存在，owner 只能在首次部署之后录入值。应用运行时，缺少值的环境变量为空，应用调用第三方系统会失败，表现与能力被收回相同。owner 补录值后，平台重启应用实例使其生效。owner 删除一个仍被已上线版本引用的密钥时，弹窗提示影响；删除后该引用注入为空。

**知识库检索范围。** 应用运行时的检索结果经过两层过滤。第一层是声明层：应用没有声明的知识库对应用完全不可访问，即使当前访问用户本人有权限。第二层是用户层：按当前访问用户的身份逐个资源鉴权，在声明范围内，检索结果与该用户在平台上自行检索的结果完全相同。

声明层是对一份显式白名单的收窄，不是对两个主体的可见集合求交集。鉴权 PRD 否决的是「权限取交集」，两者不是一回事。

应用运行时的「当前访问用户」由 app-proxy 根据平台登录态注入，这与鉴权 PRD 模式 D 的委托头是两套机制。实现时不得把应用内的用户身份传递挂在模式 D 委托头上：模式 D 禁止以超级管理员或租户管理员为委托目标，复用它会让管理员无法使用任何托管应用。

过滤强度是文件级，与平台工作台检索使用同一条过滤路径（与 DEV-02 规则 ① 相同）。检索遵循 fail-closed（NFR-1）：无法取得当前访问用户的身份时，检索被拒绝，不回退为按应用声明全量返回；权限评估失败时返回明确错误，不返回未过滤或部分过滤的结果。

**验收要点。**

1. 租户管理员在管理面完成一次能力配置后，租户内的应用不需要再配置就能声明使用。
2. 应用侧没有任何底层账号或端点的配置入口。
3. 生产实例实际可用的能力 = 其声明且经审批的能力，未声明的能力不能调用。审批期预览按「已声明的能力 + owner 本人的权限」放行（RT-03）。
4. 收回某个已上线应用声明的能力后，调用该能力返回明确错误，应用其余功能可用，owner 看到失效提示。
5. 用户本人有权限、但应用没有声明的知识库，经该应用检索不到。
6. 应用声明了、但当前访问用户无权限的知识库内容（包括库内无权限的文件），不出现在该用户的检索结果中。声明范围内的检索结果与该用户在平台上自行检索的结果相同。
7. 使权限引擎不可用后，应用内检索得到明确错误，不返回未过滤或部分过滤的结果（NFR-1）。
8. owner 在发布 tab 录入密钥后，应用运行时能从同名环境变量读到值；任何界面、日志和审计记录中都不出现密钥明文。
9. 修改已录入密钥的值不生成审批单，新值在应用实例重启后生效；新增引用名的发布生成审批单，审批单摘要中出现该引用名。
10. 能力声明引用了未录入值的密钥时，`deploy` 输出警告，审批单标注「缺少值」，发布不被阻断。

**GOV-07 应用工场权限控制**

> 本册在租户内不新增任何配置项。界面入口沿用已有的「创建应用」权限点，CLI 入口由密钥上的 `app:manage` 权限位控制，两者互不校验。

**需求描述。** 谁能创建托管应用，由两个入口各自的准入条件决定。本册不新增一级菜单，也不新增权限点。

| 入口 | 准入条件 | 由谁控制 |
|---|---|---|
| 界面（构建 → 应用 → 新建） | 已有的「创建应用」权限点（「构建」菜单的子项） | 租户管理员配置角色 |
| CLI（`bisheng deploy` 首次部署） | 服务账号密钥上的 `app:manage` 权限位（DEV-01） | 租户管理员签发密钥时勾选 |

**界面与交互。** 托管应用涉及三个使用面，都位于已有页面中，可见性沿用已有的菜单权限。升级前后，角色配置面上的项数不变。

| 使用面 | 位置 | 可见性控制 |
|---|---|---|
| 构建面（创建和管理自己的应用） | 构建页应用列表 | 已有的「构建」菜单权限；新建入口另受「创建应用」控制 |
| 治理面（管理全租户的应用） | 同一个页面，租户管理员天然能看到本租户全部应用 | 「构建」菜单权限加租户管理员身份 |
| 使用面（使用同事的应用） | 应用广场和 `/apps/{slug}` | 已有的应用广场可见性加应用可见范围（GOV-01） |

**规则与边界。**

① 界面入口。「创建应用」只控制新建入口，不影响已有应用的运行、访问、迭代发布和管理。它是「构建」的子权限，关闭「构建」时它一并失效。有「构建」但没有「创建应用」时，用户可以管理已有应用，但不能新建。这套组合早已对工作流和助手生效，托管应用只是被它管理的第三种类型。默认值沿用已有设置：新建角色默认开启「构建」、不开启「创建应用」，所以升级后没有任何角色凭空获得新建能力。复用这个权限点的代价是无法单独对托管应用灰度开放，本册判断这个代价可以接受（§5.2）。

② CLI 入口。界面的权限点和菜单都不参与 CLI 判定。CLI 的请求主体是服务账号，服务账号没有角色。如果改为检查资源归属人的角色权限，就违反了鉴权 PRD「资源归属人只决定归属、不出借权限」的规定，还会导致「资源归属人一被停用，其名下密钥立即失效」的连带效应。CLI 入口并不因此失控：密钥只能由租户管理员签发，开发者没有自助入口；部署出的应用 owner 始终是资源归属人，责任和审计落在具体的人身上。

③ 灰度开放。灰度开放是运营动作，两个入口分别处理：界面入口按角色勾选「创建应用」，CLI 入口按人签发带 `app:manage` 的密钥。两边都不另设开关。

**验收要点。**

1. 没有「创建应用」权限的用户在构建页看不到新建入口，其已有应用的运行、访问、迭代发布和管理入口不受影响。
2. 密钥未勾 `app:manage` 时，CLI 首次部署被拒绝并有明确提示；勾选后可以部署，与资源归属人有没有「创建应用」权限无关。
3. 资源归属人的角色权限被修改或账号被停用后，其服务账号名下已有密钥的部署行为不变。
4. 本册在角色权限体系中没有新增：升级前后角色配置面的菜单项和权限点数量相同；三个使用面分别位于已有的构建页和应用广场中。

**GOV-08 开放 API 鉴权改造与密钥承诺**

> 本条管两件用户能感知的事：v2 开放 API 从「内网可信」改为密钥鉴权，以及密钥的四条产品承诺。细化需求和验收以鉴权 PRD 为准。

**需求描述。** 已有的 v2 开放 API 从「内网可信」模型改为密钥鉴权，签发和吊销在管理面进行（表单和流程见 DEV-01）。v2 开放 API 改造的细化需求和验收以鉴权 PRD 为准。

应用运行期使用的凭据不作为产品概念，也不设管理入口，owner 和使用者感知不到它。它的行为分别由 GOV-05（能力生效与收回）、RT-07（下线）、GOV-04（审计）和本条验收 5 约束。

**密钥底座与四条产品承诺。** 全平台各类密钥使用同一个底座，实现细节以鉴权 PRD 为准。

| 承诺 | 内容 |
|---|---|
| 不暴露明文 | 明文只在签发时展示一次，此后一切界面只显示掩码（前缀加末四位）。服务端只存 SHA-256 单向哈希，明文不可还原 |
| 可吊销且立即生效 | 吊销是软删除，记录保留供审计。吊销时主动清除缓存，生效时间上限 5 秒。支持一键吊销某个服务账号名下的全部密钥 |
| 可被扫描拦截 | 服务账号密钥的前缀是 `bs-sak-`，该前缀内置在发布前密钥扫描规则中（RT-03、DEV-04），也可以注册到代码托管平台的密钥扫描规则 |
| 全部事件留痕 | 签发、吊销和自动失效都计审计（GOV-04） |

**流程：v2 开放 API 鉴权改造。**

① 发布即带鉴权，不设兼容开关，也不设兼容窗口。任何「默认关闭」的过渡开关都意味着升级后匿名越权通道仍然开着，鉴权 PRD 已否决这种做法。升级后所有 `/api/v2` 调用必须携带密钥，没有密钥的调用一律返回 401。裸 `user_id` 参数随本版一并移除。

② 迁移动作必须在升级前完成。发布说明在醒目位置给出三步指引：为每个存量调用方创建服务账号并按最小权限授权；签发服务账号密钥；修改调用方代码，增加 `Authorization` 头（原来的裸 `user_id` 参数改为 `X-Bisheng-On-Behalf-Of` 头）。签发人是租户管理员，迁移责任人是各调用方的 owner。

③ 平台不做任何自动迁移，不改动任何存量用户和资源。原 `default_operator` 配置项随本版移除，它指向的用户保持普通用户身份，名下资源不变。从升级到管理员配好密钥之间存在接入空窗，须在升级沟通中说明。

**界面与交互。** 管理后台的 API 密钥管理页是平台密钥和服务账号管理的唯一入口，也就是鉴权 PRD 服务账号模块的承载页。服务账号模块包括列表和详情页（概览、API 密钥、资源授权），构成和验收以鉴权 PRD 为准。本册在其上只增加两项：签发表单中的「本地开发工具包」三个权限位，以及详情页的接入信息区（DEV-01）。应用运行期凭据没有管理界面。

**规则与边界。** 应用运行期能力的生效和收回，在产品上一律以「能力」表述，不以「凭据」表述。发布审批通过后，新的能力声明生效，旧声明立即失效（GOV-05、RT-04）；应用下线时冻结，删除时回收（RT-07）。底层凭据的重签和吊销随之自动发生，不单独暴露操作入口。

应急处置统一为下线（RT-07）。怀疑凭据泄漏或应用滥用平台能力时，一律下线该应用。本版不提供「应用仍可访问、但能力调用失败」的中间状态，因为这种状态对使用者来说就是应用坏了。

服务账号密钥是否同时能用于本地开发三面和开放 API，由同一张权限位清单上勾了哪些权限位决定，与凭据类型无关。

**验收要点。**

1. 服务账号密钥能在管理面签发和吊销；明文只在签发时展示一次，此后所有界面只显示掩码。
2. 吊销后 5 秒内调用被拒绝；一键吊销某个服务账号时，其名下全部密钥同时失效。
3. 密钥的签发、吊销和自动失效事件都计审计（GOV-04）。
4. 存量环境升级后，不带密钥的 v2 调用一律返回 401，没有任何回退路径（细化验收以鉴权 PRD 为准）。
5. owner 的自然人账号被禁用后，其应用照常运行，可见范围内的用户正常使用。服务账号密钥同样不随自然人账号禁用而失效，须由租户管理员处理其服务账号。
6. 迭代发布上线后，应用运行期能使用的能力就是新能力声明所列的能力，旧声明中已删除的能力立即不可用（GOV-05、RT-04）。
7. 管理面没有应用运行期凭据的查看或吊销入口，应用的应急处置只有下线。
8. 存量 v2 调用方迁移时签发的是服务账号密钥（绑定不可登录的服务账号）。

**GOV-10 可选部署与运行时形态**

> 不需要应用工场的客户可以整层不装，平台其余功能的行为不变。装的客户按自己的基础设施选择单机形态或 k8s 集群形态，两种形态的产品行为完全相同。

**需求描述。** 应用工场按层可选部署。不装的环境没有新增的常驻负担，已有功能的行为不变。安装工场运行时层时，部署人员在部署时选择一种运行时形态：单机形态（compose 或 systemd，默认）或 k8s 集群形态。

**界面与交互。** 本条没有配置界面。部署形态在部署时决定，产品上唯一的可见差异是未部署时相关入口和页面不显示。

| 层 | 用户可感知的能力 | 能否独立部署 |
|---|---|---|
| 平台核心 | 平台已有的全部功能 | 必装 |
| 开放能力层 | 服务账号密钥的本地开发用途、OpenAI 兼容模型接口、MCP 工具面 | 可以独立于工场运行时层部署 |
| 工场运行时层 | 应用托管运行、应用广场中的托管应用、发布管线 | 可以整层不装；装则选单机或 k8s 形态 |

**规则与边界。** 未部署工场运行时层时，构建页不出现「托管应用」类型，应用广场不出现托管应用，访问应用路径显示未部署引导页（RT-01）而不是报错，平台其余功能的行为不变。

未部署开放能力层时，服务账号和密钥模块本身仍然存在，因为它随鉴权 PRD 交付，是 v2 开放 API 的唯一接入方式。不显示的只有应用工场的增量：签发表单的「本地开发工具包」三个权限位、详情页的接入信息区，以及 OpenAI 兼容模型接口和 MCP 工具面。

单机形态和 k8s 形态的产品面必须一致（§1.3 前提 4）：发布管线、资源档位、审批、权限、日志和崩溃自愈在两种形态下行为相同，凡本册验收项在两种形态下表现必须相同。形态差异只出现在运行时组件内部，例如资源档位在单机形态下设为容器资源上限，在 k8s 形态下映射为 Pod 的 requests 和 limits（GOV-03）。运行时形态在部署时一次性选定，本版不支持形态之间的迁移。

> 当前实现状态：单机形态已实现；k8s 形态只有需求规格（F059 spec），设计与实现尚未开始。

**验收要点。**

1. 未部署工场运行时层的环境中，平台已有功能的回归测试全部通过，行为没有变化。
2. 未部署工场运行时层时，访问应用路径显示未部署引导页，不出现报错。
3. 只部署开放能力层时，服务账号密钥的本地开发用途、OpenAI 兼容模型接口和 MCP 工具面可以正常使用。
4. 未部署开放能力层的环境中，服务账号模块照常可用；签发表单不出现「本地开发工具包」三个权限位，详情页不出现接入信息区；OpenAI 兼容模型接口和 MCP 工具面不可访问。
5. 本册全部验收项在单机和 k8s 两种形态下表现一致。

## 4. 非功能需求

本节只列产品可感知的跨域不变量，具体行为落在所引用的条目中。

**NFR-1 权限与数据边界。**

1. 应用（包括其中的 AI）能访问的知识库范围不超出当前调用主体自身的权限。线上的调用主体是当前访问用户，包括文件级权限（RT-01）；本地运行和 MCP 的调用主体是服务账号，范围是被显式授予的资源（DEV-02、DEV-05）。托管运行时，范围进一步收窄为「能力声明中的知识库 ∩ 当前访问用户的可见范围」（GOV-05）。
2. 未上线的应用只有 owner 能访问，owner 在审批期间经预览试用访问（RT-03）。唯一的例外是审批期间审批人经审读视图和预览试用访问，其中平台能力按 owner 权限放行，属于审批例外，计审计（RT-03）。此外没有任何其他途径。
3. 应用获得的身份信息唯一可信来源是平台注入，客户端伪造的身份一律无效（RT-01、DEV-05）。
4. 权限评估遵循 fail-closed：无法确认调用者或访问用户的身份时拒绝，不回退为放行；权限评估失败时报错，不返回未过滤或部分过滤的结果（GOV-05、DEV-02）。

**NFR-2 密钥不暴露。** 密钥值不写入日志、不回显、不进入代码，一切界面只显示引用名和掩码。owner 录入的应用密钥加密存储，录入后不回显明文。平台签发的密钥在服务端只存单向哈希，明文不可还原，只在签发时展示一次（GOV-08）。发布产物不得包含明文密钥或连接串，发布前扫描拦截，扫描规则内置平台密钥前缀（RT-03、DEV-04）。

**NFR-3 资产持久。** 运行实例可以随时回收，代码和应用数据始终保存在平台存储中，删除只能通过显式删除流程（RT-07）。

**NFR-4 可选部署。** 不部署工场运行时层的环境，平台已有功能没有新增的常驻负担，行为不变（GOV-10）。

**NFR-5 审计可追溯。** 应用创建、能力接入、发布、删除、生产数据编辑和密钥事件全部留痕（GOV-04）。

**NFR-6 稳定性。** 应用与平台、应用与应用之间运行隔离，单个应用崩溃只影响自身，并在 5 分钟内自动恢复（RT-08）。

## 5. 范围外与顺延

### 5.1 本版明确不做

| 项 | 说明 |
|---|---|
| 本地身份模拟参数（`bisheng dev --as`） | 它是绕过平台准入的后门（DEV-05）。验证不同用户行为差异的方法是发布后用真实账号访问 |
| 公网域名、公开可见、SEO、水印 | 应用只有内网入口，由权限体系控制访问，没有「公开」开关 |
| 自定义资源规格、实例数与并发调节、自动扩缩容、GPU、应用间编排、自定义运行环境构建 | 每个应用一个实例，从预置档位中选择规格（GOV-03） |
| token 用量限制 | 私有化环境使用自有模型和算力，本版只计量不限制 |
| 运行时形态之间的迁移、同一环境同时运行两种形态 | 运行时形态在部署时一次性选定；多机调度只在 k8s 形态内由 k8s 承担 |
| 本地端专有插件 | 四种接入方式全部使用标准协议，任何 coding agent 不需要改造即可接入 |
| Anthropic 兼容模型接口 | 模型接口只提供 OpenAI 兼容协议，平台不实现协议的长尾语义（DEV-02） |

### 5.2 顺延到 v3.1

本版的目标是先走通最小闭环：拿到密钥、本地开发、部署、审批、上线、设置可见范围、同事使用。不在这条链路上的功能一律顺延。下表记录每一项顺延的理由和将来补做时的注意事项，避免重新论证。

| 顺延项 | 顺延理由 | 补做时的注意事项 |
|---|---|---|
| 租户级实例数配额（原属 GOV-03） | 实例数配额防不住它要防的问题：保护机器的是运行环境的准入控制；实例数只数个数不看档位，三档资源差 8 倍；单租户部署完全用不上 | 必须以资源量（CPU、内存）为单位，不能以实例数为单位 |
| 平台侧回滚（原属 RT-05） | 本册用户在本地有完整 git 历史，检出旧版本后重新部署就是等价方法，并且同样经过审批 | 版本快照的四要素（代码、能力声明、注入配置、资源档位）本版已按同一快照存储，补做时一起回退即可。应急止血始终是下线 |
| 迭代审批单的变更摘要（原属 RT-04） | 首次发布闭环用不到；审批人可以用审读视图的文件差异比对 | 覆盖四类变更：能力声明、可见范围、表结构、资源档位 |
| 应用标签设置（原属 RT-02） | 未打标签的应用在广场默认分类中正常显示，不影响闭环 | 复用广场已有标签体系 |
| 按密钥、按应用的聚合用量账单（原属 GOV-04） | 平台已有的用量表没有应用和密钥维度，出账单需要新建能力；本版用逐条调用审计代替 | 给用量表增加 `app_id` 和 `api_key_id` 列，并贯通调用链上下文，不要从遥测数据反查 |
| 应用代码存档计入存储配额（原属 GOV-03） | 平台存储配额的统计范围只覆盖知识库文件，加入代码存档需要新建统计；代码存档体量远小于知识库文件 | 统计改为多来源，注意各表的租户列名不同 |
| 改码权归属与交接（原 DEV-06） | 交接的对象是 PRD-2 的应用管家，PRD-2 搁置后无处交接。本版 CLI 部署的应用只能在本地改代码，平台只读 | 随 PRD-2 一起做；届时审批预览增加「复用 owner 草稿沙箱」的方式 |

下列功能本版明确取消，以后也不做。

| 取消项 | 取消理由 |
|---|---|
| 管理后台应用列表（原 GOV-09） | 它要做的四件事都不是新需求：租户管理员在构建页天然能看到本租户全部应用；授权由 GOV-01 承担；下线由 RT-07 承担；审计由 GOV-04 承担 |
| 草稿对租户管理员不可见（原属 GOV-09） | 这是对已有行为的收窄。租户管理员本来就能看到他人未发布的工作流和助手，只对托管应用加限制会制造类型间的不一致 |
| 应用运行期凭据作为产品概念（原 GOV-08 中的应用 token、会话 key） | owner 和使用者都感知不到它，属于技术设计范畴 |
| 应用运行期凭据的强制吊销入口（原属 GOV-08） | 「应用可访问、但能力调用失败」对使用者就是「应用坏了」。应急处置统一为下线 |
| 为托管应用单独设立「创建应用」权限点 | 复用已有权限点的代价是无法只开放工作流、不开放托管应用。为这一种组合新增权限点，收益抵不上角色配置面上永久多出的一项。实际的灰度手段是部署开关（按环境）和按人签发密钥（按人） |

其他顺延项：

| 顺延项 | 说明 |
|---|---|
| 精细成本控制 | token 按人记账与成本展示、会话预算、预算触顶后的处置流程 |
| 存量代码执行点迁入沙箱 | 工作流 CodeNode 和助手本地执行器 |
| 应用退役与归属转移 | owner 离职后的接管；长期无人维护的应用自动归档下线 |
| 资源归属人离职联动 | 归属人账号禁用或删除时，提示或自动回收其服务账号；本版由租户管理员手动回收 |
| 敏感字段分类分级 | 受控导出与脱敏（等保 2.0、数据安全法） |
| 能力总线调用已有工作流和助手 | 把工作流和助手作为应用可声明的能力 |
| 第三方 MCP 网关；多机调度 | — |
| 审批单超时提醒、催办与升级 | 本版的应急方法是下线（RT-07） |
| owner 自查应用的审计和访问记录 | 本版审计只能在管理面查询（GOV-04） |
| 服务账号密钥调用频率限流 | 本版只计量、不限流 |
| iframe 嵌入安全升级（原 RT-09） | postMessage 协议规范化和嵌入域名白名单（社区 #1705）。这是平台已有能力的独立安全修复，与应用工场无功能依赖，可以随任意版本交付 |
