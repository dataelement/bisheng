### 升级前检查

1. 大数据量部署先阅读[迁移性能修复与验证](../reviews/v310b1-migration-performance-fix-20261119.md)。F118 已改为批量读取、磁盘暂存完整历史行及权限资源批量原子提交，保留完整校验和原 Run 续跑。仍需在克隆环境演练完整升级与恢复，按现场数据库类型验证 MySQL 或 DM8；全量图、选中计划及引用核对仍有规模成本，维护时长以本环境实测为准。本次没有改动 Redis 回填脚本。
2. 记录旧镜像 digest、数据库版本、OpenFGA Store/model、权限目录 CURRENT、租户清单、配置、密钥引用、卷和运行目录。
3. 盘点全部 API、Celery Worker、Beat、Linsight Worker、外部同步程序和独立部署节点。先阻止新任务进入，再让旧解析、复制、移动、删除和身份同步任务收尾。迁移脚本不替运维判断停服或排空状态。
4. 检查数据库、对象存储及 Redis 容量。Redis 要保留事件流、消费组、请求账本、checkpoint 和额度计数；不通过清队列或清缓存解决迁移错误。
5. 核对自建账号写入器、旧 SSO 是否仍只发送名称、历史空账号或超长账号及跨来源同名候选。保留原值和 user_id，不提前去重或改大小写。
6. 将本文全部 `实际…` 占位值替换为现场值。模型配置备份可能包含凭据；备份、计划及日志保存到受控目录，不放临时容器的可丢文件系统。

## 二 升级步骤

### 第一阶段 更换镜像并停止服务

在现网 Compose 所在目录操作。使用 `.env` 管理镜像时修改对应变量：

```dotenv
BISHENG_BACKEND_IMAGE=cr.dataelem.com/dataelement/bisheng-backend:v3.1.0-beta1
BISHENG_FRONTEND_IMAGE=cr.dataelem.com/dataelement/bisheng-frontend:v3.1.0-beta1
BISHENG_SANDBOX_IMAGE=cr.dataelem.com/dataelement/bisheng-sandbox:v3.1.0-beta1
# 已启用应用工场时同步更新以下两项
BISHENG_RUNTIME_MANAGER_IMAGE=cr.dataelem.com/dataelement/bisheng-runtime-manager:v3.1.0-beta1
BISHENG_APP_PROXY_IMAGE=cr.dataelem.com/dataelement/bisheng-app-proxy:v3.1.0-beta1
```

若旧部署直接在 YAML 中填写镜像，则修改 `backend`、`backend_worker`、`frontend` 以及现场已有的沙箱、工场控制面服务。`backend_worker` 与 `backend` 必须使用同一后端版本；分拆的 Linsight/Beat/Worker 也同步。ARM 主机采用发行包确认的对应架构标签或 digest。

```bash
# 拉取不会启动服务；按现场启用范围补充其他服务
docker compose pull backend backend_worker frontend code-runner-1 code-runner-2
# 仅已启用应用工场的环境执行
docker compose --profile app-runtime pull runtime-manager app-proxy
```

关闭业务入口、停止外部写入并让旧任务收尾后，停止所有业务写端及消费者。标准 Compose 的示例为：

```bash
docker compose stop frontend backend backend_worker
```

分拆的 API、Worker、Beat、Linsight、跨机器副本及可继续写入的应用运行进程也要停止。使用工场时，按 Runtime 运维流程结束或暂停在途运行，不能仅停止控制面便认为应用已停止。MySQL/DM8、Redis、OpenFGA、MinIO、ES、Milvus 等中间件保持可用。

### 第二阶段 一致备份并进入维护容器

停写后保存同一维护时点的完整恢复材料：

- 业务数据库和 OpenFGA 数据库，含 schema、授权模型及 tuple；
- Redis 的 RDB/AOF 及所用全部 DB，保留消费状态、事件和额度数据；
- MinIO 对象及版本、ES/Milvus 数据与关联存储；
- 工场应用数据、运行配置、技能和其他仍在节点磁盘上的业务文件；
- 旧镜像、配置、Secret 引用、原 Alembic current 和恢复顺序。

上述一致备份及可恢复性由 DBA/运维负责，完成后通知升级负责人；迁移脚本不接收、封装或校验备份证明。不要执行 `docker compose down -v`。仅有业务 SQL 备份不足以回滚此次跨存储迁移。

维护容器显式覆盖入口，避免启动 API/Worker。**直接复用 backend 已有的 data 挂载，无需额外指定 `-v`。** `docker compose run` 会继承该服务的 volumes、环境变量和网络配置，见 [Docker Compose run 说明](https://docs.docker.com/reference/cli/docker/compose/run/)。标准配置已经将 `${DOCKER_VOLUME_DIRECTORY:-.}/data/bisheng` 挂载到 `/app/data`。

从现网同一个 Compose 目录、使用同一份 Compose 文件及 `.env` 执行：

```bash
docker compose run --rm --no-deps --entrypoint bash backend -i
```

之后第三至第七阶段均在**新镜像维护容器**内执行。本地历史准备计划、事件日志及精确备份统一存放在已有 data 卷的 `/app/data/upgrade/3.1.0-beta1/`，临时快照放在其 `tmp/` 子目录。`--rm` 删除维护容器后，这些卷内文件仍保留。自定义部署先确认 `/app/data` 对应可写持久挂载；全量一致备份仍按前面的现场备份方案保存。

若此前已在其他目录生成迁移材料，续跑继续使用原材料、原路径及其对应挂载；本布局用于新维护过程，不要求搬迁、重建或覆盖已有材料。

```bash
cd /app
umask 077
export PYTHONPATH=./
export config="${config:-config.yaml}"
export UPGRADE_OPERATOR_ID='实际平台超管用户ID'
mkdir -p /app/data/upgrade/3.1.0-beta1/tmp
chmod 700 /app/data/upgrade/3.1.0-beta1 /app/data/upgrade/3.1.0-beta1/tmp
export TMPDIR=/app/data/upgrade/3.1.0-beta1/tmp
```

#### F118 临时文件与磁盘空间

**不需要给迁移脚本设置磁盘配额或固定 GB 上限，也不需要单独增加临时盘挂载。** 上面的 `TMPDIR` 直接使用已有 data 卷。本次修复用临时磁盘保存完整历史行及索引，减少大表 payload、快照复制和整体 JSON 编码的内存占用。

| 位置 | 保存内容 | 是否用于续跑 |
| --- | --- | --- |
| `/app/data/upgrade/3.1.0-beta1/tmp/` | 历史准备的私有 `f118-history-*` SQLite 行与索引；正式新 Run 只读预检的 `f118-preflight-*` 临时页 | 否；可以重新生成，不能作为迁移计划或备份 |
| `/app/data/upgrade/3.1.0-beta1/` 下的计划和备份文件 | 历史准备原计划、相邻事件记录、候选证据、孤儿内容备份及正式迁移输入描述符 | 是；跨维护容器重建保留 |
| 数据库及持久 MinIO bucket | 正式 Run/checkpoint、原冻结 baseline/plan 和证据对象 | 是；保持原身份和哈希，不删除或替换 |

临时空间按完整历史行 JSON、mode、父边候选和索引的实际体积预留；真实修复可能同时保留多份快照，不能只按 200 条读取批次估算。新 Run 的正式只读预检也会写临时页。没有适用于所有环境的固定 GB 数，可用克隆演练的临时文件峰值判断 data 所在磁盘是否合适。计划、选中孤儿原文及切片备份与临时文件共用该卷，容量一起考虑。磁盘暂存也不代表正式发布全流程内存恒定。

维护进程用户须能读写以上子目录，不修改其他业务 data 目录的权限。`TMPDIR` 要在运行 Python 命令前设置，可用 `python -c 'import tempfile; print(tempfile.gettempdir())'` 查看实际目录。历史临时目录权限为 0700、SQLite 文件为 0600；正常退出、异常和 async 取消会清理本次临时文件。强杀或主机异常可能留下私有目录，确认原维护进程已停止后可清理 `tmp/` 中对应残留；保留其上级目录的计划、事件和物理备份。续跑时继续使用同一份 data 卷中的原材料，不清空或替换该卷。

### 第三阶段 升级数据库结构

```bash
alembic current
alembic heads
alembic upgrade head
alembic current
```

本文目标代码的唯一 head 为 **`v310b1_f016_dsh_call_pricing`**。命令逐条检查成功后再继续。若出现多 head、缺失 revision、DDL 冲突，先核对镜像和数据库历史，不在客户环境临时生成 merge 或用 `stamp head` 跳过迁移。

统一 Alembic 入口会发现模型并补齐缺失表，再执行已有表变更；不需要为了建表先启动 API。主要结构变化如下：

| 范围 | 结构变化与历史数据处理 |
| --- | --- |
| 知识与权限 | 增加知识处理默认值、模型修订、元数据结构及迁移来源；增加处理、确认、删除、迁移和引用账本；历史 ready 不由列默认值推导 |
| 托管租户一致性 | `flow`、`t_gpts_tools_type` 增加 `creation_state`；`knowledge` 增加 `copy_source_id/copy_target_id`；不自动搬迁业务数据 |
| 账号 | `user` 新增四个身份字段，唯一约束改为 `source/external_id/account_match_key`；增加账号占用和身份写入锁表；保留旧账号原值 |
| 审计 | 五类来源表增加 `operator_dept_id/operator_dept_path` 及索引；历史行保持 NULL |
| 工作流 | `flow.is_delete`，历史有效行默认 0 |
| 桌面会话 | 增加 refresh token 使用时间、设备会话活跃时间和过期策略；旧会话不伪造活动历史 |
| 工场运行时 | 产物大小和传输偏移扩展为 BigInteger；官方运行环境增加系统来源、发行版本和目录摘要 |
| 模型积分 | `dsh_model_call` 增加 `pricing/cost_micro/currency` 三个可空列；增加 `dsh_credit_setting`，不回填历史调用价格 |

### 第四阶段 迁移模型配置并补齐价格

先转换旧 Token 配置，避免后续知识空间冻结后再改变模型相关配置：

```bash
python scripts/migrate_model_token_configs.py --all-tenants
```

预检无错误后执行，备份路径必须为新文件：

```bash
python scripts/migrate_model_token_configs.py --all-tenants --apply \
  --backup-file /app/data/upgrade/3.1.0-beta1/model-token-before.json
python scripts/migrate_model_token_configs.py --all-tenants
```

要求复查计划数和错误数均为 0。脚本把旧独立 `max_tokens` 转入高级参数：Ollama 使用 `num_ctx`，其他服务商使用 `max_tokens`；保留模型 ID、状态、服务归属和其他配置。已迁移记录重复执行为空操作。

然后补齐模型价格：

```bash
python scripts/backfill_model_pricing.py
```

核对输出中已有有效价格、待补价格和 `default 0 (free)` 的模型，再执行：

```bash
python scripts/backfill_model_pricing.py --apply
python scripts/backfill_model_pricing.py --check
```

要求检查输出 **`upgrade gate: passed`** 且退出码为 0。有效已有价格保持；缺失或格式损坏的价格按内置表补齐，无法匹配则为 0。**0 是免费价格，不是待获取报价。** 收费模型应在开放访问前由管理员核价；检查命令不能替代商业价格核对。缺价当前也会放行并按免费计费，不应因对话成功就认为迁移完整。

已启用积分的租户还需核对币种、汇率、积分单价、基准模型和各部门额度。默认人民币积分单价为 0.01 元；以实际保存设置为准。新公式不重算历史用量，旧手填倍率不再作为新调用扣费依据。

### 第五阶段 知识空间统一迁移只读预检

本节适用包含本轮升级流程改造的源码或维护镜像。先完成第一至第四阶段，并保持全部业务写入者、消费者停止；数据库结构升级必须包含新的维护锁表。模型配置、价格、Redis 回填等其他功能仍按各自阶段执行。

知识空间统一只需同一入口的两条命令。首次指定 Run，保留持久 data 卷及业务同配置：

```bash
export UPGRADE_RUN_ID='upgrade-310b1-site-a'
python scripts/unify_knowledge_spaces.py --run-id "$UPGRADE_RUN_ID" --dry-run
```

不必提供环境标签、历史准备脚本、DBA 证明描述符或内部阶段参数。脚本从原生 CURRENT/ACTIVE 唯一发布信息识别环境；已有冻结 Run 则读取原冻结环境，并按原生 before/staged/after 合同核验合法恢复位置。`--environment` 仅作一致性断言，不切换数据库。

预检会构建历史修复后的只读事实，完成 SQL 计划、权限全图和六类引用来源、目标、原生索引的检查；不会写业务 SQL、Run、FGA、Redis 或远端迁移材料。私有本地计划、精确历史备份和报告会保留。自动处理方案按原规则确定，普通孤儿文件保留原行、内容及索引，旧模型名称、缺失创建者和失效保存版本保留并报告；不会逐文件询问取舍。

通过必须同时满足退出码 0、`preflight_complete=true`、`can_apply=true`。`ready=false` 表示尚未完成真实迁移。真正冲突和关键检查未完成均不生成新的可执行候选；有明确安全恢复配方前不能放行的物理清理候选会报告 `not_evaluated`。正常资源只核对原 SQL 索引绑定，不逐文件 stat、不扫描 ES/Milvus 数量或重建向量。

默认材料目录为 `/app/data/upgrade/3.1.0-beta1/f118/<run-id>/`，可用 `--materials-dir` 指定私有持久目录。目录权限 0700、文件 0600；`flow.json` 与 `objects/` 为原计划及内容寻址材料，`private/` 为完整选中行回滚备份，`reports/` 包含摘要和进度 JSONL。不要编辑哈希、覆盖原计划或把失败候选改名使用。DBA 一致备份职责保持独立。

### 第六阶段 执行与同命令恢复

使用真实、未删除用户的正整数 ID；首次 apply 会绑定该操作者：

```bash
python scripts/unify_knowledge_spaces.py \
  --run-id "$UPGRADE_RUN_ID" --apply --operator-id "$UPGRADE_OPERATOR_ID"
```

执行前会再次核验原材料、连接与结构身份及适用的当前事实。通过后，脚本自动保存共享恢复材料、绑定 preparing Run、执行历史准备、冻结实际基线，再完成 SQL 转换、权限发布、引用登记、退役及完整 Coverage。引用不移到开服后后台执行。

约每 15 秒输出阶段、租户、单位、processed/committed、已知总量、耗时、速率、ETA、最后成功时间与等待位置；阶段切换、失败和完成立即输出。未知总量或不可靠速率显示 null。不可变材料和已验证编译结果在本命令内复用；恢复仍核对必要的 current-after，不能仅凭旧 complete 标记放行。

成功要求退出码 0、`ready=true`，并保留报告、原 Run 哈希、Coverage epoch 和失效项材料定位。单个来源 ready、SQL/权限已完成或仅登记完成，都不等于完整升级成功。

中断后继续执行上面**完全相同的 apply 命令**，无需判断冻结与否或追加 `--resume`。preparing 从原共享 replay 读取，冻结后沿原基线及检查点续办；本地材料丢失时也可依原 Run 的共享绑定恢复。私有回滚备份仍应另行妥善保管。

已有旧冻结 Run 也先用同一个 `--dry-run` 评估，再 apply。旧 baseline/plan、ordinal、证明和检查点不重写。补充候选保存在 `reconciliation/<sha>/`；已绑定者优先，未绑定时只接受唯一匹配当前事实的候选，不按文件修改时间挑选。无原生证据的配置、授权或归属变化仍阻塞，不能换 Run 或删台账绕过。

外部请求结果未知或失锁后未取得原生请求终结证明时，报告 `executor_recovery_required`，不把一次 AFTER 扫描、超时或容器停止当作请求已经结束。失败报告说明原生阶段、最后确认位置摘要、提交是否未知及同 Run 恢复命令；报告 I/O 失败不会回滚已提交的业务效果。

| 退出码 | 含义 |
| --- | --- |
| 0 | 完整可执行预检，或本次声明范围的完整成功 |
| 2 | 参数或数据阻塞 |
| 3 | 材料、身份、pin 或不允许的事实漂移 |
| 4 | 运行、关键检查、输出或取消未完成 |

`--verify --apply` 可对已完成 Run 做严格只读业务复核；未完成Run或与旧阶段参数组合时明确拒绝，不隐式执行迁移。普通 completed 重跑返回原 Coverage 结果，不补写迁移 checkpoint。显式旧 `--resume` 与已有 Run 的 `--backup-ref/--schema-ref` 断言继续兼容，不需重新读取 DBA 证明内容。

旧 `prepare_f118_history.py` 仅用于已有独立历史计划的兼容恢复，不是本轮正常流程的额外步骤。保留原 schema、计划 SHA、操作者及 events/payload 备份；不要与本入口并行。旧权限/引用阶段诊断参数只允许已有冻结 Run，受同一互斥与执行身份保护，结果始终标明范围，不能代替默认 full 成功。详见 [维护脚本说明](../../src/backend/scripts/README.md#f118-knowledge-space-unification)。

### 第七阶段 回填 Redis 历史索引

继续保持所有 API、Celery、Beat、Linsight 和其他生产者/消费者停止：

```bash
python scripts/backfill_redis_processing_indexes.py
python scripts/backfill_redis_processing_indexes.py --apply --services-stopped
python scripts/backfill_redis_processing_indexes.py --verify
```

要求最终 `ready=true` 且退出码为 0。按每套服务实际使用的 Redis 配置分别执行；用量部分按该配置的客户端启用状态执行。该脚本补登记历史用量流、待处理项及 checkpoint 索引，保留载荷、消费组、ACK、请求账本、额度计数和 TTL。

失败时保留停服状态，处理错误后重复执行。不得删除旧事件或 checkpoint，也不运行旧版消费者消化新格式数据。

### 第八阶段 启动并验收

1. 确认数据库 head、知识迁移 `ready`、Redis `ready`、模型价格检查全部通过，保存材料后 `exit` 退出维护容器。
2. 先启动新版 Celery Worker 和 Beat，保持 API、Linsight 与外部入口关闭，消化已登记的旧用量积压。标准 Compose 的 `backend_worker` 同时启动这两类进程；分拆部署按实际服务启动。核对消费积压已清、SQL 用量投影与额度一致。
3. 启动新版 API、Linsight、沙箱及原已启用的工场控制面。所有业务节点使用同一目标版本；入口先仅对验收人员开放。
4. 发布新版前端和合并后的反向代理配置，完成下表验收后再开放全部访问。

```bash
# 宿主机标准 Compose 示例
docker compose up -d --no-deps backend_worker
docker compose logs --tail=200 backend_worker
# 确认用量积压消化完成后继续
docker compose up -d --no-deps backend code-runner-1 code-runner-2 frontend
docker compose ps
docker compose logs --tail=200 backend backend_worker
```

| 验收范围 | 至少检查 |
| --- | --- |
| 登录与身份 | 历史账号可登录；新账号规则和昵称保存正常；旧 SSO 仍对应原 user_id；更改昵称不会改变账号绑定 |
| 租户与权限 | 超管切换管理租户后列表、详情、写入一致；子租户管理员可管理本租户；普通用户不能越权访问其他租户 |
| 模型 | Root 共享、子租户可选模型、系统模型继承正常；模型连接与真实对话成功；旧 Token 生效值保持 |
| 知识空间 | 原 ID 和成员可见范围保持；历史文件、版本、问答、溯源可用；新增解析、分段、移动、复制、删除及任务记录正常 |
| 业务引用 | 历史工作流、助手、频道及工场应用仍能使用合法引用；失效清单可定位；删除被引用资源时正确提示 |

## 三 常见报错与恢复

| 现象 | 处理 |
| --- | --- |
| 多个 Alembic head、缺列或缺表 | 核对实际目标镜像及数据库 revision；本基线应为单 head。修复迁移问题后重跑，不跳过结构升级 |
| 历史准备 `blocked` 非空 | 根据精确资源 ID 处理归属、父链、下游或备份问题；保留原计划及物理备份，不能扩大清理范围 |
| 历史准备已有计划或 apply 中断 | 不重跑预览覆盖文件；使用原 `--plan ... --apply --operator-id ...` 续跑，没有 `--resume` 参数 |
| 临时文件写入失败、临时盘满 | 保持停服，确认失败命令/进程状态，释放无关占用或换合适的 `TMPDIR`；原计划/备份/Run 保留，按相应阶段续跑，不通过删除迁移恢复材料腾空间 |
| `material_manifest_identity` 或证据无效 | 检查 Run、环境、writer、全部租户摘要、对象键及内容哈希；新冻结前准备正确材料，已冻结后不得改写原材料 |
| `preflight_complete=true` 但 `ready=false` | 新 Run 的预检正常结果；继续正式 apply，不能据此开服 |
| `resume_requires_frozen_run` | 该 Run 尚未冻结，核对原运行记录；不要随意创建替代 Run 或伪造 checkpoint |
| 权限目录、授权模型或 Coverage 未就绪 | 维持维护状态，按原 Run 恢复并完成对账；不通过强制写模型、删 CURRENT 或清台账解除门禁 |
| 价格检查通过但不扣费 | 检查模型是否被补成默认 0、管理员实际价格与积分设置、消费积压及 SQL 投影；模型调用成功不证明计费正确 |
| Redis verify 不通过 | 保持消费者停止，核对全部 Redis DB 和配置，重跑回填；不清历史流或消费组 |
| 子租户模型缺失或仍提示复制占用 | 核对历史共享与原复制状态，走下节精确修复；不直接更新任务为成功、不删除操作围栏 |
| PPT 生成失败 | 核对实际后端/沙箱镜像内 PPTD 引擎、Node 和依赖；旧 `base.v10` 加新源码不能满足运行环境 |
| 手机/桌面连接失败、下载链接协议错误 | 核对 Nginx/Gateway 的 WebSocket 路由、公开 origin、转发 Host/协议及可信代理链 |

## 四 按需操作

以下操作按现场预检结果执行，不能作为全量升级脚本无条件运行。**若会改变正式迁移读取的模型、权限或业务配置，在首次 F118 冻结前完成并保存结果。已冻结时先沿原 Run 排查，不能穿插修改后重建基线。**

### 修复历史 Root 模型共享

仅在确认历史已共享、接收方授权漏失时使用。要求当前合法 Root 平台超管，先保存 manifest：

```bash
python scripts/repair_model_sharing.py \
  --operator-id "$UPGRADE_OPERATOR_ID" --manifest /app/data/upgrade/3.1.0-beta1/model-sharing.json
# 实际服务ID列表来自本次预览
python scripts/repair_model_sharing.py \
  --operator-id "$UPGRADE_OPERATOR_ID" --manifest /app/data/upgrade/3.1.0-beta1/model-sharing.json \
  --apply --provider-ids '实际服务ID列表'
```

脚本保留已关闭分享、现有接收范围和价格等设置。遇到已有执行或恢复围栏保留原操作记录，不能删除后重签；`--abandon-preparing` 属于单独诊断后的精确处置，不列入常规升级步骤。

### 原未启用客户端的环境首次启用

先盘点并确认无显式可见策略的模型是否应继续对全员可见，再按租户预览：

```bash
python scripts/backfill_model_visibility_everyone.py --tenant-id '实际租户ID'
python scripts/backfill_model_visibility_everyone.py --tenant-id '实际租户ID' \
  --apply --actor-user-id "$UPGRADE_OPERATOR_ID"
```

此命令会为缺失策略的聊天模型写入“全员可见”，属于实际授权变化；已有显式限制不改。客户端已经启用的环境不应把它当作通用修复。

### 托管租户和历史任务盘点

结构升级后可使用只读脚本：

```bash
python scripts/managed_tenant_preflight.py \
  --tenant-id '实际租户ID' --user-id '实际用户ID' --limit 100
```

输出 `truncated=true` 不代表全量检查完成，`UNKNOWN_LEGACY_COPYING` 不得依据同名资源自动补复制指针；FGA 显示 `NOT_RUN` 时另行核对。恢复创建、复制或文档路径应走对应业务服务或精确恢复脚本，不直接更改业务状态。

### Kubernetes 与 Helm

标准 Chart 版本为 `0.2.0`，`appVersion=3.1.0-beta1`，使用带镜像清单和官方运行目录的正式发行包。新 Chart 的初始化任务负责结构及初始化状态，不替代本文的存量知识转换、价格迁移和 Redis 回填。

先停止旧工作负载，在维护 Job 中按本文顺序完成存量迁移，再按[Helm 运维说明](../../docker/helm/bisheng/README.md)部署。复用原 PVC、Secret、Store 和运行目录；不可把原库当新库初始化。旧 values 的字段结构已大幅调整，应依据新 schema 合并，不仅修改 tag 或原样 `--reuse-values`。

## 五 回滚边界

**开放使用前**，如无法完成升级，先停止全部新版进程和应用运行，按同一维护时点的完整备份恢复业务数据库、OpenFGA、Redis、对象及关联存储，再恢复旧配置、密钥和全部旧镜像，验证后开服。迁移中的继续执行优先使用同 Run 恢复，不局部回灌旧业务行。

**开放使用后采用前向修复。** 新用量事件包含价格快照，旧版本无法正确消费；知识权限、引用和账号占用也已改变。仅切回旧镜像或执行 `alembic downgrade` 不能构成安全回滚，多条迁移本身会拒绝降级。恢复升级前备份会丢失开服后的新增业务，需另行制定数据恢复方案。
