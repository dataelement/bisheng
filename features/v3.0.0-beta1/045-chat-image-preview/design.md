# Design: 支持展示对话中上传的图片

> **本文档定位 — 现状快照（Why this How）**
> `spec.md` 回答做什么；本文回答**为什么这么实现**；`tasks.md` 是流水账。

**关联**: [spec.md](./spec.md) · [tasks.md](./tasks.md)
**版本**: v3.0.0-beta1
**最后更新**: 2026-07-24

---

## 1. 目标与非目标

- **目标**：让 client 端三类会话（日常模式、任务模式、工作流会话）里用户上传的图片，在消息中以缩略图呈现并可全屏查看；图片不可用时给出明确占位而不是裂图。
- **非目标**：不改后端与存储、不做失效链接的自动刷新、不动 AI 回复内的图片、不动输入框内发送前的预览、不改非图片附件的展示。

---

## 2. 关键约束

- 遵循 `docs/constitution.md` C1–C7（本特性仅涉及 **C7**：不在 store 里发 HTTP——本特性根本不发请求）。
- 遵循 `src/frontend/client/AGENTS.md`：Recoil / react-query v4 / shadcn / `~/` 别名 / 单文件 ≤600 行 / 命名导出 / 图标优先 `bisheng-icons`。
- **纯前端**：不新增接口、不改消息数据结构、不做数据迁移——因此必须在**现有消息数据能提供的信息**范围内实现（这直接导出决策 1）。
- 存量历史消息也要生效，意味着不能依赖任何"从今往后才会写入"的字段。

---

## 3. 方案对比与选定

### 决策 1：怎么判断一个附件是图片

- **备选**：
  - A. 按**文件名后缀**判断（`png/jpg/jpeg/gif/webp/bmp/svg`）。
  - B. 按消息里存的 MIME 类型字段判断。
- **选定**：A
- **原因**：MIME 字段是上传时前端顺手带上的，**存量历史消息不保证有**，而且不同上传入口写入的字段名并不统一。文件名则是所有入口、所有历史消息都必然存在的信息。项目内已有按后缀取文件图标的工具函数，判断口径与文件图标保持一致，不会出现"图标显示是图片、但没走图片渲染"的割裂。
- **何时该重新考虑**：若将来上传链路统一并保证 MIME 落库，可改用 MIME + 后缀双保险。

### 决策 2：三个场景各自改，还是先统一消息渲染

- **备选**：
  - A. 在两处消息渲染各自接入同一个图片渲染组件（把组件提到共用位置）。
  - B. 先把两套消息渲染合并成一套，再加图片能力。
- **选定**：A
- **原因**：日常/任务模式与工作流会话是**两套独立的消息渲染实现**（历史遗留，一套源自开源聊天框架、一套是 appChat 自研）。B 是正确的长期方向，但合并消息渲染是一次高风险重构，与"让图片能看"这个诉求完全不成比例。A 的代价只是同一个组件被两处引用。
- **何时该重新考虑**：若两套渲染的差异继续扩大到需要三处以上同步改动，应立项合并。

### 决策 3：失效判定用"加载失败"，而不是提前校验

- **备选**：
  - A. 渲染 `<img>`，监听加载失败事件 → 切换成占位。
  - B. 渲染前先探测链接可用性（HEAD 请求）再决定渲染什么。
- **选定**：A
- **原因**：B 会给每条历史图片消息多一次网络往返，且探测与真实加载之间仍有时间差（探测通过不代表加载成功）。A 零额外请求，且天然覆盖所有失败原因（对象被清理、签名过期、网络异常）。
- **代价**：失败前会有一瞬的加载态，用户可能看到占位"闪现"，可接受。
- **何时该重新考虑**：若后端将来提供"文件是否有效"的批量查询，可改为 B 以获得更准确的文案（区分"已删除"与"链接过期"）。

### 决策 4：全屏查看复用既有组件而非新写

- 项目内已有基于 Radix Dialog 的全屏图片查看实现（暗色遮罩、右上角关闭、`object-contain` 自适应），符合 PRD 描述的交互。**把它提到共用位置后两处复用**，不新写、不引入新依赖（AGENTS.md 硬规则：不得引入新 UI 库）。

## 4. 系统现状（接手必读）

### 4.1 数据流

`选文件上传 → 拿到文件路径与元信息 → 随消息发送 → 消息落库 → 会话渲染读消息附件 → 渲染`

- **上传（三场景共用）**：`client/src/pages/appChat/components/InputFiles.tsx` —— 校验、并发上传、进度；图片会另生成一个本地预览地址供输入框用（发送前会被剔除，不进消息）。
- **输入框附件条（共用）**：`client/src/components/Chat/Input/AttachmentBar.tsx` —— 已支持图片缩略图与点击预览（**本特性不动**）。
- **发送**：`client/src/hooks/useAiChat.ts` —— 把附件数组随消息一起进本地消息状态与请求体。
- **消息渲染（分两套）**：
  - 日常模式 / 任务模式：`client/src/components/Chat/AiMessageBubble.tsx` 内的上传附件列表——**当前一律渲染成"小图标 + 文件名"，不分类型**（代码注释明确写着 icon + filename only, no preview）。这是本次现象的直接来源。
  - 工作流会话：`client/src/pages/appChat/ChatMessages.tsx` → `components/MessageFile.tsx` → `components/ChatFile.tsx` —— 一律渲染成"点击下载"卡片。
- **可复用件**：`components/Chat/Messages/Content/Image.tsx`（懒加载图片）与 `DialogImage.tsx`（全屏查看）——**存在但当前未被这两条渲染链路使用**。
- **图片地址**：后端返回的是对象存储预签名地址且**已抹掉 host**，前端渲染前会把 host 段替换成当前环境地址（既有做法，沿用）。

### 4.2 关键数据结构 / 字段约定

| 契约 | 形式 | 说明 | 谁会消费 |
|---|---|---|---|
| 消息附件项 | 含文件路径、文件名、file_id 等（各入口字段名略有出入，取值需做兼容取值） | **不新增字段**；图片识别只依赖文件名 | 两套消息渲染 |
| 图片识别口径 | 文件名后缀 ∈ `png/jpg/jpeg/gif/webp/bmp/svg` | 与文件图标取值口径一致 | 两套消息渲染 |
| 失效占位文案 | 「图片已失效，无法查看」（走 i18n，三语） | 覆盖被清理与链接过期两种情况 | 两套消息渲染 |

### 4.3 关键模块职责

| 模块 / 文件 | 职责 | 不做什么 |
|---|---|---|
| 共用图片消息组件（本特性提取） | 缩略图 + 点击全屏 + 加载失败占位 | 不判断"是不是图片"（由调用方分流），不发请求 |
| `AiMessageBubble.tsx` 附件列表 | 日常/任务模式：按类型分流（图片 → 图片组件，其余 → 现状文件行） | 不改非图片分支 |
| `ChatFile.tsx` / `MessageFile.tsx` | 工作流会话：同样按类型分流 | 不改下载卡片的既有行为 |
| `AttachmentBar.tsx` | 发送前的输入框附件预览 | 本特性不动 |

## 5. 已知坑 / 反直觉事实

| # | 反直觉事实 | 如果不知道会怎样 | 在哪处理 |
|---|---|---|---|
| 1 | client 里有**两套互不相干的消息渲染**（日常/任务一套，工作流会话另一套），只有上传逻辑和输入框附件条是共用的 | 只改一处会以为做完了，另外的场景毫无变化；排查时会怀疑是数据问题 | 决策 2：两处都接同一个组件 |
| 2 | 仓库里**已经有**懒加载图片组件和全屏查看组件，但当前两条消息渲染链路都没用它们 | 会以为要从零写 lightbox，或反过来以为"组件存在=功能已实现"，误判需求已完成 | 决策 4：提取复用 |
| 3 | 图片地址是**预签名地址，有效期 7 天**；后端返回时**抹掉了 host**，需前端拼当前环境地址 | ①直接用返回值当 src → 404；②以为"图片失效=文件被删" → 排查方向错，实际一周前的会话即使文件还在也会失效 | 渲染前替换 host（沿用既有做法）；失效语义见 §8 |
| 4 | 消息里的附件字段在不同上传入口有不同的键名（文件名/路径都有多个可能字段） | 只按一个字段取值，会在某一个场景下拿到空文件名 → 图片识别失败，退化成文件卡片 | 取值时做兼容（与现有文件名取值逻辑保持一致） |
| 5 | 图片组件当前**没有加载失败处理**，链接坏了就是浏览器默认裂图 | 以为"失效占位"是新增需求之外的额外工作；实际这正是 AC-04 要补的缺口 | 决策 3 |

## 6. 对外契约与依赖

### 6.1 我提供给别人的（Outgoing）

| 契约 | 形式 | 谁在用 |
|---|---|---|
| 共用「消息图片」组件 | 前端组件 | 两套消息渲染；后续新会话形态可直接复用 |

### 6.2 我依赖别人的（Incoming）

| 依赖 | 形式 | 风险点 |
|---|---|---|
| 消息附件里的文件名 | 隐式数据契约 | 若某入口不再回传文件名，图片识别失效（退化为文件卡片，不会崩） |
| 预签名地址的 7 天有效期 | 存储层行为 | 有效期若调整，"失效"出现的时间点随之变化（本期不做刷新，见 §8） |

## 7. 测试与可观测

- **前端组件测试**：图片后缀分流（含大写后缀、无后缀文件名）、加载失败 → 渲染占位。
- **手动验证**（三场景各跑一遍）：上传 png → 消息显示缩略图 → 点开全屏 → 关闭；上传一个 pdf → 仍是文件卡片（无回归）；一条消息传 2 张图 → 各自可独立放大。
- **失效验证**：手动把图片地址改坏（或找一条 7 天前的历史会话）→ 应显示「图片已失效，无法查看」，控制台无未捕获报错。
- **存量验证**：找升级前发送过图片的历史会话打开确认。

---

## 8. 后续改进 / 不打算做的事

- **失效链接刷新**：本期明确不做（用户已拍板）。后果需知悉：**超过 7 天的历史会话，其图片一律显示为"已失效"，即便文件仍在**。若后续要改善，方向是渲染时按 file_id 现取新鲜地址，或把有效期拉长——属独立特性。
- **两套消息渲染合并**：长期正确方向，本期不碰（决策 2）。
- **AI 回复中的图片**：不在 PRD 范围；若将来要做，可直接复用本特性提取出的图片组件。
