# 3.0 工作流对外发布 MCP 服务封装 方案

> 状态：调研完成，方案待对齐（见 §9 待拍板问题）
> 日期：2026-07-29
> 输入：MCP 2026-07-28 规范联网调研 + 全仓代码取证
> 关联：对外发布页「API 访问」（`/api/v2/workflow/invoke` / `stop`）

---

## 1. 背景与问题

工作流「对外发布」目前提供三种接入方式：API 访问（`POST /api/v2/workflow/invoke` + `stop`）、免登录链接、需登录链接。API 访问的形态是：服务端生成 `session_id`，调用方轮流拿事件（输出事件直接渲染；输入事件渲染表单收集用户输入后带 `session_id` 续跑）。

问题：**这套 API 能否封装为 MCP 服务**，让 Claude Code / 各类 Agent 客户端把已发布的工作流当作 MCP tool 直接调用？恰好 MCP 规范于 2026-07-28 发布了新版本，本文基于新规范做可行性评估并给出方案。

## 2. 结论摘要

**能封装，且 2026-07-28 新规范让契合度显著提升**——新规范三大变化逐条对上毕昇现有 API 的形态：

| MCP 2026-07-28 新特性 | 毕昇现有对应物 | 契合度 |
|---|---|---|
| 无状态核心 + **server-minted handle 作为普通工具参数回传**（SEP-2567） | `session_id` 服务端生成、调用方原样传回续跑 | ★★★ 完全同构 |
| **MRTR**（SEP-2322）：tools/call 返回 `resultType:"input_required"` + ElicitRequest 表单，客户端带 `inputResponses`+`requestState` 重试原请求 | `input` / `output_with_input_msg` / `output_with_choose_msg` 三类 HITL 事件 + `session_id`+`message_id`+`{node_id:{key:value}}` 续跑 | ★★★ 语义同构 |
| **Tasks 官方扩展**（`io.modelcontextprotocol/tasks`）：`tasks/get` 轮询 + `tasks/update` 送输入 + cancel | `stream=false` 的"跑到断点"语义 + Redis 事件队列 + `/stop` | ★★☆ 可映射 |

四个非丝滑点（§6）：表单**文件上传**在 elicitation 中无对应类型；HITL 状态**钉死在 Celery worker 进程内存**；v2 API **无鉴权**不能直接透出；**SDK v2 仍 beta、客户端生态未跟上新规范**。

**总体策略**：按 2026-07-28 的理念（句柄 + 可重入 + input_required）设计工具契约，先跑在稳定 spec / `mcp` 1.x streamable-http 上；session_id-as-argument 在任何协议版本下都成立，真 MRTR 等客户端生态跟上后作为纯增量升级。

## 3. MCP 2026-07-28 规范要点

发布于 2026-07-28（正式版 + Tier 1 SDK 同步更新）。与本题相关的变更：

1. **彻底无状态**：删除 `initialize` 握手和 `Mcp-Session-Id` 头；每个请求在 `_meta` 里自带协议版本/客户端能力；新增 `server/discover`。跨调用状态的官方姿势 = **服务端铸造的句柄作为普通工具参数传回**（SEP-2567）。任意实例可处理任意请求，天然适配负载均衡。
2. **MRTR 取代服务端主动请求**（breaking change）：`elicitation/create` / `sampling` 不再由服务端反向发起，而是 `tools/call` 直接返回 `InputRequiredResult{resultType:"input_required", inputRequests:{key→ElicitRequest…}, requestState}`；客户端收集输入后**带 `inputResponses` + 原样回显 `requestState` 重试原请求**（新 request id，完全独立的请求）。规范对 `requestState` 的安全要求：影响业务逻辑时必须 HMAC/AEAD 防篡改 + TTL + 绑定 principal 防重放；服务端收到缺失输入时 SHOULD 再次返回 `InputRequiredResult` 而非报错。ElicitRequest form 模式的 `requestedSchema` 仅支持原始类型（string/number/boolean/enum）。
3. **Tasks 从实验核心转为官方扩展**（`io.modelcontextprotocol/tasks`）：`tasks/get` 轮询（废除阻塞式 `tasks/result`）、新增 `tasks/update` 做 client→server 输入、允许服务端未经请求就返回 task 句柄。状态机含 `input_required`，可与 MRTR 组合处理"长任务中途要输入"。
4. 其它相关：所有 result 必带 `resultType`（老服务端缺省视为 `"complete"`）；`tools/list` 必带 `ttlMs`/`cacheScope` 且鼓励确定性排序（利好 prompt cache）；**删除 SSE 断流重放**（`Last-Event-ID` 移除，断流 = 重发新请求）；Sampling/Roots/Logging 进入 12 个月弃用期；auth 收紧（RFC 9207 iss 校验、DCR 弃用转 Client ID Metadata Documents）。
5. **SDK 现状**：Python SDK v2（实现 2026-07-28）仍是 beta，官方明确不建议生产使用；1.x 稳定线实现 2025-11-25 及以前。毕昇后端已锁 `mcp` 1.27.1（纯 client 用途，无 fastmcp 依赖，但 `mcp` 包自带 `mcp.server.fastmcp` 与 streamable-http server）。

## 5. 映射分析

| workflow API 概念 | MCP 概念（2026-07-28） | 说明 |
|---|---|---|
| `session_id`（服务端生成、调用方回传） | server-minted handle as tool argument | 一字不改就是规范推荐模式 |
| `stream=false` 跑到断点返回 `{session_id, events}` | `tools/call` 一次调用返回 | 天然契约，invoke 内核零改动 |
| `input` 事件 + form_input schema | MRTR `InputRequiredResult` + `ElicitRequest(mode:"form", requestedSchema)` | text/select(options→enum)/required 均可映射 |
| `output_with_choose_msg` | ElicitRequest enum 单选 | 1:1 |
| `session_id`+`message_id`+`{node_id:{key:value}}` 续跑 | 重试原 tools/call + `inputResponses` + `requestState`（编码 session_id/message_id/node_id + HMAC） | 语义同构；`requestState` 防篡改要求正好补上现有 API 裸奔的洞 |
| `/stop` | Tasks 扩展 `tasks/cancel`；MVP 期一个 `workflow_stop` 工具 | |
| 720min 长任务 | Tasks 扩展（轮询 `tasks/get`） | 进阶项，MVP 先限定"断点式"用法 |
| `Flow.name/description` | tool `name/description` | 现成 |
| `guide_word/guide_question/stream_msg` 增量 | 无对应，折叠进文本结果或丢弃 | `stream=false` 路径本来就过滤增量 |

## 6. 非丝滑点与对策（按严重度）

1. **文件上传无映射**。`dialog_input` 的文件位 / form_input 的 file 类型，elicitation form 只支持原始类型。
   对策：MVP 在 tools/list 层过滤含文件输入的 workflow（或调用时返回明确错误）；进阶提供"传 URL、服务端代下载"约定。
2. **HITL 状态的后端现实**。协议无状态了，但 INPUT 态 Workflow 对象在 worker 进程内存、靠一致性哈希回同进程；worker 重启即丢会话。MCP 化不引入新问题（HTTP API 同病），但 LLM 客户端会自动重试，**丢会话必须返回可理解的错误**（"会话已失效，请重新发起"），否则模型陷入重试循环。
   对策：`workflow_continue` 对 session 不存在/超时的情况返回结构化 `{status:"failed", reason:"session_expired", recoverable_by:"re-invoke"}` 级别的语义化错误。
3. **鉴权必须新加**。直接透出 v2 无鉴权模式 = 匿名可枚举并调用全部 workflow。
   对策：MCP endpoint 强制 API key（形态见 §9 D2），且只暴露 `FlowStatus.ONLINE` 的 workflow（顺手补上 invoke 不校验 ONLINE 的缺口，至少在 MCP 侧）。
4. **生态时机**。真 MRTR 需要客户端也说 2026-07-28（发布次日，Python SDK v2 仍 beta）。
   对策：MVP 用"**模型中介式 HITL**"——工具返回结构化 `{status:"input_required", …, input_form}`，靠 LLM 理解后向用户收集输入再调续跑工具；协议级 MRTR 作为纯增量升级（契约不变，只是把 input_required 从 structuredContent 提升为 resultType）。
5. 小项：
   - stop 任务落错队列的既有 bug（`redis_callback.py:406` 走通用队列）在 cancel 语义下会放大，宜顺手修（改 `apply_async(queue=绑定队列)`）。
   - 新规范删除 SSE 断流重放 → 事件经 Redis list lpop 消费是破坏性读取，断流重试的幂等性要设计（re-issue 时从 status + 未消费事件恢复，不能假设事件还在）。

## 7. 方案设计

### 7.1 架构位置

新模块 `src/backend/bisheng/mcp_server/`（纯增量；无新依赖，`mcp` 1.27.1 自带 streamable-http server），挂载到 FastAPI（如 `/api/v2/mcp`）。**不经 HTTP 自调用**，直接复用服务层：`execute_workflow.apply_async` + `RedisCallback` + `convert_chat_response_to_workflow_event`——与 `open_endpoints/api/endpoints/workflow.py:42-124` 的同源逻辑抽成共享 service，两个入口（REST / MCP）共用。

### 7.2 工具粒度：两阶段

**阶段一（MVP）：4 个通用工具**

| 工具 | 入参 | 返回 |
|---|---|---|
| `workflow_list` | — | ONLINE workflow 列表（id/名称/描述/输入形态摘要/是否含文件输入） |
| `workflow_invoke` | `workflow_id`, `inputs?` | 见 7.3 契约 |
| `workflow_continue` | `session_id`, `message_id`, `inputs` | 同上 |
| `workflow_stop` | `session_id` | `{status}` |

实现最薄，任何已发布 workflow 即插即用，无需管理 tool 注册的动态性。

**阶段二（进阶）：每个已发布 workflow = 一个 MCP tool**
`inputSchema` 由新写的 `Flow.data` INPUT 节点静态解析函数生成（复用 `workflow/nodes/input/input.py:80-101` + `api/services/workflow.py:906-933` 的逻辑），配 `listChanged` 通知 + `ttlMs` 缓存 + 确定性排序。LLM 的工具选择体验更好（名称/描述/参数直接可见，不用先 list 再 invoke）。

### 7.3 HITL 契约（MVP，模型中介式）

`workflow_invoke` / `workflow_continue` 返回 structuredContent：

```json
{
  "status": "completed | input_required | failed",
  "session_id": "…",
  "message_id": 123,
  "outputs": [{"node_name": "…", "text": "…", "files": []}],
  "input_form": {
    "node_id": "input_xxx",
    "form_type": "form_input | dialog_input | inline_input | inline_choose",
    "fields": [{"key": "…", "label": "…", "type": "text|select|number", "required": true, "options": []}]
  },
  "error": {"reason": "session_expired | …", "recoverable_by": "re-invoke | retry | none"}
}
```

tool description 写明协议："收到 `input_required` 时，向用户收集 `fields` 各项后调用 `workflow_continue`"。升级 MRTR 时该结构原样搬进 `InputRequiredResult`（`input_form` → ElicitRequest，`session_id/message_id/node_id` → HMAC 保护的 `requestState`）。

### 7.4 鉴权

MCP endpoint 强制 API key（HTTP header），发布页生成/吊销；执行身份沿用 default_operator 语义（与现有 API 访问一致），但增加：key 校验、只暴露 ONLINE、审计日志记 key 主体。规范正向 OAuth/CIMD 收紧，为演进保留 header 抽象。具体形态见 §9 D2。

### 7.5 产品形态

对外发布页在「API 访问 / 免登录链接 / 需登录链接」旁新增「**MCP 接入**」标签页：展示 MCP endpoint URL、API key 管理、客户端配置示例（Claude Code `mcp.json` / 通用 `mcpServers` JSON——格式与 `mcp_manage/manager.py` 消费的一致）、HITL 行为说明。

### 7.6 协议演进路线

| 时机 | 动作 |
|---|---|
| 现在（MVP） | 稳定 spec（`mcp` 1.x streamable-http），模型中介式 HITL |
| Python SDK v2 GA + 主流客户端支持 2026-07-28 | 升级 SDK，`input_required` 提升为协议级 MRTR，`requestState` 加 HMAC+TTL+principal 绑定 |
| 长任务需求出现 | 接 Tasks 扩展（`tasks/get` 轮询 + cancel），与 HITL 的 `input_required` 状态组合 |

## 8. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| worker 重启丢 INPUT 态会话 → LLM 重试循环 | 中 | 语义化错误 + description 指引 re-invoke（§6.2） |
| 文件输入类 workflow 不可用 | 中 | list 层过滤 + 明确报错（§6.1） |
| API key 泄漏 = 可调全部已发布 workflow | 中 | key 按租户/按 workflow 收窄（D2），审计日志 |
| stop 落错队列，cancel 不彻底 | 低 | 顺手修队列路由（§6.5） |
| 断流重试幂等性（Redis lpop 破坏性读取） | 低 | status + 事件恢复设计（§6.5） |
| SDK v2 breaking 变化 | 低 | MVP 不依赖 v2，契约层隔离 |

## 9. 待拍板问题

- **D1 工具粒度节奏**：MVP 直接做阶段二（per-workflow tool）还是先 4 个通用工具？（建议：先通用，静态 schema 解析函数另立小任务并行）
- **D2 鉴权形态**：平台级单 key / 按 workflow 发 key / 按租户发 key？key 存哪（复用 `gpts_tools.api_key` 模式 vs 新表）？
- **D3 文件输入策略**：MVP 直接排除，还是首发就带"URL 代下载"约定？
- **D4 v2 既有行为顺手修**：invoke 不校验 ONLINE、stop 队列错配——只在 MCP 侧收口，还是连 REST 侧一起修（后者是行为变更，需评估存量调用方）？
- **D5 落版本**：进 3.0.x 哪个迭代；是否与「应用工场」的对外能力规划合并考虑。

## 10. 验证方式

- 文档阶段：本方案 review（逐项过 §6 非丝滑点取舍 + §9 拍板）。
- 实现阶段：MCP Inspector / Claude Code 作为客户端连 server 实测——`tools/list` 可见已发布 workflow → invoke 一个含 INPUT 节点的翻译流 → 模型收集表单输入 → continue 跑完 → stop 中断验证；worker 重启后续跑旧 session 应得到可理解错误而非 500；无 key / 错 key / 未上线 workflow 三类拒绝路径。
