> **范围边界**
>
> 本 Feature 是 F054 所定义「托管应用运行时」的**第二套执行后端**：在客户已有 k8s 集群的环境里，把 F054 形态无关的编排能力兑现在集群上，且**产品面与 compose 形态零差异**（候选 INV-33——随 F054 spec 定稿转正，本 spec 是其 k8s 侧承接者，不新增不变量）。它不定义任何新的产品对象、界面或状态；它拥有的 What 只有四类：**k8s 侧的能力兑现承诺**（编排 / 自愈 / 容量 / 隔离 / 出站 / 档位 / 数据库形态）、**k8s 形态独有的必需件**（命名空间级最小权限、镜像构建与分发、集群能力探测与告警）、**双形态一致性回归**、**交付物**（Helm chart / manifests、部署 / 升级 / 卸载步骤）。技术选型（构建器组件、仓库组件、CNI 适配、卷类型、运行时服务与 app-proxy 在集群内外的落位）一律在 design.md，本 spec 只写对外可观测、可核验的承诺。
>
> - **本次纳入**：
>   - **k8s 集群形态执行后端**：实现 F054 AC-14–24 定义的形态无关编排能力——工作负载 reconcile（平台声明期望态 → 集群内单副本工作负载与服务访问点〔Deployment / Service 语义〕）、崩溃自愈由工作负载控制器原生兑现（RT-08 同口径同时限）、健康检查、探活通过后切流量与旧实例宽限退休、运行时服务重启不影响已运行应用并在恢复后对齐期望态、容量准入 = 集群可调度资源判定（不足 → 待上线（资源不足），成因文案与 compose 一致「资源不足」）、状态 / 健康 / 当前版本 / 日志只读接口内容范围一致、单应用单副本、应用工作负载仅经 app-proxy 可达；审批期临时预览实例（F055 拉起 / 回收、F054 预览入口）同样经本后端兑现
>   - **命名空间级最小权限**：运行时服务以限定命名空间的集群身份操作应用工作负载，不持集群级权限、不能操作其它命名空间、不能创建特权工作负载；权限清单随交付物、可对照集群 RBAC 核验；对该身份的每次集群操作可在集群审计日志中按身份追溯；应用工作负载自身不持任何集群 API 身份；平台后端进程不持任何集群访问凭据（F054 AC-14 在 k8s 形态的等价）
>   - **档位 → Pod requests / limits 映射**：产品面（选档、默认轻量、停用只拦新选择、规格调整自下一次发布 / 重新启用生效）与 compose 完全相同（GOV-03）；内存触顶只重启自身、CPU 触顶只被限制
>   - **沙箱档位映射 RuntimeClass**（部署级配置，非产品面）：默认档 = 与 F054 AC-17 同一清单的加固（限额 / 只读文件系统除可写路径 / 不可提权 / 网络受控 / 自愈）；推荐档 / 加固档各对应一种集群 RuntimeClass，**仅在集群探测到对应 RuntimeClass 存在且节点架构 / 形态支持时启用**（加固档仅裸金属）；缺失或架构不支持 → 降级默认档并显式告警
>   - **出站白名单 = NetworkPolicy 及其等价语义**：运行期默认封禁一切出站（含直连 IP、UDP、集群内其它工作负载与命名空间、集群 API），只放行平台 API（含每应用数据库与附件存储端点）与应用包声明的域名；构建期只放行平台配置的包源 + 镜像仓库 + 平台自身分发端点（同 F054 AC-16 口径），构建执行体与运行工作负载同一规则来源；白名单声明形态与生效规则引用 F054 AC-16 / F055 AppManifest；CNI 不支持 NetworkPolicy 属硬前置缺失（见探测）
>   - **镜像构建与分发（k8s 形态净新增件）**：一次性、无守护进程、非特权的集群内构建执行体（不依赖节点容器守护进程、不用 DinD、不交出 docker.sock），受部署配置的超时 / 资源限额 / 并发上限约束、超时即回收并返回原因；两形态同一份构建定义、同一构建期包源规则、构建结果行为等价；产物推送到部署期配置的镜像仓库、所有节点可拉；仓库策略 = 优先复用客户既有仓库、无仓库时平台随工场附带最小仓库，对上层管线透明；镜像拉取凭据由平台注入、不进应用代码 / 环境 / 日志 / 界面；构建 / 推送 / 拉取失败分阶段返回可读原因；当前运行版本、待上线版本、已停运应用的待运行 / 上次运行版本的镜像恒可拉；**完全离线集群可部署**（基础镜像 / 构建执行体镜像 / 最小仓库随安装包预灌）
>   - **集群能力探测与告警**：部署 / 升级 / 运行时服务启动时探测——CNI NetworkPolicy 支持、可用 StorageClass 及其卷类型、RuntimeClass（按所配沙箱档位）、镜像仓库可达与可推送、运行时服务身份的 RBAC 权限充分性、集群可调度资源 ≥ 最小档位、集群审计日志是否启用（仅提示）；硬前置（NetworkPolicy / StorageClass / 网络文件系统类卷 / 仓库 / RBAC）不满足 → 显式告警且默认不继续（覆盖 = 部署配置项，非交互；运行时服务启动时发现则拒绝新拉起、已运行应用不受影响）；软前置（RuntimeClass / 仅节点本地卷 / 资源紧张）→ 告警 + 降级或标注后继续；**不存在静默路径**；最近一次探测结果写入 F054 AC-23 运行环境状态只读接口（两形态同一接口、平台超管可查，不新增 k8s 专有运维接口或管理界面）
>   - **每应用数据库在 k8s 上的形态承诺**：一个应用一个平台供给的专属数据库、与本地 `bisheng dev` **同名**的连接环境变量注入、标准库可读写、可快照可备份（F054 AC-45 等价）；本版只承接小档（同 F054）：单实例 + 单实例独占卷、实例重建 / 重新调度后数据完整；网络文件系统类卷对小档不成立（拒绝拉起并告警）、仅节点本地卷时标注单节点绑定；卷生命周期随资产——停运 / 实例回收 / 卸载不删卷数据、仅显式删除删（INV-35）
>   - **双形态一致性回归**：F054 稳定性 / 入口 / 生命周期 / 档位 / 日志 / 双开关组合（AC-61）用例、F055 管线用例、F053 `logs`、F052 应用状态 / 日志工具、F056 广场与审计查询面在 k8s 形态**原样执行并全部通过**（GOV-10 验收 5；F054 AC-49）；待上线成因文案、审计事件、通知、CLI / MCP 输出在两形态无形态专有词；双形态回归纳入 v3.0.0 发布验收（各跑一遍）
>   - **交付物**：Helm chart / manifests 覆盖 k8s 形态所需的全部集群侧组件与资源（运行时服务及其身份与权限、app-proxy〔若按 design 落集群内〕、应用命名空间与默认网络策略、镜像构建与仓库对接、可选最小仓库、集群能力探测）+ 离线安装包 + 部署 / 升级 / 卸载步骤与前置条件说明；形态在部署期一次性选定；升级不重启已上线应用；卸载只回收执行体与集群资源、不删应用资产；**不改变平台核心（backend / 前端 / 中间件）的既有部署方式**
> - **本次明确排除**：
>   - **compose 单机形态**的一切（编排后端、崩溃自愈、出站白名单的 compose 实现、沙箱档位的 compose 实现）——**F054**（本 Feature 只实现同一接口的 k8s 后端，不重复拥有接口语义、领域对象、状态动作、app-proxy、入口页、详情页壳、层开关）
>   - **形态间迁移（compose ⇄ k8s）与同环境双形态并存**（PRD-1 §5.1）；**自动扩缩容 / 多副本 / 跨集群调度 / 多机调度**（§5.1 / §5.2 顺延）；**GPU**；**应用间编排**
>   - **发布管线 / 审批 / 版本 / 能力总线**（F055，对形态无感）；**广场 / 授权交互 / 审计面**（F056）；**CLI**（F053）；**SDK**（F057）
>   - **k8s 版本兼容矩阵之外的发行版适配**（国产 k8s 发行版、特定 CNI 的专有能力）——兼容矩阵与适配范围写在 design；spec 只承诺「不满足前置即告警」
>   - **平台核心自身的 k8s 化部署**（平台核心目前无 Helm chart，仍以既有 compose 方式部署；本 Feature 只要求平台核心与集群网络互通、不新增平台核心的 k8s 交付物）
>   - **每应用数据库中档（schema-per-app）与小档→中档升档路径**（F054 本版只做小档，本 Feature 同口径；随 v3.1）
>   - **镜像保留与清理策略、构建缓存、跨仓库同步、镜像签名 / CVE 扫描 / SBOM**（design 记录最小承诺；CVE / SBOM 属方案 v3.1）
>   - **运行期对集群前置的周期性复核**（本版只在部署 / 升级 / 运行时服务启动时探测，运行期退化不做持续监测——见 §4 决议-5）
>   - **闲置回收 / 首请求拉起**（F054 同口径不做，k8s 形态不单独引入——见 §4 决议-3）
>   - **租户级实例数 / 资源配额**（PRD-1 §5.2 已砍；集群侧若客户已配命名空间配额则只纳入容量判定、不产品化）

## 1. 用户故事

作为 **平台超管 / IT（已有 k8s 集群的客户）**，
我希望 **把应用工场装到我们现有的集群上，安装前就知道集群缺什么（网络策略、存储、沙箱运行时、镜像仓库），装上以后应用跑在受限命名空间里、由集群自己保活，不用给平台任何 root 等价的权限**，
以便 **用我们已有的运维体系承载业务人员和开发者造出来的应用，不为它单独养一台机器**。

作为 **开发者（owner）**，
我希望 **`bisheng deploy` 到 k8s 环境和到单机环境的体验一模一样：同一份 `bisheng-app.yaml`、同样的预检 / 审批 / 上线、同样的日志与停运 / 重新启用**，
以便 **不用知道也不用关心平台底下是 compose 还是 k8s，代码在两种客户环境都能原样上线**。

作为 **安全团队**，
我希望 **平台在集群里用的身份权限清单是白纸黑字可核验的、每一次操作在集群审计日志里都能按身份追到，应用容器出不去集群、拿不到集群 API、也拉不到别人的镜像凭据**，
以便 **按最小权限原则放行这套东西进生产集群，而不是接受一个「全有全无」的守护进程权限**。

作为 **租户管理员 / 审批人**，
我希望 **审批单、待上线成因、应用状态、运行日志在 k8s 环境下的表现与培训材料里（compose）完全一样**，
以便 **治理面不因客户机房形态不同而分叉**。

## 2. 验收标准

> AC 编号在本特性内唯一。括号内标注对应 PRD-1 条目与验收序号（如 `↔GOV-10 验收 5`）；凡「实现 F054 AC-xx」者，表示本 Feature 是该 F054 能力在 k8s 形态的第二套后端——**接口语义与产品面归 F054，本 Feature 只拥有 k8s 侧兑现**，不重复拥有。错误码仅作可观测行为引用，定义在 F054 / 本 Feature design.md。

### 2.1 形态选择与部署开关（GOV-10）

- **AC-01** — THE SYSTEM SHALL 使工场运行时层的执行形态（compose / k8s）在部署期由部署配置**一次性**选定；运行期不提供形态切换入口；同一环境不并存两形态；部署文档明示不支持形态间迁移。（↔GOV-10 需求描述 / §5.1；产品方案 §4.8 形态选择）
- **AC-02** — WHERE 工场运行时层以 k8s 形态部署, THE SYSTEM SHALL 使 F054 定义的运行时层部署开关取值 = 已部署，且构建页「托管应用」类型、广场、`/apps/*` 入口与四类兜底页、详情页四 tab 的行为与 compose 形态**完全相同**（F054 AC-30 / AC-51 / AC-58 / AC-62 无差异）；不新增任何形态专有的产品界面或配置界面；界面 / CLI / MCP / 审计事件 / 通知文案不出现形态专有词（Pod / Pending / 容器 等）。（↔GOV-10 界面与交互「无新增配置界面」/ 验收 5；§1.3 前提 4）
- **AC-03** — THE SYSTEM SHALL 使平台后端进程在 k8s 形态下同样**不持有任何集群 API 访问凭据**（部署检查可核验）；集群访问凭据仅由可独立启停的运行时服务持有，且该凭据限定于工场专用命名空间（实现 F054 AC-14 在 k8s 形态的等价）。（↔产品方案 §4.5 编排特权）

### 2.2 编排能力等价（实现 F054 AC-14–24 的第二套后端）

- **AC-04** — WHEN 平台调用构建 / 启动 / 停止 / 重启 / 销毁 / 状态 / 日志 / 启动探活 / 容量准入 中任一能力, THE SYSTEM SHALL 以 F054 定义的形态无关接口语义响应；调用方（F054 状态动作、F055 管线与审批期临时预览实例、F053 `logs`、F052 MCP 应用状态 / 日志工具）不感知形态、不传任何 k8s 专有参数。（↔F054 §3「形态无关的编排接口」；实现 F054 AC-15 / AC-18 / AC-19 / AC-23）
- **AC-05** — WHEN 应用被上线或重新启用, THE SYSTEM SHALL 把平台声明的期望态兑现为集群内该应用的**单副本**工作负载与服务访问点，在启动探活通过后才把 app-proxy 入口切到新实例，旧实例宽限退休；切换窗口内入口呈「发布中」而非报错页；审批期临时预览实例同样经本后端拉起与回收、不占应用运行实例名额。（实现 F054 AC-21 / AC-37；F055 AC-26–28 调用；↔RT-08 验收 3）
- **AC-06** — WHEN 应用进程退出, THE SYSTEM SHALL 由集群工作负载控制器**原生**重启该实例；WHEN 进程存活但健康检查持续失败, THE SYSTEM SHALL 在检测窗口内重建该实例；两者合计使单应用在无人干预下 **5 分钟内**恢复可用，验收口径与时限与 compose **完全相同**。（实现 F054 AC-20；↔RT-08 规则 / 验收 2 / NFR-6）
- **AC-07** — IF 运行时服务进程重启或短暂不可用, THEN THE SYSTEM SHALL 保持已运行应用继续对外服务（由集群保证）；WHEN 运行时服务恢复, THE SYSTEM SHALL 在部署配置的对齐窗口内自动对齐期望态（重建缺失或不健康的实例）。（实现 F054 AC-22 / AC-50）
- **AC-08** — WHEN 上线 / 手动上线 / 重新启用前执行容量准入, THE SYSTEM SHALL 判定集群当前**可调度资源**（含客户已配置的命名空间级配额，若有）能否承载所选档位；不足 → 返回「容量不足」而**不拉起**处于无限等待调度的半可用实例；应用态进入待上线（资源不足）、成因文案与 compose 一致为「资源不足」。（实现 F054 AC-19 / AC-65；↔§3.0.2「k8s 无可调度资源」/ GOV-03 验收 5）
- **AC-09** — IF 上线 / 手动上线 / 重新启用的拉起超过部署配置的时限仍未就绪（无法调度 / 镜像拉取失败 / 探活失败）, THEN THE SYSTEM SHALL 判定为拉起失败并返回**分类的可读原因**（资源不足 / 镜像不可拉 / 应用未就绪），按 F054 AC-65 置待上线并返回成因，不让应用无限期停留在「发布中」；IF 已上线应用崩溃后的自动恢复迟迟未就绪, THEN THE SYSTEM SHALL **持续尝试恢复**（不引入任何「恢复失败」终态、不新增应用态）、入口保持「应用恢复中」页而非报错页，且一旦超过 RT-08 的 5 分钟时限即视为承诺被违反——在运行环境状态接口（AC-32）与运行日志中告警可查（含当前阻塞原因：资源不足 / 镜像不可拉 / 应用未就绪）。（↔RT-08 验收 2 / 4；F054 AC-36 / AC-65）
- **AC-10** — THE SYSTEM SHALL 使实例状态、健康、当前运行版本与运行日志只读接口在 k8s 形态取到的**内容范围与 compose 一致**，日志语义（内容范围、时间范围、刷新与筛选、空态、权限口径）与 F054 AC-23 / AC-55 完全相同，不作 k8s 侧强化或削弱。（实现 F054 AC-23 / AC-55；↔WB-13 / DEV-04 验收 12）
- **AC-11** — THE SYSTEM SHALL 使每个应用在集群内恒为单副本：不提供副本数、并发或自动扩缩容的任何调节入口，规格调整仅经档位。（实现 F054 AC-24；↔GOV-03 验收 1 / §5.1）
- **AC-12** — THE SYSTEM SHALL 使应用工作负载仅经 app-proxy 可达：不为应用创建任何集群外可达的暴露方式（节点端口 / 负载均衡 / 集群入口路由），集群内其它命名空间的工作负载不能直连应用；绕过入口直连不可行。（实现 F054 AC-33；↔产品方案 §4.5 不变量①）

### 2.3 命名空间级最小权限与可审计（RBAC）

- **AC-13** — THE SYSTEM SHALL 使运行时服务以专用集群身份运行，其权限限定于工场专用命名空间内应用工作负载与构建执行体所需的资源类型与动作；该身份不持集群级权限、不能读写其它命名空间、不能创建特权或挂载宿主机敏感路径的工作负载。（↔产品方案 §4.5「限定命名空间的 ServiceAccount + RBAC」）
- **AC-14** — THE SYSTEM SHALL 随交付物提供该身份的完整权限清单（资源类型 × 动作 × 命名空间），使安全团队可对照集群实际 RBAC 逐项核验；WHERE 集群已启用审计日志, THE SYSTEM SHALL 使运行时服务对集群的每一次操作可在集群审计日志中按该身份追溯（本 Feature 不新增平台侧审计面；集群审计日志是否启用属客户集群配置，AC-30 探测项与 AC-39 前置说明各提示一句、不作硬前置）。（↔产品方案 §4.5「天然可审计」）
- **AC-15** — THE SYSTEM SHALL 使应用工作负载与构建执行体自身**不持有任何集群 API 访问身份**（不挂载可用于调用集群 API 的凭据），应用代码与构建过程无法调用集群 API。
- **AC-16** — WHEN 实例以默认沙箱档启动, THE SYSTEM SHALL 使其具备与 F054 AC-17 **同一清单**的加固：按档位的 CPU / 内存上限、除平台指定可写路径（临时目录与数据目录）外文件系统只读、不可提权、网络受控（AC-21）、崩溃自愈（AC-06）；本 Feature 不在该清单之外单方面追加对应用进程运行身份等的形态专有强制（否则与 AC-25「同一构建定义」冲突）；核验手段随交付物。（实现 F054 AC-17；↔产品方案 §4.5 分档表「等价的 Pod securityContext」）

### 2.4 档位与沙箱档位映射（GOV-03 / 产品方案 §4.5）

- **AC-17** — WHEN 实例按某档位启动, THE SYSTEM SHALL 使其 CPU / 内存的请求量与上限与该档位规格一致（可在集群中核验）；档位的产品面——发布时从预置档位选择、未声明取轻量、停用只拦新选择、规格调整自应用下一次发布 / 重新启用生效、运行中实例不受影响——与 compose **完全相同**。（↔GOV-03 规则「k8s 映射为 Pod 的 requests / limits」/ 验收 4；实现 F054 AC-63 / AC-64）
- **AC-18** — WHEN 某应用耗尽其内存上限, THE SYSTEM SHALL 只重启该应用自身；WHEN 耗尽 CPU 上限, THE SYSTEM SHALL 只限制该应用自身；平台与其它应用不受影响。（实现 F054 AC-47；↔RT-08 验收 1 / GOV-03 验收 4）
- **AC-19** — THE SYSTEM SHALL 把沙箱档位作为**部署级配置**（非产品面）提供三档：默认档（AC-16 加固 + 资源限额 + 出站白名单 + 控制器自愈）、推荐档、加固档——后两档各对应一种集群 RuntimeClass（具体运行时选型在 design）；WHERE 部署配置为推荐档或加固档, THE SYSTEM SHALL 仅在集群探测到对应 RuntimeClass 存在**且**节点架构 / 形态支持该档（加固档仅裸金属；不被任一沙箱运行时支持的架构两档均不可用）时启用；IF 不满足, THEN THE SYSTEM SHALL 降级为默认档并在探测结果与部署输出中**显式告警**（标明不可用档位与原因），不静默。（↔产品方案 §4.5 分档表；《调研》§2.4 修正一 / 二、§3 信创矩阵）
- **AC-20** — THE SYSTEM SHALL 使沙箱档位切换不改变出站白名单、资源限额、身份注入、只读文件系统等一切其它运行时承诺；换档只增减隔离强度。（↔F054 §3「出站控制不因换隔离档位而变化」；《调研》§2.8「换 runtime 不解决 egress」）

### 2.5 出站白名单（NetworkPolicy 及其等价语义）

- **AC-21** — WHILE 运行期, THE SYSTEM SHALL 默认封禁应用工作负载的一切出站——含直连 IP、UDP、集群内其它工作负载与其它命名空间、集群 API——只放行平台 API（含平台供给的每应用数据库与附件存储端点）与应用包声明的域名；白名单的声明形态、按域名生效、随发布上线生效等通用规则**引用** F054 AC-16 与 F055 AppManifest（表 1），本 Feature 不另定义；与 compose 使用**同一验收用例**。（实现 F054 AC-16 运行期；↔DEV-04 契约「白名单外的外网地址」）
- **AC-22** — WHILE 构建期, THE SYSTEM SHALL 只放行平台配置的包源、镜像仓库（拉取基础镜像 / 推送产物）与平台自身分发端点（同 F054 AC-16 构建期口径），其余出站一律阻断；构建执行体与运行工作负载的白名单来自同一规则来源，两形态同规则。（实现 F054 AC-16 构建期；↔产品方案 §4.5「构建期 egress 白名单两形态同规则」）
- **AC-23** — IF 集群 CNI 不支持 NetworkPolicy（或探测到出站策略不被执行）, THEN THE SYSTEM SHALL 在部署前探测阶段显式告警「出站白名单将不生效」并**默认拒绝继续部署**；仅当部署配置中显式设置了覆盖项时方可继续（覆盖是部署配置项、不是交互确认），且该环境处于「出站白名单未生效」状态在运行环境状态接口（AC-32）中持续可查、运行时服务每次启动重复告警；不存在默认它存在的路径。（↔产品方案 §4.5「k8s 形态的前置条件」；§4 决议-4）

### 2.6 镜像构建与分发（k8s 形态净新增件）

- **AC-24** — WHEN 收到构建请求, THE SYSTEM SHALL 在集群内以**一次性、无守护进程、非特权**的构建执行体完成镜像构建（不依赖节点容器守护进程、不使用 DinD、不交出 docker.sock），构建完成或失败后回收该执行体；构建执行体只在构建期存在、不计入应用运行实例。（↔产品方案 §4.5「构建器」；§4 决议-1）
- **AC-25** — THE SYSTEM SHALL 使两形态对同一 `runtime` 取值使用**同一份构建定义**，同一应用包在两形态的构建结果行为等价：成功 / 失败判定一致、失败阶段与原因分类一致；`runtime` 取值不在支持集合内 → 同 F054 AC-15 拒绝并列出支持的取值。（↔产品方案 §4.5「产品面一致性」；实现 F054 AC-15）
- **AC-26** — WHEN 构建成功, THE SYSTEM SHALL 把产物推送到部署期配置的镜像仓库，使集群所有节点可拉取；仓库策略：优先复用客户既有仓库（部署配置地址与凭据）、无仓库时平台随工场附带最小仓库；两种来源对发布管线与上层调用方**透明**。（↔产品方案 §4.5「镜像仓库」；§4 决议-2）
- **AC-27** — THE SYSTEM SHALL 使镜像拉取凭据由平台注入到应用工作负载与构建执行体，不进应用代码、不出现在应用可读的环境变量 / 文件、不出现在运行日志与任何界面。（↔产品方案 §4.5「凭据经 imagePullSecret 注入，不落进应用代码」/ NFR-2）
- **AC-28** — IF 镜像仓库不可达、推送失败或节点拉取失败, THEN THE SYSTEM SHALL 返回**分阶段**（构建 / 推送 / 拉取）的可读失败原因供 F055 预检与上线终检输出；上线终检因拉取失败 → 应用态置待上线、成因为「上线失败」而非「资源不足」（F054 AC-65 分支）。（↔DEV-04 验收 7；F055 AC-11 / AC-31）
- **AC-29** — THE SYSTEM SHALL 使每个应用下列版本对应的镜像在仓库中恒可拉：当前运行版本、待上线版本、以及已停运应用的待运行版本与上次运行版本（崩溃重建、重新调度、重新启用、手动上线均不因镜像缺失而失败）；任何镜像清理均不得影响上述版本（清理策略的其余部分不在本版承诺，design 记录最小口径）。（↔RT-07 验收 6 / RT-08 / F054 AC-04 / AC-41）

### 2.7 集群能力探测与告警

- **AC-30** — WHEN 以 k8s 形态执行部署或升级、以及运行时服务启动时, THE SYSTEM SHALL 执行集群能力探测，至少覆盖：CNI NetworkPolicy 支持（含出站策略实际生效性）、可用 StorageClass 及其**卷类型**（能否满足小档每应用数据库的单实例独占卷要求：网络文件系统类 / 仅节点本地 / 可跨节点跟随）、RuntimeClass（按所配沙箱档位）、镜像仓库可达与可推送、运行时服务身份的 RBAC 权限充分性（对照 AC-14 清单）、集群可调度资源 ≥ 最小档位、集群审计日志是否启用（仅提示）；输出逐项通过 / 不通过与原因。（↔产品方案 §4.5「部署前必须探测并在不满足时显式告警」；discovery §5 风险 4）
- **AC-31** — IF 任一**硬前置**——NetworkPolicy 不支持 / 无可用 StorageClass / StorageClass 卷类型为网络文件系统类（对小档每应用数据库不成立）/ 镜像仓库不可达 / RBAC 不充分——不满足, THEN THE SYSTEM SHALL 显式告警且**默认不继续**（仅当部署配置中显式设置了覆盖项方可继续，覆盖事实记入探测结果；覆盖是部署配置项、不是交互）；IF 任一**软前置**——RuntimeClass 缺失或不适用 / StorageClass 仅提供节点本地卷 / 可调度资源紧张——不满足, THEN THE SYSTEM SHALL 告警并继续：RuntimeClass 按 AC-19 降级、节点本地卷在探测结果中标注「单节点绑定：节点故障时该类应用需人工干预恢复、RT-08 自愈时限对该情形不成立」、资源紧张按 AC-08 在上线时体现为容量不足；WHEN 运行时服务启动时探测到硬前置缺失且无覆盖项, THE SYSTEM SHALL 拒绝新的拉起 / 重新启用 / 构建请求（返回可读原因，已运行应用不受影响）并告警；**任何前置缺失都不存在静默路径**。（↔discovery §5 风险 4；《调研》§2.7 硬约束；§4 决议-4）
- **AC-32** — THE SYSTEM SHALL 把最近一次探测结果（探测时间、逐项结论与原因、覆盖记录、当前生效的沙箱档位）写入 F054 AC-23 定义的**运行环境状态只读接口**（容量 / 编排后端可用性 / 前置自检结果——两形态同一接口、平台超管可查），本 Feature 只扩充该接口的前置自检项、不新增 k8s 专有运维接口或管理界面（GOV-10 无新增配置界面）；部署工具同时在输出中给出同一结果。（实现 F054 AC-23 前置自检项；§4 决议-5）

### 2.8 每应用数据库与数据卷（k8s 形态承诺）

- **AC-33** — THE SYSTEM SHALL 在 k8s 形态为每个应用供给一个平台专属数据库，以与本地 `bisheng dev` **同名**的连接环境变量注入、标准库可读写、可随存档快照与平台备份（实现 F054 AC-45）；本版只承接**小档**（与 F054 同口径——F054 只做小档；中档与小档→中档升档路径随 v3.1、不在本 spec 承诺）：小档 = 单实例 + **单实例独占卷**（不共享、不多写），卷来自探测通过的 StorageClass；实例重建或被重新调度到其它节点后应用数据完整无损。（↔RT-07 验收 1 / DEV-07；《调研》§2.7 硬约束）
- **AC-34** — IF 拉起小档应用时其数据卷只能落在网络文件系统类 StorageClass 上, THEN THE SYSTEM SHALL 拒绝拉起并返回可读原因（成因归「上线失败」，非「资源不足」）、同时告警可查（AC-32）；仅节点本地卷时按 AC-31 软前置口径拉起并标注单节点绑定。（↔RT-08 / 产品方案 §4.5 前置②；AC-31 硬 / 软清单）
- **AC-35** — THE SYSTEM SHALL 使应用数据卷的生命周期随应用资产而非随实例：停运、实例回收 / 崩溃 / 重建、运行时服务重启、工场运行时层卸载均不删除卷数据；仅 owner 显式删除流程（F054 AC-43）删除。（↔INV-35 / F054 AC-39 / AC-40）

### 2.9 双形态一致性回归（INV-33 承接）

- **AC-36** — THE SYSTEM SHALL 使下列既有验收用例在 k8s 形态**原样执行并全部通过**（用例不含形态专有步骤、断言不含形态分支）：F054 稳定性（AC-20–22、AC-46–50）、统一入口（AC-25–36）、生命周期动作（AC-39–44、AC-65）、档位落地（AC-63–64）、日志与数据面（AC-23、AC-55–56）、两个部署级开关任意组合下平台可正常启动（AC-61）；F055 发布管线用例（提交 → 预检 → 扫描 → 审批 → 上线终检 → 待上线 → 手动上线 → 停运态提交，含审批期临时预览实例）；F053 CLI `logs`；F052 MCP 应用状态 / 日志工具；F056 广场可见性与审计查询面——均为「两形态表现一致」的验证；双形态回归纳入 v3.0.0 发布验收，两形态各跑一遍、任一形态失败即不通过。（↔GOV-10 验收 5 / §1.3 前提 4；F054 AC-49；候选 INV-33）
- **AC-37** — THE SYSTEM SHALL 使待上线成因、上线失败成因、应用态徽标、审计事件内容、站内消息文案、CLI 与 MCP 输出在两形态**逐字一致**（成因统一为「资源不足」/「上线失败」），不出现形态专有词。（↔§3.0.2 / GOV-03 验收 5 / GOV-04）
- ~~**AC-38**~~ — **已移除**（2026-08-17 审查：原条目是用例编写纪律而非可验收的系统行为，移至 §3「用例纪律」与 §4 决议-9；编号保留、不复用）。

### 2.10 交付物与升级 / 卸载

- **AC-39** — THE SYSTEM SHALL 交付 Helm chart / manifests，覆盖 k8s 形态所需的全部**集群侧组件与资源**：运行时服务及其集群身份与权限、app-proxy（若按 design 落在集群内）、应用命名空间与默认网络策略、镜像构建执行体与仓库对接配置、可选的平台附带最小仓库、集群能力探测；并交付部署 / 升级 / 卸载步骤与前置条件说明（含 AC-14 权限清单与集群审计日志启用建议、AC-30 探测项清单、形态选择说明、离线部署说明）以及**离线安装包**（AC-42）；**不改变平台核心（backend / 前端 / 中间件）的既有部署方式**，只要求平台核心与集群网络互通。（↔GOV-10 需求描述 / 产品方案 §4.8「Helm chart / manifests」）
- **AC-40** — WHEN 执行 k8s 形态的升级, THE SYSTEM SHALL 保持已上线应用持续对外服务（运行时服务与 app-proxy 升级不重启应用实例，AC-07 同向）；升级步骤自动重新执行 AC-30 探测并按 AC-31 处置。
- **AC-41** — WHEN 卸载工场运行时层（k8s 形态）, THE SYSTEM SHALL 只回收执行体与本 Feature 交付的集群侧资源，不删除应用资产（代码快照、每应用数据库与数据卷、附件）；卸载后 `/apps/*` 呈 F054 AC-30 引导页、构建页与广场按 F054 AC-58 隐藏、平台其余功能零变化。（↔RT-07 验收 2 / GOV-10 验收 1–2 / F054 AC-40 / AC-59）

### 2.11 审查增补（2026-08-17）

- **AC-42** — WHERE 目标集群为完全离线（air-gapped）环境, THE SYSTEM SHALL 仍可完成部署、构建与拉起：各 `runtime` 取值的基础镜像、构建执行体镜像、平台附带最小仓库及其它集群侧组件镜像随离线安装包**预灌**，构建期包源为平台配置的自托管镜像源；无任何外网访问即可走通「部署 → 探测通过 → deploy 构建 → 推送 → 拉起」；镜像仓库可达性仍按 AC-30 探测。（↔《调研》§3 信创矩阵「完全离线」行 / 产品方案 §4.5「信创可离线预灌」；F054 AC-16 构建期）
- **AC-43** — WHEN 构建执行体运行, THE SYSTEM SHALL 使其受部署配置的**超时**、CPU / 内存**资源限额**与**并发上限**约束：超时 → 立即回收执行体并向调用方返回「构建超时」的可读失败原因（F055 预检 / 上线终检据此输出）；达到并发上限的新构建请求排队并可查询排队状态，不静默丢弃；执行体资源触顶只影响该次构建、不影响运行中的应用与平台。（↔DEV-04 验收 7 / RT-08 需求描述「运行隔离」；F055 AC-11）

## 3. 边界情况

> 只写期望的对外行为；机制与落点见 design.md §4 / §5。

- **三前置缺失 = 告警而非静默降级**：NetworkPolicy 缺失 → 出站白名单为空、属硬前置（默认阻断、部署配置项显式覆盖后状态持续可见）；StorageClass 缺失或卷类型为网络文件系统类 → 小档应用数据卷不成立、硬前置；RuntimeClass 缺失 → 推荐 / 加固档降默认档、软前置；仅节点本地卷 → 软前置、标注单节点绑定。任一缺失都不能让部署「看起来成功」；运行时服务启动时发现硬前置缺失 → 拒绝新拉起、已运行应用不动。
- **镜像仓库不可达时的失败归因**：构建成功但推送失败 ≠ 构建失败——分阶段返回原因；上线终检时拉取失败是「上线失败」不是「资源不足」，否则管理员会去加资源而实际是仓库问题。
- **容量不足 vs 拉起失败 vs 恢复中**：前两者落应用态（待上线（资源不足）/ 待上线（上线失败））；已上线应用崩溃后的恢复**没有失败终态**——持续尝试、入口保持「应用恢复中」、超过 5 分钟即 RT-08 承诺被违反并告警可查。k8s 上「无限 Pending」在上线路径必须被时限收敛为待上线成因，在恢复路径表现为可查的阻塞原因，不能让应用永远「发布中」、也不能给「恢复中」发明一个新应用态。
- **单实例独占卷与单实例**：小档数据卷单写者，与 GOV-03 单应用单实例自洽；升级切换（新旧实例并存的宽限窗口）不得让两个实例同时写同一卷——对外表现为「切换成功后数据连续、无丢失无双写」，机制在 design。网络文件系统类卷对小档不成立（拒绝拉起，非降级）；节点本地卷 → 跨节点重调度受限，探测阶段标注。
- **离线集群**：完全离线是信创常态而非特例——基础镜像 / 构建执行体镜像 / 最小仓库随安装包预灌；「仓库可达」探测在离线场景指向平台附带最小仓库或客户内网仓库，不指向外网。
- **构建执行体的失控**：超时 / 资源触顶 / 并发上限是构建期的三道闸——超时回收并返回原因、触顶只影响该次构建、达上限排队可查；构建执行体不计入应用实例、也不能因构建拖垮平台或运行中的应用。
- **用例纪律（原 AC-38，非系统行为）**：本 Feature 新增的验收用例只覆盖 k8s 专有承诺（§2.3 RBAC / §2.4 沙箱档映射 / §2.6 镜像 / §2.7 探测 / §2.10 交付物 / §2.11 离线与构建治理）；凡产品行为一律复用 F054 / F055 / F053 / F052 / F056 用例在 k8s 上原样跑，不另写 k8s 版本，避免两套用例漂移（§4 决议-9）。
- **CNI / 防火墙栈差异**：NetworkPolicy 由 CNI 实现，不同 CNI 对出站策略与按域名放行的支持不同；对外承诺恒为「域名白名单语义生效」，实现路线（策略原生能力 / 等价出口代理）由 design 按探测结果选择；nftables / iptables 差异属 compose 形态（F054）关注点，k8s 形态只关注 CNI 能力。
- **LoongArch 无 RuntimeClass**：gVisor 与 Kata 全系均无 LoongArch 支持，龙芯集群唯一可用档 = 默认档；探测报告标明、不给「加固档」想象空间。
- **加固档仅裸金属**：虚机（含嵌套虚拟化）不启用加固档；探测按节点形态判定，不给「虚机上开加固档」留想象空间。
- **镜像保留与清理不在本版**：只承诺当前运行版本与待上线版本恒可拉；旧版本镜像的保留期与清理、构建缓存、多仓库同步在 design 登记为后续。
- **平台核心与集群互通**：平台核心（backend / app-proxy 的调用方 / 中间件）可能不在集群内；对外只要求「互通」（app-proxy 可达应用工作负载、应用可达平台 API），落位在 design。
- **运行时服务身份被收窄后的自检**：若集群管理员事后缩减该身份权限，运行时服务下一次启动的探测（AC-30 RBAC 充分性）应报告缺失项，而不是在某次上线时才以模糊错误失败。
- **卸载 ≠ 删除**：卸载工场运行时层回收执行体与集群资源、保留一切应用资产；重新部署后应用可按 F054 重新启用语义恢复。
- **形态选择不可逆是承诺不是缺陷**：文档明示；将来做形态迁移须先解决每应用数据库与镜像的搬迁路径（PRD-1 §5.1）。

## 4. 待澄清决议

> 2026-08-17 用户授权全自动模式：以下各项按建议直接定案，记录理由供追溯。

- **[决议-1] 构建器 = 无守护进程构建器跑在一次性构建 Pod 中；DinD 与节点 docker.sock 均否决。** 理由：产品方案 §4.5 编排特权是全案最重安全约束——不交出 docker.sock、不起 DinD；无守护进程构建与该立场同向而非妥协；多节点上 Pod 可被调度到任意节点，本机产物不成立、镜像必须进仓库。**何时重新考虑**：不会——这是安全立场，不是性能取舍。
- **[决议-2] 镜像仓库策略 = 优先复用客户既有仓库；无仓库时平台随工场附带最小仓库；不做多仓库同步、不做镜像签名 / CVE / SBOM。** 理由：用 k8s 的企业多半已有 Harbor，复用零新增运维面；附带最小仓库只为无仓库客户兜底；签名 / CVE / SBOM 属方案 v3.1 发布期安全门。
- **[决议-3] k8s 形态不做闲置回收 / 首请求拉起。** 理由：F054 已把闲置回收列入排除（PRD-1 §5.1 未列、方案 §4.5 只作 runtime-manager 容量治理的可选项）；双形态产品面一致要求两形态同口径，k8s 侧单独引入会造成行为分叉。**何时重新考虑**：随 F054 一起。
- **[决议-4] 前置缺失的处置只分两档，无第三档：硬前置 = NetworkPolicy 不支持 / 无可用 StorageClass / 卷类型为网络文件系统类 / 镜像仓库不可达 / RBAC 不充分（默认阻断；覆盖 = 部署配置项而非交互确认，覆盖后状态持续可见；运行时服务启动时发现则拒绝新拉起、已运行应用不受影响）；软前置 = RuntimeClass 缺失或不适用 / 仅节点本地卷 / 可调度资源紧张（告警 + 降级或标注后继续）。** 理由：产品方案 §4.5 判定出站白名单比换沙箱 runtime 更重要——它缺失时防线是空的，必须阻断；网络文件系统类卷对小档每应用数据库是正确性问题（《调研》§2.7 硬约束）而非性能取舍，同样阻断；沙箱档位是隔离强度增量、缺失可降级；节点本地卷只影响节点故障场景的自愈承诺，标注即可；资源紧张是运行期常态，由容量准入在上线时体现更准确。审查删去了「管理员知情后方可继续」这类介于阻断与继续之间的第三档——它既不可测也不可自动化；「显式覆盖」是部署配置项，保留给非生产 / 试用集群，不给静默路径。
- **[决议-5] 探测在部署工具中执行（部署 / 升级）并在运行时服务启动时复核；结果写入 F054 AC-23 的运行环境状态只读接口（两形态同一接口、平台超管可查），本 Feature 只扩充前置自检项；不新增 k8s 专有运维接口或管理界面；不做运行期周期复核。** 理由：GOV-10 明示「无新增配置界面」且两形态产品面一致——若只在 k8s 侧加告警页面或专有接口即产品面分叉；F054 已定义两形态共用的状态接口，复用即可；启动时复核覆盖「集群管理员事后改权限 / 换 CNI」的多数场景；周期复核的价值不抵新增常驻负担，design 可作为可选项。
- **[决议-6] 沙箱档位是部署级配置、不进产品面；本 Feature 只承诺「若配置则映射 + 缺失即降级告警」。** 理由：与 F054 一致（F054 只交付默认档，推荐 / 加固档的 compose 实现列入其 design §8 后续）；产品方案 §4.5 分档表本就按环境能力选择而非按应用选择；PRD 未把沙箱档位暴露给任何角色。
- **[决议-7] 运行时服务与 app-proxy 在 k8s 形态的落位（集群内 / 集群外）由 design 定；spec 只约束凭据限定命名空间、平台后端不持凭据、平台核心部署方式不变。** 理由：落位是纯 How（取决于客户网络与平台核心的部署位置）；三条约束已足以保证安全边界与产品面不变。
- **[决议-8] 容量准入 = 集群可调度资源判定；客户已配置的命名空间级配额只纳入判定、不产品化；不引入任何租户级配额。** 理由：PRD-1 §5.2 已砍租户级实例数配额并注明补做须以资源量为单位；GOV-03 待上线成因已泛化为「资源不足」，k8s 侧无论是节点资源还是命名空间配额不足，对用户都是同一成因。
- **[决议-9] 双形态回归 = 复用 F054 / F055 / F053 `logs` / F052 应用状态与日志工具 / F056 广场与审计查询面的用例集在 k8s 上原样跑，不另写 k8s 版产品用例；本 Feature 只新增 k8s 专有承诺的用例（原 AC-38 改为 §3 用例纪律，不作系统行为验收）。** 理由：F054 AC-49 已要求用例不含形态专有步骤——两套用例必然漂移，复用一套才能真正验收「产品面一致」；凡对形态无感的消费方（CLI / MCP / 广场 / 审计）都应被验证为「表现一致」而不是被假设一致；k8s 专有部分（RBAC / 探测 / 镜像 / 离线 / 构建治理 / 交付物）在 compose 上无对应物，只能单写。
- **[决议-10] 排期：与 F055 并行、须在 F055 联调前可用（方案 Wave-2）；不在 MVP-114 纵切上；k8s 验证环境（自建 / 客户 / 云）在 design 阶段登记并作为 tasks 前置。** 理由：方案 §5.1 波次说明「F113 须在 F112 发布管线联调前可用」且「不可裁剪顺延」；114 是 compose 单机，无法承载本 Feature 的 E2E。
