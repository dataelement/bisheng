用户与问答的所属组织筛选 · 技术设计

版本 1.0 · 2026-11-03 · 状态：设计已确认 · 需求：USER-QA-ORG 1.0

做什么

给用户统计和实时问答写入所属公司、所属部门、所属科室，让已关联的筛选能按这三列缩小图表。

为什么

需求 1.0 已确认。现在这两类统计没有这三列，筛选会被跳过。

影响谁

看板查看者和编辑者。内容统计、其他数据集、已保存的筛选关联名单不变。

关键选择

三列直接写进统计文档，字段名与内容统计相同。问答不改用这个人今天的部门。设计 1.0 已确认。

失败后怎么办

回刷没做完时，选了组织会暂时少算缺列的人。代码回滚后筛选再次跳过，已写入的名称可以留在索引里。

当前进度与待决

无产品待决。上线日期未定。确认本设计后才编码。

1. 方案摘要

人员主部门沿组织路径拆成三个全称，写到统计文档的 belonging_company_name、belonging_department_name、belonging_office_name。数据集声明同名字段后，现有图表查询会把筛选当成普通条件。查询代码不新加一套组织算法。

用户统计索引 mid_user_engagement_stat 里，新增用户文档和参与度文档都要写。实时问答索引 mid_realtime_qa_question_fact 把已经记下的提问人三级复制过来；没有提问人三级时，才用该行记下的主部门编号展开，不用这个人今天的主部门。

空组织不写「未分类」，也不写空字符串。按这三列分组时，缺字段的文档归进一个空键分组，界面沿用现有的「未分类」展示。这个空键只加在用户统计和实时问答上，内容统计的分组不变。

重要失败结果代码发布后、用户索引回刷完成前，选中某个部门会把还没有这三列的用户行排除。未选组织时，人数与发布前一致。

3. 现状及目标架构

现状：内容统计已经把文件登记组织写成这三个字段。实时问答把提问人主部门写成 asker_company_name、asker_department_name、asker_office_name。用户统计只有主部门编号或部门列表，没有公司、部门、科室三级。图表查询在数据集维度里找不到字段时，跳过该筛选。

组织展开函数是 resolve_organization_names。它沿部门 path 取每一级第一个有效名称，名称用 department.name 全称。唯一主部门判断是 _load_unique_primary_departments。部门是否可用沿用 _registered_uploader_department：必须属于该行租户、状态为 active、未删除。

数据集定义在 init_dataset.py。启动时 _upgrade_dashboard_datasets 会按种子覆盖已列入刷新名单的数据集。用户数据统计 mid_user_increment 和实时问答 mid_realtime_qa_question_fact 已在这个名单里。隐藏的 mid_user_daily_participation、mid_active_user 指向同一用户索引，一并加上这三列，避免旧图的数据集编码认不出字段。不因此把隐藏数据集重新开放到选择器。

4. 核心流程与状态

写入

写入点
路径现有入口本次
新提问RealtimeQaQuestionFact.record_success 和实时回填构造与提问人三级同时赋值。值相同
提问合并merge_qa_document 已保留事件当时的提问人三级三列与提问人三级使用同一保留规则
登录与参与度对账record_login、_reconcile_participation_days用本次写入主部门编号的那个部门展开三列
参与度合并merge_participation_document主部门编号被保留时，三列也从当前文档保留，不用本次希望写入的新部门
新增用户同步sync_mid_user_increment写入时取唯一主部门。整份文档替换，因此新文档必须自带三列

回刷

单独的回刷只做局部更新，不整份替换。文档编号不变。用户参与度按文档里的 primary_department_id 展开。问答优先复制 asker_*；这三列都空时才用该行 primary_department_id。新增用户按回刷当时的唯一主部门。没有可用部门时删除这三列。

回刷可重复执行。同一规则重复写入不新增人数。日志只记检查数、写入数、清空数和文档类型，不记姓名和令牌。

查询

筛选逻辑不改。数据集有字段且查看者选了值，就按全称做 terms 条件。缺字段的文档匹配不到。

分组时，仅当数据集是用户统计或实时问答、且维度是这三列之一，terms 聚合增加 missing: ""。空键到界面后仍显示「未分类」。内容统计不加这个参数。

5. 关键决策

DEC-1 三列写进文档，而不是查询时改字段名
选项结果不选的原因
选定：文档写入同名字段筛选、分组、导出都读同一字段。用户统计没有可对照的旧列，本来就要写问答需要一次复制回刷
查询时把 belonging 改写成 asker问答旧数据不用回刷分组、导出、明细若漏一处就仍对不上。用户统计仍然要写字段，两套机制并存

重新考虑条件：如果实时问答索引不能做局部更新，再改成查询对照。当前索引更新机制已经存在。

DEC-2 参与度三列跟随被保留的主部门编号
选项结果
选定：编号保留时，三列也保留满足 AC-UQ-007。已登录行不会在名册同步时被今天的部门改写三列
回刷和每次同步都按今天的主部门重算会违反「不改成今天的主部门」

未登录名册行今天就会更新主部门编号。三列与该编号一起更新，这是现有名册行为，不是新口径。

DEC-3 是约束而不是取舍：新增用户旧行没有注册当时的部门快照，回刷只能用执行当时的唯一主部门。需求 1.0 已写明。

6. 详细契约

无新的 HTTP 接口，无 MySQL 加列，无看板组件数据改写。筛选下拉仍由现有组织树接口按字段前缀 belonging_ 给出全称选项，展示简称的规则不变。

统计文档字段
字段含义写入空值
belonging_company_name路径上第一个有效公司的 namekeyword，可被现有映射更新逻辑追加不写字段。不写空字符串，不写「未分类」
belonging_department_name路径上第一个有效部门的全称同上同上。科室挂在部门下时这里是上级部门
belonging_office_name路径上第一个有效科室的全称同上路径没有科室则为空

数据集维度名称是所属公司、所属部门、所属科室，字段标识与上表相同。加到 mid_user_increment、mid_user_daily_participation、mid_active_user、mid_realtime_qa_question_fact。后两个用户数据集保持隐藏。

分组聚合仅在上述用户与问答数据集、且字段是这三列时附加 missing: ""。筛选条件不使用 missing，因此选中具体组织时缺字段行不计入。

模块与不改的边界

投影代码在 src/backend/bisheng/telemetry/domain/mid_table/ 和 src/backend/bisheng/worker/telemetry/mid_table.py。数据集种子在 init_dataset.py。分组缺失桶在图表查询组装处按数据集判断。

不改 DimensionFilterConfigurator 的同数据集限制。不改内容统计投影。不改 dashboard、dashboard_component。

安全：回刷日志不包含姓名、部门全称清单和令牌。组织名称只出现在统计文档和现有查询结果里。

性能：不在打开看板时查主部门。不承诺新的时延数字。回刷按现有批量更新执行，没有新的并发度指标。

9. 发布与恢复

前提：组织表可读，两个统计索引允许追加 keyword 字段。现有索引类已经会在启动时补映射。

启用：部署后端后执行一次用户索引回刷和一次问答索引回刷。完成标准是日志里新增用户、参与度、问答三类的检查数都大于零，或该环境确实没有该类文档。清空数单独可见。

暂停：没有开关。若回刷日志失败，停止继续使用筛选后的用户人数作为正式数，未选组织的图仍可看。

回滚代码：筛选对没有维度定义的数据集会再次跳过。已写入索引的三列不删除。回滚不修改已保存看板。不保证回滚后分组「未分类」桶消失前的文档被改回；缺字段行只是不再被新查询归组。
