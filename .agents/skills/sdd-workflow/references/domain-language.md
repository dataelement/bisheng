# 领域语言与跨阶段命名

生成或修改业务文档、涉及模块／实体／重要抽象命名、或发现语义冲突时读取。只消费已有定义时，按下述方式取得相关条目即可；新增／改变概念或无法解释的冲突，才读取并应用 [domain-modeling](../../domain-modeling/SKILL.md)。它不是额外必经阶段。

## 一份有效来源

用户指定及项目已有词典、术语库、契约和模块知识优先。用当前特性登记或交接确定相关业务范围、词典位置与修订、本次概念增量位置；已有来源有效就沿用，不从全局 skill 路径推断业务项目位置。
没有约定时，单业务范围可从项目根 GLOSSARY.md 开始；多范围确需分开时再用 GLOSSARY-MAP.md 指向实际词典。按需创建，不复制同一概念的多份可编辑正文。简单 Bug 的对象和预期已清楚时直接复用已有依据，缺词典不成为新门槛。

每条业务定义保持简短，记录规范名、含义、业务范围、易混别名或区别及必要关系。已有概念标识／稳定锚点优先；跨范围重名或改名确需追踪时再补稳定标识，不把所有类、方法、通用技术词登记成领域概念。
技术名称映射归设计或模块契约：业务概念 → 模块职责／实体 → 真实代码、接口、存储或展示名称。一个任务与多次执行尝试可以是不同对象；同一对象的业务名和历史 API 名也可不同，需解释真实对应关系。

## 候选、目标与现状

新定义立即记录在当前需求／设计草稿并标候选，不自行提升为项目已确认规则。既有确认继续有效；业务定义随需求确认、技术映射与取舍随设计确认。措辞一致化在授权内处理；改变身份、关系、职责、生命周期或对外契约时按原有规则重新对齐。
各阶段消费“选定词典基线＋本次已确认增量”。需求／设计确认表示目标约束，不等于代码已实现或生产已生效。交付收尾核实实际变化后更新必要模块知识，注明代码与状态；旧特性、旧构建及其 QA 证据保留原基线。未提交材料用修订或内容指纹说明，不只给旧 HEAD。
词典位置、修订、增量、确认与技术映射引用保存在现有登记或接续索引中；已有格式能表达时直接复用。跨工程给出可取得的仓库／版本／路径或制品，不能只有个人绝对路径。多人编辑共享定义时按条目核对冲突后合并，不用整体文件替换吞掉他人定义。

## 生成与收尾

需求、设计、用例、任务与代码沿用同一概念；正文、图标签、表格、数据、状态、断言及技术标识的对应关系一并检查。正式 HTML 可展示相关条目的有来源、修订和状态的摘录，不独立维护第二套定义；业务规则、完整状态机与实现细节仍归需求或设计。
改名先判断是措辞、别名还是实质模型变化，列出本次受影响引用；不全仓替换、不重写旧交付基线。历史引用、示例、代码兼容名及不同业务范围的同词不自动判错。
工具可检查路径、标识和别名候选，语义复核负责判断身份与职责。核心验收依赖的概念冲突未解时阻塞相关工作；不影响正确含义的措辞建议只提醒，不扩大成全局命名治理。
复用有效条目和确认，只处理本次变化。没有新概念时不启动完整访谈、建模、ADR 或后台代理。
