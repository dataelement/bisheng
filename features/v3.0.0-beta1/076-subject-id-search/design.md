# Design: 现有检索入口增加 ID 搜索

关联：[spec.md](./spec.md)。版本：v3.0.0-beta1。更新：2026-10-15（第三版，收敛版）。
状态：功能已实现并完成本地后端回归；真实 API/页面和 MySQL、DM8 性能尚待验收，详见 [verification.md](./verification.md)。

## 1. 本次只做什么

在已经确认的授权、用户管理与选人入口中增加 ID 搜索。同一搜索框可输入名称或 ID；用户、部门查各自的 `external_id`，用户组查现有数字 ID 的文本前缀。候选与已选信息显示相应 ID，提交仍使用原内部稳定 ID。

前后端一起更新，直接扩展现有搜索接口。删除前版的查询模式、版本探测、响应合同标记、混合版本降级、能力开关与新增候选复检接口。授权写入、事务、审计和原错误处理继续走现有流程。

依据用户本轮“不要过度设计、核心满足 ID 搜索、不影响已有性能优化”，收敛前版额外承诺：不将所有名称检索改为包含；不为搜索新增逐项授权失效定位；不搭建独立目录子系统。

## 2. 搜索规则

- 名称保留每个入口原规则：原来前缀的仍是前缀，原来包含的仍是包含；原触发方式与空关键词默认行为保持。
- ID 支持完整值与前缀，区分大小写、按文本匹配：`jia`、`jia0100` 能找到 `jia0100`；`0100` 不能通过 ID 命中它。名称独立按原规则判断。
- ID 不做整数化、大小写转换或去前导零；用户组 ID 的显示值则为原数字主键的规范十进制文本。
- 业务 ID 为空的对象仍可按名称找到，不用内部 ID 或部门 `dept_id` 补成业务 ID。
- 特殊字符按字面值匹配，不把 `%`、`_` 当通配符；数据库参数化查询。
- 名称和 ID 均遵守入口原有租户、部门、隐藏/禁用状态与可授权/可管理范围，不把资源授权范围换成组织管理范围。
- 平铺结果中完整 ID 相等优先，其余保持原排序；同一对象命中两路只出现一次，身份以“类型＋原稳定 ID”去重。数据库先合并去重和排序，再分页，不能每路各取第一页再合并。
- 树保留层级与同级顺序；命中路径自动展开。截断种子前优先保留完整 ID 命中，不能让完整命中被较早的普通前缀结果挤掉。祖先节点只做路径上下文。

## 3. 保住已有性能优化

### 3.1 已有优化不回退

源码锚点：`permission/domain/services/grant_subject_service.py` 的 F038 前缀匹配注释，以及 `department/domain/services/department_service.py:aget_global_members_search` 的三项性能优化注释。

必须保留：

1. 授权用户和 global-members 的名称 `keyword%`，不改回 `%keyword%`。
2. 租户、部门子树、主属部门条件下推数据库；不拉全量组织到前端筛选，不新增长 user_id IN 列表。
3. 主属部门查询不恢复已经去掉的 GROUP BY。
4. global-members 保留窗口计数、现有分页上限和部门信息批量补齐；空页沿用必要的计数兜底，不强求整个请求只有一条 SQL。
5. 原防抖、请求取消、树懒加载与有界命中上限保持；不把原回车/按钮入口统一改成每次输入查询。

### 3.2 新增 ID 条件不能拖慢名称分支

- 名称和 ID 候选使用各自可索引的匹配分支，再在数据库按稳定 ID 合并。不得直接将未索引或对列做函数转换的 ID 条件 OR 到原名称前缀查询上，然后假设原索引优化仍有效。
- 用户/部门先用原文本列的前缀范围缩小候选，再做必要的大小写精确残余判断；不得仅用 `CAST(external_id AS BINARY)` 作为唯一筛选表达式而使普通索引失去范围访问机会。双库差异封装为小型纯表达式，不改列值或全局数据库设置。
- 用户组数字 ID 以前缀对应的有限数值区间匹配主键，完整值为主键相等；不把整列转文本后做前导通配扫描。输入 `01` 不会等同数字 ID `1` 的显示文本。
- 当前模型用户/部门只有 `(source, external_id)` 联合唯一约束。跨来源查询不能假设它等价于以 external_id 开头的索引，必须检查目标库实际索引和执行计划。
- 若现有索引不能有效支持 ID 前缀，仅为受影响表补 external_id 为前导列的非唯一查询索引；保留原唯一性与来源合同。不加业务字段、不回填、不加全文索引、不建搜索服务。索引变更同步模型与 Alembic，遵守迁移目录 AGENTS，支持 MySQL/DM8，并记录索引创建/删除的部署和回滚步骤。
- 不以 UNION 的写法本身证明性能：两路匹配、去重、排序、计数、补路径与鉴权耗时均纳入实际验证。短前缀、宽范围、空结果、越界页必须测。

### 3.3 性能验收

保留已定义的 ≥15 万用户、≥3 万部门、最宽可见范围、服务端 P95 ≤500 ms 的目标，MySQL/DM8 均验证；同环境、同负载对照改动前名称检索基线。记录并发数、请求分布、样本量、冷热缓存与执行计划，不能用开发小库或仅候选 SQL 的耗时替代。

不达标则修正查询/必要索引后重测，作为正常发布检查，不建设逐入口运行时能力门禁，也不靠浏览器 abort 假定远端数据库扫描已停止。未执行的目标库性能验证明确记为待验收，不宣称无回退。

## 4. 最小接入范围与职责

遵循 [constitution](../../../docs/constitution.md) C1–C8 与 [release-contract](../release-contract.md)。复用现有 Endpoint → Service → Repository 链路；只把本次实际改动的查询下沉，不开展整套旧权限/组织代码重构。新 endpoint 逻辑不得直接调用 Repository。

权限模块不新增业务 ORM 查询：沿用已有 application 主体目录端口与 `TenantPermissionSubjectDirectory`，把本次候选查询放在数据所属业务 Repository。公共层只放规范化、LIKE 字面转义、前缀及精确文本表达式，不认识业务模型。不再预建一个独立 user_group 子系统或一套新通用目录协议。

| 已有入口 | 数据源/改动锚点 | 需要补齐 |
|---|---|---|
| client/platform 新增授权与创建时授权 | `permission/api/endpoints/grant_subjects.py`；`prospective_grant.py`；`tenant/domain/services/f048_permission_subject.py` | 用户/部门 ID 前缀；用户组数字 ID；原鉴权和子树不变 |
| 系统用户、用户组成员、组织添加成员/管理员 | `/user/list`、`department/search/global-members`；`Users.tsx`、`DepartmentUsersSelect.tsx` | 搜索、候选和已选业务 ID；simple 响应补 external_id |
| 租户管理员、挂载、租户用户列表 | `CreateTenantDialog`、`MountTenantDialog`、`TenantUserDialog`；`/tenants/{id}/users` | 保留挂载 root 与主属部门归属，增加 ID 前缀 |
| 审批人和异常处理 | `ApprovalPage/index.tsx` 两处 simple 选人 | 接共享选人逻辑，保存仍用 user_id |
| 标注任务成员 | `LabelPage/index.tsx` → `Users.tsx` → `DepartmentUsersSelect.tsx` | 共享组件覆盖，不新增已分配成员筛选入口 |
| 应用日志用户筛选 | `FilterByUser.tsx` → `/user/list` | 候选增加 ID，日志仍传 user_id |
| 服务账号所有者 | `CreateServiceAccountDialog.tsx` → `DepartmentUsersSelect.tsx` | 保留单选及 resource_owner_user_id |

部门节点序列化补 `external_id`，用户 simple 响应补 `external_id`，均为已有结构增加可空字段，不另包一层新合同。中间选择适配保留 externalId，仅用于显示，不参与身份提交。

用户组选择器当前只取 200 条后本地过滤；本次改为既有服务端搜索和分页，保证后续页的组也能按 ID 找到。修正受影响列表的 total 与当前页长度混用；树沿用 limit/truncated。窗口总数空页无行可读时保留必要 COUNT 兜底，不返回伪 total=0。

## 5. 前端改动与提交

- 同一搜索框，按类型提示“搜索用户/部门/用户组名称或 ID”，不新增名称/ID 模式切换。
- 沿用原触发与防抖；输入法组词完成后发起搜索。新查询使旧响应失效，晚到成功、失败和 finally 均不覆盖最新状态。
- 输入保留原文，查询去首尾空白、换行替换空格；上限 255 Unicode code point，超限保留输入并提示，不吞键盘或截断粘贴。两端空白集合一致。
- 结果与已选区显示名称及字段名＋ID，保留原辅助信息和范围内路径；支持选中复制，选择文字不触发行勾选。空 ID 不显示伪值。
- 搜索和翻页保留已选；加载暂停选择旧候选；失败保留输入与已选，提供同条件重试。关闭/切类型后按原约定恢复搜索默认态。
- 授权提交、成员分配、审批人保存和日志筛选继续使用原稳定 ID、原接口与错误处理，不新增 check、逐项失效定位或部分成功机制。
- 两端各用自己的 API 包装与状态，复用已落地组件和现有辅助信息样式；三语文案齐全，不改设计规范。历史中文随触及文件提取 i18n；超长审批页面只抽相关选人逻辑，不整体重写。

## 6. 验证、升级与数据

按用户“开发完统一测试”指示，完成实现后统一验证：完整/前缀 ID、大小写、前导零、同名和跨来源相同 ID、特殊字符、空 ID、范围隔离、精确优先、合并去重后分页、空页 total、树截断及路径。回归原名称前缀/包含和默认列表，确认没有扩大范围或改变写入。

使用两个 SPA 对上述入口逐项手动核对；后端执行相关单元/契约及可运行的 API E2E，真实 MySQL/DM8 执行与性能留完整证据。前端按用户约定不默认在本地跑测试、lint、typecheck、构建，未运行不宣称通过。

前后端同版发布；无业务数据迁移、无权限模型或权限缓存迁移。若需要最小查询索引，则作为唯一可能的结构增量单列说明；不要再承诺无条件“无结构变化”。回滚按原发布流程协调前后端；已有授权数据继续保留。普通日志不记录搜索词和人员 ID。

## 7. 已知坑与接手提示

- external_id 并非内部主键，且按来源唯一；不能只凭业务 ID 合并不同用户。
- 本地部门 dept_id 与 external_id 常相同，同步部门可能不同；检索字段固定 external_id。
- 主属部门筛选要在用户树种子截断前完成，不能 LIMIT 后丢掉无法放入树的用户。
- 候选范围与写入范围是既有不同合同，本次不增加搜索之外的授权策略。
- 单纯保留名称前缀还不足以证明没有性能回退，新增分支、排序和计数也必须验收。

修订：2026-10-15 第三版依据用户指示移除混合版本及候选复检设计；同轮确认 ID 完整＋前缀、保留原名称匹配与性能优化。中段 ID 包含不在本期范围。

## 8. 实际落点与验证边界（2026-10-15）

- 纯规则位于 `common/subject_search.py`，方言表达式单独放 `core/database/subject_search.py`，避免扩大原方言工具职责。MySQL/DM 编译已覆盖；本地真实 SQL 使用 SQLite，不等同于双库验收。
- 授权查询位于 `tenant/domain/repositories/grant_subject_search_repository.py`，沿现有主体目录服务接入；API 和 worker 的既有 F048 装配均注册目录实例。管理查询各归 user、department、tenant 的 `management_search_repository.py`，没有增加通用目录服务。
- 新增 `ix_user_external_id_search`、`ix_department_external_id_search` 非唯一索引，Alembic revision `f076_subject_id_search_indexes` 接在实际原 head `cofco_923_information_cursor` 后；无数据回填。
- 用户组成员的已有选中信息、部门完整树响应补可空 external_id，避免重新打开选择器丢失 ID 展示。Platform 跨类型已选以类型加稳定 ID 区分；部门树路径和包含子部门设置随原选择保存。
- 最终审查发现的租户候选分页遗漏、切类型丢已选均已修正。审批原超长页面只抽取选人组件，本次不整体重构。
- 本地不执行前端测试/构建；发布前还需镜像或 CI 的前端质量门禁、页面清单以及双库性能证据，不能据当前结果宣称原名称性能无回退。
