F114 · Developer Token 配置知识上传人 · 技术设计

文档版本 0.2 · 2026-11-06 · 状态：设计已确认 · 需求基线：requirements.html v0.2

做什么

在 developer_token 增加知识上传人；Filelib 写路径拆分「权限用户」与「落库上传人」，对齐 PRD 决策表。

为什么

源码里 KnowledgeFile 上传字段取自 login_user；当前若干写依赖 get_default_operator_async，与「绑定用户鉴权」不一致，需一并修正。

影响谁

Platform Token 配置页；/api/v1/admin/developer-tokens；/api/v2/filelib/* 写接口；Alembic 双库迁移。

关键选择

认证成功后从 Token 行加载 knowledge_uploader_user_id 注入 DeveloperTokenPrincipal；写路径用显式依赖解析「权限用户 + 记录用户」，禁止仅改 KnowledgeService 全局假设。

失败后怎么办

缺上传人配置或解析失败：写请求拒绝、无文件行；Admin 保存拒绝并提示必选。

待决

设计评审确认后实施；file/sync 与责任人回填规则见 §5.2。

1. 方案摘要

在 developer_token 表新增「知识上传人」外键列（存 user_id），管理端与 Admin API 强制校验选人。Token 认证成功时把该 ID 带入 DeveloperTokenPrincipal。Filelib 所有会写入 KnowledgeFile 的入口，在请求上下文中同时解析：

  • permission_user：沿用现有规则——无 external_id 时为 Token 绑定用户；有 external_id 时为全局解析出的目标用户（F069）。用于配额、PermissionService、空间路由、prepare_upload 等。
  • record_user：无 external_id 时为 Token 配置的知识上传人（须预解析为完整 UserPayload）；有 external_id 时 等于 permission_user（PRD 决策表）。用于 KnowledgeFile.user_id、user_name、original_uploader_id、updater_* 及依赖上传人的组织解析（与现网 upload_original_file 写入一致）。
现状缺口（源码事实） get_filelib_space_command_service 使用 Depends(get_default_operator_async)，与 Token 绑定用户无关；upload_original_file 将 user_id/original_uploader_id 设为 login_user。实施时必须把写路径接到 Token 鉴权链，否则无法满足 AC-01/AC-03。

3. 现状与目标架构

3.1 模块职责

  • developer_token：模型 + migration + Admin CRUD + authenticate_principal 装载新字段；校验上传人属于 Token 租户且账号可用。
  • open_endpoints/api/dependencies.py：新增 get_filelib_write_context（名称可最终实现定稿），替换 get_filelib_space_command_service 对写接口的 get_default_operator_async 依赖。
  • FilelibSpaceCommandService：构造函数或 upload 方法接受 record_user；内部调用 KnowledgeService 时传入「权限用 login_user」与「行字段用 record_user」。
  • knowledge/domain/services/knowledge_service.py：为 aprocess_knowledge_file / sync_process_knowledge_file / upload_original_file 增加可选 record_user: UserPayload | None；None 时保持现网「全部用 login_user」。
  • FilelibSyncService：见 §5.2。
  • Platform：DeveloperToken.tsx + controllers/API/developerToken.ts 类型与表单。

4. 核心流程

4.1 Admin 保存 Token

  1. 请求体包含 knowledge_uploader_user_id（与 user_id 绑定用户区分）。
  2. Service 校验：与绑定用户同租户；用户未删除、租户关系 active（对齐绑定用户校验强度）。
  3. 持久化至 developer_token 新列。

4.2 Filelib 上传（multipart / chunks / 同步）

  1. Depends(get_developer_token_principal) 或等价：无 Header → 保持现有「无 Token」行为（若仍存在）；有 Header → 认证。
  2. 解析 permission_user：external_id 逻辑沿用 FilelibUserContextService.use_user；否则为 principal.user。
  3. 解析 record_user：若有 external_id 成功解析 → record_user = permission_user；否则从 principal.knowledge_uploader_user_id 异步 UserPayload.init_login_user（或现有异步工厂）；若为空或用户无效 → 返回业务错误（198xx 模块内新增码，设计评审对齐 common/errcode/）。
  4. FilelibSpaceCommandService.upload(...)：self.user = permission_user；将 record_user 下传到 KnowledgeService。
  5. upload_original_file：配额/路由用 login_user（权限）；写 KnowledgeFile.user_id、original_uploader_id 等用 record_user；KnowledgeFileOrganizationService.uploader_organization 对上传人组织：入参改为 record_user.user_id（与 PRD「上传人展示/归属」一致）。

4.3 读列表/检索（不在范围）

保持 get_filelib_request_user；不写库，不改。

5. 关键决策

5.1 列名与迁移

建议列名：knowledge_uploader_user_id，类型 INT NOT NULL（应用层新建必写）＋ Alembic 对存量行：允许短期 NULL，由「保存时必填」与「写接口拒绝」兜底（PRD REQ-002 建议）。列注释（中文）：「知识上传人用户 ID（Filelib 未传 external_id 时写入知识文件的上传人）」。

DM8：与 MySQL 同步迁移；遵守 dual-DB 类型规范。

5.2 Filelib 同步（POST /filelib/file/sync）

已决定（设计推荐，随实现前可作最终确认）
  • 当请求解析出 责任人/负责人（responsible_person* 语义，见 F066）时：保持现网 FilelibSyncService 对 user_id、original_uploader_id 的覆盖逻辑，不因 F114 覆盖责任人。
  • 当同步路径会退回到「责任人 = Token 绑定用户」（代码注释已有「页面上传人因此不是调用方令牌用户」场景）：改为 使用 Token 配置的 knowledge_uploader_user_id 作为记录上传人（若该场景同时需要组织归属，同步用 record_user.user_id 计算 belonging_organization_id）。
  • 若同步请求同时存在「可解析责任人」与「配置上传人」，以责任人为准（业务可归责对象优先于默认上传人）。

5.3 Principal 扩展

DeveloperTokenPrincipal 增加 knowledge_uploader_user_id: int | None，在 authenticate_principal 从 token ORM 行读取。Pydantic 模型与依赖注入保持不可变；不得在 endpoint 侧手改 principal.user 冒充上传人。

5.4 无 Developer Token 的调用

若当前环境仍存在未带 X-Developer-Token 的 /api/v2/filelib 写调用：不改语义，仍用 default_operator 作为唯一用户（权限与记录合一）。F114 仅在有 Token 认证时拆分。
