# 昆联多租户与新用户自动开通设计

- **Feature ID**：`F130`
- **Version**：`v3.0.0`
- **Updated**：2026-11-12
- **Status**：`IMPLEMENTING`，规格、修订设计及任务规划已确认；T001–T012 已本地验证并经后续授权部署，T013–T032 已部署到 104，真实同步与试点 SSO 通过；后续控制面、完整浏览器与联合验收待执行。
- **关联**：[规格](./spec.md) · [需求发现](./discovery.md) · [任务](./tasks.md) · [验证记录](./verification.md) · [整体规划](../../../docs/architecture/proposals/昆联多租户接入与Workflow资产调用改造规划.md)

## 1. 目标与非目标

为可信完整目录中的有效租户自动建立独立毕昇租户，为有效成员自动配置工作流管理入口与新建能力。复用现有身份投影、菜单和资源授权，让新用户在开通完成后通过 SSO 进入自己的工作流空间。

本批不开放跨租户 Workflow，不自动任命管理员，不迁移或合并历史账号，不开发模型平台、组织树或实时推送。先交付隔离 Mock，真实多租户客户端范围另行验收；部署单独授权，已发生的首批部署见当前实现快照。

## 2. 关键约束

- 遵循 [架构约束](../../../docs/constitution.md) C1—C8、[版本契约](../release-contract.md)及 F118 已确认的 [用户投影栅栏](../118-kunlian-sso-user-sync/design-owner-projection-fencing.md)。本设计不修改这些架构规则。
- 昆联已交付客户端仍限定 Workflow 试点租户。全租户只读目录不赋予其他租户登录权；目录自动开通和 OIDC 允许范围是两项独立条件。
- 当前只有用户分页及详情，租户事实随成员返回，不保证包含空租户，也不是一致性快照。仅完整发布后的当前目录可驱动新增开通；不按一轮缺失删除本地对象。
- 本地目前采用 Root／Child 两层租户。新建独立 Child 需有本地部门挂载锚点；该锚点只服务毕昇租户拓扑，不代表昆联已提供组织树。
- 新增三张独立领域状态表，不给已有 User、Tenant、Role、UserRole 增列，不回填历史账号。模型及发现登记已实现；本地先以临时 SQLite 验证，后续授权部署时已按既有补表流程在 MySQL 创建三张空表，详见部署记录。
- 昆联网关和毕昇后端分别核验身份；后端每次受保护访问仍在线内省，不新增允许缓存或外部角色到管理员的转换。

## 3. 方案对比与选定

### D-01：目录完成后异步开通，不在浏览器登录里建租户

- **备选**：登录回调即时创建；或完整目录发布后由已有 Worker 恢复任务开通。
- **选定**：后者。浏览器只检查结果，未就绪时登记补同步／恢复需求并拒绝本次登录，由用户稍后重新登录。
- **原因**：F118 已确认首次缺目录不接续原登录事务；创建租户和权限投影可能部分完成，不能放在一次性授权回调中重做。
- **何时重新考虑**：上游提供可靠的成员事件或增量时，增加触发来源；仍复用同一开通状态，不另建登录内写入路径。

### D-02：以原领域的持久回执保证幂等

- **备选**：按名称查询后调用普通创建接口；全部领域共用一个集成事务；或由领域分别保存操作与回执。
- **选定**：集成层编排，租户、角色、用户分别保存自己的操作结果。租户与本地挂载锚点的结构初始化在租户 Owner 的专用事务中完成，部门写入交给部门 Owner 的事务适配；不把 F118、用户投影和权限服务合成一个大事务。
- **原因**：普通 `TenantService.acreate_tenant` 要求管理员且有独立提交；`TenantMountService.mount_child` 也先提交结构再执行后续动作。直接重试不能保证源绑定与创建结果一致；按名称认领又会误合并历史对象。
- **何时重新考虑**：原租户 Owner 提供等价的带稳定来源及回执的原生创建能力时，替换专用适配，不改变来源身份和重试语义。

### D-03：独立最小角色与工作流专属创建能力

- **备选**：自动授予通用 `create_app`；建立昆联来源专用的旁路资格判断；或在现有角色菜单体系新增 `create_workflow`。
- **选定**：第三种。自动基础角色固定包含 `admin`、`build`、`create_workflow`，不含 `create_app`；自动来源与人工决定仍分开保存，没有业务资源 Grant 或管理员关系。
- **原因**：现有 `create_app` 同时控制 Workflow 和助手创建，不能满足只开放 Workflow 的范围。新增一个现有菜单体系的子能力可复用角色授权、菜单生效、撤销和前端展示，无需按昆联来源绕过原角色体系。`admin` 仅为父菜单，禁止授予 `AdminRole=1`。
- **兼容**：Workflow 创建接受当前有效 `create_workflow` 或既有 `create_app`；助手、托管应用、通用模板继续原规则。不给新能力自动添加通用权限，也不撤销用户已有的人工通用权限。
- **何时重新考虑**：以后统一重构应用类型创建能力时可归并菜单命名，但必须保留本批只授予 Workflow 的语义及原通用权限兼容。

### D-04：精确校验租户与 Workspace 组合

- **备选**：删掉固定租户检查；分别维护两个全局允许列表；或按租户保存允许的 Workspace 集合。
- **选定**：新增组合准入模式，旧固定租户模式作为默认兼容路径。网关和后端使用同一组契约样例校验。
- **原因**：两个各自合法的值可能属于不同租户。仅切换后端登录判断还不够，OIDC 客户端初始化、令牌校验、内省和已有会话准入都有固定范围检查。
- **何时重新考虑**：昆联交付权威的动态租户／Workspace 范围契约后，可替换组合来源；未知或未登记组合继续拒绝。

### D-05：复用恢复调度与前端，控制面只做必要增量

- **备选**：新建独立调度系统和管理页面；或扩展 F118 Beat／恢复任务及现有状态入口。
- **选定**：复用后者，补分页开通诊断与显式阻断／恢复接口，不开发新配置 UI。
- **原因**：已有持久同步需求、Beat 漏投恢复和工作流管理页可复用；新增独立调度会增加重复扫描及失败路径。
- **何时重新考虑**：开通量使已有默认队列无法满足约定时效，或对方交付事件能力时，再按实际容量拆队列或触发器。

### 4.2 新增配置与范围判断

后端在 `sso_sync.kunlian` 下增加：

```yaml
auto_onboarding_enabled: false
login_scope_mode: fixed
tenant_workspace_allowlist: {}
```

- `auto_onboarding_enabled` 默认关闭；只控制新的自动租户／基础资格协调，不决定客户端能登录哪些租户。启用还要求既有目录、连接及策略有效。
- `login_scope_mode=fixed` 保留 `allowed_tenant_id` 加 `allowed_workspace_ids` 的原语义。
- `login_scope_mode=tenant_workspace_map` 只使用 `tenant_workspace_allowlist`，结构为 `{external_tenant_id: [workspace_id, ...]}`。不与旧全局列表求并集，不接受通配符、空集合、空标识或隐式默认 Workspace。
- 网关 `custom.kunlian` 同步增加 `login-scope-mode`、`tenant-workspace-allowlist`；不需要目录 Key，也不负责自动开通。
- 两端分别把固定模式规范化为单条组合，用同一种组合判断替换原比较。身份签名、接收方、时间、nonce、PKCE、内省逐字段匹配继续执行。
- 现有 HMAC 登录交接字段不变，不新增浏览器身份参数。两端配置不一致时只可能按各自范围交集放行；不能通过降级模式补救。启用前必须用共享样例检查组合一致，并按既有 `policy_revision` 递增应用后端策略。

**分批保护**：T001–T012 曾对新模式保留 `SCOPE_RUNTIME_NOT_READY`。本地 T028／T030 已完成后端客户端初始化、令牌／会话及网关令牌接入，现已同步移除源码阶段门禁，按模式校验必填字段；fixed 仍为默认模式。此变更已随 2026-11-12 后续授权部署；实际仍 fixed，不表示真实客户端已获得多租户范围。

### 4.3 自动租户开通

主流程：`完整目录发布 → 扫描有效且未开通租户 → 租户 Owner 保留操作 → 创建结构／恢复原结构 → 核对回执 → 建映射 → 从当前批次补建成员绑定 → 原用户投影`。

1. 在 Root 控制面读取连接、当前已发布批次和租户事实。状态必须为已确认有效，批次新鲜度、策略及本地阻断同时通过；不对拉取中的分页执行创建。
2. 已存在人工映射时保留原本地租户，不为其另建租户。Owner 可按经过核验的原映射建立 `mapping_origin=manual` 的来源状态，后续只协调资格、不重建结构。被禁用或已物化后冻结的映射不能被自动重绑、启用或迁移。
3. 为未映射来源生成稳定 `source_key = SHA256(["kunlian", issuer, external_tenant_id])`，租户 Owner 保留操作及本地单调栅栏。记录固定连接归属；同一来源被不同连接认领时拒绝，连接名称变化不自动迁移。
4. Owner 在自己的事务内核对当前操作，创建唯一 Child、本地挂载锚点和双方引用，并同时写回 `local_tenant_id`／`anchor_department_id`。外部租户名只作显示；本地租户码由来源摘要生成，碰撞时拒绝，不认领同名或同码历史对象。
5. 部门锚点经部门 Owner 的事务适配创建于现有 Root 组织下，标记挂载到新 Child，不导入组织树、不移动旧部门。专用入口不要求虚构管理员账号，`create_user` 可空，另记可信自动操作来源。
6. 必要结构权限通过原权限 application 的持久投影及查回完成。保持 `auto_distribute=False` 的效果，不建立 Root 默认共享关系、不复制 Root 业务授权；工作台工具、模型、Skill 等资源分发不进入就绪条件或被顺手开启。
7. 租户 Owner 回执确认后，F118 仓储在短事务内复核当前批次、策略、操作、源租户与本地目标，建立原 `KunlianTenantBinding`。绑定和成员生成仍由 F118 拥有。
8. 提取现有发布时的成员协调逻辑，增加“从当前已发布批次为这个租户协调绑定”的入口，避免刚开通后必须等下一轮全量。旧回执若对应过期批次不得写身份；按新批次重试并复用原租户。

不删除部分成功的本地租户作为补偿。Owner 已提交、F118 尚未完成时，下一次扫描凭源记录查回同一结果；未映射或成员未就绪期间不能登录。

### 4.4 基础角色与用户资格

主流程：`映射已确认 → 原用户投影及成员关系 → 角色 Owner 确保最小模板 → 用户 Owner 确保自动成员资格 → 复核原投影与当前资格 → 允许后续登录`。

- 每个连接／本地租户创建一个 `role_type=tenant` 的基础角色，固定 `admin`、`build`、`create_workflow` 三键。稳定角色归属记录保存真实角色 ID，不按角色名认领，不使用 ID 1／默认角色，不建立 Workflow 资源 Grant。
- 用户 Owner 仅为来源明确、有效、属于已冻结映射的昆联用户添加这一条自动 `UserRole`，显式置于目标租户上下文。现有其他角色、个人菜单、管理员配置保持原值。
- 自动成员资格的来源由新用户领域记录确认，不能依赖 `UserRole` 行本身推断。人工把同一个预留角色授给其他身份时拒绝并提示使用普通人工角色。
- 用户已完成 F118 投影仍可能缺基础资格。因此恢复任务独立扫描“需要基础资格”的身份，不能被 `project_identity` 的提前返回或只扫描未成功投影的候选条件漏掉。
- 新成员自动资格提交前需核对原用户操作回执、当前身份映射及本地撤销栅栏；F118 就绪检查同时检查原物化状态和资格处理结果。资格失败不能伪装成原资料投影失败，也不能冒充开通完成。
- 模板的菜单／角色范围是受控集合。普通入口不得给该预留角色增加更宽菜单、管理员范围或业务资源 Grant；更高权限通过独立人工角色授予，沿用原权限校验。
- **已有试点**：保留人工映射、账号及原角色，不把试点角色认领为自动模板。启用后可追加独立自动基础角色；不删除或替换原角色。

#### 工作流专属创建的落点

1. 在 `WebMenuResource` 增加 `CREATE_WORKFLOW="create_workflow"`，同步后端有效菜单集合及 Platform 角色菜单清单，挂在 `build` 下。角色编辑页关闭 `build` 会清除两个子项；后端对新键额外要求 `build` 有效，原 `create_app` 的有效菜单兼容语义保持不变。普通新角色的默认菜单不新增任何创建能力。
2. 增加 `LoginUser.get_workflow_creator_user`：先核验当前登录与租户，再读取当前有效菜单，接受 `create_workflow` 或旧 `create_app`。仅全局管理员沿用原快捷路径，不能因租户管理员、目录角色或请求 `scope` 自动放行。返回的是原可信用户主体，不增加自签发凭据或新的 F048 资源动作。
3. `/api/v1/workflow/create` 改用专属依赖，保留原配额、幂等和 Owner 创建链。缺省或空 `flow_type` 规范为 Workflow，显式其他类型拒绝；实际落库始终由服务端固定 `FlowType.WORKFLOW=10`。校验在幂等结果查回之前执行，不因旧回执存在而绕过当前资格。
4. `scope=workflow_management` 只选择原管理创建逻辑，不授予权限；两种 scope、直接接口、复制产生的创建请求都走相同专属校验。复制仍先按现有管理页规则核验源 Workflow 的编辑权及租户，不新增只读用户复制能力。
5. 助手创建继续使用原 `get_app_creator_user`；托管应用及通用模板的能力检查保持原样。不得让公共 `get_app_creator_user` 接受 `create_workflow`，也不能把两个键在菜单合并时互相转换。
6. `apps.tsx` 拆分 `canCreateApp` 与 `canCreateWorkflow`。专用管理页的新建、Workflow 复制使用后者，通用新建卡片、助手复制、托管应用与模板管理使用原能力。兼容 `kunlian_workflow=new` 时只能打开 Workflow 表单，不能开放通用类型选择器。
7. 角色配置、有效菜单返回、路由白名单及三语文案均纳入改动，防止保存角色时新键被丢弃。原 F056 清单测试需显式登记本批新增的 Workflow 子能力，同时保留“托管应用不新增专属权限点”和普通新角色不默认拥有创建权的断言，不删除原安全测试。

仅自动来源受限，不收窄用户既有独立人工 `create_app`；同时有两种能力的用户保留其原合法通用创建范围。

### 4.5 三张新增领域表

三表模型、发现和租户过滤登记已实现；`role_external_basic_role` 的 `local_tenant_id` 以标准列名 `tenant_id` 存储。临时 SQLite 建表与过滤／约束已验证，后续授权部署已通过 MySQL 补表及索引冒烟；本地 Owner 写入与事务已有隔离证据；真实 MySQL 并发／事务及 DM8 仍待后续任务。保持双库类型，不修改历史行或已有表列，不重复添加只创建整表的空修订。

| 表与 Owner | 稳定键与核心字段 | 不承担的职责 |
| --- | --- | --- |
| `tenant_external_provision`，tenant | `source_key` 主键；`connection_id`、外部租户、issuer 摘要；`local_tenant_id` 唯一可空；锚点 ID；`operation_id/fence/applied_fence`；当前策略、来源批次；`state`、本地阻断修订、稳定原因及时间。完整来源单独保留并核对，摘要不是合并许可。 | 不保存 User、SSO 会话或资源权限。 |
| `role_external_basic_role`，role | `(connection_id, local_tenant_id)` 唯一；`role_id` 唯一可空；模板修订、菜单摘要、`state`、操作栅栏、回执及时间。保存暂停／删除墓碑，不能凭角色缺失自动重建。 | 不保存用户身份或成员绑定，不作为资源权限判据。 |
| `user_external_basic_access`，user | `(connection_id, identity_key)` 唯一；本地用户与租户、预留角色；源用户回执、角色模板修订；`operation_id/fence/applied_fence`；`state`、本地撤销修订、原因及时间。 | 不替代 F118 身份绑定或旧投影状态，不接管人工角色。 |

Owner 状态分别表示自己的步骤，不将外部 opaque version 当作计数器。栅栏在本地单调生成；操作 ID、预期栅栏、来源摘要全部匹配才可写入实际对象及应用回执，旧操作不能在新操作后产生作用。

```text
租户：PENDING → STRUCTURE_READY → READY
角色／用户基础资格：PENDING → APPLIED
各自失败：FAILED → 基于当前事实重试
本地阻断／撤销：BLOCKED，必须由明确的管理员恢复命令退出
角色被移除或收窄：SUSPENDED，常规同步不自动重建或补回
```

跨 Worker 恢复依赖这些持久记录、原 F118 批次和既有权限投影账本，不依赖本地文件或进程缓存。角色菜单和用户角色关系分别在原 Owner 的事务内写入，不需要新建一套资源授权模型。来源记录不对实际 Role 使用级联删除外键；角色被删除后仍保存原 ID、暂停状态和回执，不能因关联行消失而丢失墓碑。

租户来源表是 `tenant_id=1` 的受限控制面记录；角色模板及用户基础资格使用标准 `tenant_id` 绑定实际本地租户，登记到原租户过滤机制。表中 `local_tenant_id` 是说明目标含义，模型不另建可漂移的第二套租户归属。用户原投影表仍在 Root 控制面。Owner 的事务适配按经验证的映射切换作用域并返回值对象，不让调用方用请求参数覆盖过滤器；创建实际 `Role`／`UserRole` 时必须显式写目标租户，不能沿用 ORM 的 Root 默认值。

### 4.6 管理员撤销、停用和竞争处理

| 事件 | 处理与后续同步 |
| --- | --- |
| 管理员阻断租户自动开通 | tenant Owner 记录 `BLOCKED` 并提高操作栅栏；登录与已有会话读取该阻断，F118 提高对应身份 epoch／失效旧会话。禁止新增或继续该来源的自动开通。保留租户与资产。 |
| 管理员移除用户的自动角色 | 在用户 Owner 的同一事务中先写 `BLOCKED` 并提高栅栏，再移除来源对应的 `UserRole`；其他人工角色不改。重试不得补回。 |
| 管理员删除／收窄基础角色 | role Owner 在同一事务记录 `SUSPENDED`，执行有权的删除／收窄；自动任务不重建、不扩回菜单。显式停用模板时，同事务清除这个角色的三个菜单授权，不只改来源状态。普通入口增加预留角色权限的变更直接拒绝。 |
| 外部成员／租户停用 | 继续走 F118 的状态、epoch、会话失效与用户资料投影。保留人工授权；自动来源资格记录可保留，但停用期间不能凭它访问。恢复必须同时满足本地未阻断。 |
| 普通同步发现已成功资格的角色关系消失 | 视为需保留的人工撤销，写阻断／诊断，不把“行缺失”直接当成可以重建。实际并发处理仍由 Owner 锁与修订裁决。 |
| 恢复自动资格 | 使用明确管理员命令及预期修订；只恢复指定来源。角色模板恢复不清除用户级阻断；用户恢复也不自动解除租户或模板阻断。 |

新增租户来源阻断不改写原 `KunlianTenantBinding.enabled`。原映射一旦物化，既有管理接口不能简单再次启用；因此本批阻断／恢复在新的来源政策记录中完成，并作为 F130 启用来源的额外准入条件。管理员显式恢复来源后，原 F118 映射仍必须独立有效；不能把此命令用作绕过历史映射禁用或改绑的途径。准入阻断以 Owner 提交的当前状态立即判断，跨 Owner 的 epoch 补偿未完成也不得恢复访问。

自动与手工修改都必须经过同一 Owner 锁。涉及模板的操作统一先取得 role Owner 提供的模板事务锁，再由用户 Owner 依次锁原用户投影记录、基础资格记录、实际用户角色行；模板修订在同一写入事务内验证。模板读取及加锁经 role application 的事务适配提供，不由用户仓储直接查询角色来源表。角色修改／删除也取得该模板锁，与添加成员形成明确的先后顺序；不在持锁范围执行网络请求，不在不同 Owner 的独立事务之间互相等待或反向回调。原用户资料投影仍使用 F118 已确认的独立 UoW，不因此合并进菜单事务。

用户资格自动应用只接受当前用户 Owner 的已应用投影回执；被后续用户操作栅栏淘汰的回执不能再预留或完成旧资格操作。模板暂停、成员撤销与提交任一方先提交后，后一方必须按新修订拒绝旧计划。登录与已有会话仍在放行前重读模板及资格，而不是将已应用回执当作长期允许。

现有 `user_addrole` 对受管用户角色的增删需移交用户 application 的事务入口，不能仍用“先删除、之后补一条撤销标记”的顺序。只调整被本特性管理的分支；其他人工角色按原合法范围变更，并在同事务保留新旧集合与审计。角色服务与旧兼容修改／删除入口也必须统一调用角色 Owner，禁止遗漏可写路径。

F118 的身份源仍是准入权威。Owner 操作前后均需验证当前策略及来源作用域；失去原事务后不能重开事务继续旧授权计划。Owner 依靠自己的持久栅栏拒绝旧实际写入，而不只在 F118 最终回执上做 CAS。跨 Owner 部分提交后保持未就绪，重试查回；策略阻断先收紧准入，后续 Owner 停止／修复不能扩大窗口。

### 4.7 登录、已有会话与前端

1. 网关以既有授权流程验证身份及组合，后端再次验证 ID Token、内省、组合、完整新鲜目录和冻结映射。
2. 自动开通未完成时，复用 `DIRECTORY_NOT_READY` 与受控需求合并机制，触发恢复；不在页面刷新时逐次创建新工作或重试同一授权码。
3. 自动资格已处理时，读取其当前模板、阻断及有效角色，再走既有菜单准入。用户级仅撤销基础角色时，其他独立人工菜单资格可继续满足入口；租户／身份阻断则不能绕过。
4. 每次已有会话准入都使用组合校验，并在内省网络往返后重读当前用户角色／模板修订及本地阻断，避免拿网络请求前的角色快照放行。原身份停用和 epoch 判断保留。
5. 前端复用 `/build/workflows`、原编辑器、SSO 失败提示和回跳。仅在现有就绪提示缺少区分时增加“开通处理中／请稍后重新登录”说明，不改变首次尝试与手工重试规则。
6. 新建继续使用当前用户、当前租户、现有配额、创建幂等及对象 Owner 投影；不把自动基础角色当作具体资源动作的放行条件。

### 4.8 Worker 与漏投补偿

- 扩展原恢复任务：有界扫描租户开通 → 从当前批次补绑定 → 原用户投影 → 独立扫描基础资格。建议沿用每页 25 条，达到现有任务预算即提交下一页任务。
- 每一阶段有独立扫描起点，不复用同一个 `identity_key` 游标代替租户进度。按稳定键翻页；下次 Beat 从持久未完成条件重新扫描，覆盖已扫描键之前出现的新工作。
- 当前 Beat 每 300 秒触发；上游新增成员通常需下一轮完整发布及排队开通，不能承诺秒级。人工／首次登录补同步只登记合并需求；不得为未知浏览器租户创建任意任务。
- 先持久记录再投递，通知丢失和 Worker 退出由 Beat 重扫；失败回执带预期操作／栅栏，不能覆盖接管后的状态。成功 Owner 回执丢失时查回，不重新创建。

| 方法与路径 | 请求／返回要点 | 权限与并发 |

上述恢复命令保存期望状态后可返回 `PENDING`，该状态不代表角色或用户资格已应用；Worker 查回原操作继续完成。来源政策、模板和成员分别使用各自修订，避免一个跨 Owner 请求部分完成后冒称全部成功。原诊断接口返回当前处理结果，客户端用它查回丢失响应。

分页游标采用项目现有的签名及有界解析惯例，由本集成自己的游标 helper 承接，不跨域调用 Workflow 私有游标服务。载荷绑定连接、`kind`、过滤条件、最后稳定键和到期时间；以 `kunlian:onboarding:v1` 作签名域分离，使用既有受控秘密引用。编码、体积和签名校验均通过后才能访问仓储，不接受游标携带本地租户覆盖值，不新增凭据种类。

### T013–T024 实际协议与验证边界

- 部门 application 暴露参与调用方 SQL 事务的锚点创建；租户 application 暴露预留、确保结构、当前回执及 CAS 政策。来源键仍为 `issuer + external_tenant_id` 的稳定摘要，来源连接绑定、目标唯一性及过期操作均在持久状态核验，不按名称认领。
- 新租户没有管理员、默认共享或默认分发。因此结构阶段没有需要写入的管理员或 `shared_to` 权限关系，不伪造权限主体；租户服务保留事务外的必要投影适配位置，并在随后 READY 提交前重新核对栅栏。成员权限仍走原 membership application；本批仅注入 Mock，正式 OpenFGA 投影待联合验证。
- 角色 application 提供受限 `lock_template`，用户仓储通过它在同一事务获取模板锁及不可变回执，不查询角色来源 ORM。用户仍由原身份投影创建；资格命令必须携带当前已应用原回执，并校验实际用户、来源及唯一活动目标租户。
- 所有资格与用户角色变更采用“模板 → 原用户投影 → 基础资格 → UserRole”锁顺序。持久撤销提高栅栏并保留墓碑；旧回执、缺失实际关联和模板暂停不能触发自动补授。模板恢复也不能解除用户级阻断。
- 角色服务的修改、修改菜单、联合修改和删除，以及兼容角色修改／删除和 `user_addrole`，保留原操作者授权前置；受管分支交由所属 application 同事务处理。普通角色返回原路径，不套用受管用户的管理员角色限制。
- 既有租户过滤器对批量 DELETE 不提供同等注入保障；本批先在严格目标上下文选取并锁定具体行，再逐对象删除，不手写 tenant_id WHERE，也不依赖批量删除自动隔离。来源查询的短暂 bypass 仅限内部精确用户／角色标识，不能作为外部越租户许可。
- 开发证据见 verification.md E-013–E-017；[人工测试参考](./test-cases.md)仍待执行。SQLite 验证事务回滚、交错操作与持久栅栏，不证明 MySQL／DM8 的真实行锁或多进程竞争。

### T025–T032 实际衔接

- `KunlianOnboardingService` 由原 runtime 同时装配到 Worker、登录与业务会话；目录、租户、角色及用户端口仍各自拥有状态。新增的来源状态和当前投影回执读取只返回值对象，不直接跨领域查询 ORM。

## 成员列表缺失的最小修复（REQ-08）

根因是外部成员只写 `UserTenant`，而组织成员页从 `UserDepartment` 查询；成功投影短路和投影候选过滤又让历史用户无法自然补齐。

1. 租户 application 在原租户成员事务成功后，读取当前租户的根部门 ID，调用部门 application。部门新增受控校验仓储，核验账号来源、有效租户关联、根部门挂载和已有主部门；挂载节点属于 Root 管理组织，因此只在该专用入口进入 Root 执行上下文，显式核验目标，不能把业务租户当作挂载节点的存储租户。
2. 复用 `DepartmentMembershipProjectionService.aadd_member` 及其已有持久权限投影、恢复机制；在同一部门写事务内校验目标并锁定租户及用户，防止并发重复和归属变化。无主部门时新建根部门主关联；已有合法主部门保留，跨租户归属冲突拒绝；不授予管理员或新建业务对象授权。部门 SQL 已提交但权限投影未完成时，原恢复入口重读并恢复同一投影。
3. 原资料投影的成功短路先补齐当前有效成员关系；自动开通的基础资格阶段也在原来源锁和当前批次断言内调用成员确保，覆盖已成功、不再进入投影候选的历史用户。停用投影不新增部门关系；补齐不重写原资料修订或基础角色墓碑。
4. 文件落点：部门 `application/external_membership.py`、`domain/repositories/external_membership.py`、原 `department_service.py`；租户 `application/external_membership.py`；SSO 原 `kunlian_projection.py`、`kunlian_onboarding.py`。不新增表、公共接口、运行配置或网关改动。
5. 验证先复现空成员，再验证新增、成功回执补齐、幂等、保留主部门、错误目标及权限失败恢复。104 部署前保存源码和数据基线；使用原恢复任务补齐，不直接批量修改用户表。回退源码不删除已合法建立的成员关系，不迁移账号或改变角色。
