# 一、摘要

## 1.1 中心结论

**BiSheng 开放 API 必须建立三层机制：凡调用必持密钥、密钥必绑主体、身份必显式声明。**

三层各解决一个问题，按优先级展开：

1. **凡调用必持密钥 —— 解决"谁在调用"。** 任何开放 API 调用必须携带平台签发的密钥，无密钥即 401——现存的匿名通道就此关闭。同时移除"配一个固定用户当兜底身份"的现行做法，并补上被遗漏的上线状态校验与 WebSocket 鉴权。**这是 P0 的全部目标，须立即启动，可独立交付。**
2. **密钥必绑主体 —— 解决"能做什么"。** 每把密钥都绑定一个确定的主体，权限边界随主体收敛，不存在无主的密钥。主体有两类，对应两类调用者：**服务账号**承载组织的系统集成——不可登录平台（只能通过密钥调用 API）、权限单独授予、不占租户人头，边界由管理员按最小必要收敛；**自然人**承载员工把个人办公助手接入平台的场景（§3.5）——权限就是他本人的，动态继承、随人事级联失效。而现状是所有调用共用一个配置在数据库里的固定用户，接口文档还建议把它配成超级管理员（§2.2 F2/F3）。**服务账号是本次要新建的一类主体，也是工程量最大的一块（§4.5）；个人访问令牌复用同一套凭据底座，主体层零新增（§4.10）。**
3. **身份必显式声明 —— 解决"以谁的名义"。** 调用方必须显式声明两种身份模式之一：以服务账号身份执行，还是代表某个平台用户执行。二者的权限基准与审计归属截然不同，代表他人执行必须凭据先行、能力单独授予，不能靠一个可选参数的有无来区分（§4.3）。

## 1.2 背景（情境—冲突—疑问—解答）

**情境**　BiSheng 是私有化部署的企业级大模型应用开发平台，客户在其上构建工作流、知识库、智能助手。平台对外提供一组开放 API（路径前缀 `/api/v2`），供客户的自建业务系统调用——例如在自家 OA 里嵌入问答入口，或让 CRM 系统触发一条工作流。

**冲突**　这组开放 API 目前**完全没有鉴权**：任何能访问到服务端口的人都可以直接调用。更关键的是，接口已经支持在请求中指定"以哪个用户的身份执行"，而这个指定同样不需要任何凭据。两者叠加，构成一条可被任意匿名调用方利用的越权通道（§2.2）。

**疑问**　应当建立怎样的鉴权机制？调用方要代表最终用户操作时，"在请求里指定一个用户 ID"这种做法是否可接受？如果调用方服务的是与平台完全无关的外部用户，权限又该如何处理？

**解答**　即 §1.1 的三层机制。三个疑问的具体结论见下表。

## 1.3 三个核心问题的结论

| 问题 | 结论 | 详见 |
|---|---|---|
| **Q1** 开放 API 是否必须鉴权？ | 必须。且不能依赖"部署在内网"作为替代——私有化环境同样存在横向移动与内部越权，等保测评中无鉴权的内部接口是明确失分项 | §2.3 |
| **Q2** 调用方在请求里指定 user_id 代表某用户操作，安全吗？ | **拆成两问，答案相反**：它**永远无法证明**是该用户本人在操作；但它**可以合法地**让调用方按该用户的权限边界执行并归属结果——前提是护栏齐备。行业中 Zendesk [S7]、Kubernetes [S8]、FastGPT [S3] 均采用此模式 | §4.4.3、附录 A.1 |
| **Q3** 调用方服务的是外部用户体系时，是否应关闭权限过滤？ | **不应关闭，应更换过滤基准**。过滤照做，基准从"最终用户"换成"服务账号"。直接关闭过滤会产生无边界数据出口 | §3.3、§4.3.4 |

## 1.4 交付范围与优先级

| 阶段 | 目标 | 核心交付 | 估算 |
|---|---|---|---|
| **P0** | 关闭匿名通道 | 服务账号主体（含**资源归属人**，§4.5 定义 6）+ 服务账号密钥 + 全端点接入鉴权 + 管理界面 | 约 11~12 人天 ⚠️ |
| **P1** | 身份传递 | 两种身份模式 + 外部用户标识头 + 受限委托五道准入 + 审计双归属 + 裸 user_id 参数收口 + **检索补文件级过滤**（§4.4.6） | 约 12~14 人天 ⚠️ |
| **P1** | 日常模式会话开放 | 以**业务语义**开放工作台日常模式对话：选模型 + 可选挂知识库 / 开平台工具 / 传附件 + 服务端多轮 + 流式与非流式 + 会话附件上传（**契约形态归 design**；**会话列表/历史查询、第二套并行契约均本次不做**，§4.6.3） | 约 12~15 人天 ⚠️，**须按新形态重估** |
| **P1** | **个人访问令牌**（§4.10） | 自助签发面 + 自然人主体解析 + 只读权限位白名单 + 必填过期与上限 + 级联失效 + 管理员台账与强制吊销 + 审计归因；**交付形态 = remote MCP server + HTTP 双形态** | 约 11~13 人天 |
| **P2** | 企业级运营 | 限流配额、IP 白名单、幂等性、OpenAPI 规范导出、签名断言换令牌、MCP 复用同一密钥体系；**Coze / 豆包所需的 OAuth 授权服务器**（D18） | 待估 |

> ⚠️ **两项 P1 的估算需复核**：检索的文件级过滤改造（§4.4.6）是代码核实后新增的工作项，原估算未包含它；反向地，**会话列表/历史查询及其硬约束已于 2026-08-16 移出范围**，**Chat Completions 薄兼容层已于 2026-08-17 明确不做**（D12），**2026-08-18 又取消了「对标 OpenAI Responses 子集」这一形态要求**（D9 改判）——后者砍掉的是对象模型保真、事件类型对齐、SDK 反序列化验收、完整拒绝清单等一批纯兼容性工作量，日常模式会话那行应显著下调。两项需一并重算。
>
> **「模式」与「同步/异步」两个维度的增量成本≈0**：本次它们只是两次枚举校验 + 两个错误码，不引入新链路（D11）。
>
> **个人访问令牌那行的 11~13 人天有两个前提**：一是全端点接入鉴权已完成（否则拿到密钥也没有可打的受保护端点），二是统一检索门面已交付（文件级过滤不重复实现）。**它不含 R4 服务账号主体的任何一项成本**——主体是本来就存在的自然人（§4.10.2）。外部锚点校验：身份传递那项估 12~14 人天、范围可比，本行落在 11~13 与之一致。
>
> **日常模式会话开放依赖身份传递**（模式 D 是其主场，理由见 §4.6.3），两项须同期交付，不可只出 P0 版本。
>
> **任务模式（灵思）本次不点亮。** 它与日常模式在内部就是同一入口靠 `task_mode` 分流（附录 E.3），对外是同一能力的另一种运行模式；**「运行模式」与「同步/异步」是两个独立维度，不得合并成一个开关**（裁定见 D11）。不点亮的原因是四条技术前置（Redis 事件流破坏性消费、前端编排搬后端、并发准入、异步作业语义），与契约形态无关。**要求是：届时点亮不得推翻本次已开放的日常模式契约**——依据见 §4.6.3 第六小节。

> **个人访问令牌（PAT）已于 2026-08-27 由「不做」改判为交付**（原决议与推翻理由见 §7.6 D13）。
> 它服务的是 §3.5 场景四——员工自助接入个人办公助手，与前三类的系统集成不是同一件事。
> **它复用 R1 凭据底座的全部**（同一张表、同一条校验路径、同一套哈希与撤销语义），**且不需要 R4 服务账号主体的任何一项成本**；
> 本期只开 `knowledge:read` 一个权限位。范围见 §4.10。

# 二、问题定义

## 2.1 什么是开放 API

BiSheng 对外暴露两组 HTTP 接口：

| | 面向前端的接口 | **开放 API（本文档范围）** |
|---|---|---|
| 路径 | `/api/v1/**` | `/api/v2/**` |
| 调用方 | 平台自己的两个 Web 前端 | **客户的自建业务系统** |
| 鉴权 | 用户登录后的 JWT | **无** |
| 典型用途 | 页面渲染、管理操作 | 触发工作流、检索知识库、调用助手对话、上传文档 |

开放 API 当前覆盖 7 个模块：工作流、知识库、文档库、助手、会话、引用溯源、语音。实现位于 `bisheng/open_endpoints/`（**8 个路由文件、约 1600 行**；含 schema 与依赖的整包约 1900 行）。

> ⚠️ **盘点时容易漏一个文件**：语音路由 `llm.py` 不在 `open_endpoints/api/router.py` 的导出清单里，而是被 `api/router.py` 直接挂载。只照前者盘点会漏掉它的 2 个端点。

## 2.2 现状：三类问题

以下均来自对当前代码库的直接核查，非推测。五个事实归为三类，因为三类的性质与修复手段不同。

### 类型一 · 认证缺失（谁在调用无从知晓）

| # | 事实 | 位置 |
|---|---|---|
| **F1** | 开放 API 全部端点无任何鉴权——无密钥、无签名、无令牌 | `bisheng/open_endpoints/` |
| **F5** | 工作流调用接口**不校验工作流是否已上线**；两个 WebSocket 端点的登录校验被注释掉，注释写着"免登录链接" | `endpoints/workflow.py:41,157-174`；`endpoints/assistant.py:298-318` |

**修复手段**：密钥体系 + 全端点接入（R1、R2）。

### 类型二 · 授权过宽（调用能做什么无从收敛）

| # | 事实 | 位置 |
|---|---|---|
| **F2** | 所有端点统一以一个**配置在数据库里的固定用户**身份执行（配置项 `default_operator`）。该配置项决定了开放 API 的全部权限边界 | `open_endpoints/domain/utils.py:26-74` |
| **F3** | 现有接口文档明确写着"调用方需在网络层负责访问控制"，并**建议把这个固定用户配置成超级管理员**"以避免权限边界问题" | `docs/api/filelib-retrieve.md:25,28` |

**修复手段**：服务账号一等主体 + 权限位收口 + 固定身份降权（R1、R4、R8）。

### 类型三 · 委托无凭据（以谁的名义执行可被任意伪造）

| # | 事实 | 位置 |
|---|---|---|
| **F4** | **"指定用户身份"的能力已经上线**：**7 处**端点接受请求参数中的裸 `user_id`，按该用户的可见范围过滤数据或指定资源归属。其解析函数 `resolve_operator` **只检查用户存在，连账号是否被禁用都不查**。**其中 `POST /filelib/add_qa` 是写路径**——可把问答对的归属指定为任意用户，风险高于三个读端点 | `open_endpoints/domain/utils.py:77-104`；逐处清单见附录 B |

**修复手段**：受限委托五道准入（R3）。注意 `resolve_operator` 的缺陷独立于本特性也应尽快修复。

## 2.3 风险

三类问题叠加的最坏情况：

> **任何能访问服务端口的人，都可以以超级管理员权限、指定任意用户身份、读取平台上的全部知识库内容，并调用任意工作流（含未上线的草稿）。**

三个容易被低估的点：

1. **"部署在内网"不构成缓解**。私有化客户的内网通常有数百至数千台终端；一次钓鱼或一台被控主机即可触达。
2. **这不是"待加固"，而是"已开放"**。代用户能力已随一次迭代（内部编号 F030）上线并被文档化，客户可能已在使用。因此**必须把改造要求提前、显著地交付给客户**——本方案不设兼容开关也不做平台侧迁移（§4.9），存量集成会在升级瞬间全部中断，这一点只能靠发布说明与升级前沟通承接，不能等客户升级后才发现。
3. **工作流枚举是横向扩大打击面的跳板**——草稿工作流常包含尚未审核的提示词、数据库连接或外部 API 密钥。

## 2.4 为什么现在做

- 工作流对外发布为 MCP 服务的需求已提出，该方案已明确将本问题列为阻塞项——MCP 端点若直接透出现有语义，等于把匿名可枚举执行的能力再暴露一层。
- 客户侧已出现真实集成需求（§3），继续拖延会积累更多依赖现状的存量调用方，迁移成本随时间线性上升。

# 三、需求：三类调用场景

三类场景 MECE 划分。划分依据不是抽象的分类学，而是客户接入时真的要做的**两次判断**：

> **判断一：这次调用背后有"最终用户"吗？**
> 　没有——后台任务、系统间同步、数据管道 → **场景一**
>
> **判断二：这些最终用户在 BiSheng 平台上有账号吗？**
> 　有 → **场景二**　　　没有 → **场景三**

留意分叉点：**场景一与场景三的区别是"有没有最终用户"，不是"权限模型不同"**——两者的权限判定完全相同，差异在会话分区与授权尺度（§3.4）。

## 3.1 场景一：系统集成（调用方即一个系统）

**谁**　客户的后台系统、定时任务、数据管道。

**要什么**　"每天凌晨把 ERP 里的新合同同步进知识库"、"订单状态变更时触发一条审批工作流"。

**特点**　没有"最终用户"这个概念，调用方本身就是一个主体。

**当前为什么不行**　能跑通，但跑在一个无鉴权、且被建议配成超管的固定身份上。无法回答"这次同步是哪个系统发起的"，也无法在某个集成出问题时单独停掉它。

## 3.2 场景二：面向平台同一批用户的应用

**谁**　客户在 BiSheng 之外自建的业务系统，其用户就是 BiSheng 平台上的用户。

### 典型客户：中粮

中粮体系内**用户 ID 全域一致**——同一个人在 OA、业务系统与 BiSheng 里是同一个标识。他们的诉求是把 BiSheng 的 AI 能力接进这些非 BiSheng 的系统里，而不是让员工再切换到 BiSheng 平台去用。

具体到一次调用，客户关心两件事：

| 关心什么 | 具体要求 | 对应本方案 |
|---|---|---|
| **能用哪些知识库** | 张三在集团 OA 里问一句，能被检索到的必须**正好是他在 BiSheng 平台上被授权的那些知识库**——不多给（不能让他看到无权访问的文档），也不少给（不能因为走了 API 就退化成某个公共账号的可见范围） | 模式 D，权限基准整体替换为张三（§4.3.3、§7.2） |
| **是谁在操作** | 每次调用要能追溯到具体是哪个员工执行的，而不只是"OA 系统调的" | 审计双归属：actor 记 OA 这个服务账号，subject 记张三（§4.4.5） |

**用户 ID 一致是这个场景成立的前提**，也正是中粮这类客户的有利条件——调用方直接把已有的用户标识放进请求头即可，无需维护一张外部系统与 BiSheng 之间的用户映射表。当客户的用户标识与 BiSheng 不一致时，映射由**调用方**负责（换成用户名亦可），平台不承担映射职责。

### 需求归纳

- 「张三在我们自己的系统里搜索知识库，**结果必须和他在 BiSheng 里搜到的一致**」——按张三的权限过滤，不多不少。
- 「以张三的名义创建一个知识库」——创建出来的资源归属张三，他在 BiSheng 里能看到并管理。
- 「出了问题要能查到是谁干的」——审计能同时回答"哪个系统调的"和"以谁的名义调的"。

**特点**　最终用户在平台上有真实账号，权限体系是同一套。用户规模可能上千——这直接决定了委托范围不能靠逐个列举 user_id 来配置（见 §4.4.4 的类型化「委托范围」）。

**当前为什么不行**　能力已存在（F4），但没有任何信任基础：请求里写谁就是谁，且不需要凭据。任何能访问到接口的人都可以填上任意 user_id，以任意员工的身份检索。

**核心争议**　"凭什么指定一个 user_id 就代表是这个用户在操作？"——见 §4.4.3。

## 3.3 场景三：面向外部用户的应用

> **本场景与场景一走同一条技术路径**——权限基准同样是服务账号。差异只在两处：需要按外部访客分区会话，以及服务账号的授权尺度截然不同。逐项对照见 §3.4。

**谁**　客户面向自己的客户/公众提供的应用，其用户与 BiSheng 无任何账号关系。

**要什么**　「我们做了个对外客服机器人，用的是 BiSheng 的知识库。这些访客不是 BiSheng 用户，不应该被平台的用户权限体系卡住」。

**特点**　最终用户在平台上不存在，且不应该为此批量创建账号。

**当前为什么不行**　当前一律以固定身份执行，全部外部访客产生的会话统一归属那一个平台用户——无法区分调用来自哪个终端用户，用量归属与审计混作一团。可验证的直接后果：`GET /api/v1/workstation/app/conversations` 按 `user_ids=[login_user.user_id]` 过滤会话列表（`workstation/api/endpoints/apps.py:197-206`），**平台侧以该固定用户登录的人，会在自己的会话列表里看到全部 API 会话**。

**问题的边界**　外部访客之间**读不到**彼此的对话——`chat_id` 是服务端生成的随机 UUID（`open_endpoints/api/endpoints/workflow.py:52`），且 V2 没有任何按用户列举会话的端点（本次也不新增，§4.6.3）。因此本方案要求的会话分区（§4.3.4）**始终是前瞻性设计**：它防的是后续补充"按终端用户查询会话"这类能力时，精确落进 Coze 记录在案的那个坑 [S5]。对外材料按此口径表述，不作为现存漏洞陈述。

**需求澄清（重要）**　这类客户的原始诉求常被表述为"不要做权限过滤"。**直接实现会造成无边界数据出口**——一旦服务账号权限过宽，外部访客即可检索到全部内部文档。正确的产品解法是：**过滤照做，基准换成服务账号**。给该服务账号授予"这个外部应用应当能看到的那些知识库"，那就是这个应用的数据边界。客户得到的效果一致（外部访客不会被平台用户权限误伤），平台保住了边界可控与可审计。

## 3.4 场景与模式映射

**只有两种身份模式**——因为身份模式的定义是"权限基准是谁"，而场景一、三、四的权限基准都是**密钥主体本身**。下表刻意把它们排在一起：

| 场景 | 身份模式 | 权限基准 | 请求头 | 资源归属 | 会话分区 |
|---|---|---|---|---|---|
| **一 · 系统集成** | **模式 S**（主体=服务账号） | 密钥主体 | 无 | 服务账号 | 按密钥 |
| **三 · 外部用户** | **模式 S**（同上） | 密钥主体（同上） | 可选 `X-Bisheng-End-User` | 服务账号 | **按外部标识** |
| **四 · 员工自助接入**（§3.5） | **模式 S**（主体=**自然人**） | 密钥主体（同上） | 无 | 持有人本人 | 按密钥 |
| 二 · 平台同批用户 | **模式 D**（委托） | 被代表用户（受五道准入约束） | `X-Bisheng-On-Behalf-Of` | 被代表用户 | 按被代表用户 |

> 场景四**没有引入第三种模式**：它的权限基准依然是"密钥主体"，只是主体从服务账号换成了一个自然人。
> 这正是身份模式判据（权限基准是谁）的价值——它让新增一类主体不必新增一种模式（§4.10.1）。

> `X-Bisheng-End-User` **不是一种身份模式**，而是模式 S 下的一个可选请求头，只影响会话分区与审计留痕，不改变任何权限判定（§4.3.4）。把它命名为一种独立模式会强化"选它就不走平台权限了"的误读——而那恰恰是 §3.3 要澄清的。

### 场景一与场景三的差异清单

技术路径相同，不等于配置方式相同。**差异全部在权限判定之外**：

| 维度 | 场景一 | 场景三 |
|---|---|---|
| 权限判定 | 服务账号 | **完全相同** |
| 会话分区 | 不需要（没有最终用户） | **需要**，否则无法区分会话来自哪个访客 |
| 服务账号的授权尺度 | 按"这个系统要干什么"授 | 按"哪些内容可对公网访客开放"授 |
| 授权配宽的后果 | 内部集成越权 | **公网数据泄漏** |

最后一行是这份清单存在的理由。两个场景共用一条技术路径，最容易被带出的错误结论就是"那按同样的标准配服务账号权限即可"——而两者配错的爆炸半径差着量级。**正因为技术同源，这条风险提示才必须显式写出来。**

## 3.5 场景四：员工自助接入个人办公助手

### 典型形态

员工在个人中心自助申请一把属于自己的密钥，填进他日常在用的第三方办公 AI 助手（workbuddy、豆包工作台一类），此后在那个助手里直接提问，助手代他检索平台知识空间的内容。

```
员工 ──申请──▶ 个人中心签发 bs-pat-…
                     │
                     ▼
        第三方办公 Agent（员工自己配置）
                     │  Authorization: Bearer bs-pat-…
                     ▼
        POST /api/v2/filelib/retrieve
                     │
        权限基准 = 这名员工本人
```

### 与前三类场景的本质差别：**谁来配这把密钥**

§3.1–3.3 三类场景有一个未言明的共同前提：**调用方是组织采购或自建的系统，密钥由管理员配置**。因此"最小必要权限"可以由管理员集中收敛——这正是服务账号存在的理由（§4.2.2）。

场景四打破了这个前提：

| 维度 | 场景一 / 二 / 三 | 场景四 |
|---|---|---|
| 调用方 | 组织的系统 | **员工自己选的工具** |
| 谁配置密钥 | 管理员 | **员工本人**（自助） |
| 权限来源 | 服务账号被显式授予 | **持有人本人的既有权限** |
| 数据落点 | 通常仍在组织控制范围内 | **可能是第三方 SaaS** |
| 管理员的角色 | 事前授权 | **事前放行 + 事后台账与吊销** |

最后两行是治理必须存在的原因：**场景四是本 PRD 里第一条把企业知识送出组织控制边界的通道。** 前三类场景的对端是企业自己的系统；场景四的对端是员工个人选择的商业 SaaS。这不改变技术方案，但决定了 §4.10.6 的治理闸门不是可选项。

### 需求归纳

1. 员工能在不打扰管理员的前提下自助拿到密钥——**这是这个场景的全部价值，走审批就等于没做**
2. 检索结果必须**恰好等于**他在平台界面里能搜到的内容：**多一条是越权，少一条是功能不可信**
3. 员工离职 / 被禁用 / 换租户后，他的密钥必须立刻失效——**且不依赖任何人记得去吊销**
4. 管理员必须能看见本租户有哪些人签了密钥、最后什么时候用过，并能强制吊销
5. 员工需要知道"怎么填进那个助手"——**接口文档要能直接复制走**，否则拿到一串密钥等于没交付

### ⚠️ 两个不在技术方案里、但决定成败的前提

**前提一 · 连通性。** 私有化部署的 BiSheng 在客户内网，而 WorkBuddy / 豆包工作台是**公有云 SaaS**——公有云侧访问不到内网地址。因此场景四要真正跑通，必须先明确打通方式（经网关暴露 / 办公 Agent 也在内网 / 出站连接器）。**这一条须问客户，不能由我们假设**；它不改变本 PRD 的技术方案，但会影响有效期上限与 IP 白名单的优先级（**D14**）。

**前提二 · 目标平台不是都接受"一把员工自己的密钥"。** 调研核实（详见 §4.10.7）：

- **WorkBuddy** 接外部服务**只接受「安装自定义 MCP 服务」**——形态是 MCP，不是 OpenAPI [S18]
- **钉钉连接器**可以吃 `Authorization: Bearer`，但凭据是**连接器级、管理员集中托管**，没有"每人填自己 key"的位置 [S19]
- **Coze / 扣子的静态密钥是插件级全局一把，没有 per-user 填 key 的输入位**——"员工把自己的密钥填进插件"**在 Coze 上没有原生落点**，要拿到调用者本人身份只有 OAuth 授权码一条路 [S20]。⚠️ 本轮取证的是 Coze（`docs.coze.cn`），**「豆包工作台」本身未取证**，不得直接套用

> **第三条与客户的原始描述有出入，必须回问确认两件事**：① 要接的到底是哪个平台（Coze / 扣子？豆包工作台？WorkBuddy？）；② 若是 Coze 形态，"发一把个人密钥"解决不了问题（**D18**）。这不影响本需求本身的价值——WorkBuddy 与客户自研 Agent 都吃得下——但影响"能接哪个平台"这个承诺。

## 4.2 R1 · 凭据体系

### 4.2.1 为什么新建而不复用现有机制

平台已有四类"对外签发或持有的凭据"——分享链接 token、工具 `api_key`、邀请码、网关 HMAC。**逐一核实后没有一个可以复用**：没有一个做哈希存储，没有一个真正实现过期，没有一个有可用的撤销入口。

因此凭据层是纯新建。逐项核实结果与两个必须复用的现成件见**附录 E.1**。

### 4.2.2 密钥的两类主体

**每把密钥都绑定一个主体，主体决定权限边界。主体有且只有两类：服务账号与自然人。**

本节讲**服务账号**这一类——它承载 §3.1–3.3 三类系统集成，是本次工程量最大的一块。
自然人主体（个人访问令牌）承载 §3.5 场景四，规则见 **§4.10**；两类主体共用本节以下的全部凭据规约（§4.2.3–4.2.6）。

| 项 | 值 |
|---|---|
| 前缀 | `bs-sak-`（前缀即类型，便于密钥泄漏扫描 [S6][S3]；个人访问令牌用 `bs-pat-`，同样纳入扫描规则） |
| 绑定主体 | 服务账号——一种不可登录的一等主体，见 §4.5 |
| 权限来源 | 服务账号**自身**的授权，不继承任何自然人 |
| 生命周期 | 长期有效，可设过期；支持不轮换密钥直接改权限 [S6] |

**为什么不把开放 API 的权限挂在自然人账号上**——这不是假想的替代方案，正是**现状**：所有调用统一以一个数据库配置的固定用户执行，接口文档还建议把它配成超级管理员（§2.2 F2/F3）。挂在真人账号上有两个结构性缺陷：**权限边界等于那个人的权限**，无法按某一集成的最小必要收敛；**生命周期绑在人事上**——LangSmith 同时提供两类密钥，其文档明确记载了自然人密钥的这一固有缺陷：个人令牌随创建者离职失效 [S6]，而生产集成不能因某员工离职而中断。服务账号让权限归属与自然人彻底解耦，审计也能干净地回答"这次调用是哪个系统发起的"。

**这段论证的适用范围是系统集成，不可外推到场景四。** "权限边界等于那个人的权限"对一条生产集成是缺陷；对一名员工接自己的办公助手，它**恰恰就是需求**。同理，"随创建者离职失效" [S6] 对生产链路是事故，对个人密钥是必须有的行为。同一条事实的两种读法，展开见 §7.6 D13。

### 4.2.3 密钥属性

| 属性 | 说明 |
|---|---|
| **`tenant_id`** | **租户隔离字段，必填**。详见 §4.2.5 |
| 主体 ID | 指向服务账号在用户表中的主键 |
| 名称 | 用户可读，必填 |
| 前缀 / 末四位 | 列表展示用 |
| 密钥哈希 | SHA-256，唯一索引 |
| 权限位 | 见 §4.2.4 |
| **委托范围** | 持有 `delegate` 时**必填**的类型化范围，见 §4.4.4。**持有 `delegate` 即强制委托**：该密钥的每次调用都必须传 `X-Bisheng-On-Behalf-Of`，漏传返回 400（`26016`）；不设独立的"强制委托"开关（理由见 §7.3）。**与应用工场三个扩展位互斥**——理由见 §4.2.4 |
| IP 白名单 | 可选 CIDR 列表（P2） |
| 过期时间 | 可空（长期有效）；创建时可选设定 |
| 最后使用时间 | 节流写入（≥60s 更新一次），避免热路径写放大 |
| 撤销时间 | 软撤销，保留审计可追溯性 |

**以上属性两类主体通用。** 个人访问令牌只在五处与服务账号密钥不同（主体、权限来源、签发者、有效期必填、级联失效），逐项见 §4.10.2。

**有效性判据是单一事实**：`撤销时间为空 且（过期时间为空 或 未到期）`。**不设独立的 status 枚举列**——分享链接的 INACTIVE 枚举全仓无写入端点，证明可漂移的冗余状态列是负资产。

**委托的配置只有两个字段**：`delegate` 权限位是唯一开关，委托范围是必填的边界。**不设"委托模式"枚举，也不设"强制委托"开关**——理由见 §7.3。

### 4.2.4 权限位

```
workflow:invoke   workflow:read
knowledge:read    knowledge:write
assistant:invoke  assistant:read
chat:invoke       ← 日常模式会话（§4.6.3），含按 id 取回 response
delegate          ← 委托能力，独立位，不被上述任何权限蕴含
```

| 权限位 | 覆盖的能力 |
|---|---|
| `workflow:invoke` / `workflow:read` | 触发与停止工作流 / 查询工作流信息 |
| `knowledge:read` / `knowledge:write` | 知识资源与文档的读 / 写 |
| `assistant:invoke` / `assistant:read` | 助手对话 / 助手信息与列表 |
| `chat:invoke` | **日常模式会话**——`POST /responses` 直接与模型对话（§4.6.3）、按 id 取回 response、会话附件上传 |
| `delegate` | 代表平台用户执行 |

**本次不设 `session:*` 权限位（2026-08-16 决议）。** v1.0 曾规划 `session:read` / `session:write` / `session:sync` 三位，用于会话历史查询、反馈写入与消息回填。三者随其端点一并移出本次范围（§4.6.3），理由是**平台侧存会话，与给调用方开读会话的接口，是两件事**：

- **平台存会话是必须的**，它支撑场景二的核心承诺——模式 D 下员工在自建系统里的对话，回到 BiSheng 工作台能看到同一个会话并继续追问（AC-32）。这条验收在**平台工作台**里完成，一个 V2 读接口都不需要。
- **多轮对话由 `previous_response_id` 续接**，属于 `chat:invoke` 的能力，同样不需要读接口。
- **调用方自建系统本来就有自己的消息存储**，比平台更清楚该怎么索引自己的会话。平台再提供一套是重复而非补充；§3 三类场景中也没有任何一类提出过这个诉求。

「按标识取回单轮结果」是唯一保留的读动作（异步分支点亮时必需），**并入 `chat:invoke`**——调用方发起过对话才会去取回结果，是同一个消费单元，不存在只需其一的消费者（拆位判据见 `app:manage` 一节）。

`delegate` 独立成位，落实"冒充能力必须单独授予"这一跨平台共识（附录 A.5）。它是委托的**唯一开关**——勾选后必须再配委托范围才真正生效，范围为空即谁都代表不了（§4.4.4）；**勾选即强制**：持有它的密钥每次调用必须声明被代表用户，不存在"可代表也可不代表"的混用密钥（§4.4.2 铁律 2、§7.3）。需要以服务账号身份调用的集成，另签一把不带 `delegate` 的密钥。

**应用工场扩展位（2026-08-15）**：部署应用工场开放能力层时，本清单追加三个位，供本地开发工具包（MCP / 模型协议面 / CLI）使用；知识库检索**不另设位、复用 `knowledge:read`**（MCP 检索工具本就包装 V2 检索路径）。它们与本清单是同一张表、同一个签发表单、同一套默认全不勾原则，不构成第二个权限维度；标准版（未部署开放能力层）不出现。定义与端点映射见《3.0 应用工场 PRD-1》DEV-01。

| 扩展位 | 覆盖的能力 | 须留意 |
|---|---|---|
| `model:invoke` | 模型协议直连（**仅 OpenAI 兼容**，Anthropic 面本版不做）与模型清单查询 | **与 `chat:invoke` 互不蕴含**：本位是裸协议透传，不建会话、不持久化历史；`chat:invoke` 走平台会话机制（建 `MessageSession`、可挂知识库与平台工具、留历史、在平台 UI 可见）。二者数据面不同，需要哪个给哪个，不因"都是调模型"而互相顶替 |
| `identity:read` | 用户身份与组织架构查询 | ⚠️ **高危位：授予即本租户组织架构全量可读**（姓名、部门、层级）。平台不存在"把某些部门授予某个服务账号"这种资源授权，服务账号本身也刻意不属于任何部门（D10 / §7.4），因此**没有任何机制能把它收窄到组织树的一部分**。租户隔离仍然生效，跨租户读不到。签发表单须对本位显著风险提示 |
| `app:manage` | 对自己名下应用的全部操作：发布（deploy）、运行状态与日志查询、应用数据表结构与数据读写 | **整块不拆**（2026-08-16 复核后由原 `app:data` + `app:deploy` 合并）。拆位的判据不是「两个动作风险量级是否不同」，而是「**是否存在只需要其中一个的真实消费者**」——`session:sync` 之所以拆出来，是因为确有「只想收集用户点赞」的集成。本位没有这样的消费者：本 PRD 模型下 deploy 由开发者本地 agent 发起，而同一个开发者、同一把 key 也在对着应用表结构写代码；工具侧又按 owner 收窄（PRD-1 DEV-02），不存在「帮别人部署」的第三方 key。拆开只会让管理员每次都勾满，徒增配置项而无实际收敛。命名取 `manage` 而非 `deploy`，因为它含读也含写 |

**三个扩展位只走模式 S，且与 `delegate` 互斥。** 它们服务的是本地开发通道（MCP 工具面 / 模型协议面 / CLI），这三面一律以服务账号自身身份执行、**不承载委托**：

- **判据**：委托的权限基准替换只在**有第三方自然人在场**时才成立。本地通道的两端是开发者本人与他的 coding agent，没有被代表的对象。逐能力核算亦零受益——模型清单查询与身份 / 组织查询的可及范围本就是租户级配置，替换后毫无变化；而知识库清单查询与应用类工具**会被它损坏**（前者的用途是填写应用级静态能力声明，按被代表用户返回会让声明被固化成某一个人的可见集合；后者的 owner 收窄会被「模式 D 下创建的资源归属被代表用户」放大爆炸半径。逐条见《3.0 应用工场 PRD-1》DEV-02 ④）。
- **签发期硬阻断**：`delegate` 与三个扩展位在签发与编辑表单中互斥、无法同时保存（§4.7.3）。理由是 §4.2.3 的「持有 `delegate` 即强制委托」——这样一把密钥在三面的每次调用都会因漏传身份头返回 400，**签出来即是废件**。
- **运行期兜底**：持 `delegate` 的密钥接这三面时，在**通道入口按权限位直接拒绝**（CLI 在 `login` 即拒，不等到 `deploy`），错误信息指向「这把密钥配置为委托专用，本地开发请另签一把」。**不得实现为「漏传委托头就静默落到模式 S」**——那正是 §7.3 否决的失败形状；而直接抛 `26016` 这类参数错误对本地 agent 不可诊断。

**个人访问令牌只能被授予 `knowledge:read` 一个位**（§4.10.3）。`identity:read` 与 `delegate` 对自然人主体是**永久禁令**而非本期取舍——前者授予即全租户组织架构可读且无收窄机制，后者等于把横向提权做成产品功能。

**创建时默认不勾选任何权限位**。反面实证来自 n8n：「Non-enterprise API keys have full access to all the account's resources and capabilities.」[S4]——默认全权限即隐患。

### 4.2.5 存储与租户隔离

**密钥以单向哈希存储，服务端不保留明文，也不使用可逆加密。** 数据库被拖走也无法还原出可用的密钥。这与"配置里的数据库密码"那类需要还原后转发的凭据不同——入站密钥只需比对，不需还原。

**每把密钥归属且仅归属一个租户**，跨租户查询密钥列表必须返回空（AC-5）。租户隔离在平台内有一条既定的自动机制，但它有两个必须同时满足的前置条件，漏掉其一会导致**数据被静默写进错误的租户**——平台在 v2.5 出过一次这样的事故。落地要求见**附录 E.1**。

**撤销必须在 5 秒内生效**（AC-3）。校验结果允许短时缓存以避免每请求都查库，但撤销时须主动失效。

### 4.2.6 展示与泄漏应急

- **仅显示一次**：明文仅在创建响应中返回，此后任何接口不再吐出；列表页只显示前缀与末四位。
- **泄漏扫描**：前缀 `bs-sak-` 与 `bs-pat-` **两个都要**注册到代码托管平台的 secret scanning 规则。前缀即主体类型，这既服务于扫描，也服务于审计归因——从一条泄漏告警就能直接判断「泄的是一条集成，还是某个员工的令牌」，处置路径完全不同。
- **批量撤销**：支持"一键撤销某主体名下全部密钥"，用于泄漏应急。

## 4.3 R2 · 两种身份模式

**身份模式只有两种**——模式 S（以服务账号身份执行）与模式 D（代表某个平台用户执行）。判据是**权限基准是谁**：凡权限基准相同的，就是同一种模式。

除身份模式外还有一个**可选请求头** `X-Bisheng-End-User`（§4.3.4），它服务于场景三，但**不构成第三种模式**——它不改变权限基准，只影响会话分区与审计留痕。

两个身份头**互斥**：同时传入 `X-Bisheng-On-Behalf-Of` 与 `X-Bisheng-End-User` 即为参数错误（模式 D 下会话已归属被代表用户，再传外部标识没有语义）。

### 4.3.2 模式 S · 服务账号身份（默认）

不传 `X-Bisheng-On-Behalf-Of`。全部操作以密钥主体身份执行，按其可见范围过滤。**只有不持 `delegate` 的密钥能走此模式**——持 `delegate` 的密钥漏传该头是错误（400 `26016`），不会落到模式 S（铁律 2）。因此一把密钥的身份模式在签发时就已确定，不由调用方逐次选择。

**同时对应场景一与场景三**——两者的权限判定完全一致，场景三只是额外带上 `X-Bisheng-End-User` 做会话分区（§4.3.4），并在授权尺度上按"可对公网开放"从严把握（§3.4 差异清单）。

行业同构：RAGFlow [S2]、n8n [S4]、LangSmith [S6]——这三家均**完全没有**最终用户身份传递机制。

### 4.3.3 模式 D · 代表平台用户

```http
POST /api/v2/filelib/retrieve
Authorization: Bearer bs-sak-…
X-Bisheng-On-Behalf-Of: 10086
```

对应场景二。行业同构：**FastGPT `authProxy`**（最贴近）[S3]、Zendesk `X-On-Behalf-Of` [S7]、Kubernetes `Impersonate-User` [S8]。准入规则见 §4.4.4。

### 4.3.4 外部用户标识（可选请求头，非身份模式）

```http
POST /api/v2/workflow/invoke
Authorization: Bearer bs-sak-…
X-Bisheng-End-User: crm-user-88f3a2
```

服务于场景三。行业同构：Dify `user` [S1]、Coze `session_name` [S5]、FastGPT `customUid` [S3]——**这三家同样都把它定义为一个普通参数，而非一种身份模式**。

**语义声明（须原样写入对外 API 文档，措辞不容含糊）**：

> `X-Bisheng-End-User` **仅用于会话隔离与审计留痕，不参与任何权限判定**。平台不认识、不校验、不解析该标识。传与不传，数据可见范围完全相同，**均等于密钥主体（服务账号）的权限边界**。

此措辞对齐 Dify「Dify never authenticates it」与 Coze「currently utilized only in session isolation」——两家都用近乎相同的免责声明 [S1][S5]。

> **为什么它不是第三种身份模式**：身份模式的判据是权限基准是谁，而传不传这个头，权限基准都是服务账号（AC-11 即验收此点）。把它命名为一种模式，会让客户读成"选它就不走平台权限了"——正是 §3.3 花整段澄清的那个误解。**命名不该与要传达的语义相反。**

**缺省行为**：对有会话语义的端点，若未传该头，会话按密钥粒度归属并记 WARN 日志。日志是提示而非阻断——**这是前瞻性约束**，目的是让会话从一开始就带上终端用户维度，后续补充"按终端用户查询会话"能力时不必回头改存量数据（§3.3 问题的边界）。

**配额归属**：外部标识**不作为配额维度**。配额与限流一律按密钥计（§4.8）——平台无法验证外部标识，按它计量等于把配额控制权交给调用方。

**互斥**：与 `X-Bisheng-On-Behalf-Of` 同时传入返回 400（`26010`）。

| | 模式 S | 模式 D |
|---|---|---|
| 身份头 | 无 | `X-Bisheng-On-Behalf-Of` |

| 权限基准 | 密钥主体 | **被代表用户**（受五道准入约束） |
| 标识是否参与鉴权 | — | **是** |
| 目标须为平台用户 | — | **是** |
| 资源归属 | 密钥主体 | 被代表用户 |

| 覆盖场景 | 一、三 | 二 |

| | 模式 S 不传 | 模式 S 传 End-User |
|---|---|---|
| 权限基准 | 密钥主体 | 密钥主体（**不变**） |
| 会话分区键 | 密钥 | **外部标识** |
| 审计留痕 | 密钥主体 | 密钥主体 + 外部标识 |

## 4.4 R3 · 权限过滤与受限委托

**一次开放 API 调用能看到什么、能做什么，由两层"与"关系决定**——密钥被授予了哪一类动作，以及执行身份对那个具体资源有什么权限。**委托只做一件事：把第二层的执行身份换成另一个人**，并为这次替换设置一次性准入。**任何一层判定不了，一律拒绝，绝不放行。**

下面依次讲清判定框架（§4.4.1–4.4.2）与委托机制（§4.4.3–4.4.5）。相关的决策取舍记录在第七章。

### 4.4.1 判定框架：两层与关系

两层缺一不可，且**分别由不同的人在不同的界面配置**——这是运维时最容易混淆的一点，必须在文档与界面上讲清。

| 层 | 判定什么 | 配置者与位置 | 判定时机 | 不满足 |
|---|---|---|---|---|
| **① 密钥权限位** | 这把密钥能做哪**一类**动作（读知识库 / 调工作流 / 委托…） | 管理员，密钥创建或编辑（§4.2.4） | 统一鉴权层前置，见 §4.3.1 流程 ③ | `26003` |
| **② 主体资源授权** | 执行身份对**这一个具体资源**有什么权限 | 管理员，服务账号授权页（§4.7.4） | 业务执行时经 `require_business_action`（宪法 C4） | 各业务模块既有的资源权限错误 |

两层是**与**的关系：持有 `knowledge:read` 但服务账号未被授予知识库 A，读 A 失败；被授予了 A 但密钥没勾 `knowledge:read`，同样失败。

**两种失败必须给出可区分的错误**——前者返回 `26003` 并指明缺哪一位，后者沿用业务模块原有的资源权限错误码，**不得合并成同一个笼统的 403**。否则集成方拿到 403 无从判断该找管理员加权限位，还是该申请资源授权。

> **本次不引入密钥级的资源白名单**（"这把密钥只能碰知识库 A/B"这样的第三层收窄）。理由见 §6 非目标。

### 4.4.2 判定不了时一律收紧：三条铁律

§4.4.1 讲的是"满足什么才放行"，这里讲的是**另外三种情形**——凭据缺失、身份缺失、引擎故障。三者的共同点是"信息不足以做出判定"，处理原则统一为**收紧而非放行**。

| 铁律 | 行为 | 依据 |
|---|---|---|
| **铁律 1 · 无凭据即拒绝** | 移除固定身份兜底。无有效密钥 → 401，不降级 | §2.2 现状风险 |
| **铁律 2 · 缺身份即报错** | 持有 `delegate` 的密钥未传 `X-Bisheng-On-Behalf-Of` → 400（`26016`），**不降级执行** | Microsoft 2025-11 的同类改造确立了"缺身份绝不等于放行全部"[S13] |
| **铁律 3 · 评估失败即报错** | 权限引擎不可用 → 5xx，**绝不**返回未过滤或部分过滤的结果集 | 「does not return a partially filtered result set」[S13] |

#### 关于铁律 2：为什么是报错，不是降级

场景二的密钥只用于代表员工执行，服务账号自身不该有、也不需要任何知识库授权。**勾选 `delegate` 本身就是声明"这把密钥的每一次调用都必须指定被代表用户"**（§4.2.3）——不设独立的"强制委托"开关，否则"勾了 `delegate` 但没开强制"的密钥漏传身份头时会静默落到模式 S，恰是下表左列被否决的失败形状（§7.3）。

漏传身份头时有两种处理方式，本方案选报错：

| | 降级执行 | **报错（本方案）** |
|---|---|---|
| 返回 | 200 + 某个"安全"的结果集 | 400 + `26016` |
| 集成方感知 | **无从察觉**——以为拿到的是该用户的数据 | 立刻暴露，联调阶段即修复 |
| 结果正确性 | 静默错误：给多了是越权，给少了是功能缺失 | 不产生错误结果 |

**这与 §7.2 否决"权限取交集"是同一条标准**：那里的核心理由正是"返回 200、给出一个缩水的结果集、调用方无从察觉"。漏传身份头是完全相同的失败形状，没有理由在这里反而接受它。

> **铁律 3 需专项验证**：落地时须逐条确认不存在"过滤器抛异常被吞 → 返回全量"的代码路径。

### 4.4.3 委托的信任基础（回答核心争议）

**这不是身份认证（authentication），是授权委托（delegation）。**

它声称的不是"张三本人在操作"，而是"平台管理员已授权这个集成方，可以按张三的权限边界执行并把结果归属给张三"。安全性来自三处，**从不来自 user_id 本身**：

| 信任来源 | 落地在哪 |
|---|---|
| 1. 密钥的保密性——调用方先用自己的凭据完成认证 | §4.2.5 校验流程，是准入检查的前置 |
| 2. 委托能力的显式授予——一项独立的、可撤销的权限 | §4.4.4 检查 1 |
| 3. 审计双归属——可追责到具体密钥 | §4.4.5 |

这与 Kubernetes 的鉴权时序完全同构：先认证发起者，再校验其冒充权限，最后才替换身份 [S8]。**委托头永远不能单独确立身份。**

### 4.4.4 受限委托：五道准入检查

**委托的安全性由一次性准入判定保证，而非逐资源判定。** 五道检查分别回答三个问题——**谁可以委托、可以代表谁、这次调用允不允许委托**；全过之后执行身份纯替换为目标用户，后续逐资源鉴权与今天完全一致，无额外开销。

| # | 判定对象 | 检查 | 失败码 | 行业依据 |
|---|---|---|---|---|
| **1** | **密钥** | 持有 `delegate` 权限位 | 26004 | Zendesk 独立 `impersonate` scope [S7]；FastGPT 逐密钥由团队所有者显式开启 [S3] |
| **2** | **目标** | **是自然人**、存在、未禁用、与密钥主体同租户 | 26005 | Zendesk「must have an existing user profile」[S7] |
| **3** | **目标** | **不是超级管理员，也不是租户管理员** | **26007** | 本方案自主设计，见下 |
| **4** | **目标** | 在密钥配置的**委托范围**内 | 26004 | Kubernetes `resourceNames` 取值白名单 [S8] |
| **5** | **端点** | 在委托支持列表内 | 26006 | 本方案自主设计 |

检查 2–4 都作用于目标用户，构成三层收窄：**是个可用的人 → 不是特权的人 → 是被授权可代表的人**。第一层里的"人"是字面意思——服务账号也坐在用户表里，必须在这一层就被挡住。

#### 检查 2 为什么要判自然人

服务账号也是用户表里的一行：同租户、未禁用、不是超管，若不额外判定，它满足"一个可用的目标"的全部条件。一旦允许被代表，**拿到密钥 A 的人就可以指定服务账号 B 为目标，从而获得 B 的全部资源授权**——而服务账号恰恰是被授予集成权限的主体，通常比自然人更宽。这是一条"用一把密钥换另一把密钥权限"的横向提权路。

**这道判定必须在调用期，不能只放在配置保存期。** 委托范围的两类条目性质不同：`user` 条目存的是具体的人，保存时可以逐个校验；`department` 条目存的只是部门 ID，**谁在这个部门里是每次调用时才展开的**。平台存在把"没有部门的用户"兜底写进「临时访客」部门的自动逻辑，而该部门挂在根部门之下——委托范围填根部门（场景二的常规配法，见检查 4）即覆盖它。也就是说，保存当时干净的一条范围条目，此后可能在无人操作的情况下把服务账号纳入，而保存期的校验一次都不会再跑（取证见附录 E.2）。

**成本为零**：检查 2 为确认"存在、未禁用、同租户"本就要取出目标用户行，账号类型在同一行上，不增加任何查询。

#### 检查 3 掐断唯一的无界提权路径

权限引擎中只有两个"无条件放行"的短路——超级管理员与租户管理员。除这两类外，任何用户的权限都是有界的、逐资源的（取证见附录 E.5）。

**掐断这两类，即掐断了唯一的无界提权路径**；而判定成本极低，超管判定本就有 Redis 缓存。

#### 检查 4 的委托范围：必填，两种类型

> **先明确一件事：被代表的对象永远是单个用户。** `X-Bisheng-On-Behalf-Of` 的取值只能是一个用户 ID 或用户名（§4.3.3）。委托范围是一张**白名单——圈定这把密钥被允许代表哪些人**，不是被代表的对象本身。
>
> 因此 `department` 是**圈定候选人的方式**，而非"以部门的身份执行"。平台不存在非自然人主体的资源归属概念，委托生效后的执行身份、资源归属与审计 subject 全都是那一个具体的人。

白名单由**用户**和**部门**两类条目组成，**各自可多选，两类也可混用**——例如"销售部全体 + 财务部的张三"：

| 类型 | 圈进白名单的人 | 典型用法 |
|---|---|---|
| `user` | 所列的每个用户本人 | 少量固定账号；也用于"以某人名义执行"，例如把 ERP 合同同步进张三的知识库 |
| `department` | 所列部门**及其子树**内的全部成员 | 场景二的主力。填根部门即等于全员 |

之所以要有 `department`：场景二动辄上千用户，逐个勾选运维做不了，一个部门条目就够。

存储上是 `(key_id, subject_type, subject_id)` 一行一条，判定为一次索引查询。部门子树复用现有物化路径（`database/models/department.py` 的 `UserDepartment` + `Department.path`）。

**范围不可为空。** `delegate` 权限位是委托的唯一开关，勾选后必须至少配一条范围条目，否则这把密钥代表不了任何人——**没有"允许代表任意人"这一档**（理由见 §7.3）。

**保存 `user` 条目时同样校验目标是自然人——但这是早报错，不是安全防线。** 安全由检查 2 在调用期兜底；保存期校验的价值是让管理员在配置时就看到提示，而不是等集成上线后才在调用中失败。选人框里本就搜不到服务账号（§4.5 定义 5），此校验覆盖的是绕开界面直接调接口的路径（AC-37，落点见附录 E.2）。

### 4.4.5 审计双归属

信任来源 3 的落地。模式 D 的审计记录必须同时包含：

- **actor**：密钥主体 + 密钥 ID（回答"哪个系统调的"）
- **subject**：被代表用户（回答"以谁的名义调的"）

资源归属字段写被代表用户——对齐 Zendesk「the change is associated with the end user, not the admin」[S7]。

### 4.4.6 纯替换的等价性要求：检索须补文件级过滤

模式 D 承诺的是**权限基准整体替换为被代表用户，不多也不少**（§4.3.3、§7.2），AC-12 直接验收这一条。**但现有的 V2 检索路径兑现不了这个承诺**：它只做知识资源级的一次可见性校验，而平台内部的检索路径是两层过滤——索引层预过滤 + 结果层批量兜底。

平台内确实存在同一知识资源**内部**的文件级可见性差异，来源有四类：单个文件被直接授权、文件切到自定义模式后与所在资源的可见性脱钩、不同文件夹的授权不同、以及系统标记与跨租户共享。用户在平台界面里浏览和检索时**是**按文件过滤的——这是既有产品能力，不是边缘情形。

因此不补齐这层过滤，模式 D 返回的结果集就是被代表用户平台内可见集合的**真超集**：多出他无权访问的文件的正文片段，而响应里还带着文件名，属于正文与文件名的双重泄露。**这不是"多给了一点"，而是委托失去了"不多不少"的语义**——§7.2 否决取交集时立的那条标准（不接受"返回 200 + 静默的错误结果"）在这里同样适用，只是方向相反：那边是给少了，这边是给多了。

**要求**：`POST /api/v2/filelib/retrieve` 须补齐文件级过滤，与平台内部检索路径对齐。**这是模式 D 的交付前提，不是可选优化**；平台已有现成的可见性过滤组件可直接复用，落点见附录 E.3。

> **个人访问令牌（§4.10）依赖同一条改造，而且要求更强。** 模式 D 是"代表别人"，验收靠对照被代表用户的可见集；个人令牌是"就是本人"——**持有人会拿平台界面的检索结果直接比对**（AC-P5 / AC-P7）。因此这条改造是两个需求共同的交付前提，只做一次；承接方是统一检索门面（§4.10.7 末节），**不是两处各实现一遍**。

## 4.5 R4 · 服务账号主体

服务账号是本次要新建的一类主体，也是 P0 工程量最大的一块。它的产品定义只有六条：

| # | 定义 | 为什么 |
|---|---|---|
| 1 | **不能登录平台**——拿不到会话，进不了 Web 界面，只能作为密钥背后的权限主体被 API 使用 | 它不是人，没有"本人操作"这回事；能登录就意味着有人可以顶着它的身份在界面上活动，审计随即失真 |
| 2 | **权限单独授予**，不继承任何自然人 | 集成的权限边界才能按最小必要收敛（§4.2.2） |
| 3 | **归属且仅归属一个租户**，创建时指定，之后不可更换（D7） | 它的密钥、被授权的资源、可代表的用户全在这个租户内 |
| 4 | **不占用租户的用户数配额** | 它坐在用户表里但不是人，不应挤占客户购买的席位 |
| 5 | **不出现在任何面向人的选人场景中**——用户管理、审批人选择、部门加成员、创建租户选管理员等一概不可见 | 它不是可被指派工作的人。给它授权在它自己的详情页完成（§4.7.4），不经过通用选人框 |
| 6 | **必须指定一个「资源归属人」**——一个自然人，它经 API 创建的资源全部归属于此人 | 见下 |

### 定义 6 · 资源归属人

**它解决的问题**：定义 1 说服务账号不能登录。那么模式 S 下经 API 创建出来的知识库归谁？若归服务账号，这个库在界面上就没有任何自然人是它的主人——只有管理员靠权限短路（§4.4.4 检查 3）看得见它，日常无人认领，服务账号也会因为名下堆着资源而永远删不掉（§4.7.4）。

**规则**：服务账号创建时必填一个自然人作为资源归属人。**该服务账号经 API 创建的资源，创建关系直接落到归属人头上**，此人在平台界面里像自己建的一样查看与管理它。

四条边界，缺一条就会出问题：

| # | 边界 | 不这样会怎样 |
|---|---|---|
| **a** | **会话不算资源**——模式 S 的会话仍归服务账号、按 `X-Bisheng-End-User` 分区（§4.3.4），不归到归属人名下 | 否则归属人一登录工作台，就在自己的会话列表里看到全部外部访客对话——**这正是 §3.3 要修的那个缺陷**，不能一边修一边用新机制把它请回来 |
| **b** | **服务账号对自己创建的资源保留写权限**——创建时在把归属写给归属人的同时，自动回授服务账号可编辑档位。该条授权在服务账号授权页标为「创建时自动回授」，**不受「全部撤销」影响**（§4.7.4） | 否则场景一第二天的定时同步就写不进它昨天刚建的知识库 |
| **c** | **归属人只承接归属，不出借权限**——服务账号能创建什么、能读写什么，仍只由密钥权限位 ∧ 它自身被授予的资源决定，与归属人本人的权限**完全无关**（定义 2 不受本条动摇） | 否则它就变成了一条隐式的权限继承路径，绕开 §4.4.4 五道准入 |
| **d** | **归属在创建那一刻固化**——事后更换归属人只对此后创建的资源生效，不追溯既有资源 | 否则改一个下拉框会静默转移一批资产的所有权，且无人收到通知 |

**与模式 D 的关系**：两者都能让资源落到自然人名下，差别在于**模式 D 同时替换权限基准**（§4.3.3）。因此**一次调用两者并存时，以模式 D 的被代表用户为准**——委托是显式的、逐次声明的，静态字段不该盖过它。

> **归属人本身不需要任何特殊权限**，也不因此获得对服务账号的管理能力——服务账号与密钥的管理始终仅限管理员（§4.7）。

**主体形态：复用现有用户表，新增类型字段区分（D4）。** 这是深思后的选择而非零成本方案——另建平行主体体系需要改动权限模块的主体类型全链路（授权主体校验、权限模型定义、投影逻辑），代价更高。但复用有三处必须付出的成本，任一处漏掉都会出问题：

| 成本 | 症状 |
|---|---|
| **租户归属需要独立维护** | 平台的租户归属由组织架构推导而来，而服务账号不属于任何部门。既要能写入，又要保证组织同步的定期对账不会把它清掉——**这是本项最容易被漏掉的一处** |
| **登录入口需要逐一封堵** | 平台有 10 个可获得会话的入口，必须全部拒绝服务账号，且需要测试矩阵防止后续新增入口时退化（AC-14） |
| **人员选择场景需要统一排除** | 通用的用户查询接口同时服务 8 处以上消费点，排除逻辑必须做在数据访问层，**漏传参数的后果应当是"看不到"而非"泄漏"** |

三处成本的具体落点、涉及的表与调用点、以及"为什么不给服务账号挂虚拟部门"的取证，见**附录 E.2** 与 **§7.4**。

## 4.6 R5 · 端点接入

开放 API 现有 **42 个 HTTP 端点 + 2 个 WebSocket 端点**。其中 **6 个 `/chat/*` 端点本次不暴露**（2026-08-16 决议，见下），其余全部接入鉴权。按处理难度分三类：

| 类别 | 规模 | 处理方式 |
|---|---|---|
| **既有 HTTP 端点** | **36**（42 减去不暴露的 6 个） | 统一在鉴权层接入，业务代码基本不动——**唯一的例外是检索端点须补文件级过滤**（§4.4.6）。逐端点的权限位、允许模式与改动项见**附录 B** |
| **既有 WebSocket 端点** | 2 | 密钥传递方式需专门设计——现有那条路是坏的（§4.6.1） |
| **新增日常模式会话** | **3 个**（+1 可选，+2 待异步分支） | 全新契约，本节最大的一块（§4.6.3） |

**本次不暴露的 6 个既有端点**（`session:*` 三位随之取消，§4.2.4）：

| 端点 | 原规划权限位 | 不暴露的理由 |
|---|---|---|
| `GET /chat/history`、`POST /chat/gen_title` | `session:read` | 调用方自建系统有自己的消息存储，§3 三类场景无一提出过读平台会话历史的诉求 |
| `POST /chat/liked`、`/chat/solved`、`/chat/comment` | `session:write` | 会话反馈（点赞/标记已解决/评论）无任何已声明场景 |
| **`POST /chat/sync/messages`** | `session:sync` | 可向任意 `chat_id` 注入任意条消息 = **伪造对话记录**，是全清单风险最高的端点，且同样零场景需求。**它现在是匿名的——本次靠"不暴露"解决，而非靠加鉴权**，这比加鉴权更彻底 |

> 这 6 个端点**从未出现在任何对外接口文档中**（`docs/api/` 下只有 filelib 相关两份），因此不构成已承诺能力的回收。但它们目前匿名可达，**不排除有调用方从代码里摸出来在用**——发布说明须逐个列出（§4.9）。

接入过程中会碰到四处既有缺陷，一并修掉（§4.6.2）。

### 4.6.1 WebSocket 的密钥传递

两个 WebSocket 端点（工作流对话、助手对话）同样必须鉴权，且**在握手阶段完成**——无效密钥不应先建立连接再断开。

| 调用场景 | 传递方式 |
|---|---|
| 服务端集成（主要场景） | `Authorization` 请求头，与 HTTP 完全一致 |
| 浏览器直连 | 子协议或票据换取——浏览器原生 WebSocket API 无法设置自定义请求头 |

**不采用查询参数传递密钥**：它会进入访问日志，与 R7 的审计要求冲突。

> 平台现有的 WebSocket 鉴权走的正是查询参数，而那条路径**是坏的**（参数被无条件覆盖，实际依赖 Cookie）。取证见**附录 E.3**。

### 4.6.2 接入时一并修复的既有缺陷

逐端点核查时发现的四处问题。它们独立于鉴权改造存在，但都在本次的改动面上，一并修掉成本最低：

| 端点 | 缺陷 | 修复 |
|---|---|---|
| `GET /filelib/download_statistic` | **匿名读取服务器文件**，无任何身份解析，仅靠后缀 `.log` + 路径前缀 + 目录名不含 `.` 三条字符串守卫 | 加鉴权；路径守卫换成白名单目录 + 规范化后校验。**优先级与匿名删除同级** |
| `POST /workflow/invoke` | 不校验工作流是否已上线，草稿态可直接调用 | 补上线状态校验 |
| `POST /workflow/stop` | 不校验会话归属，任何人可停任意会话 | 补会话归属校验 |
| `WS /assistant/chat/{id}` | 身份解析位置不当，配置缺失时握手裸崩而非优雅关闭 | 改为失败时按协议关闭（落点见附录 E.3） |

### 4.6.3 新增：日常模式会话开放

#### 一、结论：开放“有状态的应用级对话”，本次只交付同步的日常模式

现有 V2 只能调用**已编排好的**工作流与助手，无法开放工作台中“直接选模型对话”的日常模式。本次补齐这块能力：调用方选择模型，可选挂载知识库、启用平台工具、上传附件，并连续多轮对话。

这项需求的核心不是再造一套聊天能力，而是把平台已有能力安全、稳定地封装到 V2。内部日常模式与任务模式共用同一入口、由 `task_mode` 分流（取证见附录 E.3），本次只开放日常模式。

> **本节只写业务需求，不指定对外接口形态。**
> 字段名、事件名、端点路径、以及是否对标某个第三方契约（OpenAI Responses / Chat Completions / Dify 风格 / 平台自定义），一律**由研发在 design 阶段决定**，理由与备选记入 design.md。本节给出的是该接口必须满足的**业务约束与验收口径**；凡本节未约束的形态问题，PRD 不裁定。
>
> **2026-08-18 调整**：原正文直接指定「OpenAI Responses 兼容子集」，并逐字段列出映射、事件对应与拒绝清单——那是 How，越了 PRD 的界。研发反馈对标成本高；更根本的是**该契约是模型侧契约，而本能力是应用侧能力**，强行对标等于要求调用方按模型层概念（messages / role / system message / 采样参数）组织一个应用层请求。D9 / D11 相应改判，见 §7.1 与 §7.5。

**交付边界如下，三类范围互不重叠：**

| 范围 | 能力 | 本次处理 |
|---|---|---|
| **本次交付** | 发起一轮对话并取得结果、流式与非流式两种返回、多轮续接、按标识取回单轮结果、知识库与平台工具、会话附件上传 | ✅ 实现并验收 |
| **本次不做，但形态上须留出演进位** | 任务模式（灵思）、长任务异步执行、取消、断点续传 | ⏸ 调用即明确报错、不静默降级；所选形态须使这些能力将来能加进来，而不必推翻已开放部分 |
| **明确不做** | 会话列表、会话历史查询、面向同一能力的第二套并行契约 | ❌ 不提供端点、不留占位 |

> **交付依赖：本能力必须与 P1 身份传递同期上线。** 模式 S 虽能完成模型调用，但服务账号没有个人知识库，且其会话不会出现在任何自然人的工作台中；只有模式 D 才能完整满足“员工从自建系统发起对话、回到 BiSheng 继续使用”的核心场景。因此不可先交付仅支持模式 S 的版本。

#### 二、调用方必须能表达的业务入参

对外接口至少要让调用方表达下列意图。**字段名、层级与结构由研发定**，此处只约束“必须能表达什么”与“必填与否”：

| 业务入参 | 含义 | 必填 |
|---|---|---|
| **提问内容** | 本轮用户输入 | 必填 |
| **模型** | 从该执行身份在工作台可用的对话模型中按名选择 | 必填 |
| **会话标识** | 续接同一会话；首轮不传，由平台在返回中给出 | 可选（多轮时必填） |
| **知识库** | 挂载 0~N 个该执行身份有权访问的知识库 | 可选 |
| **平台工具** | 启用 0~N 个由平台侧执行的工具 | 可选 |
| **附件引用** | 引用先前经上传端点得到的附件 | 可选 |
| **返回方式** | 流式 / 非流式 | 可选；缺省值由研发定并写入对外文档 |
| **业务上下文指令** | 叠加在平台系统提示词之上的本轮指令——**只叠加，不替换、不关闭平台提示词** | 可选 |
| **调用身份** | 见 §4.3（经请求头传递，不进请求体） | 见 §4.3 |

**同样重要的是，以下东西明确不要求调用方提供**——这是本次调整的核心诉求：

- **不要求组织 messages / role 结构，也不要求自行拼装 system message。** 平台系统提示词由平台注入；调用方需要注入业务上下文（当前页面、当前工单等）时，用上表末行的“业务上下文指令”，一段文本即可。
- **不要求回传历史消息。** 多轮由服务端会话承接，调用方只传会话标识。
- **不要求理解任何平台内部概念。** 内部会话 id、消息 id、租户 id、用户 id 以及前端专用字段一律不进对外契约——内部 schema 中 9 个零消费字段的清单与“必填死字段”陷阱见附录 E.3。
- **不要求配置采样与生成参数。** 本次由平台工作台的模型配置决定。

#### 三、必须满足的业务约束（研发选形态时的硬边界）

以下八条与形态无关，任何形态都必须满足，也是验收依据：

1. **一套契约**：同一能力不并行维护第二套对外契约（D12）。
2. **不静默降级**：本次不支持的入参、工具类型与能力一律明确报错并指明出错项，绝不“接受了但不生效”。这是全节最硬的一条——让调用方以为工具或知识库已生效、实际跑的是无工具对话，比直接报错坏得多。
3. **能力与传输是两个独立维度**：「日常模式 / 任务模式」与「同步 / 异步」不得合并成同一个开关（D11，业务理由见 §7.5）。
4. **流式事件语义可分**：思考过程、回答正文、工具的调用与结果、知识库引用必须各有可区分的承载，不得退化成一条纯文本流；每次执行以且仅以一个终态收尾；非流式返回的内容与流式聚合结果一致。
5. **有状态会话**：会话与消息由平台持久化，多轮靠服务端标识续接，不靠调用方回传上下文。
6. **附件只走上传端点**：不接受内联文件数据与外链 URL——后者是一个新的出站请求面。
7. **归属与分区**：见第四小节。
8. **逐项对外文档**：随本能力交付的文档必须逐项列出已实现的入参、返回内容、事件类型、拒绝清单，以及本次未开放能力的报错形态；不得只给一句“兼容某某”的笼统说法。

对外能力与权限位如下（**端点路径与请求形态归 design**，此处只定能力边界与权限）：

| 对外能力 | 权限位 | 本次状态 |
|---|---|---|
| 发起一轮日常模式对话（流式 / 非流式） | `chat:invoke` | ✅ |
| 按标识取回单轮结果 | `chat:invoke` | ✅ |
| 上传会话附件 | `chat:invoke` | ✅ |
| 任务模式（灵思） | `chat:invoke` | ⏸ 明确报错（`26017`），随四项前置点亮 |
| 长任务异步执行 / 取消 / 断点续传 | `chat:invoke` | ⏸ 明确报错（`26015`），随异步分支点亮 |

#### 四、身份与隔离：执行权限、会话归属、外部分区分别处理

日常模式中的“人”同时影响个人知识库范围、模型与工具授权、配额、产物路径以及会话在工作台中的可见性。因此，本节按三个互不替代的维度定义规则：

| 维度 | 模式 D | 模式 S |
|---|---|---|
| **执行权限** | 以被代表用户为权限基准 | 以服务账号为权限基准 |
| **会话归属** | 归属被代表用户；该用户可在 BiSheng 工作台看到并继续对话 | 归属服务账号；不出现在任何自然人的工作台中 |
| **终端用户分区** | 由被代表用户天然分区 | 可按 `X-Bisheng-End-User` 记录外部访客分区 |

必须同时满足以下规则：

1. 按标识取回单轮结果、以及用会话标识续接时，必须校验归属；模式 S 携带的外部标识不匹配时返回 **404 而非 403**，避免泄漏该结果是否存在。
2. 模式 S 未传 `X-Bisheng-End-User` 时沿用 §4.3.4：记录 WARN，但不阻断。本次没有按用户列举会话的端点，不具备“共享身份 + 可列举会话”同时成立的串档条件，因此不恢复已废止的 `26014`。
3. 本次仍须把外部标识写入会话分区键。该字段当前**只写不读**：端点不会按它查询，但提前双写可避免未来开放终端用户会话查询时无法区分存量数据。字段与 DAO 落点见附录 E.3。

#### 五、契约形态：PRD 不裁定，但留两条不可被形态推翻的边界

- **OpenAI 形态的对外面平台已经有了，不必在本面重复投资。** `model:invoke` 的模型协议面就是 Chat Completions 形态，专门承接“拿通用 OpenAI 客户端直连”的诉求；既有 `POST /api/v2/assistant/chat/completions` 也维持 Chat Completions 形态不动。本面若再对标一次 OpenAI，是同一诉求的第二次投资。对外文档须说明三者各自的适用范围。
- **本次明确权衡掉的东西：不再把“官方 OpenAI SDK 可直连日常模式会话”列为产品需求。** 原 v2.1 / v2.2 以此作为选型的决定性理由，现判定其价值低于代价——为兑现它要拒绝的东西已经太多（采样参数、客户端 `function` 工具、消息历史、`store` 语义、内联与外链文件、完整资源族），**SDK 能反序列化 ≠ 调用方能按 OpenAI 的习惯用法使用**，“形似神不似”反而制造预期落差。若研发在 design 阶段仍选择 OpenAI 形态，这是被允许的技术选择，但它**不再是产品承诺**，也不进对外宣传口径（附录 F）。

#### 六、后续演进：任务模式与异步执行，须先完成四项前置

任务模式与长任务异步执行本次都必须明确拒绝——前者返回 `400 / 26017`，后者返回 `400 / 26015`，**两者均不得静默降级**：异步若静默按同步执行，调用方会误以为长任务已异步提交、实际却在同步链路上超时；任务模式若静默退化为日常模式，调用方会以为跑的是灵思、拿到的却是普通对话。两个码必须分开，否则客户无法区分“能力未开放”与“异步未开放”，提出的诉求也就落不到正确的路线图上。

任务模式开放前须完成四项前置，且四项缺一不可：

1. **异步作业语义**：任务实测最长可达 56 分钟，须由独立 worker 持续执行并提供可靠状态。
2. **可重放事件流**：现有 Redis List 由 `BLPOP` 破坏性消费，平台前端与外部调用方会争抢消息；须改为支持多消费者与断点续传的持久事件序列（取证见附录 E.3）。
3. **后端统一编排**：现有 submit(SSE) → start-execute → WebSocket → 取产物四步由前端串联，并可能被 `ask_user` 中断；须把流程控制收回后端。
4. **并发准入与限流**：worker 为全租户共享固定进程池，外部请求可挤占平台用户任务；开放前必须建立限流与配额能力（§4.8.2）。

此外，任务模式有两项平台语义在选形态时就要考虑进去：一是 `ask_user` 唤醒的是同一个任务，对外需要一个“任务已暂停、等待人工输入”的可表达状态（同类产品的做法可参考：Dify 的 `workflow_paused` + `human_input_required` 就是这个位置）；二是灵思产物位于 MinIO，需要一种能返回下载入口的产物承载形式。**这两项是评估契约形态时的必考项**——一个表达不了它们的形态，会在任务模式点亮时被迫返工。

**演进要求**：完成上述前置后，点亮任务模式与异步执行**不得推翻本次已开放的日常模式契约**，调用方已写好的日常模式集成不需要改代码。这是对形态选择的约束，不是对某个具体字段的承诺。

## 4.7 R6 · 管理界面

**管理后台只新增一个入口：服务账号。** 密钥与资源授权都是服务账号的下级内容，不单独开菜单——服务账号的密钥只在这里签发，授权也只在主体侧进行（§4.7.4），两者脱离服务账号都不成立。

> **个人访问令牌不在本节。** 它的签发面在员工自己的个人中心（§4.10.5），管理员侧只有一张只读台账 + 强制吊销（§4.10.6 闸门二）——**与本节的服务账号模块不共用界面、不共用入口、互不可见**。

```
系统管理
└── 服务账号                     ← 唯一新增菜单项
    ├── 列表页 ─── 新建
    └── 详情页
        ├── 概览        基本信息 · 启停 · 删除          §4.7.2
        ├── API 密钥    签发 · 编辑 · 撤销              §4.7.3
        └── 资源授权    授予 · 撤销                     §4.7.4
```

**本模块（服务账号）仅管理员可见可操作**（租户管理员及以上），没有面向普通用户的自助入口。

> 这一句的适用范围是**服务账号模块**。个人访问令牌有独立的自助面（§4.10.5），两者不共用界面、不共用入口，也不互相可见：员工在个人中心只看得到自己的 PAT，管理员在服务账号模块看不到任何 PAT（PAT 的管理员台账是另一块，§4.10.6）。

> **与应用工场分册的整合（2026-08-15 决议，2026-08-17 清理残留）**：应用工场的本地开发工具包能力就是 §4.2.4 权限位清单上的新增三位，**不另立密钥类型、不另立签发界面**——本模块即其承载页，§4.7.3 签发表单的权限位分组多出「本地开发工具包」一组（三个扩展位，与 `delegate` 互斥），详情页「API 密钥」标签页顶部多一个接入信息区（MCP 地址 / OpenAI 兼容 base URL / CLI 下载链接 / login 指引，一键复制、不含 key 值）；服务账号的**资源归属人**已是 §4.5 定义 6 正文概念、非分册增量；应用运行期凭据由平台随发布自动签发与回收、**不设管理界面**（PRD-1 GOV-08）。见《3.0 应用工场 PRD-1》DEV-01 / GOV-08。本节其余设计不变；仅部署标准版（无应用工场）时按本节原样交付——服务账号模块本身不受应用工场部署开关影响。

**新建表单三个字段：名称、描述、资源归属人。** 归属人必填，从自然人中选择（服务账号自身不出现在该选人框，定义 5），决定这个服务账号经 API 创建的资源归谁——语义与边界见 §4.5 定义 6，表单需一句话说明「该集成创建出的知识库等资源将归属此人，由其在平台内管理」。租户取当前管理员所在租户，不提供选择——创建后不可更换（D7）。

#### 编辑与撤销

- **编辑**可改名称、权限位、委托配置、过期时间，**无需轮换密钥**，改完即时生效；**编辑受与签发相同的互斥校验**（`delegate` ⊗ 扩展位），不得靠「先签发后编辑」绕过
- **撤销**二次确认，撤销后记录保留用于审计；列表页顶部提供**"撤销该账号全部密钥"**，用于泄漏应急

### 4.7.4 服务账号授权（主体侧）

R4 定义 2「权限单独授予」落在这里。

#### 唯一入口：服务账号详情页

| 项 | 决策 |
|---|---|
| 入口 | 服务账号管理 → 某服务账号 → **资源授权** 标签页 |
| 唯一性 | 这是给服务账号授权的**唯一**入口；服务账号不出现在任何资源侧的授权选人框中 |
| 操作权限 | 查看与变更均**仅管理员**（租户管理员及以上），与本模块其余部分一致 |

**为什么不复用资源侧的权限弹窗**：那里的操作者是资源所有者，普通用户即可操作。若服务账号能在那里被选中，任何资源所有者都可以单方面扩大某把密钥的数据边界，而管理员无从感知。集成的权限边界必须由管理员集中收敛——这正是选择服务账号而非自然人账号作为密钥主体的初衷（§4.2.2）。

> **一处例外是读不是写**：资源侧的「已授权对象列表」仍需能**显示**已获授权的服务账号，否则资源所有者会看到一个查不到的主体。**可显示、不可选择。**

#### 页面内容

本页**只有一个列表**：该服务账号当前持有的全部资源授权。**不设"名下资源"分组**——资源归属人（§4.5 定义 6）让服务账号不再拥有任何资源，那个分组结构性恒为空。

每条授权带一列**来源**，两种取值处置不同：

| 来源 | 怎么来的 | 撤销 |
|---|---|---|
| **管理员授予** | 管理员在本页显式授予 | 可撤，含"全部撤销"快捷操作 |
| **创建时自动回授** | 该服务账号经 API 创建资源时，平台自动回授给它的可编辑权限（§4.5 定义 6 边界 b） | 可单条撤销，但需二次确认并明示**"撤销后该集成将无法再写入这个资源"**；**不进"全部撤销"的作用范围** |

> **"全部撤销"必须排除自动回授项**，否则管理员一次点击就会切断集成对自己维护的知识库的写入——而界面上这条授权看起来和管理员手动授予的毫无区别。这是资源归属人机制引入的唯一新增操作风险，须在实现与测试中显式覆盖（AC-47）。

授予时可选的权限档位（如知识库的可见 / 可编辑 / 可管理）由平台既有的权限模型提供，页面不自行定义。

**页面必须让另一层可见。** 权限判定是两层"与"关系（§4.4.1），本页只管第二层——主体对具体资源的权限。若不把第一层（密钥权限位）一并呈现，管理员必然遇到"这里明明授权了，调用还是失败"的困惑。因此页面顶部展示该服务账号名下的密钥数与各自的权限位，并对"本页已授权、但名下没有任何密钥持有对应权限位"的资源给出提示——这类资源等于配了个寂寞。

**委托生效时本页授权不参与判定。** 模式 D 是纯替换而非取交集（§7.2）——权限基准整个换成被代表用户，服务账号自身的资源授权此刻完全不参与。因此一把开启了委托的密钥，即使其服务账号在本页零授权，仍可读到被代表用户能读的全部内容。这是设计意图，但极易被误读为"本页授权是全局上限"，**页面在检测到名下存在持有 `delegate` 的密钥时必须显著提示**。

#### 生命周期

| 动作 | 授权如何处理 |
|---|---|
| **停用**（推荐的常规下线方式） | 授权全部保留；密钥鉴权直接拒绝。恢复后原样生效 |
| **删除** | 二次确认：列出该账号当前持有的全部资源授权（含自动回授项），明示删除后这些授权一并失效、依赖它的集成将立即失败。**确认即可删除，不阻断** |

> **删除为什么不再需要硬阻断**：资源归属人（§4.5 定义 6）让服务账号不拥有任何资源——删掉它只是让若干条授权消失，**不会产生任何孤儿资源**。原先的阻断（`26013`）是为了防止"删了账号、资源没人管"，这个前提已经不存在，硬拦只剩下让管理员多跑一趟的成本。风险从"资源失管"变成了"集成失效"，而后者是删除动作的应有之义，用清单 + 二次确认告知即可。
>
> 连带地，本特性**对 F018（资源归属转移）零依赖**：既不需要它做迁移兜底（§4.9 不做任何平台侧迁移），新账号也不会积累名下资源。取证见**附录 E.4**。

#### 审计

本页每次授予 / 变更 / 撤销记录：操作管理员、目标服务账号、资源类型与 ID、权限档位的变更前后值、时间。与 §4.8.1 的调用审计是两条不同的流水——一条记"谁改了边界"，一条记"谁用这个边界调了什么"。

**实现约束**（反查方式、写路径复用、服务账号不得加入用户组或部门的原因）见**附录 E.4**。

## 4.8 R7/R8 · 审计、限流与幂等

### 4.8.1 审计

每次开放 API 调用记录：时间、密钥 ID、主体、身份模式、被代表用户（模式 D）、外部标识（模式 S 传了 End-User 头时）、端点、来源 IP、结果状态、耗时。

**双归属是硬要求**：审计必须能同时回答"哪个系统调的"和"以谁的名义调的"。

### 4.8.2 限流与配额（P2）

按**密钥**维度限流与计量（不按外部标识，理由见 §4.3.4）。超限返回 429。

> ⚠️ **成本提示**：平台**没有任何 HTTP 层限流基础设施**，最接近的可复用原语在 Redis 故障时 fail-open，对鉴权场景语义不合适、需改写。**P2 估算时不可按"接个现成库"计**（取证见附录 E.5）。

### 4.8.3 幂等性（P2）

`POST /api/v2/workflow/invoke` 等有副作用的端点支持 `Idempotency-Key` 请求头，重复提交返回首次结果。这是企业集成的标准需求——网络重试不应导致工作流重复执行。

## 4.9 R9 · 升级须知（平台侧不做任何迁移）

**本版本发布即带鉴权，不设兼容开关。** 升级后所有 `/api/v2` 调用必须携带密钥，无密钥一律 401。

这是一次**明确的破坏性变更**，理由是：本特性修的是一条匿名超管越权通道（§2.2），而任何"默认关闭"的过渡开关都意味着升级后洞依然敞着——只有主动去翻开关的客户才受保护。默认不安全的开关，恰恰是本方案在别处反复否决的模式。

**平台侧不提供任何自动迁移**：不写转型脚本，不改动任何存量用户与资源。升级完成后，由管理员在界面上手动创建服务账号并完成配置——这是本特性唯一的接入方式。

### 升级后管理员必须完成的三步

发布说明须以显著位置给出，并在升级前的沟通中直接交付：

| 步骤 | 动作 |
|---|---|
| 1 | 在界面上为每个集成创建服务账号（指定资源归属人，§4.5 定义 6），按最小必要授予其所需资源（§4.7.4） |
| 2 | 为该服务账号签发密钥，按需勾选权限位；若集成需要代表平台用户，另配委托范围（§4.7.3） |
| 3 | 改造调用方代码：加 `Authorization: Bearer` 请求头；原先在请求参数里传 `user_id` 的调用改为 `X-Bisheng-On-Behalf-Of` 请求头 |

**裸 `user_id` 参数随本版本一并移除**，不保留过渡期——它本身就是缺口的一部分（§2.2 F4），留着等于把洞留到下个版本。

> **存在一个接入空窗**：从升级重启完成，到管理员配好密钥、调用方改完代码为止，全部存量集成处于中断状态。这是不设兼容开关的必然结果（D1），须在升级沟通中说明，由客户安排窗口期。

### 原"默认操作员"怎么办：什么都不做

全端点强制鉴权后，那个兜底身份永远不会再被取用。因此：

| 项 | 处理 |
|---|---|
| **配置项 `default_operator`** | **废弃并从配置中移除**，相关取用代码一并删除。留着是一个不再生效的死配置，会误导运维以为还有兜底身份可依赖 |
| **它指向的那个用户** | **不动**——保持普通用户身份不变，名下存量资源的归属与可见性零变化。它本就是个真人账号（多数客户按旧文档配成了超级管理员），资源本来就有人管，无须也不应由本特性代为处置 |
| **移除 `enable_guest_access`** | 该配置项默认 `true`，只守 3 个端点、其余 41 个不受影响（详见附录 B）。全端点强制鉴权后它失去意义，留着只会让人误以为存在一个"V2 总开关" |
| **文档修订** | 现有接口文档中"网络层负责访问控制""建议配置超级管理员"两处表述必须删除——它们是错误引导 |

> **不做迁移换来两处简化**：一是本特性不再需要转型脚本与资源转移逻辑；二是**对 F018（资源归属转移）的依赖彻底解除**——既不需要它做兜底转移，新建的服务账号又因为资源归属人（§4.5 定义 6）而不会积累名下资源。F018 此后只与"客户自己想清理某个历史账号"有关，与本特性无关（原取证见附录 E.4）。

## 4.10 R10 · 个人访问令牌

服务于 §3.5 场景四。本节只写它与服务账号密钥**不同**的部分——相同的部分（哈希存储、只显示一次、软撤销、5 秒撤销上界、租户隔离、泄漏应急）在 §4.2.5–4.2.6 已经写过，两类主体共用，不重复。

### 4.10.1 定位：新的**主体类型**，不是新的身份模式

身份模式的判据是**权限基准是谁**（§4.3）。个人访问令牌的权限基准是密钥主体本身——与模式 S 完全一致，只是主体从服务账号换成了一个自然人。

> **因此它不新增身份模式，而是给模式 S 增加了第二类主体。**
> §4.3.1 的请求处理流程**一个分支都不改**：提取密钥 → 校验 → 权限位 → 无 `On-Behalf-Of` → 模式 S。

这条判断决定了工程量的量级，也决定了 §1.1 第二层机制的措辞——从「密钥必绑服务账号」放宽为「密钥必绑主体」，层的含义（密钥不能无主、权限边界随主体收敛）没有变，只是主体不再只有一类。

**它永久不得持 `delegate`。** 允许员工代表别人，等于把横向提权做成产品功能。这是结构性禁令，不是本期范围取舍：`delegate` 对自然人主体在**签发期与运行期双向拒绝**。

### 4.10.2 与服务账号密钥的差异（只有五处）

| 项 | 服务账号密钥 `bs-sak-` | 个人访问令牌 `bs-pat-` |
|---|---|---|
| 主体 | 服务账号（不可登录） | **一个自然人**，即签发者本人 |
| 权限来源 | 服务账号被显式授予 | **持有人当前的权限，动态继承**（§4.10.3） |
| 签发者 | 管理员 | **持有人本人**，无需审批 |
| 有效期 | 可长期有效 | **必填，且有上限**（§4.10.4） |
| 生命周期 | 与人事解耦 | **与持有人绑定，级联失效**（§4.10.4） |

第 2 行与第 5 行，正是 §4.2.2 当初否决"把权限挂在自然人账号上"的两条理由。**它们在场景四里不是缺陷，而是需求本身**——展开见 §7.6。

### 4.10.3 权限：动态继承 + 只读白名单

**动态继承，不做快照。** 每次调用按持有人**当时**的权限判定。理由是两条：权限快照会在授权撤销后继续放行已经不该放行的访问，是一条静默的越权通道；而平台的权限判定本来就是按调用者实时算的，**不做快照反而是更少的代码**。

> **行业同构（一手原文）**：GitHub 对个人访问令牌的官方表述是「令牌拥有的资源访问能力**与其所有者相同**，并进一步受令牌自身 scope 的限制」，且给了反例——「令牌**不能**为用户带来额外的访问能力：一把配了 `admin:org` 的令牌，如果所有者不是组织所有者，就不会给出组织管理权限」[S14]。这与本节的公式是同一件事：**令牌权限 = 权限位 ∩ 持有人权限，且以持有人权限为上界。**

**双层收敛，与 §4.4.1 的两层判定同构**：

```
可访问范围 = 密钥权限位（能做哪类动作） ∩ 持有人的资源权限（能碰哪些数据）
```

**本期只能被授予 `knowledge:read` 一个位。** 判据不是"风险量级"，而是三条：

1. **场景只需要它**——检索与知识空间清单查询都在这个位下
2. **写权限的爆炸半径不可控**——密钥落在第三方 SaaS 里，一旦泄漏，攻击者可以往知识库投毒，而投毒的内容会被平台内所有检索到它的人当成可信资料
3. **`identity:read` 授予即全租户组织架构可读**（§4.2.4 已标为高危位），平台没有任何机制能把它收窄到组织树的一部分——它绝不能出现在一把员工自助签出来的密钥上

`workflow:*` / `assistant:*` / `chat:invoke` / 三个扩展位 / `delegate` 一律不在可选清单中。后续放开哪个位，判据同样是"**有没有只需要它的真实消费者**"，不是"看起来风险不大"。

#### 管理员持有的令牌**不享受管理员短路**（D17）

平台只有两个 allow-all 短路：`super_admin` 与 `tenant_admin`（取证见附录 E.5）。一名管理员在平台界面里能看见本租户的全部知识，靠的正是这条短路。

**如果他的令牌继承这条短路，那把放在第三方 SaaS 里的密钥就等于全租户知识的读取权。** 这是场景四里爆炸半径最大的一种密钥，而它恰恰最容易被签出来——管理员也是员工，也想用办公助手。

**规则：个人访问令牌执行时按普通用户判定，管理员短路不生效。**

判据是"**管理权限不是业务权限**"：短路的用途是让管理员**管理平台**，不是让他把全租户数据导出到外部工具。管理员要看某个知识空间的内容，正常路径是在平台里看，不是通过一把常驻在办公助手里的密钥。

> **实现上这是结构性的，不是一个可以配错的开关。** 服务账号那一侧已经确立了同样的做法——身份在校验路径里被直接构造，而不走登录用户的构造函数，让"服务账号永远不是超管"成为结构事实而非数据状态（附录 E.1 校验流程第 9 步）。自然人主体沿用同一条路径：构造时不带管理员标志位。

**但这条不能静默。** 对管理员而言，令牌检索到的结果会**少于**他在平台界面看到的，而"返回 200 + 静默缩水的结果"正是 §7.2 否决权限取交集时立的那条红线。因此：**签发表单在持有人是管理员时必须显式提示，密钥详情页常驻同一提示**（AC-P17）。

### 4.10.4 生命周期：必填过期 + 级联失效

**过期时间必填，且受上限约束。** 服务账号密钥可以长期有效，因为生产集成不能因为过期而中断；个人访问令牌相反——它跟着人走，而人会离职、换岗、把密钥忘在某个 SaaS 的配置页里。**密钥在无人记得的情况下长期有效，是场景四最现实的风险。**

**级联失效，且不依赖任何人记得操作。** 以下事件发生时，该持有人名下全部令牌立即失效：

| 事件 | 撤销原因 |
|---|---|
| 用户被禁用 | `subject_disabled` |
| 用户被删除 | `subject_deleted` |
| 用户离开当前租户 / 租户变更 | `subject_disabled` |

> 这三个撤销原因、按主体批量撤销的服务方法、以及对应的审计事件类型，**在服务账号那一侧都已经存在**（落点见附录 E.1）。落地的关键不是新增字段，而是**在用户禁用 / 删除 / 换租户三条路径上补触发点**，并**在校验期二次兜底**——只靠写入端触发，漏一条就是一把永不失效的密钥。

> ⚠️ **这条必须自建，不能指望"业界都这么做"。** 行业调研的结论与直觉相反：
>
> - **只有 Slack 有明文的随人级联**——「成员账号被停用时，其 API token 一并被吊销，该成员授予的用户级权限失效」；且该级联**只覆盖 user token**，bot token / slash command / incoming webhook 在成员停用后仍然活跃 [S16]
> - **GitHub 明确不做追溯吊销**：组织收紧令牌策略时「**不会撤销也不会禁用**这些令牌」，用户是通过 API 调用被拒才知道自己的令牌不合规了 [S14]
>
> 也就是说，「离职即失效」在多数产品里**不是白送的**。BiSheng 要兑现 §3.5 需求 3（"不依赖任何人记得去吊销"），必须显式实现触发点 + 校验期二次判定，并且**任何鉴权缓存都必须短 TTL + 主动失效**（本平台已有 5 秒上界这条既定约束，正好承接）。

**撤销的 5 秒上界同样适用**（AC-3）。

### 4.10.5 自助签发：个人中心

**入口在员工自己的账号面，不在管理后台。** 走审批就等于没做——场景四的全部价值是员工不必打扰管理员。

页面只需要四件事：

1. **签发**：填名称 + 选有效期（上限内），确认后**一次性展示明文**，此后只见掩码
2. **列表**：自己名下全部令牌的名称、掩码、创建时间、最后使用时间、有效期
3. **吊销**：单个吊销 + 一键吊销全部（泄漏应急）
4. **接入说明**：可直接复制的调用示例（端点、请求头、一个最小请求体），以及"填到哪里"的指引

> 第 4 项不是文档工作的附属品，而是这个功能能否被用起来的决定因素。**员工拿到一串密钥而不知道下一步做什么，功能等于没交付。**

**员工只看得到自己的令牌**，看不到任何其他人的；管理员在服务账号模块也看不到任何个人令牌——管理员侧是另一块（§4.10.6）。

### 4.10.6 治理：三道闸门

场景四是本 PRD 里第一条把企业知识送出组织控制边界的通道（§3.5），因此治理不是可选项。

**闸门一 · 能力开关，默认关闭。**
"是否允许员工自助签发个人密钥"是一条**策略**决定，必须由管理员显式打开。默认关闭的理由是升级语义：**一次版本升级不应该静默地打开一条新的数据出口。** 开关的层级（部署级 / 租户级）见 D15。

**闸门二 · 管理员台账与强制吊销。**
管理员能看到本租户全部个人令牌的**元数据**（持有人、名称、掩码、创建时间、最后使用时间、有效期、权限位），并可单个或按人批量强制吊销。看不到明文——**明文不存在**（§4.2.5）。这一面服务三个真实流程：离职交接、泄漏应急、合规审计。

> **这是三家独立厂商收敛出的范式，不是我们的发明**：Atlassian 的 Insights → API token activity（**任意套餐可用**，管理员可见"有多少把活跃令牌、何时创建、何时过期、最后一次使用时间"，支持单条与批量吊销）[S17]、GitHub 的组织 Active tokens 列表（可枚举并吊销所有能访问本组织的令牌）[S14]、GitLab 的 Credentials inventory（Ultimate 版）[S15]。三家的共同形状都是**先看得见、再点吊销**。

**闸门三 · 审计归因。**
个人令牌调用的审计记录必须能区分"这次检索是本人在平台界面里做的"还是"某个外部 Agent 拉的"。沿用 §4.4.5 的双归属形态：**actor = 具体那把密钥，subject = 持有人**。只记 subject，会让员工的正常使用与一个失控的自动化脚本在审计里长得一模一样。

#### 两条从行业教训里直接抄来的硬规则

**规则一 · 不留第二类不受治理的令牌形态。**
GitHub 的逐把审批与组织令牌台账**只覆盖新一代 fine-grained 令牌**，老一代 classic 令牌完全不受审批约束、且只有在组织启用 SSO 时才可见可吊销 [S14]。结果是治理闸门旁边永远有一条绕行道。**BiSheng 只有一套凭据底座，本来就没有这个问题——但这条要写下来，防止将来"为某个场景再开一种令牌"。**

**规则二 · 治理开关按主体类型分别挂，不共用。**
GitLab 的服务账号凭据**本身就是 PAT**，却被**显式排除**在"关闭企业用户 PAT"这条组织策略之外，并且有独立的过期设置 [S15]。Slack 同构——user token 随人失效、bot token 不随人失效 [S16]。
> 对 BiSheng 的直接含义：**关闭个人访问令牌，绝不能连带关掉服务账号密钥**（那会直接打断所有生产集成）。共用底座、分别治理——这也正是 §4.10.2「只有五处不同」那张表的意义。

### 4.10.7 交付物：形态由目标 Agent 决定，不由我们偏好决定

调研的第一条结论是**这一节不能按"我们想给什么"来写**：两个客户点名的目标平台，接入形态要求完全不同，其中一个**根本没有给 PAT 留位置**。

| 目标平台 | 官方接入机制 | 能不能吃一把「员工自己的 PAT」 |
|---|---|---|
| **WorkBuddy**（腾讯云 CodeBuddy 家族） | 「连接器」；接外部服务**只有自定义连接器一条路**，而自定义连接器的实现形态就是**「安装自定义的 MCP 服务」**；鉴权支持 OAuth token 与**手工填入的 API key** [S18] | ✅ **能**，但**必须以 remote MCP server 交付**，OpenAPI schema 在这里不成立 |
| **钉钉连接器** | 七种鉴权并列，其中「自定义签名鉴权」可把任意 HTTP Header 表达出来（官方给了直接构造 `Authorization` 头的表达式示例） [S19] | ⚠️ **形式上能**，但凭据是**连接器级、由管理员集中托管**，没有"每个员工填自己 key"的原生位置 |
| **Coze / 扣子** | 插件；OAuth 2.0 授权码是唯一能拿到"调用者本人"的路径，智能体侧强制每个终端用户各自授权；**非 OAuth 的 Service 类型是插件级固定密钥**，配置里没有 per-user 填 key 的输入位 [S20] | ❌ **不能**。员工自助 PAT 在 Coze 上只能退化成"每人各建一个私有插件"，不是可运营的形态 |

> ⚠️ **本轮取证的是 Coze / 扣子（`docs.coze.cn`），不是「豆包工作台」本身。** 二者同属字节，但**它们的插件机制是否一致，本轮没有取证**。客户若点名的是豆包工作台，须单独核实——**不得把 Coze 的结论直接当成豆包的结论**。

#### 由此得出的三条结论

**结论一 · remote MCP server 是必做项，不是增强项。**
WorkBuddy 接外部服务**只接受 MCP**——这一条推翻了本轮调研之前「MCP 只是开放能力层部署下的可选增强」的初判。平台正在建的 MCP Server 工具面已经具备所需的全部条件——标准 MCP 协议、与开放 API 同一鉴权语义、**工具清单按密钥权限位过滤**、一律模式 S。个人令牌只能持 `knowledge:read`，因此接进去后**自动只看到「知识库检索」与「知识库清单查询」两个工具**，没有新的过滤逻辑要写。增量只有一处：**让 MCP 面接受自然人主体的凭据**（与 HTTP 面共用同一个主体解析）。

> ⚠️ 但 MCP 面受「开放能力层部署开关」管辖、默认关闭，**标准版部署没有 MCP 面**。若客户要接 WorkBuddy，**部署开放能力层是前置条件**，须在方案阶段讲清楚。

**结论二 · HTTP + `Authorization: Bearer` + 接口文档同样必做。**
钉钉连接器与绝大多数自研 Agent 走的都是这条；它也是唯一与部署形态无关、恒在的路径。内容 = 端点、请求头、一个最小可跑的请求体、"填到哪里"的说明。落点是既有对外接口文档新增一章，以及个人中心密钥页里的可复制代码块。

> **权限收敛的责任完全在我们这一侧。** WorkBuddy 文档明写「自定义连接器的**访问范围由您的配置决定**，WorkBuddy 不预设范围」[S18]——对端不会替我们兜任何底。这正是 §4.10.3 只开一个只读位、§4.10.6 三道闸门的现实理由。

**结论三 · 要接 Coze 这类平台，PAT 本身不够——那需要 OAuth 授权服务器，列为二期（D18）。**
这一条与客户的原始描述有出入，**必须回给客户确认两件事**：① 要接的到底是 Coze / 扣子，还是豆包工作台（后者本轮未取证）；② 若确为 Coze 形态，那么"发一把个人密钥"解决不了问题——其静态密钥是**插件级全局一把**，拿不到调用者本人。本期不为它提前改协议：一期做 MCP + HTTP，覆盖 WorkBuddy 与客户自研 Agent；OAuth 等 D18 决策。

> **「skill 包」不是一种接入形态。** 客户提到的"skill"若指 Agent Skills 格式的技能包，它解决的是"教 Agent 怎么用"，不是"Agent 怎么连上来"；作为面向内部开发者的补充可以有，但**不能替代 MCP 或 HTTP 这两条真正的接入路径**。

#### 文件级过滤不在本需求的工作量里

平台规划中的**统一检索门面**从设计上就接受自然人作为执行身份，且明确把 `POST /api/v2/filelib/retrieve` 收敛到同一门面。**个人令牌是这个门面的又一个消费者，不是它的第二个实现**（§4.4.6 的交付前提由该门面承接）。

> **一处必须写明的能力边界**：门面对**知识空间**按文件级过滤，对**文档知识库**按**库级**过滤——因为平台没有文档知识库的文件级权限模型。这不是缺口，是模型如此；但**对外措辞不能笼统说"按文件级权限过滤"**（进附录 F）。

#### ⚠️ 两条取证限制，落地前须复核

1. **「WorkBuddy」存在同名歧义**——除腾讯云 CodeBuddy 家族的 workbuddy.cn 外，另有非腾讯的同名现场服务 SaaS。**须与客户确认指的是哪一个**；本节全部结论只对 workbuddy.cn 成立。
2. 该条证据在调研中**未完成对抗性复核**（检索配额耗尽）。结论一的份量足够大，**建议在立项前用浏览器实地复核一次连接器文档**。

# 五、验收标准

## R1 · 凭据体系

- **AC-1**　无密钥调用任意开放 API 端点返回 401，**无任何回落路径**。
- **AC-2**　密钥明文在创建后无法通过任何接口再次获取。
- **AC-3**　撤销密钥后，后续调用在 5 秒内失效。
- **AC-4**　密钥缺少对应权限位时返回 403，错误信息指明缺少哪一位。
- **AC-5**　跨租户查询密钥列表返回空——验证租户自动过滤已生效（含模块注册）。
- **AC-48**　`delegate` 与「本地开发工具包」三个扩展位**无法同时保存**——签发与编辑表单均校验并给出可读提示（**硬阻断，非软提示**；§4.2.4 / §4.7.3）。
- **AC-49**　持 `delegate` 的密钥调用本地开发三面（MCP 工具、模型协议面、CLI `login`）**一律被拒**，错误信息指向「委托专用、本地开发另签一把」；**且不得表现为按服务账号身份正常执行**（验证没有静默落到模式 S），也不得只返回 `26016` 这类参数错误（附录 B.2）。

## R2 / R3 · 身份模式与受限委托

- **AC-6**　未授予 `delegate` 的密钥传入 `X-Bisheng-On-Behalf-Of` 返回 403。
- **AC-7**　**窄权限密钥 + `delegate` 指定超级管理员或租户管理员 user_id，返回 403（错误码 26007）**——特权主体禁令生效。
- **AC-8**　委托目标为不存在/已禁用/跨租户用户时返回 403，且不泄露该用户是否存在的差异化信息。
- **AC-9**　委托范围配置为某部门时，该部门子树内用户放行、子树外用户 403；范围为空时任何目标一律 403。
- **AC-41**　委托目标为服务账号时返回 403，**且响应与 AC-8 完全一致**——不因目标类型给出差异化信息，避免被用来探测哪些 user_id 是服务账号。**须覆盖"委托范围配的是部门、而该服务账号恰在该部门子树内"这一用例**，它正是保存期校验够不到的路径（§4.4.4 检查 2）。
- **AC-37**　保存委托范围的 `user` 条目时传入服务账号的 user_id 被拒绝——**绕过选人框直接调接口同样拒绝**（§4.4.4）。这是早报错；安全防线是 AC-41。
- **AC-38**　持有 `delegate` 的密钥漏传 `X-Bisheng-On-Behalf-Of` 时返回 400（`26016`），**不返回任何业务数据**——既不返回全量，也不返回公开子集，也不静默落到模式 S 按服务账号权限执行（铁律 2）。
- **AC-10**　同时传入 `X-Bisheng-On-Behalf-Of` 与 `X-Bisheng-End-User` 返回 400（`26010`）。
- **AC-11**　传入任意 `X-Bisheng-End-User`，返回结果的**权限范围与不传时完全一致**（仅会话分区与审计留痕不同）——这条同时是"它不是一种身份模式"的验收依据。
- **AC-12**　模式 D 下以张三身份检索，返回结果与张三在平台内自行检索的结果**集合相等**（验证纯替换，无意外收窄）。
- **AC-13**　权限引擎不可用时，检索接口返回 5xx 且不返回任何结果（铁律 3）。

## R4 · 服务账号主体

- **AC-14**　服务账号无法通过任何登录入口获得会话——需覆盖全部 10 个入口的测试矩阵。
- **AC-15**　服务账号**不出现在** `/api/v1/user/list` 的任何消费点（用户管理、审批人选择、部门加成员、用户组加成员、创建租户选管理员、资源授权选人），且资源侧的「已授权对象列表」仍能正确**显示**已获授权的服务账号。
- **AC-16**　租户对账任务执行后，服务账号的租户归属不被改写。
- **AC-17**　服务账号不计入租户用户数配额。
- **AC-42**　模式 S 下经 API 创建知识库，该知识库在**资源归属人**的平台界面中可见可管理，如同其本人创建；同时该服务账号仍可继续向其写入文档（定义 6 边界 b）。
- **AC-43**　模式 S 下产生的会话**不出现在**资源归属人的会话列表中（定义 6 边界 a）——防止把 §3.3 的会话串档缺陷以新机制引回。
- **AC-44**　资源归属人本人对某资源的权限，不影响该服务账号能读写什么：把归属人加进/移出某知识库的授权，服务账号经 API 的可见范围不变（定义 6 边界 c，定义 2 不被动摇）。
- **AC-45**　更换服务账号的资源归属人后，此前已创建的资源归属不变，此后创建的归新归属人（定义 6 边界 d）。
- **AC-46**　模式 D 下创建的资源归属**被代表用户**，而非资源归属人（定义 6 优先级规则）。

## R5 · 端点接入

- **AC-18**　两个 WebSocket 端点在握手阶段校验密钥，无效密钥握手失败且优雅关闭。
- **AC-19**　调用未上线的工作流返回业务错误，而非正常执行。
- **AC-20**　停止不属于当前密钥主体的会话返回 403。

- ~~**AC-33**~~　（原验收「模式 S 调会话列表须带 `X-Bisheng-End-User`」，随会话列表端点与 `26014` 一并移出本次范围，2026-08-16；编号留空不复用，避免与既有引用错位）

- **AC-22**　按主体批量撤销后，该主体名下全部密钥在 5 秒内失效。

- **AC-28**　服务账号授权页列出的资源集合，与该主体在 `permission_grant_assignee` 中 `state='ACTIVE'` 的记录**一一对应**；每条标注来源（管理员授予 / 创建时自动回授）。**该主体不应存在任何 `source_type='CREATOR'` 的记录**——资源创建关系落在资源归属人身上（§4.5 定义 6），出现即为缺陷。

## R10 · 个人访问令牌

- **AC-P1**　能力开关关闭时，自助签发端点返回 403；开关从开到关后，**已签发的令牌在 5 秒内不可用**。
- **AC-P2**　签发不传有效期返回参数错误；超过上限同样拒绝。
- **AC-P3**　签发响应返回一次明文；此后**任何**接口（本人列表、管理员台账、审计记录）都只返回掩码。
- **AC-P4**　只可勾 `knowledge:read`；携带任何其它权限位返回参数错误；携带 `delegate` 时错误文案明示「个人密钥不支持委托」。
- **AC-P5**　同一查询、同一组知识空间下，令牌检索结果与持有人在平台界面自行检索**集合相等**——不多不少。
- **AC-P6**　请求里出现持有人无权访问的知识空间标识时，该标识无结果，且响应**不泄露该空间是否存在**。
- **AC-P7**　持有人无权访问的**文件**不出现在结果中——**文件名与正文片段均不出现**。
- **AC-P8**　持有人被禁用后，其名下全部令牌在 5 秒内失效，撤销原因为 `subject_disabled`。
- **AC-P9**　持有人被删除或离开当前租户后同上，撤销原因分别为 `subject_deleted` / `subject_disabled`。
- **AC-P10**　持有人只能查看与管理自己名下的令牌，看不到任何其他人的。
- **AC-P11**　管理员可查看本租户全部个人令牌的元数据并强制吊销，吊销 5 秒内生效。
- **AC-P12**　管理员台账不返回明文，也不返回任何可还原明文的字段。
- **AC-P13**　令牌调用的审计记录中 **actor = 那把密钥、subject = 持有人**，两者均可作为查询维度。
- **AC-P14**　令牌打白名单外的端点（如创建知识资源）返回权限不足。
- **AC-P15**　令牌携带 `X-Bisheng-On-Behalf-Of` 被拒绝，**不静默忽略该头**。
- **AC-P16**　A 租户的令牌查不到 B 租户任何数据；跨租户列令牌返回空。
- **AC-P17**　**管理员持有的令牌不享受管理员短路**：以租户管理员的令牌检索一个未显式授权给他的知识空间 → 无结果；且签发表单与详情页对该持有人显示专门提示（**不得静默缩水**）。

> **AC-P5 与 AC-P7 是这个功能"可不可信"的两条线：多一条是越权，少一条是功能不可用。**
> 二者都必须双向验证——正例验集合相等，反例验不出现。

# 六、非目标

明确不在本次范围内，避免范围蔓延：

- ❌ **个人访问令牌本期只开 `knowledge:read` 一个权限位**——原「不实现个人访问令牌」已于 2026-08-27 随场景四改判为交付（§7.6 D13）。留在非目标里的是它的**范围**：`workflow:*` / `assistant:*` / `chat:invoke` 与三个扩展位本期不对自然人主体开放；而 **`identity:read` 与 `delegate` 对自然人主体是永久禁令，不是本期取舍**——前者授予即全租户组织架构可读且平台没有任何收窄机制，后者等于把横向提权做成产品功能
- ❌ **不实现密钥级的资源白名单**（"这把密钥只能碰知识库 A/B"）——它会在 §4.4.1 的两层判定之上叠出第三层，而三层"与"关系既难配对也难向客户解释。它唯一的增量价值是"同一服务账号签多把密钥、各自再收窄"，而这个诉求用**一个集成建一个服务账号**即可满足，且边界更清晰、审计更干净。行业对照中 FastGPT [S3]、n8n [S4]、LangSmith [S6] 的密钥均无资源级白名单
- ❌ **不实现完整 OAuth 2.0 授权服务器**（授权码流、刷新令牌、同意页）
- ❌ **不实现最终用户令牌透传**（附录 A.4 的 C 档）——要求最终用户在平台有身份，对场景三不适用
- ❌ **不做即时建号**——模式 D 的目标用户必须预先存在
- ❌ **不改造 `/api/v1` 前端接口的鉴权方式**
- ❌ **不实现按端点的细粒度权限**——权限位到**模块 + 动作级**（read / write / invoke）即止，不做到单个端点
- ❌ **不为日常模式会话交付第二套并行契约**（如 Chat Completions 薄兼容层）——薄层承载不了平台工具与知识库引用，即日常模式相对裸模型的全部增量价值；交付一个功能残缺的第二契约只会让客户在"能力不全"与"再学一套"之间二选一，平台还要长期维护两套映射。想拿通用 OpenAI 客户端直连的诉求由 `model:invoke` 模型协议面承接。出现真实场景再单独立项（D12）
- ❌ **不承诺"官方 OpenAI SDK 可直连日常模式会话"**——2026-08-18 随 D9 改判取消，理由见 §7.5；OpenAI 形态的对外面由 `model:invoke` 模型协议面与既有 `POST /api/v2/assistant/chat/completions` 承接。若研发在 design 阶段仍选 OpenAI 形态，属技术选择，不构成对外承诺或宣传口径
- ❌ **不实现 Webhook 回调方向的鉴权**（平台如何向客户系统证明自己）——如客户有此需求，作为 P2 独立评估

## 7.2 D2 · 为什么不采用"权限取交集"

1. **无法实现**：权限引擎的 ListObjects 通道被显式禁用（`permission/application/sql_runtime.py:638-648` 装配 `DenyListObjectsPolicy`，注释为"待性能基线评审通过前保持关闭"），无法列出两个主体的可见集求交。
2. **成本不可接受**：单次鉴权约等于 1~2 次权限引擎往返 + 3~4 次数据库查询 + 2~4 次缓存读取，且主链路**无缓存**。知识库检索的批量预过滤（`knowledge/domain/services/knowledge_file_visibility_service.py:120-198`，阈值 5000 文件）若翻倍，将直接落在对话首字延迟上。
3. **创建场景语义无法定义**：创建类操作根本不做资源级权限前置检查（`knowledge/domain/services/knowledge_space_service.py:1035`，门槛只有配额与模型可用性）。"密钥主体的创建权限"在权限模型里**不存在可供求交的对象**，取交集在「以张三名义创建知识库」这一核心需求上无从落地。
4. **语义悖论，且击穿核心需求**：只要被代表用户的权限宽于服务账号（这是常态——服务账号本应按最小权限授予），交集就等于服务账号权限，委托头**静默失效**：接口返回 200，给出一个缩水的结果集，调用方无从察觉。而这恰好违背场景二的第一条需求「结果必须和他在 BiSheng 里搜到的一致」。**取交集因此两头堵**——服务账号权限窄则需求落空，权限宽则防护失效且服务账号本身成为高危凭据。

**改用受限委托付出的代价**：防提权的语义从"恒为降权"弱化为"提权有上界"——调用方最多获得委托范围内某个真实用户的真实权限，永远够不到无条件放行。这一边界需要在对外文档中解释清楚。

行业已识别同一问题：Kubernetes v1.36 引入 Constrained Impersonation（beta，需 feature gate），将"能扮演谁"与"扮演后能做什么"拆为两项权限 [S8]——与本方案 §4.4.4 检查 3 与检查 4 的拆分思路一致。

## 7.3 D8 · 委托范围为什么是"必填 + 两类"

设计过程中曾出现过一个「委托模式」枚举（`none` / `scoped` / `any`）与更多的范围类型（`tenant_wide` / `roles` / `user_group`），最终全部否决，收敛为**一个开关（`delegate` 权限位）+ 一张必填白名单（`user` / `department`）**。

**否决「委托模式」枚举**：`delegate` 未勾选 ≡ 模式 `none`，两个字段表达同一个布尔值。它们分属不同配置区（权限位是勾选清单，委托配置是独立入口），必然产生两种死配置——"勾了 `delegate` 但模式 `none`"与"配好了范围但没勾 `delegate`"，两者都不会有任何提示。合并为单一开关后，fail-safe 反而更强：勾选后范围默认为空即谁都代表不了，逼管理员做一次显式的范围选择，而不是留下"开了但没配"的中间态。

**否决「强制委托」独立开关（2026-08-15，同一理由的第二次适用）**：v1.0 曾在 `delegate` 之外设一个默认关闭的"强制委托"布尔，开启后漏传身份头才报 `26016`。它被否决，理由与上一条同源，且更重：

1. **它让铁律 2 只保护了一半**。"勾了 `delegate` 但没开强制"的密钥漏传身份头会静默落到模式 S——返回 200 + 服务账号（本应零授权）权限下的结果集，调用方无从察觉，恰是 §4.4.2 那张表左列被否决的失败形状。方案一边论证"绝不静默"，一边留一个默认关的开关让它照常发生。
2. **它是"默认不安全的开关"**——靠管理员记得为场景二的密钥翻开，正是 D1 拒绝的形状。
3. **它没有站得住的正面用例**。混用（有时以服务账号跑、有时代表用户跑）的集成，按 §6 已立的"一个集成一个服务账号"原则本就该签两把密钥：一把不带 `delegate` 走模式 S，一把带 `delegate` 走模式 D。多一把密钥的成本，远低于多一个静默降级的失败模式。

行业先例（Kubernetes / Zendesk）里 impersonate 确是"能力不含义务"，但那是签给人或管理员的通用令牌；本方案的密钥绑定具体集成的服务账号，一把密钥的身份模式在签发时即已确定，不该由调用方逐次选择。合并后委托配置真正只剩一个字段：范围。

**否决 `any`（代表本租户任意非特权用户）**，两条理由：

1. **不需要它**。每个租户**有且仅有一个根部门**（唯一性由 `DepartmentRootExistsError` 保证，租户创建时强制创建，`tenant/domain/services/tenant_service.py:114`），且无部门用户的兜底部门「临时访客」`BS@guest` 也挂在根之下（`common/init_data.py:283`，含自愈分支）。`department` 填根部门就是全员——多一个 `any` 只是多一条表达同一件事的路径，而且是**看起来更轻**的那条。
2. **它会让一把密钥能代表另一个服务账号**。服务账号也是用户表里的一行：同租户、未禁用、不是超管——"任意非特权用户"的条件它全部满足。后果是拿到密钥 A 的人可以指定服务账号 B 为目标，从而获得 B 的全部资源授权；而服务账号恰恰是被授予集成权限的主体，通常比自然人更宽。**等于开了一条"用一把密钥换另一把密钥权限"的路。**

   但须说明：**删掉 `any` 只移除了这条路最短的入口，并没有堵死它**——`department` 条目同样可能覆盖到服务账号。真正堵死它的是 §4.4.4 检查 2 的自然人判定，那道判定与范围类型无关，从哪条路进来都过不去。因此 `any` 的否决理由，最终落在第 1 条（不需要它）而非第 2 条。

   > **一处被推翻的中间判断，记录在此以免重提**：设计过程中曾认为"范围必填后服务账号落不进任何范围类型（`department` 侧它没有部门、`user` 侧选人框搜不到），因此只需在低频的配置保存路径上校验一次，省下每次请求的热路径开销"。该判断的两个前提都不成立：① `department` 条目存的是部门 ID 而非人员名单，成员在调用期才展开，保存期无从校验；② "服务账号永远没有部门"不是代码保证的不变量——平台有把无部门用户兜底写进「临时访客」部门的自动逻辑，而它挂在根部门之下（取证见附录 E.2）。所幸热路径开销的估计同样是错的：检查 2 本就要取出目标用户行，判定不增加任何查询。

**否决 `tenant_wide` 范围类型**：与 `any` 完全重复，两者同时保留会让"全租户"出现两条表达路径。

**否决 `roles` 范围类型**：角色在平台内是**权限载体**（RBAC 菜单与接口权限），不是组织维度。用它界定"能代表谁"，一是把"有什么权限"与"可否被代表"耦合起来，二是**给某角色加一个人就悄悄扩大了某把密钥的委托范围**，而操作角色的管理员未必知道有密钥挂在上面。

**否决 `user_group` 范围类型**：优先级不足。`user` 支持多选后，"若干特定的人"可以逐个勾选覆盖；组织规模的圈人由 `department` 承担。

## 7.4 D10 · 服务账号的租户归属为什么不用虚拟部门

`user_tenant` 是部门树的派生投影，最直觉的做法是给服务账号挂一个虚拟部门，让它顺着正常路径产生租户关联行。该方案被否决，改为直写 + 对账豁免（§4.5，落点见附录 E.2），两条理由：

1. **虚拟部门会被上游清除**。部门树受组织同步的全量对账管辖，一个不在上游组织架构里的部门，随时可能在下一次快照比对中被判为"已删除"。
2. **污染面广**。部门管理界面、审批人的部门维度、部门成员数统计、租户用户列表——至少 4 个消费面会看到这个本不该存在的部门。

相比之下，直写 + 豁免的改动集中在两个明确的位置（对账扫描与同步服务入口），且失败模式是"服务账号丢失租户关联"这种立刻可见的故障，而非静默污染。

## 7.5 D9 · 为什么不再由 PRD 指定对外契约形态

原 v2.1 / v2.2 把「OpenAI Responses 兼容子集」写死在 §4.6.3，并逐字段列出映射、事件对应与拒绝清单。2026-08-18 改判为「PRD 只给业务需求，形态交 design」。四条理由：

**1. 层级错位。** 字段名、事件名、端点路径属于 How，PRD 的职责止于「调用方必须能表达什么、平台必须保证什么」。把 wire format 写进 PRD，等于用产品文档锁死技术方案，还让形态的任何调整都要回头改 PRD。

**2. 语义错配——这是比工作量更根本的问题。** Responses 是**模型侧**契约，它的入参是 messages / role / system message / 采样参数；而本能力是**应用侧**能力，调用方真正要表达的是「问什么、在哪个会话里问、挂哪些知识库、开哪些工具、带哪些附件」。强行对标，等于要求调用方按模型层概念组织一个应用层请求——研发反馈的「开发者还要传 system message」正是这处错配的直接症状。同类产品（Dify 的 `/chat-messages` 等）在这个位置用的都是业务语义入参，不是模型协议。

**3. 兼容承诺已被自身的拒绝清单掏空。** 为兑现「Responses 子集」，正文当时要拒绝：`store: false`、`user` 字段、全部采样与生成参数、客户端 `function` 工具、`input` 中的消息历史、内联与外链文件，且 `containers` / `conversations` / `items` 全套资源族不实现、平台工具要另造 `bisheng_tool` 类型、`instructions` 只能叠加不能替换。这份清单加起来已经不是「子集」，而是形似神不似。**SDK 能反序列化 ≠ 调用方能按 OpenAI 的习惯用法使用**——兼容承诺越薄，为它付的对象模型保真与事件对齐成本就越不划算。

**4. 「一套契约覆盖日常 + 任务」这条决定性论据已经站不住。** 它是当初选 Responses 的头号理由，但 D11 已经查明：任务模式的 `ask_user` 中断与 MinIO 产物，Responses 都表达不了、只能靠自定义 output item 发明。反过来看，业务型契约天生能表达这两件事——同类产品把「任务已暂停、等待人工输入」直接做成一等状态（Dify 的 `workflow_paused` + `human_input_required` + `form_id`），正是 `ask_user` 需要的位置。

**本次明确权衡掉的东西（产品决定，不是技术细节）：不再把「官方 OpenAI SDK 可直连日常模式会话」列为需求。** 这项能力并未从平台消失——`model:invoke` 的模型协议面（Chat Completions 形态）与既有 `POST /api/v2/assistant/chat/completions` 承接「拿通用 OpenAI 客户端直连」的诉求。日常模式会话面再对标一次，是同一诉求的第二次投资。

**改判**没有**放宽的地方**：§4.6.3 第三小节的八条硬边界（一套契约、不静默降级、模式与同步/异步两个维度、流式语义可分、有状态会话、附件只走上传端点、归属与分区、逐项文档）全部保留并作为验收依据。研发在 design 阶段如果评估后仍选择 OpenAI 形态，这是被允许的技术选择——但要在 design.md 写清理由，且它不再是产品承诺、不进对外宣传口径。

## 7.6 D13 · 为什么把「不做个人访问令牌」改判为交付

### 原决议与它的三条理由

PRD v2.0 的 §6 非目标（以及 v3.0.0 release-contract 的 INV-28）都写着不做个人访问令牌，理由三条：

1. §3 的三类场景全部是系统对系统集成，无一需要它
2. 引入它会带来第二类主体、第二套权限来源（动态继承）、生命周期联动
3. 行业先例记载此类密钥的固有缺陷是**随创建者离职失效** [S6]

### 逐条重估

**理由 1 已被新场景推翻。** 场景四（§3.5）不是前三类的变体：调用方由员工自己选定、密钥由员工自助配置、权限基准是员工本人。**判据是「谁来配这把密钥」**——前三类由管理员配，所以要一个可以被集中收敛的服务账号；场景四由员工自配，服务账号在这里没有对应物。这是一个新场景，不是对旧场景的补充要求。

**理由 2 的成本估错了一个量级。** 写下这条时的假设是"PAT 需要第二类主体"，而这个假设在代码层面不成立：

| 当时的顾虑 | 核实结果 |
|---|---|
| 第二类主体 | 凭据表的主体类型本就是**可扩展枚举**，校验器本就是**按主体类型分派的注册表**（服务账号只是其中一个已注册项，另有两个已登记待注册项）——**加一个值 + 一个解析函数** |
| 第二套权限来源（动态继承） | 动态继承**比快照更省代码**：平台的权限判定本来就是按调用者实时算的，做快照才需要额外机制 |
| 生命周期联动 | 「主体被停用 / 被删除」这两个撤销原因、按主体批量撤销的服务方法、对应的审计事件类型，**都已经存在**（服务账号侧在用同一套），缺的只是三个触发点 |

更关键的是**方向反了**：§4.5 服务账号主体付出的四项成本——租户归属直写与三层对账豁免、用户列表分叉、十个登录入口的守卫、资源归属人机制——**个人访问令牌一项都不需要**，因为它的主体是一个本来就存在、本来就能登录、本来就有租户与部门归属的自然人。

**理由 3 是同一条事实的两种读法。** LangSmith 那句「持有者离开组织后令牌失效」[S6]：

- 对**系统集成**，它是缺陷——生产链路不能因为某个员工离职而中断，所以要服务账号
- 对**个人接入**，它恰恰是必须有的行为——**员工离职后他的密钥还能继续拉公司知识，那才是事故**

§4.2.2 引用它论证"密钥主体只能是服务账号"，**在系统集成的语境下依然成立、不必修改**；它只是不能被外推到场景四。

**这一读法有独立的一手佐证**：GitLab 的服务账号凭据**本身就是 PAT**，却被显式排除在"关闭企业用户 PAT"的组织策略之外、并有独立的过期设置 [S15]；Slack 把 user token 与 bot token 分成两个**生命周期不同**的令牌族，只有前者随人失效 [S16]。**两家都是"同一套令牌原语、两类主体分别治理"**——正是本次改判后 BiSheng 的形状（§4.10.2 / §4.10.6 规则二）。

> ⚠️ **但有一条不能顺手带出的结论**：随人级联失效**不是行业默认**。GitHub 明确策略收紧"不撤销也不禁用"存量令牌 [S14]，「GitHub / GitLab 离职即自动吊销 PAT」两条主张在核查中均被推翻。BiSheng 要兑现这条，**必须自建**（§4.10.4）。

### 与 2026-08-06「个人 key 整条作废」的关系

那次决议废除的是**应用工场开发者 CLI 用的个人 key**，理由是：不希望一个生产应用的权限跟着某个开发者的个人权限走。**那条理由在场景四不成立——场景四要的就是调用者本人的权限。**

因此这不是翻案，是**两个不同用途的分别裁定**。但必须显式记录：否则下一次有人读到「平台不存在自然人个人凭据」时，会把这里的设计当成漏网的旧方案再删一遍。

### 连带须修订的产物（缺一即前后矛盾）

| 产物 | 位置 | 改动 |
|---|---|---|
| 本 PRD | §1.1 第二层 / §1.4 注 / §4.2.2 / §4.2.3 / §4.7.2 / §6 非目标 | 六处「不做 PAT」——**本次已改** |
| **release-contract** | **INV-28**（「平台不存在自然人个人凭据」）+ 表 1 ApiCredential 行（「全平台唯一主体轨」「`bs-pat-` 个人主体轨已废除」） | **必须同步**，否则设计评审的 Constitution Check 直接判 INV 冲突 |
| F049 spec §4 决议-4 | 「全平台只留服务账号一类密钥主体」 | 保留原文，加「在场景四范围内被 D13 取代」的后继标注 |

## A.1 核心裁决：「传 user_id 代表用户」到底行不行

### 把问题拆成两个

| 问题 | 答案 |
|---|---|
| 传 user_id 能**证明**这是该用户本人在操作吗？ | **不能，永远不能。** 任何平台都做不到 |
| 传 user_id 能**合法地**让调用方按该用户的权限边界执行、并把结果归属给该用户吗？ | **能——当且仅当护栏齐备。** Zendesk、Kubernetes、FastGPT 均如此实现 |

### 规范层的判据

OWASP API Security Top 10 2023 将 BOLA（对象级授权失效）列为第一风险：

> 「Every API endpoint that receives an ID of an object, and performs any action on the object, should implement object-level authorization checks. The checks should validate that the logged-in user has permissions to perform the requested action on the requested object.」
> 「Comparing the user ID of the current session (e.g. by extracting it from the JWT token) with the vulnerable ID parameter isn't a sufficient solution to solve Broken Object Level Authorization (BOLA). This approach could address only a small subset of cases.」
> ——［文档］https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/

**引用分寸（必须保留，否则即为过度引用）**：
- OWASP 使用 `should` 而非 `must`，是指南而非强制标准。
- BOLA 判据针对"已认证会话内的对象级授权"。若服务账号确实持有相应对象权限，字面判据可被满足——此时真实缺陷是"未强制的委托"，更接近端点级越权（API5:2023 BFLA）而非 API1。
- 原文只说 ID 比对"不充分"，不能转述为"OWASP 禁止 ID 匹配"。

## A.2 横向对比

**两个关键区分**（常被混为一谈，本表拆开）：
- **平台是否校验该身份**——平台能否独立确认这个身份是真的？
- **该身份是否影响权限**——它是否改变了这次调用能访问什么？

| 产品 | 类型 | 调用方鉴权 | 最终用户身份如何传 | 平台是否校验 | 是否影响权限 | 来源 |
|---|---|---|---|---|---|---|
| **Dify** | 私有化 LLM 平台 | `Authorization: Bearer`，应用级 Key，一 Key 服务全部终端用户 | 请求体 `user` 字段（明文） | **否**（官方明示） | 否（仅会话/文件归属） | [S1] |
| **RAGFlow** | 私有化 RAG 平台 | `Authorization: Bearer`，租户作用域 | 有 `user_id` 参数但定义为 "Optional user-defined ID"（纯标签）；**检索接口参数表中无任何身份字段** | 否 | 否 | [S2] |

| **n8n** | 私有化工作流平台 | `X-N8N-API-KEY` 自定义头，静态 Key，**创建时必填过期时间** | **无任何机制** | 不适用 | 不适用 | [S4] |
| **Coze** | 智能体平台 | 私钥签名 JWT 换短期令牌（默认 900s，上限 86399s）；PAT 上限 30 天 | `session_name`，位于**签名 JWT 的 payload** | 否（验的是应用私钥，非用户） | **否**（官方明示仅用于会话隔离） | [S5] |
| **LangSmith** | LLM 可观测平台 | `X-API-Key` 头；双轨 Key：`lsv2_pt_`（个人）/ `lsv2_sk_`（服务账号） | **无任何机制** | 不适用 | 不适用 | [S6] |

| **Microsoft Entra OBO** | 身份平台 | 中间层自己的客户端凭据 + 用户令牌作断言 | 断言本身即用户令牌，其 `aud` **必须等于中间层自身** | **是**（平台签发并校验） | **是** | [S10] |
| **AWS STS ABAC** | 云平台 | `AssumeRoleWithWebIdentity` | 租户 ID 位于 **IdP 签名的** JWT claim，STS 验签后原样映射为会话标签 | **是**（此路径）／否（`AssumeRole` 路径由后端自行打标签） | **是** | [S11] |
| **Azure AI Search（弱档）** | 检索服务 | 服务凭据 | 调用方自行把身份串拼进过滤表达式 | **否**（官方明示"只是一个字符串"） | 是（但由调用方负责正确性） | [S12] |
| **Azure AI Search（强档，预览版）** | 检索服务 | `Authorization: Bearer`（调用应用自己的角色） | **另一个头** `x-ms-query-source-authorization`，装最终用户的真实令牌 | **是** | **是** | [S13] |

- ⚠️ 例外：2025 年 11 月的 fail-closed 变更本身**跨版本生效**（原文 "across all versions that support ACL"），该条不受预览版限制。
- ⚠️ elevated-read 仅对 Search POST 生效，明确不适用于知识库检索动作。

## A.4 三档身份传递模型

| 档 | 形态 | 代表 | 平台能否独立验证 | 适用前提 |
|---|---|---|---|---|
| **A · 受信客户端断言** | 明文头/字段传用户标识 | Dify、FastGPT `authProxy`、Zendesk、K8s、Azure 弱档 | 否 | 调用方后端受控、与平台同一信任域 |
| **B · 签名断言** | 用户标识进调用方私钥签名的 JWT | Coze、Atlassian 2LOi | 能验签，但仍是调用方自证 | 需不可抵赖、密钥可轮换 |
| **C · 用户令牌透传** | 最终用户自己的令牌直接透传 | Microsoft OBO、Azure 强档 | **是** | 最终用户即平台用户且能走统一身份源 |

**关键判断**：A 档并非"不安全"——Zendesk 与 Kubernetes 都在 A 档且被广泛接受。差别在护栏是否齐备，而非档位高低。C 档最强，但要求最终用户在平台有身份，对场景三（外部用户）根本不适用。

**本方案选型**：一期采用 A 档（与 FastGPT 完全同构），预留 B 档升级路径（决策 D6）。

## A.5 委托的护栏

四条护栏，注意**它们并非全部是跨平台不变量**——各家取舍不同：

| # | 护栏 | 采纳情况 |
|---|---|---|
| **G1** 调用方自身凭据先认证，委托头永不单独确立身份 | **跨平台一致** | K8s 的鉴权时序原文 [S8] 是最清晰的表述 |
| **G2** 冒充能力单独授予，不被任何其他权限蕴含 | **三家一致** | Zendesk `impersonate` scope、Atlassian `ACT_AS_USER` 独立 scope、K8s `impersonate` 动词；FastGPT 更进一步——**逐密钥由团队所有者显式开启** |
| **G3** 收窄可代表范围 | **两种实现** | Zendesk：目标须**预先存在**；K8s：**不要求存在**，改用 `resourceNames` 取值白名单。二者目的相同、手段不同 |
| **G4** 审计归属到被代表用户 | Zendesk 明文规定 | 「the change is associated with the end user, not the admin」 |

**反面教材（同样有价值）**：Coze 的 `session_name` **没有任何单独授予机制**——任何持私钥者可随意填写。其结果是该字段被官方明确降级为"仅用于会话隔离"，不承载任何权限语义。**这印证了 G2 的必要性：缺少单独授予，委托字段就只能被降级为标签。**

## A.6 四条可直接采纳的失败模式实证

### A.6.1 缺失最终用户身份 ≠ 放行全部

Microsoft 在 2025 年 11 月对 Azure AI Search 做过一次 fail-closed 改造，起因与 BiSheng 现状同构：服务密钥调用时即使不带用户令牌也返回全部文档。改造后「If the user token is omitted, ACL-protected content isn't returned」[S13]。

同页另有一条 Note 界定了正确的降级语义：**不是返回空，而是只返回对所有人公开的内容**。

### A.6.2 绕过过滤是一项更强的权限，不是免费开关

Azure 的排障逃生门 `x-ms-enable-elevated-read` 要求调用方另外持有 `Search Index Data Contributor` 或含 `Elevate Read` 的自定义角色 [S13]。绕过过滤被做成**单独授予的更强权限**。

同样的反面实证来自 n8n：「**Non-enterprise API keys have full access to all the account's resources and capabilities.**」[S4]——默认全权限即是隐患。

### A.6.3 共享令牌无最终用户标识 → 跨用户会话串档

Coze 官方文档自述 [S5]：

> 「all interactions utilizing the same access token are treated as originating from the same user. As a result, **multiple business users can view each other's chat histories** if they share the same access token.」

**与 BiSheng 的对照**：相同的一半已经成立——同一凭据下的调用被视为同一用户，场景三的会话确实统一归属固定身份；不同的一半尚未成立——BiSheng 没有按用户列举会话的开放端点，会话只能凭服务端生成的随机 `chat_id` 读取，因此还没有形成 Coze 这样的互读后果（取证见 §3.3「问题的边界」）。

**这正是引用它的价值**：Coze 的坑由"共享身份"与"可按身份列举会话"两个条件合成，BiSheng 已经具备第一个。一旦后续补上"按终端用户查询会话"这类能力，第二个条件即告齐备。现在就引入 `X-Bisheng-End-User`，成本只是一个可选请求头；等两个条件凑齐再补，要动的是存量会话数据。

### A.6.4 权限评估失败必须 fail-closed

> 「If ACL evaluation fails … the service returns 5xx and **does not return a partially filtered result set**.」[S13]

对 BiSheng 的直接映射：权限引擎不可用时，检索接口必须报错，绝不能退化成"过滤器没生效所以全返回"。

### 关于知识库检索的权限过滤（重要事实澄清）

平台内存在两条检索路径，权限过滤强度不同，设计与测试时不可混淆：

| 路径 | 权限过滤 | 位置 |
|---|---|---|
| `/api/v2/filelib/retrieve` 走的路径 | **只做知识资源级一次校验，无文件级过滤** | `knowledge/domain/services/knowledge_space_chat_service.py:812-872` |
| 工作台文件夹对话走的路径 | **两层过滤**：索引层预过滤（批量鉴权后下推向量库/ES）+ 结果层批量校验兜底 | 同文件 `:484-570` |

**本次要把前者升级到后者的强度**（§4.4.6）——否则模式 D 的"不多不少"兑现不了。注意调用方 `filelib.py` 的注释宣称该路径"已有 per-user 的 view_file/view_space 过滤"，**与实现不符**，不要据此认为已经做过。

此外，权限模型中并**不存在**名为 `view_file` / `view_space` 的关系——实际统一使用 `visible` 关系。历史文档与上述注释中的这两个叫法仅为描述性称呼。

### 关于 `enable_guest_access`

它是全 V2 唯一的既有访问控制，但**覆盖面只有 3 个端点**（`GET /flows/{id}`、`GET /assistant/info/{id}`、`GET /assistant/list`），其余 39 个 HTTP 端点与 2 个 WS 端点完全不受它约束——包括全部知识库增删改、文件上传、日志下载与工作流调用。**默认值是 `true`（开箱即开）。**

把它理解成"V2 的总开关"是错的。全端点强制鉴权后它失去意义，**随本次一并移除**（§4.9），以免留下一个看起来像总开关、实则只管三个端点的配置项。

## E.1 R1 · 凭据体系

### 现有四类凭据的核实结果（对应 §4.2.1）

| 现有机制 | 生成 | 存储 | 过期 | 撤销 |
|---|---|---|---|---|
| 分享链接 token | 合格（`os.urandom` + HMAC） | **明文**，且 API 原样返回整个对象 | 字段存在但**代码从不校验**（`share_link_service.py:52-56` 注释明说 intentionally not enforced） | 有 INACTIVE 枚举，但**全仓无任何写入端点** |
| 工具 `api_key` | 不生成（用户手填第三方 key） | **明文** | 无 | 无 |
| 邀请码 | **`random.choices()` 非密码学随机** | **明文** | 无（仅次数限制） | 仅回滚次数 |
| 网关 HMAC | 不签发（共享密钥签名） | 配置项 | 无 | 改配置重启 |

**两个必须复用的现成件**：

- `generate_short_high_entropy_string`（`common/utils/util.py:28-54`）——全仓唯一合格的随机源
- `sso_sync/domain/services/hmac_auth.py:44-109`——全仓唯一做对了恒时比较 + fail-closed 的校验实现，其姿势应被抄用

**分享链接的 INACTIVE 枚举全仓无写入端点**，是密钥表**不设独立 status 列**（§4.2.3）的直接反例证据：可漂移的冗余状态列是负资产。

### 为什么存哈希而不用 Fernet（对应 §4.2.5）

平台已有 Fernet 加密工具，但**其密钥硬编码在 `core/config/settings.py:20` 并随开源仓库分发**，任何人可解密全部密文，且无轮换机制。Fernet 的合理适用面是"服务端需要还原后转发给第三方"的出站凭据（数据库密码、组织同步凭据）；入站 API 密钥服务端只需比对不需还原。

**不加盐即可**：密钥本身是高熵随机值，无字典攻击面；不加盐才能直接建索引做常数时间校验。这与用户口令必须加盐的场景不同。

### 校验流程（顺序不可调换）

```
1. 提取 Authorization: Bearer bs-…
2. with bypass_tenant_filter():              ← 此时尚无租户上下文，必须绕过
       按 sha256(明文) 查密钥行                  （分享链接服务已有同构先例，其注释
                                                语义完全一致："token 本身就是授权"）
3. fail-closed 校验，全部通过才继续：
   恒时比较 → 未撤销 → 未过期 → 主体有效且类型匹配 → 主体当前租户 == 密钥租户
4. set_current_tenant_id(密钥租户)            ← 从这里开始有租户上下文，
                                                后续所有查询被自动过滤
5. 构造身份对象（复用 get_default_operator_async:66-74 的既有模式）
6. Redis 缓存步骤 2-3 的结果，TTL 5s；撤销时主动删除缓存键
```

### 租户隔离的两个必要条件，缺一不可

1. 密钥表物理带 `tenant_id` 列（自动过滤靠反射发现，`core/database/tenant_filter.py:127-140`）
2. **密钥模型的模块路径注册进 `_TENANT_AWARE_MODEL_MODULES` 手工清单**（`tenant_filter.py:39-102`）

> ⚠️ 该文件 `:36-38` 的注释记录了 v2.5 的一次事故：因漏注册导致 `knowledgefile`、`flowversion`、`roleaccess`、`userrole` **静默把子租户数据写进了根租户**。这是 §4.2.5 所说"漏掉其一会导致数据被静默写进错误租户"的出处。

**写路径规约**：自动过滤**只拦 SELECT**（`tenant_filter.py:164`）与 INSERT 自动填充（`:200-234`）。**禁止**对密钥表使用批量 update/delete 或原生 SQL——撤销走单行 ORM 更新，最后使用时间走带主键的 UPDATE。

## E.2 R4 · 服务账号主体

### 主体标识（对应 §4.5 定义 1）

新增 `user_type` 列（`human` / `service`，带索引，需 Alembic 变更）。其余用既有字段的特定取值表达：

| 字段 | 服务账号取值 | 效果 |
|---|---|---|
| `source` | `service_account`（新枚举值） | 组织同步的认领查询按渠道匹配，服务账号结构性不命中 |
| `external_id` | `NULL` | **登录候选查询、公开改密均按 `external_id` 查找，NULL 结构性不命中**——三条路径零代码免疫 |
| `password` | 哨兵值（带特殊前缀的高熵串） | 满足非空约束；密码校验输出格式与哨兵永不相等 |

> ⚠️ **不能用现有的 `delete` 字段兼职做"禁止登录"标记**：SSO 回调会在同步时把它翻回 0（`sso_sync/domain/services/login_sync_service.py:364-369`），管理员也可在用户管理页直接启用。必须独立字段。

### 租户归属：直写 + 对账豁免（对应 §4.5 成本 1）

因果链三步：

1. **授权的前置条件**是主体在 `user_tenant` 表有活跃行——授权主体校验要求 `status == "active"` 且 `is_active == 1`（`tenant/domain/services/f048_permission_subject.py:53-74`，判定在 `:70`）。
2. **但这张表不是权威数据，是部门树的派生投影**（`docs/architecture/12-multi-tenant.md:308`：「部门树是真相，`user_tenant` 是派生投影」）。它的行由部门归属推导而来，而服务账号没有部门。
3. **因此即使手工写入一行，也会被对账清掉**——对账任务按部门树重建投影，一个没有部门的用户在重建后不会留下任何行。

所以"写入"与"豁免"必须成对：

| 措施 | 位置 |
|---|---|
| **创建服务账号时直写租户关联行** | 服务账号创建流程（§4.7.1）。**必须同时写 `status='active'` 与 `is_active=1`**——授权主体校验两个条件都查（上文第 1 步），漏一个则整个主体侧授权页不可用。注意 `is_active` 受 `uk_user_active(user_id, is_active)` 唯一约束，语义是"当前叶子租户"，故**一个服务账号同一时刻只能归属一个租户**（与 §4.5 定义 3 一致；跨租户集成须每租户各建一个） |
| **对账任务的用户扫描加 `user_type == 'human'` 条件**——这是收口点 | `UserDao.alist_users_after_id`，唯一调用方是 `worker/tenant_reconcile/tasks.py:68` |
| **租户同步服务入口加服务账号守卫**——纵深防御，防未来新增调用点把它拉回根租户 | `tenant/domain/services/user_tenant_sync_service.py:71` 的 `sync_user` |
| 租户解析器**不改** | 其调用方只作用于登录用户，而服务账号不可登录，结构性不可达 |

**配额统计**需加 `user_type == 'human'`（`role/domain/services/quota_service.py:622-645` 的 `_count_user_count`），落实 §4.5 定义 4。该查询现有条件是 `tenant_id` + `UserTenant.is_active == 1` + `User.delete == 0`——**用户侧唯一的存活判定就是 `delete == 0`，不区分账号类型**，所以服务账号会被计入席位。

（为什么不给服务账号挂虚拟部门 → §7.4）

### 登录守卫：10 个入口（对应 §4.5 成本 2）

实际只需 1 处公共守卫 + 3 处单独改：

| 类别 | 措施 |
|---|---|
| **公共守卫（1 处覆盖 4 入口）** | `UserService._reject_login_if_user_has_no_usable_access`（`user/domain/services/user.py:373`）开头拒绝服务账号。经核实其有 4 个调用点：本地登录、SSO、网关登录同步、租户选择 |
| **结构性免疫（0 改动，但需测试断言防退化）** | 上文 `source` + `external_id=NULL` 的组合 |
| **单独改 3 处** | ① `resolve_operator`（`open_endpoints/domain/utils.py:77`）——既有后门，连账号禁用都不查，**P0 应独立修复**；② `get_default_operator*`（`:26/:53`）补账号状态校验；③ `/user/update`（`user/api/user.py:674`）拒绝服务账号，防管理员绕过密钥缓存失效逻辑 |

### 用户列表排除（对应 §4.5 成本 3）

`/api/v1/user/list` 一个接口同时服务 8 处以上消费点——用户管理、审批人选择、部门加成员、用户组加成员、创建租户选管理员、资源授权选人等。

**fail-safe 方向**：排除逻辑下沉到数据访问层——`_filter_users_statement`（`user/domain/models/user.py:259`）增加默认值为 `human` 的类型参数。**忘记传参的结果是"看不到服务账号"而非"泄漏服务账号"**。

因为授权走主体侧（§4.7.4），这条排除是**无例外的不变量**：不需要接口层 opt-in 参数，前端零改动。服务账号自身的管理列表走**新端点**，不复用 `/user/list`。

> ⚠️ **DAO 改一处不够**：资源侧授权弹窗的主体选择器**不走 `/user/list`**，而是 `permission/domain/services/grant_subject_service.py:70-121` 的独立查询（现有条件只有 `User.delete == 0` + 租户内 active，无账号类型过滤）。§4.7.4「服务账号不出现在任何资源侧的授权选人框」要落地，这一处须同步加过滤，AC-15 的覆盖面须含此入口。

**自然人校验有两个落点**（§4.4.4）：

| 落点 | 性质 | 位置 |
|---|---|---|
| **调用期** | **安全防线** | 委托准入检查 2 判定 `user_type == 'human'`。该检查为确认"存在、未禁用、同租户"本就要取出 `User` 行，判定不增加查询 |
| 保存期 | 早报错 | 委托范围 `user` 条目的保存路径独立校验 `user_type == 'human'`。选人框搜不到服务账号靠的是上文 DAO 的默认过滤，但绕开界面直接调接口仍可写入 |

### 服务账号可能获得部门归属的两条自动路径（对应 §4.4.4 检查 2）

**"服务账号永远没有部门"不是代码保证的不变量。** 平台有两条自动路径会把没有部门的用户写进「临时访客」部门（`BS@guest`，由 `common/init_data.py:283` 建在根部门之下，因此委托范围填根部门即覆盖它）：

| 路径 | 触发方式 | 对服务账号的实际风险 |
|---|---|---|
| `_backfill_guest_department_membership`（`common/init_data.py:439`，每次进程启动经 `:125` 调用） | **自动（启动时）** | 判据是 `user_department` **全表是否存在任意一行**，有则短路跳过。生产环境通常已有数据，实际多为空转；**危险窗口是整表为空时**——全新部署、迁移重建、或"先建服务账号、尚无任何部门成员"的引导期。它不检查账号类型 |
| `_reconcile_guest_membership`（`sso_sync/domain/services/login_sync_service.py:409`） | **自动，且不止登录**——网关组织推送端点 `gateway_wecom_org_sync.py:123` 也会逐成员调用，是一条后台批量路径 | 命中前提是被 SSO 载荷匹配上，而 `:265` 有按 `external_id` 跨 source 收编的逻辑。**服务账号 `external_id = NULL` 使其结构性不命中**——但这道防线是隐式的（`external_id=NULL` 的设计初衷是阻断登录，见上文「主体标识」），须加测试断言固化 |

**决策：不修改这两条组织架构侧的兜底逻辑。** 它们服务于真人场景（SSO 登录进来的员工没有部门时的兜底），改动会波及正常路径，且未来可能新增第三个调用点。改由委托侧的检查 2 自行守住——**该安全不变量因此不依赖"服务账号永远没有部门"**。

## E.4 R6 · 服务账号授权页

### 反查走 SQL，不走 ListObjects

主体侧页面需要"给定主体，列出它的资源"这一反向查询。**不能用 OpenFGA ListObjects**——它被 `DenyListObjectsPolicy` 显式禁用（`permission/application/sql_runtime.py:638`，装配处 `runtime.py:1113`）。

反查改走 SQL 投影账本，且**索引现成**：

```sql
SELECT ... FROM permission_grant_assignee a
  JOIN permission_grant g ON g.id = a.grant_id
 WHERE a.subject_type = 'user'          -- 服务账号复用 user 主体类型
   AND a.subject_id   = :service_account_id
   AND a.state        = 'ACTIVE'
```

命中 `ix_perm_assignee_subject_state`（`tenant_id, subject_type, subject_id, state`，`permission/domain/models/grant.py:118`）；`tenant_id` 由租户自动过滤注入，不手写。

**授权来源靠 `source_type` 区分**——资源创建者的归属关系同样以 assignee 行表达（`source_type='CREATOR'`、`protected=true`、`model_key='owner'`，见 `permission/domain/services/owner_service.py:197-207`）。**服务账号侧不应出现 `CREATOR` 行**：资源归属人机制要求把 `CREATOR` 写给归属人这个自然人，服务账号只拿一条普通的可编辑 grant（§4.5 定义 6 边界 b）。页面的"来源"列即据此区分——落在服务账号身上的自动回授行需要一个可识别的标记（新增 `source_type` 取值或复用既有字段，落地时定），否则无法把它从"全部撤销"里排除。

新增读端点 `GET /api/v1/service-accounts/{id}/grants`（分页，按资源类型筛选），负责反查 + 资源名称水合。

### 写路径复用既有 mutate，不新建

授予 / 变更 / 撤销一律调用既有的 `POST /api/v1/permissions/resources/{resource_type}/{resource_id}/grants:mutate`（`permission/api/endpoints/grant.py:114`）。

**理由是宪法 C4**：Grant 变更必须在改动 OpenFGA 之前先落持久化的操作/投影账本，且只能经由唯一的 F048 runtime。新建一条主体侧写路径等于绕开它。**本页只新建读路径。**

权限档位由既有的 `GET /api/v1/permissions/resources/{type}/{id}/grantable-models`（`grant.py:26`）提供，页面不硬编码枚举。

页面对 N 个资源的操作 = N 次调用，逐条反馈成功/失败，**不做事务化批量**——批量原子性需要跨资源的账本编排，成本远超收益。

> 管理员对目标资源本身无需另行持有权限：具体资源判定的短路顺序是 `super_admin → 租户不匹配拒绝 → 租户管理员 → …`（宪法 C4），同租户内的管理员在 `grants:mutate` 上天然通过。**复用写路径无需改动其鉴权。**

### 服务账号不得加入用户组 / 部门 / 角色

否则它的有效权限会有本页查不到的来源（授权记录挂在组或部门上，按主体反查不到），管理员据本页做的边界收敛判断将系统性失真。

这条**无需额外代码**——E.2 的 DAO 层默认排除使所有成员选择器天然搜不到服务账号；服务账号也没有主部门。但**需要测试断言防退化**。

### 删除前置校验的原因

assignee 行的外键指向 `permission_grant` 而非主体（`grant.py` 中 `ondelete="RESTRICT"`），删除用户行不会级联清理。残留的 assignee 行与对应的 OpenFGA tuple 会指向一个已不存在的主体——既是审计脏数据，也是潜在的越权残留。

### F018 资源归属转移的现状取证

仓内只有骨架：资源类型注册表（`tenant/domain/services/resource_type_registry.py`，7 种类型）与错误码（`common/errcode/resource_owner_transfer.py`，19601–19606）已就位，但**无任何生产代码 import 这个注册表**（仅单测 `test/permission/test_resource_type_registry.py` 引用），服务与端点均未落地；`TransferOwnerRequest` / `TransferOwnerResponse` 与权限点常量 `resource.transfer_owner` 同样零引用，19601–19606 里也只有一个码被用到。任何方案不得假定"调用一个现成的转移接口"。

## E.5 其他

### 特权主体短路的取证（对应 §4.4.4 检查 3）

权限引擎中仅有的两个"无条件放行"短路——超级管理员与租户管理员——判定在 `permission/domain/services/permission_action_service.py:379-384`（完整顺序是 `super_admin` → 租户不匹配即拒 → 租户管理员 → 逐资源判定）。超管判定有 Redis 缓存，但缓存在**身份解析层**（`utils/http_middleware.py:145-168`，键 `user:{id}:is_super`）而非判定层，故检查 3 的成本极低。

> ⚠️ **默认租户内不存在"租户管理员"这个身份**：身份解析仅在 `tenant_id != DEFAULT_TENANT_ID` 时才去查 `is_tenant_admin`（`permission/application/identity.py:27-31`）。因此检查 3 在默认租户下退化为只判超管——这本身是正确的（该租户下没有租户管理员），但**测试用例须按租户分别设计**，不要在默认租户里构造"租户管理员目标"然后期待 `26007`。

### 限流基础设施现状（对应 §4.8.2）

平台无 `slowapi`、`fastapi-limiter` 等任何 HTTP 层限流依赖。最接近的可复用原语是部门并发槽位的 Redis Lua 脚本（`department/domain/services/department_flow_service.py:57-118`），但它在 Redis 故障时 **fail-open**，对鉴权场景语义不合适，需改写。
