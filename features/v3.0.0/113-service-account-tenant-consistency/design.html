Design: 服务账号与应用操作租户一致性

关联：spec.md（38条AC已确认） · 需求发现 · 设计评审记录

版本：v3.0.0；发版线 feat/3.0.0。 最后更新：2026-10-28（Asia/Taipei，修订R2三项评审问题）。 阶段：用户已单独确认修订设计并授权拆任务和开发（确认版SHA-256：d16fbbd1519c404fdcddeb20c5146bf8fba4dc891c72b7f2cd0ed433a1062ed4）。实施中，进度见tasks.md；已实现与待实现分开记录，未完成真实E2E，不表示已交付。

1. 目标与非目标

在服务账号公共业务准入处阻断归属人租户失配，在应用业务入口阻断调用者跨租户操作，并为超管提供明确的服务账号管理/创建租户。异步发布资格失败时，保持当前及待生效版本不变。

不做资源移交或迁移，不改已有账号、密钥、应用的租户和owner，不自动停用应用/账号或撤销密钥；不新增发布幂等、人员迁移锁、跨阶段事务或运行时权限。本轮不改runtime-manager/代理的编排实现，不新增数据库表/列、Alembic或数据修复脚本，不改变PAT生命周期、审批引擎状态、owner-only权限和原有超管例外。

2. 关键约束

遵循constitution.md C1–C8及版本契约，不在本文重抄全局法律。特有约束：

  • 两个独立的租户判定：服务账号请求比对“服务账号租户—归属人当前有效租户”；应用操作比对“已认证调用者租户/有权管理范围—应用租户”。前者通过不代替后者。
  • 归属人关系变更后下一次调用必须见到新关系，不能依赖principal缓存TTL；查询使用现有权威数据库会话，不增第二套关系缓存。
  • 资源owner不等于请求执行主体。模式S仍是service_account主体，模式D仍采用既有受限被代表身份，不能构造拥有owner角色的临时管理员。
  • 应用自动恢复和用户新发布不同。原批准版本的可信恢复保持原运行合同，不能因为owner迁租户自动停止；用户请求和新发布仍执行本次规则。
  • 管理范围以F019共享状态为真相；单次请求接受时验证并固定范围，随后其他标签页切换不撤销已接受操作，不持有跨Redis/SQL全局锁。
  • 不对116三个存量应用、账号24、审批414/415实施维护变更；真实验收使用临时对象。只做本功能定向验证；DM8仅静态兼容核对。

3. 方案对比与选定

D1：服务账号准入采用实时关系校验

  • 备选：只在发布API检查；依靠人员迁租户事件清凭据缓存；自动撤销所有密钥；每次业务准入读取当前绑定。
  • 选定：保留原凭据有效性缓存，在其后对service_account执行实时绑定校验；HTTP、MCP工具执行和WebSocket新业务消息共用同一公开资格能力。
  • 原因：credential_validator.validate_bearer缓存的是完整principal，热命中跳过resolver；只改resolver仍允许旧owner继续使用。事件清理还依赖所有人员变更路径和消息成功，不满足AC-03；自动撤销违反AC-07。
  • 重新考虑条件：测得实时查询成为瓶颈后，另行评审具有明确变更顺序保证的共享版本机制；本轮不以TTL代替资格准确性。

D2：应用校验前先固定调用者来源，按动作保留原权限

  • 备选：依赖SQL自动租户过滤；加载App后比较ContextVar；所有应用动作改成相同管理员权限；抽取仅验证租户的公共边界，再执行各动作原规则。
  • 选定：在app_runtime提供租户边界应用接口，以请求已认证的actor/principal及管理范围为输入；先拒绝租户不符，再执行原owner/管理员/状态检查。对既有允许超管跨租户的入口显式传入例外策略，默认不允许。
  • 原因：子租户SELECT可能包含Root行；AppStateService._load、AppMetaService、AppDataService读取App后会切执行租户，比较此时的ContextVar等于自证。数据管理本来owner-only，不能因复用生命周期管理员判断而扩权。
  • 重新考虑条件：将来权限领域正式统一这些业务动作时，沿其应用协议演进；本轮不新增FGA关系、action或投影模型。

D3：服务账号管理复用F019状态，增加本模块范围准入

  • 备选：直接复制模型页ScopeBar；给账号增加可编辑tenant_id；新增独立的本页租户状态；复用F019共享状态并补范围确认。
  • 选定：共享F019底层管理范围，在服务账号模块增加受控scope读写及请求范围确认；Root必须显式1，未选择时不可创建。管理写操作携带表单打开时的预期租户，后端与权威范围比对。
  • 原因：模型页Root映射为null，而服务账号无scope时可能按owner推导创建租户；直接复制会再次误建。改已有账号租户违反AC-21；仅本地保存无法发现其他标签页切换。
  • 重新考虑条件：F019将来改为标签页独立、带请求级scope的统一协议时整体迁移；不在本feature私建第二个共享状态源。

D4：发布校验放在选择待生效版本前，失败与清理解耦

  • 备选：仅接收时检查；先stage_version再在容器启动时查；在每个已明确阶段入口、stage前检查。
  • 选定：接收、Worker开始、版本/审批生成前、审批执行stage前和新增预览分别校验冻结owner/tenant。拒绝采用现有failure/outbox执行失败通道，清理独立推进。
  • 原因：bring_online先stage_version再分支；停用应用只登记pending也属于发布副作用。审批回调正常return会被记为executed，不能通过返回一个失败字典表达租户拒绝。
  • 重新考虑条件：发布流程将来提供统一阶段资格协议时再收敛；不为本次引入人员迁移锁或通用发布工作流重写。

D5：存量数据不动，使用原状态与原存储

  • 备选：迁资源、改owner、复制授权、增加失配状态表；在调用时判定资格。
  • 选定：无数据迁移；不新增失配状态或owner快照表。已接收发布用现有AppDeployment，后台运行用现有任务/赋值记录，账号管理使用现有F019及审计。
  • 原因：用户明确不移交/迁移；新增状态副本会与人员关系和凭据启停漂移。修复不能靠改116数据使问题暂时消失。
  • 重新考虑条件：用户以后明确提出资产移交/迁移，再立独立规格及运维流程。

4.2 服务账号调用链（设计）

原token哈希/有效性/前缀检查（允许原缓存）
  → 实时载入可信账号ID的当前账号、owner及唯一有效成员关系
  → 账号租户=凭据租户，账号启用；owner当前租户=账号租户
  → 更新当次principal的owner/name，保留凭据scope及原主体
  → 原delegate、路由scope、PAT/hosted_app及业务权限流程
  → 业务执行

公开资格能力：新增open_api/application/service_account_tenancy.py，导出：

  • revalidate_service_account(principal) -> OpenApiPrincipal：仅service_account执行实时检查；其他主体直接交给原校验流程。保留mode及授权主体，不改delegate目标。
  • require_owner_tenant(owner_user_id, tenant_id) -> None：供发布消费者校验冻结owner，抛出同一错误族；它不查询原服务账号当前owner，因此不追溯换提交归属。

实现逻辑由open_api域service编排、repository查询；其他模块只依赖application入口，不导入owner仓储或直接查询成员关系。查询不接受外部参数作为已认证账号ID。

仓储查询：为执行新增account/owner/成员关系的读取，使用现有权威数据库会话与受限bypass_tenant_filter；仅对已验证principal的账号、或可信发布记录的owner做精确查询。账户未启用/删除仍按现有26027处理；凭据与账号租户不同按26002处理。成员必须is_active=1且status=active，且结果唯一；不以first()或字典覆盖判定唯一。不把User.delete标记作为新准入条件，但硬缺失用户或不存在唯一有效关系按无法确认拒绝，保留AC-08语义。

新增关系判断不缓存，使用单次查询/受限关联查询避免逐行查成员。热命中请求增加一次当前绑定读取；冷请求仍可有原resolver读取，不为消除这一次读取引入跨请求状态。绑定变化完成后下一请求读取新关系；同一已开始阶段不承诺与人员变更保持全局事务隔离。

validate_bearer在命中/未命中合流后调用实时资格能力；不将更新后的owner资格结果写回为长期真相。原凭据撤销、有效期和scope缓存仍按既有上界工作，资格拒绝不删除/改写密钥。

MCP：传输层维持原准入；call_tool在执行工具及读取其principal前，根据本次真实MCP请求的Authorization/身份头，再进入公共open_api_access_context，以工具marker限定scope/modes；不使用构造的空Request作为鉴权来源。工具内ContextVar绑定本次新principal，退出恢复，不把并发工具身份写到共享全局对象。重新校验失败直接返回现有MCP错误格式；工具体不执行。现有stateless模式不增加服务器会话缓存。

已实现的消息接线：ChatMessageExecution冻结每消息operator、执行快照及session主体；后台用连接的浅副本执行，单独初始化身份绑定的agent/callback，原连接共享的会话/取消机制保留。复制是消息内部实现，不产生新用户身份。会话partition比对排除仅用于历史兼容的owner字段，因此owner合法改绑不会把会话变成owner的自然人会话。

WebSocket：在ChatManager.dispatch_client接受每个新业务消息、执行权限检查/投递任务之前，接入由v2端点传入的可选异步准入回调。common模块仅接受中性callable，不导入open_api域；未传回调的既有Web/匿名路径保持原行为。v2回调完整复核凭据、服务账号关系、委托，刷新本消息的operator、PermissionActor及执行快照；ChatClient.handle_message新增可选的消息级执行上下文参数，后台投递也捕获该不可变快照，不通过覆盖共享client.login_user或连接scope字典改变正在执行的旧消息身份。默认未传仍使用原连接身份，只有v2端点传入此准入回调。仍以服务账号会话subject分区，不把新owner变成会话所有人。请求返回/抛错后重置ContextVar。身份失败发送现有结构化错误并拒绝该消息/关闭1008；不能仅靠后台watcher的时间窗。原watcher继续处理原有凭据失效策略，不扩展成新会话治理功能；本次不要求中断已开始的单次流式业务。

4.3 应用请求的租户边界（设计）

新增app_runtime/application/tenant_access.py与其域service，提供只读且可单测的require_app_request_tenant(app_tenant_id, actor, *, allow_global_super=False)。入口校验使用不可变的请求来源：

  1. v1平台请求取已认证UserPayload.tenant_id；入口本来支持超管管理范围时，从admin.application.current_admin_scope读取并限定该范围；普通人不能采用scope头改变自己租户。
  2. v2/MCP取已认证principal.tenant_id及原PermissionActor；兼容的owner UserPayload只用于既有字段和业务owner检查，不借其角色推导服务账号权限。
  3. 先检查租户，后允许切换执行ContextVar到应用租户；已经切换也仍比较上述actor/principal，而非get_current_tenant_id()。当前/api/v1/apps没有被F019管理范围中间件列入，本次不新增该全局范围，也不把服务账号页面的scope头套到应用操作；原来允许的超管跨租户动作保持原入口语义。
  4. 跨租户拒绝复用AppNotFoundError/既有不可见语义；不返回对方tenant或确认目标存在。只有本来允许的全局超管入口可按其管理范围继续操作。

旧导出结果/任务引用 返回结果/文件前重新检查App、actor和operation归属 过期/删除等原判定保留；不以曾创建任务替代当前授权

allow_global_super仅在生命周期/元信息/原平台详情与日志等本来允许的路径使用；数据、CLI/MCP owner-only门及环境变量写/确认重建为false。全局super即使恰好是App的旧owner，也不能从owner相等分支绕过owner-only入口的同租户条件。无actor请求不能调用该人工检查API后获得默认允许。

请求被拒时不进入资源分配、数据库/MinIO写入、实例操作或投影删除；可记拒绝日志。租户一致仍须原权限运行时/业务规则允许，不建立“同租户就允许”的替代授权器。

内部调用区分：actor=None不作为通用豁免。发布对元信息的内部调用改走显式的update_meta_for_release(deployment_id, *, app_id, name, description, logo)应用入口，由内部可信部署记录解析app/tenant/owner并检查冻结资格；人工入口继续要求actor。stage版本采用F055公开的审批执行入口而不是对外暴露无来源版本指针写入。原AppStateService已承担状态写入，仍是唯一状态写入方。

这些读取不经过AppQueryService._load_visible，必须单独接入同一租户边界；不能用详情页面被拒绝推断API已安全。对应路由是既有入口，不新增HTTP API：

后台停止/回收/运行观测继续使用已认证服务身份与持久RuntimeOperation/Assignment，校验node、app、tenant及现有epoch；不构造来自App租户的假登录用户绕过人工入口。维持旧current批准版本的自动恢复不查询当前服务账号owner，也不被本次自然人请求闸门误伤；新代码发布/新增预览必须走下节冻结资格。

4.4 发布、审批及预览（设计）

F055新增应用入口app_publish/application/release_tenancy.py：require_release_eligible(app_id, version_id=None, deployment_id=None)。域service从现有AppDeployment查冻结owner/tenant，加载App并比较两者；调用open_api的require_owner_tenant。版本场景按(app_id,version_id)定位唯一发布记录，再校验既有版本/审批来源。不存在或不唯一时失败，不借当前服务账号改绑修补历史；不新增快照表。

4.4.1 批准执行与人工启动的接线合同

批准执行入口：F055的AppPublishScenarioHandler.on_approved(instance_id, payload_snapshot)仍由原Celery/outbox调用，转到PublishOnlineService.bring_online。新增app_publish.application.release_tenancy.qualify_approved_release(instance_id, payload_snapshot) -> ApprovedReleaseSource；它只接受服务端回调的引用并重读持久记录，不把传入payload本身视为已授权。新增只读approval.application.execution_source.get_business_approval(instance_id)包装审批域的现有repository读取，返回不可变的实例引用/状态/业务键/快照；不改通用审批引擎、outbox回调参数或状态。

批准来源必须同时符合：

  1. 持久实例属于app_publish_request、business_resource_type=app；instance.tenant_id、business_resource_id、business_key及持久快照指向同一个App、AppDeployment和AppVersion。
  2. deployment.approval_instance_id=instance.id，deployment的app/version/tenant/冻结owner与App一致；外部回调快照的这些引用必须与持久快照相等。缺失、歧义或不一致拒绝，不使用_deployment_ref的审计兜底对象作为授权来源。
  3. 持久审批状态代表已批准决定（approved、executing、executed，或原有显式重试流程中的execute_failed），拒绝pending/rejected/withdrawn/cancelled/exception。状态检查不另赋予重试权，调用仍只能来自原outbox或已授权人工入口；不新增重放API/自动重试策略。
  4. 固定owner当前唯一有效租户仍与发布租户相等。以上资格必须在stage、数据迁移、停止旧实例或启动新实例之前完成；App已删除时保留原取消/清理分支，不借此启动版本。

ApprovedReleaseSource是本次阶段的不可变内部值：approval_instance_id:int、deployment_id:str、app_id:str、version_id:str、tenant_id:int、owner_user_id:int，另带服务端批准执行的审计动作来源。由资格入口生成，不能由HTTP请求体反序列化或持久缓存，也不是新凭据/管理员身份。

启动接线：新增app_runtime.application.approved_release.start_approved_release(source: ApprovedReleaseSource) -> ActionResult，仅供F055成功资格检查后的批准执行路径使用。F055的_settle显式区分“人工actor”与“批准source”，两者必须且只能选一个；批准分支不再调用_owner_actor(app)，也不把source转换为UserPayload/SimpleNamespace后送入人工publish。runtime应用入口先比对source与重新加载的App/所选pending版本/tenant/owner；冲突沿原状态冲突返回，不能用另一版本的批准来源启动当前新pending。

两类入口共用AppStateService内部的既有启动体：人工入口先做认证租户与原动作权限，批准入口先验证可信source，再进入共用的容量、编排、探活及CAS代码。启动体不提供skip_tenant_check或actor=None通行开关，不新增外部路由。AppStateService仍是状态唯一写入方。审计使用独立的执行来源字段和批准记录中的owner归属，不把它当自然人认证身份或借用owner角色鉴权；原审计action/owner通知判定保持。

阶段边界：本次资格在stage之前完成，stage与其后的同一次批准启动共用该阶段source；不在stage后才新增owner资格拒绝再回写旧pending。source仅用于本次调用，后续回调重试、人工重试或重新提交均重新验证，不把旧source跨阶段复用。人员变更与已接受阶段不新增全局锁/跨阶段事务；版本并发仍由现有状态CAS处理。持久来源/版本对照不是再次构造调用者身份。

人工启动顺序：发布页request_manual_publish先检查认证租户，再做原owner-only；PublishOnlineService.manual_publish在_settle前验证该人工来源及冻结版本资格。独立actions/manual-publish、人工publish/resume在AppStateService的人工入口先做各自原权限，再在维护/实例动作前确认选定版本资格。配置确认重建也保持原owner-only。特别是协议v1的_settle调用migrate_for_release之前必须完成上述两层检查，不能只在迁移后的_start/_require_operator补检查；协议v2同样先检查后创建持久部署操作。

批准路径主线：outbox → on_approved → 持久批准来源与冻结owner资格 → stage_version → 清理预览 → 停用则仅保留pending / 否则_settle(source) → start_approved_release(source) → 原启动体。资格失败在stage前记录失败、继续终态清理并raise，沿原execute_failed通道；同版本自动恢复仍走原RuntimeOperation/Assignment，不调用本次人工或新批准入口。

4.5 超管服务账号管理（设计）

状态与身份：F019仍是唯一共享状态源。服务账号模块通过admin.application公开接口读取/设置scope；通过admin.application新增受控setter包装与租户可用性查询协议，仅为该模块增加可用租户确认，不修改模型/知识等其他管理页的业务权限；服务账号域不直接访问Redis或Tenant ORM。设置目标先验证全局超管、Tenant存在且active；Root选项提交1，不提交null。

新增静态路由置于/{service_account_id}之前：

范围确认头：X-Service-Account-Tenant: <positive integer>仅表达客户端看到的预期范围，不能授予租户或管理员权限。新UI在本模块所有读写请求携带该头，写操作必须用表单/确认框打开时固定的值，不能在axios拦截器发送前读全局最新值替换。后端公共管理依赖：

  1. 原get_service_account_admin确认身份，再由服务账号范围service从F019权威存储确认超管scope；非超管仅用其认证租户。
  2. 多租户超管写操作必须提供头，必须已有明确scope且与头相等；缺头、scope到期/清除或不符统一拒绝为范围变化，提示选择/刷新，不猜Root。
  3. 非超管可省头（保持原客户端行为），如提供则必须等于本人认证租户；不能借头选择别租户。单租户省头仍采用原Root行为。
  4. 验证所选Tenant仍active。scope读取故障拒绝，不能采用中间件已有的读取失败回退。验证通过后，本请求固定current/visible为该租户并在结束重置；后续标签页切换只影响下一请求。
  5. 所有管理写路由统一接入，包括批量授权变更；Pure-read POST候选过滤按读取处理，不以HTTP方法代替业务动作清单。详情/密钥等仍由get_row检查账号tenant，不以仅命中ID放行。
  6. 新UI的读请求也带预期头，若范围已变化即拒绝并要求刷新，旧响应不被显示。既有不带头的读请求保持当前管理范围语义，服务端仍校验active及目标范围；不将“没有预期头”变成跨租户不检查。

兼容性：多租户超管的旧脚本管理写请求需要补头并显式选择scope；这是防误写的有意收紧，后台/前端同步发布，升级说明给出示例。普通租户管理员和单租户写行为保持；业务密钥调用不读取该管理头。
