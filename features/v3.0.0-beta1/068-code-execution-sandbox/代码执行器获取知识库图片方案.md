# 代码执行器获取知识库图片方案

状态：方案，尚未实现。

目标：日常对话里，用户让模型把知识库中的图片做成 PPT 或其它文件时，本机执行器（`local`）和隔离执行器（`container`）都能读到这些图片。

## 现象与根因

2026-10-12 在 `192.168.106.107` 上做「找到所有图片并合并到 PPT」，先后出现下面几种失败。

| 现象 | 日志位置 | 根因 | 影响范围 |
|---|---|---|---|
| `FileNotFoundError: '/bisheng/knowledge/images/1/27/image1.png'` | trace `89269c75`，`add_picture` | 脚本把检索结果里的路径当成磁盘文件，执行目录是空的临时目录 | 本机、隔离 |
| `Failed to resolve 'bisheng.cloud'` | trace `7ffbba48`，`requests.get` | 模型不知道图片在哪，自己编了一个主机名；执行进程解析不了 | 本机、隔离 |
| `FileNotFoundError: 'output/combined_images.pptx'` | trace `f5cd4daa` | 隔离模式的执行目录里没有 `output/`；`ContainerExecutor.execute_code` 没有像本机那样建目录，copy-in 又只带普通文件，空目录不会过去 | 隔离 |

图片本身是存在的：同一路径经 `http://192.168.106.107:3001` 访问返回 200。页面能显示图片，是因为浏览器经前端转发到了 MinIO。代码执行器没有这条通路，而且也不应该有。

## 设计原则

1. 执行进程不访问 MinIO，不开外网。取图在后端进程里完成。
2. 只放行本轮检索结果里真实出现过的图片。模型自己写的路径不会触发下载，权限就是用户检索时已有的权限。
3. 不改写 `open`、`requests`，不做代理。让模型拿到一个真实存在的相对路径。
4. 取不到的图要如实告诉模型，不静默跳过。
5. 不改最终答案里的 Markdown 图片格式。

## 方案

### 1. 登记检索到的图片

新增请求级对象 `KbImageStage`，与现有 `ImageRegistry` 并列，登记入口是 `chat_service.py` 的 `_annotate_retrieved_chunk`。两个对象各管一件事：

| 对象 | 服务对象 | 何时有值 |
|---|---|---|
| `ImageRegistry` | `view_image`，让视觉模型读像素 | 模型开启视觉能力 |
| `KbImageStage` | 代码执行器，把图片放进工作目录 | 本次请求选了 `bisheng_code_interpreter` |

两者互不依赖，不能共用 `ImageRegistry` 的开关：今天 `image_registry=image_registry if visual_enabled else None`，关闭视觉时 `_annotate_retrieved_chunk` 直接返回原文，什么都不登记。

只登记路径符合下面形式的图片：

```text
/{public_bucket}/knowledge/images/{知识库id}/{文件id}/{文件名}
```

查询串去掉。其它路径、其它主机一律不登记。同一路径重复出现只登记一次。

#### 对 `_annotate_retrieved_chunk` 的修改

当前实现（`chat_service.py`）：

```python
def _annotate_retrieved_chunk(chunk: str, image_registry: ImageRegistry | None) -> str:
    if image_registry is None:
        return chunk
    return annotate(chunk, image_registry)
```

修改后：

```python
def _annotate_retrieved_chunk(
    chunk: str,
    image_registry: ImageRegistry | None,
    kb_image_stage: KbImageStage | None = None,
) -> str:
    # The stage serves the code interpreter and image_registry serves view_image.
    # They are independent, so the stage must run before the image_registry early return.
    if kb_image_stage is not None:
        chunk = kb_image_stage.annotate(chunk)
    if image_registry is None:
        return chunk
    return annotate(chunk, image_registry)
```

`KbImageStage.annotate(chunk)` 扫描片段里的 `![alt](url)`，对符合上面形式的 `url` 登记并在该图后面追加 `⟦file: uploads/kb/…⟧`，其它图片原样保留。两个锚点同时存在时，`⟦img#N⟧` 紧跟在图片后面，`⟦file: …⟧` 在其后，互不干扰。

#### 需要同步改的调用链

`_annotate_retrieved_chunk` 有两个调用点，都要把 stage 传进去：

| 调用点 | 当前 | 修改 |
|---|---|---|
| `DailyChatCitationToolWrapper._dump_knowledge_chunks` | 传 `self.image_registry` | 新增字段 `kb_image_stage`，一并传入；`wrap`、`_wrap_daily_chat_citation_tool` 增加同名参数 |
| `_build_knowledge_search_tool` 内 `results = [_annotate_retrieved_chunk(chunk, image_registry) for chunk in chunks]` | 传闭包里的 `image_registry` | 增加参数 `kb_image_stage` 并传入 |

`_prepare_tools` 增加参数 `kb_image_stage`，并转交给上述两处。

stage 在 `_agent_event_stream_impl` 里、`image_registry = ImageRegistry()` 附近创建，调用 `_prepare_tools` 时传入。只有本次请求的 `tool_payloads` 里包含 `tool_key == "bisheng_code_interpreter"` 才传，否则传 `None`：没选代码执行器时，检索结果不多出任何锚点，也不增加 token。

#### 挂载到执行器

`_prepare_tools` 初始化到 `bisheng_code_interpreter` 之后，把同一个 stage 挂到工具的执行器上。stage 在检索时才被填充，挂载顺序与知识库工具的创建顺序无关。

实现时要确认两点：

- `ToolExecutor.init_by_tool_id` 返回的对象仍能取到 `.executor`。取不到就不挂载并记一条 warning，行为退回到今天的样子。
- `E2bCodeExecutor` 没有 `attach_stage`。`BaseExecutor` 提供一个空实现，E2B 调用后什么也不做。

#### 范围限制

stage 只在本轮请求内有效。用户下一轮说「把刚才那几张图做成 PPT」时，如果历史里没有带回上一轮的检索结果，模型需要重新检索，stage 才会再次登记。历史是否带回工具结果，实现时再确认；本方案只保证本轮检索到的图片。

### 2. 在检索结果里告诉模型路径

在每张图后面追加一个锚点，原 Markdown 不动：

```text
![image1.png](/bisheng/knowledge/images/1/27/image1.png)⟦file: uploads/kb/1/27/image1.png⟧
```

最终答案仍然保留原始 `![](...)`，页面渲染和系统提示词里「保留原始 Markdown 图片格式」的规则都不受影响。

代码执行器的工具说明增加一句：检索结果中 `⟦file: …⟧` 给出的路径可以直接 `open` 或传给 `add_picture`；不要访问 URL，不要自己写主机名。

### 3. 执行前把图片写进工作目录

`_prepare_tools` 里，初始化 `bisheng_code_interpreter` 之后，把 `KbImageStage` 挂到执行器上。

`LocalExecutor.run` 在调用 `run_with_dir` 之前，把已登记的图片写到：

```text
{dir_path}/uploads/kb/{知识库id}/{文件id}/{文件名}
```

取图使用执行器已有的 `self.minio` 配置建 MinIO 客户端（`BaseExecutor._minio_client`），也就是后端进程用的同一份配置。

- 本机：子进程的工作目录里直接有这些文件。
- 隔离：`ContainerExecutor` 继承同一个 `run`，现有 `_copy_in` 会把 `uploads/` 带进沙箱。runner 不需要 MinIO 地址、密钥或外网。
- 先落盘再快照：这些文件在运行前就存在，不会被当成产物上传，也不会出现在 `file_list` 里。

### 4. 限制与反馈

上限都做成可配置项。

| 限制 | 作用 | 默认值 |
|---|---|---|
| 单次运行最多写入的图片张数 | 限制后端逐张读 MinIO 的次数和隔离模式 copy-in 的包大小 | 100 |
| 单次运行写入的总字节数 | 同上，按字节兜底 | 5 × `max_copy_in_bytes`，当前 `max_copy_in_bytes` 默认 50MB，即 250MB |
| 单张图片大小 | 超过则跳过 | `max_copy_in_bytes`，当前默认 50MB |

- 总字节数的默认值是按 `max_copy_in_bytes` 推出来的，不单独写死 250MB。`max_copy_in_bytes` 改了，总上限随之变化；显式配置了总字节数则以显式值为准。
- `max_copy_in_bytes`（默认 50MB）本身是隔离模式 copy-in 的**单文件**上限，不是总量。这里只是借它的数值做基准，两者含义不同。
- `max_copy_in_bytes` 在配置里属于隔离执行的配置。本机模式也用同一个基准值，所以读取它的位置不能依赖 `ContainerExecutor` 的实例属性，要从配置读。
- 内存风险：隔离模式 `_copy_in` 会把所有待发送文件 `fh.read()` 进内存，再打成 tar.gz。总量按 250MB 算，一次运行可能在后端进程里同时占用 250MB 以上。上线前要确认后端容器的内存余量，必要时把总字节数的默认值调低，或让 copy-in 改为流式，后者超出本方案范围。
- `view_image` 每轮最多 3 张是为了控制视觉模型的上下文，和这里无关，不沿用。
- 已知样本是文件 27 的 `image1.png`，约 333KB。按这个大小，100 张约 33MB，远低于总字节上限；实际由张数先触顶。
- 配置放在现有配置体系里，不新增 YAML 顶层 key，具体位置实现时按 `src/backend/AGENTS.md` 的配置约定确定。
- 超限、对象不存在、读取失败，都跳过该图，并在返回给模型的 `log` 里列出哪几张没取到及原因。超限时要写明是哪一条限制，以及当前上限。
- 写盘时只用路径中的数字 id 和文件名拼目标路径，文件名含 `/` 或 `..` 的直接拒绝。

### 5. 隔离模式补 `output/` 和 `scratch/`

不要用 `output/.keep` 占位：`_walk_regular_files` 和 `_snapshot_files` 都会跳过以 `.` 开头的文件，占位文件过不去。

改在 runner 侧：`sandbox-runner/execute.py` 的 `handle_exec` 里，写 `_run.py` 之后、`_chown_tree` 之前，确保 `output/` 和 `scratch/` 存在。这样模型直接 `prs.save('output/x.pptx')` 也能成功，行为与本机一致。需要重新构建并发布沙箱镜像。

### 6. 失败时的提示

脚本文本里出现 `knowledge/images/`，且执行失败时，沿用 `absolute_path_advisory` 的做法，在日志末尾追加一句：请改用检索结果里 `⟦file: …⟧` 的相对路径。只提示，不拦截。

## 测试

- 路径解析：合法路径被登记；其它主机、其它桶、带 `..` 的路径不登记。
- `_annotate_retrieved_chunk` 四种组合（可扩展 `test/workstation/test_daily_chat_image_view.py`）：
  - 视觉关、stage 开：追加 `⟦file: …⟧` 并登记，没有 `⟦img#N⟧`（这是今天会漏掉的情况）。
  - 视觉开、stage 开：两种锚点都在，`⟦img#N⟧` 在前。
  - 视觉开、stage 关：与现在完全一致。
  - 都关：返回原文。
- 调用链：`DailyChatCitationToolWrapper` 和 `search_knowledge_bases` 两个入口都能登记。
- 没选 `bisheng_code_interpreter` 时，检索结果里没有 `⟦file: …⟧`。
- 越权：模型写的路径不会触发下载，只有登记过的对象会被读。
- 落盘位置：文件出现在 `uploads/kb/...`，且不进 `file_list`。
- 限额：分别超过张数、总字节数、单张大小时跳过，`log` 里点名是哪条限制；调整配置后上限随之变化。
- 隔离：copy-in 的成员里包含 `uploads/kb/...`；runner 创建会话后 `output/` 存在。
- 回归：未启用知识库、没有图片时，执行器行为与现在一致。

## 不做的事

- 不让本机子进程或沙箱直接访问 MinIO，也不给沙箱开外网。
- 不改写或代理 `open`、`requests`。
- 不动 E2B 执行器。
- 不处理灵思、工作流 Agent、助手：它们的工作目录和检索链路不同。
- 「代码有语法错误时整段被 `sh -c` 执行」（`sh: 1: from: not found`）是另一个问题，单独处理。
- 视觉模型看图走 `view_image`，不经过代码执行器，本方案不改它。

## 待确认

- 锚点格式用 `⟦file: …⟧`，只出现在模型看到的检索结果里。如果更希望把相对路径写进 Markdown 的 alt 文本，需要先确认前端渲染不受影响。
- 总字节数默认 250MB 的内存占用：见 §4 的内存风险，上线前确认后端容器内存。
