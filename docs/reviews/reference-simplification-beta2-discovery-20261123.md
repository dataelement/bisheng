## 用户最新明确的核心流程

引用关系只是辅助提示。删除某个模型或知识空间时，查询一下已有引用关系，存在就提示用户，用户可以继续删除。知识空间元数据不依赖引用关系；引用是否登记、是否同步成功、是否完成验收，都不能成为元数据处理或删除的前提。

模型和知识空间本身的引用关系保留。例如，工作流使用模型、助手使用知识空间，以及知识空间使用 Embedding 模型，都属于已有引用关系；知识空间的元数据字段定义及元数据值不作为引用来源或目标，也不因修改元数据而要求引用索引完整。这里不是取消模型引用，也不是取消对知识空间本身的引用提示。

工作流等业务修改后，引用关系通过异步任务同步；同步失败增加重试即可。业务修改已经成功，就不能因为引用同步失败而回滚、拒绝保存或拒绝后续使用。

原业务配置是事实来源。引用索引允许滞后，不承担强一致保证，也不依赖任何一次升级的 Run、Coverage 或验收证书。

引用记录复用现有数据表及已有记录，不新建替代引用体系，不为本次简化要求数据迁移、全量回填、删账本或重做升级。字段及读写兼容在设计阶段按现有约束处理。

### 删除流程

1. 按原业务规则检查当前用户能否删除，以及资源自身是否满足删除条件。
2. 查询该模型或知识空间已有的引用记录。
3. 有引用则展示提示；查不到时按现有查询结果处理，不宣称经过全库强一致验收。辅助查询失败可提示暂无法获取引用，不影响删除。
4. 用户确认后执行原业务删除；不锁定引用集合，不在执行时再次证明引用没有变化，不因引用存在而另建强制删除流程。

引用提示遵循已有租户和资源可见范围。删除不自动修改引用方的工作流、助手或其他业务配置；之后实际使用缺失依赖时，由对应业务返回实际错误。

### 引用维护流程

1. 工作流等业务按自身规则保存成功。
2. 业务提交后触发异步引用同步任务。
3. 任务读取该来源当前配置，更新该来源的引用记录；失败记录日志并重试。
4. 来源已删除时清理对应引用记录；不因残留记录影响其他租户或其他资源操作。

任务按来源更新，重复执行可以替换同一来源的结果；不把历史事件增量重放、全局版本一致性或引用锁协议作为本轮前提。任务派发、重试的具体参数在设计中沿用现有异步设施，不承诺强一致或恰好一次交付。

## 明确移除的过度设计

此前方案将辅助索引扩展成了可靠一致性子系统，偏离用户目标。本轮收敛为普通异步同步及失败重试：

- 不要求业务事务额外写引用修订、dirty/repair 或 outbox 待修账本。
- 不因引用索引、引用待修记录或同步任务异常使已成功业务失败。
- 不要求删除时验证全局 Coverage、租户 inventory、全局 epoch 或升级 Run。
- 不把引用摘要、来源修订或引用完整性签入删除执行凭证，也不因引用变化要求用户反复确认。
- 不为合法零引用、缺登记来源或索引滞后建立业务准入门槛。
- 不把引用回填完成、证书签发或后台可靠接管作为正常业务和开服的额外条件。
- 不把“完整/部分/未知”三态协议、治理面板、持久补投系统作为简单提示功能的必备设计。

业务自身的权限、租户隔离、真实目标状态和处理冲突仍遵循各自规则。业务数据库提交失败仍是保存失败；引用同步失败只是辅助任务失败，二者分别处理。

## 当前代码中需要拆除的耦合

以下是已核查的现有行为，不是新方案要求。

| 入口 | 现有耦合 | 简化方向 |
| --- | --- | --- |
| 空间及文件删除查询 | `knowledge/application/{space_delete_reference_query,direct_delete_reference_query}.py` 在收集前后验证全局及本租户 Coverage | 引用查询独立提供提示，不决定删除资格；文件等其他删除入口的具体范围待补充需求 |

| 前端删除确认 | `KnowledgeDeletionDialog.tsx`、`manage/useModelRemoval.ts` 以引用检查完成作为提交条件 | 引用提示失败或未同步不能禁用删除 |

### 166 案例

当前 `_global` 检查发现某个 Run 的租户已经不在租户表，就报 `production_coverage_orphan_coverage_run`。租户删除服务没有清理这些覆盖记录，因此残留可以影响其他租户删除预检。

本次简化的处理是解除业务对这些验收记录的依赖。历史 Run 可保留用于其原有审计或恢复职责，不要求删除账本才能恢复业务。本次没有连接 166，现场日期、镜像和当时验收结论沿用用户提供的信息。

## 背景文档的取舍

已读用户指定的 `f118-upgrade-defaults-20261120/docs/reviews/production-upgrade-20261120/05-reference-simplification-background.md` 及其中引用的 `04-remediation-plan.md §7`。背景问题继续作为核查依据；其中解决方案以用户本轮明确的简单异步策略为准，不能把背景建议全部转成新系统要求。

| 背景内容 | 本轮处理 |
| --- | --- |
| 缺索引导致读取、编辑、保存和执行失败，零引用也不能使用 | 纳入：解除这些入口的索引准入依赖 |
| 局部删除、租户创建受全局账本影响 | 纳入：移除全局引用验收依赖 |
| 引用存在或未知时删除被硬拦截 | 纳入：删除时查询已有引用并提示，引用不决定删除资格 |
| 保存后索引更新失败 | 按最新要求：异步任务失败重试，不影响业务成功 |
| 事务内必须记录引用修订、持久待修，再可靠补投 | 不采纳为本轮要求；不增加业务事务对引用账本的新依赖 |
| 全量回填、覆盖证书及后台可靠接管决定是否可开服 | 不采纳为引用层的开服要求；核心数据和权限仍按自身迁移规则验收 |
| 时间字段变化导致索引证明失效 | 不再通过引用一致性证明约束业务；任务从当前配置更新关系 |
| 存量 Run、索引和证书兼容 | 保留历史数据及其原有职责；日常业务不再依赖它们，不要求重做已完成转换 |
| 批次回填、性能优化、治理面板与覆盖进度 | 作为独立维护工作按需考虑，不扩成核心提示流程的必要条件 |

## 后续验收重点

- 既有模型、知识空间及空间所用 Embedding 模型的关系仍可查询；元数据字段和元数据值不作为引用来源或目标。
- 元数据增删改及已有元数据处理不因模型引用索引缺失、同步失败或 Coverage 不就绪而拒绝；其自身权限、参数和处理冲突规则仍生效。
- 删除模型或知识空间时，有引用则提示，用户确认后可继续。
- 引用查询失败、索引缺失或滞后，不影响资源元数据和删除操作。
- 工作流保存成功，引用同步失败并重试，工作流仍能正常查看、编辑和使用。
- 合法零引用来源没有索引记录，也不会报引用未就绪。
- 其他租户存在孤儿 Run 或未验收记录，不影响本租户操作及新租户创建。
- 任务重试按当前来源配置更新引用；来源已删除时清理对应记录。
- 权限与真实业务依赖错误仍由业务自身处理，引用提示不产生额外授权。
- 复用原引用表和原记录，升级此功能不要求数据迁移或先做全量引用回填。
