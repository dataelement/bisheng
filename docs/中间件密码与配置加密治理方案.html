更新：2026-11-15。目标：运维继续执行原部署命令，部署程序完成密码输入、加密、配置同步、启动检查和故障恢复。

2026-11-15 补充：旧 ES 无认证升级

用户已确认，纳入原部署脚本。本地 ES 8.12.0 单节点协议测试通过。166 已由用户执行原命令并选择开启认证；下面的验收矩阵不因此改为全部通过。

旧拒绝条件已改为服务端识别、交互选择和有状态迁移。需求 AC-71～AC-76，面向原标准 Compose 的 Bitnami ES 8.12.0 单节点；不新增独立部署命令或另建运行栈。

入口与识别

在 credential_setup 的 v1 转换与 rotation_select 之前增加只读 ES 识别，首次安装沿用现有初始化路径。归属从原容器项目标签、镜像 ID、端口、实际挂载和当前集群 UUID 交叉核对；新代码目录允许与原数据目录不同，不覆盖 3.0.0。识别工具通过原项目网络访问服务端，检查安全设置与认证结果，不依靠 config.yaml 是否存在 basic_auth。安全开启但允许匿名访问不能归为安全关闭；权限不足、网络失败和服务端关闭认证必须区分。

无认证的“保留”选择保留安全关闭和无 basic_auth，写入签名 pending 策略，不在普通部署时强制改密。启用选择收集加密输入，交互沿用原命令；若服务端已开认证、客户端没有认证来源，则在同一入口引导导入现用管理凭据，校验后保存加密配置，不擅自重置未知账号。已认证的普通改密继续复用现有轮换路径。

准备、执行与状态

实际 ES 子状态：PREPARED → FROZEN → PASSWORD_INTENT → PASSWORD_SET → VERIFIED；外层沿用 SEALED → VERIFIED → CONSUMERS_SWITCHED → COMPLETE。所有跨服务写入前先持久化意图。状态签名绑定源/目标配置、外置密钥身份、原容器镜像和集群 UUID；密码、完整运行配置、原环境、索引基线和恢复材料整体密封，不把密码摘要公开。保持部署锁，并要求其他节点停止写入。

PREPARED 前对照新旧配置验证只有 ES 认证及声明的消费者发生变化。保留原 data 挂载和自定义配置，固化原镜像；备份配置不等于数据备份，维护确认须说明使用客户已有数据备份，不宣称配置副本能恢复索引损坏。停止本项目写入消费者后记录所有业务索引 UUID、文档数和别名；不通过删除索引或重建数据目录初始化 ES。

宿主脚本负责 Docker 编排，后端模块只负责纯数据编译、加密状态和 ES SDK 操作。ELASTICSEARCH_ENABLE_SECURITY 配置与存量 elastic 密码是两个动作；原生认证开启后优先验证已保存目标身份。若尚未设置目标密码，在核实身份的本地容器内使用该版本官方 elasticsearch-reset-password 工具（临时 file realm 用户）完成设置；密码只经受控 stdin/内存文件传递，不用 argv、Docker Env 或明文文件。该工具的非 TTY 输入、临时用户清理及 tmpfs 要做真实版本验证；若不适配，保持停写，不换成明文命令行。不能假定 Bitnami 在发现已有 data 时会重新初始化密码。

返回结果未知时先检查目标凭据和 PASSWORD_INTENT。能验证则继续；不能验证时在原入口提供明确的恢复选择，不盲目反复重置。PASSWORD_SET 后才激活后端、worker 及实际发现的统计 ES 消费者配置；同端点可共用管理身份，外部端点不得误改。v1 adopt-key 缺失的原生密码材料在内存重建，运行配置从实际容器捕获；新交付目录只读导入旧包，不覆盖旧目录。

完成与失败恢复

完成必须同时证明目标认证成功、安全设置开启、匿名业务访问拒绝、原集群/业务索引 UUID 保留、冻结后的文档数与别名一致；再进行读取及可销毁临时探针索引的写读删，不写客户业务文档；探针归属先持久化，续跑只清理归属一致的索引。最后验证实际后端/worker 消费者配置和调用链，无引用旧材料后才能按原有清理规则收尾。后续执行原命令不重复设密。

开启认证前失败：保留原服务状态、原配置和数据；停写后失败：保持应用暂停，重跑原命令恢复。已开启认证后失败：默认继续同一目标，禁止自动降级无认证。用户明确选择配对回退时，验证旧镜像、数据归属和配置备份，恢复原安全模式及原消费者配置，并重新检查索引与连接；不恢复/删除整份数据目录。若目标密码曾写入安全索引，回退不能把“恢复安全关闭”描述为清除安全索引记录，下一次开启仍以原生账号现状为准。

影响与边界

影响 ES 容器和使用 ES 的 API/worker/统计客户端，维护期间搜索/写入短暂中断；MySQL、Redis、MinIO 和 Milvus 密码不随本次操作改变。集群、已有 TLS 与 file realm 被禁用的环境需要相应适配，禁止关闭 TLS 来套用 HTTP 单节点流程。代码改动应集中在凭据模块与原入口，不触及业务表或双数据库逻辑；C1/C2/C3/C4 不引入变化，C6 通过外置密钥和密封状态保持。

参考：官方最小安全配置 set-up-minimal-security，官方设密工具 reset-password。锁定版本真实行为仍以实际测试为准。

一、业务背景

客户环境需要各自独立的中间件密码，不能统一使用默认弱密码。MySQL、Redis、ES、Milvus 及统计 ES 至少 6 位；MinIO 原生密钥至少 8 位。不要求数字、字母、符号同时出现，已知默认密码和占位符仍拒绝。安全优化必须保持一条命令部署的操作方式，允许运维在部署过程中逐项选择是否改密。

二、原有安全问题

治理前存在默认密码、配置中明文密码、组件覆盖不一致、固定密钥风险，以及原生启动文件、轮换阶段和恢复副本残留明文的问题。仅加密后端 config.yaml 无法覆盖原生组件启动与历史材料。

三、部署入口

继续使用 bash docker/install.sh，或公司原有入口 bash scripts/deploy.sh install。首次部署隐藏输入并二次确认；重新部署逐项询问 MySQL、Redis、MinIO、ES、Milvus 是否修改，默认保留。运维无需手工运行加解密命令。

四、技术实现

首次部署生成外置主密钥，不写入代码或镜像。主密钥文件使用受控权限 600 或经过验证的 640；非 root 部署依靠文件所有者或专用组访问，不能放开到所有人可读写。

后端密码字段使用密文；部署输入、原生配置包、历史材料和恢复备份使用经过身份绑定与完整性校验的加密文件。原生组件通过配套静态启动工具，在经过检查的内存文件系统内获取启动所需明文，工具随后执行原组件入口。部署期间拒绝不符合要求的交换分区、转储与休眠环境。

六、旧版升级与恢复

经核验的受管 v1 包自动转换为 v2，实际密码不变。切换前加密备份，验证新包、原生连接、应用状态及所有容器的旧文件引用后才清理旧文件。清理要求实际挂载完整源目录，不能将容器看不到文件当作删除成功；中断后重新执行原命令恢复。

主密钥必须与对应凭据材料配套备份，保存到公司批准的受限位置。丢失主密钥无法从密文重建密码。失败不得删除状态目录、覆盖密钥或擅自修改原生密码。
