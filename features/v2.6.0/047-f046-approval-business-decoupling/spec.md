# Feature: F046 审批流程与知识业务解耦

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
>
> 本文档只回答做什么、验收标准与范围边界。模块接口、事件协议、状态映射、迁移步骤、服务拆分和文件清单在后续 `design.md` 中确定。

**关联需求**: 2026-08-12 用户确认“审批模块只负责审批流程，具体业务数据由业务模块管理；本次先只拆 F046”
**Feature ID**: F047
**优先级**: P0
**所属版本**: v2.6.0
**依赖**: [F025-approval-center-unification](../025-approval-center-unification/spec.md)、[F046-knowledge-space-file-change-approval](../046-knowledge-space-file-change-approval/spec.md)

> **范围边界**
> - **本次纳入**：
>   - 仅拆分 F046“知识空间文件变更审核”与 F025“统一审批中心”之间的职责边界。
>   - F025 继续负责 F046 的场景、流程、节点、审批实例、审批任务、审批决定、审批日志及审批通知。
>   - Knowledge 域负责 F046 的待审业务数据、上传暂存、目录归属、正式入库、权限写入、解析调度、文件变更执行、业务失败、重试、清理和补偿。
>   - 审批决定与知识业务执行之间保持可靠、幂等、可恢复的衔接。
>   - 对存量 F046 审批和执行中数据提供无重复执行、无业务丢失的平滑收敛。
> - **本次明确排除**：
>   - 不拆分菜单权限申请、频道订阅、知识空间加入、个人用户邀请确认等其他审批场景。
>   - 不全局删除或改变 F025 为其他场景提供的业务执行状态、异常处理或 outbox 能力。
>   - 不改变 F046 的审核总开关、按空间配置、私密空间免审、审核人范围、或签规则及现有权限规则。
>   - 不改变上传、重命名、移动、删除最终应产生的业务效果及其安全校验。
>   - 不新增第二套审批事实源，不恢复或扩展已废弃的 `approval_request` 旧审批能力。
>   - 不以本次解耦为由重新设计知识空间文件页或审批中心的整体交互。

### 与 F046 原需求的覆盖关系

本 spec 仅覆盖 F046 原 spec 中将“业务执行终态”绑定到 F025 审批终态的口径；其余验收标准继续有效：

- F046 **第 24 条验收标准**：删除业务是否完成由 Knowledge 域判定，不再以 F025 实例进入业务执行成功作为完成条件。
- F046 **第 32 条验收标准**：上传、重命名、移动或删除的业务执行失败由 Knowledge 域记录和恢复，不再把已通过的 F046 审批改写为审批执行失败。
- F046 **第 34 条验收标准**：文件页面与审批中心对同一申请的“审批决定”保持一致；业务执行进度和结果以 Knowledge 域为准。

## 1. 用户故事

### 1.1 审批中心维护者

作为 **审批中心维护者**，
我希望 **F025 只管理 F046 的审批流程和审批事实，不理解文件暂存、入库、解析、删除或补偿规则**，
以便 **审批引擎保持通用，知识业务演进不会持续侵入审批模块**。

### 1.2 知识空间业务维护者

作为 **知识空间业务维护者**，
我希望 **Knowledge 域完整拥有文件变更申请及其审批通过后的业务生命周期**，
以便 **业务状态、失败恢复和数据一致性可以在同一业务边界内管理**。

### 1.3 申请人与审核人

作为 **文件变更申请人或审核人**，
我希望 **审批决定与业务执行结果含义清晰且不会互相覆盖**，
以便 **能够区分“审批是否通过”和“文件变更是否执行成功”**。

### 1.4 运维与审计人员

作为 **运维或审计人员**，
我希望 **审批问题与知识业务执行问题可以分别定位、重试和审计**，
以便 **处理业务失败时不篡改已经成立的审批事实，也不重复发起审批**。

## 2. 验收标准

### 2.1 领域职责边界

- **AC-01** — THE SYSTEM SHALL 仅由 F025 管理 F046 的审批场景、流程、节点、审批实例、审批任务、审批决定、审批日志及审批通知。
- **AC-02** — THE SYSTEM SHALL 仅由 Knowledge 域管理 F046 的待审文件、暂存对象、目录归属、业务请求、资源占用、正式文件变更、权限写入、解析调度、清理及补偿数据。
- **AC-03** — THE SYSTEM SHALL 禁止 F025 直接创建、修改或删除 F046 业务数据，也禁止 F046 直接创建、修改或删除 F025 审批数据。
- **AC-04** — THE SYSTEM SHALL 使 F025 的 F046 待办列表、审批详情和审批决定在 Knowledge 业务服务暂时不可用时仍可基于审批事实与申请快照工作；需要实时业务鉴权的决定仍须失败关闭。
- **AC-05** — THE SYSTEM SHALL 使 Knowledge 域独立提供 F046 的业务执行状态、失败原因、重试、清理及补偿能力，不依赖 F025 生成业务状态投影。
- **AC-06** — THE SYSTEM SHALL 保持除 F046 外其他审批场景的流程、状态、业务执行、异常处理、通知及用户可见行为不变。

### 2.2 审批决定与业务执行

- **AC-07** — WHEN F046 申请创建成功, THE SYSTEM SHALL 建立唯一可追溯的业务申请与审批实例关联，并保持审批事实和业务事实各自只有一个权威来源。
- **AC-08** — WHEN F046 最后一个审批节点通过, THE SYSTEM SHALL 将审批流程确定为“已通过”，且该审批决定不得等待上传、重命名、移动、删除、权限写入、解析调度或外部存储操作完成。
- **AC-09** — WHEN F046 申请被拒绝、撤回或取消, THE SYSTEM SHALL 形成对应审批终态，Knowledge 域不得启动尚未开始的正式文件变更执行。
- **AC-10** — WHEN F046 审批通过, THE SYSTEM SHALL 可靠地通知 Knowledge 域启动对应业务执行；同一审批结果被重复投递时，Knowledge 域不得重复创建正式文件、重复应用变更或重复产生不可逆副作用。
- **AC-11** — IF 审批结果暂时未能交付给 Knowledge 域, THEN THE SYSTEM SHALL 保留已成立的审批决定并允许后续恢复交付，不得回退审批决定或要求用户重新审批。
- **AC-12** — IF F046 业务执行失败, THEN THE SYSTEM SHALL 在 Knowledge 域记录可观测的业务失败及恢复状态，并保持原审批决定为“已通过”。
- **AC-13** — WHEN 用户重试已通过审批的 F046 业务执行, THE SYSTEM SHALL 复用原审批结果，不得创建新的审批实例、重新打开审批任务或要求再次审核。
- **AC-14** — WHEN F046 业务执行成功, THE SYSTEM SHALL 由 Knowledge 域确认业务完成，且不得通过改写审批决定来表达业务成功。
- **AC-15** — IF 业务执行前的资源、目录、名称、权限或结构约束已经变化, THEN THE SYSTEM SHALL 由 Knowledge 域重新执行现有业务校验；校验失败应记录为业务失败，不得改写审批决定。

### 2.3 状态展示与用户操作

- **AC-16** — THE SYSTEM SHALL 在审批中心仅展示 F046 的申请快照、审批进度、审批任务、审批意见和审批决定，不展示由审批模块计算的解析、入库、清理或补偿状态。
- **AC-17** — THE SYSTEM SHALL 在知识空间文件页面展示 F046 的待审数据、目录位置、业务执行进度、业务失败原因及可用的重试或清理操作。
- **AC-18** — WHEN 用户从审批中心或知识空间文件页面处理同一 F046 待办, THE SYSTEM SHALL 在两个入口展示一致的审批决定，且不得因入口不同产生两次审批操作。
- **AC-19** — WHILE F046 审批尚未形成终态, THE SYSTEM SHALL 继续按 F046 原有规则限制待审上传及正式资源变更，不得因职责拆分提前入库、解析、移动、重命名或删除。
- **AC-20** — WHILE F046 审批已经通过但业务仍在执行, THE SYSTEM SHALL 在审批中心显示“审批已通过”，并在知识空间业务页面显示真实业务进度；两者不得被合并为一个含义不清的状态。
- **AC-21** — IF F046 业务执行失败, THEN THE SYSTEM SHALL 仅在 Knowledge 业务入口提供业务重试或清理操作；审批中心不得把该失败作为重新审批或修改审批决定的入口。

### 2.4 存量数据与发布兼容

- **AC-22** — WHEN 本次职责拆分上线, THE SYSTEM SHALL 保持存量 F046 待审批、审批异常、已拒绝、已撤回及已取消记录的审批决定、待办可见性和审计记录不变。
- **AC-23** — WHEN 本次职责拆分上线时存在已通过但业务尚未完成的 F046 记录, THE SYSTEM SHALL 使其继续收敛到唯一业务结果，不得遗漏执行、重复执行或要求重新审批。
- **AC-24** — WHEN 本次职责拆分上线时存在历史业务执行成功或失败记录, THE SYSTEM SHALL 保留其审批审计可读性，并由 Knowledge 域继续提供对应业务结果和可用的恢复能力。
- **AC-25** — IF 发布期间新旧任务或重复消息并存, THEN THE SYSTEM SHALL 对同一 F046 业务申请维持单一有效执行，并拒绝过期执行继续推进业务状态。
- **AC-26** — THE SYSTEM SHALL 支持回滚应用版本而不丢失审批决定、F046 业务申请、待审原文件、执行进度或补偿所需信息。

### 2.5 安全、隔离与可观测性

- **AC-27** — WHERE 系统存在多个租户, THE SYSTEM SHALL 对审批结果交付、F046 业务执行、状态查询、重试、清理和补偿保持严格租户隔离。
- **AC-28** — WHEN Knowledge 域接收“审批已通过”结果, THE SYSTEM SHALL 在执行正式业务前继续复用上传、重命名、移动或删除所需的既有权限与业务安全校验。
- **AC-29** — IF 审批结果关联的业务申请不存在、不属于当前租户或与审批快照不一致, THEN THE SYSTEM SHALL 拒绝业务执行、记录可观测异常并避免产生部分业务副作用。
- **AC-30** — THE SYSTEM SHALL 分别提供“审批流程失败或异常”“审批结果交付失败”“知识业务执行失败”的可观测信息，使运维人员能够判断故障所属边界。
- **AC-31** — THE SYSTEM SHALL 保留从 F046 业务申请追溯审批实例、审批决定和审批日志，以及从审批实例追溯对应业务申请的能力，同时不得把任一方的可变业务状态复制为另一方的事实源。

## 3. 边界情况

- 同一审批通过结果被重复、乱序或延迟投递时，Knowledge 域只能推进一次有效业务执行。
- 审批通过后 Knowledge 服务暂时不可用时，审批决定仍成立；恢复后应继续交付和执行，不得重新审批。
- Knowledge 业务执行已经产生部分副作用后失败时，恢复和补偿只由 Knowledge 域负责，审批决定保持不变。
- 存量 F046 记录处于原“执行中”或“执行失败”状态时，升级过程不得把它误判为新的待审批任务。
- 审批人关系在待办期间变化时，仍按 F046 原有动态审核人规则处理；职责拆分不得扩大历史审批人的查看或处理权限。
- 业务申请已经清理或损坏但审批结果仍被投递时，应失败关闭并留下可审计异常，不得凭审批快照重建不完整业务数据。
- 其他审批场景继续使用原有业务执行路径；F046 的拆分不得改变其状态机或重试语义。
- 知识空间文件页与审批中心同时提交决定时，只能有一个决定生效，另一请求应返回最新审批结果而不是触发业务重复执行。
