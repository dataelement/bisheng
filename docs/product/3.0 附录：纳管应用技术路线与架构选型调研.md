## 0. 总判定

**既有技术路线整体成立，且最核心的两条假设有商业产品官方文档逐字级的同构先例背书**：app-proxy「双 token + 身份头注入」与 manifest capabilities 声明式收权，与 Databricks Apps 的公开架构逐项对应。需要修正的是三处工程细节（header 剥离归一化、gVisor 档位判定规则、LoongArch 分档矩阵）和一处路线收窄（构建路线锚定平铺 Dockerfile 模板、显式否决 buildpacks 自动检测系）；补缺轮进一步确认：自研「薄」runtime-manager、SQLite-per-app + Postgres schema-per-app、internal 网络 + egress-proxy 双层白名单、WS「短时授权 + 服务端强制断连」均是有先例的正路，且各自带回了必须绑定的硬约束。

## 2. 逐项判定

### 2.1 app-proxy 双 token + 身份头注入 —— 支持 [3票]

Databricks Apps 与 BiSheng 假设同构，官方文档逐字：

- "Each Databricks app has a dedicated service principal that acts as its identity" —— 对应 BiSheng「应用 token = 服务账号密钥、应用即不可登录的服务账号主体」（GOV-08 已如此设计，互为印证）；
- "User authorization allows a Databricks Apps app to act with the identity of the app user"；"Databricks forwards the user's identity and access token to the app in HTTP headers... x-forwarded-access-token" —— 对应 app-proxy 注入 `X-BiSheng-User-*` + `X-BiSheng-Access-Token`（OBO）。

限定：Databricks 转发的是按 scope 降权的用户 OAuth token，且 OBO 处于 Public Preview（需管理员启用 + 用户首次显式 consent）；BiSheng 自签 OBO token——**同模式非同实现**，引用时注意措辞。

来源：docs.databricks.com/aws/en/dev-tools/databricks-apps/auth · /http-headers

### 2.2 manifest capabilities 声明式收权 —— 支持 [3票]

Databricks scopes 机制与 bisheng-app.yaml capabilities 语义一致："Databricks blocks access to any functionality outside the approved scopes, **even if the user has permission**"；未声明仅给两个只读默认 scope；有效权限 = scopes ∩ 用户自身权限（只收窄不放大），另有管理员层限制开发者可声明的 scope 集合。BiSheng 的「OBO scope = capabilities ∩ 用户实际权限」不变量与 GOV-05 双层过滤（声明层白名单收窄 + 用户层逐资源鉴权）有成熟商业先例。

### 2.3 header 剥离 —— 需修正（设计前提级红线）[3票]

oauth2-proxy **CVE-2025-64484**（GHSA-vjrc-mh2v-45x6，CVSS 8.5，2025-11 披露，v7.13.0 修复）：剥离只精确匹配连字符写法时，已认证用户可注入 `X_Forwarded_User` 下划线变体绕过——凡把下划线归一化为连字符的框架（Django/Flask/PHP 等 WSGI 系）即命中。BiSheng 托管的正是开发者/AI 生成的 Python 应用（框架不可控），且应用无条件信任 `X-BiSheng-*` 头：

**app-proxy 剥离必须对下划线/连字符/大小写做归一化匹配**（与 oauth2-proxy 修复方式一致），并写进 release-contract 不变量——现有表述「剥离客户端伪造 X-BiSheng-* 头」不够精确，按字面实现就会复刻此 CVE。

注：advisory 把 FastAPI 归入 WSGI 是原始来源不精确（ASGI 栈默认不做下划线归一化），Django/Flask/PHP 是明确命中项；但归一化剥离作为防御无条件应做。

### 2.4 沙箱分档 —— 支持 + 两处修正 [3票]

**支持面**：

- gVisor 默认平台 **systrap**（2023 年中取代 ptrace）不依赖 KVM；官方逐字："If you absolutely must run gVisor in a virtual machine, we recommend using the systrap platform"——信创无嵌套虚拟化虚机可用，产品方案把 gVisor 列为推荐档的前提成立；
- gVisor production guide 将 "Safely running untrusted code" 与多租户 app platform 列为生产推荐场景，与本案用途逐字吻合；
- Posit Connect（成熟商业产品）托管内部应用仅用 unshare(2) namespace（mount ns + user ns）+ 目录遮蔽、宿主机 OS 进程直跑、首请求拉起 + idle 15 分钟回收——BiSheng Docker 加固默认档**已强于该商业基线**，「内部低信任代码用加固容器」的定位不保守也不不足；其 launch-on-first-request + idle 回收模式可直接借鉴给 runtime-manager。

**修正一（档位判定规则）**：gVisor-KVM 平台官方**仅推荐裸金属**；虚机内即使有嵌套 KVM，systrap 通常更快，且嵌套虚拟化历史上是安全问题来源（CVE-2018-12904），官方不推荐生产。产品方案 §4.5「加固档 = 客户有裸金属/KVM 时可选」应收紧为「**仅裸金属**才启用 gVisor-KVM / Kata / Firecracker」。

**修正二（LoongArch 格）**：Kata 全系 VMM（QEMU/Cloud Hypervisor/Firecracker/Dragonball）在 Linux 上均以 KVM 为唯一硬件虚拟化接口，且**全系无 LoongArch 官方支持**（issue #7423 自 2023 开放，PR #13621 至 2026-08-13 未合并）；gVisor 仅支持 x86_64/ARM64。**龙芯机型唯一可用档 = Docker 加固档**——产品方案现文「LoongArch 等 gVisor 不支持的架构回退基础档」方向对，但分档矩阵应显式标注 Kata 同样缺席（勿给客户留「龙芯上加固档」的想象空间）。

附带边界：gVisor 性能开销官方只有定性描述（文件 I/O 最重、网络次之），无量化基准；鲲鹏/飞腾 ARM64 + 麒麟/统信内核上 systrap（SECCOMP_RET_TRAP 路径）的兼容性无一手实测——应列入 Wave-1 环境冒烟清单（见 §6）。

### 2.5 构建路线 —— 收窄：平铺 Dockerfile 为主，pack 备选，Railpack/Nixpacks 否决 [3票]

- **HF Docker Spaces**（大规模生产验证）：`sdk: docker` 即 plain docker build，零 buildpacks 层——证明「平铺 Dockerfile 模板」是承载任意 Web 应用（Streamlit/Gradio 之外的 FastAPI/Go/Phoenix 等）的最简路线，也是唯一零外部构建器依赖、可完全 air-gap 的路线。
- **CNB pack**（成熟度最高的备选）：CNCF 规范级官方 CLI、单机可用不需 K8s（区别于 kpack）；但构建必须连 docker socket（Podman 是官方承认替代）→ 若采用，构建执行必须归 runtime-manager 侧（与「backend 零 docker 依赖」红线自洽）；无 LoongArch 构建产物。
- **Railpack/Nixpacks 否决**（5 条 claim 合并，各 3-0）：Nixpacks 官方 README 已进维护模式、指向 Railpack；Railpack 是自定义 BuildKit LLB + frontend——frontend 镜像从 ghcr.io 拉取、prepare 步骤构建期联网下载 Mise（官方文档 Exit 75 = Mise 网络错误）、官方明示 CLI 不适合平台生产用（须直接驱动 BuildKit）、文档零 air-gap/mirror 支持。私有化单机引入 BuildKit + Mise + ghcr.io 三重外部依赖换自动检测，不划算。
- **已否决论据勿引用**：「Nixpacks 因 Nix commit 版本机制只能用最新 major」被 0-3 否决——反对 Nixpacks 引用 deprecated + air-gap 缺口即可。

对方案的含义：bisheng-app.yaml 的 `runtime: python3.11|node20|static` 直接映射基础镜像矩阵 + **平台持有的 Dockerfile 模板**（托管预检据 manifest 生成，开发者与 AI 都不写 Dockerfile），与本版「不做 Dockerfile 自定义构建」边界一致，并给 v3.1 留下「放开用户 Dockerfile = HF Spaces 模式」的演进路径。

### 2.6 单机编排：自研「薄」runtime-manager —— 支持 + 四条实现要点 [复核]

业界单机 PaaS **无一自研通用声明式编排器**，全部把能委托的委托给 docker 原语：

| 先例 | 做法（官方一手） |
|------|----------------|
| Coolify | SSH 命令式控制面（含 localhost 也走 SSH）；官方明确控制面宕机时已运行资源继续运行 [复核] |
| Dokku | 崩溃自愈 = docker restart policy `on-failure:10`，零自研守护循环 [复核]；零停机部署 CHECKS：新容器 health gate 通过才切流量，旧容器 SIGTERM + 60s wait-to-retire [引文] |
| CapRover | 单机也跑在 docker swarm 上，白拿 swarm 内置 desired-state reconciliation [复核] |
| Nomad 单节点 | 双角色 agent 官方仅定位 dev/test，生产参考架构要求 3/5 台 server → **否决** [引文] |
| podman quadlet | 声明式 + systemd 自愈很贴合，但 Podman 4.4+ 专属、docker 基线不可用 → 否决（信创 podman 环境远期备选）[引文] |

**四条实现要点**（自研薄层的正当性边界，建议进 F103 design）：

1. **崩溃重启下沉给 docker restart policy**（官方内置指数退避：100ms 起、每次翻倍、上限 1 分钟、运行满 10s 重置）——不要自研重启循环；
2. **reconciler 真正要补的洞**：docker 单机下 healthcheck 与 restart **无任何联动**（restart 只绑定容器终止），进程不退出的挂起型故障（unhealthy-but-alive）官方无自愈机制 [复核]——runtime-manager 轮询 health 状态并重建，这是 RT-08「5 分钟自动恢复」验收的真正落点，也是薄 reconciler 的核心职责；
3. **socket 面再收窄**：runtime-manager 与 dockerd 之间加 tecnativa/docker-socket-proxy（HAProxy 按 Docker API 端点白名单过滤、默认拒一切写操作与 exec、403 拦截）[复核]——「唯一持 socket」组件的爆炸半径进一步压缩；注意其 README 警告代理端口绝不能对外暴露；
4. **部署切流量借 Dokku CHECKS 语义**：起新容器 → health gate → app-proxy 切上游 → 旧容器宽限退休，正好承载 RT-08「版本切换不落报错页」。

另：Coolify「控制面宕机不影响已运行应用」应作为 runtime-manager 的显式验收项——容器存活依赖 docker 而非 manager 进程，manager 重启只影响 reconcile 时效。

零自研替代方案 = 单机 docker swarm（CapRover 路线，`swarm init` 即得声明式 service 自愈），代价是改变客户 compose 单机部署形态——不符合部署基线，列为备选不推荐。

### 2.7 per-app 数据库 —— 支持 + 两条硬约束 [复核]

「平台供库 + 注入连接串」是 PaaS 通行做法：Dokku（每 service 一个 postgres 容器 + `DATABASE_URL` 注入 [复核]）、Coolify（每库一独立容器 [引文]）、**Databricks Apps Lakebase**（平台按应用 service principal 自动建 PG 角色、仅授 CONNECT + CREATE、应用自建 schema——「共享库 + 应用自有 schema」的官方托管先例，即 BiSheng 中档同款 [复核]）；扣子编程/Manus 官方均宣称全托管自动集成数据库与存储 [引文]。

**小档 SQLite 的生产背书与硬约束**：

- 背书：PocketBase（嵌入式 SQLite WAL，官方 FAQ：2vCPU/4GB 撑 1 万+持久实时连接，仅单机纵向扩展 [复核]）；Cloudflare Durable Objects（每逻辑单元一个 SQLite 库、GA 后单库 10GB [引文]）——「小而多的单文件库」有大厂背书；
- **硬约束（SQLite 官方 WAL 文档 [复核]）**：WAL 单写者 + **不支持网络文件系统**（需进程间共享内存）→ 小档必须绑定「**单应用单实例 + 本机卷**」。本版 GOV-03 恰好单应用单实例，自洽；但两条衍生要求须显式化：① 工作区/数据存档走 tar 快照再上 MinIO（与产品方案 §4.1 tar 层一致），绝不把 WAL 库文件直接放网络存储；② v3.1 若做多实例/多机，SQLite 档应用必须先升档。

**中档规模安全区**：Crunchy Data 量化取舍——database-per-tenant 预计超 ~50 个即应回避；schema-per-tenant 一般可到数千 schema [引文，未过独立复核]。BiSheng 单机几十到几百应用落在 schema-per-app 安全区内，且避开了 database-per-app 的运维红线。

**反面信号**：Turso 曾以 Multi-DB Schemas 支撑「每租户一库」叙事，现已对全部新用户弃用 [引文]——海量 per-tenant 库的托管运维成本不低，BiSheng 不必为小档引入任何重型海量库托管机制（单机文件系统 + 配额即可）。

**建议补**：PRD 未定义小档→中档升档迁移路径（SQLite → Postgres schema 的数据搬迁 + manifest `appdb` 变更走审批），至少 v3.1 要有；Databricks 的凭据供给规范（per-app 独立角色、最小授权、标准 `PG*` 环境变量注入）可直接抄。

### 2.8 出站白名单落地 —— 双层实现 + 三个实锤的坑 [复核]

**推荐双层**：

- **L1 网络拓扑层（主）**：应用容器全部放进 `docker network create --internal` 网络——官方语义即「无默认路由 + 防火墙丢弃全部进出其他网络的流量」，且官方确认容器仍可达网关 IP（宿主服务）[复核]。出站统一经一个双挂网络的 **egress-proxy**（HTTP CONNECT / Host header / SNI 白名单，放行平台 API + manifest 声明域名）。这与三家沙箱产品官方做法同构：Anthropic sandbox-runtime（宿主侧 HTTP+SOCKS5 代理按权限规则过滤全部网络请求 [复核]，注意其自述 research preview、承认 domain fronting 类绕过）、E2B（80 端口查 Host header / 443 查 SNI [引文]）、Modal（`outbound_domain_allowlist` 仅作用于 TLS [引文]）——代理/SNI 路线是沙箱产品主流。
- **L2 宿主兜底层**：DOCKER-USER iptables 链（官方明确的用户自定义过滤挂点，先于 Docker 自身链处理 [复核]）限制沙箱网段仅可达 egress-proxy 与平台 API。

**三个已实锤的坑**：

1. **DNS-only 过滤有 CVE 级绕过先例**：Harden-Runner 社区版 `egress-policy: block` 被 DNS over HTTPS 绕过（数据编码进子域名经放行的 HTTPS DNS 端点外传，官方 advisory GHSA-46g3-37rh-v698）[引文]——不采用 DNS 时点过滤作为主控制；
2. **SNI/Host 路线盲区**：QUIC/HTTP3（UDP）无法做域名过滤（E2B 官方承认）→ 沙箱必须**同时封禁 UDP 出站**并阻断直连 IP（未走代理的 TCP 一律丢弃）；
3. **nftables 后端差异**：Docker 29.0.0 的 nftables 后端实验性且**没有 DOCKER-USER 链**（须自建 table/chain 或 fwmark）[复核]——信创发行版内核/防火墙栈多样，runtime-manager 需探测 iptables/nftables 后端分别下发规则，或部署基线锁定 iptables 后端。

**与沙箱档位的关系**：gVisor netstack 只提供 TBF 限速、无按域名/IP 出站过滤能力 [引文]——换 runtime 不解决 egress，白名单恒在宿主/代理层实现。这与产品方案「默认出站白名单比换 runtime 更重要」的威胁模型排序互为印证。

### 2.9 WS 长连接 OBO 过期/吊销 —— 不变量具体化 [复核]

一手证据一致表明「**反代不会替你处理长连接期间的鉴权**」：

- nginx `auth_request` 是 per-request 授权，对 WS 只作用于 Upgrade 握手那一次；101 后 nginx 进入纯隧道字节转发，唯一生命周期控制是 `proxy_read_timeout`（默认 60s 空闲断连）[复核]；
- oauth2-proxy 的 `/oauth2/auth` 端点被证实「session 存在即 202、不查 token 过期」（issue #2301 关闭为 duplicate，其上游 #1836 至今 open）[复核]——即使放个现成鉴权反代在前面，过期语义也靠不住；
- Pomerium 对 WS 路由默认把 route/idle timeout 全部自动置 0（无限存活），并官方警告 WS 有 DOS 滥用风险 [复核]。

**业界通行补偿 = 短时凭据 + 服务端强制到期断连重握手**（均官方先例）：K8s apiserver 对 watch 长连接用随机化超时强制断开 [引文]；AWS API Gateway WS 连接 2 小时硬上限 + 10 分钟空闲 [引文]；Socket.IO 官方确认鉴权中间件每连接只执行一次、换 token 需 disconnect + reconnect [引文]；Envoy `max_connection_duration` 到期 drain 并关闭 [引文]。

**建议把产品方案的「WS 不变量待细化」落成三条**（进 F107 design 与 release-contract）：

1. **连接授权有效期在握手时刻一次性定死** = min(OBO token 剩余寿命, 全局最大连接时长)，到期 app-proxy 主动关连接，加随机抖动防重连风暴（语义对齐 Envoy max_connection_duration / K8s 随机化超时）；
2. **吊销/下线走事件驱动主动 kill**：app-proxy 维护 connection→(user, app) 索引，权限撤销、应用停运、应用 token 强制吊销（GOV-08）时主动断连——反代生态没有现成先例，**必须自研，这正是自研 app-proxy 而非套用 oauth2-proxy 的核心理由**；
3. **前端 SDK 把「被断开 → 重握手 → 恢复」做成常态路径**（Socket.IO 模式），应用侧感知为瞬时重连而非错误。

## 3. 信创 / air-gapped 落地约束矩阵

| 环境 | 构建 | 沙箱档 | 备注 |
|------|------|--------|------|
| x86_64/ARM64 虚机（无嵌套虚拟化，信创典型） | Dockerfile 模板 + 自托管 devpi/verdaccio | 默认 Docker 加固；推荐 gVisor-systrap | systrap 无 KVM 依赖；鲲鹏/飞腾实测待冒烟 |
| x86_64/ARM64 裸金属 | 同上（可加 pack 增强） | 可启用 gVisor-KVM / Kata / Firecracker | 唯一可用 KVM 档的形态 |
| LoongArch | Dockerfile 模板（pack 无产物） | **仅 Docker 加固档** | gVisor/Kata 均无官方支持 |
| 完全离线（air-gapped） | 基础镜像随安装包预灌 + devpi/verdaccio 离线包 | 同上 | Railpack/Nixpacks 类构建器全部出局 |
| 防火墙栈差异（麒麟/统信） | — | egress L2 兜底需探测 iptables/nftables 后端 | Docker 29 nftables 无 DOCKER-USER 链 |

## 4. 三条红线兼容性

- **开源项目**：推荐组合全部开源可再分发（devpi MIT / verdaccio MIT / pack Apache-2.0 / gVisor Apache-2.0 / docker-socket-proxy Apache-2.0）；Databricks/Posit/E2B/Modal 仅作模式参考不引入。
- **compose profile 可整层不装**：构建、沙箱、egress-proxy、编排全部收在工场运行时层；开放能力层零 docker 组件。
- **backend 禁止依赖 docker**：docker build / pack 均要求 socket → 构建与容器生命周期全部归 runtime-manager；再加 docker-socket-proxy 端点白名单，backend→manager→socket-proxy→dockerd 特权逐级递减。

## 6. 残留开放问题

1. **gVisor-systrap 信创实测**：鲲鹏/飞腾 ARM64 + 麒麟/统信内核上的兼容性与开销无一手来源，列入 Wave-1 环境冒烟（与 runtime-manager 安全评审同波）。
2. **Kata LoongArch 跟踪**：PR #13621 合并后分档矩阵可更新。
3. **egress-proxy 组件选型**：路线已定（CONNECT/SNI 白名单代理 + internal 网络），具体组件（自研薄代理 vs Squid/Envoy vs 借鉴 sandbox-runtime）F103 design 定；注意 Anthropic srt 自述 research preview，只借模式不作依赖。
4. **Crunchy Data schema 数量红线**（database-per-tenant ~50 / schema-per-tenant 数千）有逐字引文但未过独立复核，采用前可快速复核原文；对本案（几十到几百应用）结论不敏感。
5. **主轮验证缺口备案**：Kata KVM 依赖那条 claim 因一个验证 agent 被 API 安全拦截只得 2-0（其余承重 claim 均 3-0 或独立复核确认）。
