# Sdd Review Code

先读 [阶段交接规则](../sdd-workflow/references/stage-contract.md)，按风险加载 [审核检查要点](references/review-checks.md)。

## 建立独立判断

读取真实改动、已确认需求和设计、相关项目规则及必要调用关系。先形成判断，再参考作者的解释，减少锚定。
按[产物存放与维护约定](../sdd-workflow/references/artifact-storage.md) 核对同一特性标识、有效路径和来源版本，检查本次必要知识更新、迁移／替代关联及代码证据。目录完整、归档或登记状态均需结合实际依据判断。
工具或宿主允许且已有授权时，安排独立评审上下文；最小材料为原始约束、改动和相关事实。
自己复核时明确独立性限制，不把换个角色名称称为独立审核。高风险问题需要适当独立复核或人工判断。

## 明确实际范围

先确定用户指定的起点、目标分支／提交及当前实际终点。目标包含工作区时，核对已提交差异、暂存、未暂存和相关未跟踪文件；同一文件看最终实际内容及来源，不能只看 base...HEAD 漏掉尚未提交的实现，也不把互相抵消的中间补丁当成最终行为。只审提交或 PR 时说明工作区排除范围，不要求为审核先提交。
核对各次执行证据是否对应该内容，必要时用文件指纹；旧 HEAD、旧绿报告不能代表当前工作区。

## 方法

先利用已有静态检查结果筛查低级问题，再追踪具体触发路径：
- 需求和设计符合性，实际注册、入口、调用与配置是否接通。
- 边界、异常、超时、取消、资源释放与状态一致性。
- 必要测试的预期、断言、模拟边界、阶段归属及本阶段应有执行证据。
- 相关安全、兼容性、性能、可观测性及恢复风险。

确认路径实际可达、影响由本次改动引入或加重；区分已有缺陷。缺少证据时标记待核实，不把推测包装成事实。
开发测试审核不仅看轻量检查：核对需要的单元、接口和功能测试是否真实执行目标代码，mock 是否只替换合适边界，契约是否有来源，状态和副作用是否有业务断言。不能以一组固定成功的替身结果证明业务正确，也不能把隔离功能测试当成真实 E2E。
风格、复杂度、重复率依据项目规则判断，避免无依据阈值或为了刷绿扩大重写范围。

## 发现与完成标准

每项发现包含代码位置、触发条件、后果、依据、严重程度及最小修复方向。
阻塞：有依据的需求偏差、实际缺陷、重要安全／数据风险，或开发／审核阶段应有的必要证据缺失。
提醒：不阻止正确行为的维护建议、非阻塞改进；需说明实际影响。
必要证据缺失用“未验证”标识，不能与代码已经证明错误混为一谈。
真实部署 E2E、昂贵真实依赖及按约定后置的 UI 测试记为待验收，不能仅因未执行它们就要求开发期部署全栈。需要的开发期隔离接口／功能测试缺失仍属于证据缺口，已证实的代码缺陷仍需解决。审核可复核或定向运行适当 mock／隔离测试，不启动后置 UI 或真实部署 E2E。

没有发现不表示已证明无缺陷。分别输出“需求／设计符合性”和“项目规范符合性”，各自引用来源和判断；安全、异常、并发、资源及可观测性等适用风险并入有依据的发现，不被两轴替代。单个发现引用两类依据时只计一次，保留全局严重程度和阻塞判断；无需求或规范来源时明确缺口，不编造通过。
输出实际审核范围、方式、发现、未验证项与残留风险。独立复核按风险、宿主能力与授权安排，不为双轴固定增派两个代理，也不把两个标题当成独立评审。
阻塞项解决并对相关改动复核后方可审核通过；修改范围扩大时重新评估审核覆盖。
同时检查研发测试是否位于对应前后端项目/test/、交接内容是否对应实际版本，验收代码是否与研发测试分离。审核通过后研发流程交付并结束；后续 sdd-acceptance 由测试岗位独立发起，本审核不自动调用或等待验收。
