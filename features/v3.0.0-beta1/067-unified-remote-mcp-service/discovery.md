# Spec Discovery — 通用开放 API 的统一远程 MCP 服务（F067）

> **本文定位**：Spec Discovery 调研记录，只回答需求边界、当前基线与待确认口径；不替代 `spec.md` / `design.md`。
> **日期**: 2026-09-15
> **状态**: ✅ 能力范围已于 2026-09-15 按中粮 SeedMind Apifox 文档重新确认；尚未生成 `tasks.md`
> **上游需求**: [《0923 中粮需求响应》§3「提供通用 API 与 MCP 接口」](https://dataelem.feishu.cn/wiki/YPnUwk9ZjiNYPdkmh1DcmiRnnac#doxcnWFZOYA02TvKHbI3ksU9Tvh)
> **范围基线**: [中粮 SeedMind Apifox 开发者文档](https://s.apifox.cn/a0e36780-865a-4179-b7df-b51a01d5ebcc)

> **相关 Feature**: F053（开放 API 鉴权与身份传递）· F066（PAT 数据范围）

## 1. 结论先行

本需求应作为 **F053 之后的独立 Full SDD Feature**：每个 BISHENG 部署提供一个统一远程 MCP 服务，仅把中粮 SeedMind Apifox 文档当前列出的 **10 个知识资源/文件 HTTP API** 转换为 10 个可发现、可调用的 MCP 工具，同时保持 API 与 MCP 在身份、权限、数据归属、业务结果、错误和审计上的同一语义。

这不是新增一套业务 API，也不是重做 F053。F053 原 PRD v2.6 曾把“MCP 复用同一密钥体系”列为 P2、本期不做；0923 PRD §3 是新的范围裁定，明确承接并要求交付。为了不改写已经确认和上线验证过的 F053 范围，建议由 F067 依赖 F053，而不是把 MCP 追加入 F053。

当前仓库只有 **MCP 客户端**能力（连接第三方 MCP 服务并转为 LangChain Tool），没有面向外部调用方的 MCP 服务端；`mcp>=1.27.0` 依赖已存在，但不能据此视为服务端能力已交付。

---

## 2. PRD 已明确的业务口径

### 2.1 服务与接入

- 每个 BISHENG 部署提供 **一个统一远程 MCP 服务地址**。
- 调用方沿用开放 API 的凭据获取方式，只需配置服务地址与认证信息，即可发现并调用其权限范围内的工具。
- 随服务交付接入地址、客户端配置示例与工具说明；示例中的凭据只能使用占位符。
- MCP 工具保持正式公开 API 的业务字段含义、默认值、限制、分页和结果语义；若 MCP JSON object、文件载体、结构化成功结果或标准错误结果无法原样表达 API 线格式，则由 MCP 工具定义显式兼容。既有 API 的接口逻辑与合同全部不变；工具拆分、名称、转换规则、传输与部署形态属于后续 Design 决策。

### 2.2 能力覆盖

2026-09-15 用户将需求收缩为 Apifox 链接当前展示的以下 10 个 API。本清单是显式白名单，不随 F053 其他开放路由自动扩张：

| 业务组 | Apifox 指定的能力范围 | API 数 | 沿用权限位 |
|---|---|---|
| 知识资源 | 查询列表、创建、更新、删除、清空内容、检索分段 | 6 | `knowledge:read` / `knowledge:write` |
| 文件 | 上传、查询列表、删除、批量删除 | 4 | `knowledge:read` / `knowledge:write` |

本期固定采用“一个 API 业务操作对应一个 MCP 工具”，共 10 个工具。Apifox 后续新增接口不会自动进入 F067；扩围必须先更新 spec/design 并重新确认。

### 2.3 身份、权限与执行

- 服务账号凭据继续支持 F053 已定义的“自身身份”与“代表他人”模式；主体、租户和委托目标都由服务端可信认证上下文确定。
- 模型生成的普通工具参数只承载业务输入，不得借此指定或替换执行主体。
- 个人访问令牌继续只允许 F053/F066 已开放的 `knowledge:read` 工具，不得获得写入或委托能力。
- 工具发现时按凭据权限位和主体限制过滤；每次工具执行时重新校验凭据、身份模式、资源权限、数据范围和业务状态。
- 凭据撤销/过期、主体失效、权限或数据范围变化，按 API 的同一生效规则影响后续调用；已有连接不得缓存为永久授权。
- 权限校验失败时终止业务执行；同一业务操作通过 API 或 MCP 调用，应产生相同的数据归属、业务结果与错误语义。
- 身份解析、资源授权、业务状态与审计复用 F053/F048 现有规则；MCP 不得形成第二套权限执行面。

## 3. 当前代码与契约基线

| 项 | 当前事实 | 对本 Feature 的影响 |
|---|---|---|
| v2 路由 | `/api/v2` 统一挂载 `verify_open_api_access`，每个开放端点用 `open_api_scope` 声明权限位、允许身份模式和会话语义 | MCP 必须消费同一主体与权限合同，不能仅在工具列表层做一次校验 |
| 需求能力文档 | 中粮 SeedMind Apifox 文档列出 10 个本期 API | Design 使用显式 allowlist 建立一对一覆盖，不以 F053 全量路由作为扩围依据 |
| 现有 API 合同 | F053 公开合同中已有这 10 个 `/api/v2` 路由 | 可复用其已验证的鉴权、scope、业务码与数据语义，但 MCP 输入/输出 schema 仍需显式生成和校验 |
| MCP 现状 | `bisheng/mcp_manage/` 只有 stdio/SSE/streamable HTTP 客户端和 LangChain Tool 适配 | 不能复用为服务端交付证明；服务端边界需新设计 |
| 凭据与身份 | F053 已实现服务账号、PAT、S/D、执行主体、会话主体和审计 | F067 不新造密钥类型或身份模式 |
| PAT 数据范围 | F066 可把自然人 PAT 收窄到本人创建数据 | MCP 知识只读工具同样受调用期数据范围约束，管理员短路不能绕过 |
| 旧 PRD 范围 | F053 spec/design 明确“MCP 本期不建设” | F067 必须在版本契约中登记为后续增量，不能暗改 F053 已确认事实 |

## 4. 建议范围边界

### 4.1 本次纳入

- 一个统一远程 MCP 服务及工具发现、工具执行能力。
- 仅覆盖中粮 SeedMind Apifox 文档当前列出的 10 个知识资源/文件 API。
- 服务账号 S/D 与 PAT 知识只读的完整身份/权限矩阵。
- 与上述 API 等价的成功、空结果、分页、业务错误、权限拒绝、依赖故障和文件上传语义；线格式允许按 MCP 工具合同显式转换，错误结果使用 MCP `isError` 与明确 `code/message`，不复制 HTTP 状态信封。
- 工具清单过滤与执行时二次校验。
- 接入地址、占位符配置示例、工具说明与能力覆盖清单。
- allowlist/MCP 契约漂移检查：10 个指定 API 不能漏工具，MCP 也不能多出 allowlist 之外的工具。

### 4.2 明确排除

- 不纳入 Apifox 本期清单之外的任何开放 API，包括工作流、应用/知识助手、日常对话、语音、引用、问答对、元数据、分段上传与下载统计。
- 不新增密钥类型、身份模式、OAuth 授权服务器或面向特定第三方平台的专用适配。
- 不替换、下线或改变现有 `/api/v2` 调用方式。
- 不把工具名称、工具粒度、协议版本、传输方式或部署进程写死在 spec；这些属于 Design。
- 不在文档、日志、错误或审计中记录明文凭据、Authorization 头、请求文件内容或其它敏感输入。

## 5. Spec 拟覆盖的验收主题

1. 单一服务地址、标准接入资料与占位符示例。
2. 10 个 allowlist API 与 10 个 MCP 工具一对一完整映射，不多开放、不漏开放。
3. 工具发现按权限位、凭据类型和身份限制过滤。
4. 每次执行重新校验；撤销、过期、主体/租户/权限变化对已有连接生效。
5. 服务账号自身身份、代表他人与 PAT 知识只读矩阵。
6. 委托身份只来自可信认证上下文，业务参数不能改执行主体。
7. 资源权限、租户隔离、PAT 数据范围、会话归属与审计同 API。
8. API/MCP 同一操作的业务含义、错误含义和副作用一致；已有 API 的全部接口逻辑保持冻结，协议形态无法原样复用时由 MCP 工具定义和 adapter 单向兼容。
9. 文件上传、分页、删除与批量删除不弱化原 API 限制。
10. 工具适配层失败关闭，不绕过 API 或 F048 业务门禁。

---

## 6. 已确认的 Discovery 裁定

用户已确认按以下口径进入 spec：

- F067 依赖 F053/F066，作为 0923 PRD 对旧“MCP 本期不做”裁定的独立增量。
- 能力范围不再是 F053 正式公开合同的全量业务路由，而是中粮 SeedMind Apifox 文档当前列出的 10 个 API 显式 allowlist。
- 本期每个 allowlist API 对应一个 MCP 工具；任何新增工具都需先重新确认范围。

上述收缩口径已于 2026-09-15 由用户确认，并同步写入 `spec.md` 与 `design.md`。
