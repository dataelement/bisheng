# F083 第二阶段：复用文件夹状态，刷新后恢复删除进度

关联：[spec.md](./spec.md) · [tasks.md](./tasks.md)；v3.0.0-beta1；2026-11-05。
状态：状态方案已实现并完成代码复核；部署及真实双库/浏览器验收待执行；loading 调整延期。

## 1. 怎么改

1. 复用文件夹所在 `knowledge_file` 行的 `status`：正常为现有值 2，新增文件夹专用“删除中”值 8。
2. 根目录权限通过后，先判断是否需要审批；直接删除先独立提交状态，再执行原有完整权限检查和删除。
3. 列表同时返回当前目录及祖先的删除状态；刷新后继续显示并限制操作。
4. 成功沿用原事务硬删除目录；明确失败恢复正常。失联先核对并阻止旧请求继续提交，再恢复操作。
5. 不新增表、字段或索引，不回填历史数据；需要更新后端与客户端。

本期不优化删除耗时、不解决上传重建同名目录、不改同步 DELETE、审批规则或 OpenFGA 模型。

## 2. 现状与约束

遵循 `docs/constitution.md` C1–C8、当前 release-contract、backend/client AGENTS。

- 文件和文件夹共用 `KnowledgeFile`；`knowledge_space_service.py` 的目录创建入口将 status 固定为 SUCCESS(2)，目录不运行文件解析流程。
- `request_change` 首次完整子树授权就可能耗时；需要拆出根目录存在性、租户和删除权限检查，再做轻量策略判断；预计直接执行的删除在完整子树授权之前登记状态，原授权检查仍全部执行。明确需审批的请求直接走原授权/审批路径，不写“删除中”。
- `knowledge_space_direct_delete_service.py` 在完整清单构建后才写 F046 清理账本，随后与正式资源删除一起提交。该账本不能提供前半程可见状态。
- `build_delete_manifest` 按“空间 → 根资源 → 子树”的顺序持有数据库锁。根资源锁可能一直持有到删除事务提交，独立连接的心跳会被阻塞。
- `useFolderDeletion` 目前只保存本页状态；整页刷新会丢失。
- `user_metadata` 已用于部分内部信息，但通用元数据修改入口存在整体替换。新增内部键必须保护，不能直接塞入后放任其他入口覆盖。

## 3. 存储与关键决策

### 3.1 复用 status，最少的附属信息放在已有元数据

仅对 `file_type=0` 使用独立的文件夹状态枚举：NORMAL=2、DELETING=8。8 不加入文件解析枚举，也不改文件状态含义。

已有 `user_metadata` 保留服务端专用键 `_folder_delete`：

```json
{
  "version": 1,
  "operation_id": "uuid",
  "initiator_user_id": 1,
  "phase": "running",
  "started_at": "数据库UTC时间",
  "heartbeat_at": "数据库UTC时间",
  "failure_reason": null,
  "approval_request_id": null
}
```

phase 为 running/failed/approval_pending；只保留本目录最近一次尝试，不提供操作审计。失败时 status 恢复 2，但保留这次编号和受控原因供调用方查询。成功时目录行被硬删除，不保留假目录或软删除行。

operation_id 必须与直接删除账本的 `execution_token`、`direct-delete:{token}` business_key 使用同一编号；复用既有索引精确查询成功事实，不改 F046 的执行、补偿和物理清理状态含义。

元数据更新必须在 repository 中锁定最新目录行，合并其他键，禁止整份旧快照回写；外部元数据编辑、批量编辑、复制/移动快照恢复等路径不得覆盖或复制 `_folder_delete`。目录的其他写入口也须保留最新 status，禁止用删除前旧 ORM 快照将 8 覆盖为 2；活跃删除范围内原应禁止的变更按既有操作守卫拒绝。保留键禁止作为自定义字段定义，列表与其他对外元数据输出移除该键，只返回经过权限过滤的删除状态。文件类型和索引/RAG 元数据输出也不得传播该键。

**备选及原因**：单用 status 无法区分旧、新请求，也无法安全恢复失联操作；借用 update_time 会被其他更新干扰。独立新表可以隔离这些信息，但本需求可复用已有行，按用户要求不采用。提前复用 F046 执行记录会改变原 worker 的扫描与恢复语义，同样不采用。
**重新考虑条件**：若要保留完整历史、覆盖非目录任务，或元数据保护无法可靠落地，再讨论独立操作表，不能实施中自行加表。

### 3.2 以根目录行锁和操作编号阻止旧请求继续提交

开始登记使用独立短事务，仅锁根目录行，确认没有本目录未结束尝试，再写入 status=8 和新编号并提交。该短事务不持有空间锁，不执行子树扫描，也不调用外部权限服务。权限检查在事务之前执行，后续仍走原完整授权。

直接删除仍按原顺序获取空间、根目录及子树锁；在取得根目录锁后、构建耗时清单前，核对 `file_type/status/operation_id`。到数据库切换前再次核对，根目录锁一直持有到原删除事务退出。编号被失联核对替换或恢复为正常时，旧请求必须回滚；不得重建标记后继续。

失败处理只能在业务事务明确回滚后，以旧编号为条件恢复 status=2 并记录失败。连接断开、取消或提交结果不明不写失败。任何过期心跳、finally 或异常回调都不能覆盖新编号，也不能重新插入已不存在的目录。

**备选**：超时直接恢复状态，或只在前端解除限制。否决原因：旧请求仍可能删除刚恢复操作后的目录内容。
**重新考虑条件**：若改为异步任务或修改根目录锁的持有范围，必须重新审查这个互斥前提。

### 3.3 心跳用于识别失联，不是到期自动取消

前半程每 10 秒更新 heartbeat_at，60 秒无更新投影为 unknown；取数据库时间，不使用通用 update_time。心跳只锁根目录，等待上限 1 秒；锁忙表示暂时无法续报，不宣布失败，不积压任务。

**重要区别**：删除长事务持有根目录锁时，心跳可能无法更新。此时允许页面显示“状态待确认”，不因时间超过 60 秒中止本来可以安全完成的事务，也不因“过期”自动撤销执行资格。真正的执行资格只由持锁核对后的 status 和 operation_id 决定。

失联核对使用独立短事务，仅锁该根目录行，最多等待 5 秒：

1. 删事务仍持锁：超时只返回 unknown，不解锁资源、不报删除失败。
2. 取得锁且心跳已恢复或编号变化：返回当前状态，不能覆盖新尝试。
3. 取得锁且原 running 仍超过 60 秒无更新：恢复 status=2，保留同一编号，phase=failed、原因 interrupted，一起提交。
4. 核对提交后刷新列表，目录仍存在才按原权限恢复。旧删除以后取得根目录锁时，因 status/编号不匹配被阻止。
5. 根目录已不存在：按该编号精确查询既有直接删除账本及 DB_CUTOVER 成功步骤；不能只凭不存在宣布这次删除成功。

删除先持锁并提交，核对随后读到已提交账本；核对先恢复状态，旧删除被挡住。心跳任务的停止/等待放在业务事务退出之后，避免等待自身锁阻塞的连接。

只由本次发起人且仍可见空间，或空间 manage_permission 用户核对；普通查看者继续观察。核对不提交、重试或撤销 DELETE。进程退出并释放事务锁后，下次有权查询可完成恢复；数据库不可达或提交结果不明时保持 unknown，不承诺基础设施故障期间恢复。

## 4. 正常、失败与审批流程

### 4.1 直接删除

根目录检查及轻量策略判断（直接分支） → 独立提交 status=8/操作编号 → 原完整子树权限检查 → 原空间/资源锁 → 核验编号 → 构建清单及扩展权限检查 → 再核验 → 原事务硬删除正式数据并提交 F046 清理账本及 DB_CUTOVER 成功步骤 → 原后台物理清理。

claim 还须核验既有审批 request/footprint；仍有效时不修改目录标记。检查与登记之间的竞态由原审批/删除事务内原有冲突检查兜底，失败按当前编号恢复，不覆盖原审批关联。

同一目录重复 DELETE 返回现有冲突码 18077，并提供可查询编号，不重新开始。并发祖先删除导致目标消失、移动或类型改变时，旧请求按原领域错误结束，不伪报本次成功；同名新 ID 不继承状态。

### 4.2 明确失败与结果不明

授权失败、清单失败或业务事务已确认回滚后，按旧编号将目录恢复正常并保留失败原因。目录恢复不绕过其他审批锁或原权限。
提交异常、客户端断开不等于回滚：不盲目恢复，交由状态查询及失联核对处理。成功提交后的派发/通知故障不改写失败。

### 4.3 需要审批

根目录权限通过后，按现有空间类型、owner/manager 和审批策略先做轻量分支判断；明确需审批的请求不登记 status=8，继续原完整授权及审批提交，刷新展示已有“待审核”。轻量判断不替代原完整授权，不能据此直接删除。

若预计直接执行的请求已登记标记，而原流程最终因策略变化转入审批，则在原 caller-owned UoW 中按原空间/资源锁顺序锁根目录，校验本次 status/编号；原子创建 F046 request、关联 approval_request_id，并恢复 status=2、phase=approval_pending。未登记标记的普通审批路径无需凭空建立标记。事务提交后才执行原 post-commit effects。

待审显示原“待审核”；既有审批锁继续限制操作。F083 不给待审记录续报，不触发失联核对，不提前创建 F046 执行步骤。审批获批后由原 executor/worker 执行与恢复，不改其 token、截止时间、补偿规则或 OpenFGA 操作。

有 approval_pending 关联且原请求/footprint 仍有效时，新 DELETE 返回原冲突，不替换编号或关联。拒绝/撤回或执行已真正结束且无原阻塞后，才允许新尝试；关联缺失而无法证明结束时保持 unknown。

审批分支的运行状态由既有 F046 request 与当前 execution_token 对应的步骤投影：DB_CUTOVER 已成功即表示正式资源移除；待审批仍为 approval_pending；queued/applying 按原执行状态展示，超过可确认活跃范围显示 unknown；无 cutover 的明确失败为 failed，但不能解除原 footprint。该分支始终 can_reconcile=false，恢复归原执行器。

新增批量查询只读 request 的标量字段及对应步骤，不读取包含大清单的 execution_checkpoint；不使用 JSON 路径查询。queued/applying 的保守失联判断以 request.update_time 的 60 秒为展示阈值，不视为原执行器的截止时间，不据此解锁或触发重试。原审批界面的语义和恢复真相不变。

## 5. 对外契约与前端

### 5.1 列表与范围状态

children/search/folders 响应增量保留 `deletion_status` 和分页 data 顶层 `scope_deletion_status`：
`{state, operation_id, root_folder_id, retry_after_ms}`。

目录自身及已可见项的祖先按 ID 批量读取现有行，最多 500 个 ID 一批；不扫描全空间，不增加 COUNT，不逐行请求。状态仅 running/unknown；没有限制时 null。审批展示复用已有投影。当前目录即使没有任何子项，也必须返回范围状态；不把业务字段放进全局分页基类。

status=8 的目录必须保留在目录列表、搜索、目录树中。检查原 status=2 过滤条件、通用枚举转换及前端状态展示，确保只给文件应用解析状态筛选，不把“删除中”目录当解析失败或直接隐藏。权限运行时仍用现有 folder ACTIVE 事实，不新增权限状态、动作或模型。

### 5.2 批量状态与失联核对

- `POST /api/v1/knowledge/space/{space_id}/folder-deletions/status`：`{folder_ids:[int], known_operations?:[{folder_id,operation_id}]}`，最多 100 项。标准 resp_200，data.items 含 folder_id、operation_id、state、retry_after_ms、failure_reason、can_reconcile。
- `POST /api/v1/knowledge/space/{space_id}/folder-deletions/{operation_id}/reconcile`：`{folder_id}`，响应同单项；只处理目录标记，不修改 F046 执行状态。

state 为 idle/running/unknown/succeeded/failed/approval_pending/untracked/unavailable。
有行且 status=8/合法标记：按心跳投影；无有效元数据的异常 status=8 返回 unknown，禁止凭空恢复。正常目录无已知尝试为 idle；标记记录失败为 failed；待审为 approval_pending。新编号优先，旧响应不能覆盖。

目录已删除时，只在精确匹配 tenant/space/folder/operation 的 `direct-delete:{operation_id}` 账本且对应 token 的 DB_CUTOVER 步骤成功时返回 succeeded，物理清理尚未完成也不影响成功。账本缺失、被清理或关系不符是 untracked，不是假成功；不扫描历史或依赖完整删除清单。

先核验空间/租户，再核验资源可见性。历史结果只给发起人且仍可见空间，或空间 manage_permission 用户；普通查看者目标消失/不可见统一 unavailable，未知 ID 行为一致，不返回历史编号、原因或人员信息。目录原始元数据中的内部键不对外暴露。

unavailable 移除旧快照并停止观察，不报删除成功。已知尝试 untracked 显示结果无法确认；刷新后确实已无该资源则结束该旧目标观察，不把不存在解释为本次成功。仍存在的异常标记保持限制并给可诊断编号，不能自动恢复。

## 6. 已知坑与护栏

1. **长事务会锁住心跳**：不能因为续报失败就强制本次删除回滚，更不能等独立心跳退出后才释放根锁。在生命周期 service 将 task 等待放到事务外；核对锁忙返回 unknown。
2. **status 与解析枚举共列**：通用枚举转换、状态筛选或 worker 更新若不区分类型，可能隐藏目录或覆盖标记。模型/格式化/文件任务入口按 file_type 区分并回归。
3. **user_metadata 会被整体替换**：通用文件元数据编辑和旧快照写回可丢标记。repository 合并保护保留键，对外输出移除保留键。
4. **成功后目录行不存在**：不能靠这行保存 succeeded。直接删除沿用同 token 的既有账本/步骤作证据；缺证据不报成功。
5. **超时不等于旧请求已停止**：只有持根锁恢复标记后才允许解锁，旧请求必须校验 token。失联核对不可只读再无条件 UPDATE。
6. **同名目录可能由上传重建**：所有关联均用 ID/编号，保留原问题单独排查，不让旧终态移除新 ID。
