# PRD 写作与完成标准

相关业务术语按[统一来源规则](../../sdd-workflow/references/domain-language.md) 使用，规范名、相近概念、关系与状态含义明确；本次新增定义和确认状态可定位。正式稿收尾核对正文、业务规则表、图示和验收条件，词汇相同不代替概念正确。

适用于本套通用流程中的正式需求文档。交付 HTML，具体要求见 [HTML 交付约定](../../sdd-workflow/references/html-delivery.md)。不依赖某个项目、技术栈或另一套文档 skill。

## 内容与决策边界

先定义问题、目标指标、范围和不做项，再描述功能。业务方应能判断上线换来什么，研发和测试不必猜关键规则。
优先级 P0／P1／P2 与一期／二期是两个维度，分别注明。沿用团队已有优先级含义；缺少定义时明确提出本次建议，不能把“P1”擅自等同于“二期”。未决定的后续范围记为未定，不承诺额外功能。
业务规则必须用规则表、状态机或决策表表达，可用文字解释理由，不能只写散文。规范性描述禁止“大概”“尽量”“友好提示”等无法判断是否满足的用语；说明触发条件、可观察结果和恢复方式，需要时明确提示内容或消息规则。
关键设计在 PRD 中说明业务／产品决策的真实选项、比较依据、取舍理由和拍板建议；记录实际决定及依据。实现架构、表结构、锁策略等留给技术设计，除非它们本就是已知约束。没有实际替代项时写明唯一约束，不凑选项。
事实、用户决定、AI 建议和未知分别标识。无依据的目标值、基线、字段限制、合规义务、灰度比例等不能填成已确认要求。先查已有材料；缺口影响核心范围、规则或验收时列为阻塞，沿用既定需求确认点解决，不新增一套审批。

## 固定输出顺序

标题后放元信息与目录：文档版本、日期、状态、来源、适用项目／范围和确认依据。正文使用以下十部分，变更记录为最后一部分。

| 顺序 | 章节 | 必须表达的内容与建议形式 |
|---|---|---|
| 1 | 背景与问题 | 谁在什么场景遇到什么问题、现状证据、影响和本次解决必要性；区分观察与假设 |
| 2 | 目标与指标 | 目标价值；指标表含名称、定义／计算口径、基线及来源、目标、观察周期、数据来源与负责方。无量化数据时如实标注，不能用“提升体验”代替验收依据 |
| 3 | 范围（含不做） | 本次包含／明确排除／一期／二期／未定；角色、对象和业务边界，明确哪些承诺不在本次交付 |
| 4 | 用户场景与流程 | 场景、角色、触发、前提、主路径、结束状态及相关异常出口；流程图配说明，无原型也可描述可观察交互 |
| 5 | 功能需求 | 每项稳定编号、P0／P1／P2、交付期、来源、主流程、规则表／状态机／决策表、异常清单、字段定义、关联验收编号 |
| 6 | 非功能与依赖 | 性能、安全、权限、合规、可观测性及发布恢复约束；上下游系统／接口／数据依赖、负责人、可用条件、阻塞与上线顺序 |
| 7 | 数据与埋点 | 数据来源、归属、生命周期与适用隐私约束；事件名、触发时机、属性、去重／统计口径及对应指标；不把敏感值写入埋点示例 |
| 8 | 验收标准 | 每条需求对应可观察的前提、动作、预期及必要状态／副作用，保留稳定 AC 标识。非功能要求也有验证方式；后续用例关联 REQ／AC |
| 9 | 风险与灰度回滚 | 风险、触发条件、影响、应对与负责方；启用范围、放量依据、监测、暂停／回滚触发、恢复目标和数据处理边界。与第 6 部分通过标识引用，避免两套阈值 |
| 10 | 变更记录 | 版本、日期、变更与原因、受影响 REQ／AC、关联设计／用例的更新状态、决定／确认依据 |

## 每个功能点的最低粒度

主流程交代入口、参与角色、前置条件、操作、可观察结果及结束状态。业务规则涉及多个条件时用决策表；有生命周期时给状态和允许／禁止转换及转换条件，流程图不能替代规则定义。

异常适用性逐项核对并持久化，可在功能下列出或引用共享异常表的明确行：

| 类型 | 需要确定的业务结果 |
|---|---|
| 失败 | 用户／调用方知道什么，保留或撤销哪些状态，能否重试或恢复 |
| 超时 | 等待结束后显示什么，操作是否可能已生效，如何确认最终结果 |
| 并发 | 同一资源或限额冲突时谁能成功，另一方得到什么结果 |
| 重复提交 | 再次操作的结果和副作用次数；不能默认所有操作都必须幂等 |
| 权限不足 | 可见性、允许／拒绝行为、必要无副作用与信息披露边界 |
| 空数据 | 空集合、无匹配、缺少输入等适用场景的可观察行为 |
| 边界值 | 长度、数量、时间等边界及边界两侧的预期，数值和单位需有依据 |

每类给出“适用及规则／不适用及理由／待确认及影响”，不能为补齐表格而虚构新能力。用户遇到的业务结果属于 PRD；实现恢复机制由设计细化。多个功能共用规则可以引用稳定编号，仍要能追踪各自适用性。

字段表按输入、输出或业务对象列出，列不得缺失：**名称、业务含义、类型、必填／条件必填、长度或范围及单位、默认值、校验、来源**。条件必填写出条件；无默认值或无长度约束明确表达；可变名称需确定去空格、字符计数等规则。这里定义业务字段，不凭空创建数据库列、接口路径或未确认协议。

非功能清单逐项给出可验收要求和验证方式，或不适用理由：性能的负载／分位／时间口径、安全与权限边界、合规适用条件及依据、必要日志指标告警、埋点、灰度与回滚。无发布灰度机制时可明确受控一次启用等真实安排；不能假装支持灰度或承诺回滚自动撤销数据。

## 追溯、检查与闭环

用稳定 REQ／AC 编号串起需求、设计和开发／验收用例，完整写出引用。PRD 给出验收标准即可，不提前替代 sdd-test-cases 的用例设计或执行；所有 UI 执行及真实部署 E2E 仍由独立验收安排。

输出前逐条回答并修正，报告剩余缺口及其具体影响：

1. **研发能否不问我就开工？** 关键业务规则、范围、字段和异常结果不能靠猜；技术实现仍需后续设计和确认，不能把本问当成跳过设计的授权。
2. **测试能否据此写全用例？** 每条需求都有确定预期，边界和异常适用性可查，不依赖实现给自己定义正确答案。
3. **业务方能否说出上线换来什么？** 问题、收益与指标可对应，有来源和可验证口径。
4. **三个月后新人能否看懂为什么这么设计？** 保留现状、关键选项与取舍、决定依据和变更原因。

完成条件：十部分具备实质内容或有依据的不适用说明；每个功能满足上述粒度；每条需求可转成用例；四维检查成立且阻塞为零；四问自检已修正发现的问题；HTML 可用。此时仅为“专业检查完成，待用户确认”。用户确认当前内容后，才记“需求已闭环”，保留确认对应版本。未知不隐藏，建议不冒充决定，自检不冒充人工确认。
