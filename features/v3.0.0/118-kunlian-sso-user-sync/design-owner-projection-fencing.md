# F118 补充设计提案：用户 Owner 投影的持久 fencing

- **Status**: CONFIRMED，2026-11-03 用户明确“批准新增投影状态表（推荐）”。
- **关联**: [design.md](./design.md) §4.3、§4.4、§6.4；[tasks.md](./tasks.md) T019、T020、T029、T030。
- **范围**: 只补跨事务投影顺序的技术机制，不改变用户同步、授权、停用或恢复的业务规则。

## 需要补齐的事实

当前 User 模型只有账号字段、token_version 和 DSH profile 版本，没有昆联外部投影的持久修订／操作栅栏。已确认设计允许 user／tenant Owner 独立提交，F118 仅凭自身 projected_revision 的回执 CAS，不能证明已经提交到 User 表的更新仍按当前修订排序。

可能发生的时序是：旧投影准备后失去 F118 锁／连接；新执行者发布新修订并更新用户；旧 Owner 调用迟到后仍写入旧资料；F118 拒绝旧回执，但这不能回滚 User 表的旧写入。这里指出的是后续实现需要解决的设计细节，不是已上线缺陷或真实故障复现。

## 推荐方案

新增一张 user Owner 自有的独立投影状态表，候选 `user_external_identity_projection`，放在 `user/domain/models/external_identity_projection.py`；字段包括稳定外部身份摘要、本地 user_id、当前 operation_id、单调本地 fence、源修订和已应用修订，以及 ROOT 控制面范围与时间戳。外部 opaque version 继续不排序；fence 是毕昇自行生成的本地计数。

1. F118 持有当前身份绑定锁，读取并固定当前源修订／租户映射。
2. user application 预留持久投影操作，返回操作 ID 与本地 fence。预留只修改 Owner 状态行，不修改用户资料。
3. F118 在派发用户写入前再次确认原锁／事务及源修订仍有效；失去原事务不得以新事务继续旧计划。
4. user Owner 在自己的同一事务内校验操作 ID／fence，修改 User 并更新已应用回执。旧操作不能在新操作之后修改用户，即使旧的 F118 进程仍运行。
5. F118 只有确认 Owner 当前回执与自己的预期修订一致，才能完成 projected_revision 的 CAS；冲突或崩溃保持 PENDING 并按当前源修订重新恢复。
6. 租户关联仍首次绑定、禁止迁移；开始外部账号物化前先持久冻结已有租户映射，避免部分提交后换绑。

现有 `ExternalShadowPort` 还需从“登录验证身份”细化为“受信目录投影命令”。目录本身没有 OIDC 的 sid／workspace／auth_time，不能填假登录字段来同步用户。该 DTO 修正不扩大目录事实或授权范围。

## 备选及不采用原因

- 只在 F118 回执上做 CAS：不能阻止旧 Owner 对 User 的实际写入。
- 把外部修订塞入 remark 或复用 DSH profile 版本：污染其他字段的业务含义。
- 每次投影复用 token_version 作栅栏：会额外使现有昆联 JWT 失效，扩大到期／重登行为；本提案不采用。
- 让所有 Owner 共享同一数据库事务：需要改变已确认的独立 Owner UoW 约定，牵涉范围更大。

## 影响、兼容与回退

- 增加第九张独立表；不修改已有 User／Tenant 的列、不迁移或认领历史账号、不授菜单或资源权限。
- 只在昆联新来源投影中使用；本地、企微、DSH 和开放接口的版本语义不改。
- 按既有模型发现登记和独立表创建规则编写声明；本轮仍不执行实际建表或部署。
- 回退关闭昆联准入／投影，保留状态表及证据；不删除历史状态、不恢复旧会话。
- 计划新增独立基础设施任务 T083（模型与发现登记），置于 T019／T020 前；原任务 ID 保留。相关 DTO、Owner 及投影恢复任务补齐依赖和测试。已按本次批准补入任务及模型声明，不执行实际数据库建表。

## 后续验证

在 Owner 集成中构造旧操作晚到、预留后失锁、User 提交后 F118 崩溃、同操作重试及新旧修订交错；断言 User 的最终资料属于当前操作、没有默认角色／Grant、F118 不误标投影成功。真实行锁和双 DB 仍需 T078 的环境证据。
