> **范围边界**
>
> 本 Feature 是批次 B 的「用」与「管」两面：让已上线托管应用被普通业务用户在 client 广场找到并打开（RT-02），让 owner 与租户管理员用平台既有授权件设可见范围（GOV-01 交互）、让全生命周期动作在既有审计页可查可导出（GOV-04）、验证界面通道零新增权限点（GOV-07）、验收 §3.0.3 事件触达全表并接线其中唯一未被 F055 覆盖的一处。它站在 F054（领域模型 / 类型注册 / 入口 / 详情页壳）与 F055（发布管线 / 发布 tab）之上，**不重复拥有它们交付的任何界面或对象**。
>
> **跨 Feature 归属规则（审计与触达，全文按此）**：审计事件的**写入**归事件发生的动作 owner——F054 状态动作（上线 / 待上线 / 手动上线 / 停运 / 重新启用 / 删除、元信息更新、数据行编辑、访问记录留痕）；F055 管线（提交 / 首发导入 / 预检失败 / 扫描阻断 / 审批单生成与四个终态〔复用审批中心事件、携带应用标识与版本号〕/ 待上线成因 / 手动上线请求 / 能力声明变更 / 运行期凭据签发回收 / 因删除取消）；F049 密钥全生命周期（AC-12）；F051 模型调用逐条；本 Feature 自己只写**可见范围变更**。**本 Feature 拥有的是**：事件类型的登记与查询面可查、审计查询面、导出、以及「GOV-04 事件清单每一行在审计面可查」的验收。触达同理：审批类 + 待上线（含「上线失败」成因）+ 因删除取消归 F055（AC-31 / AC-35 / AC-64）；本 Feature 只做「租户管理员停运 / 重新启用 → owner」这一处接线 + §3.0.3 全表的验收。
>

## 1. 用户故事

作为 **普通业务用户**，
我希望 **在应用广场里像找工作流、助手一样找到同事发布的托管应用，只看到我有权用的，点开就能用**，
以便 **不必知道「托管应用」和其它类型有什么技术差别，也不会点进一个自己没权限的应用**。

作为 **开发者（owner）**，
我希望 **首发上线后系统显著提醒我「现在只有你自己看得到」并直接给我设置可见范围的按钮，且这个弹窗和我给工作流授权的是同一个**，
以便 **不漏掉「设可见范围」这一步、也不用另学一套授权界面**。

作为 **租户管理员**，
我希望 **对本租户任一托管应用都能像对工作流一样在卡片 ⚙️ 里改可见范围，且谁改了什么、谁上线 / 停运 / 删除了什么、谁在用哪个应用，都能在既有审计页按「对象应用」查出来并导出**，
以便 **治理面前本地造的与平台造的应用无差别，出事能追到人**。

作为 **平台超管**，
我希望 **在审计页按租户筛选、跨租户查看托管应用的全部事件**，
以便 **多租户部署下能做平台级的合规追溯，而不必逐个切租户**。

作为 **审批人 / owner（事件接收方）**，
我希望 **审批单生成、被通过或驳回、被撤回或因删除取消、应用入待上线态、被管理员停运 / 重新启用时，我在工作台铃铛里能收到通知**，
以便 **不用守着页面刷新也能知道该我处理或该我知道的事**。

## 2. 验收标准

> AC 编号在本特性内唯一。括号内标注对应 PRD-1 条目与验收序号（如 `↔RT-02 验收 1`）；引用其它 Feature 的 AC 时写全编号（如 `F054 AC-10`）。错误码仅作可观测行为引用，定义在 design.md。

### 2.1 应用广场（RT-02）

- **AC-01** — WHERE 工场运行时层已部署, THE SYSTEM SHALL 在 client 应用广场把已上线的托管应用与工作流 / 助手**并列**呈现为同构卡片（图标 / 应用名 / 一句话描述 / owner 显示名），共用同一列表、同一组标签 tab、同一搜索框；不另开「托管应用」专属页或专属 tab。（↔RT-02 需求描述 / 验收 5；§3.0.1「用在 client」）
- **AC-02** — WHEN 托管应用首发审批通过且上线成功, THE SYSTEM SHALL 使其自上线起出现在可见范围内用户的广场中（首发默认仅 owner 可见，F054 AC-11）；审批通过前、待上线态（资源不足 / 上线失败两种成因）、草稿态一律不出现。（↔RT-02 验收 1；RT-03 验收 3；F055 决议-8）
- **AC-03** — THE SYSTEM SHALL 只把**已上线**与**已停运**两个应用态的托管应用呈现在广场：草稿 / 待上线 / 已删除态不出现；WHILE 应用已停运, 其卡片对可见范围内用户仍呈现并带「已停用」标识，点击落 F054 的「已停用」页；重新启用后标识消失。（↔RT-07 验收 4「广场呈已停用提示」；§3.0.2）
- **AC-04** — THE SYSTEM SHALL 使广场按平台权限判定结果过滤托管应用：不在可见范围内的用户，其广场的任何标签 tab、默认分类与搜索结果中均不出现该应用；租户管理员因既有身份短路可见本租户全部托管应用（不额外收窄，§4 决议-4）。（↔RT-02 验收 3 / 规则）
- **AC-05** — WHEN 用户被授予或被撤销某托管应用的可见范围, THE SYSTEM SHALL 自该用户的**下一次请求**起在广场中呈现 / 不再呈现该应用，无需重新登录、不依赖任何缓存到期。（↔GOV-01 验收 2；F054 AC-10）
- **AC-06** — THE SYSTEM SHALL 使广场对某用户呈现的托管应用集合与统一入口对同一用户放行的集合**同源一致**：不存在「广场可见但入口无权限」或「入口可进但广场不见」的稳态（AC-05 的下一次请求窗口除外）。（↔RT-01 规则「入口访问与广场可见性共用同一份可见范围」）
- **AC-07** — WHEN 用户点击托管应用卡片, THE SYSTEM SHALL 在**当前窗口**跳转到 `/apps/{应用标识}`（其后登录态 / 兜底页 / 身份注入等行为归 F054 AC-25–36），不进入对话式聊天页；托管应用卡片不提供其它类型既有的免登录分享动作（托管应用无免登录通道，§4 决议-6）。（↔RT-02 验收 4）
- **AC-08** — THE SYSTEM SHALL 使未设任何标签的托管应用在广场**默认分类**中正常可见，并可按名称 / 描述被搜索到；托管应用接入既有标签体系（若已有标签则出现在对应 tab）但本版不提供打标入口。（↔RT-02 验收 2 / 规则）
- **AC-09** — WHEN 应用元信息（名称 / 描述 / 图标）被更新（本版唯一来源 = CLI deploy 通过预检与扫描后立即更新，F055 AC-05；发布面元信息编辑随 PRD-2）, THE SYSTEM SHALL 使广场卡片自下一次加载起呈现新值，且该更新不产生审批单、不产生版本记录；其审计事件由 F054 AC-06 / F055 AC-05 写入，本 Feature 只保证在审计面可查（AC-23）。（↔RT-02 验收 5 / 规则）
- **AC-10** — WHERE 工场运行时层未部署, THE SYSTEM SHALL 使广场不出现任何托管应用卡片及与之相关的文案 / 筛选项，广场其余行为零变化。（↔GOV-10 规则；F054 AC-62）

### 2.2 授权交互（GOV-01）

- **AC-11** — THE SYSTEM SHALL 使托管应用卡片 ⚙️ →「管理权限」与应用详情页 · 发布「可见范围区」的设置按钮拉起**同一个**平台通用授权弹窗（可按用户 / 部门 / 用户组授予与撤销），两个入口保存后的可见范围结果一致；弹窗的选人场景不出现服务账号（INV-29）。（↔GOV-01 验收 1）
- **AC-12** — THE SYSTEM SHALL 在应用详情页 · 发布提供「可见范围区」：常驻呈现当前可见范围状态（「仅 owner 可见」或已授予主体的摘要）与设置按钮；WHILE 应用已上线且可见范围仍为「仅 owner 可见」, THE SYSTEM SHALL 在可见范围区**顶部常驻一条提示条**（文案含「仅 owner 可见」与「同事无法在广场看到」两个要素）并在提示条内提供设置按钮；设过可见范围后提示条消失。（↔GOV-01 验收 3；§2.2 主旅程步 5）
- **AC-13** — WHEN 经任一入口变更可见范围, THE SYSTEM SHALL 不生成审批单、不产生版本记录、不改变应用态；变更自被授权用户的下一次请求起作用于广场（AC-05）与入口（F054 AC-10）；并由本 Feature 写入「可见范围变更」审计事件（AC-22）。（↔GOV-01 验收 2 / 5）
- **AC-14** — THE SYSTEM SHALL 使租户管理员可对本租户任一托管应用经卡片 ⚙️「管理权限」查看并调整可见范围（既有身份短路，非本 Feature 新增）；审计中变更人记为该管理员本人；平台超管经租户管理视图代行时变更人记为超管本人。（↔GOV-01 验收 4；§3.3 矩阵注）
- **AC-15** — IF 非 owner 且非管理员的用户（含仅被授予可见范围的广场用户）尝试打开授权弹窗或调用其读写接口, THEN THE SYSTEM SHALL 拒绝（403）；被授予可见范围只获得广场可见与入口访问，不获得任何管理入口。（↔F054 §3「谁能进 ≠ 谁能管」）
- **AC-16** — THE SYSTEM SHALL 在 ⚙️ 菜单按类型裁剪落地后通过回归验证：**工作流与助手卡片的 ⚙️ 菜单四项与既有行为完全一致**；托管应用卡片的 ⚙️ 菜单符合 F054 AC-53（两项）与 F054 AC-42（已上线态删除置灰）。本条只做回归验证，不复述裁剪行为；为 GOV-01 验收 6 的验收归属。（↔GOV-01 验收 6 / ⚙️ 菜单裁剪注）

## 3. 边界情况

> 只写期望的对外行为；实现层的落点与数据访问细节见 design.md §5。

- **广场过滤与入口判定必须同源**（AC-06）：两者都是同一份可见范围（GOV-01）在不同面上的读出。广场若走与入口不同的判定路径，就会出现「广场看得到、点进去无权限」——这是产品明令的稳态禁区，只允许下一次请求前的短暂窗口。
- **广场是「用」面不是「管」面**：广场按平台权限判定结果显示，租户管理员因既有身份短路对本租户全部应用天然可见——本 Feature **不自造收窄**（§4 决议-4）；同理，被授予可见范围的用户只得到「能进」，不得到任何管理入口（AC-15）。
- **应用态与广场可见性的对应**：只有已上线与已停运两个态进广场（AC-03）；已停运保留卡片并标注已停用而非隐藏——隐藏会让用户误以为自己被移出了可见范围，且与 RT-07「广场呈已停用提示」相悖；草稿 / 待上线 / 已删除一律不出现，且不因用户是 owner 或管理员而例外（owner 与管理员看草稿在构建页，不在广场）。
- **未部署工场运行时层 = 广场零痕迹**（AC-10）：不出现卡片、不出现文案、不出现筛选项；广场其它类型行为零变化（NFR-4）。开关取值来自 F054（AC-61 / AC-62），本 Feature 只消费。
- **两个授权入口 = 一个弹窗**：发布面「可见范围区」只是同一弹窗的第二个触发点外加一处状态呈现，不是第二套授权界面；任何一方新增的授权语义（档位 / 主体类型）都应在弹窗内一次生效于两处。
- **「仅 owner 可见」提示是首发的必经提醒**：它常驻发布面，不是一次性 toast；owner 或租户管理员设过可见范围后提示消失、区块改为摘要呈现。
- **「写了必须查得到」是本 Feature 对每一类事件的承诺**（AC-27）：写入方（F054 / F055 / F049 / F051）只保证事件落库；事件类型能否在筛选下拉里被选中、列表里有可读文案，是本 Feature 的登记责任——任何一类事件「已写入但页面查不到」都算本 Feature 的缺陷（登记所需同步的几处实现义务见 design.md §5）。
- **高频事件同面可达、且不拖慢既有审计页**（AC-24 / AC-34）：访问记录、模型调用逐条、运行期能力调用与低频治理事件量级相差数个数量级；对管理员的承诺是「同一审计查询面经事件类型筛选可达」，同时既有审计页的低频事件查询不因它们的写入量而变慢（如何承载是 design 的事，写入方分别为 F054 / F051 / F055）。
- **访问记录只记「成功进入」**（口径与 F054 AC-38 一致）：被四类兜底页（无权限 / 已停用 / 不存在 / 未部署）拦下的访问不计入访问记录（那不是「谁在用」）；拒绝类访问的留痕不在本版范围；本 Feature 只保证可查、不写入。
- **服务账号执行的动作在审计里就是服务账号**（AC-17 / §4 决议-7）：操作人列如实呈现服务账号（+ 密钥掩码），另附应用 owner；不把 CLI 动作记成资源归属人本人所为——归属人「承接归属、不出借权限」（伴生 PRD 定义 6），审计也不替他背操作。字段由写入方（F055 AC-01）落，本 Feature 负责呈现。
- **已删除应用的审计可读性**（AC-21 / AC-28）：对象应用筛选必须能选到已删除应用（以名称快照 + 标识），否则「删除」事件本身查不到对象。
- **审计导出与查询同一权限边界**（AC-32）：导出不得成为绕过租户过滤或角色限制的旁路；超管跨租户导出按当前租户筛选范围。
- **触达的归属线**：审批类（生成 / 通过 / 驳回 / 撤回 / 因删除取消）与待上线（资源不足 / 上线失败）由 F055 AC-31 / AC-35 / AC-64 触达，本 Feature 只验收（AC-40–42）；本 Feature 唯一接线的是「租户管理员停运 / 重新启用 → owner」（AC-43）——它挂在 F054 的状态动作上、接收方是 owner，与管线无关，才落在治理面。
- **触达不阻塞业务**（AC-45）：站内消息是旁路，发送失败只影响「对方知不知道」，不影响「事情有没有做成」。
- **多租户下的广场与审计**：广场只列当前租户内的托管应用（既有租户过滤）；审计查询的租户边界沿用既有审计页的租户规则，对象应用筛选是租户内的二次筛选，不得穿透（AC-31）。
- **`create_app` 复用意味着无法单独灰度托管应用**（GOV-07 ①）：勾了该权限三种类型都能建——本版托管应用无界面新建入口，该代价暂不显现；灰度闸是部署开关（环境级）与按人签发密钥（人级）。

## 4. 待澄清决议

> 2026-08-17 用户授权全自动模式：以下各项按建议直接定案，记录理由供追溯；spec 评审（`/sdd-review`）后如有 high 级发现再增补。

- **[决议-1] 托管应用审计事件统一归入 `app.*` 命名空间（实现约定，design 承接、写入方 F054 / F055 遵守）；审批单四个终态复用审批中心既有 `approval.*` 事件、不重复记录；本 Feature 对外只承诺「托管应用事件类型在筛选下拉里成组可选」（AC-17）。**（审查修订：原为 AC-17 正文，命名空间属实现约定移入此处）理由：既有审计页按命名空间分组筛选，统一前缀让托管应用事件在事件类型下拉里天然成组（PRD-1 §3.3 锚点表建议）；审批通过 / 驳回 / 撤回 / 取消由审批引擎审计，再记一份 `app.*` 会让同一动作出现两条记录、误导取证——只要求这些记录携带对象应用与版本号、且能被「对象应用」筛选命中（AC-19，写入方 F055 AC-01 / AC-35）。**何时重新考虑**：若审计页改为按对象类型聚合视图，`approval.*` 事件无法按对象应用归组时由 F055 补一条镜像事件。
- **[决议-2] 访问记录的写入归 F054（AC-38：一次进入一条、不记请求级明细、只记成功进入）；F054 §3 留给本 Feature 定义的合并窗口取部署配置项、默认 30 分钟；本 Feature 只保证可查（AC-24）。**（审查修订：原口径把写入与「独立留痕通道」写在本 Feature，改按归属规则）理由：留痕点在统一入口（F054 组件），写入归动作 owner；PRD 要求的是「谁在用」（RT-01），一次进入即回答该问题，逐请求留痕既无产品价值又制造噪音；30 分钟窗口对齐常见会话粒度、避免刷新即多条；如何承载高频写入是 F054 / 本 Feature design 的事（Discovery §5 风险 9）。**何时重新考虑**：安全侧要求拒绝类访问留痕（如无权限尝试）时另立事件类型、写入仍归 F054。
- **[决议-3] 广场卡片的 owner 显示为其平台显示名（与工作流 / 助手卡片「创建用户」同一取值），不显示部门或联系方式。** 理由：与并列的两类卡片同构（RT-02「同构卡片」），且无权限页 / 已停用页已引导「联系 owner」——广场只需让用户认出人；部门信息在其它面（如通讯录）自查。
- **[决议-4] 租户管理员在广场按平台权限判定结果显示，本 Feature 不额外收窄。** 理由：`TENANT_ADMIN` 与 `SUPER_ADMIN` 并列身份短路对批量列表路径同样适用（Discovery §2.2），这是平台既有行为，PRD-1 §5.2 已据此取消 GOV-09 与「草稿对管理员不可见」；广场若单独对管理员收窄，将造出「构建页看得到、广场看不到」的类型特例，与工作流 / 助手不一致。
- **[决议-5] 已停运应用在广场保留卡片并标注「已停用」，不隐藏。** 理由：RT-07 操作表与验收 4 写「入口与广场呈已停用提示」；隐藏会让用户误判为被移出可见范围（与无权限不可区分），保留 + 标注让「临时下线」这一状态可感知，也与入口的已停用页口径一致。
- **[决议-6] 广场卡片点击在当前窗口跳转 `/apps/{应用标识}`；托管应用卡片不提供既有的免登录分享动作。** 理由：与工作流 / 助手卡片同为当前窗口进入，且 F054 四类兜底页均带「返回广场」按钮，同窗口语义下该按钮才成立；托管应用没有 share-token 免登录通道（RT-01 必须登录、F049 决议-1 的分享通道只覆盖工作流 / 助手两个 WS），卡片上出现分享动作只会导向一个不存在的能力——入口链接与二维码由发布面提供（F055 WB-14），owner 自行转发。**何时重新考虑**：产品要求广场卡片可复制入口链接时，加「复制入口链接」而非「分享」（语义是 URL 不是免登录票据）。
- **[决议-7] 服务账号执行的动作在审计中操作人 = 服务账号（+ 密钥掩码），并同时记录应用 owner（资源归属人）；不记成归属人本人所为——字段口径由写入方（F055 AC-01）遵守，本 Feature 负责呈现（AC-17 / AC-29）。** 理由：伴生 PRD 定义 6「归属人只承接归属、不出借权限」，审计如实记执行主体才能回答「哪把密钥干的」（泄漏取证）；同时记 owner 回答「责任落在谁头上」（GOV-07 ②）——两者并列与 F050 审计双归属（actor / subject）同向，不冲突。
- **[决议-8] 审计导出 = 导出当前筛选条件下的全部记录，受与查询相同的租户与角色边界；本条是既有审计页的新增能力。** 理由：GOV-04 界面表明写「支持导出」，而既有系统操作审计页只有查询、导出只存在于会话数据面；「按当前筛选导出」是最小且与查询语义一致的形态，避免出现「导出范围 ≠ 查询范围」的旁路。文件格式沿用平台既有导出格式（design 定）。
- **[决议-9] 发布 tab 内的「可见范围区」这一区块归本 Feature，发布 tab 其余区块归 F055（WB-14）。** 理由：release-contract 表 3 F056 行明写「发布面可见范围区两个入口拉同一弹窗、首发后仅 owner 可见显著提示」，它与 GOV-01 交互是同一件事、与发布管线状态无耦合；拆到 F055 会让 GOV-01 验收 1 / 3 跨两个 Feature 才能验。F054 首波壳中的可见范围按钮占位由本 Feature 接管为完整区块。
- **[决议-10] 本版托管应用不交付界面新建入口；GOV-07 界面通道验收以「既有新建入口受 `create_app` 控制 + 托管应用管理入口不受该权限影响」为准。** 理由：PRD-1 只定义 CLI 首发（DEV-04）与 PRD-2 工作台两条造应用来源，本册无「在构建页新建托管应用」的需求；GOV-07 验收 1 的语义是「无权限看不到新建入口、既有应用管理不受影响」，对托管应用而言后半句才是可验的实质。**何时重新考虑**：PRD-2 交付工作台入口时，该入口受同一 `create_app` 控制（零新增权限点承诺不变）。
- **[决议-11] 事件触达按归属规则：审批类（生成 / 通过驳回 / 撤回 / 因删除取消）与待上线（资源不足 / 上线失败）由 F055 触达（AC-31 / AC-35 / AC-64），本 Feature 只验收（AC-40–42）；本 Feature 唯一接线 = 「租户管理员停运 / 重新启用 → owner」（AC-43）。**（审查修订：原把「删除致取消」「待上线态」也列为本 Feature 显式接线，与 F055 AC-35 / AC-64 重复）理由：审批引擎已自动发 pending / approved / rejected / withdrawn 站内信（Discovery §2.7），F055 注册场景即得；待上线与因删除取消都是管线内事件、F055 已承接；重复接线会产生双份消息。停运 / 重新启用是 F054 状态动作、接收方是 owner、与管线无关，落在治理面最自然；「有且只有一条」按 AC-41 验收。
