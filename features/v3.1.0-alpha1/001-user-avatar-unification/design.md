# 技术设计 · 网页用户头像统一

- **依据**　[已确认规格](./spec.md)、[版本契约](../release-contract.md)、[架构宪章](../../../docs/constitution.md)
- **基线**　`alpha1-ui` · `ed1687aee8`。用户授权完成设计审阅、开发和验证。

## 1. 目标与现有链路

统一网页账号、站内通知和资源权限界面的个人头像读取、刷新与默认显示。实施边界以规格 §1 为准。

Client 与 Platform 都从 `GET /api/v1/user/info` 读取当前账户的 `avatar`。Client 通过 `POST /api/v1/user/avatar` 上传文件。用户域把头像对象键写入 `User.avatar`，由对象存储生成浏览器可访问的链接。Platform 现有窗口聚焦刷新只同步昵称和账号。

Client 默认头像已按 Unicode 读取昵称首字符。Platform 顶栏使用固定图片，资源授权界面各自处理图标和首字符。通知服务按收件人读取已有通知并补充发件人姓名，资源授权名单及选人服务分别读取各自的已授权分页。通知和这两条权限读路径均缺少统一的当前头像。

## 2. 约束

用户域拥有个人头像和签名。消息域只处理已返回的收件通知。权限应用层经业务目录端口取得展示信息，资源授权和租户判断继续走 F048。复用现有 SQLModel 兼容查询和 MinIO 浏览器路径。头像展示属于可降级的附加数据。各应用的数据查询继续留在 API 层和查询 hooks，组件接收已解析的图片地址。约束来源为 C1–C4 和 C7。

## 3. 决策

| 采用 | 考虑过的方案与判断依据 |
| --- | --- |
| 把现有 Client 头像样式迁入 `@bisheng/ui`，增加 `UserAvatar` 组合用法。调用方控制原位置尺寸，图片失败时展示同一首字符。 | 各应用本地实现会继续维护多个版本的颜色和 Unicode 回退。需要改变基准样式或增加头像类型时重审组件规范。 |
| 在 `@bisheng/identity` 统一浏览器地址解析。按应用部署前缀处理同源相对路径，保留已带前缀路径、HTTP(S) 绝对地址和签名查询。 | 在组件内部拼接会把各应用的部署规则带入展示层。生产由后端生成 `/object/` 路径，对象路由迁移时重新核对契约。 |
| 在两个业务列表读取时为当前有效身份生成地址。用户应用层按 `(租户, 用户)` 批量核对活动身份，每个可用用户按次签出。 | 在发送通知或授予权限时持久化地址，链接会过期，用户换图也无法同步到历史条目。签名吞吐成为瓶颈时可评估限时缓存并验证租户绑定和更新失效。 |
| 沿用现有刷新时机。Client 保存成功后更新本人缓存，Platform 切回标签页时将头像与最新昵称一起应用。通知页和权限弹窗重开时按既有路径读列表。 | 全局推送会新增跨应用身份订阅和版本同步。跨端需要实时更新时重新评估事件通知。 |

## 4. 数据与契约

| 入口 | 变化 | 授权与回退 |
| --- | --- | --- |
| 本人资料与更新 | 沿用 `avatar` 和上传流程。先取得签名、上传文件，再保存头像对象键。Platform 聚焦查询同步 URL 或空值。 | 保留登录身份校验和当前用户 ID 检查。存储或签名失败保留当前头像。旧资料没有字段时按空值显示。 |
| Client 通知 | 在现有每条 `MessageItemResponse` 增加可空 `sender_avatar`。头像按通知所属租户和发件人 ID 批量解析。 | 当前身份有效且在通知所属租户时签出。系统发件人使用系统图标。新版列表清理历史内容片段中的头像字段，旧接口缺字段时前端兼容旧内容。 |
| 资源授权名单 | 在 `subject` 增加可空 `avatar`。经租户目录端口批量补齐当前页的自然人。 | 名单在管理权限验证之后生成。头像使用已验证资源的租户，部门知识空间再复用现有选人范围过滤用户 ID。历史授权可见时照常返回该行，范围外仅回退头像。 |
| 新增/创建态选人 | 当前页候选用户增加可空 `avatar`，选中后把图片地址带到本地草稿。 | 复用既有候选的租户及部门范围。提交仍按已有授权参数传送。 |

用户域输出 `read_visible_user_avatar_urls(identity_pairs)`，以 `(tenant_id, user_id)` 为键映射到签名地址。权限层通过 `PermissionSubjectDirectoryPort.resource_user_avatar_urls(target, user_ids)` 只传已授权的目标和当前页 ID。存量由既有用户头像和身份关联提供。后端先行可为新版页面提供完整头像，字段缺失的页面使用兼容展示。无 DDL 与新增错误码。

## 5. 已知坑与检查

- 通知 `content` 的人名片段可能来自历史快照或带旧图，当前发件人以消息自己的 ID 为准。显式 `null` 代表服务端已判定无可见图片。
- 用户表是实例级身份。`user/application/avatar.py` 依据通知或资源的授权租户筛选。停用、迁出和歧义身份回退。`TenantPermissionSubjectDirectory.resource_user_avatar_urls` 对部门知识空间沿用部门子树边界。
- 预签名地址的查询字符串必须逐字保留。异步图片加载失败应仅影响该 URL，换图时允许新 URL 加载。
- 注意通知的已读副作用和权限写入 payload。仅在组件内渲染头像或更新草稿展示字段。

## 6. 验证

使用同名不同用户、旧通知、直接与继承授权、候选和已选草稿、跨租户与失效用户样本。页面验证包含 Client 上传、Platform 聚焦、通知和权限重开、坏图及恢复。HTTP 测试在隔离 ASGI 应用挂载真实路由，验证上传后已有通知显示新头像以及未授权读取。真实 MinIO、OpenFGA 和双库环境的验收以部署为准。测试用例与执行跟踪分别见 [测试用例](./test-cases.md) 和 [任务](./tasks.md)。

## 两端全局补查

知识广场出现破图后，用户将范围补充到两端已有的全部自然人头像位置。Client 知识列表、广场和详情使用可见创建者的 `avatar`，页面用 `creatorAvatar` 与空间图标分别传递。频道详情读 `creator_avatar`，成员列表兼容 `user_avatar` 和旧字段。Client 聊天通过 `resolveChatAuthor` 匹配作者身份，分享页面只使用该分享响应提供的作者资料。

Platform 租户成员、管理员、组织选人和模型授权接入同一 `UserAvatar`。数据由现有授权后的列表补充，按目标租户签发。组织目录当前管理租户无法签发的用户使用默认头像。应用日志、标注与日常聊天日志按授权后的消息作者和消息所属租户取得 `user_avatar`。演练发送阶段绑定本次会话的实际发送者，读历史时使用记录中的作者。应用卡片署名使用可见的创建者昵称，当创建者 ID 与本人匹配时显示当前用户资料中的头像。列表请求使用批量头像查询，头像缺失和图片错误统一在共享组件回退。

频道来源站点、租户徽标、审批流程状态和机器人使用各自的标识。
