# 租户业务边界与角色生效规则梳理

日期：2026-11-10；代码基线 `24c02859e2582ed319281bb52285c99930daf81c`，分支 `codex/3.1.0-beta1/managed-tenant-bugfix`。本次只更新文档；未修改业务代码、正式测试、历史评审快照、数据库或部署。

## 1. 结论、覆盖范围与证据等级

**建议保留“集团内全局身份 + 单一主属租户 + 租户业务资源隔离 + 明确例外”的模型。本次不引入普通用户的多租户执行身份。跨租户兼属是组织事实，不自动成为另一租户的策略角色、菜单和配额授予通道。** 此前规则已由用户在“按照建议调整后进行开发工作”中授权采用；本次将其转为正式规格，正式 spec/design 仍分别履行仓库确认点。

本轮质量属性优先级：先保证业务边界与身份正确，再保持既有合法共享/个人业务兼容，最后把提交、投影及异步失败变成可诊断、可恢复的结果。改变旧的跨租户角色生效结果属于显式行为收紧，需要影响清单和版本说明，不能当作纯查询优化无声上线。

之前未闭合的“角色绑定生产者与菜单/配额消费者”在本文按一套建议契约对齐：普通策略角色绑定给人，在其唯一当前主属租户内生效；部门是授予资格/作用域，不是现有绑定表已记录的授权来源。保持这一模型不需要立即新增“每部门一份角色授权”体系。若产品要求离开部门时连全局/无部门作用域角色也自动撤回，则必须另行增加来源账本，不能从旧 UserRole 反推来源。

本轮覆盖：

- **模型结构全量清点：** [184 个显式 ORM 模型清单](managed-tenant-model-inventory-20261110.md)，其中 150 个声明/继承 tenant_id、34 个没有。分类覆盖全部清点模型；这是源码结构统计，不是实际数据库表数、运行时注册数或安全验收。
- **业务域分类：** 下节覆盖平台控制面、身份组织、角色菜单、资源、共享、成员、审批、配额、开放凭据、运行、审计、DSH、缓存及外部存储；区分默认规则与专门例外。
- **重点调用链源码核对：** 部门加入/编辑/移除、默认角色、SSO 重建、主属迁移、归档、登录、菜单申请、配额、审批标签和 DSH 统一策略。调用者清单见 §5。
- **执行证据：** 原六项观察脚本此前合并 14 passed；本轮额外 4 个临时观察用例通过，见 §9。其余为源码结论或设计建议，明确标注；未做全量 HTTP、MySQL/DM8 或中间件验收。

证据层级：`运行观察`表示本机隔离执行；`源码确认`表示真实符号与调用者核对；`建议`表示待确认目标行为。下面的分类完整性不等于所有接口正确性已经证明。

当前模型适合单一企业/集团内部资源与配额管理。若目标是彼此独立客户、独立账号组织、独立运营控制面的 SaaS 租户，本模型的全局账号与组织挂载前提需要另行评估。

## 2. 必须分开的六个概念

| 记号 | 含义 | 权威来源及约束 |
| --- | --- | --- |
| H(u) | 用户 u 当前唯一主属/登录租户 | active UserTenant + 主部门解析；兼职不改变它，JWT 只是需要版本校验的快照 |
| M | 管理请求选择的具体目标租户 | 管理范围准入校验；只限允许的管理操作，不重写 H(u) |
| B(d) | 部门 d 的业务租户 | Tenant.root_dept_id、部门挂载元数据、有效状态与路径/祖先关系；不能直接读 d.tenant_id |
| S(d) | 部门存储 tenant_id | 原组织树的物理归属，可仍为 Root；用于存储读取，不等于 B(d) |
| O(r) | 资源/定义 r 的所属租户 | 已授权加载的记录及父对象；版本、子文件、菜单定义关系继承相应父归属 |
| T | 一次操作冻结的执行/写入租户 | 普通个人业务通常为 H(u)；超管管理写为 M；后台从持久操作/可信凭据恢复 |

`get_current_tenant_id()` 可能返回 M，不是 H(u) 的统一替身；`bypass_tenant_filter()` 只改变 SQL 过滤，不证明授权成立。全局平台身份、业务策略角色、部门管理员和租户管理员也是四种不同资格。

依据：[租户上下文](../../src/backend/bisheng/core/context/tenant.py)、[管理准入](../../src/backend/bisheng/admin/application/tenant_scope.py)、[部门授权边界](../../src/backend/bisheng/tenant/domain/repositories/grant_department_repository.py)、[身份解析](../../src/backend/bisheng/permission/application/identity.py)。

下表写“必须”时，表示建议契约；当前实现有差异的在 §4、§8、§9 单列。默认按所属租户隔离，并不表示同租户任意用户可访问；仍要检查业务动作、状态与敏感字段。

| 类别/业务 | 读取规则 | 写入及关联规则 | 代表实现、例外和核查边界 |
| --- | --- | --- | --- |
| 平台目录/控制面 | 不随 M 机械隐藏；按公共目录或平台维护资格 | 平台级维护；不因管理员切换 M 就改成子租户对象 | permission Catalog/模型发布、ResourceTier、runtime node/profile、license；完整模型见清单 G |
| 平台全局配置与租户覆盖 | 按配置 key 的专门解析协议区分平台设置、租户值、允许继承 | 本租户只写自己的覆盖，不反写 Root 原值 | `common/models/config.py`、`tenant_system_model_config.py`、`tenant_workstation_config.py`；不把 config 整表等同于用户可读目录 |

| RoleAccess 菜单定义 | 对已确定有效角色，按定义租户读取 WEB_MENU | 菜单行归定义，而不是每个消费租户；字段和关联同事务 | 仅 type=WEB_MENU 的定义读取；历史资源 AccessType 不能借机复活 |
| 工作流/助手/工具/Vibe app/灵思技能 | O(r) 范围 + 具体动作；管理读按 M 收窄，个人使用走原合同 | T、主记录、版本、children、投影一致；复制/移动另验 | `FlowDao`、工具 DAO、`app_runtime` adapters；模板/预置目录按对应类型读取，不一概等同私有或全局 |

| 会话/消息/项目/附件/引用/站内信 | 本人/会话/项目关系与原租户规则；能力分享用专门入口 | 使用可信个人执行范围；引用与附件必须验证对应会话/资源 | chat_session、message、citation、chat_attachment；个人默认/置顶是个人偏好，不是公共业务数据 |

## 4. 角色链路：代码当前实际做了什么

以下文件均在 `src/backend/bisheng/` 下，以符号为主，行号供当前基线定位。

| 环节 | 源码确认行为 | 后果/缺口 |
| --- | --- | --- |
| 部门候选 | `DepartmentService.aget_assignable_roles()` / batch 绕过过滤后按操作者 tenant_id 取自定义角色 | 不是目标部门 B(d)，也不是目标用户 H；先前已实跑复现 |
| 人员编辑展示 | `aget_member_edit_form():2972–3029` 用用户已绑角色与各部门候选交集展示 | UI 上多处出现同一个角色，不证明数据库有多份部门授权 |
| 保存编辑 | `aapply_member_edit():3166–3235` 对可分配角色域合并/替换，最终只增删 UserRole(user,role) | 无来源部门；先修改姓名/主属/组再校验角色可能部分提交；最终角色不能由操作者环境填租户 |
| 前端交互 | `OrganizationMemberEditDialog.tsx:155` 注释及 pruneSharedRoleEverywhere 明确说明多个下拉共享一个用户角色绑定 | 删除共享角色会联动其他下拉；当前产品实际不是“每部门独立 Grant” |
| 加成员/默认角色 | `aadd_members()` 后 `_grant_default_roles_to_users():1727` 只追加尚未拥有的角色 | 默认角色目前是入部门时授予，不是持续动态继承；改变默认配置并不自动收回旧角色 |
| 移除成员 | `aremove_member():1867` 删除 UserDepartment、部门权限/管理员及空间派生关系，未删除普通 UserRole | 无法凭该函数推断全局/无作用域角色应该自动撤销 |
| SSO 重建 | `LoginSyncService._replace_department_scoped_roles():548` 删除 department_id 精确命中 revoke_dept_ids 的角色，直接并入部门默认角色；调用者以全部旧/目标部门传入后再删除重建成员行 | 与本地移除不一致；同部门再次登录也可能重发种子；未复核其他合法部门仍支持同一角色；默认角色未走统一候选校验 |
| 主属改变 | `UserDepartmentService.change_primary_department()` 把旧主属降为兼属；`_apply_local_primary_department_change()` 删除旧主属关系 | 两入口组织事实都不同；均后置 sync_user；同步失败时可能主属已提交、H 未收敛 |
| 租户同步 | `UserTenantSyncService.sync_user()` 切 active 关系、token_version、身份投影/缓存/PAT、清管理范围；未重建普通策略角色 | 不自动将旧租户自定义角色变为新租户角色，资源也不会自动搬迁 |
| 归档/删除部门 | `DepartmentArchiveCleanupService`、部门删除流程清作用域角色及绑定 | 属于删除定义，不是单个用户离部门；必须避免角色消费者读到已失效定义 |
| 初始化登录身份 | `LoginUser.init_login_user():535` 用 bypass 按 user_id 读取全部 UserRole | LoginUser.user_role 可包含跨租户绑定；本轮真实 SQLite 观察已确认 |
| 当前用户信息 | `/user/info:180` 又按环境过滤查询 UserRole，传入 get_roles_web_menu | 与初始化身份的集合可不同；管理范围变化还能让后台函数读到另一组绑定 |
| 菜单 | `get_roles_web_menu():668` 合并角色 WEB_MENU、个人菜单授权、部门管理员系统入口并剔除孤立子菜单 | RoleAccess 受环境过滤，全局定义菜单会丢；个人授权用 get_current_tenant_id，管理请求中可能错读 M |
| 菜单申请模式 | `compute_menu_approval_modes():810` 从角色 quota_config OR 合并 workbench/admin flags，旧 key 回退 | 与菜单和配额必须共用同一合法角色集合；不能只修数字 quota |
| 配额 | `get_effective_quota/get_all_effective_quotas/check_quota/upload_limit` 各自查询 UserRole/Role | 绑定过滤、全局定义过滤、使用量跨租户和剩余额度比较是不同问题 |
| 审批路由 | `ApprovalGate._get_user_role_labels()` 加 role_{id}；另读平台/租户/部门管理员资格，多段异常被忽略 | 普通 role 标签应走有效集合；读取失败不能只剩 regular_user 后误命中 catch-all/pass；不能改为所有角色跨租户并集 |
| DSH | 旧 SubjectPolicy 的 ROLE 默认排除、仅迁移读取可 opt-in；现行 UnifiedPolicy 的可见性和 credit 仍接受 ROLE | 不能宣称 DSH 所有角色政策已退役。`_role_ids()` 严格按 tenant 读 UserRole，需消费同一合法绑定规则 |

关键事实：F048 的 `LegacyRBACSyncService.sync_user_role_change()` 普通角色不再投影资源权限，仅处理 AdminRole 的全局 super 身份；但“普通角色不授业务资源权限”不能推广为“角色只被菜单和普通配额使用”，审批标签、DSH 统一政策等仍有消费者。

两个额外接线风险：SSO `_execute_locked()` 先在 bypass、Root ContextVar 下重建角色/成员，再调用 sync_user，普通绑定不能靠该环境填正确目标 H；`OrgDirectoryService` 和 DSH `_departments()` 仍有按部门存储 tenant_id 读取租户部门的路径，挂载模型 S(d)≠B(d) 时可能遗漏。后者需作为业务部门解析的消费者接入，不只是修组织管理页面；本轮只核对源码，未完成这两个入口的真实 HTTP 复现。

## 6. 建议的角色、菜单、兼属规则

### D01：一个生效租户，组织关系可以跨租户

普通用户当前执行身份只有 H(u)。兼属 d 不会增加第二个 active UserTenant、修改 JWT、改变菜单/配额预算，也不会绕过资源租户门禁。组织鉴权提供器仍可读取本人完整部门与祖先事实，资源最终资格仍由现有业务目标及统一权限运行时决定。

超管选择 M 可以管理该租户资源，但这不等于普通用户拥有租户切换能力。部门管理员拥有某个外国租户部门的组织管理资格，也不自动拥有该租户所有业务资源或另一个用户 H 内的策略编辑资格。

### D02：保留按人绑定的策略角色；不要把 UI 下拉误作来源账本

本轮推荐最小兼容模型：普通绑定逻辑唯一键为 `(生效租户,H 下的用户,角色)`，由业务协议显式确定归属；是否增加对应 DB 唯一约束要先清点重复，数据修复与 DDL 分开。AdminRole=1 作为平台身份独立处理，不从部门默认角色发放，也不跟随普通绑定迁移。

普通有效角色集合 E(u,H) 需要同时满足：

1. 当前身份/租户状态有效，绑定明确属于 u 在 H 的策略；不能因 ambient M 将合法绑定隐藏或另一个租户绑定激活。
2. 全局定义 role_type=global 可跨存储租户读取，但仍需合法绑定；租户自定义/历史空 role_type 仅允许 O(role)=H。
3. 有 department_id 作用域的角色，用户至少保留一个当前有效成员部门 d，使 B(d)=H 且 d 位于该作用域子树。祖先读取完整，但不能用别的租户成员事实支持该策略角色。
4. 角色/作用域部门已归档、删除，或绑定/定义不一致时，不参与菜单、配额、审批标签及 DSH；缺失/故障不能伪装成正常“没有角色”。正常无角色仍沿用现有默认配额，不自动获得菜单。

这一步是建议新增的完整有效性协议，不是当前原始 UserRole 查询已经保证的性质。无效历史绑定要可诊断，不直接删除、改写或自动激活到别处。

### D03：跨租户兼属不能给主属租户授菜单和预算

对已有用户在部门 d 的角色编辑，普通部门授权必须同时满足 B(d)=H(u)，再校验操作者对该策略/部门的管理资格。B(d)≠H(u) 时：

- 允许按现有授权维护该兼属关系及相关组织字段；角色面板显示“跨租户兼属不授予策略角色”，不提供可提交的普通策略角色（包括全局角色）。全局角色定义可见性不等于外国部门管理员可修改用户主属政策。
- 服务端拒绝带角色变更的伪造请求，先校验再写其他字段；后台也必须拒绝，不能只隐藏 UI。
- 加兼属时不发该部门默认角色，返回可解释的“不适用”结果；不得让“组织关系成功、角色被静默过滤”看似完整成功。批量按用户判定，不用操作者租户判断全部人员。
- 超管若需要修改该用户政策，应通过明确的用户主属策略管理目标 H 完成并审计；不借外国部门编辑接口绕过边界。

单个 `assignable-roles(dept)` 没有目标用户参数，返回的是**本部门可供本租户用户选择的定义目录**；人员表单/最终保存必须再按目标 H 收窄，不能仅复用这个目录作为全部授权证明。新建本地主属人员按已验证目标部门计算预期 H，随后建立一致的成员和身份关系。

### D04：同租户多部门与撤销保持可解释

同一 H 下多个部门的 UI 仍共享一个用户角色绑定，和当前前端注释一致；角色不是“在某部门生效、到另一个部门失效”的局部菜单。角色修改是用户 H 内的政策修改，需要在 UI 明示可能影响其他部门下拉展示。

- 全局/无部门作用域角色：属于对人的直接策略。离开某个部门不自动撤销；“部门默认角色”保持入部门时种子授予，删除默认配置只影响之后发放。明确要求对存量授予时再执行受控发放；不承诺动态撤销。种子触发必须是业务上真正的新成员关系或新 H 激活，不是 SSO 重写同一快照；同部门反复登录不重发已被人工撤销的默认角色。用同步前后成员集合判定变化，不能用被 SSO 重建的成员行 ID 充当新加入事件。
- 有部门作用域角色：退出/归档/移动后重新判定剩余合法部门。若另一个同 H 的部门仍支持该作用域，保留；若没有，撤销该绑定或置为明确无效，立即退出 E。以后重新入部门不能让旧行通过过滤变化自动复活；若本次真正的新加入符合当时默认角色规则，可用新的、可审计的授予动作建立绑定，和旧行复活区分。SSO 和本地入口共用判定，不能仅按离开部门 ID 精确删除。
- 如果产品要求“哪个部门发的全局/无作用域角色，离开该部门就收回，但其他来源仍保留”，应另立来源化授权方案（user/role/有效租户/source/source_ref），维护有效绑定投影；旧数据无法还原来源，需显式 LEGACY 来源和运维裁决。**本次默认不引入此结构，也不承诺这种自动撤权。**

**评审建议落定（2026-11-10）：角色定义改作用域同样触发资格终止。** 修改角色的部门作用域后，应对已有绑定逐人核对剩余合法成员关系；失去资格的普通绑定予以终止并留审计，不能只清缓存或暂时退出 E。之后把作用域扩大、改回原部门或清空，不自动恢复已终止绑定；仍然合法的绑定继续保留，新的合法默认/显式授予可建立新绑定。定义修改需先形成受影响用户与政策预览，再完成可恢复的变更；结果不确定时不能宣称已全部生效。该规则不扩展为角色字段每次编辑都重新授予。

### D05：菜单是 H 内能力并集，资源授权另验

建议公式：`菜单 = E 的 WEB_MENU 并集 + H 内有效个人菜单授权 + 现有身份派生入口`，再执行现有父子菜单剔除。超级管理员仍走既有完整菜单资格；部门管理员保留当前组织管理入口规则，但每个实际接口仍核验具体部门/租户资格，不能仅凭 system_config 菜单改平台或外国租户设置。

全局 RoleAccess 按定义 O(role) 读，UserMenuAccess 按 H 读；M 的改变不得改变普通人的登录菜单。菜单申请模式也用同一 E，workbench/admin flags 保持 OR 与旧 key 回退，不改成数字配额聚合。菜单允许进入或创建，不代表授予某个现有资源 edit/manage_permission。

### D06：调岗、迁移、失效和缓存

主属变动前先确认本次入口到底保留还是移除旧成员关系，并规划目标 H、受影响角色与资源规则。原 UserDepartmentService 与本地人员编辑的不同语义必须在正式设计中对齐或明确保留，不能用同名“调岗”掩盖差异。

- H 未变：全局/无作用域直接策略保留；作用域角色按剩余成员重新判定；B 变化同样重算。
- H 从 A 变 B：A 的自定义角色、A 的个人菜单授权不在 B 生效；不按角色同名复制。B 的默认策略通过当前 B 合法部门/明确授予建立。全局定义可复用，但旧 A 的普通绑定**不自动迁移到 B**，避免旧管理员政策影响新租户；是否赋予 B 的同一全局角色由 B 合法发放流程决定。迁移成功时以审计支持的绑定撤销或明确终止记录结束旧普通绑定，不能只在查询时暂时藏住旧行，否则回迁会自动复活；平台 AdminRole 不走该处理。旧 A 审计历史保留。
- 部门更新、H 同步、策略重算及身份版本不能在失败时悄悄错位；应有操作状态/恢复顺序。资源转移前置策略阻止时不能返回“完全成功”。尚未收敛的个人身份敏感操作拒绝并给恢复状态，不能靠旧 H 或新 B 猜测继续授权。
- 现有调岗 token_version 失效与管理范围清理保留；角色定义/绑定/个人授权变化还要失效受影响菜单/策略/DSH 缓存，前端重取用户信息，后续请求重新解析。普通角色 LegacyRBACSyncService 目前直接返回，不等于它已经清理了这些缓存。新策略集合不应跨请求缓存而无失效依据。
- 已开始的执行是否终止按各业务既有合同；不承诺回滚已完成动作。延迟审批/后台创建在执行时复核当前资格。

策略读取故障不能退化成普通无角色：审批动态标签失败不得继续匹配 regular_user 的免审分支；DSH 角色读取失败不得变成“无匹配规则→不限”。正常成功读取后确实无匹配规则时，DSH 仍保留现有不限合同，因此撤销角色不必然降低 DSH 额度；影响预览必须显示这一点。角色改变应按 DSH 的版本化操作重算、同步 gate/epoch，不清零已用额度，也不只清一个页面缓存。

## 7. 配额生效规则与新发现

### 7.1 预算归属和计量必须分开

普通创建 T=H(u)；超管管理创建 T=M，保留现有超管短路政策。开放 API/后台从可信凭据或持久化操作取得 T，不以兼属关系构造第二套预算。

策略上限来自 E(u,H)；用户用量建议按 `(user_id,T,resource_type)`；租户上限和租户用量按 T/其有效 Root 链。旧租户资源仍留原地，消耗旧租户容量，不继续扣新租户的用户角色预算。共享使用不因为可见就算作接收方创建资源；复制成功生成接收方自己的资源才按对应创建/存储合同计量。

这里的 user_id 是该指标的**预算责任人**，不一定等于操作者。调用额度服务前必须构造经业务验证的预算上下文：操作者、预算责任人 q、策略租户 P、资源/执行租户 T、具体指标与增量。普通个人额度要求 `P=H(q)=T`；不能让任意调用者把 P 参数当作跨租户读角色的授权。

| 操作 | 预算责任人及策略/计量租户 |
| --- | --- |
| 普通用户新建资源 | 创建者 q，P=H(q)=T；计个人 (q,T) 与租户 T/Root 链 |
| 管理者给他人频道加资讯源 | 保留现有频道创建者计量合同：q=channel.user_id，T=O(channel)，先验证 H(q)=T，再用 E(q,T)；操作者只证明 edit 资格，不代替 q |
| 上传、订阅等其他指标 | 明确该指标按上传者、订阅者还是容器责任人计量；尊重现有专门合同，不能把全部指标换成资源 creator |
| 超管在 M 新建 | T=M，身份不变；按既有明确超管例外处理个人策略，不能为了满足普通等式改写身份；租户/存储例外逐项沿原合同 |
| 共享模型调用/托管 app/服务账号执行 | 按可信调用/凭据和该业务计费合同确定责任与 T，不因为底层模型在 Root 就把请求计入 Root 用户策略；不硬套自然人角色预算 |

**Q03：旧资源责任人已迁移时，默认禁止增加受个人额度约束的用量，允许有权限的读取、删除、缩减和不增量维护。** 真实消费者 `channel_service.py:1881–1889` 用频道创建者检查资讯源新增；若创建者已 A→B 而频道留 A，不能读取 E(q,B) 支付 A 扩容，也不能自动恢复已终止的 A 角色或改用编辑者预算。先走资源所属租户内的明确归属/预算责任交接，确认接收人当前 H=A 且确实承担该指标，再允许新增。若现有转移入口仅改 FGA owner 而不改变该指标的责任依据，则不视为完成交接；当前未具备可验证交接能力时返回明确阻断原因，保持止增，不为绕过而修改历史创建者字段。交接能力的字段/入口若需新增应另列正式设计，不在本批凭空建设通用计费系统。

此规则同时用于 creator/owner 与操作者不同的旧资源增量调用者盘点。资源使用授权和额度责任是两次不同判断；预算责任失效不意味着删除旧资源或扩大其访问范围。

当前 `get_user_resource_count()` 对多项资源只发 `WHERE user_id=:id` 的原生 SQL，ContextVar 不会补 tenant；本轮真实 SQLite 两租户各一条 workflow，H=1 时个人计数得到 2、租户 1 计数得到 1。修复必须核对每个资源的实际物理所属模型；不能只改一个通用模板就假定所有订阅/文件/空间计量相同。

**Q04：用量不可确定时拒绝受额度控制的增量，不伪装为零。** 当前 `_count_resource()` 的异常返回0、`_distinct_info_source_ids()` 异常返回空集合均可能使检查放行。后续实现必须区分成功查得零/空集合和统计失败；任何必需的个人、租户或 Root 链统计不可确定时，停止相应新增/扩容/订阅写入，保留可诊断错误。只读显示应明确不可用，不能把未知写成余额充足；合法减量/删除按其原权限规则可执行。此失败合同与并发允许轻微超额是不同问题，不通过分布式锁解决。

### 7.2 数值合同不是一套聚合算法

- 通常的数量型策略：各有效角色取最大；任一 -1 表示该角色预算不限；单个角色 0 不允许创建，但与其他正值/不限角色并存时按现有最大值规则；缺省按现有常量。
- `knowledge_space_file`：当前实现及 F005 AC-17b 使用**最小有限正值**；-1 只在无有限值时取不限；全部缺省/历史 0 则回默认 500 GB。生产校验函数允许 -1 或 0.1～99999，一位小数，**不接受 0**；其旧注释仍写999，本文以可执行条件为准，不顺手收紧配置。不能把数量配额的“0=禁止”机械套到这个字段。
- 菜单申请模式 flags：布尔 OR，和数字 quota 分开。
- DSH credit：现行 UnifiedPolicy 取匹配 USER/DEPARTMENT/ROLE 的最大 allowance，无匹配为不限，已匹配 0 保留；独立额度/epoch/结算，不接入普通 QuotaService 的算法。
- 超管短路、租户存储单独硬限制沿现有合同逐项保留，不把一个入口的例外推广到全部资源。

### 7.3 “上限”和“剩余”不可混比

当前 `check_quota()` 先将 role_limit 与 tenant_remaining 取 min，再与累计 user_used 比较。本轮失败注入观察：role_limit=10、user_used=5、tenant_remaining=3 时，仍抛角色超限。建议按新增量 Δ 分别检查：

- 数量创建：`user_used(u,T) + 1 <= role_limit`，同时租户链每个节点均容得下新增的 1。
- 可展示剩余额度：`available = min(max(role_limit-user_used,0), 各租户节点 remaining)`；无限值按无穷处理。
- 字节/订阅等使用其真实增量和对应计数规则；不把剩余额度再减一次累计用户用量。

这是与角色过滤不同的配额语义问题，列为方案扩展 Q02。建议分开提交/验收。现有 `role_quota/tenant_quota/tenant_used/user_used` 口径保持清楚；优先增补明确 `available` 展示并让检查使用独立上限/用量，不无声改变 `effective` 的既有响应含义。是否调整旧 effective 字段与前端消费，要在正式设计中明确兼容方式。

**并发保证维持现有 F005 AC-23 / INV-11：普通 QuotaService 是提交前检查，允许并发产生轻微超额，不在本次引入分布式锁或严格额度预留。** 上述公式是单次读取快照下的正确判断，不是多请求原子承诺；available 也为快照。两个请求争用最后一份余额仍可能都通过，后续检查应拒绝；用例需要明确这一预期，不能以算法修复宣称已提供并发硬限制。若某指标必须严格无超额，应单独确认并设计它的检查—持久化协调边界；DSH 既有原子结算/epoch 和 app 容量预留继续走各自协议。

## 8. 替代方案与迁移建议

| 方案 | 评价 |
| --- | --- |
| 本轮推荐：单 H 生效，外国兼属仅组织事实，策略角色按人绑定 | 符合现有唯一 active UserTenant、登录与资源门禁，不制造普通租户切换能力；需要收紧跨租户默认/显式角色发放并统一消费者 |
| 各兼属部门的角色都并入本人菜单/配额 | 不推荐：租户 B 的部门管理员能影响租户 A 的创建能力、预算和审批路由；隐藏数据并不能修复这种政策越界 |
| 外国角色仅在切换到该租户时生效 | 可作为未来能力，当前没有普通用户可信多租户身份/切换合同；需同时改成员准入、凭据、菜单/配额缓存、资源/审计、迁移，不能仅把过滤改宽 |
| 每部门来源独立授权与撤销 | 有明确“离部门即撤回该来源”需求时再做；新来源账本和旧数据判定成本真实存在，不为消除 UI 重复展示先加一套通用授权体系 |

存量数据先只读盘点：绑定属于目标 H 但定义外租户、绑定 tenant 与 H 不同、缺失/归档定义、重复、AdminRole、作用域已失效、全局角色菜单 tenant 错位。普通绑定实际归属可能是旧需求，也可能是操作者环境填错，不能不加证据就统一改成 H。

新协议应即时排除已明确无效政策，故障/缺失不能宽松放行；需保留诊断解释与审计。修复旧行、加唯一约束、搬迁 global 绑定、清理投影分别制订运维步骤，不在 Alembic 做数据修复，也不在本轮删除生产记录。SSO 与历史初始化数据来源不明时不得推测来源部门。

影响预览至少列出每个目标用户旧/新 E、菜单、菜单申请模式、普通配额、审批 role 标签及 DSH ROLE 匹配差异。新政策不能因兼容之名恢复越界绑定；合法行为若受影响则先定位是错误归属还是产品契约变更。新增/删除绑定与后续跨系统失效需要同一可恢复业务操作，回迁和重试不得重新激活已终止旧策略。

## 10. 建议验收场景（供正式 spec/design 使用）

| 编号 | 场景 | 建议预期 |
| --- | --- | --- |
| TB01 | u 主属 A，兼属 B；B 管理员加兼属 | 组织关系可按授权成功，H/JWT 不变，不发 B 默认角色，不改变 A 菜单/预算 |
| TB02 | B 兼属编辑伪造全局或 B 角色 ID | 服务端在任何姓名/主属/组/角色写入前拒绝政策变更；不依赖前端禁用 |
| TB03 | u 在 A 的两个部门都能选择全局角色 g | 当前按人一份策略；菜单/配额只聚合一次；同租户多下拉明确共享绑定 |
| TB04 | u 离开 A 的某部门，仍有另一合法作用域成员关系 | 作用域角色保留；否则退出 E；全局/无作用域直接角色不假装按来源自动撤回 |
| TB05 | u 从 A 调往 B，旧资源留 A | 原 A 自定义角色/个人菜单不在 B 生效，B 政策明确重建；旧资源计入 A，不扣 B 的个人角色预算 |
| TB06 | 主属提交后租户同步/角色重建故障 | 有可见未收敛状态和恢复过程；不能以错误的 H/B 继续执行敏感创建 |
| TB07 | 超管账号 H=A，管理 M=B | 身份不改；资源/版本归 B；全局角色定义/菜单仍按定义归属；无意外用户策略漂移 |
| TB08 | 全局定义菜单属于 Root，用户 H=B | 登录、user/info、菜单断言、申请模式、Quota、审批标签和 DSH 取得一致合法 E |
| TB09 | 有效数量角色 0/正值/-1，多角色及 storage | 分别按 MAX、MIN 和 flags OR 的既定规则；不存在过滤后把配置误当缺省 |
| TB10 | role_limit=10，个人5，租户剩余3 | 可再创建1；available=3；边界耗尽与精确 Δ 分别测试 |
| TB11 | SSO/本地/默认批量发放同一最终成员关系 | 有效政策一致，不因调用者 H/M 或写入先后出现不同 tenant_id |
| TB12 | 共享模型、能力链接、公共目录、Root 私有资源 | 专门合法通道保持；Root 可被 SQL 查到不意味着资源可用或可编辑 |
| TB13 | 角色/成员撤销后菜单、审批、DSH/异步任务再执行 | 后续决策取当前有效集合与各自目标，不命中跨租户旧缓存或普通角色身份捷径 |
| TB14 | AdminRole、租户管理员、部门管理员与普通策略角色混合 | 全局身份不会被普通 H 过滤撤掉；普通角色也不能伪造管理员身份 |
| TB15 | 频道创建者 A→B，频道留 A，A 的合法编辑者新增资讯源 | 原责任人 H 与资源 T 不一致时止增；不得读 B 策略或换编辑者预算；合法维护/缩减仍可按权限执行，责任交接真正完成后再增量 |
| TB16 | 两请求争用普通 Quota 最后一个名额 | 保留提交前检查允许轻微超额的现有合同，后续检查拒绝；不把快照 available 当严格预留 |
| TB17 | SSO 对同一最终部门快照重复登录，角色曾人工撤销 | 不重发种子；真正新加入/新 H 激活的新合法授予可以重新建立绑定，并有独立审计 |
| TB18 | 角色定义由 A 缩到 B 再改回 A/扩大/清空 | 缩小后无合法成员支持的绑定终止并审计，后续定义扩大不自动恢复；始终合法的绑定保留 |
| TB19 | 个人/租户/Root 用量或资讯源去重统计超时、SQL失败 | 增量操作拒绝，业务数据不写入；展示明确不可用，不返回假0或充足余额；真实零与失败分别验证 |
