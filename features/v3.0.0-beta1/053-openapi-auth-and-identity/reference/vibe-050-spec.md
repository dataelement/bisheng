## 1. 用户故事

作为 **自建业务系统的集成方（如集团 OA、CRM）**，
我希望 **拿一把管理员配好委托范围的密钥，在请求里声明「这次是替张三问的」，就能让张三在我们系统里搜到的知识库和他在 BiSheng 里搜到的一模一样、创建的资源直接归张三**，
以便 **把 BiSheng 的能力嵌进员工每天在用的系统里，而不必让员工切到 BiSheng 平台，也不必自己维护一份权限镜像**。

作为 **被代表的员工（张三）**，
我希望 **集成方替我发起的对话与创建的知识库，回到 BiSheng 工作台就能像我自己做的一样看到、续问、管理；而任何人都无法借集成之名让我"看到"我本无权访问的内容**，
以便 **在自建系统与平台之间无缝切换，同时我的权限边界不因走了 API 而放宽或收窄**。

作为 **面向外部访客的应用运营方（客服机器人）**，
我希望 **在每次调用里带上访客的外部标识，让会话按访客分区、审计能区分是哪个访客的对话，而数据边界仍然只由服务账号被授予的知识库决定**，
以便 **既不为访客批量建号，也不因"外部用户"就丢掉权限过滤——爆炸半径始终锁在服务账号的授权范围内**。

作为 **租户管理员**，
我希望 **在签发密钥时一眼看清「这把密钥能替谁说话」（部门 / 具体人）、勾了委托就必须配范围且不能同时配本地开发工具包、名下有委托密钥的服务账号在列表和授权页上被显著标出**，
以便 **委托边界由我集中收敛，不会出现"配了却谁都代表不了"或"授权页看着零授权、实际能读全员数据"的误判**。

作为 **安全与合规负责人**，
我希望 **每一次开放 API 调用都能同时回答"哪个系统调的"和"以谁的名义调的"；委托永远不能指向管理员、不能指向另一个服务账号、不能跨租户；缺了身份就报错而不是给个"安全"的子集；升级后旧的裸 `user_id` 参数彻底失效**，
以便 **委托是有上界的提权、可追责的替换，而不是"请求里写谁就是谁"的匿名冒充**。

## 2. 验收标准

> AC 编号在本特性内唯一。与伴生 PRD §五验收标准的对应关系在括号中标注（如 `↔AC-6`），便于双向追溯；伴生 PRD 未单列 AC 的需求以章节号标注（如 `↔§4.3.4`）。
> 错误码（`26004`–`26007` / `26010` / `26016`，另引用 F049 已启用的 `26003`）在此仅作为可观测的对外行为引用，其定义与归属写在 design.md（模块号 260，release-contract 已登记「委托类错误码的实际启用随 F050」）。
> 术语：**模式 S** = 以密钥主体（服务账号）身份执行；**模式 D** = 代表平台用户执行；**被代表用户** = `X-Bisheng-On-Behalf-Of` 指向并通过五道准入的自然人；**外部标识** = `X-Bisheng-End-User` 的取值。

### 2.1 身份模式与请求处理流程

- **AC-01** — THE SYSTEM SHALL 对每一次开放 API 请求按固定顺序处理：凭据校验（F049）→ 密钥权限位判定（F049 AC-04，**所有模式通用、先于模式分流**）→ 依「密钥是否持 `delegate`」与「是否携带 `X-Bisheng-On-Behalf-Of`」分流为模式 S 或模式 D → 执行；**只存在这两种身份模式**，不存在第三种模式或任何"部分身份"的中间态。（↔§4.3 / §4.3.1）
- **AC-02** — WHEN 密钥不持 `delegate` 且请求未携带 `X-Bisheng-On-Behalf-Of`, THE SYSTEM SHALL 以模式 S 执行：权限基准 = 密钥主体、资源归属 = 密钥主体（经资源归属人机制，F049 AC-24）、会话归属 = 密钥主体（F049 AC-25）；返回结果的可见范围等于该主体的权限边界。（↔§4.3.2；承接 F049 AC-32）
- **AC-03** — WHEN 密钥持 `delegate` 且请求携带 `X-Bisheng-On-Behalf-Of` 且五道准入全部通过, THE SYSTEM SHALL 以模式 D 执行：执行身份、权限基准、资源归属、会话归属**全部**为被代表用户；密钥权限位层（AC-01 的第二步）在模式 D 下**照常生效**——持 `delegate` 但缺目标端点权限位仍返回 403 `26003`。（↔§4.3.3 / §4.4.1 / §4.3.5）
- **AC-04** — IF 密钥**不持** `delegate` 而请求携带 `X-Bisheng-On-Behalf-Of`, THEN THE SYSTEM SHALL 返回 403 `26004`，不执行任何业务逻辑、不返回任何业务数据、**不静默忽略该头而按模式 S 执行**。（↔AC-6；检查 1）
- **AC-05** — THE SYSTEM SHALL 使一把密钥的身份模式在签发时即确定：持 `delegate` 的密钥只能以模式 D 调用（漏传头见 AC-30）、不持 `delegate` 的密钥只能以模式 S 调用（传头见 AC-04）；调用方无法逐次选择模式；需要两种模式的集成须持两把密钥。（↔§4.3.2 / §4.2.4「勾选即强制」/ §7.3 D8）
- **AC-06** — THE SYSTEM SHALL 只接受 `X-Bisheng-On-Behalf-Of` 的取值为**单个平台用户 ID**（被代表对象永远是单个用户）；IF 取值为空、非单值或不是该形态, THEN THE SYSTEM SHALL 返回 400 参数错误、不进入准入检查；本版**不接受用户名形态**（§4 决议-1）；调用方标识与平台标识不一致时的映射由调用方负责，平台不承担映射。（↔§4.3.3 / §4.4.4 引言 / §3.2）
- **AC-07** — THE SYSTEM SHALL 为每个开放 API 端点声明允许模式——按伴生附录 B.1「允许模式」列（绝大多数 S/D；`GET /filelib/download_statistic`、`POST /llm/workbench/asr` / `/tts` 仅 S；F058 端点上线时按其行声明）；**不存在未声明允许模式的可达端点**（与 F049 AC-29 同一条校验路径、同等完整性）；WS 两端点与 HTTP 同一套声明。（↔附录 B.1；检查 5）
- **AC-08** — WHEN 两个 WebSocket 端点的握手携带身份传递头（`X-Bisheng-On-Behalf-Of` / `X-Bisheng-End-User`，经握手请求头传递、与密钥传递方式一致）, THE SYSTEM SHALL 在**握手期**完成模式判定与五道准入；准入失败即拒绝握手并优雅关闭（不产生未捕获异常，形态同 F049 AC-31）；握手通过后整个连接期内的执行身份、会话归属与分区键按握手结果固定。（↔附录 B.1 WS 两行 ⧗ S/D；§4.6.1）
- **AC-09** — IF 以 share-token 建立的 WebSocket 连接（F049 AC-55–58）携带任一身份传递头, THEN THE SYSTEM SHALL 拒绝该连接——身份传递只对服务账号密钥有意义，share-token 会话的执行主体恒为分享创建者（F049 决议-6 i）。（§4 决议-11）
- **AC-10** — THE SYSTEM SHALL 自本 Feature 起以 §2.1 / §2.2 的正式语义处理两个身份传递头，**取代** F049 AC-33「任何身份传递头一律 403 并提示尚未启用」；除本 spec 明文的拒绝情形外，携带身份头不再产生「能力尚未启用」类响应。（↔§4.3；F049 AC-33 替代关系）

### 2.2 外部用户标识头（非身份模式）

- **AC-11** — WHEN 模式 S 请求携带任意 `X-Bisheng-End-User`, THE SYSTEM SHALL 使返回结果的**权限范围与不传时完全一致**——权限基准仍为密钥主体，任何权限判定不读取该头；仅会话分区与审计留痕不同。这条同时是「它不是一种身份模式」的验收依据。（↔AC-11 / §4.3.4 语义声明）
- **AC-12** — WHEN 有会话语义的端点（伴生附录 B.1 标 ⧗ 者）在模式 S 下携带 `X-Bisheng-End-User`, THE SYSTEM SHALL 把外部标识作为该会话的分区键写入（**本版只写不读**：不存在任何按外部标识过滤或列举会话的端点）并写入审计留痕；同一密钥、不同外部标识产生的会话互相独立。（↔§4.3.4 / §4.6.3「仍然要写分区键」/ §3.4 表）
- **AC-13** — WHEN 有会话语义的端点在模式 S 下**未**携带 `X-Bisheng-End-User`, THE SYSTEM SHALL 使会话按密钥粒度归属并记录 WARN 级日志；**不阻断、不报错**（前瞻性约束，不是强制项）。（↔§4.3.4 缺省行为；`26014` 已废止不复活）
- **AC-14** — IF 请求同时携带 `X-Bisheng-On-Behalf-Of` 与 `X-Bisheng-End-User`, THEN THE SYSTEM SHALL 返回 400 `26010`，不执行任何业务逻辑（模式 D 下会话已归属被代表用户，外部标识没有语义）。（↔AC-10 / §4.3.4 互斥）
- **AC-15** — THE SYSTEM SHALL 对 `X-Bisheng-End-User` 的取值**不认识、不校验、不解析**——只做形式约束（长度上限、可打印字符，超限 → 400 参数错误），不做任何存在性或语义判断；不以外部标识作为配额 / 限流 / 计量维度（一律按密钥计）；对外 API 文档须**原样写入**伴生 §4.3.4 的语义声明措辞。（↔§4.3.4「语义声明」「配额归属」；§4 决议-6）
- **AC-16** — WHEN 无会话语义的端点在模式 S 下携带 `X-Bisheng-End-User`, THE SYSTEM SHALL 接受该请求、只把外部标识写入审计留痕，不产生任何其它效果、不报错。（§4 决议-6）

### 2.3 `delegate` 权限位与委托配置区

- **AC-17** — THE SYSTEM SHALL 在权限位清单中提供 `delegate` 位（代表平台用户执行）：独立成位、不被任何其它权限位蕴含、也不蕴含任何其它位（持 `delegate` 而无 `knowledge:read` 仍读不了知识库，AC-03）；**只可绑定服务账号主体的密钥**——为托管应用运行期凭据或任何非服务账号主体签发 / 编辑入 `delegate` 一律拒绝；`delegate` 位**不受开放能力层部署开关影响**（委托属开放 API 面本身，标准版同样提供）。F049 AC-14「本期不提供 `delegate` 位」自此作废。（↔§4.2.4；PRD-1 GOV-05 信任机制分界；F049 AC-49 同向）
- **AC-18** — WHEN 管理员在签发或编辑表单勾选 `delegate`, THE SYSTEM SHALL 展开「委托配置」分组：可代表范围**必填**，由 `user`（所列每个用户本人）与 `department`（所列部门及其子树全部成员）两类条目组成、各自可多选、两类可混用；**不提供**「代表任意人 / 全租户」这一档（填根部门即为全员）；分组内须显著风险提示「开启委托意味着这把密钥能以他人身份读取数据，且每次调用都必须声明被代表用户（漏传即 400）；需要以服务账号身份调用请另签密钥」。（↔§4.7.3 委托配置行 / §4.4.4 检查 4 / §7.3 D8）
- **AC-19** — WHILE `delegate` 已勾选且可代表范围为空, THE SYSTEM SHALL 禁用保存并说明原因；THE SYSTEM SHALL 在**接口层同样拒绝**「持 `delegate` 但范围为空」的签发 / 编辑请求（绕过界面直接调接口亦不能保存）。（↔AC-39 / §4.4.4「范围不可为空」）
- **AC-20** — IF 签发或编辑请求中 `delegate` 与「本地开发工具包」三扩展位（`model:invoke` / `identity:read` / `app:manage`）中的任一位同时出现, THEN THE SYSTEM SHALL 拒绝保存（**硬阻断，非软提示**）并给出可读提示「配了委托的密钥不能用于本地开发，请另签一把」；该校验**签发与编辑同一套、双向生效**——已持三扩展位的密钥不能编辑加入 `delegate`，已持 `delegate` 的密钥不能编辑加入任一扩展位——不得靠「先签发后编辑」绕过；界面与接口层同一校验。（↔AC-48 / §4.2.4「签发期硬阻断」/ §4.7.3 编辑；PRD-1 DEV-01 验收 10；**INV-31 互斥校验落点**）
- **AC-21** — WHEN 保存委托范围的 `user` 条目, THE SYSTEM SHALL 校验目标为**本租户、存在、未禁用的自然人**，任一不满足即拒绝保存并提示（含绕过选人框直接调接口的路径——服务账号的 user_id 同样被拒）；WHEN 保存 `department` 条目, THE SYSTEM SHALL 校验目标为本租户存在的部门。这是**早报错**，安全防线是调用期的 AC-25。（↔AC-37 / §4.4.4 / 附录 E.2「自然人校验两个落点」）
- **AC-22** — WHEN 管理员编辑既有密钥的委托配置（勾选 / 取消 `delegate`、增删范围条目）, THE SYSTEM SHALL 使原密钥**立即**按新配置生效、不要求轮换密钥（撤销与失效上界沿用 F049 AC-08 语义）；WHEN 取消 `delegate`, THE SYSTEM SHALL 一并清除该密钥的委托范围（不留「配好了范围但没勾 `delegate`」的死配置，§4 决议-5）；上述变更计入密钥审计事件（F049 AC-12 同一事件流，记变更前后值）。（↔AC-21 类推 / §4.7.3 编辑与撤销 / §7.3 D8）
- **AC-23** — THE SYSTEM SHALL 在「API 密钥」tab 的密钥列表中为每把密钥展示**委托范围摘要**（如「销售部及下级 + 2 人」；不持 `delegate` 显示为无），并可查看完整条目清单。（↔§4.7.3 密钥列表；F049 AC-44 占位）

### 2.4 受限委托五道准入

> 五道检查依次回答**谁可以委托、可以代表谁、这次调用允不允许委托**；全过后执行身份**纯替换**为被代表用户，此后逐资源鉴权与平台内该用户本人操作完全一致。检查 1 见 AC-04，检查 5 见 AC-07 / AC-28。

- **AC-24** — IF 委托目标**不存在、已禁用、与密钥主体不同租户、或不是自然人**（服务账号——含密钥自身所属的服务账号）, THEN THE SYSTEM SHALL 返回 403 `26005`，且**四种情形的响应完全一致**（状态码、错误码、消息、响应体形状与时序特征均无差异），不泄露目标是否存在或属何类型。（↔AC-8 / AC-41；检查 2）
- **AC-25** — THE SYSTEM SHALL 在**每次调用期**判定委托目标是自然人，不得只依赖保存期校验；须覆盖「委托范围配的是部门、而某服务账号恰在该部门子树内」这一用例——该服务账号作为目标同样返回 AC-24 的响应；该判定不依赖「服务账号永远没有部门」这一并非代码保证的假设。（↔AC-41 / §4.4.4「检查 2 为什么要判自然人」/ 附录 E.2 两条自动路径）
- **AC-26** — IF 委托目标是**超级管理员或当前租户的租户管理员**, THEN THE SYSTEM SHALL 返回 403 `26007`（与 `26005` 可区分——目标合法存在只是被禁止）；判定基准 = 平台权限运行时的「系统级无条件放行」谓词（超级管理员 ∪ 当前租户的租户管理员），**不是**旧的 RBAC 管理员角色位；该判定结果须与被代表用户本人登录时权限运行时对其的判定一致，不因身份构造路径不同而漏判；默认（Root）租户不存在租户管理员这一档，该租户下本检查退化为只判超级管理员。部门管理员等有界身份**不在**禁令内。（↔AC-7；检查 3；附录 E.5；Discovery §2.2 风险 ①②）
- **AC-27** — WHEN 委托目标是自然人且非特权主体, THE SYSTEM SHALL 判定其是否落在该密钥的委托范围内：`user` 条目按用户本人匹配；`department` 条目按**调用时**该部门及其子树的成员关系动态展开——成员被移入 / 移出、子部门增删**无需重新保存密钥即时生效**；范围外 → 403 `26004`。IF 密钥持 `delegate` 但当前有效范围为空（保存路径不允许为空，但条目所指部门 / 用户事后被删除可致此）, THEN THE SYSTEM SHALL 对任何目标返回 403 `26004`。（↔AC-9 / §4.4.4 检查 4）
- **AC-28** — IF 模式 D 请求打到允许模式为「仅 S」的端点（AC-07）, THEN THE SYSTEM SHALL 返回 403 `26006`，不执行业务逻辑。（↔检查 5 / 附录 B.1）
- **AC-29** — THE SYSTEM SHALL 使五道准入是**一次性准入判定**：任一检查失败即整体拒绝——不执行任何业务逻辑、不返回任何业务数据、**不降级为模式 S**；全部通过后不再逐资源重复准入，后续逐资源鉴权与平台内该用户本人操作同一条路径、无额外开销；IF 准入所需的任一依赖（用户 / 组织 / 权限运行时 / 缓存）不可用或判定不了, THEN THE SYSTEM SHALL 返回 5xx 并拒绝，**绝不放行**（铁律 3 在准入期的形态；INV-30）。（↔§4.4.4 引言 / §4.4.2 铁律 3 / AC-13）

### 2.5 铁律 2 完整形态与纯替换

- **AC-30** — IF 密钥持 `delegate` 而请求未携带 `X-Bisheng-On-Behalf-Of`, THEN THE SYSTEM SHALL 返回 400 `26016`，**不返回任何业务数据**——既不返回全量、也不返回公开子集、也不静默落到模式 S 按服务账号权限执行；不存在任何"缺身份即降级返回某个子集"的路径。本条补全 F049 AC-35 的 P0 形态为铁律 2 完整形态。（↔AC-38 / §4.4.2 铁律 2「为什么是报错不是降级」/ §7.3）
- **AC-31** — WHILE 模式 D 执行, THE SYSTEM SHALL 使权限基准**整体替换**为被代表用户：服务账号自身在资源授权页的授权（F049 §2.7）**完全不参与判定**——服务账号零授权、被代表用户可读的资源仍可读；反之被代表用户无权、服务账号有权的资源**不可读**（不取交集、不取并集）。（↔§7.2 D2 / §4.7.4「委托生效时本页授权不参与判定」）
- **AC-32** — WHEN 模式 D 下以张三身份调用检索端点（`POST /filelib/retrieve`，经 F052 统一检索门面）, THE SYSTEM SHALL 使返回结果与张三在平台内自行检索的结果**集合相等**——无意外收窄、无超集（不出现张三无权访问的文件的正文片段或文件名）；本条的过滤能力由 F052 交付（F052 AC-25 / AC-43），本 Feature 承接验收；F052 门面未上线前模式 D **不得**在检索端点放行（伴生 §4.4.6「模式 D 的交付前提」）。（↔AC-12 / §4.4.6；Discovery N3）
- **AC-33** — WHEN 模式 D 下调用写路径端点（如 `POST /filelib/` 建知识库、`POST /filelib/add_qa` 写问答对、`POST /workflow/invoke` 触发工作流）, THE SYSTEM SHALL 以被代表用户为执行身份完成权限校验与执行——「以某人名义创建 / 写入」即模式 D，其可为与不可为与该用户本人在平台内操作一致；模式 S 下的资源归属人机制（F049 AC-24）在模式 D 下**不介入**。（↔附录 B.1 `POST /filelib/` 行「以某人名义创建即模式 D」/ `add_qa` 行）
- **AC-34** — THE SYSTEM SHALL 使模式 D 只在 **V2 开放 API 面**上、只对**服务账号密钥**成立：托管应用运行期凭据（F055 签发）不得持 `delegate`（AC-17），其调用携带任一身份传递头一律拒绝；托管运行期的访问用户身份以平台注入为唯一可信来源（INV-32），不复用委托头管道（复用会让检查 3 把管理员挡在所有应用之外）；本地开发三面（MCP / 模型协议 / CLI）不承载委托，其对持 `delegate` 密钥的入口拒绝分别由 F052 AC-28 / F051 AC-26 / F053 AC-09 交付，本 Feature 只提供 `delegate` 位判据与签发侧互斥（AC-20）。**应用工场全册无模式 D 场景。**（↔PRD-1 DEV-02 ④ / DEV-05 ① / GOV-05 信任机制分界；INV-31 / INV-32）

### 2.6 审计双归属与归属优先级

- **AC-35** — THE SYSTEM SHALL 为每一次开放 API 调用记录审计：时间、密钥（掩码 / 标识）、密钥主体（服务账号）、身份模式（S / D）、被代表用户（模式 D）、外部标识（模式 S 且传了 `X-Bisheng-End-User` 时）、端点、来源 IP、结果状态、耗时；**被拒绝的调用同样记录**（含五道准入失败、`26010` / `26016`，记录尝试指向的目标标识与失败原因码，供追责与探测检测）；记录中不出现密钥明文；F049 期仅落结构化日志的开放 API 逐调用记录自本 Feature 起升级为审计记录，在平台既有审计查询面对租户管理员可查（限本租户；平台超管可跨租户）。（↔§4.8.1 R7 / §4.4.3 信任来源 3；F049 AC-12 同口径）
- **AC-36** — WHEN 模式 D 调用被记录, THE SYSTEM SHALL 使审计记录同时含 **actor**（密钥主体 + 密钥标识，回答"哪个系统调的"）与 **subject**（被代表用户，回答"以谁的名义调的"），可据此还原完整调用链；subject 列只在模式 D 填被代表用户，模式 S 为空（外部标识另列，不写入 subject）。本 Feature 定义 subject 列的**口径**（actor = 执行凭据的主体，subject = 以谁的名义），F051 模型调用记录（F051 AC-21）与 F055 运行期能力调用记录（F055 AC-55）各自写入时遵守同一口径。（↔AC-23 / §4.4.5；PRD-1 GOV-04 双归属；§4 决议-7）
- **AC-37** — WHEN 模式 D 下经开放 API 创建资源（知识库、问答对等）, THE SYSTEM SHALL 把资源归属落到**被代表用户**名下——如同其本人在平台内所建、可见可管——**而非**该服务账号的资源归属人（一次调用两者并存以模式 D 为准：委托是显式的、逐次声明的，静态字段不该盖过它）；模式 D 下**不**向服务账号自动回授该资源（回授只是模式 S 下"服务账号不能登录、创建关系落他人"的补偿，模式 D 不存在该缺口，§4 决议-9）。（↔AC-46 / §4.5 定义 6「与模式 D 的关系」）
- **AC-38** — WHEN 模式 D 下产生会话（`POST /workflow/invoke`、WS 两端点、`POST /assistant/chat/completions`；F058 端点上线时同理）, THE SYSTEM SHALL 使会话归属**被代表用户**、按被代表用户分区，**不归服务账号**（与 F049 AC-25 模式 S 相反——定义 6 边界 a「会话不算资源」只约束模式 S，§4 决议-8）；该会话在平台内的可见性与被代表用户本人发起的同类会话一致（工作台会话列表可见与续问的端到端验收随 F058 伴生 AC-32）。（↔§3.4 表「会话分区 · 按被代表用户」/ §4.6.3 身份与会话隔离表）
- **AC-39** — THE SYSTEM SHALL 使模式 D 下的审计 subject、资源归属与会话归属**三者指向同一个被代表用户**（不存在"归属张三、审计记李四"的分叉）；被代表用户事后被禁用 / 删除不改写既有审计与归属记录。（↔§4.4.4「委托生效后的执行身份、资源归属与审计 subject 全都是那一个具体的人」）

## 3. 边界情况

> 只写期望的对外行为；实现层的落点、缓存与数据访问细节见 design.md §5。

- **`department` 范围是"圈候选人的方式"，不是"以部门身份执行"**：被代表对象永远是单个自然人；范围条目在**调用期**动态展开为当时的成员集合，组织架构变动即时反映到准入结果（AC-27），管理员不必回头重存密钥。填根部门 = 全员，这是场景二的常规配法（伴生 §7.3）。
- **服务账号可能被组织侧自动兜底进「临时访客」部门**（伴生附录 E.2 两条自动路径；该部门挂在根部门之下）：本 Feature **不修改**这些真人场景的兜底逻辑，安全不变量靠调用期的自然人判定（AC-25）守住，**不依赖**「服务账号永远没有部门」这一并非代码保证的假设。保存期校验（AC-21）只是早报错，够不到 `department` 条目在调用期才展开的成员。
- **检查 3 的判定基准必须与权限运行时一致**：平台内身份构造存在多条路径且对「是否超级管理员」的计算不对称（Discovery §2.2 / baseline-recheck §二）；本 Feature 要求被代表用户身份的构造与检查 3 的判定都以权限运行时的「系统级放行」谓词为准（AC-26）——判漏会让一把窄权限密钥换到管理员的无界权限，是全 spec 最重的单点。默认租户下没有租户管理员这一档，测试用例须按租户分别设计（伴生附录 E.5）。
- **`26005` 的无差异不只是同一个码**：不存在 / 已禁用 / 跨租户 / 非自然人四种情形的响应体形状、消息与可观测时序特征都不得成为探测哪些 user_id 是服务账号或属于哪个租户的旁路（AC-24）；而 `26007` 是**刻意可区分**的（目标合法只是被禁止），两者不能混同。
- **委托 = 「提权有上界」而非「恒为降权」**（伴生 §7.2 代价）：模式 D 下调用方最多获得委托范围内某个真实自然人的真实权限，永远够不到无条件放行；服务账号自身零授权也不妨碍模式 D 读全员可读的内容（AC-31）——这是设计意图，授权页的显著提示（AC-45）就是为防它被误读成"本页授权是全局上限"。对外措辞按伴生附录 F 红线。
- **模式 D 与资源归属人两套归属机制并存时以模式 D 为准**（AC-37）：定义 6 是模式 S 下"服务账号不能登录、创建关系落他人"的补偿；模式 D 的被代表用户本人就是自然人，创建关系直接落他，也不再回授服务账号——否则一把委托密钥就能给服务账号攒出一批跨越全员的资源写权限，正是 PRD-1 DEV-02 ④ 指出的爆炸半径放大。
- **模式 D 会话归被代表用户，模式 S 会话归服务账号**（AC-38 vs F049 AC-25）：定义 6 边界 a「会话不算资源」只约束模式 S（防止资源归属人在工作台看到全部外部访客对话）；模式 D 下会话回到员工工作台正是场景二的完整形态（伴生 §4.6.3），两者不矛盾。
- **外部标识分区键"只写不读"**：本版没有任何端点按 `X-Bisheng-End-User` 过滤或列举会话（会话列表 / 历史查询已于 2026-08-16 移出范围），串档的成立条件不齐；写分区键是前瞻性设计，让存量会话从一开始带上终端用户维度（AC-12）。F049 决议-6 i 已知代价——share-token 会话落在分享创建者会话列表——不由本 Feature 修复，本 Feature 只保证分区键机制存在（§4 决议-11）。
- **两个身份头在 WebSocket 上经握手请求头传递**（AC-08），与密钥一致、不走查询参数；握手期完成准入后，连接期内身份不可变。share-token 通道不承载身份头（AC-09）。
- **审计双归属对既有审计流的影响**：本 Feature 把 F049 期的结构化调用日志升级为审计记录并引入 subject 列的**口径**（AC-35 / AC-36）；F049 密钥事件、授权页事件、share-token 建连事件维持原形态；F051 / F055 各自的调用记录复用口径而非合并成同一张记录（是否同表属 design）。审计量级随开放 API 调用量线性增长，承压方案见 design。
- **裸 `user_id` 移除是破坏性变更**（AC-40–43）：随发布说明交付，不设过渡期；F049 + F050 必须合并发版——否则 F049 单独上线时开放 API 仍存在一条经参数指定执行身份的残余路径（F049 AC-35 已知残余）。
- **F052 门面是模式 D 检索的交付前提**（AC-32）：门面未就绪时模式 D 对检索端点返回被代表用户可见集的真超集，违背「不多不少」；因此批次 A 顺序 F052 早于 F050，模式 D 在检索端点的放行以门面上线为前提。
- **准入检查与凭据校验同取 fail-closed**（AC-29）：任何依赖不可用即拒绝，与 F049 §3「凭据校验取 fail-closed」同向、与平台会话续期的刻意宽松取向相反，这一差异是刻意的。
- **不存在「委托能力尚未启用」的中间形态**：F049 期任何身份头一律 403，本 Feature 上线后两个头有正式语义（AC-10）；不设特性开关让委托"存在但未启用"——那会复活 D8 否决的「勾了但没生效」死配置形状。

## 4. 待澄清决议

> ★ 决议 1–12 于 2026-08-17 由用户授权「全部按建议拍板」定案并在此留痕（全自动模式）；如后续伴生 PRD 修订推翻，以各条末尾「状态」为准，原文保留供追溯。

- **[决议-1] `X-Bisheng-On-Behalf-Of` 头值形态 = 单个平台用户 ID；本版不接受用户名。**（AC-06）
  伴生 §4.4.4 引言写「用户 ID 或用户名」、§3.2 写「换成用户名亦可」。建议只接受用户 ID：① 用户名可改名、跨租户可重名，按名解析会引入一层"名 → 人"的歧义与存在性探测面（与 `26005` 无差异要求相悖）；② 伴生 §4.9 三步指引本就是「原先在参数里传 `user_id` 的调用改为请求头」，存量集成手里已有 user_id；③ 场景二的前提是「用户 ID 全域一致」，映射本就由调用方负责。备选 = 同时接受用户名，代价见 ①。**已定：只接受用户 ID**；建议回写伴生 PRD §4.4.4 / §3.2 措辞（本 spec 不动 PRD）。

- **[决议-2] 委托范围校验的落点两处：保存期早报错 + 调用期安全防线，两处都做、语义分明。**（AC-21 / AC-25）
  伴生附录 E.2 已定两处；本 spec 落 AC 时明确：保存期失败 = 拒绝保存并提示（含绕过界面直接调接口），调用期失败 = `26005` 无差异响应；保存期校验的存在**不得**被当作调用期可省略的理由（`department` 条目在调用期才展开）。**已定。**

- **[决议-3] `26005` 四情形无差异 + `26007` 刻意可区分。**（AC-24 / AC-26）
  伴生附录 C 已定；本 spec 补「响应体形状与时序特征亦无差异」——只同一个码不够挡探测。**已定。**

- **[决议-4] 错误码只作引用；`26004` 语义自本 Feature 起收窄为伴生附录 C 定义。**（AC-48）
  F049 期借 `26004` 表达「身份传递能力尚未启用」（F049 design 决议）；本 Feature 上线后该语义消失，`26004` = 未授予委托 / 不在范围。定义与归属在 design（模块号 260，落码时按宪法 C5 回写登记表）。**已定。**

- **[决议-5] 取消 `delegate` 时委托范围一并清除；不允许「范围非空但未勾 `delegate`」的持久化状态。**（AC-22）
  理由 = 伴生 §7.3 否决「委托模式」枚举的同一理由：不留任何一种"开了但没配 / 配了但没开"的死配置。备选 = 保留范围以便重新勾选时复用——代价是列表与授权页提示要多解释一种"范围存在但不生效"的状态。**已定：清除。**

- **[决议-6] `X-Bisheng-End-User` 只做形式约束、不做语义校验；无会话语义端点携带它 = 接受并只留审计。**（AC-15 / AC-16）
  伴生 §4.3.4 定「不认识、不校验、不解析」；本 spec 补两条：① 请求头必有形式上限（长度、可打印字符），超限 400，这不是语义校验；② 伴生只写了有会话语义端点的行为，无会话语义端点收到它不应报错（对齐 Dify / Coze 把它当普通参数的口径），只留审计。**已定。**

- **[决议-7] subject 列引入方式 = 本 Feature 定义口径（actor = 执行凭据的主体 / subject = 以谁的名义），F051 / F055 各自的记录遵守同一口径。**（AC-36）
  release-contract 变更历史与 Discovery §2.7 已定「F050 引入 subject 列，F055 运行期复用」；F051 spec AC-21 / F055 spec AC-55 已按此写。本 spec 只立口径（What），是否同一张表 / 同一字段名属 design；模式 S 的 subject 为空、外部标识另列，避免把"不认识的字符串"混进"经准入的自然人"一列。**已定。**

- **[决议-8] 模式 D 会话归属被代表用户；定义 6 边界 a 只约束模式 S。**（AC-38）
  伴生 §3.4 表与 §4.6.3 表明文；边界 a 的目的（防资源归属人看到全部外部访客对话）在模式 D 不存在——被代表用户看到自己名义下的会话正是场景二的诉求。工作台可见与续问的端到端验收随 F058 伴生 AC-32；本 Feature 保证既有 ⧗ 端点在模式 D 下会话归属正确。**已定。**

- **[决议-9] 模式 D 下创建的资源不回授服务账号。**（AC-37）
  伴生定义 6 边界 b 的回授只写在模式 S 语境；模式 D 下执行身份是自然人、次日续写仍以模式 D 进行，无回授必要；回授反而让委托密钥为服务账号攒出跨全员的资源写权限（PRD-1 DEV-02 ④ 指出的爆炸半径放大）。备选 = 同样回授，否决。**已定：不回授**；建议回写伴生 PRD 定义 6「与模式 D 的关系」补一句。

- **[决议-10] `delegate` 位只可绑定服务账号主体、不受开放能力层开关影响。**（AC-17）
  委托属开放 API 面本身（伴生 R2 / R3 是标准版能力）；托管应用运行期凭据不得持 `delegate`（PRD-1 GOV-05 信任分界 + INV-31「全册无模式 D 场景」）——底座校验点由 F049 底座提供、规则由本 Feature 定义。**已定。**

- **[决议-11] share-token 通道不承载身份头（携带即拒）；F049 已知代价「share-token 会话落在分享创建者会话列表」不由本 Feature 修复。**（AC-09；§3）
  身份传递以服务账号密钥 + `delegate` 为唯一信任基础，share-token 会话执行主体恒为分享创建者（F049 决议-6 i）；F049 design 把 guest 会话摘出列入其后续项并等待本 Feature 的分区键机制——本 Feature 只保证分区键机制存在，摘出动作归 F049 / F058 后续，不在本 spec 登记 AC。**已定。**

- **[决议-12] 端点允许模式落地方式 = 与 F049 同一条完整性校验路径（不存在未声明允许模式的可达端点）；F058 端点上线时按附录 B.1 自行声明。**（AC-07 / AC-28）
  F049 已为每个端点建立「权限位声明 + 完整性兜底」并预留允许模式的扩展位置（F049 design 决策 3）；本 spec 只要求「无未声明允许模式的可达端点」这一可验收结果，声明形态属 design。**已定。**
