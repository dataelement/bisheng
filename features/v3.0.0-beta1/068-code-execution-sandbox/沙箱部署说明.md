# 沙箱部署说明

隔离环境把模型 / 搭建者写的 Python 从 backend、Celery、Linsight 进程里挪到独立的 `bisheng-sandbox` 副本上执行。平台侧**不挂 docker.sock、不调 Kubernetes API**，也不按主机名扫描副本。副本就是配置里的服务地址列表，再走 HTTP 租约。

架构评审材料见同目录 [沙箱架构设计说明书.md](./沙箱架构设计说明书.md)。页面上怎么选执行方式、任务模式怎么交文件，见 [沙箱使用说明.md](./沙箱使用说明.md)。本文只写**怎么配、怎么开、怎么验收**。

---

## 1. 组件与调用关系

| 组件 | 镜像 | 作用 |
|------|------|------|
| `code-runner-*` | `bisheng-sandbox` | 加固容器；提供 `/health`、`/v1/sessions`、copy-in/exec/copy-out |
| backend | `bisheng-backend` | 日常会话、助手里的代码解释器；工作流编辑器「运行一次」 |
| Celery worker | 同上 | 工作流运行时的代码节点，以及 Agent 节点、工具节点里的代码解释器 |
| Linsight | 同上（独立进程；Compose 里在 worker 容器内，Helm 里是单独 Deployment，见 2.3） | 任务模式代码解释器（`keep_session` 粘滞同一副本） |


## 2. 部署

### 2.1 Docker Compose

仓库 `docker/docker-compose.yml` 预声明具名副本（默认 `code-runner-1`、`code-runner-2`），挂在 `sandbox_net` 上。这张网默认可以访问外网（`internal: false`），不映射宿主机端口。`backend` 和 worker 都必须同时加入 `default` 和 `sandbox_net`，才能解析 `code-runner-1`，同时仍能访问 MySQL / Redis。已经建好的 `sandbox_net` 如果当时是 internal，改这份文件不会改那张网，需要删网重建后出站才会通。

backend、backend_worker、frontend 和沙箱要用开发分支同一次构建出的镜像：

| 用途 | 镜像 |
|------|------|
| backend、backend_worker | `cr.dataelem.com/dataelement/bisheng-backend:feat_3.0.0` |
| frontend | `cr.dataelem.com/dataelement/bisheng-frontend:feat_3.0.0` |
| `code-runner-*` | `cr.dataelem.com/dataelement/bisheng-sandbox:feat_3.0.0` |

`feat_3.0.0` 是当前的内部构建，会被后续构建覆盖，不是发布版。沙箱进入正式发布 tag 之后，本文的镜像改回版本号，不要把 `feat_3.0.0` 当长期版本钉死。

token 写进 `docker/.env`，不要只在当前终端 `export`。换一个终端再执行 `docker compose up` 时，export 的值带不过去，runner 和 backend 会一起回退到默认的 `bisheng-sandbox-local`：照样能连上、不报错，生产 token 就这样丢了。

```bash
# docker/.env —— 与 runner 共用；生产务必改掉默认值
SANDBOX_TOKEN=替换成足够长的随机串
```

```bash
cd docker
docker compose up -d code-runner-1 code-runner-2 backend backend_worker frontend
```

Compose 把两台 runner 写进 `BS_SANDBOX_CONF__ENDPOINTS`：`http://code-runner-1:8080` 和 `http://code-runner-2:8080`。再加一台就要把新地址追加进 backend 和 backend_worker 的这份列表。

日常会话、助手和编辑器「运行一次」都在 backend 进程里执行，所以 `backend` 也要带同一份 `BS_SANDBOX_CONF__TOKEN`。任务模式的灵思跑在 `backend_worker` 容器里（见 2.3），不需要额外接网络。

扩容：复制一份 `code-runner-N` 服务（具名，不要用 `deploy.replicas`），否则 `keep_session` 粘不住同一台。

### 2.2 Helm（两张独立 chart）

中间件（MySQL / Redis / MinIO / ES / Milvus / OpenFGA）**不在** chart 里，先指到已有地址。


```bash
export SANDBOX_TOKEN='替换成足够长的随机串'
export REGISTRY=cr.dataelem.com/dataelement
export TAG=feat_3.0.0

# 1. 沙箱：Service 名保持 code-runner（默认 fullnameOverride）
helm upgrade --install sandbox docker/helm/bisheng-sandbox \
  --namespace bisheng-sandbox --create-namespace \
  --set token.value="$SANDBOX_TOKEN" \
  --set image.repository="$REGISTRY/bisheng-sandbox" \
  --set image.tag="$TAG"

# 2. 平台（token 必须与上一张相同）
helm upgrade --install bisheng docker/helm/bisheng \
  --namespace bisheng --create-namespace \
  --set sandbox.token="$SANDBOX_TOKEN" \
  --set sandbox.endpoints='{http://code-runner-0.code-runner.bisheng-sandbox.svc.cluster.local:8080,http://code-runner-1.code-runner.bisheng-sandbox.svc.cluster.local:8080}' \
  --set backend.image.repository="$REGISTRY/bisheng-backend" \
  --set backend.image.tag="$TAG" \
  --set worker.image.repository="$REGISTRY/bisheng-backend" \
  --set worker.image.tag="$TAG" \
  --set linsight.image.repository="$REGISTRY/bisheng-backend" \
  --set linsight.image.tag="$TAG" \
  --set frontend.image.repository="$REGISTRY/bisheng-frontend" \
  --set frontend.image.tag="$TAG"
```

同一个 tag 重新构建后再升级，删 Pod 换不上新层，见 4.2。

K8s StatefulSet 序号从 **0** 起，平台侧把每台 Pod 的地址列出来：

```yaml
sandbox:
  enabled: true
  endpoints:
    - http://code-runner-0.code-runner.bisheng-sandbox.svc.cluster.local:8080
    - http://code-runner-1.code-runner.bisheng-sandbox.svc.cluster.local:8080
```

执行方式只看内置工具的 `extra.type`，见 3.3。

沙箱 chart 的 NetworkPolicy 默认开启，入站放行命名空间 `bisheng` 里标签 `app.kubernetes.io/component` 为 `worker`、`backend` 或 `linsight` 的 Pod。编辑器「运行一次」、Celery 上的执行和任务模式因此都能打到 runner。旧版本 chart 升级时，如果用 `--reuse-values` 沿用了旧的 `allowFrom`，不会带上新增的两条，要显式重设，见 2.3。

**不要**给 runner 只挂一个 ClusterIP VIP。`keep_session` 粘的是主机名（`http://code-runner-0.code-runner…`），经 kube-proxy 会把下一跳打到别的 Pod，工作目录丢失。

扩容时先加沙箱副本，再把新 Pod 的地址补进平台 chart 的 `sandbox.endpoints` 并升级平台。没有后台 DNS 扫描。

```bash
helm upgrade sandbox docker/helm/bisheng-sandbox --reuse-values --set replicaCount=4
```

Helm 安装细节另见 [docker/helm/README.md](../../../docker/helm/README.md)。

### 2.3 Linsight 进程

任务模式由 Linsight 进程执行。Compose 和 Helm 里它的来源不同，两边都不要再手动多起一份：多份进程会消费同一个 Redis 队列。

两份入口脚本在这一点上不一致，部署前要知道自己用的是哪份：

| 部署 | 实际使用的入口脚本 | worker 模式是否后台启动灵思 |
|------|--------------------|------------------------------|
| Compose | 宿主机挂载的 `docker/bisheng/entrypoint.sh`（只读挂到 `/app/entrypoint.sh`） | 是（`start_linsight &`） |
| Helm | 镜像里烘焙的 `src/backend/entrypoint.sh` | 否（该行被注释） |

**Compose。** `backend_worker` 的命令是 `entrypoint.sh worker`，在后台执行 `start_linsight`（`python bisheng/linsight/worker.py --worker_num 1 --max_concurrency 5`），和 Celery 在同一个容器里。不要再执行 `entrypoint.sh linsight`。灵思因此已经在 `sandbox_net` 上，带着同一份 token。

**Helm。** worker Pod 不跑灵思。chart 自带 `bisheng-linsight` Deployment，命令是 `entrypoint.sh linsight`，装好即有，不要再进 Pod 手动起一份。它的标签是 `component: linsight`，沙箱 chart 的 NetworkPolicy 默认已放行它，新装的环境不用再改。

升级老环境要留意：`helm upgrade --reuse-values` 会沿用旧 release 里保存的 `networkPolicy.allowFrom`，只有 `worker`，新增的 `backend` 和 `linsight` 不会生效，任务模式和编辑器「运行一次」仍然连不上 runner。升级时不要带 `--reuse-values`，或者显式传入包含这三项的 `allowFrom`。自己改过 `allowFrom`（例如换了命名空间）的环境，要把 `linsight` 一并补进去。

多套平台共用一个 Redis 时，把任务队列和会话库错开（例如平台 A 用 `/5` + Celery `/4`，平台 B 用 `/1`），否则别人的 Linsight 会抢走任务。

## 3. 配置项

配置分两边：**平台访问沙箱**（`BS_SANDBOX_CONF__*`）和 **runner 自身**（`SANDBOX_*`）。两边 token 必须一致。

`config.yaml` 可以写 `sandbox_conf:` 块；**更老的镜像遇到未知顶层键会拒启**，所以发行文件里默认整段注释掉，靠环境变量覆盖。

### 3.1 平台侧 `BS_SANDBOX_CONF__*`

对应 `SandboxConf`，环境变量是双下划线 + 字段大写。表里的默认值就是要填进环境变量的字面量。字节数只接受十进制整数：`int(raw)` 不认 `50MiB` 这种写法，照填会在启动时报错。50 MiB = `52428800`。

| 环境变量 | 含义 | Compose 默认 | Helm 默认 |
|----------|------|--------------|-----------|
| `BS_SANDBOX_CONF__TOKEN` | 调用 runner 的 Bearer，与 `SANDBOX_TOKEN` 相同 | `bisheng-sandbox-local` | values `sandbox.token` |
| `BS_SANDBOX_CONF__ENDPOINTS` | 沙箱服务地址，JSON 数组，一台副本一个。空列表表示没有副本 | `code-runner-1` 与 `code-runner-2` | values `sandbox.endpoints` 里的两台 Pod |
| `BS_SANDBOX_CONF__POOL_ACQUIRE_TIMEOUT_S` | 等空闲副本的最长时间 | `30` | `30` |
| `BS_SANDBOX_CONF__DEFAULT_TIMEOUT_S` | 单次 exec 默认超时 | `600` | `600` |
| `BS_SANDBOX_CONF__MAX_COPY_IN_BYTES` | 超过则跳过该文件，不打进 tar。容量 50 MiB | `52428800` | `52428800` |

地址和 token 要配在真正发起调用的进程上，或改在代码执行器弹窗里（构建 → 工具 → 内置工具 → 代码执行器 → 沙箱运行）。弹窗里的非空地址、非空令牌优先于环境变量和 yaml；留空回退到这里的部署值，清空已保存的页面值即恢复。配了还不够，该进程还得在网络上够得到这些地址（见 2.1、2.2 的默认范围）。页面改不了网络可达性。

保存后 60 秒内，新的执行使用页面值：日常会话的下一条消息、已经打开的助手的下一轮对话（不用断开重连）、工作流的下一次运行。写缓存失败时，旧缓存仍在自身 60 秒 TTL 内有效。正在跑的任务本轮仍用旧副本。弹窗里的测试连接只代表 backend。缓存 key `config:sandbox_endpoint` 的 db 以 `redis_url` 为准，发行配置是 `/1`。

- **Celery worker**：工作流运行（代码节点、Agent 节点、工具节点）。Compose 和 Helm 默认都覆盖这条
- **backend**：日常会话、助手、编辑器「运行一次」。Compose 已双挂 `sandbox_net` 并带 token；Helm 网络策略已放行 `component: backend`
- **Linsight**：任务模式。Compose 跑在 `backend_worker` 容器里，已在 `sandbox_net` 上。Helm 是独立 Deployment，网络策略已放行 `component: linsight`

### 3.2 Runner 侧 `SANDBOX_*`

| 环境变量 | 含义 | 默认 |
|----------|------|------|
| `SANDBOX_TOKEN` | 鉴权，须与平台 token 相同 | 空则进程拒绝启动 |
| `SANDBOX_MAX_SESSIONS` | 每副本并发会话数 | `50` |
| `SANDBOX_LEASE_TTL_S` | 空闲租约回收（秒） | `900` |
| `SANDBOX_ENABLE_UID_ISOLATION` | 会话 uid 隔离 | `true` |
| `SANDBOX_SESSIONS_ROOT` | 会话工作目录 | `/tmp/sessions` |
| `SANDBOX_MAX_COPY_IN_BYTES` | copy-in 单文件上限，容量 50 MiB。填十进制字节数，不要写 `50MiB` | `52428800` |
| `SANDBOX_PORT` | 监听端口 | `8080` |
| `SANDBOX_LOG_LEVEL` | 日志级别 | `INFO` |

每副本默认 50 个并发会话。会话数大于 1 时必须开着 uid 隔离，否则 runner 拒绝启动。还要更多并发时再加副本。


### 3.3 本机执行的 uid 隔离（`local` 时）

还在用 `local`（包括代码节点关掉沙箱时）的部署，可以打开本机隔离：每次执行都在一个私有目录里、以 `30000`–`39999` 中的一个临时 uid 运行，环境变量只保留白名单，并加上内存、进程数、CPU 时间、文件大小上限。设计见 [第一步方案](./LocalExecutor安全优化方案-第一步-uid隔离.md)。

| 环境变量 | 默认 | 说明 |
|----------|------|------|
| `BS_SANDBOX_CONF__LOCAL_ISOLATION` | `uid` | 未设置就是 `uid`。只有空串或 `off` 表示关闭，其他值都按 `uid` |
| `BS_SANDBOX_CONF__LOCAL_RUN_ROOT` | `/tmp/bisheng-local-run` | 私有运行目录的父目录 |

代码里的默认值是 `uid`。环境变量和配置文件都没写这项时，本机执行走 uid 隔离。仓库自带的 `docker/docker-compose.yml` 在 `backend`、`backend_worker` 上仍写 `${LOCAL_ISOLATION:-uid}`，要关闭就在 `docker/.env` 里写 `LOCAL_ISOLATION=off`。Helm 不写这项时同样是 `uid`；要关闭就在 `backend`、`worker`、`linsight` 的 `extraEnv` 里设 `BS_SANDBOX_CONF__LOCAL_ISOLATION=off`。

其余限额字段（`LOCAL_RLIMIT_*`、`LOCAL_DISK_LIMIT_BYTES`、`LOCAL_COPY_IN_*`）见方案的"配置字段"一节，一般不用改。

开启前提：Linux，进程是 root，镜像里有 `prlimit`，容器保留 Docker 默认能力集（含 `SETUID`、`SETGID`、`CHOWN`、`DAC_OVERRIDE`、`KILL`）。不满足时**不会退回不隔离**，两条路径的表现不同：

- 代码执行器（任务模式、日常会话、助手、工作流 Agent 节点和工具节点）返回一段英文提示（`The local code execution environment is not ready, so nothing was executed. Do not retry; tell the user that code execution is currently unavailable.`），模型据此告诉用户暂时不能执行代码。
- 代码节点不经过这段提示，直接抛出具体原因（例如 `not running as root (euid=1000)`），节点按失败处理，异常原文就是失败信息。

两条路径的服务端日志里都有一条 `local isolation unavailable: …` 的 error，排查看这条。

改权限发生在该进程第一次以 `uid` 模式执行代码时，不是容器启动的瞬间。预检通过后会改两处：

- `/app/bisheng`（后端代码目录）和 `/app/data`（Compose 对应宿主机 `data/bisheng`）顶层改为 `0700`。依赖以非 root 身份读写 `data/bisheng` 的运维脚本要调整。
- 宿主机上挂进来的 `config.yaml` 建议设为 `0600`、属主 root。它在 `/app/bisheng` 下面，已经被上一条挡住，这是第二道保险。

关闭（`off`）时完全保持原来的行为，首次执行打一条 WARNING。

## 4. 验收与排障

### 4.1 连通

```bash
# Compose：backend（日常会话、助手、编辑器「运行一次」）和 backend_worker（工作流运行 / 灵思）都要通
for c in bisheng-backend bisheng-backend-worker; do
  docker exec $c getent hosts code-runner-1
  docker exec $c curl -sS -m 5 http://code-runner-1:8080/health
done

# Helm：worker、backend、linsight 三个 Deployment 都要通
kubectl -n bisheng-sandbox get sts,svc,po
for d in bisheng-worker bisheng-backend bisheng-linsight; do
  kubectl -n bisheng exec deploy/$d -- python -c \
    "import urllib.request; print(urllib.request.urlopen(
      'http://code-runner-0.code-runner.bisheng-sandbox.svc.cluster.local:8080/health',
      timeout=5).read())"
done
```

`bisheng-linsight` 超时而另外两个正常，通常是沙箱 chart 里的 `allowFrom` 还是旧值，见 2.3。

健康检查应返回 `{"status":"ok"}`。真正执行时 runner 日志会出现：

```text
POST /v1/sessions
PUT  /v1/sessions/{id}/files     # copy-in
POST /v1/sessions/{id}/exec
GET  /v1/sessions/{id}/files     # copy-out（仅 exitcode=0）
DELETE /v1/sessions/{id}
```

只有 `/health`、没有 `/exec`：代码解释器仍是 `local`，或请求打在了另一套平台上。页面上改执行方式见使用说明。

### 4.2 更新镜像

用新 tag，再改 values 里的 `image.tag` 后 `helm upgrade`。两张 chart 都要改：平台 chart 的 `backend`、`worker`、`linsight`、`frontend` 各有一个 `image.tag`，沙箱 chart 另有一个。chart 默认 `imagePullPolicy: IfNotPresent`。节点上已经有这个 tag 时，删掉 Pod 只会用本地旧镜像再起，不会去仓库拉新层。Compose 同 2.1：backend、backend_worker、frontend、`code-runner-1` 四处 `image` 一起换，只改 `SANDBOX_IMAGE_TAG` 换不了仓库，也换不到 backend 和 frontend。同一个 tag 重新构建后，要先 `docker compose pull` 再 `up -d`，否则仍用本地旧镜像。

在宿主机上 `docker pull` 也不够：Kubernetes 用的是容器运行时自己的镜像库（常见是 containerd），和 Docker 的镜像库不是同一份。

chart 里前端的更新策略无条件写死为 `Recreate`。`hostPort` 只在 `frontend.service.clientHostPort` 非空时才挂上，默认为空，不会抢端口；写死 `Recreate` 是为了以后打开 `clientHostPort` 时不用再改策略。配了 `clientHostPort` 后更新仍卡住时，删掉停在 Terminating 的旧 Pod，再等新的 Ready。

### 4.3 部署侧常见现象

| 现象 | 原因 | 处理 |
|------|------|------|
| 任务模式不打沙箱 | Compose：`backend_worker` 没起来（灵思在它里面），或挂载的入口脚本不是仓库里的 `docker/bisheng/entrypoint.sh`。Helm：没有 `bisheng-linsight` Deployment。两边都可能是两套平台抢了同一个 Redis | 看 2.3，不要再手动起一份；错开 Redis db |
| 勾了代码执行器仍走本机 | `t_gpts_tools_type.extra.type` 为 `local` | 页面改成「沙箱运行」，或把 `extra.type` 改为 `container` |
| 代码节点直接失败，提示 Code node is disabled | 系统配置 `workflow.code_node_enabled` 不是字面量 `true` | 在系统配置里打开。执行方式由 `extra.type` 决定，见 3.3 |
| 日常会话、助手或编辑器「运行一次」选了沙箱仍失败 | backend 没带与 runner 相同的 token，或没同时挂上 `default` 和 `sandbox_net`；Helm 上 `component: backend` 被移出 `allowFrom` | 与 worker 对齐 token，并确认 backend 在沙箱网络的放行列表里 |
| 任务模式或编辑器「运行一次」选了沙箱仍失败（Helm） | 沙箱 release 里的 `allowFrom` 是旧值（升级时用了 `--reuse-values`，或自定义过），缺 `linsight` / `backend`，连 runner 超时 | 重新 `helm upgrade` 沙箱 chart 且不带 `--reuse-values`，或把缺的 component 补进 `allowFrom` |
| 下载 403 | 预签名 Host 与 nginx 反代 Host 不一致 | nginx 反代 MinIO 时 `Host` 设为 `sharepoint` |
| 选了沙箱但没有可用副本 | `BS_SANDBOX_CONF__ENDPOINTS` 为空，或列表里的地址连不上 | 把每台 runner 的地址写进列表；Compose 检查 `sandbox_net`，Helm 检查 Pod DNS 与 `allowFrom` |

文件写错路径、交付物被丢掉，见 [沙箱使用说明](./沙箱使用说明.md)「产物对不上时」。任务结束后也可以直接查库：

```sql
SELECT id, status,
       JSON_EXTRACT(output_result, '$.final_files'),
       JSON_EXTRACT(output_result, '$.invalid_deliverables'),
       JSON_EXTRACT(output_result, '$.phantom_deliverables')
FROM linsight_session_version
WHERE id = '<session_version_id>';
```

`final_files` 为空且 `invalid_deliverables` 有记录：文件写过但格式不对（例如文本冒充 xlsx）。  
`phantom_deliverables` 有记录：答案里报了文件名，工作区里没有对应文件。

## 5. 安全边界

- 口径：挡住误操作和机会主义访问，**不承诺**抗定向内核 0day。
- runner：只读根文件系统、能力全裁（再加回 SETUID/SETGID/CHOWN/DAC_OVERRIDE 做会话 uid）、cgroup 限额。默认可以访问外网；runner 仍不挂中间件网络、不映射宿主机端口。
- runner 无中间件凭据、不挂 docker.sock。
- 本地执行器的 `local_isolation` 在代码里默认是 `uid`：子进程用临时 uid，读不到配置和进程环境变量，但网络仍不隔离。设为 `off` 时与平台同用户、同网络，可以读到工作目录之外的路径。见 3.3。生产应使用 `container`。
