# 一、摘要

## 1.1 中心结论

**BiSheng 开放 API 必须立即关闭匿名通道，并建立三层机制：凡调用必持密钥、密钥必属服务账号、身份必显式声明。**

三层各解决一个问题，按优先级展开：

1. **凡调用必持密钥 —— 解决"谁在调用"。** 任何开放 API 调用必须携带平台签发的密钥，无密钥即 401。同时移除"配一个固定用户当兜底身份"的现行做法，并补上被遗漏的上线状态校验与 WebSocket 鉴权。**这是 P0 的全部目标，可独立交付。**
2. **密钥必属服务账号 —— 解决"能做什么"。** 密钥只签发给服务账号：一种不可登录的一等主体，权限独立于任何自然人。这样集成的权限边界可以按最小必要授予，也不会因某员工离职而中断 [S6]。
3. **身份必显式声明 —— 解决"以谁的名义"。** 调用方必须显式声明三种身份模式之一：以服务账号身份执行、代表某平台用户执行、还是服务外部用户体系。三者的权限基准、审计归属、数据隔离规则各不相同，不能靠一个可选参数的有无来区分。

## 1.2 背景（情境—冲突—疑问—解答）

**情境**　BiSheng 是私有化部署的企业级大模型应用开发平台，客户在其上构建工作流、知识库、智能助手。平台对外提供一组开放 API（路径前缀 `/api/v2`），供客户的自建业务系统调用——例如在自家 OA 里嵌入问答入口，或让 CRM 系统触发一条工作流。

**冲突**　这组开放 API 目前**完全没有鉴权**：任何能访问到服务端口的人都可以直接调用。更关键的是，接口已经支持在请求中指定"以哪个用户的身份执行"，而这个指定同样不需要任何凭据。两者叠加，构成一条可被任意匿名调用方利用的越权通道（§2.2）。

**疑问**　应当建立怎样的鉴权机制？调用方要代表最终用户操作时，"在请求里指定一个用户 ID"这种做法是否可接受？如果调用方服务的是与平台完全无关的外部用户，权限又该如何处理？

**解答**　即 §1.1 的三层机制。三个疑问的具体结论见下表。

## 1.3 三个核心问题的结论

| 问题 | 结论 | 详见 |
|---|---|---|
| **Q1** 开放 API 是否必须鉴权？ | 必须。且不能依赖"部署在内网"作为替代——私有化环境同样存在横向移动与内部越权，等保测评中无鉴权的内部接口是明确失分项 | §2.3 |
| **Q2** 调用方在请求里指定 user_id 代表某用户操作，安全吗？ | **拆成两问，答案相反**：它**永远无法证明**是该用户本人在操作；但它**可以合法地**让调用方按该用户的权限边界执行并归属结果——前提是护栏齐备。行业中 Zendesk [S7]、Kubernetes [S8]、FastGPT [S3] 均采用此模式 | §4.4.2、附录 A.1 |
| **Q3** 调用方服务的是外部用户体系时，是否应关闭权限过滤？ | **不应关闭，应更换过滤基准**。过滤照做，基准从"最终用户"换成"服务账号"。直接关闭过滤会产生无边界数据出口 | §3.3、§4.3.4 |

## 1.4 交付范围与优先级

| 阶段 | 目标 | 核心交付 | 估算 |
|---|---|---|---|
| **P0** | 关闭匿名通道 | 服务账号主体 + 服务账号密钥 + 全端点接入鉴权 + 密钥自助管理 + 存量兼容开关 | 约 11~12 人天 |
| **P1** | 身份传递 | 三种身份模式 + 受限委托六道准入 + 审计双归属 + 裸 user_id 参数收口 | 约 12~14 人天 |
| **P2** | 企业级运营 | 限流配额、IP 白名单、幂等性、OpenAPI 规范导出、签名断言换令牌、MCP 复用同一密钥体系 | 待估 |

> **本次不做个人访问令牌**（即绑定自然人、继承其权限的密钥）。§3 定义的三类场景全部是系统对系统集成，无一需要它；引入它会带来第二类主体、第二套权限来源（动态继承）与生命周期联动（用户禁用需级联失效），而没有对应的真实诉求。详见 §6 非目标。

# 二、问题定义

## 2.1 什么是开放 API

BiSheng 对外暴露两组 HTTP 接口：

| | 面向前端的接口 | **开放 API（本文档范围）** |
|---|---|---|
| 路径 | `/api/v1/**` | `/api/v2/**` |
| 调用方 | 平台自己的两个 Web 前端 | **客户的自建业务系统** |
| 鉴权 | 用户登录后的 JWT | **无** |
| 典型用途 | 页面渲染、管理操作 | 触发工作流、检索知识库、调用助手对话、上传文档 |

开放 API 当前覆盖 7 个模块：工作流、知识库、文档库、助手、会话、引用溯源、语音。实现位于 `bisheng/open_endpoints/`（7 个路由，约 1900 行）。

## 2.2 现状：三类问题

以下均来自对当前代码库的直接核查，非推测。五个事实归为三类，因为三类的性质与修复手段不同。

### 类型一 · 认证缺失（谁在调用无从知晓）

| # | 事实 | 位置 |
|---|---|---|
| **F1** | 开放 API 全部端点无任何鉴权——无密钥、无签名、无令牌 | `bisheng/open_endpoints/` |
| **F5** | 工作流调用接口**不校验工作流是否已上线**；两个 WebSocket 端点的登录校验被注释掉，注释写着"免登录链接" | `endpoints/workflow.py:41,157-174`；`endpoints/assistant.py:298-318` |

**修复手段**：密钥体系 + 全端点接入（R1、R2）。

### 类型二 · 授权过宽（调用能做什么无从收敛）

| # | 事实 | 位置 |
|---|---|---|
| **F2** | 所有端点统一以一个**配置在数据库里的固定用户**身份执行（配置项 `default_operator`）。该配置项决定了开放 API 的全部权限边界 | `open_endpoints/domain/utils.py:26-74` |
| **F3** | 现有接口文档明确写着"调用方需在网络层负责访问控制"，并**建议把这个固定用户配置成超级管理员**"以避免权限边界问题" | `docs/api/filelib-retrieve.md:25,28` |

**修复手段**：服务账号一等主体 + 权限位收口 + 固定身份降权（R1、R4、R8）。

### 类型三 · 委托无凭据（以谁的名义执行可被任意伪造）

| # | 事实 | 位置 |
|---|---|---|
| **F4** | **"指定用户身份"的能力已经上线**：4 个端点接受请求参数中的裸 `user_id`，并按该用户的可见范围过滤数据。其解析函数 `resolve_operator` **只检查用户存在，连账号是否被禁用都不查** | `open_endpoints/domain/utils.py:77-104`；调用方 `filelib.py:176,381,640`、`assistant.py:278`、`chat.py:85` |

**修复手段**：受限委托六道准入（R3）。注意 `resolve_operator` 的缺陷独立于本特性也应尽快修复。

## 2.3 风险

三类问题叠加的最坏情况：

> **任何能访问服务端口的人，都可以以超级管理员权限、指定任意用户身份、读取平台上的全部知识库内容，并调用任意工作流（含未上线的草稿）。**

三个容易被低估的点：

1. **"部署在内网"不构成缓解**。私有化客户的内网通常有数百至数千台终端；一次钓鱼或一台被控主机即可触达。
2. **这不是"待加固"，而是"已开放"**。代用户能力已随一次迭代（内部编号 F030）上线并被文档化，客户可能已在使用。方案必须给出迁移路径，不能简单删除。
3. **工作流枚举是横向扩大打击面的跳板**——草稿工作流常包含尚未审核的提示词、数据库连接或外部 API 密钥。

## 2.4 为什么现在做

- 工作流对外发布为 MCP 服务的需求已提出，该方案已明确将本问题列为阻塞项——MCP 端点若直接透出现有语义，等于把匿名可枚举执行的能力再暴露一层。
- 客户侧已出现真实集成需求（§3），继续拖延会积累更多依赖现状的存量调用方，迁移成本随时间线性上升。

# 三、需求：三类调用场景

三类场景 MECE 划分，**区分依据是"调用方的应用服务于谁"**。

## 3.1 场景一：系统集成（调用方即一个系统）

**谁**　客户的后台系统、定时任务、数据管道。

**要什么**　"每天凌晨把 ERP 里的新合同同步进知识库"、"订单状态变更时触发一条审批工作流"。

**特点**　没有"最终用户"这个概念，调用方本身就是一个主体。

**当前为什么不行**　能跑通，但跑在一个无鉴权、且被建议配成超管的固定身份上。无法回答"这次同步是哪个系统发起的"，也无法在某个集成出问题时单独停掉它。

## 3.2 场景二：面向平台同一批用户的应用

**谁**　客户在 BiSheng 之外自建的门户/工作台，其用户就是 BiSheng 平台上的用户。

**要什么**
- 「张三在我们自建门户里搜索知识库，**结果必须和他在 BiSheng 里搜到的一致**」——按张三的权限过滤，不能让他看到无权访问的文档，也不能少给他有权访问的文档。
- 「以张三的名义创建一个知识库」——创建出来的资源归属张三，他在 BiSheng 里能看到并管理。

**特点**　最终用户在平台上有真实账号，权限体系是同一套。用户规模可能上千。

**当前为什么不行**　能力已存在（F4），但没有任何信任基础：请求里写谁就是谁，且不需要凭据。

**核心争议**　"凭什么指定一个 user_id 就代表是这个用户在操作？"——见 §4.4.2。

## 3.3 场景三：面向外部用户的应用

**谁**　客户面向自己的客户/公众提供的应用，其用户与 BiSheng 无任何账号关系。

**要什么**　「我们做了个对外客服机器人，用的是 BiSheng 的知识库。这些访客不是 BiSheng 用户，不应该被平台的用户权限体系卡住」。

**特点**　最终用户在平台上不存在，且不应该为此批量创建账号。

**当前为什么不行**　当前一律以固定身份执行，多个外部访客共享同一会话空间，会互相看到对方的对话记录——此失败模式有厂商官方实证 [S5]。

**需求澄清（重要）**　这类客户的原始诉求常被表述为"不要做权限过滤"。**直接实现会造成无边界数据出口**——一旦服务账号权限过宽，外部访客即可检索到全部内部文档。正确的产品解法是：**过滤照做，基准换成服务账号**。给该服务账号授予"这个外部应用应当能看到的那些知识库"，那就是这个应用的数据边界。客户得到的效果一致（外部访客不会被平台用户权限误伤），平台保住了边界可控与可审计。

## 3.4 场景与模式映射

| 场景 | 身份模式 | 权限基准 | 资源归属 |
|---|---|---|---|
| 一 · 系统集成 | **模式 S**（服务账号） | 服务账号 | 服务账号 |
| 二 · 平台同批用户 | **模式 D**（委托） | 被代表用户（受六道准入约束） | 被代表用户 |
| 三 · 外部用户 | **模式 E**（外部标识） | 服务账号 | 服务账号 + 外部标识标签 |

## 4.2 R1 · 凭据体系

### 4.2.1 为什么新建而不复用现有机制

平台已有四类"对外签发或持有的凭据"，逐一核实后**没有一个可以复用**：

| 现有机制 | 生成 | 存储 | 过期 | 撤销 |
|---|---|---|---|---|
| 分享链接 token | 合格（`os.urandom` + HMAC） | **明文**，且 API 原样返回整个对象 | 字段存在但**代码从不校验**（`share_link_service.py:52-56` 注释明说 intentionally not enforced） | 有 INACTIVE 枚举，但**全仓无任何写入端点** |
| 工具 `api_key` | 不生成（用户手填第三方 key） | **明文** | 无 | 无 |
| 邀请码 | **`random.choices()` 非密码学随机** | **明文** | 无（仅次数限制） | 仅回滚次数 |
| 网关 HMAC | 不签发（共享密钥签名） | 配置项 | 无 | 改配置重启 |

**结论**：凭据层是纯新建。但有两个现成件必须复用：
- `generate_short_high_entropy_string`（`common/utils/util.py:28-54`）——全仓唯一合格的随机源
- `sso_sync/domain/services/hmac_auth.py:44-109`——全仓唯一做对了恒时比较 + fail-closed 的校验实现，其姿势应被抄用

### 4.2.2 唯一主体：服务账号

**密钥只签发给服务账号，不签发给自然人。**

| 项 | 值 |
|---|---|
| 前缀 | `bs-sak-`（前缀即类型，便于密钥泄漏扫描 [S6][S3]） |
| 绑定主体 | 服务账号——一种不可登录的一等主体，见 §4.5 |
| 权限来源 | 服务账号**自身**的授权，不继承任何自然人 |
| 生命周期 | 长期有效，可设过期；支持不轮换密钥直接改权限 [S6] |

**为什么不做"绑定自然人的密钥"**——LangSmith 同时提供两类密钥，其文档明确记载了自然人密钥的固有缺陷：**个人令牌随创建者离职失效** [S6]。生产集成不能因某员工离职而中断，这本就是要靠服务账号解决的问题。与其两类都做再引导用户选对，不如只提供正确的那一类。副作用是权限归属与自然人彻底解耦，审计也能干净地回答"这次调用是哪个系统发起的"。

### 4.2.3 密钥属性

| 属性 | 说明 |
|---|---|
| **`tenant_id`** | **租户隔离字段，必填**。详见 §4.2.5 |
| 主体 ID | 指向服务账号在用户表中的主键 |
| 名称 | 用户可读，必填 |
| 前缀 / 末四位 | 列表展示用 |
| 密钥哈希 | SHA-256，唯一索引 |
| 权限位 | 见 §4.2.4 |
| 资源白名单 | 可选：收窄到指定工作流 / 助手 / 知识库 |
| **委托模式** | `none`（默认）/ `scoped` / `any` |
| **委托范围** | `scoped` 时的类型化范围，见 §4.4.3 |
| IP 白名单 | 可选 CIDR 列表（P2） |
| 过期时间 | 可空（长期有效）；创建时可选设定 |
| 最后使用时间 | 节流写入（≥60s 更新一次），避免热路径写放大 |
| 撤销时间 | 软撤销，保留审计可追溯性 |

**有效性判据是单一事实**：`撤销时间为空 且（过期时间为空 或 未到期）`。**不设独立的 status 枚举列**——分享链接的 INACTIVE 枚举全仓无写入端点，证明可漂移的冗余状态列是负资产。

### 4.2.4 权限位

```
workflow:invoke   workflow:read
knowledge:read    knowledge:write
assistant:invoke  assistant:read
chat:read         chat:write
delegate          ← 委托能力，独立位，不被上述任何权限蕴含
```

`delegate` 独立成位，落实"冒充能力必须单独授予"这一跨平台共识（附录 A.5）。同时受委托模式二次约束：即使持有 `delegate`，模式为 `none` 仍拒绝。

**创建时默认不勾选任何权限位**。反面实证来自 n8n：「Non-enterprise API keys have full access to all the account's resources and capabilities.」[S4]——默认全权限即隐患。

### 4.2.5 存储、校验与租户隔离

**存储：单向哈希，不用可逆加密。**

> 平台已有 Fernet 加密工具，但**其密钥硬编码在 `core/config/settings.py:20` 并随开源仓库分发**，任何人可解密全部密文，且无轮换机制。Fernet 的合理适用面是"服务端需要还原后转发给第三方"的出站凭据（数据库密码、组织同步凭据）；入站 API 密钥服务端只需比对不需还原，**存哈希严格更安全**——数据库被拖走也无法还原密钥。
> 不加盐即可：密钥本身是高熵随机值，无字典攻击面；不加盐才能直接建索引做常数时间校验。这与用户口令必须加盐的场景不同。

**校验流程（顺序不可调换）：**

```
1. 提取 Authorization: Bearer bs-…
2. with bypass_tenant_filter():              ← 此时尚无租户上下文，必须绕过
       按 sha256(明文) 查密钥行                  （分享链接服务已有同构先例，其注释
                                                语义完全一致："token 本身就是授权"）
3. fail-closed 校验，全部通过才继续：
   恒时比较 → 未撤销 → 未过期 → 主体有效且类型匹配 → 主体当前租户 == 密钥租户
4. set_current_tenant_id(密钥租户)            ← 从这里开始有租户上下文，
                                                后续所有查询被自动过滤
5. 构造身份对象（复用 get_default_operator_async:66-74 的既有模式）
6. Redis 缓存步骤 2-3 的结果，TTL 5s；撤销时主动删除缓存键
```

**租户隔离的两个必要条件，缺一不可：**

1. 密钥表物理带 `tenant_id` 列（自动过滤靠反射发现，`core/database/tenant_filter.py:127-140`）
2. **密钥模型的模块路径注册进 `_TENANT_AWARE_MODEL_MODULES` 手工清单**（`tenant_filter.py:39-102`）

> ⚠️ 该文件 `:36-38` 的注释记录了 v2.5 的一次事故：因漏注册导致 `knowledgefile`、`flowversion`、`roleaccess`、`userrole` **静默把子租户数据写进了根租户**。这是必须引用的前车之鉴。

**写路径规约**：自动过滤**只拦 SELECT**（`tenant_filter.py:164`）与 INSERT 自动填充（`:200-234`）。**禁止**对密钥表使用批量 update/delete 或原生 SQL——撤销走单行 ORM 更新，最后使用时间走带主键的 UPDATE。

### 4.2.6 展示与泄漏应急

- **仅显示一次**：明文仅在创建响应中返回，此后任何接口不再吐出；列表页只显示前缀与末四位。
- **泄漏扫描**：前缀 `bs-sak-` 需注册到代码托管平台的 secret scanning 规则。
- **批量撤销**：支持"一键撤销某主体名下全部密钥"，用于泄漏应急。

## 4.3 R2 · 三种身份模式

三种模式**互斥**，由请求头显式选择。同时传入两种身份头即为参数错误。

### 4.3.1 请求处理流程

### 4.3.2 模式 S · 服务账号身份（默认）

不传任何身份头。全部操作以密钥主体身份执行，按其可见范围过滤。

对应场景一。行业同构：RAGFlow [S2]、n8n [S4]、LangSmith [S6]——这三家均**完全没有**最终用户身份传递机制。

### 4.3.3 模式 D · 代表平台用户

```http
POST /api/v2/filelib/retrieve
Authorization: Bearer bs-sak-…
X-Bisheng-On-Behalf-Of: 10086
```

对应场景二。行业同构：**FastGPT `authProxy`**（最贴近）[S3]、Zendesk `X-On-Behalf-Of` [S7]、Kubernetes `Impersonate-User` [S8]。准入规则见 §4.4.3。

### 4.3.4 模式 E · 外部用户体系

```http
POST /api/v2/workflow/invoke
Authorization: Bearer bs-sak-…
X-Bisheng-End-User: crm-user-88f3a2
```

对应场景三。行业同构：Dify `user` [S1]、Coze `session_name` [S5]、FastGPT `customUid` [S3]。

**语义声明（须原样写入对外 API 文档，措辞不容含糊）**：

> `X-Bisheng-End-User` **仅用于会话隔离与审计留痕，不参与任何权限判定**。平台不认识、不校验、不解析该标识。本模式下的数据可见范围**完全等于密钥主体（服务账号）的权限边界**。

此措辞对齐 Dify「Dify never authenticates it」与 Coze「currently utilized only in session isolation」——两家都用近乎相同的免责声明 [S1][S5]。

**缺省行为**：对有会话语义的端点，模式 E 下若未传该头，应告警并按调用方粒度隔离，避免 Coze 官方记录在案的跨用户串档 [S5]。

**配额归属**：外部标识**不作为配额维度**。配额与限流一律按密钥计（§4.8）——平台无法验证外部标识，按它计量等于把配额控制权交给调用方。

### 4.3.5 模式对比

| | 模式 S | 模式 D | 模式 E |
|---|---|---|---|
| 身份头 | 无 | `X-Bisheng-On-Behalf-Of` | `X-Bisheng-End-User` |
| 需要 `delegate` 位 | 否 | **是** | 否 |
| 权限基准 | 密钥主体 | **被代表用户**（受六道准入约束） | 密钥主体 |
| 标识是否参与鉴权 | — | **是** | **否** |
| 目标须为平台用户 | — | **是** | 否 |
| 资源归属 | 密钥主体 | 被代表用户 | 密钥主体 + 外部标识标签 |
| 配额计量维度 | 密钥 | 密钥 | 密钥 |

## 4.4 R3 · 权限过滤与受限委托

### 4.4.1 三条铁律

| 铁律 | 行为 | 依据 |
|---|---|---|
| **F1 无凭据即拒绝** | 移除固定身份兜底。无有效密钥 → 401，不降级 | §2.2 现状风险 |
| **F2 缺身份 ≠ 放行全部** | 配置为必须委托的端点若未传身份头 → 只返回对所有人公开的资源，绝不返回全量 | Microsoft 2025-11 的同类改造 [S13] |
| **F3 评估失败即报错** | 权限引擎不可用 → 5xx，**绝不**返回未过滤或部分过滤的结果集 | 「does not return a partially filtered result set」[S13] |

> **F2 的适用范围限定**：平台的权限模型中确实存在"对所有人公开"的概念（`public_reader` 关系 + `user:*` 通配符，`core/openfga/authorization_model_f048.py:346,367`），但其写入路径**硬限制只允许知识空间**（`permission/application/runtime.py:792-793`）。工作流与助手无对应概念，因此 F2 对这些端点等价于**返回空集**。

> **F3 需专项验证**：落地时须逐条确认不存在"过滤器抛异常被吞 → 返回全量"的代码路径。

### 4.4.2 委托的信任基础（回答核心争议）

**这不是身份认证（authentication），是授权委托（delegation）。**

它声称的不是"张三本人在操作"，而是"平台管理员已授权这个集成方，可以按张三的权限边界执行并把结果归属给张三"。安全性来自三处，**从不来自 user_id 本身**：

1. 密钥的保密性（调用方先用自己的凭据完成认证）
2. 委托能力的显式授予（一项独立的、可撤销的权限）
3. 审计双归属（可追责到具体密钥）

这与 Kubernetes 的鉴权时序完全同构：先认证发起者，再校验其冒充权限，最后才替换身份 [S8]。委托头**永远不能单独确立身份**。

### 4.4.3 受限委托：六道准入检查

模式 D 的准入是**一次性判定**，不是逐资源判定。六道全过才放行：

| # | 检查 | 失败错误码 | 依据 |
|---|---|---|---|
| **1** | 密钥持有 `delegate` 权限位 | 26004 | Zendesk 的独立 `impersonate` scope [S7] |
| **2** | 委托模式非 `none` | 26004 | FastGPT 逐密钥由团队所有者显式开启 [S3] |
| **3** | 目标用户存在、未禁用、且与密钥主体同租户 | 26005 | Zendesk「must have an existing user profile」[S7] |
| **4** | **目标不是超级管理员，也不是租户管理员** | **26007** | 见下方论证 |
| **5** | 目标在密钥的**委托范围**内（`scoped` 模式时） | 26004 | Kubernetes 的 `resourceNames` 取值白名单 [S8] |
| **6** | 该端点在委托支持列表内 | 26006 | 本方案自主设计 |

全部通过后，**执行身份纯替换为目标用户**，后续逐资源鉴权与今天完全相同，无额外开销。

**检查 4（特权主体禁令）是本方案防提权的核心**。依据：权限引擎中只有两个"无条件放行"的短路——超级管理员与租户管理员（`permission/domain/services/permission_action_service.py:379-384`）。除这两类外，任何用户的权限都是有界的、逐资源的。**掐断这两类即掐断了无界提权路径**，而判定成本极低（超管判定已有 Redis 缓存）。

**检查 5 的委托范围必须是类型化的，不能是 user_id 列表**：

```
users        — 指定用户 ID 集合
departments  — 部门（含子树）
user_groups  — 用户组
roles        — 角色
tenant_wide  — 本租户任意非特权成员
```

场景二的用户规模可能上千，逐个列 user_id 运维不可行。部门子树判定可复用现有的物化路径（`database/models/department.py` 的 `UserDepartment` + `Department.path`），单次索引查询即可。

### 4.4.4 为什么不采用"权限取交集"（决策记录）

v1.0 曾规定 `执行权限 = 被代表用户权限 ∩ 密钥主体权限`。经代码核实后否决，四条理由：

1. **无法实现**：权限引擎的 ListObjects 通道被显式禁用（`permission/application/sql_runtime.py:638-648` 装配 `DenyListObjectsPolicy`，注释为"待性能基线评审通过前保持关闭"），无法列出两个主体的可见集求交。
2. **成本不可接受**：单次鉴权约等于 1~2 次权限引擎往返 + 3~4 次数据库查询 + 2~4 次缓存读取，且主链路**无缓存**。知识库检索的批量预过滤（`knowledge/domain/services/knowledge_file_visibility_service.py:120-198`，阈值 5000 文件）若翻倍，将直接落在对话首字延迟上。
3. **创建场景语义无法定义**：创建类操作根本不做资源级权限前置检查（`knowledge/domain/services/knowledge_space_service.py:1035`，门槛只有配额与模型可用性）。"密钥主体的创建权限"在权限模型里**不存在可供求交的对象**，取交集在「以张三名义创建知识库」这一核心需求上无从落地。
4. **语义悖论，且击穿核心需求**：只要被代表用户的权限宽于服务账号（这是常态——服务账号本应按最小权限授予），交集就等于服务账号权限，委托头**静默失效**：接口返回 200，给出一个缩水的结果集，调用方无从察觉。而这恰好违背场景二的第一条需求「结果必须和他在 BiSheng 里搜到的一致」。取交集因此两头堵——服务账号权限窄则需求落空，权限宽则防护失效且服务账号本身成为高危凭据。

**受限委托与它的取舍差异**：防提权的语义从"恒为降权"弱化为"提权有上界"——调用方最多获得委托范围内某个真实用户的真实权限，永远够不到无条件放行。代价是需要在对外文档中解释这一边界。行业已识别同一问题：Kubernetes v1.36 引入 Constrained Impersonation（beta，需 feature gate），将"能扮演谁"与"扮演后能做什么"拆为两项权限 [S8]——与本方案思路一致。

### 4.4.5 审计双归属

模式 D 的审计记录必须同时包含：
- **actor**：密钥主体 + 密钥 ID（回答"哪个系统调的"）
- **subject**：被代表用户（回答"以谁的名义调的"）

资源归属字段写被代表用户——对齐 Zendesk「the change is associated with the end user, not the admin」[S7]。

## 4.5 R4 · 服务账号主体

服务账号复用现有用户表（新增类型字段 + 禁止登录）。**这是深思后的选择而非零成本方案**——另建平行主体体系需要改动权限模块的主体类型全链路（授权主体校验、权限模型定义、投影逻辑），代价更高。但复用的真实成本必须列清。

### 4.5.1 主体标识

新增 `user_type` 列（`human` / `service`，带索引，需 Alembic 变更）。其余用既有字段的特定取值表达：

| 字段 | 服务账号取值 | 效果 |
|---|---|---|
| `source` | `service_account`（新枚举值） | 组织同步的认领查询按渠道匹配，服务账号结构性不命中 |
| `external_id` | `NULL` | **登录候选查询、公开改密均按 `external_id` 查找，NULL 结构性不命中**——三条路径零代码免疫 |
| `password` | 哨兵值（带特殊前缀的高熵串） | 满足非空约束；密码校验输出格式与哨兵永不相等 |

> ⚠️ **不能用现有的 `delete` 字段兼职做"禁止登录"标记**：SSO 回调会在同步时把它翻回 0（`sso_sync/domain/services/login_sync_service.py:364-369`），管理员也可在用户管理页直接启用。必须独立字段。

### 4.5.2 租户归属（最硬的卡点）

**问题**：服务账号要能被授权，必须在租户关联表有活跃行——授权主体校验要求 `status == "active" 且 is_active == 1`（`tenant/domain/services/f048_permission_subject.py:53-74`，判定在 `:70`）；但该表是**部门树的派生投影**（`docs/architecture/12-multi-tenant.md:308`：「部门树是真相，user_tenant 是派生投影」），而服务账号没有主部门。

**方案**：声明式直写 + 三层对账豁免。

| 层 | 措施 | 位置 |
|---|---|---|
| 1（收口点） | 对账任务的用户扫描加 `user_type == 'human'` 条件 | `UserDao.alist_users_after_id`，唯一调用方是 `worker/tenant_reconcile/tasks.py:68` |
| 2（纵深） | 租户同步服务入口加服务账号守卫，防未来新增调用点把它拉回根租户 | `tenant/domain/services/user_tenant_sync_service.py:71` 的 `sync_user` |
| 3 | 租户解析器不改（另一调用方只作用于登录用户，服务账号不可达） | — |

**否决"给服务账号挂虚拟部门"的方案**：部门树被组织同步全量对账管辖，虚拟部门有被上游快照清除的风险；且会污染部门管理界面、审批人部门维度、部门成员数、租户用户列表至少 4 个消费面。

**配额联动**：租户用户数配额的统计需加 `user_type == 'human'`（`role/domain/services/quota_service.py:622-645` 的 `_count_user_count`，现有过滤条件仅 `User.delete == 0`），服务账号不占租户席位。

### 4.5.3 用户列表分叉

`/api/v1/user/list` 一个接口同时服务 8 处以上消费点，其中包含**资源授权选人**。服务账号必须出现在授权选人里（否则无法给它授权，模式 S/E 全部失效），又不该出现在用户管理、审批人选择、部门加成员、创建租户选管理员等场景。

**fail-safe 方向**：排除逻辑下沉到数据访问层——`_filter_users_statement`（`user/domain/models/user.py:259`）增加默认值为 `human` 的类型参数。**忘记传参的结果是"看不到服务账号"而非"泄漏服务账号"**。接口层增加显式的 opt-in 参数。

改动面：后端 2 处（DAO + 接口），前端仅 2 处 opt-in（授权选人组件），其余 6 处以上消费点零改动。

服务账号自身的管理列表走**新端点**，不复用 `/user/list`。

### 4.5.4 登录守卫

10 个入口，实际只需 1 处公共守卫 + 3 处单独改：

| 类别 | 措施 |
|---|---|
| **公共守卫（1 处覆盖 4 入口）** | `UserService._reject_login_if_user_has_no_usable_access`（`user/domain/services/user.py:373`）开头拒绝服务账号。经核实其有 4 个调用点：本地登录、SSO、网关登录同步、租户选择 |
| **结构性免疫（0 改动，但需测试断言防退化）** | 见 §4.5.1 的 `source` + `external_id=NULL` 组合 |
| **单独改 3 处** | ① `resolve_operator`（`open_endpoints/domain/utils.py:77`）——既有后门，连账号禁用都不查，**P0 应独立修复**；② `get_default_operator*`（`:26/:53`）补账号状态校验；③ `/user/update`（`user/api/user.py:674`）拒绝服务账号，防管理员绕过密钥缓存失效逻辑 |

## 4.6 R5 · 端点接入（含 WebSocket）

全部端点的改造清单见**附录 B**。此处只说明两个需要专门设计的点。

### 4.6.1 WebSocket 如何传递密钥

**现状两个事实**：
- 现有的 WebSocket 鉴权依赖 `t` 查询参数的路径**是坏的**——该参数在 `AuthJwt.get_subject`（`user/domain/services/auth.py:175-177`）中被无条件覆盖，实际 100% 依赖 Cookie。若要走查询参数必须先修这里。
- 握手请求头可读：WebSocket 中间件已在读取 `scope["headers"]`（`utils/http_middleware.py:399-408`），**服务端到服务端的调用可以传自定义头**。

**方案**：
- 服务端集成走 `Authorization` 头（首选，与 HTTP 一致）
- 浏览器直连需子协议或票据换取（浏览器原生 WebSocket API 无法设置自定义头）
- **不采用查询参数**——密钥会进入访问日志，与 R6 的审计要求冲突

**顺带修复**：`assistant.py:304` 的身份解析在 `try` 块之外，配置缺失时会让握手裸崩而非优雅关闭。

### 4.6.2 补上被遗漏的业务校验

- 工作流调用接口补**上线状态校验**（现状可调用未上线草稿）
- 工作流停止接口补**会话归属校验**（现状任何人可停任意会话）

## 4.7 R6 · 管理界面

### 4.7.1 密钥管理

| 功能 | 说明 |
|---|---|
| 创建 | 选择主体、权限位、可选资源白名单与委托配置；明文仅此一次展示，附复制按钮与"关闭后不再显示"提示 |
| 列表 | 名称、前缀+末四位、主体、权限位、委托模式、最后使用时间、过期时间、状态 |
| 编辑 | 可改名称、权限位、委托配置、过期时间——**无需轮换密钥** [S6] |

### 4.7.2 服务账号管理

独立入口，提供创建、列表、启停、删除、授权跳转。创建服务账号时同步完成租户关联行的写入与权限投影（§4.5.2）。

**权限要求**：服务账号的创建、密钥签发与委托配置**均仅管理员可操作**。由于密钥不签发给自然人，本模块无面向普通用户的自助入口。

## 4.8 R7/R8 · 审计、限流与幂等

### 4.8.1 审计

每次开放 API 调用记录：时间、密钥 ID、主体、身份模式、被代表用户（模式 D）、外部标识（模式 E）、端点、来源 IP、结果状态、耗时。

**双归属是硬要求**：审计必须能同时回答"哪个系统调的"和"以谁的名义调的"。

### 4.8.2 限流与配额（P2）

按**密钥**维度限流与计量（不按外部标识，理由见 §4.3.4）。超限返回 429。

> ⚠️ **成本提示**：平台**没有任何 HTTP 层限流基础设施**——无 `slowapi`、`fastapi-limiter` 等依赖。最接近的可复用原语是部门并发槽位的 Redis Lua 脚本（`department/domain/services/department_flow_service.py:57-118`），但它在 Redis 故障时 fail-open，对鉴权场景语义不合适，需改写。P2 估算时不可按"接个现成库"计。

### 4.8.3 幂等性（P2）

`POST /api/v2/workflow/invoke` 等有副作用的端点支持 `Idempotency-Key` 请求头，重复提交返回首次结果。这是企业集成的标准需求——网络重试不应导致工作流重复执行。

## 4.9 R9 · 存量迁移

现状已有客户在无鉴权调用，需要迁移窗口：

1. **兼容并行（P0）**——有 `Bearer bs-…` 则走密钥身份；无则回落原固定身份。新增配置开关 `open_api.require_api_key`（默认 `false`），置 `true` 后无密钥一律 401。开启前每请求记 WARN 日志。
2. **固定身份转型（P0）**——原"默认操作员"语义改为"默认服务账号"并**强制降权**；部署检查若发现其为超级管理员则告警。
3. **存量资源归属**——优先**就地转型**：把该用户直接改为服务账号类型，名下资源零迁移。仅当探测到以下任一情况时才走"新建服务账号 + 资源转移"兜底：近 90 天有登录记录、存在部门关联、持有管理员角色。转型脚本按规范放 `scripts/`，**不写入数据库变更脚本**。
4. **裸 user_id 参数兼容期（P1）**——现有 4 个端点的 `user_id` 参数保留一个版本，行为等价于模式 D（含六道准入）但记 deprecation 日志，之后移除。
5. **文档修订（P0）**——现有接口文档中"网络层负责访问控制""建议配置超级管理员"两处表述必须删除，它们是错误引导。
6. **移除（下一大版本）**——删除过渡开关与固定身份兜底路径。

# 五、验收标准

## R1 · 凭据体系

- **AC-1**　`open_api.require_api_key=true` 时，无密钥调用任意开放 API 端点返回 401。
  > ⚠️ 迁移期该开关默认 `false`，此期间 AC-1 不成立——这是显式的灰度取舍，须在发布说明中标注。
- **AC-2**　密钥明文在创建后无法通过任何接口再次获取。
- **AC-3**　撤销密钥后，后续调用在 5 秒内失效。
- **AC-4**　密钥缺少对应权限位时返回 403，错误信息指明缺少哪一位。
- **AC-5**　跨租户查询密钥列表返回空——验证租户自动过滤已生效（含模块注册）。

## R2 / R3 · 身份模式与受限委托

- **AC-6**　未授予 `delegate` 的密钥传入 `X-Bisheng-On-Behalf-Of` 返回 403。
- **AC-7**　**窄权限密钥 + `delegate` 指定超级管理员或租户管理员 user_id，返回 403（错误码 26007）**——特权主体禁令生效。
- **AC-8**　委托目标为不存在/已禁用/跨租户用户时返回 403，且不泄露该用户是否存在的差异化信息。
- **AC-9**　`scoped` 模式下，委托范围配置为某部门时，该部门子树内用户放行、子树外用户 403。
- **AC-10**　同时传入两个身份头返回 400。
- **AC-11**　模式 E 下传入任意 `X-Bisheng-End-User`，返回结果的**权限范围与不传时完全一致**（仅会话隔离不同）。
- **AC-12**　模式 D 下以张三身份检索，返回结果与张三在平台内自行检索的结果**集合相等**（验证纯替换，无意外收窄）。
- **AC-13**　权限引擎不可用时，检索接口返回 5xx 且不返回任何结果（铁律 F3）。

## R4 · 服务账号主体

- **AC-14**　服务账号无法通过任何登录入口获得会话——需覆盖全部 10 个入口的测试矩阵。
- **AC-15**　服务账号出现在资源授权选人列表中，且**不出现在**用户管理、审批人选择、部门成员、创建租户选管理员列表中。
- **AC-16**　租户对账任务执行后，服务账号的租户归属不被改写。
- **AC-17**　服务账号不计入租户用户数配额。

## R5 · 端点接入

- **AC-18**　两个 WebSocket 端点在握手阶段校验密钥，无效密钥握手失败且优雅关闭。
- **AC-19**　调用未上线的工作流返回业务错误，而非正常执行。
- **AC-20**　停止不属于当前密钥主体的会话返回 403。

## R6 · 管理界面

- **AC-21**　修改密钥权限位后无需轮换密钥，原密钥立即按新权限生效。
- **AC-22**　按主体批量撤销后，该主体名下全部密钥在 5 秒内失效。

## R7 / R8 · 审计、限流与幂等

- **AC-23**　模式 D 的审计记录同时含 actor（密钥主体）与 subject（被代表用户），可据此还原完整调用链。
- **AC-24**　（P2）超出密钥限流阈值返回 429。
- **AC-25**　（P2）携带相同 `Idempotency-Key` 重复调用工作流，仅执行一次。

## R9 · 存量迁移

- **AC-26**　`require_api_key=false` 时，无密钥的存量调用仍可工作且记 WARN 日志。
- **AC-27**　固定身份转型后，其名下存量资源的归属与可见性不变。

# 六、非目标

明确不在本次范围内，避免范围蔓延：

- ❌ **不实现个人访问令牌**（绑定自然人、继承其权限的密钥）——§3 的三类场景全部是系统对系统集成，无一需要；引入它会带来第二类主体、第二套权限来源（动态继承）与生命周期联动（用户禁用需级联失效），而没有对应的真实诉求。行业先例中此类密钥的固有缺陷是随创建者离职失效 [S6]，正是服务账号要解决的问题
- ❌ **不实现完整 OAuth 2.0 授权服务器**（授权码流、刷新令牌、同意页）
- ❌ **不实现最终用户令牌透传**（附录 A.4 的 C 档）——要求最终用户在平台有身份，对场景三不适用
- ❌ **不做即时建号**——模式 D 的目标用户必须预先存在
- ❌ **不改造 `/api/v1` 前端接口的鉴权方式**
- ❌ **不实现按端点的细粒度权限**——权限位到**模块 + 动作级**（read / write / invoke）即止，不做到单个端点
- ❌ **不实现 Webhook 回调方向的鉴权**（平台如何向客户系统证明自己）——如客户有此需求，作为 P2 独立评估

## A.1 核心裁决：「传 user_id 代表用户」到底行不行

### 把问题拆成两个

| 问题 | 答案 |
|---|---|
| 传 user_id 能**证明**这是该用户本人在操作吗？ | **不能，永远不能。** 任何平台都做不到 |
| 传 user_id 能**合法地**让调用方按该用户的权限边界执行、并把结果归属给该用户吗？ | **能——当且仅当护栏齐备。** Zendesk、Kubernetes、FastGPT 均如此实现 |

### 规范层的判据

OWASP API Security Top 10 2023 将 BOLA（对象级授权失效）列为第一风险：

> 「Every API endpoint that receives an ID of an object, and performs any action on the object, should implement object-level authorization checks. The checks should validate that the logged-in user has permissions to perform the requested action on the requested object.」
> 「Comparing the user ID of the current session (e.g. by extracting it from the JWT token) with the vulnerable ID parameter isn't a sufficient solution to solve Broken Object Level Authorization (BOLA). This approach could address only a small subset of cases.」
> ——［文档］https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/

**引用分寸（必须保留，否则即为过度引用）**：
- OWASP 使用 `should` 而非 `must`，是指南而非强制标准。
- BOLA 判据针对"已认证会话内的对象级授权"。若服务账号确实持有相应对象权限，字面判据可被满足——此时真实缺陷是"未强制的委托"，更接近端点级越权（API5:2023 BFLA）而非 API1。
- 原文只说 ID 比对"不充分"，不能转述为"OWASP 禁止 ID 匹配"。

## A.4 三档身份传递模型

| 档 | 形态 | 代表 | 平台能否独立验证 | 适用前提 |
|---|---|---|---|---|
| **A · 受信客户端断言** | 明文头/字段传用户标识 | Dify、FastGPT `authProxy`、Zendesk、K8s、Azure 弱档 | 否 | 调用方后端受控、与平台同一信任域 |
| **B · 签名断言** | 用户标识进调用方私钥签名的 JWT | Coze、Atlassian 2LOi | 能验签，但仍是调用方自证 | 需不可抵赖、密钥可轮换 |
| **C · 用户令牌透传** | 最终用户自己的令牌直接透传 | Microsoft OBO、Azure 强档 | **是** | 最终用户即平台用户且能走统一身份源 |

**关键判断**：A 档并非"不安全"——Zendesk 与 Kubernetes 都在 A 档且被广泛接受。差别在护栏是否齐备，而非档位高低。C 档最强，但要求最终用户在平台有身份，对场景三（外部用户）根本不适用。

**本方案选型**：一期采用 A 档（与 FastGPT 完全同构），预留 B 档升级路径（决策 D6）。

## A.5 委托的护栏

四条护栏，注意**它们并非全部是跨平台不变量**——各家取舍不同：

| # | 护栏 | 采纳情况 |
|---|---|---|
| **G1** 调用方自身凭据先认证，委托头永不单独确立身份 | **跨平台一致** | K8s 的鉴权时序原文 [S8] 是最清晰的表述 |
| **G2** 冒充能力单独授予，不被任何其他权限蕴含 | **三家一致** | Zendesk `impersonate` scope、Atlassian `ACT_AS_USER` 独立 scope、K8s `impersonate` 动词；FastGPT 更进一步——**逐密钥由团队所有者显式开启** |
| **G3** 收窄可代表范围 | **两种实现** | Zendesk：目标须**预先存在**；K8s：**不要求存在**，改用 `resourceNames` 取值白名单。二者目的相同、手段不同 |
| **G4** 审计归属到被代表用户 | Zendesk 明文规定 | 「the change is associated with the end user, not the admin」 |

**反面教材（同样有价值）**：Coze 的 `session_name` **没有任何单独授予机制**——任何持私钥者可随意填写。其结果是该字段被官方明确降级为"仅用于会话隔离"，不承载任何权限语义。**这印证了 G2 的必要性：缺少单独授予，委托字段就只能被降级为标签。**

## A.6 四条可直接采纳的失败模式实证

### A.6.1 缺失最终用户身份 ≠ 放行全部

Microsoft 在 2025 年 11 月对 Azure AI Search 做过一次 fail-closed 改造，起因与 BiSheng 现状同构：服务密钥调用时即使不带用户令牌也返回全部文档。改造后「If the user token is omitted, ACL-protected content isn't returned」[S13]。

同页另有一条 Note 界定了正确的降级语义：**不是返回空，而是只返回对所有人公开的内容**。

### A.6.2 绕过过滤是一项更强的权限，不是免费开关

Azure 的排障逃生门 `x-ms-enable-elevated-read` 要求调用方另外持有 `Search Index Data Contributor` 或含 `Elevate Read` 的自定义角色 [S13]。绕过过滤被做成**单独授予的更强权限**。

同样的反面实证来自 n8n：「**Non-enterprise API keys have full access to all the account's resources and capabilities.**」[S4]——默认全权限即是隐患。

### A.6.3 共享令牌无最终用户标识 → 跨用户会话串档

Coze 官方文档自述 [S5]：

> 「all interactions utilizing the same access token are treated as originating from the same user. As a result, **multiple business users can view each other's chat histories** if they share the same access token.」

这正是 BiSheng 场景三当前的实际状态（§3.3）。

### A.6.4 权限评估失败必须 fail-closed

> 「If ACL evaluation fails … the service returns 5xx and **does not return a partially filtered result set**.」[S13]

对 BiSheng 的直接映射：权限引擎不可用时，检索接口必须报错，绝不能退化成"过滤器没生效所以全返回"。

## A.7 API 密钥设计要素（已取证部分）

| 要素 | 行业实证 | 来源 |
|---|---|---|
| **绑定主体分两类** | LangSmith 显式拆个人令牌 / 服务账号密钥；**个人令牌随创建者离职失效**——这是两者确为不同主体的决定性证据 | [S6] |
| **前缀可识别** | `lsv2_pt_` / `lsv2_sk_`（LangSmith）、`fastgpt-`（FastGPT）——前缀即类型，便于泄漏扫描 | [S6][S3] |
| **作用域** | LangSmith 可 scope 到单/多工作区或整个组织；Dify 应用级 Key 只能访问一个应用 | [S6][S1] |
| **过期时间** | n8n **创建时必填过期时间**；Coze PAT 上限 30 天且不可设永久；Coze OAuth 令牌默认 900s / 上限 86399s | [S4][S5] |
| **改权限无需轮换** | LangSmith 企业版可直接调整服务账号密钥的角色 | [S6] |
| **实例级开关** | n8n `N8N_PUBLIC_API_DISABLED=true` 可整体关闭公共 API | [S4] |
| **默认全权限是隐患** | n8n 非企业版密钥拥有账户全部资源的完整访问权 | [S4] |
| **委托逐密钥开启** | FastGPT `authProxy` 须由团队所有者在创建/编辑该密钥时显式开启 | [S3] |

> ⚠️ 本次**未取到证据**的要素：密钥的哈希 vs 加密存储、仅显示一次 / 末四位展示规则、IP 白名单、限流配额、审计日志字段、幂等性。§4 中相关设计属本方案自主主张，非行业取证结论。

## A.8 取证边界与核验方法

### 关于知识库检索的权限过滤（重要事实澄清）

平台内存在两条检索路径，权限过滤强度不同，设计与测试时不可混淆：

| 路径 | 权限过滤 | 位置 |
|---|---|---|
| `/api/v2/filelib/retrieve` 走的路径 | **只做知识库级一次校验，无文件级过滤** | `knowledge/domain/services/knowledge_space_chat_service.py:812-872` |
| 工作台文件夹对话走的路径 | **两层过滤**：索引层预过滤（批量鉴权后下推向量库/ES）+ 结果层批量校验兜底 | 同文件 `:484-570` |

此外，权限模型中并**不存在**名为 `view_file` / `view_space` 的关系——实际统一使用 `visible` 关系。历史文档中的这两个叫法仅为描述性称呼。

# 附录 E · 对外措辞红线

| ✅ 可以说 | ❌ 不能说 |
|---|---|
| 委托模式让集成方按指定用户的权限边界执行并留痕 | 委托模式能验证是该用户本人在操作 |
| 委托不能代表超级管理员或租户管理员 | 委托后的权限恒小于服务账号权限（受限委托是"提权有上界"，非"恒为降权"） |
| 外部用户模式下数据边界等于服务账号的授权范围 | 外部用户模式不做权限过滤 |
| Atlassian 2LOi 是一个设计先例 | Atlassian 当前推荐这种做法（其 Connect 2027-01-31 停止支持） |
| Azure 查询期 ACL 强制双凭据（预览版能力） | Azure 已正式提供该能力 |
| 本表覆盖 13 个已取证产品 | 引用任何附录 A.8 未列入的产品做法 |
