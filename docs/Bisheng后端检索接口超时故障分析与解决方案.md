# 后端接口超时问题分析与整改情况

> 日期：2026-09-04

## 一、问题概述

近期 Bisheng 后端出现“服务运行一段时间后，接口响应越来越慢，最终部分接口超时”的现象，其中知识检索接口受影响最明显。

生产日志显示，相关容器始终处于运行状态且没有重启，因此本次问题不是服务器宕机，而是后台请求处理资源被长期占用。

## 二、原因结论

问题主要发生在知识检索过程中。

知识检索需要依次调用权限服务、Embedding 模型、Milvus 向量库、Elasticsearch 和文件存储等多个外部服务。原有实现存在以下问题：

1. 部分外部调用采用同步方式，一个环节响应变慢时，会持续占用后端处理资源。
2. 缺少完整的超时保护，异常请求可能长时间不结束。
3. 缺少合理的并发控制，高峰期会同时产生大量模型和向量库请求。
4. 随着慢请求不断累积，可用处理资源逐步减少，最终影响其他正常接口。

日志中有一条知识检索请求在权限校验完成后，超过 154 秒仍未返回，而同期其他进程仍可处理请求。这与上述资源逐步被占用的情况一致。

现有日志无法精确确认当次请求最终卡在 Embedding 还是 Milvus，但可以确认问题位于权限校验之后的知识检索链路。两项高风险环节均已纳入整改。

## 三、影响说明

- 首先影响知识检索接口的响应速度和成功率。
- 慢请求持续累积后，会占用后端工作进程，进一步影响其他业务接口。
- 容器仍显示正常运行，常规存活检查不一定能及时发现该问题。
- 本次问题属于请求处理阻塞，目前没有发现数据丢失或数据损坏的证据。

## 四、已完成整改

| 整改措施 | 解决的问题 |
|---|---|
| 将 Embedding、Milvus 等核心调用改为异步处理 | 避免单个慢请求长期阻塞后端 |
| 增加整体及分环节超时 | 保证异常请求在规定时间内结束 |
| 增加并发限制 | 防止高峰流量集中压垮模型和向量库 |
| 复用 Milvus 连接和已加载资源 | 减少重复连接及重复加载开销 |
| Milvus 与 Elasticsearch 并行检索 | 缩短正常请求处理时间 |
| 增加服务降级 | 单个检索服务异常时，尽可能使用另一服务返回结果 |
| 文件链接生成增加超时和隔离 | 文件存储异常不再拖慢整个检索请求 |

整改后，单个外部服务响应缓慢时，不会再无限占用后端资源；当请求超过系统设定时限时，会明确返回超时结果。

## 五、当前进展

- 代码整改已经完成。
- 相关自动化回归测试共 55 项，全部通过。
- 已覆盖慢请求不阻塞、超时控制、并发限制和检索服务降级等场景。
- 尚需在生产环境部署后，通过持续运行和并发压测确认最终效果。

## 六、下一步安排

1. 部署整改版本并确认网关与后端超时时间配置一致。
2. 对知识检索接口进行持续并发压测，重点观察是否还会出现“运行时间越长、响应越慢”的情况。
3. 增加 Embedding、Milvus、Elasticsearch 各环节的耗时监控和超时告警。
4. 上线后持续观察接口成功率、响应时间和后端在途请求数量。

## 七、总体结论

本次问题的根本原因是知识检索链路中的同步等待、超时保护不足和并发缺少约束。外部服务偶发变慢后，请求逐步堆积，最终引发 Bisheng 后端整体响应能力下降。

目前已从异步处理、超时控制、并发保护、连接复用和服务降级五个方面完成整改。代码验证结果正常，下一步重点是完成生产部署后的持续压测和运行观察。
