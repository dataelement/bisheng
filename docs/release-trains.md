# 发版批次与分支角色

> 配套阅读:`docs/cofco-merge-playbook.md`(合并顺序与必冲突清单)。两份都只在中粮线
> (`feat/cofco-909-*`)上维护,主版本分支上看不到。分工:手册讲「**怎么合**」,
> 这份讲「**合给谁、什么时候发**」。
>
> 这份文档存在的原因是 2026-09-15 的一次事故:分支名读反了,一条正在发版的分支被
> 快进到了下一批,开放 API 的提交连同授权模型一起进了客户包。详见文末。

---

## 1. 一句话规则

> **`-batch1` 是「本期正在发的」,不带后缀的是「下一批」。**

| 分支 | 角色 | 含新开放平台功能 |
|---|---|---|
| `feat/3.0.0-beta1-batch1` | 主线,**本期发版** | 否 |
| `feat/3.0.0-beta1` | 主线,**下一批** | 是 |
| `feat/cofco-909-3.0.0-beta1-batch1` | 中粮线,**本期发版** | 否 |
| `feat/cofco-909-3.0.0-beta1` | 中粮线,**下一批** | 是 |

「含新开放平台功能」指 09-15 那批新提交(免登录链接、v2 错误码等)。
**服务账号 / API Key / PAT 的代码本身两批都有**,客户手上一直就有,
只是开关默认值不同。不要拿「`open_api/` 目录在不在」判断分支属于哪一批。

两条 `-batch1` 对应发一批,两条不带后缀的对应发下一批。
**客户手上同时存在两个版本,这是有意的。**

### 原来的 `-test` 后缀已废弃

老的两条 `feat/*-test` 在 09-15 被污染,已于 2026-09-17 删除,删除前打了归档 tag:

```
archive/3.0.0-beta1-test-20260915
archive/cofco-909-3.0.0-beta1-test-20260915
```

归档 tag 只用于回看事故现场,**不要拿它打包发版**。

之所以改名,是因为 `-test` 读起来像「测试用、比较新」,实际它是**更保守、更靠前发布**
的那条 —— 名字是反的,09-15 就是这么读错的。`-batch1`(第一批)没有这个歧义。

## 1.1 版本怎么往下迭代

```
batch1 上线  ──▶  下一批上测试环境  ──▶  再下一个版本从下一批拉新分支
                        │                            ▲
                        └────── 下一批修的 bug ───────┘
```

**下一批永远是本期的超集**:本期的功能全都要合进下一批,客户升级时不能少东西。
再下一个版本从「下一批」拉分支开发;在「下一批」上修的 bug 再合进新拉的分支,
如此滚动。任何时刻同时存在的两条线,永远是「正在发的」和「下一批」。

---

## 2. 两条铁律

**第一,`-batch1` 落后于不带后缀的那条,是有意的,不是掉队。**

`git rev-list --left-right --count A...B` 显示 `-batch1` 落后几十个提交、且没有独有提交时,
**那不是「停在原地需要追上」**,而是「这一批还没到」。看到这个数字不要快进。

**第二,永远不要把不带后缀的合进 `-batch1`。**

方向只有一条:

```
feat/3.0.0-beta1-batch1  ──→  feat/3.0.0-beta1          (本期 → 下一批)
        │                            │
        ↓                            ↓
feat/cofco-909-…-batch1  ──→  feat/cofco-909-…          (本期 → 下一批)
        主线 → 定制线,同层级横向
```

反过来合 = 把下一批的功能提前塞进正在发的包里。

## 3. 改一个 bug 该往哪落

**通用缺陷**(两批都要):落在 `feat/3.0.0-beta1-batch1`,然后

```
3.0.0-beta1-batch1  →  cofco-909-3.0.0-beta1-batch1   (本期两条线)
3.0.0-beta1-batch1  →  3.0.0-beta1                  (带给下一批)
cofco-909-…-batch1  →  cofco-909-3.0.0-beta1        (带给下一批)
```

**只有下一批需要的功能**:直接落 `feat/3.0.0-beta1`,不要碰 `-batch1`。

**中粮定制**:落 `feat/cofco-909-3.0.0-beta1-batch1`,只在中粮两条线之间流动,
**永不回流主版本**(见合并手册 §1)。

## 4. 授权模型跟着批次走(最容易炸的一条)

F048 的 OpenFGA 授权模型**版本号写在代码里**,两批的值不同:

| 批次 | 模型 | 校验和 |
|---|---|---|
| 本期(`-batch1`) | `f048-v4-contextual-departments` | `1898712a…` |
| 下一批(不带后缀) | `f048-v5` | `2ed5c834…` |

**把下一批合进本期,模型会跟着变成 v5**,而客户环境登记的还是 v4 →
启动直接报 `authorization_model_migration_required`,**所有走权限的接口 500**。
2026-09-15 就是这么炸的。

### 判断故障时先搞清楚这一点

**真正的事实源是 OpenFGA store,不是代码,也不是数据库。**
服务启动时取 store 里**最新**的那个模型(`discovery.py` 把模型 ID 排序后取最后
一个),拿它的校验和跟代码算出的比。所以:

- 装错版本 ≠ 模型被改了。**光部署一个新镜像,不会往 store 里写任何模型** ——
  生产路径 `allow_bootstrap=False`,自动写模型只在非生产 + `force_write_model`
  时发生。
- 模型只有跑 `publish_authorization_model_change.py --apply` 才会变。
- 所以**装错版本的环境,退回对的镜像就好了,不需要任何脚本**。

2026-09-16 客户环境就是这个情况:store 和数据库自始至终都是 v4,只有镜像里的
代码是 v5,换回 v4 镜像即可,零脚本。**先查 store,再决定动什么。**

### 真发布过才是麻烦事

模型一旦发布出去就是**单向**的:OpenFGA 的模型只能追加、删不掉,而运行时又认
最新的那个。所以数据库怎么改都没用,启动还是会挑到新模型 —— 想退回旧模型,得把
旧模型内容**重新写一遍**让它变成最新的,而现成的发布脚本会因为"同一个 checksum
只能绑一个 model_id"直接拒绝。没有回退命令不是少写了个命令,是结构上回不去。

发布前先想清楚,别指望"不行就回滚"。

### 只读探测

拿不准某个环境是什么状态,先跑只读探测,别猜:桌面那份
`客户环境-F048权限诊断-给对面agent.md` 里有自包含脚本(纯标准库、只发 GET),
会打印 store 里每个模型的校验和并判定版本。已知校验和对照:

| 校验和 | 版本 |
|---|---|
| `1898712a…` | `f048-v4-contextual-departments`(本期) |
| `b6646a77…` | `f048-v4`(F053 服务账号版,**同名不同物**) |
| `2ed5c834…` | `f048-v5`(前两者合并版) |

合并前后都查一次:

```bash
git show <branch>:src/backend/bisheng/core/openfga/authorization_model_f048.py | grep '^MODEL_VERSION'
```

模型确实要升时的处置见合并手册文末「部署提醒」。

## 5. 给客户的镜像不要用分支名

CI 对每个 `feat/*` 分支构建同名镜像(`/` 换成 `_`),**每次推代码都会重建同一个 tag**。
所以分支 tag 指向的内容随时在变:

- 客户以为「换回上个版本」,拉到的其实是重建过的新内容
- 真出问题时没有可回退的坐标

**客户环境一律用日期 tag**(`v3.0.0-cofco-0916` 这种),内容固定;实在要精确到位就用镜像 digest。
分支 tag 只给我们自己的测试机用。

## 6. 附:2026-09-15 那次事故

`feat/3.0.0-beta1-test` 当时落后 `feat/3.0.0-beta1` 73 个提交且没有独有提交。
我(Claude)判断成「它只是停在原地」,快进拉平了两条线,`cofco-909-3.0.0-beta1-test`
也照此处理。

后果:

- **20 个开放 API 提交**(服务账号 / API Key / PAT / 免登录链接 / v2 错误码)进了本期分支
- 授权模型从 `f048-v4-contextual-departments` 变成 `f048-v5`
- 客户拉到重建后的分支镜像,启动即 `authorization_model_migration_required`,
  换回「上一个版本」也无效 —— 那个 tag 的内容已经不是原来的了

恢复:从快进前的提交另开干净分支
(`feat/3.0.0-beta1-batch1` ← `75455c572`,`feat/cofco-909-3.0.0-beta1-batch1` ← `857fababa`),
没有强推已被他人使用的共享分支。

**教训**:分支落后不等于该追平。动任何一条正在发版的分支之前,先确认它属于哪一批。
