> **本文档定位 — 现状快照（Why this How）**

**关联**: [spec.md](./spec.md) · [tasks.md](./tasks.md)

**最后更新**: 2026-07-24

---

## 1. 目标与非目标

- **目标**：把"添加公众号信息源失败"这条路径从"报错吓人 + 页面状态说谎 + 无法重试"，改成"说清问题 + 给出获取正确链接的引导 + 原地可改可重试"。
- **非目标**：不改后端识别能力与接口语义；不动网页 URL 爬取路径的反馈；不做图文教程页。

---

## 2. 关键约束

- 遵循 `docs/constitution.md` C1–C7 与 `src/frontend/client/AGENTS.md`（Recoil / react-query v4 / shadcn / `~/` / 命名导出 / 单文件 ≤600 行 / 三语 i18n / 品牌色走主题变量不硬编码）。
- **纯前端**：接口、错误码、后端行为全部不变——所有改动落在"同样的接口返回，前端怎么表现"。
- 全局请求层对失败会**自动弹顶部红色 toast**；本特性要求公众号添加路径不出红条，因此必须在该请求上关掉全局错误提示、由组件自己接管失败表现。
- 403 由响应拦截器统一处理，业务代码不得加 403 分支（AGENTS.md 硬规则）。

## 3. 方案对比与选定

### 决策 1：把"失败"做成独立界面状态（本特性核心）

- **现状根因**：添加面板显示什么，完全由「当前搜索关键字 + 搜索结果条数」**推导**出来——关键字是一条公众号链接且没有匹配结果时，界面就渲染"正在添加中"。失败弹窗只是叠在上面的一层，关掉它并不改变推导结果，所以页面**永远停在"正在添加中"**。
- **备选**：
  - A. 让失败成为界面状态的一个独立分支，不再由关键字推导；关闭弹窗即进入"请修改链接"状态。
  - B. 保持推导模型，在关弹窗时顺手把关键字清空。
- **选定**：A
- **原因**：B 能让"添加中"消失，但会把用户输入的链接一起清掉——与 AC-04「保留原链接」直接冲突；而且推导模型本身就是这个 bug 的温床，下次加状态还会重蹈覆辙。A 把"界面处于什么阶段"变成显式事实。
- **何时该重新考虑**：无（这是把隐式推导改为显式状态，方向单一）。

### 决策 2：重试由"提交动作"驱动，而不是"关键字变化"驱动

- **现状根因（第二个 bug）**：识别请求是在"关键字变化"时被动发起的。用户没改链接就再按回车 → 关键字没变 → 什么都不发生。叠加内部还有一层"同一链接正在处理中"的去重标记，即使强行重跑也会被拦掉。
- **选定**：回车＝一次显式提交，直接发起识别；每次提交前重置上一轮的处理标记与进行中标识。
- **原因**：这是 AC-05（未改链接也能重试）成立的唯一自然做法；同时把"防重复"的语义收敛到"同一次提交进行中不重复发"，而不是"同一个链接永远只处理一次"。
- **注意**：既有的输入防抖语义要保留（识别进行中重复回车不重复发起，AC 边界要求）。

### 决策 3：失败提示只保留中央弹窗

- 关闭该请求的全局错误 toast，由组件按 PRD 文案渲染弹窗。**不改全局拦截器**——只在这一个请求上选择不走全局提示，避免影响其它业务的错误反馈。
- 另注意既有代码里存在一条"异常分支拿到了错误码就不弹失败弹窗、只有顶部 toast"的路径，会造成**静默卡死**（页面停在添加中且没有任何弹窗）。改造后所有识别失败路径统一进失败状态，不留这条缝。

### 决策 4：帮助入口出现在两个位置

- PRD「优化目标 1」要求未收录界面**和**关闭失败弹窗后的页面都能拿到复制链接引导，因此帮助入口做成一个可复用的小组件，在两个界面状态下各渲染一次；悬停展开、移出（含浮层区域）收起。

## 4. 系统现状（接手必读）

### 4.1 交互流程

`输入框回车 → 判断输入形态 → 分三条路 → 结果反馈`

- **UI 入口**：`client/src/pages/Subscription/CreateChannel/AddSourceDropdown.tsx`（挂载于 `CreateChannelDrawer.tsx` 的创建/编辑频道抽屉）。
- **状态逻辑**：`client/src/pages/Subscription/hooks/useSourceManager.ts` —— 当前用"关键字 + 结果数"推导界面阶段（公众号链接处理中 / 网址待确认爬取 / 非网址且无结果=未收录）。**本特性的主要改造点。**
- **三条路**：
  1. 输入是**公众号文章链接** → 进入"正在添加中" → 调"添加公众号信息源"接口 → 成功入列 / 失败弹窗。
  2. 输入是**普通网址** → 展示"确认爬取 / 暂不爬取" → 走爬取队列（`useCrawlQueue.ts` + `CrawlQueuePanel.tsx`，**本特性不动**）。
  3. 输入是**普通文字且无结果** → "系统暂未收录"提示（**帮助入口加在这里**）。
- **失败弹窗**：当前是 `AddSourceDropdown.tsx` 里的一个 AlertDialog（标题"频道添加失败"），本特性改为 PRD 指定文案与按钮。
- **全局错误 toast**：`client/src/api/request.ts` 的响应拦截器在业务失败时统一弹红条——公众号添加请求需选择不走它。

### 4.2 关键数据结构 / 字段约定

| 契约 | 形式 | 说明 |
|---|---|---|
| 界面阶段 | 显式状态枚举：`空闲 / 识别中 / 识别失败待修改 / 未收录 / 待确认爬取` | 取代原先由关键字推导的隐式模型（决策 1） |
| 失败文案 | 标题「公众号文章链接未识别」；说明「暂时无法读取该链接。请确认链接完整、页面可以正常访问。」；主按钮「返回修改」 | PRD 指定，逐字使用，走 i18n |
| 返回修改后页面文案 | 「请检查并修改公众号链接。修改完成后，按回车重新识别。」 | PRD 指定 |
| 帮助浮层文案 | 「点击文章右上角「···」，选择「复制链接」，或选择「在浏览器打开」后复制地址栏中的链接。」 | PRD 指定 |
| i18n | 三份语言包（zh-Hans / en / ja），嵌套命名空间 | AGENTS.md 硬规则 |

### 4.3 关键模块职责

| 模块 / 文件 | 职责 | 不做什么 |
|---|---|---|
| `useSourceManager.ts` | 界面阶段状态机、发起识别、失败态维护 | 不直接渲染 UI；不处理网页爬取队列 |
| `AddSourceDropdown.tsx` | 按阶段渲染面板、失败弹窗、帮助入口 | 不自己判断错误码语义 |
| 帮助入口组件（新） | 悬停展开指引浮层 | 不含业务逻辑 |
| `useCrawlQueue.ts` / `CrawlQueuePanel.tsx` | 网页 URL 爬取队列 | 本特性不动 |

## 5. 已知坑 / 反直觉事实

| # | 反直觉事实 | 如果不知道会怎样 | 在哪处理 |
|---|---|---|---|
| 1 | 面板显示"正在添加中"**不是**因为有请求在跑，而是"当前关键字是个公众号链接且搜索无结果"推导出来的 | 会去找"哪里没把 loading 关掉"，但根本不存在这样一个 loading 标志——找不到就会怀疑是异步竞态 | 决策 1：改成显式状态 |
| 2 | 同一条链接再次回车**不会触发任何事**：关键字没变 → 依赖关键字的副作用不重跑；即使重跑，还有一层"该链接正在处理中"的去重标记拦截 | 会误以为是接口被限流或防抖时间太长，白调参数 | 决策 2：提交驱动 + 每次提交重置标记 |
| 3 | 失败路径存在**两种不同表现**：一种弹失败弹窗+红条，另一种只有红条不弹窗（取决于能否从异常里取到错误码），后者表现为页面完全静默卡死 | 复现时会觉得"有时弹窗有时不弹"像玄学，难以稳定复现 | 决策 3：统一收敛所有失败路径 |
| 4 | 红色报错来自**全局请求拦截器**，不是这个组件写的 | 会在组件里到处找 toast 调用却找不到，或者反过来去改全局拦截器影响所有业务 | 决策 3：只在该请求上关掉全局提示 |
| 5 | 用户"点暂不添加"才会真正重置状态机——这是当前唯一的正常退出路径 | 会以为关弹窗等价于取消，从而漏掉退出时的状态重置 | 关闭弹窗与取消统一收敛到同一套重置逻辑 |

## 7. 测试与可观测

- **手动验证主路径**：
  1. 输入公众号名称（一个必然未收录的）→ 出现"暂未收录" + 帮助入口 → 悬停出浮层 → 移出收起（AC-01/02）。
  2. 输入一条无效的公众号链接 → 回车 → **只**出中央弹窗、无顶部红条（AC-03）。
  3. 点「返回修改」→ 页面显示"请检查并修改链接"、链接还在、"暂不添加"还在、帮助入口在、无"正在添加中"（AC-04）。
  4. **不改链接**直接回车 → 重新识别 → 再次出失败弹窗（AC-05，这是本特性最关键的回归点）。
  5. 改成有效链接 → 回车 → 正常添加成功（AC-06，成功路径无回归）。
  6. 切 en / ja 复查所有新文案（AC-07）。
- **回归重点**：网页 URL 爬取路径（确认爬取/队列面板）与公众号名称命中路径必须完全不受影响。

## 8. 后续改进 / 不打算做的事

- **失败原因细化**：受限于上游返回粒度，本期用统一文案。后端若能区分失败类型，可再分文案。
- **图文/动图教程**：PRD 附了动图演示，但本期只做文字指引浮层（避免引入静态资源与体积）。
- **爬取路径的失败反馈**：已有独立队列 UI，本期不合并两条路径的反馈风格；若后续要统一，应一并重构。
