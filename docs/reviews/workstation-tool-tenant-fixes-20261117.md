## 工作台配置

最新工作台基础配置页没有模型配置字段，但 `GET /api/v1/workstation/config/daily` 经 `get_daily_chat_config_with_meta()` 仍调用 `LLMService.get_workbench_llm()`。后者按执行用途校验整份模型默认配置的资源引用，引用异常就阻断基础配置加载。

保存也有同样问题：`update_daily_chat_config()` 写入基础配置之后调用执行用途的 `get_daily_chat_config()` 回读；模型引用异常可能让已完成写入的操作在响应阶段报错。

修复：

1. 管理用途的读取继续使用当前租户配置解析、继承投影、工具同步及原有来源元数据，不读取执行用途的模型默认配置。
2. 管理响应把历史遗留的 `models` 字段置为 `None`，与现有保存时忽略该字段的规则一致；不修改独立的模型默认配置。
3. 保存回读复用管理用途的读取流程。
4. `get_daily_chat_config()` 等运行时入口不变，模型引用无效仍拒绝执行；配置存储异常仍原样传播。

## 子租户工具列表

用户提供的请求为 `GET /api/v1/tool?is_preset=2&action=visible`，错误为 `tenant_id and current_tenant_id disagree`。

`ToolServices.get_tool_list()` 把权限身份适配到服务端当前管理租户时使用 `dataclasses.replace(actor, current_tenant_id=current_tid)`。`PermissionActor` 的实际数据字段是 `tenant_id`，`current_tenant_id` 只是自定义构造器兼容别名及只读属性。`replace` 自动携带旧的正式字段，再传入新别名，便在 Root 身份、子租户管理目标不同的情况下触发构造器的一致性检查。

修复使用 `replace(actor, tenant_id=current_tid)`。不修改兼容构造器、不取消一致性检查、不修改登录用户或上下文原对象；原有身份类型、超级管理员标志、租户管理员集合、数据范围均保留。可见对象枚举、当前租户数据库候选约束和逐对象动作过滤保持原样。
