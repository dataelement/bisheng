>
> 本 Feature 把平台工作台里「直接与模型对话」的**日常模式会话**（选模型、可选挂知识库、可选开平台工具、多轮）以 **OpenAI Responses 契约子集**开放给自建系统。它站在 F049 的凭据地基与 F050 的身份传递之上，是伴生 PRD 场景二（代表员工提问、回工作台续问）在对话能力上的完整形态。它**不是**模型协议裸透传（F051）：本面建平台会话、留历史、可挂知识库与平台工具、在平台 UI 可见。

## 1. 用户故事

作为 **自建业务系统的集成方（如在企业 OA 内嵌问答入口）**，
我希望 **用一把服务账号密钥、按 OpenAI Responses 的标准写法代表当前员工发起对话、多轮续接、挂上员工有权访问的知识库与平台工具**，
以便 **不为平台学一套私有会话协议、不自己拼装权限过滤，员工在 OA 里问到的与在 BiSheng 里问到的完全一致**。

作为 **被代表的员工**，
我希望 **在自建系统里发起的对话，回到 BiSheng 工作台就能看到同一个会话并继续追问**，
以便 **对话不因入口不同而割裂，两个入口只是同一段工作的两个窗口**。

作为 **面向外部访客提供应用的开发方（场景三）**，
我希望 **以服务账号身份为每个访客开会话、用外部标识把访客彼此分开，访客只在管理员授予该服务账号的知识库范围内得到回答**，
以便 **访客不被平台的用户权限体系卡住，同时也不会看到任何超出该应用授权的内容**。

作为 **租户管理员**，
我希望 **通过与其它开放 API 同一张权限位清单授予「日常模式会话」能力、在服务账号授权页决定它能挂哪些知识库、在审计里同时看到哪个系统调的和以谁的名义调的**，
以便 **对话能力的开放与其它开放能力同一套治理，不多一套后台、不少一份追溯**。

作为 **调用方开发者**，
我希望 **传错了字段、用错了工具类型、传了本版不支持的能力时得到明确报错**，
以便 **不会以为工具或知识库已经生效、实际跑的是无工具对话；也不会因为按 OpenAI 习惯打开 `background` 就被静默切到另一种运行模式**。

## 2. 验收标准

> AC 编号在本特性内唯一。与伴生 PRD §五验收标准的对应关系在括号中标注（如 `↔伴生 AC-34`）；伴生未单列 AC 的需求以章节号标注（如 `↔§4.6.3`）。
> 错误码在此仅作为可观测的对外行为引用（`26015` / `26017` / `26010` / `26016` 取自伴生附录 C），其定义与归属写在 design.md。「Responses 对象 / 事件」指官方 OpenAI Responses 契约中的 response 对象、输出项与流式事件形状；本 Feature 已实现的子集清单以对外文档为准（AC-10）。
> **「明确错误」判据（本 spec 全部拒绝 / 不可用分支统一按此验收）**：4xx 状态 + 平台错误码（可被调用方程序化区分）+ 指明出错项（字段名 / 附件标识 / 模型名 / 工具项 / 未开放的能力名）；不静默忽略、不部分接受、不 5xx。仅归属类校验例外——按 AC-21 一律 404 且形状不区分「不存在 / 不属于你」。

### 2.1 端点与契约

- **AC-01** — THE SYSTEM SHALL 提供 `POST /api/v2/responses`（下称 `POST /responses`）：接受 OpenAI Responses 契约子集的请求、以 Responses 对象模型返回；本版只承接 `bisheng_mode: "chat"`（缺省即为 `"chat"`）的日常模式 × `background: false`（缺省即为 false）的同步执行——两者是**两条独立的轴**（能力 / 传输，伴生 D11），各自缺省、各自校验、各自拒绝；同时支持流式（`stream: true`，Responses 事件流）与非流式（返回完整 response 对象）两种返回方式，缺省按 Responses 契约为非流式。（↔§4.6.3 端点清单 / D9；伴生 AC-36；§4 决议-9）
- **AC-02** — WHEN 请求未携带 `previous_response_id`, THE SYSTEM SHALL 创建一个新的平台会话并在其中生成本轮 response；WHEN 携带 `previous_response_id` 且它指向该会话**最新留存**的 response, THE SYSTEM SHALL 在该 response 所属的**同一会话**中续接本轮（可见此前轮次上下文），且返回对象回显该值；IF 它指向该会话的历史（非最新）response, THEN THE SYSTEM SHALL 返回 400 明确错误并指明该 id 与当前最新 id——平台会话线性追加、不支持分叉。多轮对话**只**经此机制续接，调用方无需也不得回传历史消息（AC-09）。（↔伴生 AC-36「`previous_response_id` 可正确续接同一会话」；§4.2.4「多轮对话由 previous_response_id 续接」；§4 决议-3）
- **AC-03** — THE SYSTEM SHALL 提供 `GET /api/v2/responses/{response_id}`：返回经 `POST /responses` 创建并**留存**的终态 response 对象（completed / incomplete；失败轮次不留存，AC-16 / 18），与该轮非流式返回的对象一致；response_id 为**不透明标识**（不递增、不可由顺序或平台内部标识推得、不可枚举）；平台工作台内产生的轮次不经本端点暴露。（↔§4.2.4「`GET /responses/{id}` 是唯一保留的读动作，并入 `chat:invoke`」；§4.6.3 端点清单）
- **AC-04** — THE SYSTEM SHALL 使 `POST /responses`（非流式）与 `GET /responses/{id}` 的响应体可被 **OpenAI 官方 Python SDK 当前主版本**的 response 对象反序列化而不报错、`stream: true` 的事件流可被该 SDK 的流式迭代器消费——**含平台原生扩展项（平台工具调用、知识库引用等）出现在输出中的情形**；该 SDK 以 base URL + 密钥直调即可，不需要平台专有 SDK；验收所绑定的 SDK 主版本号写入对外文档。（↔伴生 AC-36）
- **AC-05** — WHEN 请求以对外文档约定的形式选择知识库（可挂多个；模式 D 下可含被代表用户的个人知识库）, THE SYSTEM SHALL 在生成时检索这些知识库并把引用以 Responses 注解（annotations）形式随文本输出返回；可挂范围 = 执行身份被授权可见的知识库，过滤强度（含文件级）与该身份在平台工作台内挂同一知识库对话时**集合相等**；IF 所选知识库超出执行身份的授权, THEN THE SYSTEM SHALL 返回业务模块既有的资源权限错误（与缺权限位的 403 可区分）并指明该知识库；IF 模式 S 下启用个人知识库, THEN THE SYSTEM SHALL 返回 400 明确错误（错误码引用、指明「个人知识库」项：服务账号无个人知识库）而不静默按空集执行。（↔§4.6.3「可选挂知识库」/ 冲突表「引用走 annotations」；F049 AC-36 同形；伴生 AC-12 取向）
- **AC-06** — WHEN 请求在 `tools` 中以 `{"type": "bisheng_tool", "tool_key": ...}` 声明平台工具, THE SYSTEM SHALL 使这些工具在本轮生效（服务端执行）、可用范围 = 平台工作台配置对执行身份开放的工具；IF `tools` 中出现无法识别的 `type`（含 OpenAI 的 `function` 等本版不支持的客户端执行工具类型）或不在可用范围内的 `tool_key`, THEN THE SYSTEM SHALL 返回 400 明确错误（错误码引用、指明该工具项），**不得静默忽略后按无工具对话执行**。（↔伴生 AC-34；§4.6.3 冲突表「`tools` 同名不同义」；§4 决议-6）
- **AC-07** — THE SYSTEM SHALL 要求 `model` 必填、取值为平台工作台配置中对执行身份可用的对话模型名称；名称基准与跨服务商同名歧义的处置与 F051 一致（模型管理页原名精确匹配、歧义时拒裸名并给出限定名、不取默认）；IF 模型不在可用范围（不存在 / 已下线 / 不在工作台配置内 / 不属于本租户）, THEN THE SYSTEM SHALL 返回 4xx 明确错误（错误码引用、指明模型名与原因），对其它租户的模型按「不存在」处理。（↔§4.6.3「选模型」；F051 AC-11–13 同源；§4 决议-8）
- **AC-08** — WHEN 请求携带 `instructions`, THE SYSTEM SHALL 把它作为本轮的调用方指令**叠加于**平台工作台既有系统提示词之上生效——不替换、不关闭平台提示词；未携带时按平台既有提示词执行。（§4 决议-7）
- **AC-09** — THE SYSTEM SHALL 使 `input` 接受的输入项类别只有两类：**本轮用户文本**、**已上传附件的引用**（经 `POST /workbench/files` 所得标识）；拒绝清单：历史角色项（assistant / system 等）、内联文件数据、外链文件 URL、其它本版不支持的项类型——IF `input` 含拒绝清单中的任一项, THEN THE SYSTEM SHALL 返回 400 明确错误（错误码引用、指明该项），不静默丢弃、不部分接受。各类别的具体形状以对外文档为准。（§4 决议-5 / 决议-11）
- **AC-10** — THE SYSTEM SHALL 随本 Feature 交付对外接口文档：显式声明本面为 Responses **子集**、逐项列出已实现的请求字段 / 输出项类型 / 事件类型 / 原生扩展 / 拒绝清单，并**分别**说明两条轴的字段语义：`bisheng_mode`（BiSheng 原生扩展，`"chat"` = 日常模式、`"task"` = 任务模式·灵思，缺省 `"chat"`，本版仅前者）与 `background`（OpenAI 原义，false = 同步、true = 异步，本版仅前者）——文档须明确二者**互不蕴含**，不得表述为「`background` 用于选择模式」；F050 AC-15「`X-Bisheng-End-User` 语义声明原样写入对外文档」在本面文档同样生效；说明既有 `POST /api/v2/assistant/chat/completions` 为 Chat Completions 形态、本次不动、两种风味各自适用范围。（↔§4.6.3 兼容边界 / 已知不一致；F050 AC-15；§4.6.3「关键收益」）

### 2.2 入参清洗与拒绝

- **AC-11** — THE SYSTEM SHALL 只接受对外文档列出的已实现字段；契约之外的字段（不论是 OpenAI Responses 已有字段还是完全未知字段）一律返回 400 明确错误（错误码引用、指名字段），**不得静默忽略**。「接受但不生效」档只容忽略后不改变调用方可观察行为的字段且**必须在本 spec 枚举——本版该清单为空**（不存在任何被接受却不生效的字段；将来要加入须先修订本条），无法枚举的字段一律 400。（↔§4.6.3「入参必须清洗」；§4 决议-5）
- **AC-12** — THE SYSTEM SHALL 对以下请求形态明确返回 400 并指明原因、不静默降级：`store: false`（平台会话机制不支持不留痕，不留痕的模型调用应走 `model:invoke` 面）；OpenAI 的 `user` 字段（终端用户标识只经 `X-Bisheng-End-User` 头传递、不设第二来源）；采样与生成参数（temperature / top_p / max_output_tokens 等，本版由平台工作台模型配置决定）；任务模式专属字段（如技能选择）；`background: true`（AC-25）；`bisheng_mode: "task"` 及该枚举外的任何取值（AC-37）。（§4 决议-5 / 决议-13；§4.6.3 冲突表「有状态 vs 无状态」）
- **AC-13** — THE SYSTEM SHALL 使对外契约不出现、不要求任何平台前端专用或已废弃的内部字段，也不存在任何平台内部会话标识——多轮只以 `previous_response_id` 表达。（↔§4.6.3「入参必须清洗：前端专用或已废弃字段一律不进对外契约」）

### 2.3 事件流转译

- **AC-14** — WHEN `stream: true`, THE SYSTEM SHALL 以 Responses 流式事件**边生成边推送**（不缓冲整段后一次性返回）；每类平台内部事件对应一个**可区分的 Responses 事件**、事件流中不出现平台内部事件名；每次执行以且仅以**一个终态事件**（completed / failed / incomplete）收尾，事件顺序符合 Responses 契约。（↔§4.6.3「事件流同理」；D9）
- **AC-15** — THE SYSTEM SHALL 使思考过程、平台工具的调用与结果、知识库引用在输出中各有**可区分的承载**：知识库引用以 Responses 注解（annotations）随文本输出返回，其余以输出项承载（各自的类型与字段属 design、以对外文档为准）；平台原生扩展的输出项与工具类型一律使用 BiSheng 自有命名，**不冒用** OpenAI 内置工具或对象的名称与语义。（↔§4.6.3 冲突表「思考过程与引用无处安放」；§4 决议-6）
- **AC-16** — IF 生成过程中模型 / 工具 / 检索失败或上游中断, THEN THE SYSTEM SHALL **流式**下先发 error 事件、再以失败终态事件收尾并关闭连接、不挂起；**非流式**下返回明确错误响应（错误码引用、指明失败环节），**不返回带失败状态的 response 对象**——失败只有一种真相；失败轮次不留存（AC-18），其 id 的 `GET` 按 AC-21 处理，该会话仍可以其**最新留存**的 response 续接。
- **AC-17** — THE SYSTEM SHALL 使非流式返回的 response 对象与同一请求流式执行时由事件流聚合出的最终对象**内容一致**（同一输出项集合、同一状态、同一用量口径）。（§4 决议-9）
- **AC-18** — IF 一轮执行失败或调用方在流式过程中断开连接, THEN THE SYSTEM SHALL 使该轮**不在会话历史留下半条消息**（要么以完整消息留存并成为会话最新 response、要么不留任何痕迹）、不留下永久 in_progress 的记录、同一会话不因此被锁死、后续可以其最新留存的 response 续接。

### 2.4 身份与会话隔离

- **AC-19** — WHEN 以模式 S（密钥不持 `delegate` 且未携带 `X-Bisheng-On-Behalf-Of`，F050 AC-02）调用 `POST /responses`, THE SYSTEM SHALL 使会话归属服务账号并按 `X-Bisheng-End-User` 分区；F049 AC-25（模式 S 会话不进资源归属人或任何自然人的会话列表，定义 6 边界 a）、F050 AC-11（外部标识不改变任何权限判定与可见范围）与 F050 AC-13（未传头记 WARN、不阻断、分区键为空）在本端点上同样生效。（↔§4.6.3 身份表；伴生 AC-43）
- **AC-20** — WHEN 模式 D（持 `delegate` 且传 `X-Bisheng-On-Behalf-Of`，经 F050 五道准入）调用 `POST /responses`, THE SYSTEM SHALL 使会话归属**被代表用户**、以其权限基准执行（模型 / 知识库 / 工具 / 个人知识库范围同其本人在工作台所见）；该会话在被代表用户的 BiSheng 工作台会话列表中可见、可在工作台继续追问；工作台侧新增的轮次同样成为该会话的**最新** response——此后 API 续接以会话最新为准（AC-02，指向旧 id → 400）；本轮上传的附件同样归属该用户。会话归属规则本身由 F050 AC-38 拥有，本条承接其端到端验收。（↔伴生 AC-32；§4.6.3 身份表；定义 6「与模式 D 并存时以被代表用户为准」）
- **AC-21** — WHEN `GET /responses/{id}`、`previous_response_id` 或 `input` 中的附件引用所指向的 response / 附件不属于当前调用的会话归属主体——模式 S 下服务账号不一致或 `X-Bisheng-End-User` 分区键不一致（含一方为空、另一方非空）、模式 D 下被代表用户不一致、跨租户、或该 id 不存在 / 未留存——, THE SYSTEM SHALL 一律返回 404 且响应形状不区分「不存在」与「不属于你」（不用 403、不泄漏 response 是否存在）；归属校验以会话归属主体为基准、**不按单把密钥**区分（同一服务账号的不同密钥、同一被代表用户经不同委托密钥视为同一归属）。（↔§4.6.3「外部标识不匹配返回 404」；§4 决议-3）
- **AC-22** — THE SYSTEM SHALL 使本 Feature 三个端点上 F049 的租户上下文规则同样生效（凭据校验通过后一切业务查询按密钥所属租户过滤，F049 AC-07 / §3「凭据校验先于租户上下文」）；会话、附件、response 一律落在该租户内，跨租户不可见（按 AC-21 的 404 处理）。
- **AC-23** — THE SYSTEM SHALL 使 F050 AC-12（模式 S 下外部标识作为会话分区键写入）在本 Feature 两个有会话语义的端点（`POST /responses`、`POST /workbench/files`）上同样生效；本版分区键**不作为任何列举 / 过滤维度、不经任何端点返回，仅用于归属一致性校验**（AC-21 / AC-29）——这是 F050 AC-12「只写不读」在本面的精确化。（↔§4.6.3「仍然要写分区键」；§4 决议-4）
- **AC-24** — WHEN 本 Feature 三个端点被调用（含被拒绝的调用）, THE SYSTEM SHALL 使 F050 AC-35（开放 API 逐调用审计）与 F050 AC-36（模式 D actor / subject 双归属）在本端点上同样生效；本面特有约束：审计不含会话消息正文与附件内容。（↔§4.8.1；伴生 AC-23）

### 2.5 异步分支与不暴露端点

- **AC-25** — IF `background: true`, THEN THE SYSTEM SHALL 返回 400（`26015`）且不创建会话、不执行任何生成、**不静默按同步执行**；该判定**只针对传输方式**，与运行模式无关。（↔伴生 AC-35；附录 C）
- **AC-26** — THE SYSTEM SHALL 为异步分支的两个端点（`POST /responses/{id}/cancel`、`GET /responses/{id}?stream=true&starting_after=N`）在契约文档中留位并标注「随异步分支点亮」；本版调用它们得到 4xx 明确错误（错误码引用、指明未开放的能力名「异步分支」；错误码与 `26015` 同族或复用，归 design），不静默成功、不 5xx、不实现为对同步 response 的伪取消或伪续流；同步分支的对象模型 / 字段 / 事件类型 / 错误形状不为将来点亮异步分支预留任何需要调用方改代码的差异。（↔§4.6.3 端点清单 ⏸ / 「关键收益」；附录 B.1）
> 能力轴（任务模式）的留位与拒绝见 **AC-37**（§2.9）——与本节的传输轴留位并列、互不替代。
- **AC-27** — THE SYSTEM SHALL NOT 提供任何按会话 / 按用户 / 按外部标识列举 response 或会话的端点（含 `GET /workbench/sessions`、`GET /workbench/sessions/{id}/messages`、任何 `GET /responses` 列表形态），也不提供会话反馈写入与消息回填；F049 已关闭的 6 个 `/chat/*` 端点不因本 Feature 复活；不占用 `/conversations` 路径。（↔§4.2.4「不设 `session:*`」/ §4.6.3「会话列表与会话历史查询本次不做」/ 「刻意不叫 `/conversations`」；F049 AC-30）

### 2.6 会话附件上传

- **AC-28** — THE SYSTEM SHALL 提供 `POST /api/v2/workbench/files`（`chat:invoke`）：上传单个会话附件并返回可在 `POST /responses` 的 `input` 中引用的附件标识；该端点为 BiSheng 原生扩展、不作 OpenAI files API 兼容承诺；它是有会话语义的端点：附件的归属主体与 `X-Bisheng-End-User` 分区键（若传）随上传记录（AC-19–23），供 `POST /responses` 引用时做归属一致性校验（AC-29）。（↔§4.6.3 原生扩展表；附录 E.3 复用映射）
- **AC-29** — IF `POST /responses` 引用的附件标识不存在、归属主体不一致、`X-Bisheng-End-User` 分区键不一致（含一方为空、另一方非空）、被代表用户不一致或跨租户, THEN THE SYSTEM SHALL 返回 404（AC-21 口径、形状不区分）且不执行生成；IF 附件尚不可用于对话（如仍在解析）或解析失败, THEN THE SYSTEM SHALL 返回 4xx 明确错误（错误码引用、指明该附件标识与原因）而不静默忽略该附件后继续作答。
- **AC-30** — THE SYSTEM SHALL 使附件的类型白名单、单文件大小上限与每轮附件数量上限**沿用平台工作台既有上传限制**（同一配置、同一判定），超限或类型不允许时返回 4xx 明确错误（错误码引用、指明触发的限制项与限值）；本 Feature 不新增独立的附件配额或计量维度。（§4 决议-11）

### 2.7 权限位与互不蕴含

- **AC-31** — THE SYSTEM SHALL 使本 Feature 三个端点（及留位的两个异步端点）均要求 `chat:invoke`；IF 凭据有效但缺该位（含仅持 `model:invoke` 或其它任何位的密钥）, THEN THE SYSTEM SHALL 返回 403 并指明缺少 `chat:invoke`（F049 AC-04 同形）；`chat:invoke` 与 `model:invoke` **互不蕴含**——反向（持 `chat:invoke` 而无 `model:invoke` 调模型协议面被拒）由 F051 AC-06 承接。（↔§4.2.4 权限位表 / 扩展位表 `model:invoke` 行）
- **AC-32** — THE SYSTEM SHALL 使 F049 AC-01（无凭据 401、无回落路径）/ AC-03（撤销 5 秒内拒绝）/ AC-21（主体停用 / 删除 5 秒内拒绝）/ AC-34（权限评估失败即 5xx、不返回任何结果）在本 Feature 端点上同样生效；被拒时不创建会话、不返回任何数据。（↔INV-27 / INV-28 / INV-30）
- **AC-33** — WHEN 本 Feature 端点上线, THE SYSTEM SHALL 使 F049 权限位清单中既有的 `chat:invoke` 位（伴生 §4.2.4 基础位、始终在清单中；开放前表单标注「端点随后续版本开放」——F049 范围边界）的说明与悬停所覆盖端点指向本 Feature 三个端点与两个留位端点、去除该标注；本 Feature 只拥有该位的**消费端点**，不拥有位的定义、分组或出现与否，不新增第二处位定义。（§4 决议-10；F049 AC-13 / AC-44）
- **AC-34** — THE SYSTEM SHALL 使本 Feature 端点按伴生附录 B.1 声明允许模式 S/D（F050 AC-07 的端点声明）；F050 AC-30（持 `delegate` 漏传头 400 `26016`、不落回模式 S）、F050 AC-14（两身份头并存 400 `26010`）、F050 AC-04（不持 `delegate` 传头 403，伴生 AC-6）在本端点上同样生效——判定与错误由 F049 / F050 的同一鉴权路径给出，本 Feature 不另设第二套判定。（↔INV-27 / INV-30）

### 2.8 审查修订追加（2026-08-17）

- **AC-35** — WHILE 某会话的上一轮尚未收敛到终态（生成中）, IF 再次以该会话的 response 续接（`previous_response_id`）, THEN THE SYSTEM SHALL 返回 4xx 明确错误（错误码引用、指明「会话忙」与该会话当前进行中的 response id）且不并行写入同一会话；上一轮收敛后按 AC-02 正常续接。
- **AC-36** — THE SYSTEM SHALL 使本 Feature 端点属 v2 开放 API 主体、**不受开放能力层部署开关约束**：WHERE 开放能力层未部署, 本 Feature 三个端点（及两个留位端点）对持 `chat:invoke` 的服务账号密钥同样可达、行为无差异（与 F051 AC-28 / F052 / F053 三面「未部署即不可达」不同）；服务账号模块恒在（F049 AC-49）。

### 2.9 能力轴留位追加（2026-08-17，伴生 D11）

- **AC-37** — IF 请求携带 `bisheng_mode: "task"`, THEN THE SYSTEM SHALL 返回 400（`26017`）且不创建会话、不执行任何生成、**不静默退化为日常模式**；IF `bisheng_mode` 取该枚举（`"chat"` / `"task"`）之外的值, THEN THE SYSTEM SHALL 同码返回 400 并指明该字段；WHEN 字段缺省, THE SYSTEM SHALL 按 `"chat"` 执行。`26017`（任务模式能力未开放）与 `26015`（异步传输未开放）**互相独立、不得合并为一个码**：同时触发两者时都不放行，且响应须能让调用方分辨是哪一项未开放，二者将来可各自独立点亮。（↔伴生 AC-50 / D11；附录 C）

## 3. 边界情况

> 只写期望的对外行为；实现层的落点、映射与数据访问细节见 design.md §5。

- **两条轴各自留位，不合并成一个开关**（伴生 D11）：**能力轴** `bisheng_mode`（`"chat"` 日常 / `"task"` 灵思，对应内部 `task_mode`）与**传输轴** `background`（同步 / 异步）正交。合并的后果有取证：内部两个分支（`_task_mode_stream_completion` / `_agent_stream_chat_completion`）**都是同步 SSE 流**，映射不成立；且调用方按 OpenAI 习惯打开 `background` 只为躲网关超时，若因此被切到灵思，拿到的是耗时、计费与输出形态都不同的另一种能力。任务模式的四条技术前置（异步作业语义 / 事件流破坏性单消费者 / 前端编排搬后端 / 并发准入）见伴生 §4.6.3，本 spec 只引不写；本 Feature 对两条轴的全部承诺 = 各自明确拒绝（AC-37 / AC-25）+ 契约留位（AC-26）。将来任一轴点亮都不改同步日常模式契约，且 `("chat", background: true)` 这一格保持可开。
- **`previous_response_id` 跨会话 / 跨用户一律 404、只指向会话最新**（AC-02 / AC-21）：不能用它把两个会话拼起来，也不能用它探测别人的 response 是否存在；平台会话线性追加、不支持分叉——指向历史 response 得到 400 并被告知当前最新 id；模式 D 下员工在工作台续问的轮次同样成为「最新」，API 下一次续接须以之为准。指向 incomplete 的 response 允许续接；失败轮次不留存、不占位（AC-16 / 18）。上一轮生成中再次续接 → 「会话忙」（AC-35），不并行写入。归属校验以**会话归属主体**为基准而非单把密钥：密钥可轮换、可多把，会话不因此失联。
- **End-User 分区键与定义 6 边界 a**：模式 S 会话永远归服务账号、按 `X-Bisheng-End-User` 分区、不进资源归属人的会话列表——归属人机制解决的是「知识库归谁认领」，会话不算资源，否则 §3.3 那个缺陷会被新机制请回来。分区键不改变任何权限判定（F050 AC-11）；本版它**不作为任何列举 / 过滤维度、仅用于归属一致性校验**——`GET /responses/{id}`、`previous_response_id`、附件引用三处都要求分区键与创建时一致（AC-21 / AC-29），这也是场景三里访客 A 拿不到访客 B 的 response 与附件的唯一防线；缺省 WARN 不阻断（F050 AC-13），因为串档的两个成立条件（共享身份 + 可按身份列举会话）本版只具备第一个——**将来若补做任何按用户 / 按外部标识列举会话的端点，必须先把缺省行为改为强制**（原 `26014` 的语义），本 spec 把这条写进 AC-23 / AC-27 的守门口径。
- **契约外字段的处置原则**：白名单式接受 + 契约外 400 指名字段（AC-11）；「接受但不生效」档只容忽略后不改变可观察行为的字段且须在本 spec 枚举——**本版清单为空**。反面教材是 Chat Completions 形态下 `tools` 同名不同义导致的**静默降级成无工具对话**（伴生 §4.6.3 冲突表）——本面宁可拒绝也不静默。`store: false`、`user`、采样参数、`function` 工具、含历史角色的 `input`、内联 / 外链文件均属明确拒绝（AC-06 / 09 / 12）。
- **失败与中断的单一真相**：流式失败 = error 事件 + 失败终态事件收尾、不挂起；非流式失败 = 错误响应、不返回带失败状态的 response 对象（AC-16）；失败或断连的轮次不在会话历史留下半条消息、不留永久 in_progress、会话不锁死（AC-18）；非流式与流式的成功对象一致（AC-17）。合起来保证 `GET /responses/{id}` 只有两种结果——留存的终态对象（completed / incomplete）或 404，不存在第三种状态。
- **附件**：大小 / 类型 / 数量沿用平台工作台既有上传限制（AC-30），不为开放 API 另设一套；只经上传端点获得标识、不接受内联数据与外链 URL（AC-09）——外链拉取是新的出站请求面，本版不开。附件归属跟随会话（模式 D 归被代表用户），不算「资源」、不落归属人名下。
- **模型可用范围与 F051 不必相同**：本面 = 平台工作台配置中启用的对话模型（与员工在工作台里可选的一致），F051 = 模型管理页全部已启用对话模型；两者各按其产品面配置，但**名称基准与歧义规则同源**（AC-07），避免同一个模型名在两面解析成不同服务商。
- **两层判定与 F049 一致**：`chat:invoke` 位（AC-31）∧ 执行身份对具体知识库 / 工具 / 模型的授权（AC-05 / 06 / 07），两层失败可区分；模式 S 下服务账号能挂哪些知识库只由其主体侧授权页决定（F049 §2.7），与资源归属人本人的权限无关（定义 6 边界 c）。位本身在 F049 清单中恒在（开放前标注「端点随后续版本开放」），本 Feature 上线只是让它有了消费端点（AC-33）。
- **不受开放能力层开关约束**（AC-36）：本面是 v2 开放 API 的一部分、与服务账号模块同属「发布即带鉴权」的开放 API 主体，不像 F051 / F052 / F053 三面那样随开放能力层部署与否出现或消失；标准版（未部署开放能力层）同样可用。
- **平台原生扩展只用自有命名**（AC-15 / 28）：不占 `/conversations`、不冒用 `file_search` / `web_search` / files API 等 OpenAI 对象名——占用同名即做出兑现不了的兼容承诺（伴生 §4.6.3「刻意不叫 `/conversations`」同一取向）。官方 SDK 对未知输出项类型须能容忍（AC-04 的验收含扩展项在场）。
- **response_id 不可枚举、工作台轮次不经本 API 暴露**（AC-03）：模式 D 的被代表用户在工作台看得到会话，但 API 侧只能取回经 API 创建的 response——避免以委托身份逐个猜 id 拉取该用户在工作台内的全部对话。
- **两种 OpenAI 风味并存**（AC-10）：既有 `POST /api/v2/assistant/chat/completions` 是助手外壳的 Chat Completions 形态、本次不动；本面是 Responses 形态；F051 是模型面的 Chat Completions 形态（另一数据面）。三者在文档中各说各的适用范围，不互相顶替。
- **模式 D 是主场，不可只出模式 S**（依赖 F050）：纯模式 S 跑得起来，但服务账号的个人知识库为空、会话在平台 UI 里无人可见，场景二的核心承诺（AC-20）落不了地；本 Feature 与 F050 同期发版，spec 里凡引用两身份头判定处均以 F050 为准。
- **薄兼容层已在伴生 PRD 层面关闭**（v2.2 D12 + §六非目标；本 spec §4 决议-2 与之一致）：`POST /workbench/chat/completions` 不做，也不在本版留占位。它承载不了平台工具与知识库引用，交付即等于让客户在「能力不全」与「再学一套」之间二选一。Responses 第三方生态支持面窄于 Chat Completions 属**待验证假设而非已确认诉求**；将来若出现必须直连 LangChain / Dify / n8n / Cherry Studio 且其版本不支持 Responses 的真实客户，单独立项重估，不改本面契约；自建后端直调 HTTP 不受影响。
- **审计**：本面调用频率介于管理操作与模型面之间，逐次记录按开放 API 通用口径进审计（AC-24）；具体落点、写路径与 F051 逐条模型调用记录的关系属 design（DM8 写放大教训沿用）。

## 4. 待澄清决议

> 2026-08-17 用户授权全自动模式：以下各项按建议直接定案，记录理由与备选供追溯；spec 评审（`/sdd-review`）后如有 high 级发现再增补。Discovery N2「F058 是否进 v3.0.0」在此复述为决议-1。

- **[决议-1] 版本层登记为 v3.0.0 Feature、排期由产品定；与 F050 同期、不可只出模式 S；不在 MVP-114 纵切上。** 理由：伴生 PRD §1.4 明确「日常模式会话开放依赖身份传递、两项须同期交付」且要求估算重算（会话列表已移出，应下调）；PRD-1 全册零引用，Discovery N2 已定「登记为版本层 Feature、排期由产品定」。备选 = 直接排进 v3.0.0 必做——PRD-1 主线（应用工场）不依赖它，强绑会拖累 MVP。**何时重新考虑**：产品确认场景二客户（如中粮式 OA 嵌入）的交付窗口时。若本 Feature 不随 v3.0.0 发版，`chat:invoke` 位仍在 F049 清单中并保留「端点随后续版本开放」标注（决议-10）、附录 B.1 中 `/responses` / `/workbench/*` 行随之顺延，其余 v2 开放 API 契约不受影响。
- **[决议-2] Chat Completions 薄兼容层 `POST /workbench/chat/completions` 不做。**（2026-08-17 伴生 PRD v2.2 **D12** 已把它从「待客户场景决定」改判为明确不做并写入 §六非目标；本决议由「本版不做的可选项」相应升格为与伴生一致的「不做」）理由：薄层承载不了平台工具与知识库引用，而这两项是日常模式相对裸模型的全部增量价值——交付一个功能残缺的第二契约，等于让客户在「能力不全」与「再学一套」之间二选一；同一套 API 内已存在两种 OpenAI 风味（既有助手端点 + 本面），再加第三个只会加深「哪个端点该用哪个」的困惑；Chat Completions 是 Responses 的能力子集，先出 Responses 不损失任何能力；「第三方生态对 Responses 支持度偏弱」目前是**待验证假设而非确认诉求**。备选 = 同期做薄层（无平台工具、无引用）——多一条契约多一份映射维护，且能力残缺，否决。**何时重新考虑**：出现确认的客户须直连 LangChain / Dify / n8n / Cherry Studio 等生态工具且其版本不支持 Responses 时，单独立项重估，不改本面契约、不在本版留占位。
- **[决议-3] `GET /responses/{id}`、`previous_response_id` 与附件引用的归属校验基准 = 会话归属主体（模式 S：服务账号 + `X-Bisheng-End-User` 分区键；模式 D：被代表用户），不按单把密钥；不匹配、跨租户、不存在一律 404 且形状不可区分；只能取回经本 API 创建并留存的 response，id 为不透明标识；`previous_response_id` 只允许指向该会话最新留存的 response（平台会话线性追加、不支持分叉），指向历史 response → 400 指明，模式 D 下工作台侧新增轮次同样成为最新。** 理由：线性追加是平台会话的既有产品语义（工作台无分叉），API 侧若允许指向历史 response 就等于引入分叉、两个入口的会话形状不再一致；伴生 §4.6.3 只定了「外部标识不匹配返回 404（不用 403）」，须补齐基准——密钥可轮换、一个服务账号可多把密钥，按密钥校验会让轮换后旧会话失联；模式 D 下会话本就归被代表用户（工作台可见），同一用户经不同委托密钥取回同一 response 与其在工作台看到的一致。404 不区分「不存在 / 不属于你」是为了不泄漏 response 存在性（与伴生 AC-8 / AC-41 同一取向）。「只取回 API 创建的」是防以委托身份逐个猜 id 拉取该用户在工作台内的全部对话。备选 = 按密钥校验（更严但轮换即失联，否决）；备选 = 模式 D 下允许取回该用户工作台任何轮次（把「不设 session:read」从后门打开，否决）；备选 = 允许指向历史 response 并静默续接到会话末尾——调用方以为在分叉、实际被拼到末尾，是「不报错只错」，否决。
- **[决议-4] 分区键在本 Feature 两个有会话语义的端点（`POST /responses`、`POST /workbench/files`）上按 F050 AC-12 写入；本版不作为任何列举 / 过滤维度、不经任何端点返回，仅用于归属一致性校验（`GET` / `previous_response_id` / 附件引用三处）；缺省 WARN 不阻断（F050 AC-13）。与 F050 AC-16 的分界：无会话语义的端点携带 `X-Bisheng-End-User` 只留审计、不产生其它效果，而本面两个端点有会话语义、走 F050 AC-12 的写入并在本 Feature 内消费。** 理由：伴生 §4.6.3「仍然要写分区键，尽管本次没人读它」——一次性成本极低，将来补「按终端用户查询会话」时存量会话已带维度、不必回头补数据；`26014` 强制约束随会话列表端点一并移出（串档成立条件不齐）。备选 = 本版不持久化——将来补数据成本高且存量不可补，且场景三里访客 A 就能拿到访客 B 的 response，否决；备选 = 严格「只写不读」连归属校验也不读——那 `GET /responses/{id}` 在模式 S 下就只剩服务账号一层，同一服务账号下的全部访客互相可读，否决。**红线**：将来若增加任何按用户 / 外部标识列举会话的端点，必须先把缺省行为改为强制（AC-23 / AC-27 守门口径）。持久化落点属 design（伴生附录 E.3 有建议）。
- **[决议-5] 契约外字段处置 = 白名单式接受、契约外 400 指名字段；明确拒绝清单：`store: false`、`user`、采样 / 生成参数（temperature / top_p / max_output_tokens 等）、任务模式专属字段（技能选择等）、`input` 中的 assistant / system 角色历史项、内联文件数据与外链文件 URL；「接受但不生效」档只容忽略后不改变可观察行为的字段、须在本 spec 枚举、**本版清单为空**。** 理由：伴生 §4.6.3 冲突表的核心教训是「调用方按直觉传了、平台静默降级」——Chat Completions 的 `tools` 就是这样静默变成无工具对话；本面对任何会让调用方误以为生效的字段一律明确拒绝。`store: false` 与平台会话机制矛盾（不留痕请走 `model:invoke`）；`user` 与 `X-Bisheng-End-User` 是同一语义的两个来源、只留请求头一处；采样参数在平台工作台链路里由模型配置决定、本版不做逐次透传（透传 = 新能力，且工作台自身也不支持逐轮改采样）；`input` 里塞历史 = 无状态用法，与 `previous_response_id` 的有状态设计双真相；内联 / 外链文件绕开平台上传与解析链路、外链还是新的出站请求面。备选 = 采样参数「接受但不生效」——违反「不改变可观察行为」判据，否决；备选 = 采样参数透传——待平台工作台链路支持逐轮采样时再开。**何时重新考虑**：工作台链路支持逐轮采样参数、或出现须回传历史的真实集成场景时，逐项从拒绝清单移到已实现清单，不改既有字段语义。
- **[决议-6] 平台原生扩展一律 BiSheng 自有命名：平台工具 = `{"type": "bisheng_tool", "tool_key": ...}`（伴生 §4.6.3 已定）；知识库挂载、附件引用、平台工具的输出项类型同样用自有命名（具体形状属 design），不冒用 OpenAI 内置工具 / 对象名（`file_search` / `web_search` / `conversations` / files API 等）；引用走 Responses 注解；客户端执行的 `function` 工具本版不支持、明确拒绝。** 理由：伴生 §4.6.3「刻意不叫 `/conversations`——占用那个路径名等于做出兑现不了的兼容承诺」，同一取向适用于工具与对象命名；`bisheng_tool` 是服务端执行、`function` 是客户端执行，方向相反，本面所复用的平台会话链路没有「返回 tool_calls、等调用方回传结果」的往返语义，支持它是新能力而 §3 三类场景无此诉求；官方 SDK 对未知输出项类型可容忍（AC-04 验收含扩展项）。备选 = 把知识库映射到 OpenAI `file_search`（`vector_store_ids`）——调用方会顺着去找 vector stores API，兑现不了，否决。**何时重新考虑**：出现须由调用方执行工具的真实场景时，按 Responses 的 function 往返语义补做，不改 `bisheng_tool` 语义。
- **[决议-7] `instructions` 叠加于平台工作台既有系统提示词之上，不替换、不关闭。** 理由：`chat:invoke` 与 `model:invoke` 的分界之一就是「走平台会话机制、注入平台提示词」（伴生 §4.2.4 扩展位表；F051 AC-17 反向对照）；平台提示词承载安全与产品约束，允许调用方替换即让一把 `chat:invoke` 密钥拆掉平台围栏。备选 = `instructions` 整体替换平台提示词——等于「便宜版模型面 + 留痕」，与两位互不蕴含的取向相悖，否决；备选 = 不接受 `instructions`——场景二的自建系统常需注入业务上下文（当前页面 / 当前工单），拒绝会逼调用方把指令塞进用户输入，否决。叠加的具体位置与优先级属 design。
- **[决议-8] `model` 必填、按名解析；可用范围 = 平台工作台配置中对执行身份可用的对话模型；名称基准（模型管理页原名精确匹配）与跨服务商同名歧义规则（拒裸名 + 给限定名 + 不取默认）与 F051 决议-2 / 决议-3 同源。** 理由：Responses 契约 `model` 必填，缺省回落到「工作台默认模型」是又一处调用方不知道自己在用什么的静默行为；工作台链路本就以工作台配置为可用范围（与 F051 的模型管理页全集不同，各按其产品面），但同一个模型名在两面若解析成不同服务商就是「不报错只错」，故名称与歧义规则必须同源。备选 = 本面按平台内部模型 id 选模型——把内部标识写进对外契约、与 F051 的按名解析割裂，否决。
- **[决议-9] 流式与非流式同时支持；非流式返回的 response 对象与同一请求流式执行的最终对象内容一致；失败只有一种真相（流式 = error 事件 + 失败终态事件，非流式 = 错误响应），失败轮次不留存。** 理由：Responses 契约缺省即非流式，官方 SDK `responses.create` 不带 `stream` 的写法必须直接可用（伴生 AC-36 就是对非流式响应体的验收）；两种返回方式只是传输差异、不是契约差异，成功对象必须一致；失败若在非流式下以「带 failed 状态的对象」返回、在流式下以事件返回，同一失败就有两种真相，且会话历史里会留下半条消息、下一轮续接语义含糊——统一为错误响应 + 不留存最干净。备选 = 只支持流式——与「OpenAI SDK 可直调」冲突，否决；备选 = 失败也留存为 failed 对象供 `GET` 取回——引入「可取回但不可续接」的第三种状态，否决。非流式的超时与长响应处理属 design。
- **[决议-10] `chat:invoke` 位归 F049 权限位清单、始终在清单中（伴生 §4.2.4 基础位）；本 Feature 只拥有该位的消费端点，上线时让清单中该位的说明与覆盖端点指向本 Feature 端点、去除「端点随后续版本开放」标注；不写「未发版则不出现」。**（2026-08-17 独立审查裁定，取代初稿「位随本 Feature 同期出现 / 未发版不出现」）理由：权限位清单是 F049 的对象，一个位「出现与否」由清单 owner 决定；F049 已在其范围边界写明「`chat:invoke` 的消费端点随 F058 开放，开放前签发表单对该位以说明标注『端点随后续版本开放』、其余行为同普通位」——把「勾了没用」的困惑用标注化解，而不是让另一个 Feature 反向控制清单里某一位的出现，避免两个 spec 对同一位各写一套规则。备选 = 初稿的「未发版不出现」——需要 F049 清单按 F058 发版状态动态增删位，形成反向依赖，否决。
- **[决议-11] 附件只经 `POST /workbench/files` 上传获得标识；`input` 中的附件项只接受平台标识、不接受内联数据与外链 URL；类型 / 大小 / 数量限制沿用平台工作台既有上传限制；不新增独立配额。** 理由：伴生 §4.6.3 把附件上传定为原生扩展端点、附录 E.3 给出复用映射，平台的解析 / 摄取链路以上传为入口；外链拉取是新的出站请求面（与 F054 出站白名单取向相反）；限制沿用工作台是为了同一个租户里两个入口的附件行为一致、也不为开放 API 另设一套配额（伴生 §4.8 配额按密钥且 P2）。备选 = 接受内联 base64——绕开上传链路且大 payload 直接压在会话请求上，否决。附件的生命周期与清理属 design、沿用工作台既有口径。
- **[决议-12] 异步分支两个端点契约留位、调用返回明确「本版未开放」（错误码归 design，与 `26015` 同族或复用）；不做会话列表 / 历史 / 反馈 / 回填；不占 `/conversations`；F049 已关闭的 6 个 `/chat/*` 不复活。** 理由：伴生 §4.6.3「契约现在就按 Responses 定型，异步分支点亮时不需要改契约第二遍」——留位是这条收益的载体，但留位端点若静默成功或 5xx 会让调用方误判；会话列表与 `session:*` 已于 2026-08-16 整体移出（平台存会话 ≠ 给调用方开读接口），本 Feature 是最容易把它们「顺手」加回来的地方，故显式写成 AC-27 守住。备选 = 留位端点直接 404——调用方分不清「路径打错」与「本版未开放」，否决。**何时重新考虑**：四条技术前置消化后点亮异步分支，届时只补 `background: true` 分支与两个端点的实现，不动同步契约。

- **[决议-13] 日常 / 任务模式的对外区分用 BiSheng 原生扩展字段 `bisheng_mode`（`"chat"` / `"task"`，缺省 `"chat"`），`background` 保持 OpenAI 原义（同步 / 异步传输）；两轴各自校验、各自拒绝、各自留位（AC-37 / AC-25），错误码 `26017` 与 `26015` 不合并。**（2026-08-17 伴生 PRD v2.2 **D11** 裁定，本 spec 初稿「任务模式 = 同契约 `background: true` 分支」的表述随之作废）理由：① 内部 `task_mode` 的两个分支 `_task_mode_stream_completion` / `_agent_stream_chat_completion` **都是同步 SSE 流**（`chat_service.py:2148-2150` / `:2158`），任务模式真正的异步在后续 start-execute + WebSocket 段，把能力布尔映射到传输布尔连现状都不成立；② 按 OpenAI 语义写 `background: true` 的动机通常只是躲网关 / LB 超时，若它同时切到灵思，调用方拿到的是耗时分钟级、计费不同、输出形态不同（产物、`ask_user` 中断）的另一种能力，还会挤占全租户共享的灵思 worker 池——这正是本 spec 反复守的「静默降级」失败模式（决议-5 / 决议-6 同源）；③ `("chat", background: true)`（日常模式异步）是已识别的后续需求，`background` 一旦被模式占用就只能破坏性改契约，恰好抵消选 Responses 的核心收益。备选 = 沿用 `background` 兼任模式开关（初稿写法）——省一个字段，但换来上述三项，否决；备选 = 用 `model` 承载模式（对照 OpenAI deep research 以 `model` 选能力）——本面 `model` 已被真实对话模型占用（AC-07），否决。**本版增量成本≈0**：只是一次枚举校验 + 一个错误码，不引入新链路。**何时重新考虑**：任一轴点亮时按其自身前置推进，不改另一轴语义。
