## 1. 四项发现的闭环

| 编号 | 原级别/问题 | 修订位置 | 复审反例与结论 |
| --- | --- | --- | --- |
| R1 | high：默认路线可被逐次打镜像的旧实现满足 | AC-11、AC-13，INV-39 | 新描述不选模式必须应用包；代码修改若触发 OCI build/push 则失败。旧描述保持 legacy 构建，新描述仅显式选择才兼容。通过 |
| R2 | high：管理主体及 owner-only 边界含糊 | AC-14、AC-15、AC-30、AC-45、§2.11，INV-42 | 全局环境/公开基础材料仅平台超管；应用私有补包及生产恢复仅目标自然人 owner；租管、非 owner 超管、其他租户、服务账号独立操作拒绝。超管恰为 owner 时仅按 owner 操作。通过 |
| R3 | medium：双架构交付为可不声明的条件项 | AC-55，INV-43 | 首轮必须交付 amd64 和 arm64 的服务、官方运行及准备镜像；只交付 amd64 即不合格，不扩大到其他国产 CPU。通过 |
| R4 | medium：新准备任务残留资源不受约束 | 新增 AC-63；保留 AC-26、AC-09 | 成功、失败、超时、取消、重启遗留均回收；先确认停止后释放容量，未知状态报告且仍占额；保留生产数据、引用产物及唯一未确认快照。通过 |

R2 是本轮按既有 F054 AC-56 owner-only 原则收窄后的明确主体规则，不引入可任意跨应用恢复的“运维”身份。依据已核对 `app_data_service.py` 的 `_require_owner` 业务前置，不能仅依赖管理身份的权限短路。

## 4. 已核对的既有契约

- F055 AC-09 保留破坏性结构变更确认；F057 AC-03 保留兼容 SDK 不强制重发。

- F054 AC-56 的 owner-only 数据业务前置不被超管/租管短路替代。
- 现有源码基线仅做静态核查；这份报告没有执行 Docker、K8s、断网发布、DM8 或授权联调。
