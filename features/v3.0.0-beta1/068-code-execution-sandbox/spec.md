# Feature: 代码执行沙箱统一底座

**关联 PRD**: [docs/PRD/2.6 灵思 deepagents 迁移 PRD/灵思代码执行沙箱选型调研（私有化场景）.md](../../../docs/PRD/2.6%20灵思%20deepagents%20迁移%20PRD/灵思代码执行沙箱选型调研（私有化场景）.md) §6 推荐路线图 · §8 POC 记录；[docs/product/3.0 应用工场 产品方案.md](../../../docs/product/3.0%20应用工场%20产品方案.md) §4.6 平台既有资产复用 · §5.2 存量代码执行点迁入沙箱设施
**优先级**: P0
**所属版本**: v3.0.0-beta1
**依赖**: 无（与 F103 应用工场 sandbox-core 并行；本 Feature 不依赖其交付）

> **范围边界**
> - **本次纳入**：
>   - 代码执行器新增第三种执行模式（自建隔离环境，新装默认），覆盖灵思 / 日常会话 / 助手 / 工作流 Agent 与工具节点五条路径；与本地模式、E2B 模式并列可配置。云沙箱走同一执行器插件缝，本期不新增其它云厂商实现
>   - 工作流「代码节点」迁入同一隔离环境，消除进程内 `exec()`
>   - 隔离环境的加固基线（非 root、只读根文件系统、能力裁剪、资源限额、无中间件网络可达）
>   - 执行环境依赖收口：一份受控执行镜像，取代「后端进程环境 + 各客户手工部署环境」的漂移
>   - 执行环境的凭据隔离：执行进程不再继承对象存储、网关、数据库口令
>   - 宿主侧配置面对执行侧不可写（平台配置文件与启动脚本今天以可写方式挂进容器）
>   - 管理端可选择执行模式；系统级配置承载隔离环境的接入参数与容量参数
> - **本次明确排除**：
>   - **Fernet 主密钥外置**（`secret_key` 硬编码为开源常量）——影响面覆盖全部 `config.yaml` 密文，远超代码执行，独立立项，见 §3
>   - **gVisor（runsc）强隔离档**——目标内核上未实测，作为可选加固档延后
>   - **按次新建容器 / 持 docker 的编排控制面**——本期用预声明副本 + 租约，编排控制面等 3.0 应用工场 F103 `runtime-manager` 统一提供，不在此自造第二个特权面
>   - **日常会话把用户上传原件送进执行环境**——今天日常会话只把附件抽成文本进 prompt，这是既有产品缺口，本期不改其语义，另行立项
>   - **知识库 / 附件解析链路里的 LibreOffice 调用**——那是平台自有可信代码，不是模型代码，继续留在解析流水线
>   - **E2B 模式的功能改进**——冻结为境外部署与存量兼容，不再投入（含其产物清单只列一层目录的既有缺陷）
>   - **K8s 编排清单**——协议兼容（worker 持副本 URL 列表，可用 StatefulSet + headless Service），本期必交 compose；不引入 k8s 客户端、不要求客户新上 K8s
>   - **对外 API 与前端新页面**——除管理端既有代码执行器配置弹窗增加一个选项外，不新增对外 API 路径

## 1. 用户故事

作为 **私有化交付的实施与安全负责人**，
我希望 **平台执行模型生成的代码时不落在后端进程里，且执行环境读不到其它租户的数据、连不上数据库与对象存储**，
以便 **通过客户安全评审与等保测评，不必为「AI 会执行任意代码」这一条单独出具补偿说明**。

作为 **业务用户（灵思任务 / 日常会话）**，
我希望 **代码执行能力在换成隔离环境后行为不变**：产出物照样出现在结果区、技能包照样可用、报错照样看得懂，
以便 **不用因为平台内部改造而改变自己的用法**。

作为 **工作流搭建者**，
我希望 **代码节点仍然按原来的入参/出参约定工作**，
以便 **存量工作流不需要重做**。

作为 **平台运维**，
我希望 **能按工具逐个切换执行模式并随时回退，且执行环境的容量与排队情况可观测**，
以便 **灰度上线出问题时不必回滚整个版本**。

## 2. 验收标准

### 2.1 执行模式与装配

- **AC-01** — THE SYSTEM SHALL 为内置代码执行器提供第三种执行模式（进程外隔离执行），与既有本地模式、E2B 模式并列，三者互斥且由管理端配置决定。
- **AC-02** — WHERE 代码执行器配置为隔离执行模式, THE SYSTEM SHALL 使灵思任务模式、工作台日常会话、助手、工作流 Agent 节点、工作流工具节点五条调用路径全部经由该模式执行，不存在任一路径仍在 backend / Celery worker 进程内执行模型代码。
- **AC-03** — THE SYSTEM SHALL 使隔离执行模式返回给模型的工具结果字段与本地模式逐字段一致（退出码、日志、产物清单三项的字段名与语义不变）。
- **AC-04** — WHERE 代码执行器配置为隔离执行模式, THE SYSTEM SHALL 使工具描述中声明的可用库清单与隔离环境实际安装的库一致。
- **AC-05** — IF 隔离环境不可达、无空闲容量或返回非预期响应, THEN THE SYSTEM SHALL 返回可归因的失败结果并记录可检索日志，且不得静默回落到进程内执行。

### 2.2 文件进出与产物

- **AC-06** — WHEN 灵思任务模式调用代码执行, THE SYSTEM SHALL 在执行前把该任务工作区的当前文件送入隔离环境，使代码可用相对路径读到用户上传的原件与已物化的技能包。
- **AC-07** — WHEN 一次执行成功结束, THE SYSTEM SHALL 仅把本次新增或修改的文件回收为产物，不把执行前已存在的输入文件重复计入产物清单。
- **AC-08** — WHEN 代码把交付物写到工作目录根级而非交付目录, THE SYSTEM SHALL 将其归入交付目录并在结果中告知新路径。
- **AC-09** — WHERE 灵思任务模式使用隔离执行模式, THE SYSTEM SHALL 使执行产生的产物在同一轮内可被文件类工具读取，并可被下一轮继承。
- **AC-10** — IF 待送入隔离环境的单个文件超过配置上限, THEN THE SYSTEM SHALL 跳过该文件并在日志中点名该文件，不得静默丢弃。
- **AC-11** — WHERE 代码执行器配置为隔离执行模式, THE SYSTEM SHALL 使技能包在执行环境内真实可见且可执行（不复现 E2B 模式下技能目录结构性缺失的行为）。

### 2.3 隔离与加固

- **AC-12** — WHILE 隔离环境运行中, THE SYSTEM SHALL 使其无法连通平台的关系数据库、缓存、对象存储、搜索引擎与权限服务。
- **AC-13** — THE SYSTEM SHALL 使隔离环境以非 root 身份、只读根文件系统、裁剪全部 Linux capability、保留默认 seccomp 策略运行。
- **AC-14** — THE SYSTEM SHALL 为隔离环境设置内存、进程数与 CPU 上限，使单次执行无法耗尽宿主资源。
- **AC-15** — THE SYSTEM SHALL 使执行代码的进程环境变量不含对象存储访问凭据、网关密钥与数据库口令。
- **AC-16** — WHEN 一次执行超过配置超时, THE SYSTEM SHALL 终止该次执行及其派生的全部子进程，并把「超时且未完成、产物不存在」的结论返回给模型。
- **AC-17** — WHEN 一次执行结束或其租约释放, THE SYSTEM SHALL 清除该次执行的工作目录，使后续执行读不到其残留文件。
- **AC-28** — THE SYSTEM SHALL 使平台配置文件与启动脚本对执行侧不可见，且对承载执行的容器不可写。

### 2.4 工作流代码节点

- **AC-18** — THE SYSTEM SHALL 使工作流代码节点在隔离环境中执行，节点的入参映射与出参字段校验行为保持不变。
- **AC-19** — IF 代码节点主函数的返回值无法序列化为节点出参, THEN THE SYSTEM SHALL 返回指明该原因的节点错误，而不是静默产出空值。
- **AC-20** — WHEN 搭建者保存的代码存在语法错误, THE SYSTEM SHALL 在节点初始化阶段报错，报错时机与信息与改造前一致。
- **AC-21** — WHERE 代码节点隔离执行被系统级开关关闭, THE SYSTEM SHALL 回退为改造前的进程内执行行为。

### 2.5 配置、灰度与可观测

- **AC-22** — THE SYSTEM SHALL 允许按单个工具配置执行模式，切换与回退均不需要重启服务。
- **AC-23** — WHEN 存量部署升级到本版本, THE SYSTEM SHALL 保持该部署原有的执行模式不变，不静默切换为隔离执行模式。
- **AC-24** — WHERE 部署为全新安装, THE SYSTEM SHALL 以隔离执行模式作为内置代码执行器的默认值。
- **AC-25** — IF 配置文件缺失隔离执行相关配置段, THEN THE SYSTEM SHALL 以内置默认值正常启动，且旧版本镜像配上新版本配置文件时不得启动失败。
- **AC-26** — THE SYSTEM SHALL 输出隔离执行的可观测数据，至少覆盖单次执行耗时、退出码分布、送入字节数与因容量不足被拒绝的次数。
- **AC-27** — IF 隔离环境容量已满, THEN THE SYSTEM SHALL 使请求进入等待或返回可归因的容量错误，并使该事件在可观测数据中与执行失败区分开。

## 3. 边界情况

- 当同一灵思会话跨多轮执行时，系统应让后一轮读到前一轮的产物；会话结束或空闲超时后应释放其占用的执行容量。
- 当同一时刻的并发执行请求超过隔离环境容量时，系统应表现为排队或明确的容量错误，不应表现为执行失败或超时。
- 当代码尝试访问工作目录之外的宿主路径、用户主目录或从根目录递归扫描时，系统应拒绝该次执行并说明原因（本期沿用既有拒绝行为；隔离环境在多次执行间复用，故该防线不撤除）。
- 同一 runner 容器默认同一时刻只承载一个会话。若配置为同一容器并发多会话，系统须使其中一个会话既读不到、也写不了、也删不掉另一个会话的工作目录与租约。
- 当代码把交付物写到带前导斜杠的绝对路径时，系统应告知该写入不会交付并给出正确的相对路径写法。
- 当执行日志过长时，系统应保证模型仍能看到产物清单与结论，不因日志过长而丢失这两项。
- 当隔离环境缺少某个可选外部程序（如文档渲染所需的办公套件组件）时，技能包脚本应如实说明缺失并降级，不应使整个任务失败。
- 当执行进程因内存超限被内核终止时，系统应给出可归因的结论——该场景的原生报错不指向内存，容易误判为功能缺陷。
- 当存量工作流的代码节点引用了执行环境中不存在的第三方库时，系统应报出可归因的导入错误，运维可通过系统级开关回退。
- **Fernet 主密钥硬编码**（`secret_key` 为开源常量，导致 `config.yaml` 中的密文对任何在后端进程内运行的代码等价于明文）不属本 Feature 范围。本 Feature 通过「代码不再在后端进程内运行」降低其可利用面，但不构成修复；该问题须独立立项处理。
