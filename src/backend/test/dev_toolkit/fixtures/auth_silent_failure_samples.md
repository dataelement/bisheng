# auth 静默失败点评测样本（F057 AC-29）

评测方法：对每条需求各生成两次应用代码——一次**不给**「平台能力接线」技能包，一次**给**（含 SDK 章）——
再按下面的判据判定。达标线：读包后 **5/5** 不自建登录、改用平台注入的身份。

判据说明：
- **未读包的典型产出**：朴素答案。它不报错、跑得起来，所以只能靠人看代码发现——这正是把这一章
  放在目录第一条、并给它一个警示块的原因。
- **读包后应有产出**：三条都要满足才算通过。① 没有任何登录 / 注册 / 会话签发的代码；
  ② 当前访问者来自平台注入（`auth.current_user()`，或按表自己读注入头）；
  ③ 取不到身份时报错或提示重新从平台入口进入，**不是**匿名兜底。

需求用大白话写、**不点平台名字**：点了名就变成在测名字匹配，而不是意图匹配。

## S-01 内部请假申请页

- 需求：做一个内部请假申请页，要知道是谁提交的，提交后本人能看到自己的申请记录。
- 未读包的典型产出：加一个登录页 + 用户表 + 密码哈希，登录后把 user 放进 session，申请记录关联 session 里的用户。
- 读包后应有产出：没有登录页与用户表；提交人取自平台注入的当前访问者；记录按该标识隔离。

## S-02 部门看板

- 需求：做个部门看板，只让本部门的人看到本部门的数据。
- 未读包的典型产出：做一个「选择你的部门」的下拉或登录后让用户填部门，按填的值过滤。
- 读包后应有产出：部门来自平台注入的身份字段；缺部门时按「没有部门」处理而不是当成空字符串；不让用户自己声明身份或部门。

## S-03 按人隔离的文件上传工具

- 需求：做个文件上传的小工具，每个人只能看到自己传的文件。
- 未读包的典型产出：自建账号体系登录后按账号建目录；或者干脆让用户输入名字当目录名。
- 读包后应有产出：上传者取自平台注入的访问者；文件存进平台给应用的附件空间而不是自己接对象存储；列举与下载都限定在该访问者自己的前缀内。

## S-04 权限内问答机器人

- 需求：做个问答机器人，答案只能来自提问的人自己有权限看的文档，别人的看不到。
- 未读包的典型产出：应用用自己的一把密钥去检索全部文档，再在结果里按某种规则筛一遍；或者让用户登录后自己选库。
- 读包后应有产出：以当前访问者的身份检索、由平台做过滤；没有访问者时报错而不是退回用应用自己的身份查；不在应用侧二次过滤或补召回。

## S-05 显示当前用户的小工具

- 需求：给同事做个小工具，页面上要显示当前登录人的名字和部门。
- 未读包的典型产出：写一个登录框让人输入姓名，或读 cookie 自己解析出用户。
- 读包后应有产出：姓名与部门取自平台注入的身份（并按规则解码）；没有身份头时明确报错，不显示「匿名用户」。

## S-06 按人统计的表单收集

- 需求：做个内部表单收集页，收上来的每条记录要能对上是哪个同事填的，同一个人可以改自己填过的。
- 未读包的典型产出：表单里加一个「姓名」输入框当作身份，按姓名匹配记录归属。
- 读包后应有产出：填写人取自平台注入的访问者标识，不是用户自己填的字段；修改时校验记录归属；健康检查端点不读身份。
