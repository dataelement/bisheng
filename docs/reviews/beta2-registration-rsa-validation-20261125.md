# beta2 注册 RSA 密文长度修复

基线：`82d8e38ea6`；目标：`feat/3.1.0-beta2`。按 hotfix 流程处理，
没有新增接口、字段、前端协议或数据库迁移。

## 原因与修复

`POST /api/v1/user/regist` 的 UserCreate 接收前端 RSA 加密后的 Base64 密文。
当前 2048 位密钥对应 344 字符密文。注册流程先将它送入 `User.model_validate`，
触发持久化 password 字段的 255 字符上限，未执行到解密与密码强度检查。

修复保留验证码、账号和昵称校验顺序，随后调用原
`decrypt_md5_password_strict` 解密、校验并生成哈希，以 model_validate 的 update
参数替换 password 后再构建 User。输入对象不被改写；数据库只接收原格式密码哈希。
原身份创建、首用户管理员/后续用户默认角色、租户和部门初始化链路保持不变。
不扩大数据库字段，不降低 RSA 位数，不放松密码规则。

## 回归证据

新增 `test/user/test_registration_rsa.py`，不 mock 加解密、密码规则或模型校验；
使用实际 2048 位 RSA、生产 public_key/注册 HTTP 路由、实际身份服务和 SQLite 身份表。
仅替换 Redis 传输及外部租户/部门/权限投影。

- HTTP 注册接受 ASCII、Unicode 和 128 字符密码产生的 344 字符密文；数据库保存
  32 字符哈希，响应不含 password，来源/停用字段仍由服务端规范化。
- 真实加密的弱密码及 129 字符密码按原强度规则拒绝，身份表零写入，未进入租户初始化。
- 验证码拒绝发生在解密前；开发环境原有明文输入兼容路径仍保存哈希。
- 修复前初始五例中三例复现 `string_too_long`，两例通过，确认测试能够捕获原缺陷。
- 注册/RSA/账号规则/首次注册角色/密码列长度/身份规则的定向回归：88 项通过；
  排除的一个配置加载测试在未修改基线同样失败。
- 用户模块完整对照：基线 256 passed、26 failed、2 skipped；修复后
  263 passed、26 failed、2 skipped。失败名称集合一致，没有新增失败。
- ruff format、架构守卫、diff whitespace 检查通过。测试文件完整 lint 通过；
  服务文件原有五处中文审计文案 `RUF001` 与基线位置/内容一致，无新增 lint；
  排除该既有规则后服务文件检查通过。

测试使用本地原生 SQLite，不代表 MySQL/DM8 或现场注册页面验收。本轮不部署 116，
未创建现场测试账号。
