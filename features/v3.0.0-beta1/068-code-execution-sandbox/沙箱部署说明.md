# 沙箱部署说明

隔离环境把模型 / 搭建者写的 Python 从 backend、Celery、Linsight 进程里挪到独立的 `bisheng-sandbox` 副本上执行。平台侧**不挂 docker.sock、不调 Kubernetes API**，只靠主机名模式发现副本，再走 HTTP 租约。

架构评审材料见同目录 [沙箱架构设计说明书.md](./沙箱架构设计说明书.md)。页面上怎么选执行方式、任务模式怎么交文件，见 [沙箱使用说明.md](./沙箱使用说明.md)。本文只写**怎么配、怎么开、怎么验收**。

---

## 1. 组件与调用关系

| 组件 | 镜像 | 作用 |
|------|------|------|
| `code-runner-*` | `bisheng-sandbox` | 加固容器；提供 `/health`、`/v1/sessions`、copy-in/exec/copy-out |
| backend | `bisheng-backend` | 工作流编辑器「运行一次」、部分同步路径 |
| Celery worker | 同上 | 工作流代码节点、日常会话 / 助手 / Agent 节点里的代码解释器 |
| Linsight worker | 同上（独立进程） | 任务模式代码解释器（`keep_session` 粘滞同一副本） |

五条业务路径共用 `CodeInterpreterTool` → `ContainerExecutor`，**不各自接沙箱**。工作流代码节点另走 `SandboxCodeParser`，同样打 `/v1/sessions/.../exec`。

```
任务模式 / 日常会话 / 助手 / 工作流 Agent·工具节点
        └── bisheng_code_interpreter（type=container）
工作流代码节点（code_node_enabled=true）
        └── SandboxCodeParser
                └── HTTP 租约 → code-runner-{n}:8080
```

Runner **不连 MinIO**。文件由 worker 打 tar 送进去、再 copy-out 回来。

## 2. 部署

### 2.1 Docker Compose

仓库 `docker/docker-compose.yml` 预声明具名副本（默认 `code-runner-1`、`code-runner-2`），挂在 **internal** 网络 `sandbox_net` 上，不映射宿主机端口。`backend` 和 worker 都必须同时加入 `default` 和 `sandbox_net`，才能解析 `code-runner-1`，同时仍能访问 MySQL / Redis。

```bash
# 与 runner 共用；生产务必改掉默认值
export SANDBOX_TOKEN='替换成足够长的随机串'
export SANDBOX_IMAGE_TAG=v3.0.0-beta1   # 或 CI 打好的 tag

docker compose up -d code-runner-1 code-runner-2 backend backend_worker
```

Compose 下 DNS 从 **1** 起：`code-runner-1`、`code-runner-2`。worker 默认 `discover_index_start=1`，一般不用改。

`backend` 与 `backend_worker` 都加入 `default` 和 `sandbox_net`，并带同一份 `BS_SANDBOX_CONF__TOKEN`。编辑器「运行一次」在 backend 进程里执行，因此它必须能解析 runner。仓库里没有 Linsight 服务；任务模式要另起进程，同样必须能解析 `code-runner-*`。

扩容：复制一份 `code-runner-N` 服务（具名，不要用 `deploy.replicas`），否则 `keep_session` 粘不住同一台。

### 2.2 Helm（两张独立 chart）

中间件（MySQL / Redis / MinIO / ES / Milvus / OpenFGA）**不在** chart 里，先指到已有地址。

```bash
export SANDBOX_TOKEN='替换成足够长的随机串'

# 1. 沙箱：Service 名保持 code-runner（默认 fullnameOverride）
helm upgrade --install sandbox docker/helm/bisheng-sandbox \
  --namespace bisheng-sandbox --create-namespace \
  --set token.value="$SANDBOX_TOKEN"

# 2. 平台（token 必须与上一张相同）
helm upgrade --install bisheng docker/helm/bisheng \
  --namespace bisheng --create-namespace \
  --set sandbox.token="$SANDBOX_TOKEN" \
  --set sandbox.discoverHostPattern='code-runner-{n}.code-runner.bisheng-sandbox.svc.cluster.local'
```

K8s StatefulSet 序号从 **0** 起，平台侧必须：

```yaml
sandbox:
  enabled: true
  discoverHostPattern: "code-runner-{n}.code-runner.bisheng-sandbox.svc.cluster.local"
  discoverIndexStart: 0
```

`sandbox.codeNodeEnabled` 会写成 `BS_SANDBOX_CONF__CODE_NODE_ENABLED`。这项**不再决定**代码节点走本机还是沙箱，保持默认 `false` 即可。执行方式只看内置工具的 `extra.type`，见 3.3。

沙箱 chart 的 NetworkPolicy 默认开启，入站放行命名空间 `bisheng` 里标签 `app.kubernetes.io/component` 为 `worker` 或 `backend` 的 Pod。编辑器「运行一次」因此能打到 runner。Linsight（`component: linsight`）不在默认放行里；任务模式要进沙箱，把该 component 加进 `networkPolicy.allowFrom`。

**不要**给 runner 只挂一个 ClusterIP VIP。`keep_session` 粘的是主机名（`http://code-runner-0.code-runner…`），经 kube-proxy 会把下一跳打到别的 Pod，工作目录丢失。

扩容只改沙箱 chart：

```bash
helm upgrade sandbox docker/helm/bisheng-sandbox --reuse-values --set replicaCount=4
```

worker 后台按 TTL 刷新 DNS，一般不用重启。

Helm 安装细节另见 [docker/helm/README.md](../../../docker/helm/README.md)。

### 2.3 Linsight 进程

Compose 和 Helm 不要按同一种方式再起一份，两份进程会抢同一个 Redis 队列。

**Compose。** `backend_worker` 的命令是 `entrypoint.sh worker`。这个模式在后台执行 `start_linsight`（`python bisheng/linsight/worker.py --worker_num 1 --max_concurrency 5`），和 Celery 在同一个容器里。不要再执行 `entrypoint.sh linsight`。灵思因此已经在 `sandbox_net` 上。

**Helm。** chart 自带 `bisheng-linsight` Deployment，命令是 `entrypoint.sh linsight`，装好即有，不要进 Pod 再手动起一份。它的标签是 `component: linsight`，默认 NetworkPolicy 不放行，这一份打不到 runner。worker Deployment 用的也是 `entrypoint.sh worker`，镜像里的这份脚本同样会在 worker Pod 里再后台拉起一份灵思；那一份走 worker 的网络，可以打到 runner。两份同时在就会抢队列。只要一份时，停掉独立 Deployment，或改 worker 镜像的入口、去掉后台的 `start_linsight`。

多套平台共用一个 Redis 时，把任务队列和会话库错开（例如平台 A 用 `/5` + Celery `/4`，平台 B 用 `/1`），否则别人的 Linsight 会抢走任务。

## 3. 配置项

配置分两边：**平台访问沙箱**（`BS_SANDBOX_CONF__*`）和 **runner 自身**（`SANDBOX_*`）。两边 token 必须一致。

`config.yaml` 可以写 `sandbox_conf:` 块；**更老的镜像遇到未知顶层键会拒启**，所以发行文件里默认整段注释掉，靠环境变量覆盖。

### 3.1 平台侧 `BS_SANDBOX_CONF__*`

对应 `SandboxConf`，环境变量是双下划线 + 字段大写。表里的默认值就是要填进环境变量的字面量。字节数只接受十进制整数：`int(raw)` 不认 `50MiB` 这种写法，照填会在启动时报错。50 MiB = `52428800`。

| 环境变量 | 含义 | Compose 默认 | Helm 默认 |
|----------|------|--------------|-----------|
| `BS_SANDBOX_CONF__TOKEN` | 调用 runner 的 Bearer，与 `SANDBOX_TOKEN` 相同 | `bisheng-sandbox-local` | values `sandbox.token` |
| `BS_SANDBOX_CONF__DISCOVER_HOST_PATTERN` | 副本主机名，`{n}` 为序号 | `code-runner-{n}` | `code-runner-{n}.code-runner.bisheng-sandbox.svc.cluster.local` |
| `BS_SANDBOX_CONF__DISCOVER_INDEX_START` | 扫描起始序号 | `1` | `0` |
| `BS_SANDBOX_CONF__DISCOVER_TTL_S` | 后台刷新间隔（秒），不是缓存过期 | `60` | `60` |
| `BS_SANDBOX_CONF__DISCOVER_PORT` | runner HTTP 端口 | `8080` | `8080` |
| `BS_SANDBOX_CONF__DISCOVER_MAX` | 连续扫多少个序号后停止 | `32` | `32` |
| `BS_SANDBOX_CONF__ENDPOINTS` | 非空则跳过 DNS，值为 JSON 数组 | 空 | 空 |
| `BS_SANDBOX_CONF__CODE_NODE_ENABLED` | 遗留字段。Helm 仍会注入，运行时不用它选择执行方式 | `false` | `false` |
| `BS_SANDBOX_CONF__POOL_ACQUIRE_TIMEOUT_S` | 等空闲副本的最长时间 | `30` | `30` |
| `BS_SANDBOX_CONF__DEFAULT_TIMEOUT_S` | 单次 exec 默认超时 | `600` | `600` |
| `BS_SANDBOX_CONF__MAX_COPY_IN_BYTES` | 超过则跳过该文件，不打进 tar。容量 50 MiB | `52428800` | `52428800` |

发现变量要配在真正发起调用的进程上。变量本身不够，该进程还得在网络上够得到 runner（见 2.1、2.2 的默认范围）：

- **Celery worker**：异步工作流、日常会话、助手。Compose 和 Helm 默认都覆盖这条
- **backend**：编辑器「运行一次」。Compose 已双挂 `sandbox_net` 并带 token；Helm 网络策略已放行 `component: backend`
- **Linsight**：任务模式。Compose 跑在 `backend_worker` 容器里，已在 `sandbox_net` 上。Helm 独立 Deployment 默认不放行，见 2.3

### 3.2 Runner 侧 `SANDBOX_*`

| 环境变量 | 含义 | 默认 |
|----------|------|------|
| `SANDBOX_TOKEN` | 鉴权，须与平台 token 相同 | 空则进程拒绝启动 |
| `SANDBOX_MAX_SESSIONS` | 每副本并发会话数 | `1`（compose/helm 示例常用 `2`） |
| `SANDBOX_LEASE_TTL_S` | 空闲租约回收（秒） | `900` |
| `SANDBOX_ENABLE_UID_ISOLATION` | 会话 uid 隔离 | `true`（推荐） |
| `SANDBOX_SESSIONS_ROOT` | 会话工作目录 | `/tmp/sessions` |
| `SANDBOX_MAX_COPY_IN_BYTES` | copy-in 单文件上限，容量 50 MiB。填十进制字节数，不要写 `50MiB` | `52428800` |
| `SANDBOX_PORT` | 监听端口 | `8080` |
| `SANDBOX_LOG_LEVEL` | 日志级别 | `INFO` |

并发租户靠**加副本**，不要指望在同一容器里堆很多会话。`SANDBOX_MAX_SESSIONS=2` 只是单副本槽位数。

### 3.3 代码解释器类型（决定会不会进沙箱）

`bisheng_code_interpreter` 读库表 `t_gpts_tools_type.extra`（内置工具配置写在类型上，行上的 `extra` 常为 NULL）：

```json
{
  "type": "container",
  "config": {
    "container": {},
    "local": {},
    "e2b": { "api_key": "" }
  }
}
```

| 页面上的选项 | `type` | 行为 |
|--------|------|------|
| 本地隔离运行 | `local` | 在 backend / worker 本机进程里跑，不访问 `code-runner`。是否换成临时 uid，看 `local_isolation`（见 3.4），页面上没有单独的开关 |
| 沙箱运行 | `container` | HTTP 租约进自建 `code-runner` |
| E2B沙箱运行 | `e2b` | 云端 E2B，与自建副本池无关 |

存量升级**不会**悄悄改成 `container`。页面上的改法见 [沙箱使用说明](./沙箱使用说明.md)「选择执行方式」；也可以直接改 `extra.type`。

代码解释器和代码节点读的是同一份 `extra`。`sandbox_conf.code_node_enabled` 不参与这次选择。

代码节点还有一道总开关：系统配置里的 `workflow.code_node_enabled` 必须是字面量 `true`，否则节点直接拒绝执行，跟选了哪种执行方式无关。它来自配置表的 `workflow` 段（种子在 `initdb_config.yaml`），不是 `BS_SANDBOX_CONF__*`。

### 3.4 本机执行的 uid 隔离（`local` 时）

还在用 `local`（包括代码节点关掉沙箱时）的部署，可以打开本机隔离：每次执行都在一个私有目录里、以 `30000`–`39999` 中的一个临时 uid 运行，环境变量只保留白名单，并加上内存、进程数、CPU 时间、文件大小上限。设计见 [第一步方案](./LocalExecutor安全优化方案-第一步-uid隔离.md)。

| 环境变量 | 默认 | 说明 |
|----------|------|------|
| `BS_SANDBOX_CONF__LOCAL_ISOLATION` | `off` | 设 `uid` 开启；只有空串或 `off` 表示关闭，其他值都按 `uid` |
| `BS_SANDBOX_CONF__LOCAL_RUN_ROOT` | `/tmp/bisheng-local-run` | 私有运行目录的父目录 |

代码里的默认值是 `off`；仓库自带的 `docker/docker-compose.yml` 在 `backend`、`backend_worker` 上设为 `${LOCAL_ISOLATION:-uid}`，即 Compose 部署默认开启，要关闭就在 `docker/.env` 里写 `LOCAL_ISOLATION=off`。Helm 部署需要在 values 里自行加上。

其余限额字段（`LOCAL_RLIMIT_*`、`LOCAL_DISK_LIMIT_BYTES`、`LOCAL_COPY_IN_*`）见方案的"配置字段"一节，一般不用改。

开启前提：Linux，进程是 root，镜像里有 `prlimit`，容器保留 Docker 默认能力集（含 `SETUID`、`SETGID`、`CHOWN`、`DAC_OVERRIDE`、`KILL`）。不满足时**不会退回不隔离**：灵思返回"本机代码执行环境未就绪"，代码节点直接失败，原因在服务端日志里。

开启后启动预检会改两处权限，部署侧要知道：

- `/app/bisheng`（后端代码目录）和 `/app/data`（Compose 对应宿主机 `data/bisheng`）顶层改为 `0700`。依赖以非 root 身份读写 `data/bisheng` 的运维脚本要调整。
- 宿主机上挂进来的 `config.yaml` 建议设为 `0600`、属主 root。它在 `/app/bisheng` 下面，已经被上一条挡住，这是第二道保险。

关闭（`off`）时完全保持原来的行为，首次执行打一条 WARNING。

## 4. 验收与排障

### 4.1 连通

```bash
# Compose
docker exec bisheng-backend-worker getent hosts code-runner-1
docker exec bisheng-backend-worker curl -sS -m 5 http://code-runner-1:8080/health

# Helm
kubectl -n bisheng-sandbox get sts,svc,po
kubectl -n bisheng exec deploy/bisheng-linsight -- python -c \
  "import urllib.request; print(urllib.request.urlopen(
    'http://code-runner-0.code-runner.bisheng-sandbox.svc.cluster.local:8080/health',
    timeout=5).read())"
```

健康检查应返回 `{"status":"ok"}`。真正执行时 runner 日志会出现：

```text
POST /v1/sessions
PUT  /v1/sessions/{id}/files     # copy-in
POST /v1/sessions/{id}/exec
GET  /v1/sessions/{id}/files     # copy-out（仅 exitcode=0）
DELETE /v1/sessions/{id}
```

只有 `/health`、没有 `/exec`：代码解释器仍是 `local`，或请求打在了另一套平台上。页面上改执行方式见使用说明。

### 4.2 更新镜像

用新 tag，再改 Helm values 里的 `image.tag` 后 `helm upgrade`。chart 默认 `imagePullPolicy: IfNotPresent`。节点上已经有这个 tag 时，删掉 Pod 只会用本地旧镜像再起，不会去仓库拉新层。

在宿主机上 `docker pull` 也不够：Kubernetes 用的是容器运行时自己的镜像库（常见是 containerd），和 Docker 的镜像库不是同一份。

单节点若给客户端配了 `hostPort: 4001`，滚动更新会和新旧 Pod 抢端口，chart 里前端应使用 `Recreate`；卡住时删掉旧 Pod 再等新的 Ready。

### 4.3 部署侧常见现象

| 现象 | 原因 | 处理 |
|------|------|------|
| 任务模式不打沙箱 | Compose 上 worker 没起来（灵思在它里面）；或两套平台抢了同一个 Redis | 看 2.3，不要再手动起一份；错开 Redis db |
| 勾了代码执行器仍走本机 | `t_gpts_tools_type.extra.type` 为 `local` | 页面改成「沙箱运行」，或把 `extra.type` 改为 `container` |
| 代码节点直接失败，提示 Code node is disabled | 系统配置 `workflow.code_node_enabled` 不是字面量 `true` | 在系统配置里打开。不要改 `BS_SANDBOX_CONF__CODE_NODE_ENABLED`，那一项不决定执行方式 |
| 编辑器「运行一次」选了沙箱仍失败 | backend 没带与 runner 相同的 token，或没同时挂上 `default` 和 `sandbox_net`；Helm 上 `component: backend` 被移出 `allowFrom` | 与 worker 对齐 token，并确认 backend 在沙箱网络的放行列表里 |
| 任务模式选了沙箱仍失败 | Helm 上实际在跑的是 `component: linsight` 那一份，默认网络策略不放行 | 改用 worker Pod 里已有的那份，或把 `linsight` 加进 `allowFrom`。不要两边同时跑 |
| 下载 403 | 预签名 Host 与 nginx 反代 Host 不一致 | nginx 反代 MinIO 时 `Host` 设为 `sharepoint` |
| DNS 解析失败 | worker 不在 `sandbox_net`，或 Helm 序号 / 模式写错 | Compose 检查双网络；K8s 从 0 扫 FQDN |

文件写错路径、交付物被丢掉，见 [沙箱使用说明](./沙箱使用说明.md)「产物对不上时」。任务结束后也可以直接查库：

```sql
SELECT id, status,
       JSON_EXTRACT(output_result, '$.final_files'),
       JSON_EXTRACT(output_result, '$.invalid_deliverables'),
       JSON_EXTRACT(output_result, '$.phantom_deliverables')
FROM linsight_session_version
WHERE id = '<session_version_id>';
```

`final_files` 为空且 `invalid_deliverables` 有记录：文件写过但格式不对（例如文本冒充 xlsx）。  
`phantom_deliverables` 有记录：答案里报了文件名，工作区里没有对应文件。

## 5. 安全边界

- 口径：挡住误操作和机会主义访问，**不承诺**抗定向内核 0day。
- runner：只读根文件系统、能力全裁（再加回 SETUID/SETGID/CHOWN/DAC_OVERRIDE 做会话 uid）、cgroup 限额、默认禁出站。
- runner 无中间件凭据、不挂 docker.sock。
- 本地执行器在 `local_isolation=off`（默认）时与平台同用户、同网络，可以读到工作目录之外的路径；生产应使用 `container`。开启 `uid` 隔离后换成临时 uid、读不到配置和进程环境变量，但网络仍不隔离，见 3.4。

|------|------|

| `docker/docker-compose.yml` | `code-runner-1/2` + `sandbox_net` |

| `src/backend/bisheng/core/config/settings.py` | `SandboxConf` |
| `src/backend/bisheng_langchain/gpts/tools/code_interpreter/` | `ContainerExecutor` / 发现 |
