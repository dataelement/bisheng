>
> 本 Feature 把平台工作台里「直接与模型对话」的**日常模式会话**（选模型、可选挂知识库、可选开平台工具、多轮）以**业务语义契约**开放给自建系统。**对外接口的具体形态（字段名、事件名、端点路径、是否对标某个第三方契约）由 design 决定**，本 spec 只写「调用方必须能表达什么」与「平台必须保证什么」——伴生 PRD v2.3 D9 改判，见 §4 决议-14。它站在 F049 的凭据地基与 F050 的身份传递之上，是伴生 PRD 场景二（代表员工提问、回工作台续问）在对话能力上的完整形态。它**不是**模型协议裸透传（F051）：本面建平台会话、留历史、可挂知识库与平台工具、在平台 UI 可见。
>

>   - **发起一轮日常模式对话**（仅日常模式 + 同步执行）：调用方能表达——本轮提问、模型（工作台可用模型，按名）、会话标识（续接同一会话）、可选知识库挂载、可选平台工具、可选附件引用、可选业务上下文指令（叠加于平台提示词）、返回方式；流式与非流式两种返回

>   - **采样 / 生成参数的逐次透传**（temperature / top_p / max_output_tokens 等）——本版由平台工作台模型配置决定、明确拒绝（§4 决议-5）

## 1. 用户故事

作为 **自建业务系统的集成方（如在企业 OA 内嵌问答入口）**，
我希望 **用一把服务账号密钥、按业务语义直接描述「代表谁、问什么、在哪个会话里、挂哪些知识库与工具」发起对话并多轮续接，而不必自己组织 messages / role 结构或拼装 system message**，
以便 **不为平台学一套私有会话协议、不自己拼装权限过滤，员工在 OA 里问到的与在 BiSheng 里问到的完全一致**。

作为 **被代表的员工**，
我希望 **在自建系统里发起的对话，回到 BiSheng 工作台就能看到同一个会话并继续追问**，
以便 **对话不因入口不同而割裂，两个入口只是同一段工作的两个窗口**。

作为 **面向外部访客提供应用的开发方（场景三）**，
我希望 **以服务账号身份为每个访客开会话、用外部标识把访客彼此分开，访客只在管理员授予该服务账号的知识库范围内得到回答**，
以便 **访客不被平台的用户权限体系卡住，同时也不会看到任何超出该应用授权的内容**。

作为 **租户管理员**，
我希望 **通过与其它开放 API 同一张权限位清单授予「日常模式会话」能力、在服务账号授权页决定它能挂哪些知识库、在审计里同时看到哪个系统调的和以谁的名义调的**，
以便 **对话能力的开放与其它开放能力同一套治理，不多一套后台、不少一份追溯**。

作为 **调用方开发者**，
我希望 **传错了字段、用错了工具类型、传了本版不支持的能力时得到明确报错**，
以便 **不会以为工具或知识库已经生效、实际跑的是无工具对话；也不会因为打开异步就被静默切到另一种运行模式**。

## 2. 验收标准

> AC 编号在本特性内唯一。与伴生 PRD §五验收标准的对应关系在括号中标注（如 `↔伴生 AC-34`）；伴生未单列 AC 的需求以章节号标注（如 `↔§4.6.3`）。
> 错误码在此仅作为可观测的对外行为引用（`26015` / `26017` / `26010` / `26016` 取自伴生附录 C），其定义与归属写在 design.md。**本节 AC 一律以业务语义表述**：「一轮结果」「会话标识」「运行模式」「传输方式」等指对外可观测的业务概念，其字段名、结构与端点路径由 design 决定（§4 决议-14）；已实现清单以对外文档为准（AC-10）。
> **「明确错误」判据（本 spec 全部拒绝 / 不可用分支统一按此验收）**：4xx 状态 + 平台错误码（可被调用方程序化区分）+ 指明出错项（字段名 / 附件标识 / 模型名 / 工具项 / 未开放的能力名）；不静默忽略、不部分接受、不 5xx。仅归属类校验例外——按 AC-21 一律 404 且形状不区分「不存在 / 不属于你」。

### 2.1 端点与契约

- **AC-01** — THE SYSTEM SHALL 提供**发起一轮日常模式对话**的能力：接受以业务语义表达的请求（伴生 §4.6.3 二的入参清单），返回本轮结果；本版只承接**日常模式**（未指定运行模式时即日常模式）×**同步执行**（未指定时即同步）——两者是**两个独立维度**（运行模式 / 传输方式，伴生 D11），各自缺省、各自校验、各自拒绝；同时支持流式与非流式两种返回方式，缺省值由 design 决定并写入对外文档。**端点路径、字段名与请求形态归 design**（§4 决议-14）。（↔伴生 §4.6.3 二 / 三 / D9 / D11；§4 决议-9）
- **AC-02** — WHEN 请求未携带**会话标识**, THE SYSTEM SHALL 创建一个新的平台会话、在其中生成本轮结果，并在返回中给出该会话标识；WHEN 携带会话标识, THE SYSTEM SHALL 在**同一会话**中续接本轮（可见此前全部轮次上下文，含模式 D 下该用户在平台工作台内新增的轮次）。平台会话**线性追加、不支持分叉**：调用方不指定"从哪一轮接着说"，只指定"在哪个会话里说"。多轮对话**只**经此机制续接，调用方无需也不得回传历史消息（AC-09）。（↔伴生 §4.6.3 二「会话标识」/ AC-36；§4 决议-3）
- **AC-03** — THE SYSTEM SHALL 提供**按轮次标识取回单轮结果**的能力：返回经本 API 创建并**留存**的终态轮次结果（失败轮次不留存，AC-16 / 18），内容与该轮非流式返回一致；轮次标识为**不透明标识**（不递增、不可由顺序或平台内部标识推得、不可枚举）；平台工作台内产生的轮次不经此能力暴露。（↔伴生 §4.2.4「按标识取回单轮结果是唯一保留的读动作，并入 `chat:invoke`」）
- **AC-04** — THE SYSTEM SHALL 使调用方**用通用 HTTP 客户端即可完成本 Feature 的全部能力**，不需要平台专有 SDK、不需要任何平台专有的签名或握手步骤；对外文档须给出**可直接运行的调用示例**（至少覆盖：首轮提问、续接一轮、挂知识库、开平台工具、带附件、流式与非流式各一），示例随契约变更同步更新。（↔伴生 §4.6.3 三.8；**原「响应体可被 OpenAI 官方 SDK 反序列化」已随伴生 v2.3 D9 取消为需求**，见 §4 决议-14）
- **AC-05** — WHEN 请求以对外文档约定的形式选择知识库（可挂多个；模式 D 下可含被代表用户的个人知识库）, THE SYSTEM SHALL 在生成时检索这些知识库，并把引用以**可与回答正文区分的形式**随本轮结果返回（具体承载形式归 design，AC-15）；可挂范围 = 执行身份被授权可见的知识库，过滤强度（含文件级）与该身份在平台工作台内挂同一知识库对话时**集合相等**；IF 所选知识库超出执行身份的授权, THEN THE SYSTEM SHALL 返回业务模块既有的资源权限错误（与缺权限位的 403 可区分）并指明该知识库；IF 模式 S 下启用个人知识库, THEN THE SYSTEM SHALL 返回 400 明确错误（错误码引用、指明「个人知识库」项：服务账号无个人知识库）而不静默按空集执行。（↔伴生 §4.6.3 二「知识库」/ 三.4；F049 AC-36 同形；伴生 AC-12 取向）
- **AC-06** — WHEN 请求声明启用平台工具（声明形式归 design）, THE SYSTEM SHALL 使这些工具在本轮生效（**由平台侧执行**）、可用范围 = 平台工作台配置对执行身份开放的工具；IF 出现无法识别的工具声明（含本版不支持的、由调用方执行的工具类型）或不在可用范围内的工具, THEN THE SYSTEM SHALL 返回 400 明确错误（错误码引用、指明该工具项），**不得静默忽略后按无工具对话执行**。（↔伴生 AC-34 / §4.6.3 三.2；§4 决议-6）
- **AC-07** — THE SYSTEM SHALL 要求**模型必填**、取值为平台工作台配置中对执行身份可用的对话模型名称；名称基准与跨服务商同名歧义的处置与 F051 一致（模型管理页原名精确匹配、歧义时拒裸名并给出限定名、不取默认）；IF 模型不在可用范围（不存在 / 已下线 / 不在工作台配置内 / 不属于本租户）, THEN THE SYSTEM SHALL 返回 4xx 明确错误（错误码引用、指明模型名与原因），对其它租户的模型按「不存在」处理。（↔伴生 §4.6.3 二「模型」；F051 AC-11–13 同源；§4 决议-8）
- **AC-08** — WHEN 请求携带**业务上下文指令**（一段文本，如当前页面 / 当前工单）, THE SYSTEM SHALL 把它作为本轮的调用方指令**叠加于**平台工作台既有系统提示词之上生效——不替换、不关闭平台提示词；未携带时按平台既有提示词执行。**不要求调用方自行拼装 system message 或组织 messages / role 结构**（伴生 §4.6.3 二）。（§4 决议-7）
- **AC-09** — THE SYSTEM SHALL 使本轮输入所接受的内容只有两类：**本轮用户文本**、**已上传附件的引用**（经上传端点所得标识）；拒绝清单：历史消息 / 角色结构、内联文件数据、外链文件 URL、其它本版不支持的输入类型——IF 请求含拒绝清单中的任一项, THEN THE SYSTEM SHALL 返回 400 明确错误（错误码引用、指明该项），不静默丢弃、不部分接受。各类别的具体形状以对外文档为准。（§4 决议-5 / 决议-11）
- **AC-10** — THE SYSTEM SHALL 随本 Feature 交付对外接口文档：逐项列出已实现的入参 / 返回内容 / 事件类型 / 拒绝清单 / 本次未开放能力的报错形态，并**分别**说明两个维度的语义——**运行模式**（日常模式 / 任务模式·灵思，缺省日常，本版仅前者）与**传输方式**（同步 / 异步，缺省同步，本版仅前者），文档须明确二者**互不蕴含**，不得表述为「用某一个开关同时决定模式与同步/异步」；WHERE design 选择了对标某个第三方契约, 文档须显式声明只承诺已开放能力、不承诺其完整 API 面。F050 AC-15「`X-Bisheng-End-User` 语义声明原样写入对外文档」在本面文档同样生效；说明既有 `POST /api/v2/assistant/chat/completions` 与 F051 `model:invoke` 面各自的适用范围。（↔伴生 §4.6.3 三.8 / 五；F050 AC-15）

### 2.2 入参清洗与拒绝

- **AC-11** — THE SYSTEM SHALL 只接受对外文档列出的已实现入参；契约之外的字段（不论它在 design 所选形态的原契约里是否存在）一律返回 400 明确错误（错误码引用、指名字段），**不得静默忽略**。「接受但不生效」档只容忽略后不改变调用方可观察行为的字段且**必须在本 spec 枚举——本版该清单为空**（不存在任何被接受却不生效的字段；将来要加入须先修订本条），无法枚举的字段一律 400。（↔伴生 §4.6.3 二 / 三.2；§4 决议-5）
- **AC-12** — THE SYSTEM SHALL 对以下请求意图明确返回 400 并指明原因、不静默降级：**要求本轮不留痕**（平台会话机制一律留痕，不留痕的模型调用应走 `model:invoke` 面）；**在请求体内另传终端用户标识**（该标识只经 `X-Bisheng-End-User` 头传递、不设第二来源）；**采样与生成参数**（temperature / top_p / 最大输出长度等，本版由平台工作台模型配置决定）；**任务模式专属入参**（如技能选择）；**要求异步执行**（AC-25）；**要求任务模式**或指定枚举外的运行模式（AC-37）。（§4 决议-5 / 决议-13；伴生 §4.6.3 三.2）
- **AC-13** — THE SYSTEM SHALL 使对外契约不出现、不要求任何平台前端专用或已废弃的内部字段，也不暴露任何平台内部标识（内部会话 id / 消息 id / 租户 id / 用户 id）——多轮只以对外的**会话标识**表达，该标识不得可反推平台内部标识。（↔伴生 §4.6.3 二「不要求理解任何平台内部概念」；附录 E.3 的 9 个零消费字段清单）

### 2.3 事件流与返回内容

- **AC-14** — WHEN 调用方选择流式返回, THE SYSTEM SHALL **边生成边推送**（不缓冲整段后一次性返回）；每类平台内部事件对应一个**语义可区分的对外事件**、事件流中不出现平台内部事件名；每次执行以且仅以**一个终态事件**（成功 / 失败 / 未完成）收尾，事件顺序稳定且在对外文档中列明。（↔伴生 §4.6.3 三.4）
- **AC-15** — THE SYSTEM SHALL 使**思考过程、回答正文、平台工具的调用与结果、知识库引用**在返回内容中各有**可区分的承载**（各自的类型与字段属 design、以对外文档为准），不得把它们混成一条纯文本流；WHERE design 选择了对标某个第三方契约, 平台特有的内容一律使用 BiSheng 自有命名、**不冒用**该契约中已有名称的语义——占用同名等于做出兑现不了的兼容承诺。（↔伴生 §4.6.3 三.4 / 五；§4 决议-6）
- **AC-16** — IF 生成过程中模型 / 工具 / 检索失败或上游中断, THEN THE SYSTEM SHALL **流式**下先发错误事件、再以失败终态事件收尾并关闭连接、不挂起；**非流式**下返回明确错误响应（错误码引用、指明失败环节），**不返回带失败状态的正常结果对象**——失败只有一种真相；失败轮次不留存（AC-18），用其标识取回时按 AC-21 处理，该会话仍可正常续接下一轮。
- **AC-17** — THE SYSTEM SHALL 使非流式返回的结果与同一请求流式执行时由事件流聚合出的最终结果**内容一致**（同一内容集合、同一状态、同一用量口径）。（§4 决议-9；伴生 §4.6.3 三.4）
- **AC-18** — IF 一轮执行失败或调用方在流式过程中断开连接, THEN THE SYSTEM SHALL 使该轮**不在会话历史留下半条消息**（要么以完整消息留存、要么不留任何痕迹）、不留下永久“进行中”的记录、同一会话不因此被锁死、后续可正常续接下一轮。

### 2.4 身份与会话隔离

- **AC-19** — WHEN 以模式 S（密钥不持 `delegate` 且未携带 `X-Bisheng-On-Behalf-Of`，F050 AC-02）发起对话, THE SYSTEM SHALL 使会话归属服务账号并按 `X-Bisheng-End-User` 分区；F049 AC-25（模式 S 会话不进资源归属人或任何自然人的会话列表，定义 6 边界 a）、F050 AC-11（外部标识不改变任何权限判定与可见范围）与 F050 AC-13（未传头记 WARN、不阻断、分区键为空）在本能力上同样生效。（↔伴生 §4.6.3 四；伴生 AC-43）
- **AC-20** — WHEN 模式 D（持 `delegate` 且传 `X-Bisheng-On-Behalf-Of`，经 F050 五道准入）发起对话, THE SYSTEM SHALL 使会话归属**被代表用户**、以其权限基准执行（模型 / 知识库 / 工具 / 个人知识库范围同其本人在工作台所见）；该会话在被代表用户的 BiSheng 工作台会话列表中可见、可在工作台继续追问；工作台侧新增的轮次同样进入该会话，API 下一次以同一会话标识续接时可见（AC-02）；本轮上传的附件同样归属该用户。会话归属规则本身由 F050 AC-38 拥有，本条承接其端到端验收。（↔伴生 AC-32；§4.6.3 四；定义 6「与模式 D 并存时以被代表用户为准」）
- **AC-21** — WHEN 取回轮次结果、会话标识或附件引用所指向的轮次结果 / 会话 / 附件不属于当前调用的会话归属主体——模式 S 下服务账号不一致或 `X-Bisheng-End-User` 分区键不一致（含一方为空、另一方非空）、模式 D 下被代表用户不一致、跨租户、或该 id 不存在 / 未留存——, THE SYSTEM SHALL 一律返回 404 且响应形状不区分「不存在」与「不属于你」（不用 403、不泄漏该对象是否存在）；归属校验以会话归属主体为基准、**不按单把密钥**区分（同一服务账号的不同密钥、同一被代表用户经不同委托密钥视为同一归属）。（↔伴生 §4.6.3 四.1「外部标识不匹配返回 404」；§4 决议-3）
- **AC-22** — THE SYSTEM SHALL 使本 Feature 三个端点上 F049 的租户上下文规则同样生效（凭据校验通过后一切业务查询按密钥所属租户过滤，F049 AC-07 / §3「凭据校验先于租户上下文」）；会话、附件、response 一律落在该租户内，跨租户不可见（按 AC-21 的 404 处理）。
- **AC-23** — THE SYSTEM SHALL 使 F050 AC-12（模式 S 下外部标识作为会话分区键写入）在本 Feature 两个有会话语义的能力（发起对话、上传附件）上同样生效；本版分区键**不作为任何列举 / 过滤维度、不经任何端点返回，仅用于归属一致性校验**（AC-21 / AC-29）——这是 F050 AC-12「只写不读」在本面的精确化。（↔伴生 §4.6.3 四.3；§4 决议-4）
- **AC-24** — WHEN 本 Feature 三个端点被调用（含被拒绝的调用）, THE SYSTEM SHALL 使 F050 AC-35（开放 API 逐调用审计）与 F050 AC-36（模式 D actor / subject 双归属）在本端点上同样生效；本面特有约束：审计不含会话消息正文与附件内容。（↔§4.8.1；伴生 AC-23）

### 2.5 异步分支留位与不暴露能力

- **AC-25** — IF 请求要求**异步执行**, THEN THE SYSTEM SHALL 返回 400（`26015`）且不创建会话、不执行任何生成、**不静默按同步执行**；该判定**只针对传输方式**，与运行模式无关。（↔伴生 AC-35；附录 C）
- **AC-26** — THE SYSTEM SHALL 为异步分支的两项能力（**取消**、**断点续传**）在契约文档中留位并标注「随异步分支点亮」；本版调用它们得到 4xx 明确错误（错误码引用、指明未开放的能力名「异步执行」；错误码与 `26015` 同族或复用，归 design），不静默成功、不 5xx、不实现为对同步结果的伪取消或伪续传；**同步分支的入参、返回内容、事件类型与错误形状不得为将来点亮异步分支预留任何需要调用方改代码的差异**。（↔伴生 §4.6.3 一「须留出演进位」/ 六「演进要求」；附录 B.1）
> 运行模式（任务模式）的留位与拒绝见 **AC-37**（§2.9）——与本节的传输方式留位并列、互不替代。
- **AC-27** — THE SYSTEM SHALL NOT 提供任何按会话 / 按用户 / 按外部标识列举轮次结果或会话的能力（含会话列表、会话历史查询、任何列表形态的读端点），也不提供会话反馈写入与消息回填；F049 已关闭的 6 个 `/chat/*` 端点不因本 Feature 复活；不占用 `/conversations` 路径。（↔伴生 §4.2.4「不设 `session:*`」/ §4.6.3 一「明确不做」；F049 AC-30）

### 2.6 会话附件上传

- **AC-28** — THE SYSTEM SHALL 提供**会话附件上传**能力（`chat:invoke`）：上传单个附件并返回可在发起对话时引用的附件标识；它是有会话语义的能力：附件的归属主体与 `X-Bisheng-End-User` 分区键（若传）随上传记录（AC-19–23），供发起对话引用时做归属一致性校验（AC-29）。（↔伴生 §4.6.3 二「附件引用」/ 三.6；附录 E.3 复用映射）
- **AC-29** — IF 发起对话时引用的附件标识不存在、归属主体不一致、`X-Bisheng-End-User` 分区键不一致（含一方为空、另一方非空）、被代表用户不一致或跨租户, THEN THE SYSTEM SHALL 返回 404（AC-21 口径、形状不区分）且不执行生成；IF 附件尚不可用于对话（如仍在解析）或解析失败, THEN THE SYSTEM SHALL 返回 4xx 明确错误（错误码引用、指明该附件标识与原因）而不静默忽略该附件后继续作答。
- **AC-30** — THE SYSTEM SHALL 使附件的类型白名单、单文件大小上限与每轮附件数量上限**沿用平台工作台既有上传限制**（同一配置、同一判定），超限或类型不允许时返回 4xx 明确错误（错误码引用、指明触发的限制项与限值）；本 Feature 不新增独立的附件配额或计量维度。（§4 决议-11）

### 2.7 权限位与互不蕴含

- **AC-31** — THE SYSTEM SHALL 使本 Feature 三项能力（及留位的两项异步能力）均要求 `chat:invoke`；IF 凭据有效但缺该位（含仅持 `model:invoke` 或其它任何位的密钥）, THEN THE SYSTEM SHALL 返回 403 并指明缺少 `chat:invoke`（F049 AC-04 同形）；`chat:invoke` 与 `model:invoke` **互不蕴含**——反向（持 `chat:invoke` 而无 `model:invoke` 调模型协议面被拒）由 F051 AC-06 承接。（↔§4.2.4 权限位表 / 扩展位表 `model:invoke` 行）
- **AC-32** — THE SYSTEM SHALL 使 F049 AC-01（无凭据 401、无回落路径）/ AC-03（撤销 5 秒内拒绝）/ AC-21（主体停用 / 删除 5 秒内拒绝）/ AC-34（权限评估失败即 5xx、不返回任何结果）在本 Feature 端点上同样生效；被拒时不创建会话、不返回任何数据。（↔INV-27 / INV-28 / INV-30）
- **AC-33** — WHEN 本 Feature 端点上线, THE SYSTEM SHALL 使 F049 权限位清单中既有的 `chat:invoke` 位（伴生 §4.2.4 基础位、始终在清单中；开放前表单标注「端点随后续版本开放」——F049 范围边界）的说明与悬停所覆盖端点指向本 Feature 三个端点与两个留位端点、去除该标注；本 Feature 只拥有该位的**消费端点**，不拥有位的定义、分组或出现与否，不新增第二处位定义。（§4 决议-10；F049 AC-13 / AC-44）
- **AC-34** — THE SYSTEM SHALL 使本 Feature 端点按伴生附录 B.1 声明允许模式 S/D（F050 AC-07 的端点声明）；F050 AC-30（持 `delegate` 漏传头 400 `26016`、不落回模式 S）、F050 AC-14（两身份头并存 400 `26010`）、F050 AC-04（不持 `delegate` 传头 403，伴生 AC-6）在本端点上同样生效——判定与错误由 F049 / F050 的同一鉴权路径给出，本 Feature 不另设第二套判定。（↔INV-27 / INV-30）

### 2.8 审查修订追加（2026-08-17）

- **AC-35** — WHILE 某会话的上一轮尚未收敛到终态（生成中）, IF 再次以该会话标识续接, THEN THE SYSTEM SHALL 返回 4xx 明确错误（错误码引用、指明「会话忙」与该会话当前进行中的轮次标识）且不并行写入同一会话；上一轮收敛后按 AC-02 正常续接。
- **AC-36** — THE SYSTEM SHALL 使本 Feature 端点属 v2 开放 API 主体、**不受开放能力层部署开关约束**：WHERE 开放能力层未部署, 本 Feature 三个端点（及两个留位端点）对持 `chat:invoke` 的服务账号密钥同样可达、行为无差异（与 F051 AC-28 / F052 / F053 三面「未部署即不可达」不同）；服务账号模块恒在（F049 AC-49）。

### 2.9 运行模式留位追加（2026-08-17，伴生 D11）

- **AC-37** — IF 请求要求**任务模式（灵思）**, THEN THE SYSTEM SHALL 返回 400（`26017`）且不创建会话、不执行任何生成、**不静默退化为日常模式**；IF 请求指定枚举（日常 / 任务）之外的运行模式, THEN THE SYSTEM SHALL 同码返回 400 并指明该项；WHEN 未指定运行模式, THE SYSTEM SHALL 按日常模式执行。`26017`（任务模式能力未开放）与 `26015`（异步传输未开放）**互相独立、不得合并为一个码**：同时触发两者时都不放行，且响应须能让调用方分辨是哪一项未开放，二者将来可各自独立点亮。（↔伴生 AC-50 / D11；附录 C）

## 3. 边界情况

> 只写期望的对外行为；实现层的落点、映射与数据访问细节见 design.md §5。

- **两个维度各自留位，不合并成一个开关**（伴生 D11）：**运行模式**（日常 / 任务·灵思，对应内部 `task_mode`）与**传输方式**（同步 / 异步）正交，承载字段归 design。合并的后果有取证：内部两个分支（`_task_mode_stream_completion` / `_agent_stream_chat_completion`）**都是同步 SSE 流**，「模式 ⟷ 同步/异步」的映射不成立；且调用方打开异步的动机通常只是躲网关超时，若因此被切到灵思，拿到的是耗时、计费与输出形态都不同的另一种能力。任务模式的四条技术前置见伴生 §4.6.3，本 spec 只引不写；本 Feature 对两个维度的全部承诺 = 各自明确拒绝（AC-37 / AC-25）+ 形态留位（AC-26）。将来任一维度点亮都不改已开放的日常模式同步契约，且「日常模式 + 异步」这一格保持可开。
- **会话标识跨会话 / 跨用户一律 404**（AC-02 / AC-21）：不能用它探测别人的会话是否存在。平台会话**线性追加、不支持分叉**——调用方只说"在哪个会话里说"，不说"从哪一轮接着说"，因此不存在"指向历史轮次"这一分支（**该分支随伴生 v2.3 D9 改判连同 `previous_response_id` 机制一并消失，决议-3 已订正**）；模式 D 下员工在工作台续问的轮次自动进入同一会话，API 下一次续接直接可见。失败轮次不留存、不占位（AC-16 / 18）。上一轮生成中再次续接 → 「会话忙」（AC-35），不并行写入。归属校验以**会话归属主体**为基准而非单把密钥：密钥可轮换、可多把，会话不因此失联。
- **End-User 分区键与定义 6 边界 a**：模式 S 会话永远归服务账号、按 `X-Bisheng-End-User` 分区、不进资源归属人的会话列表——归属人机制解决的是「知识库归谁认领」，会话不算资源，否则 §3.3 那个缺陷会被新机制请回来。分区键不改变任何权限判定（F050 AC-11）；本版它**不作为任何列举 / 过滤维度、仅用于归属一致性校验**——取回轮次结果、会话标识、附件引用三处都要求分区键与创建时一致（AC-21 / AC-29），这也是场景三里访客 A 拿不到访客 B 的结果与附件的唯一防线；缺省 WARN 不阻断（F050 AC-13），因为串档的两个成立条件（共享身份 + 可按身份列举会话）本版只具备第一个——**将来若补做任何按用户 / 按外部标识列举会话的端点，必须先把缺省行为改为强制**（原 `26014` 的语义），本 spec 把这条写进 AC-23 / AC-27 的守门口径。
- **契约外字段的处置原则**：白名单式接受 + 契约外 400 指名字段（AC-11）；「接受但不生效」档只容忽略后不改变可观察行为的字段且须在本 spec 枚举——**本版清单为空**。反面教材是同名不同义的工具声明导致的**静默降级成无工具对话**——本面宁可拒绝也不静默（伴生 §4.6.3 三.2）。要求不留痕、在请求体内另传终端用户标识、采样参数、由调用方执行的工具、历史消息 / 角色结构、内联与外链文件均属明确拒绝（AC-06 / 09 / 12）。
- **失败与中断的单一真相**：流式失败 = 错误事件 + 失败终态事件收尾、不挂起；非流式失败 = 错误响应、不返回带失败状态的正常结果（AC-16）；失败或断连的轮次不在会话历史留下半条消息、不留永久"进行中"、会话不锁死（AC-18）；非流式与流式的成功结果一致（AC-17）。合起来保证「按标识取回单轮结果」只有两种结果——留存的终态结果或 404，不存在第三种状态。
- **附件**：大小 / 类型 / 数量沿用平台工作台既有上传限制（AC-30），不为开放 API 另设一套；只经上传端点获得标识、不接受内联数据与外链 URL（AC-09）——外链拉取是新的出站请求面，本版不开。附件归属跟随会话（模式 D 归被代表用户），不算「资源」、不落归属人名下。
- **模型可用范围与 F051 不必相同**：本面 = 平台工作台配置中启用的对话模型（与员工在工作台里可选的一致），F051 = 模型管理页全部已启用对话模型；两者各按其产品面配置，但**名称基准与歧义规则同源**（AC-07），避免同一个模型名在两面解析成不同服务商。
- **两层判定与 F049 一致**：`chat:invoke` 位（AC-31）∧ 执行身份对具体知识库 / 工具 / 模型的授权（AC-05 / 06 / 07），两层失败可区分；模式 S 下服务账号能挂哪些知识库只由其主体侧授权页决定（F049 §2.7），与资源归属人本人的权限无关（定义 6 边界 c）。位本身在 F049 清单中恒在（开放前标注「端点随后续版本开放」），本 Feature 上线只是让它有了消费端点（AC-33）。
- **不受开放能力层开关约束**（AC-36）：本面是 v2 开放 API 的一部分、与服务账号模块同属「发布即带鉴权」的开放 API 主体，不像 F051 / F052 / F053 三面那样随开放能力层部署与否出现或消失；标准版（未部署开放能力层）同样可用。
- **平台特有内容只用自有命名**（AC-15 / 28）：WHERE design 选择了对标某个第三方契约, 一律不冒用该契约中已有名称的语义（含路径名、工具类型名、对象名）——占用同名即做出兑现不了的兼容承诺（伴生 §4.6.3 五同一取向）。
- **轮次标识不可枚举、工作台轮次不经本 API 暴露**（AC-03）：模式 D 的被代表用户在工作台看得到会话，但 API 侧只能取回经 API 创建的轮次结果——避免以委托身份逐个猜标识拉取该用户在工作台内的全部对话。
- **三个对外面各说各的适用范围**（AC-10）：既有 `POST /api/v2/assistant/chat/completions` 是助手外壳的 Chat Completions 形态、本次不动；F051 是模型协议面的 Chat Completions 形态（另一数据面，承接"拿通用 OpenAI 客户端直连"的诉求）；本面是应用级会话面、形态归 design。三者在文档中各说各的适用范围，不互相顶替——**本面不再承担 OpenAI 兼容职责**（伴生 v2.3 D9 / §7.5）。
- **模式 D 是主场，不可只出模式 S**（依赖 F050）：纯模式 S 跑得起来，但服务账号的个人知识库为空、会话在平台 UI 里无人可见，场景二的核心承诺（AC-20）落不了地；本 Feature 与 F050 同期发版，spec 里凡引用两身份头判定处均以 F050 为准。
- **第二套并行契约已在伴生 PRD 层面关闭**（D12 + §六非目标；本 spec §4 决议-2 与之一致）：不做 Chat Completions 薄兼容层，也不留占位。它承载不了平台工具与知识库引用，交付即等于让客户在「能力不全」与「再学一套」之间二选一。「第三方生态支持度」属**待验证假设而非已确认诉求**；想拿通用 OpenAI 客户端直连的诉求由 F051 `model:invoke` 面承接；将来若出现真实客户场景，单独立项重估，不改本面契约；自建后端直调 HTTP 不受影响。
- **审计**：本面调用频率介于管理操作与模型面之间，逐次记录按开放 API 通用口径进审计（AC-24）；具体落点、写路径与 F051 逐条模型调用记录的关系属 design（DM8 写放大教训沿用）。

## 4. 待澄清决议

> 2026-08-17 用户授权全自动模式：以下各项按建议直接定案，记录理由与备选供追溯；spec 评审（`/sdd-review`）后如有 high 级发现再增补。Discovery N2「F058 是否进 v3.0.0」在此复述为决议-1。

- **[决议-1] 版本层登记为 v3.0.0 Feature、排期由产品定；与 F050 同期、不可只出模式 S；不在 MVP-114 纵切上。** 理由：伴生 PRD §1.4 明确「日常模式会话开放依赖身份传递、两项须同期交付」且要求估算重算（会话列表已移出，应下调）；PRD-1 全册零引用，Discovery N2 已定「登记为版本层 Feature、排期由产品定」。备选 = 直接排进 v3.0.0 必做——PRD-1 主线（应用工场）不依赖它，强绑会拖累 MVP。**何时重新考虑**：产品确认场景二客户（如中粮式 OA 嵌入）的交付窗口时。若本 Feature 不随 v3.0.0 发版，`chat:invoke` 位仍在 F049 清单中并保留「端点随后续版本开放」标注（决议-10）、附录 B.1 中日常模式会话相关行随之顺延，其余 v2 开放 API 契约不受影响。
- **[决议-2] 不为本能力交付第二套并行契约（如 Chat Completions 薄兼容层）。**（2026-08-17 伴生 **D12** 已把它从「待客户场景决定」改判为明确不做并写入 §六非目标；2026-08-18 随 D9 泛化为形态无关的规则）理由：薄层承载不了平台工具与知识库引用，而这两项是日常模式相对裸模型的全部增量价值——交付一个功能残缺的第二契约，等于让客户在「能力不全」与「再学一套」之间二选一；平台内已有两个 OpenAI 形态的对外面（既有助手端点 + F051 模型协议面），再加第三个只会加深「哪个端点该用哪个」的困惑；「第三方生态支持度」目前是**待验证假设而非确认诉求**，且该诉求本就由 F051 承接。备选 = 同期做薄层（无平台工具、无引用）——多一条契约多一份映射维护，且能力残缺，否决。**何时重新考虑**：出现确认的客户须直连某生态工具而 F051 面也无法满足时，单独立项重估，不改本面契约、不在本版留占位。
- **[决议-3] 取回轮次结果、会话标识与附件引用的归属校验基准 = 会话归属主体（模式 S：服务账号 + `X-Bisheng-End-User` 分区键；模式 D：被代表用户），不按单把密钥；不匹配、跨租户、不存在一律 404 且形状不可区分；只能取回经本 API 创建并留存的轮次结果，标识为不透明值。多轮以「会话标识」表达，不以「上一轮标识」表达。**（2026-08-18 随伴生 D9 改判修订：原「`previous_response_id` 只允许指向会话最新、指向历史 → 400」是 Responses 形态的产物，改用会话标识后该分支自然消失）理由：平台会话线性追加、工作台无分叉，用会话标识表达多轮与产品语义天然一致，也省掉「最新 / 历史」的一整套判定；伴生 §4.6.3 只定了「外部标识不匹配返回 404（不用 403）」，须补齐基准——密钥可轮换、一个服务账号可多把密钥，按密钥校验会让轮换后旧会话失联；模式 D 下会话本就归被代表用户（工作台可见），同一用户经不同委托密钥取回同一轮次结果与其在工作台看到的一致。404 不区分「不存在 / 不属于你」是为了不泄漏存在性（与伴生 AC-8 / AC-41 同一取向）。「只取回 API 创建的」是防以委托身份逐个猜标识拉取该用户在工作台内的全部对话。备选 = 按密钥校验（更严但轮换即失联，否决）；备选 = 模式 D 下允许取回该用户工作台任何轮次（把「不设 session:read」从后门打开，否决）；备选 = 保留「上一轮标识」机制——多一套「是否最新」的判定与错误分支，而调用方并不需要分叉能力，否决。
- **[决议-4] 分区键在本 Feature 两个有会话语义的能力（发起对话、上传附件）上按 F050 AC-12 写入；本版不作为任何列举 / 过滤维度、不经任何端点返回，仅用于归属一致性校验（取回轮次结果 / 会话标识 / 附件引用三处）；缺省 WARN 不阻断（F050 AC-13）。与 F050 AC-16 的分界：无会话语义的端点携带 `X-Bisheng-End-User` 只留审计、不产生其它效果，而本面两项能力有会话语义、走 F050 AC-12 的写入并在本 Feature 内消费。** 理由：伴生 §4.6.3「仍然要写分区键，尽管本次没人读它」——一次性成本极低，将来补「按终端用户查询会话」时存量会话已带维度、不必回头补数据；`26014` 强制约束随会话列表端点一并移出（串档成立条件不齐）。备选 = 本版不持久化——将来补数据成本高且存量不可补，且场景三里访客 A 就能拿到访客 B 的结果，否决；备选 = 严格「只写不读」连归属校验也不读——那取回单轮结果在模式 S 下就只剩服务账号一层，同一服务账号下的全部访客互相可读，否决。**红线**：将来若增加任何按用户 / 外部标识列举会话的端点，必须先把缺省行为改为强制（AC-23 / AC-27 守门口径）。持久化落点属 design（伴生附录 E.3 有建议）。
- **[决议-5] 契约外字段处置 = 白名单式接受、契约外 400 指名字段；明确拒绝清单：要求本轮不留痕、在请求体内另传终端用户标识、采样 / 生成参数（temperature / top_p / 最大输出长度等）、任务模式专属入参（技能选择等）、历史消息 / 角色结构、内联文件数据与外链文件 URL；「接受但不生效」档只容忽略后不改变可观察行为的字段、须在本 spec 枚举、**本版清单为空**。** 理由：核心教训是「调用方按直觉传了、平台静默降级」——同名不同义的工具声明就是这样静默变成无工具对话；本面对任何会让调用方误以为生效的字段一律明确拒绝。「不留痕」与平台会话机制矛盾（不留痕请走 `model:invoke`）；请求体内的终端用户标识与 `X-Bisheng-End-User` 是同一语义的两个来源、只留请求头一处；采样参数在平台工作台链路里由模型配置决定、本版不做逐次透传（透传 = 新能力，且工作台自身也不支持逐轮改采样）；塞历史消息 = 无状态用法，与「服务端会话」的有状态设计双真相；内联 / 外链文件绕开平台上传与解析链路、外链还是新的出站请求面。备选 = 采样参数「接受但不生效」——违反「不改变可观察行为」判据，否决；备选 = 采样参数透传——待平台工作台链路支持逐轮采样时再开。**何时重新考虑**：工作台链路支持逐轮采样参数、或出现须回传历史的真实集成场景时，逐项从拒绝清单移到已实现清单，不改既有字段语义。
- **[决议-6] 平台特有内容一律用 BiSheng 自有命名，不冒用任何第三方契约中已有名称的语义**（含路径名、工具类型名、对象名）；平台工具、知识库挂载、附件引用、引用承载的具体形状属 design；**由调用方执行的工具本版不支持、明确拒绝**。（2026-08-18 随伴生 D9 去掉具体字段名，规则不变）理由：占用同名等于做出兑现不了的兼容承诺（伴生 §4.6.3 五）；平台工具是服务端执行、调用方工具是客户端执行，方向相反，本面所复用的平台会话链路没有「返回待执行调用、等调用方回传结果」的往返语义，支持它是新能力而 §3 三类场景无此诉求。备选 = 把知识库映射到某第三方契约的检索工具名——调用方会顺着去找它的配套资源族，兑现不了，否决。**何时重新考虑**：出现须由调用方执行工具的真实场景时，按往返语义补做，不改平台工具语义。
- **[决议-7] 业务上下文指令叠加于平台工作台既有系统提示词之上，不替换、不关闭；调用方不需要、也不允许自行拼装 system message。** 理由：`chat:invoke` 与 `model:invoke` 的分界之一就是「走平台会话机制、注入平台提示词」（伴生 §4.2.4 扩展位表；F051 AC-17 反向对照）；平台提示词承载安全与产品约束，允许调用方替换即让一把 `chat:invoke` 密钥拆掉平台围栏。备选 = 让调用方整体替换平台提示词——等于「便宜版模型面 + 留痕」，与两位互不蕴含的取向相悖，否决；备选 = 完全不接受调用方指令——场景二的自建系统常需注入业务上下文（当前页面 / 当前工单），拒绝会逼调用方把指令塞进用户输入，否决。叠加的具体位置与优先级属 design。
- **[决议-8] 模型必填、按名解析；可用范围 = 平台工作台配置中对执行身份可用的对话模型；名称基准（模型管理页原名精确匹配）与跨服务商同名歧义规则（拒裸名 + 给限定名 + 不取默认）与 F051 决议-2 / 决议-3 同源。** 理由：缺省回落到「工作台默认模型」是又一处调用方不知道自己在用什么的静默行为；工作台链路本就以工作台配置为可用范围（与 F051 的模型管理页全集不同，各按其产品面），但同一个模型名在两面若解析成不同服务商就是「不报错只错」，故名称与歧义规则必须同源。备选 = 本面按平台内部模型 id 选模型——把内部标识写进对外契约（违反 AC-13）、与 F051 的按名解析割裂，否决。
- **[决议-9] 流式与非流式同时支持；非流式返回的结果与同一请求流式执行的最终结果内容一致；失败只有一种真相（流式 = 错误事件 + 失败终态事件，非流式 = 错误响应），失败轮次不留存。缺省返回方式由 design 决定并写入文档。**（2026-08-18 随伴生 D9 去掉「缺省非流式因 Responses 契约如此」的形态依据）理由：两种返回方式只是传输差异、不是契约差异，成功结果必须一致；非流式是自建后端最省事的接法（一次请求一个结果），只支持流式会把简单集成场景挡在门外；失败若在非流式下以「带失败状态的正常结果」返回、在流式下以事件返回，同一失败就有两种真相，且会话历史里会留下半条消息、下一轮续接语义含糊——统一为错误响应 + 不留存最干净。备选 = 只支持流式——挡住简单集成场景，否决；备选 = 失败也留存供取回——引入「可取回但不可续接」的第三种状态，否决。非流式的超时与长响应处理属 design。
- **[决议-10] `chat:invoke` 位归 F049 权限位清单、始终在清单中（伴生 §4.2.4 基础位）；本 Feature 只拥有该位的消费端点，上线时让清单中该位的说明与覆盖端点指向本 Feature 端点、去除「端点随后续版本开放」标注；不写「未发版则不出现」。**（2026-08-17 独立审查裁定，取代初稿「位随本 Feature 同期出现 / 未发版不出现」）理由：权限位清单是 F049 的对象，一个位「出现与否」由清单 owner 决定；F049 已在其范围边界写明「`chat:invoke` 的消费端点随 F058 开放，开放前签发表单对该位以说明标注『端点随后续版本开放』、其余行为同普通位」——把「勾了没用」的困惑用标注化解，而不是让另一个 Feature 反向控制清单里某一位的出现，避免两个 spec 对同一位各写一套规则。备选 = 初稿的「未发版不出现」——需要 F049 清单按 F058 发版状态动态增删位，形成反向依赖，否决。
- **[决议-11] 附件只经上传端点获得标识；发起对话时的附件项只接受平台标识、不接受内联数据与外链 URL；类型 / 大小 / 数量限制沿用平台工作台既有上传限制；不新增独立配额。** 理由：伴生 §4.6.3 二 / 三.6 把附件定为「只走上传端点」，附录 E.3 给出复用映射，平台的解析 / 摄取链路以上传为入口；外链拉取是新的出站请求面（与 F054 出站白名单取向相反）；限制沿用工作台是为了同一个租户里两个入口的附件行为一致、也不为开放 API 另设一套配额（伴生 §4.8 配额按密钥且 P2）。备选 = 接受内联 base64——绕开上传链路且大 payload 直接压在会话请求上，否决。附件的生命周期与清理属 design、沿用工作台既有口径。
- **[决议-12] 异步分支的两项能力（取消、断点续传）形态上留位、调用返回明确「本版未开放」（错误码归 design，与 `26015` 同族或复用）；不做会话列表 / 历史 / 反馈 / 回填；不占用任何第三方契约的兼容路径名；F049 已关闭的 6 个 `/chat/*` 不复活。** 理由：伴生 §4.6.3 一 / 六要求「所选形态须使这些能力将来能加进来，而不必推翻已开放部分」——留位是这条要求的载体，但留位端点若静默成功或 5xx 会让调用方误判；会话列表与 `session:*` 已于 2026-08-16 整体移出（平台存会话 ≠ 给调用方开读接口），本 Feature 是最容易把它们「顺手」加回来的地方，故显式写成 AC-27 守住。备选 = 留位端点直接 404——调用方分不清「路径打错」与「本版未开放」，否决。**何时重新考虑**：四条技术前置消化后点亮异步分支，届时只补异步分支与两项能力的实现，不动同步契约。

- **[决议-13] 「运行模式」（日常 / 任务·灵思）与「传输方式」（同步 / 异步）是两个独立维度，不得合并成同一个开关；两者各自缺省、各自校验、各自拒绝、各自留位（AC-37 / AC-25），错误码 `26017` 与 `26015` 不合并。承载字段归 design。**（2026-08-17 伴生 **D11** 裁定；2026-08-18 随 D9 去掉具体字段名，规则不变）理由：① 内部 `task_mode` 的两个分支 `_task_mode_stream_completion` / `_agent_stream_chat_completion` **都是同步 SSE 流**（`chat_service.py:2148-2150` / `:2158`），任务模式真正的异步在后续 start-execute + WebSocket 段，把「模式」映射到「同步/异步」连现状都不成立；② 调用方打开异步的动机通常只是躲网关 / LB 超时，若它同时切到灵思，拿到的是耗时分钟级、计费不同、输出形态不同（产物、`ask_user` 中断）的另一种能力，还会挤占全租户共享的灵思 worker 池——这正是本 spec 反复守的「静默降级」失败模式（决议-5 / 决议-6 同源）；③「日常模式 + 异步」是已识别的后续需求，一旦被模式占位就只能破坏性改契约。备选 = 合并成一个开关——省一个字段，但换来上述三项，否决。**本版增量成本≈0**：两次枚举校验 + 两个错误码，不引入新链路。**何时重新考虑**：任一维度点亮时按其自身前置推进，不改另一维度语义。


- **[决议-14] 对外契约形态由 design 决定，spec 只写业务语义。** 字段名、事件名、端点路径、以及是否对标某个第三方契约（OpenAI Responses / Chat Completions / Dify 风格 / 平台自定义）均不在本 spec 范围内；本 spec 的 AC 只约束「调用方必须能表达什么」「平台必须保证什么」，形态选型的决策、备选与否决理由写入 design.md §6。**连带取消 AC-04 原有的「响应体可被 OpenAI 官方 SDK 反序列化」要求**，改为「通用 HTTP 客户端即可集成 + 可直接运行的调用示例」。（2026-08-18 伴生 PRD v2.3 **D9 改判**，展开见伴生 §7.5；本 spec 初稿及第三次同步中「OpenAI Responses 契约子集」的全部表述随之作废）
  理由：① **层级**——wire format 是 How，写进 spec 会让形态的任何调整都要回头改 spec 与伴生 PRD 两处；② **语义错配**（比工作量更根本）——Responses 是模型侧契约，其入参是 messages / role / system message / 采样参数，而本 Feature 是应用侧能力，调用方真正要表达的是「问什么、在哪个会话、挂哪些知识库、开哪些工具、带哪些附件」；强行对标就是要求调用方按模型层概念组织应用层请求（研发反馈的「开发者还要传 system message」即此症状）；③ **兼容承诺已被自身的拒绝清单掏空**——决议-5 / 决议-6 一路拒绝掉不留痕、终端用户标识、采样参数、调用方工具、消息历史、内联与外链文件，再加不实现完整资源族，加起来已是形似神不似，SDK 能反序列化 ≠ 调用方能按其习惯用法使用；④ **「一套契约覆盖日常 + 任务」这条决定性论据已站不住**——决议-13 已查明 `ask_user` 与 MinIO 产物 Responses 都表达不了，而业务型契约天生能表达（同类产品把「任务已暂停、等待人工输入」直接做成一等状态）。
  备选 = 维持「Responses 子集」写死在 spec——保住「官方 SDK 可直连」的宣传口径，但该口径的兑现度已经很低，且要付对象模型保真、事件类型对齐、SDK 反序列化验收、完整拒绝清单的持续成本，否决；备选 = spec 直接改指定 Dify 风格——只是把一个形态换成另一个形态，同样越位，否决。
  **未放宽的地方**：伴生 §4.6.3 三的八条硬边界（一套契约 / 不静默降级 / 两个独立维度 / 流式语义可分 / 有状态会话 / 附件只走上传端点 / 归属与分区 / 逐项文档）全部保留，仍是验收依据；design 若评估后仍选 OpenAI 形态，属被允许的技术选择，但须在 design.md 写清理由，且它**不再是产品承诺、不进对外宣传口径**。
  **何时重新考虑**：出现「必须由某个第三方生态工具直连本面且 F051 `model:invoke` 面无法替代」的确认客户场景时，重新评估形态——但那属于 design 层的改型，不需要动本 spec 的 AC。
