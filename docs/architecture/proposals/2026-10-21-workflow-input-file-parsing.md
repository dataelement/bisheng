- 日期：2026-10-21
- 修订日期：2026-10-22
- 状态：方案已确认，已完成代码修复与本地相关测试，尚未提交；真实环境联调待执行
- 分支：`feat/3.0.0`
- 排查基线：`8510a9645382c7ac5f886503e26ae68cb8a0d935`，已 fetch 并快进到 `origin/feat/3.0.0`
- 范围：工作流输入节点的文件解析、解析图片留存及访问、是否进入检索切分的判断

## 1 方案结论

两个问题来自同一个调用边界：输入节点把“只提取正文”和“生成检索切片”统一交给 `TempFilePipeline`，但这条管线既没有图片上传步骤，又始终应用知识库切分规则。

实现已在输入节点进入解析管线之前明确处理目的，并为图片增加独立的存储上下文：

1. **仅提取正文**：解析文件、上传解析图片、按既有正文长度上限输出；不执行知识库切分、分段长度校验和向量写入。
2. **解析并存入临时知识库**：解析文件、上传解析图片、执行现有切分并写入 Milvus 和 ES；正文输出变量继续兼容现有契约。
3. **保留原始文件**：继续跳过解析，不创建解析图片或检索切片。

正式会话的原始附件和解析图片统一保存在主桶，随会话留存，由会话附件清单负责定位和删除。这项存储策略已于 2026-10-22 确认。访问链接的有效期与对象留存时间分开处理：链接过期后可以重新签发，对象不会因链接过期或临时桶到期而删除。

调试和未关联历史消息的解析产物进入 `tmp_bucket`。临时知识库不是正式知识库，正文提取和临时入库均不创建 `knowledge` 或 `knowledge_file` 记录。

## 2 排查基线与根因

以下位置均基于排查基线；部署环境的实际桶策略与报错样本尚未核对。

| 环节 | 当前行为 | 代码位置 |
|---|---|---|
| 输入策略 | 已能区分 `extract_text`、`ingest_to_temp_kb` 和 `keep_raw`，兼容字符串、数组及旧版类型映射 | `workflow/nodes/input/input.py` 的 `_modes_for_file()` |
| 创建解析管线 | 固定构造 `FileProcessBase(knowledge_id=0)`，调用 `TempFilePipeline.run(PipelineConfig())`，没有传入是否需要检索切片 | 同文件 `get_upload_file_path_content()`，327 行起 |
| 判断是否入库 | 拿到解析结果以后才判断是否需要初始化向量客户端、写入 Milvus 和 ES | 同文件 `parse_upload_file()`，437 至 467 行 |
| 临时管线 | 普通文件添加 Splitter 或按页 DirectChunk；Excel 在 Loader 内切片；均没有图片上传 Transformer | `knowledge/rag/temp_file_pipeline.py` |
| 图片引用 | 未指定 `image_object_dir` 时，Loader 把本地路径写进 Markdown | `knowledge/rag/pipeline/loader/base.py` 的 `build_image_url()` |
| 图片实际寿命 | `BaseFilePipeline.run()` 退出 `TemporaryDirectory` 后，解析图片随目录删除 | `knowledge/rag/base_file_pipeline.py`，120 行起 |
| 知识库图片 | 有独立对象目录，并配置 `ImageUploadTransformer`，在临时目录销毁前上传字节 | `knowledge/rag/knowledge_file_pipeline.py` |

因此，工作流返回的 Markdown 可能包含 `![](/tmp/.../figure.png)`。文件解析本身成功，也不代表图片已经上传。前端无法访问 Worker 的本地文件；管线结束后该文件也已不存在。

第二个问题发生在是否入库的判断之前。`file_content_size` 默认 15,000 字符，是输入节点输出正文的截断上限；它与检索分段的 10,000 字符上限不是同一个限制，不能互相替代。

### 最新分支已经具备的修复

普通 `SplitterTransformer` 已接入 `hard_split_limit`，对默认分隔符无法切开的超长片段进行强制切分。对应提交为 `b358664c61`，不能再把所有长文本报错都归因于缺少这项修复。

但 PPT 默认按页进入 `DirectChunkTransformer`，单页超过 10,000 字符仍抛出 `KnowledgeFileChunkMaxError`，业务码 `10912`。Excel 还有 Loader 内部的字符预算和 `10916` 校验。因此，仅删掉普通 Splitter 或扩大它的上限都不能完整解决“仅提取正文不应受检索分段约束”。

### 本地验证

- 现有相关测试：`test_splitter_hard_limit.py`、`test_input_parse_mode.py`、`test_input_node_media.py`，合计 **38 passed**。
- 用模拟 Loader 运行真实 `TempFilePipeline`：返回的图片引用仍为本地路径，管线退出后该文件不存在。
- 用模拟 Loader 返回 10,001 字符的 PPT 单页：真实默认临时管线抛出 `10912`。
- 同步 `NormalPipeline.run(stop_at=LOAD)` 当前返回的 `documents` 为 `None`。直接改为这个停止阶段既取不到正文，也会跳过图片上传；Excel 的 Loader 内切片还会照常发生。

这些验证确认代码路径，不等同于真实 OCR、MinIO 和浏览器联调。用户现场报错具体属于哪种文件路径，需要实施验收时用原样本确认。

## 3 临时桶与历史图片的处理

### 当前与历史行为

需要区分桶名和对象目录名：

- 原始上传件默认进入 `tmp_bucket`。工作流问题消息落库时，已有 `promote_chat_attachments_sync()` 将可识别附件复制到主桶，记录 `files[].object_name`。
- 当前代码为整个 `tmp_bucket` 设置 **7 天到期**，且初始化时会校正旧规则。部分 F043、F062 文档和注释仍写 3 天；方案以 `minio_storage.py` 的 `_TMP_OBJECT_EXPIRE_DAYS = 7` 为准，实际部署需核验。
- `KnowledgeUtils.get_knowledge_file_image_dir()` 在没有知识库 ID 时返回 `tmp/images/<doc_id>`，但图片上传 Transformer 使用的是**主桶**。`tmp/images` 目录不等于 `tmp_bucket`，也不会自动获得后者的过期清理。
- 检查图片上传集中化之前的父提交，临时管线也没有指定图片对象目录，Loader 的上传辅助方法在此情况下直接返回本地路径。因此，所检查的这条历史实现也不能证明解析图片曾经存入 `tmp_bucket`。

### 方案比较

| 选项 | 结果与代价 | 建议 |
|---|---|---|
| 所有解析图片进入 `tmp_bucket` | 改动较小、自动回收；7 天后历史答案中的图片失效，重新签名也无法恢复已删除字节 | 不采用 |
| 所有图片进入主桶 `tmp/images`，只补上传 | 可以沿用部分图片 URL，但没有归属清单和删除链，会产生长期孤儿对象；该目录已有匿名读策略 | 不采用 |
| 正式会话原件与解析图片统一主桶留存，调试产物使用临时桶 | 历史可回看；补齐派生图片清单、链接解析和会话删除 | **已确认并实现** |

“不进入临时知识库”只决定是否生成检索数据，不决定正式会话中的对象是否留存。正式会话主桶留存同时覆盖仅提取正文和入临时知识库两种模式，不再把正式会话解析图片的 7 天失效作为候选实现。

现有原始附件已经按会话保存在主桶，没有代码内置的 7 天自动删除策略；本次为解析图片补齐同样的留存规则。这里的留存不是永不删除：删除会话时清理相关对象。历史上已经失效的临时链接或被回收的对象，不因这项决定自动恢复。

## 4 图片留存的实现建议

### 存储上下文与图片上传

输入节点为每个文件传入处理目的、源文件引用、执行标识，以及服务端确认的会话和主体信息。图片对象键使用会话、工作流、运行、节点、源文件身份与本次尝试 UUID 组成的文件键，不使用默认 `document_id=0` 作为图片身份。重试和并发尝试均使用独立对象键，已发布的历史图片不被覆盖或退回 `pending`；同一上下文禁止再次上传。检索用的每文件 UUID 保持原有契约。

外部 HTTP URL 的身份保留域名、编码路径和业务查询参数，不能仅使用路径。只有地址属于本系统 MinIO 共享域名及已知桶，或使用已知桶的相对地址时，才移除签名参数并统一绝对/相对表示；业务参数仍参与匹配。源附件匹配与对象身份计算复用同一规则。

复用 `ImageUploadTransformer` 上传图片字节，增加显式目标桶参数；默认行为保持知识库主桶上传。仅隔离了本次尝试对象键的工作流上下文显式启用失败回滚，知识库、预览及其他默认上下文不删除已发布对象。Loader 的图片引用构造也必须接受同一存储上下文，不能只改上传的桶，而让正文仍指向默认主桶。

保持现有解析契约：**先确定图片在正文中的最终稳定引用，再计算 `metadata.indexes`，随后在清理本地目录前完成上传**。不能等切分后再替换成长度不同的图片 URL，否则会再次破坏 bbox 与正文偏移对齐。OFD、信创格式的委托 Loader 要传递同一上下文。

### 正式会话图片

复用主桶现有 `chat/...` 附件边界，派生图片键为 `chat/<tenant_id>/<user_id>/workflow/<source_key>/images/<filename>`。租户取持久会话所属租户，而非共享工作流的配置所属租户。原件沿用现有临时桶到主桶的复制流程；已留存的原件不重复复制，解析图片在本地暂存目录销毁前上传到主桶。

在问题消息对应附件下增加可选 `derived_assets` 清单，保存图片 ID、对象键、桶、来源文件与状态；同时在独立 `workflow_file_manifest` 表按本次尝试保存原件和图片清单。清单归属会话而非某条问题消息，单独删除源问题后，历史图片仍能解析，删除会话仍能回收原件及图片。这是内部派生资源，不增加用户上传的附件卡片，也不挤占现有 `dialog_image_files` 变量；后者表达用户直接上传的图片，不是文档内抽取图片。

正文使用稳定 HTTP 图片地址 `/api/v1/chat/{chat_id}/files/{asset_id}/content`。这个新增的薄端点复用现有附件链接解析 Service；每次请求先校验会话归属，再从持久清单查找 `ready` 状态图片，返回 307 跳转到本次签发的 MinIO 地址，并设置 `Cache-Control: no-store`。既有 `/url` 端点也支持相同派生资源。签名有效期沿用现有附件访问策略，链接续签不改变对象随会话留存的生命周期。

这里选择服务端稳定地址代替前端自定义图片引用解析器：现有 client 和 platform Markdown 的标准图片请求即可携带登录 Cookie 访问，无需新增前端解析分支或更改组件样式。正式会话的预签名 URL 不写死在历史正文中。端点从服务端清单选对象，同时校验图片键与会话用户、租户及图片 ID 一致，不接收调用方指定的任意对象路径。沿用既有会话附件读取权限，不新增匿名读取授权。

### 临时运行与清理

没有保存会话的调试运行，图片进入 `tmp_bucket`，复用 7 天生命周期，按执行主体和运行标识隔离；运行期链接解析只使用该次运行登记的清单。旧的独立工作流与免登录路径沿用其现有身份边界，不把发布者身份当成访客拥有者。

正式图片先在独立表和源附件中登记 `pending` 清单，再上传主桶，成功后更新为 `ready`；两份清单写入使用会话与消息行锁，并在同一事务提交。源问题在上传中途被删除时，使用独立清单完成登记。上传或完成登记失败时只清理本次尝试已经上传的图片，不返回成功结果；若与会话删除并发，完成登记会拒绝已删除会话，并触发上传清理。删除失败保留对象键和日志，可再次调用会话删除重试物理清理。临时运行的失败字节由清理及临时桶生命周期兜底。

首次删除和重试删除均先校验自然人会话归属、用户及叶子租户，拒绝其他用户、其他租户及 API 主体会话后才执行审计、软删除和物理清理。软删除 UPDATE 显式绑定会话、用户、租户及主体类型，不能依赖只拦截 SELECT 的自动租户过滤。

会话删除时，扩展现有 `_remove_attachments()`，同时处理 `derived_assets`，合并读取消息附件与独立清单并按对象键去重。两类记录均按主键分页，覆盖超出 1,000 条消息及 500 条清单的历史，不以空字符串作为字符串主键的首屏边界，避免 DM8 空串语义影响查询。MinIO 删除失败保留清单以供重试，不宣称已完成物理回收。

本期不新增知识库记录或独立资源管理系统。为修复消息硬删除后清单丢失，新增独立 `workflow_file_manifest` 表，数据读写集中在 `WorkflowFileRepository`，使用双库通用 `LargeText` 而非数据库特有 JSON 操作。模型位于标准 `domain/models` 目录，加入租户模型注册；部署时按现有流程执行 `alembic upgrade head`，自动发现并创建该缺失整表，不需手工建表或数据迁移。既有已丢失的清单不自动回填。

## 5 解析与检索切分分离

### 在调用之前决定处理目的

`parse_upload_file()` 在调用解析方法之前计算是否包含 `ingest_to_temp_kb`，将结果显式传入临时管线。新增的 `split_for_retrieval` 参数默认保持当前行为，仅由工作流输入节点按策略覆盖。

| 输入模式 | Loader 与图片上传 | 检索切分与分段长度校验 | Milvus 和 ES |
|---|---|---|---|
| `keep_raw` | 跳过 | 跳过 | 跳过 |
| 仅 `extract_text` | 执行 | 跳过 | 跳过 |
| 包含 `ingest_to_temp_kb` | 执行 | 保持现有行为 | 执行 |

已有字符串、数组、类型映射和缺失值的历史兼容规则保持不变；缺失配置的旧表单仍按原来的入库默认处理。组合模式只解析一次，再用该次产物完成切分、正文输出与入库。

### 各类文件的处理

- **PDF、Word、Markdown、HTML、图片 OCR、音视频转写**：仅提取模式返回 Loader 解析内容并持久化图片，不接入 Splitter、HierarchicalSplitter、DirectChunk 等检索 Transformer。
- **PPT**：可以保留 Loader 的自然页顺序，但仅提取模式不经过 DirectChunk 的 10,000 字符校验。入库模式继续执行已有页切片约束。
- **Excel、CSV、ET**：必须同步处理 Loader 内切片。仅提取模式按工作表输出内容，关闭检索用途的行分片、重复表头、字符预算和分段超长校验；保留数据、表头、工作表顺序与图片。ET 转换后的 Excel 委托也要收到该参数。入库模式继续使用原有预算与长行处理。

输入节点继续执行用户配置的正文长度上限，不提高默认 15,000 字符，不以“去掉分段上限”为名允许无限正文进入模型。保留现有文件大小、媒体数量、解析超时和格式错误处理；解析完成前仍可能因这些真实限制失败。

`TempFilePipeline` 还被日常聊天和灵思调用，禁止直接把它全局改成不切分或自动永久保存图片。新参数保持兼容默认，工作流显式选择。知识库及预览管线保持现有图片目录、切分、bbox 和入库行为。

本期不批量重解析历史消息、不重建历史向量。历史图片若只存在于已删除的本地目录，不能通过修改 URL 恢复；需要原件仍在并重新运行解析，不能制造正常样式的失效链接。现存 `tmp/images` 对象不自动迁移或删除。

## 7 验收标准

| 编号 | 验收要求 |
|---|---|
| AC-01 | 含图片的 PDF、DOCX、PPTX、XLSX 解析后，正文中保留下来的每个图片引用都有对应可读对象；管线临时目录删除后仍可展示 |
| AC-02 | 仅提取模式处理超 10,000 字符 PPT 单页、长正文、超宽表格或长单元格时，不触发检索分段类 `10912`、`10916`；正文仍受输入节点长度上限控制 |
| AC-03 | 仅提取模式不初始化 embedding、Milvus 或 ES，不调用检索 Splitter；Excel 也不走检索用途的行分片 |
| AC-04 | 入临时知识库模式继续生成切片并写入两种检索存储，bbox、page、chunk_index 与图片引用对齐；不全局放宽知识库分段限制 |
| AC-05 | 正式会话的原始附件和解析图片均在主桶随会话留存，不因临时桶过期而失效；签名过期后，有权读取会话者可获取新签名；对象寿命和签名寿命分别验证 |
| AC-06 | 调试图片按临时策略过期，不要求永久历史回看；跨进程、跨主机读取不依赖 Worker 本地目录 |
| AC-07 | 同名文件、多个文件、并发运行和不同租户不会串图；不同外部域名或业务参数不得合并；无权读取或删除会话者不能取得对象链接或触发物理删除 |
| AC-08 | 删除会话能够收集并删除其原始附件和派生图片，源问题消息被单独删除后仍成立；失败重试不删除已发布图片，上传失败、执行重试、Worker 中断及删除失败均不会被当作完整成功 |

## 8 已确认的实施范围

1. **已确认的正式会话存储策略**：2026-10-22 用户确认“统一都复制到主桶里保留”。原始附件和解析图片统一主桶留存，随会话清理；访问链接仍有有效期，过期后按权限重新签发。此前讨论的“正式会话解析图片只在临时桶有效期内可访问”不再采用。
2. **解析与调试策略**：仅提取正文完全跳过检索切分，同时保留现有正文长度上限；进入临时知识库时继续切分。未保存会话的调试图片按临时桶生命周期回收。
3. **历史范围**：本次只保证修复后的新解析；历史坏图不自动批量补偿，原件仍在时可以重新运行恢复。
