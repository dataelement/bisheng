# Sdd Requirement Validation

先读 [阶段交接规则](../sdd-workflow/references/stage-contract.md)。
专业检查使用 [产品验证清单](references/product-checks.md)。
形成或审核需求文档时读取 [PRD 写作与完成标准](references/prd-writing-standard.md) 和 [HTML 交付约定](../sdd-workflow/references/html-delivery.md)。

## 读取与验证

允许从口头描述或一段原始诉求开始。Word、PDF、Markdown 等按宿主可用工具读取；整理格式不作为开工门槛。
查相关现有能力、入口、业务规则和角色事实。核实事实由 AI 完成，产品取舍由用户决定。
区分源码观察、文档、已验证运行行为、用户要求与 AI 建议；不把实现细节反推为产品规则。

先检查四维：合理、闭环、边界、交互与结果可验收。每维给出“成立／有缺口／不成立”及必要证据。
只检查本次需求涉及的能力。必要的技术可行性探索用于发现约束，详细方案留给设计阶段。

涉及业务对象、模块或重要抽象时，按[领域语言约定](../sdd-workflow/references/domain-language.md) 核对本次对象、关系、规范名与易混概念。已有定义直接复用，新定义即时写入需求评审稿并保留候选状态；确认并入既定需求节点。核心验收依赖的概念歧义属于阻塞，非阻塞措辞不扩大访谈。

## 按需引用 grilling

四维发现需用户决定的缺口时，读取 [grilling](../grilling/SKILL.md)，使用其决策依赖、编号提问和推荐理由方法。
向它提供本次范围、相关事实、问题编号和级别、决策依赖、既有决定及授权。提问限于当前需求；每轮优先当前可决定的重要问题，控制问题量。
每个待用户决策的问题先列出至少两个真实可行、互不混淆的选项，简述各自的结果或取舍，再明确标出 AI 建议的选项及理由，最后请用户选择或提出自己的方案。无论用聊天文字还是提问工具，都要让用户在作答前看到这些选项；工具支持选项时，将建议项放在第一位。不要把 AI 建议写成已确认决定，也不要为了凑数编造不可行选项；若查证后确实只有一种可行做法，将其作为事实约束说明，不伪装成选择题。
依赖尚未解决的问题放到下一轮，独立问题可同轮处理。已明确的对象、角色和范围直接复用，没有冲突证据时不把额外能力扩展为待确认问题。依赖上游选择的条件式追问仍属于下游问题，应在该选择确定后展开。
事实查证利用宿主允许的工具和协作能力；保持当前权限与用户意图。
grilling 中的事实调查委派以宿主支持和授权为前提。无法派发、派发失败或当前任务要求单进程时，由当前 agent 使用获准的读取工具继续调查；不能因协作机制不可用而挂起事实查证，也不能替用户决定业务取舍。

需求验证负责问题分级：
- 阻塞：影响四维、核心范围、规则、重要风险或验收判断。未解决时不能通过。
- 澄清：四维仍成立且不影响核心验收，例如沿用规则下的局部措辞。记录影响，随整体结果供用户确认。

澄清结果回写问题与答案、决定和需求；重新检查四维。grilling 访谈结束不能代替验证通过。
依赖缺失时说明实际缺口，继续整理已知内容，不宣称已经使用它。不要静默换成其他同名访谈方法。
已知信息足够时直接验证，不机械启动访谈。

## 形成需求依据

为需求保留稳定标识和可观察的验收条件：谁在什么前提下做什么、结果和必要副作用是什么。
记录本次包含和排除项、重要约束、已接受的需求修正、证据及非阻塞残留事项。
按 PRD 写作标准形成 HTML 需求稿，先写问题、目标指标和范围，再进入功能；优先级、分期、业务规则、异常和字段、非功能要求、依赖风险及验收条件必须有明确安排。不适用说明理由，未知保留问题及影响，不能自行编造指标、规则或确认。
业务场景交给 sdd-test-cases 细化，内部契约和实现取舍交给 sdd-design。

## 完成标准

四维均成立、未解决阻塞为零、每条需求可验收且预期有来源，HTML 需求稿符合 PRD 标准并完成四问自检，才能标记“专业检查完成，待用户确认”。
接受风险不能自动把未满足的标准改为通过；缩小范围或修正规则后重新核对。
明确用户确认对应内容后，标记“需求已闭环”。文档写完、自检完成、人工确认分别记录。
将 grilling 的共同理解确认纳入这一既定确认点，减少重复确认；沉默不视为批准。

## 交付

按[产物存放与维护约定](../sdd-workflow/references/artifact-storage.md) 将需求位置登记到本次特性，后续设计和两岗位用例引用该来源。已有有效 PRD 分处其他目录时保留其来源关系，不因新默认结构再建同内容定稿。
交付 HTML 需求稿及实际位置，保留四维结论、事实依据、开放问题及级别、残留事项和确认状态。确认前为评审稿，确认后为需求闭环依据；不能只有聊天摘要。
仅要求咨询或检查现有材料时可先给分析，不擅自重写完整 PRD；需要形成需求定稿时按上述格式交付。处于已授权总流程时，将已确认 HTML 需求交给设计和业务用例阶段。
