## 0. 一句话结论

积分模块本质是「**事件驱动的激励账本 + 可配置规则 + 排行榜缓存 + 运营后台 + 外部增量同步**」。  
BiSheng 侧已有空间层级/角色、上传/发布审批、收藏、专家采纳、站内信、日活事实、Celery Beat；Portal 首页已有**硬编码积分榜 UI**。  
仓库内**无**积分 ledger / 规则引擎 / 余额账户。可落库新建独立 DDD 模块，但必须先把下文「不清晰点」拍板，否则联调阶段会反复改语义。

## 1. 需求拆分归纳（按交付切片）

### 1.1 用户端（Portal 为主）

| 切片 | PRD 要点 | 现状对照 |
|---|---|---|
| **U1 我的积分** | 入口在账号下拉；总积分 / 本月获得 / 本月扣减 / 部门与总榜排名；规则弹窗；明细筛选；空状态文案 | Portal `Header` 有账号下拉；**无**积分页。Client `UserPopMenu` 另有一套账号菜单，需产品确认入口是否仅 Portal |
| **U2 首页榜单** | 本月 / 本年度 / 总榜 TOP10；当前用户高亮或置底「我」；每小时刷新 | Portal `HomePage.tsx` 已有领奖台 + 列表 **mock 数据**（`POINTS_PODIUM` / `POINTS_ROWS`），可替换 API |
| **U3 消息提醒** | 积分变动站内信，多模板，链到「我的积分」 | BiSheng `MessageService.send_message` + `action_code` 可扩展；无需先扩 `MessageTypeEnum` |

### 1.2 管理端

| 切片 | PRD 要点 | 现状对照 |
|---|---|---|
| **A1 数据概览** | 平台总发放 / 有效可用总积分 / 违规扣减；5min 刷新；原型还含环比 | Platform 或 Portal 管理页？PRD 写「后台」，**落点未定义** |
| **A2 规则配置** | 获取 G* / 扣减 R* / 管理员 M* / 说明文案 4 Tab；预置可删可改；编码互斥 | 全新；规则表 + 种子数据 |
| **A3 用户积分管理** | 搜索/筛部门与角色、调分、详情、操作审计（不可改删） | 全新；依赖用户主部门与空间角色聚合 |
| **A4 前台扣减入口** | 知识库文档列表/阅读页、专家问答删除弹窗挂「扣减」 | 跨 Portal 知识 iframe（Client）+ 专家问答页，**权限与入口分散** |

### 1.3 规则与自动化（领域核心）

| 规则族 | 编码 | 触发 | 关键约束（PRD） |
|---|---|---|---|
| 获取 | G1/G2（预置）、G5/G6/G7（可选增） | 上传/发布成功；分享成功；收藏阶梯；问答采纳 | 每日上限；所有者/管理员管辖库内上传发布**不叠加** G1/G2/G5/G6/G7；收藏同用户只计一次；阶梯阈值只记首次 |
| 扣减 | R1–R3 | **管理员手动** | 负分；前台挂载入口 |
| 月奖 | M1/M4/M6 预置，其余可增 | 次月 1 日 00:05；当月登录 ≥1；多角色取最高不累加 | 依赖「管理员角色」识别 + 日活 |
| 文案 | 5 条预置可改 | 前台规则弹窗展示 | 「用途 / 申诉」仅文案，无功能 |

### 1.4 外部系统

| 切片 | PRD 要点 | 状态 |
|---|---|---|
| **E1 协同办公同步** | 每日增量推送 `user_point_log`；字段/鉴权/地址「对接后确认」 | **接口未闭环**，只能预留 Outbox |

### 1.5 非功能

- 列表/明细千人级 ≤1.5s  
- 审计日志禁止删改  
- 积分表每日全量备份保留 30 天（偏运维，非应用层）

### 1.6 业务目标（成功指标，非功能）

| 目标 | 指标 | 说明 |
|---|---|---|
| 内容增长 | 上传/发布月环比 ≥20% | 需埋点基线对比，积分模块本身不保证达成 |
| 用户留存 | MAU 环比 ≥15% | 同上 |
| 内容质量 | 违规占比 &lt;2% | 「违规」定义与统计口径 PRD 未给 |

## 2. 可行性与技术选型

### 2.1 可行性总评

| 维度 | 评级 | 说明 |
|---|---|---|
| 业务价值落地 | 中高 | 激励闭环清晰；兑换/申诉仅文案，短期可不做兑换引擎 |
| 后端落地 | **可行** | 新建 `points`（建议 errcode **182**）DDD 模块；账本 + 规则 + 排行快照 |
| 触发挂钩 | **可行但侵入** | 无领域事件总线；需在 upload / 发布审批通过 / favorite / adopt / 手动调分 等成功路径显式调用 `PointsService` |
| 前端落点 | **跨仓** | 用户端与首页榜 → **Portal**；管理端可能 Portal 运营页或 Platform；知识库扣减入口在 Client iframe |
| 多租户 / DM8 | 需遵守现有规范 | `tenant_id` 自动注入；`JsonType` / Alembic；月任务按租户 fanout（Beat × N） |
| 外部同步 | **阻塞风险** | 报文未定；必须做本地 Outbox，避免业务被外部接口拖死 |
| 总体工期量级（粗估） | **中大** | 账本+规则+挂钩+Portal 三页+管理端+Beat+同步骨架 ≈ 多迭代；不含协同办公联调 |

**风险等级（跨边界）：高** —— 触及知识空间语义（管理员是否计分）、审批发布结果、收藏计数、专家采纳、站内信、Portal/Client 多端 UI、未来外部积分互通。按仓库规则：**澄清清单确认前不宜直接写生产代码**。

### 2.2 推荐架构（业界 ledger 实践 × 本仓约束）

对齐业界常见做法（append-only ledger、idempotency key、余额缓存、日 cap、异步副作用）：

```
业务成功路径（upload / approve-publish / favorite / adopt / admin adjust / monthly job）
        │
        ▼
PointsAwardService.award / deduct / adjust
  · 读启用规则 + 解析分值（含 G3 阶梯）
  · 日上限 / 幂等键 / 管理员豁免校验
  · 同一事务：INSERT ledger + UPDATE balance（行锁）
        │
        ├─► 站内信（可异步 / outbox）
        ├─► 失效排行缓存标记 or 写 Redis ZSET
        └─► 外部同步 outbox（日批 drain）
```

#### 核心数据表（建议）

| 表 | 职责 |
|---|---|
| `user_point_account` | 用户余额缓存：`balance`、`lifetime_earned`、`lifetime_deducted`、版本号/更新时间 |
| `user_point_log` | **append-only** 流水：delta、balance_after、rule_code、biz_type、biz_id、idempotency_key、operator_id、remark、occurred_at |
| `point_rule` | 规则配置：code、type(earn/deduct/admin_reward)、name、score_expr、daily_cap、beneficiary、status、remark |
| `point_rule_copy` | Tab4 说明文案（5 条或 key-value） |
| `point_admin_audit` | 仅管理员调分审计（也可与 log 合并并用 `source=manual` 区分） |
| `point_rank_snapshot` | 小时榜快照：scope(dept/global)、period(month/year/all)、rank、score、refreshed_at |
| `point_sync_outbox` | 外部推送：pending/sent/failed、payload、retry |

**硬约束（最佳实践）：**

1. **流水不可 UPDATE/DELETE**（应用层禁止；审计同理）。纠错用**冲正流水**，不改历史。  
2. **幂等键**唯一：`(tenant_id, idempotency_key)`，例：`g1:file:{file_id}:publish`、`g3:file:{id}:tier:75`、`m1:user:{id}:2026-07`。  
3. **余额与流水同事务**；并发用 `SELECT … FOR UPDATE` 锁账户行。  
4. 排行榜：**小时批算快照**（对齐 PRD）+ Redis ZSET 可选加速；「我的排名」读快照并展示 `refreshed_at`。  
5. 日上限：Redis `INCR` + TTL 到日切，或 SQL 日聚合；失败要可回滚一致性。

#### 技术栈选型（贴合本仓）

| 层 | 选型 | 理由 |
|---|---|---|
| 后端模块 | FastAPI DDD：`points/{api,domain,repositories}` | 对齐 knowledge / message |
| 异步 | Celery：月奖、小时排行、外部 sync、可选延迟站内信 | 已有 Beat 注册模式（`CeleryTaskSettings`） |
| 缓存 | Redis Sorted Set（榜）+ 日 cap key | 本仓已有 Redis |
| 消息 | `MessageService` + 新 `action_code`（如 `points_changed`） | 已有企微 outbox 旁路 |
| 登录条件 | `DailyParticipationFact` / mid-table 按月聚合 `logged_in` | 已有日活，无需新登录表 |
| 空间角色 | `SpaceChannelMember`（creator/admin）+ `KnowledgeSpaceLevelEnum` + ReBAC `can_manage` | 映射 M1–M8；**「科室」≈ `TEAM_KS`，需产品确认** |
| 前端用户端 | Portal（首页榜 + 我的积分 + 规则弹窗） | 已有 mock 榜单 |
| 前端管理端 | **待定**：Portal 运营后台 or Platform | 见开放问题 |
| 错误码 | 模块号建议 **182** | 181=approval、189=migration 已占 |
| 规则引擎 | **首期不做通用规则引擎** | 编码白名单 + score_expr（整数或阶梯 JSON）足够；避免过度设计 |

#### 明确不推荐

| 方案 | 原因 |
|---|---|
| 只改用户表一个 `points` 字段 | 无法审计、无法对账、并发不安全 |
| 全量实时算全站排名 | 千人尚可，增长后拖垮；与 PRD「每小时」不符 |
| 先接协同办公再上线积分 | 外部字段未定，应 Outbox 解耦 |
| 在 Client/Platform 混放用户「我的积分」主入口 | 与首钢知库主入口（Portal）不一致，除非产品明确双端 |

### 2.3 与现有挂钩点映射

| 业务事件 | 现有落点（核实） | 积分动作 |
|---|---|---|
| 上传到某级库 | `POST .../knowledge/space/{id}/files` + hook | G1/G2/G5/G6（按 `space.level`） |
| 跨库发布 | 审批 scenario `knowledge_space_file_publish_request`，通过后 handler | G1/G2…（按**目标库** level）；注意「上传」与「发布」是否重复计分 |
| 知识库间分享（非外链） | 文档分发 `SHARE`：`KnowledgeDocumentDistributionService.share_approved`（分享到其他知识空间，如部门库→部门库） | G7 |
| 收藏 | `create_shougang_portal_favorite` + `aget_favorite_referrers` | G3 阶梯；需自建阈值状态 |
| 问答采纳 | `QuestionService.adopt_answer` | G4 |
| 月登录 | `DailyParticipationFact` | M* 发放条件 |
| 站内信 | `MessageService.send_message` | 变动通知 |
| 扣减 UI | 文档列表/阅读、问答删除弹窗 | R* 或自由原因？PRD 混用规则名与手填原因 |

## 3. 异常与边界（必须设计，PRD 大量未写）

### 3.1 账本与余额

| 场景 | 建议默认（待产品确认） | 风险 |
|---|---|---|
| 扣减后余额 &lt; 0 | 允许负数 **或** 扣到 0 | 榜单、外部兑换、展示样式全受影响 |
| 并发双击调分 / 重复采纳回调 | 幂等键拒绝第二次 | 否则双倍积分 |
| 规则中途改分值 | 仅影响新流水（PRD 已明确） | 历史对账按流水当时分值 |
| 规则禁用后已触发事件 | 不计分 | 用户感知「做了没分」需否提示 |
| 规则删除 | 流水保留 rule_code 快照名；列表「已删规则」展示 | 外键勿级联删流水 |
| 冲正 / 误发 | PRD 无；建议仅管理员调分或显式 reversal | 禁止改历史行 |

### 3.2 业务事件语义

| 场景 | 问题 | 建议澄清 |
|---|---|---|
| 同一文档先上传部门库(+G2)再发布公共库(+G1) | 是否两次都给？ | 场景一暗示发布审核通过后 +2，需定义「上传成功」vs「发布成功」 |
| 上传即进公共库（无审批） | 触发点？ | 与审批发布是否共用幂等维度 |
| 文档删除 / 下架 / 回收站 | 已发积分是否回收？ | 业界多为**不回滚激励**（防刷另靠日 cap）；若回收需冲正 |
| 取消收藏导致人数跌破 75 | PRD：再次达 75 **不再**加 | 需持久化 `tier_awarded` 集合 |
| 同一用户对一文多次收藏 | 只计一次 | favorite 唯一约束已有？需核实 |
| 管理员/所有者在本库上传 | 不叠加 G* | 「管辖库」定义：任一 admin/creator 的 space？含子空间？ |
| 兼任多空间管理员 | 月奖取最高 M* | 跨 level 取 max(score)；一人多 public admin 不叠 |
| 平台管理员 | 矩阵写不可获积分 | 手动调分给自己？月奖？需禁或审计例外 |
| G3「单文档上限 15」与阶梯 +5/+10/+15 | 是累计封顶 15 还是三档互斥？ | **高歧义** |
| G1 每日 15 分(5 篇) vs 分值可改成 +5 | 上限按「分」还是「次」？ | 改分后 15 分可能不足 5 篇或超过 |
| 获益人「上传人/发布人」 | 两人不同时给谁？ | 单选配置：只给一个角色 |
| 分享 G7 | ~~外链~~ → **知识库间 SHARE 分发成功**；与发布(publish)是否重叠需防双计 | 挂钩 `share_approved` |
| 科室库 / 团队库 | 代码 `TEAM` vs `TEAM_KS` | 与 M5–M8、G5/G6 映射表 |
| 时区 | 「每月 1 日 00:05」「本月 1 号 00:00」 | 建议 Asia/Shanghai 固定，写入配置 |
| 用户调部门 | 部门榜用当前主部门还是历史？ | 快照按刷新时主部门 |
| 多租户 | 榜单租户内还是集团？ | 默认租户隔离 |
| 外部同步失败 | 重试？补推？对账？ | Outbox + 告警；PRD 未写 |
| 申诉（文案有、功能无） | 7 个工作日申诉 | 仅展示 or 工单？ |

### 3.3 权限与安全

| 项 | 说明 |
|---|---|
| 谁可配规则 / 调分 | 矩阵：公共库管理员 + 平台管理员；需映射现有 RBAC/ReBAC，避免只靠前端藏按钮 |
| 前台扣减按钮 | 文档页在 Client iframe：权限校验必须后端强制 |
| 审计不可删 | 无管理 API；DB 账号权限与备份策略 |
| 刷分 | 日 cap + 管理员豁免 + 分享/收藏幂等；缺设备/IP 风控（首期可不做，需产品接受） |
| 备份 30 天 | 属 DBA/运维；应用层做逻辑删除备份不满足「全量备份」表述 |

### 3.4 性能边界

| 项 | 策略 |
|---|---|
| 明细分页 | `(user_id, occurred_at, id)` 索引；禁深翻页大 offset 可考虑 cursor |
| 排行小时任务 | 增量聚合当月流水比全表 sort 用户更稳 |
| 统计卡片「实时」 | 账户表 + 当月流水聚合；注意与榜「每小时」不一致，UI 需展示榜更新时间 |
| 管理端全用户列表 | 千人可接受；需部门/角色筛的预聚合或 JOIN 优化 |
| Beat × 租户 | 月奖、排行、同步均按活跃租户循环，评估耗时 |

## 4. 数据埋点与监控

PRD 几乎只给业务 KPI，**缺少工程可观测性**。建议分层补齐（可与现有 telemetry / audit 对齐）。

### 4.1 产品 / 运营指标（验证 PRD 目标）

| 指标 | 口径建议 | 周期 |
|---|---|---|
| 知识上传/发布量 | 已有 audit/telemetry；对比积分上线前后 | 月 |
| MAU | 日活 mid-table | 月 |
| 违规占比 | **需产品定义**（扣减次数？删文？举报？） | 季 |
| 人均积分获得、规则命中分布 | 按 `rule_code` 聚合流水 | 周/月 |
| 日 cap 触达率 | cap 拒绝次数 / 触发次数 | 日 |
| 榜单曝光与「我的积分」PV | 前端埋点 | 周 |
| 外部同步延迟与失败率 | outbox | 日 |

### 4.2 工程埋点（事件）

建议统一前缀 `points.*`（后端结构化日志 + 可选 telemetry）：

| 事件 | 关键字段 |
|---|---|
| `points.award.success` / `.rejected` | rule_code, user_id, delta, reason(cap/idempotent/exempt/disabled) |
| `points.deduct.manual` | operator_id, target_user, delta, rule_or_reason |
| `points.monthly_reward` | role_code, users_paid, skipped_no_login |
| `points.rank.refresh` | scope, duration_ms, user_count |
| `points.sync.push` | batch_size, success/fail |
| `points.balance.mismatch` | 对账任务发现余额≠流水和 | **P0 告警** |

前端（Portal）：

- `points_page_view` / `points_rules_open` / `leaderboard_tab_switch` / `points_message_click`

### 4.3 监控与告警

| 监控项 | 阈值建议（初值） |
|---|---|
| 记分失败率 | &gt;1% / 5min 告警 |
| 月奖任务未跑完 / 未触发 | 每月 1 日 01:00 仍未 success |
| 排行刷新延迟 | &gt;2h 未更新 |
| 同步 outbox 积压 | &gt;1000 或 oldest &gt;24h |
| 余额对账不一致 | 立即 P0 |
| 接口 P95 | 我的积分/明细/榜 &gt;1.5s |

### 4.4 对账任务（强烈建议，PRD 未写）

日批：抽样或全量校验 `sum(log.delta) == account.balance`；不一致写修复工单，**禁止静默改流水**。

## 5. 需求完整性与闭环检查

### 5.1 已相对闭环的部分

- 用户查看积分与明细、规则展示（配置驱动）  
- 管理员配置预置规则、手动调分、审计列表

## 7. 业界 / 开源实践对照（对本案的启示）

| 实践 | 来源共识 | 对本案建议 |
|---|---|---|
| Append-only ledger + 余额缓存 | 忠诚度/积分 LLD 通识；开源实现常见 trigger 禁 UPDATE | 直接采用；流水为 SSOT |
| Idempotency key | 防 MQ/HTTP 重试双计 | 所有自动发放必带业务幂等键 |
| 规则版本化 | 部分系统 DRAFT→PUBLISHED | 首期「改规则立即生效 + 流水快照名称/分值」即可；不必上完整版本状态机 |
| 日 cap / cooldown | 防刷标配 | 按规则 daily_cap；分享/收藏尤其需要 |
| 冲正而非改史 | 会计惯例 | 误操作走调分或 reversal |
| 排行异步物化 | 游戏/社区榜单 | 严格按 PRD 小时批，避免实时全表 |
| 积分与兑换拆域 | 航空里程/电商积分 | **兑换放协同办公**；知库只做发放与增量同步，边界清晰是优点 |
| 事件总线 | 大厂常见 | 本仓无总线，首期显式调用；若挂钩点 &gt;10，再评估轻量 Domain Event 表 |

参考方向（非选型依赖）：Bricqs points/ledger 论述、常见 Loyalty LLD（ledger + idempotency + expiry）、以及开源「append-only ledger + daily cap + adjustments」类实现。  
**过期/FIFO 核销**本 PRD 基本不做——不要过早引入 FIFO 复杂度。

### 11.2 组织四级层级 — 已闭环（2026-08-06）

#### 模型

| 项 | 决议 |
|---|---|
| 用户挂载 | **不改**：仍 `user_department` + 主部门 `is_primary` |
| 主数据 | **复用**现有 `department` 树，不新建并行组织表 |
| 四级标签 | `公司 → 部门 → 科室 → 班组`（建议字段如 `org_level`） |
| 推导规则 | 指定某节点为「公司」后，相对深度 +1→部门、+2→科室、+3→班组，递归打标 |
| 深度溢出 | 班组之下更深层 **仍标班组** |
| 深度不足 | 允许缺省中间层（如公司下仅一层则只出现「部门」） |
| 公司根数量 | **全树仅允许一个「公司」**（O5' B） |
| 未覆盖节点 | **不允许长期无标签**：组织须挂到该公司子树下并完成打标（O6' B） |
| 部门排名桶 | 从用户主部门节点 **向上找最近的「部门」标签**，在该桶内排名（O3' A） |
| 与知识库计分 | **两套独立**（O7' A）：标签服务排名/筛人；G* 仍按 knowledge space level |
| 维护入口 | **Platform**，仅 **超级管理员 / 平台管理员**（O8' B）；Portal 积分管理不开放打标 |
| O2 | **不适用**（已作废） |

示意：

```text
[唯一指定] 首钢股份 = 公司
  └─ 技术部           → 部门
      └─ 连铸车间     → 科室
          └─ 甲班     → 班组
              └─ 更深层 → 仍为班组
```

张三主部门 = 甲班 → 部门榜归入「技术部」桶（向上最近部门标签）。

#### 风险与约束（SDD 必写）

- **风险等级：中高**（改共享 `department` 语义/字段，波及部门树展示、筛选、可能影响依赖部门名的报表；**不改**用户挂载与 ReBAC 主路径）。  
- 可行性：可改干净；前置条件为超管完成「指定公司根 + 级联打标」；工作量中等（字段 + 级联 API + Platform UI + 积分排名读标签）。  
- 上线前校验：存在且仅有一个 `org_level=company`；其余活跃部门均在其子树并已打标，否则部门榜/筛人降级策略须在 SDD 写明（建议：阻断发布或运维告警）。  
- **建议不做**：借打标重做组织同步、改用户挂载、把知识库 level 与 org_level 强绑。

1. 权限矩阵：配规则/全站调分改为**仅平台管理员**；公共库管理员仅前台违规扣减。  
2. 删除「冻结/过期」措辞；有效积分 = 全站余额合计。  
3. 申诉改为「线下联系管理员」。  
4. 去掉原型「文档被订阅」、概览环比。  
5. 首页榜不展示当前用户置底行。  
6. 明确 G7=知识库间 SHARE（非外链），**本期接线**；G3 为补差价至最高档、单文档终身 ≤15。
