# 图解与选图方法

## 以理解问题为起点

复杂、抽象或难以跟踪的知识点、关系、流程优先用图解释：先让读者建立直观模型，再用文字／表格补充精确条件、字段和限制。识别本次难点，例如多方协作、分支和异常、生命周期、竞争时序、归属依赖、数据变换和环境边界；为需要图解的难点选择能回答问题的图。
通常先用一张概览图交代范围，再按实际复杂度和风险补图；概览可选择上下文或架构图，不强制各画一张。已有图仍有效时引用其版本并标明本次变化。简单局部修改可以简述，表格更清楚的枚举／字段不必改成图；不固定图数，不按类型凑齐。

## 场景与图类型

下表是选图规则。遇到对应复杂或关键设计点时，应给出相应图解；可用能同样讲清问题的组合／替代图，并说明理由。不可用一张概览图代替所有细节。

| 要回答的问题／触发场景 | 优先选择 | 图中至少表达 |
|---|---|---|
| 使用者、外部系统和本次边界容易混淆 | 系统上下文图 | 使用方、目标系统、外部依赖、交互方向及本次包含／排除边界 |
| 模块拆分、职责或依赖发生变化，内部机制难以理解 | 架构／组件图 | 模块职责、调用或依赖、数据归属及必要信任边界；需要时分现状／目标 |
| 业务分支、失败出口或多角色协作难以跟踪 | 流程图／泳道图 | 入口、动作、判断条件、成功和失败出口；跨角色时明确泳道及交接责任 |
| 跨模块调用、异步、回调、重试、超时或竞争时序是关键 | 时序图／时序对照图 | 参与者、消息方向／顺序、相关同步／异步、失败返回、重试及原子区。竞争要展示重叠与先后，不能只画成功直线 |
| 对象有生命周期、终态、禁止转换或状态竞态 | 状态图 | 真实业务状态、允许转换、触发／守卫条件及终态；禁止、重复和失败行为可在图旁表中精确说明 |
| 数据实体、归属或关系变化需要理解 | 实体关系图（ER） | 实体、主标识、关系含义及基数，必要的唯一性／归属；不把领域对象擅自画成已存在的数据库表 |
| 数据来源、变换、存储、敏感信息流转或信任边界复杂 | 数据流图 | 数据源、处理、存储／接收方、带含义的流向及相关权限／敏感边界；与调用顺序区分 |
| 部署形态、进程／节点、路由或真实基础设施边界变化 | 部署拓扑图 | 实际或拟定进程／实例、连接、协议及单／多节点范围；不能把本地保证画成分布式保证 |
| 抽象原理、多维关系或设计差异难以用上述图讲清 | 原理解释／概念关系／层次／时间线／前后对照图 | 先明确要解释的知识点，用分步示意、关系或对照呈现；类比须标明用途和失效边界，不充当实际架构 |

在相应章节附简短选图说明：**难点／要回答的问题 → 图类型及位置 → 关联需求／INV／决策／契约 → 选择理由**。记录本次选用和重要省略原因即可，不要求每份文档填完所有类型的“不适用”清单。若某个难点不适合画图，说明理由并给能有效解释它的替代形式。

## 画法与阅读层次

- 每张图有稳定标识、目的明确的标题、必要图例和简短解读。说明该看哪里、得到什么结论、适用边界；避免留下一张没有解读的复杂图。业务图先用通俗角色／动作；技术图保留与正文一致的真实模块名，首次技术词给解释。
- 概览与细节分层。一张图聚焦一个核心问题，节点过多、连线交叉或标注挤压时按职责／阶段拆图；复杂关系可以分步呈现，不把所有层次堆在一图。
- 箭头标明调用、数据、依赖或状态转换的含义，关键条件写在相应分支；同步／异步、可选／必须、现有／拟新增／未知通过标注和图例区分，不只依靠颜色。
- 关键失败结果对非技术读者也可见；技术时序可以展开阅读。使用图旁表格补齐边界、错误、字段、基数、超时窗口和恢复规则，不用“图大概如此”掩盖精确定义。
- 图中的组件、调用、关系、状态和能力来自有效需求、已核实代码／契约或明确标为建议的设计。不虚构服务、数据库、队列、UI、协议、故障恢复或部署节点来填图。

## HTML 与可用性

实际交付直接可见的内联 SVG 或 HTML/CSS 图解，默认不依赖 CDN、在线字体或打开后下载的库。Mermaid 等可以作编写中间格式，有获准的本地渲染能力时转为图形；仅交付源码、占位符或失效图片链接不算画完。
SVG 提供标题和文字说明，复杂图保留文字等价解释；确保文字和箭头可辨，宽图在窄屏可滚动／分层阅读，图例和说明可访问。按需打印时完整显示，避免节点、连线或文字裁切。遵守 [HTML 交付约定](../../sdd-workflow/references/html-delivery.md)。

## 内容核对与完成

先检查选图是否覆盖了实际复杂难点，再检查图本身是否正确；SVG 个数、页面能打开或一张图很精美都不能代替内容审查。

- 对照 REQ／AC、INV、正文和契约，核对参与方、职责、命名、箭头、条件、状态、基数及终态，变更时同步受影响图。
- 失败、重复、超时及并发涉及的关键保证在适用图或邻近说明中可查；原子区应覆盖实际检查和修改，不以分开的“先检查、再写入”暗示并发安全。
- 图中合法中间状态、结果未知与明确失败分别表达；不能把超时画成确定未生效，或画出契约禁止的终态恢复。
- 业务流程、调用时序、数据关系和部署拓扑各自承担解释职责。没有新存储／部署变化的任务，不为了凑图创造 ER 表或部署设施。
- 图中保证与证据范围一致；方案示意和静态推演不冒充运行验证。必要的复杂难点仍仅靠难懂文字、必要图解缺失或图文矛盾时，先修正再声明设计就绪。
