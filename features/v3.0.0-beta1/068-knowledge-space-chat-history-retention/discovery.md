## 1. 结论先行

PRD 的核心不是“删除目录时删除会话”，而是相反：**目录对象可以消失或离开原空间，但用户在原知识空间产生的历史对话必须保留，并在原空间根目录重新可见。**

当前数据并未真的丢失。根因是会话把空间和目录编码进 `flow_id`（例如 `space_12_folder_34` / `space_12_file_56`），而会话列表、历史读取、继续问答和删除操作都要求请求中的 `space_id + folder_id/file_id` 与该编码精确匹配，并先校验关联目录对象仍可见。目录被硬删除或跨空间移动后，`message_session` 和 `chat_message` 仍在，但入口失配，因此表现为历史对话消失。

本需求涉及会话归属、文件/目录删除、跨空间移动、历史数据和权限边界，建议按 **Full SDD** 处理。

---

## 2. PRD 已明确的业务口径

- 用户在知识空间中的文件夹内发起问答后，即使关联文件或文件夹被删除，历史对话也不能随目录入口消失。
- 关联文件或文件夹被移出当前知识空间后，对应历史对话仍归原知识空间。
- 上述失去目录入口的历史对话统一显示在 **原知识空间根目录**。
- PRD 明确这是当前客户需求的先行实现，后续仍可能由产品重新做完整设计和更新；因此本期应控制范围，不提前扩成全局会话重构。

---

## 3. 当前代码基线事实

### 3.1 会话与入口绑定方式

| 场景 | 当前绑定 | 当前读取条件 | 失配结果 |
|---|---|---|---|
| 知识空间根目录问答 | `space_{space_id}_folder_0` | 原空间可见 + flow_id 精确匹配 | 正常 |
| 文件夹问答 | `space_{space_id}_folder_{folder_id}` | 文件夹仍属于该空间且可见 + flow_id 精确匹配 | 文件夹删除/跨空间移动后不可读取 |
| 单文件问答 | `space_{space_id}_file_{file_id}` | 文件仍属于该空间且可见 + flow_id 精确匹配 | 文件删除/跨空间移动后不可读取 |

`message_session` 当前没有独立的知识空间或问答范围字段；空间/文件/目录归属只存在于 `flow_id` 和 `flow_name` 字符串中。

### 3.2 删除与移动链路

- 删除文件夹会收集整棵子树、清理权限和业务数据并硬删除文件/文件夹行，但不会处理对应会话。
- 批量删除复用单文件/文件夹删除链路，因此存在同样问题。
- 同空间移动保持资源 ID 和知识空间 ID，不会让当前 `flow_id` 失配；PRD 也只要求“移出当前知识空间”时回收历史。
- 跨空间移动会把文件、目录及子树的 `knowledge_id` 改为目标空间，但旧会话的 `flow_id` 仍带原空间 ID；它既不能在目标空间按新 flow_id 找到，也不能在原空间通过已离开的目录校验。
- 删除或移动知识空间本身不在 PRD §10 的触发范围。

### 3.3 前端行为

- client 的 `useFolderChat(spaceId, folderId)` 按当前空间/目录加载会话、历史并发起 SSE。
- 根目录只请求 `folder_id=0`；因此只有被归入根目录范围的会话才会显示。
- 历史列表已经支持多会话、切换、改名和删除；本期不需要另造一个“丢失会话”页面。
- 当前 active chat 由 `(space, folder)` 做前端内存记忆；目录消失后不能依靠该内存映射恢复，服务端归属必须成为真相。

## 4. 建议的业务范围

### 4.1 本次纳入

- 文件、文件夹或文件夹子树被删除时，把其关联的知识空间会话保留在原空间根目录。
- 文件、文件夹或文件夹子树跨空间移动时，把其在源空间产生的会话保留在源空间根目录；不把历史对话带到目标空间。
- 同时覆盖文件夹问答和单文件问答，避免 PRD“关联文件或文件夹”只修一半。
- 覆盖单项删除、批量删除和跨空间移动等所有现有业务入口；直接调用 API 与页面操作结果一致。
- 会话标题、消息、引用、点赞/点踩、创建人、会话创建时间、消息时间和用户手动删除状态保持不变；会话元数据更新时间可随入口归属更新，且当前不参与知识空间会话排序。
- 根目录按既有会话排序、切换、改名和删除规则展示回收后的会话。
- 用户仍需具有原知识空间的可见/使用权限；回收不能让无权用户重新看到空间或他人会话。
- 对上线前已经因文件/目录删除或跨空间移动而失去入口、但会话与消息仍存在的数据，提供可验收的恢复口径。

### 4.2 明确排除

- 同一知识空间内仅改变父目录时不回收到根目录，仍跟随原文件/文件夹 ID。
- 文件或文件夹重命名不改变会话归属。
- 不把源空间历史迁移或复制到跨空间移动后的目标空间。
- 不恢复用户主动删除的会话或已清空的消息。
- 不恢复已删除知识空间的会话入口。
- 不改变普通工作台、助手、工作流、灵思或频道文章会话。
- 不在本期新增跨用户共享会话、会话导出或全局历史中心。

## 5. 必须在 spec 固化的边界

1. **原空间归属**：目录移出后，历史只回原空间根目录，不进入目标空间。
2. **子树完整性**：删除/跨空间移动文件夹时，文件夹本身、所有后代文件夹和文件的关联会话都按同一规则处理。
3. **幂等**：同一业务动作重试不能复制会话或消息，不能让同一会话在根目录重复出现。
4. **并发**：目录操作与问答流并发时，已经持久化的历史不能丢失；迟到的结束事件不能把会话重新绑回失效目录。
5. **权限**：回收只改变会话在原空间内的展示范围，不改变会话所有者，也不绕过原空间访问权限。
6. **失败可见**：目录删除/跨空间移动若未能完成会话归属处理，不得把整体操作伪装成完整成功并留下永久不可见历史。
7. **历史数据**：上线前已失去入口的存量会话是否恢复，必须有明确验收结果，不能只保证新操作。
8. **后续问答**：用户从原空间根目录打开回收会话后，是只能查看历史，还是可以按根目录（全空间）范围继续问答，必须由产品拍板。
9. **回绑行为**：已回收到根目录的会话，在原文件/文件夹随后重新出现或移回原空间时，是否仍留在根目录，必须固定口径。

---

## 6. 已确认的 Discovery 裁定

用户已确认采用以下最小且一致的产品口径：

- **可继续问答**：回收会话在原空间根目录可查看，也可继续提问；后续检索范围按原空间根目录（全空间）计算，而不是引用已失效目录。
- **包含存量恢复**：上线时恢复仍有会话/消息、但关联文件或目录已不存在或已不属于原空间的历史记录；用户主动删除的数据不恢复。
- **回收后不自动回绑**：一旦因删除或跨空间移动回收到根目录，后续即使同 ID 资源重新回到原空间，会话仍留在根目录，避免历史入口来回跳动。
- **同空间移动不触发**：资源仍在原空间时，会话继续绑定资源 ID；只有删除或跨空间移出才触发根目录回收。

上述产品决策已写入 `spec.md`，并以 EARS 验收标准覆盖删除、批量删除、子树、跨空间移动、并发、权限和存量恢复；Spec 与修订后的 Design 已确认，尚未生成 `tasks.md`。
