# 发版批次与分支角色

> 配套阅读:`docs/cofco-merge-playbook.md`(合并顺序与必冲突清单)—— 那份只在中粮线
> (`feat/cofco-909-*`)上维护,主版本分支上看不到它。两份分工:手册讲「**怎么合**」,
> 这份讲「**合给谁、什么时候发**」。这份在两条线上都保留。
>
> 这份文档存在的原因是 2026-09-15 的一次事故:分支名读反了,一条正在发版的分支被
> 快进到了下一批,开放 API 的 20 个提交连同授权模型一起进了客户包。详见文末。

---

## 1. 一句话规则

> **带 `-test` 后缀的是「本期正在发的」,不带的是「下一批」。**

名字读起来是反的 —— `-test` 听着像「测试用、比较新」,实际它是**更保守、更靠前发布**的那条。
每次动这两条分支之前,先把这句话念一遍。

> 2026-09-16 起,两条 `-test` 已被 `-batch1` 取代(09-15 事故后另开的干净分支),
> 下表的「本期发版」现在指 `feat/3.0.0-beta1-batch1` 和
> `feat/cofco-909-3.0.0-beta1-batch1`。`-test` 两条已污染,不要再往上发版。

| 分支 | 角色 | 含新开放平台功能 |
|---|---|---|
| `feat/3.0.0-beta1-batch1` | 主线,**本期发版** | 否 |
| `feat/3.0.0-beta1` | 主线,**下一批** | 是 |
| `feat/cofco-909-3.0.0-beta1-batch1` | 中粮线,**本期发版** | 否 |
| `feat/cofco-909-3.0.0-beta1` | 中粮线,**下一批** | 是 |

「含新开放平台功能」指 09-15 那批新提交(免登录链接、v2 错误码等)。
**服务账号 / API Key / PAT 的代码本身两批都有**,客户手上一直就有,
只是开关默认值不同。不要拿「`open_api/` 目录在不在」判断分支属于哪一批。

两条 `-test` 对应发一批,两条不带的对应发下一批。**客户手上同时存在两个版本,这是有意的。**

---

## 2. 两条铁律

**第一,`-test` 落后于不带后缀的那条,是有意的,不是掉队。**

`git rev-list --left-right --count A...B` 显示 `-test` 落后几十个提交、且没有独有提交时,
**那不是「停在原地需要追上」**,而是「这一批还没到」。看到这个数字不要快进。

**第二,永远不要把不带后缀的合进 `-test`。**

方向只有一条:

```
feat/3.0.0-beta1-test  ──→  feat/3.0.0-beta1          (本期 → 下一批)
        │                            │
        ↓                            ↓
feat/cofco-909-…-test  ──→  feat/cofco-909-…          (本期 → 下一批)
        主线 → 定制线,同层级横向
```

反过来合 = 把下一批的功能提前塞进正在发的包里。

---

## 3. 改一个 bug 该往哪落

**通用缺陷**(两批都要):落在 `feat/3.0.0-beta1-test`,然后

```
3.0.0-beta1-test  →  cofco-909-3.0.0-beta1-test   (本期两条线)
3.0.0-beta1-test  →  3.0.0-beta1                  (带给下一批)
cofco-909-…-test  →  cofco-909-3.0.0-beta1        (带给下一批)
```

**只有下一批需要的功能**:直接落 `feat/3.0.0-beta1`,不要碰 `-test`。

**中粮定制**:落 `feat/cofco-909-3.0.0-beta1-test`,只在中粮两条线之间流动,
**永不回流主版本**(见合并手册 §1)。

## 4. 授权模型跟着批次走(最容易炸的一条)

F048 的 OpenFGA 授权模型**版本号写在代码里**。**两批现在统一为 `f048-v5`**
(2026-09-16 起)。原来本期是 v4、下一批是 v5,那个分裂本身就是个雷:任何一次
合并方向搞错,模型就跟着变,客户环境启动即报
`authorization_model_migration_required`,**所有走权限的接口 500**。

统一取 v5 是因为它是 v4 的**严格超集** —— 只多允许服务账号作为几个技术标记
关系的主体,类型定义一个没加。本期分支上没有任何代码会写这类 tuple,也没有
任何权限检查用服务账号主体(检查一律走 `user:`),所以对本期是纯惰性的。
配套的写入改动(`TECHNICAL_MARKER_SUBJECTS`,7 个文件)留在下一批,跟开放平台
功能一起发。

**为什么不能反过来把客户降回 v4**:运行时认的是 OpenFGA store 里**最新**的那个
模型(`discovery.py` 把模型 ID 排序后取最后一个),而 OpenFGA 的模型只能追加、
删不掉。所以数据库怎么改都没用,启动还是会挑到 v5。这就是「单向、没有回退
命令」的实际含义 —— 不是少写了个命令,是结构上回不去。

合并前后都查一次:

```bash
git show <branch>:src/backend/bisheng/core/openfga/authorization_model_f048.py | grep '^MODEL_VERSION'
```

模型确实要升时的处置见合并手册文末「部署提醒」。

## 5. 给客户的镜像不要用分支名

CI 对每个 `feat/*` 分支构建同名镜像(`/` 换成 `_`),**每次推代码都会重建同一个 tag**。
所以分支 tag 指向的内容随时在变:

- 客户以为「换回上个版本」,拉到的其实是重建过的新内容
- 真出问题时没有可回退的坐标

**客户环境一律用日期 tag**(`v3.0.0-cofco-0916` 这种),内容固定;实在要精确到位就用镜像 digest。
分支 tag 只给我们自己的测试机用。

## 6. 附:2026-09-15 那次事故

`feat/3.0.0-beta1-test` 当时落后 `feat/3.0.0-beta1` 73 个提交且没有独有提交。
我(Claude)判断成「它只是停在原地」,快进拉平了两条线,`cofco-909-3.0.0-beta1-test`
也照此处理。

后果:

- **20 个开放 API 提交**(服务账号 / API Key / PAT / 免登录链接 / v2 错误码)进了本期分支
- 授权模型从 `f048-v4-contextual-departments` 变成 `f048-v5`
- 客户拉到重建后的分支镜像,启动即 `authorization_model_migration_required`,
  换回「上一个版本」也无效 —— 那个 tag 的内容已经不是原来的了

恢复:从快进前的提交另开干净分支
(`feat/3.0.0-beta1-batch1` ← `75455c572`,`feat/cofco-909-3.0.0-beta1-batch1` ← `857fababa`),
没有强推已被他人使用的共享分支。

**教训**:分支落后不等于该追平。动任何一条正在发版的分支之前,先确认它属于哪一批。
