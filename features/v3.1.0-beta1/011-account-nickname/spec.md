# Feature: 账号与昵称规则及前后端统一

**关联 PRD**：[账号与昵称规则优化 PRD](../../../docs/PRD/3.1beta1%20账号与昵称规则优化%20PRD（页面标注版）.docx)；[已确认需求发现](./discovery.md)；[注册页最新要求](../010-registration-validation/spec.md)。
**优先级**：P0；**所属版本**：v3.1.0-beta1；**依赖**：现有用户身份、人员管理、组织与身份同步，以及 F010 注册页。
**状态**：规格、设计及组合编辑事务范围均已确认；前后端实现与本地验证完成，真实环境验收待执行。

## 1. 用户故事与范围

作为用户，我希望账号用于登录、昵称用于展示，能够修改自己的昵称并保留原有账号、登录及资产关联。

作为有权限的管理员，我希望创建独立的账号与昵称，查看和编辑受管辖人员的真实系统昵称，并能准确区分同名人员。

作为历史用户，我希望升级后保留原来的账号和昵称；仅在主动修改昵称时遵守新规则。

纳入后台编辑用户资料、后台创建本地用户、后台成员列表、个人账号信息、注册和登录，以及已有本地创建兼容入口、名称展示、查重、同步和操作记录。既有批量导入入口若存在，执行相同的新建与变更规则；不新增导入产品功能。

本期不更换密码存储方案，不新增账号修改入口，不改变角色、部门、租户和资源归属，不批量清洗历史身份数据。公司测试后端发布与共享业务数据变更另行安排。

## 2. 验收标准

### 2.1 字段规则与历史数据

- **AC-01** — THE SYSTEM SHALL 在本特性页面、相关名称标签、搜索提示、错误和导出字段中统一使用「账号」「昵称」，不把内部用户 ID、部门 ID、组织 ID 改称账号。
- **AC-02** — WHEN 注册或创建本地账号，THE SYSTEM SHALL 接受 1 与 64 个字符的合法账号，拒绝空值与超过 64 个字符的账号；保留原大小写及数字前导零。
- **AC-03** — WHEN 创建本地账号，THE SYSTEM SHALL 要求以英文字母或数字开头，后续仅允许英文字母、数字及 `. _ - @`；拒绝空白、控制或不可见字符及其他字符。
- **AC-04** — WHEN 新建用户或实际修改昵称，THE SYSTEM SHALL 在前后端统一接受 1–32 个可见 Unicode 字符、拒绝空值与 33 个字符，并允许昵称重复；中文、英文及单个 Unicode 字符的计数口径一致。
- **AC-05** — WHEN 在账号或昵称输入框键入、粘贴或提交输入法结果，THE SYSTEM SHALL 阻止空格及空白字符进入有效输入；当请求直接携带非法新值到达服务端，THE SYSTEM SHALL 拒绝写入，不静默修正该请求值。
- **AC-06** — WHEN 读取或维护历史人员资料，THE SYSTEM SHALL 保留原账号、昵称及其大小写、长度、特殊字符和身份关联；仅因启用、禁用、恢复或变更部门、角色、用户组，不得触发未变更字段的新校验。
- **AC-07** — IF 历史昵称保持原值，或编辑后在提交前恢复原值，THEN THE SYSTEM SHALL 按未改名处理；IF 昵称实际变化，THEN THE SYSTEM SHALL 仅对新昵称执行新规则，不以历史账号不符合新规则阻断改名。

### 2.2 账号唯一性与登录

- **AC-08** — WHEN 创建新本地账号，THE SYSTEM SHALL 在完整实例范围内查重，覆盖部门、租户、账号来源以及禁用和已删除账号；不允许以不同入口绕过查重。
- **AC-09** — WHERE 不存在历史账号兼容占用冲突，THE SYSTEM SHALL 允许新账号 `AB001` 与 `ab001` 分别存在并各自精确登录；`Ab001` 不得自动匹配其中任一账号。
- **AC-10** — IF 待创建的新账号落入历史账号原有的匹配占用范围，THEN THE SYSTEM SHALL 拒绝创建并提示账号已存在，不改变原历史账号。
- **AC-11** — WHEN 历史账号登录，THE SYSTEM SHALL 保留该账号原有匹配能力，不因新账号的长度或字符限制使其失效；不得给所有登录输入统一套用新建规则。
- **AC-12** — WHEN 新账号登录，THE SYSTEM SHALL 按完整大小写识别账号，不以昵称、自动转小写或裁掉空白后的另一账号代替。
- **AC-13** — IF 历史身份存在多个候选而不能唯一识别，THEN THE SYSTEM SHALL 明确拒绝并提示处理，不自动合并、改名或通过遍历候选密码选择身份。
- **AC-14** — WHEN 同一个新账号被并发创建，THE SYSTEM SHALL 至多创建一个身份，其余请求返回明确失败结果；大小写不同的新账号仍按各自规则判断。
- **AC-15** — THE SYSTEM SHALL 保留既有验证码、密码验证、错误次数与锁定、禁用账号、租户归属及会话控制；昵称修改不得改变账号或使当前有效会话无故失效。

### 2.3 个人信息与后台页面

- **AC-16** — WHEN 打开个人账号信息，THE SYSTEM SHALL 展示当前昵称和可选中、可复制的只读账号，并提供「修改昵称」入口；账号不存在时不得用昵称虚构登录账号。
- **AC-17** — WHEN 本人修改昵称，THE SYSTEM SHALL 在当前页展开编辑，默认填入原值，展示字符计数、「1–32 个字符，不支持空格和空白字符」及「保存后，你在系统内显示的昵称都会更新」；支持取消和 Esc 放弃输入。
- **AC-18** — WHEN 本人请求修改昵称，THE SYSTEM SHALL 仅修改当前认证身份，拒绝通过指定其他用户标识、身份字段、权限或账号信息修改他人及受保护字段。
- **AC-19** — WHEN 管理员打开人员编辑，THE SYSTEM SHALL 展示昵称与只读账号，说明「修改后，该用户在系统内显示的昵称都会更新」；沿用现有来源、部门、租户和管理权限边界，不把改名实现为备注。
- **AC-20** — WHEN 创建本地用户，THE SYSTEM SHALL 分别收集账号、昵称和初始密码，显示可读取的填写规则、密码显隐和具体字段错误；创建结果包含完整账号。
- **AC-21** — WHEN 查看或搜索后台成员，THE SYSTEM SHALL 展示昵称与账号并支持二者搜索；同名成员可通过完整账号区分；可编辑成员行进入编辑时，不影响行内按钮、开关、选择等操作，且尊重现有不可编辑状态。
- **AC-22** — WHEN 本人或管理员保存昵称成功，THE SYSTEM SHALL 使两者在刷新用户资料后读取同一个新昵称，并更新当前用户展示；账号、内部身份、密码、角色、资产归属及已有记录关联保持不变。
- **AC-23** — IF 保存失败，THEN THE SYSTEM SHALL 保留本次输入、原昵称及其附属状态，显示失败原因并允许重试；WHILE 保存处理中，THE SYSTEM SHALL 阻止重复提交；WHEN 取消，THE SYSTEM SHALL 不写入修改。
- **AC-24** — WHEN 人员改名，THE SYSTEM SHALL 记录操作者、目标用户、修改前后昵称、时间及结果；保留过去事件中的昵称快照，不批量改写历史记录。

### 2.4 同步、显示及注册交互

- **AC-25** — WHEN 第三方组织或身份同步，THE SYSTEM SHALL 保留原始外部身份标识及对接匹配约定；IF 用户已主动修改站内昵称，THEN THE SYSTEM SHALL 保留该昵称，同时继续同步其他有权威来源的字段。
- **AC-26** — WHERE 既有本地批量导入或兼容创建入口存在，THE SYSTEM SHALL 区分新建和更新，逐条反馈非法字段；未改变的历史字段不被静默清洗，实际新建及改名不能绕过统一规则。
- **AC-27** — WHEN 展示长昵称或历史长账号，THE SYSTEM SHALL 保持布局可用、提供全文查看，账号复制结果与完整原值一致；键盘和触屏均可读取填写规则、定位错误并完成昵称编辑。
- **AC-28** — THE SYSTEM SHALL 保持注册页最新 medium 输入框、与登录页一致的宽度、问号规则入口、密码显隐，以及仅两项密码强度圆点提示：「至少8个字符」「必须同时包含大小写字母、数字和字符」；长度独立判断，字符组合同时满足四类才通过，颜色跟随当前主题。
- **AC-29** — WHEN 在本地创建入口设置新密码，THE SYSTEM SHALL 要求至少 8 个字符及大写字母、小写字母、数字、符号同时存在；空白或汉字不得被误算作符号，前后端拒绝结果一致。
- **AC-30** — WHEN 注册时两次密码不一致，THE SYSTEM SHALL 显示确认密码红框及原因；正确或未输入时不显示常驻确认说明。登录仍以「账号」「密码」作为占位，不额外添加大小写提示或页面介绍。
- **AC-31** — IF 新值违反规则或账号冲突，THEN THE SYSTEM SHALL 在写入前拒绝，并返回可识别、可展示的错误；前端显示具体原因，页面和服务端的中文、英文、日文口径一致。
- **AC-32** — WHEN 升级并启用本功能，THE SYSTEM SHALL 保持历史账号、昵称及身份关联原值，能够识别各账号适用的规则；不得通过批量转换或将旧字段缩短到新上限实现规则统一。

## 3. 边界场景

| 场景 | 预期 |
| --- | --- |
| 昵称 1、32、33 个字符 | 前两者合法；最后一个拒绝。 |
| 历史昵称含空白或超过 32，提交时昵称未变 | 原值保留，允许其他有权限的资料修改。 |
| 历史昵称实际改为新值 | 新值必须满足 1–32 及可见字符要求。 |
| 两个新账号仅英文字母大小写不同 | 按精确账号分别创建和登录，不自动转写。 |
| 新账号撞入历史账号的兼容范围 | 拒绝新建，历史账号及其占用不变。 |
| 禁用、已删除账号或跨来源冲突 | 新建查重不得漏过。 |
| 修改第三方用户站内昵称后再同步 | 主动昵称保留，原始外部身份及其他字段按原约定处理。 |
| 普通用户指定他人身份进行改名 | 拒绝，双方资料及权限保持不变。 |
| 成员行内启禁开关、重置密码、其他按钮 | 执行各自动作，不额外打开编辑弹窗。 |

## 4. 原 PRD 与最新口径

原 PRD AC-ACC-01～26 的字段语义、查重、历史兼容、自助与管理员改名、审计、同步、导入及可访问要求均在上表覆盖。注册页样式采用用户后续明确修订：简短占位、移除常驻说明、medium、密码显隐、两项圆点提示。前端按已确认要求过滤空白，直接请求服务端时拒绝非法新值。

本文仅规定可观察行为；具体字段、约束、接口契约、迁移及实施步骤归后续设计与任务文档。
