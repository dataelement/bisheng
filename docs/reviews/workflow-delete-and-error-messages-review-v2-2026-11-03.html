工作流逻辑删除与错误提示

两项改进：用一个标记完成逻辑删除；用五类固定提示说明问答失败环节，复用已有原因补充恢复建议。

功能一：工作流逻辑删除功能二：五类问答失败提示

功能一：工作流逻辑删除

只加一个删除标记，正常列表和新操作统一检查；在途实例不增加协调机制。

核心改动

未删除is_delete = 0，正常查看和使用
→
已删除is_delete = 1，保留数据，关闭新操作

上线 / 下线保持原意。不增加“删除中”状态或删除进度表。

删除后会怎样

对象处理方式
主记录与版本一起标为已删除，工作流定义仍留在数据库中。
列表、搜索、推荐不再显示；配额和新建重名检查排除已删除记录。
新的编辑与调用旧页面、分享链接、网页及接口发起新操作时，检查删除标记并拒绝。管理员同样受限。
历史会话与文件按原有权限查看；已有模板和复制件保留。
执行中的任务不因删除主动打断；运行中仍可能因再次查询工作流信息而失败，正常聊天入口再次输入时会拒绝续跑。不额外改造在途处理。

沿用原流程，替换物理删除

  1. 检查删除权限。沿用现有授权校验及权限撤销流程。
  2. 更新删除标记。在一个数据库事务里更新主记录和版本。
  3. 执行原有清理。记录谁删除了工作流、移除用户组使用入口、给历史会话保留名称等信息，并让分享链接失效。历史会话和消息不删除。

保留原接口和异常处理，不新增后台删除协调器或自动补偿系统。

配套改动，集中在三处

查询统一过滤。列表、详情、计数、模板来源等都检查同一标记；历史读取保留自己的权限和读取路径。

新操作检查。编辑、发布、调试和新调用检查未删除；不改后台任务调度和运行状态机。

避免旧页面写回。保存时只更新未删除记录，不允许修改标记或把旧对象重新插入。

本期不做：删除进度表、运行实例清理、额外业务版本号、回收站、恢复和定时清空。

展开取舍与验收重点

简化后保留什么限制

权限撤销和数据库更新仍不是一个事务。如果权限已撤销、标记更新失败，可能出现记录还在但不能使用；清理失败也可能需要排查日志。沿用现有权限账本与运维修复机制，不承诺所有异常都能靠再次点击删除恢复。

执行中的实例可能继续，也可能因现有检查失败。本期不增加跨进程同步、定时清理或运行快照，也不以“全部终止”或“全部完成”为验收标准。

数据库和并发怎么处理

主表只新增非空整数 is_delete，默认 0，与版本已有字段的命名和取值一致。只为工作流启用逻辑删除；不改变共享表中其他类型的删除行为。删除时间和操作者沿用现有审计。

普通修改带上未删除条件，更新不到记录时拒绝保存。版本修改与删除使用同一父记录短锁，父记录检查与版本写入在同一事务完成；不另建版本号体系。

上线与验收

  • 先迁移字段，再更新所有相关进程；旧版本退出后再开放删除。
  • 验证 MySQL、DM8；删后主记录、定义、版本仍在，标记一致。
  • 验证列表与数量、新编辑和调用入口、历史与文件权限，以及跨租户隔离。
  • 验证并发保存不会恢复标记或重新插入旧记录。
  • 回滚仍须保留删除过滤和禁止物理删除的处理，不能直接换回忽略标记的旧代码。

以前已经物理删除的数据不能自动补回。保留数据会持续占用存储，清理期限另议。

功能二：问答失败提示

页面固定五类，帮助用户找到异常环节和对应维护方；最终故障原因和责任归属仍依据日志排查确认。

五类固定主提示

每次基础服务异常只显示一个主分类。细分原因不改变主文案；服务名称、报错时间和已有定位信息紧邻展示。

分类固定主提示相邻辅助信息
数据库【数据库】数据服务访问异常，请联系对应的数据服务维护人员排查。已识别的业务数据库、缓存或检索组件，例如达梦、MySQL、Redis、Elasticsearch、Milvus。
网络【网络】网络连接异常，请检查网络连接；持续异常时，请联系网络维护人员排查。已确认的连接环节，例如当前设备到平台或接入网关链路。
模型服务【模型服务】模型调用异常，请联系模型服务维护人员排查。当前模型展示名称；按已有可见范围展示相关调用信息。
单点登录【单点登录】登录认证异常，请重新登录；持续异常时，请联系单点登录维护人员排查。当前登录入口及已有登录定位信息。
对象存储【对象存储】文件存储服务访问异常，请联系对象存储维护人员排查。已识别的对象存储组件，例如 MinIO，以及当前文件操作。

页面怎么展示

模型服务

模型调用异常，请联系模型服务维护人员排查。

模型：企业配置的模型 A　报错时间：2026-11-03 10:30

定位信息：沿用已有追踪编号（有则显示）

恢复建议：稍后重试；若持续出现，请联系模型服务维护人员检查调用限制。

上例仅演示“已有错误分类明确为模型限流”时的补充建议；不是每次模型异常都显示限流建议。真实错误、原始异常和堆栈留在受控日志或既有问题详情中。

恢复建议只做简单映射

已有错误码或已识别原因能确定，就补一句对应建议；确定不了，就使用该类固定提示中的默认建议。

已有识别结果补充恢复建议
模型限流、临时超时稍后重试；持续异常时联系模型服务维护人员。
模型认证失败、余额不足、模型不可用按已有原因分别提示维护人员检查凭证与权限、账户余额或模型启用配置。
上下文超限、内容安全拦截分别提示缩短或拆分内容、调整输入表达后重新提交。
已确认登录失效重新登录；沿用现有输入保留能力，不新增恢复机制。
仅页面连接断开恢复连接后先查看原任务状态，避免重复提交。

不增加复杂原因推断、供应商专属适配、多层兜底或新的问题追踪系统；不改自动重试、任务调度及失败步骤恢复逻辑。

归类边界要清楚

  • 按已确认的调用对象归类。连模型超时归模型服务，连 MySQL 超时归数据库；仅确认设备到平台或入口传输链路异常时归网络。不能看见“超时”就都归网络。
  • 业务提示保留。平台积分、正常权限拒绝、输入校验、文件损坏或格式不支持、资源已删除，继续用原业务提示，不硬塞进五类。
  • 平台错误和未知原因不甩给第三方。平台自身处理异常或证据不足，沿用通用失败提示并进入内部待定位；不凭 HTTP 401、403 就认定是单点登录问题。
  • 检索、文件和工具按实际依赖归并。例如 Milvus 失败归数据库、Embedding 模型失败归模型服务、MinIO 失败归对象存储；独立解析服务或工具自身异常沿用原提示或通用提示。

五类用于标识异常对象，不代表已确定最终责任。只能使用已识别的来源和可见信息，缺少组件名称或定位编号时不猜测、不补造。

展开研发范围与验收重点

研发只做三件事

  1. 把已有错误分类与异常入口归并到五类；业务校验和未知异常保留原处理。
  2. 复用现有提示组件，显示固定主文案、已有辅助信息；已识别的细分原因通过简单配置补充恢复建议。
  3. 沿用已有错误字段和定位信息，核查实时、刷新后和历史提示的口径一致；不为文案新增复杂识别链路。

验收抓住四点

  • 数据库、网络、模型服务、单点登录、对象存储主提示与 PRD 固定文案一致；同次失败只有一个主分类。
  • 模型连接失败不误归入口网络，模型鉴权不误归单点登录；业务拒绝与未知错误不被错误覆盖。
  • 已识别原因命中对应建议；无细分原因时只有默认建议，不显示猜测。辅助信息遵守原有可见范围。
  • 实际已知的步骤失败、任务停止或仅页面断开不混淆；未确认任务状态不宣称任务已停止。不暴露密钥、敏感请求内容或堆栈。

维护人员对应企业现有的数据、网络、模型、单点登录及存储维护角色；有既有联系方式时沿用，不新增人员目录或通知流程。
