# F073 测试关注点与影响范围

> 依据：[spec.md](./spec.md)、[design.md](./design.md)（截至 2026-09-28）。
> 影响范围按代码实际调用方核对，不是按目录猜的。

## 1. 影响范围

新增的 E+ 线路本身是隔离的。会波及现有功能的，是要改动的两处共用代码。

### 1.1 会波及现有功能

**助手执行核心 `AssistantAgent`（改动大，风险最高）**

这个类有 5 个调用入口，改完都要回归：

| 入口 | 代码位置 | 用户侧功能 |
|---|---|---|
| 内部助手对话 | `common/chat/client.py:222` | 平台和客户端里跟助手聊天（WebSocket） |
| 开放 API / 分享页调用已发布助手 | `assistant/domain/services/published_assistant_service.py:86`，被 `open_endpoints` 和 `public_endpoints` 使用 | `/api/v2` 调用助手、免登录分享页 |
| 助手上线 | `api/services/assistant.py:600` `update_status` | 上线时会初始化工具做校验 |
| E+ 连接生命周期 | `eplus/worker.py` + supervisor 对账 | 保存离线助手配置只落库；上线且启用后连接，下线或关闭配置后断开；在线时启用或换凭据会连接/重连；worker 重启可从数据库恢复目标状态 |
| 助手自动优化提示词 | `api/services/assistant.py:474` / `724` | 助手编辑页的「自动优化」 |
| 评测 | `evaluation/domain/services/evaluation_service.py:275` | 用评测集批量跑助手 |

要改的四处都在这个类里：接收图文输入、历史裁剪、执行上下文、装载工具。原则是内部入口默认行为不变，测试必须证明这一点。

**日常对话的图片处理 `_process_agent_files`（改动中等）**

只有一个调用方 `workstation/domain/services/chat_service.py:1657`，即客户端日常对话里上传图片或文件。要把其中的图片分流逻辑抽成共用函数，日常对话的附件处理需要回归。

### 1.2 不波及现有功能

- 新表、管理接口、连接 worker、业务编排、机器人知识检索都是新代码，只在 E+ 线路里用。
- 内部知识空间检索 `space_flow_retrieval` 不改。
- 权限模型不改；保存绑定只校验操作者有助手编辑权限及空间同租户、有效，不检查操作者个人空间权限。
- 组织同步不改，只读用户表。
- 部署多一个进程类型（连接 worker）。部署编排要加上它；不配 E+ 机器人时，它应该空转或不启动。

## 2. 测试重点

P0 是越权和数据泄露，一条都不能漏。

### 2.1 P0：知识越权（AC-11 到 AC-17）

| 场景 | 预期 |
|---|---|
| 两个机器人分别绑定互不重叠的空间 A 和 B，问 B 里才有的内容 | 机器人 1 答不出来，也不引用 B 的内容 |
| 提问人对空间 C 有个人权限，甚至是空间管理员，但机器人没绑 C | 查不到 C |
| 绑定空间里有设了自定义权限、不继承空间授权的文件夹 | 机器人能检索到；这是和内部助手刻意不同的地方 |
| 管理员没有目标空间的个人权限，但有该助手 E+ 接入管理权限 | 可以绑定该同租户有效空间；机器人用户可问答，操作记审计 |
| 管理员尝试绑定其他租户、已删除或不存在的空间 | 保存失败，原绑定不受影响 |
| 机器人没绑任何空间 | 知识检索结果为空，不会回退到助手自己原本关联的知识库 |
| 回答生成到一半，管理员撤销绑定 | 本轮继续使用启动快照并正常返回；下一轮使用新绑定；旧历史继续保留 |
| 绑定空间被删除 | 已启动轮次继续；下一轮不再把该空间纳入新检索范围 |
| 助手挂了会查毕昇知识的工作流或 API 工具 | E+ 入口不装载这类工具 |
| 管理员没有某空间的个人管理权，但有助手 E+ 接入管理权限 | 可绑定同租户有效空间；这是机器人授权而非管理员个人授权 |

### 2.2 P0：身份（AC-02 到 AC-04、AC-18）

| 场景 | 预期 |
|---|---|
| 库里不存在的 E+ 员工 ID | 回复「无权限使用」，助手、工具、检索都没被调用（查日志确认） |
| 员工已停用或删除；员工存在但不属于当前租户 | 同上 |
| 同一个群里一个人能用、一个人不能用 | 各自按本人判定，互不影响 |
| 消息里的 `aibotid` 和当前订阅的机器人不一致 | 丢弃 |
| 网关把 IAM `userid` 写入 `external_user_id` 后同步入库 | `user.source='wecom'` 且 `user.external_id` 原样保存；E+ `from.userid` 能精确命中 |

### 2.3 P0：内部入口回归（AC-17）

- 上表 5 个入口各走一遍主路径：
  - 助手对话覆盖纯文字、带知识库、带知识空间，「用户知识库权限校验」开和关各一次；
  - 开放 API 调用；
  - 分享页；
  - 上线；
  - 自动优化；
  - 评测。
- 日常对话上传图片，视觉模型和非视觉模型各测一次；上传文档和视频附件。
- 现有测试原样通过：`test_assistant_knowledge_auth_gate.py`、`test_assistant_runlog_frames.py`、`test_assistant_llm_executor_default.py` 等。

### 2.4 P1：消息与会话（AC-05、AC-06、AC-19）

- 重复投递：同一个 `msgid` 投两次，只回答一次。
- 并发重复投递到同一/不同 worker：只有 `(tenant_id, bot_id, msgid)` 原子插入成功者执行 Agent；Redis 热键丢失也不会重复执行。
- 会话隔离：单聊和各个群的上下文互不串；同一个群里两个机器人的历史不共享。
- 排队：同一会话连发 3 条，先按到达顺序以 `PREPARING` 预占轮次；图片保存完转 `QUEUED`，后发文字不能越过尚在下载的图片。前一轮终态后由同一 worker 的会话消费协程主动取下一条，无需用户重发、无需 Celery 触发；轮到执行并发出首帧时才开启该消息自己的 6 分钟回复流窗口，并能看到前序完整问答历史。第 4 条立即回复「消息处理中，请稍后再试」且不执行 Agent。
- worker 崩溃：回答中途杀掉 worker，这条消息不能永远卡住，也不能重复回答。
- 长回答：超过 20KB 时截断并提示。整个回答过程发送次数不超过 30 条/分钟，最后的结束消息一定能发出去。
- 模型快速产生大量小片段时按约 1–2 秒或缓冲阈值合并刷新，不按字/按 token 逐帧发送；每帧仍为累计全文。

### 2.5 P1：图片（AC-07 到 AC-10）

- 输入形式：单聊纯图片、单聊图文混排、群聊 @机器人 加图片；一条消息里带多张图时，顺序和对应的文字保持一致。
- 模型能力：
  - 视觉模型：能描述图中内容；
  - 非视觉模型但配了 OCR：能读出图里的文字；
  - 两者都没有：明确说看不了图，不编造。
- 失败情况：图片 URL 超过 5 分钟、解密失败、图片过大时，明确提示；同条消息里的文字部分照常回答。
- @ 前缀：群聊里的 `@机器人` 不出现在模型输入和会话历史里。

### 2.6 P1：连接稳定性

- 断线重连：断网或重启 worker 后自动重连，不丢消息；重连间隔按 1s、2s、4s…上限 30s 递增。
- 心跳判死：连续 2 次心跳没有回执，主动断开并重连。
- 多副本：多个 worker 副本同时运行时，每个机器人只有一条连接，不会互相踢。
- 被踢下线：用别的客户端（例如客户 demo）抢占同一个机器人，毕昇收到被踢事件后停止发送、不自动重连并告警，不会和对方互踢。
- 订阅被拒：E+ 拒绝订阅时，立即断开连接并退避重试，不会紧密重试；后台状态显示「未认证」而不是「已连接」。
- 连接方式：`ws://` 地址能连；`wss://` 加客户自签 CA 能连，图片下载也用同一 CA。

### 2.7 P1：回复协议

- 回执串行：同一条消息的多次流式刷新按顺序发出，每帧等到回执再发下一帧；回执超时（5 秒）或 `errcode≠0` 时停止该轮刷新并记录。
- 占位失败：首条「处理中」发送失败时，不调用助手。
- 超时上限：整轮回答约 5 分钟内必须发出结束帧；模型/工具一直等待且没有任何文本片段也必须被外层超时取消。
- 解密对拍：同一份密文和 aeskey，毕昇解密结果与官方 SDK `decrypt_file` 一致（覆盖 aeskey 缺 `=`、密文长度非 16 倍数、填充值大于 16 的情况）。
- 协议容错：`msgid` 缺失的消息被丢弃并告警，不会被重复回答；图文混排里某项缺 `msgtype` 时仍能按内容识别文字和图片。

### 2.8 P2：管理后台与其他

- Secret 不回显；轮换后新连接生效。
- 同一租户内助手 ID 与机器人 ID 都不能重复绑定；单个机器人可保存多个知识空间。
- 连接状态显示准确。
- 界面中、英、日完整。
- MySQL 和 DM8 上建表与唯一键都正常。
- 日志里没有消息原文、Secret、aeskey、完整的图片 URL。

## 3. 测试上的难点

- **没有真实 E+ 环境时怎么测。** 做一个模拟 E+ 的 WebSocket 服务，按客户文档的报文格式推消息、收回复。单聊、群聊、重复投递、被踢下线、限流都能在 CI 里测，联调时只验证真实差异。
- **图片解密。** 在客户给出样例之前没法确认对错，这项测试只能联调时完成。见 [customer-checklist.md](./customer-checklist.md) Q2。
- **越权测试要查「没发生什么」。** 只看回答内容不够，要在审计记录或日志里确认没有检索未绑定空间、没有调用被禁的工具。
