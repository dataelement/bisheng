## 范围边界

**本次纳入**：

- 全开源、可选安装、无商业上线额度的 Docker 托管交付。
- 平台统一处理附件、源码/依赖产物及数据库快照；执行服务保留受控数据库维护。
- 运行环境与代码版本分离、依赖准备和复用、源码应用及完整镜像两类交付。
- 运行环境登记、默认选择、替换与冻结；断网依赖制作、导入、补包及诊断。
- 发布独占、失败补偿、可信运行事实、入口与出站连续性、SQLite 安全升级和恢复。
- 预构建服务镜像、离线安装、存量版本/SDK/CLI 和部署升级兼容。

**本次明确排除**：

- 商业许可证、免费 10 个上线名额、Gateway 归仓和 Java 重写；这些方向已取消。
- 新建平台管理界面、应用编辑器、任意宿主命令/SQL 执行入口。
- 应用多副本、自动跨节点迁移、自动扩容、双活动数据库写入和任意结构变更零停机。
- 新增面向业务用户的“一键代码回滚/数据回滚”入口。历史代码重新发布仍走既有审批，数据恢复仅为应用 owner 发起的受控维护动作，主体边界见 §2.11。
- 本 Feature 内实现 K8s 执行适配。其后续交付归 F059，不因此取消双形态一致要求，也不把 Docker 验收说成 K8s 已交付。
- 应用发布以外的开放 API、权限、审批或资源档位业务改版；只通过其所属功能现有入口使用能力。

## 1. 用户故事

### 1.1 应用开发者

作为应用开发者，我希望发布源码或完整镜像，并复用已经验证的运行环境和依赖，以便代码修改无需反复构建、传输整份应用镜像，且可在无公网的客户环境发布。

### 1.2 平台与交付管理员

作为平台超管，我希望统一配置存储、登记全局运行环境和基础离线材料；作为应用 owner，我希望导入本应用的私有补包并定位失败，以便不增加商业组件依赖，也不用在执行服务重复维护存储账号。交付人员使用上述已有身份，不因岗位名称获得额外权限。

### 1.3 应用 owner 和审批人

作为应用 owner 和审批人，我希望版本、审批材料、运行内容及数据变更一致，发布或迁移失败可诊断，以便避免错误版本上线和生产数据丢失。

### 1.4 应用访问者

作为有权限的访问者，我希望应用入口、身份与平台能力保持原有语义，执行管理服务短暂重启时仍可使用已运行应用，以便平台维护不直接中断业务访问。

## 2. 验收标准

### 2.1 开源与可选安装

- **AC-01** — WHERE 未安装商业 Gateway 且没有商业许可证, THE SYSTEM SHALL 允许完成托管层安装、应用发布、审批、上线和有权限用户访问，不将商业组件作为前置条件。
- **AC-02** — WHERE 实际资源足够且业务权限满足, THE SYSTEM SHALL 允许第 11 个同时在线应用上线，不存在固定“免费 10 个”或累计上线数量授权限制。
- **AC-03** — WHERE 未安装托管层, THE SYSTEM SHALL 保持平台其他功能可启动和使用，相关入口遵循 F054 未部署语义，不产生依赖未安装托管服务的常驻任务。
- **AC-04** — WHEN 托管执行管理服务单独升级或停止, THE SYSTEM SHALL 允许入口和出站服务独立运行，并保持运行服务身份、业务身份及应用身份的权限范围相互独立。

### 2.2 平台存储与身份范围

- **AC-05** — WHERE 只在平台配置对象存储并禁止执行服务直连该存储, THE SYSTEM SHALL 仍可准备应用代码、读写应用附件、保存和取回数据库快照；不要求第二套对象存储实例或执行服务专用存储账号。
- **AC-06** — WHEN 执行服务取得代码或依赖材料、提交或取回快照, THE SYSTEM SHALL 按获授权应用、版本和操作校验范围；伪造、过期或跨范围请求必须被拒绝。
- **AC-07** — WHEN 任意上传、下载、解包或导入材料超出部署限制、摘要不符或存在路径逃逸, THE SYSTEM SHALL 拒绝该材料并保留可定位阶段的原因，不覆盖已有资产。
- **AC-08** — WHEN 应用经 SDK 上传、下载、列举或删除附件, THE SYSTEM SHALL 保留既有公开使用语义、单文件上限和错误可区分性，禁止跨应用或跨租户读写，不暴露底层存储账号或匿名直链。
- **AC-09** — WHILE 审批预览运行, THE SYSTEM SHALL 使用与生产隔离的临时数据库和附件空间；预览结束后清理临时材料，不修改或清除生产资产。
- **AC-10** — WHEN 应用停用、更新、实例回收或执行服务重启, THE SYSTEM SHALL 保留其持久数据和仍被引用的产物；整体清除应用资产仅可经既有 owner 显式删除流程，管理身份不得绕过该业务限制；应用按 SDK 契约显式删除单附件的能力不变。

### 2.3 交付方式与运行环境

- **AC-11** — WHEN 使用新版发布描述提交平台已支持语言环境的源码应用且未显式选择兼容构建方式, THE SYSTEM SHALL 默认采用预制运行环境加版本化应用包交付；仅业务源码变化时，平台发布过程不得为该版本构建或推送新的完整 OCI 应用镜像。显式选择兼容构建方式的提交依 AC-13 处理。
- **AC-12** — WHEN 提交已获准使用的完整应用镜像, THE SYSTEM SHALL 使用其被冻结的运行内容完成预检、审批和上线，不强制重复安装源码依赖，也不绕过平台的资源、网络、数据和身份约束。
- **AC-13** — WHEN 使用既有版本发布描述或显式选择兼容源码构建方式提交有效应用, THE SYSTEM SHALL 保持既有源码构建应用镜像的可用流程；不得将旧描述静默解释为新版默认应用包方式，并明确拒绝不支持或含糊的交付描述。
- **AC-14** — WHEN 平台超管登记或替换全局运行环境, THE SYSTEM SHALL 校验其来源、平台兼容性和运行契约，并按 §2.11 的主体矩阵授权；租户管理员、应用 owner、普通用户及服务账号不得仅凭这些身份修改全局环境定义或取得拉取凭据。
- **AC-15** — WHEN 平台超管按 §2.11 修改新发布默认环境, THE SYSTEM SHALL 仅影响之后尚未冻结的发布；已冻结、审批中及正在运行版本的代码、依赖和环境保持原组合。
- **AC-16** — WHEN 应用选择运行环境的新版本, THE SYSTEM SHALL 重新验证相关依赖与启动兼容性，并按正常发布审批后才生效；不得原地改变历史环境版本的内容。
- **AC-17** — WHEN 应用启动, THE SYSTEM SHALL 按冻结的启动约定和健康要求执行业务进程；应用启动失败、入口不存在或健康不满足时，不得将其宣布为已上线。
- **AC-18** — WHERE 多个应用使用相同容器内监听端口, THE SYSTEM SHALL 通过统一入口分别访问各应用，不要求为每个应用分配或开放宿主端口，不将平台控制权限暴露给应用。

### 2.4 依赖准备与复用

- **AC-19** — WHEN 首次准备应用依赖, THE SYSTEM SHALL 固定完整解析结果和产物内容；同一批准版本再次运行时，不得随包源变化取得另一套依赖。
- **AC-20** — WHEN 仅修改不参与依赖安装的业务代码且原依赖组合仍兼容, THE SYSTEM SHALL 复用已验证依赖，同时完成本次所需的编译和应用预检。
- **AC-21** — WHEN 依赖、相关安装输入、运行环境或目标平台变化, THE SYSTEM SHALL 重新准备或选择匹配产物，不得因顶层依赖文件相同而误用不兼容环境。
- **AC-22** — WHEN 已验证的同版本应用在有效节点缓存下重启, THE SYSTEM SHALL 直接使用对应代码和依赖，不重新解析依赖，不在正常启动时访问公网安装软件。
- **AC-23** — WHEN 节点缓存丢失或应用被分配至新的受支持执行节点, THE SYSTEM SHALL 从平台保存的固定材料重建环境；不能依赖其他节点的本地目录或开发机已安装软件。
- **AC-24** — WHILE 多个应用使用可复用依赖, THE SYSTEM SHALL 防止任一应用修改其他应用使用中的环境，不跨租户泄露私有依赖内容及命中信息。
- **AC-25** — WHEN 应用需要前端编译、安装脚本或原生扩展准备, THE SYSTEM SHALL 在发布准备阶段完成并验证所需产物；影响安装结果的业务源码变化必须使相应复用判定失效。
- **AC-26** — IF 平台支持范围内的准备任务失败或并发重复发生, THEN THE SYSTEM SHALL 不发布半成品环境，返回可定位的依赖/编译/验证错误，并允许使用相同固定输入重试。

### 2.5 无公网与离线补包

- **AC-27** — WHERE 无公网但批准的内网包源已包含完整依赖, THE SYSTEM SHALL 可完成首次发布及新增依赖准备，不隐式依赖该源转发公网。
- **AC-28** — WHERE 无公网且无内网包源, THE SYSTEM SHALL 支持导入预制基础依赖集合和应用专用补充材料；目标依赖齐备并验证后可完成发布。
- **AC-29** — IF 目标包、传递依赖、SDK、目标架构或所需系统库不齐备, THEN THE SYSTEM SHALL 在进入审批前拒绝预检并给出可确定的缺失项和环境原因，不回退公网，不把空结果当作成功。
- **AC-30** — WHEN 平台超管导入全局基础离线材料，或应用 owner 导入本应用的私有补充材料, THE SYSTEM SHALL 按 §2.11 校验主体及材料归属，验证完整性和目标兼容性；在目标环境断网验证通过后才允许复用，补齐后可重新发起预检，跨应用或跨租户导入及引用必须被拒绝。
- **AC-31** — WHERE 离线材料在某个 CPU 或操作系统环境制作, THE SYSTEM SHALL 不将其默认认定为适配其他目标平台，也不得把通用下载选项当作任意原生依赖编译能力。
- **AC-32** — WHERE 应用运行需要模型、检索或外部业务接口, THE SYSTEM SHALL 在安装/预检结果中区分镜像可用、依赖可用和运行期接口可用，不以页面存活代替能力可用。

### 2.6 发布与运行一致性

- **AC-33** — WHEN 首发、迭代或以历史代码重新发布, THE SYSTEM SHALL 先完成相应校验和启动预检，再经 F055 既有审批流程；没有免审或完整镜像免审路径。
- **AC-34** — WHEN 执行上线准入, THE SYSTEM SHALL 在影响旧服务或迁移生产数据前检查容量，并防止并发发布重复承诺同一份可用资源；容量不足时保留待上线版本及可诊断原因，允许按原审批结果手动重试，不得归类成商业额度不足。
- **AC-35** — WHEN 同一应用的发布、迁移、恢复或停用相互竞争, THE SYSTEM SHALL 只允许一个有效执行所有者进行变更，拒绝过期操作覆盖新状态，不启动第二个活动数据库写入实例。
- **AC-36** — WHEN 同一操作重复提交或调用响应丢失, THE SYSTEM SHALL 可确认其已完成/进行中/失败结果，不重复产生应用、正式实例、迁移或无法关联的快照；相同操作标识但内容不同必须拒绝。
- **AC-37** — IF 候选实例未就绪或对外切换结果无法确认, THEN THE SYSTEM SHALL 不报告虚假上线，不提前回收仍可用且与数据兼容的旧执行体，并显示真实发布阶段。
- **AC-38** — WHEN 新版本正式切换, THE SYSTEM SHALL 按批准能力启用新版本，并在既有撤销上界内使旧版本已移除能力失效；候选失败不能因过早撤销旧凭据而无提示破坏旧服务。
- **AC-39** — WHEN 用户停用或删除应用、或访问权限撤销, THE SYSTEM SHALL 阻止不再允许的新访问并按既有约定断开对应长连接；执行层对账不得把已停用应用重新拉起。
- **AC-40** — WHEN 应用持续退出或不健康, THE SYSTEM SHALL 遵守 F054 既有恢复和过渡提示承诺，避免无限高速重建，并提供应用、版本、运行操作和失败阶段的诊断记录。

### 2.7 SQLite 数据安全

- **AC-41** — WHEN 应用进行数据库结构升级或恢复, THE SYSTEM SHALL 保证生产写入者已隔离；不以两个活动版本同时写同一数据库的方式完成升级。
- **AC-42** — WHEN 执行已确认的破坏性结构变更, THE SYSTEM SHALL 先保存可验证的一致快照，并确认平台已经保存内容和关联记录；仅在本地生成备份不构成完成条件。
- **AC-43** — IF 快照保存失败或确认状态不明, THEN THE SYSTEM SHALL 不执行破坏性变更，并允许确认上传结果后继续或按维护状态恢复服务。
- **AC-44** — WHEN 迁移完成但新实例启动失败, THE SYSTEM SHALL 明确显示数据库及运行状态是否已变化，不声称旧版本一定未受影响，也不得自动覆盖可能已产生的新业务数据。
- **AC-45** — WHEN 应用 owner 本人按 §2.11 发起指定生产数据快照的恢复, THE SYSTEM SHALL 校验其当前归属、租户和快照范围，明确恢复点及可能丢失的数据范围，在隔离写入并验证材料后恢复及审计；平台超管、租户管理员和交付人员不得凭管理身份绕过 owner-only 规则，代码重新发布不得自动恢复旧数据库。
- **AC-46** — WHEN 普通应用实例被回收、重建或服务进程重启, THE SYSTEM SHALL 保持外置持久数据完整；物理执行节点损坏时，按现场备份恢复点处理，不承诺单机盘自动跨节点零损恢复。
- **AC-47** — WHEN owner 使用既有数据查看、单行编辑及导出能力, THE SYSTEM SHALL 继续通过 F054 数据服务执行权限收窄和审计，不新增任意 SQL 或 DDL 输入入口。

### 2.8 入口、出站与能力权限

- **AC-48** — IF 执行管理服务短暂重启或不可达且平台授权和应用仍可用, THEN THE SYSTEM SHALL 保持既有代理连接不被该重启直接关闭；超过原短路由缓存窗口后，新请求仍可取得已确认的有效运行目标。
- **AC-49** — IF 平台身份、权限或出站策略无法确认或已失效, THEN THE SYSTEM SHALL 按既有有效期拒绝不再允许的访问，不为保持可用而无限放行旧授权。
- **AC-50** — WHEN 平台 API、worker、入口或出口服务不在同一主机运行或重启, THE SYSTEM SHALL 仍能取得一致的任务、运行目标及策略，不能以共享某台机器的本地文件为成立条件。
- **AC-51** — WHILE 正式运行, THE SYSTEM SHALL 保留身份头防伪、当前访问者身份、平台能力声明和用户权限共同约束；检索缺少访问者身份时不得回退为 owner。审批预览的能力授权继续遵守 F055 AC-27 和 INV-36 的既有例外，不扩散到正式访问。
- **AC-52** — WHILE 应用准备或运行, THE SYSTEM SHALL 保留对应阶段的出站限制，对绕代理直连、私网解析和未经允许的目标按既有安全契约拒绝；应用及通用代理不能调用容器或集群管理能力。
- **AC-53** — WHEN 服务交互或处理文件传输, THE SYSTEM SHALL 校验身份、动作及范围，拒绝伪造、过期和重放的敏感操作；服务管理凭据、对象存储主凭据及任务传输授权不得进入应用环境，日志和公开版本材料不得泄漏注入的应用敏感值。

### 2.9 镜像交付与环境替换

- **AC-54** — WHEN 官方托管服务版本交付, THE SYSTEM SHALL 提供由项目 CI/CD 预构建并发布到 Docker Hub 的运行服务镜像，正式 Compose 使用已发布镜像，客户无需现场构建 manager 源码。
- **AC-55** — WHEN 官方交付本 Feature 首轮 Docker 版本, THE SYSTEM SHALL 同时提供 linux/amd64 和 linux/arm64 的 manager、入口代理、出站代理服务镜像，以及官方支持的应用运行镜像和准备镜像，提供与源码版本一致、可核验内容的双架构版本组合及分别验证的证据；不得仅以不声明多架构支持省略其中一种架构，其他未验证的国产 CPU/系统组合不得宣称已支持。
- **AC-56** — WHERE 客户不能访问 Docker Hub 或没有内网镜像仓库, THE SYSTEM SHALL 可使用预先导入执行引擎的匹配镜像完成首轮 Docker 交付；缺失镜像或不可用执行引用必须在前置检查中显式失败。
- **AC-57** — WHEN 升级 manager 服务镜像, THE SYSTEM SHALL 保留已冻结应用的代码、依赖和运行环境组合，允许执行管理服务与应用环境分别升级及回退。
- **AC-58** — WHEN 安装或升级托管层, THE SYSTEM SHALL 验证数据目录映射、存储/平台接口、身份、网络、执行引擎、目标镜像和包源/离线材料等前置，分别呈现未满足项，不把进程存活作为全部安装成功。
- **AC-59** — WHEN 运行依赖需要超出当前环境的系统库或工具链, THE SYSTEM SHALL 要求匹配的新运行环境或已批准完整镜像及其离线材料，不承诺预装常见库可以适配任意应用。

### 2.10 升级兼容与完成证据

- **AC-60** — WHEN 从当前托管版本升级, THE SYSTEM SHALL 保持已发布应用资产、历史版本和兼容 SDK 的公开行为，提供既有运行信息的迁移、核验及失败处置；不因内部存储接口迁移强迫所有兼容应用重新提交代码。
- **AC-61** — WHERE 采用平台支持的任一业务数据库或开启多租户, THE SYSTEM SHALL 保持同样的发布、运行环境管理和产物隔离语义，不引入仅某数据库或单机共享目录才成立的行为。
- **AC-62** — WHEN 完成首轮交付验收, THE SYSTEM SHALL 分别提供正常发布、离线新增依赖、服务重启、失败重试、数据库快照/恢复及权限隔离的实际证据，未执行环境明确标为未验证。

### 2.11 管理主体与准备任务回收

以下是新增动作的业务授权边界；复用现有身份，不新增“运维”或“交付”角色。表内“owner”均指目标应用当前的自然人 owner，同租户管理员和超管若同时也是该应用 owner，仅以 owner 身份执行该应用动作。既有发布凭据的发版权限不变，但不因此获得这些新增管理动作。

| 动作 | 允许主体及范围 | 明确拒绝 | 执行服务的地位 |
| --- | --- | --- | --- |
| 登记/替换全局运行环境、修改全局默认映射 | 平台超管；全局环境目录 | 仅有租户管理员、应用 owner、普通用户或服务账号身份 | 只消费已冻结环境，不能自行登记或改默认 |
| 导入全局基础离线依赖集合 | 平台超管；仅可作为公开基础材料供引用，不得夹带租户私有包 | 租户管理员、应用 owner、普通用户、服务账号 | 验证指定材料，不自行扩大可见范围 |
| 导入/引用应用私有离线补包 | 当前应用自然人 owner；仅限现有应用或其已建立归属的发布草稿；材料不得被其他应用或租户引用 | 非 owner、仅有管理身份者、其他租户、服务账号独立发起 | 仅执行已授权的同应用准备任务 |
| 恢复生产 SQLite 快照 | 当前应用自然人 owner；仅限同租户、同应用的已确认快照，需明确确认恢复范围 | 非 owner、仅有管理身份者、其他租户、服务账号独立发起 | 根据 owner 已确认的维护意图执行，不取得独立数据操作授权 |

- **AC-63** — WHEN 新增依赖准备、前端编译或启动预检任务完成、失败、超时、取消，或执行服务重启后发现这些任务的遗留资源, THE SYSTEM SHALL 在配置的回收期限内清理属于该任务的临时执行体和工作空间，并在确认执行体停止后释放其资源预占；保留限期诊断材料，不删除生产数据库、仍被引用的有效产物或唯一尚未确认保存的快照；未确认停止的任务必须显式报告并继续占用对应资源，不得把容量提前重复分配。

## 3. 边界情况

- 无依赖的静态应用不应因为未提供 Python/Node 包源而失败；仍要求站点材料和运行环境齐备。
- 只有包源地址但没有实际所需包文件，不构成离线依赖已就绪。
- 完整镜像模式不被强行加入源码依赖，也不能逃过平台运行与审批约束。
- 缓存只是加速材料；失效后重建，不能借缓存失效删除生产数据库或唯一未确认备份。
- 停写维护中的应用需要呈现可识别状态，不能承诺任意 SQLite DDL 零停机。
- 库结构变化后发布失败，数据恢复与代码重新发布是两个独立操作。
- 运行环境同名修改和默认环境切换不得影响历史冻结版本。
- 代理管理服务不可达与平台权限服务不可达是不同故障，不能用同一无条件放行策略处理。
- 单机数据卷的物理节点灾难按备份恢复处理；实例级恢复不等于节点级无损迁移。
