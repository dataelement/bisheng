# Design: 引用关系辅助提示

**关联**：[已确认规格](./spec.md) · [需求及核查记录](../../../docs/reviews/reference-simplification-beta2-discovery-20261123.md)
**版本**：v3.1.0-beta2。**最后更新**：2026-11-25。
**状态**：用户已授权开发，主体实现及本地定向验证完成；环境 E2E 待执行，见 [验证记录](./verification.md)。本文为当前实现快照，先前设计评审见 [修订记录](./review-fixes-20261123.md)。

## 1. 目标与非目标

引用关系仅供删除前查看已有影响，查询失败和同步滞后均不影响业务。保留模型、知识空间及已有资源引用；知识空间的元数据字段和值不纳入引用。

沿用旧表，以业务提交后触发 Celery 同步、失败重试实现维护。不增加业务事务待修记录、outbox、全局验收、引用冻结、版本栅栏、治理面板或数据迁移，也不要求全量回填后开服。

## 2. 关键约束

- 遵循 [constitution.md](../../../docs/constitution.md) C1–C8 及[本版本契约](../release-contract.md)，业务 Owner、权限入口和已有处理任务职责不变。
- 数据库表、列、索引及约束均不修改；无 Alembic 增量，无旧记录批量转换或清空。
- 实际权限、资源存在性、来源版本及在途任务检查，不能随引用检查一起删除。模型“有引用”保留；模型“必须先有引用证明才能读取或修改”移除。
- 普通异步任务允许滞后及重复执行，不承诺消息不丢、恰好一次或并发修改与索引原子一致；这些限制不转为业务准入条件。

## 3. 方案对比与选定

### 决策 1：引用提示独立于删除资格

- **备选**：保留原 Coverage、引用摘要确认和强制删除分支；或直接查询已有引用后提示。
- **选定**：直接查询。权限及资源资格先由业务判断，引用查询使用独立的只读 Session；执行时不重查或锁定引用。
- **原因**：`space_delete_reference_query.py` 和模型删除服务当前都验证全局证书；166 孤儿 Run 的故障正由此扩大到其他租户。用户明确要求有引用仅提示。
- **重新考虑条件**：只有产品将某种关联明确改为业务禁止删除条件时另行确认，不能以索引准确性为由恢复阻断。

### 决策 2：提交后异步刷新，失败用现有任务重试

- **备选**：业务事务内 prepare/apply、持久 dirty/outbox；或提交后触发普通 Celery 任务。
- **选定**：提交后触发任务。任务重新读取当前配置，按来源根替换旧表中的关系；失败重试。
- **原因**：`write_runtime.py` 当前要求旧索引完整并锁定业务根/目标，正是保存被辅助功能拖住的原因。用户已排除强一致与新增账本。
- **重新考虑条件**：只有引用提示需要另行承诺严格送达或时效时再评估，当前不建立该承诺。

### 决策 3：复用两张索引表，历史证明退出在线准入

- **备选**：建新简表并迁移；或兼容原有记录和表约束。
- **选定**：兼容 `business_resource_reference` 与 `business_reference_set`；既有 root_guard、legacy 字段及历史 Run 留在原处，在线业务不读取它们证明可执行。托管应用新版本的原目标选择作为业务配置保存在已有 `app_version.injections` JSON；旧版本只读既有目标 ID，不迁移或更新旧版本。
- **原因**：原表已有来源/槽位/目标唯一约束及反查索引，足以提供提示；用户明确不做数据迁移。
- **重新考虑条件**：今后独立进行表结构清理时评估，本功能不捎带清理历史表或字段。

### 决策 4：拆出实际业务校验，不删除整套执行入口

- **备选**：遇到引用错误整体放行；或保留真实配置及权限检查，仅去掉派生索引校验。
- **选定**：后者；同步和异步读取都覆盖。
- **原因**：`source_read.py` 同时协调原配置加载、授权、目标状态与引用摘要；整段绕过会丢失真实授权。`metadata_owner.py` 还通过模型读取间接进入这套检查。
- **重新考虑条件**：业务自身的配置或权限契约发生变化时由所属 Owner 调整，不由引用任务扩展职责。

### 决策 5：保留应用原目标，不按名称重新猜绑

- **备选**：旧应用运行或后台同步时按当前名称重新解析；或保留原目标，无法确定时仅相关实际调用报错。
- **选定**：后者，用户已在本轮修订中明确选择。新版本写现有业务 JSON，旧版本按已有明细恢复已记录目标；缺失目标身份不全局阻断应用，不自动指向同名新资源。
- **原因**：现有 `_frozen` 将原业务选择和反向索引混在一起；能力名称不足以恢复原目标，已有同名替换测试明确要求保留原 ID。新版本自身的配置 INSERT 不依赖异步索引成功，也不增加引用事务协议。
- **重新考虑条件**：用户明确改变能力的名称绑定语义时另行确认，不能把后台索引刷新当作重新选模型。

### 决策 6：旧知识库模型名称按原配置兼容

- **备选**：沿用目标分支新增的引用保留标记准入；或从真实保存值识别旧名称。
- **选定**：从原值识别合法旧名称，不读取引用集合的 ready/保留标记。允许查看与有权显式重配；无法确定模型 ID 时仅相关实际调用报错，不按现名重绑。新建仍必须指定真实有效的 Embedding ID。
- **原因**：最新 beta2 引入旧名称兼容，合入时需要同时保留它与本规格的主流程独立性。异步提取只记录可确定关系，旧名称不产生虚构模型目标。
- **重新考虑条件**：产品明确重新定义历史名称绑定语义时；本次不回填、不迁移历史配置。

## 4. 改造前现状与已实现流程

### 4.1 当前代码（基线 `23c82f7769`，已核实）

| --- | --- | --- |

| `tenant/application/{tenant_creation,installation}.py` | 创建/安装签发、检查全局引用证书 | 仅移除引用验收调用，原有租户初始化和安装标记保留 |

| `assistant/application/reference_source_owner.py::_load` | 根据 source set 标记决定旧名称配置的解析方式 | §4.7 改为根据真实配置值解析，不读取 source set 选择兼容分支 |
| `knowledge/application/move_processing_owner.py::aensure_logical` | 文件逻辑移动 SAVEPOINT 中同步维护引用归属 | §4.8 移除引用维护，提示查询按文件实际归属取数 |

实际要使用的模型、知识和权限，继续由各 Owner 从业务配置及目标实体读取。`source_read_target_owner.py` 及两领域的 `source_read_target_repository.py` 中，凡依赖引用明细或 F118 Run 才能判断目标的分支，改成读取实体当前状态；不再通过 `SourceReadRepository` 获取 original 引用。不存在即 missing，查看和修复不要求历史证明。跨租户目标的实际访问仍检查原共享/授权，不能因配置中写了外租户 ID 就放行；仅查看自身失效配置不加载无权查看的外部详情。为真正的业务任务保留已有删除状态判断。

### 4.2 删除流程（已实现）

`原业务预检 → 创建业务确认信息 → 查询已有引用并附带提示 → 用户确认 → 原业务执行`

1. 业务预检处理身份、目标范围、共享只读、权限、状态和在途任务。失败返回原业务错误。
2. 正常业务确认信息不包含引用明细摘要、Coverage epoch 或租户 inventory；签名/幂等仅保护实际业务参数及目标，不签入提示内容。
3. 独立 Session 查询已有引用明细；按目标类型/ID 查询。空间内容引用通过文件当前所属空间定位，不能用可能滞后的引用 `target_space_id` 判断归属；文件入口按实际选择范围查询，具体见 §4.8。只读取已有关系，不扫描所有工作流或其他来源配置。
4. 使用现有来源披露逻辑按权限返回可见名称；跨租户来源保留原聚合口径，隐藏无权查看的详情。租户已不存在或来源已删除的陈旧记录从展示结果中排除，不先要求清理数据库。
5. 辅助查询及披露总预算 2 秒；超时或索引查询异常返回“暂无法获取引用”，不撤销已生成的业务确认信息。权限与身份检查在降级边界外，不能被包装成辅助异常。
6. 用户确认后执行原删除，不重新计算引用影响。已有资源自身版本、物理删除范围及实际处理状态变化仍按原业务规则处理。
7. 被引用方删除后不自动改写来源配置；后续真实使用缺失目标报业务错误。删除任务的 SQL/FGA/对象清理和恢复流程保留，但不执行引用 prepare/finalize 作为前置条件。

### 4.3 异步维护（已实现）

`业务事务提交成功 → 通知同步 → Celery 读取当前配置 → 替换旧表记录；失败重试`

- 一个任务定位一个来源根：`tenant_id, source_type, source_id`。任务处理该根现存的有效来源版本，同时清理已删除版本的记录；不在消息内携带配置快照、凭证、引用摘要或期望修订。
- 六类已有来源继续沿用：工作流未删版本、应用可管理版本、助手配置、频道同步配置、知识空间模型配置、模型默认配置。一般来源复用现有 extractor；应用按 §4.6 读取原目标映射，旧名称助手按 §4.7 提取可确定关系，不直接套用要求完整映射/合法模型 ID 的原提取入口。保留原有关联范围，不增加元数据来源。
- 各 Owner 的仓储读取当前数据，任务只维护索引，不使用操作者 token，也不通过执行准入取得读取权。任务体验证显式租户参数、恢复租户上下文，并校验来源实际归属；租户已删除时按来源失效清理该根的旧关系，不因残留业务行重新登记。
- 普通 SQL 事务仅保证本次旧表替换成功或回滚；不锁业务根/目标，不与业务提交绑定。重复任务按同一来源覆盖，唯一约束避免重复明细。
- 来源根已删除，删除该来源根的明细及 `record_kind='source'` 集合行；只按完整租户/来源键处理。历史 `root_guard` 留存，不为这次任务维护或补齐。
- 用 Celery 现有 `celery` 队列，新增一个任务模块并在 `worker/__init__.py` 注册；API 与 worker 使用同版代码。
- 任务 `acks_late=True`，失败最多重试 5 次，间隔 10、30、60、120、300 秒；每次重新读取当前配置。失败日志包含租户、来源、任务 ID 和次数，不打印配置/凭证。
- 发布消息使用现有 Celery producer 的有限重试，连接超时 1 秒、最多重试 2 次；最终失败记录日志，仍返回原业务成功。任务适配层仅捕获 broker/数据库/提取异常，不捕获或改写业务提交错误。
- 在已经提交的应用层边界通知；共享 Session 的内部方法只返回待通知的来源 ID，由拥有 commit 的上层统一通知。批次按来源根去重，不在未提交时 `.delay()`，不引入全局 ORM 提交钩子。

最小新增实现预计为 `resource_reference/application/source_sync.py`、`domain/repositories/reference_sync_repository.py` 和 `worker/resource_reference.py`。`ReferenceSyncRepository` 显式按六类 SourceType 读取既有实体，复用各业务的纯提取器；由一个任务入口调度，不建立 loader 注册框架。反查独立放在 `reference_hint_repository.py`，避免调用带严格 receipt 校验的历史入口。

### 4.4 旧表写入与兼容

| 表/字段 | 处理约定 |
| --- | --- |
| `business_resource_reference` 来源/版本/槽位/目标及 owner 字段 | 保留现有含义和唯一约束。任务重建当前根的已知关系，使用实际目标归属，不能假设目标与来源同租户 |
| `business_reference_set` 的 `source` 行 | 仍保存本次提取信息，含合法空集合；digest/extractor_version 只描述索引，业务不读取它们验收自身 |
| `source_revision` | 沿用旧行数值并在本次刷新中递增，明细写入对应值；仅满足旧表约定，不用作业务版本或删除栅栏 |
| `ready/effective` | 保持该来源索引写入状态，不作全局覆盖声明；业务资格按业务实体，不根据此标记判断 |
| `root_guard` | 原行保留，新在线同步不要求其存在，也不更新它为业务签发凭据 |
| `legacy_*` | 原有失效项仍在当前配置中时可保留原标量；不回查 Run。目标恢复存在时按真实 owner 正常写入，不再带旧 missing 标记 |
| `resource_reference_tombstone`、`knowledge_unification_run` | 不删表、不清行、不批量改旧值；真实删除任务恢复有需要的部分继续使用，引用提示/读取不依赖它们 |
| `app_version.injections` | 仅新版本首次 INSERT 时保存 `resource_bindings` 业务选择，见 §4.6；旧版本 JSON 不回写，不新增列或迁移旧数据 |

旧表要求 `target_tenant_id` 已知，除非已有完整 legacy 标量：若当前目标已缺失，优先沿用同一槽位、同一目标的旧 owner/legacy 标量；若目标从未登记且无从确定 owner，跳过该未知关系并记录任务日志，不猜 owner、不伪造 migration Run。其他可确定关系照常写入；这批来源集合可记为 `ready=False`，只供诊断，不阻止业务。错误的来源配置解析使任务失败重试，不把旧索引先清空再提交。

旧记录升级后直接可查询，无启动回填和数据迁移。后续业务保存触发刷新，不因为未修改的历史索引未更新而要求全量治理。

### 4.5 主流程拆分位置

| 业务链 | 保留 | 移除/替换 |
| --- | --- | --- |
| 工作流、助手、频道、应用保存/复制/导入/版本切换及删除 | 原业务校验、实际根/版本更新、业务自身事务 | 引用 prepare/apply、旧索引一致性条件；在最终提交后通知所属根 |
| 模型默认配置、空间 Embedding 切换/重建 | 实际模型、权限和处理状态检查，模型配置版本及任务约束 | 引用索引参与业务事务；实际配置成功变化后通知对应来源根 |
| 同步/异步读取、执行、发布、预览 | Owner 原配置、授权、目标状态和业务版本检查 | `source_read._index`、source set 前后比较、旧 Run 证明；结果对象去掉仅服务索引的 source/root_revision，调用者同步修改，不填伪造 revision |
| 元数据字段及文件元数据值修改 | 原元数据校验、空间 edit、检索更新及处理版本冲突 | 间接引用准入与任何引用同步通知；从实际空间配置读取所需处理版本 |
| 文件/目录跨空间移动 | 原权限投影、文件逻辑归属变更、检索迁移和任务恢复 | 移除事务内 `amove_file_ownership`，不新增移动引用任务；提示读实际文件归属 |
| 空间/文件/清空及模型/服务删除 | 实际删除计划、权限投影、状态、清理与任务幂等 | 引用导致 invalid/skip/blocked/force、epoch/inventory/inbound 比较及引用目标冻结 |
| 安装/租户创建、挂载及删除 | 安装来源标记、租户初始化和授权、原成员约束 | 全局引用验收与空租户证书必需性；残留历史 Run 不参与资格 |

空间清空不删除空间自身使用 Embedding 模型的关系；空间本体删除后，来源根刷新清理它的模型引用。只修改元数据不意味着空间不再使用模型，不能误删该模型引用。来源软删、版本软删、实际发布/回滚和系统默认配置写入等非页面入口也必须到达同一提交后通知点。

### 4.6 应用原目标选择与辅助索引分开

**新版本**：在 `VersionService._insert_version` 原有业务配置解析与授权后，将已选定的模型/知识目标写入同一次 `AppVersion` INSERT 的 `injections.resource_bindings`。形状为 `slot_key -> {target_type, target_id}`，槽位沿用现有 extractor 的稳定 slot。原 `manifest/capabilities` 不改，也不增加公开 manifest 字段。该内容是版本自身的业务选择，不是待修账本；写入普通业务快照成功后才通知异步索引，二者不要求原子一致。

`resource_bindings` 与现有 `injections.env` 分开：容器交付仍只读取 env，不注入该映射。Owner 的授权快照只包含不含秘密的目标映射/缺失槽位，不把整个 injections（可能含 env）放进返回数据或日志。旧 `AppVersion` 保持 INSERT-only，不进行在线回填。

**读取规则**：

1. `resource_bindings` 键存在时按版本 JSON 读取；空映射对空声明合法。根据 slot、目标类型和显式声明 ID 校验业务配置，不能用异步索引覆盖它。键存在但格式或必需槽位损坏时标记相关能力目标不明，不回退名称解析或旧索引来猜值。
2. 旧版本没有此键时，仅按完整租户/app_id/version_id/slot 从旧引用明细读取原 ID。忽略 source set、ready、digest、revision、Coverage 和 Run；不要求索引完整、不因某个槽位缺失使整个来源读取失败。已有明确数字知识 ID 的声明直接使用该 ID。
3. 旧记录保留原 ID，即使资源已删、改名或同名新目标已出现也不改绑。旧记录缺失、相互矛盾或兼容读取失败时，该名称槽位标为目标无法确定，保留原声明供查看；不将整份声明当成空集，不按当前名称重新解析。
4. 应用查看、版本管理/编辑、页面预览及其他不使用该能力的操作继续；实际调用才检查被请求能力的目标身份、现有权限和真实状态。目标不明只拒绝该能力调用。这是用户已确认的历史边界（AC-14），不是恢复引用就绪门槛；旧版本通过显式提交新版本修复，不改写历史版本。

**调用链**：`HostedAppReferenceSourceOwner._frozen/_load` 改为加载上述业务能力快照；已知目标和未确定槽位分别表达，不再用 `AuthorizedSourceSnapshot.invalid_reason` 或全局 `_require_valid` 拒绝整个应用。`capability_bus_service.load_effective_declaration`、`inspect_saved_capabilities` 保留每项声明及其状态，不因某项未确定导致其他项加载失败。未确定的名称槽位仅在内存快照中表达未知目标，相关 `DeclaredKnowledge.knowledge_id` 允许为 None；不伪造 0、随机 ID、空 TargetKey 或数据库占位关系。

模型实际调用沿用 `HostedAppDeclarationAdapter.assert_model_binding`，只检查本次请求名称对应的原目标与本次解析 ID 是否一致；名称解析指向新同名模型时拒绝调用，不更改映射。不能继续通过 `_read_effective_source(purpose='execute')` 验证所有声明来实现该检查。

知识实际调用在 `CapabilityBus._require_declaration/_require_declared_ids` 按本次请求 ID 检查；移除 `EffectiveDeclaration.knowledge_whitelist` 的“任意一个未确定则全部拒绝”。显式请求已知合法 ID 时不受其他未确定槽位影响；未指定范围的检索请求会使用整份知识声明，其中存在无法确定的目标时拒绝这一次检索，不静默缩小原请求范围。模型调用不因知识槽位异常而失败，反之亦然。

**后台提取**：新版本直接使用业务 JSON 中的原目标，旧版本复用现有原 ID；不调用当前名称解析器重新选择。旧版本先读取原映射再在任务自己的事务内替换索引，缺失映射只同步可确定部分，原可确定槽位继续保留。没有真实新证据时重试也不猜原 ID。此过程不回写旧版本或新增存量数据迁移。

### 4.7 旧名称助手按业务值兼容

`AssistantReferenceSourceOwner._load` 不再调用 `ahas_legacy_name_retention`。由原 `assistant.model_name` 直接区分：合法数字模型 ID 按 ID 处理；空值保持现有缺省行为；非空旧名称字符串保留原值，并标记实际模型尚未确定，不按当前同名模型自动解析。

旧名称不使查看、编辑或保存原配置的解析失败。未改旧名称、只修改其他字段时可保存；用户通过模型选择器显式换为合法 ID 才修复模型选择。执行确实需要未确定的模型时返回业务配置错误，不因缺 source set、ready 或 Coverage 报错。

后台同步助手已有知识关系，遇到未确定模型槽位记录日志并略过该槽位，不使其他关系全部失败。来源的兼容提取方式仅由真实配置决定，不由 `BusinessReferenceSet` 标记决定。旧读取/迁移工具若仍需要原 helper，保留在其原调用边界；正常查看、保存及执行不再经过该 helper。

### 4.8 文件移动不维护引用位置缓存

从 `MoveProcessingOwner.aensure_logical` 的 SAVEPOINT 中移除 `reference_owner.amove_file_ownership`；该 Owner 构造不再要求绑定 runtime，移动专用的 receipt/归属更新方法在确认无其他使用者后移除。原 FGA 投影、`cutover.aapply_logical`、`touch_move_spaces`、任务阶段与业务恢复不变，不捕获并吞掉这些业务失败。

不新增“移动后刷新引用”任务。文件 ID 和已有直接引用未变，引用中的 `target_space_id` 只是可能滞后的旧派生字段：空间反查由 `resource_reference/domain/repositories/reference_hint_repository.py` 提供普通只读查询，以 `target_type='knowledge_file'` 的已有关系按文件 ID 关联实际 `KnowledgeFile.knowledge_id`，限定当前目标租户和空间；空间本身的引用仍按目标 ID 查询。SQL 放在仓储，不在 service 拼接查询。

因此移动文件后，内容关联跟随实际文件归属，不再用旧引用 `target_space_id` 判断应归哪个空间。该字段及旧表约束保留，来源将来正常刷新时可顺便写当前值，不要求专门回填。运行时目标状态和权限也使用实际文件实体，不依据该缓存定位父空间。

验收至少包含：同步引用仓储被故障注入时移动仍成功；未改引用行的情况下，文件移动前后从两侧空间查到的内容关联跟随实际文件位置；原业务移动权限/检索迁移失败仍按原规则失败。

### 4.9 实际引用失败的诊断（2026-11-24）

执行读取仍先完成原身份/租户与来源重校验，再拒绝真实不可用目标。`ReferenceSourceReadRuntime` 从已授权快照和本次 Owner 返回的事实构造错误明细，不查询失效资源名称，不读取引用辅助索引。保存/发布使用相同的节点定位逻辑；默认模型额外区分未上线和类型不匹配。是否放行、事务和删除行为保持原规则。

助手上线前会先保存配置。保存请求中的知识选择由 `AssistantBoundaryService` 先行校验，已保存的缺失目标曾在此直接返回通用 404，未进入执行读取。现在该拒绝路径通过 `assistant/application/reference_validation.py` 先验证调用者具有助手编辑权限，再以 inspect 读取已授权来源，且只解释仍在本次请求中的已保存失效知识目标。原校验通过时不增加来源读取；新 ID、已移除的失效目标和没有匹配事实的拒绝仍保留原 404。无编辑权限不能读取诊断；该分支在业务写事务之前抛错，不保存配置或上线，不改动原绑定授权规则。详情的 `invalid_missing/invalid_scope` 状态补齐平台三语翻译，避免直接显示翻译键。

错误码仍为 `10996`，`data.reason` 保留；可选增加 `data.reference_errors`：每项含 `resource_type/target_id/state`，工作流额外含 `node_id/node_name`。最多五项，同一目标在不同节点引用时分别保留，节点名称最多 100 字符。`state` 区分 `invalid_missing/invalid_legacy/invalid_deleted/deleting/invalid_scope/unavailable/offline/type_mismatch`；无法区分不存在和不可见时只报告 unavailable。发布接口继续保留旧 `workflow_reference_errors` 字段，旧客户端可继续消费。

两端 HTTP、对话 WS、编排调试、助手流式错误及知识文件/导入/任务失败摘要共用 `@bisheng/api-client` 的原因解析。WS 兼容对象和 JSON 字符串信封，保留其中的 data。三语文案只在 locales 包维护。已知原因按显式白名单映射为修复建议；未知原因、无明细的旧服务或只保留错误码的历史记录说明“服务未返回具体失效项”，不猜测删除原因，不展示 exception/SQL/路径。若未来错误协议改用独立业务错误码，应重新评估该白名单，不再继续扩大 10996 的职责。

### 4.10 免登录工作流使用服务端当前版本（2026-11-24）

公开 HTTP 的脱敏图只用于展示，不能与数据库完整执行图直接比较。`/api/v3/workflow/chat/{id}` 在完成公开入口身份和会话校验后，为执行端口绑定 `published_only=True`；该策略不从浏览器消息或“是否携带登录凭据”推断。每次首次执行准入按连接绑定的工作流 ID、执行身份和租户读取当前保存版本，忽略浏览器回传的展示图，继续执行来源重校验与实际引用可用性校验。显式 preview 一律拒绝，版本提示仅可匹配本次读取的当前版本，不能切换到历史版本。普通登录编排入口保持原有保存图比较与编辑预览规则。

定向回归覆盖公开 HTTP 脱敏后经实际 v3 WS 适配器读取 SQLite 完整保存图、恶意图忽略、禁止预览、拒绝历史版本和工作流换绑、租户隔离及当前版本切换。现场根因、本地验证及部署边界见 `docs/reviews/public-workflow-saved-execution-20261124.md`。

### 4.11 免登录输入续跑与失败反馈（2026-11-25）

WS 侧的 `RedisCallback` 与 Worker 使用同一个服务端执行快照判定存储来源：端点传入 `execution_snapshot` 时为 `api`，否则为 `platform`。首次初始化和重连状态恢复共用构造方法；浏览器提交的 `source` 或 `execution_snapshot` 不参与判断。此选择沿用 Worker 现有规则，避免公开会话的输入误入只接受自然人会话的 `ConversationPersistence.scope`。若将来增加其他执行主体，必须同时复核 WS 和 Worker 的来源契约。

每次 input/stop 仍先调用 `ChatSessionService`，按端点绑定的 `SessionSubject` 校验租户、会话主体、资源与删除状态。自然人持久化校验不改动；经过验证的输入在 API 来源下也必须匹配消息的 chat_id、flow_id 和 user_id，并通过 pending 消息、节点及字段检查后才能写入或续跑。公开来源不能绕过这些检查。

`WorkflowClient` 将业务异常原码反馈，HTTP 403/404 映射为对应既有业务错误，其余异常使用 10541，日志保留堆栈；页面不接收内部异常详情。错误帧后发送既有 `processing/close` 帧结束等待，不清除 pending 输入或伪造执行成功，因此合法输入仍可重试。协议、错误文案及前端生产逻辑沿用现有实现。实际 WS、图执行、SQLite 消息持久化和前端错误处理回归及边界见 `docs/reviews/public-workflow-input-continuation-20261125.md`。

## 6. 对外契约与依赖

### 6.1 接口与提示数据

保留既有 URL 和普通删除确认参数：

- 知识引用：`GET /api/v1/knowledge/space/{space_id}/references`、`POST /api/v1/knowledge/space/{space_id}/files/references`，对应 `knowledge/api/endpoints/references.py`。
- 模型：`POST /api/v1/llm/removal-plan`、`/server-removal-plan`、`/removal-sources`，对应 `llm/api/router.py`。
- 原业务删除预检和确认接口保留，`confirmation_id/plan_digest` 仍保护业务参数；`force` 兼容接收，但不再表示绕过引用保护，不建立单独强制引用确认。

复用提示已有字段，不新增完整性三态协议：

| 字段 | 新语义与消费方式 |
| --- | --- |
| 独立知识引用查询响应的顶层 `check_complete` | 仅表示这次查询是否成功；失败为 false，不代表业务预检失败 |
| 知识删除预检的 `impact.reference_check_complete` | 新增一个提示布尔字段，成功 true、失败 false；不进入数据库表、计划签名或删除资格。旧响应缺该字段时前端按未知提示处理，不用顶层业务字段代替 |
| 模型预检的 `inspection.check_complete` | 本次索引查询是否成功；失败 false，前端展示暂不可获取，不禁用删除 |
| 引用 `blocked` | 固定 false；是否有已知关系从已有计数/列表展示，不决定执行资格 |
| `source_counts/slot_counts/restricted_counts/source_page` | 成功时返回已有记录及按原权限披露的分页；查询失败时为空结构，UI 根据 check_complete 显示未知，不显示“0 个引用” |
| 业务预检 `check_complete/can_execute` | 仍只表示实际业务检查及可执行性；引用失败不改变这两个值 |

知识预检的字段位置固定为：

```json
{
  "check_complete": true,
  "can_execute": true,
  "impact": {
    "reference_check_complete": false,
    "source_counts": {},
    "restricted_counts": {},
    "source_page": {"data": [], "page_size": 50, "has_more": false, "next_cursor": null},
    "file_count": 2
  }
}
```

示例省略原有确认 ID、摘要、有效项和过期时间，完整响应仍保留这些业务字段。`OperationPrecheck.impact` 本来是开放字典，无须改数据库或整个预检协议。仅在 `knowledgeDeletion.ts::DeleteImpact` 增加可选布尔字段；新后端总返回该字段，兼容旧响应时缺失表示提示未知。

`KnowledgeDeletionDialog` 的引用提示状态取只读场景 `view.inspection.check_complete` 或删除场景 `view.result.impact.reference_check_complete`；提交按钮和 `useKnowledgeDeletion.confirm` 只取业务 `result.check_complete/can_execute` 及原有权限/业务确认条件。引用提示 false/缺失时不渲染零引用计数，也不禁用提交。模型页面同样只把 inspection 状态用于提示，不能作为提交条件。

提示区标题使用“已记录的引用”，空结果使用“暂未查到已记录引用”；查询失败显示“暂无法获取引用”。来源列表变动后允许重新加载分页，但不会使删除确认失效；分页 cursor 不绑定全局 Coverage。

提示结果在业务计划创建后附加到响应，不写入新计划签名。新模型计划 `impact` 可为空；仓储兼容旧 impact 形状并按原字节校验 hash，执行不比较其引用状态。知识计划同样不再比较旧 epoch/inventory/inbound。已进入真实删除阶段的 operation 保留原 ID 和业务恢复字段，不借此重做删除；未消费且已过期的确认沿原重新预检流程处理。

内部提供两个简单调用：提交后的 `notify_reference_sync(tenant_id, source_type, source_id)`，以及 worker 调用的 `refresh_root(...)`。独立引用查询由现有模型/知识引用服务提供；实际业务读取不再返回索引 revision。均为内部方法，不新增公共写 API。

## 8. 接受的限制

发布消息最终失败或提交后进程退出时，这次同步可能遗漏；当前只做有限重试，下一次相关业务变更可再次触发。并发刷新可能留下滞后提示，不建立严格时效、顺序或自动补投承诺。原有未修改来源不要求先完成回填；提示始终按“已记录”展示。

这些限制是辅助功能的边界，不以增加 outbox、定期全库扫描、强一致协议或开服阻断补偿。将来若要治理全部历史引用，另起维护需求，不改变本次正常业务可用性。

旧应用只有名称、原映射也已丢失时，无法无损恢复原 ID。用户已选择只拒绝相关实际调用；这不是可由任务重试凭空修复的信息，不能借修订设计偷偷按当前名称绑定或回填旧版本。新版本业务 JSON 解决后续版本的独立性，不为历史版本增加迁移要求。

### 实施补充

- `invalid_missing` 仅是读取结果/接口 DTO 状态，不新增表或约束；缺失目标不再需要 Run 来证明其“曾经存在”。助手前后端状态类型同步接受此值。
- 新应用版本的 `resource_bindings` 只随原有 INSERT 保存；同一请求的旧版原绑定仅读取一次，之后重校验业务版本与身份，不重新比较辅助索引。模型网关仅对实际请求名称使用已有名称解析器，保留同模型别名、在线状态和共享校验，不遍历全部声明做准入。
- 提示来源页失败只更新提示错误，不销毁已生成的删除确认，也不标记业务范围失效。
- 普通新模型、空间删除不再写引用 tombstone，也不以其作为删除完成凭证；既有业务 operation/lease/FGA projection/物理范围恢复继续保留。历史 tombstone 仍保留；恢复旧模型删除时，仅对该 operation 读取其原 tombstone 以计算原资源版本，并在原业务完成时将该标记结束为 deleted。新操作不读取它。旧计划的原摘要保持，既有签名校验保留，不重新验收 Coverage/Run。
- 本地执行证据及尚未覆盖的环境验证见 [verification.md](./verification.md)。

模型提示查询和来源披露使用独立事务，并受同一个 2 秒预算约束。不能用业务事务内的 SAVEPOINT 代替连接隔离，因为驱动取消/连接失效可能使外层事务也失效。本地相关模型 fixture 改用文件 SQLite，允许两个真实独立连接；单连接内存 SQLite 不能验证该边界。
