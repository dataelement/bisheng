# Design：账号与昵称规则及前后端统一

**关联**：[已确认规格](./spec.md) · [执行状态](./tasks.md) · [版本契约](../release-contract.md)
**版本**：v3.1.0-beta1 / F011；**更新**：2026-11-10；**阶段**：设计及事务范围调整均已确认；前后端实现及本地验证完成，目标数据库和公司环境验收待执行。

## 1. 目标与非目标

统一注册、本地创建、本人及管理员改昵称的写入规则；新本地账号精确区分大小写，历史账号保持原匹配方式。保留历史字段及身份关联，使改名、组织同步、资料刷新和审计使用同一个昵称事实。

本期不更换密码摘要和会话体系，不新增账号修改或批量导入产品，不调整既有管理权限。公司测试服务的发布和共享数据库升级由研发安排；本地前端仍通过现有代理连接公司测试服务。

## 2. 关键约束

- 遵循 [constitution.md](../../../docs/constitution.md) C1–C8；领域归属沿用版本契约 F011。新增逻辑经 service → repository；旧 DAO 仅作既有入口的兼容适配，不增加新的 DAO 公共入口。
- `User.user_name` 存储上限为 128，`external_id` 为 255；新规则是写入规则，不能缩短原列或用 Pydantic 新上限阻止读取、提交未变更的历史值。
- 当前账号依赖数据库对 `external_id == 输入值` 的比较。数据库可能不区分大小写；当前 `uk_user_source_external_id` 又限制相同来源的大小写变体。仅改变 Python 比较无法实现两个新账号的独立创建。
- 新账号必须全实例查重，包括来源、租户和停用状态。`User` 是实例级自然人身份，不把这项查重降为某部门或当前租户范围。
- 两个 Vite 应用必须分别更新，复用现有组件和主题。F010 已有 medium、320px 注册表单及两项密码强度提示作为基线，不重做登录卡片。
- 部门人员删除当前保留 `User` 行并置 `delete=1`；账号占用继续保留。现有源不提供已物理清除记录的还原能力；本次不执行物理清除。

## 3. 方案对比与选定

### 决策 1：保留历史匹配，新本地账号使用精确索引

- **备选**：全量改成大小写敏感；统一转小写；针对 MySQL 更换列排序规则；只在查询结果中做 Python 精确过滤。
- **选定**：新增规则版本、账号匹配键及精确账号登记表。旧行通过新增列默认值归为历史规则，原账号、昵称和身份字段不变；新本地账号登记原始字符串的 SHA-256 键，以固定十六进制串提供跨数据库精确唯一性。
- **原因**：全量转换破坏 AC-06、AC-10、AC-11；单独过滤不能突破既有唯一约束；数据库专属排序规则不满足 C2。固定摘要比较不依赖业务账号列的排序规则，也不存储密码或替代原账号。
- **重新考虑条件**：未来明确批准历史账号升级、开放账号修改，或要求相同实例内多个独立账号命名空间时，重新设计版本和占用迁移；不能直接重算旧值。

### 决策 2：事务串行化身份创建，并保留来源唯一约束

- **备选**：只在创建前查询；只依赖精确摘要唯一键；使用进程锁或 Redis 锁；删除旧唯一约束且不替代。
- **选定**：新增数据库身份写入锁行，所有自然人创建入口在同一短事务中完成查重、用户插入、精确登记及初始角色/组绑定。旧唯一约束替换为 `(source, external_id, account_match_key)`；历史及普通外部身份的键为 `legacy`，新本地身份为精确摘要。
- **原因**：摘要键能防止相同新账号并发写入，却无法单独保护历史数据库匹配范围与并发外部身份写入。锁行跨进程有效；保留扩展后的来源约束仍能在数据库层保护外部身份的既有唯一性。
- **重新考虑条件**：身份写入出现持续排队或单次锁等待超过 1 秒，应先检查事务内网络和批量操作；若确认是创建吞吐瓶颈，再以实测为依据设计可保留数据库历史比较语义的分区锁。

### 决策 3：明确标记主动昵称，并在锁内决定能否同步名称

- **备选**：同步一律覆盖；停掉全部人员同步；分别维护后台备注和前台昵称；仅在同步开始前检查布尔值。
- **选定**：新增 `nickname_customized`。本人或有权限管理员实际改名时置真；组织/SSO 更新在锁定用户、读取最新标记后决定是否更新 `user_name`，其他权威字段继续同步。
- **原因**：`LoginSyncService._apply_user_attrs` 当前直接覆盖名字；仅在请求开始时检查会被并发改名击穿。本人和管理员必须更新真实 `user_name`，并使用现有 DSH 资料版本事务能力。
- **重新考虑条件**：未来提供「恢复组织同步昵称」产品操作时，再增加显式解除标记及审计；本期没有自动解除条件。

### 决策 4：共享纯校验，保留每个应用的状态和接口适配

- **备选**：复制注册校验到各页面；复用整套平台表单到 client；更换现有组件库。
- **选定**：新增无 React 依赖的 `@bisheng/identity` 工作区包，提供字符计数、空白过滤、账号/昵称/密码校验及错误标识；F010 的 `registrationRules.ts` 保留薄适配。页面继续各自使用 Zustand 或既有 Recoil、react-query，不新增跨应用状态共享。
- **原因**：规则必须一致，页面流程和状态归属不同。原注册校验返回平台翻译键，不适合直接作为 client 的领域规则。
- **重新考虑条件**：若后续多个领域也需要共享身份输入控件，再按已落地的组件规范提炼 UI；当前只共享规则。

### 决策 5：保留人员所属事务，最后原子提交昵称

- **备选**：将整张人员表单、调岗、用户组及权限恢复统一纳入新事务；先保存昵称再处理其他字段。
- **选定**：先校验昵称，完成原有人员操作后，最后独立提交昵称、保护标记、旧 SSO 识别快照、DSH 版本及成功审计。用户已明确选择「采用建议，聚焦账号昵称」。
- **原因**：原部门、组、角色及调岗各自有权限投影和恢复合同；本期聚焦账号与昵称，保留这些原事务。失败审计存储不可用时记录异常，保留原业务拒绝；成功审计写入失败必须回滚昵称及附属状态。
- **重新考虑条件**：人员管理另一期明确要求整张表单强原子性时，统一设计所属事务、权限投影和故障恢复。

后台表单未改昵称时不发送 user_name，避免修改其他人员字段时把旧昵称回写；兼容旧调用方仍可提交历史原值，服务端原文相同则 no-op。

## 4. 系统现状与目标结构

§4.1 记录基线 `cd02c8344` 的改动前行为；§4.2 起记录已完成的本地实现及契约。

### 4.1 已核实基线

| 范围 | 改动前行为与入口 |
| --- | --- |
| 注册 | `/user/regist` → `UserService.user_register`；账号被 `.strip()`，注册昵称仍单独限制 30，密码已有四类规则但把部分空白或汉字误当符号。 |
| 登录 | `UserService.user_login` → `UserDao.aget_login_candidates_by_account`；账号被 `.strip()` 后按数据库比较取候选，逐个验证密码。 |
| 后台创建 | 部门 body/path 两个 `local-members` 路由 → `acreate_local_member`；另有 `/user/create` 兼容入口，以 `user_name` 同时作为账号。 |
| 后台编辑 | `aapply_member_edit` 只允许 `local_primary` 修改名字，原实现会 trim，并绕过资料版本事务；来源和角色权限已有独立约束。 |
| 本人信息 | client `AccountSection` 显示头像、用户名及密码；`AccountPane` 与桌面 `DesktopSettingsPane` 复用它，没有改昵称 API。 |
| 外部身份 | 主要写入由 `LoginSyncService._upsert_user` 完成；弃用但仍保留的 `/user/sso` 也可创建用户。组织目录 reconcile 当前主要更新部门，不能把它误认为另一套直接用户写入器。 |
| 删除和资料 | 部门删除保留身份行；`UserDshProfileRepository.apply_detached_changes` 会锁用户并应用字段差异，`UserService` 在需要时同步递增 DSH profile version。 |

用户创建检索还覆盖 `UserDao.create_user` 及 `add_user_and_*`；兼容适配必须接入统一身份存储，不能只修两个显眼的路由。当前未找到独立的本地 CSV/Excel 人员导入接口，不新增该能力；若实现追踪发现可达入口，按 AC-26 接同一服务并反馈行错误。

### 4.2 持久化结构

| 对象 | 新增或保留的结构 | 契约 |
| --- | --- | --- |
| `User` | 新增 `account_rule_version: int NOT NULL DEFAULT 0` | `0`：历史/外部既有匹配；`1`：本次新建本地账号的精确匹配。不得从创建时间推断版本。 |
| `User` | 新增 `account_match_key: varchar(64) NOT NULL DEFAULT 'legacy'` | v0 为 `legacy`；v1 为原账号 UTF-8 的 SHA-256 小写十六进制串。用于扩展来源唯一约束，不在公开资料中暴露。 |
| `User` | 新增 `nickname_customized: boolean NOT NULL DEFAULT false` | 仅实际人工改名时置真；原值不变、取消、失败不置真。 |
| `User` | 新增 `legacy_sso_name: varchar(128) NULL` 及索引 | v0 身份首次人工改名时保存旧版 SSO 的原识别名称；只作旧协议绑定，不作为新账号或昵称唯一约束。字段不公开。MySQL 升级沿用原 user_name 列字符比较配置，DM8 沿用原库比较。 |
| `User` | 保留 `user_name(128)`、`external_id(255)` 和原始值 | API 字段名保持兼容；页面标签统一为昵称、账号。内部 `user_id` 仍是身份主键。 |
| `UserAccountReservation` | 新表：`account_key(64)` 主键、唯一 `user_id`、创建时间 | 只登记 v1 本地账号；创建与 User 同事务，停用或删除人员不释放登记，不提供普通删除接口。摘要相同但原文不同也按冲突拒绝。 |
| `UserIdentityWriteGuard` | 新表：整数主键 `id=1` | 实例级身份创建事务锁。基础设施行按需在独立短事务中初始化，不把业务数据回填写入 Alembic。 |

既有唯一约束 `uk_user_source_external_id(source, external_id)` 替换为 `uk_user_source_account_match(source, external_id, account_match_key)`；原外部 ID 搜索索引保留。新表遵循模型自动发现和启动建表约定，已有表的增列、索引变更进入 Alembic。

### 4.3 创建、查重和登录

**创建 v1**：原始字段校验 → 完成验证码/密码解密等前置处理 → 创建全新的 repository 事务并锁 `id=1` → 用数据库原比较查全部 v0 `User.external_id`，不附加启用、来源或部门过滤 → 查精确登记键 → 插入 v1 User、登记、初始角色/组 → 提交 → 沿用已有权限同步、租户初始化及响应。

规则版本、匹配键、来源及主动昵称标记由服务端决定，不能从注册或创建请求透传。首次注册的管理员初始化在同一身份锁内重新核对，避免两个并发请求都沿用锁外的「尚无管理员」判断。

锁行首次使用：在独立短事务中插入常量主键；并发唯一冲突只在确认该锁行已存在时视为初始化成功。随后业务事务使用 `SELECT FOR UPDATE`。不要在同一事务先锁不存在的键再插入，不把远程调用、解密、整批导入或审计网络操作放进锁内；事务开始后不得复用先前的查询快照做查重。

**外部身份新建/绑定**：来源内先按原有合同查 v0，涉及 v1 时按原文精确比较；多个身份候选拒绝。外部新建仍使用 v0 匹配语义，其兼容范围若覆盖已有 v1 身份，必须先按原对接合同精确绑定到同一身份或明确报冲突，不创建覆盖该范围的另一行。新增身份最终仍在统一锁内重新查重。原始外部 ID、`source` 迁移许可及已有租户/角色同步合同不变，不能按昵称绑定。

**密码登录**：同时查询「原始输入的 v1 精确登记」和「按旧逻辑 trim 后的 v0 数据库匹配」并按 `user_id` 去重。沿用既有启用候选与禁用查询区分：多个可登录身份明确报歧义，唯一启用身份进入原密码与次数控制；没有启用候选时用相同匹配语义判断禁用。不能遍历多个人的密码来决定身份。v1 不 trim、不降低大小写、不用昵称代替；v0 不套 64 或 ASCII 新建校验。找不到精确 v1 不转为大小写模糊匹配 v1。

公开改密码等以账号识别身份的可达入口也使用同一解析器，保留验证码和权限门禁；以已认证 `user_id` 操作的入口不重新按昵称查找。

旧 `/user/sso` 协议带 external_id 时优先按原始账号识别；未带时先查询已保存的旧识别名称，再兼容尚未人工改名的 v0 名称，最后查询账号。多个候选均拒绝。人工改名不改旧协议绑定；v1 昵称不能成为 SSO 登录别名。旧 DAO 只薄适配 repository 与纯候选决策，不从模型反向导入 service。

### 4.4 昵称与同步事务

本人请求 → 从认证主体取得唯一目标 → service 调用 repository 用户锁事务 → 读取最新原值 → 字符串完全相同则返回原资料 → 校验新值 → 修改 `user_name` 并置 `nickname_customized` → 按既有条件更新 DSH 资料版本 → 写成功审计 → 提交。

管理员仍先经过 `DepartmentService.aapply_member_edit` 的既有管理范围、成员关系、角色及 `local_primary` 判断，再调用同一昵称服务；不开放原先被禁用的同步人员或附属部门编辑能力。用户名以外的部门、角色、组修改保留原有服务，昵称写入不取得它们的权限。

后台保留一个保存按钮。先完成既有管理范围、成员状态和来源检查；对实际变化的昵称按新规则预检，不 trim 原文。随后由 _aapply_member_fields 调用原有部门、用户组、角色和权限投影流程，保留原事务。其他操作成功后，最后调用 NicknameService.arename_managed，在独立事务中写昵称、保护标记、DSH 资料版本及成功审计。任何前序失败都不提交本次昵称；最后昵称事务失败只回滚昵称及其附属状态，已完成的其他人员操作沿原机制保留。该边界由用户在 design-adjustment.md 中明确确认，不承诺整张人员表单全局回滚。

同步更新经 repository 在锁定用户后读取最新 `nickname_customized`。`UserDshProfileRepository.apply_detached_changes` 的同步来源路径必须跳过已被主动保护的 `user_name`，同时继续应用有权限的 email、phone、来源和其他变更；不能提交一个旧 detached 对象把保护标记或昵称覆盖回去。人工改名路径与同步路径显式区分，默认保护标记只由人工改名设置。

第三方原始身份标识不套本地账号格式；其昵称新建及未受主动保护的实际名称变化仍满足 AC-04 的 1–32 规则。已存在的原值不变时不重新校验。新名字非法时返回字段错误并保留原资料，不 trim、截断或用另一名字悄悄替代；受到主动保护时忽略来源的名字字段，继续处理其他权威字段。

改名不递增 `token_version`，不换密码、不重发或撤销现有 JWT。显示名字从当前资料读取；不能依赖旧 JWT 中的昵称继续展示。

### 4.5 对外字段和接口

统一成功响应继续使用 `{status_code: 200, status_message: "SUCCESS", data: ...}`；错误继续使用既有 `BaseErrorCode` 及统一处理器。

| 接口 / 字段 | 请求和响应 | 行为 |
| --- | --- | --- |
| 新增 `PATCH /api/v1/user/profile/nickname` | JSON `{ "user_name": "新昵称" }`；成功 data 为 `{user_id, user_name, external_id}` | 仅认证本人；请求模型 `extra='forbid'`，不接收目标 ID、账号、角色或身份字段。 |
| `GET /api/v1/user/info` | 保留原响应及 `user_name`、`external_id` | client 将其映射为当前昵称和只读账号；`external_id=null` 显示无账号状态，不用昵称补造。 |
| `POST /api/v1/user/regist` | 保留 `external_id`、`user_name`、加密 password、captcha 结构 | 账号和昵称新规则；接入 v1 身份事务，取消注册单独 30 限制。 |
| `POST /api/v1/departments/local-members` 及 `/api/v1/departments/{dept_id}/local-members` | 保留 `person_id`、`user_name`、加密 password、角色和部门结构 | 两个入口行为一致，均创建 v1；字段业务标签为账号。 |
| `POST /api/v1/departments/{dept_id}/members/{user_id}/apply-edit` | 保留现有 body，`user_name` 允许省略和传入历史原值 | 只有实际改名触发新校验和保护标记；账号不可写。 |
| `POST /api/v1/user/create` | 兼容原 `user_name`，新增可选 `external_id`；取消请求模型单独 30 限制 | 新 UI 明确传独立账号；老调用未传时继续以原字段兼作账号，但二者分别满足新建规则，不静默清洗。原 role/group 权限保持。 |
| 内部资料版本输出 | 保留 DSH `username`、`display_name` 及 `profile_version` | 字段协议不改名；值反映同一个 User 昵称。 |

规则校验为纯函数：前端以 Unicode code point 计数，后端以 Python 字符计数；不做大小写或 Unicode 归一化。昵称拒绝空白、Cc/Cf 控制与不可见字符、默认可忽略字符及孤立代理字符；后端使用项目已锁定的 `regex` 包表达同一 Unicode 属性，并补入直接依赖声明，跨语言用同一组边界样本验证。

账号空白过滤只发生在前端输入阶段，覆盖键入、粘贴和输入法结束；后端新值按原文校验并拒绝非法值。编辑历史昵称先比较原值，再过滤用户后续的实际输入；打开编辑不能先清洗原值。

新密码保留现有 128 字符上限，至少 8 个字符，并包含 ASCII 大写、小写、数字和 Unicode 标点或符号；空白、汉字不能充当符号。前端超过现有上限显示错误，强度提示仍只显示用户指定的两项；不改变历史密码登录校验。

新增 user 段错误码：`10612` 账号格式不符、`10613` 账号占用、`10614` 昵称规则不符、`10615` 历史身份不唯一。实现前再次检查占用；保留原 10600 认证、10607 验证码、10620 禁用及 10622 密码错误合同。三语翻译从共享 `api_errors` 源生成，字段错误由页面映射到对应输入框。

## 5. 已知坑与反直觉事实

| 事实 | 如果忽略会怎样 | 处理位置 |
| --- | --- | --- |
| 30 是注册 service 的单独判断，不是昵称存储列上限 | 错误缩列或拒绝历史长昵称 | `UserService.user_register`、新增纯规则；保留 User 列长度。 |
| 昵称重复合法，外部 ID 原比较也可能返回多行 | 用昵称登录或遍历密码会误选身份 | `AccountIdentityService` 的唯一候选解析；所有可达账号认证入口复用。 |

| 登录、只读账号和历史昵称不能统一套新建 maxLength | 旧账号不能登录，旧昵称被截断 | 两端表单适配及读取模型；只校验实际新值。 |
| shared Tooltip 明确不响应触摸 | 规则只放 Tooltip 会使触屏无法填写 | 页面规则按钮显式展开，不修改共享组件约定。 |

## 7. 测试、可观测与升级

### 7.1 验证策略

纯规则层使用前后端同组边界样本覆盖长度、中文/单 Unicode 字符、空白/不可见、账号首字符及符号。仓库层验证全局占用、唯一候选、同账号并发、大小写变体并发和事务回滚。登录服务回归验证码、密码失败、次数锁定、禁用及租户/会话控制；不得为测试关闭这些门禁。

昵称服务/API 覆盖认证本人、拒绝额外目标字段、管理员范围、历史原值 no-op、主动改名与同步并发、DSH 版本、失败保留和审计。成功审计与昵称在同一事务；授权后的业务失败记录结果和原因，未认证/越权请求沿用安全日志，不泄露他人昵称。

审计沿用 `update_user` / 用户配置模块合同，同时保存 `target_id`、操作者、`before`、`after`、`result`、发生时间，复用 `stamp_audit_logs` 的组织快照。新日志不修改历史事件的名字快照，不记录密码、验证码或 Token。

组件交互验证注册、创建、后台编辑、列表、个人资料及桌面共用入口：键入/粘贴/输入法、规则可读取、密码显隐、行内操作隔离、保存中防重复、失败/取消/刷新。浏览器 E2E 必须运行，使用隔离的合成用户与 API fixture；真实公司环境在发布后用研发提供的专用测试用户联调，不改现有真实用户资料。

### 7.2 执行入口

- 前端：在 `src/frontend` 用本任务固定 pnpm 运行规则/组件测试、`pnpm lint`、`pnpm typecheck`、`pnpm check-i18n`；最后执行架构检查及本功能代码审查。
- 后端：Python 3.11 环境运行 `pytest test/user/ test/department/` 中相关测试，迁移单头测试及新迁移幂等/双库用例；不依赖运行整套 RAG 中间件验证纯身份规则。
- 本地真实页面：`http://localhost:3001/login` 注册入口；`http://localhost:3001` 系统 → 组织与成员 → 创建或编辑；`http://localhost:4001/workspace` 设置 → 账号信息。桌面共用资料入口另外走组件/E2E fixture。
- 联调数据：专用合成账号 `F011Case01`、`f009case01`，同名昵称；历史账号/长昵称用隔离库 fixture。数据准备、权限和清理步骤在设计确认后的八列测试用例外围列出。
- 日志可按 request id、actor/target user_id、规则版本、错误码和锁等待定位；账号冲突和身份歧义是明确业务错误。不得用候选密码探测来诊断歧义。

### 7.3 DDL 与部署次序

1. 实现前用 Alembic 实际读取单一 head；新 revision 的 `down_revision` 只能取该结果。提交前再跑单头测试；不按文件名猜测。
2. 发布前备份并执行只读检查：确认唯一索引现状、默认账号比较和历史歧义；输出 ID/数量供研发核对，不清洗原字段。若发现与模型不同的索引或外部写入器，先修正部署方案。
3. 暂停身份创建/同步写入并排空旧服务写请求，执行新增列、扩展唯一索引 DDL。新表由统一模型建表机制创建；增列使用 server_default，不写原字段回填 UPDATE。不允许新旧写入程序混跑新身份规则。
4. 发布完整后端写入和解析逻辑后恢复身份写入，再发布前端；验证两个大小写账号、旧账号、改名同步保护和审计。MySQL/DM8 各自完成 DDL、并发与回归记录。
5. 有 v1 账号后不得直接回滚到旧二列唯一索引或旧模糊登录。故障时先关闭新建入口，保留数据，以前向修复为主；需要回退版本时由研发先核对新账号及冲突，不自动删除或合并身份。

本地阶段只产出迁移和运行说明，不对公司测试库执行升级。当前记录部署限制不代表双库或共享环境验收已经完成。

## 8. 后续改进与边界

- 本期保留历史数据库匹配，因而新账号不能占用旧账号的兼容范围；这是保护历史用户的已确认要求，不用自动改名解除。
- 单锁只覆盖低频身份创建，且没有真实公司并发性能数据；先验证正确性及观察锁等待，不引入未经测量的复杂分布式锁。
- 不提供账号改名、账号注销后复用或恢复组织昵称的操作；这些都会改变身份和占用合同，需单独需求。
- 前端页面完成不等于目标后端已发布。后端部署和两库联调的实测结果单独写入验收记录，不能以 fixture 成功代替。
