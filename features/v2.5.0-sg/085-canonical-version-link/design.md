# 修复设计

已核对线上容器与本地对应实现。保留旧关联路径，新增仅供正常独立manager使用的路径。

1. `KnowledgeVersionService` 保留开关、解析状态检查；通过既有入口解析器校验源和目标manager内容编辑权限。两者任一不是有效manager则沿用拒绝。
2. `KnowledgeDocumentDistributionService` 负责生命周期提交、全文意图及异常回滚。版本仓储新增事务内合并方法，按稳定顺序锁定两个文档、版本和文件，重新检查身份、权限检查时的主版本/代次及全部入口。新代码的ORM查询与变更落在仓储，避免旧基础仓储的逐条自动提交。
3. 源必须是唯一物理主版本；目标可包含历史版本。迁移原版本行，按目标最大版本号加一，不复制物理文件。旧主版本移除分发身份，新manager指向目标文档，原始来源和组织继承目标；保留物理文件自己的上传人、路径、ACL及对象。目标文档目录同步新manager路径，与旧关联保留新文件位置的行为一致，不引入权限迁移。
4. 目标代次递增且高于两个原文档代次，新manager标记pending并清除旧租约。旧源文档清除主版本指针，置invalid，创建deleting/pending的projection_tombstone；以既有投影任务及扫描补偿清理旧canonical正文，最终清理器再删除空源文档与墓碑。原物理文件不交给删除器。
5. 重复提交发现当前文件已经是目标主manager时返回原版本号；不生成额外墓碑、版本或代次。并发状态改变时拒绝，禁止旧快照合并。存在租约或投影未收敛时拒绝，防止旧任务与身份迁移竞争。
6. 成功后清相似候选缓存，沿用收藏通知、统计刷新，并加速派发新manager和墓碑投影。派发失败由持久状态扫描恢复；接口不宣称索引已同步。

不采用只删除18094判断或清空数据库入口字段的方式：这会遗漏manager切换、旧正文清理和代次更新。复用投影器，不另建任务队列、Schema或索引。

补充核对：反向兼容入口 `version/merge` 的manager场景复用同一安全路径，保持原相似度/force检查和通知事件语义。真实最终清理器在删除墓碑后却判断剩余入口数为1才删除invalid文档，既会遗留空文档，也可能误删仍有其他入口的文档；以0个剩余入口且0个物理版本为准修复。测试覆盖空文档删除、其他入口保留及物理版本保留三种结果。该清理器变更是旧canonical索引清理闭环的直接依赖。

文件落点：`knowledge_version_service.py`、`knowledge_document_distribution_service.py`、版本仓储接口/实现、内部结果schema和定向测试。V-001覆盖关系事务、幂等、拒绝与权限；V-002覆盖新主正文、旧canonical清理和失败重试；V-003复用版本及投影回归。SQLite不证明MySQL/DM8真实锁竞争；线上验收待部署后执行。回退代码应暂停新关联，先让已有pending投影收敛，不回滚已成功的版本关系。
