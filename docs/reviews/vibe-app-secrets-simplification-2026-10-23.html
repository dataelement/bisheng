应用密钥简化方案：保存配置，用户确认后重建

状态：修订规格待确认；本文为后续设计方向，不是已确认设计或实现。 用户最新边界优先：保存环境变量不能自动重启；页面只提示当前实例与最新保存配置不一致，由用户决定是否重建。

1. 为什么原先设计了三张表

原方案把“保存”与“自动使其生效”绑定：AppSecretValue 保存值、AppSecretState 跟踪自动生效状态、AppSecretMutation 保存独立请求及重试意图。运行控制底座已经有 RuntimeOperation、冻结环境、实例和路由投影，再为本功能维护一套自动生效状态不符合当前最小需求。

按本次边界，建议只增加一个应用配置资产，复用现有生命周期和操作账本；不增加独立自动重建队列、配置状态表、请求表、配置成功回执或新的跨领域提交协议。

2. 单表保存，复用已有数据

数据 建议保存位置 用途
最新已保存的键值 一张 AppSecretConfig 表，每应用一行 app_id 主键、tenant_id、revision、加密的完整键值映射、updated_by/at；名称大小写精确；完整值不回显
本次启动实际选中的变量 现有 RuntimeOperation 的受限 sealed_env 按批准版本声明取子集，冻结后用于 Docker/K8s 启动和故障恢复；新增非秘密 config_revision 注记即可
当前使用哪次执行 现有 RuntimeRoute / AppInstance 与对应 operation 识别当前正式实例实际使用的配置；不把最新保存版本号直接当已生效版本号
重建进度、失败、重试 现有 RuntimeOperation 复用现有 generation、deadline、租约、停止确认、幂等键和日志
保存与确认重建的留痕 现有操作审计 记录应用、引用名、操作者、动作和结果，不记录值

选择加密完整映射的一行，可以去掉逐名称索引及大小写 collation 问题；每应用数量和大小继续有界。使用既有持久部署加密 key，密文绑定租户/应用及用途，错误 key 明确失败；换 key 仍只作运维说明。最终字段、迁移及锁顺序在修订后的 design 定稿，本文不作为数据库变更授权。

3. 保存路径

  1. owner 在页面编辑名称和值；backend 校验租户、业务归属、名称、保留变量和大小限制。
  2. 同一个短事务按配置 revision 防止旧页面覆盖，更新加密配置和审计。首次创建用 app_id 唯一约束处理并发。
  3. 保存路径不调用 manager、不创建部署操作、不停止或启动实例。 不论新增、替换还是删除均如此；停用应用保持停用。
  4. 不需要独立保存请求账本。保存响应丢失时先重新读取安全元数据核对，不自动重复写入、不误报成功；旧 revision 的重复提交按冲突处理。
  5. 明确提示“已保存，有未生效变更”；运行中已经取得的旧值不会因删除平台保存值而消失。若第三方 key 泄漏，第三方系统撤销凭据是另外的操作，不能承诺平台删值会立即撤销它。

4. 如何判断是否有未生效变更

backend 根据当前正式路由绑定的 operation，在受限内存中解密该次执行的环境，再与最新保存配置在当前批准版本声明的引用名上逐项比较。对缺值统一按空值语义处理。

  • 只返回 has_unapplied_changes、有差异的引用名和安全状态，不返回新旧明文或可枚举值摘要。
  • 全应用 revision 不同不一定需要重建：改了未被引用的项不提示当前实例需要重建。
  • A → B → A 恢复原值后，与运行值相等就清除该项差异，不永久标脏。
  • 没有运行实例时显示“下次启动使用最新配置”；无法获取可信运行配置时显示“无法确认”，不误报已一致。
  • 对应受限执行上下文的留存与现有日志保护使用同一生命周期。若已清理，状态显示未知；不为查询新建一份明文或密钥摘要历史库。

因此不需要单独的 AppSecretState/applied_revision；运行配置取现有已切流的执行事实，而不是在两个模块分别写“已生效”。

5. 用户确认后的重建路径

页面显示差异后提供明确动作，例如“重建使配置生效”，说明当前版本和可能短暂中断。用户取消不发执行请求；不能把点击保存视为重建确认。

  1. 确认请求携带预期当前运行版本和配置 revision。backend 重新核验 owner、实际运行状态及现有生命周期互斥；过期确认拒绝，要求重新核对。
  2. 原子受理本次配置快照并创建既有类型的 RuntimeOperation，复用既有幂等键；同一请求恢复原操作，不叠加另一个重建。快照受理后再保存的值不改变本次环境，也不被旧结果覆盖。
  3. 复用部署执行器的明确“重建当前实例”分支：绕过同版本直接返回；使用当前已批准的 version/delivery/profile/镜像/档位，不启动 pending_version，不重新构建镜像、不重新审批、不生成代码版本。
  4. 停止旧 writer 并确认，再创建 Docker 容器或 K8s Pod，保留 SQLite 数据卷；不迁移、不备份/恢复数据库。正式值通过 Docker Env 或 K8s Secret + secretKeyRef 注入；预检、预览仍只取名称与空值。
  5. 探活成功后沿原部署提交路径切换实例/路由；不追加 AppSecretState 写入或 ConfigurationApplyPort。页面根据新路由对应的冻结环境重新计算差异，不把操作成功等同于所有后续保存值已生效。
  6. 失败沿既有操作记录显示；已保存配置保留，运行状态如实呈现。停止不明确时不启动第二个 writer；用户再次确认后才重试，不后台自动循环重建。manager 在途恢复仍是原操作续办，不是另发一次用户动作。

正常新版本发布和原重新上线动作仍可按原规则启动，此时选择当次最新配置；本次只取消“保存配置自动触发重建”。停止应用不会因保存、差异提示或本功能动作自行上线。
