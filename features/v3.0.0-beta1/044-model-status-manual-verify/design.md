# Design: 模型状态手动验证

> **本文档定位 — 现状快照（Why this How）**
> `spec.md` 回答做什么；本文回答**为什么这么实现**；`tasks.md` 是流水账。

**关联**: [spec.md](./spec.md) · [tasks.md](./tasks.md)
**版本**: v3.0.0-beta1
**最后更新**: 2026-07-24

---

## 1. 目标与非目标

- **目标**：把已存在但只在"配置时"跑一次的模型探活能力，暴露成模型管理页上的一个手动动作，并让"这个状态是什么时候测的"变成可见信息。
- **非目标**：不做定时巡检、不做批量验证、不让业务运行时的调用失败回写状态。

---

## 2. 关键约束

- 遵循 `docs/constitution.md` C1–C7。特别是 **C2 双 DB**：新增字段必须用 `dialect_helpers`，不得用 MySQL 专有语法。
- 不新增领域对象、不新增 DAO 类；新增取数/写入方法在既有 `LLMDao` 职责内扩展。
- 不新增错误码：验证失败是**业务结果**（状态=异常 + 原因文本），不是接口错误——接口本身应返回 200 并带回新状态。
- 每次验证 = 对模型的一次真实调用（会产生一次上游计费/配额消耗），因此必须是**用户显式触发**，且不可被页面自动轮询放大。

---

## 3. 方案对比与选定

### 决策 1：验证同步执行还是异步任务

- **备选**：
  - A. 同步执行：请求内直接探活，返回新状态。
  - B. 异步任务：投 Celery，前端轮询结果。
- **选定**：A
- **原因**：探活本身就是一次模型调用，正常在秒级；配上超时上限后最坏也就 30 秒。B 需要引入任务态、轮询端点和前端状态机，为一个"点一下看结果"的动作增加三处复杂度，不划算。
- **何时该重新考虑**：若出现批量验证需求（一次几十上百个模型），必须改异步。

### 决策 2：超时上限取 30 秒

- **备选**：10s（快但会误判慢模型为异常）／30s／不设上限（跟随上游超时，可能挂住请求）。
- **选定**：30s
- **原因**：探活提示词极短（`hello`），30 秒对任何正常服务都绰绰有余；超过 30 秒即便模型"最终能返回"，在业务里也已经不可用。不设上限会让一个坏地址把连接挂死。
- **何时该重新考虑**：若接入了冷启动型推理服务（首次调用需分钟级预热），需要单独放宽或按模型类型分档。

### 决策 3：状态写入行为修正——成功也要回写

- **现状**：既有探活逻辑**只在失败时**把状态写成"异常"，成功时不写任何东西（状态保持原值，新模型停在默认的"未知"）。
- **选定**：改为成功写「正常」+ 清空异常原因，失败写「异常」+ 原因。
- **原因**：不改这一点，AC-03 直接不成立——一个曾经异常、现已修好的模型，怎么点都还是红的，功能形同虚设。这同时顺带修正了"新加模型即使探活通过也显示未知"的既有观感问题。
- **风险与边界**：这条修改会同时影响**新增/编辑模型配置**时的既有探活调用（同一函数）。这是期望的一致化，但需在测试中确认没有别处依赖"成功不写库"的隐含行为。
- **何时该重新考虑**：若发现某些模型类型的探活假阳性率高（探活通过但真实业务调用失败），应改为区分"探活通过"与"可用"两个语义。

### 决策 4：状态更新时间用新字段，不复用通用 update_time

- **备选**：
  - A. 新增独立的「状态更新时间」字段。
  - B. 复用模型表既有的 `update_time`。
- **选定**：A
- **原因**：`update_time` 由数据库在**任何**字段变更时自动刷新——改个模型名、换个 API Key 都会刷新它，拿它当"上次验证时间"展示是直接的错误信息。且状态更新目前走的是批量 `update()` 语句，更无从区分变更来源。
- **何时该重新考虑**：无（这是语义正确性问题，不存在推翻场景）。

## 4. 系统现状（接手必读）

### 4.1 数据流

`模型管理页 hover → 点「更新状态」 → 新验证端点 → 复用既有探活 → 写状态+时间 → 返回新状态 → 前端刷新行 + Toast`

- **页面**：`platform/src/pages/ModelPage/manage/index.tsx` —— 按服务提供方分组列出模型；状态列按 `status` 数值取色取文案（0 正常 / 1 异常 / 2 未知），异常时旁边挂一个问号 tooltip 显示 `remark`。**本特性在状态右侧加 hover 出现的按钮，并新增一列时间。**
- **既有探活**：`backend/bisheng/llm/domain/services/llm.py` 的 `test_model_status()` —— 按模型类型分别真实调用一次（对话模型 `hello`、向量模型算一次 embedding、语音识别用内置示例音频、重排序压一条文档），失败时写状态=异常+原因。调用时带 `MODEL_TEST` 应用类型且 `ignore_online=True`（**因此已下线模型也能验证，AC-06 天然成立**）。
- **既有触发点**：只有两处——新增服务提供方、更新服务提供方（且只对新增或改了模型名/类型的模型重测）。**没有定时任务**。
- **状态写入**：`LLMDao.update_model_status` / `aupdate_model_status`（`llm/domain/models/llm_server.py`）——批量 `update()` 语句写 `status` + `remark`。**本特性在此扩展写入状态更新时间。**
- **新增端点**：挂在既有 LLM 路由（`llm/api/router.py`，与 `/online` 同级），入参模型 ID，租户管理员权限（与同文件其余管理端点一致）。

### 4.2 关键数据结构 / 字段约定

| 契约 | 形式 | 说明 | 谁会消费 |
|---|---|---|---|
| 「验证模型」端点 | HTTP POST，入参模型 ID | 返回验证后的状态、异常原因、状态更新时间 | platform 模型管理页 |
| 模型「状态更新时间」字段 | 新增 DateTime 列（Alembic 迁移，走 `dialect_helpers`） | 最近一次状态检测/验证的时间；历史行为空 | 模型列表接口 → 前端时间列 |
| 状态枚举 | `0=正常 / 1=异常 / 2=未知`（既有，不变） | 前端按此取色 | 模型管理页 |

### 4.3 关键模块职责

| 模块 / 文件 | 职责 | 不做什么 |
|---|---|---|
| `llm/api/router.py` 新端点 | 参数校验 + 权限 + 调 Service | 不含探活逻辑 |
| `llm.py` `test_model_status()` | 按类型真实调用一次模型并写状态 | 不负责鉴权、不负责挑选模型 |
| `LLMDao.update_model_status` | 写 status / remark / 状态更新时间 | 不判断业务语义 |
| `ModelPage/manage/index.tsx` | hover 按钮、loading 态、时间列、Toast | 不缓存状态（以接口返回为准） |

## 5. 已知坑 / 反直觉事实

| # | 反直觉事实 | 如果不知道会怎样 | 在哪处理 |
|---|---|---|---|
| 1 | 既有探活**成功时不写库**，只有失败写"异常" | 异常模型修好后点验证永远变不回正常，AC-03 直接失败 | 决策 3：补成功分支 |
| 2 | 模型表的 `update_time` 是"任何字段变更都刷新"，不是"状态变更时间" | 拿它当验证时间展示 → 用户改个模型名，页面就显示"刚刚验证过"，是假信息 | 决策 4：新增独立字段 |
| 3 | 模型状态**平时不会自己更新**——没有定时巡检，只在新增/编辑配置时测一次 | 会误以为状态是实时的，从而认为"状态显示可用但调用失败"是 bug；实际那是几周前的旧结论 | 本特性正是为此而做；§8 记录了巡检的取舍 |
| 4 | `online`（上下线开关）与 `status`（可用性）是两个独立字段 | 会把"下线"误当"异常"，或给已下线模型禁用验证按钮（与 AC-06 相悖） | 探活已 `ignore_online=True`，前端按钮不看 `online` |
| 5 | 探活对 ASR 类型模型要读一个仓库内置的示例音频文件 | 打包/镜像若漏了该资源文件，ASR 模型验证会恒失败且原因看起来像模型问题 | 既有实现，注意别在精简镜像时删掉 |

## 6. 对外契约与依赖

### 6.1 我提供给别人的（Outgoing）

| 契约 | 形式 | 谁在用 |
|---|---|---|
| 「验证模型」端点 | HTTP API | platform 模型管理页 |
| 模型列表响应新增「状态更新时间」字段 | HTTP 响应字段（新增，向后兼容） | platform 模型管理页；其他消费方忽略即可 |

### 6.2 我依赖别人的（Incoming）

| 依赖 | 形式 | 风险点 |
|---|---|---|
| 各模型类型的客户端构造与调用（`get_bisheng_llm` 等） | 内部 Python API | 新增模型类型时若不在探活里补分支，该类型验证会静默无操作 |
| 上游模型服务 | 外部网络 | 验证结果受网络波动影响，可能出现偶发"异常"；用户可再点一次 |

## 7. 测试与可观测

- **后端单测**：探活成功 → 状态=正常且时间刷新；探活抛异常 → 状态=异常 + 原因 + 时间刷新；超时 → 按异常处理。
- **手动验证**：模型管理页找一个配错 API Key 的模型 → 点更新状态 → 应变红并可看原因 → 改对配置 → 再点 → 应变绿（这一条同时验证决策 3）。
- **回归点**：新增/编辑服务提供方的既有探活路径（同一函数）行为是否仍正确，尤其是"保存时检测状态"的提示不能被破坏。
- **日志**：探活失败已有 `logger.exception`，可据模型 ID 排查。

---

## 8. 后续改进 / 不打算做的事

- **定时巡检**：本期不做——每次巡检都是对所有模型的真实计费调用，成本与告警噪音都要设计（频率、退避、只测在线模型、失败通知），值得单独立项。
- **批量验证**：需要异步化（决策 1），本期不做。
- **"探活通过 ≠ 业务可用"**：探活只发一句 `hello`，不覆盖长上下文、并发、限流等真实场景；若要更强的健康语义需引入分级探测。
