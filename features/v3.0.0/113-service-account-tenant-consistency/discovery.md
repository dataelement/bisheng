# F113 服务账号租户一致性 — 需求发现

## 1. 需求来源与确认

2026-10-28用户在116问题排查后明确要求简化为：

1. “归属人租户和服务账号租户不一致，拒绝处理业务请求，明确返回租户不一致”。
2. “现有资源不迁移不变更，看不到属于正常现象”。
3. “服务账号管理界面，增加一个切换租户的功能（只有超管可以看到），可以切换创建服务账号时所属的租户”。

对第3项追问“是否只切换管理和创建时的租户，已有服务账号及密钥仍保持原租户”，用户确认：“是，只切换管理和创建时的租户”。

用户随后明确：“确认这个简化方案，按 SDD 流程推进，先产出规格文档供我评审，只做本功能必要的定向验证，不跑全量测试。”

用户进一步明确：“先不做应用移交和迁移，保持存量资源不变。把应用操作的租户校验也纳入本次修复，修订规格并修复前面两个评审问题，然后重新评审。”本轮据此追加应用管理操作的租户资格，收口待生效版本和管理写动作清单。

**以上是需求发现阶段确认，不是正式spec或design确认。** 本轮只编写spec、契约增量登记及规格自审；不实施、不修116数据、不部署、不提交推送。

## 2. 已确认边界

- 拒绝范围扩大为该服务账号的所有业务调用，包含已有资源的读写、模型及MCP等业务；不只拦应用发布，不因持有delegate而豁免。
- 服务账号与密钥租户固定；租户选择仅控制管理员查看、管理和创建范围。
- 应用上线/停用/恢复/删除、元信息、日志/数据与配置等入口补调用者租户校验；owner相同不能跨租户，保留原权限规则与既有超管入口例外，不扩大owner-only操作权限。
- 失配发布拒绝不得改变当前或待生效版本；服务账号管理写操作明确穷举，跨标签页范围变化时拒绝旧提交。
- 存量应用及其归属、权限、版本、数据、审批与访问地址不迁移或修复；迁租户后的owner不获得跨租户可见例外。
- 不自动停止已有应用，不自动撤销失配账号密钥，不拦截人员迁租户；新的业务请求与发布阶段拒绝按规格定义。
- 在途发布使用提交时固定的归属人与租户，后续开始执行/创建审批/正式上线前复核；不改成新租户继续执行，不改变已作出的审批决定。
- 超管为新租户创建新服务账号、新密钥和所需授权；不提供旧账号换租户、旧授权复制或旧应用自动重建功能。

完整已确认方案见[简化方案](../../../docs/reviews/vibe-owner-tenant-consistency-fix-plan-2026-10-28.md)。规格只保留业务要求，不复制其中技术建议。

## 3. 静态核查基线

发版线采用本机已有的 `origin/feat/3.0.0@3d0406bc6615a4c04dcc3e846879d8e7524df47f`，未在本轮fetch，不能宣称已核对最新远端。该基线与上一轮方案所用release提交的工作文件一致。已切到本功能分支 `codex/113-service-account-tenant-consistency`；复用当前任务拥有的隔离worktree，不改脏主工作区。

| 核查入口 | 已确认现状及本次影响 |
|---|---|
| open_api的credential_validator、access_context | 账号/密钥租户比对存在；未查owner当前租户；principal缓存命中时不再解析主体。本次需要保障后续请求实际采用当前关系 |
| open_api的owner_repository | 通过有效用户租户关系取得归属人租户；批量结果按user覆盖，不能用此行为承诺“多条有效关系也能确定唯一租户” |
| open_mcp/auth.py | MCP采用公共访问上下文；长连接后新的业务调用仍须接受本次规则 |
| service_account_service及repository | 创建时同租户校验、已有账号固定租户、管理目标范围检查已存在；超管未指定管理范围时可能按owner推导创建租户 |
| AdminScopeMiddleware、useAdminScope、模型管理ScopeBar | 已有超管共享管理范围且service-accounts已在管理路径中；根租户在模型选择器中采用“清除范围”，不能据此推断服务账号创建一定落1 |
| platform服务账号管理页/创建弹窗 | 暂无管理租户选择入口，归属人选择使用既有部门用户组件 |
| app_state_service、app_meta_service、app_data_service、app_query_service | 生命周期、元信息、应用数据和平台日志存在只比owner就放行的路径；加载应用会切换执行租户，不能用该上下文证明调用者同租户。详情读取、CLI迭代发布及应用配置入口已有部分显式校验，不视为所有入口都无检查 |
| F049 AC-23、AC-24、AC-26、AC-27、AC-28 | 涉及不提供租户选择、owner可管理、权限不继承、改绑不追溯和owner禁用不级联失效；本次增量适用关系见spec §3.2 |

116事实来自同日之前已完成的只读查询、请求日志和OpenFGA核查；本轮不重复远端验收：gzx01为849/当前60，服务账号24为租户1/owner849，三个应用均在租户1且owner授权已存在。当前方案不把该现象归为漏写授权。

## 4. 领域归属与验证范围

本特性协调既有开放API、管理范围和发布场景的增量，不接管自然人、租户成员、权限投影、审批引擎或运行时对象。F049历史规格作为来源；当前实现由发版线open_api及归档的beta版F053承接，不重新激活旧F049实现分支。F055继续拥有发布阶段资格和失败处置及配置入口；F054继续拥有应用状态、元信息、数据和日志业务规则，本次只补租户前置条件。

验证只覆盖本功能的同租户允许/失配拒绝、热缓存和会话复用、归属关系变化、异步发布阶段、超管切换完整写动作及越权、跨租户owner的应用操作拒绝与同租户允许、可信后台作业/存量不变。未来E2E使用专用临时账号/应用；不修改116三个存量应用，不跑Vibe全量或编排故障全量，不以单机结果替代其他形态。DM8按用户既定要求仅静态核对兼容约束。
