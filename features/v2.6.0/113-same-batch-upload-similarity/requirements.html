1. 背景与问题

知识库上传者一次选中多个文件并确认上传。这些文件解析成功、进入知识库之后，彼此之间经常没有相似提醒。上传者因此看不到同一批里的重复或近重复文件。

客观事实（来自当前毕昇代码，不是生产实测计数） 每个文件在自己解析成功时，只和当时已经解析成功的其他文件比一次，结果只写在自己名下。候选按来源文件保存。文件列表上的相似徽标只看这个文件自己有没有待处理候选。比较范围是同一个知识库，不看文件夹。先解析完的文件不会因为同批后面的文件解析完而再算一次。解析可以并行，两边都可能在对方指纹写入前就算完。

逻辑推演 串行时，后完成的文件有机会看到先完成的文件；先完成的文件看不到后完成的文件。并行时，两侧候选都可以没有对方。这和「同一批落库后互相看不出来」一致。代码里没有一条「同一批跳过」的专门规则。

已核对的文件夹事实 相似候选查询按知识库列出已解析成功的主版本和已就绪发布入口，条件里没有文件夹。已确认的发布相似需求也按目标知识库比较，不按目录。因此，不同文件夹之间算出相似，是当前规则，不是文件夹误判。

本次要补的是比较时机：同一次上传里后解析成功的文件，要让同批里已经解析成功、且用户还没点「不关联」的文件再按现有规则算一遍。

确认时追加的约束 上传解析是核心功能。文件是否解析成功、解析失败、超时或违规，以及这些结果提交时已经做的全文同步意图和自动发布登记，都保持现在的行为。相似互判失败不得改写这些结果。

3. 范围

本次包含

  • 毕昇知识库里，用户一次确认上传、最终登记成功的文件。
  • 客户端知识库上传，以及门户上传对话框。一次确认即使按文件夹拆成多次登记，仍是一批。
  • 不经过上述界面、直接调用登记接口时：同一次请求里登记成功的文件是一批。
  • 这些文件解析成功之后的相似候选、文件上的待处理相似状态、列表徽标所读的那份结果。

明确不做

  • 两次分开的确认上传之间，不回头更新更早的那一次。
  • 不补算上线前已经落库的文件。现有数据没有「哪一次确认」的记录，无法按本规则还原历史批次。全库重算是另一个范围，本次不做。
  • 不改变发布到目标库之后的发布入口刷新。发布入口仍只在自己就绪时算一次。
  • 不改变相似度算法、公司编码第一段、两套阈值、每个文件最多 3 条、同一文档的不同版本不互推。
  • 不把已点「不关联」的文件重新打开。
  • 不新增文件夹过滤，也不把跨文件夹相似改成错误。
  • 不改门户自己的页面。门户没有独立的相似判定；毕昇列表已经展示徽标。
  • 不改权限、积分、解析成功与否。

一期就是上表。二期未定，不承诺历史回填，也不承诺发布入口互判。

4. 用户场景与流程

上传者在知识库或门户上传对话框一次选择多个文件并确认。文件逐个解析。某个文件解析成功后，系统用现有规则更新这个文件的相似候选，并回头更新同批里已经解析成功、且未点「不关联」的其他文件。用户在文件列表上看到待处理相似；点开后仍是现有的相似候选，最多 3 条。

结束状态

  • 进入对方前 3 名的两侧文件：各自有待处理相似，候选里有对方。
  • 达到阈值但排不进前 3：这一侧不显示对方。
  • 已点「不关联」的一侧：保持已处理，不因为同批后到的文件重新出现提醒。
  • 解析失败的文件：没有相似候选，也不使别人把它写成候选。

异常出口

相似计算失败时，该文件保持解析成功，不写入这次没算出来的相似关系。用户仍可在列表看到文件已解析。详细规则见 异常表。

REQ-002 解析成功后互判 P0 · 一期

来源：决定 D2、D3、D5、D6。算法本身沿用现有相似规则。

前置：文件已经登记成功，并且这次解析成功，具备现有比较资格（有效指纹、有公司编码，且通过现有状态过滤）。

操作与结果：该文件解析成功时，系统做两件事。

  1. 按现有规则计算这个文件自己的候选。比较范围是同一个知识库里当时已具备资格的文件，包含同批里已经解析成功的文件，也包含更早就不在这一批里的文件。
  2. 对同一批里其他已经解析成功、且相似状态不是「已不关联」的文件，各自再按现有规则计算一次。尚未解析成功的同批文件不在这次被更新。

结束：每个被更新的文件只保留相似度最高的 3 条。某条达到阈值但排在第 4 名及以后，不显示。用户没有新的页面，仍看文件列表上的待处理相似和现有候选弹层。

回头更新决策
同批其他文件的状态后一个文件解析成功时
已解析成功，未点「不关联」按现有规则重算它的前 3 条
已解析成功，已点「不关联」不重算，不重新打开提醒
还在解析，或解析失败，或没有有效指纹不把它写入别人的候选；等它自己以后解析成功时再参与
不属于这一批不因为这一批而回头重算
相似状态
状态含义本次允许的变化
无待处理当前没有需要用户处理的候选重算后若前 3 里有候选，变为待处理
待处理有仍有效的候选，用户还没点「不关联」可随重算更换前 3 条；候选变为空时回到无待处理
已不关联用户点过「不关联」同批后到文件不得把它改回待处理

重算使用当时整个知识库的资格文件，所以先完成文件的前 3 名可能因为新文件加入而替换其中一条。这是决定 D5 的结果，不是只往旧列表末尾追加。

7. 数据与埋点

相似结果仍然落在毕昇已有数据上：文件的待处理或已不关联状态、该文件名下的相似候选、计算时使用的比较快照。比较时读取文件指纹、解析状态、公司编码、文档与主版本、知识库归属。

事实 当前没有「上传批次」字段。本需求要求系统在这些文件解析结束前知道它们属于同一次确认。用任务参数记住，还是在现有表增加一列，由技术设计决定。需求不指定表结构。

上线前的旧文件没有这个批次事实，所以不回填。

埋点：不适用。没有新的统计指标需要事件。不记录文件正文。

隐私：候选里继续只使用现有已展示的文件信息。不新增身份证、电话等字段。

AC-07REQ-001、REQ-002 第一次确认只有甲，且甲已解析成功。第二次确认只有乙。二者会互相进入前 3 乙解析成功 乙的候选可以包含甲。甲不被这次上传回头重算，因此甲不因为乙而新增候选
AC-08REQ-001 不经过上传对话框，连续两次登记请求，各登记一个文件 两个文件都解析成功 它们不属于同一批。结果与 AC-07 相同
AC-09REQ-003 同批两个文件分别属于：公司编码第一段不同、同一文档的两个版本、没有有效指纹、不在同一知识库，这四种里的一种 两者都解析成功 沿用现有规则，不把对方写入候选
AC-10REQ-001、REQ-002 一次确认只登记成功一个文件，库内已有另一个可相似文件 该文件解析成功 没有同批回头更新。它与库内旧文件的比较保持现有一次计算的结果
AC-11范围排除 两个相似文件在本功能上线前已经解析成功，当时两侧都没有对方 完成本次发布，不另做回填 这两个旧文件不被自动补上对方
AC-12异常：失败 同批文件解析已经成功，随后的相似计算失败 计算失败 文件仍是解析成功。不写入这次没算出的候选。已不关联状态不被改回待处理
AC-13范围排除 同一次上传的两个文件后来都发布到同一个目标库 两个发布入口先后就绪 发布入口仍只在自己就绪时刷新。本次不追加「同批发布入口回头更新」
AC-14REQ-003 现有列表规则下，某用户本来看不到相似徽标 同批文件形成待处理相似 该用户仍然看不到徽标。能看见的用户仍按原入口查看，最多 3 条
AC-15REQ-002 同 AC-01，但两个文件几乎同时解析成功 两侧更新都结束 最终与 AC-01 的结束状态相同。允许结束前短暂只有一侧有候选

四问自检

研发能否不开工前再问产品规则 批次、两侧重算、不等整批结束、前 3、不重新打开、文件夹不设边界，都有决定和验收。表结构、并发锁和失败后的自动重试次数留给技术设计，不是未定的产品规则。
测试能否写用例 AC-01 至 AC-15 覆盖主路径、跨文件夹、部分完成、失败、已不关联、前 3 挤出、两次上传、直接接口、资格排除、单文件、历史不回填、计算失败、发布入口排除、权限和同时完成。
业务方能否说出上线换来什么 同一次确认上传并且解析成功的文件，会按现有相似标准互相参与比较。先传完的那份也会在后一份成功后更新。两次分开的上传、历史文件和发布入口不在这次收益里。
三个月后能否看懂原因 第 1 节写了漏判来自单向、单次计算，不是文件夹误判。决定表保留了没选的方案。

9. 风险与灰度回滚

风险
风险触发影响应对
先完成文件的前 3 名发生变化 同批后一个文件解析成功并触发重算 用户如果正打开旧的候选，可能看到其中一条被换掉 接受。这是按分数重新取前 3 的结果，不额外保留旧候选
同时完成时短时间只有一侧有提醒 两个解析几乎同时结束 用户刷新得太早，可能先只看到一侧 验收看两侧更新结束后的结果，见 AC-15。锁和重试由设计处理
历史相似仍缺失 上线前的同一次上传 旧文件不会自动补上 接受。没有批次记录就不回填，避免把全库重算混进本次
发布入口仍可能单侧缺失 同批文件发布到目标库 目标库发布入口不一定互相出现 接受，并写进 AC-13。要做需另开需求

启用范围：跟随现有知识库相似能力，不新增开关。版本管理关闭时，徽标继续按现在的条件隐藏。

回滚：撤回本次代码后，新的解析只保持原有的「每个文件算自己一次」。已经写入的候选和待处理状态保留，不在回滚时批量删除。需要清数据时另作确认。
