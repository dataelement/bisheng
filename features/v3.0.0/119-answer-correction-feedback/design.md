# F119 应用回答纠错反馈设计

状态：总体设计与角色映射已确认。以下为计划契约。
规格：[spec.md](./spec.md)

## 1. 边界

工作台承载提交和我的反馈，管理端承载负责人队列和维护人员任务。纠错反馈拥有自己的处理记录。现有聊天评价、知识库内容写入、应用配置仍由原模块负责。

## 2. 分层和权限

在 chat_session 内按 API → application → domain 编排，依赖现有会话读取、应用配置、权限运行时的应用层接口。API 挂在现有 v1 router。DAO 承担租户作用域下的存取和原子状态更新。两端使用各自请求封装。工作台用 React Query 刷新反馈记录，管理端用页面查询状态取消过期请求并在写入后重新加载队列。

宪法检查覆盖 C1–C8。跨模块调用走应用服务。迁移使用两库通用列和索引，读写按租户上下文执行，更新显式携带已验证记录的租户条件。通过 PermissionService 对实际应用和知识库判权。业务错误按 C5 查重并优先复用语义一致的已有错误。无新增密钥、前端 store HTTP 或共享本地文件。

| 操作 | 服务端授权 |
|---|---|
| 资格与提交 | 验证调用者对该会话和回答的可见性，再从回答所属应用查询当前关联库 |
| owner 队列、详情、分派、回复 | 按反馈对应应用实时校验应用负责权限 |
| 分派目标 | 校验应用与库的当前关联，校验候选人在同租户且拥有该库的维护权限 |
| assigned 队列、详情、处理结果 | 校验当前用户是受派人，并复查该库的维护权限 |
| mine 列表、详情 | 限定当前租户和提交人 |

候选列表与写入复用同一授权谓词。按权限过滤在分页之前完成。按已确认的角色映射，应用负责人使用 workflow 或 assistant 的 `manage_permission`，知识库维护人员使用 knowledge_space 或 knowledge_library 的 `edit`。

## 3. 决策

- 服务端以已保存回答验证原句。客户端上传整条回答会允许篡改来源。保存原句快照用于处理和回看。如果以后需标记重复句子的具体位置，再加位置契约。
- 分派时读取当前应用关联，并由负责人选库。按引用推断库会漏掉已确认支持的无引用回答。后续若有稳定的来源映射，可将它用于提示。
- 独立状态记录和条件更新。复用点赞点踩记录无法表达受派人和处理结果。每次动作按期望旧状态更新一次，冲突时返回业务冲突并由界面刷新。重新分派或多轮回复纳入范围时，再引入动作历史。
- 队列承担接收和进度查询。独立站内信会额外引入消息投递与重试语义，用户已确认留待后续。

## 4. 状态与持久化

`pending_assignment → pending_processing → pending_reply → replied`。迁移新建纠错反馈表，保存租户、应用、回答、提交人、原句、更正说明、依据、状态及创建和更新时间。分派、处理、回复分别追加知识库与受派人、处理结果、回复文字及对应动作时间与操作者。文本按纯文本存取和显示。列表按创建时间及 ID 倒序，分别为提交人、应用和受派人建立租户前缀索引。

在应用服务中拒绝空白文字，原句需匹配服务端保存的用户可见回答正文。列表权限过滤及关联读取沿用业务资源接口。展示回复时，用户端投影仅暴露自己的反馈信息、状态和已发送回复。

## 5. 运行风险

- 列表页缓存的关联库和候选维护人可能过期。分派命令重新校验，防止过期页面将内容交给无权限人员。
- 并行处理或双击可能重复提交动作。DAO 将状态前置条件和字段更新合并为一次写入，受影响行数为零时刷新状态。
- 流式回答在落库前没有稳定校验来源。提交入口在持久化回答可读后启用。

## 6. HTTP 契约

前缀 `/api/v1/answer-corrections/`，成功使用现有统一响应。各资源 ID 沿用源资源类型，反馈 ID 为整数。文字字段使用 JSON 字符串。

| 方法和路径 | 输入 | data |
|---|---|---|
| GET eligibility/{answer_id} | 回答 ID | eligible 布尔值 |
| POST / | answer_id, quote, correction, evidence | 反馈详情 |
| GET / | view 为 mine、owner 或 assigned，page 默认 1，page_size 默认 20、最大 100 | items、total |
| GET {id} | view 同列表 | 对应角色的详情 |
| GET {id}/knowledge-options | 反馈 ID | items，每项 id、name |
| GET {id}/assignee-options | knowledge_id、page、page_size | items，每项 id、name，及 total |
| POST {id}/assignment | knowledge_id, assignee_id | 更新后的详情 |
| POST {id}/result | result | 更新后的详情 |
| POST {id}/reply | reply | 更新后的详情 |

详情公共字段为 id、answer_id、quote、correction、evidence、state、reply、created_at、updated_at。owner 和 assigned 视图增加 app_id、knowledge_id、assignee_id、result，未发生动作的字段为 null。前端根据角色和状态显示动作。写入后刷新详情和相关列表。鉴权、输入无效、状态冲突走既有响应机制。

入站依赖为会话回答、应用关联库和统一授权运行时。正文存储格式、应用绑定来源或权限动作变更都会影响资格和可见性。当前仅对两端提供 v1 契约，内部不新增跨模块调用入口。

## 7. 验证

先使用已保存的 FLOW-087 功能场景，再在设计确认后编写独立 API 用例覆盖候选权限、字段投影和状态冲突。运行前执行后端 `scripts/dev_env_check.sh`，用真实租户、应用、回答和角色配置执行 `uv run pytest live_tests/answer_correction -v`。服务实现之前仅验证测试文件可编译。

## 8. 跨租户共享应用边界

首期仅支持当前租户自有应用。资格查询和提交均比较会话所在租户与可信应用记录的归属租户。根租户共享应用产生的回答可能存在子租户会话中，单凭回答所属租户不能确认应用符合资格。
