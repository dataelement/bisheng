# Feature: 部门知识空间唯一管理员与超级管理员前台隐藏

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
>
> spec 只回答 **做什么 / 验收标准 / 不做什么**。
> 所有 How（决策、数据流、字段、API、Service、前端、文件清单）一律在 [design.md](./design.md) 与 [tasks.md](./tasks.md)。

**关联 PRD**: 中粮 cofco-818 需求（需求文本 + 飞书截图：部门知识空间管理弹窗、权限与展示规则表）
**优先级**: P0
**所属版本**: v2.6.0（cofco 分支）
**依赖**: F033-department-space-member-scope（部门空间授权范围收敛）、F026（space_channel_member 频道字段归属，不冲突）

> **范围边界**
> - **本次纳入**：
>   - 部门知识空间创建时强制配置**唯一空间管理员**（空间负责人），创建后可由超管更换
>   - 创建操作人（超管）不写入任何前台权限关系，仅保留审计记录
>   - 空间管理员失效（停用 / 删除 / 移出企业）→ 空间进入【待配置管理员】状态
>   - 超级管理员在**全部知识空间**的前台成员、管理员、权限界面、人数统计、候选人接口中统一隐藏其隐式治理身份
>   - **下线「部门管理员自动同步为空间管理员」机制**（含调岗 / SSO 同步 / 删号 / 部门管理员任免各钩子）— 用户已确认（2026-08-13）
>   - 存量部门空间的一次性迁移规则
> - **本次明确排除**：
>   - 个人空间、普通共享空间不新增「必须配置管理员」要求（超管隐藏规则仍适用）
>   - 不改变部门成员自动获得本部门空间 viewer 的机制（F033 口径不动）
>   - 不做「创建者转交 / 所有者转移」类功能——部门空间不再有前台创建者角色，转交无从谈起
>   - 频道（channel）的成员与权限模型不动

---

## 1. 用户故事

A. 作为**平台超级管理员**，我希望批量为部门创建知识空间时**必须为每个空间指定一名负责人**，以便空间从诞生起就有明确的日常管理责任人，而不是挂在我（超管）名下。

B. 作为**空间管理员（部门空间负责人）**，我希望在成员与权限界面中以管理员身份正常展示并拥有成员、权限、空间设置的管理能力，以便独立完成日常治理。

C. 作为**平台超级管理员**，我希望能查看并进入全部部门知识空间进行治理（含更换管理员），但**不出现在任何空间的前台成员 / 权限展示中**，以便平台治理身份与空间权限身份彻底分离。

D. 作为**普通空间成员**，我看到的成员列表、管理员信息、人数统计相互一致，不出现「隐身的管理员」或对不上的数字。

## 2. 验收标准

### 2.1 创建时强制配置空间管理员

- **AC-01** — WHEN 超管创建部门知识空间, THE SYSTEM SHALL 要求为每个待创建空间指定一名空间管理员；未指定时拒绝创建整个请求项并返回业务错误码。
- **AC-02** — IF 指定的空间管理员不属于当前企业（租户）或账号非正常启用状态, THEN THE SYSTEM SHALL 拒绝创建并返回业务错误码。
- **AC-03** — WHEN 创建成功, THE SYSTEM SHALL 使该用户成为空间的唯一空间管理员，在前台成员与权限界面正常展示，并拥有成员、权限、空间设置管理能力。
- **AC-04** — THE SYSTEM SHALL 不把创建操作人写入前台成员列表、权限列表、负责人信息、人数统计与空间详情；创建事实仅保留在审计记录中。

### 2.2 管理员唯一性与变更

- **AC-05** — THE SYSTEM SHALL 保证任一部门知识空间在任一时刻**至多一名**空间管理员；正常启用状态下**恰好一名**。
- **AC-06** — WHEN 超管更换空间管理员, THE SYSTEM SHALL 先校验目标用户属于当前企业且账号有效，再**原子替换**管理员关系；不出现零管理员或多名管理员的中间状态；校验失败时保持原管理员不变。
- **AC-07** — WHEN 管理员被更换, THE SYSTEM SHALL 撤销原管理员的管理身份；若其在被配置为管理员之前已是空间成员，回退为原成员身份，否则移出空间（见 §3 边界-4）。

### 2.3 【待配置管理员】状态

- **AC-08** — WHEN 空间管理员账号被停用、删除或移出所属企业, THE SYSTEM SHALL 将该空间标记为【待配置管理员】，并通知超级管理员补充有效管理员。
- **AC-09** — WHILE 空间处于【待配置管理员】状态, THE SYSTEM SHALL 限制新增授权及其他需要管理员确认的操作（含需管理员审批的上传等流程）；已有成员的浏览、检索、问答不受影响。
- **AC-10** — THE SYSTEM SHALL 在任何情况下不把超级管理员自动写为空间管理员或审批人。
- **AC-11** — WHEN 超管为待配置空间补配有效管理员, THE SYSTEM SHALL 解除【待配置管理员】状态并恢复全部受限操作。

### 2.4 超级管理员前台隐藏（适用全部知识空间）

- **AC-12** — THE SYSTEM SHALL 在全部知识空间的前台成员列表、管理员信息、权限详情、人数统计及授权候选人接口中隐藏超级管理员的隐式治理身份；人数统计与成员列表必须一致。
- **AC-13** — THE SYSTEM SHALL 允许超管基于平台级治理权限查看、进入全部部门知识空间并配置 / 更换空间管理员；该能力不依赖、也不产生空间成员 / 权限关系。
- **AC-14** — WHERE 超级管理员被**显式配置**为某空间的空间管理员或成员, THE SYSTEM SHALL 正常展示该显式身份（隐藏规则仅针对隐式治理身份）。

### 2.5 部门管理员自动同步下线

- **AC-15** — THE SYSTEM SHALL 不再因部门管理员任免、人员调岗、SSO 组织同步、账号删除而自动授予或回收部门知识空间的管理权限；部门空间管理权限的唯一来源为超管显式配置。

### 2.6 存量迁移（一次性）

- **AC-16** — WHEN 执行存量迁移, THE SYSTEM SHALL 对每个已有部门知识空间：恰好存在一名有效管理员时沿用该用户为空间管理员；存在零名或多名时标记为【待配置管理员】，待超管一次性修复。
- **AC-17** — WHEN 执行存量迁移, THE SYSTEM SHALL 将存量「部门管理员自动同步」产生的管理员成员按 AC-16 归一：未被选中沿用者按 AC-07 规则回退或移出；同时清除超管作为创建者遗留的前台身份（成员关系与权限关系），审计记录保留。

## 3. 边界情况

1. **管理员不要求属于该部门** — 空间管理员的资格条件仅为「同企业 + 账号正常启用」，不要求属于绑定部门（PRD 截图中搜索范围为企业内部用户）。
2. **并发更换管理员** — 两个超管同时更换同一空间管理员时，以后提交者为准或后者失败，但任何交错下不得出现零 / 多管理员的落库状态（AC-05/06 的并发面）。
3. **待配置期间的在途审批** — 空间进入待配置时,已流转到空间管理员节点的在途审批任务的处置口径 → **待确认**（候选：挂起并在补配管理员后转交新管理员 / 直接终止并通知发起人）。实现策略见 design.md §5。
4. **原管理员的成员身份回退**（AC-07）— 「被配置为管理员前已是成员」的判定与回退细节见 design.md；对外行为：不凭空剥夺其原有的普通访问权限，也不遗留管理权限。
5. **空间被隐藏（is_hidden）期间管理员失效** — 仍然打【待配置管理员】标记并通知；恢复显示后状态可见。
6. **管理员用户在同企业内调动部门** — 不影响其空间管理员身份（口径同边界-1）。
7. **超管账号本身停用** — 与本需求无耦合；若该超管同时是某空间的显式管理员，走 AC-08。
