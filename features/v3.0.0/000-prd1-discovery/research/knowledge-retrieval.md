# knowledge-retrieval

## summary
工作台检索的双层过滤（F029）在代码中真实存在且已服务三条调用链：索引层预过滤由 KnowledgeFileVisibilityService.build_index_prefilter 下推 Milvus expr/ES filter，结果层由 post_filter_visible_files 按 view_file 有效权限批量兜底。旧 v2 开放 API 的 aretrieve_chunks（/api/v2/filelib/retrieve）确证只做库级一次校验、无文件级过滤（其端点注释声称有 view_file 过滤，与实现不符），与 PRD 禁令一致。双层路径可用任意 key 解析身份驱动（request=None + UserPayload.init_login_user + set_current_tenant_id 均有生产先例），但当前权限引擎失败语义是「静默降级为缩小集/空集」而非 PRD NFR-1.4 要求的「明确错误态」，且仓库内只有 MCP 客户端、没有 MCP Server——严格 fail-closed 调用面与 MCP 服务端均需新建。

- Milvus+ES 双路召回与 RRF 融合原样复用：KnowledgeRag.init_knowledge_milvus_vectorstore/init_knowledge_es_vectorstore（knowledge_rag.py:112/:130）+ KnowledgeRetrieverTool（tool/domain/langchain/knowledge.py:34）；索引层预过滤经 search_kwargs expr/filter 注入的机制无需改动

## gaps
- MCP Server 侧全新建：仓库只有 MCP 客户端（mcp_manage/ 是 ClientManager 消费外部工具），无任何 MCP 服务端；个人 API key 鉴权、scope 过滤、六类工具面均为新建
- 无会话、跨库、跨 type 的『纯检索服务』：chat_folder 与 MessageSession 耦合且单空间，_retrieve_and_filter 是聊天服务私有方法；需抽出可被 MCP/SDK 调用的检索门面，把 F029 双层过滤应用到多库（含 type=0 文档知识库与 type=3 知识空间），替代（或改造）aretrieve_chunks 的弱分支 _aretrieve_chunks_for_kb/_aretrieve_chunks_for_knowledge_base
- 严格 fail-closed 调用面：list_accessible_ids/check/post_filter_visible_files 三处现全是静默降级（fallback scopes、owner 兜底、丢文件），需新增 strict 模式——权限引擎（FGA/缓存）失败即 raise 明确错误码，绝不静默缩集；这是 PRD 验收 9/GOV-05 验收 7 的硬前提，现有代码无一处满足
- 『声明白名单 ∩ 用户可见范围』的声明层收窄逻辑：现有任何路径都没有『应用声明白名单』概念，需在检索门面入口新增白名单校验（未声明库直接拒绝，即使用户本人有权限）
- type=0 文档知识库的文件级过滤能力：现权限模型只有库级（ensure_knowledge_read_async），无 view_file/lineage 概念；若 PRD『含文件级权限』覆盖 type=0 则是权限模型级新建
- 修正 filelib.py:635 的失实注释，并按开放 API PRD 附录 B 对 POST /filelib/retrieve 做参数收口/SAK 化改造（resolve_operator 的裸 user_id 通道需替换为委托准入）

## risks
- C4/一致性风险：MCP 检索若绕开 _get_child_item_effective_permission_ids 这一与列表 UI 同源的 primitive（INV-6），会破坏 PRD 验收 8『与工作台检索集合相等』；且工作台内部两条路径本身强度不一致（chat_folder 有索引层预过滤，workstation queryChunksFromDB 没有），『同一条双层过滤路径』需先指定锚点
- C3 租户上下文：MCP/SDK 请求不走 HTTP middleware，必须手动 set_current_tenant_id（resolve_operator 模式），漏掉即 NoTenantContextError 或跨租户读；子租户 IN-list 陷阱（memory：租户过滤只拦 SELECT）同样适用
- fail-closed 语义与现有降级哲学冲突：check 曾是硬 fail-closed 后被刻意改成 owner 兜底（permission_service.py:194-200 注释），strict 模式若全局生效会回退这次修复，必须做成调用面隔离而非全局翻转
- admin 短路放大面：list_accessible_ids 对 admin 返回 None（不过滤）、post_filter 对 admin 短路——个人 key 解析出管理员身份则 MCP 检索=全量库全量文件；须复用开放 API PRD 的『禁代表 super_admin/tenant_admin』准入，否则 key 泄露=全租户知识外泄
- 性能：build_index_prefilter 每次调 list_accessible_ids 列举全租户 can_read knowledge_file（memory：ListObjects 曾被禁用/无缓存×2，F037 优化在途），MCP 高频检索会放大；缓存则引入『撤销后陈旧窗口』与 fail-closed 判定的交互
- 术语映射陷阱：开放 API PRD 附录 B 声明 FGA 关系模型里不存在 view_file/view_space（实为 visible/can_read），代码中 view_file 是 effective permission id——spec/design 必须按代码事实写，避免照 PRD 字面造出不存在的 relation
- 文件级过滤只在结果层是概率兜底：strategy=none（双侧过大）时索引层不过滤、全靠 post_filter，两轮扩量后仍可能返回空（可见文件排名靠后被截断）——MCP 验收『集合相等』在该策略下与工作台一致，但需在测试样本中覆盖
