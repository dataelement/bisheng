# BiSheng 3.1.0-beta1 知识迁移材料与备份职责

2026-11-19 按用户确认调整：DBA 完成一致备份并通知升级负责人即可；脚本不接收、上传、封装或验证 DBA 备份证明。此前要求手工准备 manifest、生成 `f118-materials.json` 和 `f118-inputs.json` 的操作已取消，不再执行旧生成片段。

## 升级人员的操作

使用与服务一致的配置，在维护窗口按[升级指南](v3.1.0-beta1.md)完成任务收尾、停服、一致备份、数据库结构升级及历史准备后，直接执行第六阶段命令：

```bash
python scripts/unify_knowledge_spaces.py --run-id upgrade-310b1-20261119 --environment 实际环境标识
python scripts/unify_knowledge_spaces.py --run-id upgrade-310b1-20261119 --environment 实际环境标识 --apply --operator-id 实际操作者ID
```

`--run-id` 由升级人员指定，整次迁移及恢复保持同一个值；`--environment` 必须与当前权限发布的环境相同，实际存储连接由服务配置决定。预览默认只读，正式执行必须显式 `--apply`。实际结构、全租户业务数据、权限、引用及最终 Coverage 检查保留。

## 需要保留的迁移材料

- DBA 全量备份由 DBA/运维保管，完整性和可恢复性由其负责，脚本不宣称验证通过。
- 第五阶段生成的 `f118-history.json`、相邻事件日志和实际生成的选中行/物理内容备份继续保留，用于历史修复及同计划恢复；不由全量备份通知代替。
- 第六阶段的业务/权限/引用快照、转换计划和哈希由脚本写入 MinIO，Run 台账及检查点写入数据库；它们是迁移自身的恢复依据，不能删除或替换。
- 新 Run 的冻结 metadata 明确记录 `external_material_policy=not_required`，`backup_ref/schema_ref` 为空；不伪造备份、结构材料或校验和。

## 旧 Run 与断点恢复

已冻结 Run 使用原 Run、环境、writer 及操作者，加 `--apply --resume` 恢复。脚本从经原哈希校验的冻结计划读取历史字段，无需重新提供 DBA 描述符或本地输入文件，不重写旧快照。旧 Run 的租户集合、业务/权限事实、计划哈希及检查点仍须通过原有检查；外部备份/schema 证明对象不再是读取前置。

旧 `--backup-ref/--schema-ref` 参数仅为已有冻结 Run 保留兼容断言，显式提供时必须与原字段一致；新 Run 拒绝这些参数。不要补造描述符、换 Run 或删除台账来处理恢复冲突。冻结前失败不使用 `--resume`；具体判断与命令见升级指南第六阶段。
