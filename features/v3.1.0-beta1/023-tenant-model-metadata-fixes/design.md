# Design: 子租户视图与文件元数据修复

## 1. 概述

基于用户已确认计划及 33bcadaa3e。角色展示由 role 应用接口提供，组织模块只传已授权成员集合；模型候选复用 LLM 可见服务解析，元数据复用现有 SPACE 加工与值写入接口。遵守 constitution C1/C2/C3/C4/C5/C7/C8。

## 2. 当前代码

成员列表对 UserRole 与 Role 在当前租户内联查，漏掉 Root 共享定义；工具修复已在分支，116 仍使用构造器别名。助手配置读取正确，但候选直接 DAO 查询过滤共享 Root 模型。共享模型行的更新状态按钮未按只读属性收敛。文件元数据只展示已有字段且均为文本输入，缺少创建字段。

## 3. 方案与取舍

- role 提供展示专用读取，复用有效角色的绑定、定义及部门规则，不修改登录/权限解析；失效绑定只作为超管诊断返回。拒绝放开组织联查的全局租户过滤，否则无效绑定会被当作有效权限。
- LLM 只读取服务端已确认可见服务下、配置指定的模型；不在前端拼全部模型，不绕过配置引用校验。
- 更新状态沿用服务端管理目标与共享只读规则，子租户禁止 Root 状态写入；不新增无状态连接测试能力。
- 元数据在单一弹窗内切换已有字段/新建表单，复用旧类型编辑方式及现有组件；新字段使用 SPACE schema job 完成后刷新字段，不恢复旧直接写入。未来若需文件独立字段应另定契约。

## 4. 数据流、字段与模块

成员列表授权/分页 → role 应用展示读取 → roles（有效角色）及可选 role_binding_issues。异常项含 binding_id、role_id、role_name（可为空）、reason；只给当前管理范围的超管。普通用户与租户管理员响应不带异常详情。

助手默认配置严格读取 → 可见服务集合 → 配置模型交集 → 原提供方分组响应；接口形状不变。verify 先确认当前管理目标可以写实际模型/服务，禁止先发模型调用再拒绝。

文件弹窗读取 file info 和 SPACE schema；字段创建沿用 metadata_schema_change 的 precheck/confirm/job 幂等链；任务成功后刷新 schema；值写入继续 PUT /knowledge/file/user_metadata 的原形状。以 scope/space/file/本次挂载隔离异步生命周期。

### 实现锚点与运行语义

- `role/application/member_role_display.py` 接收已授权且至多 100 人的分页；`user/application/policy_bindings.py` 提供确切用户批量事实，绑定和定义不会被当前子租户物理过滤。foreign-home 附属成员不返回其私有角色。复用 `eligible_role_definition`、`eligible_role` 和主部门拓扑验证；绑定错误逐项诊断，缺失定义不会掩盖其他合法角色。此展示读取不是严格登录策略，不能作为授权依据；登录策略遇缺失定义仍失败关闭。
- `DepartmentService.aget_members` 在原目录授权、分页后，切换到目录的业务范围进行展示读取。仅可信全局超管身份启用异常字段；租户管理员和普通部门管理员不包含该字段。停用用户保留目录行但无有效角色。
- `LLMService.get_assistant_llm_list` 先严格读取当前助手配置，再用 `acollect_visible_servers(strict=True)` 解析合法提供方；只有配置中的模型才经确切 ID 读取，模型与提供方物理归属必须一致。原默认模型及默认服务置首逻辑保持，前端继续过滤下线项，已选不可用项保留显示。`ModelItem` 展示读取错误及重试，错误期间禁止切换候选。
- `verify_model_status` 在缓存失效、模型探测及状态写入之前检查实际提供方是否属于当前目标。合法可见但共享只读返回既有 19801；不可见或归属不一致保持 404，不能用超管身份跳过所选管理目标。
- `useSpaceMetadataSchema` 是空间元数据面板及文件编辑器共用的 precheck/confirm/job owner。请求结果不确定时保留原冻结请求和幂等键，只允许重试相同操作；明确业务拒绝清除该请求，允许修正草稿。
- `SpaceFileMetadataDialog` 按 scope/space/file 挂载键隔离生命周期；在单一弹窗内切换值、已有字段、新建字段视图。schema 任务成功且刷新读到字段之后才给当前文件新增空值，不因确认请求已接收就提前赋值。文件保存失败不清草稿；组件退役后的响应不触发保存回调或关闭新的弹窗。

重新评估触发条件：若需给普通管理员开放历史诊断，应单独定义信息边界；若需子租户更新共享模型状态，应明确共享状态归属；若需取消失败源任务，应设计带副作用清理的取消协议，不能借展示修复绕过保护。

## 5. 已知坑

| 事实 | 不处理的后果 | 处理 |
| --- | --- | --- |
| 合法绑定和角色定义可分属子租户与 Root | 普通联查漏掉角色 | role owner 按确切绑定读取定义 |
| 历史绑定可能仍在 Root，但用户主属已改变 | 当作有效角色会误导或扩权 | 只读诊断标记，禁止迁移 |
| 创建字段是空间级异步操作 | 创建请求返回不代表字段可赋值 | 等待任务成功后刷新 schema |
| 失败的出站任务也保护源空间 | 无源空间本地任务却仍无法删除 | 报告关联目标任务，不清保护 |

## 6. 契约与依赖

只有成员响应新增可选异常字段；其余 API、错误码、数据库和授权数据不变。复用 user policy facts、department business scope、role effective policy、LLM 可见集合及知识加工应用接口。不跨模块导入业务 DAO。
