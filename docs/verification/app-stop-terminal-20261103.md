## 根因与实现

原助手将生成任务和停止任务以 WebSocket 的同一 trace ID 提交到任务池。停止路径虽然截掉最后一个 task ID，任务池仍按 key 取消整组任务，包含停止处理本身。遇到会挂起的发送操作时，停止任务可能在发送持久化 ID、结束确认之前被取消。取消后的生成任务与停止任务还各自负责发送 close；若模型调用吞掉取消并返回结果，原正常路径继续保存完整回答。

当前每个助手连接持有自身的生成 Task。停止请求在接收路径等待这些任务完成，取消范围以连接拥有的 Task 为准。生成任务统一负责取消收尾：

1. 从本轮缓冲提取正文和思考，各自保存内容及 `break_answer`。
2. 发出已保存回答的消息 ID。
3. 发出一次 `processing/close`，前端沿现有逻辑恢复输入。

模型调用返回后检查 Task 的取消请求，取消分支负责保存截断终态。正常保存和结束确认阶段继续完成，重复停止沿用同一次收尾。已记录问题但首个 token 尚未到达时保存空的停止回答；初始化阶段取消则完成收尾，历史仅包含已接受的问题。停止历史保存失败会发出既有业务错误，再完成输入状态收尾。

数据结构、停止请求格式和历史 API 沿用既有契约。SQL 写入继续使用现有 ChatMessageDao，数据库字段保持原定义。运行时改动集中在 `common/chat/client.py`；Ruff 按项目要求格式化该文件。工作流执行引擎保持原实现。
