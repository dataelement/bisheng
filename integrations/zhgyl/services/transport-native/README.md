# 运输原生 API 接入

2026-11-19。当前 D 环境已接通并实测；本轮未修改或重启平台后端。**现用底座的干净镜像存在原生 API 参数解析缺陷，跨干净环境迁移尚未通过，不能把当前 D 的成功当成任意版本可直接导入。**

## 组成与配置

- `service.py`：独立运输业务服务，仅依赖 Python 标准库。`engine/` 复用本轮从运行中的运输 Skill 下载的业务代码；费用、共享覆盖和推荐算法未重写。
- `openapi.json`：在平台“构建 → 工具与技能 → API工具”导入。操作为 `transport_execute`，模型参数仅两个字符串 `request_json`、`context_id`。工具密钥由管理员放在鉴权配置中，不能放进 Schema、Skill、模型参数或交付包。
- `SKILL.md`：原生 API 版 Skill，ID 名称为 `transport-native-api`。工具实际名称和数字 ID 由平台分配，通过操作描述/参数识别，不能照抄当前 D 的数字 ID。
- 平台前台可选工具范围还需要加入该 API 工具组，默认不全局勾选。在普通原生 Chat 选择本 Skill 和该 API 即可使用；当前 D 的运输专属入口已自动选中这两项，不再选择代码执行器或旧运输 Skill。

## 业务服务运行条件

Python 3.10+；历史 API 遵循现行运输合同，具备完整分页和关联账单成员。当前演示环境使用已存在的私网历史 API `http://bs-d-transport-api:8080`，没有把业务服务发布到公网。

通过受控环境提供 `TRANSPORT_API_ORIGIN`、`TRANSPORT_MOCK_TOKEN`，创建仅业务服务账号可读写的状态目录，然后运行：

```sh
python service.py --state /your/private/state --bind 127.0.0.1 --port 8080
```

容器网络内服务可按实际受控网络绑定 `0.0.0.0`，无需发布主机端口。将 OpenAPI 的 `servers.url` 配成平台后端能访问的业务服务地址。当前历史取数器仅接受 loopback 或合同中声明的私网 origin；对接其他数据中台地址时，在独立业务服务侧核对并配置白名单和数据合同，不能让模型传任意 URL。

当前演示用同一受控样例密钥鉴权业务服务和历史 API，平台 API Key/header 配置为 `Authorization: Bearer <受控密钥>`。换环境应配置自己的密钥，不复制 D 的私有配置。当前状态引用是不可猜测的能力标识，配合静态服务密钥使用；未验证多用户身份/行级隔离，不作为生产鉴权方案。

## 2026-11-26 范围收口（本地与 3.0.2 候选）

历史查询不自动获取推荐池或附推荐；只有明确新货推荐请求走 inquiry。当前输出和公开参数撤回历史报价时间、运费开票日及开票日筛选/排序。推荐排序移除隐藏人民币中位数依赖。旧 fixture 原列仅用于读取和完整性校验，旧排序恢复来源顺序；依赖撤回条件的历史状态须重新查询。主分单精确匹配、毛重与包装尺寸、费用单去重和共享覆盖继续保留。本轮未发布 D、推送或部署。

## F01 与失败结束

### 2026-11-26 本地主分单查账

历史查询新增 `master_numbers`。与 `house_numbers` 同时传入时，先按主单定位，再要求同一行的分单号匹配。只给主单号时返回候选费用单并标记分单未确认。组合无结果时保留未核实状态。金额按费用单原币总额展示，覆盖只取该费用单实际成员。详情继续使用同次查询的稳定费用引用。

新货改用 `gross_weight_kg`，也接收带单位的 `gross_weight`。历史明细的毛重为可选来源字段。原联调快照只有净重时，毛重显示未提供，不能进入重量全匹配。包装数量暂不参与匹配。旧询价口径需重新查询。回复展示原币费用或按原币分组的历史范围，隐藏人民币开票金额、货值和运费占比。推荐同分时按服务商与运输方式名称稳定排序，不再依赖人民币金额。

本地运行用 `python3 test_waybill.py -v`。原始 Excel 关联核对与测试记录详见[主分单精确关联](../../验证/运输主分单精确关联-20261126/README.md)。

2026-11-19 已同步到 D 的运输固定入口。新版读取当前 Chat 中已完成的原生运输工具回执，提取上下文和查询编号，随详情请求一起提交。用户直接问「查看 F01 详情」即可，首轮模型输出可以只有纯文本 F01。入口由 `build_transport_entry.py` 从已核对的工作台前端构建。[无链接 F01 隔离验收](../../验证/平台原生API接入-20261119/clean-platform/f01-reference/README.md)及[演示发布实测](../../验证/平台原生API接入-20261119/demo-f01-release/README.md)。

首次查询 `context_id` 为空，服务为该查询创建独立状态。F01 的 Markdown 链接携带不在页面正文显示的上下文标识，通用 Chat 可用它作为兼容引用。运输固定入口点击 F01 只填入详情问法，仍由用户发送。

没有可用上下文、旧引用、未知 F 编号、工具缺失、鉴权错误、连接失败、服务超时与参数错误均必须明确结束；不能当成“没有历史”或自动换工具。业务调用只尝试一次。业务进程上限 25 秒，原生 HTTP 客户端当前约 30 秒，模型整理/调度还会额外用时；当前观察到超时 Chat 约 47 秒结束，不是正式 SLA。前端资源准备设 12 秒报错上限。

状态最多 256 个，上下文有效期 24 小时，满额或过期明确失败；当前演示未实现自动清理/持久存储扩容。容器重启保留挂载状态目录，不能删除状态冒充无历史。

## 换环境的必要检查

1. 独立业务服务可达，鉴权正确；原生 API 工具可见，并进入前台可选工具配置。
2. 实际模型能看到 `request_json` 和 `context_id` 两个字符串参数。**工具登记、OpenAPI 导入和工具 HTTP 测试成功均不能替代这个检查。**
3. 原生 Chat 真实走独立账单、共享账单、F01 续问和缺工具报错；不要绑定代码执行器或导入旧 `transport-history` 掩盖问题。
4. 如果平台原生 Schema 仍丢失参数，应停止并交由平台正式版本修复/升级解决；本方案不提供或自动应用 BISHENG 后端补丁，不切换为 MCP 绕过本轮要求。

干净镜像证据见 `../../验证/平台原生API接入-20261119/clean-image-native-schema.json`：未加载运行挂载的现用镜像，`required` 有参数名但 `properties` 为空，参数被错误写在 Schema 根部。当前 D 已有历史修复，本轮保持其文件哈希不变。**因此当前交付只对当前 D 原生接入验收通过，干净镜像迁移仍有平台版本阻塞。**
