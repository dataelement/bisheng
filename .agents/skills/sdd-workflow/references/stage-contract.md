# 阶段交接规则

这套通用流程支持不同项目与技术栈。实际项目约束、工具能力和用户当前要求决定执行细节，沿用已有授权及偏好。本文提供默认协作方式，不替用户扩大任务或变更已确认规则。

## 读取与协作

按需读取当前阶段及直接需要的引用，不把整套 skills 和全仓文档一次装入上下文。
相对链接以当前 SKILL.md 所在目录解析，不以 shell 的工作目录解析。引用 skill 表示读取并应用其指引，不假设存在统一的 slash-command API。
本套件依赖自身各阶段、澄清时的 grilling 和按需领域建模的 domain-modeling；不因参考来源自动调用旧项目 skills。
使用宿主实际可用、获准的文件、终端、测试和协作能力；原生 hooks 的存在需核实，不能假设别的工具配置会自动生效。

生成业务文档、涉及模块／实体／重要抽象命名或发现语义冲突时，按[领域语言与命名约定](domain-language.md) 沿用同一术语基线及本次已确认增量。只有新概念或未解冲突才展开建模；已有定义明确的简单 Bug 不增加词典、访谈或 ADR。

## 路径与人工节点

- 新功能及功能扩展走完整 SDD。
- 简单 Bug 五项准入均满足时，直接修复和针对性开发验证，按范围交接独立验收。
- 信息不足先自主调查；已发现复杂影响或重大取舍时，和用户决定必要阶段切入。
- 需求闭环和设计完成分别由用户确认。执行中推翻已确认内容或出现高风险取舍时重新对齐。
- 沉默、文件存在、作者写下“已确认”或勾选任务本身不构成用户确认。复用与当前内容一致的真实确认记录，无需重复询问。
- 确认规则用于任务的需求与设计决策，不能把当前明确授权的执行再次当作未授权事项反复询问。
- 普通实施细节与已授权的可逆工作自主推进。必要决策待答时，可以继续不依赖该答案的工作。

## 岗位与测试代码归属

研发负责应用代码，以及各前后端项目自身 test/ 下的开发测试；测试工程师负责独立验收工程中的 UI、真实集成和 E2E 代码及验收结论。
本次新增的后端测试放后端项目/test/，前端测试放对应前端子项目/test/，由各项目配置发现和执行。检查已有发现配置并做必要的范围内兼容，不擅自搬迁整仓历史测试。
验收代码不放入这些研发 test/ 目录。独立验收工程的真实位置由测试岗位或当前任务指定；路径未知时可准备场景和提测材料，写脚本前明确目标工程，不猜测写回应用项目。
可以共享需求编号、业务预期、接口契约和数据规范；不以共享开发测试代码、mock 或私有 fixture 代替验收独立性。具体协作见[岗位协作与提测规则](qa-handoff.md)。

研发入口的默认终点是“研发完成，待独立验收”。输出提测材料后结束，不自动调用或等待 sdd-acceptance，不自动发起远端验收 CI。独立验收由测试工程师显式发起；AI 可以辅助该岗位的用例、脚本、执行和报告，不能冒充测试工程师已签字。

## 阶段依据与记录

各阶段说明：输入及其依据、实际完成内容、结果、必要证据、未决事项与下一步。
事实、用户决定、AI 建议和未知分开记录；工作区源码不等于生产事实。

首次落盘、接续或位置变化时，读取[产物存放与维护约定](artifact-storage.md)，统一确定项目根目录、稳定特性标识、主模块、版本及有效产物位置，各阶段持续沿用。用户指定位置及项目现有约定优先；没有约定时默认使用 `features/v<版本>/<主模块>/<编号>-<特性名>/`，版本未定使用 `_unplanned`。旧平铺结构、`.sdd/` 或分散的有效来源可登记接续，迁移按实际需要处理。需求定稿、技术设计和测试用例文档均交付 HTML。
生成或更新这三个文档时读取 [HTML 交付约定](html-delivery.md)。已有 Markdown、Word 等材料可作输入，不维持内容各自独立更新的 Markdown／HTML 双份定稿。不覆盖已有同名无关内容。独立需求评审可先在对话分析；准备完整需求确认时提供可审阅 HTML，确认后将其作为闭环依据。简单 Bug 仍可用简短记录承载，不因格式要求强制补一整套 PRD。

接续记录保留：任务与范围、当前阶段、各产物位置、需求及设计的确认依据、相关术语基线与概念增量、已完成工作、实际验证与代码对应关系、未决问题和下一步。已有正文用来源引用，候选定义和假设不在摘要中变成已确认事实。
优先复用项目已有登记；需要新载体时使用产物约定中的 `feature.yaml` 模板。登记维护标识、归属、版本、产物位置和岗位状态，接续与提测材料引用该来源。已交付基线、模块当前知识及各次运行证据按约定维护，状态和正文避免多处独立更新。
用 Git 提交及相关工作区改动摘要／指纹，或无 Git 项目的相关文件指纹，说明证据对应内容。不要只记一个会随改动失效的“通过”。

## 完成与证据

“产物就绪”“专业检查完成”“用户已经确认”和“执行验证通过”分别判断。
需求和设计在规定确认后才能交接依赖工作；测试用例定义完成不代表已经执行，计划完成不代表实现完成。

## 测试策略与执行阶段

用例设计与执行分开。需求闭环后两岗位可以分别设计开发和验收用例；契约明确后测试工程师可以在独立工程准备 UI／E2E 脚本。研发可以交付场景建议，但不把验收脚本写进应用 test/，也不因准备工作触发执行。

| 阶段 | 执行安排 |
|---|---|
| 需求、设计与用例准备 | 定义场景、预期、数据和执行前提；不运行 UI 或真实环境验证 |
| 开发、局部修复与代码审核 | 优先使用 mock／fake／stub 或隔离环境，执行本次需要的单元、接口、功能和契约测试，并完成适用静态检查 |
| 测试工程师独立发起的验收 | 在指定验收工程和可用的 CI／共享环境验证真实依赖、UI 与关键端到端链路，不属于研发入口自动执行的后续步骤 |

开发验证的范围由需求和风险决定，“运行成本低”不是把测试减少为 lint、语法或少量单测的理由。应在可隔离环境覆盖需要的正常、异常、权限、状态变化和副作用。
保留真实被测代码，优先替换昂贵、不稳定或难部署的外部边界；不能把正在验证的业务、权限或接口处理 mock 成固定成功。快速、确定性且易用的真实本地组件可以复用，不为 mock 而 mock。
设计隔离边界、接口和功能测试及真实验证缺口时，按需读取[测试环境与证据策略](../../sdd-test-cases/references/test-strategy.md)。

不要求个人电脑复刻线上整套部署，不在开发期安装或启动完整真实环境执行端到端测试。进程内接口客户端、轻量 mock 服务及必要本地隔离测试不属于真实部署 E2E，应按需求执行。昂贵的真实依赖集成和 E2E 安排到开发完成后的验收。
真实验收环境优先复用 CI 或共享环境；按测试目标核对依赖类型与版本、关键配置、权限、协议和拓扑等一致性，记录差异。容量和规模相关结论另行验证，不要求每位开发者本机具备线上硬件规模。
UI 的执行继续沿用已明确的单独约定：当前开发期不运行组件 UI、浏览器、截图或手工页面验收；mock 后端的 UI 也不因本次放宽后端测试而自动放行。用户明确调整 UI 安排时再更新。
执行命令前查看实际脚本和依赖，选择符合阶段安排的单元、接口和功能测试子集；混入后置测试的聚合入口不能直接执行。新增 hooks、watch 或 CI 配置同样遵守该安排。

每个用例记录执行阶段、测试环境、真实保留与替换的边界、覆盖行为及仍需真实验证的结论。后置用例在开发期记为“待验收／未执行”，不记为通过、不适用或已执行跳过。
代码、本阶段需要的单元／接口／功能测试及适用检查完成后，可以标记实现就绪；必要代码审核与交接完成后标记“研发完成，待独立验收”并结束研发流程。后置用例不反向要求开发期部署全栈，已证实的代码缺陷和必要开发测试缺失仍需处理。
验收缺环境时保持相关行为未验证，记录测试岗位阻塞；不把它转成要求研发在本机部署全栈或等待的自动任务。mock 测试通过不能冒充真实兼容性或整体验收通过。验收发现缺陷后交研发修复并完成自身回归，再以新版本交接测试工程师复测；不自动把两岗位执行串回同一次本地开发等待。
沿用已确认的测试阶段安排，不反复询问是否提前执行；用户明确改变当前任务安排时按其新要求处理。

验证结论采用：

| 状态 | 含义 |
|---|---|
| 通过 | 适用标准满足，有与声明相称的实际依据 |
| 不通过 | 已发现未满足标准的具体问题 |
| 未验证 | 必要证据不足、尚未执行或环境缺失 |
| 不适用 | 与当前范围无关，简述理由即可 |

记录执行方式、环境、真实与模拟范围、用例及业务断言、失败／跳过和必要产物。dry-run、静态成功、空测试和全跳过不能单独证明功能通过。
环境缺失不自动变成人工审批，也不能用假通过代替。报告缺口，继续可独立推进的工作。
需求变化检查关联设计和用例；设计变化检查关联实现；代码变化检查验证证据。只让受影响部分失效，保留仍然有效的工作。

## 审核与成本

作者自查用于发现问题，不能作为唯一放行依据。用需求与契约中独立确定的预期、实际执行结果及适当独立复核进行交叉验证。
简单 Bug 可以通过聚焦检查与实际证据完成；高风险工作加强独立审核及必要人工判断。没有独立评审环境时，明确独立性限制。
安全、并发、重试和性能检查按相关风险选择，并遵守上面的阶段安排。优先用隔离环境验证可控行为，真实存储并发、部署兼容性和容量结论保留对应真实验证。复用已有工具、fixture 和有效用例，不机械安装重型服务或追求统一覆盖率。
修复后的复核按影响范围安排；同类失败反复出现或修改范围持续扩大时，报告实际问题和选择，与用户决定下一步。

用户要求复盘或真实失败反复出现时，按[使用反馈与维护](maintenance-feedback.md) 提出有证据的最小改进。普通任务不自动增加复盘、环境整治或后台代理；工具成本只在能实际取得时记录，不用估算值宣称固定节省比例。

## 交付边界

准确报告已完成范围、验证结果、真实性边界和剩余风险。实现就绪、审核通过、验收完成分别陈述。
本流程不把实现授权自动扩展为提交、推送、合并、部署或向他人发消息；按用户的实际授权处理这些动作。
