**REVISE — 需求覆盖和结构克制基本合理，但部门组织变更的生产者闭环、DSH版本桥接及重叠政策操作的恢复协议尚不足以支撑当前承诺。**

以下 `design.md` 均指 `features/v3.1.0-beta1/009-managed-tenant-consistency/design.md`。本次仅作只读检查，未修改文件或运行测试。

### Blocker

**B1 — 部门组织变更缺少覆盖全部受影响人员的持久生产者协议。**\
**维度：4、6。**

- **锚点：** `design.md:118–127` 定义按人政策事务；`:274` 将生产者概括为成员退出、主属变更、归档等，没有明确部门树移动、挂载变化如何发现并封闭全部受影响人员。`spec.md:59` 的 AC-09 明确要求组织移动后失去最后支持的绑定被终止。
- **已核实仓库：** `src/backend/bisheng/department/domain/services/department_service.py:1604–1621` 先提交子树路径变化，`:1638–1661` 随后仅以 best-effort 调用 `sync_subtree_primary_users`；`src/backend/bisheng/tenant/domain/services/user_tenant_sync_service.py:197–202` 明确只枚举 `is_primary=True` 的成员。这不能覆盖主属不变、但兼属部门被移出角色作用域的人员。
- **影响：** 新E可能暂时过滤掉不合法绑定，但旧绑定没有被持久终止；部门之后移回时可隐式复活，违反 AC-09/AC-10 的终止语义。进程在组织提交后退出，也没有已明确记录的全部人员政策恢复意图。
- **建议方向：** 在现有部门变更操作上增加明确的政策影响步骤：枚举受影响子树内全部相关成员，包含兼属成员；在发布组织事实前持久记录影响集合或可恢复扫描边界，定义封闭、逐人终止及完成条件。直接命名需要适配的 move/archive/mount 和组织同步生产者，不必另建通用引擎。

**B2 — “复用DSH版本化结算”尚无能够表达普通角色变化的版本和门禁协议。**\
**维度：4、6、7。**

- **锚点：** `design.md:52`、`:123–127`、`:138–139` 承诺先关闭旧gate，再按新政策代次传播并确认；`:29` 仅命名拟新增 `dsh.application.policy_refresh`，没有定义其版本、所有权和发布契约。
- **已核实仓库：** 活跃路径 `src/backend/bisheng/dsh/runtime.py:18–28` 使用 `UnifiedPolicyRepository.effective`。后者在 `dsh/domain/repositories/unified_policy.py:193–205` 从角色计算额度，却将每个结果的 `version` 设为 `ModelVisibility.version`；`dsh/domain/schemas/model_policy.py:80–82` 再对这些版本求和。保持可见模型集合不变的角色额度变化可以完全不改变版本。另一方面，`dsh/infrastructure/quota_redis.py:291–311` 的现有安装接口要求单模型 `version == expected_version + 1`；`dsh/infrastructure/lua/policy.lua:1` 明确其所有权和版本属于单个 user/model 行。
- **影响：** 用户政策代次、统一策略快照版本和现有单模型direct版本不是同一合同。仅将新E接入读取，无法证明旧gate能被正确封闭、共享额度能被正确替换，以及重试不会错误解封另一操作。
- **建议方向：** 补充一个具体的DSH桥接协议，明确普通角色变化使用的持久版本、按人门禁所有权、完整模型集合与共享额度发布方式，以及与现有direct操作并发时的处理。明确从旧快照到新快照如何在保留已用量的情况下完成，而不是直接把用户政策代次传给现有单模型接口。

### Should-fix

**S1 — 多个角色政策操作共享用户时，缺少持久冲突处理顺序。**\
**维度：6。**

- **锚点：** `design.md:129` 规定已有用户操作时拒绝新操作；`:135` 规定角色进行中时普通E不可读；`:138–139` 允许本操作候选快照，并保留角色和用户标记直至传播完成。`:122` 的锁顺序只解决数据库事务内的锁，不解决跨事务持久标记。
- **影响：** 用户同时绑定角色A和B时，两者可分别预留角色操作。A取得用户操作后，计算最终政策可能因B进行中而失败；B又因A占有用户操作而不能推进。各自候选快照只解决本操作的标记，周期重试不会自行消除这个循环。
- **建议方向：** 选定一个最小的持久准入规则，例如对重叠政策操作规定确定性顺序，或在预留阶段将冲突操作排队；必须说明等待方不会阻挡当前操作完成所需的政策读取。补充A/B共享用户、相反扫描顺序及进程重启的交错过程。

**S2 — 部门管理目标解析与普通用户政策事实读取共用了不匹配的授权前置条件。**\
**维度：2、4。**

- **锚点：** `design.md:103` 的 `resolve_verified_department_scope(dept_id, actor)` 首先检查部门管理权限；`:107–108` 又要求普通用户E读取当前作用域事实；`:272` 表明E生产者调用department窄协议。设计没有给出普通成员可使用的另一事实读取接口。
- **影响：** 普通成员不具备部门管理权限。若E复用该resolver，会把合法作用域角色解析成政策不可用；若实现时绕过管理检查，则原接口的可信证明含义被破坏。
- **建议方向：** 区分管理写目标解析和受限政策事实读取。后者只接受已验证主体或内部受控请求，返回计算该主体资格所需的成员、祖先和边界版本；不要求主体具备部门管理资格，也不向调用者开放任意部门查询。
