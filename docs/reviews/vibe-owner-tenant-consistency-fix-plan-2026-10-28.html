服务账号租户一致性修复方案（简化版）

日期：2026-10-28（Asia/Taipei）｜状态：简化方案及38条AC规格已于2026-10-28获用户确认；设计已单独确认，代码/L1完成51/53，待真实E2E及最终合入门

1. 本次范围

按用户确认及本轮追加范围，做以下四项：

  1. 服务账号归属人的当前租户与服务账号租户不一致时，拒绝该服务账号的业务请求，明确返回“归属人租户与服务账号租户不一致”。 覆盖使用该账号密钥的业务接口，不再只限应用发布。
  2. 存量资源不迁移、不变更。 资源仍属于原租户；归属人切换租户后看不到旧租户资源是正常隔离行为。
  3. 服务账号管理页增加超管专属的租户选择。 用于查看、管理和在所选租户创建服务账号；用户已明确：不修改已有服务账号及其密钥的所属租户。
  4. 应用管理操作补调用者租户校验。 上线/停用/恢复/删除、元信息、日志/数据及配置管理不能因owner相同跨租户执行；原有入口权限与超管边界不扩大。

不新增资源迁移器，不恢复人员原租户，不新增人员迁移拦截、迁移作业或维护围栏。服务账号继续以自己的主体、原租户和授权范围调用；不会获得归属人的完整权限。

3. 统一业务请求校验

3.1 规则和错误

在服务账号业务身份准入处校验：

密钥有效、服务账号启用、密钥租户 = 服务账号租户
  → 查询该账号当前归属人的唯一有效租户
  → 归属人租户 = 服务账号租户：继续原scope、委托及业务权限检查
  → 不相等：拒绝业务请求，返回明确的租户不一致错误
  • 新错误使用统一错误码机制，文案为“归属人租户与服务账号租户不一致，请联系管理员在正确租户创建服务账号，或调整资源归属人。”具体编号在正式规格/设计时按注册表分配，本文不预占编号。
  • 归属人当前有效成员关系不存在或不唯一时，拒绝，并返回“无法确认归属人所属租户”类错误；不能随意取第一条或默认为根租户。
  • 查询故障返回鉴权依赖不可用，不冒充租户不一致。归属人禁用/删除的既有规则另按当前合同执行，不把“禁用”误判为“迁出租户”。
  • 不自动撤销旧密钥或停用服务账号。关系恢复一致后，仍有效的密钥可按原规则继续调用；归属人A→B→A不需要人工清除失配状态。
  • 管理员使用登录会话进行账号管理不受这个业务密钥闸门阻断，仍须满足超管/租户管理员权限。因此可以查看问题、按原规则改绑同租户归属人或显式停用。

3.2 最小实现边界

校验逻辑放在open_api公共业务准入链路，HTTP与MCP共用，不在各业务接口重复添加。

必须覆盖密钥缓存命中： 当前validate_bearer会缓存整个principal，单改resolve_service_account只在缓存未命中时生效。每次业务准入都要重新取得服务账号当前归属人及其有效租户进行核对，不能以旧principal里的owner或缓存TTL作为判断依据；账户改绑后亦不能继续使用旧owner。令牌哈希、有效期等原缓存可保留，不新增一致性状态表或第二套失配缓存。

MCP长连接按实际业务调用重新校验，不能只在建连时检查一次。若现有传输有仅握手鉴权的路径，应在每次工具调用的公共准入点补齐。流式调用已开始后不追溯撤销已执行动作；下一次业务调用必须检查当前关系。

本项只约束service_account主体，不扩展到个人PAT或独立的hosted_app运行凭据。已上线应用不会因为服务账号失配而自动停止；其运行期权限仍由原应用凭据与租户隔离控制。应用内部若使用失配服务账号密钥调用平台业务，同样会被拒绝。

3.3 发布链路的必要补充

新发布在公共准入即拒绝，不能创建应用、保存平台源码快照、投递发布任务或生成审批；HTTP临时接收文件与清理不算平台资源写入。

异步任务无法靠一次HTTP鉴权覆盖整个生命周期，保留三个必要复核点：

时点 检查与失败行为
Worker实际开始预检 核对发布记录冻结的归属人和租户；失配则失败，不改写为归属人的新租户
创建版本/审批前 再检查同一冻结关系；失配不创建新审批，临时产物按原流程清理
审批正式上线前 再检查冻结关系，且在登记待生效版本、数据库迁移、停旧实例、启动正式实例前拒绝；当前/待生效版本和路由保持原状，应用已停用而仅登记版本时同样先检查

已接收部署以冻结owner/tenant为准，不随服务账号后来改绑而换资源归属。审批已经通过但上线前失配时，审批决定留档，业务执行进入现有失败状态并给出原因；不把失败伪装成成功或自动驳回，也不自动重试到另一租户。预览等后续消费者按同一冻结关系拒绝新增执行，清理独立进行。

不为此改造所有人员迁移入口、引入跨模块租约或接收占位协议。本方案提供每个业务准入/执行阶段的校验，不承诺撤销阶段内已执行副作用；正式设计需明确各阶段开始与终结的位置。

4. 超管管理页租户选择

4.1 界面行为

  • 多租户模式下，只有全局超管看到“管理租户”选择器；租户管理员沿用自己的租户，单租户模式不展示切换。
  • 选择的是页面管理/创建范围，不是修改已有服务账号tenant_id。界面明确显示当前管理租户，列表、详情、密钥管理、资源授权和归属人候选保持同一范围。
  • 创建时必须是具体租户；账号与新密钥均属于该租户，只能选择该租户的合格归属人。切到租户60后创建的账号，未来新建资源写入60。
  • 切换成功后返回列表，清空旧详情、搜索结果、已选归属人及未提交表单，重新加载数据。切换中禁用全部服务账号管理写提交；迟到的旧租户响应不覆盖新列表。
  • 复用已有管理范围能力及现有组件样式，不新增UI库；新增文案同步zh-Hans/en/ja。

4.2 后端和已有能力复用

优先复用F019管理范围与useAdminScope，而不是新增账号迁租户API。service-accounts管理API已受该范围控制，新增工作重点是页面接入、候选查询和创建时的范围确认。

需要落实三个已有机制的边界：

  1. 根租户显式选1。 现有模型页把根租户选项映射到“无管理范围”，服务账号在无范围时可能按owner租户推导创建目标。此次不能直接照搬该映射：根租户管理必须固定到1，创建不得悄悄落到其他租户。
  2. F019是超管共享的管理范围。 该状态按管理员保存，会影响已有纳入中间件的其他管理页/标签页；不是人员租户迁移，也不是只存在于本页的局部变量。界面读取实际范围，切换后刷新相关管理缓存。全部服务账号管理写提交携带打开表单时的预期租户，后端与实际管理范围比较，不一致则拒绝并要求刷新，避免另一标签页切换后误建。这个字段用于范围一致性校验，不授予租户权限。
  3. 后端不能只依靠隐藏控件。 设置管理范围接口校验全局超管身份、目标租户存在且可用；普通管理员不能伪造范围跨租户。列表/详情/密钥/授权操作仍按实际范围与账号tenant_id匹配，不绕过已有权限检查。归属人候选必须真正限定到选定租户，不能仅显示提示文案。

本次不修改已有账号和密钥的tenant_id，不复制旧授权。创建新租户账号后，按实际需要签发新密钥、配置所需资源授权，再更新CLI或调用端的凭据。
