# Feature: Vibe 全操作权限动作统一与具体租户管理视角

> **规格已确认，修订设计已于2026-10-30单独确认；当前实施中，不是全部已交付。** 原 70 条 AC 已由用户确认，确认时全文 SHA-256：`f9feba32cc67bd812908f5a3d369ec942ede8955e15ca6206101c5a62305c45b`。随后用户明确共用接口维持原权限，并在了解 v1/v2 后要求“收敛统一一下”。本次据此新增 AC-71；用户在收敛稿评审后明确“按照建议修改”，进一步将 AC-57 收窄为旧绑定导入/升级/重绑退役，已有配置确认重建和新版本发布分别复用原条款。本轮只修改 AC-57，其余 70 条 AC 正文不变；当前共 71 条。该修订设计现已单独确认，任务和编码进行中，完整交付仍待后续验收。

**Feature**：F114 · **版本**：v3.0.0 · **发版线**：feat/3.0.0 · **优先级**：P0（资源授权一致性与租户隔离）。

**关联需求**：[已确认需求映射](./discovery.md) §3–§6及本次具体租户视角要求；[应用工场 PRD-1](../../../docs/PRD/3.0-release/3.0%20应用工场%20PRD-1%20专业开发者通道与应用运行时.md)的角色与动作、生命周期、管理数据和开放通道场景为既有背景。本文按用户新增要求替换其中创建人特判及全平台管理视角，不沿用已被明确改变的旧限制。

**依赖与归属**：F048 拥有资源授权；F019 拥有管理视角；F054 拥有应用状态与数据/日志；F055 拥有发布与环境变量；F056 拥有广场及记录查询；F049/F052/F053 的既有开放通道、F086/F059 的现有运行能力及 F113 的租户资格继续适用。本特性统一这些既有能力的操作资格，不重建其领域对象。

**纳入**：全部现有 Vibe 用户操作映射到六个现有动作，移除原创建人/创建人失效的额外限制；界面、API、CLI/MCP 及异步续办的一致性；数据、日志、密钥配置、预览、运行管理的资格；具体租户单选及相应管理数据范围；真实操作者审计；唯一运行控制协议 v2 与旧 v1 执行入口退役。

**排除**：新增权限动作/模型体系、移交/迁租户/存量授权补齐、PAT 新通道或凭据轮换、密钥明文读取、新的界面创建/提交入口、回滚/版本切换、未支持的数据 CRUD/DDL、通用审批系统重写、平台运维降权、独立通用实例重建功能、重新实现 Docker/K8s 编排及全量回归。

## 1. 用户故事

- 作为应用管理者，我希望只按已授予的具体动作管理他人的应用，以免列表可见却被创建人特判阻止。
- 作为应用使用者，我希望 use 只用于业务访问，不使应用内部管理数据暴露。
- 作为集成开发者，我希望 CLI/MCP 按真实主体和应用授权执行，而不借用资源归属人身份。
- 作为租户管理员，我希望始终只看到本租户管理数据；作为超管，我希望明确选择一个租户并在该范围操作，避免误操作其它租户。
- 作为审批人和运维人员，我希望资源权限统一后仍保留审批资格、发布安全条件、运行隔离及可追溯记录。

## 2. 验收标准

> 所有动作均针对同一目标 app；组合动作使用 AND。基础管理信息的“任一管理动作”不含 use。权限模型以其当前生效动作集合为准。

### 2.1 统一授权与管理可见性

- **AC-01** — THE SYSTEM SHALL 对 Vibe 应用复用 `use`、`edit`、`manage_permission`、`delete`、`publish`、`unpublish` 六个现有 F048 动作，不新增 app.read、app.log、app.export、app.secret 等动作，也不改变其它资源的有效动作集合。
- **AC-02** — WHEN 任意主体发起应用操作，THE SYSTEM SHALL 根据该操作要求的具体动作决定资格；原创建人、平台超管、租户管理员及普通授权用户不得由应用业务层另设角色或创建人放行/拒绝分支覆盖 F048 的判定。F048 自身的身份短路、数据范围及模式规则保持有效。
- **AC-03** — WHEN 用户的授权仅适用于某个应用，THE SYSTEM SHALL 只允许在该应用上使用对应动作，不因模型名称为所有者、管理者或编辑者而推定其它应用或未包含动作的权限。
- **AC-04** — WHEN 一项操作要求多个动作，THE SYSTEM SHALL 要求全部满足；任一动作缺失或不可判定时拒绝整项操作，且不执行其写入、部署或数据导出。
- **AC-05** — WHEN 非原创建人通过有效授权操作应用，THE SYSTEM SHALL 保持应用原归属人与所属租户不变，并将实际操作者与资源归属人分别记录；本期不提供移交或迁租户。
- **AC-06** — WHERE 用户仅持 `use`，THE SYSTEM SHALL 允许其按应用状态使用应用，不授予构建管理页、源码、环境变量、运行日志、平台生产数据或管理审计记录的读取/修改能力。
- **AC-07** — WHEN 用户在当前租户视角内具有某应用的任一管理动作（`edit`、`publish`、`unpublish`、`delete`、`manage_permission`），THE SYSTEM SHALL 在构建管理列表和基础详情中呈现该应用及确认操作对象所需的名称、状态、实例状态、版本号、发布说明和发布/审批结果；仅有某个管理动作不能使响应夹带需要其它动作的内容。
- **AC-08** — IF 应用权限评估失败、不可判定、目标不存在或已删除，THEN THE SYSTEM SHALL 拒绝相应操作，不返回未过滤的数据、不变更资源或启动新的执行体，并遵守原资源存在性保密规则。

### 2.2 必须绑定具体租户的管理视角

- **AC-09** — THE SYSTEM SHALL 从顶部租户选择中移除“整个平台/全部租户”选项，管理视角必须限定一个具体租户；Root 也是一个具体租户，选择 Root 不得显示其它租户的业务资源。
- **AC-10** — WHEN 非平台超管访问管理模块，THE SYSTEM SHALL 将其管理视角限定为当前所属租户；伪造租户参数、使用历史选择或缓存状态不得改变该范围。
- **AC-11** — WHEN 平台超管切换管理视角，THE SYSTEM SHALL 仅接受存在且可用的具体租户，显示实际生效的租户，并记录从原视角到新视角的切换。
- **AC-12** — WHEN 平台超管首次访问且没有有效选择，THE SYSTEM SHALL 将有效管理视角设为该登录人当前所属租户；不得把“没有选择”解释为全平台。
- **AC-13** — WHEN 已选租户不再可用、选择已过期或选择内容无效，THE SYSTEM SHALL 回到登录人当前所属租户并显示实际生效范围；IF 无法确定一个合法的默认租户，THEN THE SYSTEM SHALL 拒绝加载管理数据，不选择任意租户或扩大为全平台。
- **AC-14** — WHEN 调用方请求空租户、全平台或其它不能唯一确定具体租户的切换，THE SYSTEM SHALL 拒绝切换并保留原有效范围；切换校验失败不得清除原范围。
- **AC-15** — WHEN 加载知识库、模型、工作流、助手、托管应用、审批管理、审计、用户组及租户自定义角色等管理资源，THE SYSTEM SHALL 根据同一个有效视角过滤列表、基础详情和可操作目标；选择租户 A 时不能列出或操作租户 B 的业务资源。现有公共预置目录的合法共享可读性保留，不把其解释为跨租户业务资源访问。
- **AC-16** — WHEN 管理视角切换或失效回退，THE SYSTEM SHALL 清除前一范围的页面数据与可提交表单状态；旧页面或旧表单不得在新范围下操作原租户的资源，多个页面不得展示与请求实际生效范围不一致的数据。
- **AC-17** — WHEN 管理视角改变，THE SYSTEM SHALL 保持用户真实所属租户、登录身份、服务账号身份、凭据 scope 与已有授权不变；管理视角不是迁租户或取得权限的途径。
- **AC-18** — WHERE 后台任务、开放 API、应用 SDK 或内部运行时请求未使用浏览器管理视角，THE SYSTEM SHALL 按其已经验证的主体及目标租户执行，不继承超管的页面选择，也不得因没有页面选择而扩大范围。

### 2.3 应用管理内容统一映射到 edit

- **AC-19** — WHEN 用户修改名称、描述、图标等元信息，THE SYSTEM SHALL 要求 `edit` 并记录操作；不得仅因与原创建人不同而拒绝。
- **AC-20** — WHEN 用户读取源码快照、源码文件、完整声明、版本内容或内容差异，THE SYSTEM SHALL 要求 `edit`；只有发布/下线/删除等其它动作时仅能获得 AC-07 的基础信息。审批任务的临时审读按 AC-50。
- **AC-21** — WHEN 用户查看应用运行输出、错误栈、构建或预检详细诊断，THE SYSTEM SHALL 要求 `edit`，并保留脱敏、筛选、截断及留存限制；界面、CLI 与 MCP 不得另按原创建人身份限制。
- **AC-22** — WHEN 用户读取生产数据的表清单、结构、行数据或导出数据，THE SYSTEM SHALL 要求 `edit`，并保留表范围、分页、行数及导出数据范围限制；其它动作不包含该管理数据读取资格。
- **AC-23** — WHEN 用户编辑现有生产数据行，THE SYSTEM SHALL 要求 `edit`、二次确认并记录审计；不开放任意 SQL、表结构修改或本期原本不支持的行级操作。
- **AC-24** — WHEN 用户查看环境变量的名称、配置状态、引用或运行配置差异，THE SYSTEM SHALL 要求 `edit`；获授权管理者可查看完整配置项的管理信息，但已保存密钥明文仍不允许读取或回显。
- **AC-25** — WHEN 用户新增、替换或删除环境变量值，THE SYSTEM SHALL 要求 `edit`，保留加密保存、并发冲突提示和审计，不自动重启、停止或重建实例；删除某个值不要求删除整个应用的 `delete` 动作。
- **AC-26** — WHEN 用户确认使用最新环境变量配置重建正式实例，THE SYSTEM SHALL 要求 `edit` 与 `publish`，保留同版本、当前运行配置和确认对象一致性检查；取消确认不创建重建操作。
- **AC-27** — WHEN 用户管理应用私有离线依赖、启停该依赖的可用状态，或读取已有应用数据库快照内容/列表，THE SYSTEM SHALL 要求 `edit` 并限定该应用的资产，不因创建人账号状态改变结果，也不授予公共依赖或全局运行环境的维护权限。
- **AC-28** — WHEN 用户恢复应用数据快照，THE SYSTEM SHALL 要求 `edit` 并确认数据覆盖影响；IF 恢复操作包含正式实例启动，THEN THE SYSTEM SHALL 同时要求 `publish`；保留旧写入者停止确认、独占维护及恢复验证。

### 2.4 生命周期、授权与记录查询

- **AC-29** — WHEN 用户上线、手动上线或重新上线已有已批准版本，THE SYSTEM SHALL 要求 `publish`，继续满足审批结论、应用状态、容量准入与运行健康条件，不另要求是原创建人。
- **AC-30** — WHEN 用户下线正式应用，THE SYSTEM SHALL 要求 `unpublish`、二次确认并记录审计，停止执行体而保留代码、数据库及附件资产。
- **AC-31** — WHEN 用户显式删除整个应用，THE SYSTEM SHALL 要求 `delete`；普通获授权用户、租户管理员、原创建人和平台超管均以 F048 结果为准，不再判断原创建人是否有效或已停用。
- **AC-32** — WHEN 用户删除应用，THE SYSTEM SHALL 继续拒绝在线态直接删除并提示先下线；非在线可删除状态须二次确认，明确代码、对话历史及生产数据的删除范围，取消不得执行删除；确认后保留资产清理、授权清理、在途审批取消和实际操作者审计。
- **AC-33** — WHEN 用户读取授权主体详情、增删授权、选择权限模型或设置可见范围，THE SYSTEM SHALL 要求 `manage_permission`，沿用既有授权入口；基础摘要可显示是否已设置范围，但不能向缺少该动作的用户返回完整授权主体清单。
- **AC-34** — WHEN 用户查看或导出某个应用的模型/能力调用、访问等运行记录，THE SYSTEM SHALL 要求该应用的 `edit` 并限制数据范围；跨应用审计页仍要求其既有审计入口资格且受当前具体租户视角限制。

### 2.5 发布管线与发布代行

- **AC-35** — WHEN 用户上传新的应用内容并提交首发后的迭代发布，THE SYSTEM SHALL 要求 `edit` 与 `publish`，不再以调用者是否等于原创建人为资格条件。
- **AC-36** — WHEN 用户更改资源档位、运行环境、启动配置或平台能力声明并使其通过新版本发布生效，THE SYSTEM SHALL 要求 `edit` 与 `publish`，继续扫描、预检、冻结待审内容，不直接修改历史版本或正式实例。
- **AC-37** — WHEN 有 `publish` 的用户主动撤回某应用的发布，THE SYSTEM SHALL 允许其代行并记录实际撤回者；仅限该应用可撤回的在途发布，不更改其它业务审批或已进入不可撤回终态的记录。
- **AC-38** — WHEN 有 `edit` 的管理者查看当前在审提交的应用管理预览，THE SYSTEM SHALL 允许其使用受控预览能力，不要求原创建人；注入实际预览者本人身份，平台能力同时受该版本声明和预览者本人权限限制，不借用应用归属人权限；预览仍绑定该提交内容、隔离执行且受原时限和生命周期约束。
- **AC-39** — WHEN 非原创建人提交、撤回或重试发布，THE SYSTEM SHALL 保留资源归属事实，继续以应用归属人为审批申请人并保留既有审批路由依据；分别记录实际自然人或服务账号操作者，通知与审批展示区分审批申请人、实际提交主体和应用归属人；发布自审排除按 AC-67、AC-68 执行，不把服务账号调用记成已验证的归属人自然人操作。
- **AC-40** — WHEN 在途发布或恢复操作继续执行到新的扩权、正式启动或新路由生效阶段，THE SYSTEM SHALL 再验证该操作所需授权及凭据仍有效；失效时拒绝新增效果并保留可解释状态，不影响仍正常提供服务的旧版本，也不阻止必要的失败清理。
- **AC-41** — WHERE 首发、迭代或配置声明按原产品合同需要发布审批，THE SYSTEM SHALL 继续在审批通过后才能上线；具备 `publish`、管理员身份或代行资格都不能跳过审批。
- **AC-42** — WHEN 用户查看历史版本、发布说明及提交记录，THE SYSTEM SHALL 保留只读冻结内容和版本切换限制；本次不新增界面造应用、未实现的“提交发布”按钮、任意回滚或版本切换能力。

### 2.6 开放通道、首次创建与存量兼容

- **AC-43** — WHEN CLI/MCP/开放 API 调用已有的应用操作，THE SYSTEM SHALL 同时检查该通道原有的 scope、身份模式及对应 F048 动作；服务账号以自身授权主体判定，已支持的自然人凭据以其真实身份判定，不模拟资源归属人。
- **AC-44** — WHEN 经既有创建资格首次创建应用并提交发布，THE SYSTEM SHALL 保留单命令首发体验，在新应用上为真实创建主体登记本次所需且仅限该应用的初始管理授权，使其能查看提交进度并在具备 `edit` 与 `publish` 后完成提交；初始授权应可查询、可审计，不授予全租户权限，也不覆盖归属人的既有受保护所有者授权。权限初始化失败不得报告发布成功或遗留无法按既有治理方式管理的应用。
- **AC-45** — WHEN 调用者在 F048 上获得其它人应用的相应动作，THE SYSTEM SHALL 允许通过已支持的 CLI/MCP 操作该应用，不要求服务账号资源归属人与应用原归属人为同一人；缺少动作则拒绝。
- **AC-46** — WHEN 开放通道查询应用列表、基础详情、发布状态、日志或数据，THE SYSTEM SHALL 按各内容相应动作过滤或拒绝，不仅返回“资源归属人的应用”，也不因为持有粗粒度 scope 而返回全部应用。
- **AC-47** — WHERE 服务账号归属人资格、账号/应用租户一致性、凭据有效性、身份模式或 scope 不符合既有要求，THE SYSTEM SHALL 继续拒绝；本次不新增 PAT 的 app:manage 签发或未支持通道，不放宽 delegate 互斥或凭据失效规则。
- **AC-48** — WHEN 存量凭据只有通道 scope 而没有目标应用所需的 F048 授权，THE SYSTEM SHALL 拒绝并提示需要对应应用动作；不得为了兼容继续按 owner 身份放行。历史资源不迁租户、不移交、不批量补授权，服务账号补授权沿用既有主体侧入口。

### 2.7 审批资格与可信内部执行

- **AC-49** — WHEN 用户同意/驳回审批任务或处理异常审批，THE SYSTEM SHALL 继续要求既有审批任务或审批管理资格；app.publish 等资源动作不替代审批人或异常管理资格，也不使其取得其它场景的审批权。
- **AC-50** — WHEN 具有该次有效审批任务资格的审批人审读冻结内容或访问审批预览，THE SYSTEM SHALL 保留限于该审批任务/应用/版本/期限的业务授权，不要求原创建人或长期 app 管理授权；审批预览注入审批人本人身份，平台能力继续按该版本声明与应用归属人权限限定并计审计，不把临时审批资格转换成通用管理权限。
- **AC-51** — WHERE 执行预检、管理预览或审批预览，THE SYSTEM SHALL 继续不注入真实环境变量密钥；管理预览按 AC-38 的本人身份与权限执行，审批预览仅按 AC-50 的任务资格使用既有审批例外，不因权限统一扩大模型/知识库或其它底层资源访问。
- **AC-52** — WHEN 审批管理展示应用异常记录、进度或执行允许的异常处理，THE SYSTEM SHALL 限定当前具体租户，保留个人审批与管理审批不同的查看/处理资格，不因删除全平台选项而使同租户合格管理员无法查看进度。
- **AC-53** — WHEN 后台或运行层为已授权操作获取源码、快照、数据或执行生命周期步骤，THE SYSTEM SHALL 验证请求确实属于该应用、版本、操作及用途；前端声称有某动作、仅知道应用标识或持有其它操作的内部凭据均不能代替授权。
- **AC-54** — WHEN 应用被删除或在途发布取消，THE SYSTEM SHALL 继续按原生命周期处理审批与运行资源，保留幂等、终态保护及失败审计；权限统一不得使重复处理恢复已经失效的版本或授权。

### 2.8 运行管理与产品一致性

- **AC-55** — WHEN 用户读取运行操作的基础状态，THE SYSTEM SHALL 按任一管理动作提供确认对象和进度所需的信息；详细日志、私有依赖及快照内容仍按 `edit` 控制。
- **AC-56** — WHEN 用户取消运行管理操作，THE SYSTEM SHALL 按该操作的原业务用途，对当前取消者检查原业务操作要求的全部动作，具体集合见 §3.1；取消者可以不同于发起者，不以原发起者仍有权限代替当前判定，也不因操作统称为“部署”而省略组合动作；不得使单个 edit 或 publish 动作能够取消所有种类的操作。
- **AC-57** — WHEN 用户请求已退役的旧运行绑定导入、升级或重绑操作，THE SYSTEM SHALL 拒绝请求，且不创建执行体、不变更路由或存储资产；同版本环境变量确认重建继续按 AC-26 执行，代码、镜像或运行环境变更通过 AC-35、AC-36 的正常新版本发布生效，本次不新增独立通用实例重建功能。
- **AC-58** — WHEN 用户维护公共运行环境、公共依赖、默认运行环境、宿主隔离或集群能力，THE SYSTEM SHALL 保留现有平台运维资格，不把拥有某一个应用的 `edit` 或其它动作视为全局编排和平台配置权限。
- **AC-59** — WHEN 应用 SDK 调用平台能力或附件服务，THE SYSTEM SHALL 继续使用可信运行身份、访问者身份、能力声明和底层资源授权限定请求；SDK 业务附件操作不被错误映射成删除整个应用，客户端伪造身份或应用标识必须被拒绝。
- **AC-60** — WHEN 正常运行应用发生既有实例自愈或旧执行体清理，THE SYSTEM SHALL 按已验证的运行意图执行，不模拟原创建人，不因某个历史操作者个人撤权自动停用应用，也不借自愈修改已授权版本或增加能力；Docker 与 K8s 的产品权限语义应一致。

### 2.9 前端一致性、拒绝与审计

- **AC-61** — WHEN 界面呈现应用卡片、详情、数据、日志、配置和操作按钮，THE SYSTEM SHALL 根据同一动作映射与有效状态显示、隐藏或禁用；不得在动作允许之后另叠加原创建人或创建人停用条件，也不得只在前端检查而使直接调用绕过。
- **AC-62** — WHEN 权限、模型有效动作或凭据资格发生变化，THE SYSTEM SHALL 在后续请求按最新生效结果决定；旧页面缓存、已打开表单或按钮状态不能维持已失去的资格。
- **AC-63** — WHEN 操作被拒绝，THE SYSTEM SHALL 区分缺少具体动作、应用状态不允许、审批/运行前置条件未满足等原因；不得继续把已获授权管理者的失败笼统描述为“仅创建人可操作”。
- **AC-64** — WHEN 应用管理动作或租户切换成功、失败、取消或由后台继续执行，THE SYSTEM SHALL 按既有留痕合同记录真实操作者、目标租户/应用、相关版本/操作、结果与成因，区分资源归属、提交者和审批者，不记录密钥明文或凭据原文。
- **AC-65** — WHERE 存在原有二次确认、密钥保护、脱敏、数据和附件隔离、资源配额、审批及运行围栏，THE SYSTEM SHALL 保持其作用；权限统一不删除这些非创建人资格类条件。
- **AC-66** — THE SYSTEM SHALL 保持未纳入本需求的工作流、助手、知识库等资源动作语义不变；具体租户管理视角按 AC-09 至 AC-18 统一收窄，不能由此改变这些资源的授权模型或数据归属。

### 2.10 代发布、预览与取消的补充边界

- **AC-67** — WHEN 解析应用发布的审批候选，THE SYSTEM SHALL 排除应用归属人，以及与该次实际提交关联的自然人；自然人直接提交时排除该本人，服务账号提交时排除提交时固定的服务账号归属人并保留真实服务账号主体记录；二者为同一人时不重复排除，服务账号随后改绑不能改写该次自审关联人，按 AC-68 满足单管理员例外时除外。
- **AC-68** — IF 按 AC-67 排除后没有合格审批人且不满足原产品“全租户仅一名管理员且无其他候选”条件，THEN THE SYSTEM SHALL 进入异常审批处理并保留原因，不直接通过；WHERE 满足该单管理员条件，THE SYSTEM SHALL 仅允许该管理员按原规则自审并明确审计，不把“仅配置一名候选”或“过滤后仅剩一名”视为符合例外。这一排除与例外同样约束后续节点及异常处理中的重试、指定审批人，不改变其它审批场景的资格规则。
- **AC-69** — WHEN 同一人同时具有应用 edit 和该次审批任务资格，THE SYSTEM SHALL 按本次预览用途分别执行 AC-38 或 AC-50；管理预览不能继承审批预览的能力例外，两种用途的身份、数据和访问资格保持隔离；缺少该次有效审批任务资格时，即使拥有管理员身份、edit 或声明自己在审批，也不得获得审批例外。
- **AC-70** — WHEN 当前取消者已失去原业务操作所需任一动作，THE SYSTEM SHALL 拒绝其取消请求且不改变在途操作；仍具全部所需动作的其它主体可以按原规则取消。已生效或按既有规则不可取消的阶段继续拒绝取消，不借取消回退已生效版本或重放已完成效果；必要的失败清理不依赖原操作者继续持有权限。

### 2.11 运行控制协议统一

- **AC-71** — THE SYSTEM SHALL 仅支持统一运行控制协议 v2 承载 Docker 与 K8s 应用运行管理，拒绝旧 v1 控制配置及请求，不通过旧控制入口或自动回退继续执行；协议收敛不得取消既有应用交付、数据、附件及平台能力，也不得擅自删除或迁移测试应用的资产与归属。

## 3. 动作与业务范围

| 现有动作 | 业务范围 |
| --- | --- |
| use | 业务入口与应用使用 |
| edit | 管理内容读写：元信息、源码、日志、生产数据、环境变量、私有依赖与快照 |
| publish | 提交/撤回发布及正式启动；改内容后发布、配置重建等需同时有 edit |
| unpublish | 下线正式应用 |
| delete | 显式删除整个应用 |
| manage_permission | 授权和可见范围管理 |

审批任务资格、平台运维资格、运行身份可信性是不同业务边界，不由单个 app 动作代替。新应用尚无资源授权时的受控创建与初始授权按 AC-44；不是持有 app:manage 就自动有历史应用权限。

### 3.1 取消操作所需动作

本表描述可取消阶段的业务资格；不扩大任何操作原有的可取消阶段或效果。所有动作针对被取消操作所属的同一应用，由当前取消者满足；同一运行操作名称可能对应不同业务用途。

| 被取消的原业务操作 | 当前取消者所需的全部动作 |
| --- | --- |
| 启动、手动上线或恢复已有已批准版本 | `publish` |
| 新内容发布准备（含代码、镜像或运行环境变更）、确认环境变量配置重建 | `edit AND publish` |
| 数据快照恢复，不包含正式实例启动 | `edit` |
| 数据快照恢复，包含正式实例启动 | `edit AND publish` |
| 下线正式应用 | `unpublish` |
| 显式删除整个应用 | `delete` |
| 其它现有运行管理操作 | 其原业务操作已定义的全部动作，不从操作名称或发起者身份推断 |

## 5. 边界情况

- 创建人名称、owner 事实或权限模型名称不等于某项动作的授权结果；后台也不能以 owner 代行补足丢失的权限。
- 用户在设计阶段再次明确：创建资源仍归属服务账号配置的自然人，owner 与租户按既有规则写入；真实服务账号用于动作判定、初始授权及操作者审计。本期保持这一归属逻辑和自然人的受保护所有者授权。
- 一个人在租户 A 的 app 有动作，不代表迁到租户 B 后仍能在 A 操作；存量资源与授权保持原归属，具体租户视角和主体资格继续约束请求。
- 本轮退役运行控制协议 v1，以及旧绑定导入/升级/重绑链路。前端 `/api/v1`、开放 API `/api/v2` 和应用包的 manifest_version 是各自独立合同，不按相同数字一并删除；已有源码交付仍可由统一运行层承载。
- 助手、工作流、知识库共用读取/调用保持现有可见性及 use/业务条件，不新增 Vibe 管理动作或统一必填管理头；专用管理写保持原写入资格。
- Root 是具体租户；公共预置角色等共享目录的读取不代表可以查看/修改其它租户业务对象。
- 编辑者可以管理该应用全部已纳入的管理数据；这是采用现有六动作的明确粒度，不能再以隐藏的 owner 特判分拆 edit。更细的只读/导出/密钥专用动作不在本期。
- 同一版本保存环境变量与确认应用到正式实例是两个不同操作；保存只需 edit，确认生效需 edit 与 publish。
- 删除配置项、编辑数据行和操作 SDK 业务附件不是删除整个应用；不能误用 app.delete 导致一般编辑能力缺失。
- 持 publish 不代表有 edit，持 manage_permission 也不直接替代其它动作；具体模型是否同时包含多个动作由 F048 的生效定义决定。
- 自动清理、终态回调和自愈不应因操作者撤权卡住旧 writer 停止，但也不能借内部操作产生新的未授权启动或扩权。
- 代发布保留应用归属人作为审批申请人与路由依据；实际提交主体另记，自审排除同时考虑应用归属人与提交关联自然人；服务账号关联自然人不是已验证的实际用钥人身份。
- 管理预览与审批预览是两种受控用途：即使同一人具备两种资格，管理预览也只能使用本人底层权限；两者都不注入真实密钥。
- 取消资格取决于原业务用途和当前取消者的全部有效动作；配置重建取消不能仅凭 publish，原发起者资格与旧按钮状态也不能替代当前判定。
- 旧客户端请求全平台视角、旧页面跨租户提交和仅持粗 scope 的历史凭据均按新规则拒绝或回退具体范围；不会自动扩大授权以保持旧体验。

## 7. 设计与验证边界

原 70 条规格已获确认；本轮按用户明确的 v2 收敛决定补充 AC-71，并按“按照建议修改”将 AC-57 收窄为旧绑定导入/升级/重绑退役，既有配置确认重建和正常新版本发布不扩展。身份解析、接口兼容、首次创建授权、审批代行衔接、后台阶段重校验、旧客户端失效与范围回退的一致性由 design.md 说明，不在本规格中提前定实现。设计仍须单独评审确认。

后续仅做本功能必要的允许/拒绝配对、六动作与组合、租户范围、真实主体、异步续办、前端/API 一致、确认/审计及专用临时对象 E2E；重点覆盖代发布的双重自审排除及单管理员例外、无候选异常、管理/审批双用途预览、撤权后取消与不可取消阶段；不运行 Vibe 全量或编排故障全量。只验证 v2 的 Docker/K8s 主流程及本次权限边界，补旧 v1 配置/接口拒绝、源码/应用包/完整镜像功能保留及数据不误清理的必要定向检查；不再运行 v1 成功路径或旧协议迁移验收。Docker/K8s 使用相同产品验收标准，DM8 按既定口径仅静态核对。未执行的部署、测试和发行不记为通过。
