# Feature: F059 K8s 应用托管执行后端

> **当前后继合同（F114，2026-10-30，本地实现，未部署）**：Kubernetes 仍沿原执行租约、准入、PVC/SQLite 独占及停止证明；统一使用 v2 的当前授权来源与阶段许可。预览原子登记在平台，helper/数据围栏不放宽。 详见 [F114 已确认规格](../114-vibe-permission-actions/spec.md) 与 [验证记录](../114-vibe-permission-actions/verification.md)。下文保留原 Feature 的 AC 编号、当时口径及历史证据，不将历史通过记录当作 F114 部署证明。

> **状态：2026-10-21 修订草案，R1、R2、R3 已修复，sdd-review 复审通过，用户已确认，进入设计阶段。** 本文只定义 What，不表示已经实现或部署验收通过。沿用原 AC-01 至 AC-43，AC-38 保留退役；新增 AC-44 至 AC-56 承接 F086。原有 AC 没有重新编号。

**关联 PRD**：[PRD-1](../../../docs/PRD/3.0-release/3.0%20应用工场%20PRD-1%20专业开发者通道与应用运行时.md) GOV-10、GOV-03、RT-01、RT-07、RT-08；[技术架构方案](../../../docs/PRD/3.0-release/3.0%20应用工场%20技术架构方案.md)；[F086 spec](../086-vibe-runtime-delivery/spec.md)与已确认的应用包交付合同。

**优先级**：P0；**版本**：v3.0.0；**依赖**：F054、F055、F053、F057、F086；复用 F048 权限、F025 审批和平台存储。

**需求来源**：用户在确认全开源、预制镜像加应用包、backend 中介存储之后，要求“继续完成k8s的开发和部署验收”；指定 192.168.106.189 为单节点 K8s 测试环境。此前 F086 的 spec/design 确认不冒充本修订已经签收。

## 范围边界

本次交付应用工场的 K8s 执行后端：准备、启动、停止、预览、健康、自愈、日志、容量、持久数据、升级与清理，以及集群安装物和真实部署验收。发布、审批、权限、SDK 与用户操作仍归已有 Owner，K8s 不引入第二套业务对象或管理流程。

- 默认应用包、用户完整镜像和显式兼容源码构建三类合同与 F086 一致。应用包发布不要求逐版本构建或推送 OCI 应用镜像；兼容模式保留构建能力，不静默转换旧项目。
- 运行环境目录、代码、依赖产物、附件和快照继续由 backend 管理；运行时执行服务不持平台数据库或 MinIO 凭据。实际工作数据库使用应用独占持久卷。
- manager、app-proxy、egress-proxy 保持独立进程，采用已有开源服务镜像和范围化服务身份。应用数量不引入商业授权或免费额度。
- 本次不改变平台核心的既有部署方式，不新增业务管理页面，不提供多副本、自动扩缩容、跨集群或 Docker/K8s 形态间迁移，不增加任意宿主命令、任意 SQL 或用户一键回滚。
- 节点本地卷允许作为明确告知风险的单节点部署方案。仅有单节点测试环境时，不把单节点重建结果当作跨节点故障恢复证明。

## 1. 用户故事

作为已有 K8s 集群的部署人员，我希望用既有集群运行托管应用，安装时明确知道缺少的网络、镜像、存储和权限条件，以便按现有运维流程上线和排障。

作为开发者，我希望同一份应用包在 Docker 和 K8s 环境经过相同的发布、预检、审批、上线和日志流程，以便不用改写业务代码或提供集群配置。

作为应用 owner，我希望停用、升级、实例重建后数据库和附件保留，预览与生产数据隔离，并能按既有权限流程备份和恢复。

作为安全团队，我希望编排权限只授予独立运行时服务，应用和准备任务不能获取平台控制身份、集群身份或其它应用数据，并能验证隔离实际生效。

## 2. 验收标准

本 Feature 承接 INV-33 的产品面一致要求。应用业务态、审批态、权限和错误呈现沿用原 Owner，不因执行形态发明新业务状态。运维诊断允许展示必要的集群信息，业务用户文案不暴露底层对象名。

### 2.1 形态选择与部署开关

- **AC-01** — THE SYSTEM SHALL 在部署期选择 Docker 或 K8s 执行形态，同一环境只启用一种，不提供运行期切换或形态间迁移入口。
- **AC-02** — WHERE 启用 K8s 运行时, THE SYSTEM SHALL 保持已有托管应用入口、四类兜底页、广场、详情页和 CLI/MCP 行为；未部署运行时层时平台其余功能正常，相关入口按已有开关隐藏或引导。
- **AC-03** — THE SYSTEM SHALL 使 backend、Celery、app-proxy、egress-proxy 和应用均不持集群编排凭据；仅独立 manager 持有其作用范围内的集群身份。

### 2.2 编排能力等价

- **AC-04** — WHEN 平台请求准备、启停、销毁、状态、日志、探活或容量判定, THE SYSTEM SHALL 复用 F086 的业务操作和事实合同，调用方不传 Pod、卷路径或其它 K8s 执行参数。
- **AC-05** — WHEN 应用上线或重新上线, THE SYSTEM SHALL 准备候选、探活并提交就绪事实后才切换正式路由；预览使用独立临时执行体。涉及生产 SQLite 的启动与切换必须同时满足 AC-50 的单写要求。
- **AC-06** — WHEN 已运行应用退出或持续不健康, THE SYSTEM SHALL 自动恢复服务；在集群及持久卷前置正常且资源可调度时，恢复时间不超过 5 分钟。节点本地卷物理故障不作跨节点自动恢复承诺，按 AC-31 显式报告。
- **AC-07** — IF manager 重启或短暂不可用, THEN THE SYSTEM SHALL 保持已运行应用及入口、既有出站连接可用；manager 恢复后在配置的对账期限内恢复对缺失执行体和持久操作的处理。
- **AC-08** — WHEN 审批通过后的上线、手动上线或重新上线因容量不足、所选档位、卷拓扑或配额约束而无法调度, THE SYSTEM SHALL 进入既有待上线（资源不足）状态，保留已通过的审批及待上线版本，资源恢复后可原单手动上线；WHEN 审批前准备或启动预检因同类约束失败, THE SYSTEM SHALL 返回预检失败阶段及资源不足原因，不生成审批单或正式版本，不进入审批后的待上线状态，释放候选及本次预占，资源恢复后重新提交发布。两阶段均不得遗留无限等待的候选；有界清理继续遵守 AC-49、AC-52。
- **AC-09** — IF 新发布的拉起超过配置期限, THEN THE SYSTEM SHALL 区分容量、镜像、材料下载和健康失败并结束该次拉起；已上线应用恢复失败时持续对账，保留原恢复状态并报告阻塞原因，不发明恢复失败业务终态。
- **AC-10** — THE SYSTEM SHALL 通过既有状态、健康、版本和日志接口返回与 Docker 相同的范围、刷新、筛选和权限语义，日志经过现有敏感信息脱敏。
- **AC-11** — THE SYSTEM SHALL 对每个正式应用维持单个活动实例，不开放副本数或自动扩缩容；临时预览和准备任务不成为额外正式实例。
- **AC-12** — THE SYSTEM SHALL 只允许经 app-proxy 访问应用；不为每个应用开放节点端口、外部负载均衡或独立入口，非授权工作负载不能绕过代理直连。

### 2.3 最小权限与审计

- **AC-13** — THE SYSTEM SHALL 限制 manager 只能操作明确授权的工场命名空间和资源，不能操作其它命名空间、授予新身份权限、创建特权工作负载或挂载宿主敏感路径；部署验收须包含实际允许与拒绝结果，不能仅检查权限声明文件。
- **AC-14** — THE SYSTEM SHALL 随交付物提供资源类型、动作、命名空间的完整权限清单；集群启用审计日志时，manager 的操作可按其身份追溯。集群审计未启用时明确提示，不伪造审计证据。
- **AC-15** — THE SYSTEM SHALL 使应用及准备、探活、数据维护执行体不持集群 API 身份，不获得 manager 控制密钥；准备、预检和数据维护的材料身份限定于当前有效操作及指定材料，运行期初始化的材料身份按 AC-47 限定于当前有效部署归属及冻结引用。两类材料身份均不得被业务容器读取或继承，不得取得通用控制权限。
- **AC-16** — THE SYSTEM SHALL 对应用和任务执行非特权、不可提权、资源有界、根文件系统只读及明确可写路径限制；应用代码和依赖环境正式运行时只读，业务数据目录按应用隔离。

### 2.4 档位与沙箱映射

- **AC-17** — THE SYSTEM SHALL 按已有资源档位设置请求量和上限，档位默认值、停用、修改生效时机与 Docker 一致，不能静默修改已运行实例的冻结规格。
- **AC-18** — WHEN 单个应用达到内存或 CPU 上限, THE SYSTEM SHALL 将重启或限流影响限制在该应用，不影响平台及其它应用。
- **AC-19** — THE SYSTEM SHALL 保留默认、推荐、加固三档部署级隔离选择；配置的更强隔离不可用时，明确告警并按既有部署合同回退默认档，记录实际生效档位，不静默声称已启用。
- **AC-20** — THE SYSTEM SHALL 在改变隔离档位时保持身份注入、资源限制、单写持久化和出站控制等业务承诺不变。

### 2.5 网络隔离

- **AC-21** — WHILE 应用运行, THE SYSTEM SHALL 默认拒绝直连外网、平台内部服务、其它应用和集群 API，只允许经受控通道调用当前授权的平台能力及声明域名；域名策略和权限撤销的拒绝上界沿用 F086，不因 manager 不在线而失效。
- **AC-22** — WHILE 准备或兼容构建任务执行, THE SYSTEM SHALL 仅允许阶段所需的平台材料接口、配置包源或镜像端点；禁网解析、安装与编译阶段不得使用公共包源兜底，任务不能连接生产数据库和其它应用。
- **AC-23** — IF 必需的入口或出站隔离缺失、未生效或无法确认生效, THEN THE SYSTEM SHALL 拒绝新的托管部署及相关准备、预检和维护执行，返回实际探测失败原因；不提供跳过必需隔离的配置或降级放行路径。管理服务可保留诊断能力，隔离恢复并重新验证通过后才允许相关执行；既有应用也不得豁免 AC-12、AC-21 的隔离要求。

### 2.6 应用交付与镜像分发

- **AC-24** — WHEN 使用 F086 的默认应用包交付, THE SYSTEM SHALL 使用冻结的预制运行环境和版本化代码、依赖产物完成准备与启动；仅业务源码变化时不构建或推送新的 OCI 应用镜像。
- **AC-25** — THE SYSTEM SHALL 支持与 Docker 相同的 Python 3.11、Node.js 20、static 应用包、用户完整镜像和显式兼容源码构建；兼容构建使用受限、一次性、无节点守护进程权限的执行体，不依赖 DinD 或 docker.sock。所选模式前置缺失时在审批前拒绝，不静默转换模式。
- **AC-26** — THE SYSTEM SHALL 将应用包的代码、依赖和编译产物通过 backend 持久保存并向执行位置分发；镜像交付和兼容构建则保证冻结镜像可供目标执行节点取得。默认应用包不以具备应用镜像推送仓库为必要条件。
- **AC-27** — THE SYSTEM SHALL 使镜像仓库凭据只供受控拉取或构建使用，不出现在应用可读的环境、挂载文件、日志或用户界面。
- **AC-28** — IF 准备、镜像推送或拉取失败, THEN THE SYSTEM SHALL 保留对应阶段和安全的可读原因；镜像不可拉、缺包、错架构和材料损坏不归为资源不足。
- **AC-29** — THE SYSTEM SHALL 保留当前运行、待上线以及停用应用待运行/上次运行版本所引用的冻结镜像与产物可恢复性，清理不得使这些版本无法重建或重新上线。

### 2.7 集群能力探测

- **AC-30** — WHEN 安装、升级或启动运行时服务, THE SYSTEM SHALL 检查网络隔离实际生效性、最小权限、所选隔离能力、镜像可取得性、平台材料接口、可用持久存储及其卷类型/拓扑、最小资源和所选兼容构建前置；输出逐项结论、时间和原因，不能只依据组件名称推断能力成立。
- **AC-31** — IF 所选发布路径的硬前置不满足, THEN THE SYSTEM SHALL 拒绝新的相关执行并报告原因；既有应用仅在仍满足 AC-12、AC-21 时继续运行。必需隔离失效按 AC-23 拒绝，不能通过配置覆盖。缺少更强沙箱或仅有节点本地持久卷时明确告警，节点绑定和故障恢复限制持续可见；更强沙箱回退仅可依 AC-19 回到满足必需隔离的默认档。无动态存储供应器但有符合约束的预置持久卷时允许使用，不因缺少默认 StorageClass 单独失败。
- **AC-32** — THE SYSTEM SHALL 将最近一次探测结果、硬前置失败原因、可选沙箱档位的回退记录及实际隔离档位呈现在既有运行环境状态接口，供平台超管和部署工具查询，不新增业务管理页面。

### 2.8 每应用数据与持久卷

- **AC-33** — THE SYSTEM SHALL 为应用 SQLite 工作数据提供独占持久存储，延续已有连接环境变量；在存储支持的故障范围内，容器/Pod 重建及可支持的重新调度不丢失已提交数据。平台附件、快照及源代码真身仍由 backend 保存。
- **AC-34** — IF 数据卷不满足 SQLite 锁、同步和单写要求, THEN THE SYSTEM SHALL 拒绝上线并报告存储不兼容；节点本地卷须报告节点绑定，不假定它可以跟随跨节点调度。NFS/SMB 等不满足既定 SQLite WAL 合同的存储不能作为静默替代。
- **AC-35** — THE SYSTEM SHALL 在停用、重建、manager 重启、升级和卸载运行时层时保留应用持久卷；仅在既有 owner 显式删除应用流程及确认没有活动写入者后清理对应数据。

### 2.9 双形态一致性

- **AC-36** — THE SYSTEM SHALL 通过既有发布、审批、权限、CLI/SDK、日志、附件、数据、预览、停用/恢复及运行时开关用例在 K8s 上的回归；Docker 回归继续通过，不能用模拟执行器结果代替真实平台链路。
- **AC-37** — THE SYSTEM SHALL 保持业务状态、待上线原因、审计事件、通知和 CLI/MCP 输出的语义及文案与已有 Owner 一致，形态信息仅进入运维诊断。
- ~~**AC-38**~~ — 已退役；编号不复用。用例追溯和复用纪律见第 3 节。

### 2.10 安装、升级和卸载

- **AC-39** — THE SYSTEM SHALL 交付可复核的集群部署资源与安装、升级、卸载、最小权限、存储和镜像供应说明；覆盖运行时服务、入口/出站代理、任务、应用卷及前置探测。平台核心继续按既有方式部署；全部组件保持开源，不引入商业授权执行点。
- **AC-40** — WHEN 升级或重启 manager 及相关运行时服务, THE SYSTEM SHALL 保持已有应用实例不被连带重建，并复核前置和期望态；代理升级按已有连接/排空合同处理，不承诺进程被强杀后原 TCP 连接不变。
- **AC-41** — WHEN 卸载运行时层, THE SYSTEM SHALL 仅回收本次安装明确拥有的执行和控制资源，保留应用代码、依赖、快照、附件及数据库持久卷；平台其它功能不受影响，入口按既有部署开关呈现。

### 2.11 离线与执行治理

- **AC-42** — WHERE 客户环境不能访问公网, THE SYSTEM SHALL 支持预先供应精确服务/运行/准备镜像与完整依赖材料后完成默认应用包发布、审批、启动和重建；镜像可通过经目标运行时验证的预灌方式或内网仓库供应。需要镜像推送的兼容构建使用配置的内网分发端点，缺少它只阻断该路径，不以公共仓库兜底或阻断已满足前置的应用包模式。
- **AC-43** — THE SYSTEM SHALL 对准备、探活、构建和数据维护任务设置期限、CPU/内存和并发限制；超限可查询、取消或超时后有界回收，保留可读阶段和原因，不能占满集群或影响已上线应用。

### 2.12 F086 承接与可靠性补充

- **AC-44** — THE SYSTEM SHALL 将冻结代码、依赖锁和材料分发到实际执行位置；venv 等可执行环境按所选镜像、架构和依赖生成，Pod 重建后可从持久产物重建，不依赖 manager 的本机目录或上传者现成虚拟环境。
- **AC-45** — WHEN 只修改业务代码且依赖输入兼容, THE SYSTEM SHALL 复用已验证依赖材料；WHEN profile、架构、依赖锁、离线材料或影响安装的源码变化, THE SYSTEM SHALL 阻止错误缓存复用。缓存丢失只影响重新准备，不丢失已提交产物。
- **AC-46** — THE SYSTEM SHALL 仅经 backend 的范围化接口下载源码、读写产物、上传/下载数据库快照和处理附件；manager 与应用不获得平台 MinIO 或关系数据库凭据，SDK0.1.1既有附件合同保持可用。
- **AC-47** — THE SYSTEM SHALL 将准备、预检和数据维护材料身份限制在当前有效操作，运行期初始化材料身份限制在当前有效部署归属及冻结引用；准备操作完成不使合法运行实例失去重建所需材料。运行期初始化的短期凭据过期时，可由 backend 重新核验当前归属及冻结范围后签发新凭据，不依赖 manager 在线，不得仅凭已过期或撤销凭据续期。两类身份均不授予通用控制能力，且按 AC-15 与业务容器隔离；已停用或撤销归属、过期凭据直接访问、重放、篡改、跨租户或跨应用请求被拒绝，未确认或摘要不符材料不执行。
- **AC-48** — THE SYSTEM SHALL 以 backend 持久操作、当前归属、事实和路由/策略投影为权威；重复通知、manager 重启或多进程竞争不能产生重复正式实例、重复审批或提前释放资源。
- **AC-49** — IF 无法确认旧实例已停止写入, THEN THE SYSTEM SHALL 保守保留资源和写入归属，不启动第二个正式数据库写入者；超时后返回可查的阻塞原因，不能把 API 删除请求被接受当作停止证明。
- **AC-50** — WHEN 更新、迁移或恢复涉及生产 SQLite, THE SYSTEM SHALL 确认生产写入者停止，在隔离下做一致备份/迁移或恢复；预览与预检使用独立数据。新旧正式实例即使处于切换窗口也不能同时写生产数据。
- **AC-51** — WHEN DDL 前备份上传, THE SYSTEM SHALL 等待 backend 对快照内容、摘要和关联记录持久确认后才执行 DDL；确认失败禁止迁移，DDL 后启动失败保留维护/数据可能改变状态，不自动恢复旧数据库。恢复继续要求自然人 owner 显式确认并保护当前数据。
- **AC-52** — WHEN 准备、探活、迁移或上线取消、超时、执行服务被杀或响应丢失, THE SYSTEM SHALL 按 F086 期限对账执行体、临时数据和预占，记录清理是否完成；未知活动写入者或唯一未确认备份不能被回收。Pod、服务或卷身份被同名替换时不得按名字误认原执行体。
- **AC-53** — THE SYSTEM SHALL 保持 HTTP/WebSocket 入口及 CONNECT 出站连接的既有授权、撤权和失联拒绝期限；manager 停止超过路由短缓存期限时，新访问仍按 backend 的持久投影处理，不能要求每次访问查询 manager。
- **AC-54** — THE SYSTEM SHALL 保持 amd64/arm64 运行材料隔离及原生镜像交付；所选 profile 与目标架构不兼容时在审批前拒绝。镜像可用、依赖材料可用和平台能力接口可用分别核验，不能互相代替。
- **AC-55** — THE SYSTEM SHALL 提供可重复执行的 K8s 专有部署验收和既有平台 E2E 记录，明确每项为静态、模拟、真实执行、未验证或受环境限制；原有非测试资源在验收前后保持不变，不用单节点结果声称跨节点故障恢复已通过。
- **AC-56** — WHEN 后续发布或升级执行本 Feature, THE SYSTEM SHALL 保持 Docker 既有源码/应用包/完整镜像路径和数据合同不退化；共享权限、审批或模型修复按发布线归属继承，不在 K8s 分支复制出另一套业务规则。

## 3. 边界情况与用例纪律

- 发布审批及数据维护的 Owner 不变；预览的既有 owner 能力例外和普通访问者权限交集不因 K8s 改变。预检失败不创建审批单或正式版本；只有审批通过后的上线准入不足才进入待上线（资源不足），两阶段的重试动作按 AC-08 区分。
- 包源不可达、缺 wheel、摘要错误、错 ABI、镜像拉取失败、PVC 未绑定、健康失败与资源不足各自留有阶段证据。前置检查不能跳过真实启动验证。
- 持久卷类型及节点拓扑影响恢复能力；无动态供应器不等于没有持久卷，单节点本地盘也不等于跨节点持久存储。
- 资源预算可读不等于一定可调度；有界执行中遇到调度失败须清理候选，不能为满足新旧并存而违反单写。
- 应用与准备任务不能读取控制身份；命名空间权限声明不能替代对特权、宿主挂载、跨命名空间和网络绕行的实际拒绝验证。运行期初始化按当前部署归属取得材料，不延长已完成准备操作的权限，也不把材料身份交给业务容器；凭据签发和续期须重新授权。
- 必需隔离属于硬前置；默认档也必须满足入口与出站限制。可选强沙箱回退与必需隔离失效分开处理，不存在未隔离状态下继续部署的覆盖项。
- 未被引用的临时目录可回收，已提交产物和正式数据不能因任务失败、卸载或工作负载级联删除而丢失。
- 产品面复用既有用例，不另写断言分叉；K8s 专有测试覆盖集群权限、卷、调度、隔离、镜像供应和执行体生命周期。每个允许路径配套拒绝/失败路径，AC 编号完整追溯。
- 当前验收环境只有一台 amd64 节点。真实跨节点调度及节点丢失后的卷迁移需要另一节点与适配存储，未执行时明确记录，不视为通过。
- DM8 按本会话已确认口径只做相关模型/迁移规范静态检查；真实驱动/数据库回归由中央环境承担，不借用旧 schema 的验收结果证明新迁移已执行。
