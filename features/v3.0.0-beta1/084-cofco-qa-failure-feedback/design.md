# F084 问答失败分类与恢复提示：设计草案

状态：待确认，未开发。更新：2026-11-05。

依据：[spec.md](./spec.md)及其引用的飞书第4章。代码核对基线：中粮1111分支 `f9a687415`；飞书旧盘点基线为10月31日，本方案核对了下面列出的当前关键路径，未声称完成全部错误定义的运行验证。

## 1. 怎么改

在实际访问模型、数据、登录、存储或网络的地方记录失败对象，随现有错误一起传递。页面按这个对象显示五类固定提示，旁边显示具体服务和定位信息。刷新后继续使用同一份分类。

本期仅处理工作台日常模式和任务模式。复用现有消息、任务结果和步骤历史，不新增表、字段或数据回填。模型细分原因、重试和降级继续使用现有规则。当前交付是可评审的设计草案；实施任务、接线台账及运行验收在设计确认后推进。

## 3. 关键决策

### 3.1 在实际调用处记录来源，统一出口只负责传递

备选是只按错误码或异常文字归类。现有11090覆盖多种任务失败，`Connection error`又可能来自多个服务，因此该方式不能可靠区分对象。

选定：在已有依赖适配器或明确的SDK调用处，捕获真实调用异常并附带来源。保留原异常链；外层包装继承已有来源，只有此前没有来源且当前确实是依赖调用边界时才补充。普通编排层不猜测来源。

模型供应方返回“内部数据库错误”仍是本次模型调用失败；平台自己在模型调用前访问Redis失败，则继承Redis来源。事务中的任意Python异常也不自动变成数据库故障。正常业务拒绝单独保留。

SDK升级、调用边界迁移或发现误分类样本时，调整对应适配器并补回归用例；不增加全局关键词猜测。

### 3.2 服务分类与恢复策略独立

页面新增五类分类；原 `error_type`、模型限流状态、执行身份及重试参数继续保留。五类决定主提示，旧规则决定能否重试、是否正在恢复及是否允许切换模型。

不把五类替换进旧 `error_type`：否则可能改变限流恢复和终态判断。只有明确需要改变恢复机制时，才另行设计。

### 3.3 使用现有扩展数据，不新建错误表

分类跟随本次失败结果，不需要独立查询或维护生命周期。现有消息 `extra`、任务 `output_result` 和步骤历史均可承载可选对象。

全局错误表会增加跨表写入、关联和清理成本，本次没有相应收益。未来若需要独立工单、跨会话错误检索或故障统计，再单独评估。

## 4. 统一传递内容

### 4.1 内部来源与公开分类

新增一个不依赖业务领域的失败上下文结构，建议放在 `common/schemas/failure.py`，归一化与安全序列化工具放在 `common/services/failure_context.py`。基础设施适配器及业务执行边界调用它；公共层不导入业务模块。

图示定位约定（均为拟新增，未实现）：D节点的 `FailureContextAdapter` 放在 `common/services/failure_context.py`，负责给真实调用异常附上来源、继承原异常链及生成脱敏公开信息；`FailureContext`（内部来源）和 `FailureInfo`（公开结构）放在 `common/schemas/failure.py`。它不接管重试、Agent调度或权限。E节点只将既有结果与这些数据合并，G节点复用已有存储。

**D不只是增加一个类，还要修改现有异常返回点。** 图中拆成D1（真实调用处捕获来源）和D2（现有包装处透传），不能等异常已经变成字符串后才在E猜测分类。

| 现有位置 | 当前处理 | 本次拟改动 |
|---|---|---|
| 模型调用适配器；`chat_service.py` / `task_exec.py` 的错误收口 | 已有模型异常分类、异常链展开及重试；外层通用异常也可能进入模型分类 | D1在真实模型调用处补充来源及已有可见模型信息；D2继承根异常上下文，再交给E。复用已有细分分类和重试，不把其他依赖错误当模型错误。 |
| `workstation_service.py:queryChunksFromDB`；`chat_service.py` 的知识工具 `_search` | 单库异常写成 `str(exc)`；外层异常可能返回空结果；日常工具还有直接返回 `[]` 的分支 | D1先保存原异常来源；D2在原失败项上保留结构化错误，外层catch不能再把异常事实丢成正常空结果。成功资料继续返回，故障与无命中分别反馈。 |
| `linsight_knowledge.py:SearchKnowledgeBase._arun` | 捕获技术异常后返回“无结果＋错误信息”的JSON文本 | D1在转文本前保留根来源；D2保留可继续执行的软返回，并携带可靠的 `failure_info`。技术失败不能作为正常无命中显示。非法输入、无权限和真正无命中仍走原业务分支。 |
| `executor.py:ToolExecutor._arun` 的任务分支 | 工具异常转成JSON错误文本返回Agent | D2在已有错误返回中继续透传D1上下文/可靠的公开信息，记录原异常链；保留软失败机制，不改成一律抛异常终止任务。 |

完整根异常、类型与堆栈留在受控日志/内部上下文；跨任务显式序列化安全的来源数据，消息只发脱敏公开对象。没有可靠分类时仍应保留“发生了失败”这一事实并走通用反馈；不能以缺少 `failure_info` 推断成功，也不从任意第三方返回文本中猜分类。

内部保留：来源种类（依赖失败/业务结果/内部错误/未知）、实际依赖、发生步骤、原异常类型与错误码、已授权的显示名称、最初发生时间、关联请求或执行标识。内部结构可携带受控诊断字段，但公开序列化只允许下表字段。

原异常通过 `raise ... from ...`、`BaseErrorCode.exception` 或既有异常包装保留；跨队列及存储时显式序列化上下文，不能只依赖进程内变量或异常对象属性。

### 4.2 公开的可选对象 `failure_info`

| 字段 | 类型 | 约定 |
|---|---|---|
| `version` | 整数 | 本期为1；未知版本按旧错误处理。 |
| `failure_id` | 字符串 | 首次生成的失败标识，包装、补发和历史读取不重新生成。 |
| `category` | 枚举 | `database/network/model_service/sso/object_storage`，仅在来源可靠时生成。 |
| `service` | 可选字符串 | 已确认的稳定组件标识，例如 `dm/redis/elasticsearch/milvus/minio`；模型调用可用 `llm/embedding/rerank/asr/tts`。 |
| `service_name` | 可选字符串 | 已有权限范围内的服务或模型展示名；不为补充名字额外查询权限或依赖服务。 |
| `operation` | 可选字符串 | 安全的步骤标识，例如 `search/read_file/invoke_model`，由前端本地化，不传动态原始异常。 |
| `occurred_at` | 字符串 | 首次发生时的带时区ISO8601时间。 |
| `trace_id` | 可选字符串 | 复用已有Trace ID；任务继续携带原请求/执行关联信息。没有时不伪造已有追踪记录。 |

未知或业务结果不生成五类对象；不对页面增加第六类。无效字段、未知枚举或未知版本忽略该对象，回到原业务或通用错误反馈，不影响状态收敛。

`failure_info` 不承载原始堆栈、SQL、连接串、Cookie、Token、API Key、内部URL或未经授权的资源名。两种模式的SSE/WS事件及历史读取执行相同的安全序列化，原 `detail/exception` 等旧字段也只返回允许公开的脱敏信息，不能把异常字符串原样透传。前端折叠原文不作为安全控制。旧库原文不批量改写，通过服务端读取适配器限制可见内容。

### 4.3 放在哪里

| 通道或存储 | 增量位置 | 兼容方式 |
|---|---|---|
| 日常/任务提交SSE `error` | 原错误信封中的 `data.failure_info` | 事件名、终止信号及旧字段不变；由对应流Hook读取，不依赖全局HTTP拦截。 |
| 任务WS `error_message` | 事件数据的 `failure_info` | 与同次任务 `output_result.failure_info` 相同。 |
| 日常失败消息 | `ChatMessage.extra` JSON中的 `failure_info` | 合并已有键；解析旧值失败时按旧格式读取，不覆盖旧内容。 |
| 工具/检索局部失败 | 日常工具事件的 `failure_info`；任务 `ExecStep.extra_info.failure_info` | 日常跟随 `ChatMessage.message.events`，任务跟随 `LinsightExecuteTask.history` 保存；均与原事件/步骤合并。 |
| 任务结果 | `LinsightSessionVersion.output_result.failure_info` | 合并而非替换已有结果，保留答案、成功文件、恢复参数与原字段。 |

任务历史以原任务版本结果为来源，消息指针关系不变。日常历史读取消息扩展信息；两种模式既有的历史适配器和只读序列化都保留分类，不能只修改卡片。

## 5. 各类怎么判断

| 已确认的失败对象 | 页面分类 | 边界 |
|---|---|---|
| DM/MySQL连接、池等待、驱动错误、重试耗尽；Redis/ES/Milvus调用 | 数据库 | 锁被占用、队列为空、普通Python/序列化错误分别判断。 |
| LLM、Embedding、Rerank、OCR/VL、ASR、TTS及其供应方网关 | 模型服务 | 供应方认证、余额、限流都归此类；平台权限、席位和月用量继续使用业务提示。 |
| MinIO/S3调用失败 | 对象存储 | 对象正常缺失、资料已删除沿用原业务提示；存储签名错误不归SSO。 |
| 两种模式已确认的企业会话认证异常 | 单点登录 | 沿用已有登录处理，只在本次反馈中识别可靠来源；模型认证归模型服务，普通权限拒绝继续使用原业务提示。不改SSO开户或全站登录流程。 |
| 设备离线、已确认的页面到平台/网关传输失败 | 网络 | 泛用HTTP库的连接异常不能单独决定分类，必须带调用对象；协议/JSON解析错误不是网络证据。 |
| OpenFGA、工具、沙箱或外部信息服务 | 按已确认的实际失败依赖，或通用反馈 | 不直接凭服务名称塞进五类；权限拒绝及自身逻辑错误保留各自结果。不修改OpenFGA模型、权限规则和投影逻辑。 |

源码定义和调用链只提供静态证据；客户网关、身份服务和供应方的实际响应另行补样本。保留现有错误码，不能只按11090、10541或重复码值建分类表。

## 6. 执行、局部失败与保存

1. 实际依赖调用失败，生成或继承来源。原有重试先继续执行；尚在重试/恢复时维持原处理中反馈。
2. 如果重试耗尽形成最终失败，使用同一个来源生成 `failure_info`。不因经过模型包装而改分类。
3. 工具软失败继续按原机制给Agent返回观察结果，同时保存对应失败元数据；可见提示挂在工具步骤，不把整轮回答强制改成失败。
4. 多库检索保留成功资料和失败资料；全部服务失败也不能伪装成正常无命中。在检索步骤明确反馈，是否继续作答沿用原Agent策略。
5. 终态分类与原业务结果一并写入现有权威存储，供实时事件和后续读取复用；任务结果优先保存后推送。日常流允许先发失败、再按现有逻辑收尾，但使用同一上下文，避免生成两套分类。
6. 保存本身失败时记录真实错误并结束本次加载；实时可显示已有分类，但不能承诺刷新后有新记录。刷新读取权威结果，缺少记录时按现有中断/未知状态处理，不补造终态。
7. 断流只表示连接状态变化。先按原会话/任务标识查询已有结果：已完成显示结果、处理中恢复订阅、明确失败显示失败；查询也不可用时显示网络/通用反馈，禁止自动创建第二个执行。

同一轮发生多个独立局部失败时，分别留在对应步骤；整轮失败有一个独立主提示，以真正终止执行的错误为主，不挑“严重程度最高”的类型。后续持久化失败通过独立日志记录，不覆盖已发生的服务来源。

## 7. 页面展示与恢复

复用现有失败卡片、工具步骤反馈和操作区；五类原文见 `spec.md §2`。不新增全局弹窗、不新建页面，也不把重要失败仅放在短暂Toast中。

| 位置 | 展示规则 |
|---|---|
| 没有生成答案 | 原失败位置显示五类固定主提示，紧邻显示服务/模型、操作、发生时间及定位标识；无来源则保留业务或通用提示。 |
| 已生成部分答案后失败 | 保留答案、成功引用和附件，在答案后使用同一主提示；不能因有部分正文而省略分类。 |
| 工具或检索局部失败 | 在对应步骤展示分类，保留其余结果。只读/分享历史不提供执行类按钮。 |
| 已有重试/切换模型操作 | 沿用原权限、重试资格、限流状态、attempt/execution/recovery标识；分类不自行新增自动重试。 |
| 单点登录 | 当本次模式内有可靠会话认证来源时显示固定提示；沿用已有登录入口，不改全局401/403处理或账号权限分支。 |

网络提示中的“检查连接”、登录提示中的“重新登录”及其他类别的“联系对应维护方”就是本期统一恢复说明。已有安全重试动作仍可保留；本期不建设联系人通讯录或自动通知维护方。

固定文案在共享 `packages/locales/src/api_errors/{zh-Hans,en,ja}.json` 增加命名键（例如 `failure_model_service`），不新增数值业务码、不修改旧码翻译。辅助标签在各应用既有本地化体系同步三语。生成产物按既有脚本生成。

遵循UI规范的现有字体、颜色、换行和移动端触达规则；复用已落地组件及现有失败容器。没有新增共享失败组件时不新造组件规范；任何视觉样式变化先由设计师确认。实现前不以此草案修改设计规范。

## 8. 接线范围与模块职责

| 责任模块 | 需要完成的接线 | 保留的边界 |
|---|---|---|
| common失败上下文及流错误出口 | 安全结构、继承/序列化、两种模式SSE/WS可选字段。 | 不猜业务归属，不导入领域服务，不改变错误码或全局HTTP异常处理。 |
| 模型/数据/存储/身份依赖适配器 | 在真实SDK或驱动调用失败处确定对象；识别模型子调用和数据依赖。 | 不将整个业务事务一律标为数据库；不改权限和外部协议。 |
| workstation日常模式/检索/附件链路 | 直接异常、业务包装、检索失败项、工具事件和答案extra。 | 保留局部成功、停止、文件业务校验及模型恢复；不改独立问答页面。 |
| linsight提交/执行/工具/状态管理 | 入队失败、附件处理、工具软失败、整体失败、输出结果、WS事件和补发。 | 保留当前执行身份与继续/恢复/降级行为。 |
| client流Hook/任务管理/历史/失败容器 | 日常useAiChatSSE/useAiChat，任务提交流、Websocket、useLinsightManager，以及对应消息与步骤渲染。 | 无新状态库；api/request.ts仅复用原翻译函数，不改其实现。辅助HTTP请求沿用现有包装器。 |

实施接线限定为：日常生成、任务提交流/入队、任务执行失败、两种模式的检索与工具软失败、附件解析与文件操作，以及对应实时/重连/历史展示。这里的文件操作仅指两种模式执行中的调用，不扩展到知识空间后台入库/复制页面。

## 9. 兼容、部署和取舍

1. 分类单测：两种模式中实际触达的五类来源、模型供应方内部数据库错误、平台额度、对象缺失、未知内部服务及普通Python/协议错误等反例。

## 11. 已知坑与待补证据

| 容易踩的坑 | 后果及处理位置 |
|---|---|
| 把模型细分原因当服务类别 | 数据库超时会被当模型错误，且可能改变重试行为；由common上下文与原llm分类器分层处理。 |
| 用新的对象覆盖extra/output_result | 丢失消息关联、成功文件和恢复参数；在现有保存函数中合并，补覆盖断言。 |
| 只补实时事件 | Hook和任务历史白名单仍会漏字段；同步修改useAiChatSSE、Websocket、useLinsightManager及历史/分享适配器。 |
| 只改失败卡片 | 部分答案路径和ServiceBusyNotice可能绕开卡片；在各终态渲染分支接入统一的主提示解析。 |
| 把流连接断开视为任务失败 | 重提后可能重复执行；沿用状态查询/恢复订阅机制，不改执行幂等协议。 |
| 只把任务错误留在临时Redis | 缓存到期后历史丢失；现有任务output_result及步骤history承担持久化。 |
| 在外层捕获后拼模型名称 | 失败时再查数据库可能引发二次失败或泄露名称；只使用调用前已有的授权上下文。 |

客户网关/身份错误样本、SDK版本、旧Hook活动入口和独立解析服务自身错误仍需补证。无法确定来源时保留通用反馈，不把这些证据缺口写成已覆盖。
