工作流删除后，数据保留，入口关闭

主记录只增加一个删除标记。用户不能再找到或新使用这个工作流，原来的定义、版本和历史仍保留。

设计摘要：先看效果，再看流程与取舍；研发定位信息收在页尾。

旧链接、构建预览和管理员也遵守删除状态。历史会话与文件按原有权限查看；保留定义不等于开放定义下载。

点击删除后，系统做四步

第 1 步检查权限

确认操作者有权删除。

→
第 2 步撤销授权

沿用原有权限处理。

→
第 3 步改删除标记

主记录和所有版本一起标记，内容不清空。

→
第 4 步清理使用入口

清用户组入口与分享链接，保留会话展示信息并记审计。

这次主要替换第 3 步的物理删除。上线 / 下线仍是原来的含义，不增加“删除中”状态或进度表。

为让标记生效，配套补齐三处

查的时候过滤

列表、数量、推荐、模板来源等排除已删除记录。历史读取单独保留，避免历史也消失。

新操作先检查

网页、接口、分享和调试入口都检查标记，旧页面不能继续发起新操作。

保存不能恢复删除

只更新未删除的工作流，版本保存与删除互相排队，防止旧页面把数据重新写活。

删除后释放工作流业务配额，允许同名新建并生成新 ID；已有模板和复制件作为独立数据保留。

低复杂度方案，接受两个边界

运行中任务不额外协调

不因删除主动停止。已经提交或运行中的任务可能继续，也可能因再次读取工作流而失败；正常聊天入口再次输入时会拒绝续跑。

不承诺立即终止，也不保证最终跑完。

跨系统失败沿用现有处理

如果授权已经撤销、数据库标记却更新失败，可能出现“记录还在，但不能使用”；清理失败也可能需要排查日志。

不增加自动补偿系统，也不保证再次点击就能修复。

本期不做回收站、恢复和定时清空。以前物理删除的数据不能自动补回；保留数据会持续占用存储。

需要你决定什么

没有新增业务取舍。这份设计落实此前确认的“单标记、低复杂度、在途不强要求”。评审只需核对上面的效果和两项边界是否符合预期。

研发附录：改动范围、技术取舍和怎么验收

一个字段，保留原接口

工作流表新增 is_delete：非空整数，默认 0；删除后为 1。主记录与关联版本在同一数据库事务更新；现有 status 上下线状态不变。仅工作流启用新的删除语义，其他应用类型不变。普通编辑请求不可提交删除标记。

沿用 DELETE /api/v1/flows/{flow_id}、原成功响应和错误反馈；重复删除按现有资源不存在反馈。不新增删除时间和操作者列，沿用原审计。

改动范围

范围处理方式
数据与迁移主模型增加标记；Alembic 为存量增加默认 0 的列，兼容 MySQL 与 DM8。父迁移取真实单一 head，不猜文件顺序。
普通资源读取同步、异步、批量、简单信息、列表和计数显式过滤；联合应用列表在工作流内层查询过滤，避免分页与总数失真。
绕过普通查询的路径补模板来源、推荐、权限迁移、资源归属及资产计数等直接 ORM / SQL 查询；配额计数沿调用链核查。
并发保存主记录按可写字段、带未删除条件更新，不回写删除字段、不把旧对象重新插入。版本写入与删除使用同一父记录短锁，检查与写入合并事务。
历史读取优先用已有会话信息；必要时通过内部 Repository 读取有限元数据，保持历史权限和租户隔离，不向普通接口开放绕过过滤参数。
调用入口网页、预览、API v2/v3 和分享的新操作检查父记录；不改 Worker 调度及运行状态机。

为什么这样选

  • 单标记与现有版本表语义一致；三态、操作表和额外业务版本号会扩大本期复杂度。
  • 查询显式过滤，历史专用读取；全局隐藏钩子难以兼顾联合查询、列投影与历史用途。
  • 已有保存入口有整对象保存和分段提交，需补条件写入与父锁；不把锁持有到任务执行结束。

怎么证明做对

验证删除后主记录、定义和版本仍在；普通列表、数量、新操作不可访问；历史、文件仍按原权限可读；同名新建和配额释放正确；并发保存不能复活。覆盖普通用户、管理员和不同租户，验证权限失败与数据库异常不被当成成功。

完成后端测试、API E2E、迁移单 head、Ruff 与架构检查；MySQL / DM8 行为需按环境验证，未运行的检查如实记录。当前针对性本地检查 72 项通过；真实部署 API E2E 与 MySQL / DM8 验收待完成，完整记录见 verification-report.md。

上线和后续边界

先迁移数据库、更新相关进程并清退旧代码后开放删除。回滚必须保留过滤与禁止物理删除的兼容处理，或暂停相关入口。沿用现有授权、审计、分享清理和日志，不新增外部依赖、配置或后台监控体系。

只有未来新增恢复、删除进度、跨系统自动修复或严格在途保证时，才重新评估协调机制。
