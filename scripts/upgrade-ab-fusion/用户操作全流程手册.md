# 毕昇升级与数据迁移操作手册

| 项 | 内容 |
|---|---|
| 目的 | 将源环境 **B** 升级到 **2.5.0-sg**，再把 B 的业务数据迁入目标环境 **A** |
| 终态 | 业务运行在 A。A 原有知识空间不改；B 的知识空间本轮不迁 |
| 执行位置 | 全程在 **B** 上操作。迁移脚本经 SSH 写入 A |
| 工作目录 | 见第 2 节 |

下文命令均在工作目录执行。某步输出 `FAIL`：**停止**，不要跳步。

---

## 1. 通则

1. **升级立即生效**，没有演习开关。必须先完成冻结，再逐站升级。
2. **迁移用 `full-migrate.sh` 编排**。默认 `APPLY=0` 不写 A；真写必须同时 `APPLY=1` 和 `CONFIRM_FULL_MIGRATE=1`。
3. 密码、密钥只留在当前终端，**禁止**写入 `env.sh` 或代码仓库。
4. 禁止 `alembic stamp`。禁止打开 B 的组织同步。
5. 身份映射按工号绑定，禁止按姓名合并。

数据范围（无单独业务 DDL）：升级改 B 的 MySQL 结构、compose/配置，并冻结 MySQL + MinIO + Milvus + ES/etcd。迁移在 A 写入控制表 `fusion_*` 及传统知识库、工作流、助手、会话等；表清单见 [README.md](./README.md)。A 原 `knowledge.type=3` 只读。

本手册不含：入口切到 A、不兼容知识库重解析、观察期项目。切流量见 `p6/cutover-runbook.md`。

---

## 2. 投放代码

把最新毕昇代码上传到 B 上某个路径，然后进入该路径下的升级目录：

```bash
cd <上传路径>/scripts/upgrade-ab-fusion
```

例如传到 `/data/`，则：

```bash
cd /data/bisheng/scripts/upgrade-ab-fusion
```

## 3. 升级 B 至 2.5.0-sg

### 3.1 是否执行本章

```bash
docker inspect bisheng-backend --format '{{.Config.Image}}'
```

```sql
SELECT version_num FROM alembic_version;
```

| 现状 | 处理 |
|---|---|
| 已是 2.5.0-sg，版本号 `f058_dashboard_dataset_flags`，服务正常 | 跳过本章，进入第 4 章 |
| 已是 2.4.0，尚无 `f058_...` | 只做 §3.2 冻结，再从 §3.4 的 `30-hop-2.5.sh` 继续。不要重跑 `10`～`21` |
| 仍为 2.2 | 按 §3.2～§3.5 顺序执行 |
| 有 `alembic_version` 但不是 `f058_...`，或 backend 无法正常启动 | **半升级。进入第 5 章回滚。禁止继续 hop。** |

### 3.2 预检与冻结

冻结会停止写入，并完整拷贝 MySQL、MinIO、Milvus、ES、etcd。缺任一块，后续升级都会失败。执行期间不要中断。

```bash
bash p2/00-precheck.sh
bash p2/01-freeze-and-backup.sh
```

**通过：** 预检打印 `预检通过`；冻结打印 `OK p2.01-backup`；`logs/p2/current-freeze.txt` 有冻结戳。

预检中 2.4 相关列已是 `PRESENT`，表示该站已做过，不要重跑对应 hop。

### 3.3 升到 2.4.0（仅 2.2 起点）

```bash
bash p2/10-hop-2.3-beta1.sh
bash p2/11-hop-2.3-release.sh
bash p2/20-hop-2.4-beta1.sh
CONFIRM_TYPE2=1 bash p2/21-hop-2.4.sh
```

**通过：** 镜像为 `v2.4.0`；个人知识库 `type=2` 行数为 0。存在 `type=2` 却未带 `CONFIRM_TYPE2=1` 会失败并列出待转记录。

### 3.4 升到 2.5.0-sg 并迁移权限

```bash
bash p2/30-hop-2.5.sh
CONFIRM_F006=0 bash p2/31-f006-workstation.sh
CONFIRM_F006=1 bash p2/31-f006-workstation.sh
```

`CONFIRM_F006=0` 只预览，结束为 `OK ... dry_run`，**不是失败**。核对清单后再执行 `=1`。迁入 A 知识空间之后，禁止再全局重跑 F006。

**通过：** `alembic current` 等于当前 backend 镜像的 `alembic heads`。出现 `WARNING: alembic migration failed` 即失败。日志中的 `Event loop is closed` 若步骤已 `OK` 且版本号与镜像 head 一致，可忽略。

### 3.5 升级验收

```bash
bash p2/40-verify.sh
```

此为 **B 本机**验收，不是迁入 A 后的 `p5/40-verify.sh`。

**通过：** 结尾出现 `OK p2.40-verify`（库版本、type=2 剩余 0、failed_tuple 未成功 0）。业务计数只展示、不自动判分。再在 B 页面登录，打开原有工作流和传统知识库。

## 4. 数据迁移 B → A

前提：B 已 hop 完 2.5，且 A、B 的 `alembic_version` **相同**。不一致时 `APPLY=1` 会被拒绝。

迁移主路径是 **`full-migrate.sh`**：按固定顺序跑完控制表、A 基线、身份、业务、MinIO、向量、OpenFGA、验收。不必手工复制 `env.sh.example`。首次会询问 A 的地址、账号、端口（写入 `env.sh`）和密码（只留当前窗口）。输出 `连接 A: ...` 与现场不符则停止。

批次号由脚本生成（一般为 `fusion-当天日期`），打印为 `本批 BATCH_NO=...`，并写入 `logs/current-batch.txt`。验收与回滚沿用该批次。

`all` 会执行：

`control → a-baseline → identity-export → identity-propose → identity-apply → business-export → business-apply → minio → vectors → openfga → verify`

不随 `all` 自动跑：检索金标（`--stage retrieve-gold`）、增量（`--stage incr`）、工作流发布（`--stage publish`）。首次业务导出前，脚本会抓一次水位。

`env.sh` 不要写死 `APPLY=0`，否则命令行 `APPLY=1` 会被盖掉。

### 4.1 演练（不写 A）

```bash
bash full-migrate.sh
```

等价于 `APPLY=0 bash full-migrate.sh`。

出现 `logs/p4/*.conflicts.csv`：**停止**，处理后续跑：

```bash
bash full-migrate.sh --stage identity-propose
```

不要复用上一批次对照表。冲突消除后，从失败的下一阶段继续，例如：

```bash
bash full-migrate.sh --stage identity-apply
```

**通过后再写入：**

- 连的是 A
- 脚本打印 `OK full-migrate`
- 无未处理冲突
- 向量步骤 `pending=0`（`need_reparse` 进例外表，不自动解析）

复核：`logs/p5/gaps-model-tool.tsv`（只处理冲突行）、`exceptions-session-groups.tsv`、`gaps-assistant-links.tsv`。

### 4.2 正式写入

演练通过后：

```bash
APPLY=1 CONFIRM_FULL_MIGRATE=1 bash full-migrate.sh
```

只设 `APPLY=1`、不设 `CONFIRM_FULL_MIGRATE=1` 会被拒绝。`APPLY=1` 时验收自动带 `VERIFY_STORAGE=1`。

某步失败后不要从头再跑一遍写入。用 `--stage` 从该阶段续跑，阶段名见本节开头列表。

### 4.3 验收

**通过：**

- A 原知识空间数量不减少；原空间文件与原会话仍在
- 迁入的知识库、文件、问答、工作流、助手、会话、消息与导出清单一致
- 本批无悬挂引用
- `VERIFY_STORAGE=1`：抽查对象存在，检索命中率不低于 `GOLD_MIN_HIT`（默认 0.8）

在 **A 页面**抽检迁入工作流并跑通。脚本不能替代该步骤。

工作流改为「已发布」须现场明确同意后再执行（不包含在 `all` 里）：

```bash
CONFIRM_PUBLISH_FLOWS=1 APPLY=1 bash full-migrate.sh --stage publish
```

### 4.4 仅在排障时分步执行

与 `full-migrate.sh` 等价，不要和全量编排混着穿插：

```bash
APPLY=0 bash p4/00-install-control.sh
APPLY=0 bash p5/00-protect-a-baseline.sh
bash p4/01-export-identity.sh
bash p4/02-propose-maps.sh
APPLY=0 bash p4/10-apply-identity.sh
bash p5/10-export-b-business.sh
APPLY=0 bash p5/30-apply.sh
APPLY=0 bash p5/20-copy-minio.sh
APPLY=0 bash p5/22-copy-vectors.sh
APPLY=0 bash p5/35-apply-openfga.sh
bash p5/40-verify.sh
```

真写时把对应步骤改为 `APPLY=1`，最后一次验收用 `VERIFY_STORAGE=1 bash p5/40-verify.sh`。

## 5. 回滚

升级回滚与迁移回滚对象不同，不要混用。入口切到 A 之后，禁止用迁移回滚恢复。

### 5.1 将 B 退回冻结点

先演练：

```bash
APPLY=0 bash p2/90-rollback.sh
```

冻结戳取自 `BACKUP_STAMP` 或 `logs/p2/current-freeze.txt`。

完整冻结（§3.2 成功）且确认覆盖对象存储：

```bash
CONFIRM_VERSION_ROLLBACK=1 CONFIRM_RESTORE_STORAGE=1 APPLY=1 bash p2/90-rollback.sh
```

仅有库与 compose、无存储副本：

```bash
CONFIRM_VERSION_ROLLBACK=1 ACCEPT_INCOMPLETE_STORAGE=1 APPLY=1 bash p2/90-rollback.sh
```

完整冻结禁止加 `ACCEPT_INCOMPLETE_STORAGE`。没有对应版本的 dump，不能退到该版本。禁止用 A 库覆盖 B。

### 5.2 撤销本批写入 A 的数据

```bash
APPLY=0 bash p5/90-rollback.sh
```

核对删除名单不含 A 原空间后：

```bash
APPLY=1 bash p5/90-rollback.sh
```

名单：`logs/p5/rollback-vector-stores.tsv`、`logs/p5/rollback-minio-keys.tsv`。只删本批对象，不整桶清空。
