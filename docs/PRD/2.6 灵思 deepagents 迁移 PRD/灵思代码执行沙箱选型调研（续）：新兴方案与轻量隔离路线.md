# 灵思代码执行沙箱选型调研（续）：新兴方案与轻量隔离路线

> **调研日期**：2026-09-15
> **前篇**：[灵思代码执行沙箱选型调研（私有化场景）](./灵思代码执行沙箱选型调研（私有化场景）.md)（2026-08-11）。前篇结论：E2B、Daytona、LangSmith Sandbox 出局；推荐基线为「独立容器 + compose 原生加固」；硬隔离需求叠加 gVisor。
> **本篇范围**：agent-infra/sandbox、CubeSandbox、microsandbox、Clone、sandlock、OpenHands runtime、gVisor、V8 Isolate / Wasm、nsjail / bubblewrap、自研路线
> **关注维度**：① 本地私有化部署与信创适配 ② 资源消耗与速度（能否提升任务模式运行速度）③ 开源许可证的商用友好性
> **方法**：
> - deep-research 工作流：5 个检索方向，抓取 24 个来源，抽出 120 条论断，其中 25 条做了三票对抗核验，21 条成立、4 条否决。
> - 另派 4 个 agent 定向补核：OpenHands、V8/Wasm、nsjail/bwrap/自研、许可证与 gVisor 落地。
> - 两路结论冲突的地方，人工复核一手 commit diff。
> - 所有结论都以一手来源为准（README、LICENSE、源码、release、issue/PR、官方文档）。厂商自测数据会单独标注。

**一句话结论**：
- **默认档不变。** 本轮 10 个方向里，没有一个能替代「加固容器」。
- **升级档仍是 gVisor systrap。** 它是唯一能在「VMware 虚机、无嵌套虚拟化」下提供更强隔离的方案，但 2026-08 起最低内核从 4.14.77 提到 5.6，而且代码层面真的依赖 `openat2`。4.19 客户只能钉旧版本。
- **新兴 microVM 进不了默认交付形态。** CubeSandbox、microsandbox、Clone 的毫秒级启动全都建立在 KVM 上。
- **sandlock 不可用。** 内核低于 5.13 时它直接拒绝启动。
- **任务模式提速不该押在隔离技术上。** 实测瓶颈是 LLM 轮次和镜像工具链缺失。沙箱层真正能拿到的收益来自「会话级常驻容器 + 常驻解释器 + 预热池 + 工具链完整的镜像」，这几项跟用哪种隔离技术无关，在加固容器上就能做。

## 1. 结论先行

| 分档 | 方案 | 适用客户 | 一句话理由 |
|---|---|---|---|
| **默认档** | **加固容器**（自研 `ContainerExecutor` 或 llm-sandbox），配合会话级常驻、预热池和收紧的 seccomp profile | 全部，包括 4.19 内核和龙芯 | 唯一不挑内核、架构、虚拟化平台的方案；前篇 POC 已验证 office 链路在最严加固下全绿 |
| **硬隔离升级档** | **gVisor（runsc，systrap 平台）**，通过 compose `runtime: runsc` 或 K8s RuntimeClass 开关 | x86_64 / arm64，且内核 ≥ 5.6（例如 5.10） | 唯一不需要 `/dev/kvm` 的用户态内核隔离；arm64 有性能折损，上线前必须 POC |
| **观察档**（只看不接） | CubeSandbox（KVM 路线）、microsandbox | 物理机或 KVM 系私有云、能开 `/dev/kvm` 的少数客户 | 许可证都友好，但一个还在 0.x 且性能宣称自相矛盾，一个自认 beta |
| **借鉴设计，不集成** | OpenHands runtime、agent-infra/sandbox | — | 前者的会话生命周期管理值得抄；后者的「一体化运行环境」镜像组织方式值得参考。两者隔离都弱于我们的基线 |
| **不推荐** | Clone、sandlock、CubeSandbox PVM 路线、V8 Isolate / Wasm、nsjail/bwrap 替代容器、gVisor KVM/ptrace 平台、Judge0/isolate | — | 分别卡在：KVM + 早期项目、内核 5.13+、要换宿主内核、跑不了原生二进制、要放宽容器、嵌套虚拟化性能差或已停止支持、GPL |

**龙芯（LoongArch64）客户**：本轮所有隔离增强方案（gVisor、sandlock、各 microVM、workerd、Deno）都**没有官方支持**，只能用加固容器。另外，麒麟/UOS 龙芯版属于「旧世界」ABI，Docker 默认 seccomp 在上面是否真正生效还没有一手证据，必须实机验证（见 §8）。

**前篇三处安全缺陷的现状**（2026-09-15 复核 `3.0-vibe` 分支）：**三处都还没修**，选型前应先处理。
- Fernet 密钥仍硬编码在开源代码里：`src/backend/bisheng/core/config/settings.py:22`。
- 执行器现在**传了** `env=`，但 `_child_env()` 的实现是 `os.environ.copy()`（`bisheng_langchain/gpts/tools/code_interpreter/local_executor.py:180`），子进程仍然全量继承 compose 注入的 `BS_MINIO_ACCESS_KEY` / `BS_MINIO_SECRET_KEY`。**缺陷的实质没有变**。
- `docker/docker-compose.yml` 里 backend（L111）和 backend_worker（L151）仍然是 `seccomp:unconfined`。

| 约束 | 现状 | 对选型的影响 |

## 4. 逐项结论

### 4.1 agent-infra/sandbox（AIO Sandbox）：运行环境集成方案，不是隔离技术

- **它是什么**：README 写明把 Browser、Shell、File、MCP、VSCode Server、Jupyter 打包进**同一个 Docker 容器**，共享文件系统。浅克隆全仓库 grep `gvisor/runsc/kata/firecracker/microvm/runtimeClass`，**零命中**。K8s 示例是普通 Deployment，没有 `runtimeClassName`。「cloud-native lightweight sandbox」只是宣传用语。
- **隔离比我们的基线弱**：README 的 4 个 `docker run` 示例、Compose 示例和仓库自带的 `docker-compose.yaml` **全部带 `seccomp=unconfined`**，理由是给 Chromium 自己的 sandbox 用。`security.md` 把它定位为 trusted local development。如果要接入，必须自己写 seccomp profile 并补上 cap_drop 等加固。
- **部署**：普通 Docker 即可，不依赖 KVM 或 privileged。这一点从部署方式推出，文档没有明说。多架构镜像情况本轮未核实。
- **许可证与成熟度**：Apache-2.0，5,907★，2025-08 创建，最近 push 2026-09-14，release 1.11.0。维护方背景的推断在核验中被否决，**不要写成定论**。
- **对 BiSheng 的价值**：「一个会话一个一体化运行环境」的镜像组织方式可以参考，比如浏览器、Jupyter 内核、文件服务共存。**不能**拿它替代加固基线。
- 来源：https://github.com/agent-infra/sandbox

### 4.2 CubeSandbox（腾讯云）：所有部署路径都离不开 KVM

- **架构**：KVM microVM，基于 RustVMM，改造自 kata-containers 和 cloud-hypervisor，宣称兼容 E2B SDK。roadmap 仍写着「Close remaining gaps」，**兼容并不完整**。
- **部署依赖**：
  - 标准部署要 `/dev/kvm` 可读写，也就是物理机或开了嵌套虚拟化的虚机。
  - 必须 root 加 Docker，控制面还要 MySQL、Redis、MinIO、CoreDNS 等组件。
  - 宿主要求 glibc ≥ 2.31 和 XFS reflink。
  - K8s 部署（Helm chart）标为 **preview**。
- **PVM 路线**（README 标为「推荐」，不需要 `/dev/kvm`）：
  - 要装定制宿主内核 `kernel-*opencloudos9.cubesandbox.pvm.host*` 并重启，再 `modprobe kvm_pvm`。PVM 是没进主线的 out-of-tree 补丁，**麒麟/UOS 自带的 4.19 / 5.10 内核里不可能有**。
  - v0.5.0 release notes 原文：「PVM (nested KVM) is x86_64-only; ARM64 requires bare-metal with native KVM」。
  - 文档里没有任何 VMware 验证。Issue #1722（2026-09-11，open，维护者未回复）报告在 VMware Workstation 上装定制内核后 OOM kernel panic；Issue #161 报告 AWS C8i 装 PVM 内核后起不来。
- **离线**：部署文档前置条件写着 Internet access。one-click 离线包可以手动下载，`deploy/one-click/env.example` 支持把镜像指向私有仓库或 `@sha256`，但**没有完整的官方离线安装指南**。
- **架构支持**：物理机文档写 x86_64 / aarch64，但 `online-install.sh` 只认 x86_64 包，ARM64 要手动装。LoongArch 未被提及，release 产物只有 amd64 / arm64。
- **性能宣称自相矛盾**，这是本轮最需要警惕的一点：
  - README 原文是「under 60ms with less than 5MB of memory overhead」。实现方式是「Resource pooling and snapshot cloning skip all cold-start overhead」，即**资源池预置 + 快照克隆，不是真正的冷启动**。脚注注明裸金属测试：单并发 60ms；50 并发平均 67ms、P95 90ms、P99 137ms；内存数据仅在沙箱规格 ≤ 32GB 时成立。
  - 官方自己的 benchmark 博客（`docs/blog/posts/2026-06-01-cubesandbox-perf-benchmark.md`）：BMI5 裸金属 96 核 / 375GiB，沙箱规格 2vCPU / 2GiB。串行平均 47.8ms；**50 并发平均 276.1ms、P95 508ms**；**每个沙箱内存约 21.5–25.7MB**；报告里找不到 P99 137ms。
  - ⇒ **README 的并发与内存数字无法被自家报告复现**，引用时只能用博客数据，并注明是裸金属。
- **许可证**：根 LICENSE 主体 Apache-2.0，并列出第三方组件：kata / cloud-hypervisor 为 Apache-2.0（腾讯修改）；cilium/bpf 原为 BSD-2 / GPL-2.0 双许可，声明选用 BSD-2。`hypervisor/` 另带 BSD-3-Clause。代码搜索 GPL-2.0 命中 24 个文件（主要是 CubeNet eBPF 源码），**未逐一核对 SPDX 头**；guest 内核镜像未列入 LICENSE。商用分发前需要法务做一次 SPDX 审计。
- **成熟度**：12,269★，2026-04-10 创建，v0.7.1（2026-09-11），未到 1.0。
- **判定**：**观察档**，仅面向能提供原生 KVM 的物理机客户，而且要等 K8s 转正、性能数据口径统一后再评估。**PVM 路线不推荐**：要替换客户宿主内核，这在信创项目里基本不可能过审。
- 来源：https://github.com/TencentCloud/CubeSandbox 、https://cubesandbox.com/guide/pvm-deploy

### 4.3 microsandbox：KVM 硬依赖，beta

- README 的 Requirements 明写「Linux: KVM enabled」，因此没有嵌套虚拟化的 VMware 虚机跑不了。
- 最新 v0.6.18（2026-09-09）的 Linux 产物只有 x86_64 和 aarch64；仓库 issue 与代码里搜 `loongarch` 结果为 0。
- Apache-2.0；README 原文「still beta software. Expect breaking changes」。8,252★，0.6.x 补丁版近一个月每 1–6 天发一版。
- 存疑：「是否存在非 KVM 兜底」的核验论断被 0-3 否决，推测是 issue 回复细节有误，但「Linux 上要 KVM」由 README 独立支撑。
- 前篇已指出商业化风险：Super Rad Company 的云服务在闭测，形态与转闭源前的 Daytona 相似；guest kernel 作为 release asset 分发，上游停发即无法离线部署。
- **判定**：观察档，仅限 KVM 客户。
- 来源：https://github.com/superradcompany/microsandbox

### 4.4 Clone（unixshells/clone）：fork 很快，但太早期

- README 写明「KVM-based」，要求「Linux host with KVM (/dev/kvm)」「Kernel 6.5+ recommended」（严格说是 e2e 测试用的 guest 内核）。
- 从 x86 PCI MMIO hole、bzImage 加载、`--target x86_64-unknown-linux-musl` 等细节看，**事实上只做了 x86_64**。
- 速度数据来自 README 自测，测试机是 OVH 独服（Xeon E-2386G、Ubuntu 24.04、kernel 6.8）：
  - 冷启动约 2.2s，最好成绩 2,217ms，5 次平均 2,338ms；
  - 从预热模板 fork 最小 Alpine（128–512MB、无网络）<20ms；
  - fork 带网络的 4GB Ubuntu 约 160ms。
  - fork 数据没给运行次数和分布，**最小模板的数字不能代表带 LibreOffice / Python 的重模板**。
- 许可证 MIT（Copyright 2026 Unix Shells Limited Company）。2026-03-16 创建，421★，默认分支 25 个 commit，**0 个 release、无 tag**。README 把 MSI-X、SR-IOV、TDX/SEV、qcow2 per-fork overlay 列为 Needs work。
- **判定**：不推荐。KVM、仅 x86_64、项目太早期，三条各自都足以否决。
- 来源：https://github.com/unixshells/clone

### 4.5 sandlock：信创内核上完全不可用

- **机制**：Landlock（文件系统 + 网络 + IPC）+ seccomp-bpf + seccomp user notification。「No root, no cgroups, no containers」，对比表 Kernel 一栏写 Shared。论文 arXiv 2605.26298 把内核漏洞列在威胁模型之外，并说对抗性多租户场景仍应使用 microVM。
- **内核门槛**：完整功能要 6.12+（Landlock ABI v6）。分项最低要求：seccomp notify 5.6、Landlock FS 5.13、TCP 规则 6.7、IPC scoping 6.12。
- **没有降级路径**（源码 HEAD f58072c9e，2026-09-12）：默认 Strict 模式缺保护就拒绝启动。`Protection` 枚举只覆盖 ABI v2–v6，基础 Landlock FS（ABI v1）不能关闭；`landlock.rs` 里 `abi_version()` 失败直接返回 `LandlockUnavailable`，`context.rs` 随即失败。⇒ **5.13 以下内核上 `allow_degraded` 也救不回来**。
- Landlock 本身还要求 `CONFIG_SECURITY_LANDLOCK=y` 并在 `lsm=` 中启用（内核文档原文「first introduced in Linux 5.13」）。没有搜到麒麟、UOS 或 openEuler 4.19 回移 Landlock 的证据。
- **架构**：`crates/sandlock-core/src/arch.rs` 只定义了 x86_64 / aarch64 / riscv64，没有兜底分支，**龙芯上编译不过**。另提供 `sandlock-oci` shim，可接 containerd / CRI-O / K8s。
- **性能**（自报，不可信）：README 性能表写 `/bin/echo` 启动 7ms，顶部表格写 5ms；COW fork 1000 个 README 写约 530ms，官方博客写 718ms；论文里的 Redis 数字也和 README 不同。论文测试机是 Ryzen 5 5500U 笔记本 + Linux 6.18。
- 许可证 Apache-2.0，405★，v0.8.7（2026-09-04）。
- **判定**：不推荐。4.19 / 5.10 内核直接无法启动，而且共享内核也算不上硬隔离。
- 来源：https://github.com/multikernel/sandlock 、https://docs.kernel.org/userspace-api/landlock.html

### 4.6 OpenHands runtime：值得借鉴设计模式，不适合直接集成

**先纠正一个前提**：网上大多数资料描述的 V0 runtime **已不存在**。PR #14117（2026-04-24）删除了 `openhands/runtime`；2026-07-27 主仓清空，改为 TS 前端「Agent Canvas」（#15397）；Python 服务端拆到 `OpenHands/sandbox-server` 和 `OpenHands/enterprise`。下文 V0 行号取删除前 commit `137bede1`。

- **V0 形态**：
  - 用 `docker.from_env()` 起普通容器，不涉及 KVM。容器按会话常驻，容器名为前缀加 sid。backend 通过 `POST /execute_action` 下发 action；容器里有 bash 会话、Jupyter 和 VSCode 插件。
  - `impl/` 下有 docker / local / remote / **kubernetes** / cli 五种 runtime。
  - **Remote runtime 依赖闭源 Runtime API**：文档写明仅用于评测、需填表申请，源码不公开，Helm chart 在 OpenHands-Cloud 仓（PolyForm Free Trial），**不能按开源方式自托管**。
  - 三级镜像 tag（source / lock / versioned）做构建缓存，支持自定义 `base_container_image`。
- **会话生命周期的演进**：
  - PR #6403（2025-01-23 合并）把闲置容器从 remove 改为 stop，`keep_runtime_alive` 默认改为 False；V0 后来又加了 `pause_closed_runtimes=True`。
  - V1 sandbox-server 的 `max_num_sandboxes` 默认 **5**，超出时暂停最旧的沙箱（`docker_sandbox_service.py#L600-L603@f19f9e0d`）。常被引用的「3」是 `max_concurrent_conversations`，不是沙箱数。
  - Issue #9156 提出的 none / pause / keep_alive 复用策略没有实现，2026-05-21 以 not_planned 关闭。「每会话启动 30–60s」是提案作者的估计，不是实测。
- **「只把执行放进容器」的尝试失败了**：PR software-agent-sdk#4883 由 neubig 本人开，09-06 标 ready，09-07 自己转回 Draft。
  - 设计：可信的外层 agent-server 保留 agent loop 和凭据，只有 terminal / file_editor / grep / glob / apply_patch 通过 RPC 在每会话一个的容器里执行。
  - docker run 参数：cap-drop ALL、no-new-privileges、tmpfs /workspace、tmpfs /tmp 512m、pids-limit 512，端口只绑 127.0.0.1；**没有 `--network none`、内存 / CPU 限额和 `--read-only`**（`execution_runtime/workspace.py#L297-L331@7096d432`）。
  - 该模式直接拒绝 skills、memory、plugins、hooks、MCP、自定义工具（`#L215-L232`、`#L280-L295`）。维护者的结论是更倾向「每会话一个完整 Agent Server 容器」。
  - **对 BiSheng 的启示**：任务模式要在沙箱里读 SKILL.md、跑 skill 脚本，「只把单个工具 RPC 转发进沙箱」会撞上同样的能力缺口。**沙箱里要能看到完整工作区与技能包**，这印证了前篇「技能包挂载时序是一等公民」的判断。
- **V1 主线的加固**：
  - SDK `DockerWorkspace` 默认几乎不加固，只有 `--rm` 和 `--ulimit nofile`。
  - sysbox-runc / gVisor 通过 RuntimeClass 选择的加固，**只在商业版 K8s remote 路径里有**。
  - 编排端 `docker-compose.yml` 挂了 `/var/run/docker.sock`，沙箱容器本身不挂。
- **许可证**：software-agent-sdk 与主仓为 MIT；`OpenHands/enterprise`、OpenHands-Cloud 为 **PolyForm Free Trial 1.0.0（禁止分发）**，典型 open-core。MIT 部分保留版权声明即可，**不能拷贝 enterprise / Cloud / runtime-api 的任何代码或 chart**。
- **架构**：`agent-server`、`runtime`、`runtime-api` 镜像在 GHCR 上只有 amd64 / arm64。
- **直接集成的阻碍**：
  - V1 agent-server 自带完整 agent loop，与 deepagents 重叠；
  - SDK 要求 Python ≥ 3.12，BiSheng 是 3.11，而且依赖 litellm、fastmcp、browser-use 等重型包；
  - 编排端需要 docker.sock；
  - 加固路径在商业许可部分；
  - 无 loong64 镜像。
- **值得抄的设计**：
  - 会话级懒启动容器；
  - 超上限暂停最旧的沙箱；
  - 容器打 server label，启动时清扫孤儿容器；
  - 三级镜像 tag 缓存；
  - 端口只绑 loopback，每个 workspace 一个 capability token，token 写入 0600 权限的 env 文件；
  - 用 RuntimeClass 做可切换的加固开关。

### 4.7 gVisor：仍是唯一的硬隔离升级档，但门槛比前篇写的高

**平台选择**
- systrap 自 2023 年中取代 ptrace 成为默认平台。它用 seccomp `SECCOMP_RET_TRAP` 让内核发 SIGSYS，再交给 Sentry 处理。官方博客原文：「Systrap runs on most Linux machines out of the box without virtualization」。platforms 文档写明，虚机内和没有虚拟化支持的机器上 systrap 是更好的选择。
- KVM 平台：「good performance when using bare-metal virtualization, but has a noticeable impact with nested virtualization」，performance 文档写的是「runs poorly with nested virtualization」。在没有 `/dev/kvm` 的客户虚机里根本起不来。
- ptrace 平台：「no longer supported and is expected to eventually be removed」，**不能当备选**。
- 能跑在 VMware 虚机里是从「不依赖 `/dev/kvm`」推出来的，**官方没有 VMware 专门实测**。

**内核门槛（订正前篇）**
- 官方安装页现在写「gVisor supports x86_64 and ARM64, and requires Linux 5.6+」。
- 门槛来自 commit [a7402ea5de](https://github.com/google/gvisor/commit/a7402ea5de253311ea085d054fc8540eb26af4be)（2026-08-18，标题「Guarantee that `getParentFD()` doesn't follow symlinks」）。**人工复核 diff 确认这不是纯文档改动**：`runsc/fsgofer/lisafs.go` 新增 `unix.Openat2(..., RESOLVE_NO_SYMLINKS)`，`runsc/fsgofer/filter/config.go` 在 gofer 的 seccomp 白名单里加入 `SYS_OPENAT2`，diff 里没有 ENOSYS 回退分支。`openat2` 是 5.6 才有的系统调用，因此**新版本在 4.19 内核上走到这条 gofer 路径会失败**。directfs 默认开启时有多少操作会走到这里，本轮未核实。
- 第一个包含该 commit 的版本是 `release-20260824.0`；最后一个文档仍写 4.14.77+ 的是 `release-20260817.0`。
- ⇒ **4.19 客户若要用 gVisor，只能钉 `release-20260817.0` 或更早，而且放弃后续安全修复**。考虑到 gVisor 没有 LTS、官方推荐 latest，这在长期维护上是明显负担。
- 社区文章称 `release-20250331.0` 在银河麒麟 V10、4.19.90 x86_64 上配置成功，但**没有容器实际运行输出**，只能当弱证据。

**架构**
- 官方只支持 x86_64 和 ARM64，`pkg/sentry/arch` 下只有 amd64 / arm64。
- **arm64 缺少 systrap 的主要加速手段**：x86_64 上会把 syscall 指令改写成跳到 trampoline；arm64 的 `usertrap_arm64.go` 里 `PatchSyscall()` 直接 `return false`，到 2026-08-27 仍未补上。「arm64 更慢」是由此推断，没有 arm64 benchmark。
- arm64 已知问题：#10487（open）Graviton2 上 CPU 密集负载变慢，维护者认为和 SSBS 位有关；#10900（已修）systrap 在 5.4 老内核的 c7gd 上 syscall 返回值出错。
- **鲲鹏 920 / 飞腾没有找到任何人跑过 gVisor 的记录**。
- LoongArch64：社区移植 PR #13332（ptrace 平台，目标银河麒麟 V11）因没签 CLA 被关，未合入。

**LibreOffice / Chromium 兼容性**
- **Dangerzone 是最接近我们场景的一手实现**：
  - 外层 Podman / Docker 容器：`--cap-drop all --cap-add SYS_CHROOT`、`no-new-privileges`、`--userns nomap`、`--network=none`，外加一份放行 ptrace 的自定义 seccomp（`dangerzone/isolation_provider/container.py` 的 `get_runtime_security_args`）。
  - 内层：`runsc --rootless=true --network=none --directfs=false run`，OCI 配置里 capability 全空、rootfs 只读（`dangerzone-image/src/helpers/entrypoint.py`）。
  - LibreOffice 和 runsc 装在同一个 Debian 镜像里。
  - ⚠️ **Dangerzone 两个仓库都是 AGPL-3.0**，只能借鉴做法，**不能拷贝代码或镜像脚本**。
- Chromium / playwright：官方 compatibility 页面没有条目。gVisor 官方博客的 MAGI 多 agent 示例在 gVisor 里跑 Chrome，配置 `"noSandbox": true`；issue #7416 显示有人在生产环境用 gVisor 跑 Chromium。「为什么必须 `--no-sandbox`」只找到二手解释。

**性能**
- 官方 performance 页**已过时**：测的是 ptrace 平台、n1-standard-4 虚机，文档自己声明不能代表 systrap，**不宜拿来判断**。其中通过 Docker 启动空容器 runsc 1,144ms、runc 1,193ms，说明启动时间主要耗在 Docker 本身。
- directfs（现为默认）：stat 快 2 倍以上，真实负载快约 12%，Ruby 加载快约 17%。rootfs 默认 `--overlay2=root:self`，写入落在文件支撑的 tmpfs 上，不占内存。
- **systrap 下 runsc 冷启动与 IO 开销没有一手数值**，必须 POC 实测。soffice 转换和 Python 大量 import 这两类负载 IO 和 syscall 都密集，是最可能变慢的地方。

**接入与离线**
- Docker：`sudo runsc install` 写 `/etc/docker/daemon.json`，compose 里写 `runtime: runsc`。
- K8s：containerd 配 `runtime_type = "io.containerd.runsc.v1"`，RuntimeClass 写 `handler: runsc`。
- 离线：发布包含 `runsc`、`containerd-shim-runsc-v1` 和 `gvisor-bin/`。`gvisor-bin/` 是 2026-07 起新增的 sidecar 目录，**必须和 runsc 放在一起**；缺文件时 `runsc install` 会尝试联网下载，离线包必须带全。
- 权限：安装需要 root。rootless Docker 至今不可用（issue #12575 未关）；`--rootless` 基本只适用于 `runsc do`，而且不支持 checkpoint/restore。

**checkpoint/restore 能否用于提速**
- 能力：`runsc restore --background` 可以先恢复内核状态让程序跑起来，内存在后台加载；应用可通过 `/proc/gvisor/checkpoint` 在自选时机触发快照。但 **Docker 只能恢复到原来那个容器，不能恢复成新容器**。
- 生产用例：
  - Modal 基于 runsc，restore 比正常启动约快 2.5 倍，`import torch` 从约 5s 降到 p50 1.05s；
  - GKE Pod snapshots 必须开 GKE Sandbox，恢复要求相同机型系列和 CPU 架构。
- 对 BiSheng：可行，但需要自研编排层，而且和 compose 形态不合，**近期不建议投入**。

**许可证与维护**：Apache-2.0，19,319★，按日期发版（`release-YYYYMMDD.N`，约每周一版），**无 LTS**。

- 来源：https://gvisor.dev/docs/user_guide/install/ 、https://gvisor.dev/docs/architecture_guide/platforms/ 、https://gvisor.dev/blog/2023/04/28/systrap-release/ 、https://gvisor.dev/docs/architecture_guide/performance/ 、https://gvisor.dev/blog/2024/09/23/safe-ride-into-the-dangerzone/ 、https://github.com/freedomofpress/dangerzone 、https://modal.com/blog/mem-snapshots 、https://docs.cloud.google.com/kubernetes-engine/docs/concepts/pod-snapshots

### 4.8 V8 Isolate / WebAssembly：形态不匹配，不推荐

**三项硬需求都不满足**
- **原生二进制**：Wasm 和 V8 里都无法 fork/exec。CPython 官方文档原文「The `subprocess` is importable but does not work」，Pyodide 的 multiprocessing、threading、sockets 能 import 但不能用，所以 soffice、pandoc、playwright 执行不了。
- **带 C 扩展的 Python 包**：
  - Pyodide 314.0.7 自带 pandas、lxml、numpy、Pillow。
  - openpyxl、python-docx、python-pptx 不在自带列表里，但它们是纯 Python wheel，理论上可用 micropip 装（**推断，未实测**）。
  - **PyMuPDF 官方文档写明 Pyodide 构建「currently experimental」「micropip.install() does not work」**；PyPI 上的 `pyemscripten_2025_0` wheel 与 Pyodide 314 的 `2026_0` ABI 能否兼容不确定。
- **产物写回宿主**：langchain-sandbox README 原文「You will not be able to access the files written by the sandbox」。其他方案要写回就得挂宿主目录，隔离随之打开。

**自认不是安全边界**
- workerd README：「WARNING: `workerd` is not a hardened sandbox」，运行可能恶意的代码时「must run it inside an appropriate secure sandbox, such as a virtual machine」；Cloudflare 托管服务额外的纵深防御不在开源版里。
- Deno 官方文档：权限在 JS 层实施；`--allow-run` 派生的子进程「runs … outside the sandbox」；`--allow-ffi` 可绕过权限检查。不可信代码建议再叠 chroot / cgroups / seccomp 或 VM / gVisor / Firecracker。
- isolated-vm：2026-08-07 发布 **Critical** 漏洞 GHSA-864f-rcv7-6rh4（ExternalCopy type confusion，沙箱内代码可破坏宿主内存、劫持控制流），影响 ≤ 7.0.0，修复于 7.0.1 / 6.2.0。根因在 C++ 胶水层，V8 isolate 边界本身没被攻破。README 自称「maintenance mode」，许可证 ISC。

**信创不兼容**
- workerd 最新版 v1.20260914.1 的 Linux 预编译包只有 x86-64 / arm64，**要求 glibc 2.35+**；麒麟 V10 SP3、UOS 20 都是 2.28，直接跑不起来。
- workerd、Deno（v2.9.6）、Wasmtime（v48）都**没有 LoongArch 官方构建**。

**LangChain 自己已放弃这条路线**：langchain-ai/langchain-sandbox（Pyodide + Deno）于 **2026-01-14 归档**，README 写明不建议用于生产，改推 sandbox API 或 LLM 厂商 API；每次运行启动有「few seconds of latency」。

**WASI 路线**
- CPython `wasm32-unknown-wasip1` 是 Tier 2 平台，但 PEP 816 只支持 WASI 0.1，线程要等 WASI 0.3.1，subprocess 同样不可用；没有标准化的 WASI 版 C 扩展分发渠道。
- Wasmtime 能用 `--dir` 按目录授权读写宿主文件，这点比 Pyodide 顺手。
- Wasmer 靠非标准的 WASIX 支持 numpy、pandas，但没有 LibreOffice 和 PyMuPDF。

**局部适用的子场景**：只跑纯 Python 或 pandas 计算片段、不需要子进程和网络时，Pyodide 或 Wasmtime 可以当低成本前置执行器。但它**替代不了主沙箱**，而多维护一套执行后端的成本明显高于收益，**不建议做**。

### 4.9 nsjail / bubblewrap：适合当「容器内第二层」，但代价是放宽容器

**基本事实**
- **nsjail**：只用 namespaces、cgroup（v1 / v2）、rlimits 和 Kafel seccomp-bpf，不依赖 KVM。Apache-2.0，README 末尾注明「This is not an official Google product」。3.5（2026-03-05）、3.6（2026-03-18），最近 push 2026-08-27。
  - README 没有统一的最低内核版本，只有按功能的门槛：cgroup ns 4.6、`SECCOMP_FILTER_FLAG_LOG` 4.14、time ns 5.3、core scheduling 5.14；新 mount API 要 6.3，低于 6.3 自动走 legacy 路径。**按源码推断 4.19 能跑核心功能，未实机验证**。
- **bubblewrap**：`bubblewrap.c` 头部标 `SPDX: LGPL-2.0-or-later`。按独立二进制 exec 调用时，调用方代码不被传染；**但随私有化包分发 bwrap 本身时要附许可证并提供源码**，改过 bwrap 还要公开改动。0.12.0 已移除 setuid 模式。
- **OpenAI Codex CLI 生产实践**（`codex-rs/linux-sandbox/README.md`）：
  - 「Bubblewrap is the default filesystem sandbox」，Landlock 降为「explicit legacy fallback」；
  - 需要能创建 user namespace，不能创建时启动阶段就告警；
  - 系统里没有 bwrap 时回退到随包自带的二进制；
  - 受限容器里可用 `--no-proc`。
  - ⇒ 生产级 agent 沙箱**可以不依赖 Landlock 和它的 5.13 门槛**。

**关键冲突：和加固容器叠加时，必须先放宽容器**
- Docker 默认 seccomp profile（一手 `moby/profiles/seccomp/default.json`）中，`unshare`、`setns`、`mount` 以及带 namespace 标志（掩码 `0x7E020000`）的 `clone`，**只有容器拥有 CAP_SYS_ADMIN 时才放行**；`clone3` 直接返回 ENOSYS。
- 需要纠正一个常见误解：`cap_drop: ALL` 本身并不禁止创建非特权 userns。真正挡住的是三样东西：**默认 seccomp、docker-default AppArmor、runc 对 /proc 的屏蔽**。
- bwrap 在没有特权的 Docker 里会报「No permissions to create new namespace」，维护者表态这不是 bwrap 的 bug（containers/bubblewrap#505）。
- nsjail 的 README Docker 示例直接用 `--privileged`，不开特权要么 root 运行加 `--disable_clone_newuser`，要么宿主开启非特权 userns。注意 `kernel.unprivileged_userns_clone` 是 Debian/Ubuntu 补丁参数，主线和 RHEL 系用 `user.max_user_namespaces`。
- Coder 文档里「至少需要 CAP_NET_ADMIN」说的是它自家 Agent Firewall 模式（要配 veth + iptables），不是 nsjail 的通用要求；CAP_SYS_ADMIN 只建议 testing 用。
- ⇒ 在容器里套 nsjail / bwrap，要么给 CAP_SYS_ADMIN，要么自定义 seccomp 加 AppArmor 放开 namespace 相关调用。**这等于先削弱外层**；而放开 userns 会把一大块内核代码暴露给非特权进程，历史上很多提权 CVE 都要先创建 userns。

**信创可得性**
- 麒麟 Server V10 SP3 软件源里 x86_64 / aarch64 / loongarch64 三个架构**都有 `bubblewrap-0.3.3`**（版本很老，不支持 `--argv0`）；loongarch64 还有 `libseccomp-2.5.0`（上游 2.6.0 才支持 LoongArch，应是厂商补丁版）。
- **nsjail 在龙芯上不能直接编译**：Kafel 的 `src/common.h` 在未知架构上直接 `#error "Unsupported architecture"`，也没有 loongarch 的 syscall 表。
- 麒麟桌面版源返回 403、UOS 源返回 401；两者的 `max_user_namespaces` 默认值查不到一手来源，**只能到目标机上 `sysctl` 实测**。

**LoongArch 上的 seccomp**
- 主线内核 v5.19 合入 LoongArch 时已有 `HAVE_ARCH_SECCOMP_FILTER`；libseccomp 2.6.0（2025-01-23）加入 LoongArch；moby/profiles 于 2025-10-15（commit 8a3110624）加入 `SCMP_ARCH_LOONGARCH64`，moby/moby PR #45302 仍 open。
- **风险**：Gentoo wiki 指出麒麟 / UOS 的龙芯版属于「旧世界」ABI，与上游「新世界」不兼容。4.19 厂商内核上 seccomp 和 Docker 默认 profile 是否真的生效，**必须实机验证**。

**判定**
- ① **不作为容器替代**：替代容器意味着宿主机跑 root 守护进程，或 K8s 用 privileged Pod，破坏交付形态。
- ② **不建议作为容器内第二层**：如果坚持一次会话一个容器，更划算的做法是**直接收紧容器自身的 seccomp profile**（在默认 profile 基础上再禁掉 ptrace、bpf、io_uring、keyctl 等），不必套娃。套娃只在「一个容器复用给多个任务，或和 Agent 凭据放在同一容器」时才有收益，而这两种设计本身就该避免。
- ③ **对 4.19 内核加龙芯客户，基本多不出有效隔离层**：namespace 和 seccomp 与容器共用同一内核，内核被提权时两层一起失守；老内核上开 userns 反而扩大攻击面。

- 来源：https://github.com/google/nsjail 、https://github.com/containers/bubblewrap 、https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md 、https://github.com/moby/profiles/blob/main/seccomp/default.json 、https://github.com/containers/bubblewrap/issues/505 、https://update.cs2c.com.cn/NS/V10/V10SP3/os/adv/lic/base/loongarch64/Packages/ 、https://github.com/google/kafel/blob/master/src/common.h 、https://github.com/seccomp/libseccomp/blob/main/CHANGELOG 、https://github.com/moby/moby/pull/45302

### 4.10 自研路线：就是默认档的实现方式，风险在工程细节

「自研」在本篇里指「在加固容器之上自建 code-runner」，也就是前篇路径 A（约 20–30 人天）。本轮补充了现成实现的核验和风险清单。

- **llm-sandbox（vndee/llm-sandbox）**（源码核实 HEAD `eedb05b`，2026-09-14）：MIT，后端支持 Docker / Kubernetes / Podman。能力齐全，但**默认值、池、常驻会话都和我们的加固要求冲突**，不能开箱即用：
  - **维护**：1,120★；最新 release 0.3.44（2026-08-03）；vndee 一人 553 次提交，排第二的是 dependabot（29 次），巴士系数 1 不变。
  - **前篇未决两项已从源码确认**（未实测）：
    - `runtime_configs` 通过 `container_config.update(...)` 原样传给 docker-py（`docker.py:383-384`），`runtime="runsc"`、`cap_drop`、`network_mode`、`read_only`、`mem_limit`、`pids_limit` 都能透传；
    - `copy_to_runtime` 只检查容器存在（`core/mixins.py:173-176`），**session 打开后可随时调用**，技能包挂载时序可控。
  - **默认不安全**：
    - Docker 创建容器写死 `"user": "root"`，不加任何限制；K8s 默认 Pod 为 `runAsUser: 0`（`kubernetes.py:447-456`）。
    - 「严格模式」PR #169 自 2026-05 起一直 open 未合入；K8s 的 SA token 自动挂载与出网问题（#170）也 open。
  - **`security` 模块不是隔离手段**：它是正则代码扫描策略（`SecurityPolicy`）加包名校验。另有人于 2026-08-08 称在 `SecurityPolicy` 扫描路径发现漏洞、等待私下披露（#210）。
  - **与非 root + cap_drop ALL 可能不兼容**：非 root 时，复制文件后它以 root `chown -R` 且不检查返回值（`docker.py:211-214`）。去掉所有 capability 后 root 无 CAP_CHOWN，推断会静默失败，导致非 root 用户写不了复制进去的文件，**需实测**。
  - **`InteractiveSandboxSession`（常驻 IPython）**：
    - `open()` 无条件执行 `pip install ipython`（`interactive.py:292-301`），断网环境必须把 ipython 预装进镜像（推断已安装时 pip 不联网）。
    - 执行采用文件投递：`put_archive` 写入命令 JSON，每 0.1s 一次 `docker exec test -f` 轮询结果，再取回、删除（`interactive.py:381-414`）。每次调用都有若干次 docker exec 开销。
    - 默认单次超时 300s。
  - **容器池**：
    - 默认 `max_container_uses=None`、`max_container_lifetime=3600`，归还时只判断是否过期，**不清理工作区**（`pool/base.py:278-309`）。⇒ 默认跨任务复用会有残留，必须设 `max_container_uses=1`。
    - 常驻会话不支持池化（`interactive.py` 里没有任何池相关逻辑，`PooledSandboxSession` 只提供 run / execute_command / copy）。⇒ **预热池和常驻解释器不能同时开箱即用**。
  - **结论**：前篇估算的「用 llm-sandbox 可省 5–8 人天」偏乐观，加固参数、池策略、常驻会话与池的组合、断网依赖都要自己补。**倾向自研 `ContainerExecutor`**，并借用其 MIT 源码中的文件复制与 IPython runner 实现，不把它作为运行时依赖。
- **GPL 陷阱**：Judge0 是 **GPL-3.0**；它的隔离层 ioi/isolate 是 **GPL-2.0-or-later**，依赖 cgroup，默认 root 运行；piston 代码是 MIT，但镜像打包了 isolate 的 fork。私有化交付属于「分发」，会触发 GPL 义务。
- **主要工程风险**：
  1. **池化复用残留**：复用容器时 /tmp、后台进程、环境变量清理不干净会跨任务泄漏。⇒ 池里只放**没用过**的容器，用完即销毁，绝不回池。
  2. **资源控制**：要同时适配 cgroup v1 / v2（4.19 以 v1 为主）；要防 fork bomb、防 tmpfs 写满；PID 1 要回收僵尸进程；超时后要清理并回收结果。前篇 POC 已测出 4 路并发时 soffice 的内存下限是 384Mi，OOM 时报错完全指不到内存。
  3. **两套编排**：compose 路线要挂 docker.sock，这等同宿主 root，**控制面必须和执行面隔离**，不能让执行容器摸到 docker.sock（前篇已点名 RAGFlow 的 `privileged + docker.sock` 反例）；K8s 路线冷启动秒级，还要配 RBAC。
  4. **多节点**：输入输出文件必须走对象存储，不能依赖本地盘（宪法 C8）。
  5. **多架构镜像**：LibreOffice、Chromium / Playwright 在 loongarch64 上能否拿到可用构建，本轮**未核实**，需单独立项确认。
  6. **离线**：`network: none` 与模型现场 pip install 冲突，需要预置离线 wheel，并在工具描述里如实告知模型。
  7. **安全维护**：自定义 seccomp profile 要按架构维护，龙芯旧世界的 syscall 号尤其要注意。

## 5. 速度：隔离技术能帮任务模式提速多少

**先看瓶颈在哪**。这是 2026-08-09 在 180 POC 环境做的一次内部复盘（会话「帮我生成一个思源电气的 ppt」，总时长 56 分 29 秒，净机器时间 45.6 分钟）：

| 耗时来源 | 量级 | 与沙箱隔离技术的关系 |
|---|---|---|
| 容器没装 node，模型把 Node 工具链手工移植成 Python，重试 7 版 | **18 分 13 秒**（最大单因） | 无关，属于**镜像工具链是否完整** |
| LLM 首 token 延迟（TTFT）累计 | 650 秒（平均 6.08s） | 无关 |
| 上下文 168k 时触发的 summarization | 213 秒（单次） | 无关 |
| 11 次 429 限流重试 | — | 无关 |

**再看执行器每次调用的开销**：
- 当前 local 执行器每次调用都 `subprocess.Popen([sys.executable, file])` 新起一个进程（`local_executor.py:196-210`），没有常驻解释器。
- 本机实测（i9-9880H、backend `.venv`、磁盘缓存已热）：空 Python 启动约 0.02–0.04s；**`import pandas, openpyxl, docx, pptx, fitz, matplotlib.pyplot` 每次约 1.4–1.7s**。首次运行 31s 是冷缓存和 pyc 编译，不计入。
- 每次文档转换也要冷启动 soffice，这部分本轮未测。

**结论：隔离技术的选择对任务模式整体速度影响很小；提速要靠执行环境的「形态设计」。**

| 提速手段 | 预计收益量级 | 是否依赖隔离技术 | 建议 |
|---|---|---|---|
| **镜像工具链一次补全**（node / npm、defusedxml、poppler-utils、zip / unzip，统一字体） | **分钟级**：消除模型绕路 | 否 | **P0**，前篇已列，与选型无关 |
| **常驻解释器**：会话内复用 Jupyter kernel 或 `InteractiveSandboxSession`，避免每次重新 import | 每次调用省约 1–2s，一个任务几十次调用累计可达**分钟级** | 否 | **P1**，默认档一起做。注意状态残留：模型上一轮的变量会留在内核里，工具描述要讲清楚 |
| **会话级常驻容器 + 懒启动**（OpenHands 模式） | 每次调用省去容器启动（秒级） | 否 | P1，和常驻解释器一起落地 |
| **预热池**（提前创建未用过的容器） | 每会话首次调用省去容器启动（秒级） | 否 | P2，并发高的客户再开 |
| **soffice 常驻 listener**（例如 unoserver 一类方案） | 每次转换省去 soffice 冷启动（秒级，**未实测**） | 否 | P2，先 POC 量化；要注意常驻进程崩溃恢复和多会话串扰 |
| 快照 / fork 克隆（Clone、sandlock、CubeSandbox、gVisor C/R） | 在已有预热池基础上再省**毫秒到秒级** | **是** | **不建议投入**：前三者进不了交付形态；gVisor C/R 需要自研编排，而且 Docker 只能恢复到原容器 |

**隔离层本身的速度代价**：
- runc 容器的 syscall 开销接近原生。
- gVisor systrap 在 syscall 密集、文件 IO 密集的负载上会变慢，soffice 转换和 Python 大量 import 正是这两类负载；arm64 还没有 syscall patch 加速。**官方没有 systrap 的开销数值**，所以升级档 POC 必须和 runc 对照测：大量 import 的 Python、soffice 转 docx / xlsx / pptx、pandoc。
- **不能拿厂商的毫秒级启动数字推断任务模式会变快**：那些数字都是裸金属、最小模板、池化快照下测的，而任务模式单次任务是分钟到小时级。

## 6. 分档推荐与落地建议

### 6.1 P0：与选型无关，先止血（前篇已列，本轮复核仍未完成）

- **Fernet 密钥外置**：`settings.py:22`。
- **`_child_env()` 改为白名单**：只透传 PATH、LANG、HOME、MPLCONFIGDIR 等必要变量，**不要用 `os.environ.copy()`**。验证方法：执行器子进程的 `/proc/<pid>/environ` 不含 `BS_MINIO_*`。
- **去掉 `docker-compose.yml` backend / backend_worker 的 `seccomp:unconfined`**，并给执行负载加 cgroup 限额。
- **镜像工具链补全**：node / npm、defusedxml、poppler-utils、zip / unzip。

### 6.2 默认档：加固容器执行后端

在前篇「中期」方案（`ContainerExecutor`，20–30 人天；或 llm-sandbox 省 5–8 人天）基础上，本轮新增以下要求：

1. **生命周期按会话，不按调用**：一个灵思会话一个执行容器，首次调用时懒启动，会话结束或空闲超时后销毁。容器打上 label，服务启动时清扫孤儿容器。设置并发上限，超出时暂停最旧的容器（参考 OpenHands V1）。
2. **常驻解释器**：容器内保持一个 Python 内核（Jupyter kernel 或 llm-sandbox `InteractiveSandboxSession`），避免每次重新 import。
3. **预热池只放新容器**，用过的容器绝不回池（防止残留泄漏）。
4. **收紧 seccomp，不套娃**：在 Docker 默认 profile 基础上额外禁掉 ptrace、bpf、io_uring、keyctl 等，**不引入 nsjail / bwrap 做第二层**。
5. **控制面与执行面隔离**：执行容器不挂 docker.sock，不接入中间件网络；compose 路线由独立的受控组件持有 docker.sock。
6. **隔离运行时做成配置项**：compose 的 `runtime` 字段、K8s 的 `runtimeClassName` 从一开始就留成可配置，为升级档留开关。
7. **沙箱内看得到完整工作区与技能包**：不要走「只把单个工具 RPC 转发进沙箱」的路线（OpenHands #4883 的教训）。

### 6.3 硬隔离升级档：gVisor systrap

- **适用范围**：x86_64 或 arm64，且内核 ≥ 5.6（例如 UOS / 麒麟 5.10）。4.19 客户原则上**不进**这一档；确有需要时钉 `release-20260817.0`，并书面说明放弃后续安全修复。
- **接入方式**：compose 用 `runtime: runsc`（宿主 root 执行 `runsc install`），K8s 用 RuntimeClass `handler: runsc`。离线包必须同时带 `runsc`、`containerd-shim-runsc-v1`、`gvisor-bin/`。
- **资源限额**仍靠宿主 cgroup 兜底（前篇已引用官方「resource limits are not enforced within the sandbox」）。
- **Chromium / playwright** 预期需要 `noSandbox`。
- **版本管理**：gVisor 无 LTS，需要自己建立「钉版本 + 定期升级回归」的节奏。
- **前置条件**：§8 的 POC 1–2 通过。估算 +3–5 人天（沿用前篇），arm64 实测另计。

### 6.4 观察档：KVM 客户

CubeSandbox 和 microsandbox **不接入**，每季度复查一次。复查条件：
- CubeSandbox：K8s 转正、有完整离线安装指南、README 性能数字与 benchmark 口径统一；
- microsandbox：发布 1.0、商业化路线明朗。

### 6.5 不推荐（附一句理由，方便评审时引用）

| 方案 | 理由 |
|---|---|
| Clone | KVM + 仅 x86_64 + 0 个 release |
| sandlock | 5.13 以下内核拒绝启动，无降级路径；龙芯上编译不过 |
| CubeSandbox PVM 路线 | 需要替换客户宿主内核为 OpenCloudOS 定制 6.x；仅 x86_64；VMware 上有 panic 报告 |
| V8 Isolate / Wasm | 跑不了原生二进制；workerd 要 glibc 2.35+；LangChain 已归档同类项目 |
| OpenHands 直接集成 | V0 runtime 已删；V1 agent loop 与 deepagents 重叠；要求 Python 3.12；加固能力在 PolyForm 商业许可部分 |
| agent-infra/sandbox 作为隔离方案 | 隔离边界是普通容器，官方示例关闭 seccomp，定位 trusted local development |
| nsjail / bwrap 替代容器或作第二层 | 需要放宽外层容器的 seccomp / AppArmor；对 4.19 加龙芯无增量 |
| gVisor KVM / ptrace 平台 | KVM 在嵌套虚拟化下性能差、无 `/dev/kvm` 起不来；ptrace 已停止支持 |
| Judge0 / isolate | GPL-3.0 / GPL-2.0+，私有化分发触发义务 |
