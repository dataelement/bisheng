# Sdd Test Cases

先读 [阶段交接规则](../sdd-workflow/references/stage-contract.md)，按风险使用 [用例方法](references/case-methods.md)。涉及 mock、接口／功能测试或真实环境安排时使用[测试环境与证据策略](references/test-strategy.md)。
生成、改写或评审正式用例时，使用 [测试用例写作与完成标准](references/case-writing-standard.md)，按其四部分结构输出 HTML。

## 输入与时机

业务用例以当前已确认需求及验收条件为依据，需求闭环后即可设计，无须等代码。
接口、协议、数据库和集成用例等，在相关契约明确后补充；没有契约时保留待补项，不猜接口。
复杂 Bug 或简单修复可用已有预期和缺陷证据设计针对性回归，不强制完整需求文件。

用例的对象、数据、状态和断言沿用本次需求／契约对应的术语基线与已确认增量。按[领域语言约定](../sdd-workflow/references/domain-language.md) 区分同义名、不同生命周期对象和技术映射；规则分歧回到相应阶段，不另起一套测试定义。

## 岗位用途与代码位置

按[产物存放与维护约定](../sdd-workflow/references/artifact-storage.md) 沿用稳定特性标识和来源登记，先确定本次岗位及目标工程，再解析用例位置。研发用例登记在本次研发产物来源中；QA 用例与结果归独立验收工程，通过仓库／版本／路径或可访问制品引用关联。
按调用任务明确用途：sdd-workflow 内默认研发验证；测试工程师或 sdd-acceptance 调用时为独立验收。同一套需求和验收条件可关联两岗位用例，但完成状态分别记录。
研发用例指导各前后端项目 test/ 下的单元、接口和非 UI 业务功能测试。独立验收用例、UI／真实集成／E2E 脚本由测试岗位在指定的独立验收工程维护，不混入应用 test/。
需求闭环后测试岗位可提前设计验收场景，无须等待代码稳定；这不触发 UI 或真实环境执行。研发可交付验收场景建议，不自动替测试岗位生成或执行独立验收代码。
归档和交接按[岗位协作与提测规则](../sdd-workflow/references/qa-handoff.md)，共享来源与标识，避免维护两套互相漂移的业务规则。

## 方法

建立“需求／验收条件 → 风险 → 场景 → 预期 → 验证层”映射。
选择相关的成功、失败、边界、权限和状态场景；并发、重复请求、重试、容量等根据实际风险启用。
预期来自需求和契约；当前实现仅用于核对入口和可执行性。关键断言或弱测试疑点按[独立预期与有效反馈](references/assertion-quality.md) 核对，不用实现的同一算法生成期望值。发现规则不明时返回需求阶段，发现契约不清时返回设计。
每个用例给出稳定标识、来源和风险、负责岗位、目标工程、前提、数据、步骤、可观察结果、必要清理、自动化候选层级、执行阶段、环境模式及真实／替身边界。
每条只验证一个明确意图，具有标题、P0／P1／P2 优先级和规定类型；数据与编号原子步骤分离。独立建立前提，不依赖其他用例先执行。预期来自已确认规则，包含适用副作用，能够二值判定；必要的多个断言可以共同验证同一意图。

执行阶段分为开发期 mock／隔离验证与开发完成后的真实环境验收。开发期按需安排单元、接口、功能和契约测试，不把全部功能场景推迟到验收。真实部署 E2E 和昂贵的真实依赖验证后置到 CI／共享验收环境；提前生成用例不代表提前部署环境。
UI 功能用例可在需求闭环后设计并随交互规则细化；执行继续按当前单独约定后置，mock 后端的 UI 也不因允许后端模拟功能测试而自动执行。

选择能验证目标的最低成本可信层，优先保留真实被测业务、路由和权限规则，隔离昂贵外部依赖。替身基于已确认契约；不要 mock 掉被验证机制，不把模拟业务链路称为真实 E2E。
检查断言是否覆盖必要状态、副作用与拒绝后无额外写入。代码覆盖率不能替代业务断言。
复用已有有效用例；需求变化时只更新受影响部分。

## 专业复核与完成标准

按 [HTML 交付约定](../sdd-workflow/references/html-delivery.md) 交付本岗位的实际 HTML 用例文档，关联需求版本与稳定 REQ／AC；可配套机器可读数据，不以测试脚本、Markdown 或聊天摘要代替。用例定义、评审状态和各次运行结果分别记录，未执行不能填通过。HTML 文档不改变两岗位代码工程和执行阶段。
输出覆盖概览矩阵、规定九列的用例清单、异常与边界专项清单、自动化可行性标注。逐条核对验收条件和本岗位必要场景，检查单一意图、独立前提、具体数据与边界值、明确断言及副作用；缺规则或必要契约时记录待补，相关定义仅为草稿，不标记已就绪。
通过独立需求推导、不同检查视角或独立评审补查遗漏；说明实际采用的复核方式，不把作者自评称为独立审核。
本岗位用例就绪表示对应定义完整且必要契约已补足，不表示测试已经通过；另一岗位的用例和执行待办独立记录，不自动阻塞本岗位已完成的范围。
交付本岗位的需求映射、模拟边界、执行前提和剩余缺口；研发交接验收建议，测试岗位独立补充和复核，不能把作者自己的开发用例直接当作已完成独立验收。
新增测试代码的框架与入口从项目实际配置确认。
