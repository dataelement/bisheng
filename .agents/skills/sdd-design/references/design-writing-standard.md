# 设计文档写作与完成标准

按[领域语言约定](../../sdd-workflow/references/domain-language.md) 标明选定词典基线和本次已确认增量；补业务概念、模块职责、实体／接口／存储及展示名称的必要映射。图标签与正文共同核对，技术旧名通过兼容映射说明；未实施目标不冒充现状。局部取舍可留本文，跨特性重要决定按需引用同一 ADR，不为每个术语新建决策文件。

## 阅读目标

同一份 HTML 服务不同读者：概览先说明做什么、为什么、改变哪里、重要风险和待决事项；工作机制用业务语言解释成功与失败；技术细节保留研发实施所需的精确内容。非技术读者应能复述方案与失败结果，研发不必猜关键业务决定，测试能找到可观察验证点。
首次出现的术语用通俗语言解释，保留准确技术名称及必要术语表。业务图使用角色与动作名称；技术图可附真实模块、接口和数据对象名，不能为通俗而丢掉代码对应关系。概览中也要说明重要失败结果，不把所有风险藏在折叠区。

## 模板与结构

使用 [HTML 模板](../assets/design-template.html)，保留其分层阅读、可见图示、可展开技术细节、宽表滚动及打印安排。模板是可填写资源，不是具体方案；填写实际内容，移除无关示例和撰写提示。未解决内容改成编号问题及影响，不能留下没有含义的占位符并称已完成。保持 [HTML 交付约定](../../sdd-workflow/references/html-delivery.md)。

完整设计按以下顺序组织；短小修复可合并相关部分，保留适用依据和结论，不为形式制造方案或重建无关 PRD：

| 部分 | 内容与证据 |
|---|---|
| 方案摘要 | 通俗说明目标、主要改变、受影响方、关键选择、重要失败结果、当前状态及待决事项；上线时间未定时如实说明 |
| 依据与范围 | 有效 PRD／REQ／AC、需求确认依据、代码／配置／契约基线和证据类型；本次改变、不做、沿用；关键正确性约束及其保证／验证映射 |
| 现状及目标架构 | 已核实入口、调用与组件职责、目标差异、数据与信任边界；有价值的业务概览图与对应技术图 |
| 核心流程与状态 | 前提、步骤、结束状态、副作用；相关成功、明确失败、超时结果未知、部分成功、重复、并发及恢复；资源释放责任 |
| 关键决策 | 真实可行选项、依据、取舍、推荐与代价、适用／重审条件；建议、已决定和待决定分开，实际确认对应版本 |
| 详细契约 | 适用模块、接口字段／错误／权限／兼容、数据与事务／外部副作用边界、安全、资源、性能和可观测性；按实际风险选用表格 |
| 影响与依赖 | 使用方、上下游、配置、迁移、历史数据、版本兼容及上线顺序；责任和未知明确 |
| 验证安排 | REQ／AC → 设计安排／模块 → 验证方法／既有用例 → 岗位 → 阶段／环境与真实／替身边界；未知不能用假用例 ID 补齐 |
| 发布与恢复 | 可部署前提、启用与观测、暂停／回滚条件、代码／配置／数据及外部副作用恢复边界；环境与能力以实际证据为准 |
| 待决事项及变更记录 | 问题编号、事实缺口／需人决策、影响和依赖；自检依据、审核发现、真实确认记录、版本与受影响 REQ／AC／用例 |

## 图解与选图

复杂难懂的知识点、关系和流程优先图解，再用文字与表格补足准确条件。按 [图解与选图方法](diagram-methods.md) 将本次难点映射到适用图类型，记录目的、位置、相关依据及选择理由；概览和细节分层，关键失败结果也需易读。按场景选图，不画齐所有类型，不用概览图替代时序、状态等关键细节。
图与正文、需求／INV、契约、状态及部署边界保持一致；正式 HTML 显示实际图形，移除占位。已有图可复用其有效版本，简单修改可简述。

## 正确性约束与保证

在确定关键机制前，从已确认需求和契约提取本次必须守住的规则（正确性约束），可以用稳定 INV 标识，不另造一套业务定义。只列与本次变化和风险有关的关键规则；简单局部修复可以用简短记录表达，不要求凑数量。

每条至少说明：**规则及需求／契约来源 → 适用对象、条件、作用范围与时间窗口 → 负责模块及保证机制 → 相关失败／并发下如何保持或恢复 → 可观察验证方式与证据限制**。相关设计和验证表引用同一条约束，避免互相矛盾。

先写必须得到及禁止出现的结果，再说明机制如何保证；“加锁”“幂等”“校验权限”等术语本身不能代替保证。例如已确认要求不允许重复生效时，说明如何识别同一次业务动作、去重范围／窗口、原子性边界和冲突返回。业务规则不清回到需求，机制或契约不清回到设计调查，不从当前错误实现倒推出正确规则。
区分始终成立的约束、合法中间状态和限定窗口内最终达到的结果。明确哪个资源、用户、进程／节点和外部边界受保证；本地锁或模拟仓库不能证明跨进程／真实存储保证。“拒绝无业务写入”与允许的审计／指标等副作用分别定义，不擅自扩大为系统任何地方均不许写入。
逐条推演相关正常、失败、超时、重复、并发和取消路径；不适用说明理由。机制要与检查／状态改变发生在同一有效边界，避免用“先检查再写入”直接宣称并发安全。缺少原子操作、状态核实或恢复能力的证据时，标出实际缺口；不能用 mock 成功或待验收计划宣称已证明真实保证。

## 严谨性规则

- 目标指标沿用已确认 PRD，设计补充实现与测量办法；引用同一来源，避免复制成两套可独立变更的业务目标。实测、目标、估算、建议、假设和未知分开，保留来源、负载／单位和适用条件。没有证据不编数字、工期、灰度比例或系统能力。
- 有实际取舍时比较选项；只有一个满足约束的方案时解释约束，不强制至少两个。比较成本和风险时给出具体原因及边界，避免仅用“低、中、高”得出结论。
- 主流程图不能替代状态与异常定义。超时仅说明未在规定窗口获知结果；是否已生效要依据实际协议确定。结果未知、明确失败和部分成功分别给出核实、恢复与负责方，不能默认所有失败都能自动撤销。
- 明确适用的事务、锁／并发、重复动作、重试、取消、连接／任务等资源所有权与释放。业务结果、真实存储状态和外部已发生动作分别判断；代码回滚不自动恢复数据或外部副作用。
- 容量、安全、合规等按需求和风险决定深度。每项关键检查给出适用性、依据、发现与处理状态；涉及权限或敏感数据的关键缺口可阻塞交付，不固定将安全放到低优先级，也不把所有局部修复都要求容量估算或灰度设施。
- 验证安排沿用两岗位分离：研发在对应项目 test/ 运行所需 mock／隔离单元、接口、非 UI 功能和契约测试；测试岗位在独立工程验收 UI、真实依赖及部署 E2E。方案与文档检查不能自动发起产品验收。

## 完成与确认

逐条核对：相关需求有设计安排；关键正确性约束有可靠来源、作用边界、保证机制、适用失败／并发推演及验证方式；复杂难点有适用图解且图文及契约一致；关键机制、契约、状态与失败处理明确；重要取舍有理由；验证、影响及恢复边界可查；非技术阅读与专业接手均可进行；阻塞问题已处理。关键规则或保证缺失时相关范围保持草稿，应用实际自查／独立复核，记录证据及独立性限制。
专业自查、独立复核和用户确认分别记录。额外独立复核是否为就绪前提，依据项目规则和本次已识别风险确定；未要求额外复核且本段检查满足时，可基于需求／契约／源码交叉检查交付“设计就绪，待确认”。需要但未完成的独立复核保留缺口；宿主无法派发 agent 本身不产生新的固定审批节点，作者自查也不冒充独立审核或用户确认。
自检表只记录检查事实，不能勾选即批准。专业检查完成后为“设计就绪，待确认”；只有真实用户确认对应当前内容，才能记为已确认。新设计不继承无内容对应关系的旧确认。模板完整、浏览器检查或 PDF 导出成功不能证明设计业务正确。
检查实际 HTML 的锚点、表格、图示与展开交互；交付含打印能力时核对折叠内容完整展开、文字可读及长表不丢列。对文档使用浏览器／打印检查不等于产品 UI 测试；没有执行的部分如实记录。
