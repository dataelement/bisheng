# 产品需求验证清单

目标是得到合理、闭环、有界、可验收的需求依据。每维给出成立／有缺口／不成立，问题关联证据、编号及建议。不要为填表制造需求没有的能力。

## 合理

核对谁在什么场景完成什么任务、结果有什么价值。用户决定目标和范围取舍，AI 提供事实与建议。
对照相关现有能力，识别重复、规则冲突或术语混用。全新项目使用已有目标和约束，不虚构现网。
发现重要成本、不可逆行为或跨模块影响时说明证据，与用户决定当前范围；不替用户制定产品战略。

## 闭环

检查触发与入口、前提、主成功路径、结束时用户和系统状态，以及失败出口。
“可以提交”需要相关结果和恢复规则；等待、异步、审批等按适用性核对结果接收、超时及取消。
写操作按风险明确用户可遇到的上限、重复提交和并发冲突结果。事务、锁、熔断等技术机制留给设计。
成对行为按业务需要检查另一侧：创建与结束、同意与拒绝、进入与退出等；不把每个动作强制配上没有业务意义的逆操作。

## 边界

明确本次包含、排除、参与者、角色能力、数据归属及可见范围、用户可区分的状态和模块业务职责。
中文角色名与代码身份按目标项目核实，不默认管理员就是超管，不引入参考项目的身份表。
上限可来自本次要求或已核实的现有产品规则，不能仅凭数据库字段长度反推产品约束。
引用或分享资源时核对访问边界；内部原因和对用户披露的信息分别判断。安全策略可能要求隐藏资源存在性，不固定要求某种错误文案或 HTTP 状态。

## 交互与结果可验收

规则能表达为谁在什么前提／状态下做什么、得到什么结果，界面、API、CLI 或后台流程均适用。
选择必要的主路径、空结果、无权限和业务拒绝场景；有状态变化时检查必要副作用。
原型并非一般业务验证的前提；若视觉或交互本身是需求，明确相应验收依据。
需求只覆盖某些角色和状态时，检查相关范围，不穷举整个系统的所有排列。

## 条件式专项

| 需求出现的能力 | 补充检查 |
|---|---|
| 通知／待办 | 谁接收、在哪里处理、何时失效、返回入口的权限 |
| 匿名／隐藏身份 | 需求涉及的列表、详情、搜索、通知等位置是否一致 |
| 引用外部对象 | 选择、保存和再次打开是否对应同一对象，权限是否改变 |
| 用户可见时间 | 时区、到期、延期等业务预期 |
| 批量或重复动作 | 范围、部分成功、重试或重复结果，以及必要的数量约束 |

## 澄清与闭环

阻塞：不决定就会影响四维、核心规则、范围或验收；未解决时不能通过。
澄清：四维已经成立，剩余事项不改变核心验收判断；记录影响并纳入整体确认。
有缺口时向 grilling 提供事实、依赖关系、问题级别和既有决定。答案回写规则，重新检查；访谈完成不自动等于通过。

可交付的需求记录至少能说明：目标与范围、需求标识与验收条件、事实和决定、四维结论、开放问题与残留事项、确认状态。正式需求稿按 [PRD 写作与完成标准](prd-writing-standard.md) 交付 HTML；原始材料的咨询分析不强制重写完整稿。
接受风险不能抹去未满足的标准；用户选择调整范围或规则后重新验证。
