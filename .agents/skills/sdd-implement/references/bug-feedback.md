# 围绕原症状的有界诊断

用于常规定位不足以解释的 Bug；简单问题继续五项准入和最低成本可信验证，不强制经历所有步骤。

1. 说明用户原始触发条件、预期、实际与来源。用获准的日志、真实调用关系及 mock／隔离接口或业务测试建立能抓住该症状的反馈；输入、代码、命令、输出绑定当前内容并脱敏。
2. 先证明反馈针对原问题，尽量减少无关输入与启动成本；不要求慢任务或低频故障必然达到秒级确定复现。偶发问题记录重复次数、失败频率与条件，不用一次通过宣称修复。
3. 围绕证据列出少量可证伪假设，每项写预测与验证办法。能区分假设的探测优先；一次改变一个相关条件，记录实际结果，避免只追逐第一个合理解释。
4. 适合隔离自动化且存在正确入口时，用修复前失败、修复后通过的回归锁定问题，再验证原始未缩减场景及受影响行为。修好旁边另一问题不等于原 Bug 已解决。
5. 临时探测有明确标识并清理，保留根因、修复为何有效、实际证据及剩余未知。没有可信回归入口时说明限制，不制造只测内部替身的浅层测试。

无法取得可信反馈时记录已试方法、缺失材料与判断边界；继续有依据且可逆的调查，不把假设写成根因。反复同类失败、影响扩散或需要真实环境／重要业务决定时报告证据与选择，按风险共同决定下一步，避免无界试错。
研发诊断不启动产品 UI、浏览器、真实部署 E2E 或整套线上环境；需要这些证据的部分交接独立验收。后置证据缺口不伪装为通过，也不阻止可独立完成的隔离验证。
