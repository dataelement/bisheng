1. 背景与问题

用户决定 外部系统经 Open API 写入知识库文件时，希望上传人在界面上体现为业务指定的系统用户，而不是默认落在 admin 或 Token 绑定账号上。

用户决定 鉴权与资源权限仍按现有 Developer Token 规则（绑定用户、IP、路由、限流；Filelib 可选 external_id 切换业务权限主体），不得因新增配置而「对调用方完全放开权限」。

客观事实（源码，非生产统计） developer_token.user_id 为绑定用户；Filelib 写接口通过 get_filelib_request_user 解析请求用户：未传 external_id 时使用 Token 绑定用户作为 login_user，业务写库时的操作者/上传人字段与 login_user 一致。F069 仅覆盖四个只读 Filelib 接口；上传与 file/sync 等写路径不在 F069 规格内，但沿用同一用户解析依赖。

逻辑推演 当 Token 绑定 admin 且调用方不传 external_id 时，上传人记录为 admin，与业务期望不符。需要在 Token 配置层增加独立的「知识上传人」，与绑定用户解耦。

3. 范围

3.1 本次包含

  • Platform：系统配置 → Developer Token 新建/编辑/详情，增加「知识上传人」选人字段（与「绑定用户」并列，文案区分权限 vs 上传人）。
  • 后端：Token CRUD 持久化知识上传人；Admin API 入参/出参携带该字段。
  • Filelib 经 Developer Token 的写接口（设计阶段列完整路径清单；至少包含 multipart 上传与 POST /api/v2/filelib/file/sync 等会创建/登记知识文件的接口）。
  • 写路径规则：权限仍用现有 login_user 解析；仅上传人/创建者类落库字段按本需求决策表写入。
  • 存量 Token：保存/编辑时强制补齐知识上传人（见 REQ-002）。

3.2 明确不做

  • Filelib 只读接口（列表、详情、retrieve 等）：不涉及上传人变更。
  • MCP 工具链、非 Filelib 的 /api/v2 写接口（除非设计阶段发现与 Filelib 共用同一写库入口且属同一落文件语义——须追溯 REQ-004）。
  • 修改 Token 绑定用户、路由白名单、IP、限流、file_sync_rule 的既有语义。
  • 回溯修改历史已落库文件的上传人。
  • 知识门户 BFF、门户侧配置页。

4. 用户场景与流程

4.1 管理员配置 Token

租户管理员在 Platform 打开 Token 编辑，选择绑定用户（接口权限主体）与知识上传人（落库上传人主体），保存后 Admin API 持久化。

4.2 外部系统上传（未传 external_id）

4.3 外部系统上传（已传 external_id）

用户决定 2026-11-06 权限与上传人均使用 external_id 解析出的唯一有效用户（与 F069/F081 对「业务主体」的既有语义一致）；Token 上配置的知识上传人不覆盖该结果。

5. 功能需求

REQ-001 · Token 管理端字段 P0 · 一期

来源：聊天 + Q3。在 Developer Token 新建/编辑表单增加「知识上传人」，必选系统内用户；界面说明：绑定用户决定接口权限，知识上传人决定未传 external_id 时的落库上传人。

字段：知识上传人
名称业务含义类型必填校验默认值
知识上传人 Filelib 写请求未传 external_id 时，写入知识/文件的上传人身份 用户 ID（正整数） 是（新建与编辑保存时） 用户存在、可用；不可与绑定用户相同字段混淆（允许 A≠B 或 A=B，产品不禁止同人） 无

REQ-002 · Admin API 契约 P0 · 一期

POST/PUT /api/v1/admin/developer-tokens 必须接受并返回知识上传人；缺失或无效用户返回明确业务错误，不落库。详情/列表返回展示用用户名（与绑定用户展示方式对齐）。

AI 建议 · 待设计确认 历史 Token 在下次编辑保存时必须补齐知识上传人；仅启用写接口时若库内为空则写接口拒绝（见 REQ-004 异常表）。不在本需求做批量后台回填默认值。

REQ-003 · Filelib 写路径上传人决策 P0 · 一期

决策表 D-UPLOADER
条件权限主体（login_user）落库上传人
有效 Token；未传或空 external_id Token 绑定用户（现状） Token 配置的知识上传人
有效 Token；传合法 external_id 且解析唯一有效用户 解析用户（现状） 解析用户（现状，配置不上传人不覆盖）
external_id 非法/重复/不存在 — —；请求拒绝，无写库副作用（现状）
Token 未配置知识上传人（仅可能存量脏数据） 按现状解析 写接口拒绝；读接口不受影响

REQ-004 · 写接口范围 P0 · 一期

来源：Q1。覆盖 Filelib 模块内所有经 Developer Token 认证、会创建或登记知识文件记录的写操作；设计阶段输出路径清单并与本 REQ 追溯。只读接口排除。

REQ-005 · 权限与 OpenFGA 不变量 P0 · 一期

PermissionService 及资源授权仍基于权限 login_user；不得因上传人写成 B 而让 B 的权限参与本次请求鉴权。上传人 B 仅作为元数据写入与展示。

异常清单（REQ-003/004 共用）

类型场景调用方可见结果落库
权限不足绑定用户（或 external 用户）无目标库写权限拒绝；与现网一致无新文件
配置缺失未传 external_id 且 Token 无知识上传人拒绝（业务码设计阶段定义）无新文件
重复提交与现网 filelib 重复策略一致不适用本需求单独变更按现网
并发多请求并行上传不适用本需求单独变更各请求上传人按决策表独立计算

6. 非功能与依赖

  • 双库：developer_token 加列须 Alembic + DM8 兼容（JsonType 等既有规范）。
  • 多租户：知识上传人选人范围规则在设计阶段与现有 Token 绑定用户选人一致（通常同 Token tenant_id）。
  • 安全：日志不得打印 Token 明文；拒绝响应不泄露无权限资源正文。
  • 依赖：F044 Developer Token、Filelib 写服务链、F069 用户解析（external_id）、F066 file/sync（权限仍绑定用户，上传人字段按决策表与 sync 已有 responsible 逻辑在设计中统一，避免双写冲突）。

7. 数据与埋点

无新增产品埋点要求。运维日志建议可区分 token_id、权限 user_id、写入 uploader_user_id（实现细节见设计），不记录 Token 秘密。

8. 验收标准

AC ID前提动作预期关联 REQ
AC-01 Token：绑定用户=admin(A)，知识上传人=业务用户(B)；未传 external_id 调用 Filelib 写接口成功上传/同步落文件 文件上传人相关字段为 B；列表/详情展示为 B REQ-003
AC-02 同上 管理端保存 Token，知识上传人为空 保存失败，提示必选 REQ-001、REQ-002
AC-03 绑定用户 A 对目标库无写权限，知识上传人 B 有权限 未传 external_id 写上传 拒绝；无新文件；不因 B 有权限而成功 REQ-005
AC-04 绑定用户 A 有写权限；传合法 external_id 对应用户 C Filelib 写上传 权限按 C；上传人为 C（非 B） REQ-003
AC-05 存量 Token 无知识上传人 未传 external_id 写上传 拒绝；无脏行 REQ-003

10. 四维检查结论

维度结论说明

闭环成立配置 → 写请求 → 落库/展示 → 失败拒绝均有出口；存量 Token 编辑补齐 + 脏数据写拒绝。
