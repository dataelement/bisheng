# 升级到 2.5.0-sg（从 2.4.0）

本文按官方《版本升级注意事项》的章节来写，**内容来自代码对比**，不是「升级到 2.5.0」那一节的摘抄。

对比对象：

| | 起点 | 终点 |
|---|---|---|
| Git | tag `v2.4.0` | 分支 `feat/2.5.0-sg`，Alembic head `f058_dashboard_dataset_flags` |
| 镜像 | `dataelement/bisheng-backend:v2.4.0` | `cr.dataelem.com/dataelement/bisheng-backend:2.5.0-sg`（现场钉 digest） |

**结论（先读这个）：** 名字叫 2.5.0-sg，库不是官方 2.5.0。从 `9ba42685e830` 到 `f058` 大约 **128** 个 revision，包含 2.5.0、2.5.1，以及大量写在 `v2_6_0_*.py` 里、已被本分支吸收的表（门户、积分、专家问答、审批 outbox、知识文档版本链、共享存储路由等）。照抄 2.5.0 文档会漏掉这些，也会误跑 2.5.0 里那条工作台 JSON SQL（本仓库没有对应升级脚本）。

前提：2.3 / 2.4 的手工 SQL 和 `type=2` 兼容已经做完。`knowledge.auth_type`、`knowledgefile.file_level_path` 应已存在。

演练机 B 不要手改 compose / 注释 entrypoint。先备份，再跑脚本：

```bash
# 先把整个 bisheng 仓库压缩包解压到 /data/bisheng，2.5 hop 会用其中 docker/ 整份覆盖现场配置。
cd /data/bisheng/scripts/upgrade-ab-fusion
# DRILL 仅演练机可设。P2 hop 跑起来就升级。
export DRILL=1
bash p2/01-freeze-and-backup.sh
bash p2/30-hop-2.5.sh
CONFIRM_F006=0 bash p2/31-f006-workstation.sh
CONFIRM_F006=1 bash p2/31-f006-workstation.sh
bash p2/40-verify.sh
```

compose 文件位置、project 名、`config.yaml` / `entrypoint.sh` 的宿主机路径都由 `lib/discover.sh` 从容器标签和挂载表反查，不依赖 `/data/bisheng-main/docker` 这类约定，换机器无需改脚本。`p2/30-hop-2.5.sh` 会先打印发现结果并断言 MySQL 数据目录非空——卷指错位置时 Alembic 会在空库上一路建表成功，这道断言就是拦它的。

---

## 对比：2.4.0 实际有什么

- **没有** OpenFGA 服务；权限是 RBAC（`roleaccess` 等）。
- **entrypoint 不跑 Alembic**，表主要靠启动时 `SQLModel.metadata.create_all`。树里只有 revision `9ba42685e830`。生产库常常 **没有** `alembic_version`。
- `user`：`user_name` **全局 UNIQUE**；无 `source` / `external_id` / `token_version` / `guid` / `wechat_user_id`。
- **没有** `department` / `user_department` / `tenant` 模型文件。
- `space_channel_member` 在 2.4 代码里已有，靠 create_all，不在 Alembic 里。

2.5.0-sg 的 `user` 增加 `source`、`external_id`、`external_code`、`guid`、`token_version`、`wechat_user_id` 等；`user_name` 不再唯一（f010）。

## 修改 docker-compose.yaml

v2.4.0 compose **没有** OpenFGA。2.5.0-sg 的 `docker/docker-compose.yml` 新增 `openfga-migrate`、`openfga`，backend `depends_on` openfga。

把现场 MySQL 密码填进 URI。生产不要用浮动 `latest`，与目标 2.5.0-sg 同一套 OpenFGA 镜像。

```YAML
  openfga-migrate:
    container_name: bisheng-openfga-migrate
    image: openfga/openfga:latest
    command: migrate
    environment:
      OPENFGA_DATASTORE_ENGINE: mysql
      OPENFGA_DATASTORE_URI: "root:<MYSQL密码>@tcp(mysql:3306)/openfga?parseTime=true"
    depends_on:
      mysql:
        condition: service_healthy

  openfga:
    container_name: bisheng-openfga
    image: openfga/openfga:latest
    command: run
    environment:
      OPENFGA_DATASTORE_ENGINE: mysql
      OPENFGA_DATASTORE_URI: "root:<MYSQL密码>@tcp(mysql:3306)/openfga?parseTime=true"
      OPENFGA_LOG_FORMAT: json
      OPENFGA_PLAYGROUND_ENABLED: "false"
    ports:
      - "8080:8080"
    depends_on:
      openfga-migrate:
        condition: service_completed_successfully
    restart: unless-stopped
```

mysql 的 healthcheck 需能建库（当前 sg compose 已是）：

```YAML
test: ["CMD-SHELL", "mysql -u root -p$$MYSQL_ROOT_PASSWORD -e 'CREATE DATABASE IF NOT EXISTS openfga;'"]
```

```YAML
backend:
  container_name: bisheng-backend
  image: cr.dataelem.com/dataelement/bisheng-backend:2.5.0-sg
  environment:
    BISHENG_DASHBOARD_PRO: "true"
    BS_SSO_SYNC__GATEWAY_HMAC_SECRET: "<与 config.yaml 一致>"
  depends_on:
    openfga:
      condition: service_started

backend_worker:
  container_name: bisheng-backend-worker
  image: cr.dataelem.com/dataelement/bisheng-backend:2.5.0-sg

frontend:
  container_name: bisheng-frontend
  image: cr.dataelem.com/dataelement/bisheng-frontend:2.5.0-sg
```

注意：

- 若 volumes 挂了 **2.4 的 entrypoint.sh**，必须换成 2.5.0-sg 那份（API 启动前有 `alembic upgrade head`）。继续挂 2.4 entrypoint，Alembic 根本不会跑。
- 2.5.0-sg 镜像自带的 entrypoint 是：`alembic upgrade head || echo WARNING...` 然后启动。**WARNING 仍会启动进程，不能当升级成功。**

## 修改配置文件

对照 `docker/bisheng/config/config.yaml`（v2.4.0 无这些块），在现场 `config.yaml` **新增**：

```YAML
openfga:
  enabled: true
  api_url: "http://openfga:8080"

sso_sync:
  gateway_hmac_secret: "请替换为实际密钥"
  signature_header: "X-Signature"
```

代码里 `multi_tenant` 默认 `enabled=false`（`core/config/multi_tenant.py`），docker 默认 config **可以不写**。本窗口不要打开组织同步。

`points:` 等块镜像内配置已有默认值；不要为了「对齐 2.5.0 文档」去改 Gateway 企业微信同步——那不是 2.4→2.5.0-sg 的库升级步骤。

OpenFGA 的 store / model：`core/openfga/manager.py` 在 **API 启动且 enabled=true** 时查找或创建，不是手工 SQL。

## 数据库变更

### 只手跑这一条 SQL

```SQL
CREATE DATABASE IF NOT EXISTS openfga DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

2.5 起的业务表 **不要**对照 2.5.0 文档手写 ALTER。本分支由 Alembic + 启动 `create_all` 共同落表。

### 必须分成两段（代码决定的，不是文档习惯）

`department` **没有**任何 `op.create_table('department')`。  
`f011_tenant_tree` 却对 `department` 做 `ADD COLUMN`。`column_exists` 在表不存在时返回 false，接着 `add_column` 会失败。

2.4 库没有 `department`。若直接 `alembic upgrade head`，会在 **f011_tenant_tree** 炸掉。

2.5.0-sg 启动顺序是：entrypoint 先 Alembic，应用起来后 `init_default_data()` 才 `create_all`。所以 **不能**指望「先启动一次」来建 `department`，除非你先拦住 Alembic 不要一次跑到 head。

按下面做：

**1）换成 2.5.0-sg 镜像，OpenFGA 起来之后，先只升到 f011 的前一个 revision：**

```Shell
docker exec -it bisheng-backend bash
export PYTHONPATH=./
alembic upgrade f011_backfill_create_knowledge_web_menu
alembic current
```

应显示 `f011_backfill_create_knowledge_web_menu`。

**2）用同一镜像做一次 create_all（补 2.4 没有、Alembic 也不建的表）：**

临时改 entrypoint：注释掉 `alembic upgrade head` 那行，只启动 API，等 `/health`。  
`init_default_data()` 会 `create_all`，并尝试种默认 tenant / 根部门（已有用户则不会重建管理员）。

```SQL
SHOW TABLES LIKE 'department';
SHOW TABLES LIKE 'user_department';
```

有表之后把 entrypoint 改回带 Alembic 的版本。

**3）升到本分支 head：**

```Shell
docker exec -it bisheng-backend bash
export PYTHONPATH=./
alembic upgrade head
alembic current
```

必须是 `f058_dashboard_dataset_flags`。  
`docker logs bisheng-backend` 出现 `WARNING: alembic migration failed` 即失败。

禁止 `alembic stamp head`。

### Alembic 实际会改什么（摘要）

| 阶段 | revision 范围 | 对 2.4 库的影响 |
|---|---|---|
| 2.5.0 | f001–f010 | `tenant`/`user_tenant`/`failed_tuple`/`org_sync_*`；业务表加 `tenant_id`；`user.source`+`external_id`；去掉 `user_name` 唯一 |
| 2.5.1 | f011_tenant_tree–f037 | 租户树、SSO 字段、部门知识空间、审批申请、LLM 共享、工作台租户配置等 |
| 被本分支吸收的 2.6 + sg | f038–f105，以及 `v2_5_0_sg_*` | 知识文档版本链、标签库、回收站、门户课/热搜/推荐、积分全套、专家问答扩展、企微推送、developer_token、共享存储路由等；最后 `f058_dashboard_dataset_flags` 改 `dashboard_dataset` |

Alembic **会建**的表示例：`tenant`、`failed_tuple`、`org_sync_config`、`knowledge_document`、`portal_course*`、`user_point_*`、`point_*`、`qa_publish_request` 等。

Alembic **不建、靠 create_all** 的表示例：`department`、`user_department`、`approval_scenario`/`approval_instance`/`approval_task`、`qa_expert`/`qa_question`/`qa_answer`、`dashboard`/`dashboard_dataset`。

涉及表（本 hop 会读/改，无单独业务 DDL 文件）：`user`、`knowledge`、`knowledgefile`、`role`、`roleaccess`、`group`、`config`、`alembic_version`，以及上表新增表。无手工 DROP。

## 重启服务

两段 Alembic 之间已经启过一次。head 对齐后：

```Shell
docker-compose pull

```

确认 backend healthy、openfga 在、`alembic current` 仍是 `f058_dashboard_dataset_flags`。

## 执行数据迁移（Alembic 不做的）

OpenFGA store 要等 **API 已成功启动**（manager 自动建 store）。然后再做权限。

工作目录容器内 `/app`。脚本在 `scripts/`，不是 2.3 时代的 `bisheng/script/`。

```Shell
docker exec -it bisheng-backend bash
export PYTHONPATH=./

bash scripts/permission_migration.sh dry_run
bash scripts/permission_migration.sh
bash scripts/permission_migration.sh verify

bash scripts/migrate_workstation_models_to_workbench.sh apply
```

说明（相对 2.5.0 文档）：

- **不要**执行 2.5.0 文档里那段 `UPDATE config ... JSON_TABLE ... assistant_llm` 的工作台 SQL。本仓库对应能力是 `migrate_workstation_models_to_workbench.py`。
- F006 **不会**在 `init_default_data` 里自动跑。
- 导入 A 知识空间之后，不要再全局重跑 `permission_migration.sh`。
- 积分规则种子在 Alembic `f078`/`f079`/`f080` 里，不用另跑脚本。

本窗口不要开首钢组织同步。
