# Sdd Implement

先读 [阶段交接规则](../sdd-workflow/references/stage-contract.md)。

## 开始前

完整 SDD 核实需求和设计已经由用户确认，并读取当前任务、相关用例和实际项目约束。
简单 Bug 依据 sdd-triage 的五项判断直接执行。复杂 Bug 依据人工选定的切入路径，复用有效决定。
检查现有工作区改动，保留其他人的工作；修改与本任务有关的内容。
按[产物存放与维护约定](../sdd-workflow/references/artifact-storage.md) 读取当前特性登记，沿用各产物位置；每次验证追加可识别的运行记录并绑定实际代码。核实本次落地后更新必要的模块知识与索引，已交付基线和后续变更保持可追溯。
研发测试代码放在对应项目/test/：后端归后端项目，前端归各自前端子项目。检查测试发现配置并做必要的范围内适配，不擅自搬迁历史测试。UI／真实集成／E2E 验收代码属于独立验收工程，不在研发任务里生成或放入应用 test/。

## 实施与自查

复用项目有效机制和已安装工具，代码范围由根因和需求决定。修复不顺带扩大到无关重构。按已确认概念和技术映射查找与实现；新代码沿用约定，历史标识按兼容关系处理，不能因统一术语擅改对外契约。
按任务同时补充需要的单元、接口、功能和契约测试，优先复用已有 fixture 和 mock／隔离环境。低影响可逆修改仍使用足够可信的最小验证，不为流程凑测试，也不把复杂业务验证压缩成静态检查。
按[测试环境与证据策略](../sdd-test-cases/references/test-strategy.md) 选择替身：真实运行被测业务、路由、校验及相关权限判断，仅替换昂贵或不稳定的外部边界。接口可用进程内客户端或轻量 mock 服务，功能场景验证状态和副作用，不必部署整套系统。
模拟成功、拒绝、异常、超时和重复等相关场景，断言真实被测行为及必要的无副作用结果。替身依据契约，不得把目标业务或权限 mock 成固定成功；数据库真实语义等无法证明的事项交接验收。
适合隔离自动化的 Bug 尽量以修复前能暴露缺陷、修复后通过的回归证明修复有效。复杂定位按需用[原症状反馈方法](references/bug-feedback.md)，关键测试用[独立预期检查](../sdd-test-cases/references/assertion-quality.md)；保留本次实际规则来源，不为测试先行或红绿次数凑步骤。运行适用格式、lint、类型和构建检查；检查实际测试入口，保留允许的接口／功能子集，排除后置套件。
开发期不要求本机复刻线上，不启动完整真实部署执行 E2E；真实依赖集成与关键端到端回归集中验收。UI 执行继续遵守单独约定，当前后置，不能因允许后端 mock 功能测试而自动运行。
记录实际测试层级、真实组件、替身边界、用例数和断言，区分 mock 环境通过与真实部署验证通过。
解释本次关键执行路径、边界、异常、超时或取消、资源生命周期以及部分成功后的状态；说明证据与未知。

模型输出和测试失败暴露的问题应据实处理。不能通过删断言、扩大 mock 或改验收预期来制造通过。
发现影响扩散、重要安全或数据风险、契约变化或需要推翻已确认决定时，返回评估并与用户对齐。
缺环境时说明实际未验证范围，继续可独立推进的已授权工作。

## 完成与交接

交付实际修改、需求／任务映射、检查结果、环境与模拟边界、代码对应关系及剩余问题。
代码、本阶段所需单元／接口／功能测试和适用检查完成后标记实现就绪，交给 sdd-review-code 审核；必要的隔离业务测试不能以“真实环境重”为由省略。审核与提测材料就绪后，研发入口在“研发完成，待独立验收”结束，不调用或等待 sdd-acceptance。
简单 Bug 同样先完成针对性开发验证，再按范围交接测试岗位；不自动开始 UI／真实环境验收，也不代写该岗位通过结论。
修复后按影响重跑必要检查，保留仍然有效的证据。
