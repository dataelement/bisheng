# Feature：中间件密码与配置加密治理

**关联需求**：[用户已认可的 HTML 方案](../../../docs/中间件密码与配置加密治理方案.html) §1–§13；本会话用户明确要求密钥不得写入代码。
**优先级**：P0（配置凭据安全与已有部署可用性）。
**所属版本**：v3.1.0-beta2，F003-middleware-credential-security（本版本）。
**状态**：原42条规格已实施主要代码；用户于2026-11-12补充部署无感硬约束，当前安装实现不满足，需据此返工。
**流程**：Full SDD；工作保持在当前分支与工作区，不创建分支或 worktree。
**依赖**：既有配置加载、数据库迁移、五个中间件及其消费者、组织同步和沙箱配置能力。领域边界见 [版本契约](../release-contract.md)。

## 范围边界

本次纳入：

- MySQL、Redis、MinIO、Elasticsearch、Milvus 的客户自备凭据、认证配置、业务配置加密与启动检查。
- 客户独立外置解密密钥、已有共用密钥关联凭据的重加密、后续轮换和恢复。
- 新装、已有环境启用认证、已有认证环境改密，以及服务端与全部现有消费者的同步验证。
- Compose 优先、兼顾源码/systemd 和 Helm；外部中间件由其运维流程实际改密，毕昇同步客户端配置。
- 操作说明、配置准备与检查能力，以及失败后的人工可控恢复。

本次明确排除：

- 强制新增 Vault/KMS 或要求所有部署 Secret 文件加密保存；本次允许受权限保护的部署明文凭据文件。
- 拆分现有中间件账号、调整其权限或变更租户数据与资源归属；避免将认证与权限治理混为一次变更。
- 密码管理页面、自动感知数据库改密、密码热更新或每次启动自动改密。
- 零停机升级保证、运行中自动关闭认证、自动清理业务数据恢复连接。
- 新增 Redis Cluster broker 支持；外部 Sentinel 不扩展为未经验证的统一支持承诺。
- 与当前共用加密工具无关的独立密钥体系、业务密钥及其数据迁移。

## 1. 用户故事

- 作为**客户部署人员**，我希望部署时填写本公司的中间件密码，并获得明确的配置检查结果，以便摆脱统一默认密码且能顺利启动。
- 作为**安全管理员**，我希望每套部署的解密密钥独立、外置且可轮换，以便代码泄露不会同时暴露所有客户配置密码。
- 作为**已有环境运维人员**，我希望明确区分初始化、真实改密和密钥轮换，并掌握全部消费者及恢复步骤，以便在维护窗口完成升级且不损坏数据。
- 作为**测试与交付人员**，我希望认证、迁移及恢复都能通过真实连接和业务操作验收，以便避免只看容器健康状态而遗漏故障。

## 2. 验收标准

### 2.1 密钥与业务配置安全

- **AC-01** — THE SYSTEM SHALL 不在交付源码或镜像中包含可用于客户生产配置解密的固定密钥，也不提供硬编码备用密钥。
- **AC-02** — WHEN 新部署首次准备加密配置, THE SYSTEM SHALL 要求独立外置密钥可用；重复准备或启动不得覆盖已有密钥。
- **AC-03** — WHERE 运行数据库迁移、API、Celery、Beat 或 Linsight, THE SYSTEM SHALL 在该进程连接依赖之前取得本部署有效外置密钥并完成所需配置解密。
- **AC-04** — IF 必需密钥缺失、不可读、无效，或生产数据库配置缺失, THEN THE SYSTEM SHALL 阻止对应进程启动，指出失败项目，不回退默认密钥、空密码或替代数据库。
- **AC-05** — THE SYSTEM SHALL 在本次治理的毕昇业务配置中保存中间件密码密文；保留已约定的旧密文兼容，标记为密文的内容解密失败时不得作为明文继续连接。
- **AC-06** — WHEN 输出检查结果、启动错误、第三方连接错误或诊断信息, THE SYSTEM SHALL 不泄露实际密码、解密密钥或包含秘密的完整连接配置。

### 2.2 部署输入、准备与检查

- **AC-07** — WHEN 客户准备部署凭据, THE SYSTEM SHALL 要求客户填写中间件密码，拒绝空值、模板占位符、已知默认弱密码及不符合对应组件限制的输入，不自行生成或替换中间件实际密码。
- **AC-08** — WHEN 准备新的凭据配置, THE SYSTEM SHALL 提供可检查的待启用结果，保留客户其他配置和当前可用版本；准备失败不得覆盖原配置。
- **AC-09** — WHEN 执行配置检查或仅准备操作, THE SYSTEM SHALL 不创建或修改服务端账号、不变更其实际密码，也不启动业务服务。
- **AC-10** — THE SYSTEM SHALL 明确区分首次初始化、已有账号改密和仅更换加密密钥的操作结果；重复启动或安装不得隐式执行服务端改密。
- **AC-11** — WHEN 客户切换凭据配置, THE SYSTEM SHALL 检查实际生效来源及必需消费者，不能将被旧配置覆盖的待启用值判定为生效；认证验证使用新建连接，不以已有连接成功替代。

### 2.3 各中间件及其使用方

- **AC-12** — WHEN 新装 MySQL, THE SYSTEM SHALL 使用客户提供的实际密码完成初始化，并使毕昇、OpenFGA 及其迁移任务可正常访问；WHERE 启用 Gateway, THE SYSTEM SHALL 同步其数据库初始化所需凭据。
- **AC-13** — WHEN 已有 MySQL 环境改密, THE SYSTEM SHALL 支持确认应用实际账号后同步服务端及全部相关消费者；仅修改初始化配置不能被判定为实际改密完成。
- **AC-14** — WHEN MySQL 凭据切换完成, THE SYSTEM SHALL 通过数据库迁移、API 与后台数据库访问、OpenFGA 权限检查验证结果；认证失败不得恢复完整业务流量。
- **AC-15** — WHEN Redis 首次启用认证或修改密码, THE SYSTEM SHALL 同步缓存、Celery、Linsight 队列及启用时的 Gateway，保持原有数据库选择和业务权限语义。
- **AC-16** — WHERE Redis 使用新旧密码过渡, THE SYSTEM SHALL 在全部相关客户端通过新凭据验证后才撤销旧凭据，并保证再次启动后的认证状态与已确认配置一致。
- **AC-17** — WHEN 验证 Redis 凭据, THE SYSTEM SHALL 以有效认证后的响应和缓存、队列实际操作判定成功，不把未认证错误视为健康成功。
- **AC-18** — WHEN MinIO 首次配置或修改凭据, THE SYSTEM SHALL 同步 MinIO 自身、毕昇及 Milvus 对象存储访问，使已有对象读取、新对象写入和既有向量数据访问均可验证。
- **AC-19** — WHEN MinIO 实际凭据变化影响旧签名链接或临时凭证, THE SYSTEM SHALL 在交付说明中明确其影响和重新获取方式，保留原有对象数据并验证新签名链接。
- **AC-20** — WHEN 使用新 MinIO 凭据启动毕昇, THE SYSTEM SHALL 保持现有存储初始化与业务能力，凭据错误或所需操作不可用时明确报错，不仅检查服务存活。
- **AC-21** — WHEN Elasticsearch 启用认证或改密, THE SYSTEM SHALL 覆盖知识检索的同步、异步路径和已配置的独立统计实例，并验证已有索引查询、必要的新索引及文档写入。
- **AC-22** — WHEN 已有 Elasticsearch 账号修改密码, THE SYSTEM SHALL 验证真实账号凭据已变化，不能以初始化变量更新替代；交付说明须给出已验证前提下的管理凭据恢复流程。
- **AC-23** — WHERE 部署要求 TLS 或证书校验, THE SYSTEM SHALL 保持相应连接保护要求，不通过关闭认证或证书校验使凭据切换看似成功。
- **AC-24** — WHEN 真正全新部署 Milvus, THE SYSTEM SHALL 在客户端接入前完成客户凭据配置及服务端认证启用，验证有效凭据可操作且无凭据访问被拒绝。
- **AC-25** — WHEN 已有 Milvus 环境启用认证或改密, THE SYSTEM SHALL 区分已有账号与首次初始化，对已有账号验证真实密码变化，不把初始化配置变化当作密码覆盖。
- **AC-26** — IF Milvus 改密返回失败或超时，且结果可能不确定, THEN THE SYSTEM SHALL 在操作流程中要求以全新连接验证新旧凭据实际状态后再继续或恢复，不盲目重试或仅恢复客户端文件。
- **AC-27** — WHEN Milvus 凭据切换后完成验收, THE SYSTEM SHALL 保证全部使用路径通过新凭据建立有效连接，并验证已有 collection 查询及必要的新数据写入，不以存活检查或旧连接成功替代。

### 2.4 存量重加密、轮换与恢复

- **AC-28** — WHEN 已有部署首次迁移外置密钥, THE SYSTEM SHALL 在保持各中间件实际密码不变的条件下完成重加密，防止密钥更换与服务端改密混合执行。
- **AC-29** — WHEN 迁移当前共用加密工具保护的存量数据, THE SYSTEM SHALL 覆盖相关中间件配置、组织同步凭据及沙箱配置令牌，保留逻辑凭据、其他业务内容与所有租户归属；不迁移无关独立密钥体系的数据。
- **AC-30** — WHILE 尚有未迁移密文或未切换消费者, THE SYSTEM SHALL 允许运维显式提供有效过渡密钥；只有全部存量密文及消费者验证完成后，才从运行配置移除旧密钥。
- **AC-31** — WHEN 重加密涉及运行缓存, THE SYSTEM SHALL 使后续实际业务读取到匹配有效密钥的配置，并验证组织同步和沙箱配置的实际使用，不以隐性回退或仅 API 启动成功判定完成。
- **AC-32** — IF 重加密中断或部分失败, THEN THE SYSTEM SHALL 保留可恢复的原值、提供失败项目与阶段，允许重复执行且不重复改变逻辑凭据；不得提前删除仍需使用的密钥。
- **AC-33** — WHEN 运维恢复旧版本或旧凭据, THE SYSTEM SHALL 提供密钥、密文、服务端实际凭据与相关消费者的配套恢复说明；不得承诺只恢复客户端文件或只回退旧镜像即可恢复。
- **AC-34** — IF 所有有效解密密钥或必需管理凭据丢失, THEN THE SYSTEM SHALL 明确说明无法自动恢复，停止自动切换并进入人工恢复或凭据重置，不以新生成密钥伪装恢复成功。
- **AC-35** — WHEN 任一认证切换失败, THE SYSTEM SHALL 保留数据库数据、队列、索引、对象及向量元数据，不通过删除或重新初始化它们修复认证；恢复配置不得盲目覆盖切换后新增业务数据。
- **AC-36** — WHEN 在途任务因维护或认证切换导致结果不确定, THE SYSTEM SHALL 在恢复流程中要求确认实际执行结果后再决定重试，不通过清队列或盲目重复投递恢复业务。

### 2.5 部署形态与交付验证

- **AC-37** — WHEN 使用 Compose 安装或更新, THE SYSTEM SHALL 保留已有部署配置及密钥，并确保已启用的凭据配置被相应容器重新加载，不以未生效的文件修改或环境变量修改宣告成功。
- **AC-38** — WHERE 使用源码或 systemd 启动, THE SYSTEM SHALL 提供与容器部署一致的外置密钥、配置校验和进程重启行为说明，不依赖 Docker 安装步骤生成本地业务配置。
- **AC-39** — WHERE 使用 Helm, THE SYSTEM SHALL 支持从外部 Secret 提供密钥和必要凭据，不将本次实际密码明文放入普通 values 或应用 ConfigMap；外部中间件改密由其管理流程完成，应用配置同步覆盖全部相关进程。
- **AC-40** — WHERE 同一部署包含多个节点或副本, THE SYSTEM SHALL 要求每个相关进程使用匹配的密钥与凭据配置版本，不能依赖单个节点本地文件的自动共享。
- **AC-41** — THE SYSTEM SHALL 在交付说明中明确私有镜像、外部 Sentinel、集群 TLS 和各恢复工具的验证前提及未验证边界，不将上游文档支持等同于当前交付环境已验证。
- **AC-42** — WHEN 标记本特性完成交付验收, THE SYSTEM SHALL 提供新装、存量密钥迁移、逐组件改密及失败恢复的验证证据，包含全部相关消费者的真实连接与业务结果；未执行项目明确标记，不以容器运行状态代替。

### 2.6 原部署命令与过程引导（用户2026-11-12明确要求）

- **AC-43** — WHEN 运维执行原有 `bash docker/install.sh` 或 `bash scripts/deploy.sh install`, THE SYSTEM SHALL 通过同一部署入口完成标准安装，不要求先手动执行keygen/prepare/check或提供bundle/key/revision参数。
- **AC-44** — IF 首次部署缺少客户密码等必需信息, THEN THE SYSTEM SHALL 在当前部署过程中给出明确引导；密码输入隐藏且不进入日志或命令参数，不以默认弱密码或自动生成中间件密码替代客户提供。
- **AC-45** — WHEN 正常重复部署, THE SYSTEM SHALL 复用当前有效密钥、凭据及配置，并且不再次要求填写已齐备信息，不覆盖已有key或默认触发真实改密。
- **AC-46** — WHEN 部署中断后重新执行原命令, THE SYSTEM SHALL 识别已有配置与部署状态，继续必要检查或给出恢复引导，不要求运维手工拼接配置版本或重复初始化账号/数据。
- **AC-47** — IF 检测到存量环境的必要密钥或管理信息缺失, THEN THE SYSTEM SHALL 在同一入口说明缺失内容和后续引导，阻止将该环境当全新部署生成身份覆盖，不通过额外手工脚本序列掩盖该缺口。

以上为部署体验的新增验收条件，原安全约束继续生效；旧测试通过不得用于宣称这些条件已满足。

## 3. 边界情况

- 当前版本没有用户侧 HTTP 新接口；运维工具的非成功结果应可判别，错误不得包含秘密内容，具体命令与格式留给设计。
- 未启用 Gateway、独立统计 ES 或其他可选消费者时，不要求为了本特性额外启用它们；一旦启用必须纳入联动验收。
- 客户已有自定义地址、库名、对象路径、索引和 collection 不因凭据治理改变；非法凭据字符与密码特殊字符应区分，合法输入不得重复编码或误执行。
- 外部凭据文件允许受权限保护的明文；这一点不等同于所有持久化材料加密，也不替代网络传输保护。
- 保留维护窗口和人工管理通道；服务端变更不确定时先确认状态，不自动继续其他组件切换。
- 组织同步合法空凭据及未配置沙箱页令牌不应被误判为需要恢复的有效密文；已配置但不可解密必须明确失败。
- 首次外置密钥升级与后来正常轮换须分别验证；旧镜像不能解读新密文的边界必须显式交付。
