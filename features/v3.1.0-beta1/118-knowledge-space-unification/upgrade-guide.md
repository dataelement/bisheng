## 1. 执行前提与职责

**正式迁移脚本必须在停服期间执行。** 停服、任务收尾、备份和恢复由升级运维流程负责；迁移脚本不检测是否停服，不探测端口/健康检查/进程/Worker 心跳，不要求停服标记或停服确认参数，也不替运维启停服务或恢复队列。

脚本负责数据与版本/权限合同预检、转换计划、持久账本、幂等转换、业务绑定回填/对账、结果校验、检查点恢复及报告。停服检测不属于脚本的校验项；这不取消脚本对数据完整性、Catalog/model/checksum、幂等键等内容的检查。

## 2. 运维停服准备

1. 确定维护窗口预算和执行负责人，准备维护入口与回退材料；提前盘点只能用于估算，正式转换以停服后的数据基线为准。
2. 暂停本次迁移影响范围内的新请求/写入、新任务派发及启动；覆盖 Beat、定时派发和相关队列消费者，保留已有排队消息及必要 broker 数据。
3. 等待已经运行的受影响任务自然完成。确认旧 Worker 不再有活跃写入后，停止旧 API、Worker、Beat 等应用进程；迁移要连接的数据库、OpenFGA、ES/Milvus、MinIO、Redis 等必要存储/中间件仍需可用。
4. 如果超过维护窗口预算仍有任务未完成，保持维护并交人工处置，不自动强杀任务，也不继续数据转换。后续如何结束任务或调整窗口由现场人员处理，不由迁移脚本判断。
5. 完成可恢复的一致备份与对象/索引清单，明确 SQL、FGA、索引及必要变更对象的同一恢复点。不要清空未执行任务来获得“空队列”。

## 3. 停服期间执行迁移

1. 运维在已停服前提下运行实现后提供的正式迁移入口；脚本本身不检查这个前提。
2. 脚本复核数据关联、资源/版本、模型/索引、授权及发布合同，生成或读取冻结计划和持久检查点。
3. 按已确认规则进行全平台 use 退役与文档库→空间转换，保留主体/可见范围/其他动作、资源及文件 ID、原模型和索引位置；不默认重切分/重建全部向量。
4. 文件/版本及旧 ID 规范化完成后，用各业务同版本提取器回填有效配置和可执行/线上/待上线版本的绑定明细及来源集合；零引用来源也须标记已提取，任务不回填。同时核对删除标记及失效引用，禁止回填清除失效绑定、自动改写业务配置或复活目标。按来源修订/摘要和全量覆盖对账；已有合法强删标记及原绑定的失效关系须保留并报告待修复；其他无效目标、歧义配置或缺口报告失败，未就绪不能启用按绑定表的删除保护。
5. 核对每资源、每租户的 SQL 与 FGA、文件/版本/标签/元数据、配额和业务绑定，输出迁移报告。原已可见但无 use 的资格变化属于预期变化，其他非预期变化须处理。
6. 任一步骤失败时不开放业务：运维继续保持停服，按原计划检查点修复重跑；必要时恢复完整一致备份。脚本不自动重启服务，也不只改回 type=0 冒充回退。

## 4. 升级校验与恢复

1. 全部租户的数据/权限及业务绑定覆盖校验通过后部署匹配的新版本，不能让旧 Worker 继续连接升级后的数据或权限模型。
2. 在外部入口和自动派发继续受控时，校验新旧调用、预览下载、抽样检索及管理员范围；核对保留排队任务的资源归属、版本、原冻结解析/切分配置与新类型/权限语义是否可解释。模型通过所属业务资源/有效版本和适用默认配置读取，任务携带的历史模型 ID 不构成独立绑定或回退来源。
3. 排队任务校验通过后再恢复执行。无合法业务模型配置的任务明确失败，不因任务参数仍含模型 ID 而恢复调用。其他无法安全解释的任务保留并人工处置，不静默丢弃、不按最新默认重建历史任务，也不盲目交给旧版本消费。
4. 由运维按部署方案恢复 Worker/Beat/入口，核对实际任务结果与业务状态；保留备份、迁移来源、报告与检查点。

## 6. Q-05 强制删除后的升级核对

强删保留引用方原 ID/版本/绑定及目标删除标记。升级备份和恢复必须包含绑定明细、来源集合、删除标记与删除操作账本；完整性对账将有合法标记的失效引用识别为预期状态并保留待人工修复，无标记的缺失目标仍属异常。应用恢复后验证失效提示、运行报错及无静默模型回退；不因升级自动清除业务配置。任务不建立模型绑定，停服职责仍按 §1–§4。
