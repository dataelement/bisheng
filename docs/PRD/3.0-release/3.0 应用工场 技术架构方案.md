## 0. 术语

下表中的术语全文只用这一个说法。

| 术语 | 定义 |
|---|---|
| 托管应用 | 开发者在本地开发、经 `bisheng deploy` 导入平台、由平台构建并以容器运行的 Web 应用。代码中的资源类型名是 `app`，构建页 UNION 中 `flow_type=35`。 |
| 平台核心 | BiSheng 既有的全部功能（backend、两个 SPA、Celery、六类存储）。 |
| 开放能力层 | 对外开放平台能力的一层：凭据底座、`/api/v2` 鉴权管线、模型协议面、MCP 面、开发者工具分发。它全部在 backend 进程内，零 docker 依赖。 |
| 工场运行时层 | 运行托管应用的一层：runtime-manager、app-proxy、egress-proxy、docker-socket-proxy 和托管应用容器。 |
| runtime-manager | 编排器。独立包、独立进程，接收 backend 的编排意图并调用 docker API 执行。 |
| app-proxy | 托管应用的入口反向代理。负责 `/apps/{slug}` 的入口判定、身份头剥离与注入、HTTP 与 WebSocket 转发。 |
| 编排意图 | backend 发给 runtime-manager 的声明式请求（build / deploy / stop / destroy / probe / db-migrate / preview），用 HMAC 签名。 |
| 服务账号密钥 | 前缀 `bs-sak-` 的凭据，主体是不可登录的服务账号。开发者用它登录 CLI。 |
| 个人访问令牌 | 前缀 `bs-pat-` 的凭据，主体是自然人。 |
| 应用运行期凭据 | 前缀 `bs-app-` 的凭据，主体类型 `hosted_app`。发布管线自动签发，以环境变量 `BISHENG_APP_TOKEN` 注入容器，没有管理入口。 |
| OBO 令牌 | app-proxy 在每次请求中注入的 `X-BiSheng-Access-Token`，表示「当前访问用户」。backend 用 `app_runtime.obo_secret` 签发，默认寿命 900 秒。 |
| 能力声明 | `bisheng-app.yaml` 中的 `capabilities` 段：应用要调用的模型和知识库。审批通过即授权。 |
| 能力总线 | 把能力声明变成运行期注入与运行期判权的服务（`CapabilityBusService`）。本版只覆盖模型和知识库两项。 |
| 应用态 | `app.state` 的五个取值：`draft` / `online` / `pending_capacity` / `stopped` / `deleted`。 |

## 1. 总览

### 1.1 结论

应用工场在平台核心之外新增两层，两层都可以整层不装。开放能力层是 backend 进程内的模块，它用平台自签发凭据替换了 v2 开放 API 原来的「内网可信」模型，并对外提供 OpenAI 兼容模型面和 MCP 面。工场运行时层是三个新进程加一组容器：backend 只发编排意图，runtime-manager 执行构建与容器生命周期，app-proxy 承担入口与身份注入，egress-proxy 承担出站白名单。backend 编译期与运行期都不依赖 docker，这条约束由 `scripts/arch-guard.sh` RULE-10 强制。托管应用获得访问者身份的唯一途径是 app-proxy 注入的请求头，应用调用平台能力时同时出示「哪个应用」（应用运行期凭据）和「为谁」（OBO 令牌）两把凭据。

### 1.3 三层与部署开关

| 层 | 组件 | 部署开关 | 开关关闭时的行为 |
|---|---|---|---|
| 平台核心 | 既有全部功能 | — | 不变 |
| 开放能力层 | `open_api`、`open_api/mcp`、`dev_toolkit` | `open_platform.enabled`（三个扩展权限位能否签发、模型面与 MCP 面是否挂载、分发端点是否注册）；`open_api.management_ui_enabled` / `pat_enabled`（管理界面，beta2 起默认开） | 模型面与 MCP 面不挂载，路径返回与不存在路径逐字节相同的 404；`/api/v2` 其余端点照常 key 鉴权 |
| 工场运行时层 | runtime-manager、app-proxy、egress-proxy、docker-socket-proxy | `app_runtime.enabled`（backend）+ compose profile `app-runtime` 或 systemd 单元是否安装 | 两个 SPA 读 `/api/v1/env.app_runtime_enabled` 隐藏全部入口；deploy / preview 端点被 `require_app_runtime_enabled` 拒绝；新表随 alembic 建出、空置无害 |

两层的依赖方向是单向的：工场运行时层依赖开放能力层的凭据底座，平台核心不感知任一层。平台核心与两层共享的只有两个注册式扩展点：OpenFGA 资源类型 `app` 和审批场景 `app_publish_request`。

### 1.5 主链路

下面是 PRD-1 主旅程在系统中的执行顺序，各步的设计见后续章节。

1. 租户管理员在 platform「服务账号」页建服务账号（必填资源归属人），签发勾选 `app:manage` 的服务账号密钥（§2.1）。
2. 开发者执行 `bisheng login <平台地址> --api-key …`。CLI 调 `GET /api/v2/auth/whoami` 校验密钥，写 `~/.bisheng/credentials.json`，随后自动同步技能包（§3.1、§3.2）。
3. 开发者执行 `bisheng deploy`。CLI 打包上传到 `POST /api/v2/apps/deploy`；backend 同步完成解包、manifest 校验、建草稿或归属判定、快照入 MinIO，然后把异步段交给 Celery default worker（§5.1）。
4. 异步段依次执行密钥扫描、结构预检、构建（runtime-manager 渲染 Dockerfile 模板并 `docker build`）、启动探活；全部通过后写版本记录并提交审批单（§5.2–§5.5）。
5. 审批人在审批中心通过。审批 outbox 在 Celery default worker 上调用 `on_approved`，执行上线终检：容量准入、签发应用运行期凭据、合并能力注入变量、下发 deploy 意图、切换路由（§5.6、§5.7）。
6. owner 在卡片 ⚙️「管理权限」或发布面可见范围区授权给同事（§6.2）。
7. 同事从应用广场点卡片，浏览器整页跳到 `/apps/{slug}`。app-proxy 向 backend 做入口判定，剥离伪造头，注入身份头与 OBO 令牌，反代到容器（§4.6）。
8. 应用代码用 SDK 读身份、调检索；用标准 `openai` 客户端调模型；用标准库读写 `/data/app.db`（§3.3、§5.7）。

## 2. 开放能力层

### 2.1 鉴权底座（取 beta2 F053 实现）

开放能力层的鉴权底座整体使用发版线 beta2 F053 的实现，vibe 分支自己的 F049 实现于 2026-09-10 归档。决策理由是两套实现在同名表上结构不同、并存会让权限主体判定出现两个真相；合并方案与冲突解法见 `features/v3.0.0/beta2-openapi-base-migration.md` M1–M17。

**凭据与主体。** 平台自签发凭据共用一张表 `api_credential`，服务端只存 `sha256(明文)`，明文只在签发时展示一次（INV-28）。主体类型由 CHECK 约束限定为三种：`service_account`（`bs-sak-`）、`natural_person`（`bs-pat-`）、`hosted_app`（`bs-app-`）。服务账号是独立的 `service_account` 表，不在 `user` 表上打标；它不可登录、不进选人场景、授权只走主体侧（INV-29）。`hosted_app` 主体由 F055 加入，见 §5.7。

**单一鉴权管线。** `/api/v2` 的路由级依赖是 `verify_open_api_access`（`open_api/api/dependencies.py`）。每个端点必须带 `@open_api_scope(...)` 标记，漏标记的端点结构性拒绝。管线按顺序做：校验 bearer、个人访问令牌的额外策略检查、端点标记检查、`hosted_app` 只能进标了 `hosted_app=True` 的路由（否则 26052）、`delegate` 与三个扩展位互斥（调用期 26051）、权限位检查（26003）、身份模式解析。主体对象是 `open_api/domain/context.py` 的 `OpenApiPrincipal`。

**权限位。** PRD-1 使用三个扩展位：`model:invoke`（模型面）、`identity:read`（MCP 身份组织工具）、`app:manage`（CLI deploy / logs、MCP 应用数据与日志工具）。三位都随 `open_platform.enabled` 可签发，个人访问令牌永远拿不到这三位。三位与 `delegate` 位在签发期硬阻断（26050）、在调用期拒绝（26051），因为本地开发三面一律以服务账号自身身份执行，不承载委托（INV-31）。

**身份模式。** 无委托头时是模式 S，以凭据主体身份执行。持 `delegate` 位的服务账号可经 `X-On-Behalf-Of` 头进入模式 D，以目标自然人身份执行，目标须在委托范围表 `credential_delegate_scope` 内且不能是特权管理员。应用工场全程只用模式 S。头名用 beta2 的 `X-On-Behalf-Of` / `X-End-User`，不是伴生 PRD 写的 `X-Bisheng-*`，这是按 beta2 现状接受的偏差。F050 spec 所列的「两种身份模式、受限委托」在代码中已由 beta2 交付大半，`features/v3.0.0/README.md` 中 F050 的「未做」描述需要按代码重核。

**错误与审计。** v2 返回真实 HTTP 状态，信封仍是 `{status_code, status_message, data}`；模型面前缀单独渲染为 OpenAI 错误体。每次 v2 调用由 `open_api/api/middleware.py` 写一条 `open_api.call` 审计，带身份模式与授权主体。错误码段 260 归 beta2 F053，以 `common/errcode/open_api.py` 为准。

### 2.2 模型协议面（F051）

模型协议面只做 OpenAI 兼容，挂在 `/api/v2/model/v1`，提供 `POST /chat/completions`（含 SSE 流式与工具调用）和 `GET /models`。其余路径由显式 catch-all 返回 26501，Anthropic `messages` 的两种路径拼法返回专用码 26502；embeddings 与 Responses 不提供。设计期曾计划同时提供 Anthropic 兼容面并用 LiteLLM / one-api 类现成代理承载协议面，实现改为在 backend 内自研一层薄翻译（OpenAI 请求 ⇄ `BishengLLM`），原因是现成代理需要同步第二份服务商凭据、不知道租户可见范围与服务商日上限，同步延迟即静默越权，且信创部署要多一个组件（F051 design D1）。

**模型解析。** 模型名以平台模型管理中的 `LLMModel.model_name` 为准，跨服务商同名时用限定名 `{服务商名}/{模型名}`。可用范围由 `llm` 域的 `model_catalog.py` 计算（进程内 60 秒缓存，失败即拒），`ModelRangePolicy` 按主体类型分派：服务账号取租户已启用模型，托管应用取能力声明（经 F055 注册的端口读取）。

**记录与计量。** 每次调用写一行独立表 `model_call_record`（主体、资源归属人、`app_id`、访问用户、模型、token、首 token 时延、`trace_id`），由批量异步写入器落库。被范围策略拒绝的调用不写这张表，由 `open_api.call` 审计承接。token 口径与 MODEL_INVOKE 遥测同源，计费归资源归属人，不写 `llm_token_log`。本面不新增任何限流闸，只沿用服务商的 `limit_flag / limit`，超限返回 26517 / 429；聚合账单顺延 v3.1。

**接入地址。** `GET /api/v1/dev-toolkit/versions` 的 `model` 段给出 base URL、协议与鉴权方式。错误码段 265（`common/errcode/model_face.py`），每个码同时带 OpenAI 的 `type` / `code`。细节见 `features/v3.0.0/051-model-protocol-gateway/design.md` D1–D14。

### 2.3 MCP 面与统一检索门面（F052）

MCP 面使用 FastMCP 的 streamable-http 传输，`stateless_http=True`、`json_response=True`，以精确 `Route` 挂在 `/api/v2/mcp`，只在 `open_platform.enabled` 为真时装配。鉴权由自建 ASGI 闸 `McpAccessGate`（`open_api/mcp/gate.py`）完成，它复用 v2 的 `validate_bearer`，接受服务账号密钥与个人访问令牌，一律模式 S，持 `delegate` 的凭据在入口被拒。`list_tools` 按权限位过滤，没有任何权限位的凭据能完成握手但只得到空清单。

工具注册表是 `open_api/mcp/registry.py` 的 `TOOL_REGISTRY`，共六类：

| 类别 | 工具 | 权限位 |
|---|---|---|
| 知识库检索 | `bisheng_knowledge_search` | `knowledge:read` |
| 知识库清单 | `bisheng_knowledge_list` | `knowledge:read` |
| 模型清单 | `bisheng_model_list` | `model:invoke` |
| 身份组织 | `bisheng_identity_get_user`、`bisheng_org_tree`、`bisheng_dept_members` | `identity:read` |
| 应用数据 | `bisheng_app_db_tables`、`_schema`、`_rows`、`_row_update` | `app:manage`（仅本人名下应用） |
| 应用状态与日志 | `bisheng_app_status`、`bisheng_app_logs` | `app:manage`（运行时层未部署时返回 16207） |

模型调用不走 MCP，本地 agent 直连模型协议面；MCP 只提供模型清单。每次 `tools/call` 写一条 `open_api.mcp.tool_call` 审计。

**统一检索门面**是 `knowledge/domain/services/retrieval_facade_service.py`，它有四个调用方：MCP 检索工具、v2 `POST /filelib/retrieve`、托管运行期的能力总线、SDK `retrieve`。门面按文件级做权限过滤，权限引擎不可用或结果不可判定时整体报错、绝不返回部分过滤的结果（INV-30、INV-36）。错误码段 263（`common/errcode/mcp_face.py`）：26300–26319 归 MCP 传输与工具面，26320–26339 归检索门面。细节见 `features/v3.0.0/052-mcp-server-face/design.md` D1–D12。

## 3. 开发者工具

### 3.1 CLI（F053）

CLI 是独立 Python 包 `src/bisheng-cli/`，发行名 `bisheng-cli`、import 名 `bisheng_cli`、命令名 `bisheng`，运行依赖只有 `httpx` 与 `PyYAML`，与 backend 代码零耦合。命令集如下：

| 命令 | 作用 | 平台接口 |
|---|---|---|
| `login BASE_URL --api-key / --api-key-stdin` | 校验服务账号密钥并落盘；成功后自动 `skills sync`；只拿到 `delegate` 位的密钥在写盘前被拒 | `GET /api/v2/auth/whoami` |
| `deploy [PATH]` | 打包上传，按服务端 `stage` 输出进度；`--wait` 轮询到终态，每种终态一个退出码 | `POST /api/v2/apps/deploy`、`GET /api/v2/apps/deployments/{id}` |
| `logs` | 读运行日志，`--follow` 每 3 秒短轮询 | `GET /api/v2/apps/{id}/logs` |
| `skills sync` | 拉取技能包并接入本机 AI 编程工具 | `GET /api/v1/dev-toolkit/skills/{pack}` |
| `dev` | 本地起迷你代理，注入与线上同名的身份头和环境变量 | 无 |
| `platforms list / use` | 在多个已登录平台间切换 | 无 |

凭据文件 `~/.bisheng/credentials.json` 以 `O_CREAT|O_EXCL` 加 0600 一步创建，目录 0700，结构支持多平台 profile。应用标识写在项目根 `.bisheng/app.json`，平台一接收上传就写入，避免重跑时再建一个同名草稿。打包产物是可复现的 `tar.gz`（mtime 归零、路径 posix 化），忽略规则依次为 git、内置 gitignore 子集、`.bishengignore`，`.venv` / `node_modules` / `.bisheng/` 硬排除；上传是一次性 multipart POST，上限取自 `GET /api/v2/apps/deploy-limits`。CLI 不提供 `init`、`logout`、`whoami`、`--as` 和设备码登录。

**安装件分发。** 平台自身分发 CLI 与 SDK 的 wheel，端点在 `dev_toolkit/api/endpoints/distribution.py`，前缀 `/api/v1/dev-toolkit/`，匿名可达，`open_platform.enabled` 关闭时不注册。`scripts/pack_cli_wheel.sh` 与 `pack_sdk_wheel.sh` 构建 wheel 并拷入 `src/backend/bisheng/dev_toolkit/artifacts/`，同时更新带 sha256 的 `manifest.json`。wheel 必须提交进 git，因为后端镜像的 build context 只有 `src/backend/`；修改 CLI 或 SDK 后不重跑脚本并提交，平台会继续分发旧版本。

### 3.2 技能包（F053）

技能包源目录是 `src/backend/bisheng/dev_toolkit/skills/`，共两包：`deploy-hosting`（托管运行契约、manifest 写法、安全红线、部署工作流、自检清单）和 `platform-wiring`（访问者身份、检索、附件存储、应用数据库、模型接线、`bisheng dev`、SDK 来源）。每包带可运行样例与 `selfcheck.py`。技能包使用 Agent Skills 开放格式，不做任何本地端专有插件。

平台按请求把技能目录实时打成字节确定的 gzip tar，版本放在响应头 `X-Bisheng-Pack-Version`。CLI 把它落到 `~/.bisheng/skills/<平台标识>/<pack>/`，然后在检测到的 `~/.claude/skills/`、`~/.codex/skills/` 下建软链（Windows 改为复制）；没有技能目录约定的工具，由 `deploy` 在项目 `AGENTS.md` 写一行路径指针。这一步是 2026-08-18 缺陷修订的结果：只同步到 `~/.bisheng/skills/` 时没有任何编程工具会扫描该目录，「同步成功」并不代表 AI 读得到。技能内容同时是 SDK 开发者指南的唯一来源（F057 design D12）。

### 3.3 SDK（F057）

SDK 是 `src/bisheng-sdk/`，只有 Python 版，版本 0.1.1 独立于平台，唯一依赖 `httpx`。公开面恰好是四个模块，由 `test_public_surface.py` 守住：

- `auth`：`current_user()` 从请求头读出 `Identity`，用 ContextVar 绑定到请求上下文，提供 ASGI / WSGI 中间件与 `bind()`；没有注入身份即抛 `PlatformIdentityMissingError`，不返回 None。
- `retrieve`：`search()` / `asearch()` 调 `POST /api/v2/filelib/retrieve`，同时送 `Authorization: Bearer <BISHENG_APP_TOKEN>`（哪个应用）与 `X-BiSheng-Access-Token`（为谁）。
- `storage`：附件六函数 put / get / open / stat / list / delete 及其异步版本；托管期走 runtime-manager 附件接口，本地期走 `BISHENG_APP_STORAGE_DIR` 目录。
- `errors`：19 个异常类，服务端码经 `_codes.py` 映射，未登记的码原样呈现。

模型与应用数据库刻意不进 SDK（PRD-1 DEV-07）：应用用官方 `openai` 客户端读平台注入的 `OPENAI_BASE_URL` / `OPENAI_API_KEY`，用标准库或任意 ORM 读 `BISHENG_APP_DB_URL`。SDK 也不封装 MCP。托管构建期 runtime-manager 经平台的 PEP 503 索引 `/api/v1/dev-toolkit/simple/` 安装 SDK。

### 3.4 `bisheng dev` 本地身份注入

`bisheng dev` 在本地起一个迷你代理（`bisheng_cli/devproxy.py`），向本地应用注入与 app-proxy 同名的十个身份头和同名环境变量，身份是开发者的服务账号（`subject_kind=service_account`，部门三头缺省）。本地数据库是 `<项目>/.bisheng/dev/app.db`，附件目录是 `<项目>/.bisheng/attachments/`。本地期的 `X-BiSheng-Access-Token` 是 CLI 用 HMAC 签的 `bsdev.` 句柄，平台无法验签，所以本地无法端到端验证 `retrieve`，技能包把这一点标为「不要依赖」。平台不提供身份模拟开关，平台能力调用恒以服务账号真实身份计权限（INV-32）。

## 4. 应用域与运行时（F054）

### 4.1 领域模型与状态机

托管应用的表定义在 `src/backend/bisheng/database/models/`，放在这里而不放进 `app_runtime/domain/` 的原因是构建页列表的 UNION 要在 `flow.py` 中引用它，放进 domain 会触发 arch-guard RULE-2。

| 表 | 作用 | 要点 |
|---|---|---|
| `app` | 应用本体 | id 为 uuid 字符串；`slug` 全局唯一（跨租户）；`state` 显式列；`current_version_id` 指向正在运行的版本 |
| `app_version` | 版本记录 | 只增不改，唯一会变的列是 `terminal_state`；冻结 `code_object_key` / `manifest` / `capabilities` / `injections` / `tier_id` / `runtime` / `image_ref`；无 `tenant_id`，隔离由所属 `app` 行派生 |
| `app_instance` | 运行实例 | `phase`、`health`、`restart_count`、`last_probe_at`；`exec_ref` 只用于审计，不参与路由 |
| `app_access_log` | 访问记录 | 一次进入一条，同一用户同一应用 1800 秒内合并（Redis `app_access:{app_id}:{user_id}`） |
| `resource_tier` | 资源档位 | 平台级、无 `tenant_id`，F055 拥有，见 §5.6 |
| `app_deployment` | 一次发布尝试的进度 | F055 拥有，CLI 轮询它 |
| `hosted_app_subject` | 应用到整数主体 id 的映射 | F055 拥有，见 §5.7 |

状态机定义在 `app_runtime/domain/constants.py` 的 `AppState` 与 `ALLOWED_TRANSITIONS`：

```
draft ──► online | pending_capacity | deleted
online ──► online（迭代发布切版本）| stopped
pending_capacity ──► online | deleted
stopped ──► online | pending_capacity | deleted
deleted ──► （终态，行保留供审计）
```

状态机没有 `online → deleted` 这条边：删除运行中的应用必须先下线，保证容器与宿主卷总是由状态动作回收，不会因为行消失而成为孤儿（INV-35）。`app_runtime/domain/services/app_state_service.py` 是 `app.state` 的唯一写入方，用带前态断言的单行 UPDATE 落库，冲突返回 16102；新建草稿走 `app_provision_service.create_draft`。只有 `online` 与 `stopped` 两个状态能从入口访问到（`stopped` 显示「已下线」页）。

### 4.2 backend 与编排层的契约

backend 侧的 `app_runtime` 模块只做三件事：维护领域模型与状态机、向 runtime-manager 发编排意图（`orchestrator_client.py`）、为 app-proxy 提供入口判定端点（`api/endpoints/internal_app_proxy.py`）。进程间有三处认证，各用一把独立的密钥：

| 调用方向 | 认证方式 | backend 配置键 | 对端环境变量 |
|---|---|---|---|
| backend → runtime-manager | HMAC-SHA256，签名串 `METHOD\nPATH\nbody`，放在 `X-Signature` | `app_runtime.manager_hmac_secret` | `RTM_HMAC_SECRET` |
| app-proxy → runtime-manager（查路由） | 同上，同一把密钥 | — | `APP_PROXY_MANAGER_SECRET` |
| app-proxy → backend（入口判定） | HMAC | `app_runtime.proxy_hmac_secret` | `APP_PROXY_BACKEND_SECRET` |
| backend 签发 OBO 令牌 | HMAC 签名令牌 | `app_runtime.obo_secret`（必须不同于 `jwt_secret`） | — |

任何一把密钥为空时，对应调用方 fail-closed：runtime-manager 返回 401，backend 把它折叠为 16121「编排器不可用」，排查时容易误判为 dockerd 故障。容量准入阈值、数据目录、构建包源只在 runtime-manager 的 `RTM_*` 环境变量里生效，backend `config.yaml` 中的同名旧键已删除，写了只会打一条告警（`core/config/app_runtime.py`）。

### 4.3 runtime-manager

runtime-manager 是独立包 `src/runtime-manager/runtime_manager/`，FastAPI 单 worker，默认监听 `127.0.0.1:8091`，只有 `/healthz` 免签。它的接口按用途分四组：

| 组 | 端点 | 文件 |
|---|---|---|
| 编排意图 | `POST /v1/admission`、`/v1/intents/{build,deploy,stop,destroy,probe,db-migrate}`、`/v1/intents/preview[/stop]`、`GET /v1/builds/{id}` | `api/intents.py` |
| 路由 | `GET /v1/apps/{id}/route`（返回容器 bridge IP:端口、版本、generation）、`GET /v1/previews/{session}/route` | `api/routes.py` |
| 只读 | `/v1/apps/{id}/status`、`/v1/apps/{id}/logs`、`/v1/runtime/status`（含部署自检 preflight） | `api/readonly.py` |
| 数据面与附件 | `/v1/apps/{id}/db/*`（HMAC）、`/v1/apps/{id}/storage/*`（应用自己的 bearer） | `api/appdb.py`、`api/storage.py` |

**编排访问面的边界。** backend 不持有任何编排访问面，这一点在所有形态下都成立。runtime-manager 访问 dockerd 有两种配置：D2-A 直连 `/var/run/docker.sock`（进程需要 docker 组），D2-B 经 `tecnativa/docker-socket-proxy` 的端点白名单访问（`RTM_DOCKER_HOST=tcp://…:2375`，EXEC 等写能力关闭）。compose 形态固定使用 D2-B，此时 socket 由 docker-socket-proxy 容器持有，它没有业务代码；systemd 形态由 `RTM_DOCKER_HOST` 是否设置决定。端点白名单由 `docker_backend.socket_proxy_env()` 唯一给出，compose 文件与测试逐字比对。设计期提法「runtime-manager 是唯一持有 docker socket 的进程」应理解为「编排访问面只属于工场运行时层的编排侧，backend 与 app-proxy、egress-proxy 都不持有」。

**自愈。** 进程退出类故障交给 docker 的 `RestartPolicy: unless-stopped`（内置指数退避），runtime-manager 不自研重启循环。`reconciler.py` 每 15 秒一轮，只处理 docker 自身不处理的「unhealthy 但进程未退出」实例：重建容器并把 generation 加 1，使 app-proxy 的路由缓存失效。期望态存放在本机状态文件，同时双写到容器 label 作灾备；从 label 恢复时，「容器存在但未运行」判为期望停止，避免状态文件丢失后把已下线的应用全部复活。已运行的容器不依赖 runtime-manager 进程存活。

**容量准入**（`admission.py`）。准入要同时通过两道闸：闸① 宿主 `MemAvailable − RTM_RESERVE_MB` 不小于本次所需；闸② 已承诺规格之和不超过总量 × `RTM_OVERCOMMIT_RATIO`（默认 0.8）。构建与拉起共用这套判定，构建按 `RTM_BUILD_RESERVE_MB` 预留。准入失败时应用进入 `pending_capacity`，不自动重试，由 owner 显式「手动上线」。

### 4.4 构建路线

构建使用平台持有的 Dockerfile 模板矩阵，开发者与 AI 都不写 Dockerfile（`runtime_manager/builder.py` + `templates/{python3.11,node20,static}/*.j2`）。manifest 的 `runtime` 字段选择模板目录，基础镜像分别是 `python:3.11-slim`、`node:20-slim`、`nginx:1.27-alpine`，镜像内以 UID 10001 的非 root 用户运行。支持的 runtime 列表由实际存在的模板目录决定，所以只预置了 python 基础镜像的离线环境只会宣告 `python3.11`。构建阶段依次是 `build_admission → fetch_source → render_dockerfile → docker_build`，在 runtime-manager 所在主机上执行。

构建期与运行期的出站策略是分开的。构建容器跑在专用 `--internal` 网络 `bisheng-build` 上，唯一出口是 egress-proxy，只放行部署配置的包源（`RTM_BUILD_INDEX_URL`、`RTM_BUILD_NPM_REGISTRY`）与平台自身分发端点；能力声明中的域名不作用于构建期，防止借 manifest 把依赖绕过审批带进来。镜像 tag 为 `bisheng-app/{slug}:{version_no}-{id[:8]}`，每个应用保留 2 个版本。Railpack / Nixpacks 与 CNB buildpacks 均被否决，理由见附录 A。

### 4.5 容器规格与沙箱

runtime-manager 在 `lifecycle.py::build_container_payload` 中一次性写定容器规格，之后不原地修改：

- 资源限额：`NanoCpus` / `Memory` / `MemorySwap` 取自档位，创建时固化；超管调整档位规格后，只在下次发布或重新上线时生效。
- 文件系统：`ReadonlyRootfs`；`/tmp` 为 64 MB 的 `noexec,nosuid` tmpfs；唯一可写持久路径是 bind 到宿主 `{data_root}/apps/{app_id}/db/` 的 `/data`。
- 权限：`no-new-privileges`，非 root 用户运行。
- 网络：`NetworkMode=bisheng-apps`，不发布任何端口，入方向只能经 bridge IP 到达。
- 日志：json-file，10 MB × 3 份轮转，这也是日志的保留窗口。

沙箱只实现了「Docker 加固」一档。gVisor 与 Kata / Firecracker 在 F054 design §8 列为不做，代码零引用；容器规格中也没有 `CapDrop` 与 `PidsLimit`，列为技术债（§9）。

### 4.6 app-proxy

app-proxy 是独立包 `src/app-proxy/app_proxy/`，默认监听 `127.0.0.1:8090`，不 import bisheng 包，不持有任何 docker 权限。nginx 用变量式 upstream 把 `location /apps/` 转发给它（`docker/nginx/conf.d/default.conf`）；商业版 Java 网关只认 `/api/**`，同样只需把 `/apps/` 转发到 app-proxy，入口安全逻辑只在 app-proxy 一处实现。

**入口判定。** 每个请求，app-proxy 带 HMAC 调 backend `POST /api/v1/internal/app-proxy/authorize`。backend（`app_runtime/domain/services/entry_authz_service.py`）依次判断：运行时层开关、平台登录态（token_version、账号禁用、租户禁用）、应用存在且曾上线、`check_business_action(app, use)`、应用态。判定结果与路由各缓存 3 秒，键为（cookie 哈希，slug）。权限引擎不可用时拒绝；backend 返回 app-proxy 不认识的判定值时按拒绝处理。backend 在放行时 fire-and-forget 写 `app_access_log`，app-proxy 本身不连库。

**身份头剥离与注入**（`headers.py`）。剥离按归一化前缀匹配：头名先 `lower()` 并把 `_` 换成 `-`，凡以 `x-bisheng-` 开头的一律丢弃。这条规则直接来自 oauth2-proxy CVE-2025-64484：只按连字符写法精确剥离，会让 `X_BiSheng_User_Id` 这类下划线变体经 WSGI 框架的归一化后绕过。app-proxy 同时丢弃客户端的 `x-forwarded-*` / `forwarded` 与 hop-by-hop 头，并从 Cookie 中摘掉平台会话 cookie `access_token_cookie`，防止把长效平台凭据交给容器。之后注入十个头：

`X-BiSheng-User-Id`、`X-BiSheng-User-Name`、`X-BiSheng-Tenant-Id`、`X-BiSheng-Dept-Id`、`X-BiSheng-Dept-Name`、`X-BiSheng-Dept-Path`、`X-BiSheng-Subject-Kind`、`X-BiSheng-App-Id`、`X-BiSheng-Access-Token`（OBO 令牌）、`X-BiSheng-Request-Id`。

含中文的三个头做 UTF-8 percent-encoding。app-proxy 重写 `X-Forwarded-Prefix: /apps/{slug}` 等转发头，转发时剥掉 `/apps/{slug}` 前缀，容器经环境变量 `BISHENG_APP_BASE_PATH` 得知前缀。应用响应里以 `/` 开头的 `Location`，app-proxy 补回前缀（`routing.restore_entry_prefix`），平台不改写 HTML 与 JS。`bisheng dev` 的本地代理按同样的规则把应用挂在 `/apps/{slug}` 下，前缀之外的请求返回 404 和原因说明，漏写前缀的根绝对路径在本地就会暴露。SDK 的 `_headers.py` 与 CLI 迷你代理使用逐字相同的十个头名。

**路径与兜底页。** GET / HEAD 请求裸 `/apps/{slug}` 时，app-proxy 在鉴权放行之后返回 308 到 `/apps/{slug}/`；缺这一步时应用的相对资源路径会解析错位，表现为白屏。未登录、无权限、已下线、不存在或未上线四类情况由 app-proxy 自渲染兜底页；导航请求一律返回 200 加页面，只有非导航的 JSON 请求返回 401 / 403 / 404 / 503，原因是扫码打开时浏览器错误页和「平台故障」无法区分。未登录时兜底页用内联 JS 跳平台登录页并回跳。

**WebSocket。** WebSocket 鉴权有三条不变量，均已实现（`websocket.py`）。第一，连接的授权有效期在握手时定死为 min(OBO 剩余寿命, `ws_max_lifetime_seconds`) 加随机抖动，到期以 4001 关闭。第二，权限撤销、应用下线时 backend 调 `/internal/connections/close` 主动断连，另有周期性重新鉴权兜底。第三，所有关闭码的语义都是「请重连」，应用侧把重握手当作常态路径。

**审批期预览。** `/apps/preview/{session}` 是审批人预览实例的入口，由 F055 管理（§5.5）。

### 4.7 per-app 数据库

每个托管应用一个 SQLite 文件，宿主路径 `{data_root}/apps/{app_id}/db/app.db`（`data_root` 默认 `/opt/bisheng/app-data`），容器内为 `/data/app.db`，平台注入 `BISHENG_APP_DB_URL=sqlite:////data/app.db` 与 `BISHENG_APP_DB_PATH`。隔离靠文件与卷边界，没有账号密码类凭据。应用库与平台 MySQL / DM8 解耦，不受双方言约束 C2，生成代码也不需要认识 DM8 方言。设计期曾规划「SQLite 小档 + Postgres schema-per-app 中档」，本版只实现 SQLite，Postgres 中档顺延。

SQLite 带来两条硬约束：WAL 模式单写者，且不支持网络文件系统。所以 SQLite 应用必须「单实例 + 本机卷」，多实例或多机之前必须先升档到 Postgres。backend 从不直接打开应用库：数据面读写经 runtime-manager 的 `appdb.py`，接口只接受类型化参数（表名、主键、列值），所有标识符先对照 `sqlite_master` 校验再引用，接口上不存在携带 SQL 的参数，所以 DDL 无法从数据面发出。建表与改表只走发布管线的 `db-migrate` 意图，输入是声明式计划（§5.4）。数据面目前只有单行 PATCH，F052 需要的 `insert_row` / `delete_row` 未交付。

### 4.8 附件存储、代码快照与日志

托管应用相关对象全部放在独立 MinIO 桶 `bisheng-apps`，不放平台的 `bisheng` 桶，原因是 nginx 的 `location /bisheng/` 会把任意 key 转发给 MinIO，放进公共桶就只剩桶策略一道防线。该桶不挂 nginx location、不设匿名策略，由 runtime-manager 首次使用时创建。

| 对象 | 键 | 写入方 |
|---|---|---|
| 代码快照 | `apps/{app_id}/versions/{version_id}/code.tar.gz` | backend `package_service` |
| 应用附件 | `apps/{app_id}/attachments/…`（越界 key 直接拒绝） | runtime-manager `storage.py`，应用经 SDK 调用 |
| 数据库快照 | `apps/{app_id}/db-snapshots/…`（先 `.backup` 再 tar） | runtime-manager |

应用经注入的 `BISHENG_APP_STORAGE_ENDPOINT` / `_TOKEN` / `_MAX_FILE_MB` 访问附件；未配置 MinIO 时句柄照常注入，但所有存储调用返回 503，`/v1/runtime/status` 的 preflight 会指出。附件不计入租户存储配额。运行日志由 runtime-manager 从 docker 读取，保留窗口即日志轮转窗口；CLI 与 MCP 读日志只允许 owner，platform 详情页按入口分口径。

### 4.9 出站白名单

出站白名单由三层组成，每一层存在的理由是上一层在某些主机上可能缺席（`runtime_manager/egress.py` 文件头）：

| 层 | 实现 | 作用 |
|---|---|---|
| L1 网络拓扑 | `bisheng-apps` 与 `bisheng-build` 均以 `--internal` 创建，容器无默认路由 | 断开一切直接出网；零成本、配错时可被 preflight 发现 |
| L2 egress-proxy | runtime-manager 包的另一个入口点 `runtime_manager.egress_proxy`，监听 3128，同时接在内网与可出网网络上 | 唯一能看到主机名的一层：CONNECT 盲隧道，按 `Proxy-Authorization` 区分应用，每个应用只放行平台 API、附件端点和它自己声明的 `egress.domains`；直连 IP 拒绝；默认只放 80 / 443；解析后的地址再查一次，防止被当跳板进入内网 |
| L3 宿主防火墙 | `firewall_rules()` 生成 iptables `DOCKER-USER` 或 nftables `bisheng_egress` 表：允许到代理、丢弃全部 UDP、其余丢弃 | 兜住「网络未以 --internal 创建」的情况；也是唯一能拦 UDP（QUIC / HTTP3 无法按主机名过滤）的一层 |

egress-proxy 与 runtime-manager 的全部契约是策略文件 `{data_root}/egress/policy.json`，代理按 mtime 热加载并在读取失败时保留上一份，所以编排器重启不会带走所有应用的出站。runtime-manager 自动探测防火墙后端：Docker 29 默认的 nftables 后端没有 `DOCKER-USER` 链，iptables 规则会「下发成功」却不生效，探测到 nftables 时 preflight 判红。`RTM_EGRESS_PROXY` 留空表示整层未部署，preflight 明说「出站不受限」，不存在「开关已开但代理不在、出站全断」的组合。设计期曾称「双层」，实现按上表拆为三层。systemd 形态下有一个已知缺口，见 §7.4。

## 5. 发布管线（F055）

### 5.1 管线形态

发布管线是「同步接收端点 + Celery 异步阶段机」，`app_deployment` 表记录一次发布尝试的进度，CLI 轮询 `GET /api/v2/apps/deployments/{id}`。`/api/v2/apps/*` 端点标记 `open_api_scope("app:manage")`，走 §2.1 的单一鉴权管线；应用 owner 取凭据的资源归属人，归属人为空即拒，迭代发布只允许 owner。

同步段在 `publish_pipeline_service.accept()` 中秒级完成：解包（包体、解包后大小、文件数三道闸，默认 50 MB / 200 MB / 20000）→ manifest 校验 → 首发建草稿或迭代做归属判定 → 在途与待上线两道闸 → 能力引用校验（16224）→ 代码包写入 MinIO。异步段是 `worker/app_publish/tasks.py::run_publish_pipeline`，跑在 Celery **default 队列**上，与审批 outbox 共用 default worker，不另建队列；所以改动 `app_publish` 后必须重启 celery default worker。异步阶段顺序由 `PIPELINE_STAGES` 决定：

```
secret_scan → precheck_schema → precheck_build → precheck_probe → 写版本记录 → 提交审批
```

密钥扫描排在构建之前，与 PRD DEV-04 的字面顺序相反，这是有意的：含密钥的包不应该进入构建容器（spec 决议-13）。任一阶段失败即停，失败原因统一为五元组 `{stage, code, message, details, hints}`（`schemas/failure.py`），CLI 原样展示服务端的 `stage`。预检或扫描失败的提交不进版本列表。

### 5.2 应用包声明 `bisheng-app.yaml`

manifest 的权威定义是 `app_publish/domain/schemas/app_manifest.py`，pydantic `extra='forbid'`，未知字段直接拒绝。CLI 与 runtime-manager 只消费它，不各自定义。

| 字段 | 含义 |
|---|---|
| `manifest_version` | 当前为 1，前向兼容闸 |
| `name` / `description` / `icon` / `slug` | 元信息；`slug` 决定入口 `/apps/{slug}`；元信息在通过预检时更新 |
| `runtime` | `python3.11` / `node20` / `static`，不支持返回 16222 |
| `port` | 应用监听端口 |
| `tier` | 资源档位，不写即 `light` |
| `capabilities.models[].name` / `capabilities.knowledge_bases[].{id\|name}` | 能力声明（RT-04） |
| `database.tables[].columns[]` | 应用数据表结构，由平台建表 |
| `egress.domains[]` | 运行期出站域名白名单 |

设计期 manifest 中的 `entry`、`appdb: sqlite|postgres`、`secrets` 三个字段没有实现：入口命令由模板约定，应用库只有 SQLite，密钥引用原划归 PRD-2，当前预检遇到能力声明中的密钥引用会拒绝；2026-10-09 改判为本版交付最小版（PRD-1 GOV-05），该字段待实现（§9）。

### 5.3 密钥扫描

扫描器是 `secret_scanner.py` 中的常量规则表 `SECRET_SCAN_RULES`，不引入 gitleaks / detect-secrets，原因是 PRD 要求「与平台内发布同一规则集」，这要求规则集由本仓库持有。规则包括 `bs_sak`、`bs_pat`（引用凭据底座的前缀常量）、`aws_akid`、`openai_sk`、`private_key_pem`、`db_conn_string`（用户名与密码同时出现才命中）和带占位符白名单的 `generic_high_entropy`。命中结果只含 `{rule_id, file, line}`，不带值，也不带掩码值。二进制文件与超过 1 MiB 的文件跳过，并在结果中列为 `skipped`，不静默放过。扫描器不提供行内豁免注释。

### 5.4 版本记录、冻结快照与结构演进

每次通过预检的发布生成一条 `app_version`，代码包、manifest、能力声明、注入配置（不含明文凭据）、档位标识、runtime、镜像引用作为同一个快照冻结（RT-05）。写入顺序是「先过审批 Gate，再 INSERT」（F055 design D6）。档位只存标识，规格按运行时的当前值解析。平台侧版本回滚本版不做（PRD-1 §1.5），WB-15 只提供版本差异的只读查看。

结构演进由 `schema_evolution_service.py` 比较新旧 `database.tables`：只加列时自动迁移；改列或删列必须由开发者显式确认（`bisheng deploy --confirm-schema-change`），并在迁移前留数据库快照。迁移以声明式计划经 `db-migrate` 意图交给 runtime-manager 执行（§4.7）。生产数据不随代码回退。

### 5.5 审批接入

发布审批复用审批中心（F025），新增场景 `app_publish_request`，接入点四处：预置定义 `approval/domain/services/approval_registry.py`、种子数据 `approval_seed_service.py`（启动时与新建租户时各执行一次）、运行期 handler 工厂分支 `approval_runtime_handler_factory.py`、业务 handler `app_publish/domain/services/app_publish_scenario_handler.py`。预置流程是「owner 主部门的部门管理员 ∪ 租户管理员，或签」，Root 租户回退平台超管；申请人是应用 owner 本人，不是服务账号。审批通过后，outbox 在 Celery default worker 上执行 `on_approved`。审批模块的整体结构见 `approval-module` 技能。

**发布必审**（INV-34）。场景预置带 `mandatory_approval=True`。`ApprovalScenarioAdminService._assert_route_type_allowed` 在新建与修改路由时拒绝免审分支，返回 18119；`ApprovalGate._forbids_pass` 是第二道防线，即使库里已有免审路由，匹配到也按「未匹配」处理并记 `route_missing` 异常，不放行。这一缺陷在 2026-09-18 验收时发现并修复。

**审批期预览。** 审批人可以拉起待上线版本的临时预览实例（`preview_instance_service.py`，`app_preview_session` 表），入口为 `/apps/preview/{session}`。预览实例的 `/data` 用 tmpfs、不注入附件凭据，寿命由 `app_runtime.preview_ttl_days`（默认 7 天）与审批终态共同决定。预览中平台能力按 owner 权限放行并计审计，这是 INV-36 唯一的例外。审读视图提供文件树、代码与版本差异（`snapshot_browse_service.py`、`version_diff_service.py`）。

### 5.6 上线终检与资源档位

上线终检在 `publish_online_service.py` 中执行，规则是「应用会自己好转或点一下就好的，标状态返回；真正出错的，抛异常」。容量准入失败时应用进入 `pending_capacity`（待上线·资源不足）；拉起或探活失败时应用同样进入待上线态，版本终态标「待上线」；应用已删除或已下线时只登记版本、不拉起；编排器不可达或状态机拒绝时抛异常，outbox 把审批实例记为 `execute_failed`。F055 从不直接写 `app.state`，一律调用 F054 的 `AppStateService`。手动上线不再走审批。

资源档位（GOV-03）预置三档，常量是 `app_runtime/domain/constants.py::DEFAULT_TIERS`，F055 从它 seed `resource_tier` 表，表存在后以表为准：

| 档位 | 规格 | 适用 |
|---|---|---|
| `light` 轻量（默认） | 0.5 vCPU / 1 GiB | 内部工具、表单、看板类，并发个位数 |
| `standard` 标准 | 2 vCPU / 4 GiB | 带数据处理或文件解析，日常并发几十 |
| `performance` 性能 | 4 vCPU / 8 GiB | 计算密集或常驻大内存 |

轻量档在 PRD-1 中写为 1C/2G，F055 spec 决议-10 于 2026-09-09 按实测下调为 0.5C/1G：五个在线应用合计只用 0.05% CPU 与 98 MiB，每应用占一整核会让 8 核机器最多同时运行 6 个应用，瓶颈在 CPU 配额闸而不在机器本身。档位只能停用不能删除，平台超管在系统管理「资源档位」tab 调整规格（审计 `app.tier_update`）。未写过档位的部署可以在首次启动前用 `app_runtime.default_tiers` 覆盖出厂规格。

### 5.7 能力总线与应用运行期凭据

**能力总线**（GOV-05，`capability_bus_service.py`）把能力声明变成注入与判权。当前实现覆盖模型与知识库；第三项应用密钥（owner 掩码录入、平台注入同名环境变量，PRD-1 GOV-05）于 2026-10-09 定为本版交付，尚未实现，注入通道已为引用名预留位置。模型侧，平台注入 `OPENAI_BASE_URL` 与 `BISHENG_MODEL_BASE_URL`（均为 `{平台}/api/v2/model/v1`）以及 `OPENAI_API_KEY`（等于 `BISHENG_APP_TOKEN`），应用用标准 `openai` 客户端调用 F051，可调范围是当前生效的声明，拒绝沿用 265 段错误码。知识库侧，白名单在运行期从 `app.current_version_id` 指向的版本读取，不缓存、不由应用上报，可及范围 = 白名单 ∩ 当前访问用户可见范围，由 §2.3 的检索门面按文件级计算；拿不到访问用户身份即返回 26320，不回退为 owner 权限或声明全量（INV-36）。能力被管理员收回后，「已失效」状态在查询时实时计算，不落库，收回与未声明分别返回 16273 / 16274。注入变量经 `app_runtime/domain/services/runtime_env_ports.py` 端口合并，因为 arch-guard RULE-5 禁止 `app_runtime` 反向 import `app_publish`；`BISHENG_` 前缀是平台保留名，平台值覆盖同名的应用值。

**应用运行期凭据**（GOV-08，`app_credential_service.py`）是主体类型 `hosted_app` 的 `bs-app-` 凭据。因为 `api_credential.subject_id` 是整数而 `app.id` 是字符串，每个应用在 `hosted_app_subject` 表领一个整数代理 id，该行永不删除，保证代理 id 不被复用。签发时机是审批通过、拉起新容器之前：先撤销旧凭据再签发新凭据，明文只经环境变量 `BISHENG_APP_TOKEN` 注入一次，不落库。下线时停用主体，重新上线后同一把凭据恢复可用；删除应用时由 F054 `lifecycle_hooks` 的订阅者撤销。撤销 5 秒内生效。`hosted_app` 主体只能进入标了 `hosted_app=True` 的路由，目前只有 `POST /filelib/retrieve` 与模型面三条路由。签发与撤销写 `open_api.api_key.issue/revoke` 审计，操作者为系统。

应用调用平台能力时出示两把凭据：`Authorization: Bearer <BISHENG_APP_TOKEN>` 证明「哪个应用」，`X-BiSheng-Access-Token`（OBO 令牌）证明「为谁」。应用运行期凭据本身的 `effective_user_id` 有意为空，访问用户只能来自 OBO 令牌。

**能力调用记录。** 托管应用的检索调用写 `app_capability_call_record`（应用、能力、目标、结果、chunk 数、时延、凭据 id，双归属为「应用 × 访问用户」），模型调用写 F051 的 `model_call_record`，两者都不进 `audit_log`。这两张表与 `app_access_log` 目前只写不读，见 §6.3。

## 6. 治理（F056 及 F054 类型注册）

### 6.1 权限资源类型

托管应用以资源类型 `app` 注册进 F048 权限体系，走 `MIGRATED_RESOURCE_TYPES` 全适配器路线（`core/openfga/authorization_model_f048.py`，适配器 `app_runtime/domain/services/f048_app_permission.py`），注册归 F054，F056 只消费。`app` 按扁平资源类型建模，与 channel、dashboard 同形，适用动作是 `manage_permission`、`edit`、`delete`、`use`、`publish`、`unpublish`；入口判定用的是 `use`。

FGA 模型在本分支命名为 `MODEL_VERSION = "f048-v5-app"`，规则是「所基于的发版线版本号 + `-app`」，避免占用发版线编号。114 上登记名仍是 `f048-v6`，checksum 相同，无需重新发布。应用工场正式合入发版线时，116 / 105 需要停服执行 `src/backend/scripts/publish_authorization_model_change.py` 发布含 `app` 的模型。存量环境的 Catalog 范围表变更靠 F054 新写的升级脚本补 scope 行，该脚本只覆盖 `app` 一种类型。

### 6.2 应用广场与可见范围

应用广场复用工作流 / 助手的既有列表，在 `database/models/flow.py` 的 UNION 中加第三支（投影 10 列，含 `app_state`）。广场请求对托管应用豁免 `status` 条件，改为服务端写死只取 `{online, stopped}`，所以草稿在行集层面就不存在；动作口径从 `visible` 改为 `use`；搜索只按名称。卡片点击用 `window.location.assign('/apps/{slug}')` 整页跳转。

可见范围有两个入口：构建页卡片 ⚙️「管理权限」与发布面的 `VisibilityScopeSection`，两者拉起同一个 `PermissionDialog`，零新建授权界面。「仅 owner 可见」的判据是非 protected 授权行数为 0。可见范围变更不经审批、即时生效，由挂在 F048 `mutate_grants` 上的按类型回调写 `app.visibility_change` 审计。界面通道的「创建应用」沿用既有 `create_app` 权限点，CLI 通道由密钥 `app:manage` 位把关，两条通道互不校验（GOV-07）。

### 6.3 审计

应用工场写四类记录，可查询性不同：

| 记录 | 内容 | 写入方 | 查询入口 |
|---|---|---|---|
| `audit_log` 中的 `app.*` / `app.release.*` 事件族 | 发布、上线、下线、删除、元信息、可见范围、数据编辑与导出、档位调整 | F054 / F055 / F056 | 有：审计页，后端白名单、`log.ts`、三语文案四处同步 |
| `model_call_record` | 逐条模型调用 | F051 | **无**：DAO 有 `alist` / `aiter_export`，业务代码零调用 |
| `app_capability_call_record` | 托管应用检索调用 | F055 | **无**：只有 `ainsert` |
| `app_access_log` | 谁在什么时间进入哪个应用 | F054 | **无**：`alist_page` 零调用方 |

后三类只写不读，PRD-1 GOV-04 验收要点 1、3 目前不可达。2026-10-09 定为方案 A：审计页新增「应用运行记录」tab，三类记录各一个子视图（PRD-1 GOV-04），待实现（`features/v3.0.0/056-app-square-governance/tasks.md` 末节）。实现时运行期凭据审计行的 `metadata` 需顺带补 `app_id`。`audit_log` 新增 action 时必须四处同步（`AppAuditAction` 枚举、`audit_log.py` 白名单、platform `log.ts`、三语文案），否则事件写入但界面不可见，lockstep 测试遍历的是 `AppAuditAction`。

### 6.4 事件触达

发布相关事件通过站内信触达，全部是纯陈述消息，不带操作按钮（`app_publish/domain/services/publish_notification_service.py`）。审批通过、驳回、撤回的消息由审批引擎发出；F055 只补发三类：审批单创建后通知首节点审批人、容量不足进入待上线、拉起失败进入待上线，后两类发给 owner 与管理员的并集。应用删除导致审批取消时由 `cancel_instance_by_business` 通知。上线成功不额外发站内信。应用态变化的其余通知在 `app_runtime/domain/services/state_change_notify.py`。

## 7. 安全模型

### 7.1 身份信任根

托管应用获得访问者身份的唯一可信来源是 app-proxy 注入的请求头（INV-32）。这条不变量依赖四个条件同时成立：容器不发布端口、只能经 app-proxy 到达；app-proxy 按归一化前缀剥离一切 `x-bisheng-*` 客户端头；app-proxy 摘掉平台会话 cookie，不把平台凭据交给容器；OBO 令牌用独立的 `obo_secret` 签发，与 `jwt_secret` 不同，防止 OBO 令牌被当作平台会话重放。应用侧不得自建登录页，SDK 在缺身份时抛异常而不是返回匿名。本地 `bisheng dev` 期身份是开发者服务账号，不提供模拟开关。

进程间调用用三把独立的 HMAC 密钥（§4.2）。HMAC 只防篡改、不防暴露，所以 runtime-manager 与 app-proxy 默认只监听回环地址；systemd 形态下若要让容器访问附件接口，runtime-manager 需要改监听 `bisheng-apps` 网桥网关地址，该地址只在宿主本地可达。

### 7.2 编排特权隔离

backend 编译期与运行期零编排依赖：`scripts/arch-guard.sh` RULE-10 禁止 `src/backend/bisheng/**` import docker / kubernetes 客户端、出现 `/var/run/docker.sock` 字面量、读取 `DOCKER_HOST`。编排一律经 runtime-manager 的意图 RPC 下发期望态。app-proxy 与 egress-proxy 都不持有 docker 权限。compose 形态下 runtime-manager 也不直接持有 socket，只能经 docker-socket-proxy 调用白名单端点（§4.3）。特权逐级递减的链路是 backend → runtime-manager → docker-socket-proxy → dockerd。

### 7.3 沙箱分档

| 档位 | 实现 | 状态 | 适用环境 |
|---|---|---|---|
| 基础档 | Docker 加固：只读 rootfs、`no-new-privileges`、非 root、`--internal` 网络、资源限额、restart policy | **已实现，唯一一档** | 全部环境，含 LoongArch |
| 推荐档 | gVisor systrap 平台（无需 KVM） | 未实现 | x86_64 / ARM64 虚机 |
| 加固档 | gVisor-KVM / Kata / Firecracker | 未实现 | **仅裸金属** |

档位规则来自选型调研：gVisor 官方只推荐在裸金属上用 KVM 平台，虚机内即使有嵌套 KVM 也应用 systrap；Kata 全系 VMM 硬依赖 KVM；gVisor 与 Kata 都不支持 LoongArch，龙芯机型只有基础档。gVisor 的 netstack 没有按域名过滤出站的能力，换 runtime 不解决出站问题，所以出站白名单的优先级高于沙箱档位。

### 7.4 出站白名单与已知缺口

出站白名单的三层实现见 §4.9。它有一个已知安全缺口：开启白名单后，**systemd 形态**下托管应用容器仍可经 `bisheng-apps` 网关 IP 直连宿主上监听 `0.0.0.0` 的服务（114 上实测可达 MySQL 3306、backend 7860、MinIO 9000、SSH 22）。原因是 `--internal` 只断默认路由，访问网关地址的包走宿主 INPUT 链，而 L3 规则以 `-s <应用网段>` 挂在 `DOCKER-USER`（FORWARD 路径）上，碰不到这些包。修复方向是在宿主 INPUT 链补规则：对应用网段只放行 egress-proxy 与附件端口。2026-10-09 定为合入发版线前修复，已登记到 F054 tasks.md。compose 形态下 `docker/docker-compose.yml` 把 MySQL 3306、backend 7860、MinIO 9100 等端口发布到宿主，容器经网关 IP 访问这些发布端口的包是否会被 L3 规则拦截，取决于 docker 的端口转发实现，目前没有验证，合入前需要一并核对。

### 7.5 密钥零暴露

平台自签发凭据服务端只存单向哈希，明文只在签发时展示一次（INV-28）。CLI 凭据文件 0600 原子创建。发布前密钥扫描门阻断含裸密钥或连接串的包，命中结果不含值（§5.3）。应用运行期凭据只经环境变量注入一次，不进 `app_version.injections`、不落库。HMAC 密钥与 OBO 密钥经环境或 `config.yaml` 注入，`config.yaml` 中的密码按平台惯例 Fernet 加密。应用级密钥录入（secret store）划归 PRD-2，本版不提供。

### 7.6 fail-closed 矩阵

下表列出各判定点在依赖不可用时的行为。前五行是 fail-closed；后两行是已知的 fail-open，均有记录在案的理由，但需要在合入前复核。

| 判定点 | 依赖不可用或结果不可判定时 |
|---|---|
| `/api/v2` 端点漏标 `open_api_scope` | 拒绝 |
| 检索门面权限评估（MCP / v2 / 能力总线 / SDK） | 整体报错，不返回部分结果（INV-30） |
| 托管运行期检索缺访问用户身份 | 26320 拒绝，不回退为 owner 或声明全量（INV-36） |
| app-proxy 入口判定：权限引擎不可用、未知判定值、HMAC 密钥为空 | 拒绝 / 503 |
| runtime-manager HMAC 密钥为空 | 401，backend 报 16121 |
| 入口判定中「租户已禁用」检查遇 Redis 不可达 | **放行**，与 `CustomMiddleware` 行为一致；只有权限引擎是 fail-closed。2026-10-09 确认维持：改成拒绝会让一次 Redis 抖动锁死所有租户的所有托管应用，而它防的只是刚停用的租户在故障期间短暂可进入 |
| `obo_secret` 缺失或等于 `jwt_secret` | **不签发 OBO 令牌但照常放行入口**；此时应用的能力调用因缺身份被拒。2026-10-09 定为合入发版线前改为**拒绝进入**（入口显示配置不完整页，启动日志报错），已登记到 F054 tasks.md |

## 8. 部署形态

本节说明各形态的架构差异。装机步骤、`app_runtime` 与 `open_platform` 配置项、升级顺序和排障对照表见 `docs/architecture/14-app-factory-deployment.md`。

### 8.1 compose 形态

compose 形态在 `docker/docker-compose.yml` 中以 profile `app-runtime` 声明四个服务：runtime-manager、docker-socket-proxy、egress-proxy、app-proxy，都不发布端口。不带这个 profile 启动即等于工场运行时层整层不装。两张网络 `bisheng-apps` 与 `bisheng-build` 以 `internal: true` 和显式 `name:` 声明，显式命名是因为 runtime-manager 用裸 Docker API 按真名引用网络，compose 默认的项目名前缀会让它找不到网络。runtime-manager 需要同时设置 `RTM_DATA_ROOT`（容器内路径）和 `RTM_HOST_DATA_ROOT`（宿主路径），因为 bind 路径由宿主 dockerd 解释。静态守卫是 `docker/verify-app-runtime-compose.sh`。compose 形态从未在真机启动过（F054 T074），此前发现的三个缺陷都被 systemd 形态恰好正确的配置掩盖，所以 114 跑通不能证明 compose 可用。

### 8.2 systemd 形态（114）

114 运行 systemd 形态。三个单元的模板在 `features/v3.0.0/054-app-domain-runtime/deploy/`：`bisheng-runtime-manager.service`（`Requires=docker.service`）、`bisheng-app-proxy.service`、`bisheng-egress-proxy.service`，均 `PartOf=bisheng.target`，环境变量分别读 `/etc/bisheng/{runtime-manager,app-proxy}.env`。真身在独立运维仓 `bisheng-ops/systemd/`，`/opt/bisheng-ops/deploy.sh` 部署时一并重启。前置资源是 `docker network create --internal bisheng-apps` 与 `bisheng-build`；已存在的网络不会被 `create` 改为 internal，必须先停全部托管应用、删网、重建，preflight 的 `application_network_internal` 一行用来发现这种情况。egress-proxy 必须监听 `bisheng-apps` 网桥网关地址而不是 `0.0.0.0`，且与 runtime-manager 的 `RTM_EGRESS_PROXY` 逐字相同。nginx 在 `/etc/nginx/conf.d/` 的入口 conf 中加 `location /apps/`。

### 8.3 k8s 形态（本版交付，尚未实现）

k8s 执行后端是 F059。2026-10-09 定为本版交付、不顺延（PRD-1 GOV-10），目前只有 spec（42 条有效 AC），design 与 tasks 待写。规划内容是：Deployment / Service reconcile、命名空间级 RBAC、档位映射 Pod requests / limits、RuntimeClass 沙箱档位、NetworkPolicy 出站白名单、无守护进程构建器加镜像仓库对接、集群能力探测与告警、Helm chart。设计约束是 INV-33：两种形态的产品行为不得有任何差异，差异全部压在编排器内部；形态在部署期二选一，不做形态间迁移。backend 与 app-proxy 的契约不变，只替换 runtime-manager 的执行后端；`docker_backend.py` 的 Protocol 抽象就是为此保留的接缝。注意 SQLite 应用在多节点下必须先解决「单实例 + 本机卷」约束（§4.7）。PRD-1 §1.4 仍把 k8s 列为本册功能，与顺延登记不一致，待拍板。

### 8.4 可选部署（GOV-10）

不部署工场运行时层的环境，平台既有功能零新增常驻进程、行为零变化（NFR-4）。开关组合见 §1.3。`/api/v1/env` 同时下发四个互相独立的开关：`open_platform_enabled`、`app_runtime_enabled`、`personal_token_enabled`、`open_api_management_enabled`。`config.yaml` 新增顶级键会让老镜像拒绝启动，部署新版本时需要确认镜像与配置同步升级。

### 8.5 信创与离线约束

| 环境 | 构建 | 沙箱 | 出站 L3 | 备注 |
|---|---|---|---|---|
| x86_64 / ARM64 虚机（无嵌套虚拟化） | Dockerfile 模板 + 私有包源 | 基础档 | iptables `DOCKER-USER` | gVisor systrap 在鲲鹏 / 飞腾 + 麒麟 / 统信内核上无实测 |
| x86_64 / ARM64 裸金属 | 同上 | 基础档（KVM 类档位未实现） | 同上 | — |
| LoongArch | 同上 | 仅基础档 | 同上 | gVisor 与 Kata 均不支持 |
| 完全离线 | 基础镜像随安装包预置；`RTM_BUILD_INDEX_URL` / `RTM_BUILD_NPM_REGISTRY` 指向内网源 | 同上 | 同上 | 只预置部分基础镜像时，runtime 列表自动收窄 |
| Docker 29+（nftables 后端） | — | — | 无 `DOCKER-USER` 链，需 nftables 表或锁定 iptables 后端 | preflight 判红 |

设计期规划的 devpi（PyPI）与 verdaccio（npm）自托管镜像没有随产品交付，实现只提供包源地址配置项，由部署方自备内网源。

## 10. PRD-2 相关的技术设计（搁置）

PRD-2（平台内对话式造应用工作台与应用管家）已无限期搁置，下列设计均**未实现**，只保留结论供将来立项时参考。

**引擎适配层。** 设计为 Python `RuntimeAdapter` 抽象，按「CLI 进程 + JSONL / JSON-RPC 事件流」建模，统一 `run(RunConfig)` 契约，流式事件归一化为 text_delta / thought / tool_use / tool_input_delta / tool_result 五类。引擎候选按 2026-07 调研排序为 Qwen Code（Apache-2.0，默认候选）、Codex CLI（Apache-2.0，第二适配器）、Kimi Code CLI（MIT，观察位）；Claude Code 无分发授权，永不内嵌，只作客户自装的兼容位。默认引擎须由 Wave-0 PoC 按量化 go/no-go 门槛决定，评测口径必须包含多轮鲁棒性，并以模板生成器作对照基线；若开源引擎在国产模型上无法稳定多轮驱动，模板生成器即成主干。

**引擎凭据。** 设计为凭据档案 `auth_profile`，与引擎种类正交，三条路径均由管理员配置：A 平台模型代理（默认，会话 key 随会话签发吊销）、B 客户订阅登录态（加密入档、挂载注入、档案级并发闸）、C 客户自有厂商 key（建议仍作为平台代理上游）。会话 key 与本版应用运行期凭据是不同用途，届时仍应复用 §2.1 的凭据底座。路径 A 若要支持 Anthropic 协议引擎，需要重新评估 §2.2「只做 OpenAI 兼容」的决定。

**基础组件注入。** 设计为四条通道：模板预接线、声明式资源清单（manifest 能力声明与数据表结构）、MCP 工具面、引擎指令约束加发布前扫描。其中声明式清单、MCP 工具面与发布前扫描已在 PRD-1 中实现，PRD-2 可直接复用同一规则集与同一 manifest。

**草稿沙箱与工作区。** 设计为草稿态与生产态共用 runtime-manager 设施，预览经 `/apps/preview/{session}/`；工作区（git + node_modules）需要新增 tar / bulk-snapshot 层，因为灵思 workspace 是逐文件 write-through 对象缓存，不是时间点快照。PRD-1 已实现的审批期预览实例（§5.5）可作为草稿预览的起点。应用级 secret store（Fernet）、管家持续看护及其依赖的平台触发 / 调度子系统、通知外发服务、postMessage 嵌入白名单均随 PRD-2 或 v3.1 立项。
