# Feature: 前端请求错误完整透传

> 本文档只定义需求、验收标准和范围。状态：2026-10-22 用户已确认；已进入产品代码实施，验收状态见 tasks.md。

**关联 PRD**：无独立 PRD；需求来自 2026-10-22 本会话，已确认的目标与发现见 [discovery.md](./discovery.md)。
**优先级**：P1
**所属版本**：v3.0.0 / F088
**依赖**：两端现有请求、错误提示、登录与权限处理能力；复用发版线已合入的 React Query 4.44.0 升级。

## 1. 用户故事与范围

作为平台使用者，我希望操作失败后保留输入、恢复可操作状态，并看到准确且不重复的提示，以便知道是否需要重试或调整输入。

作为业务功能维护者，我希望两端都能取得完整失败原因，以便处理表单错误、业务冲突和页面状态恢复，无需为每个接口绕开统一请求处理。

本次纳入：platform 与 client 经各自统一 HTTP 请求入口发出的请求；其 API、页面与 hooks 的错误消费；错误提示与失败状态的分离；旧调用方式迁移和回归。

本次排除：后端返回协议和错误码定义调整；两端成功结果结构合并；请求库、查询库和状态库升级；提示样式或权限规则变更；自动重试和新业务恢复机制；SSE、WebSocket、原生 fetch 等未经过上述统一入口的通道。排除的原因是这些能力不需要随错误透传调整，改动会扩大兼容范围。

## 2. 验收标准

### 2.1 识别失败与保留原因

- **AC-01** — WHEN 接口在 HTTP 成功响应中明确返回业务失败，THE SYSTEM SHALL 将这次调用判为失败，使调用方进入失败处理，不能继续执行成功后的动作。
- **AC-02** — WHEN 请求因 HTTP 错误、网络异常或超时失败，THE SYSTEM SHALL 使调用方进入失败处理，不将失败作为空的成功结果返回。
- **AC-03** — WHEN 调用方处理请求失败，THE SYSTEM SHALL 允许其分别取得实际存在的 HTTP 状态、业务错误码、用户可读消息、服务端附加信息及原始失败证据；不存在的信息不得被伪造为成功或其他业务错误。
- **AC-04** — WHEN 任一端处理同类请求失败，THE SYSTEM SHALL 提供一致的错误含义，使业务分支无需依赖字符串猜测、消息文本比较或“有没有弹窗”来判断失败类型。
- **AC-05** — WHEN 已有业务包装层接收到请求失败，THE SYSTEM SHALL 在完成本次迁移后继续向调用方传递失败及完整原因，不能仅以 false、undefined、null 或消息字符串替代该失败。

### 2.2 提示与业务处理

- **AC-06** — WHEN 请求采用统一提示策略并失败，THE SYSTEM SHALL 保留对应入口既有的默认提示效果，同时允许调用方继续取得 AC-03 所列信息。
- **AC-07** — WHEN 同一请求失败已由统一提示展示，THE SYSTEM SHALL 避免因 API 包装层或业务层的通用提示再次展示相同错误。
- **AC-08** — WHERE 请求由业务自行提示或明确要求静默，WHEN 请求失败，THE SYSTEM SHALL 保留完整失败信息并执行所需业务恢复，不因关闭普通提示而将请求判为成功。产品既有强制全局处理仍满足 AC-15。
- **AC-09** — WHEN 失败消息已有简体中文、英文或日文翻译，THE SYSTEM SHALL 按当前语言展示对应消息；未登记的服务端消息仍须可阅读，不得展示翻译键、对象默认字符串或未替换的模板占位符。
- **AC-10** — WHEN 请求被主动取消，THE SYSTEM SHALL 使调用方可识别取消，且不将取消展示为普通失败提示。

### 2.3 页面行为

- **AC-11** — WHEN 表单提交或编辑保存失败，THE SYSTEM SHALL 恢复可操作状态、保留用户输入，不显示成功提示，不因失败自动关闭编辑窗口或执行成功后的跳转。
- **AC-12** — WHEN 列表加载失败且未被既有业务恢复规则明确处理，THE SYSTEM SHALL 保持失败可辨认，不能把失败伪装成成功加载的空列表。
- **AC-13** — WHEN 删除或状态切换失败，THE SYSTEM SHALL 不把目标显示为已成功变更；已有乐观更新的入口须恢复或重新同步页面状态。
- **AC-14** — WHEN 业务已存在针对特定错误码的恢复流程，THE SYSTEM SHALL 保持该流程可用，并让其依据错误码及附加信息执行，不依赖通用提示文案。

### 2.4 全局与兼容边界

- **AC-15** — WHEN 发生登录失效、账号被踢、通用权限不足、许可证失效或维护状态，THE SYSTEM SHALL 保留该入口既定的跳转、确认、提示节流或遮罩效果，并向调用方保留可识别的失败信息。
- **AC-16** — WHEN 并发请求触发同一会话或许可证全局事件，THE SYSTEM SHALL 保持既有去重、节流和确认顺序，不因错误透传叠加重复全局提示或跳过确认。
- **AC-17** — WHEN 请求本身成功，THE SYSTEM SHALL 保持两端各自既有成功结果和文件下载效果；合法的非统一格式响应不能仅因缺少业务状态码被判为失败。
- **AC-18** — WHEN 接口约定中的非普通结果需要调用方继续交互，THE SYSTEM SHALL 保留该交互流程，不能仅因结果形式特殊而将其当作普通成功或普通失败处理。
- **AC-19** — WHEN 请求返回不可读或不符合预期的错误内容，THE SYSTEM SHALL 使失败保持可识别，展示可读的既有通用错误消息，并保留原始证据；错误消息解析自身不能中断失败处理。
- **AC-20** — WHILE 两端迁移分批进行，THE SYSTEM SHALL 使每批受影响入口同时满足对应失败传递及页面恢复要求，不要求使用者承担失败后错误成功提示、按钮卡住或未处理异常造成的功能故障。
- **AC-21** — WHEN 本特性交付验收，THE SYSTEM SHALL 使两个统一请求入口及实际消费它们错误的调用方均满足 AC-01 至 AC-20；不能仅用局部选择开启透传来宣称完成。

## 3. 边界情况

- HTTP 状态和业务错误码可能不同；二者保留各自含义，见 AC-03。
- 网络断开或取消时可能没有服务端响应；保留真实原因，见 AC-02、AC-03、AC-10。
- 错误消息可能为数组、嵌套对象或未替换模板，见 AC-09、AC-19。
- 关闭普通提示不能被解释成关闭已有登录/安全处理；既有明确的请求级全局处理例外在设计阶段逐项核实，见 AC-08、AC-15。
- 下载成功返回二进制，下载失败也可能返回二进制包装的错误；成功须可用，失败须可识别，见 AC-17、AC-19。
- 已有明确允许的“许可证状态不可用时隐藏”等业务恢复不是通用吞错；须逐项保留并测试，见 AC-12、AC-14。
- 特殊状态 11010 当前只有拦截器放行证据，尚未找到活跃业务语义；实施不得凭猜测新增恢复流程，按 AC-18 核实后在 design 中记录。
