## 结论

确认两处正常界面可达的规则冲突，均沿自 v3.0.0，不是本轮数据集修复引入：

| 编号 | 页面/业务 | 前台规则与接口规则 | 实际影响 | v3.0.0 对照 |
| --- | --- | --- | --- | --- |
| M01 | 模型 → 模型微调：训练任务、训练数据、FT 服务、GPU、训练发布 | `/model/finetune` 只需 `model` 菜单；顶部分页和创建/FT 管理按钮未按管理员身份收口。`/finetune/job`、`/server/filters`、`/model/list`、`/gpu` 等接口仍要求全局超管或当前租户管理员 | 有模型菜单但不是租户管理员的人能进入页面，列表/筛选加载失败，仍看到创建等不可用入口；错误复用 19801“Root 共享模型只读”。多租户中的部门管理员也受影响 | 菜单路由、模型微调页入口及管理员依赖均相同，原有问题 |
| M02 | 模型管理：单租户部署的添加服务、系统模型设置等管理入口 | `canManageModelSettings` 在单租户/未提供多租户标记时允许普通角色的 `model` 菜单；后端 `get_tenant_admin_user` 不区分单租户模式，Root 上非超管即拒绝 | 单租户的模型菜单用户可看到部分管理入口，但新增/保存仍失败。模型行自身若标记只读，配置按钮另有只读限制，并非所有编辑入口都可点。多租户普通用户的管理按钮已隐藏，不计入此项 | 同一前端单租户回退和后端管理员依赖已经存在 |

M01 的业务包括训练、发布和训练服务维护，与数据集文件管理不同。不应直接沿用“有菜单即放开所有模型写接口”。若保持现行管理员管理合同，应先按管理员资格隐藏微调入口/按钮，并将身份准入失败与“正在修改 Root 共享模型”的业务错误区分。

M02 则需要统一单租户合同：前端当前明确承诺按模型菜单可管理，后端仍只认管理员。修复时应明确保留该菜单能力，还是收紧界面；本轮未自行修改权限。

## 接口直调缺口：按之前范围偏好单列

以下不作为“正常界面可点击后失败”的问题，也未擅自修复。它们在 v3.0.0 已存在。

| 编号 | 业务 | 已确认缺口 | 影响与验证边界 |
| --- | --- | --- | --- |
| A01 | 标注任务创建/删除 | 前端新建限管理员（当前另含子租户管理员），`POST /mark/create_task` 仅登录；直接进入创建及应用/标注员分配。`DELETE /mark/del` 也仅登录，直接调用删除 DAO，未复核操作人；其批量 DELETE 不应依赖只拦 SELECT 的租户过滤 | 自写客户端可绕过界面管理入口；删除还需核对任务归属与显式 SQL 租户边界。创建在本地无菜单/非管理员身份下返回 200 并调用存储 spy；未在现场创建或删除任何任务。删除仅确认源码调用链，不进行破坏性验证 |
| A02 | 评测结果文件下载 | `GET /evaluation/result/file/download` 仅登录，直接给传入 `file_url` 签名；不核对 evaluation 菜单、本人评测任务或对象归属 | 知道其他对象键时可能取得本不应提供的下载许可。正常列表仍按本人任务过滤，不能据此说列表泄漏。现场仅给专门构造的不存在对象键请求签名并确认成功，没有访问对象内容；本地无菜单身份也可调用签名 spy |

本地探针保留真实 ASGI 路由、TENANT 请求准入和接口函数，只隔离认证来源及实际存储/签名；不能以此声称已完成真实无菜单账号或跨租户破坏性验收。原始本地日志在 `/tmp/bisheng-menu-permission-audit-probes.log`。

## 已检查且不应直接按数据集方式放开的业务

| 页面/入口 | 当前业务规则与核对结果 |
| --- | --- |
| 模型列表、应用/知识中的模型选择器 | `/llm` 等只读目录允许登录用户读取授权范围并排除敏感配置，Root 显式共享可见；修改仍管理员。v3.0.0 已是此分工。不能给共用选择器统一叠加 model 菜单或管理员条件 |
| 工作台配置、工具与技能管理中的管理员配置项 | `HeaderMenu`、`canManageWorkbenchConfig` 将管理入口限超管/子租户管理员；后台写入同样受限。普通人的 `workstation` 菜单主要是使用工作台，不能据此放开管理配置。单独敲 `/build/client` 的旧路由可能进入部分页面，但正常导航已隐藏，按既定范围不列为优先界面问题 |
| 系统参数、主题、组织同步、邀请码 | 当前页面只对全局管理员显示相应页签，后台亦限全局身份/PLATFORM 范围。这些含实例级配置，与普通 sys 菜单不同。此轮未发现同类正常入口误拦截 |
| 系统组织与成员、角色、用户组 | 不是所有 sys 菜单用户都能管理所有人。当前真实管理员/部门范围、组创建者和可见性各有边界。用户组页面走 `/user-groups` 新 Service，并非旧 `/group/create`；不能只看到旧接口的 get_admin_user 就判定当前页坏了。v3.0.0 已有部门/租户管理员及创建者分工 |
| 应用模板 | 前端 `canManageAppTemplates` 和后端 `TemplateService.require_admin` 都限超管/当前租户管理员；普通应用创建者可以使用模板，不代表可维护全租户模板。原有分工，不是菜单误拦截 |
| 看板 | 创建入口与服务端均认 `create_dashboard` 或当前管理员；已有看板另按资源 visible/edit/delete。board 菜单不等同可任意编辑所有看板；当前未发现同类整页管理员误拦截 |
| 应用/工具/知识资源的具体操作 | 菜单是入口，资源操作还有 F048 动作与目标租户验证。构建菜单不等同编辑所有应用；知识菜单不等同所有文件动作。此轮核对入口及代表性调用链，不代替逐资源完整 E2E |
| 前台知识空间创建 | v3.0.0 的普通创建受原配额等校验；当前未显式选模型/处理参数的旧协议仍保留兼容。新增高级字段/创建初始设置才要求 create_knowledge（或管理员）。前台普通表单发送旧字段，因此不能仅看到新 KnowledgeCreationPolicy 就推断所有前台创建都被该菜单拦住 |
| 前台频道/订阅与知识空间设置 | 普通业务入口沿自然人、角色配额及具体资源动作，不是管理员配置接口。当前未发现与数据集相同的整个前台模块误接管理员依赖；未覆盖每条执行/流式/审批路径 |
| 评测列表、执行、删除 | 当前本人评测身份、任务归属和目标租户有独立验证；不是租户管理员管理整租户任务。不能将数据集“本租户数据集整体管理”规则套用；下载独立缺口见 A02 |

审批引擎、外部凭证/开放接口和分享链接未在本轮逐项审计；它们的菜单/身份合同不同，不依据后台一级菜单推定可用能力。
