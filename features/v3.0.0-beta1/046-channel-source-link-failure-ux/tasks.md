## Tasks

### Wave 1 — 状态机改造（核心，两个 bug 同源）

> T001–T003 **按序改同一个文件**（`useSourceManager.ts`）的三个不同层面：状态模型 → 请求驱动方式 → 失败路径收敛。刻意拆成三步是为了每步可独立验证、出问题能定位到层，不是重复劳动；实现时按顺序做，不要并行。

- [ ] **T001**: 添加面板界面状态显式化
  **文件**: `src/frontend/client/src/pages/Subscription/hooks/useSourceManager.ts`
  **逻辑**: 把"面板显示什么"从 **由关键字+结果数推导** 改为**显式状态**：`空闲 / 识别中 / 识别失败待修改 / 未收录 / 待确认爬取`。关闭失败弹窗 → 进入「识别失败待修改」（**保留关键字与输入框内容**，不清空——这是 AC-04 的要求，也是不能用"关弹窗清关键字"方案的原因，design §3 决策 1、§5 坑 1）
  **覆盖 AC**: AC-04
  **依赖**: 无

- [ ] **T002**: 识别请求改由提交动作驱动
  **文件**: `src/frontend/client/src/pages/Subscription/hooks/useSourceManager.ts`
  **逻辑**: 回车 = 一次显式提交，直接发起识别（不再依赖"关键字变化"这一副作用触发）；每次提交前重置上一轮的处理标记与请求令牌，使**同一链接可重复提交**；保留"识别进行中不重复发起"的防抖语义（design §3 决策 2、§5 坑 2）
  **覆盖 AC**: AC-05, AC-06
  **依赖**: T001

- [ ] **T003**: 失败路径统一收敛
  **文件**: `src/frontend/client/src/pages/Subscription/hooks/useSourceManager.ts`
  `src/frontend/client/src/api/channels.ts`（公众号添加请求关闭全局错误提示）
  **逻辑**: ①该请求不走全局红色 toast；②**所有**失败分支统一进「识别失败」状态并弹弹窗——堵掉既有「拿到错误码时只弹红条不弹窗」造成的静默卡死（design §5 坑 3）；③关闭弹窗与「暂不添加」共用同一套状态重置入口（§5 坑 5）
  **覆盖 AC**: AC-03, AC-04
  **依赖**: T001

### Wave 2 — UI 呈现

- [ ] **T004**: 失败弹窗 + 返回修改页 + 帮助入口
  **文件**: `src/frontend/client/src/pages/Subscription/CreateChannel/AddSourceDropdown.tsx`
  （帮助入口可抽为同目录下小组件）
  **逻辑**:

  - 浮层文案：「点击文章右上角「···」，选择「复制链接」，或选择「在浏览器打开」后复制地址栏中的链接。」
  **覆盖 AC**: AC-01, AC-02, AC-03, AC-04
  **依赖**: T003

## 手动验证清单（全部任务完成后按序跑）

1. 搜一个必然未收录的公众号名 → 出现"暂未收录" + 帮助入口 → 悬停出浮层 → 移出收起（AC-01/02）
2. 输入无效公众号链接回车 → **只**出中央弹窗、**无顶部红条**（AC-03）
3. 点「返回修改」→ 保留原链接、提示改链接重试、无"正在添加中"、「暂不添加」在、帮助入口在（AC-04）
4. **不改链接直接回车** → 重新识别 → 再次弹失败弹窗（AC-05，本特性最关键回归点）
5. 改成有效链接回车 → 正常添加成功（AC-06）
6. 切 en / ja 复查全部新文案（AC-07）
7. **回归**：网页 URL 路径（确认爬取 / 队列面板）与公众号名称命中路径完全不受影响
