# Design: 个人技能上传与技能中心

> **本文档定位 — 现状快照（Why this How）**
>
> spec 回答做什么。本文回答为什么这么实现。原先待确认的配额、同名再上传、运行中删除和临时文件都已定案。

**关联**: [spec.md](./spec.md)
**版本**: v3.0.0-beta3
**最后更新**: 2026-10-19

---

## 1. 目标与非目标

- **目标**：让用户把已有技能包存进服务端，技能中心统一展示「分给我的」和「我自己的」。每次任务把任务候选（已启用的企业技能和个人技能）整包拷进会话；勾选只在提示词里标明「用户选中了这个技能」。
- **非目标**：Kimi 创建、Office 转技能、个人技能分享或公开、浏览器本地预览库。平台管理员维护租户技能的现有入口保持原样，本需求不收紧那条路径的体积上限。

---

## 2. 关键约束

- 遵循 `docs/constitution.md` C1–C7。个人技能的写入只经过灵思技能服务；接口层不做仓库访问。
- 技能包今天整包进内存再写入对象存储（`SkillStore`）。个人上传必须用需求确认过的更紧上限：上传 50 MiB、解压 200 MiB、`SKILL.md` 1 MiB、条目 1000。这组数字小于现网租户技能的默认上限（上传 200 MiB、解压 500 MiB），两套上限并存。
- 现表唯一约束是 `(tenant_id, name)`。个人技能若仍用技能名当全局键，会和平台技能、其他用户的个人技能撞车。
- 任务启动时按内容哈希把每个候选的整包拷进会话。勾选只在提示词里标明「用户选中了这个技能」，未勾选的同样拷入整包。会话版本记下每个目录对应的技能 ID、归属用户和内容哈希，供后续读取和执行判断这个目录属于哪一行。已经放进会话目录的文件留到该任务结束；这份会话副本不依赖技能对象，删除和覆盖时直接回收旧对象。

## 3. 方案对比与选定

### 决策 1：个人技能挂在 `linsight_skill`，用归属用户区分

- **备选**：
  - A. 同一张 `linsight_skill`，增加 `owner_user_id`。`0` 表示租户技能（平台分配、内置、管理员上传），非 0 表示该用户的个人技能
  - B. 新建个人技能表，执行路径再合并
- **选定**：A
- **原因**：启用开关、对象路径、内容哈希、会话物化已经全走这张表和 `SkillStore`。第二张表会让自动匹配和物化各写一套。`owner_user_id` 不用 NULL：MySQL 唯一索引里 NULL 互不相等，平台技能的重名挡不住
- **何时该重新考虑**：个人技能要独立审核流、独立计费，或字段已经和租户技能分叉到无法共表

### 决策 2：唯一键改成「租户 + 归属用户 + 技能名」

- **备选**：
  - A. 保持 `(tenant_id, name)`，个人技能自动加用户前缀
  - B. 唯一键改为 `(tenant_id, owner_user_id, name)`，对外和运行时用技能 id
- **选定**：B
- **原因**：前缀会改写用户包里的技能名，和「导入已有技能文件」冲突。技能标识相同仍在「我的技能」的两个分组里都列出，AC-12 要求标来源。「技能广场」只保留企业技能。展示名相同而标识不同，按新技能保存。技能 id 已经是主键
- **何时该重新考虑**：产品要求个人技能与平台技能在自动匹配时按展示名合并成一个

### 决策 3：服务端出两份列表，共用归属条件，不由前端拼接

- **备选**：
  - A. 前端分别拉「平台技能」和「我的技能」再合并
  - B. 技能中心和任务候选用同一份列表
  - C. 服务端提供两个读取方法，共用同一套归属条件：本租户 `owner_user_id = 0` 的企业技能，加上本租户 `owner_user_id = 当前用户` 的个人技能。技能中心列已启用的企业技能和该用户全部个人技能（含停用，并返回启停状态）。任务候选只取已启用的企业技能和已启用的个人技能
- **选定**：C
- **原因**：AC-06 和 AC-09 要求停用的个人技能仍留在「我的技能」里可以再打开，而 AC-11 要求停用的不进入新任务。用一份列表必然有一边做错。归属条件只写一处，两边就不会在「谁的技能」上分叉。平台技能的使用范围是租户：已启用则本租户每个登录用户都能用，没有按人的使用授权
- **调用方**：技能中心调用技能中心列表。输入框菜单、任务装载、开放接口的任务模式调用任务候选
- **何时该重新考虑**：候选集大到单次查询不可接受。当前量级是每人可管理的技能，不是全库检索

### 决策 4：同名再次上传先提示，确认后再覆盖

- **备选**：
  - A. 同一用户同一技能名再次上传直接覆盖，不提示
  - B. 再次上传直接拒绝，只能从详情里更新
  - C. 先提示该技能已存在；用户确认覆盖后，用新文件替换，保留原 ID 和启停状态
- **选定**：C
- **原因**：静默覆盖会让用户分不清旧技能是不是被换掉。先提示再覆盖，和「上传时发现重复」是同一次操作，不必先失败再去详情里找更新。未确认不写文件。
- **何时该重新考虑**：产品要求再次上传直接生成另一个技能，或禁止覆盖

### 决策 5：个人技能的单条操作先核对归属，再走统一授权

- **备选**：
  - A. 详情、更新、删除只判断 `owner_user_id` 是不是当前用户，不调用 `require_business_action`
  - B. 先调用 `require_business_action`，拒绝再返回无权限
  - C. 先查出当前租户的这一行。没有这条，或归属不是本人，返回 11053，不调用统一授权。归属是本人，再调用 `require_business_action`
- **选定**：C
- **原因**：C4 要求具体资源先由业务核对，再交给统一授权。先问授权时，拒绝是 11054，调用方因此知道这条技能存在。创建个人技能时写下的所有者就是上传者本人，归属核对通过后用的就是这条记录。企业技能不能走这条：那条所有者是当时的管理员，拿它当使用权限会把同租户的其他人全部挡住
- **何时该重新考虑**：个人技能要按人或按部门再授权给所有者以外的人

### 决策 6：技能中心沿用现在的页面

- **备选**：
  - A. 按需求原文做成一个「我的技能」列表，企业技能和个人技能排在一起，卡片上不显示来源，只有一个总数
  - B. 沿用现在已合入的页面：页签「我的技能」和「技能广场」
- **选定**：B。这是讨论后的最终页面，不再按需求原文改回一个列表
- **页面**：
  - 「我的技能」是一个列表，分成「我创建的」和「企业提供」。个人技能可以启停，更新和删除在详情里；企业技能始终启用。每一行是名称、来源和一行用途说明，点击整行打开详情。可以搜索，并按最近更新或名称排序。页签上的数量是个人技能个数
  - 「技能广场」只放本租户已启用的企业技能，只读卡片，点击卡片打开详情。页签上的数量是企业技能个数
  - 搜索只筛当前页签里的名称、技能标识和用途说明。切换页签时清空搜索词
  - 标识相同的个人技能和企业技能，在「我的技能」的两个分组里都出现；「技能广场」只有企业技能那一张
- **何时该重新考虑**：产品要求拿掉「技能广场」，或要求卡片上不再显示来源

## 4. 系统现状（接手必读）

本节描述 **2026-10-14 这条开发线上的代码**。个人归属、技能中心页面、服务端个人库都不在这条线上。需求文档里提到的前端预览把文件放在浏览器，那不是本方案要交付的行为。

### 4.1 数据流

1. 管理员或内置播种写入 `linsight_skill`（`source` 为 `manual` / `builtin` / `sop_migrated`），包在对象存储前缀 `linsight/skills`，键里带内容哈希。
2. 用户在任务里打开选择器，客户端请求 `GET /api/v1/linsight/skill/selectable`。
3. 任务启动时 `materialize_session_skills` 按哈希把包落到该次会话的本地目录。工作区权威副本仍在对象存储，本地只是缓存和执行目录。

个人技能接通后，步骤 1 增加「当前用户上传」，个人技能包写入独立前缀 `linsight/personal-skills`，不写入 `linsight/skills`。步骤 2 的可选列表改为决策 3 的任务候选。步骤 3 要改：每个候选在任务开始时把整包拷进 `/skills/{名字}/`，名称和用途说明进入提示词。同一用户的个人技能与企业技能同名时只拷个人技能的整包。勾中的技能在提示词里标明「用户选中了这个技能」，未勾选的不加这句。装载时把每个目录对应的技能名、技能 ID、归属用户和内容哈希记到该次会话版本。

### 4.2 模块职责

| 模块 | 今天 | 本需求 |
|---|---|---|
| `linsight/domain/models/linsight_skill.py` | 租户级元数据，唯一 `(tenant_id, name)`，`created_by` 只是创建人 | 增加 `owner_user_id`，改唯一键。`created_by` 仍是创建人，不拿来当归属 |
| `linsight/domain/services/skill_store.py` | 校验包、写入对象、体积上限走系统配置；对象键在 `linsight/skills` | 个人上传走固定的 50 / 200 MiB 等上限，不读那套更大的租户默认值。个人技能改写独立前缀 `linsight/personal-skills` |
| `linsight/api/endpoints/skill.py` | 租户技能的上传与可选列表 | 个人技能的上传、列表、启停、删除走同一服务，按归属用户鉴权 |
| 客户端任务选择器 `SkillSelector.tsx` | 只拉可选技能；点一行勾选本次任务 | 技能中心是单独页面：卡片、搜索、上传，点卡片进详情。输入框菜单继续勾选，改为读取任务候选，不跳转详情。技能中心读技能中心列表，含停用的个人技能 |

### 4.3 数据模型

在 `linsight_skill` 增加：

| 列 | 含义 |
|---|---|
| `owner_user_id` | `0` 租户技能；否则为个人技能所属用户。非空，默认 `0` |
| `last_import_id` | 最近一次个人技能导入标识，可空。企业技能保持空。同一用户的非空值唯一 |

唯一约束从 `uq_linsight_skill_tenant_name (tenant_id, name)` 改为 `(tenant_id, owner_user_id, name)`。迁移要先确认现网没有同租户同名重复行（按现约束不应有），再把存量行的 `owner_user_id` 填 `0`。

租户技能继续放在 `linsight/skills/{租户}/{名字}/{内容哈希}.zip`，存量对象不搬。删除按 `linsight/skills/{租户}/{名字}/` 前缀进行。

个人技能放到独立前缀：

```text
linsight/personal-skills/{租户}/{用户}/{名字}/{内容哈希}.zip
```

个人技能若仍放在 `linsight/skills/{租户}/{名字}/` 下，用户删掉自己的技能会连同同名的企业技能一起删掉。也不能在原前缀下加一层 `u{用户}`：`u123` 本身是合法技能名，会和同名技能的前缀撞上。`SkillStore` 的对象键、本地缓存、读取和删除按归属选择对应前缀。

## 5. 已知坑

- **`created_by` 不是归属。** 管理员替租户上传的技能 `created_by` 是管理员，但所有有权用户都能用。个人技能必须看 `owner_user_id`，不能用创建人过滤。
- **租户过滤默认会带上根租户。** `LinsightSkillDao` 的查询已经用 `strict_tenant_filter()` 收成当前租户。个人技能查询必须留在这个过滤里，再加归属条件，否则子租户会看到根租户技能。
- **平台技能的使用范围是租户，不是个人。** 已启用且 `owner_user_id = 0` 的技能对本租户每个登录用户可用；停用后谁都不能用。创建时写入的 OpenFGA 所有者不参与企业技能的使用校验，那条记录上的人是当时的管理员。按人或按部门分配另行立项。技能入口和默认勾选不是授权。
- **个人技能的单条操作分两步。** 详情、读取文件、更新、启停和删除先查当前租户的这一行。没有这条，或 `owner_user_id` 不是当前用户，返回 11053，不调用 `require_business_action`。归属是本人之后再调用，资源类型仍是 `linsight_skill`，资源编号是技能 ID。更新和启停的动作是 `edit`，删除的动作是 `delete`，详情和读取文件也用 `edit`：模型里没有单独的查看动作，所有者对这条记录的可访问用同一个动作表达。现有模型的 `edit`、`delete` 还没有列入 `linsight_skill`，实现时补进这两种动作的资源范围，不新建资源类型。列表和任务候选仍是一次查询，不逐条调用。企业技能的使用不进入这次调用。
- **运行中删除不拒绝。** 技能记录立即从候选和技能中心消失。已经返回给模型的文件内容留在当前步骤。会话目录里的副本留到该任务结束，不靠删这些文件来停用。下一步 `read_file` 读 `/skills/{名字}/` 之前，以及代码执行器执行之前，再查一次：已停用或已删除就拒绝这次读取或执行。本地代码执行直接打开会话目录，只拦 `read_file` 挡不住。同一次会话的 “Available Skills” 写在检查点的 `skills_metadata` 里，已有这份名单就不再扫描磁盘，恢复和继续提问不会把停用的技能从提示词里拿掉；停用靠上面两次拒绝生效。新任务不再拷入该技能。正在跑的任务读的是会话自己的副本，不再回到技能对象，所以删除时在本次请求里直接删掉对象，覆盖时删掉这一行不再指向的旧对象。
- **取消或失败的导入不留文件。** 校验在内存中完成，确认覆盖且校验通过后才写入对象存储。请求结束时删除本次解压临时目录。崩溃留下的、没有技能记录的对象由后台清扫删除，不面向用户承诺保留时间。
- **解压条目上限和路径穿越**沿用 `SkillStore` 已有校验。个人路径只是加更紧的体积和条目上限，不另写一套解压。
- **个人技能配额已定。** 每个用户在当前租户最多 20 个个人技能，上传文件合计最多 200 MiB。停用的仍占用额度，企业技能不计入。超出时拒绝新增，不删除已有技能。当前没有服务端存量。上传前展示已用个数和已用容量。

## 6. 对外契约

- 读取方法有两个，共用归属条件，见决策 3。技能中心列表含停用的个人技能；任务候选只含已启用的。输入框菜单、任务装载、开放接口的任务模式都读任务候选。每个候选在任务开始时整包拷进会话，不另调模型生成名单。用户勾中的技能在提示词里标明「用户选中了这个技能」；未勾选的同样拷入整包，但不加这句。同一用户的个人技能与企业技能同名时，只拷个人技能的整包。企业技能记录保留。
- 错误码沿用技能段：校验失败 11051、单文件过大 11052、不存在 11053、无权限 11054、同范围重名 11055、解压过大 11059。本需求追加并写入三语 `api_errors`：11061 个人技能个数超出，11062 合计容量超出，11063 压缩包已加密，11064 版本过期，11065 文件类型与内容不一致，11066 同一次导入的文件不一致，11067 压缩包损坏，11068 缺少 `SKILL.md`，11069 路径越界，11071 文件为 0 字节，11072 压缩包内含多份技能。11068 的中文是「压缩包中缺少 SKILL.md，请检查后重新上传。」11060 和 11070 已有指导手册检索的三语文案，不改写、不挪作本需求。技能段延伸到 11079，11080 已是工作台工具初始化失败。这些原因不共用 11051，否则文件区只会显示通用校验失败。体积四条限制分开报：上传超过上限用 11052，解压后超过上限用 11059，`SKILL.md` 超过 1 MiB 用 11073，压缩包内文件超过 1000 个用 11074。11052 和 11059 由企业上传、GitHub 导入和个人上传共用，上限不同，而前台有译文时不显示 `status_message`，所以具体数值放进响应的 `data`，由译文代入：11052 改为「技能文件超过 {{limit_mb}} MiB，请精简后重新上传」，11059 改为「技能包解压后超过 {{limit_mb}} MiB，请精简后重试」。企业路径传系统配置里的上限，个人路径传 50 和 200。11073 和 11074 同样带上限值。上传接口、`_parse_upload`、GitHub 导入里每一处抛这两个错误码的地方都要带 `limit_mb`，并和三语文案在同一次改动里提交；漏掉一处，页面会原样显示 `{{limit_mb}}`。访问他人的个人技能按不存在返回 11053，不用 11054，且不先调用统一授权。11054 表示调用方已知资源存在但没有管理权限；用在他人的个人技能上会暴露这条技能存在。归属是本人的详情、更新和删除再调用 `require_business_action`，见决策 5。用户能看到的句子以 `api_errors` 为准，同一错误码不靠 `status_message` 再写另一句中文。
- 租户技能管理接口的请求和响应不增加必填字段。`owner_user_id` 对旧客户端不可见；旧的按名更新仍只命中 `owner_user_id = 0` 的行。
- 历史行全部视为租户技能（`owner_user_id = 0`）。没有个人技能可迁移。`last_import_id` 留空。

## 7. 需求中其余行为的做法

本节补上需求里已经写明、前面各节还没落地的行为。用户可见中文以需求原文为准，并写入三语包。

### 7.1 审计记在现有审计表

- **备选**：新建技能审计表；或只打应用日志。
- **选定**：写入现有 `audit_log`。个人技能的新增、覆盖更新、启停发生实际变化、删除各记一条。`system_id` 用 `linsight`，这样租户管理员在现有「系统操作」里能看到。不为此单开页面。
- **原因**：需求要的是操作者、租户、技能 ID、来源、版本和结果。这些列审计表已经有：操作者、`tenant_id`、`target_id`。来源、内容哈希和结果放 `audit_metadata`，只这三项。不写技能正文、用途说明、文件字节、密码或密钥。
- **不记的情况**：启停提交后状态没有变化，不另记一条。审计插入失败只记应用日志，不把已经保存成功的技能改成失败。企业技能的原有管理接口本期不补审计。

### 7.2 版本用内容哈希，不用更新时间

- **备选**：用 `update_time` 当版本；或另加递增版本号。
- **选定**：个人技能详情和「已存在」提示都返回当前 `content_hash`。覆盖请求带上客户端看到的 `expected_content_hash`。不一致则不写对象、不改行，返回 11064，文案为「该 Skill 已更新，请刷新后重试」。一致时先写新对象，再改这一行的哈希、对象路径和大小；技能 ID 和启停状态不动。行更新成功后删掉旧哈希的对象；新旧哈希相同则不删，删除失败同样交给后台清扫。行更新失败时旧哈希仍指向旧对象，新对象没有技能行引用，交给已定的后台清扫。
- **原因**：启停也会改 `update_time`。用它做版本，会把「只是停用过」误判成文件冲突。内容哈希只在文件被替换时变化，和对象键是同一套版本。

### 7.3 启停和删除的重复提交

- 启停：技能还在，且已经是请求里的状态，返回当前技能，不报错，不改 `update_time`。失败时开关保持操作前的值，并提示重试。
- 删除：当前用户名下已经没有这个 ID，返回与删除成功相同的空结果，不报错。响应里没有名称和正文。他人的个人技能也落在这条上，因此不会变成 11054，也不会露出这条技能是否存在。
- 启停打到一个当前用户名下不存在的 ID，返回 11053。启停没有「已删除」这种可回放的当前结果；删除才有。

### 7.4 导入标识，响应丢了先查再重试

- **备选**：服务端生成导入标识；或另建导入任务表。
- **选定**：浏览器在一次保存开始时生成 `import_id`，创建和确认覆盖都带上它，重试沿用同一个。成功后写进该行的 `last_import_id`。唯一约束是 `(tenant_id, owner_user_id, last_import_id)`。MySQL 唯一索引里空值互不相等，企业技能和尚未导入的行可以都是空，不会互相挡住。
- **原因**：需求要求重试不重复创建，并且保存响应中断后先查服务端。技能行本身就是「已保存」的标志，不必再维护一张导入表。
- **查询**：按当前登录用户和 `import_id` 查。查到则把这次保存当成功，不再上传。查不到返回 11053。
- **同一标识再提交**：已有行且内容哈希与本次文件一致，返回该技能。哈希不一致返回 11066，不覆盖。两个请求同时写入时，唯一约束只留一行，后到的请求改为按上面的规则回读。

### 7.5 加密压缩包和 MIME

- 解包前看 ZIP 条目的加密标志（通用标志位 bit 0）。任一文件加密，返回 11063，文案说明压缩包已加密、请解除密码后重新选择。不尝试解密，也不把密码写进日志。今天加密包会落到 `BadZipFile`，和损坏包同一句，所以要分开。
- 扩展名决定格式。`.md` 的 MIME 只接受 `text/markdown`、`text/plain`、`application/octet-stream` 或空值。`.zip` 与 `.skill` 只接受 `application/zip`、`application/x-zip-compressed`、`application/octet-stream` 或空值。内容还要和扩展名一致：`.md` 不能是 ZIP；`.zip` 和 `.skill` 必须是 ZIP。对不上返回 11065。MIME 只是声明，字节才算数。
- 压缩包损坏返回 11067，缺少 `SKILL.md` 返回 11068，路径越界返回 11069，文件为 0 字节返回 11071，压缩包内含多份技能返回 11072。文件区展示对应译文，并提供【重新选择】。这些原因不用 11051：前台在错误码有译文时显示那句译文，11051 只有通用的校验失败，盖不住「压缩包中缺少 SKILL.md，请检查后重新上传」。11060 与 11070 不使用。

### 7.6 删除文案、文件缺失和详情失效

- 删除确认句用需求原文：「删除‘{名称}’后，后续任务将无法使用该 Skill，已有对话和生成结果保留。」`{名称}` 用展示名。按钮为【取消】【删除】。请求失败时卡片留着，提示「删除失败，请重试」。
- 技能行还在、对象存储里的包读不出来：详情返回 200，并带 `bundle_missing`。详情里说明原因，提供【更新技能】。该按钮走同一套覆盖：带上当前内容哈希，校验通过后替换，保留 ID 和启停状态。不要把缺文件报成 11053，否则页面无法区分「被删了」和「文件丢了」。
- 当前详情对应的技能已删除，或平台技能已被管理员停用、删除：提示原因，关闭详情回到列表，其他卡片保留。用户停用自己的个人技能时留在详情里，只把开关关掉；停用后的个人技能仍在技能中心里。本期没有按人收回平台技能，需求里的「撤销授权」就是管理员停用。
- 技能表上没有隐藏开关。不新增隐藏字段。技能中心是否列出，由归属和启停决定；新任务能否装载，由候选规则决定。

### 7.7 输入框同名仍是两行

候选接口按技能 ID 返回，不按名字合并。勾选按技能 ID 记。同名去重只在任务候选里做：已启用的个人技能盖住同名企业技能；个人技能停用或删除后，新任务拷企业技能的整包。两行都在时，勾了任意一行，对留下的个人技能加上「用户选中了这个技能」，菜单里不藏企业技能那一行。菜单里只有企业技能那一行时，勾中它就强调这份企业技能。

### 7.8 候选刷新、整包拷入，以及工具不可用

- 新建任务取当前用户的任务候选，把每个候选的整包拷进 `/skills/{名字}/`，并把名称和用途说明写入 “Available Skills”。同名时只拷个人技能的整包。
- 同一次会话的恢复和继续提问沿用检查点里已有的名单。会话里已经有的技能目录不再写入另一份技能：同名个人技能停用后，同名企业技能进入候选，但不拷进这个目录。否则企业技能的文件会写进同一个目录，新包里没有的旧文件不会被删，目录里会混着两份技能的文件。同名企业技能等新任务再装载；新一轮对话不继承上一轮的 `skills/`，会按当时的候选重新拷。
- 用户勾中的技能（含默认勾选且未摘掉的）在提示词里标明「用户选中了这个技能」。未勾选的候选同样拷入整包，但不加这句。`SKILL.md`、脚本和参考文件在任务开始时一次拷完。
- 这句由平台在贴 “Available Skills” 时追加，不写进 `SKILL.md`，技能正文保持上传时的样子。现有 `SkillsMiddleware` 列出每个技能时只有名字、用途说明、许可、兼容性和 `SKILL.md` 路径，读不到勾选。实现时在它外面包一层：按会话版本上的勾选名单，在对应技能那一行后面加这句。勾选按技能 ID 记，先换成实际拷入的目录名再比对；勾的是被同名个人技能盖住的企业技能时，强调落到留下的个人技能上。
- 整包要在建代码执行器之前拷进会话目录。E2B 在建工具时就拍下要推进沙箱的文件清单，技能晚于这一步拷入，E2B 里就没有技能包。本地执行和容器沙箱在执行时读会话目录，不受这个顺序影响。单个文件超过 5 MiB 仍推不进 E2B，这个限制不变；技能里有这类文件时，该技能在 E2B 下用不全，任务里如实说明。
- 装载时在 `linsight_session_version` 增加 JSON 列，记下每个目录名对应的技能：技能名、技能 ID、归属用户和内容哈希。MySQL 和 DM8 都要迁移。会话上原有的 `skills` 只存勾选的技能名，同名时分不清目录里是个人技能还是企业技能，所以不能用那一列。这份快照只用来回答「这个目录属于哪一行」，不用来决定对象留不留。
- 已经返回给模型的文件内容留在当前步骤，已完成的结果保留。会话目录里的副本留到任务结束，不靠删除这些文件来停用。
- 下一步再使用之前有两处检查，都先按快照找到这个目录对应的技能 ID，再查这一行。只按目录名查不对：同名时这个名字上有两行，个人技能已停用、企业技能仍启用，按名字查会放行，模型用的却是目录里的个人技能文件。`read_file` 读到 `/skills/{名字}/` 时，这一行已停用或已删除就拒绝这次读取。代码执行器执行前再查一次：本地执行的工作目录就是会话目录，脚本用 `skills/{名字}/...` 直接打开文件，不经过 `read_file`。容器沙箱也是从这份会话目录送文件进去。只拦 `read_file` 时，这两处仍会用到已停用的技能。
- “Available Skills” 在代理开始前扫描一次 `SKILL.md`，写入检查点的 `skills_metadata`。之后每次叫模型只重贴这份名单。检查点里已经有名单时不再扫描磁盘，所以同一次会话的恢复和继续提问不会因为停用而改写提示词。新任务没有这份检查点，会按当时的候选重新生成名单，已停用或已删除的技能不会再拷入。
- 正在跑的任务不需要保留技能对象。拷入时写的是本地目录和这次会话自己的对象存储副本 `workspace/{会话}/skills/{名字}/`；之后 `read_file`、恢复和换机器继续，读的都是这份会话副本，不再回到技能对象。所以删除和覆盖时，在本次请求里直接删掉这一行已经不再指向的旧对象，不查哪些会话还没结束。当前行仍指向的哈希不删。
- 恢复和继续提问不再把已停用或已删除的技能装进候选，但第一次拷进会话目录的文件还在，仍由上面两处检查拒绝下一次读取和执行。
- 技能前言里的 `allowed-tools` 若有条目不在本次任务的工具里，该技能在 “Available Skills” 中加一句「该技能需要的工具当前不可用」。真正调用到缺失工具时，任务结果用同一句，不用堆栈。没有声明工具则不加这句。不因此拒绝整个任务，也不在上传时安装工具。上传不改变用户原有的工具和数据权限。
