## 一、平台全景

按"技术形态"分五类：

### ① 开源自托管型（知识库 + 工作流一体）

| 平台 | 沙箱设计 |
|---|---|
| **RAGFlow** | 沙箱做得最"标准"：独立 `sandbox/` 模块，`executor_manager` 编排 + **gVisor(runsc)** 容器隔离，可选 seccomp profile，Python 额外做 AST 静态检查。Provider 可插拔：`self_managed`（默认）/ `local` / `ssh` / `aliyun_codeinterpreter` / `e2b` / `tenki`（每次执行起一个 microVM 后销毁） |
| **FastGPT** | "预热进程池 + 语言级加固"路线，不依赖 Docker：默认预热 20 个 JS worker + 20 个 Python worker，stdin/stdout 传 JSON，进程崩溃自动 respawn；JS 冻结 `Function` 构造器、遮蔽原型链、模块白名单；Python 做 import 拦截 + AST 检查 |
| **MaxKB** | `ToolExecutor` + C 写的 seccomp 过滤器（`installer/sandbox.c`），执行前 `setuid` 切 sandbox 用户、清空环境变量、限制网络/子进程 |
| **Flowise** | NodeVM（`@flowiseai/nodevm`）做 V8 隔离 + 依赖白名单（`TOOL_FUNCTION_BUILTIN_DEP` 等）；配了 `E2B_APIKEY` 才走 E2B，否则静默降级 NodeVM（已因此出过 CVSS 9.9 事故） |
| **Langflow** | 官方文档直接声明"不提供任何隔离"，多租户隔离责任推给基础设施层 |
| **n8n** | Code / Execute Command 节点演进史：主进程内执行 → task runner 子进程（internal，3.0 弃用）→ external sidecar 容器（推荐）。详见第七、八节 |

### ② 国内云厂商托管平台

| 平台 | 沙箱设计 |
|---|---|
| **阿里云百炼 Sandbox** | 直接做**兼容 E2B SDK** 的沙箱服务，底层是函数计算"沙箱函数"+ 实例隔离（一个 session 独占一个实例，请求结束转浅休眠保活）。模板：`code-interpreter-v1` / `browser` / `all-in-one`；配置 1C2G 或 4C8G；支持文件挂载（NAS/PolarFS）、OSS 执行角色、网络白黑名单、空闲超时、最长存活 7 天 |
| **腾讯云 ADP** | `AGS Cube` 安全沙箱：内核级隔离 + session 级实例隔离，**凭证不落沙箱**（真凭证留在云端可信区）；workspace 靠快照 + COS 保存恢复。配套开源 **CubeSandbox**（KVM microVM、XFS reflink 做 CoW 快照、兼容 E2B SDK，官方 P95 冷启 78.3ms、单 VM 内存 27–34MB） |
| **火山引擎云沙箱** | 40ms 预热 / 100ms 冷启，12 万沙箱/分钟级拉起，支撑扣子 / 豆包 / 飞书 |
| **百度千帆** | 代码解释器用轻量级容器沙箱：禁网络、禁宿主文件读写、超时强杀，用完即销毁 |
| **智谱 BigModel** | `tools=[{"type":"code_interpreter"}]` 直接用；Managed Agents 中沙箱能力抽象为工具集 `agent_toolset_20260601`（bash/read/write/edit/grep/find/ls），每个工具可配 `permission_policy`（自动放行 or 人工确认） |

### ③ 海外模型厂商

| 厂商 | 沙箱设计 |
|---|---|
| **OpenAI** | Code Interpreter：gVisor(runsc) 跑在 K8s/Azure 上，9GB 内存 / 4 vCPU，镜像内 FastAPI 管 Jupyter Kernel，网络基本锁死。Codex 云端：Docker 两阶段（Setup 阶段有网有 secrets，Agent 阶段默认离线且 secrets 已清除，容器缓存 12h）。Codex CLI：Landlock + seccomp / Seatbelt，少数默认开启沙箱的 |

## 二、沙箱隔离强度五档阶梯

各家设计差异，本质上是在五个档位里选位置（外加一条 Wasm/V8 旁路）：

| 档位 | 技术 | 逃逸后果 | 代表 |
|---|---|---|---|
| ① 语言级加固 | AST 检查、import 拦截、模块白名单、V8/Wasm 同进程 | 逃逸 = 直接拿到宿主/整个应用进程 | Langflow、n8n 旧版（进程内 Pyodide）、FastGPT 的语言层 |
| ② 子进程 + OS 加固 | setuid 降权 + seccomp 过滤 | 逃逸 = 同 UID 同容器 | MaxKB、FastGPT worker 池、n8n internal mode |
| ③ 共享内核容器 | Docker 等独立容器 | 逃逸 = 撞容器边界 | Dify sandbox、千帆 |
| ④ 用户态内核 | gVisor (runsc) | 拦截大部分内核攻击面 | RAGFlow、OpenAI Code Interpreter、Modal |
| ⑤ MicroVM | Firecracker / Kata / KVM / libkrun | 硬件虚拟化边界 | E2B、Vercel、腾讯 Cube、百炼 |
| 旁路 | Wasm / V8 isolate | 隔离尚可，毫秒启动 | Coze (Pyodide)、Cloudflare Workers、**但跑不了 pip/npm 原生扩展** |

## 三、五平台执行链路对比

"沙箱放在哪一层"是各家的核心设计分歧：

- **Coze**：模型输出 → Pyodide(Wasm) 内存 FS 执行 → 结果经管道回传。最轻，但处理不了真实文件。
- **Dify**：代码落临时目录（UUID 命名）→ `TempDirRunner` 挂载必需文件 → 独立 sandbox 容器执行 → 收集 stdout + 产物 → 销毁。
- **RAGFlow**：代码 + 文件 → gVisor 容器（每次一个）→ 写入 `artifacts/` 的自动作为 run artifacts 返回 → 容器销毁。
- **OpenAI Code Interpreter**：对话绑定容器 → Jupyter kernel 在 `/mnt/data` 直接读写 → 多轮共享状态。
- **腾讯 ADP**：session 级 Cube microVM → 凭证不落沙箱 → workspace 快照 + COS 恢复。

## 四、选型框架：按顺序问四个问题

沙箱没有"最好的"，只有"最配的"。五个维度互相拉扯：**冷启动、隔离强度、会话持久化、SDK 手感、计费模型**——没有平台五个都赢。按"哪个维度选错会让 Agent 崩掉"定顺序：

1. **代码从哪来？** 自己写的节点代码 → 第 1–2 档够用；用户输入或模型生成 → 至少第 3 档；多租户 → 第 4–5 档。
2. **要不要原生生态？** 需要 pip/npm 原生扩展、需要 `fork()` → **Wasm / V8 isolate 直接出局**（Coze 的 Pyodide 路线、Cloudflare DW 都跑不了原生包）。这是最容易被忽略的一刀。
3. **环境要活多久？** 单次请求 → 无状态即可；要保住 `node_modules`、数据集、多轮编码会话 → 必须选带**暂停/恢复或快照**的（E2B pause/resume、Cube 的 CoW 快照、Daytona snapshot）。会话上限是真约束：E2B 24h、Vercel 45min–5h、百炼 7 天。
4. **数据能不能出域？** 不能 → 自托管路线：CubeSandbox、阿里 OpenSandbox、RAGFlow sandbox（gVisor 自建）、自己拿 Firecracker 拼。

一句口诀：**E2B 是"紧循环 + 强隔离"的默认项；Modal 是"连 GPU 的重活"；Daytona 是"极致冷启 + 长会话"；Cloudflare 是"边缘 + 最便宜"；腾讯 Cube 是"要 E2B 兼容又要能自托管"。**

## 五、各平台沙箱的启用方式与配置项

| 平台 | 怎么启用 | 关键配置 |
|---|---|---|
| Dify | 独立 sandbox 容器随 compose 起 | `sandbox.env` 的 `SANDBOX_*`（超时、SSRF 代理、端口）、`shared.env` 的 `CODE_*`（输出上限） |
| Coze Studio | **默认 `local`，等于不隔离** | `docker/.env` 里 `CODE_RUNNER_TYPE=sandbox` |
| RAGFlow | `.env` 里 `SANDBOX_ENABLED=1`，先装好 gVisor | Admin › Sandbox Settings 选 provider；`SANDBOX_ENABLE_SECCOMP=true` 开严格 seccomp |
| FastGPT / MaxKB | 内置，无开关，进程池/沙箱用户自动生效 | MaxKB 的 syscall 白名单在 `installer/sandbox.c` |
| Flowise | **有 `E2B_APIKEY` 才走 E2B，否则静默降级 NodeVM** | `TOOL_FUNCTION_BUILTIN_DEP` / `TOOL_FUNCTION_EXTERNAL_DEP` |
| 阿里云百炼 | 控制台建模板拿 `templateCode` | 镜像三选一；网络白黑名单、空闲超时、最长存活 7 天 |
| 腾讯 ADP | 平台托管，Claw 模式直接用 | session 隔离、凭证不落沙箱、workspace 快照 + COS |
| E2B / 腾讯 Cube / Daytona | SDK 直接调（Cube 兼容 E2B SDK） | 会话上限、快照策略、出站白名单 |
| Codex CLI | **默认开启** | Landlock+seccomp / Seatbelt，工作目录+出站白名单 |
| Claude Code | 权限确认后启用 | `@anthropic-ai/sandbox-runtime`，Seatbelt/bwrap + 代理白名单 |
| Gemini CLI | `GEMINI_SANDBOX=true\|docker\|sandbox-exec\|runsc` 或 `-s` 旗标 | OS 原生档 permissive-open/restrictive-* 等 profile；forbiddenPaths 项目级配置 |
| n8n | `N8N_RUNNERS_MODE=external`（2.0 起默认启用 task runner） | sidecar 容器 + `N8N_RUNNERS_AUTH_TOKEN`；配 distroless 镜像、nobody 用户、只读根 FS、AppArmor |

## 六、工作区机制与文件处理流程

### 谁有真正的"工作区"

按"文件能活多久"分三档：

**① 持久工作区（session 级，跨请求存活）**

| 平台 | 形态 |
|---|---|
| OpenAI Code Interpreter | 每个对话绑定一个容器，文件落在 `/mnt/data`，Jupyter kernel 直接读写 |
| 阿里云百炼 | `sbx.files.write/read/make_dir` 文件 API；空闲暂停、恢复不丢；FC 沙箱函数可挂 NAS/PolarFS、经执行角色读写 OSS；最长 7 天 |
| 腾讯云 ADP | workspace 整体快照，实例销毁后经 COS 恢复重建；凭证不落工作区 |
| E2B / Daytona / Fly Sprites | 暂停恢复 / 快照 / 持久优先，为"保住 node_modules 和数据集"设计 |
| Codex 云端 | 仓库级工作区：Setup 阶段 clone + 装依赖，容器缓存 12h |
| Claude Cowork | 宿主目录经 VirtioFS 直接共享进 VM，工作区即本地项目目录 |

**② 临时工作区（一次执行一个目录，用完即弃）**

- Dify：临时目录 + UUID 命名代码文件，`TempDirRunner` 挂必需文件，执行完销毁
- RAGFlow：约定 `artifacts/` 目录，写入的文件自动作为 run artifacts 返回
- MaxKB / n8n：降权 + 临时目录，无跨请求状态

**③ 没有文件系统**

- Coze sandbox：Pyodide 跑在 Wasm 内存 FS，"文件"只是变量，经管道传进传出
- FastGPT worker：数据走 stdin/stdout JSON 行协议，无真实文件 IO
- Langflow：反着来——直接共享宿主 FS，有"工作区"但没有隔离

> 关键推论：**Wasm 路线隔离轻，但天生处理不了真实文件**——Excel 解析、文件分析这类功能，几乎所有平台最后都退回容器/VM 路线。

### 执行流程两种模式

**模式 A：无状态注入型**（Dify / RAGFlow / FastGPT / MaxKB）

1. 上游文件存对象存储（MinIO/S3/OSS），拿到引用；
2. 执行器把文件拉取/挂载到沙箱临时目录（Dify：`TempDirRunner` + `required_files`，每请求独立目录 + 独立 UID）；
3. 文件路径作为**函数参数注入**生成代码（`def main(input_file: str) -> dict`），路径契约由平台保证；
4. 代码在沙箱内处理文件，产物写入约定目录（RAGFlow 约定 `artifacts/`，自动收集返回）；
5. 平台收集 stdout + 产物 → 回传对象存储 → 生成下载链接 → **临时目录整个销毁**。

特点：每轮干净、安全好清理；代价是跨轮次无状态，第二轮要用上一轮产物得重新注入。

**模式 B：有状态工作区型**（百炼 / 腾讯 ADP / E2B / Code Interpreter）

1. `Sandbox.create(template)` 建实例，或按 `session_id` 从快照恢复；
2. 通过文件 API 写入数据（E2B 兼容：`sbx.files.write("/home/user/workspace/data.xlsx", ...)`），或模板预置挂载；
3. 生成的代码**直接用绝对路径读写**——真实 Linux FS，pandas/openpyxl 随便用，适合 Excel 多-sheet 解析类需求；
4. 多轮共享同一工作区：第一轮装依赖写脚本，第二轮直接跑，中间产物都在；
5. 结束时三选一：**暂停**（恢复续用）/ **快照**（落对象存储，实例可销毁）/ **TTL 销毁**。

**模式 C：仓库级**（Codex 云端 / Claude Code / Daytona）——B 的特例：工作区 = git 仓库，Setup 有网（clone + install + 注密钥），Agent 阶段默认离线且**密钥已清除**，产物走 commit/PR。

### 设计工作区的六个工程要点

1. **路径契约显式化**：工作区根目录（如 `/workspace`）作为环境变量/参数注入，不让模型从 prompt 里猜路径；
2. **大文件不进 context**：代码在沙箱内读文件，只回传统计摘要/报错——Code Mode 省 60–90% token 的核心机制；
3. **产物双通道**：固定 `artifacts/` 目录（自动收集）+ 显式文件 API（精确控制）；
4. **凭证不落工作区**：密钥只在 Setup/安装期可用，执行期不可见；
5. **状态三层**：热（实例续用）→ 温（暂停/快照）→ 冷（对象存储），用 TTL 串联；
6. **session 独占**：一个 session 独占一个实例，否则跨租户文件残留是最难查的数据泄漏。

## 七、同容器进程级沙箱分类

"沙箱与 Agent 是否在同一容器/主机里"是另一条独立的设计轴。

### ① 同一进程（无边界）

- **Langflow**：官方声明无隔离
- **n8n 1.x 旧版**：Code 节点在主进程内跑 Pyodide

### ② 语言级隔离（同进程内虚拟机）

- **Flowise**：NodeVM（V8 隔离 + 依赖白名单）
- **Coze 云端**：Pyodide（Wasm 内存 FS）
- 逃逸后果 = 整个 Node/应用进程

### ③ 子进程 + OS 加固（同容器）

- **FastGPT**：预热 worker 池（20 JS + 20 Py 子进程）
- **MaxKB**：seccomp 过滤器 + setuid 降权
- **n8n internal mode**：task runner 作主进程子进程（同 UID 同主机，3.0 已弃用）
- 逃逸后果 = 同 UID 同容器

### ④ OS 原生沙箱（同主机，CLI Agent 主流）

| 产品 | 机制 | 特点 |
|---|---|---|
| Codex CLI | Linux: Landlock+seccomp；macOS: Seatbelt | **默认开启** |
| Claude Code | Seatbelt / bubblewrap | 开源为 `@anthropic-ai/sandbox-runtime`；网络走 Unix socket 代理 + JWT 域名白名单 |
| Gemini CLI | Seatbelt（按 session 生成 profile）/ bwrap+namespaces+seccomp / Windows AppContainer | deny-by-default、forbiddenPaths、密钥专项 deny、动态扩权 |

CLI Agent 只能走这条路是架构决定的：跑在**用户机器上**，不可能要求用户装 Firecracker。这条赛道收敛到同一配方：**子进程 + 内核 syscall 过滤 + 文件系统路径白名单 + 代理式网络管控**。

### ⑤ 跨容器 / VM（不在同容器）

- Dify（独立 `dify-sandbox` 容器）、RAGFlow（gVisor 容器池）、百炼（FC 实例）、腾讯 ADP/Cube（KVM microVM）、OpenAI Code Interpreter / Codex 云端、Claude Cowork（完整 VM）、E2B/Daytona/Modal
- 多租户托管平台的唯一合理选择

### n8n 的演进是教科书案例

每一步都被 CVE 逼出来：

1. **同进程**（Pyodide）→ CVE-2025-68668：Pyodide 沙箱逃逸，语言级隔离被打穿；
2. **同容器子进程**（internal runner，同 UID）→ CVE-2025-61917：task runner 中 `Buffer.allocUnsafe()` 分配未初始化内存，读到**同进程残留的其他请求密钥/token**（共享进程空间的原罪：隔离了执行，没隔离内存）；
3. **跨容器**（external sidecar + distroless + nobody + 只读根 FS + AppArmor）→ 现在唯一推荐姿势，官方原话："task runner 是用户代码和 n8n 之间**唯一的隔离层**"。

### 规律总结

- 跑在用户机器上的 CLI Agent 只能选 OS 原生进程沙箱，且收敛到"deny-by-default + 代理白名单网络"；
- 多租户托管平台一律上跨容器/VM；
- **语言级沙箱不是安全边界**；同进程共享内存会泄漏、同 UID 子进程逃逸即失守。

## 八、安全事件复盘与上线检查清单

### 三个必须知道的事故

| 事件 | 根因 | 教训 |
|---|---|---|
| **Flowise RCE**（GHSA-9rvc-vf7m-pgm2，CVSS 9.9） | 路由缺权限校验 + NodeVM 可被 `e.constructor.constructor` 逃逸出 host realm，攻击者拿到 `child_process` → 认证后 RCE | 根因不是"沙箱不够强"，而是**没配 E2B 就静默降级**——安全边界必须 **fail-closed** |
| **n8n RCE 链**（CVE-2026-21858） | LLM 节点 → 任意文件读 → 捞到 SQLite + `N8N_ENCRYPTION_KEY` → 伪造 admin → 内置 Execute Command 节点执行 shell | **编排器把 LLM 和 shell 节点串在一起的那一刻，就是最大的风险面** |
| **Langflow 官方声明** | "不提供任何隔离"，n8n Code 节点默认也是宿主权限 | "编排器"类产品必须靠容器/VM 层兜底，且文档要明说边界 |

### 上线前最小检查清单

- [ ] **默认关闭出站**（域名/SNI 白名单）
- [ ] **block `169.254.169.254` 等云元数据地址**和所有 RFC1918 段
- [ ] CPU / 内存 / 进程数 / 超时四项限额（防 fork 炸弹）
- [ ] 每次执行的命令 + 输出 + 退出码 + 文件变更**全审计**
- [ ] 安全边界 **fail-closed**：沙箱不可用时拒绝执行，绝不静默降级
- [ ] **凭证不落沙箱**：密钥只在安装/Setup 期可见
- [ ] 注意 E2B 这类基于 SNI 过滤的方案**不支持 UDP/QUIC/HTTP3**，镜像内强制 HTTP/2 以下

## 九、与 PTC 的关系及对 bisheng 的建议

### PTC 与沙箱的关系

Cloudflare 的 Code Mode、Anthropic 的 "code execution with MCP"、以及 PTC（Programmatic Tool Calling），本质是同一个转向：**不再让模型一次吐一个 tool call，而是让模型写一段代码去调 API**。中间结果留在沙箱里不进 context，多步链路 token 能降 60–90%（Cloudflare 把 2500 个端点压成 `search()` + `execute()` 两个工具，从 117 万 token 降到约 1000）。

**沙箱从"可选的安全组件"变成了 PTC 的前置依赖**——没有沙箱，根本不敢跑模型现写的代码。

### 对 bisheng 3.0 的落地建议

1. **沙箱运行时先行**：上 PTC 的第一步不是设计 prompt，而是先立沙箱运行时；接口照着 **E2B SDK 的形状**做（`sbx.files.*` / `commands.run`），后续可无缝切到百炼 Sandbox / 腾讯 Cube 这类兼容实现；
2. **别停在语言级/子进程档**：n8n 用两次 CVE 证明同进程共享内存会泄漏、同 UID 子进程逃逸即失守。最低限度独立容器（Dify 档），认真做上 gVisor（RAGFlow 档）；
3. **文件类 Agent 能力**：模式 A（无状态注入）可复用现有对象存储 + 临时执行目录；"多轮数据分析"场景需上模式 B 的快照/暂停机制；
4. **CLI/本地部署形态**（可选）：抄 Gemini CLI 的 OS 原生配方——Seatbelt/bwrap + deny-by-default + 路径白名单 + 代理出站，不需要容器运行时，但文档里必须明确声明边界弱于容器档。
