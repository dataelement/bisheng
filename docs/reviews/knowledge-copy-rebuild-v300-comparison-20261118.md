## 二、元数据调整

之前笼统说“元数据修改都需要同步索引”不够准确。新增字段和改名/删除已有字段应分开处理。

- 普通新增字段恢复轻量路径：空间 edit、字段名/类型合法性、schema revision CAS 后保存字段定义，历史文件空值通过缺失字段表达，不启动全量文件索引任务。
- 字段改名、删除及修改文件值继续同步 ES/Milvus，保留可查询任务、逐文件失败与重试，避免只更新 SQL 后检索过滤仍使用旧值。
- 如果重新使用同名字段且历史文件/索引存在旧键残留，不能把旧值当作新字段值；需定向清理残留或拒绝复用直到清理完成，不能直接省略这类必要处理。
- 当前 `MetadataProcessingService.apreview` 会为 scope 中每个文件创建处理项，即使 before/after 相同；这会把无须处理的文件带入冲突面。纯新增字段不应因此与无关文件修改、模型配置变化相互阻塞。

## 三、复制：空间可用性与文件处理结果分开

### 推荐执行顺序

1. 同步完成目标空间记录、空间配置、目录与文件/版本记录、合法权限投影，以及空目标索引初始化。大批量目录记录可分批初始化，初始化期间如实显示，不伪称空间就绪。
2. 上述必要初始化成功后，目标空间即可进入正常可用状态；后台逐文件复制原文、预览、分段、元数据及检索数据。页面显示任务进度，但不以 COPYING 状态遮挡整个空间。源空间不设置整段复制期的全局写锁。
3. 每个文件独立从排队/处理中转为成功或失败。成功文件可预览、下载、检索；尚未复制完成的文件不伪装为可下载/可检索。新上传、其他就绪文件的正常操作不因某文件失败被阻止。
4. 单文件复制/入库失败只标该文件 FAILED，记录实际失败阶段与原因，继续其他文件。整批全失败也只令任务 FAILED，目标空间保持可用，显示暂时没有可检索的成功文件。
5. 用户重试只处理失败项，复用目标文件/版本 ID 和授权，不重复建空间/文件。复制失败走“重试复制”，不能无条件调用解析重试——原文可能尚未复制到目标。已有目标原文和分段时，应从自身输入恢复，逐步消除源依赖。

### 源空间允许变化时的一致性

- 提交时固定空间配置和复制清单，后新增文件不自动加入；不再因源空间任意一个文件或说明改变就拒绝整个任务及所有重试。
- 按文件记录源版本、内容摘要、分段修订和输入对象；读取可用的确定版本，读取期间继续校验必要的读取权限。原文/分段独立复制完成后，后续入库和重试使用目标输入。
- 源文件改名、移动等与内容无关的操作，不应使其他文件失败；本次目标路径/名称按已确认的复制清单确定。
- 如果源内容版本已替换且原版本无法读取，仅该文件标记“源版本已变化/不可用”。恢复时可由用户明确选择按当前源版本重新复制；不悄悄把新内容当作提交时版本。
- 目标文件已被用户修改/删除后，迟到 worker 不得覆盖或复活它。保留目标逐文件修订校验、删除围栏、任务租约与幂等约束；空间正常使用不等于去掉这些校验。
- 相同 Embedding 和确定索引修订时可以复制向量；源模型/索引已经改变时，不能混入不同模型的向量。可从已取得的分段按目标模型重新向量化，缺少原输入则明确失败到该文件。
- 源输入保护按文件是否仍依赖源数据决定，不能以“整个任务及所有文件必须成功”作为永久解锁条件。输入已独立的文件释放源依赖；未独立的文件须保留明确的依赖或终止恢复途径。移动原有保护不在此方案中放开。

### 当前实现需要改动的地方

`SpaceCopyOwner.aensure_logical/afinalize/aretry`：目标初始化完成后正常可用，重试不再重新冻结整个空间；`SpaceCopyScope.execution_digest` 的全空间比较拆成配置必要约束和文件输入修订；`SourceMoveInputRepository` 将复制输入依赖与移动完成保护分开；空间 UI 不再因后台复制任务遮挡目录。权限 owner 和文件级写入围栏继续保留。

## 四、模型：可用性通过后切换，文件失败独立处理

上一轮新增的“全部文件失败后禁止切换模型”不适合当前原地重建方式，应替换。原向量已清理时，仅保留旧 model 值并不能保留旧模型检索。

1. 确认目标模型存在、类型/权限正确，并实际调用验证；此时不清理旧集合、不切换配置。探测失败维持原配置与原索引。
2. 探测通过、用户确认仍有效后，通过原配置 CAS/模型引用事务切换目标模型，并持久记录任务执行代次与文件范围；先切模型、再清理/初始化目标向量集合。网络调用不放入长时间持锁事务，提交前重验配置及删除状态。
3. 重建期间按原约定暂停相关检索和冲突写入，保留目录、预览、下载；不能在新模型下查询旧模型向量。
4. 文件成功则使用新模型的结果，文件失败复用 FAILED 状态但说明“向量重建失败”。任务结束后释放空间重建状态；即使全失败也保留已切换的新模型，允许正常使用空间和上传新文件，检索只使用成功入库文件。
5. 重试只处理失败文件，复用已有 ES 分段、元数据、人工 Chunk 修改，不重新解析原文、不清除已成功文件向量。用户选择恢复旧模型时，也应明确再执行一次重建，不提供虚假的自动回滚。
6. 清理/初始化等全局步骤在切换后失败：持久记录实际阶段，把受影响未完成文件标为失败，任务失败并释放使用状态；提供恢复该阶段的重试。worker 异常退出时由租约/恢复任务收尾，不能长期停留 REBUILDING。已删除空间的任务仍按删除围栏取消。

实现上需同时调整 model_reference/processing_owner/worker 的切换阶段及期望修订交接；不能只删除“全失败不切换”判断，否则仍是结束时切模型，未实现此处要求。

## 五、验收重点

- 新增普通字段不产生历史文件处理项；改名、删除、修改值最终在 SQL/ES/Milvus 一致。
- 复制中可浏览目标空间并正常操作其他文件；一个/全部文件失败不改变目标空间可用性，重试不重复生成资源。
- 复制期间源新增、改名、替换、删除文件或变更授权，有明确逐文件结果，不整批无关失败、不越权继续读取。
- 目标后续修改、删除、删除整个空间，不被旧 worker 覆盖或复活。
- 模型探测失败完全不触碰原配置/索引；探测通过后先切模型，部分/全部文件失败均保留新模型并恢复空间使用。
- 全失败、初始化失败、worker 崩溃及手动重试均可恢复，无永久空间锁；人工分段和版本/权限保留。

方案核对阶段没有修改代码。用户确认后已实施本地修改及回归；尚未合并、推送或部署，未重试现场任务。
