# F132 一次性开发的执行规程

这份规程给无人值守的一次性开发用。它规定做什么、按什么顺序做、遇到问题谁来定、怎样算做完。`/goal` 的条件只引用本文件，细节以本文件为准。

## 1. 范围

**要做**：`tasks.md` 的 T001–T088、T090–T093、T095，共 93 个任务。

**不做，留给人**：T089（在 test 环境用真实模型跑评测）、T094（test 环境手动验证）、T096（端到端测试，需要运行中的后端与中间件）。这三项在最终报告里列为"待人工执行"。

## 2. 开工前

1. 读 `spec.md`、`design.md`、`tasks.md` 全文，以及仓库根 `CLAUDE.md`、`src/backend/AGENTS.md`、`src/backend/bisheng/linsight/AGENTS.md`、`src/frontend/client/AGENTS.md`、`src/frontend/platform/AGENTS.md`。
2. 在本目录新建三个记录文件（已存在则沿用）：
   - `progress.md`：每完成一个 Wave 追加一节，写命令输出的摘要。
   - `decisions-self.md`：自己做了的决定，每条一行。
   - `pending-confirmation.md`：需要用户确认的事项。
3. 对话会被压缩。任何时候不确定进度，以 `tasks.md` 的勾选状态和这三个文件为准，不凭记忆。

## 3. 执行顺序

按 Wave 0 到 Wave 15 的顺序做。同一个 Wave 里按任务编号做。

Wave 0 的 T009（把验证结论回写 design）按第 4 节的分级处理：属于"自己定"的直接回写；属于"要用户确认"的记入 `pending-confirmation.md`，并按第 5 节处理受影响的任务。

## 4. 决策分级

遇到 `design.md` 或 `tasks.md` 没写清、写错、或与代码现状不符的情况，先判断它属于哪一类。

**自己定，不停下来。** 满足下面全部条件：
- 不改变 `spec.md` 里任何一条验收标准的含义；
- 不放宽隔离、权限、脱敏这三类约束（AC-01 到 AC-10、决策 6、决策 9、决策 10）；
- 不新增第三方依赖，不改动禁区里的东西。

典型例子：文件该放哪、函数怎么拆、行号与文档不符、任务文件清单漏了一个文件、某个接入点的实际位置与 design 写的不同但做法不变、测试替身怎么写、错误码用哪个号、任务粒度太大需要分几次提交、design 的某条决策在实现上有更简单的等价做法。

做法：选一个方案，在 `decisions-self.md` 记一行（任务号、遇到什么、怎么定的、为什么），同步改 `design.md` 的对应位置，并在 `tasks.md` 的"实际偏差记录"加一行指针。

**要用户确认，但不停下来。** 出现下面任一情况：
- 要改 `spec.md` 某条验收标准的含义，或某条验收标准做不到；
- 要放宽隔离、权限、脱敏约束，或发现现有方案在这三方面有漏洞而补法不止一种；
- 要改变用户看得见的行为（界面上多出或少掉东西、默认值、文案含义）；
- 要新增第三方依赖、改数据库里已有表的既有列、改其他功能的对外行为；
- Wave 0 的验证结论推翻了 design 的某条决策，且替代做法会影响上面任何一项。

做法：在 `pending-confirmation.md` 记一条，写清：编号、涉及的任务与验收标准、问题是什么、有哪几种做法及各自后果、建议选哪个、目前按哪个做法在继续（如果有）。然后按第 5 节处理。

拿不准属于哪一类时，按"要用户确认"处理。

## 5. 被卡住的任务

一个任务依赖某条待确认事项时：

- **有一个保守的做法可以先做**（更严的隔离、默认关闭、不暴露）：按保守做法做完，在 `pending-confirmation.md` 里写明"已按保守做法实现，确认后如需改动涉及哪些文件"。任务照常勾选。
- **没有保守做法**：不做这个任务，在 `tasks.md` 该任务标题后加"（阻塞：见待确认 P-NN）"，不勾选。继续做不依赖它的任务。依赖它的后续任务同样标为阻塞。

不许为了让测试通过而删测试、改断言、加 skip、或放宽判定。测试写错了属于"自己定"，要在 `decisions-self.md` 里说明错在哪。

## 6. 每个任务的固定动作

1. 先写测试并运行，确认它因为功能未实现而失败。
2. 写实现，直到这个任务的测试通过。
3. 运行 `uv run ruff check --select F821` 检查被自动删掉的导入（见 `src/backend/AGENTS.md`）。格式化只对具体文件做，不对目录做。
4. 在 `tasks.md` 勾选该任务。
5. 单独提交一次，提交信息写任务号。不 push。

## 7. 每个 Wave 的固定动作

1. 运行该 Wave 的"Wave 验收"里写的测试命令。
2. 运行 `tasks.md` 定义的〔架构检查〕〔分层检查〕〔基线比对〕。
3. 四项里有任何一项不符合预期，先修，修好再进下一个 Wave。修不好且原因在本功能之外的，记入 `pending-confirmation.md`，继续。
4. 把四条命令的关键输出行追加到 `progress.md`。

## 8. 禁区

- 不执行 `git push`，不执行仓库级 git 写操作（`git stash`、`git reset --hard`、`git clean`、`git checkout .`、不带路径的 `git restore`）。
- 不运行 `uv sync`、`pnpm install`，环境只用软链。
- 不修改任务点名以外的既有测试文件。
- 不新增第三方依赖。
- 不改动 `core/vectorstore/`、`knowledge/` 下的检索行为。
- 不在 `common/`、`core/` 里导入 `memory`。
- 不改 `spec.md` 的验收标准。发现要改的，走第 4 节的"要用户确认"。

## 9. 什么时候停

**正常结束**：范围内的任务全部勾选，或者没勾选的每一个都标了阻塞并在 `pending-confirmation.md` 里有对应条目。此时执行第 10 节。

**提前停止**，并执行第 10 节后说明原因：
- 连续 5 轮没有任何任务的状态发生变化；
- 基线比对出现新增失败，修了 3 轮仍在；
- 发现已提交的实现违反了隔离、权限或脱敏约束，且不知道怎么修；
- 被阻塞的任务超过范围内任务总数的四分之一。

## 10. 最终报告

结束前在对话里一次性打印下面全部内容，供判定与用户阅读。每一项都是真实运行的命令输出，不是转述。

1. `grep -c '^- \[x\]' tasks.md` 与 `grep -n '^- \[ \]' tasks.md` 的输出：已勾选数量与未勾选任务清单。
2. `cd src/backend && uv run pytest test/memory -q` 的结尾汇总行。
3. 〔架构检查〕〔分层检查〕〔基线比对〕三条命令的输出。
4. `cd src/frontend && pnpm lint && pnpm typecheck && pnpm check-i18n` 的结果。
5. `git status --short` 与 `git log --oneline origin/feat/3.0.0..HEAD | wc -l` 的输出。
6. `cat pending-confirmation.md` 的全文。
7. `decisions-self.md` 的条数，以及其中对 design 改动最大的五条。
8. 待人工执行的三项：T089、T094、T096。
9. 一段不超过十行的总结：做完了什么、哪些被阻塞、哪些地方自己没有把握。
