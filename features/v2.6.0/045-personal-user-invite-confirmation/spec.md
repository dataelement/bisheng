# Feature: 个人用户邀请本人确认后生效

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
>
> 本文档只回答做什么、如何验收以及明确不做什么。实现方案、数据结构、接口、服务职责和文件清单在后续 `design.md` 与 `tasks.md` 中定义。

**关联 PRD**: [0811 中粮需求响应 §1.2「知识空间/频道邀请个人用户需本人确认后生效」](https://dataelem.feishu.cn/wiki/MWHZwS0mbihH7NkbBvpckvSRnwc)
**优先级**: P0
**所属版本**: v2.6.0（COFCO 0811 定制）
**依赖**: F025-approval-center-unification、F026-channel-active-authorization、F033-department-space-member-scope、F044-unified-permission-entry、F047-f046-approval-business-decoupling

> **范围边界**
>
> - **本次纳入**：
>   - 知识空间和频道的资源所有者、管理者或其他具备权限管理能力的用户，向个人用户发起邀请。
>   - 每名被邀请用户本人独立确认；确认前权限处于待生效状态，确认并通过实时校验且授权成功后才生效。
>   - 批量邀请的逐人建单、逐人反馈、独立处理和独立执行结果。
>   - 权限管理页面展示待生效邀请，并与已生效权限明确区分。
>   - 管理后台预置并默认启用一个由知识空间和频道共用的「知识空间用户邀请确认」场景。
> - **本次明确排除**：
>   - 部门和用户组授权；继续沿用直接授权流程，不进入本人确认。
>   - 已有个人用户的角色修改和权限移除；继续沿用既有流程。
>   - 用户主动申请加入知识空间或订阅频道；继续沿用既有加入/订阅审批场景。
>   - PRD §1.1 的统一权限设置入口、创建资源时设置权限以及页面重排；这些能力已由 F044 提供，本特性只复用，不重复建设。
>   - PRD §1.3、§1.4 的文件变更审核。
>   - 「同一对象只保留一条授权记录」等 PRD 评论中已明确保持现状的授权存储重构。

## 1. 用户故事

### 故事 A：邀请人

作为 **知识空间或频道的资源所有者、管理者或其他具备权限管理能力的用户**，
我希望 **可以一次邀请一名或多名个人用户，并清楚看到邀请正在等待本人确认**，
以便 **不会把“邀请已发送”误认为权限已经生效**。

### 故事 B：被邀请用户

作为 **被邀请的个人用户**，
我希望 **在审批中心查看邀请内容并自行同意或拒绝**，
以便 **只有经过我本人确认的资源权限才会生效**。

### 故事 C：权限管理者

作为 **有权查看资源权限的管理者**，
我希望 **在权限管理页面区分待生效邀请与已生效权限，并看到每名用户的独立结果**，
以便 **准确判断当前真正拥有资源权限的成员范围**。

### 故事 D：系统管理员

作为 **系统管理员**，
我希望 **系统首次初始化时已经提供并启用个人用户邀请确认场景**，
以便 **无需手工新增场景即可执行本人确认流程**。

## 2. 验收标准

### 2.1 邀请发起与反馈

- **AC-01** — WHEN 具备权限管理能力的用户在处于分享状态的知识空间或频道中选择一名或多名个人用户、为其选择现有权限角色并提交, THE SYSTEM SHALL 为每名尚无在途邀请的用户分别发起本人确认邀请。
- **AC-02** — WHEN 一次提交包含多名个人用户, THE SYSTEM SHALL 为每名用户分别记录邀请、确认任务、处理结果和权限执行结果，任一用户的结果不得影响同批其他用户。
- **AC-03** — WHEN 个人用户邀请提交成功, THE SYSTEM SHALL 对每名用户反馈“邀请已发送”语义，不得反馈“授权成功”或其他表示权限已立即生效的语义。
- **AC-04** — WHEN 邀请提交成功, THE SYSTEM SHALL 向每名被邀请用户发送提醒，并使其能够从审批中心查看自己的确认任务。
- **AC-05** — WHEN 同一用户在同一知识空间或频道下已经存在待确认邀请时再次被邀请, THE SYSTEM SHALL 返回或关联既有在途邀请并保留其原邀请内容，不得创建新的确认任务或新的在途邀请。
- **AC-06** — WHEN 被邀请用户在同一资源下不存在待确认邀请，且上一条邀请已拒绝、撤回或取消后再次被邀请, THE SYSTEM SHALL 允许创建一条新的本人确认邀请。
- **AC-07** — WHEN 授权对象是部门或用户组, THE SYSTEM SHALL 沿用既有直接授权流程，不创建个人用户确认任务。
- **AC-08** — WHEN 操作对象是已拥有有效权限的个人用户且管理者修改其角色或移除其权限, THE SYSTEM SHALL 沿用既有角色修改或移除流程，不创建个人用户确认任务。

### 2.2 待确认状态与可见性

- **AC-09** — WHILE 个人用户邀请处于待确认状态, THE SYSTEM SHALL 不向被邀请用户授予该知识空间或频道的任何邀请角色权限。
- **AC-10** — WHILE 个人用户邀请处于待确认状态, THE SYSTEM SHALL 不把被邀请用户计入或展示为已生效成员。
- **AC-11** — WHILE 个人用户邀请处于待确认状态, THE SYSTEM SHALL 在资源权限管理页面向资源所有者、管理者及其他具备权限管理能力的用户展示被邀请用户、邀请角色和“待生效”状态。
- **AC-12** — WHILE 个人用户邀请处于待确认状态, THE SYSTEM SHALL 仅允许被邀请用户本人处理对应确认任务；其他用户不得代其同意或拒绝。
- **AC-13** — WHILE 邀请尚未结束, THE SYSTEM SHALL 以权限业务申请记录邀请与授权处理事实，以审批中心任务记录本人确认决定；提醒消息的已读、未读、发送失败或删除状态不得改变任一结果。

### 2.3 本人确认与权限生效

- **AC-14** — WHEN 被邀请用户同意邀请, THE SYSTEM SHALL 在权限生效前重新校验资源仍然存在且允许授权、邀请人仍具备相应权限管理能力、目标用户仍有效、目标用户仍符合租户或部门范围限制、所选角色仍然有效。
- **AC-15** — WHEN 被邀请用户同意邀请且全部实时校验通过, THE SYSTEM SHALL 执行邀请角色对应的现有授权行为；仅在授权成功后把权限标记为已生效。
- **AC-16** — WHEN 本人同意、实时校验和授权执行全部成功, THE SYSTEM SHALL 把权限管理页面中的该用户从“待生效”转换为正常的已生效权限，并允许用户按邀请角色访问资源。
- **AC-17** — IF 被邀请用户同意后任一实时校验失败, THEN THE SYSTEM SHALL 不授予权限、保留审批中心“已同意”的决定事实，并在权限管理页面把该邀请展示为可追踪的业务失败；审批结果不得被业务校验失败反向改写为审批异常。
- **AC-18** — IF 被邀请用户同意后授权执行失败, THEN THE SYSTEM SHALL 不把该用户展示为已生效成员、不向其开放资源权限，并在权限管理页面保留该邀请及失败原因；具备权限管理能力的用户 SHALL 对原邀请业务申请发起重试，重试不得创建新的本人确认审批。
- **AC-19** — WHEN 已成功生效的确认任务被重复处理或授权结果被重复执行, THE SYSTEM SHALL 保持单一有效授权结果，不得重复增加权限或成员记录。

### 2.4 拒绝、撤回与并发终态

- **AC-20** — WHEN 被邀请用户拒绝邀请, THE SYSTEM SHALL 结束该邀请且不授予任何权限，并从资源权限管理页面移除对应待生效行。
- **AC-21** — WHEN 邀请人在邀请仍待确认时撤回邀请, THE SYSTEM SHALL 结束该邀请、使待确认任务不可再处理、不授予任何权限，并从资源权限管理页面移除对应待生效行。
- **AC-22** — IF 同意、拒绝或撤回请求针对已经结束的邀请, THEN THE SYSTEM SHALL 拒绝改变既有终态，不得产生新的权限结果。
- **AC-23** — IF 同意与撤回或其他终态操作并发发生, THEN THE SYSTEM SHALL 只接受一个终态；若邀请未成功完成“本人同意、实时校验、授权成功”的完整链路，则不得产生有效权限。

### 2.5 预置场景与强制确认

- **AC-24** — WHEN 系统首次初始化且尚不存在个人用户邀请确认场景, THE SYSTEM SHALL 自动创建并默认启用一个供知识空间和频道共同使用的「知识空间用户邀请确认」场景，管理员无需手工新增。
- **AC-25** — WHEN 系统初始化时已经存在该场景, THE SYSTEM SHALL 不重复创建场景，不覆盖管理员已有配置。
- **AC-26** — WHEN 知识空间或频道新增个人用户, THE SYSTEM SHALL 进入该共用场景的默认本人确认流程；该流程只包含一个“被邀请用户确认”节点，处理人固定为被邀请用户本人并采用任一处理人同意即可通过的规则。
- **AC-27** — IF 个人用户邀请确认场景不存在或已关闭, THEN THE SYSTEM SHALL 将本次提交中的新增个人用户授权降级为直接授权流程：直接授权成功、不创建本人确认邀请，并沿用直接授权既有的实时校验（资源仍存在且允许授权、调用者仍具备权限管理能力、目标用户有效且符合租户或部门范围、所选角色有效）。
- **AC-27a** — IF 个人用户邀请确认场景已启用但未能定位被邀请用户本人或无法创建确认任务, THEN THE SYSTEM SHALL 明确返回个人用户授权失败，不创建邀请、不授予权限，且不得退化为直接授权。
- **AC-28** — WHERE 个人用户邀请确认场景已启用, THE SYSTEM SHALL 保证个人用户邀请只有在本人同意、实时校验通过且授权成功后才能生效，任何配置或异常路径均不得绕过本人确认直接授予权限；WHERE 场景不存在或已关闭, THE SYSTEM SHALL 按 AC-27 降级为直接授权。

### 2.6 隔离、安全与兼容性

- **AC-29** — WHERE 多租户模式启用, THE SYSTEM SHALL 将邀请、确认任务、权限管理展示和授权结果严格限制在目标资源所属租户内，不得跨租户邀请、查看或处理。
- **AC-30** — WHEN 部门知识空间邀请个人用户, THE SYSTEM SHALL 在发起邀请和确认生效时都遵守该知识空间现有的部门范围限制。
- **AC-31** — WHEN 用户主动申请加入知识空间或订阅频道, THE SYSTEM SHALL 保持既有加入或订阅审批行为，不进入本特性的个人用户邀请确认场景。
- **AC-32** — THE SYSTEM SHALL 保持知识空间与频道现有的有效权限角色语义不变；本特性只改变个人用户新增授权的生效时机。

## 3. 边界情况

- 批量邀请中部分用户已存在待确认邀请时，已有邀请的用户沿用原在途邀请，其余用户正常创建独立邀请；整批不得因单个重复对象而全部失败。
- 同一用户在知识空间 A 的待确认邀请，不影响其在知识空间 B 或频道中的邀请；唯一性边界为“用户 + 单个资源”。
- 同一用户在同一资源下的在途邀请保留首次邀请的角色；再次提交其他角色不得静默修改被邀请用户正在确认的内容。
- 邀请等待期间资源被删除、转为不允许授权的状态，邀请人失去管理权限，目标用户被停用、移出租户或不再满足部门范围，或者邀请角色失效时，本人同意不得产生有效权限。
- 提醒消息发送失败不得把邀请误判为已授权；审批任务只是真实的本人确认决定来源，邀请业务申请才是授权排队、执行、失败和生效状态来源。
- 审批场景不存在或已关闭时，提交中的新增个人用户授权降级为直接授权流程：直接授权成功且不创建本人确认邀请，并沿用直接授权的实时校验；不得以“待生效/邀请已发送”语义误导，也不得静默忽略该用户。场景已启用但流程异常（无法定位本人或无法建单）时才明确拒绝且不退化为直接授权。
- 已拒绝、已撤回或已取消的邀请不在权限管理页面继续显示为待生效；执行失败的邀请保留为明确的业务失败行且不计入有效成员，可按原业务申请重试。审批中心只追踪本人确认的审批决定，不承担授权执行状态。
- 本功能不得改变部门、用户组授权包含范围及现有授权记录展现方式。
