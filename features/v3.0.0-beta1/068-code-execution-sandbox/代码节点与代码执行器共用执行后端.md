# 代码节点与代码执行器共用执行后端

状态：已按本方案实现。

代码节点和代码执行工具共用一个模块来选择并调用 `local`、`container`、`e2b`。两边要的结果不同，所以公共模块只负责「选后端、跑一段代码」。工具入口的收割、路径检查，以及代码节点的 `main` 返回值解析，都留在各自的调用方。

## 结论

可行。`local` 和 `container` 已经实现同一条执行缝：

```text
execute_code(code, lang, work_dir, timeout) -> (exitcode, logs, stderr)
```

代码执行工具的 `run` 和代码节点的 `exec_method("main")` 都停在这条缝之上，不合成一个函数。`e2b` 目前只有自己的 `run`，工厂可以先把它登记给工具；代码节点要等它补上同一签名之后才能用。

## 两条入口

| | 代码执行工具 | 代码节点 |
|---|---|---|
| 入口 | `CodeInterpreterTool._run` → `executor.run` | `CodeNode._run` → `exec_method("main")` |
| 结果 | `{exitcode, log, file_list}` | `main` 返回的字典 |
| 共用点 | `execute_code` | 同一签名 |

工具在 `run` 里抽代码块、做路径检查、注入字体、收割 `output/`、上传。代码节点在 `SandboxCodeParser` 里包一层脚本，从标准输出的标记里取出 JSON。这些都不进公共模块。

## 公共模块

放在 `src/backend/bisheng_langchain/gpts/tools/code_interpreter/`，与三个执行器放在一起。工作流节点已经从这里引用 `ContainerExecutor`。放进工作流包会让工具层反向依赖节点。

```python
def build_code_executor(kind: str, **kwargs) -> BaseExecutor:
    """kind: local | container | e2b"""
```

构造规则从 `load_tools._get_native_code_interpreter` 搬过来：

- `container` 丢掉工具配置里的副本池字段，副本地址和 token 读 `settings.sandbox_conf`。
- `e2b` 丢掉配置里的 `type`。前端把 `config.e2b.type` 写成 `private` / `official`，那不是执行器参数；自建还是官方只看 `domain` 是否为空。
- 未知 `kind` 直接报错，不改走另一种。

## 代码执行工具

`_get_native_code_interpreter` 只负责读工具上的种类，调用 `build_code_executor`，再包成 `CodeInterpreterTool`。`_run` 仍调用 `executor.run`。

- `local` / `container` 的 `run` 继续走共享的 `run_with_dir`，里面再调 `execute_code`。
- `e2b` 继续走现有的 `run`，直到它也实现 `execute_code`。

灵思在读完配置之后，再绑 `local_sync_path`、`keep_session`、`workspace_prefix`。这些是会话工作区，不属于公共模块。

## 代码节点读哪一份配置

节点的后端和代码执行工具读同一份配置：内置工具「代码执行器」（`tool_key=bisheng_code_interpreter`）extra 里的 `type`。`sandbox_conf.code_node_enabled` 不再参与选择。

`t_gpts_tools.type` 是分类 id（代码执行器是整数），不是 `local` / `container` / `e2b`。执行器种类在 extra 的 JSON 字段 `type` 里。管理端保存时写在分类表 `t_gpts_tools_type.extra`，并把工具行的 extra 置空。节点必须走和灵思相同的 `ToolExecutor.parse_preset_extra`：工具行 extra 非空就用工具行，否则用分类 extra。

在工作流所属租户的上下文里，用同步的 `GptsToolsDao.get_tool_by_tool_key("bisheng_code_interpreter")` 查询。每次 `exec_method` 读一次，不在进程里缓存。缺 `type` 时默认 `local`，和工具装载一致，避免空配置被当成 `container`。未知值直接报错。

`code.py` 不改调用方式。`workflow.code_node_enabled` 仍是总闸：关闭时节点在构造时拒绝，不会去查工具表。它打开之后，进程内 `CodeParser` 不再作为 `local` 的实现。

## 三种 type 在节点上怎么跑

节点仍然只调用 `execute_code`，不调用工具的 `run`。从 extra 里只取种类，以及 `e2b` 的 `api_key`、`domain`。灵思事后绑上的 `local_sync_path`、`keep_session`、`workspace_prefix` 不带过来，节点没有工作区。

| extra.type | 节点行为 |
|---|---|
| `local` | `LocalExecutor.execute_code`，每次新建临时目录。`work_dir=None` 会写到共享的 `extensions/` |
| `container` | `ContainerExecutor`，`keep_session=False`，`work_dir=None`，不把 worker 的 `/app` 拷进沙箱。副本地址和 token 仍来自 `sandbox_conf` |
| `e2b` | 密钥和 domain 用同一份 `config.e2b`。要先补上 `E2bCodeExecutor.execute_code`：只跑这段代码，把 stdout / stderr 收成 `(exitcode, logs, stderr)`，不做工作区拷入和产物收割。适配器还没有时，节点报错，不回落到 `local` 或进程内 `exec` |

包装脚本、哨兵和从标准输出取 JSON 留在 `SandboxCodeParser.exec_method`。

## 不放进公共模块

- 工具的 `run`：抽代码、把以 `pip` / `python ` 开头的内容推断成 shell、删字体缓存、工作区逃逸检查、收割上传。
- 代码节点的包装脚本和哨兵解析。
- 进程内 `exec`。它不是 `local` / `container` / `e2b` 的第四种后端。
- 灵思的会话目录、粘滞租约、工作区镜像。
