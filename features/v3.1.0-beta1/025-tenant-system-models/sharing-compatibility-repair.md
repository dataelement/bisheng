## Contract and evidence

These disagree after upgrade. Model defaults are not grants; execution must continue checking actual provider sharing.

Dominant qualities: preserve the existing switch contract across upgrade, retain tenant restrictions, and use the existing recoverable permission projection rather than direct tuple writes.

## Repair

2. Use this resolution for Root sharing coverage, mount/new-child/reenable selection, and adding models to existing legacy shared providers. Read native sharing outside SQL transactions; recheck explicit intent under the provider lock before a lifecycle mutation. A competing explicit off invalidates a stale legacy decision. Permission failure propagates instead of returning an empty success. For the legacy additive new-model writer, first adopt the already existing recipients through a guarded zero-delta sharing reservation, persist its enabled intent and real plan ID, then obtain the normal new-model producer snapshot. Adoption never expands recipient scope; the receiver initializer consumes the actual completed adoption plan ID. Repeated/failed calls use the original frozen reservation.
3. A legitimate legacy receiver command uses the existing provider reservation, original operator, frozen before/after tuple projection and visibility receipt. Finalization promotes legacy intent to persisted enabled alongside COMPLETED. Only absent receiving policies are initialized; existing restrictions and explicit off remain unchanged.
4. A maintenance command defaults to preview. Its apply mode requires explicit provider IDs and a Root global-super operator; a conditional repair command includes the preview's intent pin (enabled/version/plan_id) in its digest and checks that exact pin under the provider lock before creating the original sharing reservation. A completed OFF or other intervening change rejects the stale command rather than enabling again. It reports per-provider outcomes/remaining gaps. No direct FGA writes, no default-config inference, no credential/config output. Existing unfinished commands retain their original actor/digest/frozen data; they are never deleted, re-signed or overwritten to make repair pass.
5. 116 restoration covers providers shown as enabled by this same legacy switch contract and current explicit-on providers. Snapshot grants/policy versions first, retain evidence and verify exact deltas. Test the reported non-global user 841 in tenant 69 through real authenticated HTTP, user candidate selection and a small real model invocation; verify another child and policy preservation. A blocked historical plan is reported separately until its integrity and original command can be safely recovered.

## Unstarted historical preparation recovery

116 provider 12 has an old PREPARING record whose full request payload hash still matches, but whose expiry digest cannot be reconstructed from its stored second-precision timestamp. Its original command digest does not match a current enable/disable command. It has no frozen sharing, no acknowledgement, no reserved target revisions and no permission projection journals. It must never be re-signed or executed as a current enable command.

A separate explicit maintenance cancellation may retire only this provably unstarted class of preparation. Preview returns an exact fingerprint including every original plan/execution field, never credentials. Apply requires a currently authenticated Root global super, that same fingerprint, and the same provider lock used by normal sharing. Under that lock the LLM repository requires PREPARING + canonical empty execution frame, structurally valid original actor/targets, intact request hash, and no receiver receipt. The permission application queries its own journal repository in the same native SQL transaction and refuses cancellation if any journal exists for the exact provider/confirmation scope (regardless of status). It performs no FGA mutation. A current locking read detects already existing journals; it cannot prevent a delayed preparation inserting a journal after cancellation. Such a late journal remains fail-closed because ABANDONED cannot be rebound or executed; both cases are covered by regression tests.

This explicit maintenance path atomically transitions the original plan to ABANDONED and writes an audit acknowledgement containing the cancelling actor and old fingerprint. Original actor, command/request hashes, plan digest, operation ID and all original frozen business fields remain unchanged. A stale worker cannot bind or execute a retired plan. This maintenance entry refuses RESERVED/SHARING_COMPLETE/FAILED_CLOSED or any journal/receipt/nonempty execution facts; a conditional repair still requires its own fresh preview.

The subsequent failure-recovery fix adds automatic request cleanup and recovery before normal edits (design.md §2.1). It can atomically retire PREPARED journals together with an unstarted reservation, and must reconcile started/unknown sharing before admitting a new command. Users do not need this maintenance entry to unblock an ordinary failed edit. ABANDONED retry receipts become SUPERSEDED when a fresh command is accepted; both remain non-executable, preserving their signed payloads and audit.
