# Domain Modeling

本入口借鉴 Matt Pocock 的领域建模方法，按本套 SDD 的项目位置、版本和确认规则适配。先读[领域语言接入规则](../sdd-workflow/references/domain-language.md)，复用调用方已确定的范围和来源；不自动改建项目目录或开启整套 SDD。

## 澄清与记录

1. 读取当前业务范围的有效定义、相关需求／设计增量和必要代码。核对材料的修订与适用状态，不从当前代码自行确定正确业务规则。
2. 遇到新称呼或重载词，先判断是否同一对象：含义、归属、关系及生命周期是否一致。能查明的事实先查；真实业务选择列出可行选项、取舍和建议，交用户决定。已确认内容直接复用。
3. 用具体场景检验关系，例如失败重试究竟创建新任务还是同一任务的一次执行。不同范围的合理同名和不同对象的相近名称应消歧，不机械合并。
4. 结论形成后立即写入当前获准的记录。未确认定义留在本次需求／设计草稿，注明候选；目标方案与当前事实分开。确认随既定需求或设计节点完成，不逐词新增审批。
5. 业务定义进入适用词典；模块职责、代码／接口／存储标识与展示名称的对应关系进入设计或已有模块契约。旧技术名可通过有依据的映射保留，不能因文案统一而擅改公共契约或批量重构。

词典默认格式可参考 [GLOSSARY-FORMAT.md](references/GLOSSARY-FORMAT.md)，但项目已有位置和载体优先；目录只在确有已确认内容需要维护时按需创建。重要跨特性取舍同时满足难逆转、缺背景难理解、有真实备选时，参考 [ADR-FORMAT.md](references/ADR-FORMAT.md)；项目强制记录照常遵循，局部取舍可直接留设计。

## 完成与交接

本次核心行为所依赖的概念无未决歧义，候选与确认状态明确，规范名／相近对象／技术映射可定位，相关正文、图示和用例一致，才可交接依赖这些定义的工作。非阻塞措辞和无关历史别名不扩大处理范围。
交接保留词典来源与修订、本次概念增量及确认依据、映射位置和未决项；旧构建与旧文档继续使用对应基线。缺乏来源或确认时如实保留缺口，继续可独立推进的工作。
