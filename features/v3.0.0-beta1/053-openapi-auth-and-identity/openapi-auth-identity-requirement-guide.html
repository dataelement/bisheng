01 · Executive map

一页结论：一次 v2 调用到底过什么关

先不要把“鉴权”理解成只验一串 token。真正的允许条件是：凭据有效 + 租户有效 + PAT 开关（如适用）+ endpoint scope + 身份模式合法 + 业务资源真实存在 + 资源权限通过。

1认出密钥bs-sak- 或 bs-pat-；Redis 缓存 / MySQL 哈希查找。
2认出主体SAK → 独立服务账号；PAT → 活跃自然人。
3锁住租户ContextVar 只放根租户共享行 + 凭据租户。
4检查能力api_credential.scopes 是否含端点标记所需 scope。
5解析身份S 自身、D 代表用户；X-End-User 只切会话分区。
6检查资源业务 Service 验证真实对象，再以 typed actor 查询 OpenFGA。
凭据层

“你是谁？”

api_credential.token_hash 找到钥匙；subject_kind + subject_id 找到服务账号或自然人。

能力层

“这把钥匙能调什么？”

scope 是接口能力开关。例如 workflow:invoke，不是资源授权。

资源层

“这个主体能碰哪个对象？”

例如 service_account:17 can_use workflow:abc，最终由 OpenFGA 判定。

绝不能出现的回退：无密钥 → 默认操作员；密钥没有资源权 → 借 resource_owner_user_id 的权限；D 模式 → 服务账号权限与目标用户权限取并集。这三种都属于越权。

04 · Issuance

密钥从哪里发、谁能发、发的时候查什么

SAK · 管理员签发

Platform → 系统管理 → 服务账号

前端入口对 user.role === 'admin' 或 is_child_admin 可见；后端管理依赖只接纳全局超管或当前租户管理员。

  1. 创建服务账号：名称、描述、资源归属人。
  2. 成功后自动进入详情页“密钥”页签并打开签发弹窗。
  3. 选择 endpoint scopes、有效期、可选的代表范围。
  4. 服务端返回明文一次；用户勾选“已保存”后才可关闭。
  5. 之后只显示掩码，例如 bs-sak-********a9Qx。
PAT · 员工自助

Client /workspace → 设置 → 账户 → 个人令牌

入口同时受部署级 open_api.pat_enabled 与租户级 open_api_tenant_setting.pat_enabled 控制。管理员台账位于 Platform 系统管理“个人令牌”。

  1. 无名称、scope、有效期输入；员工一键获取。
  2. scope 固定为 knowledge:read。
  3. 同一人同一租户最多一把有效 PAT；重新获取先撤销旧令牌。
  4. 管理员持有人有效期取 min(租户 TTL, pat_admin_ttl_days=7)。
  5. 关闭开关只是停用；未过期令牌重开后恢复。

05 · Authorization

最容易混淆：权限位 scopes ≠ 资源授权

第一道门 · MySQL

接口能力 Scope

问题：这把钥匙允许调用哪一类 endpoint？

数据：api_credential.scopes JSON。

规则：route decorator 决定所需 scope，调用者不能在请求中自选。

失败：26003 / 403，资源逻辑尚未开始。

+
第二道门 · OpenFGA

资源权限 Grant

问题：当前 typed actor 能否对这个真实对象执行 action？

数据：permission_grant* 投影到 OpenFGA tuples。

规则：业务 Service 先加载对象，再查 can_<action> / visible。

失败：403；不存在/不可见按业务反枚举语义可能 404。

两道门都通过，业务动作才允许执行
Scope资源权限结果说明
缺少即使有 editor26003 / 403在公共 v2 依赖提前拒绝，不查业务资源。
具备没有403能进入该类接口，不等于能操作任意资源。
具备具备继续业务仍要满足参数、状态、版本等业务校验。
D 模式的关键语义：代表用户后，授权主体直接替换为 user:{target_id}；服务账号已有的资源 grant 不做交集，也不做并集。一个 SA 有 workflow editor，但被代表用户没有 use，结果仍应拒绝。
06 · Exact validation pipeline

一次 v2 请求的 12 道校验（按当前代码顺序）

这是排查错误最有用的一段。前 11 步位于统一 v2 依赖；第 12 步由具体业务 Service 执行。Redis 或数据库在认证关键路径异常时 fail closed，返回 26030 / 503。

Authorization 语法
必须是 Bearer bs-sak-<43字符> 或 Bearer bs-pat-<43字符>；secret 仅允许 [A-Za-z0-9_-]。scheme 大小写不敏感。

哈希找凭据

26002 / 401

26002 / 401

SAK 查启用 SA 且 tenant 一致；PAT 查 user.delete=0 与活跃 user_tenant 且 tenant 一致。
26002 / 26043
租户状态
每次都读 Redis disabled_tenant:{tenant_id}；禁用租户的凭据统一视为 invalid。
26002 / 401

Redis oapi:cred:lastused:{credential_id} 以 NX 60 秒节流，更新 last_used_at；该遥测失败不阻断。
best effort

current_tenant_id=凭据租户；visible tenants 仅根租户共享行与凭据租户，PAT 管理员也不得横跨子租户。

WebSocket 与 HTTP 有何不同？

握手复用同一 v2 dependency。认证/授权失败用 WebSocket policy violation code 1008，reason 放业务错误码。连接建立后每 3 秒重新执行凭据验证；凭据被撤销、过期或主体失效后应主动关闭，而不是让长连接永久存活。

07 · Identity

S、D、X-End-User：三者改变的不是同一件事

形态如何触发授权主体兼容业务 user_id / owner会话分区权限来源
SAK · S普通 SAK，无身份头service_account:{sa_id}resource_owner_user_id，仅兼容旧字段/创建归属，不含管理员短路tenant + SA + 可选 external user服务账号自己的 OpenFGA grants
SAK · S + End-UserX-End-User: customer-001仍是 service_account:{sa_id}不变再按 external user 精确隔离仍是 SA 权限；End-User 不是平台用户
SAK · Dkey 含 delegate 且发送 X-On-Behalf-Of: 123user:123目标用户 123自然人会话只用被代表用户权限
PAT · Sbs-pat-*user:{holder_id}持有人自然人会话用户本人实时 OpenFGA 权限，可享管理员短路但租户仍锁定

D 模式不是传个 user_id：要连续过 7 项检查

  1. X-On-Behalf-Of 与 X-End-User 不能同时出现：26010 / 400。
  2. 值必须是 ASCII 十进制正整数；空、0、负数、全角数字均无效：26005 / 403。
  3. 凭据必须是 SAK，且 scopes 含 delegate；PAT 永远不能代表他人：26004 / 403。
  4. 如果 key 含 delegate，每次调用都必须给 OBO header，禁止漏传后静默落回 S：26016 / 400。
  5. 目标必须满足 user.delete=0、活跃 user_tenant、tenant 与 credential 一致：26005 / 403。
  6. 目标不能是全局超管或该租户管理员：26007 / 403。租户管理员判断会查 OpenFGA。
  7. 目标必须落在该 credential 的直接 user 范围，或其部门 path 位于获授部门 path 子树中；且 endpoint 必须支持 D，否则 26006 / 403。
部门包含子级的真实算法：从 api_credential_delegate_scope 取选定 department；读取这些 department.path；再通过 user_department 找目标用户的部门。只要任一 member_department.path.startswith(scope_department.path) 即允许。测试必须覆盖相似前缀误命中、跨租户部门、删除/停用部门。
X-End-User 的精确格式与安全含义

非空，UTF-8 编码后最多 128 bytes，并且每个 byte 都在 0x20..0x7E 可打印 ASCII 范围。中文、换行、TAB、控制字符、129 个 ASCII 字节都会返回 26018 / 400。

它只用于同一服务账号下的会话/附件隔离，不查 user 表、不产生 OpenFGA subject、不改变资源权限。不要把它当代表用户。

08 · OpenFGA

到底哪些步骤会查 OpenFGA

阶段是否查 OpenFGA查询形态说明
Bearer 格式、token hash、过期/撤销否Redis + MySQL凭据事实不在 OpenFGA。
endpoint scope否required in api_credential.scopes能力位是凭据配置。
D 模式目标是否租户管理员是user:{id} admin tenant:{tenant_id}用于拒绝代表特权目标；全局超管由既有检查判定。
PAT 持有人管理员事实是同上决定 PermissionActor 的租户管理员短路；visible tenant 仍不扩张。
具体业务资源动作是{actor} can_{action} {resource_type}:{id}例如 can_use、can_edit、can_upload_file。可见性关系使用 visible。
资源列表/批量过滤是BatchCheck / ListObjects不能 OpenFGA 故障后返回未过滤全集。
签发 SAK间接检查 F048 runtime/Catalog readiness模型未就绪不允许产生不可用钥匙。
配置 SA 资源授权是F048 mutate + projectionMySQL grant 为治理记录，OpenFGA tuple 为在线判定。

资源授权入口与存储

管理员怎么配

服务账号详情 → “资源授权”。可选资源类型：知识空间、知识库、工作流、助手、工具、频道、看板。候选资源来自 resource_permission_mode 的 CURRENT 行，按名称/ID 搜索，最多 200，不允许任意手输伪造对象，也不直接列 folder/file。

服务端怎么防越权

POST /api/v1/service-accounts/{id}/resource-grants:mutate 固定 subject 为目标 SA；请求需带 idempotency key、资源版本与 Catalog release id。先验证资源真实类型/tenant/parent/version，再写 grant 并投影。

自动授权：SA 在 S 模式创建顶层 CUSTOM 资源时，业务归属字段仍写自然人 owner 以兼容旧服务；同时给真正授权主体 SA 建 CREATOR_GRANT（manager model）。这样后续不是借 owner 的权限，而是 SA 拥有可审计、可撤销的独立 grant。

OpenFGA 模型标识为 f048-v4，新增基础主体 service_account 及 user:*/service_account:* 技术标记。动作包括 manage_permission、rename、edit、create_folder、upload_file、move、download、delete、share、use、publish、unpublish。

09 · Session isolation

为什么不能只靠 message_session.user_id

为了复用旧聊天链路，SA 模式仍把 message_session.user_id 写成 resource_owner_user_id。如果查询也只看这个字段，同一 owner 名下的所有 SA、v1 用户会话就会串在一起。因此 F053 增加 typed session subject。

来源持久化匹配条件兼容 user_id附件分区
自然人 / PAT / Dtenant_id + api_subject_type IS NULL + user_id本人{user_id}
SAK · Stenant_id + api_subject_type='service_account' + api_subject_id=sa_id + external_user_id 精确相等资源归属人service-account/{sa_id}/{sha256(external)[:16]}
public v3tenant_id + api_subject_type='public_v3' + flow_id=resource_id默认操作员public-v3/{sha256(resource_id)[:16]}
测试陷阱：同一个 SA，X-End-User 缺失与值为空不是同一输入；空 header 会被 26018 拒绝，完全不传才产生 external_user_id IS NULL 的 SA 级分区。不同 SA 即使 owner 相同也不能看到彼此会话或临时附件。
10 · Concrete examples

v2 如何复用既有业务逻辑而不改变接口行为

策略是“薄适配，不内调 v1”：v2 负责建立 typed identity 和校验边界，然后直接调用现有 Domain Service。兼容的 UserPayload 只满足旧字段/审计/归属需要，PermissionActor 始终保留真实授权主体。

案例 A：POST /api/v2/workflow/invoke
  1. 统一依赖要求 workflow:invoke。
  2. 从 JSON workflow_id 取 UUID；加载 Flow 真实行并确认 flow_type=workflow。
  3. 以当前主体检查 can_use workflow:{workflow_id}。
  4. 复用既有 workflow service；S 模式兼容 owner user，D 模式使用目标用户。
  5. 进入 Celery 前生成不可变 OpenApiExecutionSnapshot：tenant、actor、authorization subject、resource owner、effective user、mode、credential_id、trace_id、channel='open_api_v2'；绝不含明文密钥。
  6. worker 按 credential_id 重查凭据/主体/PAT 开关并恢复 tenant 与 PermissionActor ContextVar，finally reset；不得从 user_id 或默认操作员猜身份。
curl -X POST 'https://host/api/v2/workflow/invoke' \
  -H 'Authorization: Bearer bs-sak-<secret>' \
  -H 'Content-Type: application/json' \
  -d '{"workflow_id":"<uuid>","input":"hello"}'
案例 B：GET /api/v2/assistant/info/{assistant_id}
  1. scope 为 assistant:read，资源 ID 来自 URL path。
  2. 先加载 assistant，确认存在、未删除、tenant 正确。
  3. 查询 OpenFGA visible on assistant:{id}；不是 can_visible。
  4. 响应中能否分享还会单独检查 share action，不因“可见”自动获得。

助手对话接口的模型/助手 ID 来自 body 的 model UUID，但走同一 get_info 可见性检查。

案例 C：知识库 QA 编辑，防“拿 A 的知识库 ID 修改 B 的 QA”
  1. GET detail_qa?id={qa_id} 先以 QA 主键加载 qa_knowledge 行。
  2. 从真实行读 qa.knowledge_id，而不是信任调用者声称的 knowledge_id。
  3. 读操作查 knowledge library 的 visible；更新/删除查 can_edit。
  4. 如请求同时带 knowledge_id，必须与真实 qa.knowledge_id 相等。
  5. 权限失败发生在 DAO 更新、索引重建、Celery 任务等副作用之前；测试可比对前后内容 hash。
案例 D：知识检索与结果过滤

POST /api/v2/filelib/retrieve 需要 knowledge:read。服务在检索前后都执行文件/知识库权限过滤；OpenFGA 不可用时应返回 503，绝不能“为了可用性”返回未过滤结果。PAT 只能通过这类只读端点，真实可见范围随用户在平台上的权限实时变化。

案例 E：日常聊天 5 个端点与入参兼容

以下都要求 chat:invoke：GET workstation/config、POST workstation/chat/completions、GET chat/list、GET chat/info、POST knowledge/upload。

  • clientTimestamp 与 model 都是必填字符串；extra fields 禁止。
  • v2 去掉 task_mode / use_knowledge_base；适配层固定内部值 false / null，外部传入则 schema 拒绝。
  • model 必须在 config 返回的 models 中；每个工具 (id, tool_key) 必须在 config 的可用 tool children 中。
  • 临时文件引用必须属于当前 typed SessionSubject。
  • 直接复用 stream_chat_completion、WorkStationService、ChatSessionService、TempUploadService；不向本机发内部 HTTP 请求。
案例 F：SA 创建新资源时为什么不先查该资源权限

创建前对象不存在，无法检查对自身的权限。接口先检查对应 scope 与父上下文/创建规则；既有 service 用兼容 UserPayload 写业务 owner；创建完成后 F048 投影 user owner，并给 SA 本身建立 CREATOR_GRANT。随后对该资源的一切访问都以 SA grant 判定。

14 · Deployment

部署前置、版本基线与正确上线顺序

不是“发个后端包就结束”。已运行 F048 的环境必须升级 OpenFGA 不可变模型、补齐技术标记并切 Catalog；商业网关必须支持 v3 HTTP/WS；三条 DDL 必须按顺序执行。

推荐发布序列

  1. OpenFGA 先行：发布包含 service_account 与技术标记的向后兼容 f048-v4；schema contract 通过前关闭 SAK 签发。
  2. 数据库：依次运行 f053_api_credential_tables → f053_delegate_session_subject → f053_pat_tenant_setting。只做 DDL，不回填业务数据。
  3. 后端：先冒烟 v3 7 HTTP + 2 WS，再验证 v2 key 面和 5 个 daily chat 端点。
  4. 前端：client guest 请求与 platform 发布示例切到 v3；管理入口上线。
  5. 商业网关：验证 v3 HTTP 与两个 WS 绕过登录/API Key 网关，保留 guest policy。
  6. PAT 渐进开启：部署级和租户级默认保持关闭；确认 TTL、风险提示、台账、级联失效后按租户开。
