# 独立预期与有效反馈

设计关键断言、评审 AI 生成测试或出现全绿但行为错误时读取；不把测试先行变成每次低影响修改的固定门槛。

| 情况 | 问题 | 有效做法 |
|---|---|---|
| 期望值用与实现相同的 reduce／条件分支重新计算 | 实现和断言可能共享同一错误 | 依据确认规则的已知值、独立算例或契约给出预期，并说明来源 |
| checkout 的测试只断言 mockPayment 被调用 | 未证明真实业务和可观察结果正确 | 保留 checkout 与必要权限／状态逻辑，隔离支付外部边界，检查业务结果和适用副作用 |
| 修复授权问题，把权限判断 mock 成 true | 被验证机制消失 | 执行真实权限代码，替换昂贵授权存储边界，配允许／拒绝及拒绝后无写入场景 |
| 两次顺序调用声称覆盖并发 | 没有产生竞争 | 在可控层安排真正重叠或受控调度；无法证明真实存储竞争时明确交接限制 |

例如已确认两行金额分别为 10 和 5、无额外费用，预期总额为 15；不能再按被测代码同一逻辑生成 expected，也不能脱离费率、币种等实际规则硬填 15。
测试入口选择看本次行为、风险、可替换外部边界与运行成本；既有已确认入口直接复用。入口改变影响核心验证方案时纳入设计确认，不逐用例新增人审。
优先验证调用者关心的公开行为，内部机制确有独立契约时说明理由；必要数据库、消息或状态副作用按需求验证，不能因“只测接口”丢掉业务保护。
一个用例保持一个明确意图，允许多个互补断言；按风险检查异常、边界和无副作用。预期来自确认来源，mock 成功和当前实现不单独定义正确结果。
对于核心逻辑，可按成本观察错误实现或回归前代码能否使测试失败。变异／属性测试仅按需，测试“先红后绿”不能代替独立业务预期或原始故障因果。
