# 研发产物定位、分类与维护

在首次落盘、阶段交接、任务接续或位置变化时读取。本规则供全部 SDD 阶段共用，按任务范围应用。

## 一次定位，持续沿用

先确认当前任务的项目根目录、稳定特性标识、主业务模块、目标版本和有效产物位置。项目根目录来自实际工作工程或用户指定，不能从全局 skill 所在目录推断。

位置选择依次依据：

1. 用户为当前任务明确指定的位置。
2. 项目适用的产物规范和目录约定。
3. 当前特性已有的有效登记与实际产物路径。
4. 项目和任务均无约定时，使用 `features/v<版本>/<主模块>/<编号>-<特性名>/`。

接续任务先查既有登记、交接及实际文件，保留有效位置。项目规则更新与旧登记冲突时说明差异，处理必要冲突后再迁移，不能因新默认目录另建一个同内容特性包。已有平铺 `features/v<版本>/<编号>-<特性名>/`、`.sdd/` 或分散的 PRD／设计／用例可继续使用，通过登记关联各自的有效来源。

把定位结果保存在项目现有任务登记中；没有合适载体时，可用特性包内的 [feature.yaml 模板](../assets/feature-template.yaml)。登记文件在包内时，其实际父目录确定包位置；外部登记中记录相对项目根目录的包路径。后续阶段读取这份登记，不分别推导路径、重编标识或复制业务正文。
相对路径明确其基准目录。包内产物默认相对登记文件所在目录，仓库其他位置可用明确的相对路径；跨仓库使用仓库／版本／路径或可访问制品引用。只打开相应阶段需要的文件。
持久登记中的项目与来源采用可移植的仓库标识及相对位置，实际机器绝对路径在运行时解析或用于本地诊断。搬到另一工作区时，应能依据项目入口和登记重新定位原内容。

## 默认目录与业务归属

以下为完整任务示例，按产物数量和风险创建实际需要的文件及子目录：

```text
features/
  README.md                         # 特性索引，可从登记生成
  _templates/                       # 已采用的项目模板
  v3.1.0/
    release-contract.md             # 项目采用时登记版本范围与跨特性约束
    approval/
      087-delegated-approval/
        feature.yaml                # 项目没有等价登记时使用
        requirements.html
        design.html
        test-cases.html              # 研发用例
        tasks.md
        state.md                    # 接续、待决事项、下一步
        handoff.md
        reviews/                    # 按需保存审核记录
        evidence/dev/<run-id>/       # 每次开发验证摘要及证据引用
docs/
  modules/approval/index.md          # 当前模块知识入口
  architecture/                     # 复用已有权威架构正文
  decisions/                        # 按需保存跨特性的重要决策
```

模块优先采用稳定业务能力的现有名称，例如审批、知识管理、身份权限。前端、后端、Worker 等技术范围可作为附加标签。跨模块变更选定一个主模块保管特性包，`affected_modules` 列出全部受影响模块，其他模块索引指向同一包。
模块尚无法确定时先调查归属；需要暂存且项目无其他约定，可用 `_unclassified` 并保留待归类事项。版本未定时默认放 `features/_unplanned/<主模块>/<特性包>/`，`target_release` 保持未知，不从分支、日期或最近版本猜测交付承诺。

## 标识、版本与状态的归属

| 信息 | 有效来源与维护规则 |
|---|---|
| `feature_id` | 已有稳定任务／特性 ID 优先。新 ID 按项目机制分配并检查占用；多人同时分配时采用现有登记／issue 机制或其他可避免冲突的标识，不能依赖未经核对的最大编号加一。历史重复编号用命名空间或完整来源消歧。目录显示编号和稳定 ID 可分别记录。 |
| 标题、`kind`、主模块及受影响模块 | 维护在一份特性登记中。ID 持续沿用，标题、模块或位置变化时同步登记与引用。 |
| `target_release` | 表示计划目标，可在未交付阶段调整。目录版本与这一目标一致或说明已有项目的实际含义。 |
| `deliveries` | 只登记有实际依据的交付，分别注明 release／版本线、代码或构建、证据与交付状态。研发提测、QA 验收和实际发布分别陈述；创建目录或归档不构成交付证明。 |
| 文档修订与确认 | 文档自身记录当前修订；确认引用实际内容版本／指纹及真实决定依据。文档修订、特性 ID、目标版本和实际交付是独立维度，不通过改目录或版本号继承确认。 |
| `artifacts` | 一份登记定位各产物的有效来源。记录路径用于发现文件，本身不证明文件存在、就绪、确认或执行通过。旧来源被替代时明确指向新来源。 |
| 研发／独立验收状态 | 使用项目已有状态口径，各岗位按实际依据更新自己的状态。登记为状态来源时，`state.md`、README 与索引仅引用或生成摘要，不独立维护第二份状态。 |
| 接续和交接说明 | `state.md` 保留待决、依赖、下一步和证据索引；`handoff.md` 关联登记及当前交付依据。正文中的必要摘要注明来源，避免多个文件各自修改元数据。 |

模板中的未知值保持 `null` 或明确待决。真实确认、产物完成及运行结果由各自证据支撑。已有登记系统覆盖这些信息时直接复用，无须为了文件名再创建一份 `feature.yaml`。

## 变化、基线与长期知识

- 未交付任务定版、延期或归属变化时，沿用稳定 ID。只有实际需要调整位置时迁移，并同步登记、索引、链接和相对路径，检查原处有无无关内容。版本未定不阻止可以独立完成的需求调查或草稿工作。
- 交付前在有效产物中修订，通过版本控制保留过程。已交付范围保留对应基线与证据，后续实质变更形成关联特性包，说明扩展、修正或替代关系。勘误注明原因和所涉基线，避免把旧交付记录改写成新事实。
- 补丁与版本回移沿用业务来源关联，分别登记各版本的代码／构建、差异和验证。可以建立关联变更包或交付记录，遵循项目约定；复制文档或移动旧目录不能证明另一版本已实现、验收或发布。
- 收尾时检查本次是否改变跨版本有效的业务规则、契约、架构、重要取舍或已知限制。将核实的改变更新到对应模块知识，并注明代码／版本基线和验证状态。计划目标与已实现、已验收、已发布事实分别标识。
- 模块知识入口定位当前权威正文和相关变更。已有架构／契约正文时通过链接复用；需要独立当前规格时明确其维护范围和来源。特性包保留本次改变、理由及证据，避免把每次完整上下文复制成多套持续维护正文。
- 跨特性的重要决策可在项目已有 ADR／决策位置维护背景、选项、理由、后果、状态和重审条件，各特性引用同一记录。本次局部取舍可以直接留在设计中。
- 特性索引支持按版本、模块与状态检索，只维护标识及有效链接等导航信息，可由登记生成。按需检查引用、过期状态与代码变化，临时诊断结论经核实后再纳入长期知识。

相关领域词典属于共享模块知识，特性包只登记所选来源／修订、本次概念增量与技术映射位置，不复制每个版本的完整词典。候选、已确认目标与代码现状按[领域语言约定](domain-language.md) 区分；已有有效术语载体优先，简单 Bug 不增加词典文件。

## 测试工程、证据与最小成本

开发测试代码仍归各对应前后端项目 `test/`。测试岗位的正式用例、UI／真实集成／E2E 脚本及运行结果归指定独立验收工程，应用特性包只关联可访问的需求／构建及验收引用。QA 按本工程规则组织目录，沿用同一业务标识与来源，不默认创建研发特性包的镜像。

每次运行用独立 `run-id` 追加记录，绑定实际代码／构建、环境、用例、断言、结果及真实／替身边界，避免覆盖旧报告。大日志、视频、Trace 等按项目制品方案存储，仓库保存必要摘要、可访问引用和适用保存期限。跨机器材料要能实际取得，引用失效属于证据缺口。

简单 Bug 可以将标识、范围、修复依据、验证和交接压缩到现有 issue 或短记录，按项目版本／模块分类即可。`feature.yaml`、模块索引、全套文档及空子目录不成为简单修复的新准入条件。只有新增／更新当前范围所需产物时才创建对应位置。

## 阶段收尾核对

核对本阶段沿用同一任务登记、真实路径和来源版本；已生成文件可定位，必要相对链接有效，新增标识无冲突；状态与证据匹配，迁移／替代／补丁关联明确。设计、用例等业务完成条件仍由专业 skill 判断。
研发收尾记录提测与必要知识更新后，在“研发完成，待独立验收”结束。目录维护不会触发 QA、提交、合并、发布或向他人发送材料。
