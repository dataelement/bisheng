# Sdd Design

先读 [阶段交接规则](../sdd-workflow/references/stage-contract.md)，再用 [设计检查要点](references/design-checks.md) 选择适用检查。
撰写或优化设计文档时，使用 [设计文档写作与完成标准](references/design-writing-standard.md) 和 [HTML 模板](assets/design-template.html)。模板提供阅读结构和可填写表格；生成正式方案时替换模板字段、移除撰写提示，不把模板示意当作项目事实。

## 进入条件

核对当前需求及用户确认。缺少确认时可调查事实、记录选项，不能把需求视为已闭环。
接续已有设计时先核实变更范围和既有决定，保留有效部分。
按[产物存放与维护约定](../sdd-workflow/references/artifact-storage.md) 读取同一特性登记及有效需求／设计位置，复用模块现行知识和已有决策来源。设计更新说明本次改变及应同步的长期知识，记录实际适用基线。
复杂 Bug 从本阶段进入时，依据已确定的修复目标和人工选择，不强制重建无关需求文档。

按[领域语言约定](../sdd-workflow/references/domain-language.md) 沿用已确认概念，补业务概念与模块职责、实体、接口／存储和展示名称的真实映射；正文、图与契约共同核对。旧标识可有兼容映射，目标定义不冒充已实现现状。

## 方法

1. 阅读实际相关代码、配置、依赖、约束和现有机制，说明当前行为及需要改变的行为。
2. 从已确认需求和契约提取关键正确性约束，逐项明确来源、适用范围／时间窗口、设计保证及验证方式；包括必要的禁止结果。优先复用有效机制。存在有意义的取舍时说明选项、理由和重新考虑条件，不为凑数制造替代方案。
3. 明确适用的模块职责、接口和错误行为、数据归属、状态及事务或外部副作用边界。
   复杂知识点、关系和流程优先图解，按 [图解与选图方法](references/diagram-methods.md) 选择概览、架构、流程／泳道、时序、状态、ER、数据流、部署或原理解释图。让图回答具体问题，配必要的精确定义；按场景选用，不要求画齐所有类型。
4. 分析适用的异常、超时、取消、重复和并发；设计必要的资源释放、状态恢复、安全、兼容性和可观测性。
5. 说明验证层级、环境、依赖与真实／模拟边界，让测试能力据此补充技术用例；标明开发期隔离验证与验收集中执行项。

设计时明确真实被测组件和可替换的外部边界，优先复用已有测试接缝，让开发阶段能充分执行 mock／隔离单元、接口和功能测试。相关方法见[测试环境与证据策略](../sdd-test-cases/references/test-strategy.md)。
真实部署 E2E 及昂贵的真实依赖验证由测试岗位安排在独立验收工程和 CI／共享环境，不把个人电脑复刻线上当作设计前提。研发测试归对应项目/test/，设计交代可测试入口、构建与配置前提，供两个岗位协作；不把环境能力全留给 QA 猜测。影响核心选择的未知如实记录并处理。

职责不清、调用者负担大或重要方案难判断时，参考[接口与方案推敲](references/interface-options.md)，按实际需要比较方案或使用逻辑原型；不固定增加多代理、三套设计或删除旧测试。

关键技术假设需要证据。遇到影响核心方案的未知，先做范围受控的探索或标记待决，不能凭空编造系统能力。
若方案需要推翻已确认需求或重要设计，说明原因、影响与选择，交用户决定。

## 产物与完成

按 [HTML 交付约定](../sdd-workflow/references/html-delivery.md) 交付实际 HTML 设计文档，含现状、关键决策和理由、必要契约、影响范围、已知限制、验证办法及需求映射。关联有效需求版本和稳定 REQ／AC；已有非 HTML 材料仍可作输入，记录来源，本轮新形成需求稿时交付 HTML。设计本身不能只输出 Markdown 或对话摘要。
按分层阅读检查：非技术读者能复述方案、重要取舍和失败后的结果；研发能定位职责、契约、状态和约束；测试能推导正常、异常、边界及副作用的验证点。首次技术术语先解释业务含义再保留技术名，摘要、图中名称和图注同样遵守，不能只在后文补解释。
每项需求有安排，关键正确性约束在适用正常、异常和并发路径下均有明确机制、验证方法及证据边界，关键取舍和阻塞已处理，才能标记“设计就绪，待确认”。规则来源或关键保证不明时保留草稿与缺口，不凭作者判断补成已确认规则。
完成前核对复杂难点及适用场景的选图安排、实际可见图解、图与需求／正文／契约／状态的一致性；必要图解缺失或矛盾应先处理。简单修改可复用有效图或用简短说明，不为数量增加图。
模板自检只记录检查依据和发现，不能靠勾选自行批准。设计确认记录必须对应实际用户及当前版本；文档呈现／打印检查不属于产品 UI 或真实环境验收。
用户确认当前设计后交给 sdd-test-cases 补充契约用例及 sdd-plan。必要技术细节由实施者在约束内决定。
局部修复的设计可以很短；文档深度随风险调整。
