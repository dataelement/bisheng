## 根因与处理

构建页使用 `/api/v1/workflow/list?managed=true&action=use`。`managed=true` 实际将筛选动作设为 `edit`，租户管理员走列表快捷分支，不逐资源做权限过滤。默认数据库读取范围为本租户及根租户，导致根租户资源也被标记为可管理；卡片随后请求 `my-permissions` 时，业务校验按当前租户拒绝根租户托管应用。

`WorkFlowService.get_all_flows_envelope` 现仅在“管理列表、租户管理员、非平台超管”条件下，将完整游标扫描包在现有 `strict_tenant_filter()` 中。三类应用的 UNION 子查询沿用既有过滤器，在 SQL 分页前排除根租户和其他子租户资源；本租户其他创建人的应用仍可列出。超管、普通用户及非管理列表保留现有路径。上下文退出或异常时自动恢复，不改变广场共享读取的过滤机制。

本修复没有给跨租户资源增加授权。旧应用仍属于原租户，因此创建人迁租户后在新租户管理列表看不到它们，符合本次确认边界。

## 错误码

权限旧码与信息源模块重复使用同一数字，前端共享文案无法区分。现仅迁移冲突的七个权限码，保留类名和已有 Python 别名，保留 `19000` 权限拒绝和信息源原码：

| 权限错误 | 原码 | 新码 |
|---|---|---|
| 权限检查失败 | 19001 | 25020 |
| 权限服务不可用 | 19002 | 25021 |
| 资源不存在或不可访问 | 19003 | 25022 |
| 权限投影写入失败 | 19004 | 25023 |
| 权限关系无效 | 19005 | 25024 |
| 权限模型名称重复 | 19006 | 25025 |
| 禁止移除最后一位所有者 | 19007 | 25026 |

三语文案修改在 `packages/locales/src/api_errors`，由仓库生成器同步 platform/client 产物；权限无效资源不再显示信息源的“解析失败”文案。`25022` 保持缺失资源与跨租户资源相同的外部错误，避免泄露存在性。权限服务不可用的 HTTP 503 语义不变。

部署时应同时更新 backend/worker 与前端文案。自行按旧 `19001–19007` 识别权限错误的外部调用方需要同步更新；本次不为旧码增加歧义兼容。历史 E2E 中相应断言已更新，未执行这些远端用例。两份旧 E2E 文件因 Ruff 规范发生格式整理及少量类型/未使用变量修正，测试函数与断言数量未变。
