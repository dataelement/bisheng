# 测试环境与证据策略

开发阶段优先在可控、可重复且部署成本合理的 mock／隔离环境里，充分完成需要的单元、接口和功能测试。真实部署端到端测试后置验收。成本影响环境和执行频率的选择，不替代覆盖需求和风险的判断。

研发在对应前后端项目/test/ 维护开发测试；测试工程师在指定的独立验收工程维护 UI、真实集成和 E2E 代码。两岗位共用需求、契约和版本依据，代码与执行入口分离，按[岗位协作与提测规则](../../sdd-workflow/references/qa-handoff.md) 交接。

## 以真实被测行为为中心

这里的 mock 环境泛指外部依赖替身或隔离环境，按实际需要选用：

- 真实实现本身快速、确定性且无昂贵部署时，直接复用。
- fake：有实际状态和简化行为的内存仓库等，适合验证业务状态变化。
- stub：返回可控的成功、拒绝、超时或错误响应。
- mock／spy：观察必要的调用参数、事件和副作用次数。

优先隔离数据库连接、缓存、消息、外部 HTTP、邮件等难部署边界，保留测试目标的真实代码。检查权限时运行真实权限规则，检查路由时进入真实路由，不能将它们替换成恒定成功。
复用项目 fixture 和已有替身。必要时增加最小测试接缝；不要为建立 mock 环境强行重构整个项目。

## 开发阶段的执行范围

| 层级 | 真实运行的目标 | 可隔离的边界 | 重要断言 |
|---|---|---|---|
| 单元 | 当前函数、规则或状态转换 | 时钟、随机、I/O 等外部依赖 | 返回值、异常、边界与状态变化 |
| 接口 | 实际应用入口、路由、校验、相关鉴权、业务处理和序列化 | 外部服务、存储或消息适配器 | schema、错误语义、权限与拒绝后无副作用 |
| 功能 | 与场景相关的真实业务组件及操作链路 | 外部基础设施和第三方服务 | 业务结果、状态、事件、重复／失败及恢复 |
| 契约 | 真实消费方请求处理或真实提供方的契约响应 | 双方各自的外部依赖 | 当前约定与实际实现是否一致 |

每层的真实范围由目标决定，不要求单个用例覆盖所有组件。接口测试可通过进程内客户端或轻量本地 mock 服务完成，无须部署整套线上环境。
模拟业务链路验证应标为隔离功能测试，不能叫作已完成真实端到端验证。
UI 测试执行遵守当前单独偏好；后端功能测试得到允许，不自动改变 UI 后置安排。

## 控制替身失真

- 响应、字段、错误和事件依据已确认契约或核实的实现，记录来源与版本。
- 保留真实业务断言；不能只断言测试自己配置的 mock 返回值。
- 对重要接口采用现有 schema／契约校验，必要时分别验证消费方与真实提供方代码；无需引入特定框架或同时部署两个系统。
- 功能断言与契约断言分开。消息形状正确不能证明记录已经持久化。
- 契约变化时更新受影响替身与用例；不要只改 mock 来迎合错误实现。
- 依赖特定数据库语法、事务隔离、锁、消息投递或真实权限配置的结论，隔离测试不能证明时明确列为验收待验证项。

## 开发完成与验收

研发完成要求：约定代码完成，所需单元／接口／功能测试在各项目/test/ 的适当隔离环境执行并通过，静态检查及审核要求满足，真实环境缺口和提测材料已交接。不能以“环境重”为由省掉可隔离验证。研发入口随后结束，不自动触发或等待测试岗位验收。
按任务执行相关测试和受影响回归；合适节点汇总所需覆盖，避免每次修改重复运行全量。记录耗时，优先复用替身、数据和测试框架，按风险调整高成本用例。

测试工程师独立组织验收，优先使用已有 CI 或共享环境，先验证必要真实依赖兼容性，再检查关键端到端业务旅程及重要失败路径。完整范围仍由需求和风险决定，不能用“小集合”掩盖必要覆盖缺失。QA 可以提前准备用例和脚本，执行仍遵守研发交付和验收阶段条件。
核对数据库／消息／缓存等类型和版本、关键配置与权限、相关协议和多节点边界；只对本次结论需要的一致性作承诺。资源规模与性能可另设专门验证，不以个人电脑完整复刻线上作为开发前提。
mock／隔离环境通过、真实组件通过、真实 E2E 通过分别记录。缺少共享环境时保持相关行为未验证，不要求开发者自行安装全部服务，也不宣布整体验收已完成。

## 用例记录的附加信息

除需求、风险、步骤和预期外，记录执行阶段、环境模式、实际保留组件、替身边界及依据、证据能证明的行为、仍需真实验证的事项。
同时记录负责岗位和目标工程。同一验收条件可关联研发隔离测试与测试岗位真实链路用例，复用业务依据而分别保留执行步骤、边界和结果，不强行共享脚本或 fixture。
测试定义、专业复核和每次实际执行结果分别保存，避免一次通过长期掩盖契约变化。

## 方法参考

- [Software Engineering at Google: Test Doubles](https://abseil.io/resources/swe-book/html/ch13.html)：替身的适用性、保真度与维护成本。
- [Pact: How Pact works](https://docs.pact.io/getting_started/how_pact_works)：消费方模拟及真实提供方验证可分别进行；不是要求安装 Pact。
- [The Twelve-Factor App: Dev/prod parity](https://12factor.net/dev-prod-parity)：关键依赖类型和版本差异的兼容性风险。个人电脑与线上硬件规模是否相同是另一项验证目标。
