## 1. 验收目标与准入链路

```text
Bearer Key与接口能力验证
 → user_account精确匹配毕昇user_name
 → 唯一有效成员关系确定本地租户
 → Key连接下唯一昆联身份绑定及租户映射
 → 权威Key允许的外部租户范围复核
 → 当前目录/投影/用户/成员/租户资格核验，拒绝全局超管
 → 固定本次租户及实际用户权限上下文
 → Workflow业务权限校验
```

重点证明三件事：账号不能匹配错人；请求不能越过租户边界；持有Key不等于拥有资源权限。

公开业务Query仅有身份参数 `user_account`，20条业务接口共用该依赖。`external_tenant_id`/`external_user_id`已删除，传入旧参数也应拒绝。内部可信外部映射、Key的`tenant_ids`范围仍存在；本清单不要求删除内部字段。

## 3. 测试账号、Key与资源矩阵

下列均为别名，执行前填入真实测试标识，不使用示例数字代替实际事实。

| 别名 | 所属/资格 | 用途 |
|---|---|---|
| A-reader | A唯一有效成员；目标W-A只有可见/使用权，无edit/publish/manage_permission | 验证可见不等于可读图/编辑/发布/授权 |
| A-editor | A唯一有效成员；对W-A有明确edit；其他动作单独设定 | 编辑允许、发布/授权独立拒绝 |
| A-manager | A普通用户；对W-A有发布与授权管理资格 | 非管理员的合法管理操作 |
| A-none | A有效账号，但对W-A无资源权限 | 同租户无权拒绝 |
| B-user | B唯一有效成员，对W-B有权 | 双租户正向与反向越权 |
| C-user | C有效映射，但不在Key AB允许范围 | Key范围不得随账号扩大 |
| A-admin | A租户管理员，不是全局超管 | 本租户管理快捷路径仍不能跨租户 |
| Global-super | 有测试映射的全局超管 | 业务代操作必须拒绝；不要用它做允许路径验收 |

Key AB覆盖A/B，Key A仅覆盖A。W-A、W-B、W-C由不同租户拥有。另准备Key Read（仅read）等能力收窄Key，保证“Key缺能力”和“用户缺资源权限”可以分别测试。

## 4. 请求与断言规范

正常读取示例（仅格式，不在本轮执行）：

```http
GET /api/v2/kunlian/workflows?user_account=<毕昇登录账号>
Authorization: Bearer <受限测试Key>
```

- 账号URL编码一次，大小写、字符和首尾空格不自动修正；不加旧租户/用户参数，不混用Cookie或身份头。
- 同时断言HTTP与`status_code/status_message/data`；成功通常业务码200，HTTP按具体接口200/201/202。拒绝路径不能只验“非200”。
- 当前身份解析拒绝通常403/19322；缺失/非法Query为422（原生参数校验与Owner输入拒绝的body可能不同）；无效Key401/26002；目录未就绪409/19321；必要身份依赖不可用503/19324。具体五位码按当前Owner实际合同核对，不能随意固定所有拒绝为一个码。
- 业务无权可能403或为隐藏资源返回404；验收前按目标入口固定期望的HTTP/Owner码，不能把任意400/500视为正确拒绝。
- 所有拒绝均核验无业务副作用、无其他租户内容；必要时通过可信GET、权限Owner或只读数据库佐证，不只看请求响应。

### 5.1 U09展开：旧参数单传与混传拒绝矩阵

使用有效Key、有效账号和正常依赖执行，避免被其他错误掩盖。`OLD_T`、`OLD_U`分别是可信映射中对应的旧外部租户/subject；`OTHER_T`、`OTHER_U`是不同租户/用户标识。下列只展示Query，域名、Key及真实标识不写入报告。

| ID | Query组合 | 预期 |
|---|---|---|
| M00 | `user_account=A-manager` | 正向对照，走当前账号合同；只读接口返回预置可见资源。 |
| M01 | 仅`external_tenant_id=OLD_T`；仅`external_user_id=OLD_U`；两者同时且无user_account（分3例） | HTTP422；缺user_account且旧参数不能替代，不能继续账号或业务解析。 |
| M02 | `user_account=A-manager&external_tenant_id=OLD_T` | HTTP422，即便旧值与真实映射一致，也不能接受兼容别名。 |
| M03 | `user_account=A-manager&external_user_id=OLD_U` | HTTP422，旧subject不得覆盖账号。 |
| M04 | `user_account=A-manager&external_tenant_id=OLD_T&external_user_id=OLD_U` | HTTP422，三项全传也不能按“优先新参数”继续处理。 |
| M05 | M02/M03/M04中的旧值换为`OTHER_T`/`OTHER_U`（逐项及同时） | HTTP422，不切换租户、用户，不依靠旧值冲突才拒绝。 |
| M06 | 新账号配`external_tenant_id=`、`external_user_id=`或两个空值（分3例） | HTTP422；按旧参数出现即拒绝，不因空值当作未提供。 |
| M07 | 新账号配重复旧参数（相同值/不同值），或旧参数放在Query首/尾 | HTTP422；不取first/last，不受顺序影响。 |
| M08 | 重复`user_account`（相同值/不同值）；新账号配旧身份Header | HTTP422；不允许身份输入多来源。 |

参数层非法请求可能由FastAPI返回原生422验证体；已提供合法账号而因旧Query/混合身份被Owner拒绝的情况，当前为HTTP422、业务码19320。分别核验，不要求所有422都具有同一个body；500/200不能算正确拒绝。

**覆盖入口与副作用：**

- 对20条正式业务路由检查OpenAPI：有且仅有必填身份Query `user_account`，无旧两字段；其他业务Query如cursor/version仍可存在。
- 真实HTTP至少覆盖GET列表、POST创建、POST运行启动、POST授权授予/撤销；写请求的Body、路径、修订等均使用本来合法的测试值，确保失败来自旧参数。
- 对M02～M07在每类入口验证准入在账号发现/业务之前拒绝。用受控观测或审计事实证明，不为了取证新增包含秘密的全量日志。
- 写请求拒绝前后核对工作流数、运行记录、权限ledger及目标访问均无业务变更；不把安全日志/失败审计本身视为业务副作用。客户端或代理不得自动重试失败写请求。
- 本矩阵只针对公开Query和身份Header，不能将Key控制面的`tenant_ids`、内部持久映射字段或合法业务载荷同名字段直接当作旧Query处理。

## 6. 第二阶段：租户隔离（AC-02、AC-04、AC-05、AC-14、AC-18）

1. **Key边界**：Key A配B-user、Key AB配C-user，账号/目录/映射均正常也必须拒绝；不得因账号合法而自动扩大`tenant_ids`。
2. **同Key双向测试**：Key AB+A账号访问W-B；Key AB+B账号访问W-A。分别覆盖详情、Schema、版本、保存、选择版本、发布/下线、权限读取/变更与启动。跨租户对象均不可读写，不因Key覆盖两个租户就获得跨租户资源权限。
3. **管理员快捷路径**：用A-admin访问W-B/W-C；必须在管理员放行前拦截目标归属，不能拿租户管理员身份作为全局权限。
4. **嵌套目标一致性**：路径W-A配B的version_id，或创建版本引用B来源版本；拒绝且W-A/W-B原资料均未变。GET返回不得包含B图或内部凭据。
5. **列表与分页**：A/B各有已知可见资源，交替使用同一个连接池/Keep-Alive调用并续页；结果必须限定实际账号租户。A游标不能让B继承可见集；不要只断言总数或空成功。
6. **无请求租户覆盖**：JSON附tenant_id/user_id、旧Query或身份头不能改变对象归属。创建后通过可信读端口核验归属和创建人，不依赖客户端提交值。
7. **异步归属**：A启动拿session_id；B用同Key查询/取消/提交其interaction，必须拒绝。A原身份可继续；Worker记录仍为启动时的实际用户和租户，不取Key所属管理员或默认租户。
8. **异常后复原**：同一进程并发/交替执行A成功、B拒绝、依赖异常，再请求A/B；确保管理员范围、bypass、tenant context和权限主体不串请求。真实并发而非只顺序两个请求。
9. **入口隔离**：昆联Key调用普通开放平台/v1管理拒绝；普通平台Key不能带user_account获得昆联跨租户委托能力。Key控制面仍只允许真实当前全局超管。

## 7. 第三阶段：权限交集（AC-07～AC-10、AC-15～AC-18、AC-20）

| 目标动作 | 允许路径 | 配对拒绝与生效检查 |
|---|---|---|
| 可见列表/详情/Schema | read Key + A-reader，必须读到预置W-A | A-none不可读；Key缺read拒绝；普通详情/列表无编辑图，不能把visible当edit。 |
| 编辑图/保存/版本选择 | 所需Key能力 + A-editor；取revision保存草稿后GET核对 | A-reader无edit拒绝；If-Match缺失/过期409；错误flow/version拒绝；ONLINE直接编辑保护；脱敏GET→PUT不清空SQL秘密。 |
| 创建 | write Key + 有create_workflow/create_app资格的普通用户或本租户管理员，且配额允许 | 无创建资格或配额不足拒绝；固定Workflow类型；服务端真实归属正确，不遗留可用半成品。 |
| 发布/下线 | publish Key + 有对应业务权限的A-manager；发布有效版本后Schema/调用可用 | A-editor没有独立publish/unpublish时拒绝；旧版下线不能下线新版本；失败不形成部分发布。 |
| 运行 | invoke Key + 有use权限的普通用户；轮询真实结果 | 有read但无use、缺invoke Key均拒绝；未支持协议受理前拒绝；不能用管理员替代普通用户验证。 |
| 授权 | grant Key + 有manage_permission的A-manager，目标为同租户有效用户 | A-editor无manage_permission拒绝；Key有grant不替用户提权；跨租户/受保护/继承来源不可改。 |

### 授权闭环

- 操作人使用`user_account`；Body `subject_ref`仍是目标昆联OIDC sub，字段没有随操作人Query改为账号。
- 查询当前可授予模型和修订，以原修订提交一次授权；PENDING使用202，不当作最终生效。由平台凭operation_ref核对投影最终状态，再以目标普通用户实际访问W-A验证权限已生效。
- 以陈旧修订提交变更应冲突，授权来源和现有访问不被覆盖。撤销可编辑直接来源后，再验证目标有效权限；如果还有独立组/继承来源，应仍按其有效授权可用，不能误认“撤销未生效”。
- 全局超管可管理Key，但即使有昆联映射也不能作为user_account业务代操作人。租户管理员可以被代表，但仅在当前可信租户内操作。

### 7.1 操作人账号与授权目标subject_ref专项矩阵

执行前额外准备两个**不同用户**：操作人O与目标T。记录O的毕昇登录账号、user_id及权限；记录T的毕昇登录账号、OIDC sub、member_id和user_id。确保T的登录账号、显示名、sub与member_id互不相同，且T账号字符串不是任何有效目标的sub，避免意外字符串重合使负例失去意义。另准备B租户目标与无授权管理资格的操作人N。

| 字段 | 位置 | 当前解释 | 禁止误解 |
|---|---|---|---|
| `user_account` | 所有业务请求Query | 操作人的毕昇登录账号，决定实际授权主体、权限判断和审计操作人 | 不是被授权目标；不能因目标有权限就给操作人提权 |
| `subject_ref` | 仅授予权限JSON Body | 被授权目标的昆联OIDC sub，在操作人解析出的同一可信外部租户与连接内查找 | 不是毕昇登录账号、显示姓名、user_id或member_id，不覆盖Query操作人 |
| `assignee_id` | 撤销权限路径 | 待撤销的直接授权记录ID，取自权限查询结果 | 不是目标账号或用户ID；撤销JSON不使用subject_ref |

| ID | 操作步骤 | 预期与取证 |
|---|---|---|
| S01 | Query为O账号，Body为T的sub，以O的当前资源/目录修订提交一次合法授权 | 校验的是O的manage_permission；授权目标解析为T，审计操作人是O而非T。投影确认后以T账号实际访问验证，O与其他人权限不因身份混淆改变。 |
| S02 | Query仍为O，Body分别换为T登录账号、显示名、member_id、本地数字user_id的字符串（分4例） | 在事先排除这些字符串是有效sub的前提下拒绝，不回退账号查找或自动猜字段；T原授权与实际访问不变。业务拒绝可403/404或Owner身份分类，须固定实际预期码，不能接受500。 |
| S03 | Query填O的sub而非O登录账号，Body为有效T sub | 若该sub不是任何有效登录账号，应在操作人解析阶段拒绝；不能把目标解析成功当作操作人准入。 |
| S04 | Query为无manage_permission的N账号，Body为有管理权限用户的sub | 拒绝；目标用户的管理员/管理资格不能借给操作人，Key有grant也不能兜底放行。 |
| S05 | Query为有权O账号，Body为B租户目标sub，Key覆盖A/B | 不得授予B用户。当前目标解析仅在O所属租户内；若相同sub在A也合法存在，只能解析为A的那个身份，不能靠sub跨租户选B。执行前记录完整连接/租户/sub映射，避免把同sub误判成必拒条件。 |
| S06 | Query为O，Body缺subject_ref；或者把subject_ref只放Query | HTTP422（缺Body必填字段），不得从Query补齐目标；Body错误新增user_account也不能替代操作人Query。 |
| S07 | Query为O，Body附external_tenant_id/external_user_id等未声明字段，试图指定目标租户/身份 | 严格DTO拒绝HTTP422，无权限变更。此为授权Body额外字段检查，不替代M02～M07的旧Query混传检查。 |
| S08 | O授予T后读取授权列表取得assignee_id，再由O按该记录及当前修订撤销 | 只撤该直接授权记录；审计操作人仍为O，目标仍为T；验证独立组/继承来源保留。把T账号/sub当作assignee_id不能被解释成撤销用户全部权限。 |

所有授权写入均需单独执行授权；PENDING只表示待确认，不立即断言T已获权限。平台凭operation_ref及真实F048投影核对后取证，**不盲目重复提交相同HTTP**（已移除客户端幂等键）。每例记录O/T的脱敏别名、预期本地ID、目标记录和实际访问结果；不得只记录“授权返回200/202”。撤销/拒绝路径均检查其他用户、其他租户与受保护来源未改变。

## 8. 第四阶段：资格变化、异步与故障（AC-11～AC-14、AC-17、AC-21、AC-22）

仅在专用测试运行中执行：

- 用户停用/成员失效/租户禁用/资源use撤销后，HTTP后续操作与Worker领取/恢复/节点推进不得新放行；不只测试首次入口。
- 对排队、WAITING_INPUT和运行中三个状态分别测试；运行中节点尽力停止，已发生外部副作用不能虚假报回滚。记录“变更提交、下一次边界校验、最终状态”的时间与策略版本，不在文档承诺未经测量的即时毫秒窗口。
- 账号改名/账号被重新分配后，不允许新的本地用户借相同字符串接管原session；原运行绑定持久user_id/tenant/接入方，身份和映射发生变化时按当前资格拒绝或重新核验。
- Key撤销/范围收缩后拒绝新业务；正常轮换新Key在同接入方、同用户/租户与当前能力允许时可查/取消旧run，但旧Key撤销后其等待运行不能恢复，不复活终态。
- Redis限流、目录资格或权限依赖不可确认时失败关闭，不回退默认用户、超管或Mock成功。权限依赖故障应按不可用分类，不应当成允许或伪成功空列表。
- 验证真实Broker断线、Worker进程退出和15秒有界补偿：仅处理正式运行，消息没有Key明文；重复内部任务不二次执行，重复HTTP不承诺去重。
- 验证MySQL/DM8用户行锁跨workflow活跃上限默认5与修订并发；请求限流120/60和活跃配额是不同控制，不能互相替代。
- 审计意图写失败时不执行业务；完成写失败保留INTENT并告警，不能据此推导未执行。过期终态payload清理不删除归属/内部操作摘要，不误清候选运行。

## 9. 执行顺序、取证与通过门槛

### 建议顺序

前置签认 → 只读路由/账号/目录/权限基线核对 → U01/U02/U09/U10 → 全部账号拒绝场景 → Key与资源双向租户隔离 → 普通用户权限矩阵 → 获准测试资源写入闭环 → 动态撤权/故障/双库并发 → 恢复与清理。

前阶段发现身份错人、默认租户回退、跨租户可见或权限绕过时立即停止后续写测试，保留证据，不用继续“跑完用例”掩盖安全失败。

### 每例证据模板

| 字段 | 填写要求 |
|---|---|
| 用例/AC | Uxx或阶段步骤与对应AC |
| 环境 | Origin、构建摘要、Python/数据库/权限Catalog版本 |
| 受信输入 | Key别名与credential_id（不含明文）、账号别名、预期内部user/tenant及目标ID |
| 请求 | HTTP方法、服务端路径模板、参数类型；不附秘密/敏感输入 |
| 结果 | HTTP、业务码、安全原因、脱敏响应、trace/session/operation_ref |
| 副作用核对 | 可信GET/只读事实或目标普通用户实际访问结果 |
| 判定 | PASS / FAIL / NOT_RUN及原因，恢复结果与执行人 |

### 必须满足

- 所有关键身份、租户和权限场景都有允许/拒绝配对证据；拒绝无业务副作用、无敏感数据泄露。
- 至少一个普通用户完成真实创建—保存—发布—运行闭环，至少一个授权变更经真实FGA投影后以目标用户实际访问确认。
- A→B和B→A双向越权均拒绝；租户管理员不能越界；全局超管代操作拒绝。
- MySQL/DM8分别验证精确账号比较与真实事务/锁语义；未执行项目标NOT_RUN，整体至多PARTIAL，不能合并为全部PASS。
- Python3.11、完整main中间件、独立Worker/Broker/Beat及真实映射必须有证据。本地Python3.14/SQLite/mocked端口不替代。

## 10. 恢复与收尾

- 恢复本次测试账号状态、成员资格、授权及测试实例依赖，核验恢复后当前资格；不能顺手恢复已撤销的独立人工授权。
- 撤销本次测试Key并验证失效。只清理明确记录的测试前缀和资源ID，既有接口未开放删除时由获准平台管理流程处理，禁止无条件SQL删除。
- 授权持续PENDING按原operation_ref核对F048 ledger；本轮无通用自动修复端点，不能换新HTTP请求盲写或直接改OpenFGA。
- INTENT未完成按trace和实际业务结果核对，不以缺FINISHED认定业务未执行。
- 与基线比对非测试资源、权限及数据未变化；归档脱敏结果，撤除临时故障与测试访问资格。
