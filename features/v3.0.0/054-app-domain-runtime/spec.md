> **范围边界**
>
> 本 Feature 是批次 B 的地基：定义「托管应用」这个领域对象、把它注册进平台权限体系、提供 compose 单机形态的运行时与统一入口，并交付 platform 构建页的第三种类型与应用详情页壳。发布管线 / 审批 / 版本写入（F055）、广场与治理面（F056）、k8s 形态（F059）站在它上面。**技术选型（容器加固手段、嵌入式数据库、构建模板、代理算法）一律在 design.md，本 spec 只写对外可观测的承诺。**
>
> - **本次纳入**：
>   - **托管应用领域模型**：App（应用标识、名称 / 描述 / 图标、owner、租户、类型 = 托管应用、应用态）、AppVersion（只增不改的版本记录：版本号、类型首发 / 迭代、提交时间、终态标注、代码快照引用、能力声明、注入配置、资源档位——**四者同属一个快照**）、AppInstance（运行实例：状态、健康、当前运行版本、执行体引用）；**应用态状态机**（草稿 / 已上线 / 待上线（资源不足）/ 已下线 / 已删除，PRD-1 §3.0.2）及其**五个状态动作**：上线（含结果分支：成功 → 已上线 / 容量不足 → 待上线）、手动上线、下线、重新上线、删除——审批单态由 F055 拥有，F055 的管线在相应节点**调用**本 Feature 的状态动作
>   - **GOV-01 `app` 资源类型注册**：托管应用作为平台权限体系（F048 ReBAC）的一种资源类型；创建即 owner；可见范围按用户 / 部门 / 用户组授予；租户管理员因身份短路对本租户全部应用天然可见可管；**存量环境**（如 114）上新增资源类型的生效手段
>   - **运行时（compose 单机形态）**：编排能力由独立于平台后端进程、可单独启停的运行时服务承担，平台后端进程不持有编排后端的访问凭据；对外能力：按应用包与 `runtime` 取值构建可运行镜像（开发者与 AI 不提供 Dockerfile）、启动 / 停止 / 重启 / 销毁实例、查询状态与健康、读取运行日志、**启动探活**（供 F055 托管预检、上线终检、审批期临时预览实例复用）、**运行环境容量准入**（供 F055 上线终检与本 Feature 重新上线消费）；实例按资源档位受 CPU / 内存上限约束、文件系统除平台指定的可写路径外只读、不可提权、网络受控、崩溃自动重启、进程存活但不健康时自动重建；**出站白名单**（运行期默认封禁一切出站，只放行平台 API 与应用包声明的域名；构建期只放行平台配置的包源）；单应用单实例
>   - **统一入口 app-proxy**：`/apps/{应用标识}` 唯一入口，版本无关；复用平台既有登录方式——已登录 + 在可见范围内 → 免二次登录进入；无登录态 → 重定向平台登录页、登录后回跳原地址（含 query 与 hash）；已登录无权限 → 统一「无权限」页；已下线 → 「已下线」页；已删除 / 从未上线 → 「应用不存在或未上线」页；未部署工场运行时层 → 引导页；**注入当前访问者身份与组织信息**（客户端伪造的身份头一律无效）+ 请求级短时访问凭据的注入通道（能力范围语义由 F055 定义）；反代 HTTP 与 WebSocket；应用容器不可绕过入口直连；发布切换与崩溃恢复窗口内不落报错页（「发布中」「应用恢复中」过渡态）；**审批期临时预览实例的访问入口**（仅审批人可达、注入审批人身份，实例生命周期由 F055 控制）；**访问记录留痕**（谁在用：用户 / 应用 / 时间，供 F056 审计面）
>   - **RT-07 资产持久与生命周期动作**：代码快照、每应用数据库、附件的真身恒在平台存储、运行实例只是可回收执行体；下线 / 重新上线（owner 或租户管理员，平台超管经租户管理视图代行、审计记超管本人；重新上线叠加容量准入）；**显式删除**（仅 owner；前置状态闸：已上线态入口置灰须先下线；二次确认不要求输入应用名、文案明示删除范围含代码 / 对话 / 应用生产数据；资产删除、入口链接与二维码呈「不存在」页；删除时通知 F055 取消在途审批单）；存档随平台数据备份
>   - **RT-08 稳定性**：应用与平台、应用与应用运行隔离；单应用崩溃或资源触顶只影响自身并在 5 分钟内自动恢复；运行时服务重启不影响已运行应用；两个过渡态不落报错页
>   - **每应用数据库与附件供给**：每个应用一个平台供给的专属数据库，经与本地 `bisheng dev` **同名**的连接环境变量注入、标准库可读写、可备份可快照；附件存储由平台中介、按应用收窄、不进公共可读存储、不计租户存储配额；两者的 SDK 面随 F057
>   - **platform 构建页与应用详情页壳**（§3.0.1）：构建 → 应用列表的类型筛选新增第三项「托管应用」；卡片（图标 / 名称 / 描述 / 创建用户 / 类型角标 / 应用态徽标 / 版本下拉〔只读〕/ 上下线开关 = 下线 · 重新上线）；状态筛选覆盖应用态五值；卡片 ⚙️ 菜单对托管应用只出现「管理权限」与「删除」（**裁剪由本 Feature 实现**，因它是新类型卡片的一部分；F056 承接 GOV-01 验收 6 的回归验证）；owner「我的应用列表」= 同一页按归属过滤视图；**应用详情页四 tab 壳**：发布（本 Feature 只保证 tab 存在 + 应用态徽标 + 入口链接与二维码；其余区块由 F055 填充、可见范围区由 F056 填充）· 数据（**WB-06 最小形态：应用自有数据的查看、编辑与导出**，编辑生产行需二次确认并计审计；导入随 PRD-2）· 运行日志（**WB-13**：只读运行日志）· 版本（列表由 F055 填充）；无左侧对话区、无管家；**本册不提供托管应用的界面新建入口**（唯一创建路径 = CLI 首发；界面新建随 PRD-2 WB-01）
>   - **GOV-10 工场运行时层部署开关**：整层可不装——未部署时构建页不出现「托管应用」类型、广场不出现托管应用（F056 消费同一开关）、`/apps/*` 呈统一引导页而非报错、平台其余功能零变化、无新增常驻负担；已部署 compose 形态时上述能力全部生效

## 1. 用户故事

作为 **普通业务用户**，
我希望 **在应用广场点开同事做的托管应用就能直接用、不用再登录一次，且它自动知道我是谁、我在哪个部门**，
以便 **像用平台里其它功能一样用它，不必为每个小应用记一套账号**。

作为 **开发者（owner）**，
我希望 **我的应用一旦上线就有一个长期不变的入口地址与二维码，代码和数据的真身在平台上、容器坏了会自己恢复，我需要时能一键下线、退役时能显式删除**，
以便 **放心把它发给同事，出问题时有可控的止血与退出路径**。

作为 **平台管理员 / IT**，
我希望 **每个托管应用都跑在资源受限、网络受控、与平台和其它应用隔离的执行体里，任何单个应用崩溃都不影响平台与其它应用；不需要工场的环境可以整层不装**，
以便 **在单机上安全地承载业务人员与开发者造出来的应用，同时不给不需要它的客户增加负担**。

作为 **租户管理员**，
我希望 **在构建 → 应用里像看工作流、助手一样看到本租户全部托管应用，能下线 / 重新上线、能进详情看日志与数据**，
以便 **治理面前本地造的与平台造的应用无差别**。

## 2. 验收标准

> AC 编号在本特性内唯一。括号内标注对应 PRD-1 条目与验收序号（如 `↔RT-01 验收 1`）；与 F055 / F056 存在调用关系的条目注明「F0xx 调用 / 承接」。错误码仅作可观测行为引用，定义在 design.md。

### 2.1 领域模型与应用态状态机

- **AC-01** — THE SYSTEM SHALL 把托管应用作为与工作流 / 助手并列的独立应用类型持久化，每个应用具有**全局唯一**且**首发时确定、此后不变**的应用标识（入口地址与二维码据此生成）、名称 / 描述 / 图标、owner、所属租户与应用态。（↔§1.0 / RT-01 规则「入口地址不随版本变化」）
- **AC-02** — THE SYSTEM SHALL 使版本记录**只增不改**：每条含版本号、类型（首发 / 迭代）、提交时间、终态标注（已上线 / 被驳回 / 已撤回）、代码快照引用、能力声明、注入配置、资源档位；四者同属一个快照，任何写入方（F055）不得只改其中之一。（↔RT-05 需求描述）
- **AC-03** — THE SYSTEM SHALL 使应用态只在下列取值中流转：草稿 → 已上线（上线动作成功）；已上线 ↔ 已下线（下线 / 重新上线）；上线动作遇容量不足 → 待上线（资源不足）→（手动上线成功）已上线；草稿 / 待上线 / 已下线 → 已删除（终态）；**已上线不得直接进入已删除**。（↔§3.0.2）
- **AC-04** — WHILE 应用处于已下线态, THE SYSTEM SHALL 允许 F055 落新的待运行版本但**不自动重新上线**；重新上线后新版本生效。（↔§3.0.2 / RT-07 验收 6；F055 AC-36 为管线侧调用）
- **AC-05** — THE SYSTEM SHALL 使迭代审批被驳回不改变应用「已上线」态：当前版本继续运行，仅待上线版本标记为被驳回。（↔§3.0.2；F055 AC-33 为管线侧调用）
- **AC-06** — WHEN 应用元信息（名称 / 描述 / 图标）被更新, THE SYSTEM SHALL 不改变应用态、不产生版本记录，并记审计。（↔RT-02 规则「元信息不属能力声明」）
- **AC-07** — THE SYSTEM SHALL 使每个应用有且只有一个 owner（自然人）；CLI 首发应用的 owner 取值 = 该密钥所属服务账号的资源归属人（取值由 F055 AC-04 在首发管线中写入，本 Feature 只保证 owner 是唯一归属字段且不因归属人后续变更而追溯改变）。（↔DEV-04 规则；F049 定义 6 边界 d）
- **AC-08** — THE SYSTEM SHALL 使应用标识来自应用包声明（未声明时由平台按名称生成），全局唯一；首发时若与任一租户内既有标识冲突 → 拒绝首发并提示更换标识；名称可重复且可修改、修改不影响标识。（↔RT-01 规则 / DEV-04「发布输入以应用包为准」）

### 2.2 权限资源类型（GOV-01 注册部分）

- **AC-09** — THE SYSTEM SHALL 把托管应用注册为平台权限体系的一种资源类型：可对用户 / 部门 / 用户组授予可见范围；创建即 owner；租户管理员对本租户任一应用可查看并调整可见范围（既有身份短路，非本 Feature 新增）。（↔GOV-01 需求描述 / 验收 4）
- **AC-10** — WHEN 可见范围变更, THE SYSTEM SHALL 自被授权用户的**下一次请求**起生效于入口访问与广场可见性；不经审批、不进版本快照、计审计并记录变更人。（↔GOV-01 验收 2 / 5；授权交互面由 F056 承接）
- **AC-11** — THE SYSTEM SHALL 使首发上线后默认**仅 owner 可见**，直到 owner 或租户管理员设置可见范围。（↔GOV-01 规则）
- **AC-12** — IF 权限引擎不可用或评估失败, THEN THE SYSTEM SHALL 拒绝入口访问并返回明确错误页，绝不放行（INV-19 / INV-30 同向）。
- **AC-13** — WHEN 在已有权限模型的存量环境（如 114）升级部署, THE SYSTEM SHALL 提供使 `app` 资源类型在该环境**生效**的运维手段（升级说明中列明步骤），且不影响既有资源类型的授权数据。（Discovery §5 风险 1）

### 2.3 运行时编排（compose 单机形态）

- **AC-14** — THE SYSTEM SHALL 使平台后端进程不持有任何编排后端的访问凭据（部署检查可核验），编排能力由一个可独立启停的运行时服务承担；平台后端只向其声明期望态并读取结果。（↔产品方案 §4.5 编排特权 / GOV-10 需求描述）
- **AC-15** — WHEN 收到构建请求（应用包 + `runtime` 取值）, THE SYSTEM SHALL 在支持的取值集合（`python3.11` / `node20` / `static`）内构建可运行镜像，开发者与 AI 不提供 Dockerfile；`runtime` 取值不在集合内 → 拒绝并列出支持的取值；依赖安装或构建失败 → 返回可读的失败原因与失败阶段（供 F055 预检输出）。（↔DEV-04 托管运行契约「语言运行时」/ 流程①）
- **AC-16** — WHILE 构建期, THE SYSTEM SHALL 只放行平台配置的包源与平台自身的分发端点（供安装 bisheng-sdk 等平台发布件）；WHILE 运行期, THE SYSTEM SHALL 默认封禁一切出站，只放行平台 API 与应用包声明的域名，其余出站连接（含直连 IP、UDP）一律被阻断。（↔DEV-04 契约「白名单外的外网地址」）
- **AC-17** — WHEN 启动实例, THE SYSTEM SHALL 按所选资源档位设置 CPU / 内存上限；应用只能写平台指定的可写路径（临时目录与数据目录）、其余文件系统只读；应用进程不得提权；注入平台约定的环境变量（应用数据库连接、附件存储访问句柄、应用标识等）；实例不暴露可被 app-proxy 之外访问的端口。（↔GOV-03 验收 4 / 产品方案 §4.5 默认档 / DEV-04 契约）
- **AC-18** — THE SYSTEM SHALL 提供**启动探活**：拉起后在配置的超时内探测应用就绪；未就绪 → 判定失败并返回可读原因（供 F055 托管预检、上线终检、审批期临时预览实例复用）。（↔DEV-04 预检①）
- **AC-19** — THE SYSTEM SHALL 提供**运行环境容量准入**判定：拉起 / 重新上线前判定本机可用资源能否承载所选档位；不足 → 返回「容量不足」而非拉起失败；判定结果供上线动作（AC-65）与 F055 上线终检消费。（↔GOV-03 规则 / §3.0.2 待上线态）
- **AC-20** — WHEN 应用进程退出, THE SYSTEM SHALL 自动重启该实例；WHEN 实例进程存活但健康检查持续失败, THE SYSTEM SHALL 在检测窗口内重建该实例；两者合计使单应用在无人干预下 **5 分钟内**恢复可用。（↔RT-08 验收 2 / NFR-6）
- **AC-21** — WHEN 新版本上线切换, THE SYSTEM SHALL 先拉起新实例并通过启动探活，再把入口切到新实例，旧实例宽限退休；切换窗口内访问入口得到「发布中」提示而非报错页。（↔RT-08 验收 3）
- **AC-22** — IF 运行时服务进程重启或短暂不可用, THEN THE SYSTEM SHALL 保持已运行应用继续对外服务。（↔RT-08 / 产品方案 §4.5）
- **AC-23** — THE SYSTEM SHALL 提供实例状态、健康、当前运行版本与运行日志的只读读取接口，以及**运行环境状态**（容量、编排后端可用性、部署前置自检结果——k8s 形态由 F059 扩充探测项）的只读接口（平台超管可查，两形态同一接口），供应用详情页运行日志 tab、CLI `logs`（F053）与 MCP 应用状态 / 日志工具（F052）消费；三处取到的**内容范围一致**，权限判定各按其入口口径（详情页：owner 与本租户租户管理员；MCP / CLI：仅密钥归属人 owner 的应用）。（↔DEV-04 验收 12 / DEV-02 ③）
- **AC-24** — THE SYSTEM SHALL 使单应用单实例：不提供实例数与并发调节入口。（↔GOV-03 验收 1 / §5.1）

### 2.4 统一入口与身份注入（app-proxy）

- **AC-25** — THE SYSTEM SHALL 使每个已上线应用可经 `/apps/{应用标识}` 访问，该地址在迭代发布、下线 / 重新上线后保持不变；应用内相对路径与 WebSocket 均经该入口正常工作——WHEN 浏览器导航到**不带尾斜杠**的应用根路径 `/apps/{应用标识}`, THE SYSTEM SHALL 先永久重定向到带尾斜杠的形式再呈现应用文档，使应用产出的相对引用（`./assets/x.js`）以应用自身为基准解析。（↔RT-01 需求描述 / 规则；**2026-08-18 原号改写**：原文只要求「相对路径正常工作」而未写出达成它的必要条件，实现遂漏掉尾斜杠、托管应用白屏，见 §3 边界情况「应用根路径的尾斜杠」）
- **AC-26** — WHEN 已登录平台且在可见范围内的用户访问入口, THE SYSTEM SHALL 免二次登录直接进入应用。（↔RT-01 验收 1）
- **AC-27** — WHEN 无登录态的浏览器（含手机扫码）访问入口, THE SYSTEM SHALL 重定向到平台登录页（含平台已配置的 SSO 方式），登录成功后回跳原应用地址（含 query 与 hash）。（↔RT-01 验收 3）
- **AC-28** — WHEN 已登录但不在可见范围内的用户访问入口, THE SYSTEM SHALL 返回统一「无权限」页：含应用名与 owner、无访问权限文案、引导联系应用 owner 或租户管理员开通权限、「返回广场」按钮；本版无在线申请入口。（↔RT-01 验收 4）
- **AC-29** — WHEN 在可见范围内的用户访问已下线应用的入口, THE SYSTEM SHALL 返回「已下线」页（应用名 + 已下线提示 + 引导联系 owner 或租户管理员 + 返回广场）；WHEN 任何用户访问已删除应用的存量链接 / 二维码或从未上线（草稿 / 待上线）应用的入口, THE SYSTEM SHALL 返回「应用不存在或未上线」页 + 返回广场按钮；两者均不落报错页。（↔RT-01 兜底页表 / 验收 5）
- **AC-30** — WHERE 工场运行时层未部署, THE SYSTEM SHALL 对任何 `/apps/*` 访问（无论登录与否）返回「本环境未启用应用工场」引导页（引导联系平台超管），不返回 404 / 5xx。（↔RT-01 兜底页 / GOV-10 验收 2）
- **AC-31** — WHEN 请求被转发到应用, THE SYSTEM SHALL 注入当前访问者的身份与组织信息（用户标识、姓名、主部门、主体类型〔自然人 / 服务账号〕等平台约定字段）；应用内可据此显示当前访问者姓名 / 部门。（↔RT-01 验收 2 / DEV-05）
- **AC-32** — THE SYSTEM SHALL 在转发前使客户端携带的任何平台身份注入头无效——包括其下划线 / 连字符 / 大小写变体；伪造头对应用无效。（↔NFR-1.3）
- **AC-33** — THE SYSTEM SHALL 使应用容器仅经 app-proxy 可达；绕过入口直连不可行。（↔产品方案 §4.5 不变量①）
- **AC-34** — THE SYSTEM SHALL 在转发前为请求注入一个短时、与访问用户绑定、不可由客户端伪造的访问凭据句柄，供应用经平台能力总线 / SDK 以当前访问用户身份调用平台能力；它是会话级瞬时令牌（不持久化、不出现在任何界面），不属 INV-28 所指的密钥类凭据；其能力范围（能力声明 ∩ 用户权限）由 F055 定义。（↔产品方案 §4.5 OBO；GOV-05）
- **AC-35** — WHEN 通过入口建立 WebSocket 长连接, THE SYSTEM SHALL 在握手时确定该连接的授权有效期（不长于访问凭据寿命与全局最大连接时长），到期主动关闭；应用下线、可见范围撤销时主动断开该用户的连接。（↔产品方案 §4.5 不变量②）
- **AC-36** — WHEN 应用处于崩溃恢复窗口, THE SYSTEM SHALL 对入口访问返回「应用恢复中」提示而非报错页，恢复后自动恢复正常访问。（↔RT-08 验收 4）
- **AC-37** — THE SYSTEM SHALL 为审批期临时预览实例提供独立于 `/apps/{slug}` 的访问入口：仅该审批单的审批人可达（其他人得到无权限页），注入审批人本人身份，其余注入与转发规则同正式入口；实例的拉起 / 回收由 F055 控制。（↔RT-03 预览试用 / 验收 7–8；F055 AC-26–28 调用）
- **AC-38** — WHEN 用户经入口成功进入某应用, THE SYSTEM SHALL 留痕一条访问记录（访问用户、应用、时间），供 F056 审计查询面按对象应用可查；不记录请求级明细。（↔GOV-04 事件清单「访问记录」；F056 承接查询面）

### 2.5 资产持久与生命周期动作（RT-07）

- **AC-39** — THE SYSTEM SHALL 使代码快照、每应用数据库、附件的真身恒在平台存储；运行实例自身不保存任何唯一数据；实例回收 / 崩溃 / 重建后应用数据完整无损。（↔RT-07 验收 1）
- **AC-40** — THE SYSTEM SHALL 使除 owner 显式删除流程外不存在任何导致应用资产被删的操作路径（下线、闲置回收、实例崩溃、工场运行时层整体不部署均只回收执行体）。（↔RT-07 验收 2 / NFR-3）
- **AC-41** — WHEN owner 或租户管理员执行下线, THE SYSTEM SHALL 要求二次确认（明示入口与广场将呈已下线）、回收执行体、应用态置已下线、入口与广场呈已下线页、计审计；WHEN 执行重新上线, THE SYSTEM SHALL 先做容量准入（AC-19），通过后拉起当前版本并恢复访问、计审计，不足则保持已下线并提示成因；平台超管经租户管理视图可代行两者，审计记超管本人。（↔RT-07 操作表 / 验收 4；§3.3 矩阵注）
- **AC-42** — IF 应用处于已上线态, THEN THE SYSTEM SHALL 使删除入口置灰并提示「请先下线」（卡片 ⚙️ 菜单与详情页危险操作区同此）；草稿、待上线、已下线态可直接删除。（↔RT-07 验收 3；F055 发布面危险操作区调用本状态闸）
- **AC-43** — WHEN owner 执行删除, THE SYSTEM SHALL 弹出二次确认（**不要求输入应用名**），文案明示将一并删除代码、对话历史与应用生产数据；确认后删除资产、应用态置已删除、存量入口链接与二维码呈「不存在」页、通知 F055 取消在途审批单、计审计。（↔RT-07 验收 3 / 5）
- **AC-44** — IF 非 owner（含租户管理员、平台超管）发起删除, THEN THE SYSTEM SHALL 拒绝；管理侧处置手段仅下线。该限制为业务规则前置拦截，不受权限运行时的管理员短路影响。（↔RT-07 验收 5 / §3.3 矩阵注）
- **AC-45** — THE SYSTEM SHALL 使存档随平台数据一同备份（备份手册列出应用存档位置）；THE SYSTEM SHALL 为每个应用供给一个专属数据库并以与本地 `bisheng dev` **同名**的连接环境变量注入，应用用标准数据库库即可读写，该库可随存档快照与备份；THE SYSTEM SHALL 为每个应用提供按应用收窄的附件存储句柄（支持上传 / 下载 / 列举 / 删除四操作、按应用隔离、越界访问拒绝、单文件大小上限为部署配置项；不进公共可读存储、不计租户存储配额），SDK storage（F057）与本地 `bisheng dev` 期以同名句柄同一 API 使用。（↔RT-07 规则 / DEV-05 ③ / DEV-07 / GOV-03 规则）

### 2.6 稳定性（RT-08）

- **AC-46** — WHEN 人为使某应用崩溃, THE SYSTEM SHALL 保持平台主功能与其他应用访问正常。（↔RT-08 验收 1）
- **AC-47** — WHEN 某应用耗尽其 CPU / 内存上限, THE SYSTEM SHALL 只限制或重启该应用自身，平台与其他应用不受影响。（↔RT-08 需求描述「运行隔离」/ GOV-03 验收 4）
- **AC-48** — WHILE 入口呈「发布中」或「应用恢复中」过渡态, THE SYSTEM SHALL 使页面自动重试并在实例就绪后自动进入应用，用户无需手动刷新。（↔RT-08 过渡态表）
- **AC-49** — THE SYSTEM SHALL 使本节稳定性验收用例（AC-46–48、AC-20–22）不含任何 compose 形态专有步骤，可原样在 k8s 形态执行（F059 复用同一用例；候选 INV-33）。（↔RT-08 规则 / §1.3 前提 4）
- **AC-50** — WHEN 运行时服务恢复运行, THE SYSTEM SHALL 在部署配置的对齐窗口内自动对齐期望态（重建缺失或不健康的实例），无需人工干预。（↔RT-08 / 产品方案 §4.5）

### 2.7 构建页与应用详情页壳（§3.0.1 / WB-13 / WB-06）

- **AC-51** — WHERE 工场运行时层已部署, THE SYSTEM SHALL 在 platform 构建 → 应用列表的类型筛选中新增「托管应用」项（与「工作流」「助手」并列）；托管应用卡片显示图标 / 名称 / 描述 / 创建用户 / 类型角标 / 应用态徽标 / 版本下拉 / 上下线开关；状态筛选覆盖应用态五值（含「待上线（资源不足）」）；复用既有搜索与标签筛选。（↔§3.0.1 / §3.0.2 引言 / §3.0.3 待上线态自查落点）
  - **2026-08-18 收窄「应用态徽标」**：徽标只在**上下线开关表达不了的两个态**（草稿 / 待上线（资源不足））出现，已上线与已下线不再出徽标——同一张卡上开关已经说了一遍，第二遍是噪声。待上线（资源不足）尤其不能省：它是「开关是关的，但要手动上线才动得了」的唯一提示。状态筛选与详情页的应用态展示不受影响。
- **AC-52** — THE SYSTEM SHALL 使托管应用卡片的上下线开关语义 = 下线 / 重新上线（AC-41）；版本下拉只读展示当前运行版本与历史版本、不提供切换与回滚。（↔RT-05 验收 4）
- **AC-53** — THE SYSTEM SHALL 使托管应用卡片 ⚙️ 菜单只出现「管理权限」与「删除」两项，「创建模板」「复制」不出现；「管理权限」拉起平台通用授权弹窗；「删除」受 AC-42 前置状态闸约束且仅 owner 可见（F056 承接 GOV-01 验收 6 的回归验证）。（↔GOV-01 ⚙️ 裁剪注）
- **AC-54** — WHEN 点击托管应用卡片, THE SYSTEM SHALL 进入应用详情页，含四个 tab：发布 · 数据 · 运行日志 · 版本；无左侧对话区、无管家；发布 tab 由本 Feature 保证存在并呈现应用态徽标、入口链接与二维码，其余区块由 F055（管线相关）与 F056（可见范围区）填充；版本 tab 列表由 F055 填充。（↔§3.0.1 / §1 分册说明）
- **AC-55** — THE SYSTEM SHALL 在「运行日志」tab 提供只读运行日志（应用运行输出与错误信息含错误栈；不含平台侧日志；不出现密钥值；可按时间范围查看、支持刷新与关键字筛选、有空态说明）；owner 与本租户租户管理员可看，其他用户不可访问该 tab 与其接口（业务规则前置拦截）。（↔WB-13 / DEV-02 ③ 例外 / NFR-2）
- **AC-56** — THE SYSTEM SHALL 在「数据」tab 提供应用自有数据表的查看、编辑与导出（表清单 → 分页查看 → 单行编辑 → 导出）；编辑生产行需二次确认并计审计；导入随 PRD-2；仅 owner 可访问（业务规则前置拦截）。支撑该 tab 的**每应用数据库服务端接口**（表清单 / 表结构 / 行数据读写，不含 DDL——表结构由应用包声明、平台建表）由本 Feature 提供，并供 F052 MCP 应用数据工具复用（同一 owner 收窄、写入同样计审计）。（↔§1 WB-06「查改导出」/ GOV-04 事件清单「生产数据行编辑」/ DEV-02 应用数据工具）
- **AC-57** — THE SYSTEM SHALL 使 owner 在构建 → 应用列表看到自己 owner 的托管应用（「我的应用列表」= 同页按归属过滤视图）；租户管理员看到本租户全部托管应用。（↔§3.0.1）
- **AC-58** — WHERE 工场运行时层未部署, THE SYSTEM SHALL 使构建页不出现「托管应用」类型与任何托管应用卡片；升级前后角色配置面的菜单项与权限点数量不变（零新增菜单 / 权限点）；本册任何形态下均不提供托管应用的界面新建入口。（↔GOV-10 规则 / GOV-07 验收 4）

### 2.8 可选部署（GOV-10 工场运行时层）

- **AC-59** — WHERE 工场运行时层未部署, THE SYSTEM SHALL 使平台既有功能回归测试全部通过、行为零变化、无新增常驻进程与定时任务。（↔GOV-10 验收 1 / NFR-4）
- **AC-60** — WHERE 工场运行时层已部署（compose 形态）, THE SYSTEM SHALL 使运行时服务与 app-proxy 作为可独立启停的服务运行，其部署 / 升级步骤随平台部署脚本交付。（↔GOV-10 需求描述）
- **AC-61** — THE SYSTEM SHALL 把工场运行时层开关与开放能力层开关（F049 拥有）作为两个独立的部署级开关；两者任意组合下平台可正常启动。（↔GOV-10 三层部署形态）

### 2.9 资源档位落地与上线动作（GOV-03）

- **AC-63** — WHEN 实例按某档位启动, THE SYSTEM SHALL 使实例的 CPU / 内存上限与该档位规格一致（可在运行环境中核验）。（↔GOV-03 验收 4）
- **AC-64** — WHEN 档位规格被平台超管调整（F055 管理 tab）, THE SYSTEM SHALL 自该应用下一次发布或重新上线起按新规格生效，运行中的实例不受影响。（↔GOV-03 规则；F055 AC-48 为管线侧写入）
- **AC-65** — WHEN 上线动作被调用（F055 上线终检 / 手动上线）, THE SYSTEM SHALL 先做容量准入（AC-19）：通过 → 拉起并切流量、应用态置已上线；不足或拉起 / 探活失败 → 不拉起半可用实例、应用态置待上线并返回成因（资源不足 / 上线失败）；WHEN 重新上线遇容量不足, THE SYSTEM SHALL 保持已下线并返回成因；**五个状态动作的每次执行与结果（含版本号与成因）均计审计**——本 Feature 是这些事件的写入方，F056 负责其在审计面可查。（↔GOV-03 验收 5 / §3.0.2 / GOV-04 事件清单「发布 / 删除动作」）

## 3. 边界情况

> 只写期望的对外行为；机制与落点见 design.md §4 / §5。

- **应用标识与名称分离**：标识首发确定、全局唯一、不可改；名称可改、可重。入口地址、二维码、审计、CLI 都以标识为准。
- **owner 唯一且不可代行的动作**：删除、撤回在途审批单（F055）仅 owner；租户管理员的处置手段 = 下线（不是删除）；owner 离职的归属转移不在本版（PRD-1 §5.2）。这些「仅 owner」限制以及数据 tab / 运行日志 tab 的访问限制都是**业务规则前置拦截**，不能依赖权限运行时的判定（管理员在那里会被短路放行）。
- **可见范围与授权是"谁能进"，不是"谁能管"**：租户管理员因身份短路对本租户应用天然可管，不需要被授予可见范围；普通用户被授予可见范围只获得入口访问与广场可见。
- **入口判定顺序与信息泄漏口径**：工场层是否部署 → 登录态 → 应用是否存在且曾上线（否则一律「不存在或未上线」页，草稿 / 待上线 / 已删除与真的不存在一视同仁）→ 可见范围（否则「无权限」页，可显示应用名与 owner——PRD 明示的引导信息）→ 应用态（已下线 → 「已下线」页）→ 转发。已下线页只对可见范围内用户呈现。
- **应用根路径的尾斜杠是必要条件，不是美观问题**（2026-08-18 补，实测于 114）：`/apps/foo` 与 `/apps/foo/` 到达同一页面，但作为相对 URL 的**基准不同**——文档在前者时 `./assets/x.js` 按 `/apps/` 解析成 `/apps/assets/x.js`，那是另一个应用标识，于是每个资源都 404、页面白屏。**这个失败在服务端完全不可见**：入口把两种形式都归一成 `/` 转发，应用规规矩矩返回 200，日志一片干净，唯一线索在浏览器 console。应用侧也无从规避——相对路径是技能包明示认可的写法，也是打包器与前缀无关的标准产物。所以补尾斜杠只能由入口做（AC-25），且只对 GET / HEAD 的应用根路径做：非 allow 分支呈现的是平台自己的页面、不解析相对 URL，API 调用也不按相对 URL 解析任何东西，给它们加一跳只有代价没有收益。
- **未登录回跳必须保留原地址的 query / hash**：手机扫码链接常带参数，丢了参数应用打开即空白。
- **过渡态是页面不是错误**：「发布中」「应用恢复中」在实例未就绪时呈现、自动重试；它们与四类兜底页互斥。
- **崩溃自愈覆盖两类故障**：进程退出与进程存活但不健康——5 分钟上限对两类都成立。
- **容量准入是硬闸门**：不足时不得拉起「先起来再说」的半可用实例；容量判定与档位限额同源。
- **每应用数据库的形态承诺**：一个应用一个库、同名连接变量注入、标准库可读写、随存档快照可备份；具体存储引擎与卷形态属 design；单实例是本版既定约束（GOV-03），任何多实例 / 多机演进前须先评估该库的升档路径（PRD-1 §5.2）。
- **出站控制是运行时承诺**：默认封禁、白名单放行；不因换隔离档位而变化。
- **删除的范围明示**：删除托管应用会一并带走代码、对话历史与应用生产数据（用户填报的业务记录），比删一条工作流编排影响面大——确认文案必须点明；不要求输入应用名（对标工作流）。
- **控制面与数据面分离**：运行时服务重启不影响已运行应用；恢复后自动对齐。
- **形态无关的编排接口**：本 Feature 只交付 compose 后端，但对外能力语义（构建 / 启停 / 状态 / 日志 / 探活 / 容量）不得含 compose 专有概念，否则 F059 无法在不改产品面的前提下接入 k8s。
- **未部署工场层 = 整层缺席**：不起运行时服务与 app-proxy、不加定时任务；构建页与广场按开关隐藏；`/apps/*` 仍要有引导页（由平台核心的极小回退承接，不算常驻负担）。
- **数据面的「改」有护栏**：单行编辑二次确认 + 审计；导入与 SQL 查询不做；生产数据编辑不走版本记录。
- **访问记录只记进入**：一次进入一条（合并窗口由 F056 定义），不记请求级明细，避免高频写放大。

## 4. 待澄清决议

> 2026-08-17 用户授权全自动模式：以下各项按建议直接定案，记录理由供追溯；同日 `/sdd-review` 独立审查后增补决议-7 / -8。

- **[决议-1] F054 不再拆分为「编排后端」与「领域 / 界面壳」两个 Feature。** 理由：两者的对外契约互相耦合（应用态流转依赖编排器结果；详情页壳依赖实例状态接口），拆开会在 release-contract 表 3 引入互相依赖的两行；用 tasks.md 的 Wave 分层承接并行即可。**何时重新考虑**：F059 k8s 后端进场后若两个后端由不同团队实现，可把「编排后端」抽为独立 Feature。
- **[决议-2] `app` 资源类型注册归本 Feature（而非 F056）。** 理由：入口访问的可见范围判定（AC-26 / AC-28）在本 Feature，没有类型注册它无法验收；F056 只做授权交互与广场过滤的验收。
- **[决议-3] 出站白名单纳入本 Feature 范围但不在 MVP-114 首波。** 理由：它是 DEV-04 托管运行契约的运行时侧承诺，属本 Feature 的 What；114 首波先跑通功能链路，白名单紧随其后（tasks.md 单独 Wave），不允许被裁掉。
- **[决议-4] app-proxy 注入的短时访问凭据由本 Feature 签发与注入，能力范围语义由 F055 定义；它是会话级瞬时令牌、不属 INV-28 密钥类凭据、不登记为领域对象。** 理由：注入通道是 app-proxy 的职责（每请求签发、绑定用户、防伪造）；「能力声明 ∩ 用户权限」是能力总线语义；瞬时令牌不持久化、不出现在界面，掩码 / 哈希 / 软撤销那套对它没有意义。**何时重新考虑**：若 F055 / F057 需要该凭据可离线校验或跨进程持久，升格为领域对象并补 INV。
- **[决议-5] 数据面本版做「查看、编辑（单行、二次确认 + 审计）、导出」，导入与 SQL 查询随 PRD-2。**（审查修订：原只做查看 / 导出，与 PRD-1 §1「查改导出」不符）理由：PRD-1 分册说明明写「查改导出」；编辑护栏沿用 PRD-2 WB-06 的二次确认 + 审计口径，两册不分叉。
- **[决议-6] 应用详情页发布 tab 与版本 tab 的内容归 F055，可见范围区归 F056，本 Feature 只交付壳 + 应用态徽标 + 入口链接与二维码。** 理由：发布面区块与管线状态耦合；可见范围区是 GOV-01 授权交互的第二触发点；壳先落、内容随各自 Feature 是最自然的分工。
- **[决议-7] 卡片 ⚙️ 菜单按类型裁剪由本 Feature 实现，F056 只承接 GOV-01 验收 6 的回归验证。**（审查修订）理由：裁剪是「托管应用」新类型卡片渲染的一部分，与类型筛选、卡片字段同一处改动；release-contract 表 3 与 mvp-114-path 已同步改口径。
- **[决议-8] 应用态的全部写入（含待上线态）由本 Feature 的五个状态动作承担，F055 只调用不直写。**（审查修订）理由：release-contract 表 1 规则「非 Owner 不得出现修改行为」；F055 AC-31 / AC-32 的措辞为「调用上线 / 手动上线动作」。
