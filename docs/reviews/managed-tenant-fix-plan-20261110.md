### 2.1 两个需要写入设计的现有契约

**部门挂载关系：** `tenant/domain/services/tenant_mount_service.py` 挂载时建立 `Tenant.root_dept_id ↔ Department.mounted_tenant_id`，不会把整棵部门树的存储 tenant_id 改成子租户。`tenant/domain/repositories/grant_department_repository.py` 已明确区分存储租户和业务租户，并校验根节点、路径与挂载关系。因此不能机械地把候选查询改为 `Role.tenant_id == dept.tenant_id`。交接中“部门属于租户 2”的简单替身不覆盖实际挂载模型。

**权限操作账本：** 权限复制不是完全没有幂等设施。`PermissionRuntime.project_copy()` 根据源/目标构造稳定 key；`permission/domain/services/owner_service.py` 调用持久化 projection prepare、execute、finalize，模型为 `permission_projection_operation`。缺少的是业务复制的源状态、目标创建、索引初始化、审计和任务投递的全过程恢复。不能再造一套 OpenFGA 直写或把所有投影异常都解释成“什么都没发生”。

## 3. 修复统一原则与本次建议决策

本版以 [业务边界及角色生效规则](managed-tenant-boundary-assessment-20261110.md) 为建议契约正文，[184 个模型分类清单](managed-tenant-model-inventory-20261110.md) 为结构覆盖依据；它们不是全仓接口安全验收。原评审是 v1 快照，本版修订见 §7。

**推荐：单一主属租户 H 生效，跨租户兼属只增加组织事实，不自动获得外国租户的策略角色、菜单和配额。策略角色继续按人绑定，部门是授予资格/作用域，不假装现有 UserRole 已记录来源部门。** 普通用户多租户执行身份、按部门来源独立授撤，作为不同产品能力另行设计，不在本轮隐式引入。

| 概念 | 可信来源 | 使用范围 |
| --- | --- | --- |
| H(u)：操作者/目标用户主属租户 | active UserTenant、主部门解析、当前身份版本 | 普通用户生效策略、菜单、个人授权及预算资格；管理选择不改它 |
| M：管理目标 | 管理准入已验证的具体范围 | 超管管理资源目标；不能拿来填目标用户的角色绑定 |
| B(d)：部门业务租户 | 权威根部门、挂载/路径/状态 | 部门候选和授予资格；不等于部门存储 tenant_id |
| O(r)：资源/定义所属租户 | 授权加载的记录、父资源 | 主子对象、角色菜单定义、重命名唯一性、复制一致性 |
| T：冻结执行目标 | 普通个人 H、管理 M 或持久化操作/可信凭据 | 资源写入、租户用量、权限投影、审计目标及 worker |
| E(u,H)：有效普通策略角色 | 该用户 H 内合法绑定 + 全局/本租户合法定义 + 当前有效部门作用域 | 普通角色、菜单、配额、菜单申请模式、审批动态标签及 DSH 统一策略的共同依据 |

平台目录、全局身份、精确共享/能力通道保留专门授权；有无 tenant_id 不能代替业务分类。AdminRole 的平台 super、租户管理员和部门管理员不并入普通 E，当作独立身份协议，避免为修策略角色误删平台身份。

Service 负责授权、身份与目标解析；Repository 负责有边界的 SQL。新增角色/身份查询通过所属领域 application 协议导出，不在 core 里导入业务域，不把各 DAO 的所有读取统一 bypass。保留自动过滤作为默认保护和合法范围内的 refresh，原生 SQL/批量写/显式 tenant 值由所属 Repository 保证目标一致。遵循 [宪法](../constitution.md) C1～C5。

## 4. 各模块实施方案

### 4.1 MT01：角色定义与菜单原子保存

1. 在角色 Repository 中统一“当前可见自定义角色 + 合法全局定义”的读取规则，单条读取和事务内锁定重读共用。绕过自动过滤只用于受约束的定义查询，必须仍限定角色 ID、允许的定义租户及类型。
2. 修改前保留现有系统超管、租户管理员、部门管理员和创建者约束；事务内重读后复核角色类型、归属及可修改字段，避免首次读取到写入之间目标变化。
3. 更新使用角色记录的 tenant_id 校验名字唯一性；不能使用操作者所属租户查重。作用域变更后对已有绑定按最终合法成员关系重算；失去资格的绑定终止并审计，之后扩大/改回/清空定义作用域不自动恢复。始终合法的绑定保留；新的授予另行校验。
4. 全局角色的 RoleAccess 查询、删除、插入都在**定义所属租户**内完成。显式继承角色租户，角色字段和菜单关系同一事务提交；菜单读取也沿用定义解析。UserRole 的绑定租户保持独立，不能随定义搬到 Root。
5. 所需 refresh 在 flush 后、commit 前于合法定义访问范围内完成，刷新失败仍可回滚整笔修改；提交后必要读取也沿用相同定义规则。提交结果不确定时查验并恢复操作，不宣称 rollback 能撤销已成功的 commit。正式测试同时验证旧菜单全部替换、不重复、切换视角后定义一致。

相邻风险：`create_role()` / `create_role_with_menu()` 同样显式使用账号租户，且后者使用同一菜单 helper。实施时补全局角色新建、删除、查重的回归，保持既有全局定义归属约定；本轮未执行这些入口，不能把它们标成已复现或已安全。

### 4.2 MT02：统一有效角色协议与所有政策消费者

1. 提供受约束的 E(u,H) 解析协议：明确查询目标用户的当前 H，读取属于 H 的普通绑定，再加载合法全局定义/本租户自定义定义；有部门作用域时验证当前同 H 成员关系仍能支持。缺失/故障不伪装成正常无角色；已明确无效的旧绑定退出 E 并保留诊断。
2. 定义读取与绑定读取分离：全局 Role/RoleAccess 可按定义跨存储租户取；UserRole 不能因此跨所有租户并集。写绑定时显式写目标用户 H，不能由操作者或当前 M 自动填充。AdminRole 独立处理，不跟普通绑定搬迁。
3. 同步接入 get_effective_quota、get_all_effective_quotas、check_quota、上传限额；并接入 LoginUser 初始化、user/info、菜单断言、菜单申请模式、OrgDirectory 角色显示、审批 role_{id} 标签和 DSH 现行 UnifiedPolicy。详细生产者/消费者清单见边界正文 §5，不能只改一个批量 RoleDao。
4. 个人菜单授权按 H；管理资源写的租户上限和用量按冻结的 T；普通 quota API 保留 H 语义，不顺便加入管理白名单。平台 super 与租户/部门管理员解析保持各自权威来源。
5. 数量型配额维持 MAX、0/-1/缺省；knowledge_space_file 保留最小有限正值、-1 与现有缺省/历史 0 语义（新配置 0 非法），不能套数量配额“0=禁止”。布尔申请模式保持 OR；DSH credit 用现行专用聚合和 ledger，不改成 QuotaService 算法。
6. 真正没有合法普通角色时保留现有默认配额契约；无角色不自动给予菜单。超管短路及存储硬限制逐入口沿用，不按一个例外推广全部资源。

### 4.3 MT03：工具父子事务及创建恢复

1. 在 ToolServices 校验创建资格并解析管理目标；父记录、每个非空 child、权限 record 显式使用同一目标 tenant_id。拒绝客户端携带的冲突归属，或按现有 schema 规则忽略该字段，不直接信任请求。
2. 在一个 SQL 事务内插入父记录，flush 获取 ID，生成 children 的 type/tool_key，插入 children，校验归属后提交。children 失败必须回滚父记录。
3. 保留 `add_gpts_tools_hook()` 的统一权限适配器。业务创建过程记录可恢复操作并关联现有权限账本；SQL 预留与最终可用状态分开，投影成功后才能完成业务 finalize。
4. 投影失败或结果不确定时标记待恢复，按同一 operation/target 重试；不能直接删除可能已经投影的父记录。确认尚未开始投影时才可以回滚预留或执行受控清理。审计失败要保留待补写状态，不能让同次重试再建一套父子资源。

`POST /api/v1/tool` 当前属于管理前缀，但不在 expected-management-write 头校验规则中。此为相邻的陈旧页面提交风险，尚无本轮复现；本方案不静默新增必填请求头。若要与 workflow 写保护对齐，需在正式设计中同时核对平台调用者并明确契约。

### 4.4 MT04：工作流主记录与版本一致

1. create_flow 采用已验证管理目标；把目标传入创建 Service 的业务事务，不在 Endpoint 扩大 ORM 编排。
2. FlowDao 的初始版本显式继承主记录 tenant_id，其他调用者如助手、模板复制也必须保留各自已验证目标；不能让主、版本分别依赖不同来源的默认值。
3. 主记录和 v0 保持同一 SQL 事务，版本写入失败时整体回滚。后续创建版本、取 current version、详情及列表均验证所属工作流和租户一致。
4. 配额装饰器、创建 hook 的权限 record 和审计都使用同一写入目标；采用与工具一致的业务预留/权限操作恢复方式，避免 SQL 已提交、hook 失败后留下永久不可用对象。

### 4.5 MT05：文档库和 QA 库共用可恢复复制编排

**目标规则：** 保持权限运行时已有的同租户复制契约。源通过原有菜单和读权限检查，且必须位于本次已验证复制范围；目标 tenant_id 等于源的已验证业务租户，并与具体操作范围一致。不同租户时应在改源状态或建目标之前拒绝，提示切换到正确范围；本次不引入跨租户复制。

**推荐编排：** 在 knowledge 领域维护业务复制操作及投递 outbox，关联现有权限 projection operation。它记录的是复制流程，不替代权限账本。至少持久化 operation_id、请求幂等键/参数摘要、源/目标 ID、目标租户、操作者身份、源原始状态/版本、阶段、错误、重试次数、任务 ID/租约。已有 `Knowledge.creation_request_id` 可参与目标唯一约束，但不是完整任务恢复机制，需区分普通创建与复制的幂等命名空间。

复制目标的 SQL 预留与外部初始化应拆开，不再直接复用当前同步 `create_knowledge_base(..., skip_hook=True)` 作为完整创建步骤：该 helper 仍会覆写目标租户并提前初始化索引。新复制编排显式传递已验证目标，保持操作者身份不变；普通 Web 创建的 `KnowledgeCreationPolicy` 另有本人归属契约，不随本次管理复制一并改写。

建议先用现有 KnowledgeState 映射 UI：预留目标 UNPUBLISHED，完成 PUBLISHED，终止失败 FAILED；内部阶段放业务 operation，避免把一串新状态值直接加入前端枚举。具体可见性和恢复入口在正式设计中确定，禁止 pending 对象直接可用。

| 阶段 | 成功动作 | 失败或进程退出后的处理 |
| --- | --- | --- |
| 请求校验 | 冻结源、目标、权限资格与幂等键；校验同租户、源可复制、文件状态 | 不修改源、不开目标；同 key 不同参数拒绝 |
| SQL 预留 | 同事务建立操作、唯一目标；用条件更新把源从可复制状态改为 COPYING，记录原始状态/版本 | 事务失败整体回滚；同 key 返回/恢复已有 operation；不同 key 并发复制由源占用规则拒绝 |
| 权限复制 | 通过现有 adapter/project_copy，保存其稳定目标及账本关联 | 未开始投影可安全取消；已开始或结果未知则进入恢复，先查账本/重试原冻结计划，不盲删目标 |
| 外部准备 | 权限确认成功后幂等初始化所需 ES/Milvus 等目标资源 | 记录失败并恢复同一目标；清理只作用于该 operation 独占的资源，并确认 worker 未持有租约 |
| 审计与任务投递 | 持久化审计事件/补写意图及 outbox，再由 dispatcher 发复制任务 | 审计未完成可恢复；Broker 失败保留待投递；发送成功但确认落库失败允许重复投递，消费者按 operation 去重 |
| Worker 执行 | 以 operation/目标租户恢复执行范围，领取租约，幂等复制文件/QA/向量，记录进度 | 单项、整批、进程崩溃均记录可恢复失败；重试不得重复创建目标、文件或 QA 行，不得清理仍在运行的资源 |
| 完成或终止 | 完成目标并条件释放源占用；终止时先停止/围栏任务，再处理投影及外部清理 | 只恢复本 operation 占用且版本符合预期的源，避免覆盖之后的编辑；有不确定副作用时保留恢复状态与操作 ID |

不能只给当前 copy 函数加 `try/except` 后恢复源、删除目标：异常可能发生在权限提交或消息发送成功之后。源只有在本操作已安全终止或完成、且仍持有源占用时才能恢复。

需一并调整两个 worker：文档任务 `worker/knowledge/file_worker.py:31` 的外层异常没有统一状态终结；QA 任务 `worker/knowledge/qa.py:38` 有部分异常恢复，但投递前根本不会进入 worker，且部分失败可能继续结束流程。新状态机要覆盖空任务、部分失败、重投及 worker 崩溃。失败结果必须可观察，不能把“任务函数返回了”当作全部复制成功。

Celery 已有 `worker/tenant_context.py` 自动从有效 ContextVar 注入 tenant header；新 outbox dispatcher 不依赖残留 HTTP 上下文，应显式绑定持久化的目标租户发布。worker 校验源、目标及 operation 归属后执行，沿用重置机制防止线程上下文泄漏。

### 4.6 MT06：跨租户兼属、同租户策略绑定与迁移

1. 候选目录通过已授权部门和根挂载关系求 B(d)，不使用操作者 H、M 或存储 tenant_id。单个/批量共用规则，批量必须按每个部门边界过滤；边界失效拒绝，不把登录身份解析器的 Root 回退用作管理授权。
2. 部门级 assignable-roles 是定义目录，人员表单和保存还要验证目标用户 H。对已有用户，仅 B(d)=H(u) 的合法部门政策管理入口允许普通角色变更；B(d)≠H(u) 的兼属面板只读/不适用，不提供全局或自定义策略角色写入。伪造角色变更在任何其他字段提交前拒绝。
3. 加外国兼属不发该部门默认角色；组织关系可按授权成功，但须显式返回角色不适用的解释，批量按每个目标用户判定。全局定义公共不意味着外国部门管理员能改变用户主属菜单与预算。超管修改用户政策走明确 H 的策略入口，不以外国部门上下文绕过。
4. 当前 UserRole 没有来源部门，前端也明确共享同一人/角色绑定。本版不新增来源账本：同 H 的全局/无作用域角色是直接策略，离开某部门不自动收回；默认角色是实际新加入/新 H 激活时的种子授予，不因 SSO 同一成员快照重建而重发。作用域角色按剩余合法同 H 部门重算，无任何支持时撤销；旧行不因回迁/重入被查询隐式激活，新的合法默认/显式授予可另建可审计绑定；其他支持仍存在则保留。
5. 若要实现“离开部门时撤回该部门发的全局/无作用域角色”，另行确认来源化授权及 LEGACY 数据处理；不能从旧行猜来源，也不能只为 UI 多个下拉创建重复绑定。
6. 本地新建/旧 user/create/DefaultRole 初始化、默认角色批量、SSO 的 _replace_department_scoped_roles、归档/删除、两个主属变更入口和 UserTenantSync 均接统一生产规则。先校验最终角色、组和成员关系，再执行一致的业务变更，避免角色校验失败之前姓名/组/主属已提交。
7. H=A→B 后，A 自定义角色和 A 个人菜单不在 B 生效；不按名称复制角色，全局旧绑定也不自动搬到 B。迁移成功时以可审计撤销/明确终止结束旧普通绑定，不能仅暂时过滤，以免回迁自动复活；平台 AdminRole 独立保留。B 的合法默认/显式发放重新建立政策。旧资源留在 A，身份同步未收敛时拒绝依赖新旧 H 的敏感操作并保留恢复状态。两种主属入口“降旧为兼属/删除旧关系”的差异需正式设计明确。
8. 角色/定义变化同步失效受影响策略、菜单及 DSH 缓存，前端刷新 user/info；审批/延迟创建执行时复核。普通角色 LegacyRBACSync 返回不代表缓存已更新。不引入没有失效依据的跨请求 E 缓存。

### 4.7 Q01/Q02/Q03/Q04：配额计量、剩余额度与责任人（明确新增范围）

**Q01：** 当前 user count 原生 SQL 多项只过滤 user_id，本轮真实 SQLite 已观察跨租户累计。建议按 `(user_id,T,resource_type)` 统计，订阅/文件/空间各自核对父对象计量，不用 ORM visible 集合代替原生 SQL 条件。旧租户资源不扣新租户个人预算；tenant chain 用量仍归原资源所属租户。

**Q02：** 已用生产 check_quota 注入 role_limit=10、user_used=5、tenant_remaining=3，观察到误抛角色超限。检查应分别验证“角色上限容纳 user_used+Δ”和“租户链各节点容纳 Δ”，不要把 min(role_limit,tenant_remaining) 再与累计 user_used 比较。数量 Δ=1，上传使用真实字节/单位。

数量型可展示 available=min(role_limit-user_used,各层 tenant_remaining)，下限为0，不限单独处理。保留清晰的 role_quota/tenant_quota/user_used/tenant_used；优先增补 available 并核对客户端，旧 effective 混合口径的兼容/弃用方式正式设计单列。Q01/Q02 与 MT02 角色过滤分开提交和回归；本轮未实施任何算法变更。

**Q03：** 操作者、额度责任人 q、策略租户 P、执行/资源租户 T 必须分开。普通个人额度要求 P=H(q)=T。真实频道更新按创建者而非编辑者计资讯源额度；创建者从 A 迁到 B、频道留 A 时，默认允许按权限维护/缩减，但拒绝新增受该预算限制的资讯源，直到资源在 A 的计量责任通过明确交接完成。不能读 B 的角色支付 A 增量，也不自动恢复旧 A 角色或改计编辑者。只有 FGA owner 转移但计量仍用旧 creator 的情况不算交接；无已验证责任交接入口时保持止增，后续能力单列设计。

**Q04：** 必需用量/资讯源去重/租户链统计失败时抛出可诊断的不可用错误，停止受额度控制的增量写入；不能沿用异常返回0/空集合而放行。展示将未知用量明确标为不可用，真实零、未知和额度耗尽分开；不阻断无需新增额度的合法减量/删除。

普通 Quota 并发保证维持 F005 AC-23 / INV-11 的提交前检查，允许轻微并发超额；本批公式不承诺严格原子预留，不引入通用分布式锁/额度账本。严格控制指标另行点名协调边界；DSH 结算和 app 容量预留保持各自现行协议。新增“两个请求争用最后名额”和“创建者迁移后他人编辑旧资源”的明确验收。

### 4.8 创建/复制恢复的最小交付边界

MT03/MT04 的同目标主子 SQL 和合法 refresh 是直接修复；MT05 的源状态恢复与任务故障是已证实缺陷。权限操作必须继续满足 C4，不能把未完成投影的资源当可用；但不预设给所有资源新增同构 operation 表或通用恢复引擎。

| 业务 | 正常消费者必须覆盖 | 恢复路径/最小状态建议 |
| --- | --- | --- |
| 工具 | 列表、详情、schema、更新、executor 调用及导出 | 先验证现有权限 projection CURRENT/操作账本能否门控；不足时在工具域加最小 pending 状态，操作恢复由领域明确负责；超管也不能把半成品交给执行器 |
| 工作流 | 列表、详情、版本创建/读取、发布/状态、运行与队列任务 | 主/v0 原子写；未完成创建不得运行或派生新版本；恢复按既有权限账本/领域状态继续，不能只靠页面隐藏 |
| 文档/QA 复制 | 列表/详情与使用、编辑、删除、文件与向量写、重复请求 | 复用已有 KnowledgeState 与权限目标状态门禁，补业务 operation/outbox 及 worker 幂等；受控恢复消费可读取 pending，普通消费不可绕过 |

每项正式 design 必须点名恢复发现者（worker/dispatcher/受控管理入口）、租约和围栏、重复 finalize 判定、暂不可恢复时对用户的状态与操作 ID。先复用已有结构，再以实际缺口决定新增持久状态；不得只增加预留写入而不检查其消费者。

## 10. 最小改动重新评审：撤回七表方案

用户最新要求“最小改动最小影响范围的修复租户的缺陷”。[独立复审](../../features/v3.1.0-beta1/009-managed-tenant-consistency/minimal-change-architecture-review.md)对完整七表稿结论REVISE：域内正确性与跨系统恢复工程捆绑，缺少同步小事务/父资源承载必要状态的更小备选。原LGTM/PROCEED不能代替本次范围判断。

当前候选以[F009最小修复设计](../../features/v3.1.0-beta1/009-managed-tenant-consistency/design.md)为准：

- MT01/MT02：精确O/H查询、角色/菜单同SQL事务、统一当前有效角色读取，不改全局隔离框架。
- MT03/MT04：工具父子/flow-v0同T同事务；父资源仅加创建状态，权限仍用原冻结账本，super前检查pending。
- MT05：复制私有预留保持源T，源/目标同SQL事务并加两个关联指针；worker使用目标现有state CAS唯一领取，完成/失败不得解除别次源占用。未知消息/外部效果不盲删、不自动重放。
- MT06：候选和最终写基于B/H及成员/管理事实，跨租户兼属政策参数写前拒绝；触及生产者同步删除非法普通绑定，不造来源账本/全员持久编排。
- Q01～Q04：真实(q,T)计量、独立余额、责任迁出止增、统计失败非0；不造额度账本。
- DSH仅接当前有效角色读取及失败拒绝。活跃调用每次读取政策并向Lua传本次限额，不扩展为按人generation/全模型封闭与Redis重建改造。

不新增七张业务表、不强制复制UUID、不新增恢复中心/周期扫描，不重做全站audit sink；候选DDL仅Flow/GptsToolsType创建状态和Knowledge两个关联，共四列。

此候选不能交付原40条全部恢复保证。逐条[范围调整](../../features/v3.1.0-beta1/009-managed-tenant-consistency/scope-revision.md)明确复制逐项幂等、任意重启自动续传、跨系统强收敛及全效果审计等延期；用户确认前不删原AC、不标完成、不开始实施。

最小候选[最终独立复核](../../features/v3.1.0-beta1/009-managed-tenant-consistency/minimal-change-architecture-review-v3.md)为PROCEED，复制唯一领取CAS、DSH round边界、SQL提交未知分支均已补齐；技术意见不代替28条纳入/11条部分/1条延期的范围确认。
