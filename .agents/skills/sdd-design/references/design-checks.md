# 技术设计检查要点

按实际风险使用，重点是让实施者能够理解核心机制和约束。

- 现状：入口、实际调用、配置和使用方是否查证；明确现有系统与目标差异。
- 正确性：关键规则是否来自有效需求／契约，作用范围和时间窗口明确；每条是否有负责模块、可行保证、适用失败／并发推演和可观察验证。检查先后与原子性边界能否真正守住规则；未知不能冒充保证。
- 图解：复杂知识、关系与流程是否按 [图解与选图方法](diagram-methods.md) 选择实际可见的图；关键调用、状态、关系和边界是否与需求、INV、正文及契约一致；图例、解读、文字和窄屏呈现是否清楚。不能只检查图数或用一张概览代替所有细节。
- 决策：关键选择的依据、真实可行的替代方案与取舍、何时需要重新考虑。
- 职责：沿用项目架构和现有机制，说明业务与数据由谁负责、谁调用。
- 契约：相关请求、响应、错误、权限、兼容性和副作用足够明确；不编造尚不存在的接口。
- 状态：正常、异常、部分成功、超时、取消和恢复时的结果；适用的事务与外部动作边界。
- 重复与并发：存在相关风险时明确幂等、冲突、顺序或重试策略，避免重复副作用。
- 资源：连接、文件、锁、后台任务等所有权、结束及失败释放。
- 安全：相关信任边界、输入处理、访问控制、敏感信息与日志约束。
- 运行：真实依赖和环境差异、性能容量、现有监测缺口、必要发布与恢复安排。
- 验证：需求映射、用例来源、真实被测组件、可隔离边界、替身契约和执行前提。开发侧需要的单元／接口／功能测试使用适当隔离环境，真实部署 E2E 及真实依赖缺口安排到 CI／共享验收环境；UI 执行遵守单独约定。

设计要回答关键失败方式及处理，不要求穷尽所有技术细节。技术假设的证据不足时保留未知；影响核心决定的事项解决后才交付确认。
已证实的坑及其原因保留在当前方案中，避免后来者重复踩坑；只保留对理解现行方案有价值的说明。
