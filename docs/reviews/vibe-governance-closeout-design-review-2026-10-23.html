What：spec.md（73 条 AC）；流水账：tasks.md；不变量：release-contract.md。本轮只补 AC-66、AC-67、AC-68、AC-69、AC-70、AC-71、AC-72、AC-73，对应历史 T098 / T099，不重开 F059 / F086 验收。

1. 目标与非目标

保持统一应用入口、平台身份注入、持久化数据和独立编排边界，补齐 Docker 应用访问宿主服务的隔离，以及 OBO 配置不完整时的入口拒绝。为 F055 用户确认的配置重建提供现有部署执行与受限运行环境只读协议。

非目标：商业授权、重写 manager、重新实现 F059 Kubernetes、扩大第三方 egress 白名单、密钥管理页面或运行记录查询（分别归 F055 / F056）；不在 backend 中运行防火墙命令或容器 SDK。

2. 关键约束

  • 领域真相由 backend 数据库持有；manager 经内部认证下载代码/上传快照，不直连 MinIO。附件已迁 backend。源码、依赖、启动参数由已冻结交付描述决定；本轮不改镜像构建路线。
  • Docker Engine 仅由 manager 经 socket proxy 访问；K8s 由独立 manager 使用受限 ServiceAccount 操作。没有挂 socket 不意味着编排 API 权限很小。
  • Docker 隔离规则必须在 Docker 宿主网络命名空间生效。manager 容器中执行 iptables 或检查容器自己的 INPUT，不能证明宿主已隔离。
  • 原生 nftables 与 iptables 是两种支持路径；本轮 Docker 托管网络只声明支持 IPv4。发现 IPv6、未识别网络后端、无法证明实际隔离时，拒绝新部署，不假装支持。
  • 宿主规则变更只操作自有链/表，不能清空 INPUT/FORWARD/DOCKER-USER，也不能修改其他网络的全局默认策略。
  • Constitution Check：遵守 constitution.md C1–C8。新增隔离报告由 Repository 落库（C1/C8）；租户对象、权限入口沿用 C3/C4；新字段/迁移用通用类型（C2），错误码沿用 161 段（C5）；HMAC 与 OBO 分开配置（C6）。本轮无铁律例外。

3. 方案对比与选定

D1：独立 manager + backend 持久意图

保留独立进程；选用 F086 的持久 RuntimeOperation、执行事实与路由投影，而非 backend 直接控制 Docker。证据是 runtime_operation_service.py、runtime_delivery_repository.py 的租约/代次/操作围栏；仅 HTTP 一次性命令无法恢复响应丢失。若执行协议整体升级再评估，不增加并列状态机。

D2：Docker 经 socket proxy，K8s 经受限 API

当前 Docker 配置已经是 socket proxy，不再采用旧设计的“先直挂 docker.sock”。通用代理限制 API 面但不是业务授权器；manager 仍持有高权限编排面。拒绝把三种代理与 backend 合并来省进程。只有权限模型改变且验证隔离等价时重议。

D3：交付模式服从 F086 / F059

当前有 bundle、完整 image、source-image，支持 Python 3.11 / Node 20 / static，不再是首发 Python 模板单一路线。选用已冻结 delivery/profile/digest；拒绝运行中重新选择可变默认镜像。依赖缓存、离线交付和 K8s 组装的详细契约分别见 F086 design、F059 design。新增运行时时再评估。

D4：自愈与切流复用现有围栏

探活成功才提交路由；旧写入者确认停止才允许新的 SQLite 写入者；恢复沿用原操作、deadline、资源 UID，不以重启为理由无限延长。禁止只用容器名判定安全。底座证据见 F059 既有验收；本轮用户确认重建只复用这些机制。引入多实例数据模型时重议。

D5：app-proxy 保持独立入口

nginx → app-proxy → backend 授权与路由投影 → 应用，支持 HTTP/WebSocket；不改为代理向 manager 查路由。proxy 持有 entry 只读角色，不持编排或数据库凭据。若统一入口基础设施替换再评估。

D6：OBO 配置失效时 fail closed（本轮变更）

选用现有 unavailable 决策并新增 reason=identity_config_incomplete，不增加可放行的“匿名降级”。entry_authz_service 提供同一 obo_configuration_status() 校验器：值缺失、全空白、与 JWT secret 相同均无效；校验不 trim 后再签名，实际有效值原样用于签名与验证。正式入口完成登录、应用存在、租户、可见范围、下线/维护判定后，在 _identity_material 前检查；预览完成会话、预览归属与应用/租户核验后同样检查。任一无效返回拒绝，不生成身份头、OBO、allow 访问记录。

app-proxy 的 BackendAuthzClient / preview 授权客户端不再缓存含身份材料的 allow 决策：每个新的 HTTP 请求和 WebSocket 握手到 backend 重新判定，避免 backend 配置失效后旧 allow 缓存继续放行。路由缓存与拒绝缓存维持独立；已经建立的 WebSocket 不承诺逐帧重鉴权。此取舍增加授权 RPC，定向验证请求数与延迟，不把“保留有效配置行为”理解为继续缓存旧身份。若未来有可信配置 epoch 推送协议，再评估恢复 allow 缓存。

签发器自身再防御性校验并返回显式失败，调用者不可把失败当缺省可选值；验证器亦拒绝无效配置。请求期间以同一配置快照完成检查/签发，避免动态刷新间隙。应用运行时开启时，FastAPI lifespan 输出一次脱敏 ERROR（字段名和失败原因，不含值），不终止整个平台进程，入口保持拒绝；开关关闭不产生“已启用”或误报。选择此方案而非整站启动失败，因为 spec 要求关闭运行时/其他平台能力不被连带停用。若未来 OBO 采用非对称签名，再重新审查发行/验证契约。

D7：拒绝页面沿用既有契约

app-proxy 对 unavailable 保留既有不可用页与状态码；当 backend 已完成原登录、对象存在、租户、访问权限和运行层开关判定后，消费可信 reason=identity_config_incomplete，正式/预览均显示 “本环境配置不完整，请联系平台管理员”（三语同义）。该提示不显示配置值、字段值、内部 URL 或真实应用环境；无权者仍得到原来的登录/不存在/无权限等决策，不靠浏览器参数切换到此提示。无需新视觉模式；沿用不可用页模板只增加此原因对应文案。新增状态码需先检查 nginx error_page 合同。

D8：领域与列表投影保持兼容

App / AppVersion / AppInstance 继续分别表达业务状态、冻结版本、运行观察；构建/广场列表通过既有 UNION 第三支表达 flow_type=35、app_state，不为新安全项改列表含义。若新增状态，需同时审查两个 SPA 的白名单。

D9：权限走已验证业务目标

应用身份、owner、租户与资源状态先由业务服务核实，业务动作走 F048 统一入口；manager 与代理不自行查 OpenFGA。管理员的通用 shortcut 不能扩大 F055 的 natural owner-only 密钥写权限。新增管理动作时重审 Catalog，而非手写 role_access。

D10：SQLite 与平台存储解耦

Docker 绑定本地持久目录，K8s 用已验收独占 PVC；manager 执行本地 backup/迁移，经 backend 存取快照。应用附件走 backend 存储接口；manager 不读平台 MinIO 配置，也不需要独立 MinIO 实例/新桶。升级代码不等于恢复数据库；恢复必须显式选快照。存储拓扑变化时重议单写入者证明。

D11：容量与资源档位

沿用平台档位与持久 reservation；释放依赖停止证据，不以超时自动当作已停。用户确认的配置重建依然需要执行资源预算，不绕过准入。并发拓扑改变时重审预算。

D12：宿主 INPUT + FORWARD 的同源隔离（本轮变更）

否决仅补 DOCKER-USER（不覆盖 INPUT）、只看 --internal（不证明宿主入口关闭）、在 manager 容器里加 NET_ADMIN（作用域错误且扩大权限）、允许整个 backend 端口给附件（附件也应经 egress）。选定：保留 egress 唯一出口，安装侧 root 工具维护宿主自有规则，backend 持有短时有效的独立隔离证明，新部署消费证明。

现有 runtime_manager.egress 已有规则渲染和 CLI，扩展同一规则模型，不另写两套白名单。具体安装、报告和准入合同见 §4.4。已建立连接也不能用宽泛 ESTABLISHED 一律放过，必须区分应用响应与应用主动发起。真实宿主配对探测是依据，命令存在不等于隔离成立。若后续采用经过验证的 eBPF/专用网络插件，可替换证明生产方，不能取消拒绝边界。

D13：详情页扩展点

保留发布 / 版本 / 数据 / 日志页壳与命名 slot。F055 密钥管理放既有 settingsSlot，不为安全项新增管理菜单。壳变更时需检查三个 Feature 消费者。

D14：运行日志与访问记录分开

stdout/stderr 是调试日志；backend 入口 allow 产生合并窗口访问记录；F056 的读接口不创造新访问事件。保留既有合并窗口实现/配置，本轮不改频率。安全拒绝不计成功访问；日志包含配置原因但不含身份材料。若审计语义变更，应先改规格。

D15：收尾边界与交付声明

旧 MVP “后置”不再表示未实现：F086、F059 已有实现/证据，本轮只修改与安全/密钥刷新直接相关的接口。历史未完成验收不自动勾选，ARM、完整离线安装和正式镜像发行不冒充本轮完成。只在本轮 AC 定向证据成立后更新相应任务。

1. 目标与非目标

为已有发布/审批/运行管线补齐 owner 私有应用密钥：仅保存名称引用进版本，值加密存平台数据库，已审批正式实例按当前值注入。保存值不触发重启；页面提示当前实例与最新保存配置的差异，owner 确认后才复用部署流程重建当前版本。预检和审批预览只注入声明名与空值。

非目标：第三方 Vault/KMS 托管、第三方凭据有效性探测、密钥 SDK/CLI 管理、商业限额、平台模型供应商密钥编辑、批量应用重启。F054 管生命周期执行，F056 管管理员运行记录查询，不复制这两个领域。

2. 关键约束

  • 预检、构建、依赖安装、前端编译、扫描、审批预览均不得取得真实值；预览身份和隔离存储原有规则仍有效，不以“无应用业务密钥”取消正常权限检查。
  • 值只由同租户应用 natural owner 经平台会话修改；管理员、超管、审批人、SAK、PAT 均不能替 owner 写。权限 shortcut 不代替这个业务前置。
  • 声明属于冻结版本并需审批；值属于应用当前配置，改值/删值不创建版本或审批，也不自动创建运行操作。手动重建只能运行确认时的已批准当前版本，不能借机启动 pending_version。
  • 字段边界（拟定实现常量）：每应用最多 64 项；名称 ASCII [A-Za-z_][A-Za-z0-9_]{0,127}，区分大小写且精确匹配；值 UTF-8 不超过 16 KiB，整组不超过 128 KiB，禁止 NUL（无法放入进程 env），支持 Unicode/换行/空格/特殊字符且原样传递。空字符串表示缺失；全空格值不自动 trim 成空。
  • 遵守 constitution.md C1–C8，不复制全局铁律。Constitution Check：新 Model/Repository/Service/Endpoint 分层；tenant_id 默认 None、非空、索引且注册自动注入；通用 LargeText/JsonType 和迁移单 head；仅 162 段新增错误码；平台持久 DB 为权威；不向 backend 引入容器 SDK。无例外。

3. 方案对比与选定

D1：同步接收 + Celery 阶段机

保留同步鉴权/安全解包/manifest 校验，异步扫描、准备交付、探活、审批。拒绝把整条分钟级管线放 HTTP 请求或把失败尝试写成已发布版本。现有 AppDeployment 与 worker 已接线；管线可并行分支真正出现时再重议。

D2：源码快照由平台保存

backend 拥有私有对象存储与代码引用，manager 经受限传输 API 获取。拒绝 manager 直读 MinIO 或通过临时本地文件在 API/worker 间共享；现有 runtime_artifact_service 已提供传输协议。交付物类型改变时重新评估。

D3：manifest 严格校验，新增引用而非值

CapabilityDeclaration 增加 secrets: list[SecretRef]，SecretRef={name: str} 且 extra=forbid，旧 manifest 不带该字段仍通过。采用与 models/knowledge_bases 同处的声明入口而非任意 env 字典；没有平台 issued scope，derive_scopes 不因 secrets 新增开放 API 权限。

当前 _reject_secret_references 会泛化拒绝 secret/token 等键，必须只豁免合法 capabilities.secrets[*].name 子树，其他位置仍禁明文/不支持的引用形状；全源码扫描继续先于构建。is_empty、部署适配、预览、摘要/diff、CLI 校验与提示、审批审读都同步识别名称。若未来支持外部 secret provider，另改规格与 schema，不接受 vault://... 偷渡。

D4：fail-fast 阶段结果保留

沿用 {stage,code,message,details,hints} 失败形状；缺值是 warning，不单凭缺值拒绝发布。应用自身无法启动则正常探活失败，不跳过 Gate。不得将第三方 key 的值放进 details/hints。若发布阶段拆服务再评估传输合同。

D5：明文扫描继续阻断

合法声明名不视作密钥明文；实际源文件/打包内容仍扫描、只返回文件/行号/规则，不返回匹配值。密钥不进源码或依赖缓存，不能为“用户确实需要 key”放宽扫描。新检测模式只更新规则与配对用例。

D6：版本只保存声明快照

同 app 的受理受 App 行串行，既有 node/assignment 围栏仍控制执行；活动冲突读取以拒绝/后续精确 origin 与代次检查保守处理，不把快照里暂未出现的 queued op 当作唯一安全证明。实现阶段用两个真实 SQL session 覆盖与 claim、maintenance fact、ready commit 的交错，不以单进程锁 mock 代替。若实际 helper 引入表外锁/独立 session，必须先修正此局部调用，不将上表当全仓已验证事实。

  1. 现有 create 会拒绝 caller sealed_env，因此由受信 inject_environment 在同一 UoW 装配 seal，不把 env 放进公开 OperationInput。持久非秘密字段为 purpose=config_restart,auto_commit=true,secret_config_revision,sensitive_env_names,approved_declaration_digest,origin_operation_id,origin_exec_ref,origin_route_epoch 以及既有 expected_app/current/pending 等围栏；秘密只在 sealed_env。普通新部署/恢复也要从其受理快照装配，不留“先创建操作、之后读任意最新值”的窗口。 同事务环境生产者，不复用独立提交方法冒充原子性：现有 inject_environment → AppRuntimeCredentialService.stage → CredentialService.issue 会通过 CredentialRepository 和 HostedAppSubjectDAO 自开事务提交，签发审计也独立提交。新增受理路径由凭据 Owner 提供显式 stage_in_transaction(...,session) 公共服务入口：受信主体解析/首次创建、ApiCredential/委托子项、RuntimeCredentialBinding、签发审计都使用 caller 的同一个 AsyncSession，只 flush、不 commit；原无 session 的签发入口保持原行为。返回 token DTO 从本事务已 flush 的数据构建，不调用另开 session 的 _to_item/delegate 查询去读未提交行，不在提交前发 Redis/消息/外部回调。seal、任何 flush 或最终提交失败时，候选主体/凭据/binding/审计/op/预占均回滚；原幂等重放先返回已有操作，不再次签发。该新增协议只补本次受理所需的 producer，不宣称修复历史回收审计 S1，也不重写全部签发流程。

  2. deploy() 普通同版本快速返回保持原语义；只对显式确认的 config_restart 路径创建新实例。active deploy 的查询/复用必须校验 purpose 和冻结请求，普通发布不得接管 config_restart，反之亦然；冲突复用既有忙/unknown 拒绝。重建固定 migration_plan=[]、不允许 snapshot/restore、preserve_pending_version=true，不调用 schema_evolution_service；源 version/delivery/profile/digest 和原执行 tier 不变，不重建镜像、不创建代码版本、不触发审批。

  3. manager 明确声明支持 config_restart 与敏感输出协议，否则重建拒绝并提示升级；保存仍可独立完成。按既有停止证明→新实例→探活→ready 事实执行。Docker 用 Engine Env，K8s 复用执行专属 Secret/secretKeyRef，Secret 只供 serve，helper/preparer/assembler 无真实值。不能仅 docker restart，也不通过 shell 插值。

  4. 本操作自身的 maintenance 路由转换：原 manager _deploy 在停止旧 writer 前会上报 maintenance，backend fact 调 RuntimeProjectionService.block 会递增 route_epoch；因此不能在 ready 时仍要求原 epoch 原样不变。新增该 purpose 的受围栏投影适配：在同一既有 fact/UoW 中核验 op 的有效归属和冻结 origin route（id/version/operation/exec_ref/epoch），再幂等消费 maintenance 事实、变更路由；在该 RuntimeOperation.payload 记录非秘密 maintenance_transition={fact_sequence,route_id,before_epoch,after_epoch}。同一 sequence 重放只返回原事实/转换收据，不再修改当前路由（即使后来已经 serving）；没有重复 block/递增。新的 maintenance 事实若已有转换，只能验证同一尚在途的维护状态，不能追加任意 epoch 或把新路由再封回旧维护态。ready 提交只接受未变的原 route，或本操作这条事实导致的精确 after_epoch、maintenance 状态及原 route 身份，不能用“epoch 更大即可”放行。其他 stop/delete/切流或不同操作造成的改变仍拒绝；不把网络封入口当作 writer 停止证明。该记录只是既有维护事实到路由投影的幂等消费，不是密钥 applied 状态、额外表或新配置成功回执。

  5. commit_runtime_delivery 为该 purpose 保留 current/pending 指针和原版本终态，只更新原有实例/route/credential/storage 投影；不调用 mark_runtime_online 重标版本，不写 F055 表或 applied receipt。原 expected state/current/pending/UID/代次校验不放宽，origin route 只允许上条证明的自身维护转换；审批或停用等改变关键指针时按既有冲突清理，不能覆盖新指针。保存配置变化不作为拒绝提交的条件：受理后 revision 可以继续增加，本次仍按被冻结环境完成，页面保留真实差异。

  6. 明确的异步 ready→commit 消费者：受理冻结 auto_commit=true，由现有 RuntimeOperationService.fact 在 ready 事实事务完成后调用 AppStateService.commit_runtime_delivery 的 config_restart 分支，不依赖一个已返回的 HTTP handler 等待。manager 仍按原协议等 serving；首次 commit 回滚时，持久 ready 事实保留，ready 上报的同参重放也必须再次尝试同一提交，不能因 fact 已存在而跳过 auto_commit。提交前 backend 进程退出由 manager 的原 operation/node-plan ready 续办触发原事实重报；不创建新操作、延长期限或配置专用调度器。manager/backend 都恢复不了则按原 deadline 显式失败，不挂成永久 pending。该消费者本身先结束 op→node 的 fact 事务，再进入 op→App 的 commit 事务，不跨两段持锁。

route/实例沿既有 UoW 原子提交。DB 回滚则只重试原 ready 提交；响应丢失或 serving/completed 重放，检查既有 op/route/exec_ref 的一致性即可返回原结果，不再增加配置结果双写。未知结果不再创建 operation/执行 DDL，不把已变更的 route 归为旧结果成功。差异仅从实际当前路由计算，不从某个成功回包推导。 9. 用户请求受理后可以继续保存；既有 operation 的 sealed_env 不替换。手动重建失败/取消/超时后，RuntimeDeliveryCoordinator.recover 与其他调度入口都读取现有 op.purpose/status，不把它自动转换成 recover deploy 再试；同一在途操作仍可按原期限续办/清理。旧 writer 未确认停止或 cleanup 未完成时，拒绝用户新 attempt；终态不等于已停。stop 可按原协议取消并清理，不授权强删。正常新版本发布、用户重新上线和独立崩溃自愈仍按各自既有生命周期；保存本身不会触发它们。

④ 差异计算合同

F055 查询服务消费 F054 公开 running_environment_snapshot(app_id) 只读协议，返回经租户/当前正式路由校验的内部 DTO（版本声明、operation/exec_ref/route_epoch、受限运行 env）；不从 F055 跨域查询 runtime ORM、不调用 manager inspect，不把 env 放进响应。生产方为 F054 route/operation Repository，权限在调用前由业务服务确认。

在短时一致读取中选取 current App/version、route 与对应 operation 的 sealed_env；重新确认 route identity 未变化后才报告 same/different。最新配置在本次读的 revision 上比较声明子集，未引用项忽略，缺项归一为空；不作值 trim/编码转换。A→B→A 归为 same；仅配置 revision 增长不能归 different。若无运行实例，not_running；已有执行但快照缺失/无法解密、状态未知或 route 变化不能安全比较，unknown 并给安全原因，不返回空集合冒充 same。读后再发生保存属于下一次查询，响应含所观察 revision/route epoch；前端丢弃旧请求并在保存/操作终态刷新。

运行上下文已由 operation 持有；只读服务不能返回任意历史 operation 的明文环境。日志及比较需要的受限上下文按现有操作留存管理；清理后不额外复制秘密历史，比较可用性退化为 unknown。changed_names 仅包含调用者有资格读取的当前声明名；审批人看版本缺值，不读生产差异。

⑤ 名称、平台变量与输出保护

保留 BISHENG_*、RTM_*、KUBERNETES_*、MINIO_*、OPENAI_*、HTTP_PROXY/HTTPS_PROXY/ALL_PROXY/NO_PROXY（含小写），及 PATH/HOME/LD_*/PYTHONPATH/PYTHONHOME/NODE_OPTIONS/PORT/HOST、启动器实际保留项，统一 deny policy、两侧测试锁定。禁止别名覆盖平台身份、模型通道、启动/依赖路径或出口；后续新增平台注入名必须同改 policy。

平台不打印写请求体/环境/引擎创建请求，错误只含 ref 与安全原因；runtime status/diagnostic 递归白名单序列化，禁 raw inspect/Secret 内容，日志下载不得拼接 env。客户端埋点不得读取密钥输入。

operation 绑定的敏感项合同：backend 从已批准版本的 capabilities.secrets 生成 sensitive_env_names（只含名），与 revision/declaration_digest 一起冻结在可信 operation；值仍只在 sealed_env。普通客户端不能提交或修改该集合。manager 从这一 operation 的 runtime_env 取这些名的值构建内存 SensitiveValues，不从“当前保存值”代替历史执行值；除原有平台 token/代理凭据规则外，这些业务值不受名称启发式或最短长度限制，空值忽略，短值/普通名一样处理。跨重启从受限 operation 重新取值，不能把敏感值清单写本地状态、日志、材料、query cache 或普通 JSON 诊断。

⑥ 前端/CLI/审读

应用页显示“应用密钥”，列名称、配置状态、每项更新时间与批准/待审批/未引用。保存只提示“已保存”；另一区域根据 comparison 显示“运行配置与最新保存配置不一致”、差异名或“无法确认”。无运行实例显示“下次启动使用最新配置”。提供“重建使配置生效”动作及独立确认，说明重建当前版本可能短暂中断，取消不发执行请求；保存按钮、删除确认和关闭表单都不能触发重建。操作进度消费既有 RuntimeOperation；失败保留配置和真实运行状态，需再次确认才试。删除说明当前实例可能继续持旧值；不显示新旧值。PUT 成功刷新安全元数据，不以旧 revision/HTTP 成功判生效。编辑空草稿、固定 mask 不作输入值，冲突保留未提交草稿；关闭/换应用/退出清理内存，过期异步响应丢弃。

D13：稳定列表与一次导出的固定读取视图（修订）

否决仅按秒级时间排序、offset 翻页、开放式追随新日志的无限导出，以及把 10,000 行/90 天预算当产品限制。列表采用 (event_time DESC,id DESC) keyset，首次查询固定 filter/scope 摘要、upper_time 与当前可见最大 id 的 watermark，cursor 绑定该选择条件；未知时间单独排序并以 id 决胜，不能在 NULL 比较上丢页；all 保留未知时间行，recent7d/custom 不能判入区间的未知时间行不伪造时间，筛选语义明确说明。新请求严格校验 cursor，不把解码失败当第一页。

列表只保存短时 RuntimeAuditQuerySnapshot 条件元数据并返回第一页；不为了列表先收集所有 ID，不依赖 MinIO 才能看数据。刷新/改变条件重新选择范围。列表与随后导出共享冻结的条件、watermark 和权限；并发写入下不额外承诺两个不同读取时点的数据库成员集合完全相等。导出会展示其实际选取时点及最终行数，不把导出完成数冒充此前列表的即时统计。

完整导出在后台的一次受权读取视图中完成：任务受理时冻结 QuerySnapshot 的过滤/范围，source-owner Repository 在 worker 开始扫描时打开一条、范围有界的 ORM SELECT 只读一致游标，按稳定顺序流式输出全部匹配记录。该语句的读视图固定、watermark 固定；后续新增/回填提交不能把本次扫描变成无限流。每批最多 500 行处理/输出，但一直扫描至该读取视图 EOF，不能达到某行数后拒绝或截断。无资格/跨租户条件在源 SELECT 构造/执行时仍走自动租户过滤或显式授权的全局 Repository，而不是把多租户约束留给 CSV 写入端。

source Repository 提供 stream_export(scope, frozen_filter, watermark, batch_size)，持有只读 source session/游标至本 attempt 扫描结束；任务进度写入用另一短事务 session，不在源读取事务中写状态。底层必须采用真正流式/受限 fetchmany，不用 all()/fetchall() 把整表搬进内存；MySQL/DM8 由各 source-owner 适配其固定读视图游标/事务，定向检查驱动的实际缓冲和语句范围，不能仅设置 yield_per 就宣称有界。占用一个后台读连接/读视图至扫描结束是此方案的显式成本，以导出 worker 并发、可观测持续时间及运维取消控制，不在 HTTP 请求保持长事务，也不转成 90 天/行数硬门槛。

worker 崩溃后无法恢复数据库游标读视图，因此未 ready 的 attempt 整次只读重建，不拿旧游标偏移接新视图造成漏/重；同一冻结条件与 watermark 下重新开启读视图，显示新的 selection_started_at。旧 attempt 从未交付字节，只保留待清理私有分块；只有一次完整扫描的 manifest 才能原子发布为 ready。ready 后的文件成员与字节固定，重复下载不会重新查事实表。若历史清理/读取故障导致不能完整输出，显式失败，不标空文件或部分文件成功。

D14：受权异步导出与不可变分块产物（修订）

否决公开 presigned URL、前端只导当前页、提交时授权永久放行。选用后台固定读取视图 → 标准 CSV → MinIO 私有不可变分块 + 有序 manifest；backend 认证下载按 manifest 依次流式拼接为一个 CSV，不暴露对象 URL。CSV 标题/BOM 只在首块，每个分块在完整行边界收束。任务状态为 pending/running/ready/failed/expired；总记录数不设产品上限。

任务通过 DB 租约/epoch 取得单一输出权；对象 key 绑定 job/attempt/epoch/part_no，上传确认后短事务登记分块及累计行数。ready 的 CAS 必须同时校验当前 lease/epoch、同一 source read-view attempt 已 EOF、全部分块已确认且 manifest 有序/完整。旧 worker 只能遗留未引用的私有对象，不能覆盖新 attempt 或把任务标 ready；响应丢失重查持久 ready/manifest，不能追加重复 CSV 行。失败或重启按 D13 从头读取新 attempt，不拼接不同读视图的分块。

受理、worker 开始/每批和 ready 发布、状态读取、下载开始/受限块之间都核验当前自然人管理员资格与保存的 scope。失权或无法确认即取消交付/停止任务，不使用提交时缓存永久授权；已交付字节无法收回。条件快照未被任务引用时 10 分钟过期；任务受理后其冻结条件由任务持有，不因排队/扫描超过 10 分钟被清理。下载保留期从 ready_at 开始计算 10 分钟，未完成 attempt 由租约/取消和终态 GC 管理，不能用该保留期限制记录总量或扫描时长。

CSV 仅白名单字段；危险公式文本前置单引号后按标准 CSV 转义，测试空白/控制字符绕过、逗号、引号、换行与 Unicode；数值按数值，null 不替成其他主体。对象/worker/source 不可用时明确失败，GC 只删没有活跃 lease/ready manifest 引用的本任务对象；就绪产物到期/取消清理有 durable 状态，不依赖本地盘。未来确需更高吞吐再独立调度，不改变完整导出的规格。

D15：可信应用关联的操作审计（新增）

F055 负责写 app.secret.*；凭据 owner 在签发/撤销时从持久 ApiCredential.subject_kind/subject_id 与可信 hosted-app 归属映射计算 target_app_id，不取查看者传的 app_id；SAK/PAT 的资源 owner 不等于 app 归属，不能把该人的所有 key 自动关联给某应用。

现有 CredentialService._audit 只写 credential_id/subject/scopes/key_mask，需要补可信关联；历史记录只能在原始可信字段足以确定时通过只读关联查询，不补写历史“现在属于”。不增加第三方业务密钥末位/长度，API key 原有前缀/末位 mask 继续保留。若普通凭据没有可信 app 绑定，明确不相关，不硬凑。后续新 credential owner 需提供同一审计关联协议。

③ QuerySnapshot / RuntimeAuditExport（拟新增）：仍为两个申请者私有实体，不新增永久审计大表或全量 ID 选集副本。RuntimeAuditQuerySnapshot 保存 UUID、tenant_id（默认 None/NOT NULL/索引）、creator_user_id、scope_mode/scope_tenant_id、kind、normalized_filter JsonType、filter_digest、watermark、created_at/expires_at；只含条件，不含事实正文或完整 ID 集。tenant_id 取服务端确认的申请者有效工作租户，global 是经超管核验的过滤范围，不以 NULL tenant 绕过自动过滤。

worker 按持久任务 tenant_execution_scope 初始化租户过滤，只有源数据读取在已授权的 global source Repository 中 bypass；后台每批重验申请者当前资格，不能只信任务里旧角色。源只读扫描与任务短写事务分开；领取/重试/ready/GC 以数据库 CAS 和租约处理多进程。未引用条件快照 10 分钟清理，受理后由 job 保留冻结条件，下载到期从 ready 算起；失败/取消且无活跃 lease 的孤儿块可回收，活跃扫描不删。

④ Scope / Cursor 安全：

  • AuthorizedRuntimeAuditScope 仅由服务端权限适配生成；自然人角色来自可信登录态与权限 application 协议当前核验，不信请求角色/租户。旧审计允许 log-menu 的逻辑不复用到此处。
  • 普通租户 Repo 在 tenant_execution_scope 下自动过滤；全局超管 Repo 仅在明确授权 scope 下 bypass；客户端 tenant_id 只允许进一步收窄。跨租户 app/visitor/credential ID（含历史 tombstone）在限权解析器中验证，拒绝与未知 ID 对外同样不泄漏详情，不把 foreign ID 默默当“查无”。候选从事实表/可信删除保留信息产生，不能凭当前用户/应用列表扩范围。
  • cursor 是服务端签名/摘要校验的 {version,kind,scope_digest,filter_digest,snapshot_id,last_event_time,last_id,expires_at}，不包含明文凭据。切租户/视图/筛选不能重用；解码/签名/过期错明确拒绝而非回第一页。
  • 每次 list/candidates/export/status/download 都重验角色/范围；后台任务实际执行时再验提交者资格。无法确认权限 fail closed；不是仅靠 JWT 缓存角色永久允许。已交付字节不可收回，失权后不开始新下载或继续交付后续 chunk；不承诺撤回浏览器已收到的文件。
