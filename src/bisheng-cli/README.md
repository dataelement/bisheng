# bisheng CLI

`bisheng` 是毕昇应用工场的开发者命令行工具：拿服务账号密钥登录平台、把本地项目打包发布成托管应用、查看自己名下应用的运行日志。

它是一个**独立的 Python 包**，不依赖后端代码、不连任何数据库、不访问公网。安装件由平台自己分发，运行期只访问 `login` 时指定的那一个地址。

本版本提供 `login` / `deploy` / `logs` / `skills sync` 四条命令。`dev` 随后续版本提供 —— 它**没有**注册进命令行，`--help` 里看不到，也不会给出占位报错。

---

## 安装

安装件由平台分发，不需要连公网 registry：

```bash
# 下载到一个带 .whl 后缀的文件名，再装（-o 指定文件名，别用 -sO：
# 那会按 URL 最后一段存成 download，装不上）
curl -o bisheng_cli-3.0.0-py3-none-any.whl http://<平台地址>/api/v1/dev-toolkit/cli/download
pip install ./bisheng_cli-3.0.0-py3-none-any.whl

bisheng --version
```

要求 Python ≥ 3.11。运行期依赖只有 `httpx` 与 `PyYAML` 两条 —— 每多一条依赖，就多一次「客户内网 pip 镜像里没有这个包」的失败面。

平台上是否提供该端点，取决于是否部署了开放能力层。若 `GET /api/v1/dev-toolkit/versions` 返回 404，说明该环境未部署（或平台版本过老），此时 CLI 无法使用，`login` 会给出可读原因并以确定的退出码结束（见退出码 8 / 9）。

## 命令

### 全局参数

| 参数 | 说明 |
|---|---|
| `--version` / `--help` | 版本与帮助 |
| `--json` | 机器可读输出：NDJSON 走 **stdout**，人读文本走 **stderr** |
| `--verbose` | 打印请求方法 / 路径 / 状态码 / 耗时（**Authorization 头恒掩码**） |
| `--quiet` | 只输出错误 |
| `--timeout` | 普通请求读超时秒数（默认 60；上传固定 240） |
| `--no-proxy` | 忽略 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 环境变量 |

本版本**没有** `--platform` 参数：命令一律使用 `credentials.json` 里 `current` 指向的平台（由最近一次 `login` 覆盖）。也**没有** `--as` 或任何指定他人身份的参数。

### `bisheng login <BASE_URL>`

校验密钥并把凭据写入 `~/.bisheng/credentials.json`（目录 `0700`、文件 `0600`）。

| 参数 | 说明 |
|---|---|
| `--api-key` | 直接传密钥（会进 shell 历史，建议用其它方式） |
| `--api-key-stdin` | 从标准输入读密钥（非交互环境首选） |

密钥来源优先级：`--api-key` > 环境变量 `BISHENG_API_KEY` > `--api-key-stdin` > 终端隐藏输入。四者皆无且没有终端可问 → 退出 2（**不会**默认取空值去试）。

```bash
BISHENG_API_KEY=bs-sak-… bisheng login http://<平台地址>
ls -l ~/.bisheng/credentials.json     # 必须是 -rw-------
```

输出目标平台、服务账号名、资源归属人、密钥掩码、到期时间。
**`login` 不校验任何权限位** —— 一把还没勾任何位的有效密钥也能登录成功，这样「密钥不对」和「密钥缺权限位」才是两个可区分的诊断。
被配置为**委托专用**（`delegate`）的密钥会被拒绝，且**不写入凭据**：这类密钥用于身份传递，本地开发要另外签发一把。

> 密钥以**明文**保存 —— 每次请求都要用原值，没有可派生的东西。文件权限位是唯一保护，所以文件用 `os.open(..., 0o600)` 一步创建，不存在「先写再 chmod」的可读窗口。凭据**永不**写进工程目录，也**永不**进上传包。
> 凭据里**不存 `scopes`**：权限位由服务端每次调用重新判定，客户端一旦缓存就会出现「管理员补勾了但 CLI 还说没权限」。

### `bisheng deploy [PATH]`

打包当前项目并发布。`PATH` 默认为当前目录。

| 参数 | 说明 |
|---|---|
| `--app-id` | 显式指定目标应用（覆盖 `.bisheng/app.json`） |
| `--dry-run` | 只做本地校验与打包、打印体量统计，**不上传**，平台上不创建任何东西 |
| `--wait` | 等待审批与上线结果落定（默认不等：审批是人工动作，可跨天） |
| `--wait-timeout` | `--wait` 的最长等待秒数，默认 1800 |
| `--confirm-schema-change` | 确认本次发布包含应用数据表结构变更 |
| `--yes` | 跳过迭代发布时的目标应用确认 |

```bash
bisheng deploy --dry-run                       # 先看打包体量与忽略统计
bisheng deploy
bisheng deploy --wait --json | tee deploy.ndjson; echo "exit=$?"
```

**本地只做三项快速失败**：`bisheng-app.yaml` 存在、可解析、含 `name` / `runtime` / `port`。其余字段（`tier` / `capabilities` / `database` / `egress` …）一律不在本地判 —— 声明的权威校验在平台托管预检，本地自造校验或缺省值只会制造「本地过、上传被拒」。

**打包规则**（三层，从内到外）：

1. 结构性排除。**硬排除、`!` 取不回**：`.git/` `.hg/` `.svn/` `node_modules/` `.venv/` `venv/` `env/` `__pycache__/` `*.pyc` `.pytest_cache/` `.ruff_cache/` `.mypy_cache/` `*.egg-info/` `.DS_Store` `.bisheng/`。**软排除、可用 `.bishengignore` 的 `!` 取回**：`*.db` `*.sqlite` `*.sqlite3` `dist/` `build/` `attachments/` `uploads/`。
   （`dist/` 刻意不硬排：存量应用把前端构建产物放那里交后端静态托管是常见形态，硬排会把它静默剥掉，而故障要到构建或探活阶段才暴露。）
2. `.gitignore` 语义。是 git 仓库且本机有 git → 直接交给 `git ls-files` 算；否则回落到自研子集解析器，并在输出里明说。
3. `.bishengignore`（可选，同 `.gitignore` 语法，最后加载、优先级最高）。

打包**绝不静默截断**：超限就整包拒绝并列出「已排除多少 + Top 10 最大文件 / 目录」。符号链接、设备文件、FIFO 会被本地跳过**并列出**（服务端解包闸会拒它们）。文件模式归一为 `0644`，但**保留 owner 执行位为 `0755`** —— 丢了它，entrypoint 上线后不可执行，而排查方向会指向「平台构建有问题」。同样内容两次打包产出同样的 sha256。

**应用标识**存在项目根的 `.bisheng/app.json`，按平台地址分键。建议**提交进 git**（团队共享同一个应用），它**不会**进上传包 —— 「进 git」与「进包」是两件事。
标识在 `POST /deploy` 返回 200 的那一刻就写盘，**不等管线成功**：首发预检失败时平台已经建好草稿应用并分配了标识，只在成功时才保存会让你修完 manifest 重跑时**再建一个应用**。

**迭代发布有误投护栏**：上传前打印目标应用的名称与标识。指定了归属人不同的应用会被服务端拒绝（安全），但指定了**同一归属人的另一个应用**会真的更新那一个 —— 那是无声的错误，所以非交互环境下这行输出就是唯一的护栏。

**默认不等审批**：轮询到审批单生成即返回 0，并给出三条跟踪路径（应用详情页·发布 / MCP 应用状态工具 / `deploy --wait`）。撤回只在应用详情页·发布做，CLI 不提供撤回命令。

### `bisheng logs`

查看自己名下应用的运行日志。

| 参数 | 说明 |
|---|---|
| `--app-id` | 显式指定应用（覆盖 `.bisheng/app.json`） |
| `--tail` | 返回最后 N 行，默认 200 |
| `--since` | 起始时间：**epoch 秒**，或 `30m` / `2h` / `7d` 相对窗口 |
| `--keyword` | 只返回含该关键字的行 |
| `--follow` | 持续拉取（短轮询 3 秒；服务端无流式接口） |

```bash
bisheng logs --tail 200
bisheng logs --since 30m --keyword ERROR
bisheng logs --follow
```

几条容易误判的事实：

- **带 `--keyword` 时返回行数可能少于 `--tail`** —— 过滤发生在服务端，这是设计不是截断，CLI 不会因此重试或告警。
- **`--follow` 会去重**：容器日志时间戳是秒级，同一秒的行会在下一轮窗口里重复返回。
- **取不到日志不等于「什么都没发生」**：可能是应用没有运行实例（草稿 / 待上线 / 已下线），也可能是该时间段的日志已被轮转。平台对日志保留期不做承诺。
- **归属判定完全在服务端**：owner-only 按密钥的**资源归属人**判，CLI 不做任何预检 —— 它拿不到权威数据，加一处判定只会与服务端分叉。

### `bisheng skills sync`

把平台**当前版本**的开发者技能包同步到 `~/.bisheng/skills/`。技能包是给 AI 编程工具读的指引 —— 让它照着平台的托管运行契约写出可部署的应用。

- **登录时自动执行一次**（`login` 成功后即触发），一般无需手动敲；平台升级后重跑即更新到新版本。
- **单向覆盖**：技能包是平台发布物，sync 以平台版本覆盖本地内容、并列出被覆盖的文件，**不做合并、不保留本地改动、不覆盖前确认**。要定制团队自己的约定，写在项目的 `AGENTS.md` 里、放在技能目录**之外**。
- 同步完成后会输出「怎么让你的 AI 工具用上它」的指引（Claude Code 自动发现；其它引擎经 `AGENTS.md` 指向同一目录）。
- 平台未部署开放能力层（端点 404）时以退出码 8 结束并提示。

```bash
bisheng skills sync
```

## 退出码

退出码是**对外契约**，本地 coding agent 靠它决定下一步。分格判据是**下一步动作是否不同**，不是错误的严重程度。

| 码 | 含义 | 下一步 |
|---|---|---|
| 0 | 成功（`--wait` 下 = 通过并上线） | — |
| 1 | CLI 内部未预期异常 | 加 `--verbose` 重跑并报障；可以先重试一次 |
| 2 | 用法 / 参数错误 | 补齐参数 |
| 3 | 未登录 | 先 `bisheng login` |
| 4 | 鉴权失败（`26001` / `26002` / `26027`） | 换 / 重签一把密钥；`26027` 是账号被停用，要找管理员启用 |
| 5 | 权限不足或委托专用密钥（`26003`） | 找租户管理员编辑该密钥的权限位（无需重新签发） |
| 6 | 本地校验失败 / 包不合法（`16101` `16201` `16202` `16203`） | 改本地再传 |
| 7 | 平台不可达 / 服务暂不可用（网络错误、`26030`、`16121`） | **可重试** |
| 8 | 环境未启用（分发端点 404、`16207`） | 找管理员开开关并重启后端 |
| 9 | 平台版本过老，不支持本 CLI | 升级平台，或换用与平台同版的 CLI |
| 10 | 托管预检失败（`16221`–`16224` `16227` `16228` `16230` `16231`） | 改 manifest / 改代码后重发（`16230` / `16231` 是删掉 `capabilities` 声明） |
| 11 | 密钥扫描命中（`16241`） | 移除密钥后重发 |
| 12 | 发布流程冲突 / 归属与操作权限（`16205` `16229` `16251` `16252` `16254`） | 撤回在途单，或换归属人正确的密钥 |
| 13 | 平台未配置发布审批场景（`16225`） | 找平台管理员，**改代码无用** |
| 14 | 运行环境容量不足（`16226`） | 等资源 / 稍后重试 / 让归属人手动上线 |
| 18 | **缺陷类**（`26004` = CLI 缺陷，`26031` = 平台缺陷） | 停下报障；**重试与改参数都无用** |
| 19 | 平台返回未登记的错误码 | 按打印出的 `code` + `message` 处置 |
| 20 | `--wait` 终态：审批被驳回 | 按驳回理由（全文输出，不截断）修改后重发 |
| 21 | `--wait` 终态：审批被撤回 | 撤回发生在应用详情页·发布 |
| 22 | `--wait` 终态：待上线 | 等资源，或由归属人在应用详情页·发布手动上线 |
| 23 | `--wait` 超时 | **这不是失败** —— 继续等或换跟踪方式 |
| 24 | `--wait` 终态：审批单已取消（目标应用被删除） | 这一单不会有结论；重新发布会创建新应用 |
| 25 | `--wait` 终态：审批异常（审批人解析为空） | 找管理员处理审批异常；这一单不会有结论 |

> `13` 与 `14` **绝不合并**：前者是「平台没配审批场景，改代码没用」，后者是「机器没资源，等一会儿」。
> `18` 与 `1` / `19` 也**绝不合并**：`1` 值得重试一次，`19` 可以改参数再试，`18` 两者都保证无用。

## `--json` 事件契约

加 `--json` 后，**stdout 的每一行都是一个 JSON 对象**（人读文本一律走 stderr，所以管道不会被进度文本污染）。三种事件：

```jsonc
{"event":"stage","command":"deploy","stage":"precheck_build","status":"running","ts":"…"}
{"event":"progress","command":"deploy","phase":"upload","sent_bytes":123,"total_bytes":456}
{"event":"result","command":"deploy","ok":false,"exit_code":10,
 "data":{"deployment_id":"…","app_id":"…","version_id":"…","entry_url":null,
         "stage":"…","app_state":"…","pending_reason":null,"approval":{…}},
 "failure":{"stage":"…","code":16227,"message":"…","details":{…},"hints":["…"]}}
```

可依赖的不变量：

- **`result` 恒为最后一行，且每次运行恰好一条** —— 崩溃路径也有。只读最后一行就能判定结果。
- **`stage` 恒为服务端原值**，不翻译；不认识的阶段原样透传，**不是错误**。阶段的**顺序由服务端决定**，CLI 不做顺序假设（服务端已经调整过一次），所以不要在消费端写死顺序。
- **`failure` 是服务端五元组的原样透传** —— `details` 与 `hints` 一个字都不吞，那是本地 agent 自动修复的全部输入。
- 同步段的失败**没有 `stage` 事件**：`POST /deploy` 的同步错误直接落进 `result.failure`。
- `data.entry_url` 只可能来自 `POST /deploy` 的返回，首发时通常为 `null`；**不要把 `null` 当成上线失败**，看 `exit_code` 与 `data.app_state`。

```bash
bisheng deploy --wait --json | jq -c 'select(.event=="stage")'
bisheng deploy --json | tail -1 | jq .exit_code
```

## 排障

**1. 先看 body 里的 `status_code` 是 `20001` 还是 `260xx`。**
多租户环境下默认租户被禁用会返回一个与密钥完全无关的 `20001`/403。把它当成「密钥不对」会让人反复重新签发密钥，而真正要做的是去解禁默认租户。

**2. 「平台不可达」十有八九是代理。**
`httpx` 默认读 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`，而开发机上常年挂着通往公网的代理、平台却是内网地址 —— 请求被送去代理后超时或拿到代理的 502，看起来就像平台挂了。CLI 在连接失败时会把检测到的代理变量名和值打出来。处置：把平台地址加进 `NO_PROXY`，或加 `--no-proxy`。

**3. `deployment_id` 是与平台侧对账的唯一凭据。**
「CLI 说失败了」要拿 `deployment_id` 去平台侧的发布记录与 `app.release.*` 审计事件对账，不要只看终端输出 —— CLI 没有服务端日志。

**4. 首次 deploy 就被拒且提示包太大？** 先看输出里「已排除多少项」。绝大多数情况是 `.venv/` 或 `node_modules/` 没被排除（本地不是 git 仓库时忽略规则走子集解析，复杂规则要写进 `.bishengignore`），而不是平台上限太小。

**5. 输出里永远不会出现密钥。** 包括 `--verbose`：`Authorization` 头恒掩码。扫描命中只打 `文件:行号` 与规则名，CLI 也不会去本地文件里把那一行读出来补打 —— 那等于把服务端刻意不给的东西自己补回来。

## 开发与发版

```bash
cd src/bisheng-cli
uv sync --extra dev
uv run pytest            # 带 @pytest.mark.network 的用例默认跳过
uv run ruff check .
uv run ruff format --check .
```

**发版契约**：改了 CLI 就必须重跑

```bash
bash scripts/pack_cli_wheel.sh
```

并把产物（`src/backend/bisheng/dev_toolkit/artifacts/` 下的 wheel 与 `manifest.json`）**一起提交**。后端镜像的构建上下文只有 `./src/backend/`，`src/bisheng-cli/` 不在镜像里 —— 不提交产物，平台分发的就还是上一版 wheel，而且没有任何提示。该脚本自带「装进干净 venv 后 import 生产入口」的冒烟：源码树里跑 pytest 永远看不见「依赖解析到新版本后 import 期就崩」这一类问题，因为它测的是开发环境已经解析好的那组版本。

两条依赖（`httpx` / `PyYAML`）**都带上界**。CLI 的分发路径是开发者机器上的 `pip install <wheel>`，`uv.lock` 在那条路径上完全不参与解析 —— 能约束它的只有 wheel metadata 里的上界。放宽上界是一次显式决定（先跑通打包脚本的冒烟），不是顺手升。
