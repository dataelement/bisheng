## 3. Constitution Check

全局规则以 [constitution.md](../../../docs/constitution.md) 为准，以下只记录本设计的检查结果与落点。

| 约束 | 检查结论 |
|---|---|
| C1 | 新接收端只编排 Service/Repository；拟提取通用 HMAC primitive 供既有 SSO 与 DSH 入站适配共同调用，不跨 API 调用 SSO。审计增量不接入 model.complete 的执行判断 |
| C2 | backend 使用现有方言适配，Gateway 提供两种 DDL；条件领取、游标和摘要不依赖 MySQL 独有语法。真实 DM8 验证仍待实现阶段 |
| C3 | 精确服务认证分支不启用前缀 bypass；签名后建立严格租户范围，执行线程单独设上下文；写操作显式限定租户、编号和版本 |
| C4 | 管理操作经既有 backend 自然人及租户管理运行时校验；不以 profile、浏览器角色字段或本地角色表自行授权 |
| C5 | 使用既有 261 模块；候选 26170–26175 当前静态无占用，实施时重查并登记。平台与 DSH 两种错误合同区分 |
| C6 | 密钥沿用 Gateway 与 backend 现有共享 HMAC 配置，不另复制为 DSH 独立配置；不记录 Token、Cookie、正文或签名内容 |
| C7 | 平台请求走 API wrapper，新增取数按当前根 AGENTS 的 v4 约定；不在 store 中请求 |
| C8 | 事实、租约、dirty、版本和保留水位在 SQL/Redis；本机缓存及连接不可作为跨实例真相 |

未发现设计违反以上约束的 BLOCKER。该结论是静态设计合规性，不是运行时权限或双库兼容证明。

## 5. 用户评审时需关注的设计取舍

- 外部事实表配主表摘要，默认明细不自动清理；30 天只是容量评估，实际保留要与原审计规则统一。
- 为满足 30 秒有界续读，模型上游连接由 DSH 专用路由管理，不依赖默认代理闭流后的游离订阅。
- 策略管理临时复用已有 DSH 审计 settings 的只读授权能力，保持 backend 不新增 Gateway 专属管理接口；该依赖只在管理动作发生，不进入模型检查热路径。
- 词库摘要不相符的副本拒绝检查；首期不承诺跨内置词库版本滚动发布不停服。

用户确认 design 后才进入 tasks 拆分。本记录未将“自审通过”替代用户确认。

## 7. HMAC 配置确认与 profile 定义

用户明确使用现有相同 HMAC 密钥配置。design §3.4、§4.3、§4.7、§4.10、§4.11、§6.2 已同步：Gateway 使用 bisheng.gateway-hmac-secret，backend 使用 sso_sync.gateway_hmac_secret，两端值一致；签名头和 METHOD/PATH/raw body 规则沿用现有实现，移除 DSH 独立密钥变量、密钥登记表及独立 key_id 协议。接收端仍独立处理正文、时间窗口、幂等和租户上下文，不将 SSO 正文回放或租户 bypass 接到 DSH 模型路径。

源码复核：desktop_principal 调用 DshAccessService.authenticate 验证 Token、当前身份及会话；GET /dsh/profile 再调用 IdentityService.profile 读取当前用户和租户资料，返回 user 与 tenant。design §4.4 已注明 profile 是服务端成功验证后的返回信息，缓存对象是该验证结果，Gateway 用 tenant.id 选择租户策略。

本次仅修改 design 与评审记录，spec 验收条目未改动，未进入 tasks 或业务实现。
