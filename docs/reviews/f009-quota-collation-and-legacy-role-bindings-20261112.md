## 配额排序规则修复

`QuotaRepository.usage_statement` 的频道/空间订阅计数都曾使用裸 `CAST(parent.id AS CHAR(36))` 连接 `space_channel_member.business_id`。MySQL连接与列排序规则不同时报1267，同时影响F009预检和线上配额读数。

复用现有 `StrJoinKey`：MySQL显式使用 `utf8mb4_unicode_ci`，非MySQL走公共helper的普通CAST，不把MySQL的COLLATE发到DM。不改表、字符集、连接设置、预算逻辑和租户谓词。个人订阅仍计当前Home与Root，排除其他子租户；租户总量仍仅本租户。查询失败仍报不可用，不按0放行。

验证：MySQL个人/租户×频道/空间4项SQL回归先红后绿。含SQLite三租户计数、配额链、有效角色/登录和dialect_helpers的选集 **101 passed / 2 skipped**；真实DM方言编译因本机方言模块不可导入而跳过。未验证真实MySQL/DM8服务端或迁移现场。Ruff、架构守卫及空白检查通过。

## 推荐：独立的一次性绑定归属转换

全局角色的定义可复用，不等于用户同时拥有Root与各子租户的执行权限。以用户A为例：

| 事实 | 当前值 | 建议处理 |
| --- | --- | --- |
| 全局角色定义 | 角色12由Root维护，Role.tenant_id=1 | 定义、角色ID、菜单与作用域不搬、不复制 |
| 用户主属 | 实际主部门及运行时确认Home=13 | 以当前身份/组织事实为准，不从旧绑定猜归属 |
| 旧绑定 | UserRole记录A→角色12，tenant_id=1 | 确认为旧存储语义后，将这条绑定归到13 |

转换后仍用同一角色12，并按定义原归属读取菜单，不把Role.tenant_id一并改成13。用户在13使用这份普通策略；访问具体资源仍受当前租户和PermissionService约束。

当前源码支持此区分：`effective_roles._binding_ids`只读Home内绑定，`eligible_role`判断global/本租户角色及部门作用域，`effective_role_repository._menu_statement`按Role定义归属读取WEB_MENU。登录、info、菜单、配额、审批标签及DSH必须使用一致的有效策略，不能只在登录时兼读Root。

### 候选与例外

| 当前事实 | 建议 |
| --- | --- |
| 原Root普通绑定，角色为合法global且满足现有部门作用域 | 列入一次性转换候选；截图4位用户属于该类的描述，实施时核对实际行 |

| Home已有相同角色 | 不重复授予；保留目标行，只备份并退役计划内Root冗余源 |
| 外租户非合法global角色、角色已删、部门作用域不符、主属歧义或明确撤权 | 不自动转换，列例外名单，由当前租户管理员显式分配合法角色 |
| 平台超级管理员或独立管理员身份 | 不通过本转换新增、迁移或推断管理员身份 |

首批仅处理已确认的旧Root存储场景，不将所有“绑定租户不等于Home”都视为历史bug。真正跨租户调动后的旧政策可能本应终止。不能通过清空department_id、猜同名角色、复制外租户角色或补默认角色来解决登录。

### 操作与业务影响

1. **独立F009升级步骤**：旧写服务停止、新版SSO及角色写入口尚未启用时盘点。扩展专用盘点为完整分页与完成标志；现有只读preflight有limit/truncated，单次截断输出不是全量完成。不把角色治理塞回F118知识迁移。
2. **预览有限计划并批准**：保存源复合键、原tenant/时间/行摘要、目标Home、角色定义/部门资格及策略差异，备份选中行；按类别批量审阅，例外单列。比较角色、菜单、角色额度与Home租户上限、审批标签、DSH策略。不清资源用量、账单、余额或资源ACL。重新生效的角色会影响这些能力，不能仅凭global就宣称没有授权影响。
3. **原位条件更新**：按用户锁定并重验主属、源行与角色事实；只把仍匹配原复合键及原tenant的源行改归Home，user_id/role_id和创建时间不变。已有目标时不INSERT，处理已批准的冗余源。变更及前后证据在同一用户事务入现有策略审计；事实漂移时停止该用户，不另选目标。
4. **验证后恢复服务**：验证登录、info、菜单、配额、审批与DSH一致，外租户资源仍拒绝；普通角色恢复不复制资源授权。真正无角色和未解决例外保持原拒绝，作为开服可用性清单处理，不静默吞掉。

现有`grant_policy_bindings`/`replace`只对Home增删，直接补插会留下Root旧源，不能直接充当转换操作。需在既有策略Repository/application边界提供专用条件转换，沿用AuditLog约定增加迁移原因和原值。无需恢复中心或长期补偿队列；本方案尚无apply脚本。

### 不能让后续撤权被重跑恢复

迁移来源只能是已批准计划中**当前仍存在、原值未变的源行**，不能从备份INSERT。原位更新提交后Root源不再符合条件；之后用户撤销Home绑定，源行已不存在，重跑只能报告已处理/已变化，不能再补。去重也应退役计划内Root冗余源，不留下未来的恢复依据。

逐用户事务及结果记录支持同一有限计划续跑；只重试未成功且原值未变项。服务恢复写入后不后台自动重试旧计划。不自动全量回滚，纠正也须核对后续操作并生成新的有限计划。

UserRole确有创建/更新时间，但它们不能证明从未撤权；Root旧行还在也不能证明仍有授予意图。**已开服且发生过角色操作的环境**，须结合当前管理员确认及可用审计限定候选；不能把“没有撤权日志”当成未撤权。无法确认的先不迁，备份仅供核对与审计，不是恢复指令。

### 运行时保持严格

有效普通角色继续只取当前Home绑定，不长期合并Root/其他租户绑定。角色定义范围、菜单归属、管理员身份与资源授权各按现有规则；不自动发默认角色或移除10609闸。

若产品希望“全局角色不仅所有部门可选，而且用户换租户后绑定也永久跟随”，那是另一种契约。需统一全局绑定的授予、撤销和全部消费者，并明确谁有权给未来其他租户中的用户授予这份政策，避免原租户管理员持续影响新租户。不能只删除读取中的tenant过滤而保留按Home撤权的写法。推荐先采用本方案的“定义复用、绑定归属当前Home”，不把跨租户永久人员策略混入升级兼容。

若后续希望无角色人员也能认证进入“待分配”页面，应单独评审最小账户入口和业务API拒绝规则，不能直接去掉登录校验。此提案不包含该产品变更。
