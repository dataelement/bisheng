## 1. 推荐结论与交付边界

保留现有两种 `role_type`，不新增角色继承体系：

| 概念 | 存储与语义 | 维护和分配 |
| --- | --- | --- |
| 本租户角色 | `role_type=tenant`；定义属于一个业务租户 | 沿用现有租户/部门管理资格；只在定义租户内合法分配 |
| 平台共享角色 | `role_type=global`；同一角色 ID 可被多个租户引用 | 仅平台超管维护定义；租户内有权管理员可以合法分配 |
| 部门范围 | 独立使用 `department_id`；空值表示在该角色可用租户内不限制部门 | 不用“全局”同时表达全部部门和跨租户共享；既有部门资格规则仍有效 |
| 人员普通绑定 | 继续属于用户唯一当前主属租户（下文称 Home） | 共享定义不使绑定随人永久跨租户，也不产生跨租户资源权限 |

本批交付三条闭环：新建角色明确范围；已有定义/绑定兼容；部门行政划分时按预览确认的计划承接普通角色。真正人员调岗继续终止旧普通绑定、按目标规则重新授予。

不纳入：整体复制父租户角色目录、按名称推断角色、共享定义自动分叉/同步、资源授权复制、资源搬迁、全平台恢复中心、重做 DSH 结算或审批引擎。管理员身份、个人菜单授权与具体资源授权均不随普通角色承接。

| 当前源码事实 | 必要修改 |

## 3. 创建、维护和界面规则

1. `RoleCreateRequest`增加可选 `role_type: Literal['tenant', 'global']`，缺省为 `tenant`。超管在具体租户管理视角创建本租户角色时，定义、查重、WEB_MENU 和部门校验均使用该已授权目标。全租户汇总视角须先选择具体目标，不能猜为本人 Home。
2. 显式选择 `global`必须通过平台超管资格校验。新平台共享定义统一以 Root 为定义所有者；WEB_MENU 跟随定义所有者保存。既有共享定义即使所有者不在 Root，也保持原所有者，继续按现有精确归属读写，不顺带迁菜单。
3. 现有定义编辑不提供类型/所有者转换。需要让某租户独立维护时，显式复制为新的本租户角色；这是新定义，不自动替换所有使用者。共享定义调整前展示影响租户/人数，说明所有引用者后续决策会跟随变化。
4. 部门管理员保留现有更窄的创建和维护范围；本批不借默认类型变化放宽其“全部部门”资格。部门归属按业务挂载事实判定，不用 `Department.tenant_id`代替业务租户。
5. 列表/详情沿用 `role_type`，补充定义所属 `tenant_id`（必要时附名称）供汇总视角识别来源。共享定义对租户管理员只读，但合法分配候选可见。候选可见、定义可编辑、最终绑定合法分别校验。
6. 三语界面统一为“本租户角色 / 平台共享角色”和“全部部门 / 指定部门”。原有 API 路径及角色 ID 保持；省略类型的旧创建请求仍可提交，但新建结果改为本租户角色。确需共享的旧调用方须显式传类型，不能保留“超管隐式共享”的旁路。

平台内置角色常量及 AdminRole 的独立身份语义保持原样；不能把管理员角色当普通模板复制或改绑。

## 4. 已有角色定义与合法绑定的兼容

| 存量 | 本批处理 |
| --- | --- |
| 已有 global 定义 | 原 ID、所有者、菜单、quota、部门范围全部保留，展示为平台共享角色；不批量降为 tenant |
| 已有 tenant 定义 | 原 ID、所有者及合法绑定保持；Root 自定义 tenant 角色也只是 Root 的本租户角色 |
| 当前 Home 内的合法绑定 | 原行不动；不重发、不重置 create_time，不重新聚合计数 |
| 空/旧类型、缺定义、异常主属或重复行 | 单列盘点；沿用已确定的兼容读取语义，不由部署脚本猜测修复 |
| 外租户私有定义、越部门范围绑定 | 不改过滤放行；改绑租户也不会使定义合法。需要目标新定义/明确授予时，作为单独操作处理 |
| 内置管理员、个人菜单、F048 Grant、已有用量 | 不归入本次普通角色兼容，不复制、不清零 |

角色定义没有换 ID 时，部门默认配置及外部角色引用保持。任何新副本都输出明确 ID 映射；审批、DSH、SSO 等输入端不得按同名自动接到副本。

## 5. 历史 Root 错位绑定：有限修正，不补授

示例：用户 Home 已是 13，合法共享角色 G 的旧绑定仍记在 Root。只针对管理员当前明确选择、且仍存在的源行修正。

### 5.1 盘点与授权

扩展现有 `src/backend/scripts/managed_tenant_preflight.py`，增加基于 UserRole 稳定键分页的错位普通绑定盘点。现有脚本只枚举有限个活动 Home 用户；默认扫 Root 会漏掉“Home 在 13、绑定在 Root”的人，不能将其现有输出当全量迁移依据。

逐行清单至少包含：完整源键 `(id, user_id, role_id)`、原绑定租户、时间字段、当前 Home/主部门/成员事实、同人同角色目标绑定的存在性及完整键、定义类型/所有者/范围、当前与拟修正后的菜单及额度差异、阻断原因。分页必须穷尽并标明截断情况。执行前检查目标库实际 DDL 和重复行；现有 UserRole 没有保证 `(user_id, role_id, tenant_id)`唯一的约束。

先只读生成清单，由有权平台管理员确认具体行和目标 Home；残留 Root 行或“没有撤权日志”均不足以自动推导当前授予意图。备份用于核对，不作为 INSERT 恢复指令。写入是独立运维步骤，不进入 Alembic 数据回填。

### 5.2 每人一个事务的执行规则

- 按既有“角色定义 → User”的顺序锁定，重读活动 Home、成员、定义和源绑定；要求唯一合法 Home 与主部门推导一致，角色非 AdminRole、仍为共享定义且目标部门资格合法。
- 只允许对批准的同一完整源键做条件 UPDATE：源行仍属于 Root、关键快照未变时将其 `tenant_id`改为当前 Home，并检查实际影响行数。
- 目标已有合法同角色绑定时，保留目标原授予，只清理本次明确选择的重复 Root 源行；不顺带去重全库。目标绑定相对确认清单出现新增/删除/替换也须返回过期，不能在其已被撤销后改走“目标无绑定”分支重新激活源行。
- 修改与审计同事务提交。审计补充操作者、源完整键、原/目标租户、计划 ID、修正/去重结果；不能只记 removed/added 角色 ID 集合。
- 源行已在批准目标且其他条件仍相符，返回已处理；源行不存在、同人同角色出现不同新行、Home/范围/配置改变，返回已移除或过期，绝不 INSERT、调用 grant 兜底或从备份恢复。
- 单人任一条条件失败，该人事务回滚；其他已完成人员如实列出，不宣称全批次原子。

该步骤可不新增表/列。首次发现性盘点可以在线只读；**最终盘点、管理员确认和执行须处于同一受控窗口，暂停相关人员的组织及角色修改。** 仅在执行时加锁无法发现“目标后来授予又撤销、行状态恢复原样”的中间意图，本批不为此新增政策 generation。窗口无法保证就重新盘点确认，不执行旧清单；不能因为新 Repository 加锁就宣称确认到执行之间也并发安全。

## 6. 部门划为新租户：一次明确的行政划分

### 6.1 人员范围与承接来源

承接只发生在挂载入口，使用“本次行政划分”原因，不在普通 `sync_user`里按角色类型增加通用例外。

1. 改变挂载边界前，按当前权威事实枚举本次主部门位于子树、且 Home 将真正变化的人员。保存的是当前有效普通角色及其源绑定实体，不是全部历史 UserRole 行。既有主属/主部门不一致或源授权不能确认的人员先阻断，不能顺带当历史修复。
2. 主属仍在外部的兼属人员不切 Home、不承接角色。子树外人员和父租户剩余人员不改绑定。组织范围变化使兼属者某份旧策略失去支持时，仍按既有资格规则有限清理，不能将其误算为承接对象。
3. 撤销过、失效或当前无角色的人，不因划分补回旧角色。管理员若需要额外新授予，必须在本次预览中显式选择并单列审计。
4. 原资源迁离前置限制、用户停用、异常主属等继续适用，预检应在创建前暴露，并在提交事务内重验。资源及其历史用量留在原处，不因角色承接重置预算或自动搬迁。现有 `_count_owned_resources`会跳过部分读取异常，不能直接拿其返回 0 作为放行依据；本次迁离前置所必需的计数不可确定时拒绝，相关创建/归属变更须参与相同人员锁，无法证明时改走受控维护窗口。

### 6.2 定义、绑定和默认配置的映射

| 来源 | 推荐候选及确认后行为 |
| --- | --- |
| 目标范围仍合法的平台共享角色 | 预览建议沿用同一角色 ID；确认后终止原 Home 普通绑定、在新 Home 建立本次授予。不将历史非生效绑定一并带走 |
| 原租户本地角色 | 仅对本次选定且确需使用的角色创建新租户私有副本，每个源角色在本次操作最多生成一个副本；以旧 ID→新 ID 映射承接选中人员 |
| 因新边界失效的部门范围 | 不清空 `department_id`来放行。需明确选择另一合法角色，或显式设计新的目标角色；未解决的映射阻断提交 |
| 部门默认角色引用 | 同时预览子树内各部门的 `default_role_ids`。合法共享引用保留；私有引用按确认映射替换/复制；明确移除的须可见，不能静默留下父租户私有 ID |
| 管理员、个人菜单和资源 Grant | 使用各自既有独立通道，不随普通角色复制；本次管理员授予仍独立返回结果 |

复制仅包含角色名称、合法部门范围、普通角色 quota 配置、说明及 WEB_MENU。菜单使用当前合法键，quota 保持既有边界语义并经校验；不复制其他 RoleAccess 类型或源租户业务配置。目标重名由预览明确命名，不能复用恰好同名的定义。

复制范围包括“选中人员当前有效角色”和“本次明确保留的默认配置所需角色”，不扫描复制整个父目录。部门 ID 在仅划边界时不变，但目标资格按业务租户重新验证。

**对原有人员，不因这次行政划分重新运行默认角色批量发放。** 原有效角色按确认计划承接；默认配置映射用于以后真正新增成员。这样原先人工撤销的默认角色不会因划分被补回，原本无角色的人也不会被自动授予。真正人员调岗、新建人员的合法默认授予仍按原合同处理。

### 6.3 预览不能只看“仍有角色”

新增只读预览入口，复用挂载弹窗呈现：受影响人员、当前有效角色、建议/选择的映射、默认配置变化、目标菜单、角色及租户额度、审批/DSH 差异、阻断项。

- 审批动态标签为 `role_{id}`；副本新 ID 会改变匹配。DSH 按目标租户读取模型可见性和额度规则，即使保留共享 ID，也不携带源租户规则。
- 预览基于目标新租户的既有标准初始化规则；某项不能可靠预演就标记未确认，不冒充等价。有限额度变不限、必审变免审、功能入口减少等差异须明确确认；需要额外目标配置但尚未准备的，阻断提交。
- 不自动复制父租户审批路由、DSH 配置或既有消耗账本。必要的目标配置由各自 owner 定义，不把复制 Role 表称作政策完全等价。
- 对因本次划分从可登录变为不可登录/无可用菜单的人员，须先配置合法映射再提交；原本无角色、已有管理员入口等按原业务规则区分，不以“补保底角色”解决。

### 6.4 同一 SQL 事务的边界

在现有 `create_mounted_tenant_with_coverage`应用事务内完成：

1. 获得组织变更锁，重验预览所依据的拓扑、完整人员集合、主属、源绑定、角色定义及默认配置；任一关键事实改变则返回预览过期，零写入。
2. 读取并冻结原有效策略；锁定待使用的定义和人员。创建新 Tenant，更新挂载 Department。
3. 根据确认计划创建有限私有角色副本及 WEB_MENU，形成明确映射。
4. 通过 user owner 的调用者持有 session 的方法，切换本次人员 Home、递增 token/profile 版本，终止旧普通绑定并建立目标合法绑定。AdminRole 不动，不激活历史目标 Home 残留绑定。
5. 替换本次子树内已确认的默认配置，按最终事实清理其他受影响非法绑定，验证目标有效角色/菜单结果。
6. 同事务记录请求身份、映射及逐人策略审计，执行原有覆盖证明。任一必需 SQL 步骤失败，全部回滚；原有覆盖证明未就绪分支不被本方案冒充已解决。

上述服务不能内部 commit 或换 session。DSH 已有 `UserDshProfileRepository.activate_tenant(session, ...)`说明身份切换本身可以保留在 SQL 事务；需补 application 接口及 async/session 适配，不直接跨领域调用 ORM。提交后不再调用会删除绑定/发默认的 `sync_subtree_primary_users`来重复完成这批人员。

**并发前置条件：**复用现有 Root Tenant 行作为短事务组织写入门闩，但 mount、本地/SSO 成员和主部门变更、部门移动/归档、登录惰性 Home 同步及定期 reconcile 等触及路径必须共同参与，取得锁后重读事实。门闩只覆盖可能改变组织/Home 的 SQL，不让普通只读登录长期占用它。既有 coverage epoch 虽锁 Root 行，其他组织 writer 尚未参与，因此现在不具备此保证。统一顺序为组织门闩→递增角色 ID→递增 User ID，再取得主属/成员/绑定行锁；须审查触及入口是否存在反向取锁。网络调用不得放在该全局门闩内。

只给 mount 加锁或提交前再扫一次不能防止新成员并发移入。本批必须补齐触及的组织事实生产者；不能完成此接线时，只能在明确维护窗口禁用相关组织写入后执行，不宣称在线全子树并发安全。大子树先做耗时/锁验证；超过已验证规模就提交前拒绝，另做受控划分，不临时拆成可能部分提交的异步批次。

## 7. 最小持久化与请求重试

**角色、人员绑定和默认角色配置不新增表/列。建议只给现有 Tenant 增加两个可空字段：**

| 字段 | 用途 |
| --- | --- |
| `mount_request_id`，UUID 字符串，nullable unique | 标识一次挂载请求；提交后与 Tenant 一起保留，解绑归档也不清空 |
| `mount_request_digest`，SHA-256 字符串，nullable | 服务端计算的规范请求摘要，包含部门、名称/代码、承接及默认映射选择、预览摘要和其他实际创建参数 |

这两列用于解决“SQL 提交成功但响应丢失”，以及旧请求在解绑重挂后到达的问题。只凭部门名/代码或当前挂载关系无法区分这些情况；审计日志也不承担唯一请求权威，不将整份恢复计划塞入 JSON 字段。

- 新 UI 在一次尝试开始时生成固定 request_id，预览、提交和网络重试沿用它。相同 ID/摘要已提交时返回同一 tenant_id 和当前完成情况；不再复制定义、修改普通绑定、默认发放或根据旧映射补角色。
- 相同 ID/不同摘要拒绝。部门已被另一请求挂载拒绝。旧请求对应租户已归档或部门已有后续挂载时，只返回原操作已结束/被取代，不执行外部旧授权或重新创建。
- 无该 ID 的旧租户不反向生成“已承接”结论。旧 API 请求缺少新参数时，只有完全不涉及人员/默认策略变化的安全场景可直接继续；有政策影响则在任何写入前返回需要预览确认。不能静默回退原清理行为，也不能默认全继承。
- 执行前发生崩溃，SQL 全部回滚；可以按当前事实重新预览。提交结果不明时先以 request_id 查结果，不能用“目标当前少了角色”推导应重授。
- 完成后人工撤权、修改角色范围或再次调动，原 request_id 重试只能查到原操作已提交；这些后续决定永远不由旧快照覆盖。

DDL 使用双库兼容标量列及约束，旧行均为空；实际 MySQL/DM8 nullable unique 行为需集中验证。Alembic 只做 schema，不回填角色或绑定。不要在 quota/storage JSON 或账号状态字段里混放此请求身份。

## 8. SQL 之外的结果与保护边界

FGA 租户成员投影、共享投影、缓存清理、个人 token 迁移、工具/审批初始化及初始管理员授予仍有各自边界。普通角色 SQL 完成不等于这些步骤完成。

挂载响应保留 tenant 的原字段，新增普通策略已提交、后置同步结果和未完成项；SQL 已提交但后置失败时必须返回 tenant_id 及明确待处理信息，界面不能显示完整成功，也不能将其当成完全未创建而改 request_id 再建。重试先定位原请求，再按**当前权威事实**补后置步骤，不能重新调用旧整条 mount/sync 流程发角色。

本批至少抽出“人员身份后置同步”的独立入口，使其不因 Home 已正确而提前退出。只修复当前仍属于该目标 Home 的人员；已后续调动/停用则跳过旧目标动作并报告被取代。初始管理员沿用当前独立接口和部分失败反馈，不复制旧管理员身份；角色副本不会获得管理员资格。

**已知限制不能隐藏：**当前 `tenant#member`变更使用 FailedTuple，预记录自开事务，旧重试不检查当前 Home/version；它不是已覆盖 UserTenant 的 F048 操作账本。因此本方案不借 `crash_safe=True`声称 SQL/FGA 原子、所有旧身份重放已解决或全平台强撤权。本次承诺“撤权不复活”覆盖普通 Role 绑定、默认发放和本次挂载重试；角色定义共享也不替代资源边界。

上线验收必须检查触及的租户成员投影重试及具体资源隔离。若该既有重放可使当前租户边界失守，作为阻断缺陷做 user/tenant owner 的定向事实重验与 permission adapter 接线；不能用“已有账本会恢复”掩盖，也不直接升级为重做全部 FGA 投影系统。后置状态无法核实就返回未确认，不能推断成功。

本轮仅形成方案，不直接覆盖已确认的 F009 文档。后续按项目 Full SDD 确认阶段推进，复用 F009 需求与设计，不另起重复需求体系。

1. 角色创建范围、列表/表单表达、已有定义读取兼容；先不执行数据修正。
2. 错位绑定全量只读盘点、确认清单和有限条件修正工具；环境执行单独授权，先 dry-run。
3. 挂载预览/确认、有限复制及默认映射、SQL 原子承接、两个请求字段、后置结果与必要组织写入接线。一个 Owner 负责该闭环，不能拆成多个 helper 后让调用方无人集成。

发布顺序：先 schema，再后端再前端；新客户端显式选择范围，旧客户端有政策影响的挂载收到需预览响应。生产修正不随启动自动执行。若需回退，先停止新创建/挂载写入并保留新 Tenant 请求字段和审计；回退旧业务代码前核对其会否重新隐式创建共享角色或按旧方式清绑定，不能直接降 schema/恢复旧绑定备份。

## 12. 与管理视图统一方案的联合边界

本节衔接核对基线为 `3ce7e7ef3de81a06f57520a7ab74d6b9e253d8fc`；核对角色领域、普通绑定仓储及租户创建应用代码，相对本文原基线未见差异。本节不更新原评审的验证范围，也不代表已连接环境验收。

管理视图方案回答“本次请求操作哪里”，本文回答“角色定义属于哪里、人员何时合法绑定及行政划分如何承接”。二者分别建模，不把当前操作租户覆盖进真实身份或所有租户字段。

| 衔接点 | 联合规则与实施归属 |
| --- | --- |
| 第一阶段角色创建 | 共用管理准入产生的经验证目标；本文第一步负责显式类型、查重、部门校验、定义及 WEB_MENU 保存，联合交付一套实现。不能只把定义所有者改成目标却保留超管隐式共享，也不能两边各改一套 RoleService |
| 共享定义读写 | 定义候选/读取使用角色领域窄端口，维护要求平台资格；新共享定义归 Root，旧所有者及菜单保持。平台汇总是明确例外，Root 具体目标不自动代表全部租户 |
| 人员普通绑定与兼属 | 绑定始终属于被授予人的真实 Home，且定义和部门资格合法；主属 B、兼属 A 不因超管选 A 得到 A 普通绑定。管理视图不得创建第二套角色或修改 Home |
| 菜单、配额、审批与模型额度 | 有效普通角色按当前真实主属计算；定义菜单按定义所有者读取。目标资源、租户限制和使用量各循既有规则，保留超管配额例外；具体资源动作不由共享角色直接放行。复制新 ID 的审批/DSH 差异继续按本文预览确认 |
| 历史错位绑定修正 | 管理范围方案只做只读预检；本文第二步的逐行确认、条件修正与受控窗口独立执行。不把当前操作目标当修正目的地，不新增授予兜底 |
| 部门行政划分与真正调岗 | 管理视图切换不是人员迁移，不能触发本文第三步。只有挂载入口的预览确认才能建立行政承接新授予；真正调岗继续终止旧普通绑定，外部兼属不迁、不承接 |
| 数据字段及请求重试 | 管理范围修复保留原 Redis 整数格式、暂缓新视图标识；本文的 `mount_request_id` / `mount_request_digest` 仍是第三步两个独立持久字段，不能因此取消或被承诺为已交付 |
| 后置同步与权限投影 | 管理范围修复须验证所触及任务的目标恢复；本文后置同步按当前事实续办，不重放承接或默认授予。已有租户成员投影重放限制仍按 §8 验证，不因统一入口而视为已解决 |

联合验收补充：A 普通获权用户运行 Root 超管在 A 创建的流程时，不得把创建者真实主属强设为 A；知识节点创建者/运行人开关语义保留，使用经验证的资源目标及现有动作授权。此项是执行身份修复，不通过迁移创建者、给其新增 A 的普通绑定或复制角色解决。

统一方案现分为“缺陷修复→登记与预检→强制检查”，本文仍是“角色创建→有限历史修正→行政划分承接”。只有角色创建与统一方案第一阶段联合交付；沿既有可信范围入口取得目标，之后平滑迁到统一准入，不为了等待全路由强制检查而另建角色范围体系。统一方案第二阶段可读取错位绑定预检结果，但不执行本文第二步的条件修正，更不默认启动本文第三步或其 schema 变化。

超管创建缺省改为本租户角色属于行为合同变化，进入实现前除同步 F009 外，还须登记版本 `release-contract.md` 并正式确认；旧请求确需共享时应显式传类型。统一方案对本人凭据和租户令牌管理的分类、对整页刷新的复用及网关显式目标契约不改变本文的 Home 绑定、部门资格和资源授权边界。

实施前统一确认两份方案的联合范围，并同步 F009 的规格、设计、任务、测试及必要升级材料。本文第二、三步未交付时，不能将第一步及管理范围修复描述为历史绑定已修正或部门承接已完成；管理调试和计量新能力亦不因本次角色衔接自动纳入。

## 第一阶段实现指针

联合交付仅覆盖显式角色类型、经验证目标的本租户定义、新共享定义Root归属、菜单随定义保存，以及已授权可见角色的类型/定义所有者展示；历史定义所有者、菜单、绑定和额度保留。缺省类型变化已登记版本合同。详见[第一阶段交付](../../features/v3.1.0-beta1/009-managed-tenant-consistency/phase1-delivery.md)。本文历史修正和行政承接步骤（含其字段、受控窗口及锁）未实施；不要执行其中方案性操作作为本补丁升级步骤。
