## 1. 综述

### 1.0 术语：什么是「托管应用」

本册所说的**应用**，在产品界面上的正式名称是「**托管应用**」——它是「构建 → 应用」里与「工作流」「助手」**并列的第三种类型**，三者的区别是：

| 类型 | 是什么 | 跑在哪 |
|---|---|---|
| 工作流 | 编排出来的流程 | 平台的工作流引擎 |
| 助手 | 配置出来的智能体 | 平台的助手运行时 |
| **托管应用** | **有代码、有自己界面与数据的应用** | **平台托管的独立容器**（RT-08 / GOV-03） |

取名「托管」而非按生产方式命名（如「vibe 应用」），是因为**应用有两个来源**——PRD-2 的对话式生成与本册的本地开发导入——而两者的共同点恰恰是"最终跑在平台托管的运行环境里"，且这正是它与前两类的本质区别。本册正文在不产生歧义处直接简称「应用」。

### 1.1 一句话定位

**让专业开发者把本地开发的存量应用按需集成企业的知识、模型与身份能力，经 CLI 导入平台纳管发布**——本地 coding agent 一句话完成部署；应用跑在平台托管的运行环境里，发布进应用广场、同事即点即用，审批 / 权限 / 审计全程自动生效。

本册同时交付**两条造应用旅程共享的地基**——应用运行时、发布审批管线与治理面。《PRD-2 造应用工作台》的对话式造应用站在同一地基上，因此本册先行。

> **一处容易读漏的边界**：本册主用户在命令行工作，但「设置可见范围」等少数操作**没有命令行等价物**，须在**构建 → 应用 → 应用详情页 · 发布**完成——其中设置可见范围是**首发上线后的必经一步**（不设则除 owner 外无人可见）。完整清单见 §2.2。

### 1.2 三大能力与承载域

| 能力 | 一句话 | 承载域 |
|------|--------|--------|
| **导** | 本地项目按需集成平台能力、经 CLI 导入纳管；本地 coding agent 对话式完成部署与排障 | §3.1 开发者通道（DEV） |
| **接与跑** | 应用托管在平台运行环境，经能力总线接入知识库 / 模型 / 身份，天生认识组织架构与权限；统一入口与应用广场承载使用 | §3.2 运行时与发布（RT） |
| **管** | 发布审批 / 权限 / 资源档位 / 审计全程自动生效，本地造的和平台造的应用治理面前无差别 | §3.3 治理（GOV） |

### 1.3 五条贯穿全册的设计前提

读正文前先掌握这五条——它们跨越多个条目，是理解本册所有细节的框架。

| # | 前提 | 含义与影响 |
|---|------|-----------|
| **1** | **按需集成，不是从零起步工具链** | 四面供给（MCP 调用 / 技能包知识 / SDK 代码 / CLI 工作流）全部**可选**——不用任何平台能力的存量应用也可直接导入。全走标准协议、无本地专有插件，任何本地引擎零改造接入 |
| **2** | **同治理承诺** | 导入应用与平台内造的应用走**同一条发布管线**：同审批、同权限、同审计。治理面前无「本地造的」与「平台造的」之分 |
| **3** | **凭据以鉴权 PRD 为准，本册只写增量** | 服务账号、密钥底座、权限位清单、签发表单全部定义在《开放 API 鉴权与身份传递 PRD》。本册的增量只有三处：权限位新增「本地开发工具包」一组三个开关、服务账号详情页新增接入信息区、以及若干落地口径 |
| **4** | **运行时双形态，产品面一致** | 应用运行时支持 **compose 单机**与 **k8s 集群**两种执行后端，部署期二选一。发布管线、资源档位、审批、权限、日志、崩溃自愈的行为与验收在两形态下**不得有任何差异**，差异一律压在编排器内部 |
| **5** | **治理默认开箱即用，不靠先配置** | 发布审批有平台预置流程（部署即生效，审批人 = owner 所属部门的部门管理员 ∪ 租户管理员、或签）；资源档位有默认推荐档；能力总线配一次域内共享。管理员**不需要先做任何配置**，第一次发布就能跑通 |

## 2. 用户与旅程

### 2.1 用户

| 用户 | 要什么 | 主要触达面 |
|------|--------|-----------|
| 业务技术员（主用户，会用 coding agent 的人） | 本地开发的应用部署到平台给大家用 | 专业开发者通道（§3.1） |
| 平台管理员 / IT | 自建应用看得见、管得住、出事能兜底 | 治理与管理面（§3.3） |
| 普通业务用户 | 在应用广场找到并直接使用同事造的工具 | 统一入口与应用广场（§3.2） |

角色定义（全文角色词汇的单一出处）：

| 角色 | 定义 | 典型动作（详见 §3.3 角色×动作矩阵） |
|------|------|------|
| 平台超管 | 平台级运维管理员 | 维护资源档位规格、跨租户审计 |
| 租户管理员 | 租户内治理角色 | 签发 / 吊销开发者 API key、下线 / 重新上线、配置审批人、查本租户审计、配置能力总线、配置角色的应用工场菜单与新建权限 |
| 审批人 | 发布审批的处理人；具体来源与或签规则以 GOV-02 预置流程为准，租户管理员可改配 | 处理审批单、审读视图与预览试用 |
| 开发者（owner） | 导入/创建应用的所有者 | 集成与导入、发布、撤回、可见范围设置、下线、删除 |
| 普通业务用户 | 广场使用者 | 发现并使用可见范围内应用 |

注：单租户部署下平台超管与租户管理员可为同一人；本册后文提及角色时一律使用上表中的具体角色名，不泛称「管理员」。

> **唯一例外——面向终端用户的兜底页文案（RT-01 四类兜底页）用中性称呼「平台管理员」**。这些页由应用入口层（app-proxy）自渲染，它是独立进程、拿不到多租户开关，无法按部署形态在「租户管理员 / 平台超管」之间择词；而标准装机默认单租户，此时既不存在可授予的租户管理员（Root 租户禁止授予），「租户管理员」在页面上就是一个用户永远找不到的人。角色矩阵、权限口径等规格性表述仍用精确角色名，不受此例外影响。

### 2.2 主旅程：专业开发者 本地开发 → 集成平台能力 → 导入纳管

1. 开发者已在本地（vscode / cursor / coding agent）把应用开发得七七八八——这一段平台不参与。
2. 需要平台能力时按需集成：租户管理员为开发者建立服务账号并签发 API key（DEV-01）；经 MCP 使用检索/身份/应用数据等工具、经 OpenAI 兼容协议直连平台托管模型（DEV-02）；按需引入 SDK（DEV-07）；技能包在 `bisheng login` 时已自动拉取，提供接入知识（DEV-03）。集成是可选项：不用任何平台能力的存量应用也可直接导入。
3. 本地联调：`bisheng dev` 运行应用并注入与线上同构的平台身份，应用不写登录页（DEV-05）。
4. `bisheng deploy` 导入纳管，经统一发布管线（预检 → 扫描 → 审批 → 托管上线，DEV-04）；`bisheng logs` 排障。
5. **首发上线后，去**构建 → 应用**里打开该应用的详情页，在「发布」中设置可见范围**（GOV-01）——不设的话应用虽已上线进广场，但**除 owner 外无人看得见**。这是首发的**必经一步**，也是本旅程中第一次需要离开命令行。
6. 之后仍是本地改码、`deploy` 更新——**改码权恒在本地**，平台侧对导入应用的代码只读（交接给管家的能力随 PRD-2，§5.2）。

**哪些操作必须去界面上做**——本册主用户在命令行工作，但下列操作**没有命令行等价物**，须在 **platform 端「构建 → 应用」→ 点开该应用 → 应用详情页**完成（完整导航路径见 §3.0.1）：

| 操作 | 何时用到 | 出处 |
|---|---|---|
| **设置可见范围** | **首发上线后必做**，否则只有 owner 可见 | GOV-01——入口有两个：应用卡片 ⚙️ →「管理权限」（主入口，与工作流 / 助手一致），或应用详情页 · 发布的可见范围区；**同一个弹窗** |
| 待上线态手动上线 | 审批通过但资源不足时 | GOV-03 |
| 撤回在途审批单 | 提交后想反悔 | DEV-04 / RT-03 |
| 下线 / 重新上线 | 临时下线止血 | RT-07 |
| 显式删除 | 应用退役（**须先下线**，已上线态入口置灰） | RT-07 |
| 取入口链接与二维码 | 分发给同事 | RT-01 / RT-02 |

> 除设置可见范围外，其余均为**按需触发**，不在首发主旅程的必经路径上。审批状态则有两条路——应用详情页或 MCP 应用状态工具（DEV-02），**agent 在本地即可跟踪**。

### 2.3 使用旅程：普通业务用户

已发布应用的使用与来源无关：普通业务用户经应用广场 / 入口链接 / 扫二维码免二次登录使用，各自只看到权限内数据（RT-01 / RT-02）。

## 3. 功能需求

### 3.0 全册通用约定

下列三项约定被 DEV / RT / GOV 各域条目反复引用，**集中定义于此，各条目只回链、不重复定义**——分别回答「在哪操作」「处于什么状态」「谁会被通知」：

| 约定 | 回答什么 | 谁引用它 |
|---|---|---|
| 承载面与导航 | 界面操作在哪完成 | 全册凡提及「应用详情页 · X」处 |
| 应用状态机 | 应用与审批单各处于什么状态、如何流转 | RT-03 / RT-05 / RT-07 / GOV-01 / GOV-03 |
| 事件触达 | 一方动作后另一方怎么知道 | 全册凡提及「通知 / 提示」处 |

#### 3.0.1 承载面与导航：构建 → 应用

**应用与工作流、助手同属「造出来的东西」，因此共用 platform 端「构建」区的同一个列表**，不另立入口。**完整导航路径**（全册各条目提到「应用详情页 · X」时，均指这条路径的终点）：

```
platform 端（管理/构建端）
  └─ 左侧主菜单「构建」
       └─ 应用列表（既有卡片流页）
            · 顶部：搜索框 + 「全部应用类型」筛选 + 状态筛选 + 标签筛选
            · 类型筛选新增第三项「托管应用」，与既有「工作流」「助手」并列
            · 卡片：图标 / 名称 / 描述 / 创建用户 / 类型角标 / 版本下拉 / 上下线开关
            └─ 点击某张托管应用卡片
                 └─ 应用详情页 ── tab：发布 · 数据 · 运行日志 · 版本
```

各层的复用与交付形态：

| 层 | 是什么 | 本册交付形态 | PRD-2 补齐后 |
|---|---|---|---|
| **构建 → 应用**（列表） | 既有卡片流页，应用类型筛选新增第三项「**托管应用**」 | 复用既有搜索 / 类型·状态·标签筛选 / 上下线开关 / 版本下拉；**owner 侧「我的应用列表」即此页按归属过滤的视图**；租户管理员因身份短路对本租户全部应用天然可见（平台既有权限模型） | 不变 |
| **应用详情页**（点卡片进入） | 该应用的管理与迭代面 | 四个 tab：**发布**（WB-14）· **数据**（WB-06）· **运行日志**（WB-13）· **版本**（WB-15），**无左侧对话区、无管家** | 增补预览 / 代码 / 资源，并在左侧接入管家对话——演进为完整的「造应用工作台」，**入口与已有内容不变** |

> **卡片上的操作与详情页不重复**：卡片保留列表级的轻操作（上下线开关、版本切换下拉，均为既有能力）；提交发布、设可见范围、删除等需要上下文的操作一律在详情页完成。

**为什么放构建区而不是 client 工作台**：① 心智一致——工作流、助手、应用都是造出来的东西，找它们只有一个地方；② 列表能力几乎全部复用既有构建页（卡片流、筛选、标签、上下线、版本），**owner 与租户管理员看的是同一个页面**，可见范围由平台既有权限模型自然决定，无需另建治理列表；③ **本册因此不依赖 PRD-2 的对话外壳，可真正独立交付**；④ 平台的分工由此更清晰——**造在 platform、用在 client**（应用广场与 `/apps/{slug}` 访问仍在 client 侧，RT-01 / RT-02）。

#### 3.0.2 应用状态机

应用生命周期由两条正交状态线描述：**应用态**（应用当前对外可用性）与**审批单态**（单次发布请求的处理进度）；版本记录的终态标注见 RT-05。本小节不新增条目编号；构建页卡片与筛选器上的「发布状态」同样引用本枚举。

应用态：

| 状态 | 进入条件 | 该状态下可做什么（谁） | 去向 |
|------|---------|----------------------|------|
| 草稿 | 创建/导入后未曾上线；首发被驳回或撤回后 | 提交发布、`bisheng deploy`、修改草稿（owner） | 首发审批通过且上线成功 → 已上线；显式删除 → 已删除 |
| 已上线 | 首发 / 迭代审批通过且上线成功 | 使用（可见范围内用户）；提交迭代、调整可见范围（owner）；下线（owner / 租户管理员）。**不可直接删除**——删除入口在本态置灰，须先下线（RT-07） | 下线 → 已下线 |
| 待上线（资源不足） | 审批通过但上线终检发现**运行环境容量不足**（compose 资源耗尽 / k8s 无可调度资源，GOV-03） | 资源释放后手动上线（owner，无需重新审批）；删除（owner）——本态无运行实例、不对外服务，无需先下线 | 上线成功 → 已上线；删除 → 已删除 |
| 已下线 | owner 或租户管理员下线 | 重新上线（owner / 租户管理员，叠加 GOV-03 运行环境容量校验）；提交发布（审批通过仅落为待运行版本，不自动重新上线）；删除（owner） | 重新上线 → 已上线；删除 → 已删除 |
| 已删除 | owner 走显式删除流程（RT-07） | —（仅审计可查） | 终态 |

审批单态：待审 / 通过 / 驳回 / 已撤回 / 已取消（应用删除时在途审批单自动取消，RT-07）。迭代审批被驳回不改变应用「已上线」态——当前版本继续运行，仅待上线版本标记被驳回（RT-03）。

#### 3.0.3 事件触达

跨角色事件「一方动作、另一方需要知道」的触达渠道全文统一为两种——各条目的「通知 / 提示」措辞均指向此处，不逐条重复：

- **站内消息**：复用平台既有消息通知能力，接收方在工作台「消息提醒」入口（铃铛图标，含未读角标）查看；审批类事件同时进入审批中心待办（GOV-02）。管理后台不设消息面——租户管理员与审批人的消息一律在工作台侧接收。
- **界面自查**：状态与结果在固定界面常驻可查（发布面、构建 → 应用列表、管理后台 API key 管理页等），随时可达、不依赖消息。

| 事件 | 接收方 | 站内消息 | 自查落点 |
|------|--------|---------|---------|
| 审批单生成（首发 / 迭代） | 审批人（按 GOV-02 预置流程解析） | ✓（复用审批中心既有触达） | 审批中心待办（RT-03 / GOV-02） |
| 审批通过/驳回 | owner | ✓ | 发布面审批状态区（WB-14）；MCP 应用状态工具（DEV-02） |
| owner 撤回在途审批单 | 已收到待办的审批人 | ✓（复用审批中心既有触达） | 审批中心（RT-03） |
| 应用删除致在途审批单取消 | 审批人 | ✓ | 审批中心（RT-07） |
| 上线终检遇运行环境容量不足、应用入待上线态 | owner、租户管理员 | ✓ | 发布面（owner）；构建 → 应用列表的状态筛选（租户管理员，GOV-03） |
| 资源释放后可手动上线 | owner | —（无主动提示） | 发布面待上线态「手动上线」（GOV-03） |
| 租户管理员下线 / 重新上线 | owner | ✓ | 发布面状态与审计记录（RT-07） |
| 声明能力被收回（模型下线/知识库收回） | owner | — | 发布面/资源面失效提示（GOV-05） |
| 开发者 key 签发完成 | 资源归属人 | —（无主动通知） | **无开发者侧自查落点**——key 值经签发时一次性展示、接入信息经「一键复制」文本，两者均由租户管理员经企业既有渠道转交（DEV-01）；管理员侧可在管理后台 API key 管理页自查 |
| 开发者 key 被吊销/服务账号禁用自动失效 | 资源归属人 | — | 下一次调用被拒（CLI 提示重新 login，DEV-04）；管理面 key 状态（租户管理员） |
| 应用上架/新获可见权限 | 可见范围内用户 | —（本版不做上新推送） | 应用广场（RT-02）；owner 自行转发入口链接 |

- 本约定只覆盖事件发生时的一次性触达；催办、超时提醒与升级机制本版不做（§5.2）。
- 站内消息为通知性质、不承载操作，处理动作一律回各自界面完成。

### 3.1 专业开发者通道（DEV）

**本域交付：已有本地项目的开发者（vscode / cursor / coding agent 开发的存量应用，0.9 → 1）按需集成平台能力、导入平台纳管发布。**

本域六个条目按开发者的使用顺序排列（跳过 DEV-06——已取消，见 §5.2）：

| 条目 | 解决什么 |
|---|---|
| DEV-01 | 拿到凭据——服务账号与 key 怎么签发、能干什么 |
| DEV-02 | 调平台能力——MCP 工具面（调用）与模型协议面 |
| DEV-03 | 学会怎么用——技能包（知识） |
| DEV-04 | 走完整流程——CLI 五命令与 deploy 发布管线 |

| DEV-07 | 代码层怎么写——SDK 三件套，以及刻意不进 SDK 的两样 |

> **本域的操作者是 agent，不是人。** 四面供给（MCP 调用 / 技能包知识 / SDK 代码 / CLI 工作流）的直接调用方是开发者的本地 coding agent——开发者在本地对话里提出部署诉求，agent 凭技能包 + CLI + MCP 完成部署与排障全流程、不离开本地对话（端到端验收见 DEV-04）。四面的按需可选与同治理承诺见 §1.3 前提 1、2。

**DEV-01 开发者 API key（服务账号密钥）**

> **一句话**：「开发者 key」不是一种新的密钥类型，只是**服务账号密钥的一种用途称呼**——底座、签发表单、权限位清单全部沿用《开放 API 鉴权与身份传递 PRD》，应用工场只往那张权限位清单里加了三个开关。

- 需求描述：租户管理员为开发者建立**服务账号**（不可登录的一等主体，指定**资源归属人** = 该开发者）并签发 API key，开发者凭它接入 MCP 工具面、模型协议面与 CLI（DEV-02 / DEV-04）。
  - **能力来源**：key 的能力 = **密钥权限位 ∧ 对该服务账号的显式资源授予**（该 PRD §4.4.1 两层与关系），不继承任何自然人权限（全平台无个人主体轨凭据，F049 spec §4 决议-4）。
  - **应用工场的增量只有三处**：权限位清单新增「本地开发工具包」一组三个开关（`model:invoke` / `identity:read` / `app:manage`；知识库检索**不另设位、复用既有 `knowledge:read`**）；服务账号详情页新增接入信息区；以及本条列出的若干落地口径。原「scope」概念已取消。
  - **key 值零暴露**：仅在签发时一次性展示、由租户管理员转交开发者，此后任何界面只见掩码（NFR-2）。
- 界面与交互（**无独立的开发者 key 界面**——签发、列表、吊销全部就是该 PRD §4.7 服务账号模块的界面，本表只写应用工场在其上的增量）：

| 界面/入口 | 位置 | 应用工场增量 |
|-----------|------|------|
| 服务账号新建表单 | 该 PRD §4.7.1（名称 + 描述 + **资源归属人**；该字段已升格为该 PRD §4.5 定义 6 的正文概念，本册只引用不定义） | 字段与校验均无增量，仅在归属人选择处补一条**选错难纠正**的风险提示：该账号首发 deploy 的应用以此人为 owner，而删除 / 回滚 / 撤回在途审批单（§3.3 角色矩阵注）**仅 owner 可为、平台超管与租户管理员均不可代行**；归属又在创建时固化、改字段不追溯已有应用（该 PRD 定义 6 边界 d），因此选错只能等 §5.2 归属转移，本版管理侧兜底手段仅下线（RT-07）。知识库等其它资源无此约束——管理员随时可另授「可管理」给他人 |
| 密钥签发表单 | 该 PRD §4.7.3（名称必填 / 权限位默认全不勾 / 委托配置 / 过期时间） | 权限位分组新增「本地开发工具包」一组三个开关，各附白话用途说明与「部署应用需勾选 `app:manage`」提示；默认同样全不勾。**`identity:read` 须显著风险标注**——勾选即本租户组织架构全量可读，无法收窄到部分部门（该 PRD §4.2.4 扩展位表）。**`delegate` 与本组三位互斥、硬阻断**——同时勾选无法保存（签发与编辑同一约束，该 PRD §4.7.3），提示「配了委托的 key 不能用于本地开发，请另发一把」；这样的 key 三面必然全废，签出来即废件。勾选开放 API 端点权限位（`delegate` 以外）时仍只作软提示「转交个人使用的 key 建议仅配本地开发工具包权限位」，不阻断 |
| 密钥列表 / 一次性展示弹窗 / 吊销 | 该 PRD §4.7.3 原样（前缀+末四位掩码、关闭前勾选「我已保存」、二次确认吊销、批量撤销） | 列表的权限位列含新增三位；吊销确认文案补一句「MCP / 模型协议 / CLI 三面同时被拒绝」；无开发者自助吊销入口 |
| 接入信息区 | 服务账号详情页「API 密钥」标签页顶部（应用工场增量） | 集中展示 MCP Server 地址、OpenAI 兼容 base URL、**CLI 安装包下载链接**（平台自身分发、无公网依赖；**是链接不是文件**——管理员转发链接、开发者自行下载）与 `bisheng login` 指引，并提供**「一键复制接入信息」**按钮（见下）；未部署开放能力层时不出现 |

- 规则与边界：

**① 权限位与三面能力的映射**（`login` 与 `skills sync` 仅验 key 有效、不验权限位；**唯一例外是 `delegate`——持有它即 `login` 被拒**，理由见 DEV-02 ④）

| 权限位 | 来源 | MCP 工具 | 模型协议面 | CLI |
|--------|------|---------|-----------|-----|
| `knowledge:read` | 该 PRD 既有位，**复用** | 知识库检索、知识库清单查询 | — | — |
| `model:invoke` | 应用工场新增 | 模型清单查询 | OpenAI 兼容协议直连（裸透传、不建会话——**与 `chat:invoke` 互不蕴含**） | — |
| `identity:read` | 应用工场新增 | 用户身份 / 组织查询（⚠️ 全租户组织架构可读，见 ③） | — | —（`dev` 注入的是服务账号自身身份、不验位；应用在 dev 期查身份 / 组织走 MCP 身份工具，按本位判定） |
| `app:manage` | 应用工场新增 | 应用数据表结构与数据查询、应用状态 / 日志自查 | — | deploy / logs |
| `delegate` | 该 PRD 既有位 | ⛔ 全拒 | ⛔ 全拒 | ⛔ 连 `login` 都拒 |

  - **`delegate` 是唯一一个「给了反而全废」的位**：它把这把 key 定性为委托专用，只能用于 V2 开放 API 的模式 D，接本地开发三面一律被拒（DEV-02 ④）。因此它与「本地开发工具包」三位**互斥**，签发与编辑表单均硬阻断（见下表）。
  - 新增三位与该 PRD 既有位是**同一张清单、同一个签发表单、同一套默认全不勾原则**，不构成第二个权限维度。同一把 key 勾了 `knowledge:read`，经开放 API `POST /filelib/retrieve` 与经 MCP 检索工具都放行、过滤强度一致（DEV-02）。三位的能力↔权限位映射已登记进该 PRD **附录 B.2**（本地开发三面，与 B.1 的 V2 端点分表）。

**② 凭据规则**（底座即该 PRD R1，前缀 `bs-sak-`、全平台唯一主体轨）

  - 生成 / 哈希存储 / 校验 / 展示 / 撤销全部遵循 GOV-08 统一凭据底座；key 值仅签发时一次性展示，此后一切界面只见掩码。
  - 权限位签发后可由租户管理员编辑调整，**即时生效、无需重签**，变更计审计（GOV-04）。
  - 过期时间可选、默认长期有效；到期自动失效，事件计审计。
  - key 可吊销；调用频率限流本版不做（§5.2）。token 用量只计量、不设上限，每次调用按 key 计入审计（GOV-04）。

**③ 权限模型**

  - **授权入口唯一**：服务账号的资源可见范围由管理员在服务账号详情页的「资源授权」面显式授予。服务账号**不出现在资源侧的授权选人框**（普通资源所有者不得单方面扩大密钥的数据边界），仅在资源侧「已授权对象列表」中可显示、不可选择（该 PRD §4.7.4 / AC-15）。
  - **`identity:read` 是高危位**：勾选即本租户组织架构全量可读（姓名、部门、层级），**平台不存在把部分部门授予某个服务账号的机制**，无法收窄——边界由「给不给这个位」承担。租户隔离仍生效，跨租户读不到。
  - **资源归属人只承接归属、不出借权限**：定义在该 PRD §4.5 定义 6，本册只补两条落地口径——① **CLI 首发 deploy 的应用 owner = 该 key 所属服务账号的资源归属人**，与知识库等资源同一套归属机制；② **「只能操作自己的应用」这条限制以它判定**——应用数据 / 状态 / 日志工具与 CLI `logs`，都只对该归属人 owner 的应用放行（DEV-02 / DEV-04）。归属人变更由租户管理员维护、计审计，且**只对此后创建的资源生效**（边界 d）——已 deploy 的应用 owner 不随之变更，其转移走 §5.2。

**④ 安全约束**

  - **key 不落工程仓库**：CLI 凭据存本地用户目录（属主可读权限）；技能包红线引导用环境变量引用而非硬编码；平台自签发 key 的前缀模式内置于发布前密钥扫描规则集（RT-03 / DEV-04）——硬编码进应用产物的 key 在 deploy 时即被阻断。
  - **泄漏应急**：支持按服务账号一键吊销名下全部 key（GOV-08 批量撤销），吊销生效上界 5 秒（底座主动清缓存，通常即时）；发现泄漏由资源归属人联系租户管理员吊销。
  - **服务账号被禁用 / 删除时**，名下 key 全部自动失效（MCP / 模型协议 / CLI 三面即刻拒绝），事件计审计；资源归属人离职**不自动联动**，需管理员回收其服务账号（自动回收顺延 §5.2）。

**⑤ 接入信息的传递**

  - **一键复制**：把 MCP Server 地址、OpenAI 兼容 base URL、CLI 下载链接与 `bisheng login` 指引拼成一段可直接粘贴的格式化文本，管理员复制后经企业既有渠道（企微 / 邮件等）发给开发者，无需逐字段抄写。文本随时可复制、不限次数，内容实时生成不做快照。
  - **接入信息与 key 值刻意分开传递**：该文本**不含 key 值，也不含任何可换取 key 值的凭据**——接入信息不机密、可随时重发；key 值机密、只有一次，由管理员单独转交（NFR-2）。
  - 本版**不做**平台侧的分享链接、二维码或站内信推送接入信息——走企业既有沟通渠道即可，平台不引入新的分发面。

**⑥ 可选部署**

  - 未部署开放能力层时，本条相关增量（新增三个权限位、接入信息区）不出现；服务账号模块本身随该 PRD 交付（GOV-10）。

- 验收要点：
  1. key 的每次调用可在审计中归属到 key 与其服务账号（含资源归属人），含模型与 token 数（GOV-04）。
  2. 吊销后的 key 自下一次调用起在 MCP / 模型协议 / CLI 三面均被拒绝。
  3. key 值签发展示一次后不可再查看，任何界面仅见掩码。
  4. CLI 凭据存本地用户目录（属主可读），不落工程仓库。
  5. 签发时勾选的权限位生效；签发表单默认全不勾，未勾选任何权限位的 key **仅可 `login` / `skills sync`**，三面其余能力与开放 API 均被拒绝；租户管理员编辑权限位即时生效、无需重签；超出权限位的调用在三面均被拒绝（按 ① 映射表逐位验证）。
  6. key 的可及数据范围 = 密钥权限位 ∧ 服务账号被显式授予范围；未授予的资源不可及（含检索与清单查询）；同一把持 `knowledge:read` 的 key 经开放 API 检索与经 MCP 检索得到**相同的可见集合**。
  7. 服务账号被禁用后其名下 key 自下一次调用起三面均被拒绝，事件计审计。
  8. 将 key 明文写入应用产物并 deploy，被发布前密钥扫描阻断（DEV-04 / RT-03）。
  9. 接入信息区「一键复制」产出的文本含 MCP 地址、模型 base URL、CLI 下载链接与 login 指引，**不含 key 值或任何可换取 key 值的凭据**；开发者凭该文本 + 单独转交的 key 值即可完成 `bisheng login` 并调通一次 MCP 工具。
  10. `delegate` 与「本地开发工具包」三位无法同时勾选——签发与编辑表单均保存失败并提示（**硬阻断，非软提示**）；已存在的此类历史组合 key 在三面调用时被明确拒绝（DEV-02 ④）。

**DEV-02 MCP 工具面与模型协议面**

> **一句话**：平台能力分两条通道对外——**工具走 MCP，模型走 OpenAI 兼容协议直连**。两条都用同一把服务账号密钥鉴权、**以服务账号自身身份执行**、按权限位过滤，且与平台内管家**同一工具面、内外同源**。

- 需求描述：平台以 MCP Server（服务账号密钥鉴权、按密钥权限位过滤，DEV-01）对外提供下表六类工具；权限边界与平台权限体系同源。**模型调用不走 MCP**——它需要原生协议与流式，走独立的模型协议直连面。

| 工具 | 用途 |
|------|------|
| 知识库检索 | 检索结果可见范围 ⊆ 该服务账号被显式授予的知识库范围，不新增数据面 |
| 知识库清单查询 | 列出该服务账号被授予范围内可声明接入的知识库及其标识，供能力声明填写（RT-04 / GOV-05） |
| 模型清单查询 | 查询可用模型；模型调用本身不走 MCP |
| 用户身份/组织查询 | 应用开发中查身份与组织架构 |
| 应用数据表结构与数据查询 | 开发与排障时操作应用自有数据 |
| 应用状态/日志自查 | deploy 后本地 agent 可自行「读日志 → 修 → 再发」闭环，含审批状态查询 |

- 界面与交互：**无平台界面**——本条是对外协议面（MCP Server + OpenAI 兼容端点），开发者侧要看的地址与接入指引集中在 DEV-01 的接入信息区。
- 模型协议直连面（**仅 OpenAI 兼容**）：

| 要素 | 约定 |
|------|------|
| 协议 | OpenAI 兼容原生协议，支持流式。**本版不提供 Anthropic 兼容面**（上游《产品方案》§3.4 决议）——只讲 Anthropic 协议的工具（如客户自装的 Claude Code）接不了平台托管模型，须用其自带订阅 |
| 鉴权 | 开发者 API key（服务账号密钥，DEV-01） |
| 可用模型范围 | 租户管理员经能力总线配置的可用模型（GOV-05） |
| 计量 | 用量计入按 key 账单（GOV-04） |
| 适用对象 | 讲 OpenAI 协议的本地引擎（Qwen Code / Codex CLI / Kimi Code 等）。客户自装的 Claude Code 经 MCP / 技能包 / SDK / CLI 接入企业上下文，但模型走其自带订阅、不经本面 |

- 规则与边界：

**① 知识库检索的边界与强度**

  - 检索与清单查询结果 ⊆ 该服务账号被**显式授予**的知识库范围（NFR-1），授权走与平台 UI 同一套权限体系。
  - **过滤强度必须是文件级**：与平台工作台检索走同一条双层过滤路径（索引层预过滤 + 结果层批量校验兜底）。**不得复用既有开放 API 中仅做知识库级一次校验、无文件级过滤的旧检索路径**——该缺口已被鉴权 PRD §4.4.6 列为必须补齐的交付前提（复用组件与落点见其附录 E.3），补齐后 MCP 检索与 V2 检索收敛到同一条路径。
  - **fail-closed**（NFR-1.4）：权限评估失败 → 返回错误，绝不返回未过滤或部分过滤的结果集；无法确立调用者身份 → 拒绝，不降级。

**② 身份/组织查询是高危面，边界由「给不给位」承担**

  - 实际可及范围是**本租户全量组织架构**（姓名、部门、层级），**不做也无法做更细的收窄**：平台不存在「把某些部门授予某个服务账号」这类资源授权，服务账号本身也刻意不属于任何部门（鉴权 PRD D10 / §7.4），没有可供推导可见范围的立足点。
  - 因此 `identity:read` 是**高危位**——边界由「给不给这个位」承担，而非由范围收窄承担，签发表单须显著提示（DEV-01）。**租户隔离仍然生效**：跨租户的部门与用户一律读不到。
  - 若后续要收窄，只能从能力侧下手（如只允许按 user_id 点查、不提供组织树列举），属独立议题。

**③ 应用类工具按 owner 收窄**

  - **这三个工具只能操作 key 持有者自己的应用**：每把 key 都绑着一位资源归属人（DEV-01），工具仅对**这个人 owner 的那些应用**生效，查他人应用一律拒绝。CLI `logs` 同口径（DEV-04）。
    - 开发者日常感觉不到这条限制——首发 deploy 时应用 owner 就是该 key 的资源归属人（DEV-04），**「自己 deploy 上去的」天然满足**，只有越界时才会撞上。
    - 它限的是**泄漏后的爆炸半径**：key 是落在开发者笔记本上的文件，没有这条，任意一把 key 泄漏就能拖走全租户所有应用的业务数据与日志。
    - 日志内容范围与应用详情页运行日志同规则（WB-13）。**例外**：租户管理员查他人应用日志走应用详情页（其对本租户应用天然可见），**不走开发者 key 通道**。
  - 应用状态工具返回**审批终态与驳回理由全文**——本地排障闭环依赖它（DEV-04）。

**④ 三面只走模式 S——持 `delegate` 的 key 不能用于本地开发**

  - **MCP 工具面、模型协议面与 CLI 一律以服务账号自身身份执行，不承载委托**（该 PRD §4.2.4 已同步立此规则，验收 AC-48 / AC-49）。持 `delegate` 位的 key 接这三面在**通道入口**即被拒绝（CLI 在 `login` 就拒，不等到 deploy），提示「这把 key 配置为委托专用，本地开发请另发一把」。签发侧已硬阻断该组合（DEV-01），此处是对历史 key 的运行期兜底。
  - **判据：权限基准替换只在有第三方自然人在场时才有意义**——本地开发通道的两头是开发者本人与他的 agent，没有被代表的对象。逐工具看，模式 D 在本面**零个受益**：模型清单与身份/组织查询的可及范围本就是租户级配置，替换后毫无变化；另两类则会被它损坏——
    - **知识库清单查询**：它的用途是填写能力声明（RT-04 / GOV-05），而声明是**应用级静态配置**，per-user 过滤发生在运行期（GOV-05 = 声明范围 ∩ 当前访问用户可见范围）。若按被代表用户返回，开发者会把某一个人的可见集合固化进声明，运行期再叠一层，实得两次收窄的交集——**不报错、只少给**，开发者无从察觉。
    - **应用数据 / 状态 / 日志**：③ 立的 owner 收窄限的是泄漏后的爆炸半径；纯替换叠加「模式 D 下创建的资源归属被代表用户」（该 PRD AC-46），会把它从「只能拖走一个人的应用」放大到「委托范围内所有人的应用」，验收 6 一并被绕开——该 PRD 检查 3 只禁止以管理员为委托目标，不禁止委托给另一位开发者。
  - **拒绝方式不得实现为「漏传委托头就落回模式 S」**：该 PRD 铁律 2 规定持 `delegate` 的 key 漏传身份头返回 400 而非降级，静默落回正是其 §7.3 否决的失败形状；而 `26016` 这类参数错误对本地 agent 是天书。**按权限位在入口直接拒绝**是两者之外唯一可诊断的做法。
  - 与 RT-01 同向：托管应用**运行期**的用户身份以平台登录态为信任根、明令不挂委托头。**应用工场全册没有模式 D 场景**——它服务的是自建系统代表员工提问（该 PRD 场景二），与本地开发和托管运行两条路都不相交。
- 验收要点：
  1. 上表六类工具经 MCP 全部可调用；密钥未持对应权限位的工具调用被拒绝（按 DEV-01 权限位映射表逐位验证拒绝行为）。
  2. 经 MCP 检索到的知识库内容不超出该服务账号被显式授予的范围。
  3. 用 A 的 key 去查 B 的应用（数据 / 状态 / 日志三类工具）被拒绝；查 A 自己 deploy 的应用正常。
  4. 讲 OpenAI 协议的本地工具可直连平台托管模型并流式返回，调用按 key 计入审计；仅讲 Anthropic 协议的工具连接被拒并给出明确提示（本版无该协议面）。
  5. 未持 `identity:read` 的 key 调用身份/组织查询被拒；持有该位时可读本租户组织架构，且**跨租户的部门与用户一律读不到**（验证真实边界是租户隔离，而非组织子树收窄）。
  6. 经 MCP 查他人应用日志一律被拒——**即使这把 key 属于租户管理员名下的服务账号**（管理员要查他人日志得走应用详情页）。
  7. 应用状态工具可查到审批驳回终态及驳回理由全文。
  8. 集合相等：经 MCP 检索的结果与对该服务账号授予范围的预期集合相等——不多给也不少给，验证样本须含未授予知识库与同库内文件级权限差异（部分文件无权）场景。
  9. 人为使权限引擎不可用，MCP 检索返回明确错误，而非未过滤或部分过滤的结果（NFR-1.4）。
  10. 持 `delegate` 位的 key 在 MCP、模型协议面与 CLI `login` 三处均被拒绝，提示明确指向「委托专用、本地开发另发一把」；**且不得表现为按服务账号身份正常执行**（验证没有静默落回模式 S），也不得只回一个参数错误码。

**DEV-03 毕昇开发技能包（首发两包）**

> **一句话**：MCP 管「调用」，技能包管「**会用**」——平台能力的使用知识以开放技能格式随平台版本发布，本地 agent 读了才知道怎么写应用包、怎么调 SDK。

- 需求描述：使用知识以开放技能格式（SKILL.md + 可运行样例 + 连通自检脚本）发布，`bisheng skills sync` 从自家平台拉取。**首发两包**（由原四包收敛，取舍理由见下）：

| 技能包 | 何时用到 | 内容 |
|--------|---------|------|
| **部署纳管** | 要把应用发上平台时 | bisheng-app.yaml / 能力声明 / 安全红线（禁写鉴权·连接串·密钥）/ 托管运行契约（平台托管提供与不提供什么，DEV-04）/ deploy 工作流与预检排障指引（声明补全 → deploy → 预检修复 → 审批状态跟踪） |
| **平台能力接线** | 写代码要调平台能力时 | **SDK 三件套**（DEV-07）：**auth**——读平台注入身份即得用户、**禁止自建登录页**（⚠️ 本节须显著标注：这是唯一「写错了应用照样跑起来、只是身份是错的」的静默失败点）；**retrieve**——知识库检索用法与 per-user 过滤语义；**storage**——附件存取。**外加两条不走 SDK 的标准库接法**：**模型**——用官方 OpenAI 兼容客户端 + 平台注入的 base_url 与 key，模型名即平台模型管理原名（无逻辑档位转换）、token 计量；**应用数据库**——用标准库连平台注入的连接环境变量，结构演进策略（加列安全 / 改删列需确认，RT-05） |

> **为什么正好是两包**（原为四包）
>
> 判据是「**不预先知道，本地 agent 会失败吗；平台报错能否让它自己学会**」——能靠反馈学到的不必预先教，agent 本来就在错误里迭代。
>
> - **部署纳管不可替代**：预检只报「缺什么」、不教「怎么写」，不预先知道就完全做不成。
> - **接线知识合为一包**：SDK 三件套与两条标准库接法，本就是同一件事（应用怎么调平台能力），边界天然。其中 auth 一节须显著标注——它是唯一「写错了应用照样跑起来、只是身份是错的」的**静默失败点**，篇幅最短但最重要。
> - **原「模型接线」不再独立成包**：base_url 由接入信息区直接给出（DEV-01），调错了平台报错明确（404/401），agent 自己就能纠正——独立成包价值最低。
>
> **为什么不干脆合成一包**：两条路径互相独立且都真实存在——「只导入不集成」（不用任何平台能力的存量应用，§1.3 前提 1）与「只集成不部署」（本地开发期用平台模型与知识库、尚未发布）。再合会把无关知识塞给对方。
>
> **真实收益不是少写文档，是包数即同步面数量**：技能包与平台内引擎的平台能力指令须内外同源一份，每包另带可运行样例与自检脚本——四包收敛为两包，**会漂移的地方减半**。后续可按真实反馈再拆：某一节被证明高频独立触发时，从「平台能力接线」中析出即可，不影响已发布包的内容。

- 界面与交互：**无平台界面**——技能包经 `bisheng skills sync` 拉到本地用户目录，由本地 agent 直接读取。
- 规则与边界：
  - **版本对齐**：从自家平台拉取，与平台版本天然对齐、无公网依赖；重复 sync 以平台当前版本覆盖更新本地技能包。**`bisheng login` 成功后自动执行一次**，开发者无需为首次获取技能包单独敲命令（DEV-04）。
  - **内外同源**：与平台内造应用引擎读同一份内容，不维护两套文档。
  - **触发描述不绑产品名**：以通用意图表述（如「将本地项目部署 / 发布到企业的应用平台」）——BiSheng 是 ToB 开源平台，企业部署常用自有品牌名。目标平台实例由 login 凭据与 skills sync 的来源平台确定，与名称无关。
- 验收要点：
  1. `bisheng skills sync` 后本地存在两包，每包含可运行样例与自检脚本；自检脚本对已配好的环境执行通过，对缺失配置给出可读的失败原因。
  2. 两包内容与平台内引擎所用平台能力指令同源一份（抽查关键规则一致）。
  3. 非 Claude Code 引擎可经 AGENTS.md 引用同一技能目录使用。
  4. 平台升级后再次 sync，本地技能包更新到平台当前版本内容。
  5. 以不含产品名的自然语言（如「把这个应用部署到公司的应用平台」）向本地 agent 提出部署诉求，能正确触发「部署纳管」包进入部署流程。
  6. 未读技能包时 agent 倾向于自建登录页；读过「平台能力接线」包后改为读平台注入身份、不写登录页（验证静默失败点的知识确实生效，NFR-1.3）。

**DEV-04 CLI 命令集**

> **一句话**：五个命令覆盖「接入 → 本地联调 → 发布 → 排障」，`deploy` 是**唯一发布通道**且走与平台内应用**同一条管线**——同治理承诺（§1.3 前提 2）在这里兑现。命令数刻意收在最少：每一个都在主旅程关键路径上，或是没有替代路径的必需项。

- 需求描述：`bisheng` CLI 是本地开发者与平台交互的工作流入口。CLI 安装包由平台自身分发（下载指引见 DEV-01 接入信息区），纯内网环境零公网依赖。

- 界面与交互（**命令行即本条的交互面**，无平台界面）：

| 环节 | 命令 | 行为 |
|------|------|------|
| 接入 | login | 以开发者 API key（服务账号密钥）登录目标平台（DEV-01），凭据落本地用户目录；**登录成功后自动执行一次 `skills sync`**——技能包是 agent 干活的前提，不该让开发者多敲一次 |
| 接入 | skills sync | 从已登录平台拉取毕昇开发技能包（DEV-03）。`login` 已自动跑过一次，本命令用于**平台升级后更新** |
| 本地联调 | dev | 在本地运行应用，注入与线上同构的平台身份、并提供本地应用数据库（DEV-05） |
| 发布 | deploy | 把当前项目作为版本快照提交发布，**唯一发布通道**；管线见下 |
| 排障 | logs | 查看**自己的应用**的运行日志——即该 key 的资源归属人 owner 的应用，查他人应用被拒。**它是三个日志入口之一，选哪个见下** |

> **日志有三个入口，按操作者选**——三者的权限口径（owner-only）与内容范围（WB-13 同规则）**完全一致**，差别只在谁在操作：
>
> | 入口 | 适用 |
> |---|---|
> | **MCP「应用状态/日志自查」工具**（DEV-02） | **本地 coding agent**——它是 `deploy → 读日志 → 修 → 再发` 闭环的一环，也是 §3.1 操作者模型下的默认路径 |
> | **CLI `bisheng logs`**（本条） | **开发者本人在终端**，或未配置 MCP 的纯 CLI 用法（集成是可选项，§1.3 前提 1） |
> | **应用详情页 · 运行日志**（WB-13） | 需要图形界面时；**查他人应用只有这条路**（仅租户管理员，DEV-02） |

- 流程（deploy 发布管线四步）：
  - **①** **托管预检**：依赖构建 / 应用包声明校验 / 启动探活，判定标准 = 托管运行契约（见下）。失败 → 原地拒绝，说明缺失项与改造指引，不进入审批。预检检出破坏性结构变更（改/删列）→ 要求显式确认（交互确认或 `--confirm-schema-change`），未确认则拒绝；迁移前自动快照的承诺不变（RT-05）。
  - **②** **发布前安全扫描**：与平台内发布同一规则集，产物含裸密钥/连接串即阻断（RT-03）。扫描命中 → deploy 原地失败，输出命中规则与文件位置（不含密钥值本身，NFR-2），本地修复后重新 deploy（平台内应用的对应分支为回流管家改写，RT-03，两路径分述）。
  - **③** **审批**：首发与迭代每次 deploy 均生成审批单，走平台预置审批流（审批人由 GOV-02 解析），同一应用同时至多一个在途审批单，在途期间再次 deploy 被拒绝并提示；审批人对导入应用的预览试用以待上线版本快照起审批期临时实例（RT-03）。驳回 → owner 经发布面（WB-14）或 MCP 应用状态工具（DEV-02）查看驳回理由，修改后重新 deploy 生成新审批单。
  - **④** **上线托管**：审批通过后应用在平台托管环境运行、进入广场（RT-01 / RT-02）。
- 托管运行契约（预检第 1 步的判定标准，随「部署纳管」技能包对外，本地开发期即可对照，DEV-03）：

| 平台托管提供 | 应用不得自带或依赖 |
|-------------|-------------------|
| 语言运行时 | 数据库 / 消息队列 / 缓存等中间件 |
| 应用数据库 | 白名单外的外网地址 |
| 附件/文件存储 | — |
| 能力总线各项能力与密钥注入 | — |
| 依赖包经平台内网镜像安装 | — |

  契约内的应用保证可托管；契约外的依赖在预检被拒绝并给出改造指引（数据改接平台应用数据库的范式见 DEV-03「平台能力接线」包的应用数据库一节——该路径**不走 SDK**，用标准库连平台注入的连接，DEV-07），不承诺自动改造。
- 规则与边界：
  - **谁 deploy 上去的，就归谁**：首发 deploy 时，该 key 的资源归属人成为这个应用的**唯一 owner**（鉴权 PRD §4.5 定义 6；该字段必填，故不存在「无归属人也能 deploy」的情形）。
  - **之后只有同一个人的 key 能再 deploy 它**：换一把资源归属人不同的 key 去 deploy 既有应用会被拒绝并提示应用归属。owner 转移见 §5.2。
  - 发布输入以 bisheng-app.yaml 为准：能力声明与资源档位在应用包中声明（档位未声明时为默认推荐档，GOV-03）；应用元信息（名称/描述/图标）亦取自应用包、随 deploy 更新（RT-02）。
  - **有一批操作没有命令行等价物**，须去 **应用详情页 · 发布** 完成（清单见 §2.2，导航见 §3.0.1）。其中**设置可见范围是首发后的必经一步**——它不在应用包内、`deploy` 不承载它，不设则应用虽已上线进广场也除 owner 外无人可见（GOV-01）；撤回、下线、删除等为按需触发。
  - 审批状态跟踪不必离开本地：发布面与 MCP 应用状态工具两条路等价（DEV-02）。
  - **首发 deploy 的准入闸是 key 上的 `app:manage` 位**（DEV-01），CLI 不查资源归属人的「创建应用」角色权限——该权限点只管界面通道的新建入口，两条通道各有各的闸、互不校验（理由见 GOV-07）。
  - **CLI 只以服务账号自身身份执行**：持 `delegate` 位的 key 连 `login` 都被拒（DEV-02 ④），因此 deploy 的 owner 恒等于该 key 的资源归属人，不因任何请求头改变。
- 验收要点：
  1. 五个命令按上表行为可用；key 被吊销后 CLI 命令报鉴权失败并提示重新 login。
  2. `bisheng deploy` 的每次发布（首发与迭代）均进入审批流（RT-03/04）；发布前扫描与平台内发布同一规则集（常见凭据模式正则清单 + 数据库连接串模式 + 平台自签发 key 前缀模式，GOV-08），规则集内样本 100% 被阻断。
  3. 经 CLI 导入发布的应用在广场、权限、审计中的表现与平台内造的应用一致；bisheng-app.yaml 声明的资源档位生效，未声明时为默认推荐档。
  4. 依赖平台不提供的中间件（如自带数据库）的项目 deploy 被预检拒绝，报错说明缺失项与改造指引；预检失败不产生审批单。
  5. 同一应用存在在途审批单时再次 deploy 被拒绝并有明确提示。
  6. 预检通过并经审批的应用在平台托管环境正常启动运行。
  7. 端到端：在本地 coding agent 对话中以自然语言提出部署诉求（表述不含特定产品名，DEV-03），agent 凭技能包 + CLI + MCP 完成应用包声明补全 → deploy → 预检失败修复 → 审批状态跟踪——**这一段全程不离开本地对话**。
  8. 承接上条：首发上线后，owner 在应用详情页 · 发布中设置可见范围，被授权的同事即可从应用广场打开使用（GOV-01 / RT-02）——**验证「上线」与「可用」是两步，缺第二步同事看不见**。
  9. 用 A 的 key 去 deploy B 的既有应用被拒绝，提示中说明该应用归属谁。
  10. 含改/删列的迭代 deploy 未经显式确认被预检拒绝；确认后进入管线，且迁移前自动留快照。
  11. `bisheng login` 成功后本地已存在技能包，**无需再手动敲 `skills sync`**；平台升级后重跑 `skills sync` 可更新到当前版本（DEV-03）。
  12. 同一个应用的运行日志，经 MCP 工具、CLI `logs`、应用详情页运行日志三个入口取到的内容范围与权限判定一致。

**DEV-05 bisheng dev 本地运行与平台身份注入**

> **一句话**：应用**永远只读平台注入的身份、不写登录页**——`bisheng dev` 在本地注入与线上同构的身份，因此本地与线上代码零差异、本地跑通即线上跑通。

- 需求描述：`bisheng dev` 在本地运行应用，并**以与线上同构的方式注入平台身份**，使应用无需为「本地」和「线上」写两套代码。

| 项 | 线上（托管运行） | 本地（`bisheng dev`） |
|---|---|---|
| 身份从哪来 | app-proxy 验平台会话后注入当前**访问用户** | CLI 内置的迷你代理注入 key 对应的**开发者服务账号** |
| 应用怎么拿 | 读注入头 / `SDK.auth` 一行 | **完全相同** |
| 平台能力按谁的权限放行 | 当前访问用户（OBO） | 该服务账号被显式授予的范围（NFR-1） |

  **应用侧零登录代码**：身份的唯一可信来源是平台注入，应用不得自建登录页或鉴权逻辑（NFR-1.3）。

- 界面与交互：**无平台界面**——`bisheng dev` 的输出即交互面，须明示当前注入的身份来源与账号，避免开发者误以为自己在以他人身份运行。
- 规则与边界：

**① 不提供本地身份模拟开关**

  - **CLI 不提供 `--as <user>` 之类的参数**。那等于给开发者一个**绕过平台准入的后门**：命令行随便填一个 user_id，`SDK.auth` 就返回那个人——正是《开放 API 鉴权与身份传递 PRD》F4「裸 `user_id` 参数」缺口的本地翻版，而该 PRD 的整个受限委托机制就是为堵这个缺口而建。
  - **平台整体确实支持代表他人执行，但那条路不在本地**：模式 D 委托（配 `delegate` 位 + 委托范围，过五道准入、留 actor + subject 双归属审计，该 PRD §4.4.4 / §4.4.5）只作用于 **V2 开放 API 面**，服务的是自建系统代表员工提问；**本地开发三面只走模式 S，持 `delegate` 的 key 在这三面一律被拒**（DEV-02 ④）。本地要验 per-user 差异，路径见 ②。
  - `--as` 与模式 D 的分界不是「能不能以他人身份行事」，而是**「这次行事有没有经过平台授权」**——前者无任何检查，后者五道准入 + 审计。

**② 本地验不了 per-user 行为差异，这是事实而非限制**

  - 本地注入的是**服务账号**，它不是自然人，本地也不存在「真实访问者」。因此**张三看到什么 vs 李四看到什么**这类差异，本地开发期无从复现——与提不提供模拟开关无关。
  - **验证路径**：发布后用**真实账号访问已发布应用**（与工作台预览不做「模拟用户视角」同口径，PRD-2 §5.1）。

**③ 权限边界与线上同规则**

  - 本地运行期应用经 SDK / MCP 调用的平台能力，按该服务账号**被显式授予**的权限放行；过滤强度、fail-closed 行为与线上一致（NFR-1、DEV-02）。
  - **本地应用数据库由 `bisheng dev` 提供**：起一个本地 sqlite 并注入与线上**同名**的连接环境变量，使应用用标准库写的数据访问代码本地线上零差异（应用数据库不进 SDK 的前提，DEV-07）。
  - 这意味着**本地能检索到的知识库 ⊆ 该服务账号被授予的范围**，可能窄于线上真实用户的可见范围——开发期据此写代码不会「本地能跑、线上越权」，只会「本地看得少」。

- 验收要点：
  1. `bisheng dev` 下应用取到的身份为 key 对应的服务账号，注入结构与线上一致、应用代码零差异。
  2. **CLI 无任何指定其他用户身份的入口**（无 `--as` 及等价参数）；伪造注入头的尝试对应用无效——身份唯一来源为平台注入（NFR-1.3）。
  3. 本地运行中应用调用知识库检索等平台能力，结果按该服务账号被授予权限过滤；权限引擎不可用时返回明确错误而非未过滤结果（NFR-1.4）。
  4. 应用代码中不存在登录页与自建鉴权逻辑。
  5. 同一份应用代码不加改动地 `bisheng deploy` 上线后，在托管环境取到的是**当前访问用户**的身份（验证「本地与线上同构」确实成立，RT-01）。

*（**DEV-06 导入应用的改码权归属与交接：本版不做**，本轮 MVP 收敛，顺延见 §5.2。原设计的「交接给管家 / 收回到本地」在本册单独交付期本就恒为「在本地」——PRD-2 管家未上线，交接无处可去，整条是空的。**本版口径**：导入应用的改码权恒在本地开发者手中，平台侧对其代码只读；owner 在本地改完 `bisheng deploy` 重新发布，与「本地写代码 → push 发布」的日常方式一致。）*

**DEV-07 bisheng-sdk（代码面）**

> **一句话**：SDK 只封装**平台特有、且写错了会出安全事故**的三件事（auth / retrieve / storage）；数据库与模型调用**刻意不进 SDK**——那两样有行业标准库，包一层是负价值。

- 需求描述：Python 首发的 bisheng-sdk 提供**三件套**薄封装（由原五件套收敛）。每个模块都要回答「为什么需要 SDK，而不是直接调」：

| 模块 | 用途 | **为什么需要 SDK** | 权限/边界要点 |
|------|------|------------------|--------------|
| **auth** | 读平台注入身份 | **唯一的静默失败点**——自建登录页或读错头，应用照样跑起来、只是身份是错的，平台不会报任何错（DEV-03 同判据）。一行调用把正确做法变成默认做法 | 身份唯一可信来源是平台注入（NFR-1.3） |
| **retrieve** | 知识库检索 | **封装一个易错的安全决定**：必须以**当前访问者**的身份检索、而非应用自身的身份，选错即越权。SDK 把这个选择固定下来 | 托管运行期：结果 = 能力声明知识库 ∩ 当前访问用户可见范围（文件级、fail-closed，详 GOV-05）；本地 dev 期按开发者服务账号被授予权限（DEV-05） |
| **storage** | 附件文件存取 | **平台必须中介**：按应用收窄存取范围、附件不计租户存储配额（GOV-03）、且不把底层对象存储实现暴露给应用。没有可直连的行业标准形态 | 平台托管存储；托管契约禁止应用自带文件存储（DEV-04） |

**刻意不进 SDK 的两样**（收敛理由记录在此，避免实施时按惯性加回来）：

| 原模块 | 为什么不做 | 那怎么用 |
|---|---|---|
| ~~chat~~（模型调用） | 模型面已收敛为**仅 OpenAI 兼容协议**——那就是行业标准，`openai` 官方库直接可用。自研封装的收益仅是省掉 base_url / key 两行赋值，代价是让开发者学一套非标准 API、丢掉官方库的流式与重试与类型生态、并把这些长尾变成我们自己维护。**与上游《产品方案》§3.4「不自研协议长尾、采用现成实现」是同一条理由——平台不和行业标准客户端竞争** | 用官方 OpenAI 兼容客户端，`base_url` 与 key 取平台注入的环境变量；用法随 DEV-03「平台能力接线」技能包交付 |
| ~~appdb~~（应用数据库读写） | 支撑它的理由逐条都能被「注入连接 + 标准库」替代：**①** 「代码里不出现连接串」——环境变量引用不是字面量，与发布前扫描不冲突；**②** 建表改表由 manifest 声明、**平台建表**，应用只读写既有表；**③** sqlite / postgres 双档差异 **SQLAlchemy 原生就屏蔽**；**④** 租户隔离由注入的连接本身承担，是注入侧的事、不是调用侧；**⑤** 结构演进预检是平台侧 diff manifest，与 SDK 无关 | 平台注入应用数据库连接环境变量，开发者用标准库（SQLAlchemy 等）直接连；**本地由 `bisheng dev` 起一个本地 sqlite 并注入同名环境变量**，保证本地与线上代码零差异（DEV-05） |

- 界面与交互：**无平台界面**——SDK 是代码面，开发者的接触点是包与随包发布的开发者指南。
- 规则与边界：
  - **调用范式全平台唯一**：存量本地项目按需引入 SDK，平台内模板生成的应用预接线同一 SDK——本地手写的与平台内生成的应用是同一套调用范式。
  - **随 SDK 发布开发者指南**：安装、三件套用法、数据库与模型的标准库接法、与技能包 / CLI 的配合。
  - **不进 SDK 的两样不得按惯性加回**：模型调用与应用数据库的取舍理由见上表，实施时若要新增模块，须先证明它同时满足「平台特有」与「写错了会出安全事故」两条。
- 验收要点：
  1. 三件套 API 可用：auth 取到平台注入身份、retrieve 结果受调用者权限过滤、storage 可存取附件。
  2. **不经 SDK 的两条路径同样通**：用官方 OpenAI 兼容客户端 + 平台注入的 base_url 与 key 可调通平台托管模型；用标准数据库库 + 平台注入的连接环境变量可读写应用数据库。
  3. 平台内模板生成的应用与按需引入 SDK 的本地应用使用同一调用范式（抽查关键调用一致；依赖 PRD-2 WB-01 模板交付，前置依赖声明见 §1）。
  4. 开发者指南随版本发布，按指南可走通 login → dev → deploy 完整流程。

### 3.2 应用运行时与发布（RT）

**本域交付：应用发布后「跑起来、被找到、被用起来」的全部行为——统一入口、应用广场、版本记录、发布审批流、资产持久与稳定性承诺。**

**本域是两条造应用旅程的共享地基**：CLI 导入的应用与 PRD-2 工作台内造的应用，从提交发布那一刻起走的是同一套流程，本域条目对两者一视同仁。

本域七个条目按应用发布后的生命周期排列（跳过 RT-06——属 PRD-2；RT-09——顺延 v3.1）：

| 管什么 | 条目 | 本域给出的答案 |
|--------|------|---------------|
| **怎么被访问** | RT-01 | 复用平台登录，应用零登录代码 |
| **怎么被找到** | RT-02 | 与工作流 / 助手并列进同一个广场 |
| **怎么上线** | RT-03（审批流）· RT-04（审的是什么） | 每次发布必审，审的是能力声明与冻结快照 |
| **怎么留痕与演进** | RT-05 | 版本只增不改；结构变更随发布生效 |
| **怎么退役** | RT-07 | 资产恒在平台，删除唯经 owner 显式流程 |
| **坏了怎么办** | RT-08 | 应用可以不稳定，平台必须正常 |

**RT-01 统一入口与平台登录复用**

> **一句话**：应用**不自建登录**——复用平台既有登录方式，已登录即点即用，应用侧零登录代码。

- 需求描述：每个已发布应用拥有内网统一入口 `/apps/{应用标识}`；应用不自建登录，复用 BiSheng 平台既有登录方式（账号密码、SSO 扫码等，与平台登录配置一致），应用自动获得当前访问者的身份与组织信息——应用侧零登录代码。
- 界面与交互（访问分支）：

| 访问者状态 | 系统行为 |
|-----------|---------|
| 已登录平台 + 在可见范围内 | 点开即用、免二次登录，进入应用并注入访问者身份与组织信息 |
| 无登录态（含手机扫码访问） | 重定向到平台登录页（含平台已配置的 SSO 方式），登录成功后回跳原应用地址 |
| 已登录平台 + 无可见范围权限 | 进入统一「无权限」页 |

- 界面与交互（四类兜底页）：

| 兜底页 | 触发场景 | 页面要素 |
|--------|---------|---------|
| 无权限页 | 已登录但不在应用可见范围内 | 应用名与 owner + 无访问权限文案 + 引导联系应用 owner 或**平台管理员**开通权限（与已下线页指引口径一致） + 「返回广场」按钮；本版不含在线申请入口 |
| 未部署工场引导页 | 本环境未启用应用工场运行时层（GOV-10） | 「本环境未启用应用工场」文案 + 引导联系**平台管理员**开启 |
| 已下线页 | 应用处于已下线态（RT-07） | 应用名 + 已下线提示 + 引导联系应用 owner 或**平台管理员** + 「返回广场」按钮 |
| 应用不存在页 | 访问已删除应用的存量链接/二维码，或从未上线（草稿/待上线态）应用的入口地址 | 「应用不存在或未上线」文案 + 「返回广场」按钮 |

- 规则与边界：
  - **身份的唯一可信来源是平台注入**：访问者身份与组织信息由平台在入口处注入，客户端传入或伪造的身份一律无效（NFR-1.3）；应用侧不自建登录、不自行解析凭据（DEV-05 / DEV-07 auth）。
  - **能否进入由可见范围决定**：入口访问与广场可见性共用同一份可见范围（GOV-01），变更自被授权用户的下一次请求起生效。
  - **入口地址不随版本变化**：应用标识在首发时确定，迭代发布与下线 / 重新上线均不改变入口地址与二维码——已分发出去的链接长期有效，这是二维码分发能成立的前提（RT-05 / RT-07）。
- 验收要点：
  1. 已登录平台的用户点开应用链接直接进入，无二次登录。
  2. 应用内能正确取得当前访问者身份与组织信息（如应用内显示当前访问者姓名/部门）。
  3. 无登录态的浏览器扫码访问，重定向到平台登录页（含平台已配置的 SSO 登录方式），登录成功后直达原应用。
  4. 无可见范围权限的用户访问入口得到统一「无权限」页，页面含 owner 与开通指引。
  5. 已删除应用的存量入口链接/二维码访问得到「应用不存在或未上线」页，不落报错页。

**RT-02 应用广场**

> **一句话**：已发布应用与工作流 / 助手**并列**呈现在同一个广场、共用同一套标签体系，用户只看到可见范围内的应用。

- 需求描述：已发布应用进入应用广场，与工作流/助手并列呈现，接入广场既有的标签分类体系；用户只看到自己可见范围内的应用，从广场直接进入使用。
- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 广场应用卡片 | 应用广场（与工作流 / 助手卡片同构） | 图标、应用名、一句话描述、owner；点击卡片进入使用 |

- 规则与边界：
  - 应用与工作流/助手共用同一套标签体系，复用现有标签机制与打标交互，不新建标签体系。
  - **本版不做应用标签设置**（顺延 §5.2）：应用接入广场既有标签体系但不提供打标入口，**未设标签的应用在广场默认分类中正常可见**，不影响闭环。
  - 应用元信息（名称/描述/图标）来源：CLI 导入应用取自 bisheng-app.yaml、随 deploy 更新（deploy 本身走审批，DEV-04）；平台内造应用在对话/发布面生成，owner 可在发布面修改。
  - 元信息不属能力声明：修改不构成发布、不触发审批，修改计审计（GOV-04）。
  - 广场按可见范围过滤，无权限用户的广场中不出现该应用。
- 验收要点：
  1. 应用发布且审批通过后出现在有权限用户的应用广场中。
  2. 未设标签的应用在广场默认分类中正常可见，可被搜索与浏览到。
  3. 无权限用户的广场中不出现该应用。
  4. 从广场可直接打开应用使用。
  5. 广场卡片展示图标 / 应用名 / 描述 / owner；owner 修改元信息后广场随之更新且不产生审批单，修改计审计。

**RT-03 发布审批流（首发与迭代均需审批）**

> **一句话**：**任何发布都必须走审批，不存在免审路径**；审批人审的是提交时冻结的「待上线版本快照」，可只读审读 + 预览试用。

- 需求描述：审批接入平台审批中心，审批人在审批中心处理应用发布审批单（场景接入与审批人配置见 GOV-02）。**首发与迭代一律必审**，平台不提供任何免审配置项。
- 流程：
  - **①** owner 提交发布——两条入口等价：**应用详情页 · 发布**（位置见下）或本地 `bisheng deploy`（DEV-04）。
  - **②** 冻结生成待上线版本快照（审读的权威对象）。
  - **③** 发布前安全扫描——与 CLI deploy 同一管线同一门，规则集见 DEV-04。产物含裸密钥/连接串即阻断发布：平台内应用 → 回流管家改写；CLI 应用 → deploy 原地失败并输出命中规则与文件位置（不含密钥值本身，NFR-2），本地修复后重新 deploy。
  - **④** 生成审批单，进入平台审批中心；审批人按 GOV-02 预置流程解析，收到站内消息与待办（§3.0.3）。**提交发布时须一并带上 owner 的主部门标识**——部门管理员这一来源依赖它，缺失会导致该来源解析为空、审批单全部压到租户管理员。
  - **⑤** 通过 → 上线终检（运行环境容量，GOV-03）：终检通过 → 上线、进入广场；终检未通过 → 应用入「待上线（资源不足）」态（§3.0.2），资源释放后 owner 手动上线、无需重新审批。
  - **⑥** 驳回 → 首发：应用回草稿态；迭代：应用保持已上线、当前版本继续运行，仅待上线版本标记被驳回。owner 在应用详情页 · 发布的审批状态区可见驳回状态与**理由全文**（CLI 路径亦可经 MCP 应用状态工具查询，DEV-02），修改后重新提交生成新审批单。
- 界面与交互（**owner 侧：提交与跟踪**）——位置：**platform 左侧菜单「构建」→ 应用列表 → 点击该应用卡片 → 应用详情页 → 「发布」tab**（完整导航见 §3.0.1；CLI 导入的应用同样在此列表中，与平台内造的应用同页同形态）：

| 区块 | 内容 |
|------|------|
| 提交发布 | 「提交发布」按钮 + 资源档位选择（GOV-03）；CLI 路径由 `bisheng deploy` 触发，不必来此页 |
| 审批状态区 | 当前审批单状态（待审 / 通过 / 驳回 / 已撤回）、**驳回理由全文**、「撤回」按钮（在途时可用） |
| 能力声明清单 | 本应用声明接入的平台能力完整白话清单（定义见 RT-04） |
| 版本列表 | 全部版本记录与终态标注，只读（RT-05；同页「版本」tab 亦可查看） |
| 可见范围 | 「设置可见范围」按钮，拉起平台通用授权弹窗（GOV-01）——**首发上线后的必经一步** |
| 运营动作区 | 下线 / 重新上线（RT-07）；待上线态时此处出现「手动上线」（GOV-03） |
| 入口链接与二维码 | 发给同事用（RT-01 / RT-02） |
| 危险操作区（底部） | 显式删除（RT-07，仅 owner） |

> 本表即 WB-14 的最小形态。PRD-2 上线后此页左侧接入管家对话、并增补预览 / 代码 / 资源 tab，**本表内容与入口不变**。

- 界面与交互（**审批人侧：审批单详情页**）——位置：平台审批中心 → 应用发布场景 → 审批单详情：

| 区块 | 内容 |
|------|------|
| 头部基本信息 | 应用名、owner、来源（平台内造 / CLI 导入）、类型标识（首发 / 迭代）、提交时间 |
| 能力声明白话摘要区 | 待上线版本的能力声明白话摘要（定义见 RT-04） |
| 可见范围区 | 提交时快照，标注「仅供参考，可见范围变更即时生效、不经审批」（GOV-01） |
| 资源档位区 | 所选资源档位（GOV-03） |
| 操作区 | 通过、驳回（驳回理由必填）、「查看待上线版本」审读视图入口 |

- 界面与交互（审读视图）：左侧文件树 + 右侧只读代码内容；tab 承载能力声明完整清单 / 版本历史 / 文件差异（迭代时，呈现方式同 WB-15 差异查看）；「预览试用」按钮置顶。
- 预览试用：**本册只有一种承载**——CLI 导入的应用没有草稿沙箱（改码权恒在本地，DEV-06 顺延），因此审批人以**待上线版本快照拉起审批期临时预览实例**（复用 deploy 预检启动探活的同一能力），连应用草稿库：

| 项 | 约定 |
|---|---|
| 拉起 | 审批人按需拉起，不预先起实例 |
| 回收 | 审批出终态（通过 / 驳回 / 撤回 / 取消）即回收；长期未处理超时回收（默认 7 天，部署配置项）；回收后可再次拉起 |
| 资源 | 复用 deploy 预检的启动探活能力，不额外占用应用运行实例名额 |

> PRD-2 上线后，平台内造的应用有 owner 草稿沙箱，届时增加「复用草稿沙箱直接预览、不单独起实例」这条承载（草稿与待上线版本不一致时须提示）。**本册不实现该分支。**

- 临时预览实例界面状态：

| 状态 | 界面表现 | 去向 |
|------|---------|------|
| 未拉起 | 「拉起预览」按钮 | 拉起 → 拉起中 |
| 拉起中 | 进度展示；失败时展示失败原因 | 成功 → 运行中；失败 → 未拉起（可重新拉起） |
| 运行中 | 「打开预览」+「手动回收」操作 | 审批终态 / 超时 / 手动回收 → 已回收 |
| 已回收（含超时回收） | 「重新拉起」按钮 | 拉起 → 拉起中 |

- 规则与边界：
  - 审读的权威对象 = 提交发布时冻结的待上线版本快照。
  - 本册的导入应用无草稿对话；PRD-2 上线后 owner 的草稿对话同样不对审批人开放（WB-16）。
  - 审批期间 owner 可继续在本地改码，改动不影响已提交的待上线版本（下次 `deploy` 才生成新版本）。
  - 同一应用同时至多一个在途审批单；再次提交须先撤回在途审批单。
  - 审批人预览身份与数据边界：注入身份 = 审批人本人；平台能力按 owner 权限放行（审批例外条款、计审计，NFR-1.2）；草稿库对审批人可写入试用数据。
  - 审批期试用数据归宿：平台内应用发布时「保留」的范围冻结为提交发布时刻的草稿库快照，审批期新增试用数据一律不带入生产（RT-06）；CLI 导入应用首发生产库默认空库初始化。
  - 审批单催办/超时提醒本版不做（§5.2）；紧急场景的应急路径 = 下线即时止血（RT-07，无需审批）+ 回滚走正常审批恢复（RT-05）。
- 验收要点：
  1. 除审批人经审读视图与预览试用外，首次发布的应用在审批通过前不可被任何其他用户访问。
  2. 审批人可在审批单中看到能力声明摘要、可见范围与资源档位，并可打开待上线版本的只读审读视图（代码、能力声明完整清单、版本历史；迭代时含相对上一已发布版本的文件差异）。
  3. 审批通过后进入上线终检：运行环境容量充足 → 应用上线并出现在可见范围内用户的应用广场（RT-02）；容量不足 → 应用入「待上线（资源不足）」态、不对外提供服务，owner 与租户管理员收到触达（§3.0.3），资源释放后由 owner 手动上线且**不重新审批**（GOV-03）。
  4. 驳回后 owner 在发布面可见驳回状态与理由，可修改后再次提交。
  5. 提交的产物含明文密钥/连接串时发布被阻断，且分路径处置到位：平台内应用 → 阻断并回流管家改写；CLI 导入应用 → deploy 失败并返回命中项与整改指引（与 DEV-04 验收口径对齐）。
  6. 审批中 owner 可撤回审批单；撤回后修改再提交生成新审批单。
  7. CLI 导入应用：审批人可从审读视图以待上线版本快照拉起临时预览实例试用；审批出终态后实例被回收。
  8. 审批人预览期间应用以审批人身份注入、平台能力按 owner 权限放行，预览行为计审计。
  9. 临时预览实例超时回收后可再次拉起（超时时限取部署配置）。
  10. 迭代审批被驳回时应用保持已上线、当前版本继续服务，仅待上线版本被弃。

**RT-04 能力声明定义**

> **一句话**：本条是**「能力声明」的权威定义出处**（全文唯一），并约定迭代发布同样必审。

- 需求描述：

> **能力声明** = 应用声明接入的平台能力显式清单：知识库、模型、密钥引用等总线能力。发布面与 RT-03 审批单两处展示同源于此。

- 界面与交互：**无独立界面**——本条只定义术语，展示落点在 RT-03 的发布面与审批单两处。
- 术语统一：发布面展示 = 能力声明完整白话清单；审批单展示 = 能力声明白话摘要；审读视图展示 = 能力声明完整清单。全文按此措辞。
- 规则与边界：
  - **迭代与首发同等对待**：每次迭代发布同样必审（RT-03），能力声明未变也不例外——这是本条特意强调的一点。
  - 「发布后迭代 = 继续对话」仅指改动过程无需打开工程；上线生效仍以审批通过为准。
  - 可见范围变更不经审批、即时生效、计审计（GOV-01 / GOV-04）。
  - **本版不做迭代审批单的变更摘要**（本轮 MVP 收敛，顺延见 §5.2）：首发闭环用不到它，审批人可经审读视图的文件差异自行比对。**将来若补做**，摘要应覆盖能力声明变更、可见范围变更、表结构变更、资源档位变更四类。
- 验收要点：
  1. 未改能力声明与可见范围的迭代发布同样生成审批单，审批通过前新版本不上线。
  2. 新接入知识库、新增密钥引用在审批单的能力声明摘要中可见。

**RT-05 版本记录与结构演进**

> **一句话**：每次提交发布生成一条**版本记录**并标注终态，部署历史线性可审计；**本版不做平台侧回滚**——CLI 路径的等价手段是本地 checkout 旧版本重新 `deploy`。

- 需求描述：版本记录于提交发布时生成，并标注终态（已上线 / 被驳回 / 已撤回）。版本记录是审计追溯、发布快照与资产持久（RT-07）的共同承载，**不因不做回滚而省略**。
- 每条版本记录包含：版本号、类型（首发 / 迭代）、提交时间、终态标注、代码快照、能力声明、平台注入配置、资源档位。**四者同属一个快照**——将来做回滚时统一回退，杜绝「回退代码却留下新配置」。
- 结构演进（结构变更随迭代发布生效的确定规则）：

| 变更类型 | 确认时机 | 发布时行为 |
|---------|---------|-----------|
| 加列 | 无需确认 | 自动迁移 |
| 改/删列 | CLI 路径：`deploy` 时显式确认（DEV-04；工作台路径的草稿期闸口随 PRD-2 WB-09） | 发布时不再二次确认；在发布摘要中展示；**迁移前自动留生产数据快照** |

- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 版本列表 | 应用详情页 · 版本（导航见 §3.0.1） | 全量展示全部版本记录：版本号、类型、提交时间、终态标注（已上线 / 被驳回 / 已撤回）、能力声明摘要；**只读，不提供回滚入口** |

- 规则与边界：
  - 版本记录**只增不改**：被驳回 / 已撤回的版本同样留在列表供追溯，不删除、不覆盖。
  - **本版不做平台侧回滚**（本轮 MVP 收敛，顺延见 §5.2）：本册主用户是本地开发者，**本地有完整 git 历史**，回退等价手段是 checkout 旧版本后重新 `deploy`，走同一条发布管线与审批。平台回滚的增量价值主要在 PRD-2——工作台内造的应用没有本地 git，届时随 PRD-2 一并实现。
  - 应急止血手段不受影响：**下线**（RT-07）即时生效、不经审批，是新版本出问题时的第一手段。
- 验收要点：
  1. 每次提交发布生成一条版本记录，含版本号 / 类型 / 提交时间 / 终态标注；被驳回与已撤回的版本同样在列表中可见并标注终态。
  2. 版本记录不被覆盖或删除；同一应用的历史版本可完整追溯。
  3. 含改 / 删列的迭代 `deploy` 在发布摘要中展示结构变更，且**迁移前自动留有生产数据快照**。
  4. 版本列表为只读，不存在回滚入口（本版不做，§5.2）。

**RT-07 代码资产持久与显式删除**

> **一句话**：运行实例只是可随时回收的执行体，**代码 / 对话 / 应用数据的真身恒在平台存储**；删除唯经 owner 显式删除流程，除此不存在任何资产删除路径。

- 需求描述：应用的运行实例只是可随时回收的执行体、自身不保存任何唯一数据——代码、对话、应用数据的真身恒在平台存储（每轮代码版本 WB-15 + 发布版本快照 RT-05 双保险）；删除唯经「显式删除应用」流程，除此不存在任何资产删除路径。
- 界面与交互（操作入口与确认强度）：

| 动作 | 发起人 | 入口 | 确认 | 审计 | 生效表现 |
|------|--------|------|------|------|---------|
| 下线 | owner / 租户管理员 | owner：应用详情页 · 发布运营动作区；租户管理员：构建 → 应用列表的卡片操作 | 二次确认（明示入口与广场将呈已下线） | 计审计 | 入口与广场呈「已下线」页（RT-01）；资产不受影响 |
| 重新上线 | owner / 租户管理员 | 同下线 | — | 计审计 | 恢复访问；叠加 GOV-03 运行环境容量校验 |
| 显式删除 | 仅 owner（租户管理员不可删除，处置手段 = 下线；owner 离职场景回链 §5.2 归属转移） | **与工作流、助手一致**：应用卡片 ⚙️ 菜单 →「删除」（导航见 §3.0.1）；应用详情页 · 发布底部危险操作区亦可 | 二次确认弹窗（**对标工作流：不要求输入应用名**），弹窗内明示删除范围；**另有前置状态闸——已上线态删除入口置灰、须先下线**，见下 | 计审计 | 资产删除，应用入「已删除」终态；存量入口链接/二维码访问呈「应用不存在或未上线」页（RT-01） |

- 规则与边界：

**删除的确认强度与前置状态闸**

  - **确认强度对标工作流**：保留二次确认弹窗，但**不要求输入应用名**。原设计的"输入应用名"式强确认取消——它成本高、且用户会复制粘贴应付，防护力并不随之提升。
  - **改用前置状态闸补强**：**已上线态不可直接删除**，删除入口置灰并提示「请先下线」，owner 须走「下线 → 删除」两步。
  - **可直接删除的状态**：草稿、待上线（资源不足）、已下线——三者的共同点是**没有对外提供服务的运行实例**。
  - **为什么这样换更稳**：确认弹窗防的是手滑，但强度再高也抵不过确认疲劳；而"先下线"强制一次**状态转换**，且下线本身有可感知后果（同事访问立刻看到已下线页），误操作会被当场发现，还留有挽回窗口。**净效果是保护更强、操作更轻**。
  - 删除交互因此可与工作流、助手**完全一致**（卡片 ⚙️ →「删除」），本册不需要专属的删除弹窗（GOV-01）。
  - ⚠️ **确认弹窗须明示删除范围**：托管应用的删除会一并带走**代码、对话历史与应用生产数据**（用户填报的业务记录），比删除一条工作流编排的影响面大——文案须点明，不能只写「确定删除吗」。

  - 只回收执行体、不触碰存档与版本记录的场景：应用下线、闲置回收、实例崩溃、工场运行时层整体不部署（GOV-10）。
  - 存档随平台数据一同备份。
  - 删除时在途审批单自动取消（入「已取消」态，§3.0.2）并站内消息通知审批人（§3.0.3）。
  - 下线态允许提交发布；审批通过仅落为待运行版本、不自动重新上线；重新上线时叠加 GOV-03 运行环境容量校验（§3.0.2）。
- 验收要点：
  1. 应用下线/实例回收后重新上线，代码、对话历史、生产数据完整无损。
  2. 除显式删除流程外，不存在任何导致应用资产被删的操作路径。
  3. **已上线态的删除入口置灰并提示「请先下线」**；下线后删除可执行，弹出二次确认（**不要求输入应用名**，与工作流一致）且文案明示删除范围含代码 / 对话 / 应用生产数据；草稿、待上线态可直接删除。删除动作在审计记录中可查。
  4. 下线期间访问入口与广场呈已下线提示，重新上线后恢复。
  5. 租户管理员发起删除被拒（其处置手段仅下线可用）；owner 删除后在途审批单自动取消且审批人收到站内消息通知。
  6. 下线态提交发布，审批通过后应用不自动启用，重新上线后新版本生效。

**RT-08 稳定性承诺（产品级）**

> **一句话**：**应用可以不稳定，平台必须正常**——单应用崩溃只影响自身并自动恢复，切换与恢复窗口内不落报错页。

- 需求描述：应用与平台、应用与应用之间运行隔离——单个应用崩溃只影响该应用自身并自动恢复，平台其余功能与其他应用不受影响。
- 界面与交互（两个过渡态，均**不落报错页**）：

| 过渡态 | 触发场景 | 入口表现 | 去向 |
|---|---|---|---|
| 发布中 | 新版本上线生效的切换窗口 | 短暂「发布中」提示 | 切换完成自动恢复正常访问 |
| 应用恢复中 | 应用崩溃后的自动恢复窗口 | 「应用恢复中」提示 | 恢复成功自动恢复正常访问 |

- 规则与边界：
  - **本承诺与运行时形态无关**（§1.3 前提 4）：compose 形态由容器重启兑现，k8s 形态由工作负载控制器原生兑现，**验收口径与时限完全相同**。
  - 隔离是承诺的核心，自愈时限是其可验证形态——时限同时登记为 NFR-6。
- 验收要点：
  1. 人为使某应用崩溃，平台主功能与其他应用访问正常。
  2. 崩溃应用在无人工干预下 5 分钟内自动恢复可用（本承诺同时列为 NFR-6）。
  3. 版本切换窗口内访问应用不出现报错页，切换完成后自动恢复正常访问。
  4. 崩溃-恢复窗口内访问应用入口得到「应用恢复中」提示而非报错页。

*（RT-09 iframe 嵌入升级（postMessage 协议 + 域名白名单）：平台既有嵌入能力的独立安全修复（修社区 #1705），与应用工场无功能依赖，不随本册交付，顺延登记于 §5.2。）*

### 3.3 治理与管理面（GOV）

**本域交付：管理员视角的看得见、管得住。** 八条需求按「管什么」分五组，可按需直达（跳过 GOV-06——属 PRD-2；GOV-09——已取消，见 §5.2）：

| 管什么 | 条目 | 本域给出的答案 |
|--------|------|---------------|
| **管人**——谁能造、谁能用 | GOV-07（能造）· GOV-01（能用） | 两处都沿用平台既有权限件，本册零新建 |
| **管发布**——每次上线怎么审 | GOV-02 | 平台预置流程，部署即生效、无需先配置 |
| **管家底**——给多少资源、能用哪些平台能力 | GOV-03 · GOV-05 | 档位三选一；能力配一次、声明使用 |
| **管痕迹与凭据**——留什么痕、密钥怎么管 | GOV-04 · GOV-08 | 全链路留痕；密钥四条产品承诺 |
| **管交付**——装不装、装哪种形态 | GOV-10 | 可整层不装；装则 compose / k8s 二选一 |

**本域的设计取向是「默认可用、按需收紧」**（§1.3 前提 5）：审批有预置流程、档位有默认推荐档、能力总线配一次域内共享——管理员**不需要先做任何配置**，第一次发布就能跑通；需要收紧时再逐项配置。

> 本域**不建独立的管理后台应用列表**：租户管理员对本租户内所有应用天然可见可管，构建 → 应用页对他就是全租户视图；治理动作分别落在 GOV-01（授权）/ RT-07（下线）/ GOV-04（审计），下方矩阵即其单一出处。

- 标注「仅 owner」的资产处置动作（删除、撤回在途审批单），平台超管与租户管理员均不可代行：管理侧兜底手段 = 下线（RT-07）；owner 离职等归属场景见 §5.2 归属转移。

**GOV-01 权限资源类型与授权交互**

> **一句话**：应用可见范围**完全复用构建页现有的「管理权限」交互**（卡片 ⚙️ 菜单里那个，即 F048 ReBAC 授权弹窗）——与工作流、助手是同一个入口、同一个弹窗、同一套语义，本册**零新建授权界面**；变更**即时生效、不经审批、计审计**。

- 需求描述：应用作为平台权限体系的一种资源类型接入，可见范围按用户 / 部门 / 用户组授予；授权交互复用构建页卡片 ⚙️ →「管理权限」拉起的平台通用授权弹窗，应用侧只需注册为一种新的资源类型。
- 界面与交互（两个入口，**拉起的是同一个弹窗、不是两套实现**）：

| 入口 | 位置 | 谁用 | 承担什么 |
|---|---|---|---|
| **卡片 ⚙️ →「管理权限」**（主入口） | 构建 → 应用列表，与工作流 / 助手完全一致（导航见 §3.0.1） | owner；租户管理员（对本租户任一应用均可操作，平台既有行为） | **日常管理**：事后调整、批量处理。与其它类型体验一致，用户无需另学 |
| **应用详情页 · 发布 → 可见范围区** | 见 §3.0.1 | owner | **流程引导**：呈现当前可见范围状态，首发上线后若仍为「仅 owner 可见」须**显著提示**并给出设置按钮——点击拉起上面同一个弹窗 |

  > 之所以在发布面也留一个口子，是因为**首发后设置可见范围是必经一步**（不设则同事看不见，§2.2）。若只有卡片入口，owner 发布完要退回列表、找到卡片、点齿轮，流程断裂。**但它不是第二套授权界面**——只是同一个弹窗的第二个触发点，外加一处状态呈现。

- 规则与边界：
  - 可见范围变更**即时生效**（自被授权用户的下一次请求起，作用于入口访问与广场可见性，RT-01 / RT-02）、**不经审批**、**计审计**（GOV-04）。
  - 在途审批单中呈现的可见范围是**提交发布时的快照**、标注仅供参考（RT-03）——因为它可能在审批期间被改。
  - 可见范围**不属版本快照**（RT-05）；**首发默认仅 owner 可见**，审批通过后由 owner 设置（RT-03）。
  - **租户管理员对本租户任一应用可直接查看并调整可见范围**——这不是本册新增，而是平台既有权限模型的自然结果（工作流与助手早已如此），托管应用保持一致；变更计审计并记录变更人（GOV-04）。反过来要让它「不能改」才需要额外加拦截，且会造出类型间不一致（见 §5.2）。
  - 工作台会话与管家同为平台权限体系的资源类型，其授权语义见 PRD-2 对应条目与上游《产品方案》，本条不展开。
- 验收要点：
  1. 两个入口（卡片 ⚙️ →「管理权限」、应用详情页 · 发布的可见范围区）拉起的是**同一个弹窗**，可按用户 / 部门 / 用户组授予。
  2. 授权后被授权用户**下一次请求**即可从应用广场看到并打开该应用；撤销后同样即时失效（RT-01 / RT-02）。
  3. 首发上线后未设可见范围时，应用详情页 · 发布显著提示「仅 owner 可见」并给出设置入口。
  4. 租户管理员可对本租户任一应用查看并调整可见范围；变更计审计且记录变更人（GOV-04）。
  5. 可见范围变更不触发审批，也不进入版本快照（RT-03 / RT-05）。
  6. 托管应用卡片的 ⚙️ 菜单只出现「管理权限」与「删除」两项，「创建模板」「复制」不出现；删除项在已上线态不可用并提示须先下线（RT-07）。

> **卡片 ⚙️ 菜单按类型裁剪**：该菜单现有「管理权限 / 创建模板 / 复制 / 删除」四项，对托管应用——**「管理权限」与「删除」均直接复用**（删除的二次确认强度对标工作流、不要求输入应用名，但受 RT-07 的前置状态闸约束：已上线态入口置灰、须先下线，且仅 owner 可见该项）；「创建模板」「复制」涉及代码与应用数据的拷贝，语义未定，**本版对托管应用不提供**。落地时须按应用类型控制菜单项可见性。

**GOV-02 发布审批场景配置（平台预置流程，开箱即用）**

> **一句话**：审批**开箱即用、不靠先配置**——平台预置一套流程，审批人 = 应用 owner 所属部门的部门管理员 ∪ 租户管理员、**或签**，任一人处理即出终态。

- 需求描述：应用发布作为审批中心的新场景接入，**平台预置一套默认审批流程，部署即生效、无需租户管理员先行配置**；租户管理员可在此基础上改配审批人/审批链。首发与迭代每次发布均走审批（RT-03/04），不提供免审配置项。
- **预置流程规格**（场景 / 分支 / 节点 / 或签四项复用审批中心既有能力；**「新建租户时同步落库」这一挂钩点为新增**，见域末锚点表）：

| 项 | 取值 | 说明 |
|----|------|------|
| 场景 | 「应用发布」，随部署启用 | 管理员无需先建场景 |
| 分支 | 单条无条件分支 | 所有发布一律走审批，不存在直通分支 |
| 节点 | 单节点、**或签** | 任一审批人处理即出终态 |
| 审批人来源 | **① 应用 owner 所属部门的部门管理员 ② 租户管理员**（两个来源并列，同一节点内或签）；**单租户部署下来源 ② 回退为平台超管** | 复用审批中心既有的两种审批人来源，无需新增来源类型 |

> ⚠️ **本条有两项实现前置必须先做完，需求才成立**（技术细节见域末「实现锚点与前置」表）：① 审批中心现有的「租户管理员」审批人来源实际解析的是**系统超级管理员**，多租户下会把所有租户的发布审批压到超管一人；② 单租户部署下租户管理员来源会解析为空，须落实上表的超管回退。

- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 「应用发布」场景配置 | 管理后台-审批中心-场景配置（新增场景行/卡片） | 展示预置流程当前配置；审批人/审批链可改（复用审批中心既有配置交互）。**不出现「未配置审批人」提示**——预置流程保证始终有审批人来源 |

- 规则与边界：
  - 每次发布（首发与迭代）必审，无免审路径与配置项（RT-03/RT-04）。
  - **审批人 = 部门管理员 ∪ 租户管理员，或签**：谁先处理谁定终态。部门管理员承接「谁的人谁负责」的日常治理，租户管理员既是更高一级权限、也是部门侧缺位时的天然兜底——**不需要额外的兜底规则，来源并列本身就是兜底**。
  - **部门取 owner 的主部门，且不向上级部门回溯**：审批人 = 该主部门被显式授予的部门管理员。owner 无部门、或其主部门未设部门管理员时，该来源解析为空，节点仍由租户管理员承接。
  - **两个来源同时解析为空时进审批中心异常态**，通知管理员处理——**不放行、也不静默卡死**，与审批中心既有异常处置一致。
  - 提交人位于审批人候选中时自动跳过该审批人（如 owner 本人正是其部门管理员），落到其余候选；全租户仅一名管理员且无其他候选时允许自审，强制计审计标注。
  - **预置不覆盖人工改动**：按「租户 + 场景」判存在即跳过，租户管理员改过的配置在平台升级后不被重置。
  - **单租户部署下租户管理员来源回退为平台超管**：单租户形态里超管事实上就承担租户管理员职责，回退保证「部署即生效、无需先配置」的承诺在该形态同样成立——否则该来源恒空、owner 又无部门管理员时首次发布即卡死。
  - **每个租户都要有**：预置须覆盖新建租户（租户创建时同步落库），不能只对默认租户 seed——否则新租户的第一次发布会因场景缺失而失败。**这是本条唯一的新增机制**，平台现有 seed 只在启动初始化时对默认租户执行。
- 验收要点：
  1. **全新部署后未做任何审批配置，直接发布应用即可正常生成审批单**（预置流程生效），审批单落到 owner 所属部门的部门管理员与租户管理员。
  2. 部门管理员或租户管理员任一人处理即出终态，另一方的待办同步关闭（或签）。
  3. owner 无部门、或其部门未设部门管理员时，审批单仍落到租户管理员，发布不卡死。
  4. 租户管理员可改配审批人/审批链；改配后平台升级不重置其配置。
  5. **新创建的租户**内首次发布应用即可正常生成审批单（预置已覆盖该租户）。
  6. **单租户部署下**未做任何审批配置即可发布，审批单落到平台超管（租户管理员来源回退生效）。
  7. 提交人在审批人候选中时该节点自动跳过其本人；仅一名管理员的租户自审单在审计中带自审标注。
  8. 两个审批人来源均解析为空时，实例进异常态并通知管理员，**发布不被放行**。

**GOV-03 资源档位**

> **一句话**：资源规格**只能从平台预置档位中选**，不提供自定义——它是运行环境给容器设资源上限的唯一依据；**本版不做租户级配额**。

- 需求描述：平台预置服务器资源档位模板，应用发布时只能从中选档，不提供自定义资源规格。
- 档位（本版三档；规格为初始默认值，部署配置项提供、平台超管可调整；档位数与命名为开放项，见 §6）：

| 档位 | 规格（部署配置项提供初始默认值） | 白话适用说明 |
|------|---------------------------------|-------------|
| 轻量 | 1 核 CPU / 2 GB 内存 | 适合表单、台账类轻量应用 |
| 标准 | 2 核 CPU / 4 GB 内存 | 适合多数日常业务应用 |
| 性能 | 4 核 CPU / 8 GB 内存 | 适合数据处理量大、访问人数较多的应用 |

- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 资源档位管理 | 管理后台-系统管理页新增「资源档位」tab（平台超管；未部署工场运行时层时不出现，GOV-10） | 档位列表：名称、CPU/内存、适用说明、启用状态、使用中应用数；行内编辑规格与说明；停用档位时提示影响（存量应用不动、发布面不再可选） |
| 发布时档位选择 | 应用详情页 · 发布（导航见 §3.0.1）；CLI 路径在应用包中声明（DEV-04） | 从启用中的预置档位选择，每档展示规格与适用说明 |

- 规则与边界：
  - 只能从预置档位模板中选择，不提供自定义资源规格；单应用单实例，不提供实例数 / 并发调节（§5.1）。
  - 默认推荐档 = 轻量档：应用详情页 · 发布默认选中（WB-14），CLI 路径应用包未声明档位时取此档（DEV-04）。
  - 档位停用只拦新选择，存量应用沿用原档位继续运行与迭代；规格调整自应用下一次发布 / 重新上线生效。
  - **档位与运行时形态无关**：compose 形态由 runtime-manager 设容器资源限额，k8s 形态映射为 Pod 的 requests / limits，产品面与验收完全一致（上游《产品方案》§4.8）。
  - **上线仍可能因运行环境容量不足而失败**：上线终检发现 compose 资源耗尽 / k8s 无可调度资源时，审批单保持通过、应用进入「待上线（资源不足）」态（§3.0.2），并提示 owner 与租户管理员（§3.0.3）；资源释放后 owner 在应用详情页 · 发布手动上线，无需重新审批。
  - **应用代码存档与附件本版均不计入平台存储配额**（顺延见 §5.2——平台既有存储配额的统计口径当前只覆盖知识库文件）；token 用量只计量、不设上限。
  - **本版不做租户级实例数配额**，理由与将来补做的注意事项见 §5.2。
- 验收要点：
  1. 资源档位模板由平台预置、平台超管可调整规格与启用状态；发布时只能从预置模板中选择，不存在自定义资源规格与实例数 / 并发调节入口。
  2. 未声明档位的 CLI 应用取默认推荐档（轻量）；发布面默认选中轻量档。
  3. 档位停用后存量应用照常运行与迭代发布，新发布不可再选该档位。
  4. 所选档位在运行环境中实际生效——容器 / Pod 的资源上限与档位规格一致。
  5. 上线终检遇运行环境容量不足时，应用进入待上线态并提示成因；资源释放后 owner 手动上线成功、无需重新审批。

**GOV-04 全链路审计**

> **一句话**：从造应用、接能力、发布运维到密钥事件**全链路留痕**，管理面可查；租户管理员限本租户、平台超管可跨租户。

- 需求描述：应用工场全生命周期动作全链路留痕——从造应用、接能力、发布运维到密钥与 key 事件，审计记录可在管理面查询。
- 审计事件清单（每类记录至少含操作人/时间/对象/动作/结果；「关键记录内容」列仅列该类特有要素）：

| 事件类别 | 来源条目 | 关键记录内容 |
|---------|---------|-------------|
| 造应用（谁造了什么应用） | WB（平台内造）/ DEV-04（CLI 导入） | 创建/导入动作、应用名 |
| 接入知识库/模型等能力 | GOV-05 | 应用、能力声明变更内容 |
| 应用运行期能力调用（检索/模型） | GOV-05 / GOV-08 | 双归属：actor = 应用，subject = 当前访问用户——同时回答「哪个应用调的」与「以谁的名义调的」 |
| 访问记录（谁在用） | RT-01 | 访问用户、应用、访问时间 |
| 生产数据行编辑 | WB-06 | 应用、数据对象、编辑动作 |
| 发布 / 删除动作 | RT-03 / RT-07 | 应用、版本、动作结果（含下线/重新上线） |
| 密钥录入与吊销事件（不含值） | WB-05 | 密钥引用名、动作；不记录密钥值 |
| 模型调用记录 | DEV-01 / GOV-08 | 归属（开发者 key 归其服务账号、应用运行期调用归该应用）、模型、时间、token 数——**逐条留痕，本版不做聚合账单**（§5.2） |
| key 签发/权限位调整/吊销/自动失效 | DEV-01 / GOV-08 | key 掩码、动作、失效原因；应用运行期凭据的自动签发与回收同计审计（无管理入口，GOV-08） |
| 可见范围变更 | GOV-01 | 变更人（owner 或代调整的租户管理员）、应用、变更内容 |
| 元信息修改 | RT-02 | 对象、变更前后内容（应用工场权限点变更走既有角色审计，GOV-07） |

- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| 审计查询面 | 管理后台-审计页（在既有审计页上扩展事件类型；「对象应用」筛选为新增，成本见域末锚点表） | 筛选器：时间范围、操作人、事件类型、对象应用，平台超管视角另有租户筛选；列表列：时间/操作人/对象/动作/结果（超管视角含租户列）；支持导出 |

- 规则与边界：
  - 审计记录不出现密钥明文等敏感值（NFR-2）。
  - 查询权限：租户管理员可查本租户全部事件；跨租户查询仅平台超管——经审计页租户筛选，或经租户管理视图切至目标租户查看（矩阵注）。
  - 开发者侧无自助查询入口，一律走管理面；需要时由租户管理员导出转交（DEV-01）。
  - owner 应用侧审计/访问记录自查本版不提供（§5.2）。
- 验收要点：
  1. 上述每类事件发生后在审计面可查到记录（操作人/时间/对象/动作）。
  2. 审计记录中不出现密钥明文等敏感值。
  3. 模型调用可按 key / 按应用追溯到具体调用记录（含模型与 token 数）。
  4. 租户管理员查询不到其他租户的审计事件；平台超管可跨租户查询。

**GOV-05 能力总线配置（管理员）**

> **一句话**：能力总线的核心承诺是「**配置一次、声明使用、零新建配置面**」——底层账号与端点只在管理面配一次，应用经能力声明获得使用权，业务人员与 AI 都不碰底层。

- 需求描述：能力总线 = 应用消费平台能力的统一通道，核心承诺「配置一次、声明使用、零新建配置面」：底层账号与端点只在管理面配置一次，应用经能力声明获得使用权（发布审批即授权，RT-03/04），业务人员与 AI 均不接触底层账号与端点。本版总线范围 = 模型、知识库、密钥引用三项，配置动作全部复用既有界面、不新建配置页：
- 界面与交互：

| 能力项 | 谁在哪配置 | 应用如何获得使用权 |
|--------|-----------|-------------------|
| 模型 | 租户管理员在既有模型管理页配置服务商凭据并启用模型——按租户配置一次，租户内助手 / 工作流与托管应用共享同一份，无需为工场重复配置 | 应用在能力声明中写模型名（即模型管理页原名，无逻辑档位转换，DEV-03），审批通过后由平台在运行时注入调用通道 |
| 知识库 | 无新增配置动作：建库与授权走既有知识库管理与权限体系 | 应用在能力声明中声明接入的知识库，审批通过 = 应用侧授权；运行时应用内检索可及范围 = 能力声明知识库（显式白名单收窄）∩ 当前访问用户可见范围（逐资源鉴权、含文件级权限，NFR-1）——两层缺一不可，检索范围规则详见「规则与边界」 |
| 密钥引用 | owner 在工作台密钥子页录入应用自有第三方凭证（PRD-2 WB-05） | 引用名进入能力声明（RT-04），运行时按引用注入值，密钥值零暴露（NFR-2）。造应用引擎自身的模型凭据另见凭据档案（PRD-2 GOV-06），与应用能力声明无关 |

- 规则与边界：
  - 「集成管理」只在管理面，不进工作台；工作台（造应用侧）无任何底层账号/端点配置入口。
  - 能力收回后行为：已上线应用声明使用的能力被收回（模型下线、知识库删除或权限收回）时，应用对该能力的调用得到明确错误态、不回退旧值、应用整体保持可用；owner 在发布面/资源面可见失效提示（与 WB-05 密钥吊销同语义）。

  **知识库检索范围（两层过滤，与《3.0 开放 API 鉴权与身份传递 PRD》同一口径）**

    - 两层过滤 = 声明层 + 用户层：声明层是显式白名单收窄——未声明的知识库对应用整体不可及，即使当前访问用户本人有权限；用户层是按当前访问用户身份的逐资源鉴权（纯替换语义——声明范围内，结果与该用户在平台内自行检索完全一致，不多给也不少给）。
    - 口径澄清：声明层是对显式白名单的收窄，不涉及对两个主体可见集求交，与《开放 API 鉴权与身份传递 PRD》§7.2（决策 D2）否决的「权限取交集」不是一回事——该 PRD 的同构机制即「资源白名单 + 纯替换」，两文档口径一致。
    - 信任机制分界：应用运行时的「当前访问用户」身份以平台登录态为信任根（app-proxy 验真实会话后注入，另有声明层白名单收窄兜底），与该 PRD 模式 D 的委托头（服务账号密钥 + 五道准入）是两套机制；实现不得把应用内的用户身份传递挂在模式 D 委托头上——该 PRD 检查 3（26007）禁止以超级管理员/租户管理员为委托目标，复用其管道会把管理员挡在所有应用之外（上游《产品方案》§4.5 同口径）。**本地开发三面同样不承载委托**（DEV-02 ④）——运行期与开发期两头都不走模式 D，全册无该场景。
    - 过滤强度：文件级，与平台工作台检索同一条双层过滤路径（索引层预过滤 + 结果层批量校验兜底，同 DEV-02 口径）。
    - fail-closed（NFR-1.4）：无法取得当前访问用户身份 → 检索拒绝，绝不回退为按应用声明全量放行；权限评估失败 → 明确错误态，绝不返回未过滤或部分过滤的结果集。
- 验收要点：
  1. 租户管理员在管理面完成一次能力配置后，域内应用无需再配即可声明使用。
  2. 工作台（造应用侧）不存在任何底层账号/端点配置入口。
  3. 生产实例实际可用能力 = 其声明且经审批的能力集合，未声明能力不可调用；草稿/预览期按「已声明 + owner 本人权限」放行（未发布可完整试用，WB-04）。
  4. 收回某已上线应用声明的能力后，该能力调用返回明确错误态、应用其余功能可用，owner 可见失效提示。
  5. 用户本人有权限、但应用能力声明未包含的知识库，经该应用不可检索（声明层白名单生效）。
  6. 应用已声明、但当前访问用户无权限的知识库内容（含库内无权文件）不出现在该用户的检索结果中；声明范围内的检索结果与该用户在平台内自行检索的结果集合相等。
  7. 人为使权限引擎不可用，应用内检索得到明确错误态，而非未过滤或部分过滤的结果（NFR-1.4）。

*（GOV-06 引擎与凭据档案配置：造应用引擎专属条目，见 PRD-2 §3.3。）*

**GOV-07 应用工场权限控制**

> **一句话**：租户内**零新增配置项**——界面通道沿用既有「创建应用」权限点，CLI 通道由密钥的 `app:manage` 位把关，两条通道互不校验。

- 需求描述：谁能造托管应用，由两条通道各自的准入闸决定；本册不新增任何一级菜单，也不新增任何权限点，全部沿用平台既有角色权限体系。

| 通道 | 准入闸 | 谁把关 |
|------|--------|--------|
| 界面（构建 → 应用 → 新建入口） | **既有**「创建应用」权限点（「构建」菜单的子项） | 租户管理员配角色 |
| CLI（`bisheng deploy` 首发） | 服务账号密钥上的 `app:manage` 位（DEV-01） | 租户管理员签发密钥时勾选 |

- 界面与交互（**三个承载面各自寄居既有页面**，可见性沿用既有菜单权限，升级前后角色配置面的项数不变）：

| 承载面 | 位置 | 可见性由谁控 |
|--------|------|-------------|
| 构建面（造与管自己的应用） | platform 构建 → 应用（既有卡片流页，类型筛选新增「托管应用」，§2.2） | 既有「构建」菜单权限；新建入口另受其子项「创建应用」控制 |
| 治理面（管全租户的应用） | **同一个页面**——租户管理员对本租户全部应用天然可见，不另建列表 | 既有「构建」菜单权限 ＋ 租户管理员身份 |
| 使用面（用同事的应用） | 既有应用广场 / `/apps/{slug}`（RT-01 / RT-02） | 既有应用广场可见性 ＋ 应用可见范围（GOV-01） |

- 规则与边界：

  **① 界面通道**
  - 「创建应用」只控新建入口，不影响既有应用的运行、访问、迭代发布与 owner 管理入口；它与「构建」是既有的父子权限点，关闭父项时级联失效。有构建菜单、无创建权限 = 可管理存量、不可新建——这套组合对工作流 / 助手早已生效，托管应用只是第三种被它管住的类型。
  - 默认值沿用既有、本册不改：平台新建角色默认开「构建」、不开「创建应用」，因此升级后没有任何角色凭空获得新建能力。
  - **复用既有权限点意味着无法单独灰度托管应用**（勾了就三种类型都能建），判为可接受——理由见 §5.2。

  **② CLI 通道**
  - 界面侧的权限点与菜单**均不参与 CLI / API 判定**：CLI 的请求主体是服务账号，它没有角色；若改判资源归属人的角色权限，既与鉴权 PRD「归属人只承接归属、不出借权限」冲突，也会造成「归属人一停用其名下密钥立刻失效」的生命周期联动（该 PRD 否决个人访问令牌的理由之一）。
  - CLI 通道不因此失控：密钥只能由租户管理员签发、无自助入口，没有密钥的人根本连不上；deploy 出的应用 owner 恒为该密钥的资源归属人，责任与审计始终落在自然人头上（DEV-04 / GOV-04）。

  **③ 灰度放量**
  - 放量是运营动作，两条通道分别放：界面侧按角色勾「创建应用」，CLI 侧按人签发带 `app:manage` 的密钥。两侧均不另设独立开关。

- 验收要点：
  1. 无「创建应用」权限的用户在构建页看不到新建入口；其既有应用的运行、访问、迭代发布与应用详情页管理入口不受影响。
  2. 密钥未勾 `app:manage` 位时 CLI 首发 deploy 被拒并有明确提示；勾了即可 deploy，**与其资源归属人有无「创建应用」角色权限无关**。
  3. 资源归属人的角色权限被调整、或其账号被停用后，该服务账号名下既有密钥的 deploy 行为不变（验证两条通道互不校验）。
  4. **本册在角色权限体系上零新增**——升级前后角色配置面的菜单项与权限点数量完全一致；三个承载面分别在既有构建页与既有应用广场内呈现。

**GOV-08 开放 API 鉴权改造与密钥产品承诺**

> **一句话**：本条只管两件用户能感知的事——**v2 开放 API 从「内网可信」改为 key 鉴权**（有存量影响、有迁移动作、无兼容窗口），以及**密钥的四条产品承诺**（零暴露 / 只见掩码 / 可吊销 / 全事件计审计）；细化需求与验收以《开放 API 鉴权与身份传递 PRD》为准。

- 需求描述：既有 v2 开放 API 从「内网可信」模型改为 key 鉴权，签发/吊销归管理面（表单与流程见 DEV-01）；**全平台只有服务账号一类密钥主体，无自然人个人凭据**（决议见 F049 spec §4 决议-4）。本条为总纲：v2 开放 API 鉴权改造的细化需求与验收以同目录《3.0 开放 API 鉴权与身份传递 PRD》为准，两处互链。

> **应用运行期凭据不作产品概念、不设管理入口**——对 owner 与使用者全程零感知，其承诺已分落 GOV-05（能力生效与收回）、RT-07（下线冻结）、GOV-04（审计）与本条验收 5；理由见 §5.2。

- **统一凭据底座与四条产品承诺**（底座实现细化以该 PRD R1 为准；全平台各类密钥同底座）：

| 承诺 | 口径 |
|------|------|
| **零暴露** | 明文仅签发时一次性展示，此后一切界面只见掩码（掩码口径 = 前缀 + 末四位）；服务端仅存单向哈希（SHA-256），不用可逆加密、明文不可还原 |
| **可吊销且立刻生效** | 吊销为软撤销、记录保留供审计追溯；撤销主动清缓存，**生效上界 5 秒**；支持按服务账号一键吊销名下全部 key（泄漏应急） |
| **可被扫描拦截** | 主体轨全平台唯一 = 服务账号轨（前缀 `bs-sak-`；原规划的个人主体轨 `bs-pat-` 已废除），前缀模式内置于发布前密钥扫描规则集（RT-03 / DEV-04），并可注册到代码托管平台的密钥扫描规则 |
| **全事件留痕** | 签发 / 吊销 / 自动失效均计审计（GOV-04） |

  另：密码学合格随机源生成、校验恒时比较 + fail-closed，属实现要求，细化以该 PRD R1 为准。

- 流程（v2 开放 API 鉴权改造，存量升级口径同该 PRD §4.9 / 决策 D1）：
  - **①** **发布即带鉴权，不设兼容开关、不设兼容窗口**——任何「默认关闭」的过渡开关都意味着升级后匿名越权通道依然敞着，已被该 PRD 决策 D1 明确否决。升级后所有 `/api/v2` 调用必须携带密钥，无密钥一律 401、无回落路径；裸 `user_id` 参数随本版一并移除，不保留过渡期。
  - **②** 迁移动作前置到**升级前**完成，发布说明须以显著位置给出三步指引：为每个存量调用方创建服务账号（不可登录的一等主体）、按最小权限授权；签发**服务账号密钥**（平台不存在自然人个人 key，生产集成不因员工离职而中断）；改造调用方代码加 `Authorization` 头（原裸 `user_id` 参数改传 `X-Bisheng-On-Behalf-Of` 头）。签发者 = 租户管理员，迁移责任人 = 各调用方 owner。
  - **③** **平台侧不做任何自动迁移**（该 PRD §4.9 决议）：不写转型脚本、不改动任何存量用户与资源；原 `default_operator` 配置项随本次废弃移除，它指向的那个用户保持普通用户身份不变、名下资源零变化。升级到管理员配好密钥之间存在接入空窗，须在升级沟通中说明。
- 界面与交互：

| 界面/入口 | 位置 | 构成 |
|-----------|------|------|
| API key 管理页 | 管理后台-API key 管理（服务账号模块恒在；未部署开放能力层时仅「本地开发工具包」三扩展位与接入信息区不出现，GOV-10） | 平台密钥与服务账号管理的**单一入口**（开发者能力就是同一张权限位清单上的新增位，不另立入口——本页即《3.0 开放 API 鉴权与身份传递 PRD》§4.7「服务账号」模块的承载页，菜单最终命名评审时定）。构成：**服务账号模块（主体）**：列表 + 详情页（概览 / API 密钥 / 资源授权），构成与验收以该 PRD R4 / R6（§4.5 服务账号主体、§4.7 管理界面）为准，本册在其上的增量仅两处——签发表单权限位新增「本地开发工具包」三位、详情页新增接入信息区（资源归属人已升格为该 PRD §4.5 定义 6 正文，非本册增量）（DEV-01）；**应用运行期凭据不设管理界面**——由平台随发布自动签发与回收，owner 与使用者全程无感；其签发 / 回收事件经审计可查（GOV-04），应急处置走下线（RT-07） |

- 规则与边界：
  - **应用运行期能力的生效与收回，产品面一律以「能力」表述、不以凭据表述**：发布审批通过即按新能力声明生效、旧声明即刻失效（GOV-05 / RT-04）；下线冻结、删除回收（RT-07）。底层凭据的重签与吊销随之自动发生，不单独暴露操作入口。
  - **应急处置统一为下线**（RT-07）：疑似凭据泄漏、应用滥用平台能力，一律下线该应用；**不提供「保留应用可访问、但能力调用失败」的中间态**（取消理由见 §5.2）。
  - 开发者 key 与开放 API 集成密钥同底座同主体轨（都是服务账号密钥）；同一把 key 是否同时通行 MCP/模型/CLI 与开放 API，由同一张权限位清单上勾了哪些位控制，不再是凭据类型问题（原 §6 开放问题 3 已关闭；开发者面能力即该清单的新增三位，无独立「scope」维度，DEV-01）。
  - key 值零暴露口径同 NFR-2（DEV-01）。
- 验收要点：
  1. 开发者 key 可在管理面签发与吊销；明文仅签发时展示一次，此后所有界面只见掩码。
  2. 吊销后调用在 5 秒内被拒；按服务账号一键吊销可使其名下全部 key 同时失效。
  3. 密钥的签发 / 吊销 / 自动失效事件均计审计（GOV-04）。
  4. 存量环境升级后，未带 key 的 v2 调用一律 401、无任何回落路径（不存在兼容开关或兼容窗口；细化验收以该 PRD AC-1 / R9 为准）。
  5. **owner 自然人账号被禁用后，其应用照常运行**，可见范围内用户正常使用（开发者 key 亦锚定服务账号、不随自然人账号禁用联动，回收需管理员操作其服务账号，DEV-01）。
  6. 迭代发布上线后，应用运行期获得的能力即为新能力声明所列，旧声明中已移除的能力即刻不可用（GOV-05 / RT-04）。
  7. 管理面**不存在**应用运行期凭据的查看或吊销入口；应用的应急处置只有下线一条路（RT-07）。
  8. 存量 v2 调用方迁移时签发的是服务账号密钥（绑定不可登录的服务账号）。

**GOV-10 可选部署与交付形态**

> **一句话**：不需要工场的客户可**整层不装**、平台其余功能行为零变化；装则按客户环境选 compose 单机或 k8s 集群，两形态产品面完全一致。

- 需求描述：应用工场按层可选部署，不装的环境无新增常驻负担、既有功能行为零变化；已装环境按客户基础设施二选一种运行时形态，产品行为与验收不因形态而异。
- 界面与交互：**无新增配置界面**——部署形态由部署期决定，产品面的唯一可感知差异是「未部署」时相关入口与页面不出现（下表末列）。
- 三层部署形态（层内技术构成见上游《产品方案》§4，本表只写行为差异）：

| 层 | 用户可感知能力 | 可否独立部署 |
|----|---------------|-------------|
| 平台核心 | 平台既有全部功能 | 基座，必装 |
| 开放能力层 | 开发者 API key（服务账号密钥）、模型 OpenAI 兼容接入、MCP 工具面 | 可独立于工场运行时层部署（不装工场也可用） |
| 工场运行时层 | 应用托管运行、应用广场、发布管线 | 可整层不装；装则二选一——**compose 单机**（默认）或 **k8s 集群**，两形态产品行为一致 |

- 规则与边界：
  - 未部署工场运行时层：构建页不出现「托管应用」类型、应用广场不出现托管应用；访问应用路径呈统一引导页（RT-01）而非报错；平台其余功能行为零变化、无新增常驻负担。
  - 未部署开放能力层：服务账号与密钥模块本身随《开放 API 鉴权与身份传递 PRD》交付、**恒在**（v2 开放 API 发布即带鉴权，服务账号密钥是其唯一接入方式，不能被部署开关隐藏）；不出现的只是应用工场增量——签发表单的「本地开发工具包」三扩展位、详情页接入信息区，以及模型 OpenAI 兼容接入与 MCP 工具面（DEV-01 ⑥ / GOV-08）。
  - 开放能力层可独立部署：不装工场也可用开发者 API key / 模型 OpenAI 兼容接入 / MCP（DEV-01 / DEV-02）。
  - 两种运行时形态的产品面一致性是硬要求：凡本册验收项，compose 与 k8s 下表现必须相同（资源档位的落地差异见 GOV-03）。
- 验收要点：
  1. 未部署工场运行时层的环境中，平台既有功能回归测试全部通过、行为无变化。
  2. 未部署工场时访问应用路径得到统一引导页而非报错。
  3. 仅部署开放能力层时，开发者 API key、模型协议接入、MCP 工具面可正常使用。
  4. 未部署开放能力层的环境中，服务账号模块照常可用；签发表单不出现「本地开发工具包」三扩展位、详情页不出现接入信息区；模型 OpenAI 兼容接入与 MCP 工具面不可达。
  5. 两种运行时形态（compose / k8s）下，本册全部验收项表现一致。

## 4. 非功能需求

仅列产品可感知项，均为跨域不变量，具体行为落在所回链条目中：

- **NFR-1 权限与数据边界不变量**
  1. 应用（及其内 AI）可访问的知识库范围 ⊆ 当前调用主体自身权限（线上 = 当前访问用户，含文件级权限，RT-01；本地 dev 与 MCP = 开发者服务账号被显式授予范围，DEV-02 / DEV-05；审批人预览例外见 NFR-1.2）；托管运行期进一步收窄为 = 能力声明知识库 ∩ 当前访问用户可见范围（GOV-05）。
  2. 草稿全程 owner-only；唯一例外是审批期间审批人经审读视图与预览试用（含按 owner 权限放行的平台能力调用，属审批例外、计审计，RT-03；工作台侧回链 WB-16），此外无任何旁路。
  3. 应用获得的身份信息唯一可信来源是平台注入，客户端伪造的身份信息一律无效（RT-01 / DEV-05）。
  4. 权限评估 fail-closed：无法确立调用者/访问用户身份即拒绝，绝不回退为放行；权限评估失败即报错，绝不返回未过滤或部分过滤的结果集（GOV-05 / DEV-02）。
- **NFR-2 密钥零暴露**：密钥值不经对话、不写日志、不回显、不进代码；一切界面只见引用名与掩码；平台自签发 key 服务端仅存单向哈希、明文不可还原、仅签发时展示一次（GOV-08 凭据底座）；发布产物不得含裸密钥/连接串——发布前扫描门，规则集内置平台自签发 key 前缀模式（RT-03 / DEV-04 / WB-05 / GOV-04）。
- **NFR-3 资产持久承诺**：运行实例可任意回收；代码/对话/应用数据真身恒在平台存储，删除唯经显式删除流程（RT-07 / GJ-01）。
- **NFR-4 可选部署承诺**：不部署工场运行时层的环境，平台既有功能零新增常驻负担、行为零变化（GOV-10）。
- **NFR-5 审计可追溯**：造 / 接 / 发布 / 删除 / 生产数据编辑 / 密钥事件全链路留痕（GOV-04）。

## 5. 范围外与顺延

### 5.1 本版明确不做

| 项 | 说明 |
|----|------|
| 本地身份模拟开关（`bisheng dev --as`） | 不做（DEV-05）——那是绕过平台准入的后门。**平台整体支持代表他人执行**，但那条路是 V2 开放 API 面的模式 D 委托，**不在本地开发三面**（持 `delegate` 的 key 在三面一律被拒，DEV-02 ④）；本地验 per-user 差异的路径 = 发布后用真实账号访问。工作台预览的模拟视角见 PRD-2 §5.1 |
| 公网域名 / 公开可见性 / SEO / 水印 | 内网入口 + 权限体系，无「公开」开关 |
| 自定义资源规格 / 实例数与并发调节 / 自动扩缩容 / GPU / 应用间编排 / 自定义运行环境构建 | 单应用单实例；发布时从平台预置资源模板选档，不提供档位之外的规格自定义（GOV-03 / WB-14） |
| token 用量限制 | 不做（私有化环境自有模型与算力；精细成本控制顺延见 §5.2） |
| 形态间迁移（compose ⇄ k8s）与同环境双形态并存 | 运行时形态在部署期一次性选定；**k8s 本身已在本版支持**（见上游《产品方案》§4.5 / §4.8） |
| 本地端专有插件 | 不做；四面供给全走标准协议，任何本地引擎零改造接入（§3.1） |
| 已定顺延 v3.1 的项 | 只在 §5.2 维护（精细成本控制、调用既有工作流/助手、第三方 MCP 网关等），本表不重复 |

### 5.2 v3.1 顺延清单

**本轮 MVP 收敛砍掉的（2026-08-16）**——目标是先跑通最小闭环「拿 key → 本地开发 → deploy → 审批 → 上线 → 设可见范围 → 同事使用」，不在这条链上的一律顺延。每条附上砍掉的理由与将来补做时的注意事项，避免重新论证：

| 顺延项 | 砍掉的理由 | 将来补做时须注意 |
|---|---|---|
| **租户级实例数配额**（原 GOV-03） | 防不住它声称要防的——护住机器的是运行环境侧准入控制；实例数只数个数不看档位（三档资源差 4 倍）；单租户部署完全用不上 | **须以资源量（CPU / 内存）为单位而非实例数**，否则限不住实际占用 |
| **改码权归属与交接**（原 DEV-06） | 本册单独交付期恒为「在本地」——PRD-2 管家未上线，交接无处可去，整条是空的 | 随 PRD-2 管家一并做；届时 RT-03 预览试用增加「复用 owner 草稿沙箱」这条承载 |
| **平台侧回滚**（原属 RT-05） | 本册主用户本地有完整 git，等价手段是 checkout 旧版重新 `deploy`、走同一条审批 | 版本快照的四要素（代码 / 能力声明 / 注入配置 / 资源档位）**本版已按同一快照存储**，补做时直接统一回退即可；应急止血始终是下线 |
| **迭代审批单的变更摘要**（原属 RT-04） | 首发闭环用不到；审批人可经审读视图的文件差异自行比对 | 补做时覆盖四类：能力声明 / 可见范围 / 表结构 / 资源档位变更 |
| **应用标签设置**（原属 RT-02） | 未设标签的应用在广场默认分类中正常可见，不影响闭环 | 复用广场既有标签体系，不新建 |
| **按 key / 按应用的聚合用量账单**（原属 GOV-04） | 平台唯一的持久化用量表没有 app / key 维度（app 维度只活在遥测事件里），出账单属新建而非扩展；本版以逐条调用审计替代，管理员仍可追溯谁在用 | 须给用量表加 `app_id` / `api_key_id` 列并打通调用链上下文，而不是从遥测侧反查 |
| **应用代码存档计入存储配额**（原属 GOV-03） | 平台既有存储配额的统计口径写死为只覆盖知识库文件，纳入代码存档属新建；且代码存档体量远小于知识库文件，不构成本版风险 | 须把统计口径改为多源，注意各表的租户列名差异（现模板是单列占位符） |

**本版明确取消的（与顺延不同——这些不会再做）：**

| 取消项 | 为什么不做 |
|--------|-----------|
| **管理后台应用列表**（原 GOV-09） | 它声称的四件事没有一件是新需求——列出租户内全部应用是平台既有行为（租户管理员对本租户资源天然可见），授权归 GOV-01、下线归 RT-07、审计归 GOV-04 |
| **草稿对管理员不可见**（原属 GOV-09） | 是对既有行为的收窄——租户管理员本就能看到他人未发布的工作流与助手草稿，给托管应用单独加限制会造出类型特例 |
| **租户管理员代 owner 调整可见范围** | 不是待做功能而是既有行为；要让它「不能改」反而需要额外加拦截 |
| **应用运行期凭据的产品概念**（原 GOV-08 应用 token / 会话 key） | 对 owner 与使用者零感知，产品可感知面为零，属设计文档范畴——实现照做，PRD 不定义 |
| **应用运行期凭据的强制吊销入口**（原属 GOV-08） | 「保留应用可访问、但能力调用失败」对使用者就是「应用坏了」；应急处置统一为下线（RT-07） |
| **复用「创建应用」权限点的代价：无法单独灰度托管应用** | 勾了该权限的角色三种类型都能建。为「只放开工作流、不放开托管应用」这一种组合新增权限点，收益不抵角色配置面上多一行的永久复杂度——真正的灰度闸是部署开关（环境级）与按人签发密钥（人级） |

**其余顺延项：**


- 精细成本控制：token 按人记账与成本可视、会话级单轮/单会话预算、预算触顶「走完当前回合再拦截 → 转管理员」处置流程（本版不做任何配额，GOV-03 只保留资源档位选择）。
- 存量代码执行点（workflow CodeNode / gpts local executor）迁入沙箱设施。
- 应用退役与归属转移（owner 离职接管、长期无人维护自动归档下线）。
- 开发者服务账号与资源归属人的离职联动（归属人账号禁用/删除时提示或自动回收其服务账号；本版为管理员手动回收，DEV-01）。
- 敏感字段分类分级与受控导出/脱敏（等保 2.0 / 数据安全法）。
- 能力总线暴露「调用既有工作流/助手」作为应用能力。
- 第三方 MCP server 接入网关化；多机调度。
- 审批单超时提醒、催办与升级机制（本版应急路径 = 下线即时止血，RT-07）。
- owner 应用侧审计与访问记录自查视图（本版审计查询仅管理面，GOV-04）。
- 开发者 API key 调用频率限流（防滥用；本版 key 用量只计量、不设上限，DEV-01）。
- 既有 iframe 嵌入安全升级（原 RT-09）：postMessage 通信协议规范化 + 嵌入域名白名单（白名单外拒绝嵌入通信，修社区 #1705）。平台既有能力的独立安全修复、与工场无功能依赖，可随任意平台版本交付。
